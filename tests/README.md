# Rust 测试目录约束

这份目录不是为了把测试切碎，而是为了让 Rust 的 TDD 更顺手，让每个失败测试都能直接指向一个明确能力域。

## 当前分层

- `领域测试.rs`
  只守领域不变量、值对象、事件语义和错误语义。
- `用例测试.rs`
  只守 application/usecase 编排，不把 HTTP、socket、数据库外壳细节混进来。
- `启动与迁移测试.rs`
  只守配置失败、迁移结构、共享契约占位、优雅停机。
- `消息主链测试.rs`
  只守消息成立顺序、附件引用落库、ready/prepared 附件进入消息主链的边界。
- `媒体上传测试.rs`
  只守 `prepare / complete / tus hook / 公网地址推导`。
- `房间接口测试.rs`
  只守 `bootstrap / events / snapshot / history / 阅读推进`。
- `协作分发测试.rs`
  只守 `locator / torrent / presence / web seed 可用性裁决`。
- `实时链路测试.rs`
  只守 realtime 主链、控制面 kind、幂等重试、并发顺序。
- `后台与静态壳测试.rs`
  只守后台 contract、HTTP 冷路径、静态壳缓存与 service worker 暴露。

## 目录约定

- 热点能力允许使用“顶层入口 + 同名目录子模块”。
  例：`房间接口测试.rs` + `房间接口测试/快照.rs`
- `测试支撑/` 只放通用支撑。
  允许：构造请求、读取响应、环境管理、日志采集、fixture 准备、通用断言壳。
  禁止：业务成立裁决、谁该成功/失败、把多个业务步骤封成万能场景器。
- 每个顶层 `xxx测试.rs` 都必须在文件头写清楚“负责什么 / 不负责什么”。
  这是防止能力边界回流的第一道软约束。

## 新增测试怎么放

- 先判断它属于 `domain / application / integration` 哪一层，再落文件。
- 新增 integration test 时，优先追加到已有的同能力文件或子模块。
- 只有当测试覆盖的是一个新的、稳定的能力域时，才新增一个新的 `xxx测试.rs`。
- 不允许重新引入总入口式的 `集成测试.rs`。
- 如果一个文件开始同时承载两类以上无关能力，应先拆边界，再继续追加测试。

## Review 检查点

- 这个测试失败时，维护者能不能立刻知道它属于哪个能力域。
- 这个 helper 是否只是在支撑测试，而不是偷偷决定业务真相。
- 这个新测试是否把某个壳层、协议层、运输态特例倒灌进了领域或用例真相。
- 这个文件的新增内容是否仍然符合它文件头声明的“负责 / 不负责”。

## 反模式

- 把不同能力域继续堆回一个超大测试入口。
- 在 `测试支撑/` 里写业务规则或高语义场景编排。
- 为了省几行重复，把消息、分发、realtime、房间接口混成一个大测试。
- 在测试里顺手修改 `src/` 业务语义，却没有单独立项和单独验证。

## 维护原则

- 测试目录服务于 DDD 分层，也服务于 Unix 式“小而专、可组合”。
- 测试重组优先保持业务语义不变；如果拆测试需要改生产代码，说明边界判断还没做清楚。
- 每次结构重组后，都要跑能直接证明边界未漂移的 targeted tests，再跑全量 `cargo test`。

## 真DDD重构期间额外约束

- 先收 owner，再做目录落位；禁止把“目录更像 DDD”误当成“业务 owner 已经收口”。
- 新测试优先锁住三件事：旧总文件是否变薄、owner 是否不再回流、边界是否仍只在 canonical owner 决定。
- Rust 侧新增架构测试时，优先用边界守卫锁 `domain / application` 不得倒灌 `axum / sqlx / socketioxide` 等外层实现。
- 前端侧新增架构测试时，优先锁 `聊天应用内核.ts`、`聊天壳.ts`、`聊天媒体编排.ts` 不得重新长回平台全局访问和跨模块业务总控。
- `tests/架构边界守卫.rs` 现在还负责兜住“完成矩阵是否提前宣称完成”和“根目录业务文件是否逐个登记到矩阵”。
- 前端对应的根目录迁移门禁入口是 `scripts/check-frontend-architecture-fitness.mjs`；测试如果因为 owner 迁移而失败，优先把 import 和源码断言改向新 owner，而不是强行让旧根文件继续承载真实实现。
- 不允许为了重构临时跳过 targeted tests；如果某个 targeted test 已经写不出来，先停下补清 owner 和边界，再继续改代码。
- 如果拆分生产代码后测试结构仍在默默要求旧总控存在，应同步拆测试，禁止只拆生产代码不拆测试 owner。
- 不允许把“已有门面、新目录、新模块名”包装成“真DDD已经完成”；完成声明必须以完成矩阵、架构守卫、真实烟测和最终验收证据为准。
