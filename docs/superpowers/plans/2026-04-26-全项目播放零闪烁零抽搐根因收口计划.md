# 全项目播放零闪烁零抽搐根因收口 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 从代码逻辑根因上消灭群聊消息流里任何自动播切换时的闪烁、抽搐、可见空窗与可见换源，让消息流/查看器/全屏全链路都只表现为同一条连续播放会话。

**Architecture:** 这轮不再做表面补丁，而是同时收口两层真因。第一层是真实 owner 裁决存在 `0.6` 死区，高竖视频在滚动交接时会天然出现“所有候选都低于阈值”的窗口，runtime 因而把 owner 清空；第二层是真正 owner 切换时，canonical player 不能在用户可见表面上现场 `loadstart / seeking / canplay / playing`。修复必须拆成“连续性 owner 裁决”与“hidden stage 揭帘接管”两条窄链，一条解决 `owner = null`，另一条解决“可见换源”。

**Tech Stack:** TypeScript, Lit, XState actor runtime, Video.js v10 shell, Vitest, Happy DOM, Playwright/Chrome DevTools 冒烟

---

## 0. 先把这轮真因写死

这轮要修的不是泛泛的“看起来闪一下”，而是下面两条已经被真实烟测证明的逻辑链：

1. **owner dead zone**
   - 当前候选用 `visibleHeight / rect.height` 算可见比例。
   - 当前最小进入阈值写死为 `0.6`。
   - 对高度约 `569px`、视口约 `567px` 的竖视频，滚动交接区会天然出现“两边都低于 0.6”的窗口。
   - runtime 在这个窗口里把 owner 清成 `null`，消息窗随即撤掉 canonical host。

2. **可见表面换源**
   - 目标卡片在成为 owner 之前，往往已经有一张恢复到正确时间点的暂停预览 `<video>`。
   - 当前实现却会先删掉这张可见预览帧，再把唯一 canonical player 挂到可见卡片上现场 `同步(source) + 恢复位置 + play()`。
   - 用户看到的就是 `waiting / loadstart / loadedmetadata / seeking / seeked / canplay / playing` 整条链。

这份 plan 的唯一目标，就是把这两条链一起掐断。只修其中一条，都不算完成。

要求：

1. 编排层只负责“给出当前这帧该选谁”
2. runtime 层负责“old owner / pending owner / release”的状态机语义
3. 禁止把 UI 表面、host 状态、playback source 混进裁决函数

- [ ] **Step 2: 在编排层新增 continuity 候选集合，而不是只认 `0.6` 一条阈值**

实现要求：

1. 保留现有 `默认自动播可见阈值 = 0.6` 作为进入阈值
2. 新增一条更低的“连续性阈值”，只服务 dead zone 交接

5. continuity 候选不能包含 `visibilityRatio = 0` 的预热条目

- [ ] **Step 3: runtime 在死区里继续保留连续 owner，而不是清空 owner**

实现要求：

1. 如果进入候选存在，行为沿用现在的 settled/pending 逻辑
2. 如果进入候选为空，但 continuity 候选存在：
   - 禁止返回 `null`
   - 保持旧 owner 有效，或平滑挂起新的 pending
   - `inlineAutoplayPlayback` 不得被清空
3. 只有连续空观测达到阈值，或当前 owner / continuity 候选都彻底消失，才允许真正 release
