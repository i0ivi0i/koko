# 浏览器端应用平台化·平台地基与协议 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 先把浏览器端的正式分层和协议面立起来，让后续聊天内核、后台内核、通知、多标签、离线这些能力都不再往 `聊天壳.ts` 和 `后台壳.ts` 里继续堆。

**Architecture:** 这一计划不急着重做业务真相，先做最关键的地基：`BrowserAppPlatform`、平台协议、壳层桥接、应用门面。它的作用不是新增一层包装，而是把“浏览器事件 -> 平台/应用命令 -> 快照渲染”这条正路先钉死，并明确旧入口退场点。这样后面拆 owner、接通知、做多标签时，才不会又回到大壳 patch 总线。

**Tech Stack:** TypeScript、Lit、Vitest、现有 `frontend/应用运行时.ts`、现有 `frontend/传输.ts`、现有 `frontend/存储.ts`。

---

## 为什么先做这一份

这一步是整个终局蓝图的施工地基。

如果直接去拆聊天 owner 或直接上多标签 / badge / SW 生命周期，而平台协议和壳层退场边界还没立住，结果只会是：

- 新 runtime 长出来了，旧壳入口还在；
- 新内核长出来了，旧 `chatState / updateChat()` 还是照样被四处摸；
- 通知、离线、SW 继续散落在入口和壳层上；
- 最后不是“平台化”，而是“多了一堆新名字的大壳”。

所以这一份计划只做一件事：**先让浏览器端有正式的层次、正式的协议、正式的入口。**

## 依赖与完成后边界

前置依赖：

- 已批准 spec：`docs/superpowers/specs/2026-04-12-浏览器端应用平台化-design.md`
- 现状组合根：`frontend/聊天壳.ts`、`frontend/后台壳.ts`、`frontend/应用运行时.ts`、`frontend/入口.ts`

这一份完成后，系统必须满足：

1. 浏览器端存在正式的 `BrowserAppPlatform` 入口。
2. 平台和业务之间只通过 `command / event / snapshot` 通信。
3. `聊天壳.ts`、`后台壳.ts` 不再直接持有 transport / storage / entry 级别的横切职责。
4. 后续聊天内核和后台内核可以挂到同一平台层上，不需要再从入口文件里零散接线。

## 文件结构锁定

### 新增文件

- `frontend/平台/平台契约.ts`
  - 平台层与应用层共享的命令、事件、快照类型。
- `frontend/平台/浏览器应用平台.ts`
  - `BrowserAppPlatform` 组合根；只组合 runtime，不写聊天业务规则。
- `frontend/平台/index.ts`
  - 平台层对外稳定导出面。
- `frontend/聊天应用/聊天应用门面.ts`
  - 用现有聊天模块包出 `ChatAppKernel` 的过渡门面；只暴露命令和快照，不暴露内部可变对象。
- `frontend/后台应用/后台应用门面.ts`
  - 用现有后台模块包出 `AdminAppKernel` 的过渡门面。
- `frontend/tests/平台契约测试.spec.ts`
  - 锁定平台协议的最小形状和反漂移规则。
- `frontend/tests/浏览器应用平台测试.spec.ts`
  - 锁定平台组合根不会偷懂聊天业务。

### 主要修改文件

- `frontend/聊天壳.ts`
  - 从“大壳 + 组合根 + 部分运行时 owner”退成“聊天壳桥接层”。
- `frontend/后台壳.ts`
  - 从“表单页 + 直连 transport”退成“后台壳桥接层”。
- `frontend/应用运行时.ts`
  - 收进平台层视角，变成平台输入桥的一部分，而不是聊天壳私有 helper。
- `frontend/入口.ts`
  - 只负责启动平台；不再直接散落应用启动逻辑。
- `frontend/tests/聊天壳测试.spec.ts`
- `frontend/tests/后台壳测试.spec.ts`
- `frontend/tests/入口测试.spec.ts`

## 施工红线

- 平台层只能拥有浏览器运行时真相，不能判断房间、未读、消息、权限。
- 壳层只能发命令、读快照、渲染；不能继续扩写 transport / storage / lifecycle 横切逻辑。
- `聊天应用门面`、`后台应用门面` 只是过渡门面，不得重新造一个共享大状态对象。
- 这一份计划必须删掉或收缩旧入口；如果只是新增文件、旧路径不退场，算失败。

- [ ] **Step 1: 写最小平台组合根**

  `frontend/平台/浏览器应用平台.ts` 只做三件事：

  - 接收浏览器信号；
  - 调用对应 runtime；
  - 向应用门面广播平台事件，并汇总平台快照。

  最小形状：

  ```ts
  export function 创建浏览器应用平台(deps: {
    lifecycleRuntime: { handleVisibilityChange(hidden: boolean): 平台事件 | null };
    chatApp: { dispatch(event: 平台事件 | 平台命令): void; getSnapshot(): unknown };
    adminApp: { dispatch(event: 平台事件 | 平台命令): void; getSnapshot(): unknown };
  }) {
    return {
      handleBrowserSignal(signal: { type: "visibilitychange"; hidden: boolean }) { /* ... */ },
      getSnapshot(): 平台快照 { /* ... */ },
    };
  }
  ```

- [ ] **Step 2: 收口 `frontend/应用运行时.ts`**

  规则：

  - 保留它作为聊天壳专用输入桥的职责；
  - 但它的创建和持有改由平台/聊天应用门面统一管理；
  - 不能继续让 `聊天壳.ts` 把它当私有大脑。

- [ ] **Step 3: 改造 `frontend/入口.ts`**

  把入口改成：

  - 启动平台；
  - 绑定浏览器 `visibilitychange / online / offline` 等基础信号；
  - 挂载根壳。

  入口不再直接写应用业务逻辑。

## 完成定义

这一份计划做完，必须能明确回答下面三件事：

1. 浏览器信号先经过谁，再进聊天或后台应用？
2. 壳层还能不能直接摸 transport / storage / runtime？
3. 后续聊天 owner 拆分时，是不是已经有固定的协议面和启动点可以挂？

只要这三件事里还有一件说不清，这一份就不能算完成。
