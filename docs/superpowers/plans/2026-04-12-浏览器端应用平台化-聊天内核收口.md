# 浏览器端应用平台化·聊天内核收口 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把聊天主前端从“壳层 + patch 状态 + 若干编排端口”收口成正式的 `ChatAppKernel`，让会话、房间、时间线、视口、输入、媒体各归其位，彻底减少奇怪 bug 的根源。

**Architecture:** 这一计划的核心不是加更多文件，而是消灭共享可变真相。现有 `房间时间线.ts`、`房间滚动器.ts`、`阅读推进编排.ts`、`房间恢复编排.ts`、`房间实时编排.ts`、`媒体/媒体查看器.ts` 已经有局部 owner 的雏形，这一份就是把它们挂到正式的 `ChatAppKernel` 下，并把 `聊天壳.ts` 里的 `chatState / updateChat()` 退掉。

**Tech Stack:** TypeScript、Lit、Vitest、现有 `frontend/房间时间线.ts`、`frontend/房间滚动器.ts`、`frontend/阅读推进编排.ts`、`frontend/房间恢复编排.ts`、`frontend/房间实时编排.ts`、`frontend/媒体/*`。

---

## 为什么这一份必须单独拆

聊天主链是现在 bug 最容易长的地方，也是最不该一次性“大重写”的地方。

如果把平台层、聊天 owner、浏览器能力、后台应用化全部混在一个计划里，执行时一定会出现两个问题：

- 谁在收哪类真相，会越来越说不清；
- 一次改动太大，测试一红就不知道是平台问题、聊天问题，还是浏览器能力接入问题。

所以聊天主链必须单独一份计划，目标很明确：**让聊天 bug 以后能沿 owner 找根，而不是沿壳层找运气。**

## 施工红线

- 不允许再出现第二个 `chatState`。
- 不允许 owner 共写一个共享可变对象。
- `TimelineOwner` 之外，任何地方都不能重新决定消息排序、去重、乐观消息收敛。
- `ViewportOwner` 之外，任何地方都不能继续用 DOM 读写裁决视口业务真相。
- `MediaOwner` 之外，任何地方都不能再散落全屏 / 返回 / 媒体前台模式裁决。
