# 前端房间编排内核重构 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把聊天房间前端从“超级壳组件硬撑会话逻辑”重构成“共享契约 + 传输适配 + 前端同步编排内核 + 滚动器 + 壳层渲染”的稳定结构，同时不改变后端领域真相边界。

**Architecture:** 保留 [frontend/契约.ts](/E:/koko/frontend/契约.ts)、[frontend/传输.ts](/E:/koko/frontend/传输.ts)、[frontend/视图.ts](/E:/koko/frontend/视图.ts)、[frontend/入口.ts](/E:/koko/frontend/入口.ts) 这几条已经对的边界；新增 `xstate` 驱动的 [frontend/房间内核.ts](/E:/koko/frontend/房间内核.ts)、Lit Reactive Controller 形式的 [frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts)、以及本地持久化收口的 [frontend/存储.ts](/E:/koko/frontend/存储.ts)；最后让 [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 退回渲染壳和意图转发层。

**Tech Stack:** TypeScript, Lit 3, socket.io-client 4.x, XState 5, Vitest, Happy DOM, esbuild

## 风险提示

1. 这次重构的最大风险不是后端真相被改坏，而是前端回归测试不够细导致壳层旧逻辑残留。
2. `xstate` 引入后，如果状态边界定义不清，容易把“同步编排状态”和“展示状态”重新揉回一起。
3. 滚动器提取时最容易丢掉现有刷新恢复、历史前插补偿和已读推进的细节，必须坚持 TDD。

## 执行约束

1. 默认不动后端领域真相、用例与成员资格裁决。
2. 如果实现中发现确实需要一条很薄的后端适配能力，必须单独停下说明证据和必要性。
3. 每个 Task 完成后都要跑对应验证并提交，不能一口气堆到最后。
