# 浏览器端应用平台化·后台应用化 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 `frontend/后台壳.ts` 从网页式后台页，升级成挂在 `BrowserAppPlatform` 上的 `AdminAppKernel`，避免后台继续成为整个浏览器端架构里的旧世界入口。

**Architecture:** 后台这条链路不需要复制聊天主链的复杂度，但也不能继续“表单提交 -> transport -> requestUpdate”这种网页式路径。这里要做的是三个 owner：`AdminSessionOwner`、`AdminQueryOwner`、`AdminShellOwner`，再让后台壳只做桥接和渲染。它既要和平台层一致，也要保持比聊天链路更克制。

**Tech Stack:** TypeScript、Lit、Vitest、现有 `frontend/后台壳.ts`、现有 `frontend/传输.ts`、平台层运行时与协议。

---

## 为什么后台也必须进来

如果只把聊天主链做成应用，而后台继续保持网页式做法，会留下三个坏后果：

- 整个仓库里会一直保留两套完全不同的前端心智模型；
- 平台层能力没法真正跨业务复用；
- 后台会继续成为最容易偷越边界、偷直连 transport 的地方。

所以后台虽然复杂度低，但必须正式入编。

## 施工红线

- 后台壳不得继续直接调 `transport.login / loadRooms / loadRoomDetail`。
- `AdminQueryOwner` 只负责后台查询编排，不拥有后端权威真相。
- `AdminShellOwner` 只负责本地体验态，不拥有业务查询真相。
- 后台应用化不能顺手把聊天平台逻辑又写进后台壳。
