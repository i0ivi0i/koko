## 0. 这次为什么要重写 plan

旧计划已经基本收掉了“浏览器只认一个 HTTPS 同源入口”这条网络真相，但真实烟测又暴露出另一条更深的真相还没收干净：

**系统还在把 `webseed 可读`、`本地补齐完成`、`真实 peer 已建立` 误当成同一件事。**

这会直接带来 4 个严重后果：

1. 浏览器明明只是靠 WebSeed 或冷源在读，UI 却先喊“正在协作分发”。
2. torrent 一旦 `done`，前端就把自己升级成 `complete_peer`，哪怕从头到尾根本没连上真实群友。
3. 后端本来已经把 `partial_peer / complete_peer` 当“真实 swarm 事实”来裁决 media state，前端却把它污染成“任何可读来源都算 peer”。
4. 最终就会出现一种最危险的假象：
   页面能开、视频能播、局域网也能跑，但“万人群聊协作分发已经成立”其实是假成功。

所以这份新计划不是再修一个网络补丁，而是要把 **协作分发真相** 也收进 spec 的完成定义里。

---

## 1. 已确认的真实根因

### 1.1 前端把三层语义混成了一层

当前代码把下面三件事混在一起了：

1. `streamURL` 当前可读
2. 本地文件已经补齐
3. 真实 peer / swarm 已经建立

而真正应该成立的顺序是：

1. **可读** 只证明当前有源，不证明有 peer
2. **本地补齐** 只证明这个浏览器拿全了字节，不证明帮别人传了
3. **真实 peer 已建立** 才能证明协作分发真的成立

### 1.2 当前错误已经有代码证据

1. `frontend/媒体/资产协作分发运行时.ts`
   `wire.type === "webSeed"` 也会触发 `SWARM_ACTIVE`
2. 同文件
   `done` 会无条件把 presence 升级成 `complete_peer`
3. 同文件
   无 peer 证据时，普通轻会话默认 hint 仍会落成“正在协作分发”
4. `src/媒体协作分发.rs`
   后端注释已经明确：`partial_peer` 代表“真实进入 swarm 但尚未补齐”
5. 这说明问题不是后端没有规则，而是前端把假事实上报成了真事实

### 1.3 这和 spec 的关系

`省心省力网络` spec 不只要求“浏览器别再看到内网端口”，还要求：

1. 用户视角只有一套真相
2. 运行时真相不能自我感动
3. 开发测试应尽量逼近未来公网真实用户行为

如果协作分发状态机还在自欺欺人，那 spec 就不能算彻底完工。

---

## 2. 本次完工必须达到的硬结果

执行完后，必须同时满足下面 6 条：

1. **禁止** 没有真实 peer 证据时，默认展示“正在协作分发”
2. **禁止** `wire.type === "webSeed"` 触发 `partial_peer`
3. **禁止** `wire.type === "webSeed"` 触发 `SWARM_ACTIVE`
4. **禁止** `done` 在没有真实 peer 证据时升级成 `complete_peer`
5. **禁止** 已经只是“本地完整”的会话，在重开或复用时被继续吹成 `complete_peer`
6. 局域网 HTTPS 同源入口、Tus 同源上传、同源 announce 这三条既有网络真相不能被本轮修复打坏

---

## 3. 红线

后续实现时，必须一直守住下面这些红线：

1. **禁止** 为了让 UI 看起来热闹，继续把未知态伪装成“正在协作分发”
2. **禁止** 把 `webSeed` 读取行为上报成 `partial_peer / complete_peer`
3. **禁止** 因为 `done` 了，就自动宣布“我已经成为群友来源”
4. **禁止** 新增第二套 hint 状态机，把问题越修越乱
5. **禁止** 为了通过测试，反过来把后端 `partial_peer / complete_peer` 语义放宽
6. **禁止** 动到浏览器同源网络 contract 时重新引入 `127.0.0.1`、`localhost`、`:1081`、`:7072`、`:7073`
7. **禁止** 修前端状态机时引入新的冗余 owner、冗余事件或冗余包装层

## 4. 实施顺序

### Task 1：先把“真实 peer 才算协作分发”写成红测

涉及文件：

- `frontend/tests/资产协作分发运行时测试.spec.ts`
- `frontend/tests/媒体协作分发测试.spec.ts`
- `frontend/tests/媒体会话测试.spec.ts`

必须先补失败测试，锁死下面这些裁决：

1. 普通轻会话在没有 peer 证据时，`hint === null`
2. `wire.type === "webSeed"` 只允许把 hint 拉到“正在补块”，不允许触发 `SWARM_ACTIVE`
3. `wire.type === "webSeed"` 不允许上报 `partial_peer`
4. `done` 之前如果从未连上真实 peer，就不允许自动上报 `complete_peer`
5. 已本地完整但从未连上真实 peer 的旧会话，复用时仍不允许直接开启 `complete_peer heartbeat`

验收：

1. 测试必须先红
2. 失败信息必须直指“webseed 被误判成 swarm”或“done 被误判成 complete_peer”

### Task 2：在运行时里拆开 4 个真相

涉及文件：

- `frontend/媒体/媒体协作分发.ts`
- `frontend/媒体/资产协作分发运行时.ts`

目标是把当前会话真相拆成下面 4 层：

1. 当前是否可读
2. 当前是否正在补块
3. 当前是否连上过真实 peer
4. 当前是否本地完整

实现要求：

1. 真实 peer 证据只能来自非 `webSeed` 的 `wire`
2. `SWARM_ACTIVE` 只允许由真实 peer 触发
3. `partial_peer` 只允许在“未完整但已连上真实 peer”时上报
4. `complete_peer` 只允许在“已完整且已连上真实 peer”时上报
5. `done` 只证明“本地完整”，不自动证明“真实 swarm 已成立”

### Task 3：把 UI hint 收口成诚实语义

涉及文件：

- `frontend/媒体/资产协作分发运行时.ts`
- 受影响的前端测试

硬裁决：

1. 默认轻会话无 peer 证据时，`hint = null`
2. 补块期仍可显示“正在补块”
3. 只有真实 peer 建立后，才允许显示“正在协作分发”
4. 本地完整但无 peer 证据时，默认不再硬塞“正在协作分发”

这里优先走“减少假提示”，**禁止** 顺手再发明第三套花哨文案。

### Task 4：跑协作分发回归，证明没把媒体会话和缓存编排打坏

涉及文件：

- `frontend/tests/聊天应用内核测试.spec.ts`
- `frontend/tests/聊天媒体编排测试.spec.ts`
- `frontend/tests/媒体播放测试.spec.ts`
- `frontend/tests/媒体查看器测试.spec.ts`

重点验证：

1. `ASSET_COMPLETE` 仍然只代表“本地完整”
2. 媒体会话的 `locally_complete / seeding / recovering` 流程仍成立
3. 图片查看器、视频查看器、缓存恢复、重开播放不因 hint 收紧而回退

### Task 5：重跑真实烟测，确认 spec 最关键两条真相同时成立

必须重跑：

1. `run.ps1`
2. 房间 `1234b`
3. 至少两个浏览器上下文
4. 使用 `D:\200-生活\230-照片备份\233-Telegram\色色` 里的 MP4 继续验证

必须确认：

1. 浏览器网络面板仍然只出现同源 HTTPS / WSS
2. 没有内部端口重新泄漏
3. 视频仍可上传、发送、播放
4. 如果只命中 WebSeed / 冷源，不再把状态吹成“真实协作分发已成立”
5. 如果真实 peer 建立，相关 hint、presence、事件才会进入协作分发语义

---

## 5. 可顺手修但禁止跑偏的附带问题

如果过程中证据非常明确，可以顺手修下面两类问题：

1. seeder reconcile 启动竞态
   条件：必须能清楚证明它是独立问题，且修复不会把本轮主线打散
2. 其它直接影响多人群聊真实协作分发判断的假状态
   条件：必须和“真实 peer 语义”同一条根因链

**禁止** 借机扩成大范围播放器、缓存、上传链重构。

---

## 6. 完成定义

只有同时满足下面这些条件，才允许宣布“`省心省力网络` spec 在当前代码层已经彻底完工”：

1. 新增红测先红后绿
2. `webSeed` 不再被上报成 `partial_peer / complete_peer`
3. `done` 不再被误判成“真实 swarm 已成立”
4. 默认轻会话不再凭空显示“正在协作分发”
5. 同源 HTTPS / `/files` / `/api/swarm/announce` 既有真相没有回退
6. 局域网多会话烟测仍可上传、发消息、看视频
7. `git status --short` 干净
8. 完成中文提交

## 7. 自审问题

执行前后都要反复检查下面 7 句：

1. 我是不是又把 `可读` 偷换成了 `有 peer`
2. 我是不是又把 `done` 偷换成了 `complete_peer`
3. 我是不是又让默认 UI 提示替代了真实运行态
4. 我是不是为了省事，把后端真语义改松了
5. 我是不是为了过测试引入了新的冗余状态或事件
6. 我是不是把已修好的同源网络 contract 又碰脏了
7. 这次改动能不能让以后的人一眼看懂“什么才算真实协作分发”
