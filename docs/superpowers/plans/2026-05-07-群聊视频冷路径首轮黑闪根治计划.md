**Goal:** 修复用户进房后从最新视频 `G` 往上逐条自动播放 `F/E/D/C/B/A` 时，每条视频第一次进入自动播前都会瞬间黑闪、二轮回看减轻、退出房间重进又复发的冷路径首轮曝光 bug。

**Architecture:** 本计划不再把问题归因成“冻结帧还是 `webp data URL`”，因为当前代码已经有 `ImageBitmap / OffscreenCanvas` 内存桥。真正要修的是冷路径首轮曝光模型：某条视频第一次进入可见 owner 前，系统必须先拥有“同附件、同 source、已提交”的 warm frame 或稳定占位合约；`Video.js v10` 仍是唯一 live player，`poster / runtime preview / frozen bridge / canonical host` 只能是同一可见槽位的投影。

**Tech Stack:** TypeScript, Lit, Video.js v10, WebTorrent, Vitest, Playwright CLI, Chrome DevTools CLI, browser-trace, `requestVideoFrameCallback`, `ImageBitmap`, `OffscreenCanvas`, GitNexus, Serena

## 官方依据

执行者遇到模糊点时，先回到这些官方资料，不按记忆拍脑袋：

- MDN `requestVideoFrameCallback()`：<https://developer.mozilla.org/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback>
  - 关键事实：它代表视频帧提交到 compositor 的近似证据，但可能晚一个 v-sync。
- MDN `OffscreenCanvas.transferToImageBitmap()`：<https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas/transferToImageBitmap>
  - 关键事实：它创建的是内存 `ImageBitmap`，需要消费或 `close()`，不能任由图形资源泄漏。
- MDN `CanvasRenderingContext2D.drawImage()`：<https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage>
  - 关键事实：`HTMLVideoElement / ImageBitmap / OffscreenCanvas` 都是合法画面源。
- Video.js options：<https://videojs.org/guides/options>
  - 关键事实：自动播放应优先走 Video.js option / player API，不应让外层依赖原生 attribute 误判播放成立。
- Video.js PosterImage：<https://docs.videojs.com/posterimage>
  - 关键事实：poster 是播放器 UI 生命周期的一部分，不是“暂停帧”或“已播放帧”。
- WebKit video policy：<https://webkit.org/blog/6784/new-video-policies-for-ios/>
  - 关键事实：可见性会影响自动播放/暂停，滚动信号只能当几何事实输入，不能直接成为业务真相。

## 1. 真实 bug 复现模型

用户描述的复现不是随机快滑问题，而是稳定的冷路径首轮曝光问题：

1. 群聊从上到下有 `A/B/C/D/E/F/G` 视频。
2. `A` 最早发，`G` 最新发。
3. 用户进房默认看到最新的 `G`。
4. 从 `G` 往上逐条自动播放欣赏：`G -> F -> E -> D -> C -> B -> A`。
5. 每条视频第一次成为自动播 owner 前，都会先“瞬间消失/黑一下/再出现并播放”。
6. 看完到 `A` 后，再重新往下滑 `B -> C -> D -> E -> F -> G`，黑闪明显减轻。
7. 退出房间重新进入，又回到第一轮黑闪。

这个模式说明：

- 问题不是某个附件坏了。
- 问题不是单纯滚动速度。
- 问题不是 `Video.js v10` 无法播放。
- 问题是“首次曝光时没有可立即使用的同源视觉事实；看过一次后 runtime preview / bridge / 解码状态被养热；退出房间后这批运行时视觉事实丢失”。

## 3. 根因假设

本计划的主假设是：

> 冷路径首轮黑闪来自“首次成为 owner 的视频，在 reveal 前没有同附件同 source 的 warm-frame evidence；渲染层为了避免空白又临时在 `poster / preview / stage host / canonical host` 之间切换，导致可见槽位短暂掉到黑底或错位帧。”

二轮回看黑闪减轻，是因为：

- 首轮播放已经产生 `runtime preview`、`首帧就绪源`、`冻结帧`、`Video.js` 解码/缓存状态。

退出房间重进复发，是因为：

- `时间线画面缓存Owner.清空()` 或房间生命周期会清掉运行时视觉缓存。
- 新会话还没重新建立 warm frame。

这个假设必须用真实浏览器取证验证，不能直接当事实写代码。

## 5. 架构边界

### 5.1 Domain / Application / Adapter / Shell 分层

本问题是前端 shell 体验问题，但仍要按 DDD / 六边形边界拆开：

- Domain
  - 不涉及后端业务领域。
  - 不碰 WebTorrent 字节主链裁决。

- Application
  - `视频可见槽位协议.ts` 是前端应用层纯协议：只接收事实，输出可见槽位决策。
  - 它不读 DOM，不操作 Video.js，不触发网络。

- Adapter
  - `全局唯一播放器.ts` / `videojs播放器壳.ts` 是 Video.js / HTMLVideoElement 适配。
  - 它们把浏览器事件翻译成应用层事实。

- Shell
  - `视频附件渲染.ts` / `时间线媒体基类.ts` / `时间线画面缓存.ts` 是消息窗壳层。
  - 它们只投影协议结果和管理本地视觉缓存。

### 5.2 不允许的修法

- 不允许新增“快滑模式”或“大跳转模式”第二套状态机。
- 不允许把 `poster` 当成“暂停画面”。
- 不允许把 `runtime preview` 做成第二播放器。
- 不允许用 timeout 硬等 80ms/120ms/450ms 来假装稳定。
- 不允许绕过 `Video.js v10` 直接创建第二正式播放 `<video>`。
- 不允许恢复 HTTP 直链、HLS、DASH、original_url 等第二媒体主链。
