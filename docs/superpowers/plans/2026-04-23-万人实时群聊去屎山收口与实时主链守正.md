# 万人实时群聊去屎山收口与实时主链守正 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不改聊天业务语义、不改 realtime 对外协议、不重写成熟实时轮子的前提下，收口聊天 realtime 主链与房间恢复/编排热点，实质减轻 `src/实时外壳.rs`、`src/用例.rs`、`frontend/传输.ts`、`frontend/房间实时编排.ts`、`frontend/房间恢复编排.ts`、`frontend/聊天应用内核.ts` 的热点压力，并同步删除旧胶水与重复路径。

**Architecture:** 这一阶段只做 `A + 1`，也就是“聊天 realtime 主链 + 恢复/编排热点”，且只做结构守正。后端继续以 `socketioxide` 为唯一聊天 realtime 核心，前端继续以 `socket.io-client` 为唯一聊天 realtime 核心；`contract` 继续作为唯一共享表面，adapter 只做协议翻译，shell 只做交互编排，前端禁止重新养一套业务 `domain / application` 真相。

**Tech Stack:** Rust 2021、Tokio、Axum、socketioxide、TypeScript、Lit、socket.io-client、Vitest、PowerShell、graphify

## 实施前背景与 authoritative baseline

### 为什么这个计划不能写成“整理一下结构”

这次不是普通的代码整理，也不是目录美化。  
这次如果计划写虚了，执行时最容易发生的两类 bug 是：

1. **范围漂移 bug**
   - 借“去屎山”之名，顺手把协议、错误语义、事件名、transport 全家桶一起改了。
2. **双真相 bug**
   - 后端还保留 `socketioxide` 主链，前端和恢复链却又偷偷长出第二套 realtime / recovery 解释层。

所以这份 plan 必须把“为什么这样拆”“禁止什么”“每步先验证什么”写死，而不是只给一个概念路线。

### 当前已确认的事实

1. 后端聊天 realtime 正式主链仍是 `socketioxide`。
2. 前端聊天 realtime 正式主链仍是 `socket.io-client`。
3. `src/契约.rs` 与 `frontend/契约.ts` 仍是多壳共享唯一稳定表面。
4. 当前风险不在“核心轮子换错”，而在**外围恢复链、编排层、transport 热点、壳层胶水持续吸职责**。
5. `graphify-out/GRAPH_REPORT.md` 当前第一 god node 仍是 `HttpRealtime传输`，说明 `frontend/传输.ts` 是这轮必须减压的核心热点。

### 本阶段 authoritative 热点

后端主链 / 热点基线：

1. `src/外壳.rs`
   - 只允许继续承担 app state / route / realtime namespace wiring。
2. `src/实时外壳.rs`
   - 当前聊天 realtime handler 主入口，必须削薄到“复用已认证会话 + 命令翻译 + 发权威事实”。
3. `src/用例.rs`
   - 当前仍承接 `校验房间订阅资格`、`创建消息` 等权威用例；本阶段只允许把聊天主链相关边界收清，禁止顺手重写整套 usecase 体系。

前端主链 / 热点基线：

1. `frontend/传输.ts`
   - 当前同时吸附 socket 创建、HTTP 调用、运行时策略与多条链路解析，是第一阶段必须减压的首要热点。
2. `frontend/房间实时编排.ts`
   - 当前承担订阅、收事件、控制面结果解释、待补发消息重放。
3. `frontend/房间恢复编排.ts`
   - 当前承担 `invalid_session`、snapshot reload、房间恢复、恢复失败收场。
4. `frontend/聊天应用内核.ts`
   - 当前仍是多个前端编排端口的汇聚点，必须削薄，但禁止让它继续吸回业务真相。
5. `frontend/聊天壳.ts`
   - 只允许保留壳层交互与视图协作；若仍承载 transport / 恢复 / 权限判断，一律视为退化。

### 本阶段明确排除

1. `frontend/聊天媒体编排.ts`
2. `frontend/媒体/**`
3. `src/媒体*`
4. WebTorrent / swarm / locator / 媒体浏览器应用化 owner 链
5. `contract` 表面重写

禁止把“离聊天 UI 很近”误判成“就属于第一阶段”。

## 全局禁止事项

后面所有任务都要同时遵守下面这些红线，任何一步越界都算失败：

1. **禁止改聊天 realtime 外部协议表面。**
2. **禁止改现有事件名、payload 形状、控制结果语义。**
3. **禁止新造第二套聊天 realtime 核心。**
4. **禁止把恢复链做成第二实时主链。**
5. **禁止前端长出平行业务 `领域 / 应用` 真相。**
6. **禁止 adapter 承载业务真相。**
7. **禁止 shell 承载权限、成员资格、消息成立真相。**
8. **禁止借 DDD 之名新增没有独立边界价值的 `manager / facade / helper / wrapper`。**

10. **禁止为“保险一点”长期保留新旧双活。**
11. **禁止因为结构收口顺手改媒体协作分发主链。**
12. **禁止为了拆热点，把 `contract` 倒灌壳层展示语义或某壳专属流程。**

## 结构收口阶段的测试解释

这次不是新功能开发，而是**带护栏的结构收口**。  
所以测试分成两类，执行时禁止混淆：

1. **characterization 测试**
   - 作用：把当前正确行为钉住；
   - 这些测试在当前代码上**可能直接 PASS**；
   - 如果它们直接 PASS，记录为“行为基线已被现状满足”，然后继续，不准为了追求形式上的先红而故意改坏现有行为。
2. **新边界护栏测试**
   - 作用：防止 adapter / shell / recovery owner 漂移；
   - 这类测试有些会先 FAIL，有些也可能直接 PASS；
   - 只要它们真实保护本阶段边界，就允许保留现状绿灯。

因此必须写死：

1. **禁止为了满足教条式先红，故意把现有正确行为做坏。**
2. **禁止看到 characterization 测试先绿，就误判“这一步没价值”。**
3. **结构收口阶段真正的 TDD 含义，是先补行为护栏，再在重构中保持这些护栏持续为真。**
