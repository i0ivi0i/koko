# 群聊媒体 P2P 热分发与锚点持久化 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 `koko` 的群聊媒体能力在同一轮内同时支持图片和视频发送/查看，采用 `WebTorrent 热分发 + 锚点持久化 + 消息仅引用附件` 的单一 canonical 主链，并保持当前图片能力不回退。

**Architecture:** 先用特征测试钉死当前事实，再把“仅图片”的旧边界收敛成“图片+视频共核、媒体特有逻辑薄分流”。领域与用例只拥有 `attachment/message/locator/availability` 真相，adapter 接 `Uppy/WebTorrent/tracker/锚点节点`，shell 只保留本地体验态和渲染接线。

**Tech Stack:** Rust, Axum, Tokio, SQLx, object_store, infer, image, browser media APIs, TypeScript, Lit, Vitest, Uppy, WebTorrent

---

## 当前事实

- 当前图片发送基线可用：
  - `pnpm --dir frontend test tests/聊天壳测试.spec.ts -t "进入房间后发送区会显示图片选择入口"` 通过
  - `cargo test 纯图片附件消息允许文本为空 --test 领域测试` 通过
- 当前视频发送明确未实现：
  - `pnpm --dir frontend test tests/聊天壳测试.spec.ts -t "进入房间后发送区会显示视频选择入口"` 失败
  - `cargo test 纯视频附件消息允许文本为空 --test 领域测试` 失败
- Serena 已确认：
  - 前端壳层当前只有图片入口、图片草稿、图片上传器
  - 前端 transport 只有 `prepareImageUpload / completeImageUpload`
  - 后端领域 `创建消息` 仍把 `附件种类::视频` 判为 `附件类型不支持`

这份计划默认把以上结论作为执行起点，不再回头争论“视频是不是可能已经藏在别处”。

## Scope Check

这份 spec 同时覆盖：

- 轮子比选与锚点方案定板
- 领域/契约演进
- 后端媒体发布与 locator
- 前端媒体发送、查看与播放

虽然涉及多个层，但它们共同服务于同一个能力切换：  
**把当前“仅图片附件”升级成“图片+视频共核的单一媒体主链”。**  
因此保持一份总 plan 是合理的，但每个任务必须是可独立转绿、可独立提交的纵向切片。
