# 万人群聊浏览器零崩溃零闪烁最终完工 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` for Inline Execution. This plan is written for the current `main` workspace per project instruction. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 完整落地 [2026-04-26-万人群聊浏览器零崩溃零闪烁 spec](/E:/koko/docs/superpowers/specs/2026-04-26-万人群聊浏览器零崩溃零闪烁.md)：多人群聊、移动窄视口、长时间滚动、viewer、发送视频后，浏览器仍只背必要媒体对象，`WebTorrent` 主链不被削弱，自动播放/自动暂停/viewer/fullscreen 不回退。

**Architecture:** 不新建第二播放器、不新建第二 WebTorrent runtime、不新增只转发的 manager。把现有 `房间消息窗.ts -> 聊天媒体编排.ts -> 视频预览协作.ts / 协作补齐协作.ts -> 资产协作分发运行时.ts` 收成一条媒体重量裁决链：当前重播放、邻近轻预热、远处冷表达、轻帮助态。正式字节主链继续由 `WebTorrent service worker/createServer/streamURL` 承担；`origin/original` 只允许作为明确锚点或图片冷表达，不能和 swarm 同时冒充正式视频真相。

**Tech Stack:** TypeScript, Lit, XState runtime actors, TanStack Virtual, Video.js v10 singleton shell, WebTorrent, Vitest, Chrome DevTools CLI, Playwright CLI, Serena, graphify.

## 0. 已知证据与执行原则

### 0.1 2026-04-27 CLI smoke 证据

本计划建立在真实 `chrome-devtools` / `playwright-cli` 烟测上：

1. fresh newcomer 进入 `1234b` 后，网络立刻同时出现 `locator`、`torrent`、`/webtorrent/... [206]`、`/api/attachments/...variant=original [206]`。
2. 窄视口打开第一个视频后，请求数从约 `151` 跳到约 `471`。
3. sender 页发送一个 `4.5MB` MP4 后，请求数到约 `626`。
4. 已重压页面曾让 `chrome-devtools take_snapshot` 返回 `Target crashed`。
5. `563MB` MP4 当前被上传大小限制拦住，这不是稳定性通过证明，只说明大文件 UI 压测路径被现有上限阻断。
6. 手动体验发现：点击当前自动播放视频进入真全屏时偶发无反应；退出后再次点击同一个视频，可能降级成“附件当前不可获取”。这说明 viewer/fullscreen 往返期间，自动播 owner、查看器 owner、协作源 consumer 或播放源代次至少有一处释放/复用边界不稳定。

### 0.2 当前代码根因

1. `房间消息窗.ts` 已有近视口预算，但它只能限制 DOM 表面，不能限制编排层、帮助链、冷源 URL 表。
2. `聊天媒体编排.ts` 仍能遍历整房附件构建 `contentUrlByAttachmentId`，并把 `originalSrc` 暴露给壳层。
3. `协作补齐协作.ts` 的 `恢复当前房间缓存帮助任务()` 默认参数仍是整房媒体附件。
4. `资产协作分发运行时.ts` 已有轻帮助态雏形，但零引用保留条件仍依赖 `eagerCompleting || locallyComplete`，必须用测试锁定 heavy reader/whole-file 退场。
5. `媒体播放.ts` 仍保留 `anchor` mode，不能一刀切删除；但必须防止它在同一视频上和 `swarm` 同时成为正式播放真相。
6. 当前自动播视频进入 viewer/fullscreen 后，返回群聊再点同一视频必须继续使用同一条正式媒体真相重新接管；禁止因为 viewer 关闭释放了共享协作源、旧代次 locator 或 anchor fallback 而把可播放视频误报为“附件当前不可获取”。

### 0.3 不允许的做法

1. 禁止新增仓库内 smoke 脚本；浏览器验收只用 `chrome-devtools` CLI 和 `playwright-cli` CLI。
2. 禁止用调小 overscan、调高 listener 阈值、延长 timeout 代替生命周期收口。
3. 禁止削弱 `WebTorrent` 做种/补齐/轻帮助主链。
4. 禁止恢复 HLS/original/direct URL 为长期正式视频主链。
5. 禁止新建 wrapper/manager/coordinator 只转发旧逻辑。
6. 禁止在没有红测的情况下改核心媒体生命周期。

## 1. 目标预算

### 1.1 稳态硬红线

1. `activeFormalPlayerCount <= 1`
2. `autoplayOwnerCount <= 1`
3. `nearViewportPreviewVideoCount <= 6`
4. `activeVideoSessionCount <= 12`
5. `activeMediaSessionCount <= 24`
6. `zeroRefHeavySessionCount == 0`
7. `zeroRefWholeFileReaderCount == 0`
8. `MaxListenersExceededWarning == 0`

### 1.2 瞬态硬红线

1. owner handoff / viewer 归位 / fullscreen 退出期间，真实 preview video 可短暂到 `8`，但必须在 `1500ms` 内回到 `6`。
2. locator / preview / swarm bootstrap 旧代次必须在窗口缩回、owner 切换、session 释放、生命周期降载时中止或失效，不能继续写回 ready/cache/playback。
3. `wholeFileHeavySessionCount` 只允许前台真实需要的少量会话持有，目标 `<= 4`。
4. `zeroRefLightHelpSessionCount <= 16`，超出后必须有可解释的淘汰/降级规则。

### 1.3 CLI smoke 采样点

每轮最终验收必须手动 CLI 采样：

1. fresh newcomer 首屏稳定后。
2. 窄视口打开/关闭 viewer 后。
3. 连续上下滚动至少 `30s` 后。
4. sender 发送小 MP4 后。
5. hidden/background 再回前台后。

必须记录：DOM video/img 数、playing 数、runtime budget、network 404/5xx、console error/warn、Long Animation Frame、heap/native memory、WebTorrent range/stream 请求。
