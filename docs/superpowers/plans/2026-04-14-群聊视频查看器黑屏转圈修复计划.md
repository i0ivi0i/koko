# 群聊视频查看器黑屏转圈修复计划 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 彻底修好群聊视频点击后黑屏转圈的问题，同时保持现有上传、缩略图、时间线预览、媒体会话、补齐、释放这些业务功能不掉。

**Architecture:** 这次不碰 Rust 视频资产生成主链，因为真实浏览器抓包已经证明 `master.m3u8 / main.m3u8 / init.mp4 / .m4s` 都是 `200`。修复重点放在 `frontend/媒体/媒体查看器.ts`：把“正式播放”与“P2P/backfill 增强”重新解耦，纯 `hls.js` 成为唯一正式播放引擎，`媒体协作分发` 继续只做 swarm/backfill owner，不再让 `p2p-media-loader-hlsjs` 卡住首播主链。

**Tech Stack:** TypeScript, `hls.js`, existing `媒体会话` / `聊天媒体编排` / `媒体协作分发`, Vitest (`happy-dom`), Chrome DevTools MCP 手工验收

---

## Scope Lock

- 本计划只修 `Web` 端“点击群聊视频后查看器黑屏转圈”的 bug。
- 不纳入本轮：
  - Rust 媒体打包/分片算法重写
  - 图片链路
  - `iOS / Android / Desktop / CLI`
  - 新建第二套 swarm/runtime 或私有播放器框架
- 本计划完成后必须同时满足：
  1. 发送者和其他成员点击视频都能真正开始播放，不再只有黑色覆盖层和转圈；
  2. 时间线缩略图和点击打开查看器的现有业务行为保持不掉；
  3. `MediaSessionOwner` 的 `PLAYER_PLAYING / WAITING / STALLED / ERROR` 信号仍然成立；
  4. `媒体协作分发` 的 `acquire / backfill / complete / release` 语义不因为播放修复而丢失；
  5. 计划完成后，查看器正式播放链里不再存在“P2P 增强失败把主播放链一起拖死”的结构性风险。

## Evidence Baseline

当前已知真实证据，后续实现必须以它为准，而不是再猜环境问题：

1. 房间消息能正常出现，视频缩略图能正常显示；
2. 点击后查看器能打开，但只有黑色背景和 loading spinner；
3. 浏览器内 `media-player` 的 `src` 已经是正确的 `master.m3u8`；
4. 手动抓取当前视频的：
   - `master.m3u8`
   - `video/main.m3u8`
   - `audio/main.m3u8`
   - `video/init.mp4`
   - `audio/init.mp4`
   - 首个 `video/*.m4s`
   - 首个 `audio/*.m4s`
   全部为 `200`；
5. 查看器仍然报 `error code = 4`，等价于 `MEDIA_ERR_SRC_NOT_SUPPORTED`；
6. 查看器里的真实 `<video>` 元素一直停在：
   - `currentSrc = ""`
   - `readyState = 0`
   - `networkState = 0`

结论：这不是 `FFmpeg` 缺失，也不是后端 HLS 文件坏了；故障位于前端查看器的“正式播放适配层”。

## Design Decision

### Canonical Fix

- `streaming_asset.manifest` 的正式播放必须由一个薄的 `HlsPlaybackAdapter` 直接消费。
- `媒体协作分发` 继续负责 swarm/backfill/presence/release。
- `p2p-media-loader-hlsjs` 不能再处于“首播必经链路”上。

### Why

- 现在的 bug 本质是：`PlayerAdapter` 和 `SwarmRuntime` 的职责发生了重叠。
- 当前查看器一边要做“正式 HLS 播放”，一边还试图把 `p2p-media-loader-hlsjs` 混进 `Vidstack provider.library` 主链里。
- 这违背了 `DDD + Unix` 的 owner 边界：
  - 播放器只该回答“怎么播”；
  - swarm/runtime 只该回答“怎么补齐和分发”；
  - 不能让增强层决定正式播放可不可用。

### Outcome Target

- 首播：纯 `hls.js` 一定能播；
- 补齐：仍然由 `媒体协作分发` 和会话信号负责；
- 增强：如果未来还要加分片级 P2P，也必须挂在“不影响首播”的旁路，而不是正式播放必经链。
