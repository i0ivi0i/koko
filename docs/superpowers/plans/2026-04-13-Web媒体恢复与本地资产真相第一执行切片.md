# Web 媒体恢复与本地资产真相第一执行切片 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不走补丁路线、不制造第二核心的前提下，先在 `Web` 端修掉“后端波动时视频黑屏/灰屏/转圈不可恢复”的主问题，并正式立住 `MediaSessionOwner + MediaCacheOwner`，让当前 `WebTorrent` 文件链具备持续播放、静默恢复、本地完整资产真相与做种恢复能力。

**Architecture:** 这份计划故意只做跨端大协议的第一执行切片，不直接实现整套 `HLS/DASH` 升级。做法是先在现有 `WebTorrent + 原始附件冷源` 主链上补出可长期存活的 owner 边界：`MediaCacheOwner` 负责本地完整资产与持久化真相，`MediaSessionOwner` 负责恢复状态机，`媒体协作分发` 继续做数据平面但向上暴露正式事件，`聊天媒体编排` 从“一次性解析 src”退到“驱动 owner 并读快照”。这样第一阶段就能止血当前问题，而且不会给后续标准流媒体迁移挖反向坑。

**Tech Stack:** TypeScript、Lit、Vitest、`webtorrent`、`idb`、BrowserAppPlatform、Service Worker、现有 `媒体定位` / `媒体播放` / `媒体协作分发` 模块。

---

## 范围裁决

- 这份 plan 只覆盖 `docs/superpowers/specs/2026-04-13-跨端志愿者媒体资产与P2P分发协议-design.md` 的**第一执行切片**：
  - `Web` 第一参考实现；
  - 先把恢复状态机、本地完整资产真相、做种恢复立住；
  - 先修掉当前“后端一关就黑/灰/转圈”的主失败链路。
- 这份 plan **不**直接实现：
  - 标准流媒体 `HLS/DASH` 资产生产；
  - 图片全面纳入统一协议；
  - iOS / Android / Desktop / CLI runtime adapter；
  - 原始附件链彻底退场。
- 这份 plan 的成败标准不是“终局全部完成”，而是：
  1. 当前 `Web` 主问题被协议化修掉；
  2. owner 真相边界立住；
  3. 后续 `HLS/DASH` 升级可以替换数据平面，而不必推翻恢复与缓存语义。

## 先锁死的设计决定

### 1. 第一切片不改后端契约

当前后端仍提供：

- `load_media_locator`
- `load_media_torrent`
- `load_attachment_content`
- `presence` 更新

第一切片直接站在这条链上实现恢复，不引入新的后端 DTO、HTTP 入口或数据库迁移。  
原因不是终局不改，而是先把当前失败链路和 owner 边界修干净，再做第二阶段的媒体资产协议升级。

### 2. 第一切片不发明第二套播放器或 P2P 核心

继续复用：

- `webtorrent`
- 浏览器 `<video>`
- 现有媒体 Service Worker

项目只新增：

- `MediaCacheOwner`
- `MediaSessionOwner`
- 壳层到 owner 的信号翻译

禁止在 `webtorrent` 外再包一个私有 torrent 核心，或在 `<video>` 外包一个私有播放器引擎。

### 3. 第一切片的“本地完整资产”要做成正式持久化真相

现在有播放器缓冲、HTTP cache、WebTorrent store、临时 `Map` 缓存，但没有产品级完整资产真相。  
第一切片必须正式回答：

- 哪个 `attachmentId` 已经完整落到本地；
- 哪个资产能在重进页面后被重新识别；
- 哪个资产应自动恢复做种；
- 哪个资产只能等待 peer/网络。

### 4. 第一切片不继续围绕静态 `src` 修补

`聊天媒体编排` 不能再继续做“消息变化 -> 算一次播放结果 -> 壳层死拿 src”。  
这次必须改成：

- 壳层只消费 `session snapshot`
- `<video>` 的 `waiting / stalled / error / playing` 回流到 owner
- owner 再决定恢复、等待、重取源、继续播放

### 5. 第一切片的恢复语义直接对齐 spec

第一切片里，视频最少要支持这些状态：

- `bootstrapping`
- `playing`
- `backfilling`
- `recovering`
- `waiting_for_peer_or_network`
- `locally_complete`
- `seeding`
- `degraded`

不用等到标准流媒体资产阶段才立状态机。

- [ ] **Step 3: 最小实现 `MediaCacheOwner` 与存储 runtime 扩展**

```ts
export interface 媒体缓存记录 {
  attachmentId: string;
  contentHash: string;
  complete: boolean;
  updatedAt: number;
}

export function 创建媒体缓存(deps: 媒体缓存依赖) {
  let byAttachmentId: Record<string, 媒体缓存记录> = {};
  return {
    async 启动() {
      byAttachmentId = await deps.repo.读取全部();
    },
    async 标记完整(attachmentId: string, input: { contentHash: string }) {
      const record = { attachmentId, contentHash: input.contentHash, complete: true, updatedAt: Date.now() };
      await deps.repo.保存(record);
      byAttachmentId = { ...byAttachmentId, [attachmentId]: record };
    },
    snapshot() {
      return byAttachmentId;
    },
  };
}
```
