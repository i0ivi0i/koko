# 后端唯一真相源结构化日志 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 `koko` 的日志从“启动期可见、业务期失明”推进成“后端唯一真相源、关键主链可追踪、当前终端可读、未来可非阻塞扩展到 `warn/error` 自动落盘”的结构化日志体系。

**Architecture:** 保持 `tracing` 为唯一日志事件源，`assembly` 继续承担 subscriber / panic hook / 输出层装配，`shell` 在 HTTP 与 realtime 协议边界记录 accepted / rejected / failed / succeeded，避免把业务真相拆成第二套日志事实。当前不新增 `日志.rs`，也不引入 exporter 或落盘；只把现有终端输出收口成稳定字段与关键埋点，并通过测试和手动验收锁住字段纪律。所有语义改动必须补详细中文注释，优先解释模块职责、埋点边界、为什么在这里打日志，而不是用注释重复代码动作。

**Tech Stack:** Rust, tracing, tracing-subscriber, axum, socketioxide, tokio, sqlx/PostgreSQL, cargo test, PowerShell

## Implementation Notes

### 1. 明确不做的事

- 不新增 `src/日志.rs`
- 不引入 `log` / `env_logger` 第二套 facade
- 不把日志抽成“万能工具函数中心”
- 不加文件落盘
- 不改前端代码去承担后端日志职责

### 2. 如果出现重复代码

优先策略：
- 先接受少量重复，保证边界清晰
- 只有在重复已经开始伤害可读性时，才允许提炼局部小函数

提炼条件：
- 只能是局部、明确职责的小帮助函数
- 不能变成跨 HTTP / realtime / assembly 的“通用日志中心”

### 3. 失败测试设计提醒

- 不要只断言“有日志输出”，要断言关键字段存在
- 不要把整个日志字符串写死，避免测试对格式顺序过敏
- 重点断言：`usecase`、`adapter`、`outcome`、`error_code`、锚点字段

### 4. 手动验收提醒

手动验收看到以下现象时，视为实现漂移：
- 终端仍只有启动日志
- 成功主链没有 `info`
- 拒绝路径没有稳定 `error_code`
- 某条业务事实在多个层被重复宣告
- 为了日志把主业务跑慢或卡住
