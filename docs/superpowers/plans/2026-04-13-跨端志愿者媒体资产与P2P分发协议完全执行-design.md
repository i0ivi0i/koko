# 跨端志愿者媒体资产与P2P分发协议完全执行 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不改动 [跨端协议 spec](E:/koko/docs/superpowers/specs/2026-04-13-跨端志愿者媒体资产与P2P分发协议-design.md) 的前提下，把这份终局设计按 4 个切片完整落地，让当前仓库内可落部分都进入真实可执行状态。

**Architecture:** 这不是单一切片 plan，而是总执行 plan。整体路径是：先在 `Web + 现有 WebTorrent 文件链` 上止血并立 owner，再把视频切到 `StreamingMediaAsset + HLS/DASH`，再把图片切到 `BlobMediaAsset`，最后把当前仓库里的 shared-core 收到多壳中性表面。这样既不篡改 spec，也不靠文件名偷换完成定义。

**Tech Stack:** Rust、TypeScript、Lit、Vitest、`webtorrent`、`idb`、BrowserAppPlatform、Service Worker、现有 `媒体定位` / `媒体播放` / `媒体协作分发` 模块、后续 `HLS/DASH` 流媒体资产链。

## 范围裁决

- 这份 plan 覆盖 [跨端协议 spec](E:/koko/docs/superpowers/specs/2026-04-13-跨端志愿者媒体资产与P2P分发协议-design.md) 在当前仓库内的**完整执行路径**：
  1. 第一切片：`Web` 当前主故障止血与 owner 收口；
  2. 第二切片：视频主链升级到 `StreamingMediaAsset + HLS/DASH`；
  3. 第三切片：图片切到 `BlobMediaAsset`；
  4. 第四切片：当前仓库 shared-core 收到多壳中性表面。
- 这份 plan 仍然承认一个现实边界：
  - 当前仓库没有 `iOS / Android / Desktop` 运行时代码；
  - 因此第四切片在本仓里只完成 shared-core 与 adapter 前置条件，不伪造不存在的运行时代码。
- 这份 plan 的成败标准是：
  1. 当前仓库内，spec 所定义的 4 个切片都有明确可执行任务、验证命令和退场条件；
  2. 执行完整份 plan 后，允许对照 spec 第 `18` 节宣称“当前仓库内的完整执行已完成”；
  3. 不靠文件名偷换“第一切片完成 = spec 完成”。

## 完成边界与防漂移约束

- 第一切片完成，只能声明：
  - `Web` 当前媒体恢复与本地资产真相第一切片完成；
  - 不能声明“跨端志愿者媒体资产与 P2P 分发协议已经全部完成”。
- 整份 spec 完成，必须同时满足：
  1. 四个执行切片都完成；
  2. spec 第 `18` 节“终局完成定义”全部达成；
  3. spec 第 `14` 节要求的旧路径已经出现明确退场，不再双活；
  4. 图片、视频、音频、跨端共享契约都有实证，不再只是口头方向。
- 每个切片完成时都必须补 4 项记录：
  1. 当前 authoritative truth owner 是谁；
  2. 当前切片替换了哪条旧路径；
  3. 还有哪条旧路径暂时保留，什么条件下删除；
  4. 当前切片完成后，离 spec 第 `18` 节还差什么。
- 如果某个切片只新增新层、但旧路径没有同步收缩，这个切片按失败算，不得对外宣称完成。
- 当前仓库只有 Rust 后端与 Web 前端代码，没有 `iOS / Android / Desktop` 运行时代码目录。
  - 第四切片在本仓库里的职责，是先把共享契约、shared-core 边界、CLI/多壳可消费的稳定表面收紧；
  - 具体移动端/桌面端 adapter 落地，需要在对应代码仓或运行时代码进入本仓后再执行，不能在这里编造假路径。

## 第一切片先锁死的设计决定

### 1. 第一切片不改后端契约

当前后端仍提供：

- `load_media_locator`
- `load_media_torrent`
- `load_attachment_content`
- `presence` 更新

第一切片直接站在这条链上实现恢复，不引入新的后端 DTO、HTTP 入口或数据库迁移。  
原因不是终局不改，而是先把当前失败链路和 owner 边界修干净，再做第二阶段的媒体资产协议升级。

### 2. 第一切片不发明第二套播放器或 P2P 核心

继续复用：

- `webtorrent`
- 浏览器 `<video>`
- 现有媒体 Service Worker

项目只新增：

- `MediaCacheOwner`
- `MediaSessionOwner`
- 壳层到 owner 的信号翻译

禁止在 `webtorrent` 外再包一个私有 torrent 核心，或在 `<video>` 外包一个私有播放器引擎。

### 3. 第一切片的“本地完整资产”要做成正式持久化真相

现在有播放器缓冲、HTTP cache、WebTorrent store、临时 `Map` 缓存，但没有产品级完整资产真相。  
第一切片必须正式回答：

- 哪个 `attachmentId` 已经完整落到本地；
- 哪个资产能在重进页面后被重新识别；
- 哪个资产应自动恢复做种；
- 哪个资产只能等待 peer/网络。

### 4. 第一切片不继续围绕静态 `src` 修补

`聊天媒体编排` 不能再继续做“消息变化 -> 算一次播放结果 -> 壳层死拿 src”。  
这次必须改成：

- 壳层只消费 `session snapshot`
- `<video>` 的 `waiting / stalled / error / playing` 回流到 owner
- owner 再决定恢复、等待、重取源、继续播放

### 5. 第一切片的恢复语义直接对齐 spec

第一切片里，视频最少要支持这些状态：

- `bootstrapping`
- `playing`
- `backfilling`
- `recovering`
- `waiting_for_peer_or_network`
- `locally_complete`
- `seeding`
- `degraded`

不用等到标准流媒体资产阶段才立状态机。

- [ ] **Step 3: 最小实现 `MediaCacheOwner` 与存储 runtime 扩展**

```ts
export interface 媒体缓存记录 {
  attachmentId: string;
  contentHash: string;
  complete: boolean;
  updatedAt: number;
}

export function 创建媒体缓存(deps: 媒体缓存依赖) {
  let byAttachmentId: Record<string, 媒体缓存记录> = {};
  return {
    async 启动() {
      byAttachmentId = await deps.repo.读取全部();
    },
    async 标记完整(attachmentId: string, input: { contentHash: string }) {
      const record = { attachmentId, contentHash: input.contentHash, complete: true, updatedAt: Date.now() };
      await deps.repo.保存(record);
      byAttachmentId = { ...byAttachmentId, [attachmentId]: record };
    },
    snapshot() {
      return byAttachmentId;
    },
  };
}
```

## 全局切片总览

当前按终局 spec 收口，建议总共拆成 **4 个执行切片**：

1. **第一切片：Web 媒体恢复与本地资产真相**
   - 目标：先在现有 `WebTorrent + 原始附件冷源` 主链上修掉黑屏、灰屏、转圈，并立住 `MediaCacheOwner + MediaSessionOwner`。
2. **第二切片：视频主链升级到 `StreamingMediaAsset + HLS/DASH`**
   - 目标：把视频从“普通附件文件链”升级成正式流媒体资产，后端开始产出 manifest/segment，Web 主播放链切到标准流媒体协议。
3. **第三切片：图片全面纳入 `BlobMediaAsset` 与 `24 小时` 退场规则**
   - 目标：把图片也纳入长期本地保留、P2P 分发、统一媒体协议，并让原始附件主链进一步退到冷备角色。
4. **第四切片：跨端 runtime adapter 落地**
   - 目标：`iOS / Android / Desktop / CLI` 共用同一套媒体协议核心，只做各端 runtime 适配和长生命周期做种策略。

这 4 个切片里：

- 第一切片是止血与立 owner；
- 第二切片是视频主链升级；
- 第三切片是图片与 blob 资产统一；
- 第四切片是多壳共核兑现。

## 第二执行切片：视频主链升级到 `StreamingMediaAsset + HLS/DASH`

### 目标

在第一切片已经立住 `MediaCacheOwner + MediaSessionOwner` 的前提下，把视频主播放链正式从：

- `locator -> torrent -> web_seed -> original attachment`

升级成：

- `StreamingMediaAssetDescriptor -> manifest -> segments -> P2P + origin bootstrap`

第二切片完成后，视频不再把“原始附件文件直链”当正式播放主链；原始上传文件只保留 `24 小时` 冷备与 swarm 启动保底角色。

### 这一切片为什么单独拆

如果把第二切片直接塞进第一切片一起做，会同时引爆 4 个边界：

1. 先修当前恢复 bug；
2. 再立 owner；
3. 再改后端媒体契约；
4. 再换视频主播放链。  

这很容易把“止血”和“换心脏”混成一锅。

单独拆第二切片的好处是：

- 第一切片先把恢复语义、缓存真相、做种真相立住；
- 第二切片只替换视频数据平面和后端资产契约；
- 这样 `MediaSessionOwner / MediaCacheOwner` 可以原样复用，不会再返工。

### 边界约束

- 允许新增少量 `.rs` 文件，但只能服务于明确的领域/用例/契约收口。
- 不允许为了“好看”把 Rust 切成碎片文件海。
- 新增 `.rs` 文件的唯一正当理由是：
  - 从 `src/用例.rs`、`src/契约.rs`、`src/房间外壳.rs`、`src/媒体协作分发.rs` 这种热点里切出清楚的媒体资产协议边界；
  - 而不是再造一层私有媒体框架。
- 所有新增 `.rs` 文件都必须符合：
  - `DDD`：领域真相、用例编排、契约表面、适配层分开；
  - `Unix`：小而专、可替换、可组合；
  - 不重复手搓成熟轮子。

## 第三执行切片：图片全面纳入 `BlobMediaAsset` 与 `24 小时` 退场规则

### 目标

在第二切片已经把视频主链切到 `StreamingMediaAsset` 之后，把图片从：

- 普通图片附件
- 临时 preview/original 直链
- 浏览器偶然缓存

升级成：

- `BlobMediaAssetDescriptor`
- preview/full/original 统一资产描述
- 长期本地保留
- P2P 协作分发
- `24 小时` 冷备窗口与自然死亡规则

第三切片完成后，图片不再只是“顺手缓存一下”，而是正式吃到与视频同等级的资产协议、恢复语义和长期保留语义。

### 这一切片为什么单独拆

图片和视频共享的是：

- `MediaAsset`
- `MediaCacheOwner`
- 恢复/等待/保留/做种语义

但图片不需要：

- `manifest + segments`
- 流媒体续播状态机

如果第三切片不单独拆，很容易把图片硬套成“假流媒体”，或者把视频恢复状态机继续做胖。

### 边界约束

- 不能为图片再造第二套 owner。
- 不能把图片强行做成 `HLS/DASH` 式伪流媒体。
- 不能继续保留“图片直链主路径 + BlobMediaAsset 新路径”长期双活。
- 必须复用：
  - `MediaCacheOwner`
  - `MediaSessionOwner` 的共享恢复语义
  - 已有图片查看器主路径
- 但可以为图片增加独立的 `preview_ready / backfilling_full_asset` 分支，不允许把视频分支污染成图片大杂烩。
