## 现实边界与完工标准

### 这份新 plan 为什么存在

旧的 [完全执行计划](E:/koko/docs/superpowers/plans/2026-04-13-跨端志愿者媒体资产与P2P分发协议完全执行-design.md) 已经把方向讲清楚，但还缺一个决定性东西：

1. 它没有把“视频主链升级到 `StreamingMediaAsset + HLS/DASH`”的**真实前置条件**单独拉出来；
2. 它默认后端可以直接开始产出 `manifest + segments`，但当前仓库既没有 `FFmpeg`，也没有 `Shaka Packager`，也没有明确打包产物目录、失败重试、产物回收与 `24 小时` 冷备窗口的契约；
3. 如果不先把这个前置条件钉死，后面最容易继续长成“旧附件直链 + 新 DTO + 新前端播放器”三层双活假升级。

这份新 plan 的职责就是：

- 补上第二切片的真实硬门槛；
- 把第一切片已完成部分纳入总验收矩阵；
- 明确最终什么叫“这份 spec 在当前仓库内已经完成”；
- 防止继续在旧链路外包新壳。

执行完这份 plan 后，才允许对照 [spec 第 18 节](E:/koko/docs/superpowers/specs/2026-04-13-跨端志愿者媒体资产与P2P分发协议-design.md) 宣称“当前仓库内的协议升级已完成”。必须同时满足：

1. 图片、视频、音频都已经进入统一 `MediaAsset` 协议表面；
2. 视频正式播放主链已切到 `StreamingMediaAsset + HLS/DASH`；
3. 图片已切到 `BlobMediaAsset`，拥有长期本地保留与 P2P 语义；
4. `Web` 在网络波动下具备持续播放、静默恢复、自动续做种；

7. 旧附件直链主链已经明显退场，只保留 `24 小时` 冷备与过渡引导角色；
8. 当前仓库内的 shared-core 已经是多壳中性表面，不再携带 Web 页面流程语义。

## 关键技术决策

### 决策 1：视频打包链采用 `FFmpeg + Shaka Packager`

依据官方资料：

- [Shaka Packager 文档](https://shaka-project.github.io/shaka-packager/html/tutorials/encoding.html) 明确说明：它负责 `HLS/DASH` 打包，不负责转码；
- [Shaka Packager DASH/HLS 教程](https://shaka-project.github.io/shaka-packager/html/tutorials/dash.html) 明确支持同时产出 DASH manifest 与 HLS playlist；
- [FFmpeg 官方文档](https://ffmpeg.org/documentation.html) 与 [formats 文档](https://ffmpeg.org/ffmpeg-formats.html) 说明它仍然是最成熟的通用转码/分段工具；
- [hls.js 官方说明](https://github.com/video-dev/hls.js/) 与 [p2p-media-loader 官方文档](https://novage.github.io/p2p-media-loader/docs/v2.2/) 都要求你先有标准 `HLS/DASH` 资产链。

因此这里不自研纯 Rust 打包器，不把 `mp4` crate 勉强拉成自制 packager：

- `FFmpeg`：负责转码、多码率派生、关键帧/GOP 对齐、首帧缩略图等；
- `Shaka Packager`：负责把已编码输出打包成 `manifest + segments`，并同时给 HLS/DASH 产物；
- Rust 代码只负责：
  - 调度这两类成熟工具；
  - 记录产物元数据；
  - 暴露稳定契约；
  - 执行 `24 小时` 冷备与自然死亡规则。

### 决策 2：`WebTorrent` 继续存在，但退到它擅长的位置

- 第一切片和图片资产主链继续大量复用现有 `WebTorrent` 文件级协作分发；
- 第二切片后，视频主链的正式播放器平面改成标准流媒体；
- `WebTorrent` 在视频路径里退到：
  - 现有冷启动/过渡窗口；
  - 旧附件链 `24 小时` 冷备阶段；
  - 非流媒体 blob 资产、热点图片、历史兼容链路；
- 分片级 P2P 由 `p2p-media-loader` 承担，不在 `WebTorrent` 外自研第二套分片引擎。

### 决策 3：Rust `.rs` 文件继续克制

当前 `src/` 下 Rust 文件总数仍在约束内。这个计划默认：

- 优先修改：
  - `src/契约.rs`
  - `src/用例.rs`
  - `src/房间外壳.rs`
  - `src/适配.rs`
  - `src/媒体协作分发.rs`
  - `src/领域/消息.rs`
- 只在确实 hold 不住边界时，允许新增最多 `1` 个领域文件：`src/领域/媒体资产.rs`；
- 总 `.rs` 文件数必须继续控制在 `21` 以内。
