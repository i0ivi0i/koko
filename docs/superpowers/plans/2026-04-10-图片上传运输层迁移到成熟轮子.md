# 图片上传运输层迁移到成熟轮子 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把当前图片上传从“前端 `XHR multipart` + 后端单请求全包处理”迁到“成熟上传运输层 + Rust 真相 finalize”，优先解决移动端兼容性和弱网恢复。

**Architecture:** 保留现有“上传成功不等于消息成立”的业务真相，不改消息主链和附件 owner 规则；把大文件运输、断点续传、浏览器恢复交给 `Uppy + tus` 生态，把 Rust 收口成 `finalize` 权威入口，只负责鉴权、解码、缩略图、落库和可见性。迁移分两段：先接成熟前端上传插件并引入 `tusd` 运输层，再让 Rust 接管 `finalize`，最后再退掉旧 `POST /api/attachments/image` 主路径。

**Tech Stack:** TypeScript、Lit、Uppy、`@uppy/tus`、`@uppy/compressor`、`@uppy/golden-retriever`、`@uppy/thumbnail-generator`、`heic2any`、Rust、Axum、`image`、`fast_image_resize`、`tusd`、Vitest、Cargo test、PowerShell `run.ps1`

## 迁移裁决

1. **先迁运输层，再动业务层。**  
   禁止把“换上传链”扩散成“重写消息主链”。

2. **Rust 仍然是附件真相唯一 owner。**  
   `tusd` 只负责运输，不负责落业务表。

3. **旧 `/api/attachments/image` 保留一小段回滚窗。**  
   只有当 `finalize` 全链路稳定后，才允许收旧路由。

4. **不在壳层新增第二套成功语义。**  
   浏览器上传完成只是“可 finalize”，Rust 返回 `attachment_id` 才是 `ready`。
