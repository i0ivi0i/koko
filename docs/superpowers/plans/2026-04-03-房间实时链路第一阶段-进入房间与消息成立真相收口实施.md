# 房间实时链路第一阶段: 进入房间与消息成立真相收口 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不重写传输栈、不扩散到完整补洞/多端同步的前提下，把“进入房间”“发送消息”“退出再重进”这条主链路收口到单一真相：快照给历史基线，`message_created` 给消息成立，`message_accepted` 只保留为命令结果。

**Architecture:** 本阶段只打一个热点簇，严格遵守 [审查维护.md](/E:/koko/审查维护.md) 的高风险门禁。`domain` 继续只承载业务消息语义，不引入 event position；`application / contract / adapter / shell` 负责把“消息成立真相”与“页面体验态”拆开。实现上复用现有 `socketioxide + Axum + SQLx + Dioxus` 链路，只新增最小共享契约、最小数据库位置锚点和最小壳层状态收口，不新造 manager / bridge / wrapper。

**Tech Stack:** Rust 2024, Axum, socketioxide, SQLx, PostgreSQL, Dioxus 0.7, cargo test, PowerShell 5

---

## 审查定位

- 这不是低风险改动。
- 原因：它会修改聊天热路径、共享 `contract`、数据库持久化投影、实时 adapter 和 Web 壳确认链。
- 实施前必须补齐独立复核，实施者不能自己判 `通过`。
- 本阶段非目标：
  - 不做完整 gap refill / offset backfill
  - 不做多端同步
  - 不替换 `socketioxide`
  - 不重写静态资源入口
  - 不新增第二套 realtime manager / helper / wrapper

## 分阶段边界

- 第一阶段只解决三件事：
  - 房间快照如何成为当前历史基线
  - 哪个事件才算消息真正成立
  - 退出再重进时怎样让旧结果失效
- 第一阶段允许引入最小共享锚点：`event_position`
- 第一阶段不实现“从某个 position 补齐缺口”的完整协议，只把位置先做成稳定真相

- [ ] **Step 4: 再在 `migrations/0004_message_event_positions.sql` 和 `src/store.rs` 落数据库真相**

迁移必须保证旧消息回填顺序稳定，不能依赖物理行顺序。建议步骤：

```sql
CREATE SEQUENCE IF NOT EXISTS messages_event_position_seq AS BIGINT;

ALTER TABLE messages
ADD COLUMN event_position BIGINT;

WITH ordered_messages AS (
    SELECT
        message_id,
        ROW_NUMBER() OVER (ORDER BY created_at ASC, message_id ASC) AS next_position
    FROM messages
)
UPDATE messages
SET event_position = ordered_messages.next_position
FROM ordered_messages
WHERE messages.message_id = ordered_messages.message_id;

SELECT setval(
    'messages_event_position_seq',
    COALESCE((SELECT MAX(event_position) FROM messages), 0),
    true
);

ALTER TABLE messages
ALTER COLUMN event_position SET DEFAULT nextval('messages_event_position_seq'),
ALTER COLUMN event_position SET NOT NULL;

CREATE UNIQUE INDEX IF NOT EXISTS idx_messages_event_position
    ON messages(event_position);
```
