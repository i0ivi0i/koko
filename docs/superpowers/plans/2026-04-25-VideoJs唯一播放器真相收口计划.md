# Video.js 唯一播放器真相收口 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` or `supxcode` when implementing this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把群聊时间线自动播放、点击进入全屏、退出全屏回到时间线，统一收口到同一颗 `Video.js v10` 播放器真相，彻底删除“当前 owner 走原生 `<video>` 直达、其他视频走查看器 `Video.js`”这条双轨分流。

**Architecture:** 本轮不是继续修补“当前 owner 直达全屏”的旁路，而是把它收回到唯一 canonical `Video.js v10` player/container。时间线、沉浸、全屏只是同一颗播放器在不同宿主槽位之间移动和升格；`playback.src / currentTime / autoplay owner / WebTorrent 主链` 继续只有一套业务真相，Web 壳只负责宿主槽位和用户手势接管，不再自行持有第二颗活播放器。

**Tech Stack:** TypeScript, Lit, existing media runtime / media sessions, `Video.js v10`, native Fullscreen API, Vitest, Playwright CLI / Chrome DevTools CLI.

所以本轮不是继续优化那条旁路，而是直接把它删掉，回到唯一真相：

**全应用只有一颗活着的 `Video.js v10` player/container。**

官方依据也支持这条方向：

1. Video.js 文档明确把 `Player.Container` 定义为播放器的物理表面，fullscreen 应该作用在 container 上，而不是到处临时再长一颗新 video。  
   来源：[media-container](https://videojs.org/docs/framework/html/reference/player-container)
2. Video.js fullscreen 特性明确写的是“先尝试 container，再回退到 media element”。  
   来源：[Fullscreen](https://videojs.org/docs/framework/html/reference/feature-fullscreen)
3. Video.js 的“打开 modal 时创建、关闭时 dispose”建议，适用于真正冷开的 modal player，不适用于当前已经热着的时间线播放器表面。  
   来源：[Player Workflows](https://videojs.org/guides/player-workflows/)

## 1. 最终裁决

这次实现前先把红线写死：

1. **禁止** 当前自动播 owner 继续走原生 `<video>` 直达全屏。
2. **禁止** 非当前 owner 继续走独立 `Video.js` 查看器，而当前 owner 走另一套播放器。
3. **禁止** 时间线里同时存在“活的原生播放 surface”和“活的 `Video.js` viewer surface”两套正式视频播放器真相。
4. **禁止** 为了兼容旧路径，保留“原生 `<video>` 直达全屏”和“`Video.js` 冷开查看器”双活并存。
5. **禁止** 把 DOM 元素、浏览器表面句柄或壳层细节塞进共享 `媒体查看器打开请求` 契约。
6. **禁止** 为了实现唯一 player 真相，再长一套新的 manager / service / registry 私有框架。
7. **禁止** 伤到 WebTorrent 主链、自动播放续播位置真相、帮助任务和做种语义。

允许且推荐的最终形态：

1. 时间线当前自动播 owner 使用同一颗 canonical `Video.js` player/container 挂到消息槽位。
2. 点击当前 owner 时，同一颗 player/container 直接 fullscreen。
3. 点击非当前 owner 时，同一颗 player 只是切换 attachment/source，并移动到目标宿主槽位或沉浸层。
4. 退出 fullscreen 后，同一颗 player 回到时间线宿主槽位，继续同一条 `currentTime`。

## 10. 自审

### 这份计划为什么不算过度设计

1. 它不是再造一个播放器框架，而是**删掉第二条播放器真相**。
2. 它不新增新的业务命令、不改共享 contract、不碰后端和 WebTorrent。
3. 它把复杂度集中在“同一颗 canonical player 的宿主迁移”，这是问题本身，不是额外附会。

### 这份计划为什么能防漂移

1. 先改 spec，再改测试，再改代码，先把边界钉死。
2. 当前 P0 根因已经写成失败测试，执行时不可能靠嘴说“现在统一了”。
3. 每一步都写了“禁止什么”，避免实现时又想顺手留兼容链。

### 这份计划的完成标准

1. 群聊消息流里的正式视频播放器只剩同一颗 `Video.js v10`。
