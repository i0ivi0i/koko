# 万人群聊浏览器零崩溃零闪烁 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不削弱 `WebTorrent` 协同分发主链、不打坏现有自动播放/自动暂停/无闪烁链路的前提下，把浏览器端媒体生命周期收口到严格预算内，让新用户、老用户、长时间滚动与大量收发媒体后都保持预览稳定、播放丝滑、浏览器不崩。

**Architecture:** 这轮不是继续补某个 UI 表面，而是直接收口三层 root cause：`房间消息窗.ts` 的可见窗口表面预算、`聊天媒体编排.ts` 的房间级媒体会话预算、`资产协作分发运行时.ts` 的零引用协作分发轻重态预算。正式播放继续只认一颗 canonical `Video.js v10` player；群体协作收益继续保留，但必须从前台重对象里脱身。

**Tech Stack:** TypeScript, Lit, `Video.js v10`, existing AppRuntime/media runtime actor chain, `WebTorrent`, Vitest, Playwright CLI / Chrome DevTools CLI, graphify.

### 0.3 这轮明确不做

1. 不改后端契约。
2. 不改 `WebTorrent` 正式字节主链。
3. 不长第二颗正式 `Video.js` player。
4. 不把消息流视频做回网页式小播放器。
5. 不用静态预览图兜底“像是有预览”。
6. 不靠“少帮后人”换浏览器稳定。
7. 不把 `WebTorrent/WebRTC` 正式会话硬搬进 `Web Worker` 逃避主线程预算。

### 0.4 这轮必须守住的禁止项

1. **禁止** 重新破坏今天已经修好的自动播放、自动暂停、进入 owner 平滑、离开 owner 平滑、viewer 归位平滑。
2. **禁止** 把“轻帮助态”误实现成“不再对 swarm 提供有效帮助”。
3. **禁止** 把“浏览器里少活”偷换成“房间历史和协作收益都别管了”。
4. **禁止** 为了减对象，在前端重新长第二套预览真相、第二套播放位置真相、第二套正式播放链。
5. **禁止** 用“测试绿了”代替浏览器真实烟测和对象预算复核。
6. **禁止** 在滚动热路径里靠 `getBoundingClientRect()` 或每卡片私有 scroll listener 维持可见性预算真相。
7. **禁止** 靠不断新建 `<video>` 元素去蹭 Safari/Chrome 自动播权限。

### 0.5 这轮必须服从的官方实现约束

1. `WebTorrent` 正式播放与正式图片来源继续只认官方 `client.createServer({ controller }) + file.streamTo()/streamURL` 路径；**禁止** 手搓第二条私有 raw range / 拉块播放主链。
2. 页面进入 `hidden` 时就要把它当成最后一个可靠收尾点：先持久化、先降到 `reduced/light-help`；只要浏览器仍允许页面继续运行且预算未越线，才允许保留轻帮助态；一旦进入 `frozen/suspended`，必须能关闭不该继续活着的 `WebRTC/WebSocket/轮询/重 reader`。
3. 群聊时间线里的非 owner 历史视频默认优先 `poster + preload="none|metadata" + lazy load + preview truth overlay`，而不是默认挂真实媒体源。
4. 可见性预算优先复用共享 `IntersectionObserver` / sentinel recycle；**禁止** 每个卡片自己在滚动里热算可见性。
5. 正式播放仍只认一颗 canonical player；Safari/macOS 的自动播授权按 media element 生效，所以 owner handoff 应继续复用同一正式元素，而不是新建第二颗正式视频元素。
6. 如果后续要用 `Web Worker`，只允许搬走纯计算；`WebRTC` 会话 owner、正式 `<video>`、以及业务真相仍必须留在主线程应用运行时。

  - **禁止** 继续只凭“当前房间 + 本地完整缓存”就把整房历史附件重新放大成活帮助任务。

  - 这轮它要负责把“前台重态预算”投影给编排层和协作层。

## 2. 风险闸门

### 闸门 A：不准只修数字，不修真因

如果某一轮实现只是把：

1. `overscan` 调小
2. 某个 timeout 拉长
3. 某个 warning 阈值调高

但没有回答“哪类对象不该继续活着、为什么现在还活着、该如何转成轻态”，默认视为失败。

### 闸门 B：不准让协作主链因为前台减负而变弱

允许：

1. 会话从重播放态转成轻帮助态
2. 零引用重 reader 退掉，但协作收益仍保留
3. hidden/background 只保留对群仍有价值的轻状态

禁止：

1. 直接不再补齐
2. 直接不再保租/不再帮助
3. 直接把群友之间的接力退回服务器兜底

### 闸门 C：不准为减负打坏预览和自动播

允许：

1. 减少真实 `<video>` 表面数量
2. 把 preview truth 继续保留在更轻的表达上
3. 让 owner 真接管发生在“稳定预览已就绪”之后

禁止：

1. 冷 `<video>` 先露出来，再慢慢 ready
2. owner 先成立，preview 后补齐
3. 旧 owner 刚退场，卡片就回冷底板或回占位

### 执行预算基线与采样口径

下面这组数字，是这轮实现的正式执行闸门。来源不是拍脑袋，而是：

1. `2026-04-26` 真实烟测已经观测到 `fresh newcomer previews = 15`、heavy 会话 `previews = 59 ~ 69`、renderer private memory `1GB+`、native child private memory `2GB` 级危险区。
2. 当前架构又已经明确：正式 canonical player 只能有 `1` 条，自动播 owner 只能有 `1` 条，窗口附近只允许少量 bridge/warm 表面。

规则：

1. 下面数字先作为 **v1 执行红线** 写进测试和烟测；如果当前基线已经超过它们，就让红测先红，作为本轮修复驱动力。
2. 在没有 fresh smoke 证据前，**禁止** 为了“先让测试过”临时放宽这些数字。
3. 若后续要调数字，必须附上新的浏览器烟测证据、影响范围和为什么旧数字不再成立。

#### 绝对红线

1. `activeFormalPlayerCount == 1`
2. `autoplayOwnerCount == 1`
3. `zeroRefHeavySessionCount == 0` 在 owner settled 后和 `reduced/suspended` 生命周期下都必须成立
4. `MaxListenersExceededWarning == 0`

#### 稳态/瞬态预算

1. `nearViewportPreviewVideoCount <= 6`
2. owner 交接 / viewer 归位 / fullscreen 退出这类短瞬态里，`nearViewportPreviewVideoCount <= 8`，且超额窗口不得超过 `1500ms`
3. `activeVideoSessionCount <= 12`
4. `activeMediaSessionCount <= 24`
5. `wholeFileHeavySessionCount <= 4`（前台 `normal` 策略下）
6. `zeroRefLightHelpSessionCount <= 16`

#### listener / reader / 内存红线

1. 同一 swarm session 的同类 runtime 监听器绑定必须保持单绑定：`data/close/error/wire/noPeers` 每类都只允许 `<= 1` 条当前 owner 路径监听
2. `zeroRefWholeFileReaderCount == 0` 在 owner settled 后和 `reduced/suspended` 生命周期下都必须成立
3. `rendererPrivateMemorySoftCap = 600MB`，`rendererPrivateMemoryHardCap = 800MB`
4. `chromeChildPrivateMemoryHardCap = 1400MB`
5. `jsHeapUsedSizeSoftCap = 160MB`，且连续 `3` 次采样 **禁止** 单向上升不回落
6. `steadyScrollLongAnimationFrameOver50Count == 0`
7. `steadyScrollLargeLayoutOrStyleOver40msCount == 0`

#### 采样口径

1. 窗口预算采样点：首屏稳定后、深滚动 `5` 屏后、连续上下滚动 `30s` 后、viewer 打开/关闭后、全屏退出归位后
2. 生命周期采样点：`normal`、`reduced`、`suspended`，以及浏览器 `hidden -> foreground restored`
3. 每轮烟测至少记录：`nearViewportPreviewVideoCount`、`activeVideoSessionCount`、`activeMediaSessionCount`、`wholeFileHeavySessionCount`、`zeroRefHeavySessionCount`、`zeroRefLightHelpSessionCount`、`zeroRefWholeFileReaderCount`、`MaxListenersExceededWarning` 次数、renderer/native child private memory、`steadyScrollLongAnimationFrameOver50Count`、`steadyScrollLargeLayoutOrStyleOver40msCount`
4. 如果现有代码还没有这些计数器，本轮先补预算投影和测试钩子，再补实现；**禁止** 用“现在测不出来”跳过预算门

## 8. 宏观自审

### 8.1 这份计划为什么是 root-cause plan，不是表面 plan

因为它直接对准了这次真实烟测已经证明的三条失控链：

1. 窗口附近挂太多真实媒体表面
2. 房间级活媒体会话集合过大
3. 零引用协作分发会话继续重保活

它没有再写“调参数”“补遮罩”“延迟一点揭帘”这种表面补丁。

### 8.2 这份计划为什么不会违背 WebTorrent 主链

因为它把“继续帮助后人”和“继续背前台重量”强制拆成两件事：

1. 协作收益继续留
2. 前台重量必须降

后续执行只要偏成“减少帮助本身”，就已经违背这份计划。

### 8.3 这份计划为什么不会把今天修好的 autoplay/no-flicker 又打坏

因为所有预算任务都把这些体验真相列成前置不变量：

1. 先稳预览，再自动播
2. 旧 owner 平滑退场
3. 新 owner 平滑进入
4. viewer / fullscreen / 归位链继续成立

后续只要出现“虽然更轻了，但先占一下再播、又开始闪了”，就是计划执行失败，不是 trade-off。

### 8.4 这份计划最重要的禁止项复述

1. **禁止** 把整房历史附件继续当成活媒体对象集合
2. **禁止** 把零引用“继续帮助”实现成前台重保活
3. **禁止** 为了减负打坏预览、自动播放、自动暂停和无闪烁
4. **禁止** 恢复第二正式播放链、第二播放器真相、第二预览真相
