# 万人群聊浏览器零崩溃零闪烁 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不削弱 `WebTorrent` 协同分发主链、不打坏现有自动播放/自动暂停/无闪烁链路的前提下，把浏览器端媒体生命周期收口到严格预算内，让新用户、老用户、长时间滚动与大量收发媒体后都保持预览稳定、播放丝滑、浏览器不崩。

**Architecture:** 这轮不是继续补某个 UI 表面，而是直接收口三层 root cause：`房间消息窗.ts` 的可见窗口表面预算、`聊天媒体编排.ts` 的房间级媒体会话预算、`资产协作分发运行时.ts` 的零引用协作分发轻重态预算。正式播放继续只认一颗 canonical `Video.js v10` player；群体协作收益继续保留，但必须从前台重对象里脱身。

**Tech Stack:** TypeScript, Lit, `Video.js v10`, existing AppRuntime/media runtime actor chain, `WebTorrent`, Vitest, Playwright CLI / Chrome DevTools CLI, graphify.

4. **禁止** 为了减对象，在前端重新长第二套预览真相、第二套播放位置真相、第二套正式播放链。

## 1. 文件地图与职责锁定

在拆任务之前，先把这轮真正允许动的边界锁死。

### 1.1 可见窗口与表面表达

- `frontend/房间消息窗.ts`
  - 负责消息列表可见窗口、preview overlay、canonical host、owner 进入/离开时的表面切换。
  - 这轮它必须收口“同屏附近到底允许活多少真实媒体表面”。
  - **禁止** 在这里顺手发明新的协作分发真相或第二播放器真相。

### 1.2 房间级媒体会话编排

- `frontend/聊天媒体编排.ts`
  - 负责当前房间媒体附件集合、媒体会话建立/释放、预览收敛、与 runtime/viewer 的编排。
  - 这轮它必须收口“当前房间全部附件 ≠ 当前活媒体会话集合”。
  - **禁止** 继续把整房历史附件直接当成活媒体对象表。

- `frontend/媒体/壳层/视频预览协作.ts`
  - 负责 preview truth 收敛。
  - 这轮它必须配合 `聊天媒体编排.ts` 明确：谁该预热、谁该 ready、谁该冷却。
  - **禁止** 让 `missing_source`、`loading`、`ready` 状态继续和正式播放表面混层。

### 1.3 协作分发与轻重态

- `frontend/媒体/资产协作分发运行时.ts`
  - 负责 swarm 会话、whole-file backfill、零引用保活、join ticket / heartbeat / listener 维持。
  - 这轮它必须收口“继续帮助后人”与“继续背前台重对象”之间的分层。
  - **禁止** 继续把零引用会话完整重保活。

- `frontend/媒体运行时.ts`
  - 负责 `heavyWorkPolicy`、inflight 预算、当前自动播 owner 等媒体运行时事实。
  - 这轮它要负责把“前台重态预算”投影给编排层和协作层。
  - **禁止** 在这里重写自动播播放真相。

### 1.4 唯一播放器真相

- `frontend/媒体/全局唯一播放器.ts`
  - 继续只负责唯一正式播放器 owner。
  - 这轮只允许配合窗口预算与 preview overlay 改 reveal/flush 节奏。
  - **禁止** 让它承担整房历史媒体生命周期管理。

## 2. 风险闸门

### 闸门 A：不准只修数字，不修真因

如果某一轮实现只是把：

1. `overscan` 调小
2. 某个 timeout 拉长
3. 某个 warning 阈值调高

但没有回答“哪类对象不该继续活着、为什么现在还活着、该如何转成轻态”，默认视为失败。

### 闸门 B：不准让协作主链因为前台减负而变弱

允许：

1. 会话从重播放态转成轻帮助态
2. 零引用重 reader 退掉，但协作收益仍保留
3. hidden/background 只保留对群仍有价值的轻状态

禁止：

1. 直接不再补齐
2. 直接不再保租/不再帮助
3. 直接把群友之间的接力退回服务器兜底

### 闸门 C：不准为减负打坏预览和自动播

允许：

1. 减少真实 `<video>` 表面数量
2. 把 preview truth 继续保留在更轻的表达上
3. 让 owner 真接管发生在“稳定预览已就绪”之后

禁止：

1. 冷 `<video>` 先露出来，再慢慢 ready
2. owner 先成立，preview 后补齐
3. 旧 owner 刚退场，卡片就回冷底板或回占位

## 8. 宏观自审

### 8.1 这份计划为什么是 root-cause plan，不是表面 plan

因为它直接对准了这次真实烟测已经证明的三条失控链：

1. 窗口附近挂太多真实媒体表面
2. 房间级活媒体会话集合过大
3. 零引用协作分发会话继续重保活

它没有再写“调参数”“补遮罩”“延迟一点揭帘”这种表面补丁。

### 8.2 这份计划为什么不会违背 WebTorrent 主链

因为它把“继续帮助后人”和“继续背前台重量”强制拆成两件事：

1. 协作收益继续留
2. 前台重量必须降

后续执行只要偏成“减少帮助本身”，就已经违背这份计划。

### 8.3 这份计划为什么不会把今天修好的 autoplay/no-flicker 又打坏

因为所有预算任务都把这些体验真相列成前置不变量：

1. 先稳预览，再自动播
2. 旧 owner 平滑退场
3. 新 owner 平滑进入
4. viewer / fullscreen / 归位链继续成立

后续只要出现“虽然更轻了，但先占一下再播、又开始闪了”，就是计划执行失败，不是 trade-off。

### 8.4 这份计划最重要的禁止项复述

1. **禁止** 把整房历史附件继续当成活媒体对象集合
2. **禁止** 把零引用“继续帮助”实现成前台重保活
3. **禁止** 为了减负打坏预览、自动播放、自动暂停和无闪烁
4. **禁止** 恢复第二正式播放链、第二播放器真相、第二预览真相
