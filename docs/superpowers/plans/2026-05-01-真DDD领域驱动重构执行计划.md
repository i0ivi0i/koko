# 真DDD领域驱动重构 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` when the host explicitly allows subagents, otherwise use `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 [真DDD领域驱动重构铁律](</E:/koko/docs/superpowers/specs/2026-05-01-真DDD领域驱动重构铁律.md:1>) 落成一条可执行、可回滚、可验证的重构路径，让后端唯一业务真相、前端唯一交互真相、模块化 owner、薄适配薄外壳和长期防漂移门禁真正进入代码，而不是只停留在目录设计。

**Architecture:** 这不是“大爆炸改目录”计划，而是“先冻结真相和基线，再建立新模块骨架，再把旧总控逻辑分批迁走，最后才做目录落位和旧路删除”的增量重构计划。后端先收 `usecase / contract / adapter / shell` 里的业务 owner，前端再收 `聊天应用内核.ts / 聊天壳.ts / 聊天媒体编排.ts` 里的平台污染和交互混控；整个过程中旧入口先缩成门面，不允许双活真相长期共存。

**Tech Stack:** Rust 稳定版、Axum、SQLx、socketioxide、Tokio、TypeScript 6.0.2、Lit 3、Vitest、WebTorrent 2.8、Video.js v10、Serena、graphify、`playwright-cli`、`browser-trace`。

## 0. 执行前硬门禁

### 0.1 范围裁决

这份 spec 涵盖后端、前端、媒体、恢复、实时多个表面，但它们并不是彼此独立的小项目。  
它们共用同一条“唯一真相轴”和同一组热点大文件，因此这里保留**一个分阶段总计划**，而不是拆成多份互相不知道上下游的子计划。

应该：

1. 把它当成一个按阶段推进的重构计划。
2. 每一阶段只收一类 owner 问题，完成再进下一阶段。

禁止：

1. 一边拆后端 owner，一边顺手重写前端媒体交互。
2. 一边拆前端平台污染，一边顺手改专项媒体主链裁决。

### 0.2 环境与纪律

本计划只能在当前 `main` 工作区执行。除非主人明确要求，禁止新开分支、禁止新开 worktree、禁止切到 WSL。

2. 看到专项文档就顺手改专项裁决；本计划只负责 owner、边界、落位和门禁。
