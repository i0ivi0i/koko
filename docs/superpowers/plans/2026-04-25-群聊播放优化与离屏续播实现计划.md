# 群聊播放优化与离屏续播 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在现有唯一播放器 owner 链上，把群聊消息流视频的离屏中断、回屏续播、当前自动播视频直达真全屏、消息流无控件和视觉连续性全部收口成一套稳定实现。

**Architecture:** 这轮不是再发明新的播放器状态机，而是把现有 `媒体运行时 -> 自动播协作 -> 全局唯一播放器 -> 房间消息窗/媒体查看器` 这条链上的边界补齐、红线补测、脏动作删掉。时间线继续只表达消息流表面，正式 live 播放继续只认同一颗 canonical `Video.js v10`；`WebTorrent` 主链、热会话复用、补齐和做种不动。

**Tech Stack:** TypeScript, Lit, `Video.js v10`, native Fullscreen API, existing media runtime/session coordination, Vitest, Playwright CLI / Chrome DevTools CLI.

---

## 0. 范围与前提

这份计划默认建立在下面两个事实之上：

1. [群聊播放优化与离屏续播 spec](/E:/koko/docs/superpowers/specs/2026-04-25-群聊播放优化与离屏续播.md) 已经批准。
2. 当前代码已经存在“唯一 canonical player”基础链路；本轮不是从零搭架构，而是把体验与边界收口。

这轮明确不做：

1. 不改后端契约。
2. 不重写 `WebTorrent` 主链。
3. 不引入第二颗正式 player。
4. 不把消息流视频做成带控件网页播放器。
5. 不为了“更丝滑”让同屏多条视频同时 live 解码。

这轮必须守住的禁止项：

1. **禁止** 新增第二套播放位置真相。
2. **禁止** 新增第二颗正式 `Video.js` player。
3. **禁止** 把当前 owner 点击全屏做回“消息窗直接抓原生 `<video>` requestFullscreen”。
4. **禁止** 为了修视觉问题削弱 `WebTorrent` 热会话复用、补齐、做种与帮助任务恢复。
5. **禁止** 把浏览器几何、DOM 私有字段或临时缓存上抬成业务真相。

## 2. 风险闸门

在真正分任务前，先把最容易漂移的三个点写死。

### 闸门 A：离屏中断与自然循环不能混

实现时只要发现“中断”和“自然 loop”分不清，就先停下来查证浏览器事件链。  
默认优先使用现有 `timeupdate / pause / loadedmetadata` 与位置表语义；**禁止** 一上来就发明新状态机。

只有在证据明确表明现有事件面无法区分两者时，才允许增加一个**壳层私有**信号。  
**禁止** 把这个信号做成第二张位置真相表或共享 contract 污染。

### 闸门 B：当前 owner 直达真全屏不能重新分裂播放器真相

允许：

1. 继续保留统一 viewer 打开入口
2. 在壳层内部区分“当前热 owner 升格”与“非当前视频切换”

禁止：

1. 恢复消息窗原生 `<video>` 直达全屏旁路
2. 把当前 owner 点击全屏做成冷开第二颗 player
3. 让消息流和 viewer 同时持有两条正式播放会话

### 闸门 C：视觉连续性不能靠第二颗 live 表面解决

允许：

1. 利用现有 `<video>` 暂停帧
2. 利用同源 `currentTime` 恢复
3. 利用 canonical host 迁移

禁止：

1. canvas 抓帧缓存
2. `lastFramePosterCache`
3. 每条消息一颗完整 `Video.js`
4. 时间线里第二颗 live `<video>`

## 8. 宏观自审

### 这份计划解决的真问题

它不是在“再做几个小手感优化”，而是在收口三个长期漂移源：

1. 离屏中断与自然循环混淆
2. 当前热 owner 点击后全屏路径脏动作过多
3. 消息流视觉连续性与唯一播放器真相再次分裂

### 这份计划为什么没有过度设计

1. 它不新增第二套运行时。
2. 它不引入新播放器框架。
3. 它不改共享 contract。
4. 它把复杂度限制在现有几个 owner 模块里收口，而不是再造私有基础设施。

### 这份计划最重要的三个验收信号

只有同时满足下面三条，才算这轮真的完成：

1. 用户滑出视频再滑回时，体感是“同一条会话继续”，不是“重新打开了一次”。
2. 用户点击当前自动播视频时，体感是“当前视频直接变成真全屏”，不是“先绕了一圈再进去”。
3. 工程上仍然只有一颗正式 canonical player，`WebTorrent` 热会话与主链没有被削弱。

### 这份计划最重要的禁止项复述

1. **禁止** 第二颗正式 player
2. **禁止** 第二张位置表
3. **禁止** 当前 owner 全屏回退成消息窗原生旁路
4. **禁止** 视觉连续性靠第二颗 live 表面解决
5. **禁止** 体验优化伤到 `WebTorrent`
