# 真DDD三满分 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 本项目默认在当前 `main` 上执行；除非主人明确要求，不另开分支、worktree 或平行线路；除非主人明确要求子代理，按 Inline Execution 使用 `superpowers:executing-plans`。

**Goal:** 执行完成后，把 `koko` 证明到 `DDD: 10/10`、`六边形边界: 10/10`、`简洁度: 10/10`，并能用新鲜测试、真实浏览器烟测、架构门禁和完成矩阵一起证明没有兼容链、转发壳、第二 owner、第二真相和冗余垃圾。

**Architecture:** 先把不能满分的事实变成测试和门禁，再删除旧入口、默认空实现和跨层借道，最后拆薄仍然过厚的真实 owner。后端继续按 `身份 / 房间 / 消息 / 媒体 / 恢复 / 实时` bounded context 收口；前端继续按 `房间 / 时间线 / 媒体播放会话 / 媒体查看器 / 协作分发 / 恢复 / 实时 / 总装` 收口。`domain / application` 只保留业务语言和不变量，`adapter / shell / 总装` 只翻译、编排、装配。

**Tech Stack:** Rust stable、Tokio、Axum、SQLx、socketioxide、TypeScript、Lit、XState、Vitest、Playwright CLI、browser-trace、graphify、Serena MCP。

## 4. Execution Order Rationale

1. **先门禁**：没有 RED gate，后续拆分很容易变成文件搬家。
2. **先 clippy**：warning 是未闭合事实，带 warning 拆架构会混淆验证。
3. **先删兼容链**：不能边拆边保留旧路径；旧路径会变成第二真相。
4. **先后端再前端**：前端不能发明业务成立性，必须先确认后端 owner 和契约边界。
5. **先壳再播放链**：消息窗、聊天壳、应用内核变薄后，播放会话的 owner 竞争才看得清。
6. **最后真实浏览器**：单元测试证明不变量，真实浏览器证明万人群聊体验没有被架构收口破坏。

## 5. Review Checkpoints
