# 接收者媒体极限秒开修复执行计划

## 目标

把 `specs/接收者媒体极限秒开修复.md` 落成可执行 TDD 计划，解决群聊接收者看到黑占位、媒体延迟启动、自动播冷启动的问题。

成功标准：

- **后端事件语义闭环**：`room_event` 对 ready 图片/视频附件必须携带权威 `distribution_hint`；缺少 `content_hash / swarm_id / torrent_info_hash / web_seed_until` 时不得提交媒体消息事件。
- **强种子确认闭环**：发布媒体消息前后不得把“已 ready 附件”广播成接收者可见但无可加入 swarm 的半成品；强种子启动失败必须有可追踪重试和日志。
- **接收端预热闭环**：接收 `room_event` 后立即触发 WebTorrent 预热；先取 locator/join ticket，再 announce tracker；禁止无票 announce。
- **自动播复用闭环**：inline autoplay/viewer/正式媒体会话复用同一协作分发 session，不再冷启动第二条链。
- **UI 投影闭环**：消息卡片只投影真实 runtime 状态，不显示黑占位，不靠假 loading 掩盖真实链路。
- **验证闭环**：单测、集成测试、前端测试、双浏览器真实烟测都覆盖同一条因果链。

## 当前事实

- `src/外壳/协议响应.rs::attachments_to_json` 已能在附件快照存在 `分发线索` 时输出 `distribution_hint`。
- `src/消息/适配.rs` 已有部分分发线索回填，但仍存在风险：提交后再查询、失败降级为空映射、缺元数据时仍可能提交事件。
- `src/消息/应用.rs::创建消息_异步` 当前只校验 owner/status/kind，没有把媒体分发线索作为提交前业务不变量。
- `src/实时/外壳.rs::handle_realtime_create_message` 只广播 `event_to_json(&event, None)`，所以权威事件本身必须携带完整附件快照。
- `src/外壳/协作分发做种.rs` 已有周期做种对账和 sidecar start 命令，但实时消息发布链还没有把“此条消息引用的媒体已进入强 seed 可用窗口”作为显式确认。
- `frontend/实时/应用.ts` 已有 `接收权威事件后副作用(events)` seam，适合在权威事件进入时间线后触发媒体预热，不需要改 socket 传输语义。
- `frontend/媒体/协作分发/应用.ts` 已是 locator owner 与 WebTorrent runtime 的应用层连接点，适合新增预热入口。
- `frontend/媒体/资产协作分发运行时.ts` 已支持 `prefetch` consumer，并保证 join ticket refresh 由 locator owner 统一刷新。
- `frontend/媒体/播放会话/应用.ts` 是消息窗口、自动播、查看器复用同一媒体 runtime 的 owner，适合新增“权威事件媒体预热”入口。

## 非目标

- 不把 `join_ticket` 广播到 `room_event`。
- 不把 WebTorrent tracker 信令塞进 socket.io。
- 不用 sender 端乐观 UI 作为主要修复。
- 不新增 HLS/DASH/CDN/range/原文件直链作为第二媒体真相。
- 不在 UI 层做黑卡美化补丁。
- 不新增第二套前端媒体状态机。

## 分层约束

- **domain**：只裁决消息和附件业务成立，不依赖 DB、网络、WebTorrent、UI。
- **application**：裁决“ready 媒体附件必须具备分发线索才能提交消息事件”。
- **contract**：保留 `distribution_hint` 为公共稳定事实；禁止放入 `join_ticket`。
- **adapter**：查询/落库/序列化分发线索，失败显式返回错误，不静默降级。
- **shell**：实时广播、强 seed sidecar 调用、浏览器预热副作用。

use bip_metainfo::{DirectAccessor, Metainfo, MetainfoBuilder, PieceLength};

pub fn 构造有效测试torrent元信息(seed: &str) -> (Vec<u8>, String, i32) {
    let shared_bytes = format!("koko-valid-test-media-{seed}").into_bytes();
    let file_name = format!("content-{seed}.mp4");
    let accessor = DirectAccessor::new(file_name.as_str(), shared_bytes.as_slice());
    let torrent_bytes = MetainfoBuilder::new()
        .set_private_flag(Some(true))
        .set_piece_length(PieceLength::OptBalanced)
        .build(1, accessor, |_| ())
        .expect("测试 torrent metainfo 必须能生成");
    let metainfo = Metainfo::from_bytes(torrent_bytes.as_slice())
        .expect("测试 torrent metainfo 必须能解析");
    (
        torrent_bytes,
        hex::encode(metainfo.info().info_hash().as_ref()),
        metainfo.info().piece_length() as i32,
    )
}

pub async fn 插入附件协作分发完整元数据记录(pool: &PgPool, 附件标识: &str) {

    .bind(piece_length)
    .execute(pool)

}

fn 校验媒体附件分发线索齐备(
    附件: &[domain::message::待发送附件],
    分发线索: &HashMap<String, contract::附件分发线索>,
) -> Result<(), contract::错误码> {
    for attachment in 附件 {
        match attachment.种类 {
            domain::message::附件种类::图片 | domain::message::附件种类::视频 => {
                let Some(hint) = 分发线索.get(&attachment.附件标识) else {
                    return Err(contract::错误码::附件未就绪);
                };
                if hint.content_hash.trim().is_empty()
                    || hint.swarm_id.trim().is_empty()
                    || hint.torrent_info_hash.trim().is_empty()
                    || hint.web_seed_until秒 <= 0
                {
                    return Err(contract::错误码::附件未就绪);
                }
            }
        }
    }
    Ok(())
}

### RED

新增单元测试覆盖：

- 从 `room_event` 的媒体附件分发线索收集待确认强种子的 `info_hash`。
- 缺 `torrent_info_hash` 的附件不会构造 sidecar start 命令。
- 强 seed start 失败时不会阻塞 `room_event` 广播，但会产生日志字段：
  - `application = "接收者媒体预热发布"`
  - `outcome = "seed_start_failed"`
  - `attachment_id`
  - `swarm_id`
  - `torrent_info_hash`

### GREEN

实现最小策略：

1. `创建消息_异步` 已阻止缺分发线索的新媒体事件。
2. `handle_realtime_create_message` 广播前 `tokio::spawn` 启动幂等强 seed start（非阻塞，不 await，给接收者一个时间领先量）。
3. `handle_realtime_create_message` 广播成功后 `tokio::spawn` 再触发一次幂等强 seed 确认，作为接收者进入 swarm 前后的兜底。
   - 两次 spawn 均不阻塞消息提交和 room_event 发出，保证广播零额外延迟。
4. 强 seed 确认不得把 `join_ticket` 放入 `room_event`。
5. 对 sidecar 调用保持幂等：同一 `info_hash` 多次 start 应安全。
