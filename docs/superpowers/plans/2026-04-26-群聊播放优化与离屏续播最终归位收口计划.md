# 群聊播放优化与离屏续播最终归位收口 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 [项目视频播放要求](/E:/koko/docs/superpowers/specs/2026-04-25-项目视频播放要求.md) 最后未收口的一处真相补齐：当前自动播视频进入 viewer / 真全屏后，退出归位必须继续复用同一颗 canonical `Video.js v10` player，而不是销毁后再按旧位置重建。

**Architecture:** 继续沿用 `房间消息窗 -> 聊天媒体编排 -> 媒体运行时 -> 全局唯一播放器 -> 媒体查看器` 这条既有 owner 链。修复不引入第二颗 player、不引入第二张位置表，也不让消息流或查看器长出私有恢复逻辑；只在“viewer 关闭到 inline 恢复”这条切换窗口里补一个受控的归位桥，让同一颗 canonical shell 能等到下一个时间线宿主再决定销毁还是复挂。

**Tech Stack:** TypeScript, Lit, `Video.js v10`, `media-chrome`, Fullscreen API, Vitest, Playwright CLI, Serena。

---

## 0. 这轮只修一个真实漏口

前一轮真实烟测已经证明：

1. 离屏续播成立
2. 消息流无控件成立
3. `inline -> viewer` 这一步是同一颗 canonical player
4. 退出 viewer 后时间轴基本连续

但还存在最后一个硬失败：

1. `viewer -> inline` 归位时，同一附件的 canonical `video` / `koko-video-skin` 对象身份发生变化
2. 这说明退出 viewer 时仍然先销毁了旧 shell，再等时间线 owner 回来后重建了一颗新的
3. 这违反 spec 第 `2.2`、`6.4`、`12` 节的“同一颗 canonical player 在消息流与真全屏之间迁移”

因此这轮最高裁决是：

1. **禁止** 把“时间连续”偷换成“同一颗 player”
2. **禁止** 新增 `viewerPendingShell` / `viewerPositionCache` / `restoreFromViewer` 之类第二张真相表
3. **禁止** 为了保对象身份而让旧 inline 画面在 viewer 关闭瞬间短暂闪回
4. **禁止** 破坏已经通过的离屏续播、inline 无控件、单 owner

## 1. 根因与目标文件

### 已确认根因

1. `房间消息窗.ts` 在 viewer 打开期间会把时间线 owner 传成 `null`
2. `全局唯一播放器.ts` 的 `同步时间线自动播(null)` 会立即清空 `当前时间线输入`
3. viewer 关闭时，`释放查看器并尝试归位时间线()` 发现没有可用时间线输入，于是立刻 `销毁当前播放器()`
4. 之后时间线 owner 再次出现时，只能重新创建 shell，因此对象身份变化

### 本轮会改动的文件

- `frontend/媒体/全局唯一播放器.ts`
  - 归位桥的唯一 owner
  - 负责“viewer 退场后短窗口等待时间线宿主恢复，否则再销毁”

- `frontend/媒体/媒体查看器.ts`
  - 只校准 viewer 关闭顺序，确保归位桥有机会吃到最新时间线宿主

- `frontend/tests/媒体查看器测试.spec.ts`
  - 新增 `viewer -> inline` 不重建 canonical shell 的红测

- `frontend/tests/房间消息窗媒体查看器测试.spec.ts`
  - 补一条时间线 owner 归位仍复用同一颗 canonical shell 的集成回归

- `frontend/tests/聊天壳测试.spec.ts`
  - 如果现有真实壳测试更靠近真实切换链路，就在这里补最后的对象复用断言

只在必要时补读：

- `frontend/房间消息窗.ts`
- `frontend/聊天媒体编排.ts`
- `frontend/媒体运行时.ts`

## 3. Task 2: 在全局唯一播放器里补“viewer 退场归位桥”

**Files:**
- Modify: `frontend/媒体/全局唯一播放器.ts`
- Verify: `frontend/媒体/媒体查看器.ts`

- [ ] **Step 1: 重新读取归位相关符号**

必须重新读透这些符号后再改：

1. `销毁当前播放器`
2. `应用时间线自动播表面`
3. `释放查看器并尝试归位时间线`
4. `同步时间线自动播`
5. `接管查看器`

- [ ] **Step 2: 引入最小的“待归位桥”状态，而不是第二张真相表**

允许的实现方向只有这一类：

1. viewer 关闭后，如果当前没有时间线输入，不要立刻销毁 shell
2. 先进入一个**极短、受控、可取消**的“等待下一个 inline 宿主同步”状态
3. 如果在这个窗口里时间线 owner 回来了，就直接把同一颗 shell 重新挂回去
4. 如果窗口结束后仍没有可用时间线宿主，再销毁

禁止：

1. 保存第二份业务位置真相
2. 把旧 inline host 强行保活成隐藏宿主
3. 加用户可感知的延时

- [ ] **Step 3: 保证桥只服务于“viewer -> inline”这一个窗口**

必须显式守住：

1. 正常 `同步时间线自动播(null)` 仍然可以释放 inline owner
2. 真正销毁聊天视图、切房、销毁查看器、宿主断连时，仍然可以干净销毁 shell
3. 只有“viewer 正在退场，而下一个 inline owner 即将回灌”的窗口，才允许暂缓销毁

- [ ] **Step 4: 需要时校准媒体查看器关闭顺序**

如果测试表明当前关闭顺序导致归位桥永远吃不到时间线更新，就只做最小校准：

1. 保持先回灌最新播放位置
2. 保持不引入第二套关闭逻辑
3. 只给全局唯一播放器留出吃到下一个时间线同步的机会
