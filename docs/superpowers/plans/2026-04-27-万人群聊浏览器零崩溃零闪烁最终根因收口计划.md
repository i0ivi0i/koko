# 万人群聊浏览器零崩溃零闪烁最终根因收口计划 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不削弱 `WebTorrent` 主链、不破坏现有自动播放/自动暂停/无闪烁体验的前提下，彻底完成 [2026-04-26-万人群聊浏览器零崩溃零闪烁 spec](/E:/koko/docs/superpowers/specs/2026-04-26-万人群聊浏览器零崩溃零闪烁.md)，让 `1234b` 这类重房间在 HTTPS 真机烟测下长期滚动、发送、观看后仍然不崩、不抖、不泄漏。

**Architecture:** 这轮不再围绕 `404/502` 表象补丁，而是直接收口三条根因链：`房间消息窗 -> 聊天应用内核 -> 聊天媒体编排` 的首轮窗口真相时序、`媒体定位/视频预览/媒体会话` 的不可取消请求风暴、`协作补齐协作/资产协作分发运行时` 的帮助链与零引用轻重态边界。所有实现都必须服从一个裁决：先有“当前窗口/当前 owner”真相，再允许启动重媒体对象与 locator/swarm 请求。

**Tech Stack:** TypeScript, Lit, `Video.js v10`, `WebTorrent`, fetch/`AbortController`, Vitest, Playwright CLI, Serena, graphify.

## 0. 2026-04-27 最新证据与根因裁决

### 0.0 动工前必须对齐短视频信息流预算模型

动手前必须先读 [短视频信息流丝滑播放与媒体预算模型-2026-04-27](/E:/koko/学习/整理笔记/短视频信息流丝滑播放与媒体预算模型-2026-04-27.md)，并把它压成这轮实现的执行口径：

1. 当前项重播放。
2. 邻近项轻预热。
3. 远处项冷表达。
4. 旧请求、旧 preview、旧 reader、旧 source 必须可取消。
5. `WebTorrent` 继续承担长期正式协作分发主链，但不能把前台重媒体对象长期绑死。

**禁止** 把 X / TikTok 式丝滑误解成“每条消息都挂真实 video / 每条视频都进重播放态 / 整房历史一起预热”。

### 0.1 这轮计划建立在 HTTPS 真烟测之上

`2026-04-27` 已重新验证：

1. `http://127.0.0.1:8080/` 可访问，但这只是本地 secure-context 特例。
2. `https.ps1` 启动后，`https://127.0.0.1/` 返回 `200`，Chrome 真正以 HTTPS 跑 `WebTorrent/WebRTC` 链路。
3. 正式验收必须包含 HTTPS 冒烟；**禁止** 再拿本地 HTTP 特例当成正式完成证明。

### 0.2 真实 smoke 暴露的新根因，不是旧结论的重复表述

在房间 `1234b` 的 3 页并发 HTTPS smoke 中，出现了下面这组事实：

1. 浏览器这轮没有直接崩，但仍出现 `locator 502`、大量 `/webtorrent/... 404`、`removeListener` 空引用、`wss://127.0.0.1/api/swarm/announce` 连接提前关闭。
2. `activeMediaSessionCount` 最终能回到 `24~25`，但 `inflightLocatorCount` 基线就到 `118/130`。
3. `viewerA/viewerB` 的 `longTaskCount` 在一次测试窗口内累积到 `457/472`。
4. `sender` 页 JS heap 到 `179MB`，而且不是单个附件在抖，是整房历史进入了抢跑链。

这说明当前真正问题不是“会话一直没释放”，而是：

1. **整房历史会在窗口真相到达前被错误预热。**
2. **后续即使会话数被裁回来了，早先已经放出去的 locator/preview/swarm 请求仍继续跑。**
3. **帮助链和 cached-help 恢复还会继续把过宽的附件集合重新拉活。**

### 0.3 最高根因裁决

后续所有编码和评审都必须围绕下面 4 条做：

1. **禁止** 在没有 `room-media-window-observed` 真相前，把“整房消息附件”当成当前活媒体窗口。
2. **禁止** 在活窗口已经缩回后，仍让旧代次 locator/preview/bootstrap 请求继续跑完。
3. **禁止** 让 `协作补齐协作.ts` 只凭“当前房间 + 本地完整缓存”重新放大帮助链。
4. **禁止** 用调大阈值、延长 timeout、忽略 warning 的方式掩盖上面 3 条。
5. **禁止** 把“短视频信息流丝滑”偷换成“更多重媒体对象同时活着”；正确模型只能是当前重播放、邻近轻预热、远处冷表达。

## 1. 正式预算与验收红线

### 1.1 会话/表面预算

1. `activeFormalPlayerCount == 1`
2. `autoplayOwnerCount == 1`
3. `nearViewportPreviewVideoCount <= 6`
4. owner handoff / viewer 归位瞬态允许 `nearViewportPreviewVideoCount <= 8`，但超额窗口 `<= 1500ms`
5. `activeVideoSessionCount <= 12`
6. `activeMediaSessionCount <= 24`
7. `wholeFileHeavySessionCount <= 4`
8. `zeroRefHeavySessionCount == 0`
9. `zeroRefLightHelpSessionCount <= 16`
10. `zeroRefWholeFileReaderCount == 0`

### 1.2 请求/错误预算

1. 首屏稳定后 `inflightLocatorCount <= 8`
2. 深滚动/切换瞬态允许 `inflightLocatorCount <= 16`，并且必须在 `1500ms` 内回落
3. `locator 5xx` 次数 `== 0`
4. `/webtorrent/... 404` 次数 `== 0`
5. `MaxListenersExceededWarning == 0`
6. `TypeError removeListener null` 次数 `== 0`

### 1.3 长任务/内存预算

1. `steadyScrollLongAnimationFrameOver50Delta == 0`
2. `steadyScrollLargeLayoutOrStyleOver40msDelta == 0`
3. `jsHeapUsedSizeSoftCap = 160MB`
4. `rendererPrivateMemorySoftCap = 600MB`
5. `rendererPrivateMemoryHardCap = 800MB`
6. `chromeChildPrivateMemoryHardCap = 1400MB`

### 1.4 采样口径

必须固定采这 5 个点：

1. newcomer 首屏稳定后
2. 深滚动 `5` 屏后
3. 连续上下滚动 `30s` 后
4. viewer 打开/关闭后
5. `hidden -> foreground restored` 后
