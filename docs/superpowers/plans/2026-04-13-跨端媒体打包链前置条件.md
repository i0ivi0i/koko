## 1. 为什么这份前置条件文档必须先存在

第二切片的目标不是“给现有视频附件多包一层 DTO”，而是把视频正式切到：

- `StreamingMediaAsset`
- `manifest + segments`
- `HLS/DASH`
- `hls.js / Shaka Player + p2p-media-loader`

要做到这一点，后端必须先能稳定地产出标准流媒体资产。

当前仓库真实情况是：

1. 后端已经能接住原始视频上传；
2. 后端已经会在 `complete_media_upload()` 后写入原始对象、视频宽高和 `WebTorrent` 协作分发元数据；
3. 但后端还不会产出：
   - `master.m3u8`
   - `stream.mpd`
   - `init segment`
   - `segment template`
   - 多码率变体
4. 当前本机环境也没有：
   - `ffmpeg`
   - `packager`

如果跳过这份文档，直接进入第二切片编码，最容易发生两种漂移：

- 在原始附件链外面再包一层“看起来像流媒体”的字段，最后形成双主链；
- 为了赶进度，开始手搓纯 Rust packager、纯 Rust 分片器或第二套私有转码流程。

这两条路都违背 spec 和 `AGENTS.md`。

## 2. 为什么不能手搓纯 Rust packager

结论先放前面：当前第二切片不允许手搓纯 Rust 打包器。

原因很直接：

1. `FFmpeg` 已经是最成熟的通用转码与媒体预处理工具；
2. `Shaka Packager` 已经是成熟的 `HLS/DASH` 打包器；
3. `hls.js` 和 `p2p-media-loader` 都默认你已经有标准 `manifest + segments`；
4. 项目真正需要自己掌握的是：
   - 资产领域规则
   - `24 小时` 冷备窗口
   - 产物生命周期
   - 契约与恢复语义
5. 项目不需要自己掌握的是：
   - 编码器实现
   - HLS/DASH 打包算法
   - 分片格式细节
   - MSE 兼容矩阵

所以这里的正确边界是：

- Rust 代码负责调度、记录、验收、回收；
- 成熟媒体工具负责转码与打包。

## 3. 官方资料给出的稳定边界

### 3.1 `Shaka Packager` 负责打包，不负责转码

官方教程已经明确说了：

- 输入应当是已经编码好的媒体流；
- `Shaka Packager` 负责把输入打包为 `DASH/HLS` 资产；
- 它可以同时产出 `MPD` 和 `M3U8` 主入口。

这意味着：

- 转码和 GOP/关键帧对齐要在 `FFmpeg` 侧完成；
- 打包步骤由 `Shaka Packager` 接棒；
- Rust 代码不应该在这中间插入第三套私有打包语义。

### 3.2 `FFmpeg` 继续承担转码与预处理

官方文档和长期实践都说明：

- `FFmpeg` 适合做：
  - 码率派生
  - GOP 对齐
  - 音视频流整理
  - 首帧缩略图生成
- 但不要把它和业务规则混在一起。

所以 `FFmpeg` 在 `koko` 的角色应该是：

- 外部成熟工具；
- 被后端调度；
- 产物进入统一媒体资产目录；
- 失败回写到媒体资产状态机，而不是直接变成壳层逻辑。

### 3.3 `hls.js / p2p-media-loader` 需要标准资产链

官方资料给出的边界也很明确：

- `hls.js` 是 HLS 播放引擎，不会把一个任意 MP4 自动升级成完整 HLS 资产；
- `p2p-media-loader` 工作在标准分片流媒体链上，不负责替你生成分片。

所以第二切片必须先有标准流媒体资产，再谈播放器与 P2P 主链切换。

## 4. `koko` 当前真实阻塞证据

### 4.1 当前代码能做什么

从当前代码看：

- `prepare_media_upload()` 只创建 `prepared` 附件真相；
- `complete_media_upload()` 会：
  - 读取 Rustus 临时文件；
  - 写入 canonical 原始对象；
  - 提取图片缩略图或视频宽高；
  - 把附件状态升级成 `ready`；
  - 补写 `WebTorrent` 协作分发元数据与 torrent metainfo。

这说明当前已经有：

- 原始对象存储主链；
- `WebTorrent` 文件级协作分发主链；
- 图片缩略图处理；
- 视频元数据解析。

但还没有：

- 流媒体资产目录
- 打包任务调度
- 打包状态记录
- `manifest + segments` 查询契约
- HLS/DASH 播放主链

### 4.2 当前本机环境缺少关键二进制

2026-04-13 在当前工作机执行：

```powershell
ffmpeg -version
packager --version
```

结果都是：命令不存在。

这不是可忽略噪音，而是第二切片的真实 blocker：

- 现在可以继续写契约、状态机、调度骨架；
- 但如果不先补这两个外部工具，真正的标准流媒体产物链无法在本机被验证。

## 5. 推荐工具链组合

### 5.1 开发机

必须具备：

1. `ffmpeg`
2. `packager`（Shaka Packager CLI）
3. 当前 Rust / Node 工具链

推荐角色：

- 开发机负责本地验证小样本视频的转码与打包；
- 不负责长期保留测试产物；
- 产物目录可落在临时目录或测试专用目录。

### 5.2 CI

CI 必须具备：

1. 能执行 `ffmpeg`
2. 能执行 `packager`
3. 能跑 Rust 与 frontend 测试

CI 职责：

- 不是对大视频跑完整耗时回归；
- 而是对最小样本视频验证：
  - 命令能执行
  - 打包产物目录结构正确
  - `manifest` / `segment` 元数据落库正确
  - 失败分支测试可跑

### 5.3 部署环境

部署环境至少要区分两类：

1. API / realtime 运行环境
2. 媒体打包执行环境

可以是同一台机器，也可以不是；关键不是拓扑，而是边界：

- 打包执行环境负责消耗原始文件并产出标准流媒体资产；
- API 环境负责暴露契约与冷源；
- 两者都不能把页面/壳层语义倒灌进媒体资产规则。

## 6. 约束：转码和打包由谁负责

### 6.1 `FFmpeg` 负责

- 视频转码
- 音频转码
- 关键帧 / GOP 对齐
- 码率变体派生
- 必要的首帧缩略图或预览图生成

### 6.2 `Shaka Packager` 负责

- 生成 `DASH MPD`
- 生成 `HLS master playlist`
- 生成 `init segment`
- 生成 `media segments`
- 维护标准分片命名模板

### 6.3 Rust 代码负责

- 调度转码与打包命令
- 记录媒体资产状态
- 记录产物元数据
- 控制 `24 小时` 冷备窗口
- 决定何时允许自然死亡
- 暴露稳定共享契约
- 在失败时写回统一错误语义

## 7. 第一版固定命令模板

下面的命令模板是第二切片编码时的基线，不代表最终部署脚本必须一字不差照抄，但语义边界必须一致。

### 7.1 `FFmpeg` 转码模板

```bash
ffmpeg -i input.mp4 \
  -map 0:v:0 -map 0:a:0 \
  -c:v libx264 \
  -g 120 -keyint_min 120 -sc_threshold 0 \
  -c:a aac \
  -f mp4 output_720p.mp4
```

语义：

- 输入原始上传文件；
- 先产出对 HLS/DASH 友好的编码结果；
- 关键帧间距固定，避免分段后 seek 和恢复语义混乱。

### 7.2 `Shaka Packager` 打包模板

```bash
packager \
  in=output_720p.mp4,stream=audio,init_segment=audio/init.mp4,segment_template=audio/$Number$.m4s \
  in=output_720p.mp4,stream=video,init_segment=video_720/init.mp4,segment_template=video_720/$Number$.m4s \
  --mpd_output stream.mpd \
  --hls_master_playlist_output master.m3u8
```

语义：

- 输入已编码文件；
- 同时产出 DASH 和 HLS 主入口；
- segment 命名模板进入资产元数据记录，而不是散落在壳层。

## 8. 产物目录和生命周期约束

建议的资产目录语义：

```text
videos/{attachment_id}/
  original.mp4
  variants/
    720p.mp4
  hls/
    master.m3u8
    video_720/init.mp4
    video_720/1.m4s
  dash/
    stream.mpd
    audio/init.mp4
    audio/1.m4s
```

约束：

1. `original.mp4` 只保留 `24 小时`；
2. `hls/` 和 `dash/` 是正式主资产；
3. 打包失败不得污染 ready 附件主真相；
4. 打包成功后，前端主链只消费资产描述，不再消费 `original_url` 作为正式主链。

## 9. 失败、重试、清理边界

### 9.1 打包失败

打包失败时必须：

- 记录媒体资产状态为失败；
- 不把失败偷偷吞成“仍然 ready”；
- 不让前端误以为标准流媒体资产已经存在；
- 第一版允许继续退回旧冷备链，但必须带明确 `origin_role = cold_backup_only` 语义。

### 9.2 重试

重试属于应用层调度逻辑：

- 可以有限次重试；
- 不能在壳层或 HTTP handler 里散落 `retry/timer`; 
- 不能因为转码失败就在运行时路径里临时 shell-out 二进制。

### 9.3 清理

必须区分：

- 原始文件 `24 小时` 清理
- 流媒体正式资产长期保留
- 失败半成品清理
- 临时工作目录清理

这些都应由媒体资产 owner / 用例层编排，不交给前端猜测。

## 10. 第二切片开工门禁

只有下面这些条件都满足，第二切片才允许真正进入后端打包链编码：

1. 当前仓库内的 `MediaAsset` 契约骨架已经存在；
2. `ffmpeg -version` 能运行；
3. `packager --version` 能运行；
4. 已有一条最小样本视频的本地打包验证路径；
5. 打包失败如何落状态、如何回退、如何清理已经写清；
6. 没有人再尝试手搓纯 Rust packager。

## 11. 当前结论

当前这台机器上，第二切片的**环境前置条件还没满足**。

这不代表不能继续推进，而是代表：

- 现在可以继续做：
  - 统一媒体资产契约
  - `24 小时` 领域规则
  - 后端调度骨架
  - 前端资产入口与 owner 迁移
- 现在不能假装已经完成：
  - 本机可验证的 HLS/DASH 正式主链
  - `ffmpeg + packager` 真实打包回归

这条边界必须在编码前写死，不然第二切片一定继续漂。
