# 真DDD三满分全量执行计划 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Use `superpowers:subagent-driven-development` only if the owner explicitly authorizes subagents. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 `koko` 从“已有不少结构收口、但仍未达到真 DDD / Onion Explicit Architecture 满分”的状态，推进到可证明的 `DDD: 满分 / 六边形边界: 满分 / 简洁度: 满分`。

**Architecture:** 这次真正要收口的，不再只是旧根文件或表面 warning，而是四类还会继续回流屎山的结构点：同步/异步业务规则复制、总仓储壳、总编排壳、以及命名/公开表面/迁移壳这三类“第二入口”。执行顺序必须是：先让假满分自动失败，再用 TDD 依次收掉命名与公开表面、迁移壳、业务规则复制、总仓储壳、总编排壳，最后用全量验证、独立全仓复核、graphify 和 `1234b` 双浏览器真实烟测收口。

1. 不追求把所有 barrel 一次性清零。

4. 不追求为了“像架构”增加新的中间门面或抽象层。

### 1.3 防漂移规则

后续如果再次出现“还差一点”的结论，只允许来自三类新证据：

1. 新补的正式门禁失败；
2. 新发现的真实生产主链消费者；
3. 新的 graphify / 真实烟测反证。

禁止：

- 禁止把今天已经确认的 `总装` 命名残留、`frontend/媒体/index.ts`、四个 `契约.rs`、门禁覆盖盲区，留到实现后再当成“新发现问题”。
- 禁止 scope 漂移成“顺手把所有 barrel 都清零”或“顺手全仓改名”。
- 禁止把“当前不列为主缺口”误解成“以后永不复查”。
