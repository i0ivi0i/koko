## 0. 这次不是再修 owner 选举，而是修“旧 owner 退场表面”

上一轮已经把“高竖视频 dead zone 导致 owner 掉成 `null`”修掉了。  
现在真实房间 `1234b` 里还剩下的闪烁，不是 owner 不见了，而是旧 owner 退场时，时间线表面仍然按“冷退场”处理：

1. 旧卡片一失去 owner，就立刻撤掉 `.message-video-canonical-host`
2. 然后回退到 preview `<video>` 分支
3. 这张 preview `<video>` 还是新插入/新 load/新 seek
4. 用户肉眼就会看到“抽一下、闪一下、再停住”

所以这次的计划不是补视觉遮挡，不是再调阈值，也不是再抹 `loadstart` 症状。  
这次要收口的是真正根因：

**旧 owner 退场时，必须直接露出一张已经 warm 的暂停预览表面；禁止先拆 canonical，再新建 preview。**

---

## 1. 最终裁决

这次实现以这 6 条为最高裁决：

1. **禁止** 旧 owner 退场时新建一张 preview `<video>`。
2. **禁止** 旧 owner 仍在可见区内时，先撤 canonical host，再现场 `loadstart / loadedmetadata / seeking` 一张新 preview。
3. **禁止** 把“最新播放位置”只寄托在外层回灌 snapshot 上，导致退场这一拍拿到的还是旧时间。
4. **禁止** 为了修退场闪烁，再长第二颗正式播放器、第二条正式播放会话、第二套时间轴真相。
5. **禁止** 把 outgoing 修成“延迟销毁一点点看看”这类时间碰运气方案。
6. **必须** 让 owner 卡片在成为 owner 期间也持续保留同源、暂停、可复用的 preview `<video>` 表面；canonical 只做覆盖层，不做唯一可见底板。

一句话：

**进入 owner 时是“预览帧在下、canonical 覆盖到上面”；离开 owner 时是“canonical 拿走，底下那张已 warm 的 preview 直接露出来”。**

---

## 2. 根因收口

### 2.1 当前真正的 bug 链

真实浏览器冒烟已经证明：

1. 新 owner 进场时已经有 hidden stage + reveal gate
2. 旧 owner 退场时没有对应的 warm surface bridge
3. `renderMessageAttachments()` 对 owner/非 owner 走的是两棵不同 DOM 形态
4. 一旦失去 owner，旧卡片立即切回 preview 分支
5. 这棵 preview 分支会创建或重走自己的 `<video>` 加载链

所以：

1. 问题不在 `Video.js` 壳本身
2. 问题不在 viewer/fullscreen
3. 问题也不在“再多加一点防抖”
4. 问题就在**时间线消息卡片的可见表面模型**错了

### 2.2 正确模型

正确模型必须是：

1. preview `<video>` 是时间线卡片的稳定像素底板
2. canonical player 是 owner 期间覆盖在这张底板之上的 live 表面
3. owner 进入时，不删除底板，只新增/迁移覆盖层
4. owner 退出时，不新建底板，只拿走覆盖层

这才是“同一条消息卡片自己的像素连续性”。

## 3. 实施任务

### Task 1：先把退场回归写成红测

先补失败测试，禁止先改实现。

新增/收紧的测试至少包括：

1. 当前 owner 卡片在 canonical 已就绪后，仍然保留自己那张非 canonical preview `<video>`。
2. 两条视频 owner 交接时，旧 owner 退场后露出的 preview 节点必须是同一张旧 preview，不允许是新节点。
3. 旧 owner 退场时，如果本地刚 flush 了更近的播放位置，而外层 snapshot 还没回灌，露出的 preview 也必须读到这条更近位置。
4. 旧 owner 退场时，禁止退回独立 poster `<img>`。

测试文件：

- `frontend/tests/房间消息窗媒体查看器测试.spec.ts`

### Task 2：重构房间消息窗的时间线表面模型

目标：把时间线视频卡片从“owner 专属 DOM / non-owner 专属 DOM”改成“稳定 preview 底板 + 条件性 canonical 覆盖层”。

具体要求：

1. 只要这条附件已经有同源 video 预览源，默认都渲染 preview `<video>`。
2. 当前 owner 额外渲染 `.message-video-canonical-host` 覆盖在 preview 之上。
3. hidden stage 仍然保留，但它只是 incoming handoff 的后台预热宿主，不参与 outgoing 冷退场。
4. preview 节点必须在 owner 进入/退出前后保持复用，不能随分支切换被替换掉。

主要文件：

- `frontend/房间消息窗.ts`
- `frontend/聊天壳.ts`

### Task 3：补上同组件退场位置桥，但不制造第二真相

当前 `自动播位置上报记录` 只做节流，不参与恢复。  
这会导致退场这一拍如果 runtime snapshot 还慢一拍，底板 preview 虽然在，但时间可能还是旧的。

这一步要做的是：

1. 读取恢复位置时，同时比较：
   - 外层 `inlineAutoplayPositionByAttachmentId`
   - 本地 `自动播位置上报记录`
2. 只在“同 attachment、同源、且本地记录更新更晚”时，允许本地记录作为**同组件退场连续性桥**
3. **禁止** 把这张本地表升级成新的业务真相 owner；它只服务当前组件这一拍的平滑退场

主要文件：

- `frontend/房间消息窗.ts`

### Task 4：补样式与层级，确保覆盖层/底板关系稳定

目标不是美化，而是确保 DOM 同时存在 preview 与 canonical host 时不发生布局抖动。

要求：

1. `.message-video-preview-trigger` 继续做相对定位容器
2. `.message-video-preview` 保持尺寸底板
3. `.message-video-canonical-host` 明确成为绝对覆盖层
4. **禁止** 因为新增双层表面，让命中、圆角、裁剪、指示器层级错乱

主要文件：

- `frontend/聊天壳.ts`

### Task 5：真实浏览器重新验收

单测转绿不算结束。  
必须重新进真实房间 `1234b` 做滚动冒烟，确认：

1. 进入新 owner 不闪
2. 离开旧 owner 不闪
3. 旧 owner 退场时不出现新的 preview `loadstart / seeking`
4. 同屏仍然只有一颗正式 canonical player
5. 消息流仍然无控件

## 4. 风险与禁止项

### 4.1 明确禁止

1. **禁止** 在时间线里为 outgoing owner 再造第二颗 live player。
2. **禁止** 用 canvas/image screenshot 假装冻结旧画面。
3. **禁止** 再长一个“退场专用状态机”把业务真相拆开。
4. **禁止** 让 preview 底板在 owner 期间偷偷 autoplay。
5. **禁止** 因为要复用 preview 底板，就放宽成多视频 live 解码。

### 4.2 这次真正允许的窄变化

1. 允许 owner 卡片在 canonical 覆盖层下保留一张暂停 preview `<video>` 底板
2. 允许本地位置节流表在极窄范围内参与同组件退场连续性恢复
3. 允许补充样式层级，保证底板/覆盖层稳定共存

## 6. 计划自审

这份计划已经按这 5 条自审过：

1. **有没有只修表面？**  
   没有。这次直接改的是消息卡片的可见表面模型，不是再补一层遮挡。

2. **有没有长第二真相？**  
   没有。唯一正式播放器仍然只有一颗；本地位置桥只在同组件退场这一拍补 continuity，不升格成业务 owner。

3. **有没有靠时间碰运气？**  
   没有。计划没有引入新的 sleep/debounce/等待窗来掩盖问题。

4. **会不会为了平滑把 preview 变成第二颗 live player？**  
   不会。preview 仍然是暂停、无控件、非正式表面，只做底板。

5. **有没有覆盖真实验收而不只看单测？**  
   有。计划明确要求重新做真实房间 `1234b` 滚动冒烟，并检查 outgoing 退场事件链。
