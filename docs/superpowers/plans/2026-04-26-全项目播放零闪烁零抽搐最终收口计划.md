# 全项目播放零闪烁零抽搐最终收口 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` or `superpowers:subagent-driven-development` when splitting this work. 当前执行方式固定为 `Inline Execution`，不得只停留在分析。

**Goal:** 把 [项目视频播放要求](/E:/koko/docs/superpowers/specs/2026-04-25-项目视频播放要求.md) 里“任何播放都无闪烁、无抽搐、高流畅、高帧率”的最后一条主线收口：消息流滚动切换自动播 owner 时，唯一 canonical `Video.js v10` 播放器不得出现 `host 消失 -> 收到 null -> destroy -> 重新挂载` 的空窗链；同宿主重复同步也不得再触发 `video-player` 的无意义 remove/add。

**Architecture:** 继续沿用 `房间消息窗 -> 聊天媒体编排 -> 媒体运行时 -> 全局唯一播放器 -> VideoJs 播放器壳` 这条既有 owner 链，不新增第二颗 player，不新增第二张播放位置真相表，不新增“预加载 overlay / 临时隐藏播放器 / 备用宿主”之类第二套视觉表面。修复只允许发生在三处：`消息窗如何暴露当前 owner 的 canonical host`、`唯一播放器如何处理瞬时 host 变化`、`播放器壳如何避免同宿主重复重挂`。

**Tech Stack:** TypeScript, Lit, `Video.js v10`, `media-chrome`, Vitest, Playwright CLI, Serena。

---

## 0. 这轮不是“优化一下丝滑感”，而是补齐唯一播放器交接真相

真实浏览器冒烟已经证明当前抽搐链路是成立的：

1. 滚动切 owner 时，旧卡片先失去 canonical host。
2. 新卡片只有在 `inlineAutoplayPlaybackByAttachmentId` 已经回灌时才肯渲染 canonical host。
3. 于是中间会出现若干帧“两边都没有 canonical host”。
4. `房间消息窗.ts` 会把这个空窗翻译成 `同步时间线自动播(null)`。
5. `全局唯一播放器.ts` 再把这个 `null` 翻译成真实播放器退场。
6. 等新 host 出现后又重新挂回，肉眼看到的就是“闪一下、抽一下、再开始播”。

本轮最高裁决：

1. **禁止** 把“新 owner 还没拿到 autoplay playback”翻译成“当前没有 canonical surface”。
2. **禁止** 为了掩盖空窗，再长一颗临时 live `<video>`、第二颗 player、隐藏 overlay 或第二张位置表。
3. **禁止** 让同一宿主上的重复同步继续触发 `video-player` remove/add。
4. **禁止** 破坏已通过的约束：单 owner、单 player、离屏续播、inline 无控件、viewer/fullscreen 同壳迁移。

## 1. 已确认根因与目标文件

### 1.1 已确认根因

1. `frontend/房间消息窗.ts`
   - 当前 owner 只有在 `inlineAutoplayPlaybackByAttachmentId[attachmentId]` 已经存在 swarm 播放结果时，才渲染 `.message-video-canonical-host`。
   - owner 切换时，旧 host 会立刻撤掉，但新 host 会晚到一拍。

2. `frontend/房间消息窗.ts`
   - `同步时间线唯一播放器宿主()` 一旦找不到 host，就立刻上抛 `同步时间线自动播(null)`。
   - 这里把“交接中的短空窗”误报成了“当前没有 inline 表面”。

3. `frontend/媒体/全局唯一播放器.ts`
   - `同步时间线自动播(null)` 在非 viewer 归位桥场景下会直接销毁当前播放器。
   - 于是短空窗被放大成真实 destroy/recreate。

4. `frontend/媒体/videojs播放器壳.ts`
   - `挂载到宿主()` 对“已经挂在同一宿主”的情况没有 no-op 保护。
   - 只要上层多同步几次，同一个 `video-player` 也会被重复 append，继续放大 DOM mutation 和视觉抽搐。

### 1.2 本轮改动文件

- `frontend/房间消息窗.ts`
- `frontend/媒体/全局唯一播放器.ts`
- `frontend/媒体/videojs播放器壳.ts`
- `frontend/tests/房间消息窗媒体查看器测试.spec.ts`
- `frontend/tests/媒体查看器测试.spec.ts`
- `frontend/tests/videojs播放器壳测试.spec.ts`

只在必要时补读，不默认改：

- `frontend/媒体运行时.ts`
- `frontend/媒体/壳层/自动播协作.ts`
- `frontend/聊天媒体编排.ts`

## 3. Task 2：消息窗先把“新 owner host 不晚到”修对

**Files:**
- Modify: `frontend/房间消息窗.ts`

- [ ] **Step 1: 重新读取并收口 owner 卡片的 host 渲染条件**

必须重新对齐这几个变量的语义：

1. `inlineAutoplayPlayback`
2. `playbackTimelineVideoSrc`
3. `savedTimelineFrameSrc`
4. `previewVideoSrc`
5. `shouldRenderInlineVideo`

- [ ] **Step 2: 新 owner 只要已经有同文件可用预览源，就必须立刻暴露 canonical host**

目标语义：

1. 当前 owner 不再把“必须等 `inlineAutoplayPlayback` 到场”当成渲染 host 的前提。
2. 只要已有同文件预览源可承接同一条会话，就直接暴露 `.message-video-canonical-host`。
3. 后续 autoplay playback 如果补回更正式的 swarm 源，只允许走同一颗壳的 `同步(source)`，不允许再换主节点。

禁止：

1. 回退到独立 `<img>` / poster 节点再等新视频。
2. 因为等待 swarm 播放结果，把 owner 卡片降级成“暂时没有 canonical host”。

- [ ] **Step 3: 保持非 owner 仍然只有预览壳，不长第二套 live surface**

必须守住：

1. 只有当前 owner 渲染 canonical host。
2. 非 owner 继续是首帧/暂停帧/占位表达。
3. 不因为“想让切换更丝滑”而让两条视频同时持有 canonical host。

## 4. Task 3：唯一播放器把“短暂交接”当交接，不当销毁

**Files:**
- Modify: `frontend/媒体/全局唯一播放器.ts`

- [ ] **Step 1: 重新读取 `同步时间线自动播` 与 `应用时间线自动播表面`**

必须重新读透：

1. owner 变化时什么时候 flush/pause
2. `input === null` 时什么时候 destroy
3. `应用时间线自动播表面()` 对 `mountTarget` 的前置要求

- [ ] **Step 2: 只在“已知 owner 交接中的短空窗”里避免 destroy**

允许的最小修法只有这一类：

1. 如果消息窗这一拍只是让旧 host 消失、新 host 正在同一轮或下一轮出现，就不要把它升级成真实 destroy。
2. 允许唯一播放器短暂保留当前壳，等待下一次有效 inline host 输入。
3. 一旦新输入到达，直接迁移同一颗壳。

禁止：

1. 新建第二套 bridge state machine。
2. 存第二份 source / position / owner 真相。
3. 把正常的“真释放”也误拦住。

- [ ] **Step 3: 旧 owner 与新 owner 交接时，先迁移再退场，不要先退场再重建**

必须显式保证：

1. 当新 owner 立即可用时，旧 owner flush 后直接把同一颗壳迁到新 host。
2. 不能先把当前壳 destroy，再等新 host 回来。
3. 交接期间最多只允许 source/host 变化，不允许对象身份变化。

## 8. 完成标准

同时满足以下条件，才算这轮真的完工：

1. owner 切换时，消息流不再出现可见闪烁和抽搐。
2. 真实浏览器冒烟里，不再抓到 `canonicalConnected = false` 的可见空窗。
3. 同宿主重复同步不再引发 `video-player` 重复 remove/add。
4. inline / viewer / fullscreen 继续共享同一颗 canonical player。
5. 离屏续播、退出归位、inline 无控件、单 owner 相关旧测试全部继续为绿。
6. 不引入第二颗 player、第二套播放真相或新的冗余代码。
