# 群聊视频自动播放先闪烁再续播根因收口 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task in this session. Use `superpowers:subagent-driven-development` only when the owner explicitly permits parallel agents. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 真正修复群聊里“自动播放进入前先闪烁消失一瞬间，再开始自动续播”的 bug，保证新进房首轮上滑 `G -> F -> E -> D -> C -> B -> A` 时不再黑闪、不再先掉画面后续播。

**Architecture:** 这次不再把问题定义成单纯“冷路径首帧不够快”，而是收口成一个更底层的根因：自动播放热路径里仍然存在多张画面表面、多条字节读取路径、以及一条过早晋升 owner 的状态机路径在竞争同一张视频卡片。修复方向不是继续给 `poster / preview / frozen / canonical` 打补丁，而是把自动播放热路径减到只剩一个稳定可见表面槽，并且只允许“唯一 live video + 它自己的同源同帧 bridge”参与揭帘事务；同时把 `candidate -> pending -> owner` 晋升门禁改成“先有 committed live frame 或同源 bridge 证据，再允许揭帘/晋升”。

**Tech Stack:** TypeScript, Lit, Video.js v10, WebTorrent, Vitest, Playwright CLI, Chrome DevTools CLI, browser-trace, `requestVideoFrameCallback`, `HTMLMediaElement.play()`, `OffscreenCanvas`, `ImageBitmap`, GitNexus, Serena

## 为什么旧方案还不够

本轮新证据说明，上一轮修复没有真正把自动播放热路径收纯：

1. 当前时间线视频卡片仍然同时拥有这些表面能力：
   - `poster` 图片
   - `preview <video>`
   - `frozen frame <canvas>`
   - `canonical host`
   - `stage host`
   见 `E:\koko\frontend\房间消息窗\视频附件表面渲染.ts`
2. `poster` 仍来自 `playback.thumbnailUrl ?? attachment.posterSrc ?? 默认占位图`，它本质上是静态图片，不是暂停帧，也不是已播放帧。
   见 `E:\koko\frontend\房间消息窗\附件渲染.ts`
3. 冻结帧确实不是“瞎猜的图片”，而是从同一颗视频通过 `drawImage()` 抓到 `OffscreenCanvas / ImageBitmap / HTMLCanvasElement` 的内存投影。
   见 `E:\koko\frontend\房间消息窗\视频桥接帧.ts`
4. 前端仍保留 `/api/attachments/{attachmentId}/content?variant=original|thumbnail` 内容地址构造：
   - `E:\koko\frontend\平台\传输.ts`
   - `E:\koko\frontend\媒体\壳层\快照投影协作.ts`
   - `E:\koko\frontend\媒体\播放会话\应用.ts`
5. 更关键的是，真实新进房 trace 里仍能看到视频附件的 `/api/attachments/.../content?variant=original` 206 请求。这说明自动播放附近还没纯到只剩 WebTorrent live chain。
6. `E:\koko\frontend\媒体\运行时.ts` 里的 `提升稳定自动播Owner` / `记录自动播播放结果` 现在仍会在没有“已提交 live frame”硬证据时，把 `pending` 直接抬成 `owner`。
7. `E:\koko\frontend\媒体\播放会话\自动播候选预热.ts` 现在仍在对可见候选调用 `触发视频预览收敛(...visible_candidate)`；如果计划不强制改掉这条链，执行者很容易又把第二颗 `preview <video>` 接回热路径。

所以，本计划要解决的根因不是“bridge frame 质量不够高”，而是：

> 同一张自动播放视频卡片在进入续播前后，仍然有多张画面、多条字节路径、以及一条会过早晋升 owner 的状态机链同时争抢可见主位；上一轮只是减少了其中一部分空窗，没有消灭这场竞争本身。

## 官方依据

执行过程中碰到分歧，先回到这些官方资料，不靠印象：

- [MDN: `HTMLVideoElement.requestVideoFrameCallback()`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)
  - 关键事实：它是在新视频帧送到 compositor 时回调，比 `canplay / playing` 更接近“用户能看见帧”。
  - 但它只是 best effort，可能晚一个 v-sync，不能被神化成绝对同步点。
- [web.dev: `requestVideoFrameCallback`](https://web.dev/articles/requestvideoframecallback-rvfc?hl=en)
  - 关键事实：它和屏幕视频帧率尽量同步，但仍可能一帧偏晚；如果揭帘事务设计错了，仍会闪。
- [MDN: `HTMLVideoElement.poster`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/poster)
  - 关键事实：`poster` 只是“在没有视频数据可用时显示的图片”。
- [Video.js options](https://videojs.org/guides/options)
  - 关键事实：`poster` 是播放前图片；自动播放应该走 Video.js option / player API，不靠原生 attribute 自我安慰。
- [MDN: `HTMLMediaElement.play()`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play)
  - 关键事实：`play()` 返回 `Promise`，自动播放是否真的开始，必须看 promise 结果。
- [WebKit: New `<video>` Policies for iOS](https://webkit.org/blog/6784/new-video-policies-for-ios/)
  - 关键事实：`<video autoplay>` 只有在可见时才会开始播放；滚动出视口会暂停。可见性是浏览器事实，不是业务真相。
- [MDN: `CanvasRenderingContext2D.drawImage()`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage)
  - 关键事实：`HTMLVideoElement / ImageBitmap / OffscreenCanvas` 都能被画到 canvas 上，但 video 至少要 `readyState > 1`。
- [MDN: `OffscreenCanvas.transferToImageBitmap()`](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas/transferToImageBitmap)
  - 关键事实：`ImageBitmap` 是大图形资源，用完要消费或 `close()`，不能泄漏。
- [Video.js Player API](https://docs.videojs.com/player)
  - 关键事实：`currentTime()` 和 `dispose()` 是正式播放器生命周期能力，不应该被外层 UI 分支复制成第二套真相。

## 新根因模型

本计划采用下面这条根因模型，执行时必须先证实，再修复：

1. `Video.js v10` 不是“画面真相”，它只是播放器壳和 HTML5 tech 的生命周期封装。
2. 真正出像素的是浏览器的 `HTMLVideoElement + decoder + compositor`。
3. 当前自动播放热路径里，至少存在三类竞争：
   - **第二表面竞争**
     - `poster`
     - `preview video`
     - `frozen frame canvas`
     - `canonical host`
   - **第二字节路径竞争**
     - WebTorrent 正式视频链
     - `/api/attachments/.../content?variant=original|thumbnail` 内容地址链
   - **过早 owner 晋升竞争**
     - `candidate -> pending -> owner` 只按 settle / playback resolved 推进
     - live video 还没 committed frame，表面却已经准备揭帘
4. 只要这三类竞争还存在，继续加 guard、timeout、cover、warmup 只会掩盖局部窗口，不会消灭“闪一下再播”的根因。

因此后续修复的第一原则是：

> 自动播放热路径里，唯一允许参与可见揭帘的只剩两样东西：
> 1. 全局唯一 live canonical video
> 2. 从这颗 live video 抓下来的同源同帧只读 bridge

`poster`、`preview video`、`/api/attachments/.../content?variant=original|thumbnail` 都必须被排除出自动播放热路径。
`pending owner` 也不能只因为 settle timer 或 `play()` promise resolve 就被抬成正式 `owner`；它还必须先拿到同源 `committed live frame` 或可持续显示的 `bridge frame` 证据。

## 架构裁决

### 裁决 1：自动播放热路径禁用第二颗 `preview <video>`

`preview <video>` 可以继续作为**非自动播放、非 owner、静态预览阶段**的冷态组件存在；但一旦某个附件进入自动播放候选 / pending owner / settled owner 热路径，它就不能再参与可见揭帘。

热路径里只能是：

- `bridge`
- `live`

而不是：

- `poster -> preview video -> canonical`
- `poster -> preview video + canonical -> canonical`
- `frozen + preview video + canonical`

### 裁决 2：自动播放热路径禁用 HTTP `original/thumbnail` 内容地址

`/api/attachments/{id}/content?variant=original|thumbnail` 可以继续服务：

- 静态封面
- 冷态 idle 卡片
- 图片附件

但不能继续服务：

- 自动播放候选预热
- pending owner 揭帘
- settled owner 续播过渡

只要 trace 里在自动播放热路径还看到视频附件 `variant=original` 请求，就视为本轮未完成。

### 裁决 3：自动播放只认一个稳定可见槽位

`VideoSurfaceSlot` 必须是唯一对外可见主位。内部可以有：

- `idle_poster`
- `bridge_frame`
- `live_video`

但不能让用户看到多个主壳争抢可见位。

### 裁决 4：揭帘条件只认“frame committed”

禁止用这些弱信号直接揭帘：

- `loadedmetadata`
- `canplay`
- `playing`
- `currentTime > 0`

它们可以帮助预热，但不能单独证明“用户现在真的能看见目标帧”。

揭帘必须认：

- `requestVideoFrameCallback` 提交的当前目标帧事实
- 或严格 fallback：`readyState >= HAVE_CURRENT_DATA` 且同一 live 节点已经建立 committed 标记

### 裁决 5：`pending -> owner` 晋升必须晚于 committed live frame

禁止下面这种顺序：

- `visible candidate`
- `pending owner`
- settle timer 到点 / `play()` promise resolve
- 还没 committed frame 就把 host 揭开

允许的顺序必须是：

- `visible candidate`
- hidden canonical warmup
- 同源 bridge 或 canonical committed frame 成立
- `pending owner` 升为 `owner`
- 可见 live 揭帘

### 裁决 6：候选预热目标改成 hidden canonical / bridge，不再叫醒 preview 收敛链

`同步自动播候选预热()` 后续只能推动：

- hidden canonical source prepare
- target currentTime 对齐
- bridge capture / committed-frame readiness

不再允许它继续推动：

- `触发视频预览收敛(...visible_candidate)`
- 第二颗可见 `preview <video>` 的 ready/commit 事件

## 真实浏览器诊断脚本

执行阶段统一使用这段 shadow-DOM-aware 采样脚本，禁止再用只扫 `document.querySelectorAll("article")` 的旧脚本：

```js
const collectRoots = (root = document) => [
  root,
  ...Array.from(root.querySelectorAll("*")).flatMap((element) =>
    element.shadowRoot ? collectRoots(element.shadowRoot) : []
  ),
];

const roots = collectRoots();
const cards = roots.flatMap((root) =>
  Array.from(root.querySelectorAll(".message-video-card"))
);

return cards.map((card) => {
  const preview = card.querySelector("video.message-video-preview:not([data-canonical-player='true'])");
  const canonical = card.querySelector("video[data-canonical-player='true']");
  const host = card.querySelector(".message-video-canonical-host");
  const stageHost = card.querySelector(".message-video-canonical-stage-host");
  const poster = card.querySelector(".message-video-poster");
  const frozen = card.querySelector(".message-video-frozen-frame");

  return {
    attachmentId: card.getAttribute("data-attachment-id"),
    surfaces: [
      poster ? "poster" : null,
      preview ? "preview_video" : null,
      frozen ? "bridge" : null,
      host ? `canonical:${host.getAttribute("data-covered")}` : null,
    ].filter(Boolean),
    visibleSurfaceCount: [
      poster,
      preview,
      frozen,
      host?.getAttribute("data-covered") === "false" ? host : null,
    ].filter(Boolean).length,
    previewReadyState: preview?.readyState ?? null,
    previewPaused: preview?.paused ?? null,
    canonicalReadyState: canonical?.readyState ?? null,
    canonicalPaused: canonical?.paused ?? null,
    canonicalCurrentTime: canonical?.currentTime ?? null,
    canonicalSrc: canonical?.currentSrc || canonical?.getAttribute("src") || null,
    stageHostPresent: Boolean(stageHost),
  };
});
```

## 计划风险

1. **风险：切掉 `preview video` 后首屏静态体验变差**
   - 对策：只切自动播放热路径；idle 非候选阶段仍允许 poster。
2. **风险：错误切断 `/api/attachments/.../content` 伤到图片或查看器**
   - 对策：先 trace 分类，只切视频自动播热路径。
3. **风险：bridge 过严导致 reveal 太慢**
   - 对策：允许 bridge 来自 canonical live frame capture，但不允许来自 poster/thumbnail/original。
4. **风险：某些浏览器 `requestVideoFrameCallback` 不可靠**
   - 对策：保留严格 fallback，但 fallback 不能退化成 `playing` 事件即揭帘。
5. **风险：保留 `.message-video-preview` 这个 CSS/测试约定时，执行者误以为还可以保留第二颗 preview DOM**
   - 对策：计划内明确“class 可兼容，节点 owner 不可兼容”；测试要同时断言 `data-canonical-player='true'`。

## 明确不做

- 不新增第二颗正式播放器。
- 不让每张卡片长期保活一颗解码视频。
- 不恢复 HLS / DASH / 直链 / CDN 第二视频主链。
- 不拿 poster 冒充 paused frame。
- 不用 timeout / debounce 数字微调掩盖真正的 owner / surface / source 竞争。
- 不顺手重构无关媒体模块。
