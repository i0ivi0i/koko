# 群聊视频自动播放先闪烁再续播 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task in this session. Use `superpowers:subagent-driven-development` only when the owner explicitly permits parallel agents. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修复群聊视频在自动播放接管前“先闪烁/消失一瞬间，再开始续播”的问题，覆盖新进房首轮、快速滑动、退出重进三条真实体验路径。

**Architecture:** 根因不再只定义为“首帧冷路径慢”，而是两条底层生命周期竞争：快速滑动时自动播 owner 会短暂退成 `0`，让可见卡片回到全 `poster` 冷态；退出重进时房间消息窗把同源暖帧、reveal-ready 状态和播放器壳清得过狠，导致重进像重新加载。修复要把自动播放热路径收成一个“视觉租约”：旧 live/bridge 在新 live 已提交前继续兜住画面，同源短时重进复用受版本约束的暖状态，`poster` 只保留冷占位语义。

**Tech Stack:** TypeScript, Lit, TanStack Virtual, Video.js v10 thin shell, WebTorrent, Vitest, Playwright CLI, Chrome DevTools CLI, browser-trace, `requestVideoFrameCallback`, `HTMLMediaElement`, `OffscreenCanvas`, GitNexus, Serena

### 本轮补充漏洞审查

- **组件实例缓存漏洞**：如果短时暖状态只存在 `房间消息窗` 实例里，新进房创建的新实例拿不到旧状态，计划会变成纸面复用。暖状态 owner 必须落到组件实例外的单一仓库，优先收在 `时间线画面缓存.ts` 的模块级 owner 内，不另开第二真相。
- **虚拟列表卸载漏洞**：快滑时旧 owner 卡片可能已经被 TanStack Virtual 卸载；只保留旧播放器壳不等于还有可见画面。必须同时检查 active/pending/retained 附件是否被虚拟范围保留，必要时 pin 住 owner/pending 行，而不是扩大整个列表 overscan。
- **远距离快速甩动漏洞**：视觉租约不能把很远的旧视频继续显示在新视口里。租约只服务邻近 handoff；如果用户一次性甩到很远，旧画面必须释放，同时目标可见卡片必须通过 hidden warmup/bridge 承接。
- **第二群友视角漏洞**：发送者或当前浏览器过了，不代表其他群友新进房/快滑也过。验收必须加第二身份 fresh viewer。
- **图形资源泄漏漏洞**：短 TTL bridge 若保存 `ImageBitmap` / canvas，不显式 close/release，会把快滑修成内存和 GPU 压力问题。
- **采样误判漏洞**：`activeVideoCount=0` 可能漏算 hidden stage，也可能把 covered canonical 算成活视频。采样脚本必须区分 visible live、hidden stage、covered canonical、bridge、poster。

## 官方依据

- [MDN: `HTMLVideoElement.requestVideoFrameCallback()`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)
  - 该回调在新视频帧发送到 compositor 时触发，是揭开 live video 的主要证据。
- [web.dev: `requestVideoFrameCallback`](https://web.dev/articles/requestvideoframecallback-rvfc?hl=en)
  - 该 API 仍是 best effort，可能晚一个 vsync，所以不能把回调外的弱事件当作“已可见帧”。
- [MDN: `HTMLVideoElement.poster`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/poster)
  - `poster` 是无视频数据时显示的图片，不是暂停帧，也不是续播帧。
- [MDN: `HTMLMediaElement`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement)
  - `load()` 会让媒体进入 `emptied` 等重载状态；`playing/canplay` 也不能等同于已提交画面。
- [Video.js options](https://videojs.org/guides/options)
  - Video.js autoplay 不是保证；poster 是播放器展示层能力，不应拥有业务播放真相。
- [MDN: `CanvasRenderingContext2D.drawImage()`](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage)
  - 从 video 抓 bridge 帧必须等 video 至少有当前数据。
- [MDN: `OffscreenCanvas.transferToImageBitmap()`](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas/transferToImageBitmap)
  - bridge 帧是大图形资源，必须有清晰生命周期。
- [WebKit: New `<video>` Policies for iOS](https://webkit.org/blog/6784/new-video-policies-for-ios/)
  - 可见性会影响 autoplay；滚动进出视口不能被业务层简单翻译成“立即销毁/立即重建”。

## 根因模型

当前剩余 bug 由三件事叠加造成：

1. **快滑视觉租约太短**
   - 自动播候选、活媒体窗口、虚拟列表 DOM 宿主不是同一时钟。
   - 快速滑动时，候选可能连续几帧为空或目标 host 暂时不在 DOM。
   - 当前 runtime / singleton player 最多吸收很短窗口，最终会把 owner 清成 `null`。
   - 结果是唯一播放器退场，可见卡片回到 poster，一拍后新 owner 再接回来，用户看到抽搐。

2. **重进房暖状态清理过粗**
   - `disconnectedCallback()` 把画面缓存、reveal-ready、播放器宿主都当成组件私有垃圾清掉。
   - 但用户语义上是“退出房间再进同一个房间/同一批附件”，不是媒体主链永久作废。
   - 同源同版本的 bridge/warm frame 应该短时间保留，而不是立刻归零。

3. **`poster` 仍在热路径里兜底**
   - `poster` 可以是冷占位，但不能是自动续播桥。
   - 快滑时回到全 poster，本质上就是 live/bridge 租约失败后的降级。

一句话：这次要修的是 **live/bridge 视觉租约和短时重进暖状态生命周期**，不是再给 `poster`、`preview` 或 timeout 补一层遮羞布。

## 架构裁决

### 裁决 1：引入“视觉租约”，不是加长 timeout

新增或扩展已有自动播裁决语义时，不允许只把 `16ms` 改成更大数字。必须表达清楚：

- 当前是否有已播放 live owner。
- 新 pending 是否已有 stable bridge/live committed frame。
- 当前 owner 是否仍可用作一段短暂视觉租约。
- 释放原因是“真实离开生命周期”，还是“候选/DOM 一拍暂空”。

建议命名：

```ts
type 自动播视觉租约状态 =
  | { kind: "none" }
  | { kind: "retained_owner"; attachmentId: string; src: string; currentTime: number; expiresAt: number }
  | { kind: "bridge"; attachmentId: string; src: string; currentTime: number; expiresAt: number };
```

如果现有 `inlineAutoplayConsecutiveEmptyObservedCount` 足够承载，则不用新增类型；但测试必须能证明“快滑多帧空观测不会退成全 poster”。

### 裁决 2：短时同源重进保留暖状态

`disconnectedCallback()` 不能再无条件等同于“媒体生命周期永久结束”。执行时要区分：

- **组件卸载 / 同房短时重进**：允许保留短 TTL 的 bridge/warm frame/position。
- **房间切换 / 附件源变更 / sourceVersion 变更 / 媒体错误**：必须失效。
- **页面关闭 / 长时间后台 / heavyWorkPolicy 非 normal**：必须释放。

建议 TTL 初始值：`1500ms` 到 `3000ms`，必须写成语义常量，不允许散落魔法数字。

### 裁决 3：唯一播放器壳不因一拍 null 立刻冷重置

`Video.js` 壳仍只是 thin shell。时间线自动播的正式 video 不能因为快速滑动一拍 `null` 就进入 `remove src + load()` 冷重置。

允许：

- 暂停并停在 hidden/staged holder。
- 等下一条有效 owner 或旧 owner bridge 租约续上。

禁止：

- 因候选暂空立刻 destroy。
- 因 host 暂时不在 DOM 立刻 `load()`。
- 让 poster 替代 paused/live frame 成为热路径续播表面。

### 裁决 4：bridge 只能来自同源 live video

冻结帧和 bridge 是允许的，但它们必须来自同一正式视频源：

- 同 attachment 或同 source/content hash。
- 同 src/sourceVersion。
- video `readyState >= HAVE_CURRENT_DATA`。
- 通过 `drawImage()` 抓取前必须有非零 `videoWidth/videoHeight`。

禁止：

- poster/thumbnail 冒充 bridge。
- `/api/attachments/.../content?variant=original` 冒充热路径视频源。
- 旧 sourceVersion 的 bridge 跨版本复用。

### 裁决 5：快滑验收优先级高于慢滑

上一轮慢滑已经改善，新的计划必须把快滑作为 RED 测试和真实烟测第一类场景。只证明逐条慢滑通过，不算完成。

### 裁决 6：短时暖状态 owner 不得绑死在组件实例上

重进房会创建新 `房间消息窗` 实例时，旧实例字段自然丢失。因此短时暖状态不能只存在 `this.时间线画面缓存Owner` 的实例字段里。

执行优先级：

1. 优先在 `时间线画面缓存.ts` 内建立模块级、受 TTL 和 sourceVersion 约束的单一暖状态仓库。
2. `房间消息窗` 只调用导出/导入/释放端口，不直接拥有跨实例真相。
3. 不新建 localStorage / IndexedDB 持久缓存；这个状态只服务秒级短时重进，不是恢复系统。

### 裁决 7：虚拟列表必须 pin 活跃媒体行，不能靠扩大 overscan

快滑闪烁可能来自 DOM host 被虚拟列表提前卸载。修复不能粗暴扩大所有 overscan，那会放大万人群聊长列表成本。

允许：

- 把当前 owner、pending owner、retained lease 附件所在消息行加入虚拟范围 pin 集合。
- pin 只保留少量媒体行，并且随 source/owner 失效立即释放。

禁止：

- 把 `overscan` 大幅改大。
- 让已远离视口的旧 owner 无限保活。

### 裁决 8：视觉租约必须有几何边界

视觉租约只服务“相邻视频交接”和“host 一拍暂空”。如果用户一次快速甩过多条消息，旧 owner 不应继续冒充当前视口内容。

要求：

- 近距离 handoff：旧 owner/bridge 兜住直到新 owner 有 committed frame。
- 远距离 jump：旧 owner 释放，目标卡片走 hidden warmup/bridge，不显示旧视频。
- 测试必须覆盖这两类，不能只测一种快滑。

### 裁决 9：bridge 资源生命周期是修复的一部分

如果使用 `ImageBitmap`，过期或失效时必须 `close()`。如果使用 canvas，也要清掉引用，让 GC 能释放像素内存。

验收必须证明：

- TTL 过期释放。
- sourceVersion 变化释放。
- 房间切换释放。
- 页面隐藏/冻结超过阈值释放。

### 裁决 10：第二群友体验是完成标准

群聊视频不是单人页面。最终烟测必须包含第二身份 fresh viewer，验证对方新进房后也不会首轮慢滑/快滑闪烁。
