# 群聊IM DDD稳定骨架 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 从空仓库重建一个“纯 Rust 后端 + 纯 TypeScript 前端”的群聊 IM 第一阶段闭环，同时把 DDD 边界、Unix 风格、日志门禁、测试门禁和禁止条款一起落地，确保后续迭代不再滑回混沌。

**Architecture:** 先打地基，再立骨架，再接主链，最后封壳。地基包括工具链、目录、契约、日志、配置、数据库真相；骨架包括领域、用例、adapter 和测试总线；主链先打通匿名会话、进房/建房、快照、发送消息、增量事件和补洞；最后再封前台壳、后台壳和 run 链路。整个实施顺序必须保持“权威真相先成立，壳层最后接入”的方向。

**Tech Stack:** Rust stable、Tokio、Axum、Socketioxide、SQLx、PostgreSQL、Tracing、TypeScript、Lit、socket.io-client、Vitest/Playwright（或等价前端测试）、PowerShell 启动脚本。

## 施工顺序

### 施工原则

1. 先地基，后骨架  
   不先打地基就接 UI，会把真相和外壳重新混在一起。

2. 先真相，后交互  
   先让领域、用例、持久化和事件位置成立，再接页面行为。

3. 先闭环，后铺量  
   先打通匿名会话 -> 进房/建房 -> 快照 -> 发消息 -> 实时接收 -> 补洞，后续能力都挂在这条主链上。

4. 先测试和日志，后宣称完成  
   每层都要能靠测试证明，每条主链都要能靠日志追证据。

## 执行建议

推荐执行方式：

1. 一次只做一个 Task
2. 严格 TDD
3. 每个 Task 单独提交
4. 每个 Task 做完后都跑对应验证
5. 若发现 spec 与实际实现冲突，先停下来修 spec，再继续实现
