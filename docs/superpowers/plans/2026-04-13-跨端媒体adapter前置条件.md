# 跨端媒体 Adapter 前置条件

日期：2026-04-13  
状态：Draft  
适用范围：`Web` 已落地后的 `iOS / Android / Desktop / CLI` 接入前置条件。  

## 1. 这份文档为什么存在

当前仓库已经把 shared-core 收到多壳中性表面，但实体 adapter 还没有代码仓落点。  
这份文档只回答一件事：以后各端接入时，必须先满足什么，才能不把 `Web` 页面流程重新倒灌进共享协议。

## 2. 已经稳定下来的共享表面

未来各端只能直接消费这些稳定语义：

1. `MediaAssetDescriptor`
2. `StreamingMediaAssetDescriptor`
3. `BlobMediaAssetDescriptor`
4. `ManifestDescriptor`
5. `VariantDescriptor`
6. `SwarmDescriptor`
7. `OriginDescriptor`
8. `MediaSessionOwner` 的恢复状态语义
9. `MediaCacheOwner` 的本地完整度语义

这些表面现在已经明确不包含：

1. `toast_text`
2. `panelMode`
3. `drawer_open`
4. `viewmodel`
5. `presenter`
6. 任何只对 `Web` 页面或 `DOM` 成立的状态字段

## 3. 各端落地前必须确认的前置条件

### 3.1 iOS / Android

1. 原生播放器必须能消费 `HLS` 主链。
2. 端侧缓存层必须能表达“preview/full/original”与“manifest/origin/distribution”这两类资产真相。
3. 后台恢复能力只能翻译成统一 `MediaSessionOwner` 信号，不能自己再造一套恢复状态枚举。
4. 若引入端上分片级 P2P 轮子，必须只接到 `SwarmDescriptor` 上，不能改 shared-core 字段形状。

### 3.2 Desktop

1. 必须直接消费同一份 `MediaAsset` 契约，而不是另造桌面专属 DTO。
2. 本地文件系统缓存如果比 `Web` 更强，也只能增强 `MediaCacheOwner` 实现，不能改变保留规则。
3. Headless 做种或后台做种是 runtime 能力，不是 shared-core 新真相。

### 3.3 CLI

1. CLI 只允许消费 command/query/event/snapshot/error code。
2. CLI 可以不实现图片/视频 UI，但不能定义不同的“完整资产”“等待 peer”“恢复成功”语义。
3. 若 CLI 要做后台分发节点，也只能复用 `SwarmDescriptor + MediaCacheOwner` 语义。

## 4. 禁止事项

未来任何端接入时，下面这些都算退化：

1. 为某个壳新增只服务本壳的 contract 字段。
2. 在 adapter 里定义新的恢复状态枚举。
3. 让某个壳重新把原始附件直链拔回正式主链。
4. 让某个壳把本地缓存键、Presenter 字段、页面文案写进 shared-core。

## 5. 当前仓库内已经完成的准备

1. 视频主链已切到标准流媒体 manifest 入口。
2. 图片主链已切到 `BlobMediaAsset`。
3. `WebTorrent`、`p2p-media-loader`、`hls.js`、`Workbox` 等成熟轮子边界已经就位。
4. shared-core 已通过门禁测试，明确不暴露壳层私货。

## 6. 当前仓库内还不会伪造的东西

这份仓库当前不会假装已经有：

1. `ios/`
2. `android/`
3. `desktop/`
4. `cli/`

这些实体 adapter 未来可以按同一份 shared-core 接上，但不在当前仓库里硬造目录和假代码。
