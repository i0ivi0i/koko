# 已读锚点稳定化与首屏停靠 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把聊天房间前端的“首屏停靠、已读候选采样、已读提交时机、新消息不抢视角”收成一条稳定的 IM 逻辑链，让用户久未进房、实时消息不断涌入、刷新重连、补历史这些场景下都能停在正确位置并稳定推进已读。

**Architecture:** 保持后端 `last_read_event_position / first_unread_event_position / latest_event_position` 作为唯一阅读真相，不改 Rust 领域与用例裁决；前端只在现有 [frontend/房间内核.ts](/E:/koko/frontend/房间内核.ts)、[frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts)、[frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 三处收口“视口模式 + 候选已读 + 首屏稳定完成条件”。整套实现坚持 TDD，先补失败测试，再做最小实现，再跑回归与真实链路测试。

**Tech Stack:** TypeScript, Lit 3, XState 5, socket.io-client 4.x, Vitest, Happy DOM, esbuild

## 风险提示

1. 这次最大的风险不是“代码写不出来”，而是把“视口观测”重新写成“前端第二套阅读真相”。
2. 首屏停靠如果仍然允许“试过一次就结案”，后面刷新、长消息、动态布局场景还会继续抖。

4. 真实链路测试如果只测“有没有收到消息”，不测“视角有没有被抢走”，这次专项等于没守住。
