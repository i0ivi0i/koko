# Web 群聊视频单一真相与视口自动播 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修掉群聊视频的 3 个稳定复现 bug，并把 Web 端视频链路收口成“静态封面唯一真相 + 正式播放器唯一 Video.js 壳 + 消息流同屏唯一自动播 owner”。

**Architecture:** 这不是三个分散补丁，而是一条纵向能力切片：后端复用既有 `thumbnail_storage_key` 与受控内容路由，给视频补稳定静态封面真相；前端把消息卡片默认态收口成纯封面，不再靠 `original#t=0.1` 或常驻 `<video>` 兜底；自动播继续复用同一个 `media owner / source resolver`，但按 `surface` 区分“正式查看器”和“消息流自动播”的可播放源选择，不新增第二套资产、第二套播放器壳或第二套恢复逻辑。

**Tech Stack:** Rust, Axum, SQLx, object_store, ffmpeg, shaka-packager, TypeScript, Lit, Vitest, Video.js v10, hls.js, Chrome Stable

---

## 范围裁决

这份计划只做一个能力切片，不拆成两份子计划：

1. `preview_asset`、消息快照、locator、消息卡片、查看器、自动播 owner 共用同一条真相链，拆开会让迁移顺序失真。
2. 本期不改 P2P / WebTorrent 的领域语义，只改它们在 Web 视频体验里的消费方式。
3. 本期不生成 `motion_url` 或额外 preview clip，只补静态封面。

## 文件结构与职责锁定

- `src/流媒体打包.rs`
  - 继续复用 `ffmpeg + ffprobe + shaka-packager`。
  - 在同一条视频 complete 打包链里顺手抽一张静态封面图，不新增第二条异步转码链。
- `src/媒体上传外壳.rs`
  - 继续做 `complete` 主链 owner。
  - 把视频静态封面写入既有 `thumbnail_storage_key`，并把 `preview_asset` 投影到 ready 响应。
- `src/用例.rs`
  - `媒体定位结果.允许缩略图` 改为基于附件真相，而不是“只有图片才允许”的硬编码。
- `src/契约.rs`
  - 定义共享 `preview_asset` 契约。
  - `附件快照` 与 `locator` 共享同一套 preview 语义。
- `src/消息事件适配.rs`
  - 批量组装消息附件时，把 preview 真相带进共享事件，而不是只带宽高。
- `src/外壳.rs`
  - `event_to_json / attachments_to_json` 负责把 `preview_asset` 投影到统一传输 JSON。
- `src/房间外壳.rs`
  - 继续承接 `snapshot / history / events` HTTP 出口。
  - 如果 `events_to_json` 需要感知 `session_id` 来生成受控 preview 地址，这里负责把上下文传进去。
- `src/实时外壳.rs`
  - 继续承接 `room_events` realtime 出口。
  - 保证 realtime 新消息也带同一份 `preview_asset`，不让“晚进群修好了、实时消息又丢图”。

## 全局硬约束

1. 不生成 `motion_url`、不生成第二份 preview 视频资产。
2. 不恢复 `original#t=0.1` 作为默认缩略图主链。
3. 不允许消息流默认态常驻真实 `<video>`。
4. 不允许壳层自己挑 `hls_master_url / anchor / swarm`，具体来源必须由 `媒体播放.ts` 同一 owner 裁决。
5. 不允许因为自动播再引入第二套 `Video.js / hls.js` 正式播放器壳。
6. 任一步都必须先有失败测试或 characterization test，再做实现。
