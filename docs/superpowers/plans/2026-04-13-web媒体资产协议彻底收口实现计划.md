# Web 媒体资产协议剩余缺口收口与口径校准 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把源码审计确认的 4 个剩余缺口逐项收口，让 `Web` 当前阶段的完成定义要么真实成立，要么明确下调到诚实口径。

**Architecture:** 先用源码审计对应的失败测试和特征测试，把“必须补实现”和“应该改口径”拆开，再做最小改动收口。图片链路继续站在现有 `blob_asset`、`media-sw`、`媒体缓存.ts`、`媒体协作分发.ts` 这些 owner/runtime 上，不新造第二套媒体核心；凡是会把当前阶段炸成“新后端生命周期系统”的需求，一律改成显式延期和文档降级，而不是伪装成已完成。

**Tech Stack:** Rust (`axum` / 现有媒体 locator 与 contract 输出), TypeScript (`Vitest` / `CacheStorage` / 现有媒体 owner/runtime), `WebTorrent`, `media-sw`

---

## Scope Lock

- 这份计划只处理这次源码核查确认的 4 个缺口：
  1. 图片查看后不会进入 `MediaCacheOwner.complete`
  2. 图片前端没有真正接上 `blob_asset.distribution` / backfill / runtime
  3. `blob/full` 与 `blob/original` 仍共用旧原图字节
  4. `24 小时` 当前只有 TTL / availability 语义，没有看到明确物理删除执行
- `音频 / iOS / Android / Desktop / CLI` 继续延期，不纳入本次计划。
- 当前阶段默认优先补图片完整资产闭环；如果某个缺口会把范围扩大成“新图片处理流水线”或“新附件 GC 系统”，则当前阶段只允许改 spec，不允许谎称已完成。
- 所有行为改动都先写测试，再做最小实现，再验证，再提交。

## Decision Rule

- **必须补代码**：
  - 图片查看后进入 `MediaCacheOwner.complete`
  - 图片完整资产恢复后会话能回到 `locally_complete`
- **先做特征测试，再决定**：
  - 图片是否在当前阶段必须接 `blob_asset.distribution`
  - `blob/full` 与 `blob/original` 是否必须变成两份真实后端资产
  - `24 小时` 是否必须在当前阶段实现物理删除
- **默认改口径，不硬扩范围**：
  - 任何需要新图片导出流水线、对象存储 GC、后台生命周期任务的需求
