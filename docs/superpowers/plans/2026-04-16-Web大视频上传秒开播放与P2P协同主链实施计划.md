# Web 大视频上传秒开播放与 P2P 协同主链 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 `koko` 的大视频链路真正落成“`complete` 后形成 `preview_asset + mezzanine + HLS/DASH/CMAF + distribution metadata`，前 `24 小时` 服务器保证秒开与补种，`24 小时` 后删掉原视频、服务端 mezzanine 副本、流媒体产物，系统只靠 peer 侧完整资产和 `WebTorrent` swarm 继续活”的当前阶段正式主链。

**Architecture:** 后端继续是唯一业务真相 owner：`complete` 决定 ready、资产形成、过期时间、删除事实和对外投影；前端继续是单壳多源消费方：`Video.js` 只做唯一播放器壳，`媒体播放.ts + 媒体会话.ts` 是唯一 source resolver / 播放 winner owner，`WebTorrent` 负责删源后的长期平面，`p2p-media-loader-hlsjs` 只增强 `HLS` 支路。实现顺序必须是“先补失败测试和生命周期真相，再补合同投影，再改前端 winner 逻辑和增强层接线，最后做清理与联调验证”，不允许前端先偷跑成第二真相。

**Tech Stack:** Rust, Axum, SQLx/PostgreSQL, Tokio, object_store, Shaka Packager, TypeScript, Lit, Vitest, Video.js v10, hls.js, p2p-media-loader-hlsjs, WebTorrent, WebRTC

---

## Scope / Constraints

1. 这是一个跨后端真相、共享合同、前端播放 owner 的单一媒体子系统计划，不拆成第二份子计划；但每个 Task 都必须独立可测、可提交。
2. 按当前仓库约束，本计划默认在现有 `main` 工作区执行，不另开 worktree。
3. 不新增第二套播放器壳，不新增第二套 WebTorrent runtime，不为了 `P2P` 再手搓私有 media manager。
4. `transport success != business success` 仍是硬门槛；只有 `complete` 成功才能把附件升级成 `ready`。
5. `24 小时` 后允许内容自然死亡；这不是 bug，所以计划里任何 cleanup / availability / degraded 逻辑都不能偷偷引回长期服务器播放源。
6. 所有代码改动结束后都要重建 graphify：`python3 -c "from graphify.watch import _rebuild_code; from pathlib import Path; _rebuild_code(Path('.'))"`。
