# 浏览器端应用平台化·浏览器能力入编 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把生命周期、多标签、Service Worker、离线、通知、badge、存储、传输这些能力正式纳入 `BrowserAppPlatform`，让浏览器端真的像“应用”，而不是几个页面凑出的功能补丁。

**Architecture:** 这一计划只处理浏览器运行时真相，不碰后端业务主权，也不让平台层偷懂聊天业务。平台 runtime 负责提供设备与浏览器能力，聊天/后台应用只通过命令申请能力、通过事件接收结果。通知该不该发、badge 该不该亮，由业务内核决定；平台只执行。

**Tech Stack:** TypeScript、Vitest、Workbox、`BroadcastChannel`、`Notification API`、`Badge API`、`Service Worker API`、现有 `frontend/app-sw.ts`、`frontend/media-sw.ts`、`frontend/传输.ts`、`frontend/存储.ts`。

---

## 为什么这部分要单独一份

这一块最容易“做出能力，但做坏边界”。

如果把通知、多标签、SW、离线直接散着接进聊天壳或者时间线 owner，短期会看起来能跑，长期就会变成：

- 平台层开始偷懂房间和未读；
- 壳层开始偷管 badge 和通知；
- 一切和页面生命周期相关的 bug 都会变成偶发 bug。

所以必须单独一份计划，只谈浏览器运行时真相，不让它和聊天业务真相搅在一起。

## 施工红线

- 平台 runtime 不得判断“哪条消息值得提醒”“哪个房间该红点”“什么叫已读”。
- 聊天应用和后台应用不得直接操作 `Notification`、`BroadcastChannel`、`navigator.serviceWorker`、`indexedDB`。
- `app-sw.ts` 只处理应用壳和静态资源边界，不缓存聊天 API / socket / 业务媒体真相。
- `TransportRuntime` 只托管连接与节奏，不拥有消息合流真相。
