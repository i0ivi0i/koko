# 客户端派生预览与零长期轻封面落地计划 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把视频预览主链从“后端长期 still + autoplay 顺手出首帧”切到“单一 canonical 文件 + 同文件 preview hint / 早期关键字节 + 客户端本地派生缓存”，并用测试锁死新旧边界。

**Architecture:** 采用“先锁失败测试，再收 contract owner，再迁 preview owner，最后补 swarm 预览优先级”的硬切顺序。后端对新单文件视频停止写入和正式承诺 `thumbnail_storage_key / preview_asset.still_url`，但保留对历史附件的只读兼容；前端把预览 owner 从 `房间消息窗` 壳层收回到媒体运行时，统一通过 preview cache / embedded hint / early-frame 派生给时间线和查看器消费。

**Tech Stack:** Rust、Axum、SQLx、TypeScript、Vitest、Video.js v10、Mediabunny、WebCodecs、MediaCapabilities、WebTorrent、OPFS、chrome-devtools-cli。

## Constraints

- `Video.js v10` 仍是唯一正式播放器壳；壳层只能消费已经裁决好的 preview / playback 结果，不拥有 preview 真相。
- 新单文件视频不再把 `thumbnail_storage_key`、`has_preview_asset`、`preview_asset.still_url` 当正式协议承诺；历史附件允许继续只读兼容。
- 这次不删数据库列，不做 schema migration；先停写、停正式承诺、保留 legacy read path。
- 时间线预览 owner 必须回到媒体运行时；`frontend/房间消息窗.ts` 里的 `无封面视频稳定预览源` 只能退场，不能继续扩权。
- preview cache owner 必须以 `content_hash` 为主键，不允许继续把 preview 真相绑在 `attachmentId` 上。
- `WebTorrent` 只负责关键字节优先级，不负责 poster 语义；“有 preview”与“正在播放”必须是两条状态。
- 发送端已有本地预览能力要复用，不得再手搓第二套抽帧逻辑；优先共用 `视频元数据.ts` / `视频预处理.ts` 里的现成能力和 Mediabunny。
- 真实烟测默认走 `chrome-devtools-cli`，目标房间 `1234b`，测试文件优先使用 `D:\200-生活\230-照片备份\233-Telegram\色色` 下的 MP4。
- 所有行为变更先写失败测试，本地确认红测原因，再做最小实现；提交必须小步、中文、可读。
