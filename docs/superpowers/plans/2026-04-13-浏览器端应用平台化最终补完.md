# 浏览器端应用平台化最终补完 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不改后端契约、不回滚已完成 owner 收口的前提下，补齐浏览器平台最后一批真实能力，让 [2026-04-12-浏览器端应用平台化-design.md](/E:/koko/docs/superpowers/specs/2026-04-12-%E6%B5%8F%E8%A7%88%E5%99%A8%E7%AB%AF%E5%BA%94%E7%94%A8%E5%B9%B3%E5%8F%B0%E5%8C%96-design.md) 第 15、16 章可以按源码兑现。

**Architecture:** 保持现有 `BrowserAppPlatform -> AppKernel -> Shell` 三层骨架不动，这份计划只收尾剩余平台缺口，不重开聊天/后台已完成的边界收口。实现方式是补一条窄而真实的平台控制面：`ServiceWorkerRuntime` 负责版本握手、更新接受、后台唤醒信号；`OfflineRuntime` 负责持久化待补发任务与调度；`MultiContextRuntime` 负责真正的聚焦/接管；`ChatAppKernel` 只负责把“消息发送”翻译成可排队的业务意图，不把浏览器运行时事实重新判一遍。

**Tech Stack:** TypeScript、Lit、Vitest、Workbox、BroadcastChannel、Notification API、Badge API、Service Worker、Background Sync、`idb`、socket.io-client。

- 这份 plan 只覆盖本轮审查仍未完成的三块：

## 先锁死的设计决定

### 1. 离线补发不新增后端契约

当前后端“发消息”只有 realtime `create_message`，没有独立 HTTP send endpoint。[传输.ts](/E:/koko/frontend/传输.ts) 里也没有现成 HTTP 发送接口可复用。  
因此这次“后台补发”的完成定义是：

- 任务会持久化；
- 任务会在 `online / resume / background sync / service worker 唤醒消息` 时被调度；
- 任务由**下一个受控页面客户端**用现有 transport/socket 执行；
- Service Worker 只做唤醒、通知和委托，不在 worker 里重复写聊天业务发送语义。

这是当前后端契约下唯一不倒灌业务真相、也不手搓第二套发送协议的做法。

### 2. 离线任务仓储用成熟轮子，不手搓原生 IndexedDB

为避免在平台层手搓一套易碎的 IndexedDB 胶水，这里直接引入 `idb` 作为薄封装。  
项目代码只保留：

- 任务记录结构；
- 队列去重 / 重放时机；
- 与 `OfflineRuntime` 的薄适配。

### 3. 不把 Notification 迁成另一套 SW-only 模型

当前通知主路径仍是页面 `Notification` API；这次收尾不把整条通知链重做成 SW push 模型。  
本次要补的是：

- 点击通知后真的尝试 `focus/open/claim` 当前应用；
- 多标签之间真的完成接管，而不是只广播一个“想聚焦”的消息。

### 4. 补一条窄的 platform event 面，不搞 event bus

剩余问题本质上都需要“平台事实 -> 业务内核”通知面，例如：

- `SERVICE_WORKER_UPDATE_READY`
- `BACKGROUND_DRAIN_REQUESTED`
- `PRIMARY_CONTEXT_FOCUSED`

允许在 `BrowserAppPlatform` 上补一个**有限、显式枚举、可测试**的订阅接口。  
禁止借机做成“本地 event bus 万物互联”。

## 全局红线

- 不允许在平台层判断“哪条消息该成立 / 哪条消息算已读 / 哪个房间该红点”。
- 不允许为离线补发新增后端专用 HTTP 契约。
- 不允许让 SW 直接持有聊天消息业务语义，只能持有 opaque task / wake signal。
- 不允许把 platform event 面长成万能 bus；事件种类必须显式枚举。
- 不允许引入第二套 notification 发送链。
- 不允许为了方便继续在业务文件里直读 `navigator.serviceWorker`、`BroadcastChannel`、`Notification`、`window.focus()`。
