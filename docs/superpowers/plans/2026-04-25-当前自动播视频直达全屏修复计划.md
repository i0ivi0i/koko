# 当前自动播视频直达全屏修复 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` or `supxcode` when implementing this plan. Keep this checklist updated as each task is completed.

**Goal:** 修复“点击当前自动播 owner 视频时仍然先冷开查看器/重建播放器壳”的回归；让当前热视频点击后沿同一条活跃播放链直接进入沉浸/全屏，不再创建第二颗正式播放器、不再多走一次 recovering，不再引入第二套播放真相。

**Architecture:** 这是浏览器壳层的播放表面接管问题，不是媒体字节主链问题。`WebTorrent` / locator / 会话 playback / `currentTime` / `inlineAutoplayOwnerAttachmentId` 继续保持现有单真相；本轮只收口“当前热 surface 如何被显式点击接管”。非当前 owner、无活跃表面、图片查看器仍沿现有查看器冷开路径；只有“当前自动播 owner 视频”走直达接管路径。

**Tech Stack:** TypeScript, Lit, native `<video>`, existing media runtime / media sessions, existing Video.js v10 shell, Vitest, Chrome DevTools CLI / Playwright smoke.

---

## 0. 当前根因

当前代码链路把“点击当前热视频”和“点击普通未热视频”混成了一条冷开路径：

1. `frontend/房间消息窗.ts` 点击视频统一只发 `room-open-media-viewer`。
2. `frontend/聊天壳.ts` 统一转成 `MEDIA_OPEN_REQUESTED`。
3. `frontend/聊天媒体编排.ts` 的 `打开查看器(...)` 无条件先调用 `启动查看器起始附件会话(...)`。
4. `启动查看器起始附件会话(...)` 在起点是视频时，会直接 `session.send({ type: "ENTER_RECOVERING" })`。
5. `frontend/媒体/壳层/查看器会话协作.ts` 在会话 `recovering` 时，又会把查看器 request 的视频 `src` 清空，等后续 owner 再同步回来。
6. `frontend/媒体/媒体查看器.ts` 的 `打开(...)` 对视频起点会无条件 `createVideoJsPlayerShell(...)`，也就是再造一颗新的视频播放器壳。

这条链路对“当前自动播 owner 已经在屏幕里稳定播放”的场景是过度设计，副作用有三类：

1. **重复恢复：** 明明当前会话已经热着，还被先送进一次 `ENTER_RECOVERING`。
2. **重复建壳：** 明明当前屏幕上已有活跃 `<video>`，却还是冷开新的 viewer/player。
3. **重复切表面：** 用户点的是当前活跃画面，代码却先走“新建第二表面，再把它 fullscreen”。

现有代码里其实已经有可复用的单真相线索：

1. `frontend/媒体/媒体播放.ts` 已经把播放表面收口成 `surface = "viewer" | "inline_autoplay"`。
2. 这说明系统本来就承认“同一条 playback 真相可投影到不同表面”，并不需要新增第二命令、第二会话、第二状态机。

**本轮禁止把这个问题修成新的 viewer 专属协议。**  
应该做的是：保留现有 `MEDIA_OPEN_REQUESTED` 与媒体会话真相，只在壳层补一条“当前热 surface 直达接管”的窄路径。

## 3. TDD：先写失败测试

### 3.1 当前自动播 owner 点击时，不得冷开第二颗播放器

在 `frontend/tests/媒体查看器测试.spec.ts` 与 `frontend/tests/聊天媒体编排测试.spec.ts` 补一组失败测试：

1. 当前附件已经是 `inlineAutoplayOwnerAttachmentId`。
2. 当前消息流里已经存在活着的 `video.message-video-preview[data-attachment-id=...]`。
3. 当前会话 snapshot 已是可播 `playback`，不是 deleted / no_seed。
4. 点击后：
   - 不再调用“冷开第二颗 Video.js 壳”的路径；
   - 不再出现第二个 `<video>`；
   - 不再把 request 改写成 `src: ""` 的 recovering viewer request；
   - fullscreen/沉浸动作直接落到当前活跃表面或其接管容器上。

最低断言目标：

1. `createVideoJsPlayerShell` 不增加调用次数，或只走“接管现有表面”的窄适配路径；
2. DOM 中同时活着的 `video` 数量不因为点击当前 owner 而从 `1` 变成 `2`；
3. `requestFullscreen` / 沉浸切换落在当前 active surface 所属容器。

### 3.2 当前自动播 owner 点击时，不得先 `ENTER_RECOVERING`

在 `frontend/tests/聊天媒体编排测试.spec.ts` 补失败测试：

1. 为起点附件准备“当前正在 inline_autoplay 热播”的 session snapshot；
2. 调用 `编排.打开查看器(request)`；
3. 断言：
   - 不发送 `ENTER_RECOVERING`；
   - 不会再触发一次“查看器手动打开即强制重裁决”的旧逻辑；
   - `VIEWER_OPEN_REQUESTED` 若仍存在，也只能携带“直达接管”语义，而不是新的冷开恢复语义。

这条测试的作用是把“当前热视频点击”和“用户手动重试一个普通视频”彻底分开。

### 3.3 非当前 owner / 无活跃表面时，旧冷开路径继续成立

反向测试不能少：

1. 起点视频不是当前自动播 owner；
2. 或者虽然 attachmentId 相同，但当前消息流里找不到活跃 `<video>`；
3. 或者当前会话已不是可接管的正常播放态。

断言：

1. 仍然走既有查看器冷开；
2. 仍然允许 `Video.js` viewer fullscreen；
3. 不会因为这次修复让普通视频点开失效。

### 3.4 内核和壳层事件不新增第二命令真相

在 `frontend/tests/聊天应用内核测试.spec.ts` 加一个架构守卫：

1. `MEDIA_OPEN_REQUESTED` 仍然是显式打开媒体的唯一业务入口；
2. 不新增一套平行的 `INLINE_VIDEO_FULLSCREEN_REQUESTED` 业务命令；
3. 若需要壳层私有 takeover 信息，只允许存在于壳层依赖/回调，不得污染 `contract` / `媒体查看器打开请求`。

## 4. 实现：壳层先判断“能否直接接管当前热 surface”

### 4.1 保持共享 request 纯净，不把 DOM 节点塞进 `媒体查看器打开请求`

`媒体查看器打开请求` 现在只包含：

1. `startAttachmentId`
2. `items`

这层是共享表面，不能塞：

1. `HTMLElement`
2. `HTMLVideoElement`
3. 浏览器 fullscreen handle
4. 某个壳专属的布局/overlay 状态

因此本轮裁决：

1. **禁止**给 `媒体查看器打开请求` 新增 DOM / 壳层字段。
2. 当前热 surface 是否可接管，必须在 `房间消息窗.ts / 聊天壳.ts / 媒体查看器.ts` 这些 Web 壳层内解决。

### 4.2 在壳层补“当前可接管视频表面”查询能力

建议最小实现：

1. `frontend/房间消息窗.ts` 暴露一个窄查询能力，只回答：
   - 某个 `attachmentId` 当前是否就是热的 `inlineAutoplayOwnerAttachmentId`
   - 当前 DOM 中是否存在对应的活跃 `<video>`
   - 若存在，返回该表面的只读引用或受控访问器
2. `frontend/聊天壳.ts` 在处理 `room-open-media-viewer` 时，先用这条壳层能力判断“当前点击是不是热 owner”
3. 如果是：
   - 把“直达接管”作为壳层私有上下文交给媒体查看器/编排；
4. 如果不是：
   - 保持旧的 `MEDIA_OPEN_REQUESTED` 冷开链路

这里的关键是：

1. 这是 **壳层查询能力**，不是业务真相 owner；
2. 真正的 attachment / playback / currentTime / deleted/no_seed 仍由现有 media runtime 决定。

### 4.3 优先复用现有 `surface` 真相，不新造第二套状态机

`frontend/媒体/媒体播放.ts` 已有：

```ts
type 播放表面 = "viewer" | "inline_autoplay";
```

本轮实现要站在这条真相上，而不是旁边再长一套：

1. 当前热视频点击只是从 `inline_autoplay` 表面“升格”为沉浸/全屏；
2. 不是重新创建一个新的播放会话；
3. 不是再发明一个 `fullscreen_viewer` surface；
4. 不是再发明一个“消息流点击专用播放源解析器”。

如果后续确实需要区分“普通 viewer 冷开”和“inline_autoplay 直达接管”，也应优先把它建模成：

1. 同一条会话真相下的 **接管策略**
2. 而不是第三种长期活着的播放表面

## 5. 实现：当前热视频点击时跳过旧的 recovering / 冷开链路

### 5.1 `聊天媒体编排.ts` 只对“冷开查看器”保留 `启动查看器起始附件会话`

当前的关键退化是：

```ts
启动查看器起始附件会话(baseRequest);
const nextRequest = 查看器会话协作.投影查看器请求到当前播放真相(baseRequest);
```

这对当前热 owner 不成立。  
本轮要改成：

1. **当前热视频直达接管**：
   - 不调用 `启动查看器起始附件会话(...)`
   - 不主动发 `ENTER_RECOVERING`
   - 不把 request 改写到 `src: ""`
2. **普通冷开查看器**：
   - 保持现有恢复链路

这里必须补中文注释，解释为什么当前热 owner 不能复用“手动重试查看器”的 recovering 逻辑。

### 5.2 `查看器会话协作.ts` 只裁决“是否需要等待真相”，不接管当前热 surface

`frontend/媒体/壳层/查看器会话协作.ts` 里那些逻辑：

1. `投影查看器请求到当前播放真相(...)`
2. `起始视频会话当前不可打开(...)`
3. `是否应等待本地完整视频会话真相(...)`

它们本来就是为“查看器冷开”准备的。  
本轮要求：

1. 当前热 owner 直达接管时，这层只允许做最小校验；
2. **禁止**再把热 owner 的现有 `src` 清空成等待态；
3. **禁止**让热 owner 的点击也排队进入“等待本地完整视频会话真相”。

也就是说，这层只继续守“业务真相能不能打开”，不再负责把热表面变冷。

## 6. 实现：媒体查看器支持“接管现有活跃表面”，而不是默认新建第二颗 `<video>`

### 6.1 当前热 owner 的优先级应是“接管”，不是“新建”

`frontend/媒体/媒体查看器.ts` 现在视频起点默认：

```ts
接管当前查看器(
  generation,
  createVideoJsPlayerShell(startItem, 视口占用生命周期, 运行时钩子)
);
```

本轮目标不是简单把这里前后顺序换一下，而是收口成：

1. 若存在当前可接管的活跃视频表面：
   - 优先接管它；
   - 直接对它所属容器发起沉浸/全屏；
   - 继续沿用同一条 `playback.src / currentTime / play promise` 真相；
2. 只有不存在可接管表面时：
   - 才调用 `createVideoJsPlayerShell(...)`

### 6.2 “接管现有表面”允许是壳层私有适配，但禁止变成第二活路径

允许的实现方式：

1. 让媒体查看器接受一个壳层依赖：
   - 读取当前可接管表面
   - 对该表面执行 fullscreen / immersive
   - 在退出时归还表面控制权
2. 或者把现有热表面包装成一个“可被 viewer 接管的实例适配器”

但必须同时满足：

1. **禁止**复制一份新的 `<video>` 节点；
2. **禁止**重新设置一遍等价 `src` 触发 `loadstart` / `emptied`；
3. **禁止**同时保留“旧 inline video 继续活着 + 新 viewer video 也活着”的双活路径；
4. **禁止**为了接管当前热 surface 再造一个长期常驻的“内联 Video.js 全局壳”。

换句话说：允许有壳层适配器，但不允许把适配器做成新的系统。

## 8. 禁止事项

1. 禁止新增第二个长期活着的业务命令入口来表达“当前热视频点击全屏”。
2. 禁止给共享 `媒体查看器打开请求` 塞 DOM / 壳层专属字段。
3. 禁止点击当前热 owner 时无条件 `ENTER_RECOVERING`。
4. 禁止点击当前热 owner 时新建第二颗 `<video>`、第二颗 Video.js player、第二个 overlay 会话。
5. 禁止为了图省事，把“当前热视频点击”改成完全绕过媒体运行时的浏览器原生 `window.open` / 外链播放。
6. 禁止为了接管当前热 surface 再引入一套新的 fullscreen 状态机、viewer 状态机或 preview owner。
7. 禁止误伤非当前 owner 视频的查看器冷开路径。
8. 禁止动后端、动 locator、动 swarm 主链去掩盖这个前端壳层问题。

## 9. 完成定义

满足下面这些条件，才算这轮完成：

1. 当前自动播 owner 视频点击后，沿同一条活跃播放链直接进入沉浸/全屏。
2. 点击过程中不再出现第二个 `<video>` / 第二个 player / 第二次 source 重建。
3. 当前热视频点击不再触发 `ENTER_RECOVERING` 风暴。
4. 非当前 owner 视频、图片查看器、删除态/无种子态的既有行为保持正确。
5. 所有新增测试先红后绿，浏览器真实烟测通过。
