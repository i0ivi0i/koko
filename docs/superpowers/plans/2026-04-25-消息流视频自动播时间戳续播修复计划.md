# 消息流视频自动播时间戳续播修复 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended when the active instruction policy allows delegation) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 修复群聊消息流内联自动播视频在上下滑动、DOM 被虚拟列表卸载再挂载后从 `0` 秒重播的问题；同一附件、同一播放源再次成为自动播 owner 时，必须从离屏前记录的 `currentTime` 附近继续循环播放。

**Architecture:** 播放时间戳属于浏览器壳的本地体验真相，但它不能归属 DOM 节点。`房间消息窗` 只负责从真实 `<video>` 读取浏览器暴露的播放时间，并把 `{ attachmentId, src, currentTime }` 上报为应用事件；`媒体运行时` 作为媒体体验 owner 保存“附件 + 源”的时间戳快照；`聊天媒体编排 / 聊天应用内核 / 应用运行时 / 聊天壳` 只做稳定命令和快照转发；`房间消息窗` 在同一 `attachmentId + src` 重新挂载并拿到 `loadedmetadata` 后恢复 `currentTime`，再触发自动播。WebTorrent 继续只负责分发和流式源，Video.js v10 继续只做播放器壳，TanStack Virtual 可以自由销毁和重建消息 DOM。

**Tech Stack:** TypeScript + Lit + XState + Vitest；TanStack Virtual；原生 `HTMLMediaElement.currentTime / timeupdate / loadedmetadata`；现有 WebTorrent 协作分发；现有 Video.js v10 播放器壳。

## 2. 官方与项目边界

- MDN 的 `HTMLMediaElement.currentTime`、`timeupdate`、`loadedmetadata` 是浏览器标准播放位置读写和恢复入口；这里不需要自研播放器时间轴。
- Chrome 自动播放策略要求自动播路径继续尊重 muted / play promise 失败语义；本计划不绕过浏览器策略，只在自动播前恢复时间戳。
- WebTorrent 官方提供浏览器流式播放源和 seeking 能力，但不拥有 UI 播放位置真相；它仍停留在 `src / streamURL / streamTo` 这类分发适配层。
- Video.js v10 的 `video-player` / `media-container` 心智是播放器 provider 与容器交互面分离；本 bug 不应该借机迁移消息流预览到另一套播放器，也不应该让播放器壳反向拥有附件、source 或自动播 owner。
- TanStack Virtual 是 headless 虚拟化，DOM 是可丢弃投影；任何依赖 DOM 节点长期存在的续播行为都属于脆弱偶然。

## 3. 目标数据流

1. `房间消息窗` 中的自动播视频触发 `timeupdate`、`pause`、`ended` 前的有效时间变化。
2. `房间消息窗` 派发 `room-inline-autoplay-position-changed`，payload 只包含稳定字段：
   - `attachmentId`
   - `src`
   - `currentTime`
3. `聊天壳` 转成应用命令 `MEDIA_INLINE_AUTOPLAY_POSITION_CHANGED`。
4. `应用运行时` 和 `聊天应用内核` 把命令交给 `聊天媒体编排`。
5. `聊天媒体编排` 派发到 `媒体运行时`，由 runtime 保存 `inlineAutoplayPositionByAttachmentId`。
6. `聊天媒体快照` 把位置表投影回 `聊天壳`。
7. `房间消息窗` 收到 `.inlineAutoplayPositionByAttachmentId`，在同一 `attachmentId + src` 的 `<video>` 新挂载并 `loadedmetadata` 后设置 `video.currentTime`。
8. `同步时间线自动播播放状态()` 在调用 `play()` 前再次确保同源位置已恢复，避免事件顺序导致先从 `0` 秒播一帧。

## 3.1 万人群聊性能硬约束

- 只允许当前 `inlineAutoplayOwnerAttachmentId` 对应的视频上报位置；非 owner 的首帧预览 `<video>` 不产生时间戳事件。
- `timeupdate` 不能原样穿透到应用运行时。MDN 明确该事件可能随系统负载在约 `4Hz-66Hz` 之间触发；实现必须做边界节流：
  - `currentTime` 变化小于 `0.75s` 不上报；
  - 同一 `attachmentId + src` 常规上报间隔不短于 `1000ms`；
  - `pause`、owner 退场前、`pagehide/visibilitychange hidden` 这类边界事件允许强制 flush 一次。
- 位置表必须有上界，不能随万人群历史消息无限增长：
  - `MESSAGE_ATTACHMENTS_SYNCED` 按当前已加载消息附件集合清理；
  - 额外保留一个小型按 `updatedAt` 裁剪的上限，建议先用 `256` 条，后续由真实使用数据调整。
- 位置更新不能触发整条消息流重算：
  - `房间消息窗` 的恢复逻辑只能查当前 DOM 中的 `video.message-video-preview[data-attachment-id]`；
  - 不允许因每次位置上报重新扫描全部消息数据、重新 locate media、重新创建 WebTorrent session 或重新构造 Video.js 壳；
  - `同步时间线自动播播放状态()` 只在 owner、播放结果、items 或恢复位置实际影响当前 DOM 时运行。
- 不改变媒体加载预算：
  - 继续保持内联预览 `muted playsinline preload="metadata"`；
  - 不为了恢复时间戳提高 preload、额外拉 range、额外打开查看器播放器或额外启动第二条 WebTorrent/HLS 支路；
  - `play()` 仍必须尊重 Promise 失败，不因自动恢复而吞掉 Chrome 自动播放策略。

## 6. 风险与退场

- 风险 1：测试环境里的 `HTMLVideoElement.currentTime` 行为可能被 jsdom / happy-dom 限制。退场方式：测试只断言属性写入和事件上报，不模拟真实解码。
- 风险 2：过于频繁的 `timeupdate` 触发状态更新。退场方式：按 `3.1` 的预算硬约束实现，常规位置事件必须节流，边界事件才 flush。
- 风险 3：同一附件换了播放源后误恢复旧时间。退场方式：位置表保存 `src`，恢复前必须严格匹配。
- 风险 4：用户主动打开查看器后关闭，内联预览不应被查看器释放影响。退场方式：沿用 `c1b72942` 的边界，查看器关闭不清理时间线预览会话，也不清理内联自动播位置。
