# 群聊媒体协作分发 Phase 1-Phase 3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不碰现有 `Tus/Rustus` 上传主链的前提下，分三阶段把 `ready` 附件从“只有元数据”推进到“Web 前端真实进入 swarm + 24 小时 Web Seed 保底 + 多 peer 调度削峰”。

**Architecture:** `Phase 1` 只补“分发元数据真相面”；`Phase 2` 再把 Rust 侧 metainfo、受控 torrent locator、Web 前端 `WebTorrent` 运行时、service worker 和 24 小时 Web Seed 接通；`Phase 3` 在不改业务真相的前提下，补多 peer 调度、同页会话复用、热点削峰和“内容已过期”的后端裁决面。后端继续只掌握附件/权限/定位真相，前端只负责自动接入协作分发和展示运行态提示。

**Tech Stack:** Rust (`axum`, `sqlx`, `sha2`, `hex`, `bip_metainfo`)、PostgreSQL migration、TypeScript (`vitest`, `webtorrent`)、`bittorrent-tracker`、service worker、现有 `frontend/媒体` 模块。

---

## 范围裁决

这份 spec 已经明确拆成 `Phase 1 ~ Phase 4`。  
按这轮补写后的裁决，这里一次性覆盖 **Phase 1 ~ Phase 3**，让后续执行时不用在“元数据 plan”和“真实 swarm plan”之间来回切文档。

这份 plan 现在包含：

- `Phase 1`：分发元数据真相面
- `Phase 2`：真实 Web swarm + 24 小时 Web Seed + service worker + tracker 开发编排
- `Phase 3`：多 peer 调度、同页复用、热点削峰和“内容已过期”后端裁决

这份 plan 仍然故意不包含：

- `Phase 4` 的强 peer / keeper
- tracker 严门禁的硬切执行
- 非 Web 端壳层接入

## Phase 1 locator 目标形状

这一阶段不要伪造 Phase 2 的 tracker/runtime 字段。  
`distribution` 只包含稳定真相：

```ts
export interface 媒体协作分发定位片段 {
  content_id: string;
  content_hash: string;
  swarm_id: string;
  web_seed_until: string; // Unix 秒字符串，和现有 expires_at 心智保持一致
}
```

后端 JSON 目标：

```json
{
  "attachment_id": "att-123",
  "kind": "video",
  "status": "ready",
  "original_url": "/api/attachments/att-123/content?session_id=s-1&variant=original",
  "thumbnail_url": null,
  "distribution": {
    "content_id": "content_att-123",
    "content_hash": "2cf24dba5fb0a30e...",
    "swarm_id": "swarm_2cf24dba5fb0a30e...",
    "web_seed_until": "1775942400"
  }
}
```

这里故意不把 `swarm_id` 假装成最终 `info_hash`。  
Phase 1 只要一个稳定、可持久化、不会反客为主的分发锚点。

## Phase 2 范围裁决

这一阶段开始真正让 Web 前端进入 swarm，但仍然保持两个克制：

1. 不把 tracker 严门禁一次性硬切进主链，ticket 先留接口和字段位置。

这里把 Rust 侧 metainfo 轮子先裁死：

- 不选 `librqbit::create_torrent(path)` 进 Phase 2 主链，因为它更贴文件路径，而当前 `complete_media_upload()` 已经直接握着权威字节和统一对象存储边界。
- 选 `bip_metainfo`，因为它可以用 `DirectAccessor::new(file_name, bytes)` 直接从权威字节产出 metainfo，更符合当前“上传成功时已拿到字节”的真实主链。

## Phase 3 范围裁决

这一阶段不再只是“能连起来”，而是要让 swarm 真的开始发挥多人接力的价值：

1. 同一页面不能因为多次点开同一附件就重复建一堆 torrent 会话。
2. 开始查看后必须继续补齐整个附件，而不是只按观看进度拖着走。
3. “内容已过期” 必须由后端裁决，前端只展示。
