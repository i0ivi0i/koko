## 直接证据

### 1. 正式视频字节仍走 WebTorrent 主链

viewer 初始自动播采样里，真实活着的 video 为：

- `attachmentId = att-761d40e936be`
- `canonical = true`
- `readyState = 4`
- `paused = false`
- `currentTime ≈ 14.427`
- `src = https://127.0.0.1/webtorrent/0e0e2fbbe1f5fb38da5f065f7871c29b30663b5b/content-689af1cf06232f3f609a6ae409b1b3c11f22a5a3785de3f4363f8d183009152c.mp4`

这说明正式字节入口仍是 `/webtorrent/...`，不是第二 HTTP 正式主链。

### 2. 滚动交接瞬间确实会出现多表面并存

viewer 在 `messageScroll` 上从 `scrollTop=1378` 滚到 `1000` 的采样中，出现过下面的瞬时组合：

1. 旧附件 `att-761d40e936be` 的非 canonical preview video 仍在 DOM 里，`currentTime ≈ 12.512`
2. 新附件 `att-233f8750479d` 同时出现 preview video 与 canonical player
3. `visibleCanonicalHosts = 0`
4. `stageHosts = 1`
5. `frozenFrames = 1`

这证明滚动交接不是单一表面原子切换，而是：

1. 旧 preview
2. 新 preview
3. hidden stage canonical
4. frozen frame

会在同一窗口短暂并存。

### 3. “错误时间点 preview 帧露出”不是猜测，单测可稳定复现

新增定向测试：

1. [frontend/tests/全局丝滑自动播测试.spec.ts](E:/koko/frontend/tests/全局丝滑自动播测试.spec.ts)
2. [frontend/tests/房间消息窗/自动播露出门禁测试.spec.ts](E:/koko/frontend/tests/房间消息窗/自动播露出门禁测试.spec.ts)

其中最关键的红灯是：

1. 已有保存续播点
2. 当前 preview `<video>` 已 ready
3. 但 `currentTime` 还停在错误时间点

旧代码仍会把这颗 preview `<video>` 继续露出来。  
这正对应肉眼症状“先首帧，再跳续播点”。

## 当前结论

本轮自动播问题的根因已经从真实烟测和代码红灯对上：

1. 状态机之前只知道“有帧”，不知道“这帧是不是当前续播时间点”
2. 渲染层之前即使收到了 `hidden_handoff`，仍可能继续露出错误时间点的 preview `<video>` 或 poster
3. 滚动交接时，旧 preview / 新 preview / hidden stage canonical / frozen frame 会短暂并存，说明露出门禁确实没有完全收口

## 已开始的收口动作

目前已经落下并通过定向测试的修正有两条：

1. `hold_frame` 决策现在会带 `targetCurrentTime`
2. 时间线渲染在 `hidden_handoff + 有续播点 + 当前 preview 帧时间不对` 时，不再继续露出错误 preview 或 poster
