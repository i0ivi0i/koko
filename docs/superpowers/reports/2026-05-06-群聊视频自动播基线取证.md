## 当前结论

本轮自动播问题的根因已经从真实烟测和代码红灯对上：

1. 状态机之前只知道“有帧”，不知道“这帧是不是当前续播时间点”
2. 渲染层之前即使收到了 `hidden_handoff`，仍可能继续露出错误时间点的 preview `<video>` 或 poster
3. 滚动交接时，旧 preview / 新 preview / hidden stage canonical / frozen frame 会短暂并存，说明露出门禁确实没有完全收口

## 已开始的收口动作

## 2026-05-06 夜间补充：滚动与 resize 零重接管红灯

这轮基线不是看“最后能不能播”，而是专门看：

1. 同一 `attachmentId`
2. 同一 `/webtorrent/...` source
3. 当前视频仍在自动播放
4. 只发生滚动或窗口尺寸变化

在这种前提下，系统是否还会偷偷重接管、重 seek 或把 `currentTime` 写回旧值。

本轮环境：

1. `https://127.0.0.1`
2. 房间 `1234b`
3. 关键滚动容器：`#messageScroll`
4. 探针方式：深遍历 Shadow DOM 的 video 采样 + 80ms tick + resize 事件采样

### 1. 滚动时，同一条视频的 `currentTime` 发生倒退

采样到的关键片段：

1. `attachmentId = att-9952116af22f`
2. `src = https://127.0.0.1/webtorrent/a5e7a05fc5ea88ddfed648b724124c43254d71da/content-0df9bab55e151934b1d1a28bb04f12b69ab5e1bddbe379ec71d1514334882447.mp4`
3. `before`：`currentTime = 1.760`
4. 只把 `messageScroll.scrollTop` 从 `7938` 调到 `7718`
5. `700ms` 后仍是同一条视频、同一 source、`paused = false`、`readyState = 4`
6. 但 `currentTime` 变成了 `1.636`

这不是自然 loop，因为：

1. 该视频 `duration ≈ 10.042`
2. 回退发生在 `1.x` 秒，不在结尾附近
3. 同期没有切到另一条 `attachmentId`

所以这是一条硬红灯：**仅仅滚动，就让当前正在播放的同一条视频发生了时间倒退。**

### 2. resize 时，同一条视频的 `readyState` 掉到 `1`，并伴随 `currentTime` 回写

本轮先把窗口从 `779x723` 改到 `680x723`，再装 80ms tick 探针，然后把窗口改回 `779x723`。

关键事实：

1. resize 事件触发时，仍是 `attachmentId = att-9952116af22f`
2. source 不变，仍是同一个 `/webtorrent/...mp4`
3. resize 事件采样里，`readyState` 从稳定的 `4` 掉到了 `1`
4. 同一时间段的 tick 序列里，`currentTime` 从 `6.833` 回退到 `6.589`
5. 这次回退发生在 `85ms` 内

这条红灯说明：**窗口尺寸变化不是纯几何事实输入，它已经打进了当前 live 播放会话。**

### 3. 当前基线结论

到这一轮为止，已经有两条可以直接指导代码收口的硬证据：

1. 同一 owner / source / host 稳态播放期间，滚动会让 `currentTime` 倒退。
2. 同一 owner / source / host 稳态播放期间，resize 会让 `readyState` 掉级，并伴随 `currentTime` 回写。

因此后续修复第一刀必须围绕这个不变量：

**同一 owner、同一 source、同一宿主仍有效时，滚动和 resize 只能刷新几何事实，不能再触发 seek、重挂载、hidden handoff 回退、poster 回露或任何形式的时间回写。**
