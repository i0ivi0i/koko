## 1. 项目实时通道现状（事实，2026-05-10）

### 1.1 已经做得很好的部分（不要回退）

按 `@src/实时/外壳.rs:121-181`：

- **背压观测完整**：`房间广播运行观测` 含 6 项 metrics（attempts/delivered/channel_full/closed_socket/serialize/adapter）
- **错误分级 4 档**：`分类广播发送失败` 把 `BroadcastError` 翻译成业务级别（正常断开/背压/序列化/适配器）

- **业务级 metrics 进 tracing**：每次广播都有结构化日志，便于运维侧观测
- **限流 + 文本上限**：前置 spec `2026-05-08-实时热路径加固-design.md` 已加令牌桶（10 burst / 5/s 补充）+ 消息文本长度上限（防 10MB 单包）

### 1.2 关键差距（万人规模时会暴露）

按 `@src/外壳/mod.rs:294`：

```rust
let (socket_layer, io) = SocketIo::new_layer();  // ⚠️ 全默认配置
```

| 默认值 | 万人规模建议 | 风险 |
|--------|--------------|------|
| `max_buffer_size = 128` | 256+ | 大房间广播时 `InternalChannelFull` 概率高（已被现网观测到） |
| `max_payload = 100KB` | 2-5MB（取决于附件元数据 JSON 大小） | 边界场景被 socketioxide 直接关闭 socket |
| `transports = [Polling, Websocket]` | `[Websocket]` only | polling fallback 在万人规模下进程开销翻倍（每周期一次 HTTP） |
| `ping_interval = 25s` / `ping_timeout = 20s` | 看实际网络环境调 | 弱网客户端误判断线 |
| `ack_timeout = 5s` | 业务事件用 emit_with_ack 时不够 | 暂未使用，N/A |
| `connect_timeout = 45s` | 看握手 RTT | 暂可接受 |
| 单 namespace `/` | 业务/管理/媒体分流到不同 namespace | 互相争抢事件循环 |

### 1.3 未启用但万人扩展时必须的设施

- **Redis adapter (`socketioxide-redis`)**：多节点广播跨进程协同。当前单节点不需要，但**节点数 >1 时立刻必须**
- **sticky session**：即使用 Redis adapter 也仍然要——HTTP 长轮询包必须落到持有 session 的节点；否则 HTTP 400
- **`connection-state-recovery`**（socket.io v4.6+ 特性）：断线快速重连不触发 disconnect/reconnect 事件，业务无感。socketioxide 是否支持需核实其当前版本（拉取时 socketioxide 文档未提及，需要查 release notes）
- **大房间广播限速 / 分批**：万人房间单次 emit 是顺序发送，慢连接会拖慢整个广播。socket.io 官方建议拆批 + 慢连接降级；socketioxide 是否提供原生支持需要核实

## 2. 官方最佳实践对照表（参考实施时直接抄）

### 2.1 socketioxide `SocketIoBuilder` 推荐配置

```rust
use std::time::Duration;
use socketioxide::{SocketIo, TransportType};

let (layer, io) = SocketIo::builder()
    .req_path("/socket.io")
    .ping_interval(Duration::from_secs(25))
    .ping_timeout(Duration::from_secs(20))
    .ack_timeout(Duration::from_secs(10))      // 默认 5s 偏短
    .connect_timeout(Duration::from_secs(45))
    .max_buffer_size(256)                       // 大房间必调
    .max_payload(2_000_000)                     // 2MB 兼顾消息+附件元数据
    .transports([TransportType::Websocket])     // WS-only
    .with_state(MyAppState::new())
    .build_layer();
```

### 2.2 多节点扩展（未来横向扩容时）

```rust
// Cargo.toml
```

### 2.3 namespace 分流模板

按 `AGENTS.md` "路径越少，真相越近" 与边界压力，**只在边界压力出现时**才拆 namespace：

- `/` 业务消息主链（最热）
- `/admin` 管理后台（频率低、特权操作）
- `/media-control` 媒体控制面（如 WebTorrent 协调信号）

每个 namespace 独立的连接池、独立的事件循环开销分摊。

## 6. 2026-05-11 深度审计追加（P0 房间订阅泄漏 + P1 Builder 调参）

### 6.1 P0 — 房间订阅泄漏（24h 越用越卡的结构性根因）

**发现日期**：2026-05-11
**严重等级**：CRITICAL — 多群切换场景下唯一的资源无界增长点

**事实**：
- 服务端 `@src/实时/外壳.rs` `handle_realtime_subscribe` 只调 `socket.join(room_id)`
- **整个代码库没有任何 `socket.leave()` 调用**（grep 确认 0 命中）
- 前端退场 `LEAVE_ROOM_VIEW_REQUESTED` 只清前端状态，不 emit 任何 unsubscribe
- socketioxide 官方文档明确："Rooms are left automatically **upon disconnection**"——切换时不自动清
- 用户切换 N 个群后，socket 同时在 N 个房间，收到 N-1 个房间的无效广播

**官方推荐模式**（Context7 + `学习/socketioxide/`）：
```rust
s.on("leave_room", |s: SocketRef, Data(room): Data<String>| {
    s.leave(room.clone());
});
```

**修复方案**：
1. 前端：`subscribeRoom` 前先 emit `"unsubscribe_room"` + 旧 room_id
2. 后端：新增 `"unsubscribe_room"` handler 调 `socket.leave(room_id)`
3. 后端：`handle_realtime_subscribe` 入口处先 leave 旧房间（防客户端不发 unsubscribe 的兜底）

### 6.2 P1 — SocketIo::builder() 显式调参

**已在 §2.1 记录**，此处确认官方示例与建议值：
- `max_buffer_size(256)` — 默认 128，大房间广播时 InternalChannelFull 概率高
- `max_payload(2_000_000)` — 默认 100KB，附件元数据 JSON 可能超限
- `transports([TransportType::Websocket])` — 去掉 polling fallback
- sqlx `acquire_slow_threshold(500ms)` + `acquire_slow_level(WARN)` — 连接池争抢可观测

### 6.3 P2 — IndexedDB 配额安全边际

**MDN 2025 确认**：
- Chrome 60%、Firefox min(10%, 10GiB)、Safari ~60%（新版）
- 超限抛 `QuotaExceededError`，已有 try/catch 静默兜底 ✅
- 典型用户 ~36MB/天，月级可到 GB 级
- 推荐：冷房间 LRU 淘汰（按 `cached_at`） + `navigator.storage.estimate()` 预警

### 6.4 P2 — 虚拟范围 unread-divider O(N) 扫描

`@frontend/房间消息窗/消息虚拟列表.ts:70` 每帧 `findIndex` 全扫 items。
修复：展示项派生时缓存 `unreadDividerIndex`，传入虚拟范围函数。
