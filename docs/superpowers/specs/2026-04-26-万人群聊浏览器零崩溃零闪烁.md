## 0. 这份 spec 不是“再修一个卡顿点”

这份 spec 要解决的，不是某一条视频滑动时偶发抖一下，也不是某一次点击后少等了几百毫秒。

它真正要收口的是一句话：

**我们的万人实时群聊前端，必须在功能和业务都满血成立的前提下，让浏览器始终只背必要负担。群越活跃，群友之间的协同分发可以越强；但浏览器里同时活着的重对象必须越少、越短、越受控。**

X / TikTok / Telegram 这类成熟网页给用户的感觉是“整页视频都能随意滑动、随时接管、马上播放”，但工程真相不是全页面所有视频同时活着。它们真正依赖的是：

1. 数据存在真相和 DOM 表达真相分离。
2. 可见窗口和少量邻近项才进入渲染窗口。
3. 当前项重播放，邻近项轻预热，远处项冷表达。
4. 播放源、码率、预热、取消和后台降级都由一个预算 owner 裁决。
5. 旧请求、旧 preview、旧 reader、旧 source、旧 listener 必须能被取消和回收。

`koko` 要吸收的是这套“看起来全页面都能播，真实 heavy 永远受控”的逻辑模型，而不是照抄它们的播放器、CDN、HLS 主链或私有黑盒。对 `koko` 来说，这个模型必须自然融进 `WebTorrent` 满血协同、唯一播放器、消息流窗口和浏览器生命周期预算里。

如果这句话没有被写成硬规则，后续实现很容易继续漂成下面这些坏结果：

1. 为了让预览和自动播放看起来顺，前端偷偷一直养大量真实 `<video>`、图片表面、预览会话和补齐会话。
2. 为了不让浏览器崩，反过来把 `WebTorrent` 主链削弱成“名义上是 P2P，实际主要还是前端在偷跑第二链”。
3. 为了让滚动时不闪，前台一直保留几十条历史视频的真实媒体对象，最后把 GPU 和 renderer 原生内存拖爆。
4. 为了省资源，把今天已经修好的自动播放、自动暂停、无闪烁、无抽搐重新打坏。
5. 为了让系统“看起来总有预览”，把冷的正式播放源、历史脏帧、伪 preview 泄漏成通用表面，后面又长回第二真相。

所以这份 spec 的目标不是“再做一层优化”，而是把**浏览器端媒体生命周期预算**写成正式裁决：用户眼前像信息流一样连续，系统内部像操作系统一样按窗口、重量、生命周期和设备能力调度资源，防止后续计划和编码继续漂移。

## 1. 当前已经成立的真相，禁止破坏

这份 spec 不是推翻现有裁决，而是在现有真相上补“浏览器绝不崩”的硬约束。

### 1.1 现有播放真相必须继续成立

下面这些已经成立的真相，**禁止** 在后续收口浏览器稳定性时被破坏：

1. **禁止** 长回第二颗正式 `Video.js v10` player。
2. **禁止** 破坏时间线自动播放、自动暂停、查看器、全屏、退出归位共用同一颗 canonical player 的真相。
3. **禁止** 把今天已经收口好的 owner 进入/离开平滑链又打回闪烁、抽搐、冷开、时间轴回退。
4. **禁止** 让消息流重新长出控件、网页式小播放器或第二套交互真相。

### 1.2 唯一 `WebTorrent` 主链必须满血成立

下面这些来自 `2026-04-22` 和 `2026-04-23` 两份文档的真相，也必须继续成立：

1. **禁止** 让前端正式媒体字节绕开 `WebTorrent` 正式主链。
2. **禁止** 为了省浏览器资源，偷偷恢复 `HLS` / 原文件直链 / 第二正式播放链。
3. **禁止** 把“浏览器减负”偷换成“群友少帮一点、服务器多顶一点”。
4. **禁止** 把“群越活跃越强”的主链做回“群友看过了也不继续帮后人”的弱协同。
5. **禁止** 破坏 `0-24 小时` 服务器强参与、之后 peer 接力、失败态说真话这些既有裁决。
6. **禁止** 把 `WebTorrent` 降级成提示、缓存、旁路、兜底或“有就用一下”的二等链路。
7. **禁止** 让 `HLS`、原文件直链、CDN 命中、`p2p-media-loader` 支路成功冒充 `WebTorrent` 秒开成功。
8. **禁止** 用前端首次观看、首次进房、本地时间或首次进入 swarm 时间改写 `24 小时` 起点；服务器强参与窗口仍只认后端 `complete_at`。

这份 spec 里的浏览器减负，只能把前台重量从“重播放”降成“轻预热 / 轻帮助 / 冷表达”；不能把长期正式资产 owner 从 `WebTorrent` 换掉。任何实现只要让 `24 小时` 后的正式播放、保种、完整 peer / 片段帮助者共同构成的可恢复来源接力、或失败态说真话绕开 `WebTorrent` whole-file swarm，就不算完成本 spec。

### 1.3 这份 spec 只补浏览器端生命周期预算

这份 spec 的新增裁决只有一个方向：

**在不削弱协同分发主链、不破坏现有播放体验主链的前提下，把浏览器里同时活着的重对象压进严格预算。**

### 1.4 信息流体验模型必须融入既有真相

X / TikTok / Telegram 的可借鉴点，不是某个单独播放器或某条私有网络链路，而是它们共同遵守的体验假象和资源真相分离：

1. 用户看到的是连续媒体流，系统保存的是全量数据真相。
2. 用户可以随意滑动，浏览器只渲染当前窗口和少量邻近项。
3. 用户感觉视频马上能接管，真实重播放 owner 始终极少。
4. 邻近项可以预热，但预热的是 locator、metadata、首片段、首帧探针、能力判断和有限 range，不是整房历史全量启动。
5. 远处历史只保留冷表达、轻索引、尺寸、缓存状态和协作价值，不保留前台级媒体重量。

这套模型必须和 `koko` 既有真相揉成一体，而不是贴成额外支路：

1. **禁止** 因为学习短视频信息流，就替换现有 canonical `Video.js v10` 播放器。
2. **禁止** 因为学习 XGPlayer / Shaka / Dashlet，就新增第二正式播放器栈或第二播放真相。
3. **禁止** 把“邻近项轻预热”偷换成“整房历史全量预热”。
4. **禁止** 把 `HLS/hls.js/p2p-media-loader` 提升成新主链正式播放 owner；它们最多只能作为旧媒体兼容债务、实验对照或 HLS/DASH segment-level 技术评估存在，不能服务新上传附件的正式可播真相。
5. 信息流媒体预算 owner 只能裁决窗口、重量、预热和取消；不能篡改 `WebTorrent` 主链、唯一播放器真相或房间消息真相。
6. Core Web Vitals、Long Animation Frames、`requestVideoFrameCallback()` 和设备解码能力只能作为预算证据，不能反过来驱动第二播放链或削弱协作主链。

### 1.5 WebTorrent 丝滑秒开必须走官方实链路

`WebTorrent` 和 `HLS/hls.js/p2p-media-loader` 不会天然打架；它们只有在被混成同一个“正式播放真相”时才会打架。对 `koko` 的新主链来说，用户可见的正式播放路径只能是 `WebTorrent` whole-file swarm；`HLS` 只能是旧债务兼容或实验对照，不能再被写成 `0-24 小时` 新附件冷启动播放支路。

官方资料给 `WebTorrent` 浏览器播放的正路已经很明确：注册 `service worker`，让 `client.createServer({ controller })` 提供流式 URL，再用 `file.streamTo(video)` 或 `file.streamURL` 让同一份 torrent file 边下边播、支持 seek、按浏览器实际 codec/container 能力播放。官方 API 还提供 `urlList`/`WebSeed`、tracker、默认 `sequential` piece strategy、`file.createReadStream()`、`torrent.select()`、`torrent.critical()`、`file.select()` 这些能力；这些是我们做“WebTorrent 丝滑秒开”的基础设施，不需要手搓第二套私有顺序拉块内核。

所以后续计划和实现必须守住下面几条：

1. `WebTorrent` 秒开验收必须证明真实 `WebTorrent` 播放路径成立：`service worker/createServer` 已激活，正式视频源来自同一 torrent file 的 `streamTo` 或 `streamURL`，浏览器 range/stream 请求、首帧提交、seek、peer/download/upload 指标都能被观测。
2. `0-24 小时` 的服务器强参与只能表现为 `WebTorrent` 内部的 `WebSeed + WebRTC seeder` 强帮助者；**禁止** 把它改写成前端直接走 `HLS/DASH` 或原文件直链的冷启动播放支路。
3. `HLS/hls.js/p2p-media-loader` 只能作为 legacy 旧媒体兼容、实验 benchmark 或 HLS/DASH segment-level 技术评估被记录；如果当轮对象是新主链附件，实际由 `HLS` 播放必须判为新主链验收失败，而不是“短期支路成功”。
4. 如果历史兼容阶段确实还存在 legacy HLS 播放，必须由媒体预算 owner 显式标成 `legacy_compat_hls`，并与新主链附件隔离；新上传并 `complete` 的附件只能处于 `WebTorrent 正式播放`、`轻预热`、`轻帮助态` 或 `冷表达`。**禁止** 同一附件同时挂两套正式播放源、两套 MSE/reader 重链或两套“已可播”真相。
5. `p2p-media-loader` 的边界只能是 `HLS/DASH` segment-level P2P 技术评估或 legacy 支路；它依赖 HTTP(S) manifest/segments 和 Hls.js/Shaka 这类 streaming engine，**禁止** 把它包装成 `WebTorrent` whole-file swarm、complete peer、长期保种或服务器删源后的存活证明。
6. `24 小时` 后如果服务器已经退出原视频、母本、HLS/DASH manifest 和 segments 的字节供给，长期正式播放只能由 `WebTorrent` whole-file swarm 决定；失败态不能只看“有没有单个完整 peer”，而要看当前重试窗口内完整 peer、片段帮助者、本地权威字节能否真实拼出首播关键字节与持续补齐能力。
7. 为了丝滑而做的预热，只能预热 locator、torrent metadata、首段/首块、codec 能力、首帧探针和有限 range；滑走、owner 切换或代次失效时必须 `AbortSignal + generation` 取消，**禁止** 留下隐藏 `<video>`、MSE buffer、reader、listener 或第二 source 继续活着。

一句话：**WebTorrent 要满血，HLS 只能是旧债务兼容或实验对照；能并存的是历史分流和证据记录，不是新主链双真相。**

### 1.6 新裁决：任何阻挡唯一 WebTorrent / 满血 WebTorrent 的路径都必须退场

本 spec 的新理念不是“优先试 WebTorrent”，而是：**整个项目的正式媒体字节都尽量只走唯一 `WebTorrent` whole-file swarm；新主链正式媒体字节真相只能是满血 `WebTorrent`，任何阻挡它满血成立的路径，都不能被保留成正式路径。**

落到工程上就是：

1. 凡是让新主链附件绕开 `WebTorrent` 正式播放、正式做种、正式可恢复来源判定的路径，都必须删除、隔离成 legacy，或在验收中判失败。
2. 凡是让 `HLS`、原文件直链、CDN 命中、`p2p-media-loader`、临时 range 服务、静态预览或浏览器缓存冒充新主链成功的设计，都属于阻挡满血 `WebTorrent`，必须退场。
3. 凡是因为“浏览器扛不住”“移动端不好做”“首帧更快”“先这样能跑”而削弱 `WebTorrent` whole-file swarm 的方案，都不能进入执行计划。
4. 真正允许保留的只有三类东西：`WebTorrent` 官方能力本身、帮助 `WebTorrent` 满血的薄适配层、以及被清楚标记且不参与新主链验收的 legacy / benchmark 证据。
5. 如果一个成熟轮子、旧支路或临时兼容层挡住唯一 `WebTorrent` 主线，它不是“可选兜底”，而是需要被收口、替换或退场的架构债。
6. 项目级判断统一按“有没有第二真相、第二正式播放链、第二分发链”来审；只要答案是有，就默认不合格，直到它被删掉、收口到 `WebTorrent`，或被隔离成不参与正式体验的证据支路。

## 2. 最新真实烟测已经证明的问题

这份 spec 不是凭感觉写的，而是基于真实浏览器烟测写的。

### 2.1 fresh newcomer 路径已经证明：体验主链大体成立，但同时活着的表面还是偏多

新会话真实进入房间 `1234b` 后：

1. 自动播放仍然成立。
2. 自动暂停仍然成立。
3. 打开 viewer 再退出后，自动播放仍能恢复。
4. 没有立即复现之前那类进入/离开 owner 的明显闪烁。

但同一轮真实采样也证明：

1. `rows = 34`
2. `cards = 128`
3. `previews = 15`
4. `imgs = 127`
5. 同时真正 `playing = 1`

这说明：**当前系统不是“播放逻辑坏了”，而是为了服务很少数真正活跃的视频，浏览器同时背了太多附件表面。**

### 2.2 heavy 会话已经证明：房间越用越重

在已经发送过大量视频图片、已经观看过大量视频图片的真实会话里，再做一轮滚动采样，系统会稳定落在：

1. `cards = 110 ~ 131`
2. `previews = 59 ~ 69`
3. `imgs = 73 ~ 90`
4. 同时真正 `playing = 0 ~ 1`
5. JS heap 维持在 `110MB ~ 120MB` 量级

这说明：

1. **禁止** 再把当前问题解释成“只是单个视频播放行为偶尔有问题”。
2. 当前真正的问题是：**房间使用时间越长，前端保留的媒体表面和媒体对象越多。**

### 2.3 原生浏览器进程已经进入危险区

同一轮压测里，真实 Chrome 进程出现了下面这种量级：

1. 某个原生进程 private memory 在 `2GB` 左右。
2. 某个 renderer private memory 在 `1GB+`。

即便当轮没有必然 100% 马上白屏，这也已经说明：

**当前前端不是离崩溃很远，而是已经进入“继续使用就极有可能拖崩浏览器”的区间。**

### 2.4 监听器 warning 不是噪音

真实控制台持续出现：

1. `MaxListenersExceededWarning` for `"data"`
2. `MaxListenersExceededWarning` for `"close"`
3. `MaxListenersExceededWarning` for `"error"`

这不一定是唯一根因，但它明确证明：

1. 协作分发相关对象确实在累积。
2. 浏览器里的协作分发读流、reader、listener 不是在自然收缩，而是在持续堆。

因此，这份 spec 必须明确：

**禁止** 把 `MaxListenersExceededWarning` 当成“只是阈值偏保守”的 harmless warning。  
在浏览器已重压的前提下，它必须被视作“生命周期预算已经失控”的证据之一。

### 2.5 移动端更早暴露同一根因，桌面端也不能侥幸

移动端浏览器更容易卡死、白屏、被系统杀页，不是另一个独立问题，而是同一组重量失控在更小内存、更弱散热、更激进后台策略下更早爆炸。桌面端内存和 GPU 预算更大，只是把爆炸时间往后推；它同样会被 renderer 原生内存、GPU texture、reader、listener、WebTorrent 会话和大 DOM 拖向卡顿或崩溃。

1. 移动端不能承受桌面端那种“几十个预览表面暂时还没崩”的侥幸。
2. 移动端 autoplay、inline、fullscreen、返回、页面隐藏和系统回收更依赖明确生命周期，而不能依赖浏览器默认行为。
3. 移动端同屏真实 preview `<video>`、hidden probe、MSE buffer、reader、listener 和 WebTorrent 会话预算必须比桌面更紧。
4. 移动端点击自动播放视频进入全屏、返回、再点同一视频，必须复用同一条热源和 owner 真相；**禁止** 因为 viewer/fullscreen 退场清理过猛，把仍在时间线中的自动播放附件误判成“附件当前不可获取”。
5. 桌面端也必须证明长时间滚动、发送、viewer/fullscreen 切换后重对象会回落；**禁止** 因为桌面端暂时没崩，就保留几十个历史视频表面或无限 listener/reader。
6. 桌面端和移动端必须共享同一套播放/全屏/查看器 owner 链；差异只能是预算阈值和浏览器能力适配，不能长出两套业务状态机。

所以后续验收必须同时覆盖桌面端和移动端模拟或真机：桌面端要证明长期高压不会走向 `STATUS_ACCESS_VIOLATION`，移动端要证明更紧预算下不会快速卡死、白屏或返回假失败。

---

## 3. 最高裁决：三个都要，禁止二选一

后续所有计划、实现、评审、验收，都以这三条为最高裁决。凡是只满足其中两条、牺牲第三条的实现，默认都算失败。

### 3.1 禁止为了不崩而削弱唯一 `WebTorrent` 主链

1. **禁止** 通过减少帮助者、减少补齐、减少做种、减少热会话来换浏览器稳定。
2. **禁止** 把“浏览器少背一点”偷换成“群友少帮一点”。
3. **禁止** 把前台减负做成“后端重新接管更多正式字节职责”。
4. **禁止** 把 `WebTorrent` 满血实现推迟成“后续增强”，同时先用 `HLS` / 直链 / 私有分片路径交付正式体验。
5. **禁止** 用“移动端扛不住”或“桌面端内存够”作为理由，给不同浏览器形态各自长出第二套正式分发真相。

### 3.2 禁止为了协同分发强而让浏览器无限背重对象

1. **禁止** 把“群越活跃越强”误写成“前端必须一直活着所有历史媒体会话”。
2. **禁止** 把“继续帮助后人”误写成“前台一直挂着几十个真实 `<video>` 表面”。
3. **禁止** 把“后台补齐继续做”误写成“前台继续持有大量重媒体对象和重 listener”。

### 3.3 禁止为了省资源把体验主链重新打坏

1. **禁止** 让预览再变成“先像占位，再卡一下，再开始播”。
2. **禁止** 让自动播放/自动暂停再长回闪烁、抽搐、冷开、回退。
3. **禁止** 让 viewer / fullscreen / 退出归位重新打破无缝感。

一句话：

**群友之间可以更强，浏览器里必须更轻，用户眼前必须更顺。**

---

## 4. 什么东西算“浏览器里的重对象”

这份 spec 必须先把“重对象”定义清楚，不然后续实现最容易偷换概念。

### 4.1 可见重对象

下面这些只要活着，就会明显增加浏览器前台负担：

1. 真实 `video.message-video-preview`
2. 真实 canonical player 表面
3. 真正可见的大图/原图表面
4. hidden-stage 里仍持有真实媒体源的预热表面
5. 可见区内的首帧恢复视频底板

### 4.2 不可见但仍然昂贵的重对象

下面这些即使用户暂时看不见，也会继续拖前台或原生进程：

1. 已接入正式播放源的 preview `<video>`
2. 正在做 metadata / loadeddata / canplay / seek 的隐藏 `<video>`
3. 房间级媒体会话
4. 协作分发会话
5. 零引用但仍保活的 whole-file backfill 会话
6. `streamURL` 背后的 reader / range reader
7. 对 swarm/torrent 持续绑定的 data/close/error/wire/noPeers 监听器
8. presence heartbeat / join ticket refresh / keepalive 定时链

### 4.3 禁止只盯 DOM，不盯原生资源

后续实现和验收时：

1. **禁止** 只看 DOM 数量就宣布“已经轻了”。
2. **禁止** 只看 JS heap 就宣布“已经稳了”。
3. **禁止** 忽略 GPU / renderer 原生内存、listener 数、reader 数、零引用保活会话数。

因为这次真实问题已经证明：

**真正把浏览器拖崩的，不只是 DOM，而是 DOM、媒体源、读流、会话、原生进程内存一起膨胀。**

### 4.4 重量必须按设备能力裁决

同一条视频在不同设备上不是同一份重量。成熟信息流不会把最高分辨率、最高码率、最重封装默认扔给所有设备；它们会按网络、buffer、硬解能力和当前交互状态选源。

`koko` 的裁决是：

1. 播放源必须是 source descriptor，而不是卡片自己猜一个 URL。
2. `MediaCapabilities.decodingInfo()` 或等价探针可以参与 codec / 分辨率 / 码率选择。
3. `requestVideoFrameCallback()` 或等价探针必须证明正式 owner 的帧提交真实稳定。
4. 弱网、低端设备、移动端、省电模式和后台页必须主动降级窗口与预热预算。
5. **禁止** 把设备能力降级偷换成“静默卡顿”“静默失败”或“恢复第二正式播放链”。

## 5. 根因级架构判断

后续执行必须直接对准根因，不准继续修表面。

这里的根因不是“列表里视频太多”这么浅，而是系统把几种真相混成了一种：

1. 消息存在真相：房间历史里确实有这些附件。
2. 窗口表达真相：用户当前或马上会看到哪些附件。
3. 播放接管真相：哪一个附件正在被唯一正式播放器服务。
4. 协作分发真相：哪些附件仍对群体分发有价值。
5. 浏览器重量真相：哪些对象允许持有真实媒体源、reader、listener、解码和 GPU 表面。

成熟信息流的关键就是把这五种真相拆开；当前 `koko` 的危险点，是某些路径仍会把“存在 / 可能会看 / 可能要帮 / 未来可播”直接升级成“现在就重活着”。

### 5.1 当前根因之一：房间级媒体附件集合太大

当前逻辑存在一个明显危险点：

1. 媒体编排把“当前房间全部消息里的媒体附件”当成活集合来同步。
2. 这会让大量并不在可见区、也不在近视口、甚至短时间根本不会被用户看到的附件，继续保有媒体会话或预览收敛路径。

所以这份 spec 必须写死：

1. **禁止** 把“在当前房间里出现过”偷换成“当前必须活着”。
2. **禁止** 把“存在于时间线历史”偷换成“必须继续保有真实预览对象”。
3. **禁止** 出现 `activeWindowIds.size === 0` 这类整房回退，把窗口观测缺失误处理成全量活集合。

### 5.2 当前根因之二：可见窗口预算太宽

当前烟测已经证明，在窗口附近会同时活着大量附件卡片、图片、视频 preview。

所以这份 spec 必须写死：

1. **禁止** 继续用“overscan 先大一点，体验比较稳”这种经验主义处理万人群聊媒体列表。
2. **禁止** 在没有预算证明的前提下，为了减少空白或为了首帧更快，继续扩大窗口附近真实媒体表面的数量。

### 5.3 当前根因之三：协作分发零引用保活太重

当前协作分发运行时允许零引用会话因为：

1. `eagerCompleting`
2. `locallyComplete`

而继续保活。

这条产品语义本身并不一定错；错的是它当前没有区分：

1. 对群有价值的“继续帮助”
2. 对浏览器有害的“继续背着重媒体对象、重 reader、重 listener”

所以这份 spec 必须写死：

1. **禁止** 把“继续帮助后人”实现成“继续保留重表面和重引用”。
2. **禁止** 把“零引用可保留”理解成“零引用但一切都照旧活着”。

### 5.4 当前根因之四：预览真相、自动播放真相、协同主链真相没有按重量分层

现在最危险的误区是：一旦某条附件以后可能要播、以后可能要帮、以后可能要切 owner，就让前台立刻背一套真实媒体对象。

这份 spec 必须明确：

1. 预览真相需要成立。
2. 自动播放真相需要成立。
3. 协同分发真相需要成立。
4. 但这三者**禁止** 默认都落成同样重的浏览器对象。

一句话：

**真相可以同时成立，重量不能同时拉满。**

### 5.4.1 当前根因之四的补充：预热缺少代次和取消边界

信息流预热不是“提前做完所有事”，而是“在当前代次里做一点最可能马上用到的事”。旧窗口、旧 owner、旧 viewer、旧帮助窗口一旦失效，旧预热结果就必须失效。

所以后续实现必须写死：

1. locator / preview / bootstrap / hidden probe / stream reader 必须被 `AbortSignal + generation` 绑定。
2. 旧代次任务完成后，**禁止** 写回新的 ready / playable / preview truth。
3. warm candidate 只允许有限个，并且必须能被窗口缩回取消。
4. 预热成功只能证明“当前预算下可接管”，不能升级成“长期正式可播真相”。

### 5.5 当前根因之五：缺少一个收口信息流重量的 canonical owner

现有模块分别知道一部分事实：

1. `房间消息窗.ts` 知道当前虚拟窗口和近视口。
2. `聊天媒体编排.ts` 知道哪些附件可能要建立媒体会话。
3. `媒体运行时.ts` 知道 viewer、自动播、heavy policy 和 inflight 预算。
4. `资产协作分发运行时.ts` 知道 `WebTorrent` 会话、帮助态、补齐态和零引用保活。

但如果没有一个明确的“信息流媒体预算 owner”把这些事实压成同一张重量裁决表，系统就容易继续出现：

1. 窗口真相还没到，编排层先按整房附件启动。
2. 当前 owner 已切走，旧 preview / locator / reader 继续跑完。
3. 协作帮助仍有价值，却被错误留成前台重播放态。
4. 为了“看起来丝滑”，多个模块各自保留一份真实媒体对象。

这份 spec 的裁决是：

1. 必须有唯一的“信息流媒体预算 owner”裁决每个附件当前属于 `重播放 / 轻预热 / 冷表达 / 轻帮助` 哪一类。
2. 这个 owner 可以落在现有 `媒体运行时.ts` / `聊天媒体编排.ts` 的收口边界里，也可以抽成一个很薄的新模块；但无论哪种实现，都必须删除旧的重复判断路径。
3. **禁止** 让这个 owner 变成第二套播放器、第二套 WebTorrent runtime、第二套房间媒体会话表或第二套消息真相。
4. **禁止** 新增只转发、不压缩旧逻辑的 wrapper / manager / coordinator 垃圾层。

---

## 6. 最终运行真相：群里强协同，浏览器轻负担

这份 spec 最终要把系统收成下面这个形态。

### 6.1 房间级语义

1. 群里越活跃，群友之间的分发能力越强。
2. 看过某段视频的群友，仍应尽量继续帮助后来者。
3. 后台补齐、做种、热协同仍然属于系统正式主链的一部分。

### 6.2 浏览器级语义

1. 浏览器前台只保留当前真正需要的少量重对象。
2. 离开可见窗口、离开近视口、离开当前用户路径的对象，必须迅速变轻。
3. “继续帮助后人”的收益，**禁止** 默认等于“前台一直背着真实媒体对象”。
4. 浏览器事件、IntersectionObserver、滚动位置、fullscreen、visibilitychange 和 pagehide 都只是输入信号，必须先进入应用运行时或媒体预算 owner 裁决，不能由组件局部直接宣布重量真相。
5. 桌面端、移动端、弱网、后台页和低硬解能力设备必须共享同一套裁决模型，再按能力自动收紧窗口和预热预算，而不是等崩溃后再恢复。

### 6.3 用户级语义

1. 用户进入房间后，不管是新人还是老用户，都应很快看到稳定预览。
2. 当轮到某条视频自动播放时，它必须直接在稳定预览上无缝接着播。
3. 当离开当前自动播放视频时，它必须平滑退场，不能抽、不能闪、不能先冒冷表面。
4. 长时间发送、滚动、观看后，用户仍应感觉顺，不应感觉系统越用越重。
5. 用户点击当前自动播放视频进入 viewer / fullscreen，再返回群聊，再点击同一视频，必须继续沿着同一附件、同一播放 owner、同一热源真相恢复；**禁止** 因为退场清理或 route retire 把仍有效附件显示成“附件当前不可获取”。

---

## 7. 窗口级预算：屏幕附近只允许活必要表面

窗口预算不是 UI 小优化，而是整个信息流模型的第一道阀门。全房历史可以存在，消息索引可以完整，协作收益可以保留；但只有窗口和少量邻近候选可以进入前台重媒体调度。

### 7.1 稳态预算

在任何稳态下：

1. **禁止** 可见区附近同时活着大量真实 `<video>` 预览面。
2. **禁止** 为了服务 `1` 条当前自动播视频，前台同时保留几十条历史视频的真实可读媒体表面。
3. **禁止** 非 owner 视频把正式播放源长期挂在自己的 preview `<video>` 上。
4. **禁止** 用“大一点的 overscan”掩盖预热/接管能力不足；overscan 只能扩大轻表达窗口，不能无限扩大重对象窗口。
5. 桌面端和移动端都必须有稳态回落要求；移动端阈值更紧，但桌面端同样禁止长期保留大量真实 preview `<video>`、hidden probe、MSE/reader 和 near-window 图片解码。

### 7.2 交接预算

在 owner 交接、viewer 打开、viewer 关闭、退出全屏归位这些短暂窗口里：

1. 允许存在极短暂的桥接表面。
2. **禁止** 把这个桥接窗口做成长期常驻。
3. **禁止** 以“为了防闪烁”为理由，让大量非当前卡片也一直维持重预览对象。

### 7.3 首屏预算

新人和老用户回房的首屏：

1. 必须快速收敛到稳定预览。
2. **禁止** 通过扩大首屏活对象数量来换“看起来比较满”。
3. **禁止** 通过让整屏附件同时 metadata/preload 来换首屏稳定。

### 7.4 短视频信息流三层预算

后续实现必须把时间线视频统一压成三层，不允许每个卡片自由决定自己要多重：

1. **当前重播放层**
   当前自动播 owner、viewer owner、fullscreen owner 或正在正式接管的唯一 `Video.js v10` 宿主。它可以持有正式播放源、解码、帧监控、range/stream reader 和必要的播放状态，但同一时刻只能服务一个正式 owner。
2. **邻近轻预热层**
   只允许当前窗口和少量 warm candidates 持有轻预热工作，例如 locator、preview truth、metadata、首片段、首帧收敛、codec 能力判断和有限 range。它必须服从第 14.5 节的硬数量上限，并且必须能被窗口缩回、owner 切换、页面隐藏或代次失效取消。
3. **远处冷表达层**
   远离当前窗口、当前 owner、当前 viewer、当前帮助窗口的历史附件，只能保留消息真相、轻索引、尺寸、低成本封面/占位、缓存状态和协作价值摘要；**禁止** 保留真实 `<video>`、重 reader、持续 metadata 探针、未取消的 preview 任务或前台级 WebTorrent 流引用。

这三层只决定浏览器重量，不改变消息是否存在，也不改变 `WebTorrent` 长期协作主链。它们必须可以在测试和烟测里被观测到：某附件为什么重、为什么预热、为什么冷、为什么还在轻帮助，都要能解释。

---

## 8. 房间级媒体会话预算：禁止把整房历史都养活

### 8.1 活媒体会话集合必须收缩到“当前真实需要”

后续实现必须遵守：

1. **禁止** 把“当前房间全部附件”直接当作活媒体会话集合。
2. **禁止** 让不在可见区、不在近视口、不在当前帮助窗口的附件继续保有完整媒体会话。
3. **禁止** 把“看过一次”直接升级成“长期前台常驻媒体会话”。
4. **禁止** 把“曾经成功预览 / 曾经完成补齐 / 本地已有缓存”直接升级成“当前重播放或重预热”。
5. 活媒体会话必须从窗口真相、owner 真相、viewer/fullscreen 真相、帮助窗口和设备预算共同推导，不能由房间附件数组单独推导。

### 8.2 房间里消息还在，不等于浏览器必须继续背真实媒体对象

这一点必须反复写死：

1. 消息仍在房间历史里，这是真相。
2. 这条消息未来仍可能再次进入视口，这是真相。
3. 这条附件仍可能继续帮助后人，这也是真相。
4. 但这些真相都**不等于**浏览器前台必须继续背真实 preview `<video>`、metadata 探针、冷 reader、首帧恢复链。

### 8.3 图片和视频都要减，但减法方式不同

1. 图片要优先减真正昂贵的大表面和重复解码负担。
2. 视频要优先减真实 `<video>`、metadata、preview source、stream reader、seek/loadeddata 链。
3. **禁止** 用同一套偷懒策略粗暴处理图片和视频。
4. 图片可以更偏向尺寸、缩略图、解码缓存和 `loading=lazy` / 近视口加载；视频必须额外约束播放源、解码器、reader、MSE buffer、rVFC 探针和协作流引用。
5. 图片和视频都必须服从同一个媒体预算 owner 的窗口裁决，但预算 owner 给出的动作可以不同。

---

## 9. 协作分发预算：帮助可以继续，重量必须降下来

这一节是整篇 spec 最重要的边界之一。

### 9.1 对群有价值的帮助链必须继续

1. **禁止** 让浏览器减负变成“看完就不继续帮后人”。
2. **禁止** 让零引用会话一刀切地全部立即销毁。
3. **禁止** 让系统重新回到“只有正在看的那一条才帮，别的都不帮”的弱协同。

### 9.2 继续帮助不等于继续背重对象

后续实现必须显式区分两种状态：

1. **轻帮助态**  
   对 swarm 仍有帮助，但不再持有前台重媒体对象。
2. **重播放态**  
   当前就在为用户提供预览/播放/交接，因此允许持有重对象。

这节的硬禁令是：

1. **禁止** 把轻帮助态和重播放态混成一种状态。
2. **禁止** 让零引用会话继续保留真实 preview `<video>` 或同等级重 reader，只因为“以后也许还能帮人”。
3. **禁止** 把“轻帮助态”误执行成“直接不再可发现、不再续租、不再对 swarm 提供有效帮助”。
4. **禁止** 让轻帮助态继续挂前台播放 source、hidden probe、MSE buffer 或时间线 preview consumer。
5. 轻帮助态必须能说明自己保留的到底是 peer 价值、store 价值、locator 价值还是补齐价值；不能用“可能有用”保留整套重链。

为避免和 `2026-04-23-WebTorrent群聊越活跃越强的极限协同分发.md` 打架，这里还要把“轻帮助态”拆清楚：

1. **常驻轻帮助会话** 是浏览器前台仍保留的运行时 session，有 listener、presence、swarm 参与或补齐调度，但没有前台播放级 reader 和媒体表面。
2. **冷帮助索引** 是已经从前台运行时降级出去的协作价值，例如本地完整字节、locator、metainfo、做种资格、可恢复来源记录和下次可重建的帮助任务意图。
3. 第 14.5 节的 `zeroRefLightHelpSessionCount` 只限制第一类“常驻轻帮助会话”，**不等于** 产品层只保最近若干条帮助任务。
4. 常驻轻帮助会话超预算时，只能降级到冷帮助索引或持久化完成态；**禁止** 删除真实本地收益、抹掉完整 peer 资格、停止可发现能力，或把“运行时降级”偷换成“群友不再帮后人”。

### 9.3 协作收益要尽量保住，但必须转成轻态保留

对高活跃群聊来说，正确方向不是“都删掉”，而是：

1. 能保留对群有价值的协作结果，就尽量保留。
2. 但保留时必须尽快从重态降到轻态。
3. **禁止** 把“历史协作成果”继续绑在昂贵的前台对象上。
4. 轻态保留的是对群有价值的协作能力，不是对浏览器有害的前台重量。

### 9.4 WebTorrent 满血不等于前台无限重

`WebTorrent` 的满血目标是 whole-file swarm、可 seek、可边下边播、可补齐、可做种、服务器删源后仍能由完整 peer 与片段帮助者共同形成可恢复来源接力。这个目标和浏览器轻负担不冲突；冲突的是把每个协作资产都保持成前台播放级重量，或者反过来把片段帮助者误杀成“没用”。

换句话说：轻帮助态是为了让 `WebTorrent` 更满血，而不是退出主链。它要保住 swarm、完整性、发现能力、做种收益和失败态真相，同时释放前台 `<video>`、隐藏 probe、MSE、range reader、解码器和 UI 表面。

后续实现必须遵守：

1. `WebTorrent` 正式播放必须继续走 `service worker/createServer`、`streamTo` 或 `streamURL` 这条官方实链路。
2. 当前重播放 owner 可以持有正式 stream reader；轻帮助态不能持有前台播放级 reader。
3. `torrent.paused`、`torrent.done`、`locallyComplete`、`eagerCompleting` 不能单独决定浏览器重量，它们必须被媒体预算 owner 解释成重播放、轻预热、轻帮助或冷表达。
4. `p2p-media-loader` 只能作为 HLS/DASH segment-level 技术评估或 legacy 支路，不能进入新主链正式播放 runtime，更不能伪装成 whole-file swarm 或 `24 小时` 后的存活证明。
5. 凡是绕开 `WebTorrent` whole-file swarm 才能成立的“丝滑”，只能记为 legacy / 实验支路证据；如果对象是新主链附件，验收必须判失败，不能记为项目唯一正式播放链成功。
6. 桌面端和移动端必须共用同一套 `WebTorrent` 正式链路裁决；差异只能体现在 warm 数量、reader 数量、后台释放速度和 codec 能力降级上。

## 10. 预览真相：不要静态预览图，但必须先有稳定预览

### 10.1 这份 spec 不接受“没有预览图，所以先占一下再播”

这里必须说清楚：

1. 用户不需要传统静态预览图。
2. 但系统必须先给出稳定预览真相。
3. **禁止** 把“没有静态预览图”偷换成“可以先露冷表面、冷视频、冷 metadata 链”。
4. poster、尺寸、低成本封面、模糊底图可以属于冷表达或轻预热，但不能冒充已经可无缝接管的 preview truth。

### 10.2 预览不是装饰，而是自动播放前置真相

1. 当某条视频即将进入自动播放 owner 前，它必须先拥有稳定预览真相。
2. **禁止** 让自动播放 owner 裁决跑在预览真相前面。
3. **禁止** 让用户先看到“类似占位”的冷表面，再等自动播放启动。
4. preview truth 必须带代次；旧代次预览完成后不能把已经离窗、离 owner 或被新 viewer 接管的附件写回可播。
5. 当前 owner 从预览接入正式播放时，必须保持尺寸、视觉表面和时间连续性，避免 CLS、闪白、冷帧、时间轴回退。

### 10.3 新人和老用户都一样

1. **禁止** 只有老用户靠历史缓存看起来顺。
2. **禁止** 只有新用户首屏勉强顺，老用户重返房间又露冷表面。
3. 新人首次进房和老用户回房，都必须先尽快收敛到稳定预览，再进入自动播放。

## 11. 进房、滚动、观看、发送四条主链

这四条链是后续所有实现和验收的主线，**禁止** 只修其中一条。

### 11.1 新人首次进房

必须做到：

1. 近视口视频尽快收敛成稳定预览。
2. 自动播放只在稳定预览基础上接管。
3. **禁止** 出现“先占一下、先冷一下、再接着播”。

### 11.2 老用户回房

必须做到：

1. 已有本地收益可以帮助更快收敛。
2. 但不能靠历史脏表面、历史脏帧、历史错误保活对象来伪装稳定。
3. **禁止** 老用户回房后因为历史压力更大，反而更容易拖崩浏览器。

### 11.3 长时间滚动看历史

必须做到：

1. 旧 owner 退场平滑。
2. 新 owner 进入平滑。
3. 列表前后滚很久后，浏览器里同时活着的重对象不持续单向膨胀。
4. **禁止** 滚动得越久，页面越重、越卡、越容易崩。
5. 快速滚动时允许跳过部分轻预热，优先保护滚动 INP、LoAF 和内存预算；**禁止** 为追每一条都预热而拖死滚动。
6. 滚动停止后才能按当前窗口重新收敛 warm candidates，旧滚动代次的任务必须取消。

### 11.4 大量发送图片视频

必须做到：

1. 新草稿、新消息、新附件加入后，不把浏览器前台直接推入不可回收重压。
2. 图片和视频上传成功后，预览和协同主链仍能成立。
3. **禁止** 发送量一大，浏览器就因为历史媒体对象和新媒体对象叠加而走向崩溃。
4. 新发送附件可以优先获得短暂重预热或本地热源接管，但离开发送/查看路径后也必须回到统一预算。
5. **禁止** 因为本地刚上传过、刚播放过、刚补齐过，就绕过窗口预算长期保留前台级对象。

---

## 12. 后台、离场、隐藏页策略

### 12.1 后台必须减负

浏览器进入 `hidden / background / pagehide` 后：

1. **禁止** 继续保留对前台体验无价值的重表面。
2. **禁止** 继续为不可见页维持大规模 metadata/seek/loadeddata 级重媒体活动。
3. **禁止** 把后台页仍当成前台一样使用。
4. 必须释放或暂停前台级 video source、hidden probe、rVFC 探针、warm candidate、MSE buffer 和非必要 reader。
5. 移动端 `visibilitychange/pagehide/freeze` 必须更激进，优先避免系统杀页和返回后假失败。

### 12.2 后台不等于主链断掉

但同时：

1. **禁止** 把后台减负偷换成主链直接断掉。
2. 如果某些协作收益仍对群有价值，应转成轻态继续保留。
3. 后台策略必须显式区分“前台播放体验态”和“群体协作收益态”。
4. 返回前台后，必须按当前窗口和当前 owner 重新裁决，而不是恢复隐藏前的全部重对象。
5. 如果页面曾被浏览器 discard 或 bfcache 恢复，必须重新校验 WebTorrent route、source generation、viewer/fullscreen owner 和 preview truth，不能信任旧 DOM 表面。

---

## 13. 失败态说真话，但禁止把失败态变成默认体验

### 13.1 真失败必须说真话

1. 当前重试窗口内确实没有可恢复来源，就说没有在线种子。
2. 内容已删除就说内容已删除。
3. 浏览器能力边界触发就必须按真实能力降级。
4. **禁止** 因为没有单个完整 peer，就直接宣布没有在线种子；只要完整 peer、片段帮助者、本地权威字节组合仍能提供首播关键字节和持续补齐能力，就必须继续接力。
5. **禁止** 因为存在几个零散片段，就假装已经 ready；是否 ready 只看当前客户端在当前重试窗口里是否真实拿到了可恢复来源。

### 13.2 正常链路禁止长期停在“等待中”

1. **禁止** 把“先露等待中/占位/冷表面”当成正常体验。
2. **禁止** 因为失败态已经写清楚，就默认让用户常常看到失败前状态。
3. 正常链路的目标必须是：在用户真正看到那条卡片前就尽量完成预览收敛。

### 13.3 viewer / fullscreen 退场不能制造假失败

用户点当前自动播放视频进入 viewer 或 fullscreen，再返回时间线时，这条附件仍在同一房间、同一消息、同一协作资产里。退场清理只能释放临时重对象，不能删除附件可获取真相。

后续实现必须保证：

1. viewer / fullscreen 关闭只结束对应 owner 会话，不得提前 retire 仍被时间线 owner 引用的 WebTorrent route 或正式 source。
2. 同一附件从自动播放进入 viewer / fullscreen，再返回自动播放，必须保持热源和代次连续。
3. 如果真实源不可用，必须能说明是无 peer、源删除、codec 不支持、权限或网络失败；**禁止** 因为本地生命周期清理错误显示“附件当前不可获取”。
4. 这个路径必须纳入浏览器烟测和状态转换测试，不能只测打开一次 viewer。

---

## 14. 硬预算与硬红线

这节不是为了把文档写得像参数表，而是为了让后续任何人都不能再说“感觉差不多”。

### 14.1 绝对红线

下面几条必须永远成立：

1. **禁止** `activeFormalPlayerCount > 1`
2. **禁止** `autoplayOwnerCount > 1`
3. **禁止** 在稳态下让可见区附近长期存在大批真实视频预览面
4. **禁止** 在长时间滚动与发送后，重对象数量持续单向膨胀而不回落
5. **禁止** 在零引用后继续保留无上限的重协作分发会话
6. **禁止** 同一附件同时处于两套正式播放源或两套可播真相
7. **禁止** viewer/fullscreen 退场把仍在时间线中的有效附件清成“不可获取”
8. **禁止** 桌面端使用“内存更大所以可以无限重”的预算口径
9. **禁止** 移动端使用和桌面端同样宽松的重对象预算

### 14.2 浏览器稳定性红线

后续执行时必须建立正式预算并纳入测试：

1. 同屏与近视口真实 `<video>` 预览面上限
2. 房间级活媒体会话上限
3. 零引用轻帮助态与重播放态的数量上限
4. preview 收敛时限
5. 长时间滚动/发送/观看后的对象回落要求
6. listener / reader / 原生进程内存越线规则
7. 桌面端长时间高压下的同屏 video、image、reader、listener、GPU/renderer memory 和回落规则
8. 移动端或移动模拟下的同屏 video、image、reader、listener 和 renderer memory 越线规则
9. viewer/fullscreen 打开、返回、再次打开同一视频的热源连续性规则
10. source descriptor 选择、codec 能力判断和降级原因记录规则

### 14.3 禁止只有口号，没有数字

1. **禁止** 在 plan 阶段仍然不执行第 14.5 节的 `koko v0` 数字预算。
2. **禁止** 在没有浏览器烟测数据的前提下拍脑袋给预算。
3. **禁止** 用“用户感觉还好”代替预算验证。
4. Core Web Vitals 必须进入前台体验预算：`LCP <= 2.5s`、`INP <= 200ms`、`CLS < 0.1` 是公开基线；`koko` 还必须加上媒体重对象、reader/listener、LoAF、rVFC 和原生内存预算。
5. 对 120Hz 场景，`INP <= 200ms` 只是交互底线，不是滚动和接管丝滑证明。

### 14.4 120Hz 丝滑目标必须变成可测红线

`120Hz` 不是一句“看起来顺”的口号。它在前台交互上的含义是：每帧约 `8.33ms`，而 JS、style、layout、paint、视频合成和浏览器内部工作都要分这个预算。

后续计划和实现必须把它拆成下面几条可测红线：

1. 前台滚动、owner 交接、viewer 打开/关闭、全屏归位的目标帧预算按 `8.33ms` 设计；JS / style / layout 单项不得把整帧吃满。
2. `steadyScrollLongAnimationFrameOver50Delta == 0` 只是底线，不是丝滑证明；120Hz 验收还必须记录帧时间分布，不能只看是否超过 `50ms`。
3. `steadyScrollLargeLayoutOrStyleOver40msDelta == 0` 只是底线；120Hz 验收必须继续压低 layout / style 长尾，避免偶发大帧破坏滑动手感。
4. 视频帧必须用 `requestVideoFrameCallback()` 或等价探针记录提交节奏、掉帧和处理延迟；**禁止** 只看 `<video>.paused` / `playing` 就宣布播放丝滑。
5. 播放源选择必须允许用 `MediaCapabilities.decodingInfo()` 或等价能力判断来避开当前设备不适合硬解的 codec / 分辨率 / 码率。
6. 120Hz 目标优先约束页面交互、滚动、接管和合成；**禁止** 把它偷换成“把所有 30fps / 60fps 源视频强行插帧成 120fps”。
7. 低端设备、弱网、后台页或省电模式下允许降级到更低目标，但必须由媒体预算 owner 明确降级原因和状态，不能静默退化成卡顿。
8. 连续滚动期间允许削减 warm candidates，优先保住滚动帧时间、INP 和内存；滚动停止后再按当前窗口恢复轻预热。
9. 视频帧探针必须和 owner 代次绑定，旧 owner 的 rVFC callback 不能继续写入当前 owner 指标。

这组红线必须和第 7 节窗口预算、第 9 节轻帮助态、第 15.5 节信息流媒体预算 owner 一起执行；**禁止** 为了追 120Hz 直接牺牲 `WebTorrent` 主链或恢复第二正式播放链。

### 14.5 `koko v0` 初始数字预算

公开性能资料只能给出页面级底线：Core Web Vitals 的 `LCP <= 2.5s`、`INP <= 200ms`、`CLS < 0.1`，Chrome Long Animation Frames 的 `50ms` 长动画帧边界，以及 Lighthouse / web.dev 对大 DOM 的 `800` 节点提醒、`1400` 节点过大警戒。视频信息流没有官方通用“允许几个 `<video>`”标准，所以 `koko` 必须先用下面这组保守 v0 预算起步：它们不是永久拍脑袋数字，而是执行计划的初始硬门槛；后续只能用真实桌面端和移动端烟测数据收紧或有证据地调整，不能口头放宽。

#### 14.5.1 桌面端前台稳态预算

1. `activeFormalPlayerCount <= 1`
2. `autoplayOwnerCount <= 1`
3. `currentHeavyVideoOwnerCount <= 1`
4. `bridgeVideoSurfaceCount <= 1`，并且单次桥接窗口 `<= 800ms`
5. `liveVideoElementWithSrcCount <= 6`，其中正式播放 `<= 1`、hidden probe `<= 2`、轻预热 preview `<= 4`
6. `warmCandidateCount <= 4`
7. `inflightPreviewBootstrapCount <= 4`
8. `activeStreamReaderCount <= 1`，只能属于当前重播放 owner
9. `lightHelpForegroundReaderCount == 0`
10. `activeMediaSessionCount <= 12`
11. `zeroRefHeavySessionCount == 0`
12. `zeroRefLightHelpSessionCount <= 32`，这里的计数只指浏览器前台常驻轻帮助会话；超出必须降到冷帮助索引、持久化完成态或 locator 可恢复态，不能裁掉产品层帮助承诺
13. 单个 torrent/session 对 `data / close / error` 这类事件的业务 listener 各自 `<= 3`，整轮烟测 `MaxListenersExceededWarning == 0`
14. 时间线活 DOM 节点目标 `<= 800`，整页活 DOM 节点硬警戒 `<= 1400`；超过必须证明虚拟列表和冷表达仍在回落，不能继续放大窗口
15. 渲染消息行 `<= 40`，近窗口附件卡片 `<= 80`；多附件消息可以存在，但远处附件只能冷表达
16. 近窗口真实解码图片表面 `<= 24`，可见大图/原图表面 `<= 8`
17. JS heap 稳态目标 `<= 180MB`，压力烟测后回落目标 `<= 220MB`
18. renderer private memory 稳态目标 `<= 700MB`，硬失败线 `>= 1GB` 或连续三次采样只增不回落

#### 14.5.2 移动端或移动模拟前台稳态预算

1. `activeFormalPlayerCount <= 1`
2. `autoplayOwnerCount <= 1`
3. `currentHeavyVideoOwnerCount <= 1`
4. `bridgeVideoSurfaceCount <= 1`，并且单次桥接窗口 `<= 500ms`
5. `liveVideoElementWithSrcCount <= 3`，其中正式播放 `<= 1`、hidden probe `<= 1`、轻预热 preview `<= 2`
6. `warmCandidateCount <= 2`
7. `inflightPreviewBootstrapCount <= 2`
8. `activeStreamReaderCount <= 1`，只能属于当前重播放 owner
9. `lightHelpForegroundReaderCount == 0`
10. `activeMediaSessionCount <= 6`
11. `zeroRefHeavySessionCount == 0`
12. `zeroRefLightHelpSessionCount <= 8`；进入 hidden / pagehide 后 `<= 4`；这里同样只限制移动端前台常驻轻帮助会话，不允许解释成“移动端默认少帮或不帮”
13. 单个 torrent/session 对 `data / close / error` 这类事件的业务 listener 各自 `<= 2`，整轮烟测 `MaxListenersExceededWarning == 0`
14. 时间线活 DOM 节点目标 `<= 500`，整页活 DOM 节点硬警戒 `<= 900`
15. 渲染消息行 `<= 24`，近窗口附件卡片 `<= 48`
16. 近窗口真实解码图片表面 `<= 12`，可见大图/原图表面 `<= 4`
17. JS heap 稳态目标 `<= 90MB`，压力烟测后回落目标 `<= 120MB`
18. renderer private memory 稳态目标 `<= 350MB`，硬失败线 `>= 500MB` 或连续三次采样只增不回落

#### 14.5.3 交互、视频帧和秒开预算

1. Core Web Vitals：`LCP <= 2.5s`、`INP <= 200ms`、`CLS < 0.1`；`koko` 本地目标是核心交互 `INP <= 100ms`，超过 `150ms` 进入阻断调查。
2. Long Animation Frames：压力烟测新增 `LoAF > 50ms` 的计数必须为 `0`；如果真实设备偶发不可避免，必须记录触发栈、帧阶段和媒体预算快照，不能只写“机器慢”。
3. 120Hz 滚动与 owner 交接：目标帧 `8.33ms`，`p95 <= 8.33ms`、`p99 <= 16.67ms`；60Hz 设备 `p95 <= 16.67ms`。
4. JS / style / layout 单项在 120Hz 目标下 `p95 <= 4ms`，在 60Hz 目标下 `p95 <= 8ms`。
5. 当前正式 owner 的 `requestVideoFrameCallback()` 探针必须显示连续播放 `5s` 内掉帧率 `< 5%`，处理延迟 `p95 <= 20ms`。
6. 当前窗口 preview truth 收敛：桌面端 `<= 1200ms`，移动端 `<= 1800ms`。
7. 已轻预热附件进入自动播放 owner：桌面端 `<= 250ms`，移动端 `<= 400ms`。
8. 冷 WebTorrent 正式路径在 `0-24 小时` 服务器强参与和可用 peer 条件下首帧提交：桌面端 `<= 2000ms`，移动端 `<= 3000ms`；超过只能记为冷启动失败或降级原因，不能冒充秒开。
9. viewer / fullscreen 打开：已自动播放 owner 进入 viewer/fullscreen `<= 250ms`；返回时间线自动播放恢复 `<= 250ms`；再次点击同一视频出现“附件当前不可获取”的次数必须为 `0`。
10. WebTorrent route drain：正式 source 或 browser tailwave 最后一个消费者离开后，route drain 不得短于 `2000ms`，并必须由 ref-count / generation 决定何时释放；**禁止** 用固定短 timeout 直接 retire 仍可能被浏览器读取的 `/webtorrent/...` route。

#### 14.5.4 状态冻结和调参规则

1. 这些数字进入 plan 后就是硬门槛，测试默认按它们失败；任何放宽都必须附带真实桌面端、移动端或移动模拟烟测数据。
2. 如果某个数字因为真实设备差异必须分档，只能由信息流媒体预算 owner 按设备能力输出 `desktop / mobile / lowEnd / hidden` 档位，不能由组件私自判断。
3. 每轮压力烟测必须记录 `budgetSnapshot`：DOM、video、image、activeMediaSession、warmCandidate、reader、listener、WebTorrent peer/download/upload、JS heap、renderer memory、LoAF、rVFC、CWV、owner generation。
4. `budgetSnapshot` 必须能解释每个重对象为什么存在；解释不出来的重对象默认是泄漏。
5. 调参顺序只能是先减少前台重量、取消旧代次、收紧 warm window、修正 source/reader 生命周期；**禁止** 先削弱 `WebTorrent` 主链、减少帮助者或恢复第二正式播放链。
6. `zeroRefLightHelpSessionCount` 超限时，调度器必须按协作价值、最近活跃、完整度、当前房间需求和设备档位，把常驻轻帮助会话降级为冷帮助索引；**禁止** 用“预算超了”作为删除本地完整字节、撤销 peer presence、停止可恢复来源记录或只保最近几条的理由。

## 15. 模块职责边界

### 15.1 `房间消息窗.ts`

职责：

1. 窗口附近消息与附件表面的表达
2. 可见区与近视口预算的落地
3. 当前 owner 的表面承接
4. 将滚动、IntersectionObserver、viewport、overscan 变化转成窗口信号交给媒体预算 owner

禁止：

1. **禁止** 把整房附件都长成真实前台预览对象
2. **禁止** 把“为了看起来顺”实现成无限增加可见窗口附近的重表面
3. **禁止** 自己偷偷长第二套媒体生命周期真相
4. **禁止** 在窗口观测缺失时回退成整房活集合

### 15.2 `聊天媒体编排.ts`

职责：

1. 真实需要的媒体会话编排
2. 预览收敛、播放、查看器、草稿与恢复的协调
3. 按媒体预算 owner 的裁决启动、降级、取消 locator / preview / bootstrap / probe
4. 维护 viewer/fullscreen 和时间线 owner 的热源连续性

禁止：

1. **禁止** 直接把当前房间全部附件都当成活媒体会话集合
2. **禁止** 把历史存在真相偷换成当前活对象真相
3. **禁止** 把所有协作收益都绑定到当前前台重会话
4. **禁止** viewer/fullscreen 退场时清掉仍被时间线引用的有效附件源

### 15.3 `资产协作分发运行时.ts`

职责：

1. 维持 `WebTorrent` 协同主链
2. 管理帮助态、补齐态、完成态
3. 在不削弱群体协作收益的前提下完成轻重分层
4. 区分正式播放 reader、轻帮助 swarm/store、补齐任务和 route drain tailwave

禁止：

1. **禁止** 把零引用会话继续完整重保活
2. **禁止** 把“继续帮助”实现成“继续持有前台级重量”
3. **禁止** 把协作收益留存和前台对象留存绑死
4. **禁止** 过早 retire `/webtorrent/...` route 导致浏览器尾波或 viewer 返回误报不可获取

### 15.4 `全局唯一播放器.ts`

职责：

1. 唯一正式播放器 owner
2. 自动播放 / viewer / fullscreen 的正式表面迁移
3. 保证同一附件在自动播放、viewer、fullscreen、返回归位之间复用同一正式播放真相
4. 上报 rVFC / currentTime / dropped frame / fullscreen 状态给预算验收

禁止：

1. **禁止** 替房间级历史媒体对象背锅
2. **禁止** 因为浏览器减负需求而长出第二正式播放器
3. **禁止** 自己再持有第二份房间级媒体活集合
4. **禁止** 在退出 viewer/fullscreen 时把附件可获取真相一并销毁

### 15.5 信息流媒体预算 owner

职责：

1. 把每个媒体附件裁决到 `当前重播放 / 邻近轻预热 / 远处冷表达 / 轻帮助态`。
2. 聚合窗口真相、自动播 owner、viewer、help window、`heavyWorkPolicy` 和 inflight 预算。
3. 给 `房间消息窗.ts`、`聊天媒体编排.ts`、`视频预览协作.ts`、`资产协作分发运行时.ts` 提供同一份重量裁决。
4. 推动旧 preview / locator / bootstrap / reader 在附件退场或代次切换时取消。
5. 聚合 Core Web Vitals、LoAF、rVFC、设备能力、移动端生命周期和内存压力信号，动态收紧或放宽 warm window。
6. 记录每个附件当前为什么重、为什么预热、为什么冷、为什么轻帮助，供测试和烟测读取。

禁止：

1. **禁止** 成为第二套播放器生命周期 owner。
2. **禁止** 成为第二套 `WebTorrent` 会话 owner。
3. **禁止** 成为第二套房间消息或附件存在真相。
4. **禁止** 只新增一层转发壳，而不删除旧模块里重复的重量判断。
5. **禁止** 让旧逻辑和新 owner 双活，导致同一附件被两个地方同时判定为重态。
6. **禁止** 只按 DOM 可见性裁决重量，而不看 reader、listener、source、WebTorrent 会话和设备能力。

## 16. TDD 验收清单

这份 spec 最终必须同时通过三类验证，缺一条都不算完成。

### 16.1 行为回归测试

必须证明：

1. 自动播放还在
2. 自动暂停还在
3. 进入 owner 无闪烁
4. 离开 owner 无闪烁
5. viewer / fullscreen / 退出归位无回退
6. 新人和老用户进房都先稳预览再接着播
7. 点击当前自动播放视频进入 viewer / fullscreen，返回群聊，再次点击同一视频，不会变成“附件当前不可获取”
8. 桌面端和移动端共享同一套 owner 状态转换测试，只允许预算阈值不同，不允许业务状态机分叉

### 16.2 预算测试

必须证明：

1. 窗口附近真实重表面数量满足第 14.5 节桌面端和移动端预算
2. 房间级活媒体会话数量满足第 14.5 节 `activeMediaSessionCount` 上限
3. 零引用会话满足第 14.5 节 `zeroRefHeavySessionCount` 和 `zeroRefLightHelpSessionCount` 上限
4. listener / reader 满足第 14.5 节上限，且 `MaxListenersExceededWarning == 0`
5. 长时间滚动后重对象数量、JS heap、renderer memory 都会按第 14.5 节回落
6. 同一附件只能由一个 canonical 信息流媒体预算 owner 给出重量裁决
7. 当前重播放、邻近轻预热、远处冷表达三层之间的状态切换可观测、可取消、可回落
8. 删除或压缩旧重复判断后，新旧路径不会双活
9. 桌面端长时间高压滚动、观看、viewer/fullscreen 切换后 DOM、video、image、reader、listener、renderer/GPU memory 不持续单向增长，并满足第 14.5.1 节
10. 移动端或移动模拟下使用更紧预算时，仍能维持自动播放、查看器、返回归位和 WebTorrent 主链，并满足第 14.5.2 节
11. 滚动中 warm candidates 可削减，滚动停止后按当前窗口重新收敛；旧代次任务不能写回当前状态
12. source descriptor、codec 能力判断和降级原因可观测，不能只暴露一个 URL 或一个失败文案
13. 后 `24 小时` 的失败态预算必须按“当前可恢复来源”判定：完整 peer、片段帮助者、本地权威字节能否拼出首播关键字节和持续补齐能力都要进入裁决；**禁止** 只用 `complete_peer == 0` 触发失败
14. 任何阻挡唯一 `WebTorrent` / 满血 `WebTorrent` 的旧支路、伪兜底、临时兼容层或第二真相，都必须在测试里显式暴露并退场；不能只靠人工 review 记得删

### 16.3 浏览器烟测

必须证明：

1. 新人首次进房仍然顺
2. 老用户回房仍然顺
3. 长时间滚动历史仍然顺
4. 大量发送图片视频后仍然顺
5. 长时间观看和切换 viewer 后浏览器不崩
6. Chrome/Edge 不再走向 `STATUS_ACCESS_VIOLATION`
7. 120Hz 屏幕或等价刷新率模拟下，连续滚动、owner 交接、viewer 归位的帧时间分布满足第 14.4 和第 14.5.3 节预算
8. `requestVideoFrameCallback()` 或等价视频帧探针显示当前正式播放 owner 没有持续掉帧
9. `Long Animation Frames`、layout/style 长尾、console error/warn、request failure 必须和预算快照一起记录
10. WebTorrent 秒开烟测必须单独记录 `service worker/createServer`、`streamTo` 或 `streamURL`、range/stream 请求、首帧提交、seek、peer/download/upload 指标；如果新主链附件当轮实际由 `HLS/hls.js/p2p-media-loader` 播放，必须记为新主链验收失败；只有 legacy 旧媒体或实验 benchmark 才能单独记录为 HLS 支路证据，且不能记为 WebTorrent 秒开成功
11. 桌面端必须做长时间高压烟测：大量视频/图片、连续滚动、自动播放、viewer/fullscreen、多次返回后，重对象和原生内存必须回落
12. 移动端或移动模拟必须做同等主链烟测：更小 viewport、更紧预算、触摸滚动、inline/fullscreen、后台/前台切换后不白屏、不假失败
13. Core Web Vitals 必须和媒体预算一起记录：LCP、INP、CLS 不能脱离 video/image/reader/listener 和 renderer memory 单独报喜
14. 每轮烟测必须输出第 14.5.4 节的 `budgetSnapshot`；没有 budget snapshot 的“顺滑”结论无效
15. 后 `24 小时` peer 接力烟测必须覆盖“无单个完整 peer 但片段帮助者能组成可恢复来源”和“确实无可恢复来源”两条路径：前者不能进入 `MEDIA_NO_ONLINE_SEED`，后者必须进入真实无种子态，且两者都不能回退 HLS、直链或服务器第二主链
16. 浏览器烟测的执行方式本身也是验收对象：必须使用 `chrome-devtools-cli` 和 `playwright-cli` 这两个 skill 的 CLI 命令链完成真实打开、滚动、点击、上传、viewer/fullscreen、移动模拟、console/network/performance 和 `budgetSnapshot` 采样；**禁止** 用临时 Node / Playwright 脚本、批处理脚本、隐藏脚本或测试胶水替代这两条 CLI 链路。必要的 `evaluate_script` / `eval` 只能作为 CLI 命令内的一次性探针，命令、参数和输出必须进入烟测记录，不能沉淀成脚本文件或绕开真实浏览器交互。
17. 烟测记录里如果发现新主链附件命中了 `HLS`、原文件直链、CDN、`p2p-media-loader` 或临时 range 服务，只能登记为阻挡满血 `WebTorrent` 的失败证据，不能登记成降级成功

## 17. 非目标

这份 spec 明确不做下面这些事情：

1. 不削弱 `WebTorrent` 主链
2. 不恢复第二正式播放链
3. 不用静态预览图糊弄体验
4. 不通过减少功能、减少协同、减少预览来换“看起来更稳”
5. 不把浏览器崩溃问题推给“浏览器自己不行”
6. 不因为要减负，就把今天已经修好的自动播放、自动暂停、无闪烁重新打坏
7. 不承诺把源视频内容本身强行插帧到 120fps；本 spec 的 120Hz 目标是页面交互、滚动、接管、合成和正式播放帧提交的稳定性目标
8. 不把 X / TikTok / Telegram 的信息流模型误解成照搬它们的播放器、CDN、HLS 或私有分发链路
9. 不把桌面端当成可以无限堆重对象的例外端，也不把移动端当成可以牺牲 `WebTorrent` 主链的降级端
10. 不把 `HLS/hls.js/p2p-media-loader`、原文件直链或 CDN 首播成功记成 `WebTorrent` 满血秒开成功
11. 不保留任何会阻挡唯一 `WebTorrent` / 满血 `WebTorrent` 的正式路径、灰色旁路或“先这样能跑”的临时链路

## 18. 最终一句话

**我们的万人实时群聊前端必须做到：唯一 `WebTorrent` whole-file swarm 主链越活跃越强，桌面端和移动端浏览器里同时活着的重对象始终严格受控；用户始终先看到稳定预览，再无缝进入自动播放、查看器和全屏；长时间发送、滚动、观看后仍然丝滑，不闪、不抽、不崩，也不长出第二播放真相或第二分发真相。**
