## 0. 这份 spec 不是“再修一个卡顿点”

这份 spec 要解决的，不是某一条视频滑动时偶发抖一下，也不是某一次点击后少等了几百毫秒。

它真正要收口的是一句话：

**我们的万人实时群聊前端，必须在功能和业务都满血成立的前提下，让浏览器始终只背必要负担。群越活跃，群友之间的协同分发可以越强；但浏览器里同时活着的重对象必须越少、越短、越受控。**

如果这句话没有被写成硬规则，后续实现很容易继续漂成下面这些坏结果：

1. 为了让预览和自动播放看起来顺，前端偷偷一直养大量真实 `<video>`、图片表面、预览会话和补齐会话。
2. 为了不让浏览器崩，反过来把 `WebTorrent` 主链削弱成“名义上是 P2P，实际主要还是前端在偷跑第二链”。
3. 为了让滚动时不闪，前台一直保留几十条历史视频的真实媒体对象，最后把 GPU 和 renderer 原生内存拖爆。
4. 为了省资源，把今天已经修好的自动播放、自动暂停、无闪烁、无抽搐重新打坏。
5. 为了让系统“看起来总有预览”，把冷的正式播放源、历史脏帧、伪 preview 泄漏成通用表面，后面又长回第二真相。

所以这份 spec 的目标不是“再做一层优化”，而是把**浏览器端媒体生命周期预算**写成正式裁决，防止后续计划和编码继续漂移。

## 1. 当前已经成立的真相，禁止破坏

这份 spec 不是推翻现有裁决，而是在现有真相上补“浏览器绝不崩”的硬约束。

### 1.1 现有播放真相必须继续成立

下面这些已经成立的真相，**禁止** 在后续收口浏览器稳定性时被破坏：

1. **禁止** 长回第二颗正式 `Video.js v10` player。
2. **禁止** 破坏时间线自动播放、自动暂停、查看器、全屏、退出归位共用同一颗 canonical player 的真相。
3. **禁止** 把今天已经收口好的 owner 进入/离开平滑链又打回闪烁、抽搐、冷开、时间轴回退。
4. **禁止** 让消息流重新长出控件、网页式小播放器或第二套交互真相。

### 1.2 现有 `WebTorrent` 主链必须继续成立

下面这些来自 `2026-04-22` 和 `2026-04-23` 两份文档的真相，也必须继续成立：

1. **禁止** 让前端正式媒体字节绕开 `WebTorrent` 正式主链。
2. **禁止** 为了省浏览器资源，偷偷恢复 `HLS` / 原文件直链 / 第二正式播放链。
3. **禁止** 把“浏览器减负”偷换成“群友少帮一点、服务器多顶一点”。
4. **禁止** 把“群越活跃越强”的主链做回“群友看过了也不继续帮后人”的弱协同。
5. **禁止** 破坏 `0-24 小时` 服务器强参与、之后 peer 接力、失败态说真话这些既有裁决。

### 1.3 这份 spec 只补浏览器端生命周期预算

这份 spec 的新增裁决只有一个方向：

**在不削弱协同分发主链、不破坏现有播放体验主链的前提下，把浏览器里同时活着的重对象压进严格预算。**

### 1.4 短视频信息流模型必须服从既有真相

X / TikTok 这类网页给用户的感觉是“滑到哪里都能马上播”，但工程真相不是“全页面所有视频同时重播放”，而是：

1. 当前项重播放。
2. 邻近项轻预热。
3. 远处项冷表达。
4. 旧请求、旧 preview、旧 reader、旧 source 可取消。

`koko` 可以吸收这个模型，但必须服从下面几条：

1. **禁止** 因为学习短视频信息流，就替换现有 canonical `Video.js v10` 播放器。
2. **禁止** 因为学习 XGPlayer / Shaka / Dashlet，就新增第二正式播放器栈或第二播放真相。
3. **禁止** 把“邻近项轻预热”偷换成“整房历史全量预热”。
4. **禁止** 把 `HLS/hls.js/p2p-media-loader` 提升成 `24 小时` 后的长期正式资产 owner。
5. 允许新增或收口一个很薄的“信息流媒体预算 owner”，但它只能裁决重量和窗口，不能篡改 `WebTorrent` 主链、唯一播放器真相或房间消息真相。

### 1.5 WebTorrent 丝滑秒开必须走官方实链路

`WebTorrent` 和 `HLS/hls.js/p2p-media-loader` 不会天然打架；它们只有在被混成同一个“正式播放真相”时才会打架。

官方资料给 `WebTorrent` 浏览器播放的正路已经很明确：注册 `service worker`，让 `client.createServer({ controller })` 提供流式 URL，再用 `file.streamTo(video)` 或 `file.streamURL` 让同一份 torrent file 边下边播、支持 seek、按浏览器实际 codec/container 能力播放。官方 API 还提供 `urlList`/`WebSeed`、tracker、默认 `sequential` piece strategy、`file.createReadStream()`、`torrent.select()`、`torrent.critical()`、`file.select()` 这些能力；这些是我们做“WebTorrent 丝滑秒开”的基础设施，不需要手搓第二套私有顺序拉块内核。

所以后续计划和实现必须守住下面几条：

1. `WebTorrent` 秒开验收必须证明真实 `WebTorrent` 播放路径成立：`service worker/createServer` 已激活，正式视频源来自同一 torrent file 的 `streamTo` 或 `streamURL`，浏览器 range/stream 请求、首帧提交、seek、peer/download/upload 指标都能被观测。
2. `HLS/hls.js/p2p-media-loader` 可以作为 `0-24 小时` 标准流媒体支路或分段级 P2P 增强被评估，但它不能成为 `24 小时` 后长期正式资产 owner，也不能拿自己的首播成功冒充 `WebTorrent` 秒开成功。
3. 如果某阶段确实保留 `HLS` 冷启动支路，必须由媒体预算 owner 显式裁决当前附件到底处于 `WebTorrent 正式播放`、`HLS 冷启动支路`、`轻预热`、`轻帮助态` 哪一种状态；**禁止** 同一附件同时挂两套正式播放源、两套 MSE/reader 重链或两套“已可播”真相。
4. `p2p-media-loader` 的边界只能是 `HLS/DASH` segment-level P2P；它依赖 HTTP(S) manifest/segments 和 Hls.js/Shaka 这类 streaming engine，**禁止** 把它包装成 `WebTorrent` whole-file swarm、complete peer、长期保种或服务器删源后的存活证明。
5. `24 小时` 后如果服务器已经退出原视频、母本、HLS/DASH manifest 和 segments 的字节供给，长期正式播放只能由 `WebTorrent` whole-file swarm 和在线完整 peer 决定；没有完整 peer 时必须进入真实失败态，不能静默切回 HLS、直链或伪预览。
6. 为了丝滑而做的预热，只能预热 locator、torrent metadata、首段/首块、codec 能力、首帧探针和有限 range；滑走、owner 切换或代次失效时必须 `AbortSignal + generation` 取消，**禁止** 留下隐藏 `<video>`、MSE buffer、reader、listener 或第二 source 继续活着。

一句话：**WebTorrent 要满血，HLS 支路要克制；能并存的是职责，不是双真相。**

## 2. 最新真实烟测已经证明的问题

这份 spec 不是凭感觉写的，而是基于真实浏览器烟测写的。

### 2.1 fresh newcomer 路径已经证明：体验主链大体成立，但同时活着的表面还是偏多

新会话真实进入房间 `1234b` 后：

1. 自动播放仍然成立。
2. 自动暂停仍然成立。
3. 打开 viewer 再退出后，自动播放仍能恢复。
4. 没有立即复现之前那类进入/离开 owner 的明显闪烁。

但同一轮真实采样也证明：

1. `rows = 34`
2. `cards = 128`
3. `previews = 15`
4. `imgs = 127`
5. 同时真正 `playing = 1`

这说明：**当前系统不是“播放逻辑坏了”，而是为了服务很少数真正活跃的视频，浏览器同时背了太多附件表面。**

### 2.2 heavy 会话已经证明：房间越用越重

在已经发送过大量视频图片、已经观看过大量视频图片的真实会话里，再做一轮滚动采样，系统会稳定落在：

1. `cards = 110 ~ 131`
2. `previews = 59 ~ 69`
3. `imgs = 73 ~ 90`
4. 同时真正 `playing = 0 ~ 1`
5. JS heap 维持在 `110MB ~ 120MB` 量级

这说明：

1. **禁止** 再把当前问题解释成“只是单个视频播放行为偶尔有问题”。
2. 当前真正的问题是：**房间使用时间越长，前端保留的媒体表面和媒体对象越多。**

### 2.3 原生浏览器进程已经进入危险区

同一轮压测里，真实 Chrome 进程出现了下面这种量级：

1. 某个原生进程 private memory 在 `2GB` 左右。
2. 某个 renderer private memory 在 `1GB+`。

即便当轮没有必然 100% 马上白屏，这也已经说明：

**当前前端不是离崩溃很远，而是已经进入“继续使用就极有可能拖崩浏览器”的区间。**

### 2.4 监听器 warning 不是噪音

真实控制台持续出现：

1. `MaxListenersExceededWarning` for `"data"`
2. `MaxListenersExceededWarning` for `"close"`
3. `MaxListenersExceededWarning` for `"error"`

这不一定是唯一根因，但它明确证明：

1. 协作分发相关对象确实在累积。
2. 浏览器里的协作分发读流、reader、listener 不是在自然收缩，而是在持续堆。

因此，这份 spec 必须明确：

**禁止** 把 `MaxListenersExceededWarning` 当成“只是阈值偏保守”的 harmless warning。  
在浏览器已重压的前提下，它必须被视作“生命周期预算已经失控”的证据之一。

## 3. 最高裁决：三个都要，禁止二选一

后续所有计划、实现、评审、验收，都以这三条为最高裁决。凡是只满足其中两条、牺牲第三条的实现，默认都算失败。

### 3.1 禁止为了不崩而削弱协同分发主链

1. **禁止** 通过减少帮助者、减少补齐、减少做种、减少热会话来换浏览器稳定。
2. **禁止** 把“浏览器少背一点”偷换成“群友少帮一点”。
3. **禁止** 把前台减负做成“后端重新接管更多正式字节职责”。

### 3.2 禁止为了协同分发强而让浏览器无限背重对象

1. **禁止** 把“群越活跃越强”误写成“前端必须一直活着所有历史媒体会话”。
2. **禁止** 把“继续帮助后人”误写成“前台一直挂着几十个真实 `<video>` 表面”。
3. **禁止** 把“后台补齐继续做”误写成“前台继续持有大量重媒体对象和重 listener”。

### 3.3 禁止为了省资源把体验主链重新打坏

1. **禁止** 让预览再变成“先像占位，再卡一下，再开始播”。
2. **禁止** 让自动播放/自动暂停再长回闪烁、抽搐、冷开、回退。
3. **禁止** 让 viewer / fullscreen / 退出归位重新打破无缝感。

一句话：

**群友之间可以更强，浏览器里必须更轻，用户眼前必须更顺。**

## 4. 什么东西算“浏览器里的重对象”

这份 spec 必须先把“重对象”定义清楚，不然后续实现最容易偷换概念。

### 4.1 可见重对象

下面这些只要活着，就会明显增加浏览器前台负担：

1. 真实 `video.message-video-preview`
2. 真实 canonical player 表面
3. 真正可见的大图/原图表面
4. hidden-stage 里仍持有真实媒体源的预热表面
5. 可见区内的首帧恢复视频底板

### 4.2 不可见但仍然昂贵的重对象

下面这些即使用户暂时看不见，也会继续拖前台或原生进程：

1. 已接入正式播放源的 preview `<video>`
2. 正在做 metadata / loadeddata / canplay / seek 的隐藏 `<video>`
3. 房间级媒体会话
4. 协作分发会话
5. 零引用但仍保活的 whole-file backfill 会话
6. `streamURL` 背后的 reader / range reader
7. 对 swarm/torrent 持续绑定的 data/close/error/wire/noPeers 监听器
8. presence heartbeat / join ticket refresh / keepalive 定时链

### 4.3 禁止只盯 DOM，不盯原生资源

后续实现和验收时：

1. **禁止** 只看 DOM 数量就宣布“已经轻了”。
2. **禁止** 只看 JS heap 就宣布“已经稳了”。
3. **禁止** 忽略 GPU / renderer 原生内存、listener 数、reader 数、零引用保活会话数。

因为这次真实问题已经证明：

**真正把浏览器拖崩的，不只是 DOM，而是 DOM、媒体源、读流、会话、原生进程内存一起膨胀。**

## 5. 根因级架构判断

后续执行必须直接对准根因，不准继续修表面。

### 5.1 当前根因之一：房间级媒体附件集合太大

当前逻辑存在一个明显危险点：

1. 媒体编排把“当前房间全部消息里的媒体附件”当成活集合来同步。
2. 这会让大量并不在可见区、也不在近视口、甚至短时间根本不会被用户看到的附件，继续保有媒体会话或预览收敛路径。

所以这份 spec 必须写死：

1. **禁止** 把“在当前房间里出现过”偷换成“当前必须活着”。
2. **禁止** 把“存在于时间线历史”偷换成“必须继续保有真实预览对象”。

### 5.2 当前根因之二：可见窗口预算太宽

当前烟测已经证明，在窗口附近会同时活着大量附件卡片、图片、视频 preview。

所以这份 spec 必须写死：

1. **禁止** 继续用“overscan 先大一点，体验比较稳”这种经验主义处理万人群聊媒体列表。
2. **禁止** 在没有预算证明的前提下，为了减少空白或为了首帧更快，继续扩大窗口附近真实媒体表面的数量。

### 5.3 当前根因之三：协作分发零引用保活太重

当前协作分发运行时允许零引用会话因为：

1. `eagerCompleting`
2. `locallyComplete`

而继续保活。

这条产品语义本身并不一定错；错的是它当前没有区分：

1. 对群有价值的“继续帮助”
2. 对浏览器有害的“继续背着重媒体对象、重 reader、重 listener”

所以这份 spec 必须写死：

1. **禁止** 把“继续帮助后人”实现成“继续保留重表面和重引用”。
2. **禁止** 把“零引用可保留”理解成“零引用但一切都照旧活着”。

### 5.4 当前根因之四：预览真相、自动播放真相、协同主链真相没有按重量分层

现在最危险的误区是：一旦某条附件以后可能要播、以后可能要帮、以后可能要切 owner，就让前台立刻背一套真实媒体对象。

这份 spec 必须明确：

1. 预览真相需要成立。
2. 自动播放真相需要成立。
3. 协同分发真相需要成立。
4. 但这三者**禁止** 默认都落成同样重的浏览器对象。

一句话：

**真相可以同时成立，重量不能同时拉满。**

### 5.5 当前根因之五：缺少一个收口信息流重量的 canonical owner

现有模块分别知道一部分事实：

1. `房间消息窗.ts` 知道当前虚拟窗口和近视口。
2. `聊天媒体编排.ts` 知道哪些附件可能要建立媒体会话。
3. `媒体运行时.ts` 知道 viewer、自动播、heavy policy 和 inflight 预算。
4. `资产协作分发运行时.ts` 知道 `WebTorrent` 会话、帮助态、补齐态和零引用保活。

但如果没有一个明确的“信息流媒体预算 owner”把这些事实压成同一张重量裁决表，系统就容易继续出现：

1. 窗口真相还没到，编排层先按整房附件启动。
2. 当前 owner 已切走，旧 preview / locator / reader 继续跑完。
3. 协作帮助仍有价值，却被错误留成前台重播放态。
4. 为了“看起来丝滑”，多个模块各自保留一份真实媒体对象。

这份 spec 的裁决是：

1. 必须有唯一的“信息流媒体预算 owner”裁决每个附件当前属于 `重播放 / 轻预热 / 冷表达 / 轻帮助` 哪一类。
2. 这个 owner 可以落在现有 `媒体运行时.ts` / `聊天媒体编排.ts` 的收口边界里，也可以抽成一个很薄的新模块；但无论哪种实现，都必须删除旧的重复判断路径。
3. **禁止** 让这个 owner 变成第二套播放器、第二套 WebTorrent runtime、第二套房间媒体会话表或第二套消息真相。
4. **禁止** 新增只转发、不压缩旧逻辑的 wrapper / manager / coordinator 垃圾层。

---

## 6. 最终运行真相：群里强协同，浏览器轻负担

这份 spec 最终要把系统收成下面这个形态。

### 6.1 房间级语义

1. 群里越活跃，群友之间的分发能力越强。
2. 看过某段视频的群友，仍应尽量继续帮助后来者。
3. 后台补齐、做种、热协同仍然属于系统正式主链的一部分。

### 6.2 浏览器级语义

1. 浏览器前台只保留当前真正需要的少量重对象。
2. 离开可见窗口、离开近视口、离开当前用户路径的对象，必须迅速变轻。
3. “继续帮助后人”的收益，**禁止** 默认等于“前台一直背着真实媒体对象”。

### 6.3 用户级语义

1. 用户进入房间后，不管是新人还是老用户，都应很快看到稳定预览。
2. 当轮到某条视频自动播放时，它必须直接在稳定预览上无缝接着播。
3. 当离开当前自动播放视频时，它必须平滑退场，不能抽、不能闪、不能先冒冷表面。
4. 长时间发送、滚动、观看后，用户仍应感觉顺，不应感觉系统越用越重。

---

## 7. 窗口级预算：屏幕附近只允许活必要表面

### 7.1 稳态预算

在任何稳态下：

1. **禁止** 可见区附近同时活着大量真实 `<video>` 预览面。
2. **禁止** 为了服务 `1` 条当前自动播视频，前台同时保留几十条历史视频的真实可读媒体表面。
3. **禁止** 非 owner 视频把正式播放源长期挂在自己的 preview `<video>` 上。

### 7.2 交接预算

在 owner 交接、viewer 打开、viewer 关闭、退出全屏归位这些短暂窗口里：

1. 允许存在极短暂的桥接表面。
2. **禁止** 把这个桥接窗口做成长期常驻。
3. **禁止** 以“为了防闪烁”为理由，让大量非当前卡片也一直维持重预览对象。

### 7.3 首屏预算

新人和老用户回房的首屏：

1. 必须快速收敛到稳定预览。
2. **禁止** 通过扩大首屏活对象数量来换“看起来比较满”。
3. **禁止** 通过让整屏附件同时 metadata/preload 来换首屏稳定。

### 7.4 短视频信息流三层预算

后续实现必须把时间线视频统一压成三层，不允许每个卡片自由决定自己要多重：

1. **当前重播放层**
   当前自动播 owner、viewer owner 或正在正式接管的唯一 `Video.js v10` 宿主。它可以持有正式播放源、解码、帧监控和必要的播放状态。
2. **邻近轻预热层**
   只允许当前窗口和少量 warm candidates 持有轻预热工作，例如 locator、preview truth、metadata、首片段或首帧收敛。它必须有硬数量上限，并且必须能被窗口缩回取消。
3. **远处冷表达层**
   远离当前窗口、当前 owner、当前 viewer、当前帮助窗口的历史附件，只能保留消息真相、轻索引、poster/尺寸/缓存状态这类冷表达；**禁止** 保留真实 `<video>`、重 reader、持续 metadata 探针或未取消的 preview 任务。

这三层只决定浏览器重量，不改变消息是否存在，也不改变 `WebTorrent` 长期协作主链。

---

## 8. 房间级媒体会话预算：禁止把整房历史都养活

### 8.1 活媒体会话集合必须收缩到“当前真实需要”

后续实现必须遵守：

1. **禁止** 把“当前房间全部附件”直接当作活媒体会话集合。
2. **禁止** 让不在可见区、不在近视口、不在当前帮助窗口的附件继续保有完整媒体会话。
3. **禁止** 把“看过一次”直接升级成“长期前台常驻媒体会话”。

### 8.2 房间里消息还在，不等于浏览器必须继续背真实媒体对象

这一点必须反复写死：

1. 消息仍在房间历史里，这是真相。
2. 这条消息未来仍可能再次进入视口，这是真相。
3. 这条附件仍可能继续帮助后人，这也是真相。
4. 但这些真相都**不等于**浏览器前台必须继续背真实 preview `<video>`、metadata 探针、冷 reader、首帧恢复链。

### 8.3 图片和视频都要减，但减法方式不同

1. 图片要优先减真正昂贵的大表面和重复解码负担。
2. 视频要优先减真实 `<video>`、metadata、preview source、stream reader、seek/loadeddata 链。
3. **禁止** 用同一套偷懒策略粗暴处理图片和视频。

---

## 9. 协作分发预算：帮助可以继续，重量必须降下来

这一节是整篇 spec 最重要的边界之一。

### 9.1 对群有价值的帮助链必须继续

1. **禁止** 让浏览器减负变成“看完就不继续帮后人”。
2. **禁止** 让零引用会话一刀切地全部立即销毁。
3. **禁止** 让系统重新回到“只有正在看的那一条才帮，别的都不帮”的弱协同。

### 9.2 继续帮助不等于继续背重对象

后续实现必须显式区分两种状态：

1. **轻帮助态**  
   对 swarm 仍有帮助，但不再持有前台重媒体对象。
2. **重播放态**  
   当前就在为用户提供预览/播放/交接，因此允许持有重对象。

这节的硬禁令是：

1. **禁止** 把轻帮助态和重播放态混成一种状态。
2. **禁止** 让零引用会话继续保留真实 preview `<video>` 或同等级重 reader，只因为“以后也许还能帮人”。
3. **禁止** 把“轻帮助态”误执行成“直接不再可发现、不再续租、不再对 swarm 提供有效帮助”。

### 9.3 协作收益要尽量保住，但必须转成轻态保留

对高活跃群聊来说，正确方向不是“都删掉”，而是：

1. 能保留对群有价值的协作结果，就尽量保留。
2. 但保留时必须尽快从重态降到轻态。
3. **禁止** 把“历史协作成果”继续绑在昂贵的前台对象上。
4. 轻态保留的是对群有价值的协作能力，不是对浏览器有害的前台重量。

---

## 10. 预览真相：不要静态预览图，但必须先有稳定预览

### 10.1 这份 spec 不接受“没有预览图，所以先占一下再播”

这里必须说清楚：

1. 用户不需要传统静态预览图。
2. 但系统必须先给出稳定预览真相。
3. **禁止** 把“没有静态预览图”偷换成“可以先露冷表面、冷视频、冷 metadata 链”。

### 10.2 预览不是装饰，而是自动播放前置真相

1. 当某条视频即将进入自动播放 owner 前，它必须先拥有稳定预览真相。
2. **禁止** 让自动播放 owner 裁决跑在预览真相前面。
3. **禁止** 让用户先看到“类似占位”的冷表面，再等自动播放启动。

### 10.3 新人和老用户都一样

1. **禁止** 只有老用户靠历史缓存看起来顺。
2. **禁止** 只有新用户首屏勉强顺，老用户重返房间又露冷表面。
3. 新人首次进房和老用户回房，都必须先尽快收敛到稳定预览，再进入自动播放。

---

## 11. 进房、滚动、观看、发送四条主链

这四条链是后续所有实现和验收的主线，**禁止** 只修其中一条。

### 11.1 新人首次进房

必须做到：

1. 近视口视频尽快收敛成稳定预览。
2. 自动播放只在稳定预览基础上接管。
3. **禁止** 出现“先占一下、先冷一下、再接着播”。

### 11.2 老用户回房

必须做到：

1. 已有本地收益可以帮助更快收敛。
2. 但不能靠历史脏表面、历史脏帧、历史错误保活对象来伪装稳定。
3. **禁止** 老用户回房后因为历史压力更大，反而更容易拖崩浏览器。

### 11.3 长时间滚动看历史

必须做到：

1. 旧 owner 退场平滑。
2. 新 owner 进入平滑。
3. 列表前后滚很久后，浏览器里同时活着的重对象不持续单向膨胀。
4. **禁止** 滚动得越久，页面越重、越卡、越容易崩。

### 11.4 大量发送图片视频

必须做到：

1. 新草稿、新消息、新附件加入后，不把浏览器前台直接推入不可回收重压。
2. 图片和视频上传成功后，预览和协同主链仍能成立。
3. **禁止** 发送量一大，浏览器就因为历史媒体对象和新媒体对象叠加而走向崩溃。

---

## 12. 后台、离场、隐藏页策略

### 12.1 后台必须减负

浏览器进入 `hidden / background / pagehide` 后：

1. **禁止** 继续保留对前台体验无价值的重表面。
2. **禁止** 继续为不可见页维持大规模 metadata/seek/loadeddata 级重媒体活动。
3. **禁止** 把后台页仍当成前台一样使用。

### 12.2 后台不等于主链断掉

但同时：

1. **禁止** 把后台减负偷换成主链直接断掉。
2. 如果某些协作收益仍对群有价值，应转成轻态继续保留。
3. 后台策略必须显式区分“前台播放体验态”和“群体协作收益态”。

---

## 13. 失败态说真话，但禁止把失败态变成默认体验

### 13.1 真失败必须说真话

1. 没有在线种子就说没有在线种子。
2. 内容已删除就说内容已删除。
3. 浏览器能力边界触发就必须按真实能力降级。

### 13.2 正常链路禁止长期停在“等待中”

1. **禁止** 把“先露等待中/占位/冷表面”当成正常体验。
2. **禁止** 因为失败态已经写清楚，就默认让用户常常看到失败前状态。
3. 正常链路的目标必须是：在用户真正看到那条卡片前就尽量完成预览收敛。

---

## 14. 硬预算与硬红线

这节不是为了把文档写得像参数表，而是为了让后续任何人都不能再说“感觉差不多”。

### 14.1 绝对红线

下面几条必须永远成立：

1. **禁止** `activeFormalPlayerCount > 1`
2. **禁止** `autoplayOwnerCount > 1`
3. **禁止** 在稳态下让可见区附近长期存在大批真实视频预览面
4. **禁止** 在长时间滚动与发送后，重对象数量持续单向膨胀而不回落
5. **禁止** 在零引用后继续保留无上限的重协作分发会话

### 14.2 浏览器稳定性红线

后续执行时必须建立正式预算并纳入测试：

1. 同屏与近视口真实 `<video>` 预览面上限
2. 房间级活媒体会话上限
3. 零引用轻帮助态与重播放态的数量上限
4. preview 收敛时限
5. 长时间滚动/发送/观看后的对象回落要求
6. listener / reader / 原生进程内存越线规则

### 14.3 禁止只有口号，没有数字

1. **禁止** 在 plan 阶段仍然不把这组预算数字化。
2. **禁止** 在没有浏览器烟测数据的前提下拍脑袋给预算。
3. **禁止** 用“用户感觉还好”代替预算验证。

### 14.4 120Hz 丝滑目标必须变成可测红线

`120Hz` 不是一句“看起来顺”的口号。它在前台交互上的含义是：每帧约 `8.33ms`，而 JS、style、layout、paint、视频合成和浏览器内部工作都要分这个预算。

后续计划和实现必须把它拆成下面几条可测红线：

1. 前台滚动、owner 交接、viewer 打开/关闭、全屏归位的目标帧预算按 `8.33ms` 设计；JS / style / layout 单项不得把整帧吃满。
2. `steadyScrollLongAnimationFrameOver50Delta == 0` 只是底线，不是丝滑证明；120Hz 验收还必须记录帧时间分布，不能只看是否超过 `50ms`。
3. `steadyScrollLargeLayoutOrStyleOver40msDelta == 0` 只是底线；120Hz 验收必须继续压低 layout / style 长尾，避免偶发大帧破坏滑动手感。
4. 视频帧必须用 `requestVideoFrameCallback()` 或等价探针记录提交节奏、掉帧和处理延迟；**禁止** 只看 `<video>.paused` / `playing` 就宣布播放丝滑。
5. 播放源选择必须允许用 `MediaCapabilities.decodingInfo()` 或等价能力判断来避开当前设备不适合硬解的 codec / 分辨率 / 码率。
6. 120Hz 目标优先约束页面交互、滚动、接管和合成；**禁止** 把它偷换成“把所有 30fps / 60fps 源视频强行插帧成 120fps”。
7. 低端设备、弱网、后台页或省电模式下允许降级到更低目标，但必须由媒体预算 owner 明确降级原因和状态，不能静默退化成卡顿。

这组红线必须和第 7 节窗口预算、第 9 节轻帮助态、第 15.5 节信息流媒体预算 owner 一起执行；**禁止** 为了追 120Hz 直接牺牲 `WebTorrent` 主链或恢复第二正式播放链。

---

## 15. 模块职责边界

### 15.1 `房间消息窗.ts`

职责：

1. 窗口附近消息与附件表面的表达
2. 可见区与近视口预算的落地
3. 当前 owner 的表面承接

禁止：

1. **禁止** 把整房附件都长成真实前台预览对象
2. **禁止** 把“为了看起来顺”实现成无限增加可见窗口附近的重表面
3. **禁止** 自己偷偷长第二套媒体生命周期真相

### 15.2 `聊天媒体编排.ts`

职责：

1. 真实需要的媒体会话编排
2. 预览收敛、播放、查看器、草稿与恢复的协调

禁止：

1. **禁止** 直接把当前房间全部附件都当成活媒体会话集合
2. **禁止** 把历史存在真相偷换成当前活对象真相
3. **禁止** 把所有协作收益都绑定到当前前台重会话

### 15.3 `资产协作分发运行时.ts`

职责：

1. 维持 `WebTorrent` 协同主链
2. 管理帮助态、补齐态、完成态
3. 在不削弱群体协作收益的前提下完成轻重分层

禁止：

1. **禁止** 把零引用会话继续完整重保活
2. **禁止** 把“继续帮助”实现成“继续持有前台级重量”
3. **禁止** 把协作收益留存和前台对象留存绑死

### 15.4 `全局唯一播放器.ts`

职责：

1. 唯一正式播放器 owner
2. 自动播放 / viewer / fullscreen 的正式表面迁移

禁止：

1. **禁止** 替房间级历史媒体对象背锅
2. **禁止** 因为浏览器减负需求而长出第二正式播放器
3. **禁止** 自己再持有第二份房间级媒体活集合

### 15.5 信息流媒体预算 owner

职责：

1. 把每个媒体附件裁决到 `当前重播放 / 邻近轻预热 / 远处冷表达 / 轻帮助态`。
2. 聚合窗口真相、自动播 owner、viewer、help window、`heavyWorkPolicy` 和 inflight 预算。
3. 给 `房间消息窗.ts`、`聊天媒体编排.ts`、`视频预览协作.ts`、`资产协作分发运行时.ts` 提供同一份重量裁决。
4. 推动旧 preview / locator / bootstrap / reader 在附件退场或代次切换时取消。

禁止：

1. **禁止** 成为第二套播放器生命周期 owner。
2. **禁止** 成为第二套 `WebTorrent` 会话 owner。
3. **禁止** 成为第二套房间消息或附件存在真相。
4. **禁止** 只新增一层转发壳，而不删除旧模块里重复的重量判断。
5. **禁止** 让旧逻辑和新 owner 双活，导致同一附件被两个地方同时判定为重态。

## 16. TDD 验收清单

这份 spec 最终必须同时通过三类验证，缺一条都不算完成。

### 16.1 行为回归测试

必须证明：

1. 自动播放还在
2. 自动暂停还在
3. 进入 owner 无闪烁
4. 离开 owner 无闪烁
5. viewer / fullscreen / 退出归位无回退
6. 新人和老用户进房都先稳预览再接着播

### 16.2 预算测试

必须证明：

1. 窗口附近真实重表面数量受控
2. 房间级活媒体会话数量受控
3. 零引用会话不会无限重保活
4. listener / reader 数量不会只增不减
5. 长时间滚动后重对象数量会回落
6. 同一附件只能由一个 canonical 信息流媒体预算 owner 给出重量裁决
7. 当前重播放、邻近轻预热、远处冷表达三层之间的状态切换可观测、可取消、可回落
8. 删除或压缩旧重复判断后，新旧路径不会双活

### 16.3 浏览器烟测

必须证明：

1. 新人首次进房仍然顺
2. 老用户回房仍然顺
3. 长时间滚动历史仍然顺
4. 大量发送图片视频后仍然顺
5. 长时间观看和切换 viewer 后浏览器不崩
6. Chrome/Edge 不再走向 `STATUS_ACCESS_VIOLATION`
7. 120Hz 屏幕或等价刷新率模拟下，连续滚动、owner 交接、viewer 归位的帧时间分布满足第 14.4 节预算
8. `requestVideoFrameCallback()` 或等价视频帧探针显示当前正式播放 owner 没有持续掉帧
9. `Long Animation Frames`、layout/style 长尾、console error/warn、request failure 必须和预算快照一起记录
10. WebTorrent 秒开烟测必须单独记录 `service worker/createServer`、`streamTo` 或 `streamURL`、range/stream 请求、首帧提交、seek、peer/download/upload 指标；如果当轮实际由 `HLS/hls.js/p2p-media-loader` 播放，只能记录为 HLS 支路成功，不能记为 WebTorrent 秒开成功

---

## 17. 非目标

这份 spec 明确不做下面这些事情：

1. 不削弱 `WebTorrent` 主链
2. 不恢复第二正式播放链
3. 不用静态预览图糊弄体验
4. 不通过减少功能、减少协同、减少预览来换“看起来更稳”
5. 不把浏览器崩溃问题推给“浏览器自己不行”
6. 不因为要减负，就把今天已经修好的自动播放、自动暂停、无闪烁重新打坏
7. 不承诺把源视频内容本身强行插帧到 120fps；本 spec 的 120Hz 目标是页面交互、滚动、接管、合成和正式播放帧提交的稳定性目标

---

## 18. 最终一句话

**我们的万人实时群聊前端必须做到：群友之间的协同分发越活跃越强，但浏览器里同时活着的重对象始终严格受控；用户始终先看到稳定预览，再无缝进入自动播放、查看器和全屏；长时间发送、滚动、观看后仍然丝滑，不闪、不抽、不崩。**
