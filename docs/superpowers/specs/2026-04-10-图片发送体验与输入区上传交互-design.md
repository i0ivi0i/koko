# 图片发送体验与输入区上传交互设计

日期：2026-04-10  
状态：设计已确认，待主人 review  
范围：只修图片发送体验，不改图片附件主链真相；前端输入区交互对齐 IM 直觉，后端继续复用现有附件上传与 `message_created` 主链

## 1. 目标

当前图片附件主链已经能跑通，但输入区体验存在 3 个明显问题：

1. 图片按钮过大，而且按钮文案 `"图片"` 太重，不像 IM 输入区辅助入口
2. 点击图片按钮后弹出上传面板，不像 Telegram 这类群聊 IM 的直接选图体验
3. 选图后草稿区会出现裂图，发送按钮在上传中时静默无反应，用户不知道系统在做什么

本次目标是把图片发送体验收成一条稳定、克制、可扩展的路径：

1. 小 `+` 按钮直接打开系统图片选择器
2. 选图后立刻出现本地缩略图草稿
3. 上传中、失败、可发送三种状态明确可见
4. `发送` 是否可用和禁用原因明确可见，不再 silent return

## 2. 非目标

这轮不做下面这些事，避免任务继续膨胀：

1. 不改后端附件领域模型、房间事件模型、同步锚点
2. 不改 `HTTP 上传 -> attachment_id -> realtime create_message` 主链
3. 不做视频、语音、GIF、压缩包的交互入口
4. 不做图片裁剪、拖拽排序、暂停恢复、边传边发、消息占位气泡
5. 不为了这轮体验修复重新造一套上传器或前端状态机

## 3. 边界裁决

### 3.1 领域与契约不变

后端继续持有唯一业务真相：

1. 图片上传成功，只代表 `attachment` 已 `ready`
2. 消息成立，只认后端创建的 `message_created`
3. 房间时间线只展示权威回流消息，不展示“前端假图片消息”

前端这轮只修壳层体验：

1. 选图入口
2. 草稿带预览
3. 上传状态呈现
4. 发送按钮禁用原因

### 3.2 DDD 与 Unix 裁决

这次只允许做两类改动：

1. 壳层 presenter / uploader 编排收口
2. 必要的前端临时草稿状态整理

不允许：

1. 在 shell 层新增第二套“消息是否成立”判断
2. 把上传 UI 状态写进共享 contract
3. 在前端临时状态里引入另一条附件真相主链
4. 为了一个 `+` 按钮重写现有上传基础设施

## 4. 轮子选择

### 4.1 继续复用的成熟轮子

前端已经有这些依赖：

1. `@uppy/core`
2. `@uppy/xhr-upload`
3. `@uppy/dashboard`

本次裁决：

1. 继续保留 `@uppy/core` 作为上传内核
2. 继续保留 `@uppy/xhr-upload` 作为上传适配
3. `@uppy/dashboard` 退出主交互，不再作为图片入口

原因：

1. 我们已经有成熟上传器，不该再手搓第二套
2. 当前问题不是“没有上传器”，而是“把大面板上传器用在了 IM 输入区上”

### 4.2 可新增的最小依赖

允许新增：

1. `@uppy/thumbnail-generator`

作用：

1. 统一生成本地缩略图预览
2. 减少我们手搓图片预览逻辑

但第一阶段即使用现有 `object URL` 也可以先跑通；是否引入这个依赖，以实现时复杂度为准。

## 5. 输入区交互定稿

### 5.1 入口

1. 输入框左侧改成一个小号 `+` 图标按钮
2. 不显示 `"图片"` 文案
3. 点击 `+` 直接触发原生 `input[type=file]`
4. 允许多选，`accept=image/*`
5. 不再弹出 `Dashboard` 上传框

### 5.2 草稿带

1. 选图后，输入框上方出现图片草稿带
2. 每张图先显示本地预览，不等服务器缩略图
3. 每张草稿图右上角都有删除按钮
4. 草稿带是壳层本地暂态，不进入时间线

### 5.3 状态

每张图片草稿只允许 3 态：

1. `uploading`
2. `ready`
3. `failed`

展示规则：

1. `uploading`：显示遮罩和进度
2. `ready`：显示正常缩略图
3. `failed`：显示失败文案，并给 `重试` / `删除`

### 5.4 发送按钮

发送规则固定成：

1. 只要有任意图片 `uploading`，发送按钮禁用
2. 只要有任意图片 `failed`，发送按钮禁用
3. 只有全部图片 `ready` 后才允许发送

禁用时必须给出明确原因：

1. `正在上传 2 张图片`
2. `1 张图片上传失败，请重试或删除`

这部分必须由 presenter 派生，不允许藏在点击处理里 silent return。

## 6. 前端数据流

### 6.1 草稿图片本地模型

每张草稿图最少保留这些字段：

1. `localId`
2. `file`
3. `localPreviewUrl`
4. `uploadStatus`
5. `uploadProgress`
6. `attachmentId?`
7. `errorCode?`

裁决：

1. `localPreviewUrl` 永远优先用于草稿区预览
2. 在消息真正发出前，不把草稿预览切换成远端缩略图
3. 发送消息时真正提交的是 `attachmentId[]`，不是本地文件

### 6.2 标准流程

1. 用户点击 `+`
2. 原生文件选择器返回一个或多个图片
3. 前端立刻生成每张图的本地预览地址
4. 草稿带立刻显示本地缩略图
5. `Uppy` 开始逐张上传
6. 上传成功后回填 `attachmentId`，并把草稿状态变成 `ready`
7. 上传失败后把状态变成 `failed`
8. Presenter 从当前文本草稿和图片草稿派生发送按钮状态与禁用原因
9. 用户点击发送时，只提交 `text + ready attachmentIds[]`
10. 命令被后端成功受理后，清空输入区草稿
11. 时间线继续等待服务端权威消息回流

## 7. 错误与恢复

### 7.1 删除

1. 删除某张草稿图时，立刻从草稿带移除
2. 如果该图仍在上传，取消对应上传任务
3. 如果该图已经 `ready` 但还没发送，不做额外复杂回滚；未引用附件继续由后端孤儿清理机制处理

### 7.2 重试

1. `failed` 草稿允许重试
2. 重试本质上是用同一个 `localId` 重新发起上传
3. 重试成功后回填新的 `attachmentId`

### 7.3 发送成功后的清空时机

输入区清空时机固定成：

1. 后端已经成功受理 `create_message`
2. 立即清空文本草稿和图片草稿
3. 消息列表仍只等权威回流显示

这样可以避免：

1. 点击瞬间清空导致失败时内容丢失
2. 等到回流才清空导致输入区拖泥带水

## 8. 模块落点

本次优先修改这些文件：

1. `frontend/聊天壳.ts`
2. `frontend/房间实时编排.ts`
3. `frontend/视图.ts`
4. `frontend/状态.ts`
5. `frontend/房间消息窗.ts`

允许新增少量前端文件，但前提是能压缩热点，而不是把逻辑拆碎。

推荐的新增上限：

1. 最多一个很薄的 uploader 壳层适配文件，用于收口 `Uppy` 事件到当前壳层草稿模型

原则上这轮不需要新增 `.rs` 文件；后端只在发现确实存在配套 bug 时做最小修补。

## 9. 测试与验证

### 9.1 前端测试

先补失败测试，再改实现。重点覆盖：

1. `+` 按钮触发原生多选而不是 Dashboard
2. 选图后立即显示本地预览草稿
3. 有上传中图片时发送按钮禁用并显示原因
4. 有失败图片时发送按钮禁用并显示原因
5. 全部 `ready` 后才能发送
6. 删除与重试能正确更新草稿状态

### 9.2 真实链路验证

至少验证：

1. `pnpm --dir frontend test`
2. `pnpm --dir frontend build`
3. `powershell -ExecutionPolicy Bypass -File .\\run.ps1`
4. 手工选图、上传、删除、失败重试、发送一次真实消息

## 10. 实施警戒线

实现时如果出现下面这些倾向，视为跑偏：

1. 为了 UI 修复重写上传内核
2. 把草稿状态和时间线状态混在一起
3. 在点击发送时偷偷忽略未 ready 或 failed 的图片
4. 再次把远端缩略图当草稿预览主来源
5. 为未来视频/语音入口提前埋一套附件菜单系统

一句话收口：

**这轮只把现有图片附件主链的前端壳层体验修稳，不动后端真相，不造第二套上传器，不制造新的长期债。**
