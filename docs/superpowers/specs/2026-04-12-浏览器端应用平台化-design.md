# 浏览器端应用平台化设计

日期：2026-04-12  
状态：Draft  
适用范围：`koko` 仓库浏览器端整体，包括聊天主前端、后台壳、通知、badge、多标签协同、Service Worker、离线与后台能力。

- `学习/浏览器中的应用-前端应用化方案.md`

## 1. 这份 spec 为什么存在

前一轮“前端浏览器应用化”已经完成了一批非常重要的工作：

- 建立了 `AppRuntime` 薄壳入口；
- 收口了房间视口控制权；
- 接入了虚拟列表；
- 替换了媒体查看器主路径；
- 收口了消息时间线真相；
- 接入了应用壳缓存。

这些工作把聊天主链从“明显网页式”拉回到了“开始像应用”。这是必要的一步，但还不是终局。

原因很直接：

1. 现在的前端虽然比以前更像应用，但本质上还是围着“聊天壳 + 若干编排端口”展开。  
2. 浏览器端的很多正式应用能力还没有进入统一架构中心，例如：
   - 多标签协同
   - 通知与 badge
   - Service Worker 生命周期
   - 离线与后台补发
   - 页面 `hidden / pagehide / pageshow / freeze / resume` 生命周期
3. 聊天主链已经开始应用化，但整个浏览器端还没有成为一个“浏览器中的应用平台”。

如果停在这里，后面很容易发生两种漂移：

- 一种是回到旧网页思维：继续在壳层、DOM 事件、浏览器事件里补逻辑；
- 另一种是走向新屎山：为了“平台化”再造一个更大的大前端壳，把聊天业务和浏览器运行时糊成一坨。

这份 spec 的任务，就是把终局蓝图一次讲清楚，避免后续实现时再反复返工。

## 2. 前因后果：为什么必须从“网页”升级成“浏览器中的应用平台”

### 2.1 过去的 bug 为什么会奇怪、偶发、难追因

前端历史上反复出现过这类问题：

- 点开图片、视频、附件后，聊天室误滚到最早历史；
- 视频全屏、方向、返回流程不稳定；
- 图片点击退化成下载；
- 媒体查看器和聊天滚动互相污染；
- 修一个滚动问题，另一个未读/恢复问题又被带坏；
- `聊天壳.ts` 越来越像“所有事情都知道一点”的中心。

这些问题的共同根因不是“某个 `if` 写错了”，而是代码心智模型没有彻底升级：

- 浏览器事件被当成应用事实；
- DOM 观测结果被当成业务真相；
- 壳层既收输入、又裁决、又调网络、又管恢复；
- 大状态对象被多处 patch；
- 新层加上去，旧层还活着。

于是 bug 就会表现成：

- 某个事件在浏览器里明明只是信号，却被直接当成“用户意图”；
- 某个局部修复只让表现看起来暂时正常，但真相 owner 仍然是混乱的；
- 某些问题只在“切后台 / 恢复 / 多标签 / 媒体关闭 / 网络波动”这种组合情境下出现。

这就是典型的“网页式代码遇到应用级复杂度”后的后果。

### 2.2 为什么聊天 IM 特别不能停在网页思维

`koko` 不是普通内容站点，也不是单页表单系统。它是一个面向万人实时群聊的浏览器端应用。

这类系统天然就有下面这些复杂度：

- 高频消息增量；
- 时间线重放、历史分页、未读定位；
- 媒体查看与视口竞争；
- 网络抖动、重连、补洞；
- 离线、后台、恢复；
- 多标签、多窗口协同；
- badge、通知、回到应用；
- App Shell 更新与缓存。

这些复杂度不是可选项。  
如果浏览器端还按“网页页面 + DOM 事件 + 本地 patch 状态”的思路组织，复杂度只会在壳层和临时分支里堆出来。

### 2.3 为什么不是继续修补当前结构，而是直接做终局蓝图

这次不再只做“在现有 spec 上继续渐进增强”，而是先把终局蓝图讲透，原因有三个：

1. 当前已经做过一轮重要收口，如果不尽快明确终局边界，后面每次新增能力都可能往不同方向长。  
2. 通知、badge、多标签、SW、离线、后台能力一旦晚于主架构考虑，后面接入时最容易反向污染聊天主链。  
3. 用户已经明确要求“彻底一点，省得等下又返工”，那就必须先把终局讲清楚，再写实施计划。

## 3. 核心结论

浏览器端终局不该只是“聊天前端应用化”，而应该是：

**一个浏览器应用平台 `BrowserAppPlatform`，上面运行多个业务应用内核 `AppKernel`，壳层只负责把人和浏览器接进来。**

一句大白话：

- 浏览器是运行时；
- 平台层管浏览器能力；
- 业务内核管业务编排；
- 壳层只负责表达和展示；
- 后端继续拥有业务权威真相。

## 4. 这份设计要达到什么目标

### 4.1 目标

1. 让浏览器端正式从“网页”升级成“应用平台”。  
2. 保住前后端超级解耦：  
   - 前端不能抢后端的业务主权；
   - 后端也不能抢前端的设备能力与交互编排。  
3. 让浏览器端的跨业务能力正式入编，而不是继续散落在壳层：
   - 生命周期
   - 多标签协同
   - Service Worker 协同
   - 离线与后台补发
   - 通知与 badge
   - 存储分层
   - 网络/实时运行时托管  
4. 让聊天和后台都成为平台上的“应用”，而不是各自一套网页逻辑。  
5. 为未来 Web / 移动端 / CLI 多壳共核打地基。  
6. 用 DDD + Unix 哲学压住复杂度，不制造新的大壳、新的双真相、新的私有轮子。  

### 4.2 非目标

1. 不把后端业务真相迁到浏览器端。  
2. 不为了“高级”而引入一堆装饰性 DDD 仪式。  
3. 不自研虚拟列表、播放器、图片查看器、SW 缓存框架、状态机框架。  
4. 不把平台层做成“一个更大的 `聊天壳.ts`”。  
5. 不搞“所有东西都事件化”的本地 event bus 大泥潭。  
6. 不在这一份 spec 里直接展开具体实施任务清单；实施任务另写 plan。  

## 5. 设计原则

### 5.1 DDD：真相只能有一个 owner

必须明确：

- 权限真相、成员真相、消息成立真相：在后端；
- 浏览器运行时真相：在平台层 runtime；
- 聊天业务编排真相：在聊天业务 owner；
- 后台管理业务编排真相：在后台业务 owner；
- 壳层不拥有业务真相，只拥有极少量纯 UI 临时态。

只要一个事实在两个地方都能被“顺手判一次”，就说明分层失败。

### 5.2 Unix：每层都必须小而专

平台层不是“大平台对象”，业务内核不是“大业务对象”，壳层也不是“大壳对象”。

每个 runtime / owner 都必须能回答：

- 我只负责哪一类真相？
- 我对外只暴露什么稳定接口？
- 去掉我之后，哪种复杂度会重新扩散？

回答不清，就是边界没立住。

### 5.3 浏览器事件只是信号，不是事实

下面这些都只能当“输入信号”，不能直接当“业务事实”：

- `click`
- `scroll`
- `pointerdown`
- `touchstart`
- `fullscreenchange`
- `popstate`
- `visibilitychange`
- `pagehide`
- `pageshow`
- `freeze`
- `resume`

它们必须先被翻译成应用命令或平台事件，再由 owner 裁决。

### 5.4 新抽象必须压缩旧复杂度

终局不是堆更多层，而是让旧复杂度退场。

任何新增 runtime / owner / adapter，如果没有带来以下至少一项，就不该存在：

- 删掉旧路径；
- 删掉旧分支；
- 收紧单一真相 owner；
- 让测试边界更清楚；
- 用成熟轮子替换手搓通用能力。

### 5.5 绝不手搓成熟通用能力

平台化不等于“自己写一个浏览器前端框架”。  
平台化真正该做的是：

- 用成熟轮子解决成熟难题；
- 用薄适配层把它们接成一套边界清楚的系统。

## 6. 顶层架构骨架

终局里的浏览器端分成三层：

```text
浏览器运行时
  -> BrowserAppPlatform
  -> AppKernel
  -> Shell
```

### 6.1 `BrowserAppPlatform`

职责：

- 浏览器生命周期
- 多标签/多窗口协同
- Service Worker 协同
- 离线与后台任务
- 通知与 badge
- 存储分层
- 传输运行时托管
- 应用级恢复、挂起、唤醒、更新

禁止：

- 直接理解聊天业务真相；
- 决定权限、成员、消息成立；
- 直接拼聊天时间线或后台业务查询真相。

一句话：  
平台层只拥有“浏览器运行时真相”，不拥有“聊天业务真相”。

### 6.2 `AppKernel`

每个具体业务应用都有自己的内核，例如：

- `ChatAppKernel`
- `AdminAppKernel`

职责：

- 业务应用编排；
- 消费后端稳定契约；
- 管理本地体验态；
- 向平台层申请设备能力；
- 向壳层输出稳定快照。

禁止：

- 直接操作 DOM；
- 直接把浏览器原始事件当业务真相；
- 直接摸平台 runtime 内部结构。

### 6.3 `Shell`

职责：

- 收输入；
- 翻译事件；
- 订阅快照；
- 渲染。

禁止：

- 直接裁决业务真相；
- 直接 patch 大状态对象；
- 直接与 transport / SW / badge / storage 内部结构耦合。

## 7. 平台层该拆成哪些 runtime

平台层只保留跨业务、跨壳、跨生命周期的公共能力。

### 7.1 `LifecycleRuntime`

只管应用生命周期：

- `visible / hidden`
- `pagehide / pageshow`
- `freeze / resume`
- 首次启动、挂起、唤醒、恢复

它只输出：  
浏览器端现在处于什么运行阶段。

它不负责：

- 房间恢复语义
- 消息补洞语义
- 未读语义

### 7.2 `MultiContextRuntime`

只管多标签、多窗口、多上下文协同：

- `BroadcastChannel`
- 主窗口/副窗口角色
- 多标签同步
- 通知去重
- badge 协调
- 新窗口接管与聚焦

它不负责：

- 哪条消息算已读
- 哪个房间该显示什么业务状态
- 哪些消息该提醒用户

### 7.3 `ServiceWorkerRuntime`

只管页面和 Service Worker 的关系：

- SW 注册
- 版本握手
- 页面与 SW 消息通道
- 更新提示
- 后台任务委托

它不负责：

- 聊天业务真相
- 消息缓存真相
- 业务命令语义

### 7.4 `OfflineRuntime`

只管离线、联网恢复、后台补发调度：

- 在线/离线信号
- 补发时机
- Background Sync / 周期任务登记
- 待补发任务调度

它不负责：

- 具体补发哪条业务命令
- 命令是否合法
- 消息是否成立

### 7.5 `StorageRuntime`

只管浏览器本地存储分层：

- `IndexedDB`
- `Cache Storage`
- `OPFS`
- 少量壳级 `localStorage`
- quota / persist / eviction 对策

它不负责：

- 成员真相
- 权限真相
- 聊天时间线真相

### 7.6 `NotificationRuntime`

只管：

- 通知权限申请
- badge 设置/清除
- 通知点击回到应用
- 多标签通知去重

它不负责：

- 哪条消息算业务上该提醒的消息
- 哪个房间该红点
- 哪种业务动作要触发通知

这些都必须由业务内核给出。

### 7.7 `TransportRuntime`

只管浏览器端的网络运行时托管：

- HTTP / realtime 生命周期
- socket 生命周期
- 重连节奏
- backpressure 防护
- `pagehide / pageshow / hidden` 场景下连接处理

它不负责：

- 消息去重真相
- 时间线排序真相
- 权限与成员判断

## 8. 哪些东西绝不能进平台层

下面这些一旦放进平台层，后面一定返工：

- 房间时间线真相
- 未读语义
- 阅读锚点语义
- 消息成立语义
- 房间成员语义
- 权限语义
- 聊天媒体业务语义
- 管理后台业务查询语义

这些都应该留在各自 `AppKernel`。

## 9. 聊天业务内核怎么拆

`ChatAppKernel` 至少拆成下面这些 owner。

### 9.1 `SessionOwner`

负责：

- 当前 session
- 设备级本地身份
- 会话失效后的刷新/重建
- 当前活跃房间入口状态

不负责：

- 房间时间线
- 媒体
- 视口
- 未读

### 9.2 `RoomOwner`

负责：

- 入房
- 离房
- 当前房间上下文
- 房间切换时的清理和恢复触发

不负责：

- 房间成员权威真相
- 权限权威真相
- 消息成立真相

这些只消费后端契约，不在前端端上自己发明。

### 9.3 `TimelineOwner`

负责：

- 快照消息
- 历史分页
- 实时增量
- 重连补洞
- 乐观消息与权威消息收敛
- 排序、去重、稳定输出

不负责：

- DOM 列表结构
- 滚动行为
- 播放器行为

它输出的是时间线真相，不是页面树。

### 9.4 `ViewportOwner`

负责：

- 用户滚动意图
- 程序性滚动
- 贴底跟随
- 跳到最新
- 未读定位
- 历史前插补偿
- 媒体覆盖层关闭后的滚动尾波吸收

不负责：

- 消息是否存在
- 消息成立与否
- socket 事件解释

### 9.5 `ComposerOwner`

负责：

- 文本草稿
- 附件草稿
- 待发送队列
- 本地失败重试入口
- 离线待发挂起

不负责：

- 消息最终是否成立
- 上传协议底层细节
- 房间时间线排序

### 9.6 `MediaOwner`

负责：

- 图片/视频查看模式
- 播放源切换
- 与视口 owner 协商控制权
- 与平台层同步媒体专注态

不负责：

- 房间时间线真相
- 浏览器原始全屏事件的最终业务裁决
- 聊天视口业务真相

## 10. 后台业务内核怎么拆

`AdminAppKernel` 不需要像聊天那么复杂，但也不能继续是表单页直连 transport。

至少拆成：

### 10.1 `AdminSessionOwner`

负责后台登录态、token、失效恢复。

### 10.2 `AdminQueryOwner`

负责房间列表、筛选、详情查询、刷新。

### 10.3 `AdminShellOwner`

负责后台本地体验态，例如：

- 当前筛选词
- 当前选中项
- 当前分页位置
- 当前面板展开态

## 11. 各层之间正式怎么通信

平台层和业务内核之间，正式只允许三种通信面。

### 11.1 `Command`

表示“我要你做一件事”。

特点：

- 有明确发起方；
- 有明确 owner；
- 只代表请求发生；
- 不代表事情已经成功。

例如：

- 平台发给业务：`APP_RESTORED`、`NETWORK_BECAME_ONLINE`
- 业务发给平台：`SHOW_NOTIFICATION`、`REGISTER_BADGE`

### 11.2 `Event`

表示“某个事实已经发生”。

特点：

- 是已经发生的事实；
- 不是万能总线；
- 可以被别的 owner 消费；
- 但必须有清楚的边界和顺序语义。

例如：

- 平台事件：`APP_HIDDEN`、`SERVICE_WORKER_UPDATED`
- 业务事件：`ROOM_ENTERED`、`TIMELINE_REBUILT`

### 11.3 `Snapshot`

表示“当前稳定可读状态”。

特点：

- 只读；
- 可渲染；
- 不暴露内部可变结构；
- 只暴露稳定表面。

例如：

- 平台快照：网络状态、SW 状态、通知权限、badge 状态
- 聊天快照：时间线 view model、视口 view model、输入区 view model

### 11.4 绝不允许的通信方式

1. 共享可变大状态对象  
2. 跨层直接调内部方法  
3. 传一个巨大 payload 让下游自己猜  
4. 本地 event bus 万物互联  

一句话：  
以后前端各层之间，不靠“大家都能摸状态”，而靠“命令、事实、快照”。

## 12. 壳层必须退到什么程度

终局里壳层只做四件事：

1. 收用户输入  
2. 把浏览器事件翻译成应用事件  
3. 读快照并渲染  
4. 持有极少量纯 UI 临时态  

壳层禁止做：

- patch 大状态；
- 直连 transport 并宣布业务成功；
- 自己补时间线、去重、排序；
- 根据 DOM 结果裁决业务语义；
- 直接决定 badge / 通知 / SW 行为；
- 直接管理多标签真相。

### 12.1 终局里的 `聊天壳.ts`

它不会消失，但会退化成：

- 视图结构
- 事件翻译
- 快照绑定

它不再是：

- 大脑
- 大状态总线
- 恢复中心
- 网络中心
- 媒体中心
- 滚动真相中心

它最后更像 `ChatShellView + ChatShellBridge`，而不是 `ChatShellBrain`。

## 13. 轮子策略：哪些直接用，哪些只做薄适配

### 13.1 直接用，不自己造

- 状态机 / actor：`XState / Stately`
- 虚拟列表：`TanStack Virtual`
- 图片查看：`PhotoSwipe`
- 视频播放：`Vidstack`
- SW 缓存与更新：`Workbox`
- 多标签/通知/后台能力：浏览器原生能力
  - `BroadcastChannel`
  - `navigator.serviceWorker`
  - `Clients API`
  - `Badge API`
  - `Notification API`
  - `Background Sync`

### 13.2 只做薄适配层，不做第二核心

下面这些可以封一层，但必须只做入口收口：

- `TransportRuntime`
- `StorageRuntime`
- `NotificationRuntime`
- `ServiceWorkerRuntime`

它们可以翻译入口，不能发展成第二套私有核心。

### 13.3 坚决不手搓

- 私有虚拟列表引擎
- 私有播放器核心
- 私有图片查看器核心
- 私有状态机框架
- 私有 SW 缓存框架
- 私有多标签消息总线框架
- 私有离线任务平台

## 14. 这套设计最容易长新屎山的 5 个风险点

### 风险 1：平台层偷偷变成第二个聊天业务层

表现：

- 平台开始懂未读、房间、媒体、消息语义；
- NotificationRuntime 开始判断哪些消息该提醒；
- StorageRuntime 开始判断未读如何恢复。

堵法：

- 平台层只认浏览器运行时语义；
- 聊天业务策略只能由 `ChatAppKernel` 发 command 过来。

### 风险 2：业务内核继续共享大状态对象

表现：

- 虽然名字变成 owner，但本质还是一个 `chatState` 到处 patch。

堵法：

- owner 内部状态私有；
- 对外只暴露 snapshot；
- owner 之间只走 command / event。

### 风险 3：为了“优雅”搞成本地 event bus 大泥潭

表现：

- 什么都发 event；
- 顺序靠猜；
- 谁消费、谁兜底越来越不清楚。

堵法：

- 事实才发 event；
- 请求优先走定向 owner；
- 同步调用就同步，不强行事件化。

### 风险 4：适配层越来越厚，最后变成私有轮子

表现：

- `TransportRuntime` 越写越像私有网络框架；
- `StorageRuntime` 越写越像私有数据库；
- `ServiceWorkerRuntime` 越写越像私有缓存平台。

堵法：

- 适配层只收口入口，不扩展轮子核心语义；
- 必须保证底下轮子仍能被清楚认出来。

### 风险 5：新层加上去，旧层不退场

表现：

- 新 platform / new owner 加了；
- 旧壳逻辑、旧 patch 总线、旧入口还都活着。

堵法：

- 每上一个新 owner，都必须定义一个旧入口退场点；
- 不允许“先都留着，后面再慢慢收”。

## 15. 这份蓝图的失败判定

后续只要出现下面任一情况，就说明实现已经开始漂移：

1. 平台层开始判断聊天业务真相。  
2. 壳层开始直接 patch 大状态。  
3. 业务 owner 继续共写一个共享可变对象。  
4. 新增运行时后，旧逻辑没有同步收缩或退场。  
5. 为了方便而手搓成熟轮子的替代核心。  
6. 用 CSS / timer / magic delay 继续掩盖状态归属问题。  
7. 用本地 event bus 取代清楚的 owner 和协议。  
8. 后端开始为了前端展示流程提供壳专属语义。  

## 16. 终局完成定义

做到下面这些，才能说浏览器端真的完成了平台化：

### 16.1 结构已经变成三层

- `BrowserAppPlatform`
- `AppKernel`
- `Shell`

而不再是“大壳 + 若干 helper”。

### 16.2 真相 owner 已经收紧

平台真相、聊天真相、后台真相、壳层真相都已经各归其位，不再重复判定。

### 16.3 壳层已经明显变薄

壳层只剩：

- 收输入
- 翻译事件
- 读快照
- 渲染

### 16.4 平台能力已经正式入编

这些都已经是正式架构部件，而不是外挂补丁：

- 通知
- badge
- 多标签协同
- 离线
- 后台补发
- 应用恢复
- SW 更新
- 页面生命周期

### 16.5 前后端契约已经干净

浏览器端只消费稳定契约：

- command
- query
- event
- snapshot
- error code

前端不抢后端主权，后端也不替前端决定页面/设备体验。

### 16.6 没有再造轮子

成熟轮子都已就位，项目只保留薄适配和业务边界。

### 16.7 旧路已经退场

只要下面这些还活着，就不能算完成：

- 大 patch 状态总线
- 新旧两套 owner 并存
- 壳层和平台层重复判真相
- 新 runtime 叠上去，旧逻辑没删

## 17. 为防止实现漂移，后续 plan 必须写清什么

虽然具体 implementation plan 不在这份 spec 里展开，但后续写 plan 时必须逐阶段写清：

1. 本阶段收口哪个 owner；  
2. 本阶段不让哪个旧入口继续存活；  
3. 本阶段新增什么失败测试或 characterization test；  
4. 本阶段删掉或收缩哪段旧复杂度；  
5. 本阶段复用哪个成熟轮子，为什么它只是通用能力；  
6. 本阶段不做什么，避免范围膨胀；  
7. 本阶段如何验证不会引入双真相。  

如果 plan 里只写“新增 runtime / 接入 XState / 接 SW / 加 badge”，但没有写旧路径退场点，就不能进入编码。

## 18. 一句话结论

终局不是把前端变成“更复杂的网页”，也不是把它写成“一个新的前端框架”。  
终局应该是：

**一个边界干净、owner 单一、站在成熟轮子肩膀上的浏览器应用平台，上面跑聊天内核和后台内核，壳层只负责把人接进来。**
