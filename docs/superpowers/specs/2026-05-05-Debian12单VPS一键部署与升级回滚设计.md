## 0. 总裁决

`koko` 的正式部署目标，不是“给高手一套很强的运维工具箱”，而是：

**让一个只会基本 GitHub 操作的人，也能把私有仓库里的 `koko` 安全地发到一台 Debian 12 VPS，并在出问题时明确回滚。**

从这句话推出全部硬边界：

1. 正式形态固定为：**单台 Debian 12 VPS + GitHub 私有仓库 + GitHub Actions + Cloudflare + 正式域名**。
2. 浏览器对外只允许一个正式入口：`https://正式域名/`。
3. 日常上线入口固定在 **GitHub Actions 页面**，不是把人逼到 VPS 终端里手敲一串命令。
4. 首次安装、日常升级、版本回滚都必须通过固定流程完成，**禁止靠临场手工拼命令**。
5. VPS 只负责“运行”；GitHub 只负责“版本和发布动作”；Cloudflare 只负责“正式域名外层入口与边缘能力”；三者职责不能混。
6. `run.ps1`、本地 Windows 证书流程、局域网 HTTPS 适配都不是正式部署真相 owner，**禁止偷换成 Linux 上线方案**。
7. 任何环境都继续禁止 `cloudflared`；公网只允许 `Cloudflare + 正式域名` 这一套入口脑子。
8. 首版设计目标是：**单机稳定、按钮可用、回滚明确**；不是第一天就做 Kubernetes、蓝绿发布、灰度放量、多机高可用。
9. 仓库文件布局采用“**`ops/` 统一收部署资产，但保留 GitHub 和 Docker 的官方锚点位置**”。

一句话钉死：

**第一版先把“能稳定发、能稳定回、脑子不乱”做出来；不要一上来把部署系统堆成新的屎山。**

## 1. 这份设计解决什么，不解决什么

### 1.1 这份设计要解决什么

这份设计必须解决下面 8 件事：

1. 私有 GitHub 仓库怎样安全发到一台 Debian 12 VPS。
2. 首次空白 VPS 怎样尽量接近“一次按钮上线”。
3. 以后你平时到底要点什么、记什么。
4. 升级时怎样避免一堆人工 SSH 操作。
5. 回滚时怎样明确回到哪个版本，而不是“猜上一个 commit”。
6. 数据、代码、配置、日志应该怎样分开放，避免一回滚把数据库也洗掉。
7. Docker 镜像里到底哪些东西能进，哪些垃圾必须挡在外面。
8. 出现故障时，到底去哪里看日志、看健康检查、看部署结果。

### 1.2 这份设计明确不解决什么

首版 **不** 解决下面这些事情：

1. 多机高可用。
2. 金丝雀发布。
3. 蓝绿发布。
4. 自动弹性扩容。
5. Kubernetes。
6. Coolify、1Panel 之类额外控制面。
7. 复杂审批流。
8. 多套环境矩阵编排到很花。

不是这些永远不要，而是 **现在做这些，对当前目标是噪音，不是帮助**。

## 2. 先把几个词讲清楚

为了让后面不靠术语猜意思，先把最常见的几个词说成人话。

### 2.1 VPS 是什么

VPS 就是一台你租来的 Linux 电脑。  
以后真正跑 `koko` 的，是它。

### 2.2 GitHub Actions 是什么

GitHub Actions 可以理解成：

**GitHub 帮你跑自动化任务的工人。**

比如：

1. 构建项目
2. 跑测试
3. 打 Docker 镜像
4. 通过 SSH 连到 VPS
5. 把新版本部署上去
6. 按指定版本执行回滚

它不是你的线上服务器，它只是“发布流水线工人”。

### 2.3 Cloudflare 在这里是干什么的

在本设计里，Cloudflare 只负责：

1. 用户先访问你的正式域名
2. 外层 HTTPS/边缘能力
3. 把请求送到你的源站 VPS

它不是第二套源站，不是第二套上传真相，也不是第二套 tracker 真相。

### 2.4 一键部署到底是什么意思

这里说的“一键”，不是“没有任何准备动作”。

这里真正的意思是：

1. **一次性准备**：域名、Secrets、VPS 基础 SSH
2. **日常操作**：点 GitHub Actions 的 `Deploy`
3. **出问题**：点 GitHub Actions 的 `Rollback`

也就是：

**复杂命令被固定在仓库里，日常不靠人记。**

## 3. 为什么正式方案选 GitHub Actions，而不是把人赶去 SSH

这条要先说透。

### 3.1 看起来最直接，但不适合你的方案

最原始的想法通常是：

1. 你本地改代码
2. `git push`
3. SSH 登录 VPS
4. `git pull`
5. 手工重启服务

这个方案对老运维没问题，但对你的目标不合适。因为它会带来 5 个坏处：

1. 你必须记更多命令。
2. VPS 上要长期保留 GitHub 拉代码权限。
3. 每次部署容易出现“这次漏敲了一条命令”。
4. 回滚容易变成“我记得上个版本大概是那个 commit”。
5. 未来让别人接手时，知识都藏在你脑子和终端历史里。

### 3.2 为什么 GitHub Actions 更适合这次目标

本次正式采用：

**GitHub Actions 主动把部署动作推到 VPS。**

它的好处非常直接：

1. 你平时不需要 SSH 上去手敲部署命令。
2. 发布动作集中在仓库里，可审查、可复用。
3. 私有仓库不用公开。
4. VPS 不一定要自己长期持有 GitHub 拉代码权限。
5. `Deploy` 和 `Rollback` 可以做成按钮，对小白友好。

所以这里正式裁决：

1. **日常发布控制面在 GitHub，不在 VPS 终端。**
2. **VPS 是运行面，不是人工操作主界面。**

## 4. 正式推荐架构

### 4.1 最终拓扑

```text
GitHub 私有仓库
  └─ GitHub Actions
      └─ SSH 到 Debian 12 VPS
          └─ /opt/koko
              ├─ ops/        # 部署脚本、compose、Caddyfile
              ├─ current/    # 当前生效版本软链接
              ├─ shared/     # 持久化数据、日志、备份
              └─ releases/   # 历史版本目录（用于回滚）

公网用户
  └─ Cloudflare
      └─ Caddy :443
          └─ koko app :8080
              ├─ /api/...
              ├─ /files -> 内部 tusd
              └─ /api/swarm/announce -> 内部 tracker

VPS 内部 sidecar
  ├─ postgres
  ├─ tusd
  ├─ tracker
  └─ seeder
```

### 4.2 这套拓扑里每个东西到底负责什么

#### GitHub 私有仓库

负责：

1. 存源代码
2. 存部署脚本
3. 存 GitHub Actions 工作流
4. 存版本标签（tag）

不负责：

1. 真正跑线上业务
2. 代替数据库

#### GitHub Actions

负责：

1. 按固定流程构建和部署
2. 调用 VPS 上固定脚本
3. 记录每次部署/回滚日志

不负责：

1. 长期运行你的服务
2. 替代线上监控系统

#### Debian 12 VPS

负责：

1. 真正跑项目
2. 真正存数据库
3. 真正存上传与运行数据

#### Cloudflare

负责：

1. 正式域名公网入口
2. 外层 HTTPS/边缘能力

不负责：

1. 第二套上传主链
2. 第二套 tracker 真相
3. 第二套发布控制面

#### Caddy

负责：

1. 在 VPS 上接正式域名入口
2. 反向代理到 `koko app`
3. 收口单公网入口

为什么选它：

1. 配置比 Nginx 更短
2. 对小白更友好
3. 自动 HTTPS/证书续期能力成熟

### 4.3 正式运行主链只能有一套

首版正式运行面固定为：

**Docker Compose + Caddy + 容器化 sidecar。**

这条要写死，因为最容易漂成“两套都保留，谁都算主链”。

所以正式裁决：

1. **首版正式运行主链固定是 Docker Compose。**
2. **禁止同时长期维护一套 Docker/Compose 主链，外加一套 systemd 裸进程主链。**
3. 如果未来真的要改成裸二进制或别的主链，必须整体迁移，而不是长期双活。

### 4.4 仓库内文件布局裁决

项目内正式采用下面这套布局：

```text
仓库根目录/
  .github/
    workflows/
      initial-deploy.yml
      deploy.yml
      rollback.yml

  Dockerfile
  .dockerignore

  ops/
    README.md
    compose.yaml
    Caddyfile
    env.production.example
    install.sh
    deploy.sh
    rollback.sh
    healthcheck.sh
```

为什么这样定：

1. `ops/` 让人类维护时更集中，部署资产一眼能找到。
2. `.github/workflows/` 是 GitHub 官方固定位置，不能为了整齐搬走。
3. 主 `Dockerfile` 用根目录默认文件名，最符合 Docker 官方推荐。
4. `.dockerignore` 跟 build context 根目录绑定，放根目录最稳。

所以这里的硬规则是：

1. **部署资产默认统一收进 `ops/`。**
2. **workflow 文件必须继续放在 `.github/workflows/`。**
3. **主 `Dockerfile` 和 `.dockerignore` 继续保留在仓库根目录。**

## 5. 为什么明确不选这些方案

### 5.1 不选 Coolify / 1Panel

不是说这些工具绝对差，而是 **它们对你当前目标是额外控制面**。

你现在要的是：

1. 部署脑子更少
2. 路径更短
3. 问题更容易排查

而不是：

1. 先学一套面板产品
2. 再把 GitHub、Docker、VPS、面板、Actions 叠成五层

所以首版裁决：

**禁止为了“看起来更高级”额外引入部署面板。**

### 5.2 不选 Kubernetes

原因很简单：

1. 单 VPS 上 K8s 的复杂度远大于收益
2. 你现在最缺的不是“编排宇宙”，而是“稳定上线与明确回滚”

### 5.3 不把 self-hosted runner 作为首版默认

你问过 GitHub Actions 的分钟数问题。答案是：

1. GitHub-hosted runner 的分钟数，是“发布流水线运行时间”
2. 不是线上服务运行时间
3. 单 VPS 单项目起步阶段，通常够用

确实，如果以后你构建很重，或者不想耗 hosted runner 分钟，可以升级到：

1. 本机高性能电脑构建
2. self-hosted runner

但首版默认不这么做，因为：

1. 电脑关机、睡眠、断网都会影响它
2. 你会多养一台“发布工人机”
3. 当前不必要

### 5.4 不让正式发布依赖 `run.ps1`

`run.ps1` 是 Win11 本地启动器，不是 Linux 正式部署真相 owner。  
这条前面已经有正式文档裁决，这里继续继承，不允许反悔。

## 6. GitHub 与 GitHub Actions 的现实边界

### 6.1 私有仓库能不能用 GitHub Actions

能。  
**不需要把仓库改成公开。**

### 6.2 GitHub Actions 免费吗

更准确的说法是：

1. GitHub Actions 不是“永远完全免费”
2. 而是按你的 GitHub 套餐，给你一定 hosted runner 使用额度
3. 具体分钟数和计费规则以后可能变，所以**不要把某个数字写死成长期架构真相**

这份设计的正式裁决是：

1. **首版默认允许使用 GitHub-hosted runner**
2. **当前额度是否变化，以 GitHub 官方定价页为准**
3. **如果以后 hosted runner 分钟不够，再升级到 self-hosted runner，而不是现在先把架构做复杂**

### 6.3 那 `2000 分钟/月` 到底是什么意思

它的意思不是“线上服务一个月只能跑 2000 分钟”。

它真正的意思是：

**GitHub 帮你跑构建、测试、部署这些流水线任务的总时长。**

比如一次部署工作流跑 10 分钟，那 2000 分钟大概就是 200 次这种工作流。

这和线上业务 24 小时运行不是一回事。

### 6.4 这份设计对 GitHub Features 的最低要求

首版只依赖下面这些基础能力：

1. 私有仓库
2. GitHub Actions
3. Repository Secrets
4. `workflow_dispatch` 手动运行
5. `push` 触发

首版 **不要求**：

1. 高级审批流
2. 复杂 environment gate
3. 企业级多环境策略

这样可以避免因为套餐细节把方案搞复杂。

### 6.5 GitHub 官方对 workflow 位置的要求

GitHub 官方要求 workflow 文件必须放在仓库根目录下的 `.github/workflows/`。

所以这里没有自由发挥空间：

1. **`initial-deploy.yml`、`deploy.yml`、`rollback.yml` 禁止搬进 `ops/`。**
2. `ops/` 放的是脚本和部署资产，**不是 workflow 的替代位置。**

## 7. 正式部署目录裁决

VPS 上正式采用下面这套目录：

```text
/opt/koko/
  ops/
    README.md
    compose.yaml
    Caddyfile
    install.sh
    deploy.sh
    rollback.sh
    healthcheck.sh

  env/
    .env.production

  releases/
    v0.1.0/
    v0.1.1/
    v0.2.0/

  current/   -> 指向当前生效版本的软链接

  shared/
    postgres/
    tusd/
    caddy_data/
    caddy_config/
    logs/
    backups/
```

### 7.1 每个目录是干什么的

#### `ops/`

放运维控制文件：

1. Compose
2. Caddyfile
3. 固定脚本
4. 这套目录怎么用的简短说明

这里放的是“怎么跑”。

#### `env/`

放生产环境变量文件。  
这里放的是“跑的时候需要哪些密码和配置”。

#### `releases/`

放每个已发布版本。  
这里放的是“每个版本自己的代码/镜像/发布产物”。

#### `current/`

它不是一个普通目录，而是一个指针。  
它永远指向当前正式生效版本。

回滚的一个核心动作，就是把它改指回旧版本。

#### `shared/`

放**不能跟着版本一起删掉**的数据：

1. PostgreSQL 数据
2. tusd 数据
3. Caddy 数据
4. 日志
5. 备份

### 7.2 为什么必须这样分

如果你把所有东西都扔在一个目录里，会出现 3 个后果：

1. 回滚时容易把数据也一起洗掉
2. 升级时容易分不清哪些是“版本内容”，哪些是“长期数据”
3. 故障排查时，代码、日志、数据库、脚本全部糊成一团

所以这里写死：

1. **版本内容和持久化数据必须物理分离**
2. **回滚只回滚版本，不回滚数据库目录本身**

## 8. 发布产物与 Docker 镜像裁决

### 8.1 正式镜像里允许有什么

正式运行镜像里允许存在：

1. Rust release 二进制
2. `frontend/index.html`
3. `frontend/dist/`
4. 运行所需最小依赖
5. 必要的运行配置入口

### 8.2 正式镜像里禁止有什么

下面这些默认禁止进入正式运行镜像：

1. `.git`
2. `docs/`
3. `tests/`
4. `graphify-out/`
5. `frontend/tests/`
6. `frontend/node_modules/`
7. 源码 `.rs`
8. 源码 `.ts`
9. Windows 启动脚本
10. `.codex-*.log`
11. 构建缓存
12. 调试产物

### 8.3 为什么要这么严

因为正式镜像的职责只有一个：

**稳定运行。**

它不是：

1. 源码备份压缩包
2. 文档仓库
3. 调试垃圾桶
4. 本地开发环境快照

### 8.4 正式构建方式裁决

正式采用：

**多阶段 Docker 构建。**

含义很简单：

1. 前一阶段负责编译
2. 后一阶段只留下运行真正需要的最小东西

一句话：

**构建阶段可以胖，运行阶段必须瘦。**

### 8.4.1 Docker 官方对主文件名和 ignore 文件位置的建议

Docker 官方建议：

1. 项目的主 Dockerfile 使用默认文件名 `Dockerfile`
2. `.dockerignore` 放在 build context 根目录

所以这里正式裁决：

1. **主 `Dockerfile` 保留在仓库根目录。**
2. **`.dockerignore` 保留在仓库根目录。**
3. **不要为了“所有部署文件都放一起”把它们强行塞进 `ops/`。**

### 8.5 首版默认在哪里构建

这条必须明确，不然后面会漂出三套说法。

首版默认采用：

**GitHub Actions 把当前版本发布包传到 VPS，再由 VPS 本机执行 `docker compose build` 完成正式镜像构建。**

这样选的原因：

1. 不需要先搭镜像仓库。
2. 不需要让 GitHub-hosted runner 长时间承担大构建。
3. 不需要把大镜像从外部再搬回 VPS。
4. 对单机首版更容易解释和排查。

所以首版禁止默认长出下面这些并行主链：

1. 一套在 GitHub Actions 里预构建镜像再传输。
2. 一套在 VPS 本机构建。
3. 一套再让 VPS 自己 `git pull` 后手工构建。

首版只保留一句话：

**Actions 负责发命令和传发布包，VPS 负责生成最终运行镜像并启动。**

## 9. 网络与公网入口裁决

这部分继承现有公网单入口文档，不允许重新发明第二套脑子。

### 9.1 浏览器只允许知道一个正式入口

正式用户只访问：

`https://正式域名/`

浏览器只允许感知：

1. `/api/...`
2. `/files/...`
3. `/api/swarm/announce`

### 9.2 内部 sidecar 继续只允许留在源站内部

下面这些是内部东西，不允许直接暴露给浏览器：

1. `tusd`
2. `tracker`
3. `seeder`
4. `127.0.0.1`
5. `localhost`
6. `:1081`
7. `:7072`
8. `:7073`

### 9.3 正式 TLS 入口裁决

公网入口统一收在：

1. Cloudflare 外层
2. VPS 上的 `Caddy :443`

Cloudflare SSL 模式裁决：

1. **正式环境固定使用 `Full (strict)`。**
2. **禁止使用 `Flexible`。**

原因很简单：

1. `Flexible` 会让 Cloudflare 到源站之间降回不安全链路。
2. 这和“正式入口只认 HTTPS 真相”冲突。

这里不允许再长：

1. `cloudflared`
2. trycloudflare
3. 多套额外公网端口

## 10. 首次上线到底怎么做

这一节专门按“电脑小白”写。

### 10.1 你手工只需要做一次的准备

#### 第一步：准备 VPS

你需要有：

1. 一台 Debian 12 VPS
2. 能用 `root` 或有 sudo 权限的用户 SSH 登录

#### 第二步：准备正式域名

你需要有：

1. 一个正式域名
2. 域名已经接入 Cloudflare
3. 域名 DNS 能指向这台 VPS 的公网 IP

#### 第三步：在 GitHub 仓库里填 Secrets

至少需要这些：

1. `VPS_HOST`：你的 VPS IP 或域名
2. `VPS_USER`：登录用户名
3. `VPS_SSH_KEY`：Actions 用来登录 VPS 的私钥
4. `PROD_ENV_FILE`：整份生产环境变量内容

按实际情况再补：

1. 数据库密码
2. 管理员密码
3. swarm secret

#### 第四步：你平时主要看哪些位置

为了不让你一上来面对全仓结构，先记住这 3 个位置就够：

1. **看部署资产：`ops/`**
2. **看 GitHub 按钮：`.github/workflows/`**
3. **看镜像主入口：根目录 `Dockerfile` 和 `.dockerignore`**

### 10.2 首次上线时 GitHub Actions 自动做什么

当你点一次 `Initial Deploy` 后，GitHub Actions 自动：

1. SSH 进入 Debian 12 VPS
2. 安装 Docker / Compose（如果机器还没有）
3. 创建 `/opt/koko` 目录结构
4. 写入生产环境变量文件
5. 上传部署脚本与运维文件
6. 上传当前版本发布包，并在 VPS 本机执行正式镜像构建
7. 启动 `postgres / tusd / tracker / seeder / app / caddy`
8. 执行健康检查
9. 把成功或失败结果写回 Actions 日志

### 10.3 首次上线之后你应该看到什么

如果成功，应该看到：

1. GitHub Actions 显示成功
2. 正式域名能打开主页
3. `/files` 上传主链可用
4. `/api/swarm/announce` 协作分发主链可用

## 11. 日常升级怎么做

### 11.1 对你来说，日常升级只保留两种入口

#### 入口 A：自动升级

你本地开发完：

1. 提交代码
2. `git push`

然后仓库按设定自动触发 `Deploy`。

#### 入口 B：手动按钮升级

你去 GitHub：

1. 打开 `Actions`
2. 选择 `Deploy`
3. 点 `Run workflow`

### 11.2 日常升级时 GitHub Actions 做什么

它会：

1. 确认要发布哪个版本
2. 构建或准备该版本产物
3. 传到 VPS 的新 release 目录
4. 执行数据库迁移（如果本次需要）
5. 切换 `current` 到新版本
6. 重启或滚动重建容器
7. 执行健康检查
8. 记录部署完成版本号

### 11.3 为什么日常升级不让你 SSH 进去手工操作

因为那样会让发布真相再次分裂成两套：

1. 一套写在仓库
2. 一套藏在你脑子里

这在长期维护里必然会出事。

## 12. 版本与回滚裁决

### 12.1 每次正式上线必须对应明确版本

推荐版本名：

1. `v0.1.0`
2. `v0.1.1`
3. `v0.2.0`

这样做的意义是：

1. 上线时知道自己发了什么
2. 回滚时知道自己退到什么

### 12.2 回滚到底回滚什么

首版回滚的核心对象是：

1. 应用版本
2. 前端构建产物
3. 部署配置

它**不是**：

1. 把整台机器恢复成昨天
2. 把数据库目录整体删掉重来

### 12.3 回滚时 GitHub Actions 做什么

当你点一次 `Rollback`：

1. 选定目标版本
2. Actions SSH 进入 VPS
3. 执行 `rollback.sh <版本号>`
4. 把 `current` 指回旧版本
5. 用旧版本重新启动容器
6. 做健康检查
7. 把结果显示在 Actions 日志里

### 12.4 回滚必须写死的限制

1. **回滚默认只回代码与运行产物，不自动倒库**
2. **数据库迁移如果是不可逆的，回滚必须额外谨慎**
3. **禁止把“能回退代码”偷换成“任何数据库状态都能无脑回退”**

---

## 13. 数据库迁移裁决

### 13.1 数据库迁移不是普通文件替换

代码坏了，可以切回旧版本。  
数据库一旦改了结构，不一定能像代码一样直接倒回去。

### 13.2 首版迁移规则

1. 迁移默认必须保守
2. 不允许随手做高风险不可逆破坏
3. 每次发布如果带数据库迁移，必须在部署工作流里显式执行
4. 回滚设计默认不承诺自动回滚数据库结构

### 13.3 对小白最重要的一句话

**代码回滚通常容易；数据库回滚通常更危险。不要把这两件事混成一件事。**

---

## 14. 备份裁决

### 14.1 首版至少要备份什么

至少备份：

1. PostgreSQL 数据
2. 生产环境变量文件的安全副本
3. 关键上传/媒体持久化数据

### 14.2 备份存放在哪里

默认放：

`/opt/koko/shared/backups/`

### 14.3 为什么备份优先级高于花哨发布

因为没有备份时：

1. 回滚只能救代码
2. 救不了数据

所以长期顺序必须是：

1. 先把备份和恢复演练补起来
2. 再谈更高级的发布玩法

---

## 15. 日志、健康检查与排障入口

### 15.1 出现问题时先看哪

第一入口不是瞎猜，而是按顺序看：

1. GitHub Actions 日志
2. VPS 上 `shared/logs/`
3. 容器健康检查结果
4. 正式域名真实访问结果

### 15.2 健康检查至少要检查什么

最少检查：

1. `app` 是否起来
2. `postgres` 是否可连
3. `tusd` 是否可用
4. `tracker` 是否可用
5. `https://正式域名/` 是否真的返回成功

### 15.3 小白排障原则

不要先 SSH 上去乱敲命令。  
先看：

1. 这次部署是不是 Actions 就失败了
2. 失败在构建、连接 VPS、起容器、还是健康检查

**先定位失败阶段，再决定进不进机器。**

## 16. 以后你平时到底只需要记什么

这节是给你自己看的最终简化版。

### 16.1 你平时只记住 3 件事

1. 开发完就 `push`
2. 上线就点 `Deploy`
3. 出问题就点 `Rollback`

### 16.2 你不需要长期记住什么

你不应该被迫长期记住：

1. Docker 重启命令
2. Compose 细节
3. Caddy 配置命令
4. 一堆 Linux 运维命令
5. 每次发布的手工步骤

这些都应该被固定在仓库里。

## 17. 完成态验收

这套部署方案只有同时满足下面这些条件，才算真正成立：

1. 私有 GitHub 仓库不转公开，也能完成首装、升级、回滚。
2. 正式公网入口只有 `https://正式域名/`。
3. 浏览器看不到内部 sidecar 地址和内部端口。
4. 首次空白 Debian 12 VPS 可以通过固定流程完成安装。
5. 日常升级不要求人工 SSH 登录 VPS 手敲部署命令。
6. 回滚能明确指定版本，并且动作固定可重复。
7. 版本目录、当前版本、持久化数据三者物理分离。
8. 正式镜像里没有源码、文档、测试和日志垃圾。
9. 数据库迁移边界写清，没有把代码回滚和数据库回滚混成一件事。
10. GitHub Actions 失败时，能从日志看出失败阶段。

## 18. 风险与升级顺序

### 18.1 当前已知边界

这套方案默认承认下面这些现实：

1. 单 VPS 不是高可用
2. 不是灰度发布
3. 不是蓝绿发布
4. 不是多机集群
5. 不是无限免费 CDN

### 18.2 以后如果要升级，顺序必须是

1. 先补备份与恢复演练
2. 再补 staging 环境
3. 再补更稳的版本发布规范
4. 再补 self-hosted runner 或本机构建分流
5. 最后再考虑灰度、多机、高可用

禁止倒着来。

## 19. 最终一句话

这份方案的目的，不是把 `koko` 部署成“很高级的运维展览品”。

它真正的目标只有一个：

**让你以后把 `koko` 发到 Debian 12 单 VPS 上时，脑子里始终只有一套真相：GitHub 管版本与按钮，VPS 管运行，Cloudflare 管正式域名入口。**
