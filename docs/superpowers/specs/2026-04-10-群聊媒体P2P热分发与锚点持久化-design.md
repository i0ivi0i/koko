# 群聊媒体 P2P 热分发与锚点持久化设计

日期：2026-04-10  
状态：Draft  
适用范围：`koko` 前端 TypeScript / 后端 Rust 的万人实时群聊媒体（图片、视频）能力

## 1. 背景与问题

当前项目已经完成了“附件真相与消息真相分离”的第一轮收口，这条方向本身是对的：  
消息是否成立，不应该由前端本地上传状态直接决定；附件是否可用，也不应该伪装成“消息已经成功”。

但是，项目也暴露出两个真实矛盾：

1. 现在只是本地开发，未来很久之后才可能真正上对象存储。  
   如果今天就把整条上传链完全按 `对象存储直传` 心智来搭，会让当前阶段承担过早的协议复杂度、回包契约复杂度、运维复杂度。

2. 项目目标是“万人实时群聊”，媒体天然会产生高分发压力。  
   如果把所有图片/视频都长期存放在自己的业务服务器本地磁盘，未来不仅硬盘成本高，热内容带宽压力也会不断堆到业务主服务上。

同时，用户已经明确提出三条硬约束：

- 必须继续坚持 DDD 和 Unix 哲学。
- 不能重复手搓成熟轮子，尤其不能自己发明一套媒体协议栈。
- 尽量长期可回看，不接受“发过一次就只能趁在线时看”的临时媒体模型。

这意味着：  
**纯业务服务器磁盘托管不可取；纯 P2P 唯一存储也不可取。**

本设计的目标，就是在这两个极端之间，收敛出一条既真实、又可演进、又不堆屎山的媒体主链。

## 2. 核心结论

本项目的媒体能力采用：

**`WebTorrent 热分发 + 锚点持久化 + 消息仅引用附件`**

一句话解释：

- `WebTorrent` 负责热内容分发，让看过的人自动成为临时分发者，尽量把热门图片/视频的带宽从业务主服务移走。
- `锚点持久化` 负责冷内容可回看，保证发送者和第一批观看者都离线后，历史媒体仍尽量可取回。
- `消息` 永远只引用 `attachment_id`，不把传输细节、P2P 状态、tracker 细节、做种人数等运行态倒灌进领域真相。

这条设计不是“完全免费”。  
它的真实目标是：

- **显著降低主业务服务器的媒体带宽与磁盘压力**
- **尽量避免昂贵对象存储成为第一阶段前提**
- **保住群聊历史媒体的尽量长期可回看**
- **图片与视频同一轮设计、同一轮实现，共用一条 canonical 媒体主链**

这不是“零成本魔法”，而是“把成本从业务主服务转为极小锚点层 + P2P 热分发”的现实设计。

## 3. 非目标

本设计明确不追求以下目标：

- 不追求“完全不需要任何持久锚点，还能长期稳定回看历史媒体”。
- 不追求“第一阶段同时支持 WebTorrent、IPFS/Helia、BTFS 三套媒体网络并存”。
- 不追求“后端自己手搓 BitTorrent 协议、DHT、tracker、piece 交换、WebRTC 传输细节”。
- 不追求“媒体传输层的运行状态直接成为领域真相”。
- 不追求“一次性同时落地图片、视频、语音、音乐全部媒体类型”。
  本轮只覆盖图片与视频；语音、音乐仍明确排除在当前实现范围外。

本设计只回答：

- 未来群聊图片/视频应该怎样走一条清晰、可维护、可长期演进的媒体主链。

## 4. 为什么选 WebTorrent，不选双链

候选路线曾考虑：

1. `WebTorrent`
2. `IPFS + Helia`
3. `BTFS`
4. `WebTorrent + IPFS` 双活

最终选择 `WebTorrent` 作为单一 canonical 分发网络，原因如下：

### 4.1 为什么优先 WebTorrent

- 浏览器原生接入成熟，适合“看过的人继续分发”这个目标。
- 观看者天然可以短期成为分发者，特别适合万人群聊里的热内容。
- 对视频/大图这种可切片内容的分发心智更直接。
- 可以把“热门内容的大带宽”从主业务服务器挪走。

### 4.2 为什么现在不做 WebTorrent + IPFS 双链

双链看起来“更稳”，实际会把项目重新拖回复杂度失控：

- 同一附件会出现两套定位符、两套可用状态、两套回退语义。
- 前端要同时判断 magnet/infoHash 与 CID/pinning。
- 后端要同时维护两套 locator 契约和健康语义。
- 测试矩阵与排障复杂度会指数级上涨。

当前项目已经因为图片发送链过度复杂吃过亏。  
所以这次设计刻意坚持一条原则：

**单一 canonical 媒体网络优先，避免双活。**

### 4.3 为什么现在不把 BTFS 作为主路线

BTFS 不是不能用，但它会把另一套存储网络治理问题、生态确定性问题、运维语义问题带进项目。  
对当前阶段而言，这种新增复杂度不能带来足够明确的边界收益。

因此，本设计明确：

- `WebTorrent` 是第一阶段唯一 canonical 媒体分发网络
- `IPFS/Helia/BTFS` 不在本设计实施范围内

## 5. DDD 分层裁决

这一段是本设计最重要的防漂移边界。

### 5.1 Domain 层只拥有这些真相

领域层只承认以下事实：

- 附件是否存在
- 附件属于谁
- 附件是否允许被某条消息引用
- 当前请求者是否有权获取该附件的定位信息
- 附件当前对业务来说是 `ready / degraded / deleted`

领域层**不拥有**以下事实：

- 当前 swarm 里有多少 peer
- 当前 WebRTC 连接是否成功
- tracker 有没有回包
- 谁在做种、做种速度如何
- 是走 P2P 还是回锚点源

这些都属于运行态，不属于业务真相。

### 5.2 Application 层只负责编排

应用层负责：

- 准备发布媒体
- 确认锚点持久化完成
- 登记附件真相
- 创建带附件的消息
- 查询授权后的媒体定位符
- 标记附件退化或删除

应用层不直接实现 torrent 协议、tracker 协议或浏览器传输逻辑。

### 5.3 Adapter 层负责一切媒体网络接线

adapter 负责：

- `Uppy`
- `WebTorrent`
- tracker
- 锚点种子节点
- WebRTC / 浏览器传输
- HTTP locator 接口

adapter 不负责业务裁决。

### 5.4 Shell 层只负责本地体验态

前端壳层只负责：

- 选图 / 选视频
- 本地预览
- 进度
- 失败重试
- 预热中 / 回源中 / 暂不可用的展示

前端壳层不拥有：

- 权限真相
- 附件 ready 真相
- 消息成立真相

## 6. 成熟轮子复用原则

本设计明确禁止重复手搓以下能力。

### 6.1 必须复用的成熟轮子

- 浏览器上传：`Uppy`
- 浏览器 P2P 分发：`WebTorrent`
- 浏览器视频播放：原生 `<video>` / MSE 能力
- 图片预处理：继续复用现有成熟图片预处理库
- 视频元数据探测与预览：优先复用浏览器原生媒体能力与成熟库，不手搓私有解析器
- tracker / 种子节点：必须优先复用成熟 WebTorrent 生态实现

### 6.2 明确禁止自研的东西

- 自己实现 BitTorrent 协议栈
- 自己实现 DHT
- 自己实现 peer wire protocol
- 自己实现 browser torrent client
- 自己实现媒体切片协议
- 自己在 Rust 核心里硬塞一套私有 tracker 核心

### 6.3 为什么这样做

这些问题不是业务真相，而是成熟生态已经反复踩坑打磨过的基础设施问题。  
业务自己要掌握的是：

- 谁能发
- 谁能看
- 什么时候算 ready
- 什么时候算 degraded
- 消息怎么引用附件

协议栈和传输细节，不该变成项目私有屎山。

### 6.4 实现前必须先做的成熟轮子比选

本设计已经锁定：

- 浏览器侧 canonical 分发网络是 `WebTorrent`
- 浏览器侧 canonical 上传器是 `Uppy`

但在真正进入实现前，仍必须对以下基础设施做一次小型候选比选：

- `tracker` 的成熟实现
- `锚点种子节点` 的成熟实现
- 私有 tracker ticket 如何在“不改协议核心、不手搓新 tracker”的前提下接入

这一步的目标不是重新发明方案，而是确认：

- 有没有足够成熟、维护活跃的现成实现可直接接
- 现成实现能否支持私有群聊的最小门禁
- 是否需要把 tracker / 锚点节点做成独立进程或独立边车

本轮比选后的裁决先写死：

- 浏览器侧 canonical P2P 客户端：`webtorrent`
- 第一阶段 canonical tracker：`bittorrent-tracker`
- 高负载 tracker 备选：`wt-tracker`
- 锚点种子节点：优先 `webtorrent` Node 进程；若 Node 侧对浏览器 peers 的真实互通验证被官方实现细节卡住，再退到 `webtorrent-hybrid`

这一步必须产出明确结论，且必须遵守：

- 不允许因为“想保持纯 Rust”就手搓 torrent 核心
- 不允许因为“现成轮子不完全贴脸”就直接发明第二核心
- 只有在候选实现确实不能满足边界需求时，才允许进一步讨论薄适配或最小扩展

## 7. Canonical 媒体主链

本项目未来的图片/视频 canonical 主链固定为：

1. 用户选择媒体文件
2. 前端通过 `Uppy` 管理选择、校验、预处理、上传体验态
3. 前端将媒体交给 `WebTorrent` 客户端构建可分发对象
4. 系统把媒体同步到“锚点持久化层”
5. 只有锚点确认可提供后，应用层才登记 `attachment ready`
6. 消息创建时只引用 `attachment_id`
7. 后续群成员查看媒体时：
   - 优先尝试 `WebTorrent` swarm
   - swarm 不足时回退锚点源
8. 若锚点源也不可用，则附件进入 `degraded`

关键裁决：

**消息成立，必须晚于附件 ready；附件 ready，必须晚于锚点确认可提供。**

补充裁决：

- 图片与视频从第一轮实现开始就共用这条主链
- 不允许先把图片做成新链、再让视频临时挂旧链或旁路链
- 不允许为了赶进度给视频单独发明第二套 locator、第二套 ready 语义或第二套回退语义

## 8. 为什么必须有锚点持久化层

这是本设计最容易被误读的地方，必须写死。

“万人群聊里每个看过的人都可以成为分发者”这件事，只在热内容场景下成立。  
但“群聊历史里尽量长期可回看”要求系统还能支撑：

- 发送者已经离线
- 首批观看者已经离线
- 该媒体已不再热门
- 新成员隔了几天甚至更久再打开历史消息

如果此时没有任何锚点持久化层，内容就会掉种。  
因此：

- `P2P` 只能是热分发层
- `锚点` 才是长期可回看承诺的基础

这条锚点层不等于“传统对象存储必须先上”。  
它可以是：

- 独立的种子节点
- 便宜磁盘的锚点节点
- 社区节点 / 自有低成本节点

但无论如何，**必须存在**。

## 9. 附件真相模型

为防止状态模型重新膨胀，本设计刻意压缩领域状态。

### 9.1 领域层附件状态

- `ready`
  附件已经有稳定锚点，可被消息引用
- `degraded`
  附件真相仍在，但当前分发能力退化，需要预热或修复
- `deleted`
  业务上不可再使用

### 9.2 壳层临时体验态

这些状态只允许存在于 shell / adapter：

- `preparing`
- `publishing`
- `anchoring`
- `retrying`
- `warming`

这些不能升级为领域状态。

### 9.3 为什么不把更多状态放进领域

如果把 transport 过程里的每个阶段都做成领域状态，后面一定会长出：

- 过多 if/else 分支
- 多入口行为漂移
- 测试矩阵爆炸
- 壳层和领域层重复判断

因此领域层只保留对业务有意义的结果状态。

## 10. Locator 契约

消息层永远只存 `attachment_id`，不存 magnet、peer、tracker、piece 等细节。

授权后的媒体 locator 由后端查询接口临时发给前端。  
这个 locator 的职责只有两个：

- 告诉前端“当前优先怎么取媒体”
- 告诉前端“如果失败，允许回退到哪里”

建议 locator 形状：

- `attachment_id`
- `media_kind`
- `distribution_kind = webtorrent`
- `info_hash`
- `tracker_urls`
- `anchor_fallback`
- `availability_status`
- `expires_at`

其中：

- `info_hash` 是 canonical 分发标识
- `media_kind` 负责区分图片与视频，但不改变 locator 主链
- `tracker_urls` 属于 transport 信息，不进入消息真相
- `anchor_fallback` 只是一种受控回退入口

## 11. Tracker 与权限边界

这是另一个容易做坏的点。

### 11.1 权限真相不在 tracker

tracker 不负责判断：

- 用户是不是成员
- 是否仍在群里
- 是否有权读该媒体

这些必须继续由后端应用层裁决。

### 11.2 tracker 只负责网络发现

tracker 只负责：

- peer 发现
- swarm 协调
- announce / disconnect

它不应该成为群聊业务规则持有者。

### 11.3 私密群聊的最小做法

后端给已授权成员签发短期媒体 locator / tracker ticket。  
前端只能用这个 ticket 连接私有 tracker。  
如果成员失去权限，后端停止继续签发 locator。

这不等于内容彻底不可扩散。  
这点必须诚实记录：

- 看过内容的客户端天然可能保有内容片段
- P2P 私密媒体做不到“看过之后完全不可扩散”

本设计只能做到：

- 权威入口受控
- 正常路径受控
- 历史授权受控

不能神话成 DRM。

## 12. 锚点持久化层职责

锚点持久化层只做三件事：

1. 对附件内容保留最小长期可回看能力
2. 在 swarm 不足时提供回源能力
3. 在冷内容重新被访问时，帮助内容重新升温并回到 swarm

它不做：

- 消息业务真相
- 房间权限真相
- UI 进度真相
- tracker 业务真相

### 12.1 为什么叫“锚点”，不叫“媒体主存储”

这是为了防止设计重新滑回“所有媒体压力都堆到业务服务器主盘”。

锚点层的目标不是重新做一个庞大媒体中心，  
而是：

- 只承担长期可回看的最低保证
- 让热点优先走 P2P

## 13. 成功、失败与恢复语义

### 13.1 唯一业务成功锚点

以下都不算业务成功：

- 用户已选择文件
- 本地已开始做种
- 当前有人能从发送者这里拉到数据

真正业务成功是：

- 锚点持久化完成
- 附件已被登记为 `ready`
- 后端已允许消息引用该附件

### 13.2 失败语义

- 本地预处理失败：壳层失败，不生成附件真相
- P2P 发布失败：壳层失败，不生成附件真相
- 锚点持久化失败：不得进入 `ready`
- 消息创建失败：已 `ready` 的附件不丢失，可再次发送或移除

### 13.3 恢复语义

- 热内容优先走 P2P
- swarm 弱但锚点可用：自动回锚点预热
- 预热成功后重新回 swarm
- 锚点不可用：标记 `degraded`

### 13.4 明确禁止的假成功

以下行为必须永远禁止：

- 媒体还不可回看，但消息已正式成立
- 上传失败后草稿/消息凭空消失
- 只是本地种起来了，就把附件当成 ready

## 14. 与当前代码的关系

当前项目已经有：

- 附件与消息分离
- 后端统一附件读取权限
- 图片发送链重构经验

这轮设计不推翻这些正确边界，而是把“媒体分发层”换成更适合万人群聊的形态。

### 14.1 应保留的部分

- `attachment_id` 作为消息引用锚点
- 消息层只引用附件
- 后端统一裁决附件可见性
- 壳层只做体验态

### 14.2 应替换的部分

- 当前按对象存储直传心智设计的媒体传输部分
- 本地开发阶段过早承担的 S3 协议复杂度

### 14.3 不应复活的坏味道

- 双活媒体网络
- 双活 locator 契约
- 壳层第二套上传状态机
- transport 运行态倒灌领域层

## 15. 模块建议

这里不是实现清单，而是职责边界建议。

### 15.1 frontend

- `frontend/媒体/媒体草稿.ts`
  只管理图片/视频共用的草稿体验态
- `frontend/媒体/媒体发布.ts`
  只负责编排图片/视频共用的 `Uppy -> WebTorrent -> 锚点确认`
- `frontend/媒体/媒体定位.ts`
  只处理图片/视频共用的 locator 获取与过期刷新
- `frontend/媒体/媒体播放.ts`
  只处理查看侧图片/视频共用的 `P2P 优先 + 锚点回退`
- `frontend/媒体/媒体诊断.ts`
  只统一图片/视频共用的媒体错误码与日志
- `frontend/媒体/图片预处理.ts`
  只保留图片专属的预处理与预览辅助
- `frontend/媒体/视频元数据.ts`
  只保留视频专属的元数据探测与预览辅助

补充约束：

- 这些模块从第一天起就按“图片+视频共核”设计，不允许先做图片专用实现，再靠条件分支把视频硬塞进去。
- 图片和视频可以在壳层 presenter / viewmodel 上分开渲染，但发布、定位、诊断、回退主链必须共用。
- `frontend/媒体/` 是 canonical feature 根目录，替代历史上的 `frontend/图像/` 命名，避免目录层再次重命名。

### 15.2 backend

- `application`
  准备媒体发布、确认锚点完成、创建消息、查询 locator
- `adapter`
  tracker ticket、locator HTTP、锚点种子节点集成
- `domain`
  附件可见性与消息引用规则

## 16. 测试策略

测试必须按风险而不是按文件名堆砌。

### 16.1 Domain / Application

锁住：

- 只有 `ready` 附件才能创建消息
- `degraded` / `deleted` 不得伪装成成功
- 非成员不能拿 locator
- locator 过期必须重签
- 图片与视频共用相同的 ready / degraded / deleted 业务语义

### 16.2 Adapter

锁住：

- tracker ticket 生成与验证
- locator 返回正确的 `info_hash / tracker / fallback`
- swarm 不可用时能正确回退锚点
- 锚点恢复后能重新回 swarm

### 16.3 Frontend Shell

锁住：

- 图片与视频的选文件、发布、失败、重试
- 图片预览与视频预览都只消费同一媒体主链的状态
- 查看侧的 `预热中 / 暂不可用 / 已恢复`

### 16.4 Integration / E2E

必须锁住：

- 图片与视频发出后，稍后进入房间的新成员仍可回看
- 图片与视频的热内容都优先走 P2P
- 图片与视频的冷内容都依赖锚点恢复
- 锚点失效时消息仍在，但媒体显示 `degraded`

## 17. 迁移顺序

必须小步迁移，不做大爆炸。

### 17.1 Phase 1

- 保留现有附件/消息领域真相
- 引入图片/视频共用的 `媒体 locator` 查询能力
- 引入图片/视频共用的 `availability_status`

### 17.2 Phase 2

- 同一轮把图片与视频一起接入 `WebTorrent + 锚点持久化`
- 共享同一套 locator、ready 语义、degraded 语义和回退语义
- 语音、音乐继续排除在本轮之外

### 17.3 Phase 3

- 切换图片与视频的发送、查看与回放路径到单一 canonical 媒体主链
- 同步删除图片/视频旧链遗留入口，禁止形成“图片新链 + 视频旧链”的长期双活

### 17.4 Phase 4

- 用统一测试矩阵验收图片与视频
- 删除剩余旧媒体传输路径，只保留单一 canonical 媒体主链

## 18. 风险与防漂移说明

### 18.1 最大风险

把 P2P 当成“唯一持久层”，这是错误的。  
一旦这么做，“尽量长期可回看”就会在冷内容场景下失效。

### 18.2 第二风险

把 tracker、swarm 状态、peer 数量这些运行态塞进领域层。  
这会让领域模型被网络噪声污染。

### 18.3 第三风险

一开始就做 `WebTorrent + IPFS + BTFS` 多网络并存。  
这会把项目重新拖回双链和排障困难。

### 18.4 第四风险

为了“保持纯 Rust”而自己手搓 torrent 核心。  
这违反“不重复造轮子”的根原则，必须禁止。

## 19. 完成标准

只有同时满足以下条件，这条设计才算真正落地成功：

- 消息真相与媒体传输真相清晰分层
- P2P 只做热分发，不污染领域层
- 锚点层保障冷内容尽量长期可回看
- 热内容的主带宽不再长期压在业务主服务器
- 图片与视频都已落在同一条 canonical 主链上，没有临时旁路
- 没有第二套手搓媒体协议核心
- 没有长期双活链路
- 前后端边界仍符合 DDD 与 Unix 哲学

## 20. 最终裁决

本设计不是“免费无限存储方案”，而是：

**在不把媒体全部堆进业务主服务器，也不提前押大对象存储前提下，  
用成熟 P2P 轮子承担热分发，用最小锚点层承担长期可回看责任，  
并继续让消息只引用附件、业务真相只落在领域与应用层。**

这条路线的价值不在于“零成本幻想”，而在于：

- 边界真实
- 复杂度可控
- 轮子成熟
- 未来可演进
- 不再制造协议私有屎山
