# Web 前端全面 Pretext 化设计

日期：2026-04-09  
状态：设计已确认，待进入 implementation plan  
范围：`frontend` Web 聊天壳、消息列表、消息气泡、输入区、文本 rich inline、对应测试与前端依赖  
约束：一次性切换当前 Web 前端全部文本链路；不改 Rust 后端契约；不改 HTTP / realtime 协议；不保留回退闸门；不保留兼容壳；不允许双轨文本系统长期并存；前端运行时代码新增预算默认只有 1 个 `.ts` 文件

## 0. 一句话结论

这次不是“在现有 DOM 消息流上加一个测高工具”，而是把当前 Web 前端改造成：

1. `Pretext` 成为 Web 前端唯一的文本布局主权层
2. 消息正文、聊天气泡、输入区、多行文本、mentions / chips / code span 全部改由 `Pretext` 先算，再交给宿主表达
3. 当前宿主仍然是 DOM，所以渲染后的滚动与可见性观测继续由 DOM 提供，但 DOM 不再替我们裁决文本怎么断行、多高、多宽

最终目标不是“项目里用了 `Pretext`”，而是：

**Web 前端里凡是文本几何、换行、气泡宽度、输入区高度、rich inline 断行，都只认 `Pretext`。**

---

## 1. 官方证据链与为何这次不是臆想改造

这次“全面 Pretext 化”不是基于宣传语拍脑袋，而是基于官方 README、官方 demo 和当前 `0.0.5` API 形状。

### 1.1 官方 README 已证明的能力

官方仓库明确把 `Pretext` 定义为多行文本测量与布局库，核心 API 分两层：

1. `prepare()` + `layout()`
   - 适合段落高度、行数、宽度变化后的热路径重算
2. `prepareWithSegments()` + `layoutWithLines()` / `walkLineRanges()` / `layoutNextLineRange()` / `materializeLineRange()`
   - 适合逐行手动排版和宿主自绘
3. `@chenglou/pretext/rich-inline`
   - 适合 text runs、links、chips、code span 这类 rich inline 场景

这说明它从官方设计上就不是“只量高度”的小工具，而是文本布局内核。

### 1.2 官方 bubbles demo 已证明的能力

官方聊天气泡 demo 直接展示了：

1. 聊天气泡宽度可以由 `Pretext` shrinkwrap 裁决
2. 可以用 `walkLineRanges()` 找到“保持相同行数的最窄宽度”
3. resize 热路径不需要 DOM 文本测量

这和我们项目的消息气泡场景直接对口。  
它证明的不是“气泡也能配合用”，而是“气泡宽度本身就可以由 `Pretext` 主导”。

### 1.3 官方 rich-note demo 已证明的能力

官方 rich-note demo 直接展示了：

1. 普通文本 runs
2. links
3. code spans
4. atomic chips

一起参与断行与布局。  
这意味着我们要的“输入区、多行文本、mentions/chips/code span 全部进入同一文本内核”不是空想，官方已经把这层能力做成样例。

### 1.4 官方 justification-comparison demo 已证明的能力

官方 justification comparison 证明 `Pretext` 不只是浏览器贪心换行的复刻，而是可以承载更高阶的行布局算法，例如：

1. hyphenation
2. Knuth-Plass
3. 全局行布局比较

这对当前 IM 主链不是第一阶段硬需求，但它说明：

**一旦文本链路收口到 `Pretext`，以后更高级的排版策略有真实的演进空间。**

### 1.5 这条证据链对当前设计的结论

所以这次设计不是：

1. 把 DOM 文本流继续当主角，再让 `Pretext` 在旁边帮点忙

而是：

1. 用官方已证实的消息气泡、rich inline、逐行布局能力
2. 把 Web 前端文本层一次性升级成统一内核

## 2. 当前问题与真正根因

当前前端的问题不是“文本太慢”这么简单，而是“文本主权分散”：

1. [frontend/视图.ts](/E:/koko/frontend/视图.ts) 里的 `消息展示项` 仍然以 `body: string` 为最终渲染形状
2. [frontend/房间消息窗.ts](/E:/koko/frontend/房间消息窗.ts) 直接把 `${item.body}` 交给浏览器自然换行
3. [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 继续靠 CSS 气泡和单行 `input` 隐式决定文本几何
4. [frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts) 观察的虽然是 DOM 视口事实，但它当前耦合的消息块高度来源仍然是浏览器天然排版

这会导致：

1. 文本高度、换行、气泡宽度没有唯一 owner
2. 首屏恢复、历史补页、快速滚动时的尺寸预估缺少统一基础设施
3. 输入区仍然停留在单行 `input`，无法纳入统一文本布局链路
4. 未来要做虚拟列表、rich inline、统一多端文本规则时，会再次遇到“谁说了算”的问题

所以这次要解决的根因不是“某个组件慢”，而是：

**当前 Web 前端没有文本布局主权层。**

## 3. 设计目标

### 3.1 必须达到

1. Web 前端里所有文本几何裁决全部改由 `Pretext` 主导
2. 消息正文不再由浏览器自然换行决定最终断行结果
3. 聊天气泡宽度改由 `Pretext` shrinkwrap / natural width 结果驱动
4. 输入区改造成 `Pretext` 主导的多行文本表达
5. rich inline 统一进入 `@chenglou/pretext/rich-inline`
6. 现有未读恢复、阅读推进、历史补偿、跳到最新、realtime 并流语义保持不变
7. 不保留第二套文本系统，不留下兼容层或“以后再删”的过渡垃圾

### 3.2 明确不做

1. 不改 Rust 后端领域语义、房间恢复语义、阅读推进契约
2. 不改 HTTP / realtime 协议字段
3. 不把 `Pretext` 误当成状态管理、恢复状态机、socket 适配器
4. 不把当前 Web 前端一次性改写成 Canvas / SVG 聊天壳
5. 不为了“全面”而制造文件海、私有第二排版引擎、低价值包装层

## 4. 核心裁决：什么归 Pretext，什么不归 Pretext

### 4.1 归 `Pretext` 的主权

下列能力一律改由 `Pretext` 主导：

1. 消息正文断行
2. 消息正文高度
3. 每行范围 / 每行片段
4. 自然宽度与气泡收缩宽度
5. 输入区多行高度
6. rich inline 的行内断行与片段布局
7. 首屏恢复与历史补页时的大批量消息尺寸预计算
8. 未来虚拟列表的 item 文本尺寸权威

### 4.2 不归 `Pretext` 的职责

下列能力不属于 `Pretext` API 主权：

1. 房间恢复状态机
2. realtime 事件并流
3. 阅读推进的业务裁决
4. 用户点击、焦点、IME、滚动事件分发
5. 渲染后真实像素可见性观测
6. `scrollTop / scrollHeight`
7. 某个节点距离滚动容器顶部的当前像素偏移

### 4.3 为什么这里没有给 DOM 留“第二主权”

这里要避免概念漂移。

不是说“DOM 天生该管视口”，而是说：

1. `Pretext` 官方主张的是文本测量与文本布局
2. 当前 Web 前端的最终宿主是 DOM
3. 所以渲染后的滚动观测、像素偏移、可见片段采样，自然由当前宿主 DOM 提供

如果未来宿主从 DOM 换成 Canvas / SVG，这层宿主观测也会跟着换，而不是继续绑死在 DOM。

当前更准确的边界表述是：

**`Pretext` 统治文本布局；当前 DOM 宿主只保留渲染后视口观测。**

## 5. 方案比较

### 方案 A：局部引入 `Pretext`

做法：

1. 只给消息高度预测接 `prepare()` / `layout()`
2. 正文仍由浏览器自然换行
3. 输入区维持现状

优点：

1. 改动小
2. 风险低

问题：

1. 仍然是双主权文本系统
2. 气泡宽度、rich inline、输入区都无法统一
3. 不满足“全面 Pretext 化”

不采用。

### 方案 B：消息正文和气泡全面 Pretext 化，输入区后补

做法：

1. 先切消息正文、气泡、列表
2. 输入区和 rich inline 下一轮再接

优点：

1. 热路径收益高
2. 风险比一次切全量低

问题：

1. 输入区仍处在旧文本系统里
2. 依然不是你要求的一次性全面切换

不采用。

### 方案 C：一次性 Web 前端全部文本链路全面 Pretext 化

做法：

1. 消息正文、气泡、输入区、rich inline 全部进入同一文本布局内核
2. presenter 与 render 层只消费布局结果
3. 不保留兼容壳和回退闸门

优点：

1. 文本主权最干净
2. 后续虚拟列表、更多富文本、算法演进都建立在统一底座上
3. 最符合“无双轨、无冗余”的目标

问题：

1. 改动面最大
2. 验证门槛最高

采用此方案。

## 6. 最终架构

### 6.1 新的四层关系

当前 Web 前端应重组为：

1. `contract / transport / orchestrator`
   - 继续负责契约、传输、恢复、realtime、阅读推进
2. `text layout core`
   - 新增唯一文本布局内核，薄封装 `Pretext`
3. `presenter / view model`
   - 把消息事实绑定成可渲染的布局展示项
4. `shell / host renderer`
   - DOM 只负责表达布局结果和提供渲染后视口观测

### 6.2 这次不是重写业务边界

以下边界不变：

1. 后端继续拥有成员资格、消息成立、阅读真相
2. 前端继续只承载壳层同步状态
3. `房间滚动器` 继续只做视口副作用，不进入业务裁决

变化只在文本层：

1. 文本几何从浏览器自然排版迁到 `Pretext`
2. 文本结果不再在模板里临时生成，而是在布局层先产出

**presenter 不再只翻译文案，而要绑定统一文本布局结果。**

## 9. 文本布局内核设计

### 9.1 消息正文布局模式

消息正文默认走“逐行布局权威化”：

1. 先 `prepareWithSegments()` 或对应 rich-inline prepare
2. 再按目标宽度取逐行结果
3. presenter 消费逐行结果
4. 消息窗按行表达

原因：

1. 你要求的是全面 Pretext 化，不是“只算高度”
2. 如果最终断行仍由浏览器决定，那就仍然存在双主权

### 9.2 气泡宽度策略

消息气泡宽度必须由 `Pretext` 结果驱动，而不是继续依赖 CSS 天然 `fit-content`。

目标策略：

1. 以消息可用最大宽度为上限
2. 用 `naturalWidth` / line-range 结果裁决收缩宽度
3. 保证宽度变化不改变既定断行语义

这条设计直接对齐官方 bubbles demo。

### 9.3 输入区策略

当前单行 `input` 必须升级成可承载多行表达的宿主。  
输入区文本布局统一走同一内核，至少包括：

1. 文本 runs
2. rich inline 片段
3. 高度自适应
4. 换行后的 caret / selection 所需宿主表达约束

这里要注意：

1. `Pretext` 负责文本布局
2. 当前宿主 DOM 负责实际输入事件、焦点、IME 与渲染后交互

### 9.4 rich inline 策略

本次设计默认未来消息正文与输入区都会进入 `rich-inline` 路线。  
即使第一批落地时消息正文先只含 plain text，布局内核仍按可扩展到 rich inline 的方式设计，避免二次推翻。

### 9.5 缓存策略

允许的缓存只有：

1. prepare 结果缓存
2. 同一文本在不同宽度下的 layout 结果缓存

不允许的缓存有：

1. 直接缓存 DOM 节点测量真相
2. 缓存与当前字体 / 宽度 / line-height 解绑的脏布局结果

缓存失效条件必须至少绑定：

1. 文本内容
2. 字体规格
3. 宽度
4. line-height
5. rich inline 片段结构

## 10. 一次性切换顺序

这次既然不保留回退闸门和兼容壳，切换顺序必须严格受控。

### 10.1 第一步：先立唯一文本布局内核

先新增 [frontend/文本布局.ts](/E:/koko/frontend/文本布局.ts)，并明确：

1. 依赖 `@chenglou/pretext@0.0.5`
2. 依赖 `@chenglou/pretext/rich-inline`
3. 统一对外暴露消息布局 / 输入布局查询

没有这一步，后续所有改动都会变成散落调用。

### 10.2 第二步：升级 presenter 展示模型

先让 [frontend/视图.ts](/E:/koko/frontend/视图.ts) 具备“拿布局结果、产布局展示项”的能力。  
没有这一步，消息窗和聊天壳会各自重新猜布局数据，主权又会散。

### 10.3 第三步：切消息窗表达

把 [frontend/房间消息窗.ts](/E:/koko/frontend/房间消息窗.ts) 从字符串输出改成布局结果渲染。  
这是最关键的一刀，因为它真正废掉了浏览器自然换行的旧权威。

### 10.4 第四步：同一轮切输入区

同一轮把 [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 的 composer 从单行 `input` 切成 `Pretext` 主导的多行输入表达。  
如果这一步延后，前端就会短暂同时存在“消息是新文本系统、输入区是旧文本系统”的双轨状态，不符合当前设计。

### 10.5 第五步：让滚动器对接新的块级表达

最后校准 [frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts) 对新消息块表达的观察逻辑，确认：

1. 历史补偿仍稳
2. 阅读锚点采样仍稳
3. 未读恢复仍稳
4. 跳到最新仍稳

### 10.6 旧路径删除

只有当新链路接通后，才允许删除：

1. 旧的裸字符串正文模板
2. 旧的单行输入语义
3. 依赖浏览器自然换行的旧 CSS 假设

但本次设计的硬约束是：

**删除不是“以后补做”，而是这次切换的一部分。**

## 11. 风险点与防漂移规则

### 11.1 字体一致性风险

`Pretext` 的精度依赖字体规格稳定。  
实现阶段必须明确绑定：

1. font family
2. font size
3. font weight
4. line height
5. letter spacing（如果存在）

任何一项在 CSS 里偷偷改动而不通知布局内核，都会造成文本几何漂移。

### 11.2 宽度来源一致性风险

气泡最大宽度、内边距、别名行占位、输入区有效宽度，必须来自同一套宽度定义。  
禁止一半由 CSS 决定，一半由 JS 估算。

### 11.3 输入区交互风险

输入区切换到多行宿主后，要重点防：

1. IME
2. 回车发送与换行边界
3. 粘贴长文本
4. 光标位置与选区
5. 高度变化对壳层布局的影响

### 11.4 滚动稳定风险

只要布局结果和宿主表达之间存在抖动，阅读推进与历史补偿就会被放大。  
实现阶段必须优先守住：

1. 首屏未读恢复
2. 历史前插补偿
3. 贴底跟随
4. 跳到最新

### 11.5 绝对禁止的漂移

实现阶段若出现以下行为，默认判为偏离设计：

1. 为了赶进度临时保留旧 DOM 自然换行兜底
2. 消息和输入区分别走两套文本布局逻辑
3. 再新增第二个“文本 helper / layout helper / rich helper”运行时代码文件
4. 让 presenter、消息窗、聊天壳分别各存一份布局结果真相

## 13. 依赖与版本约束

实现阶段依赖策略明确如下：

1. 直接引入官方包 `@chenglou/pretext`
2. 使用当前已核对版本 `0.0.5`
3. 不自研同类文本测量轮子
4. 不包一层“项目自定义全家桶 SDK”再去调用 `Pretext`

原因很简单：

1. 官方当前 API 已足够覆盖消息正文、气泡、rich inline
2. 当前项目原则是优先复用成熟轮子
3. 再包第二层私有抽象，很容易变成“成熟能力 shadow-core”

## 14. 实现完成时的验收标准

只有同时满足以下条件，才算这次“全面 Pretext 化”真正成立：

1. Web 前端运行时代码里只存在一套文本布局主权层
2. 消息正文和输入区都不再依赖浏览器自然换行决定最终形状
3. 聊天气泡宽度由 `Pretext` 结果驱动
4. rich inline 进入统一内核
5. 现有未读恢复、历史补偿、阅读推进、跳到最新行为未退化
6. 工作树里没有留下兼容壳、回退闸门、旧模板残骸和低价值包装
