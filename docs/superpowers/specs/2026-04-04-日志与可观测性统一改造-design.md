# 2026-04-04 日志与可观测性统一改造设计

## 背景

当前项目已经在服务端入口初始化了 `tracing`，但运行后终端几乎看不到有用的实时日志，排障成本高。根因不是“没有日志系统”，而是“有 subscriber，但缺统一事件模型、缺入口 trace、缺成功路径事件、缺结构化字段”。同时，日志真相还必须继续收口在 Rust 进程内部，不能让 `run.ps1`、`xtask` 或前端制造第二套日志语义。

这次改造的目标，是把日志系统提升为项目统一的可观测性底座：开发环境下终端一眼能看到请求、realtime 命令、拒绝原因与关键失败；生产环境继续复用同一份 Rust 事件真相；未来可以平滑切到 JSON / OpenTelemetry / 落盘，而不重写业务埋点。

## 目标

- 让开发期终端直接呈现高信噪比的人类可读日志。
- 保证开发环境与生产环境共用同一份 Rust 事件源。
- 用结构化字段取代零散字符串，便于后续 JSON / OpenTelemetry 消费。
- 为 HTTP 与 realtime 补齐最关键的成功/失败路径日志。
- 保持默认不落盘，但预留后续机器视图与 exporter 接口。

## 非目标

- 本次不默认把日志写文件。
- 本次不直接接入 OTLP、Jaeger、Tempo 或集中式日志平台。
- 本次不在 `run.ps1`、`xtask`、前端 console 中增加日志真相。
- 本次不记录敏感信息，如管理员口令、cookie、token、完整消息正文。

## 设计原则

### 1. Rust 是唯一日志真相源

所有运行时日志都由 Rust 进程内部的 `tracing` 事件产生。脚本、壳层、前端只能透传环境变量或展示输出，不能创造第二套级别、字段、事件名称或格式语义。

### 2. 同一事件源，双视图输出

同一份 `tracing` 事件必须同时兼容：

- 开发默认的人类可读视图：终端紧凑、彩色、字段直观、便于扫读。
- 未来的机器视图：JSON / OpenTelemetry layer 可挂接，但默认关闭、默认不落盘。

这意味着业务与 adapter 代码只能关注“发什么事件、带哪些字段”，不能关心最终是 pretty 还是 JSON。

### 3. 结构化字段优先于长文案

日志以稳定字段为主，短消息为辅。终端是否“好看”来自 formatter，而不是靠在代码里拼大量自然语言句子。

### 4. span 负责因果链，event 负责事实点

- HTTP 请求使用请求级 span。
- realtime 连接使用连接级 span。
- 关键命令处理使用事件或子 span。

在 async / 并发环境里，不允许只靠平铺字符串日志推断调用链。

### 5. 默认克制，不制造噪音

只记录真正有排障价值的开始、结束、拒绝、失败与关键状态变化。流式 body chunk、低价值心跳和重复成功噪音默认不打。

## 架构设计

## 1. Subscriber 与 Layer 组合

日志初始化统一收口到 `src/support.rs`。

`init_tracing` 从现在的单一 `fmt().with_env_filter(...).finish()`，升级为 `registry + filter + fmt layer (+ future layers)` 结构。默认行为：

- 读取 `RUST_LOG` 作为唯一过滤入口。
- 若未设置 `RUST_LOG`，由 Rust 内部提供默认 filter。
- 默认启用人类可读 formatter。
- 预留 JSON formatter 的构建逻辑，但默认关闭。
- 预留后续 OpenTelemetry bridge / layer 的接入点，但本次不启用 exporter。

推荐的内部结构：

- `EnvFilter`
- human fmt layer
- optional json fmt layer
- future otel/log bridge layer

## 2. 事件命名与字段约定

先统一一套跨 HTTP / realtime / app 的基础字段，后续 JSON 与 OTel 直接复用：

- `event`
- `target`
- `status`
- `error_code`
- `latency_ms`
- `request_id`
- `method`
- `path`
- `matched_path`
- `session_id`
- `room_id`
- `client_message_id`
- `socket_id`

约束：

- 字段不存在就不记录，不制造空字符串或伪默认值。
- 消息正文不直接入日志；如果需要，只记录长度或是否为空。
- 敏感 header 不记录。

## 3. HTTP 观测

在 `src/http.rs` 的 `server_router` 统一挂 `tower_http::trace::TraceLayer::new_for_http()`。

默认开启：

- `on_request`
- `on_response`
- `on_failure`

默认关闭：

- `on_body_chunk`
- `on_eos` 的额外噪音输出

`make_span_with` 负责把请求级稳定字段挂到 span 上，至少包括：

- `method`
- `path`
- `matched_path`
- `request_id`

`on_response` 负责记录：

- `status`
- `latency_ms`

`on_failure` 负责记录：

- failure class
- `latency_ms`

并且要显式屏蔽 `cookie`、`authorization` 等敏感头。

## 4. Realtime 观测

在 `src/rt.rs` 中补齐当前缺失的成功路径事件，不能只在失败时 `warn!`。

必须记录的事实：

- 连接建立
- 连接鉴权成功 / 失败
- `subscribe_room_stream` 成功 / 拒绝
- `send_text_message` 成功接收 / 业务拒绝 / 广播失败

建议字段：

- `socket_id`
- `session_id`
- `room_id`
- `client_message_id`
- `error_code`

其中：

- 业务拒绝默认记为 `warn`
- 基础设施失败默认记为 `error`
- 成功路径默认记为 `info`
- 高频但低价值细节才考虑 `debug`

## 5. 框架内置信号

`socketioxide` 打开 `tracing` feature，接收框架内部已提供的连接、extractor、发送失败等 tracing 信号。

这类日志只做补充，不能替代业务自己的事件；排障时以项目自己的业务事件模型为主，以框架日志为辅。

## 6. OpenTelemetry 预留

本次不直接接 exporter，但要求内部结构兼容未来接入：

- 继续以 `tracing` 作为唯一事件源。
- 后续通过 `tracing-opentelemetry` 或 `opentelemetry-appender-tracing` 追加 layer。
- 业务代码不直接依赖 OTel SDK，也不在 handler / use case 里写 OTel 专属逻辑。

这样未来接入机器视图时，只需要在 Rust 日志初始化层补 exporter / bridge，而不需要重写应用层日志代码。

## 落地范围

### 必改文件

- `Cargo.toml`
  - 为 `socketioxide` 打开 `tracing` feature。
  - 为 `tracing-subscriber` 补足本次 formatter 所需 feature。
- `src/support.rs`
  - 重构 `init_tracing`，引入 layer 组合与输出模式预留。
- `src/http.rs`
  - 接入 `TraceLayer`，并定制 span / response / failure 记录。
- `src/rt.rs`
  - 为关键成功路径与失败路径补齐结构化事件。

### 不改语义的文件

- `run.ps1`
- `xtask`

它们本次不承担任何日志定义职责，只继续作为启动壳与输出透传壳存在。

## 验证方案

本次改造按 TDD 执行。

### 测试先行

先补失败测试，至少覆盖：

- `init_tracing` 仍可重复调用，不 panic，不重复安装 subscriber。
- HTTP router 接上 trace 后，请求能产出开始/结束或失败事件。
- realtime 成功与失败路径都能产出结构化事件。

### 验证命令

实现后执行：

- `cargo test`
- `cargo check`

必要时追加针对 HTTP / realtime 的集成测试，只验证“事件确实被发出且关键字段存在”，避免对整行格式做脆弱断言。

## 开发期观看方式

默认直接看 Rust 人类可读 formatter 输出。

如需终端高亮，可在开发者本机使用 `tailspin` 作为观看器：

```powershell
cargo run 2>&1 | tspin
```

它只负责高亮终端输出，不进入项目依赖、不进入 Rust 核心设计、不进入启动真相。

## 预期效果

终端最终应能稳定看到类似这样的高信噪比日志：

```text
INFO  http.request.start method=POST path=/api/rooms/join request_id=...
INFO  http.request.end method=POST path=/api/rooms/join status=200 latency_ms=14
INFO  rt.connect session_id=... socket_id=...
INFO  rt.subscribe_room_stream.ok room_id=... session_id=...
WARN  rt.send_text_message.rejected room_id=... session_id=... error_code=membership_required
ERROR http.request.failed method=POST path=/api/rooms/... status=500 latency_ms=3 error_code=internal
```

开发环境与生产环境共享同一份 Rust 事件真相，只是输出视图与过滤级别可以不同。

## 官方依据

- `tracing` 作为 Rust 应用级结构化诊断框架，推荐在 async 场景使用 spans / `#[instrument]`。
- `tracing-subscriber` 官方支持 layer 组合、`EnvFilter`、human-readable formatter 与 JSON formatter 并存。
- `tower-http` 官方推荐用 `TraceLayer::new_for_http()` 观测 HTTP 请求生命周期，并通过 `make_span_with`、`on_response`、`on_failure` 定制事件。
- `socketioxide` 官方提供 `tracing` feature，可发出框架级 tracing 日志。
- OpenTelemetry Rust 生态提供把 `tracing` 事件桥接为 OTel `LogRecord` 的 layer，说明 `tracing` 继续做单一事件源是可持续路径。
