# 2026-04-04 日志与可观测性统一改造设计

## 背景

当前项目已经在服务端入口初始化了 `tracing`，但运行后终端几乎看不到有用的实时日志。  
问题本质不是“没有日志系统”，而是“日志太少、成功路径缺失、HTTP 入口没有 trace、realtime 只有失败 warn，排障时看不到主信息流”。

这个项目是纯 Rust 的单体群聊服务，未来会部署到 Linux 公网服务器上。  
当前目标不是建设一套完整观测平台，而是先把开发期和生产环境最需要的日志看见、看清、看够用。

## 目标

- 开发期终端能直接看到有价值的 Rust 日志。
- 生产环境运行时持续输出可排障的 Rust 日志。
- 补齐 `/api/**` 请求日志。
- 补齐 realtime 关键成功/失败路径日志。
- 保持日志真相只在 Rust 进程内部，不让脚本和前端长出第二套语义。

## 非目标

- 本次不做 JSON 日志。
- 本次不做 OpenTelemetry、OTLP、Jaeger、Tempo。
- 本次不做日志落盘。
- 本次不引入 `request_id`。
- 本次不建立完整“正式事件契约表”。
- 本次不专门搭一套日志捕获测试基础设施。

## 设计原则

### 1. 先解决排障痛点，不先做观测平台

先让终端里有高信噪比日志，能看出：

- HTTP 请求有没有进来
- realtime 有没有连上
- 订阅有没有被拒绝
- 消息有没有进入成功路径
- 广播有没有失败

先做到这一步，比先设计 exporter、JSON、跨系统链路字段更重要。

### 2. Rust 仍是唯一日志真相源

运行时日志仍只由 Rust 内部 `tracing` 产生。  
`run.ps1`、前端 console、Linux 部署脚本都只做启动、采集、转发、查看，不定义第二套日志语义。

开发环境与生产环境共用同一份 Rust 日志事件。  
环境不同，只体现在查看方式和过滤级别不同，不体现在“谁来定义日志真相”。

### 3. 少机制，少字段，少噪音

本次只保留排障最有价值的日志，不追求一次把所有字段、所有事件命名、所有未来预留做满。  
如果一条日志对当前本地开发排障没帮助，就先不加。

### 4. 先补关键成功路径

当前最大问题不是“失败没有日志”，而是“成功路径没日志，导致不知道链路走到哪一步”。  
所以这次要优先补：

- HTTP 请求进入 / 完成
- realtime 连接建立
- realtime 鉴权失败
- 房间订阅成功 / 失败
- 文本消息发送成功 / 失败
- 广播失败

## 方案

## 1. `src/support.rs` 只做适合开发与生产共用的 tracing 初始化

保留 `init_tracing` 单入口，不做复杂 layer 组合，不做 JSON / OTel 预留。

只做这几件事：

- 继续读取 `RUST_LOG`
- 未设置时默认 `info`
- 使用适合终端和服务器标准输出共用的 `tracing_subscriber::fmt()` 输出
- 输出级别、目标和必要上下文，便于肉眼扫读和服务器排障

目标是“Rust 一处产生日志，开发和生产都直接可用”，而不是“未来可扩展成很多输出模式”。

## 2. `src/http.rs` 只给 `/api/**` 挂基础请求 trace

在 API 边界接入 `tower_http::trace::TraceLayer::new_for_http()`。

范围固定为：

- 记录：`/api/**`
- 不记录：`/`、`/admin` 前端壳、`/assets/**`、`/wasm/**`、静态 fallback

这样能避免静态资源把终端刷满。

本次 HTTP 日志只要求终端能看到：

- 请求开始
- 请求完成
- 失败分类
- 基本路径和状态码

不引入 `request_id`，也不在本次桥接 `error_code -> response extensions`。

如果后面确实需要跨入口关联，再单独加，不在这次开发期日志优化里提前上。

## 3. `src/rt.rs` 补最关键的 realtime 日志

不建立完整事件体系，只补最有用的业务日志。

建议最少补这些：

- `info!`: socket 连接建立
- `warn!`: realtime 鉴权失败
- `info!`: `subscribe_room_stream` 成功
- `warn!`: `subscribe_room_stream` 被拒绝
- `info!`: `send_text_message` 成功进入权威成功路径
- `warn!`: `send_text_message` 被业务拒绝
- `error!`: 广播 / emit 失败

字段也只保留当前最值钱的几项：

- `socket_id`
- `session_id`
- `room_id`
- `client_message_id`
- `error_code`

字段不存在就不记，不制造空字符串。

## 4. `socketioxide` tracing feature 只做补充

可以为 `socketioxide` 打开 `tracing` feature，让框架内置信号也能出来。  
但它只是补充，不替代项目自己的业务日志。

排障时仍以项目自己补的业务日志为主。

## 5. 生产环境只负责采集和查看，不负责定义日志

生产环境同样输出 Rust 日志，但默认仍由应用写到 `stdout / stderr`。  
Linux 服务器上的 `systemd`、Docker、进程管理器、日志查看命令只负责：

- 接住 Rust 输出
- 持久化或轮转
- 实时查看
- 转发到外部系统

它们不是新的日志真相源，只是 Rust 日志的承接层。

## 落地范围

### 必改文件

- `Cargo.toml`
  - 给 `socketioxide` 打开 `tracing` feature。
- `src/support.rs`
  - 把 tracing 输出调成更适合开发终端观看的格式。
- `src/http.rs`
  - 只在 `/api/**` 接入基础 `TraceLayer`。
- `src/rt.rs`
  - 补齐关键 success / reject / failure 日志。

### 本次不改

- `run.ps1`
- 前端日志
- 日志落盘
- OTel / JSON 输出

说明：

- 生产环境允许由 Linux 运行环境保存和查看日志
- 但本次不在应用内部自研文件落盘或集中式日志接入

## 验证

这次验证不追求完整日志测试体系，只验证“改完后开发环境和生产运行方式下都能看到关键日志”。

至少执行：

- `cargo check`
- `cargo test`
- `cargo run`

然后手动验证一条最小链路：

1. 打一个 `/api/**` 请求
2. 建立一次 realtime 连接
3. 订阅一个房间
4. 发一条消息

终端应至少能看到：

```text
INFO  ... http request started/completed
INFO  ... realtime connected
INFO  ... subscribe_room_stream ok
INFO  ... send_text_message accepted
```

失败路径则至少能看到：

```text
WARN  ... auth rejected
WARN  ... subscribe_room_stream rejected
WARN  ... send_text_message rejected
ERROR ... broadcast failed
```

如果部署到 Linux 服务器，查看方式应保持同一原则：

- 应用继续输出 Rust 日志到 `stdout / stderr`
- 由服务器运行环境负责查看，例如 `journalctl -u <service> -f` 或容器日志命令
- 看到的仍是同一份 Rust 日志，不是第二套脚本日志

## 结论

这次改造的正确边界，不是“把日志系统一步做到未来十种用途都兼容”，而是先把当前这个纯 Rust 群聊项目在开发期和生产环境最缺的排障信息补出来。  
先做到“统一真实日志源只有 Rust，开发和生产都看得见、看得懂、够排障”，再决定值不值得继续往 JSON、OTel、链路字段、正式事件契约推进。
