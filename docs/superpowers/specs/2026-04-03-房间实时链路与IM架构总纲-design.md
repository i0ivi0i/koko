# 房间实时链路与 IM 架构总纲设计

日期：2026-04-03

## 定位

这份设计不是某次 bug 的补丁说明，也不是立刻展开的大重构计划。  
它是 `koko` 后续房间聊天、实时同步与多壳演进的总纲，用来回答三件事：

1. 当前房间实时链路里，哪些才是权威真相
2. `domain / application / contract / adapter / shell` 在 IM 里分别该管什么
3. 系统后续应如何向 Telegram / WhatsApp 这类成熟 IM 的稳定做法靠拢

它的作用是先把“什么必须长期成立”说清，再允许后续按批次落地，而不是继续围绕页面现象修补状态机。

## 背景

当前仓库已经具备：

- 以 `socketioxide` 为主的 Rust 实时通道
- 房间快照、加入房间、消息持久化、房间成员关系
- 以 `Dioxus` 为壳层的 Web 聊天页面

但最近连续暴露出一类反复出现的问题：

- 页面显示“连接中”，但真实订阅并未完成
- 本地 pending 被误看成历史已成立消息
- 退出房间再进入时，旧快照、旧请求、旧订阅结果污染新状态
- 构建产物、静态资源、运行时页面三者没有完全说同一种真相

这些问题说明，当前系统的主要风险不在领域规则本身，而在于：

- 连接真相、订阅真相、消息成立真相、历史同步真相没有被明确分开
- 壳层与适配层对“真实已成立”与“本地暂存体验态”的边界还不够硬

## 目标

本设计只定义长期稳定的架构总纲：

- 明确房间实时链路中的权威真相
- 明确各层职责边界
- 明确房间进入、发消息、退出重进、断线恢复的数据流
- 明确 `koko` 向成熟 IM 体系演进时应吸收哪些原则

## 非目标

本设计不直接展开：

- 具体状态枚举重命名
- 具体 offset 字段名与数据库表结构
- 具体前端组件改造清单
- 一次性完成多端同步能力
- 对 `socketioxide`、`Dioxus`、`Axum`、`SQLx` 的大范围替换

这些都应该在后续实施计划中逐步拆开。

## 外部依据

### 1. Dioxus 对静态资源与入口页面的官方建议

Dioxus 官方在 `Dioxus.toml` 的 `web.resource.script` 中明确支持把外部 JavaScript 资源纳入页面入口；同时官方示例也表明，当页面需要明确控制入口 HTML 与外部资源时，可以使用自定义 `index.html`。  
这说明对 IM Web 壳来说，外部实时资源的加载顺序与入口语义，属于必须显式建模的边界，而不是可以长期依赖默认隐式打包结果的细节。  
来源：

- [Dioxus Configure Project](https://dioxuslabs.com/learn/0.7/guides/tools/configure/)
- [Dioxus PWA example README](https://github.com/DioxusLabs/dioxus/blob/v0.6.3/examples/pwa/README.md)

### 2. Socket.IO 对消息投递与恢复边界的官方说明

Socket.IO 官方文档明确指出：

- 默认只保证消息顺序，不保证一定送达
- 默认投递语义是 `at most once`
- 若要做到更强的交付保证，需要应用自己实现 `ack / retries / event id / offset / persistence`
- Connection state recovery 能帮助处理临时断线，但恢复“不保证总成功”，客户端和服务端仍需重新同步状态
- room 是服务端概念，客户端并不拥有“我加入了哪些 room”的权威真相

这与本项目要建立的边界高度一致：  
实时库提供传输能力，但“消息成立”“历史完整”“成员资格成立”必须由应用自己保证。  
来源：

- [Socket.IO Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)
- [Socket.IO Connection state recovery](https://socket.io/docs/v4/connection-state-recovery)
- [Socket.IO Rooms](https://socket.io/docs/v4/rooms/)

### 3. Telegram 对同步状态与补洞的官方做法

Telegram 官方更新机制要求客户端基于 `seq / pts / qts` 顺序应用更新，一旦发现 gap，必须主动补差。  
这说明成熟 IM 的稳定性核心不是“某条连接永不出错”，而是“客户端拥有可恢复的事件位置，服务端允许按位置补齐缺口”。  
来源：

- [Telegram Working with Updates](https://core.telegram.org/api/updates)

### 4. WhatsApp 公开工程方向

WhatsApp 公开资料表明：

- 多设备能力的核心不是“手机始终在线”，而是把同步、身份、设备列表与消息状态做成独立的长期机制
- 每个设备拥有自己的身份与同步职责，服务端维护账户到设备集合的映射
- 历史与应用状态需要在设备间同步，而不是把单一前端壳当成唯一事实来源

这说明 `koko` 未来若要演进，不应围绕单页面状态做强绑定，而应围绕“稳定契约 + 可恢复同步”前进。  
来源：

- [How WhatsApp enables multi-device capability](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)
- [How Device Verification protects your WhatsApp account](https://engineering.fb.com/2023/04/13/security/whatsapp-device-verification-protects-your-account/)

## 核心判断

`koko` 的房间聊天系统，不应被理解成“Web 页面上挂了一条 socket”。  
它应被理解成一条轻量 IM 真相链：

- 房间快照负责建立历史基线
- 实时事件负责表达增量变化
- 服务端确认负责裁定消息是否成立
- 事件位置负责支撑断线恢复与多壳同步

这条判断比“现在能不能聊天”更重要，因为它决定后续所有壳层、协议和持久化设计是否稳定。

## 真相分层

系统长期必须把以下四类真相拆开：

### 1. 连接真相

表示客户端是否真的连到了实时传输通道。  
它只说明 transport 可用，不说明用户是否已经获得某房间的有效事件流。

### 2. 订阅真相

表示客户端是否真的订阅到了某个房间的事件流。  
它说明“这个房间的实时增量现在可以进来了”，但仍不等于历史已经完整，也不等于消息已成立。

### 3. 持久化真相

表示某条消息是否已经被服务端校验、接收、落库，并纳入房间权威历史。  
这是“消息成立”的唯一依据。

### 4. 同步真相

表示客户端当前房间视图是否与服务端权威历史重新对齐。  
它依赖快照基线、事件位置、补洞策略与去重策略共同成立。

## 分层边界

### `domain`

`domain` 只拥有：

- 房间
- 成员关系
- 消息
- 事件语义
- 错误语义

`domain` 不知道：

- HTTP
- Socket.IO
- `Dioxus`
- 数据库表结构
- 页面状态

### `application`

`application` 只拥有：

- 加入房间
- 加载房间快照
- 发送消息
- 校验成员资格
- 生成稳定事件与稳定错误码

它负责把业务规则组织成稳定用例，但不负责页面文案、不负责 socket 生命周期、不负责浏览器体验态。

### `contract`

`contract` 是多壳共享的唯一通用表面，应长期稳定承载：

- command
- query
- snapshot
- event
- error code

Web、CLI、未来移动端都只能消费这层，不得各自发明一套业务语义。

### `adapter`

`adapter` 只负责：

- 协议翻译
- 鉴权接入
- IO 编排
- 数据库存取
- 实时通道接入
- 静态资源与构建产物对外提供

`adapter` 可以知道 `socketioxide`、`Axum`、`SQLx`、静态文件路径，但不得把成员资格、消息成立、房间可见性这些业务真相藏进来。

### `shell`

`shell` 只拥有：

- 交互编排
- 视图状态
- 草稿
- pending 呈现
- 连接提示
- 最近打开房间
- 滚动位置

`shell` 不能拥有：

- 房间真实成员资格
- 消息是否成立
- 房间历史是否完整
- 订阅是否被服务端接受的最终裁决

## 壳层约束

Web 壳后续必须遵守以下约束：

1. 页面不能因为“发出了 connect 命令”就显示已连接
2. 页面不能因为“点了发送”就把消息视为已成立历史
3. 页面可以显示 pending，但 pending 只能是体验态
4. 退出房间时只能清理临时态，不能推翻服务端历史
5. 重进房间时必须重新建立快照基线与实时订阅，不能复用旧结果假装恢复成功
6. 旧请求、旧快照、旧订阅事件必须按请求身份和房间身份丢弃

## 核心数据流

### 1. 进入房间

进入房间时应严格分成两步：

1. 通过后端返回房间快照，建立房间历史基线
2. 建立实时订阅，并在收到订阅成功信号后开放实时交互

因此：

- “拿到快照”只说明当前历史基线已知
- “订阅成功”才说明增量事件流已接通

两者不能塌成一个状态。

### 2. 发送消息

发送消息的正确链路是：

1. 前端生成发送意图与稳定 `client_message_id`
2. 若当前未完成真实订阅，发送入口关闭或显式失败
3. 服务端执行合法性校验与持久化
4. 服务端返回确认
5. 前端将对应 pending 提升为已成立消息

因此：

- 本地出现一条气泡，不等于消息已经进入历史
- 历史成立只能由服务端确认、后续快照或权威事件流证明

### 3. 退出再重进房间

退出房间时应清除：

- 草稿
- 当前订阅句柄
- 本地交互临时态

但不应清除：

- 服务端历史
- 权威成员关系
- 稳定房间身份

重进时，必须重新走：

1. 房间快照
2. 新订阅成功
3. 旧结果过滤

任何残留旧请求、旧快照、旧 room 事件都必须被拒绝进入当前房间视图。

### 4. 断线重连与补洞

当连接中断时，系统不应假设本地视图仍完整。  
正确做法是：

1. 标记实时链路已中断
2. 连接恢复后，根据事件位置请求补差
3. 对补回事件执行幂等合并与去重
4. 若补差失败，则重新拉一份房间快照作为新基线

这也是后续从“可聊天”走向“可恢复聊天”的核心分水岭。

## 向成熟 IM 靠拢的演进原则

### 1. 把同步能力放在连接能力之前

成熟 IM 的韧性核心不是“连接不掉”，而是“掉了还能补回来”。  
因此 `koko` 的长期目标应是可恢复同步，而不是盲目强化单条长连接。

### 2. 引入房间级事件位置概念

后续系统应拥有房间级事件位置，例如 offset / sequence / cursor 一类概念。  
它不一定马上落具体表结构，但设计上必须预留这个锚点。

未来所有壳都围绕这个锚点恢复：

- Web
- CLI
- 未来移动端

### 3. 以服务端确认后的消息作为唯一历史

系统未来无论是否保留乐观 UI，都必须坚持：

- 本地乐观态只是体验
- 服务端确认后才进入权威历史
- 历史与实时增量应能相互对齐并去重

### 4. 多壳共核，而不是页面即流程

房间进入、历史读取、消息发送、事件补差，都应先是稳定契约能力，再被具体壳消费。  
不能让 Web 页面流程反向定义业务。

### 5. 渐进增强，而不是一次性重做

总纲先立住，落地应分批进行：

1. 先彻底拆开连接真相、订阅真相、消息成立真相
2. 再补稳定消息确认链
3. 再补房间事件位置与补洞
4. 最后再谈多端与更强恢复能力

## 对当前仓库的直接约束

在后续任何实现中，至少要满足以下约束：

1. `socketioxide` 继续作为实时主通道 adapter，不承担业务真相
2. `Dioxus` 壳层不再把连接意图当成连接成功
3. 房间历史展示必须以服务端快照为基线
4. 本地 pending 不能冒充已成立历史
5. 重新进入房间时必须允许旧结果失效
6. 静态资源、构建产物、运行时页面必须围绕同一份资源真相
7. 任何未来的 CLI / 移动端接入都应直接消费稳定 contract，而不是复制 Web 页面逻辑

## 风险提醒

如果后续实现偏离这份总纲，最容易再次出现的问题是：

- UI 抢跑真实状态
- 连接对象被误当成员真相
- pending 被误看成历史消息
- 重连后事件重复或丢洞
- 多壳之间各自维护一套“近似真相”

这些都是成熟 IM 系统最忌讳的问题，因此必须在架构层先被禁止，而不是等线上现象再修。

## 结论

`koko` 后续的正确演进方向，不是继续围绕“页面上怎么挂 socket”优化，而是建立一条稳定的 IM 事实链：

- 房间快照作为基线
- 实时事件作为增量
- 服务端确认作为消息成立依据
- 事件位置作为恢复锚点
- 多壳通过统一 contract 消费这些事实

只有这样，当前 Web 壳、未来 CLI、未来移动端，才不会在一次次“连接中”“消息不见了”“重进丢历史”这类问题里重复踩坑。
