## 0. 这份 spec 要解决的不是“小网络问题”

这次不是“某个端口偶尔没开”“局域网里某台手机偶尔连不上”这么浅的问题。

这次真正要收口的是一句话：

**浏览器用户永远只该认识一个 HTTPS 入口，项目内部再复杂，都不允许把内部地址、内部端口、内部协议真相泄漏给浏览器。**

如果这句话不写成硬规则，项目就会长期漂成下面这些坏状态：

1. 本机作者自己能跑，但局域网其他设备不稳定，最后你只能在自己电脑上“假装多人测试”。
2. 开发阶段和正式上线阶段使用两套完全不同的网络脑子，导致“本地能跑”对正式部署几乎没有参考价值。
3. 页面入口表面是 HTTPS，但上传、实时、媒体下一跳偷偷掉回 HTTP 或 `127.0.0.1`。
4. 浏览器一旦拿到 `127.0.0.1`、`localhost`、`:1081`、`:7072`、`:7073` 这种内部地址，就会把“机器内部零件”误当成“用户入口”。
5. 未来你把项目“甩”进 VPS 之后，还得继续手搓多条外部路径、额外端口和二次解释，完全违背“直接跑起来”的目标。

所以这份 spec 的目标不是“再修一个 LAN bug”，而是把**项目网络真相**正式收口成：

**开发时和正式部署时，用户视角都只有一个 HTTPS 入口；区别只是在开发时这个入口是局域网 IP，上线时这个入口是正式域名。**

## 1. 主人的真实需求，禁止被执行层偷换

这次网络整顿必须服从下面这句原始需求，禁止执行时偷换成工程师自嗨版本：

> 未来正式部署时，我只想直接把项目源代码二进制甩进公网 VPS 中就能自动完美运行，cloudflared 和域名我都准备好了；现在局域网内网也要能访问本机开发测试时的项目，这样我才能模拟未来公网用户进行测试源代码。

把它翻成项目约束，就是下面 4 句：

1. **现在开发测试时**，局域网里的其他设备必须能直接访问  
   `https://开发电脑局域网IP/`
2. **未来正式上线时**，公网用户必须只访问  
   `https://正式域名/`
3. **开发和上线禁止各玩一套**  
   现在不是“本机特殊玩法”，以后也不是“上线另起炉灶”
4. **用户永远只记一个地址**  
   开发时记局域网 IP  
   上线时记正式域名  
   除此之外，不允许再让用户理解内部端口、sidecar、代理细节

## 2. 前因后果：为什么现在必须整顿

### 2.1 表面现象

之前的项目网络形态已经出现了危险信号：

1. 有些路径在作者自己电脑上能跑。
2. 但局域网其他设备并不能稳定、完整地按未来公网用户的方式使用。
3. 页面入口、上传入口、实时入口并没有被真正收成一个用户视角。
4. 项目内部的回环地址和内部端口，仍然在某些链路里被当成“可下发给浏览器的地址”。

### 2.2 深层原因

真正的问题不是“某个端口忘了开放”，而是**项目里同时存在两套网络真相**：

1. 一套真相说：浏览器应该走统一 HTTPS 入口。
2. 另一套真相又在某些下游步骤里说：浏览器下一跳可以直接去内部地址。

这会导致一种很隐蔽但很致命的错觉：

1. 页面表面能打开，看起来像是“已经通了”。
2. 但真正进入上传、续传、实时、协作分发这些深水区后，浏览器会突然被拉去错误地址。
3. 作者自己电脑因为本机回环、缓存、历史状态、特殊可信上下文等原因，可能“侥幸没暴露完全”。
4. 局域网其他设备和未来公网真实用户，则会把这些问题更早、更直接地撞出来。

### 2.3 已经抓到的真实证据

这次不是靠猜。

已经抓到的真实复现说明：**应用层和 transport 层在说两套话。**

#### 证据 A：HTTPS prepare 正确，但 Tus 下一跳降回 HTTP

实测：

1. `POST https://192.168.100.104/api/media/image/prepare`
2. 返回 `tus_endpoint = https://192.168.100.104/files`
3. 继续 `POST https://192.168.100.104/files`
4. `201 Location` 却返回  
   `http://192.168.100.104/files/...`

这说明：

1. 应用层已经知道浏览器应该走 HTTPS 入口。
2. 但 Tus transport 下一跳又把浏览器拽回了明文 HTTP。
3. **禁止** 出现这种“入口是 HTTPS，协议下一跳却降回 HTTP”的双真相。

#### 证据 B：HTTP 局域网 prepare 已经把内部端口暴露给浏览器

实测：

1. `POST http://192.168.100.104:8080/api/media/image/prepare`
2. 返回 `tus_endpoint = http://192.168.100.104:1081/files`

这说明：

1. 局域网开发路径里，浏览器仍然被允许知道 `1081` 这个内部 Tus 端口。
2. 这和“浏览器只认一个统一入口”的目标直接冲突。
3. **禁止** 再把 `:1081` 这种内部端口当浏览器契约的一部分。

#### 证据 C：同源 `/files` 入口继续把浏览器带回 `127.0.0.1`

实测：

1. `POST http://192.168.100.104:8080/files`
2. `201 Location` 返回  
   `http://127.0.0.1:1081/files/...`

这说明：

1. 即便浏览器先走的是局域网可达入口，
2. 下一跳仍可能被某一层偷偷改写回作者电脑自己的回环地址。
3. 这对局域网其他设备和未来公网用户都是致命错误。
4. **禁止** 浏览器收到任何 `127.0.0.1`、`localhost` 作为下一跳。

## 3. 备选方案比较

### 3.1 方案 A：单 HTTPS 入口收口

开发时：

- 用户只访问 `https://开发电脑局域网IP/`

上线时：

- 用户只访问 `https://正式域名/`

浏览器下的全部能力都只从这个入口继续分发：

- `/api/...`
- `/files/...`
- `/api/swarm/announce`

优点：

1. 最符合主人的真实需求。
2. 开发和上线是同一种网络脑子，局域网测试更接近未来公网测试。
3. 浏览器、上传、实时、协作分发的真相最容易统一。
4. 后续最省心，最不容易漂。

缺点：

1. 必须认真清理现有内部地址泄漏和双真相路径。
2. 不能继续容忍“先这样跑着，以后再说”的灰色地带。

### 3.2 方案 B：页面、上传、实时继续多端口直连

例如：

- 页面一个端口
- 上传一个端口
- tracker 一个端口
- seeder 一个端口

优点：

1. 表面上改动可能少一点。

缺点：

1. 用户要理解更多地址和端口。
2. 局域网测试和正式公网测试仍然不是同一件事。
3. 极易继续出现“本机能跑、别人不行”的幻觉。
4. **禁止** 继续把这种方案当长期真相。

### 3.3 方案 C：多子域拆分

例如：

- 主站一个域名
- 上传一个域名
- 实时一个域名

优点：

1. 某些大型部署里运维边界更细。

缺点：

1. 现在完全没必要。
2. 对主人当前“简单、直接、甩进 VPS 就跑”的目标不友好。
3. 只会增加理解和配置成本。

### 3.4 结论

本次正式采用：

**方案 A：单 HTTPS 入口收口。**

并明确写成禁令：

1. **禁止** 再把多端口直连当成浏览器长期方案。
2. **禁止** 为了短期省事，让浏览器继续知道内部零件地址。
3. **禁止** 在当前阶段引入多子域复杂度，分散主入口真相。

## 4. 正式网络裁决

### 4.1 唯一外部入口裁决

从现在开始，浏览器用户永远只认一个 HTTPS 入口。

开发阶段：

- `https://开发电脑局域网IP/`

正式上线阶段：

- `https://正式域名/`

除此之外，**禁止** 让浏览器用户接触：

- `127.0.0.1`
- `localhost`
- `http://...:1081`
- `ws://...:7072`
- `http://...:7073`
- 任何“这是内部服务，先临时让浏览器直连一下”的入口

### 4.2 浏览器可见路径裁决

浏览器只允许感知下面这些同源路径：

1. `/api/...`
2. `/files/...`
3. `/api/swarm/announce`

这些路径都属于“唯一外部入口”的一部分。

默认优先级也要写死：

1. 浏览器契约**优先**返回同源相对路径
2. 如果某些场景必须返回绝对地址，也只能从“唯一 HTTPS 入口”派生
3. **禁止** 返回“相对路径一套、内部绝对地址一套、开发特例再一套”的三份并存真相

明确禁令：

1. **禁止** 浏览器绕开入口直连 `tusd`
2. **禁止** 浏览器绕开入口直连 tracker
3. **禁止** 浏览器绕开入口直连 seeder
4. **禁止** 上传 prepare 返回 `:1081` 给浏览器
5. **禁止** locator / distribution 返回裸 tracker 端口给浏览器

### 4.3 内部零件裁决

下面这些零件可以继续存在，但只属于机器内部：

1. `koko`
2. `tusd`
3. tracker
4. seeder
5. 本机 sidecar 间的回环通信

它们可以彼此通信，但必须服从下面规则：

1. **禁止** 把机器内部通信地址当成浏览器契约
2. **禁止** 让内部端口决定浏览器该访问什么
3. **禁止** 让开发脚本日志里的内部地址，反过来变成产品真相

## 5. 目标流量走向

### 5.1 开发时局域网测试

局域网用户：

1. 访问 `https://开发电脑局域网IP/`
2. 页面加载后，所有请求继续回到这个入口
3. 上传走 `https://开发电脑局域网IP/files/...`
4. API 走 `https://开发电脑局域网IP/api/...`
5. 实时/协作分发走 `wss://开发电脑局域网IP/api/swarm/announce`

浏览器看不到内部零件。

### 5.2 正式上线时

公网用户：

1. 访问 `https://正式域名/`
2. 页面加载后，所有请求继续回到这个入口
3. 上传走 `https://正式域名/files/...`
4. API 走 `https://正式域名/api/...`
5. 实时/协作分发走 `wss://正式域名/api/swarm/announce`

`cloudflared` 和正式域名只负责把用户送到这一个入口。

明确禁令：

1. **禁止** 把 `cloudflared` 理解成“浏览器应该拿到的新业务地址生成器”
2. **禁止** 让 `cloudflared` 额外长出第二套产品入口
3. **禁止** 让开发阶段和上线阶段使用不同的浏览器契约结构

## 6. 当前代码层已经暴露出的根因

### 6.1 上传链路双真相

当前代码里，上传链路已经暴露出最危险的网络漂移：

1. [src/媒体上传外壳.rs](src/媒体上传外壳.rs) 已经在尝试按请求头推导对外 Tus 地址。
2. [src/媒体上传外壳.rs](src/媒体上传外壳.rs) 里的同源 Tus 代理又只是转发 sidecar 响应。
3. [https.ps1](https.ps1) 已经把 `/files` 反代给 `tusd`。
4. 当前运行中的 `tusd` 默认也没有进入“我在代理后面”的正确模式，导致它仍可能按内部服务视角返回 `Location`。
5. 这说明“浏览器该去哪”这件事，现在仍然没有被单一 owner 完全收口。

结果就是：

1. prepare 觉得自己在服务浏览器入口。
2. Tus transport 又按内部服务视角回 `Location`。
3. 浏览器最终拿到的是混合真相。

这条必须写成硬裁决：

**禁止 prepare、proxy、transport 三层各自发明一套“浏览器下一跳地址”。**

### 6.2 开发便利真相和产品真相混在一起

当前一些默认值仍然带着明显的“本机自己跑起来就行”思路：

1. 回环地址默认值
2. 内部端口默认暴露
3. 局域网 HTTP 开发与 HTTPS 可信上下文之间的灰色混用

这在早期开发阶段可以理解，但现在已经进入明显的架构风险区。

必须明确：

1. 开发便利不是长期产品真相
2. 回环地址只能服务内部零件
3. 浏览器契约必须优先服从未来正式部署形态

### 6.3 浏览器 secure context 前提不能继续糊涂

前端已有明确信号表明：

1. `http://localhost` 之所以能跑，是浏览器对 loopback 的特殊照顾
2. `http://局域网IP` 通常不属于可信上下文
3. `WebTorrent` 浏览器协作分发、service worker 接管等能力，需要可信 HTTPS 上下文

所以必须正式禁止：

1. **禁止** 把 `localhost` 特例当成局域网用户体验依据
2. **禁止** 继续拿明文 `http://局域网IP` 当满血模拟未来公网用户的方案
3. **禁止** 因为本机作者电脑能跑，就宣布局域网/公网真相成立

## 7. 启动与部署真相裁决

### 7.1 开发启动真相

开发阶段只允许一个主启动入口。

这个主启动入口的职责是：

1. 把内部零件带起来
2. 准备局域网 HTTPS 单入口
3. 给开发者一个明确、唯一、可转发给别人的局域网测试地址

这个主启动入口**不是**第二套业务真相。

明确禁令：

1. **禁止** 开发者再手工向测试用户解释多个内部端口
2. **禁止** 启动脚本打印一堆内部地址后，让人自己猜哪个才是用户入口
3. **禁止** 再把“本机访问入口”和“局域网访问入口”分裂成两套长期产品路径

### 7.2 正式部署真相

正式部署时，应当做到下面这件简单的事：

1. 把项目放进 VPS
2. 启动项目
3. 让 `cloudflared + 域名` 把公网用户送到唯一 HTTPS 入口

此时项目内部仍然可以继续有多个服务零件，但这些零件不该让部署者天天手动解释。

明确禁令：

1. **禁止** 正式部署时还要求用户理解内部端口拓扑
2. **禁止** 把内部组件地址暴露成运维必须手改的浏览器契约
3. **禁止** 让“上线版网络脑子”和“开发版网络脑子”分裂

## 8. 本次整顿要删掉的旧网络垃圾

这次整顿不是“多保留一点兼容入口更稳”，而是要有删除勇气。

下面这些旧东西，只要确认没有正当长期价值，就应该删、合、收：

1. 任何返回给浏览器的 `127.0.0.1`
2. 任何返回给浏览器的 `localhost`
3. 任何返回给浏览器的 `:1081`
4. 任何返回给浏览器的 `:7072`
5. 任何返回给浏览器的 `:7073`
6. 任何“浏览器可以直连内部零件”的旧路径
7. 任何“入口先走 HTTPS，下一跳再掉回 HTTP”的行为
8. 任何“同一个能力有两条浏览器出口”的历史兼容逻辑

明确禁令：

1. **禁止** 以“先留着以后再清”为由长期保留这些旧路
2. **禁止** 以“本机自测方便”为理由继续让浏览器知道内部端口
3. **禁止** 为了减少短期改动，保留会制造长期漂移的双真相

## 9. 配置 owner 裁决

为了防漂移，必须先把“谁负责哪种地址”写死。

### 9.1 外部公开地址 owner

外部公开地址只允许有一个 owner：

**唯一 HTTPS 入口**

开发时它是：

- `https://开发电脑局域网IP/`

上线时它是：

- `https://正式域名/`

任何给浏览器的路径，都必须从这个 owner 派生。

### 9.2 内部地址 owner

内部地址只允许服务机器内部零件，例如：

1. `koko -> tusd`
2. `koko -> tracker`
3. `seeder -> koko`
4. `koko -> seeder`

这些地址只属于内部 owner，**禁止** 越权下发给浏览器。

### 9.3 配置边界

真正应该成为“部署可配项”的，只允许保留少数有明确业务价值的入口信息。

例如：

1. 外部唯一入口相关信息
2. 正式域名相关信息
3. 是否开发/正式环境

明确禁令：

1. **禁止** 把内部端口当成用户级配置项长期暴露
2. **禁止** 让部署者靠修改一堆内部地址才能把项目跑起来
3. **禁止** 在启动脚本、后端、前端各保留一份相互打架的入口配置

## 10. 验收标准

网络整顿完成后，不再用“作者电脑能打开页面”当成功，而要同时满足下面 4 组验收。

### 10.1 入口验收

1. 局域网其他设备能直接打开  
   `https://开发电脑局域网IP/`
2. 正式部署后，公网用户能直接打开  
   `https://正式域名/`
3. **禁止** 要求测试用户手动访问内部端口入口

### 10.2 上传验收

1. 从唯一 HTTPS 入口发起上传
2. prepare、创建、续传、完成全程都留在同一入口真相内
3. **禁止** 中途掉回 HTTP
4. **禁止** 中途掉回 `127.0.0.1`
5. **禁止** 中途暴露 `:1081`

### 10.3 实时验收

1. 浏览器实时连接只认  
   `wss://入口/api/swarm/announce`
2. **禁止** 浏览器直连裸 tracker
3. **禁止** 把 sidecar 内部 announce 当成浏览器公开 announce

### 10.4 同构验收

局域网测试和正式公网测试，必须满足下面这句：

**对浏览器来说，局域网开发和正式公网的区别只应是“入口名字不同”，不应是“整套网络规则不同”。**

### 10.5 失败判定，禁止自我感动式验收

后续执行时，只要出现下面任意一种情况，就应直接判定为**没有整顿完成**：

1. 页面虽然能打开，但上传或续传把浏览器带去了 `http://...`
2. 页面虽然能打开，但浏览器网络面板里出现了 `127.0.0.1`、`localhost`、`:1081`、`:7072`、`:7073`
3. 局域网测试要靠作者自己口头解释“这个阶段先点 A，再改成 B，再连 C”
4. 开发环境和正式环境虽然都叫“单入口”，但实际上地址推导、协议推导、下一跳规则并不是同一套逻辑
5. 页面入口是 HTTPS，但上传、实时、协作分发里仍然偷偷存在第二条浏览器出口

这条必须写死，是因为本次要解决的是“网络真相漂移”，不是“首页勉强能打开”。

### 10.6 执行防漂移清单

后续任何实现、重构、补丁、联调，都必须服从下面这些执行禁令：

1. **禁止** 把“单入口”偷换成“只有首页单入口，上传和实时例外”
2. **禁止** 在前端硬编码一份开发地址、在后端再硬编码一份正式地址、在脚本里再偷留一份回环默认值
3. **禁止** 用 `if 本机`、`if LAN`、`if 正式环境` 长出三套浏览器地址真相，只为掩盖根因
4. **禁止** 把 sidecar 直连暴露给浏览器，再把它包装成“临时开发便利”
5. **禁止** 因为担心动到旧逻辑，就把旧入口和新入口长期并存
6. **禁止** 把“用户入口地址”这个 owner 分散到前端、后端、代理脚本三处共同维护
7. **禁止** 先补表面兼容分支，再把真正的 owner 收口工作无限后拖

允许的方向只有一个：

1. 先把“浏览器公开入口 owner”收成唯一真相
2. 再让上传、API、实时、协作分发全部从这个真相派生
3. 最后删除会泄漏内部地址的旧路、旧默认值和旧兼容分支

## 11. 非目标，禁止借题扩写

这份 spec 虽然很详细，但它不是无边界扩写。

下面这些不属于本次核心目标：

1. STUN / TURN 全套公网穿透策略
2. tracker 高可用集群方案
3. 多机房多区域调度
4. 大规模公网压测平台
5. 与当前单入口收口无关的网络美化工程

明确禁令：

1. **禁止** 借本次网络整顿顺手把范围膨胀成分布式改造大项目
2. **禁止** 在唯一入口真相还没站稳时，先扩张成更复杂的网络拓扑
3. **禁止** 把“未来也许会需要”当成现在不收口的借口

## 12. 最终裁决

本次网络整顿的最终裁决只有一句：

**浏览器用户永远只认一个 HTTPS 入口；开发时是局域网 IP，上线时是正式域名；上传、API、实时、协作分发全部继续挂在这个入口下面；任何内部地址、内部端口、内部协议降级，都禁止再泄漏给浏览器。**

如果后续实现没有达到这句话，就不算真正整顿完成。
