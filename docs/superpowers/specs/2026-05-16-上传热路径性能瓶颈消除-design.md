## 1. 大白话结论

pending-first 让消息秒见了，但附件从"处理中"到"可看/可播"仍然慢。小图小视频也慢，说明不是文件大小问题，而是链路本身有固定开销在反复浪费。

核心发现：**每个 HTTP 请求都在重新建立 TCP 连接和 TLS 握手**，每次写 canonical 都在做整文件内存复制，所有重活步骤都在串行等待。

一句话：**不是网络慢，是我们在同一条路上反复交过路费。**

---

## 2. 当前真实问题

### 2.1 reqwest::Client 每次新建（最大瓶颈）

当前代码中有 5 处 `reqwest::Client::new()`：

| 位置 | 文件 | 调用频率 |
|---|---|---|
| Tus 代理转发 | `tus代理.rs:53` | **每个上传分片** |
| Tus 终止删除 | `tus代理.rs:144` | 每次取消上传 |
| sidecar 启动做种 | `协作分发做种.rs:164` | 每次 complete |
| sidecar 对账做种 | `协作分发做种.rs:331` | 每次对账 |
| Cloudflare TURN | `mod.rs:171` | 每次 ICE |

`reqwest::Client` 的官方文档明确说：

> "You should create a `Client` once, store it, and clone it for each use. Cloning a `Client` is cheap and each clone will share the same connection pool."

**每次 `Client::new()` 的代价**：
- 新建连接池（内存分配）
- TCP 三次握手（~1ms 本地，~50ms 公网）
- TLS 握手（~30ms 本地，~100ms 公网）
- DNS 解析

一个 10MB 文件按 512KB 分片 = 20 个分片 = 20 次完整握手 = **~600ms-2s 的纯连接开销**。

### 2.2 canonical 写入整文件内存复制

`完成上传.rs:428`：

```rust
canonical_video_mapping.as_ref().to_vec().into()
```

文件已经通过 mmap 映射到内存了，但 `.to_vec()` 又做了一次完整的堆内存复制。50MB 视频 = 额外分配 50MB + memcpy。

`object_store` 的 `put()` 方法接受 `PutPayload`，而 `PutPayload::from(Bytes)` 可以直接用 `Bytes::from_static` 或 mmap 的零拷贝包装，不需要 `to_vec()`。

### 2.3 torrent 生成是 CPU 密集型

`共享语义.rs:89` 的 `生成附件torrent元信息` 需要计算文件每个 piece 的 SHA1 哈希。这是 CPU 密集操作：
- 1MB 文件 ≈ 即时
- 50MB 文件 ≈ ~50-100ms
- 200MB 文件 ≈ ~500ms+

当前在 async 上下文中同步执行，会阻塞 tokio 工作线程。

### 2.4 complete 全流程串行

complete 重活的 7 个步骤完全串行：

```
等 sidecar 回执 → 读文件 → 校验内容 → 写 canonical → 生成 torrent → 写 DB → 广播
```

其中"写 canonical"和"生成 torrent"互不依赖（torrent 从 mmap 字节计算，canonical 写入存储），可以并行。

### 2.5 sidecar 做种也每次新建 Client

`协作分发做种.rs:164` 和 `:331` 各自 `reqwest::Client::new()`，虽然做种频率不如 Tus 分片高，但也是无谓的连接开销。

---

## 3. 设计目标

1. 消除 Tus 代理的连接重建开销，让分片上传复用同一个 TCP/TLS 连接。
2. 消除 canonical 写入的整文件内存复制。
3. 让 torrent 生成不阻塞 tokio 异步运行时。
4. 让 complete 中可并行的步骤并行执行。
5. 统一所有 HTTP Client 到 `应用状态` 中的单例。
6. 不改变 domain/application/contract 层，所有改动限制在 adapter/shell。

---

## 4. 非目标

1. 不改 Tus 分片大小或并行分片策略（那是前端 Uppy 配置，不在本次范围）。
2. 不改 object_store 后端（本地/S3 选择不变）。
3. 不改 torrent 生成算法（SHA1 是 BitTorrent 协议要求）。
4. 不改 sidecar 做种协议。
5. 不引入新的异步运行时或线程池。
6. 不把 complete 重活从 HTTP handler 迁到后台任务队列（那是后续优化）。

---

## 5. DDD 上下文与六边形边界

### 5.1 为什么性能优化不动 domain

DDD 的核心原则：**domain 只表达业务事实，不感知 IO 实现细节**。上传延迟是 adapter/shell 的连接策略和内存管理问题，不是"消息是否成立"或"附件状态如何迁移"的问题。domain 的附件状态机（pending→ready→failed）和消息聚合根完全不受影响。

### 5.2 端口与适配器视角

本次优化只改动六边形的**外圈**：

- **驱动适配器（HTTP adapter）**：Tus 代理的 reqwest Client 从"每次新建"改为"共享连接池"
- **被驱动适配器（存储 adapter）**：canonical 写入从 `put(to_vec)` 改为 `put_multipart(streaming)`
- **shell 编排层**：complete 重活从串行改为部分并行

**端口不变**：`ObjectStore` trait 的 `put`/`put_multipart` 是已有端口，不引入新接口。

### 5.3 边界矩阵

| 层 | 改动 | 不改 |
|---|---|---|
| domain | 无 | 消息成立规则、附件状态机、领域事件语义 |
| application | 无 | 用例编排、事件发布、权限校验 |
| contract | 无 | 事件格式、错误码、附件快照结构 |
| adapter | reqwest Client 复用、存储写入策略 | SQL 查询、鉴权 |
| shell | `应用状态` 加字段、spawn_blocking、tokio::join! | 路由、中间件、协议响应格式 |

## 6. 改动方案

### 6.1 统一 HTTP Client 到 `应用状态`

在 `应用状态` struct 中加一个 `pub http_client: reqwest::Client` 字段，在 `构建应用状态` 时创建一次：

```rust
let http_client = reqwest::Client::builder()
    .pool_max_idle_per_host(20)
    .pool_idle_timeout(Duration::from_secs(90))
    .connect_timeout(Duration::from_secs(5))
    .timeout(Duration::from_secs(300))
    .build()
    .expect("构建共享 HTTP Client 失败");
```

然后把 5 处 `reqwest::Client::new()` 全部替换为 `state.http_client.clone()`（clone 是零开销的 Arc clone）。

### 6.2 消除 canonical 写入的 to_vec()

当前：
```rust
state.attachment_store.put(&path, mmap.as_ref().to_vec().into()).await
```

改为：
```rust
state.attachment_store.put(&path, Bytes::copy_from_slice(mmap.as_ref()).into()).await
```

更进一步：如果 `object_store` 的 `PutPayload` 可以直接从 `&[u8]` 构造而不复制（取决于存储后端），可以用 `PutPayload::from_bytes`。但由于 mmap 生命周期可能在 `put` 完成前 drop，保守做法是用 `Bytes::copy_from_slice`——这和 `to_vec()` 一样有一次复制，但语义更清晰。

**真正有效的优化**：用 `put_multipart` 流式写入，把 mmap 的 slice 分批送出，避免一次性分配整文件大小的堆内存：

```rust
let mut upload = state.attachment_store.put_multipart(&path).await?;
for chunk in mmap.as_ref().chunks(4 * 1024 * 1024) {
    upload.put_part(PutPayload::from(Bytes::copy_from_slice(chunk))).await?;
}
upload.complete().await?;
```

### 6.3 torrent 生成移到 spawn_blocking

当前在 async 上下文中同步调用：
```rust
let torrent = media_distribution::生成附件torrent元信息(...)?;
```

改为：
```rust
// spawn_blocking 要求 'static，mmap 引用不能 move 进去。
// 必须先 copy 一份 owned Bytes 再 move，这是 torrent 生成不可避免的一次复制。
let torrent_bytes = Bytes::copy_from_slice(mmap.as_ref());
let torrent_hash = content_hash.clone();
let torrent_ext = 稳定扩展名.to_string();
let torrent = task::spawn_blocking(move || {
    media_distribution::生成附件torrent元信息(&torrent_hash, &torrent_ext, &torrent_bytes)
}).await.map_err(|e| format!("spawn_blocking join 失败: {e}"))??;
```

所有权说明：`spawn_blocking` 需要 `'static` 闭包，但 mmap 是借用的 `&[u8]`，不能直接 move。必须先做一次 `Bytes::copy_from_slice` 把字节 own 下来。这次复制和原来的 `to_vec()` 开销相同，但好处是让 CPU 密集的 SHA1 计算跑在独立线程池，不阻塞 tokio 的 async 工作线程。

### 6.4 canonical 写入和 torrent 生成并行

当前串行：
```
写 canonical → 生成 torrent
```

改为并行：
```rust
let (canonical_result, torrent_result) = tokio::join!(
    state.attachment_store.put(&path, payload),
    task::spawn_blocking(move || 生成附件torrent元信息(&hash, ext, &bytes)),
);
```

两个操作互不依赖：canonical 走 IO，torrent 走 CPU，正好分开。

## 7. 预期收益

| 瓶颈 | 当前开销 | 优化后 | 节省 |
|---|---|---|---|
| Tus 20 分片连接开销 | ~600ms-2s | ~30ms（首次握手后复用） | **~95%** |
| canonical 200MB to_vec | ~100ms + 200MB 堆内存 | 流式 4MB 分批 | **内存减 98%** |
| torrent 50MB SHA1 | ~50ms 阻塞 async | spawn_blocking | **不阻塞 async** |
| canonical + torrent 串行 | ~150ms | 并行 | **~40%** |
| sidecar 做种连接 | ~100ms | 复用 | **~95%** |

**小图片（<1MB）最大收益来自瓶颈 1**：消除 Tus 分片的连接重建。Phase 2/3 的收益主要体现在大文件（50MB+）的内存占用和 CPU 阻塞上，对小文件几乎无感。

## 10. 安全边界

1. `reqwest::Client` 的连接池默认有 idle timeout，不会无限持有连接。
2. `pool_max_idle_per_host(20)` 限制了对同一 sidecar 的最大闲置连接数。
3. mmap 的生命周期必须覆盖整个 `put_multipart` 流式写入过程，drop 在 `upload.complete()` 之后。
4. `spawn_blocking` 使用 tokio 的阻塞线程池，默认上限 512 线程，不会 starve async 任务。

---

## 11. 方案裁决

### 11.1 拒绝：前端增加并行分片数

原因：Tus 官方实测表明并行分片不一定更快（带宽共享），且增加服务端 concatenation 开销。真正有效的是减少每个分片的固定开销（连接复用）。

### 11.2 拒绝：把 complete 移到后台任务队列

原因：增加系统复杂度（消息队列、重试、监控），当前性能瓶颈可以通过更简单的资源复用和并行化解决。后续如果 complete 仍然慢再考虑。

### 11.3 拒绝：换掉 object_store 的 put 接口

原因：`put_multipart` 已经提供了流式能力，不需要换库。

### 11.4 选中：资源复用 + 零拷贝 + 并行化

原因：
- 改动最小（5 处 `Client::new()` → 1 个共享字段）
- 收益最确定（连接复用是 HTTP 性能基本功）
- 不改变业务语义和架构边界
- 符合 Rust 生态最佳实践

## 13. 100% 信心循环

问题：我对当前设计是否事实 100% 有信心？

第一轮：不是。风险是 `reqwest::Client` 的连接池在高并发时可能有锁竞争。

修复：reqwest 的连接池使用 `hyper` 的无锁 dispatcher，高并发下表现良好。配置 `pool_max_idle_per_host(20)` 限制闲置连接，不会资源泄漏。

第二轮：不是。风险是 mmap 在 `put_multipart` 异步写入期间被 drop。

修复：mmap 的 `drop(canonical_video_mapping)` 调用点必须在 `upload.complete()` 之后，Phase 2 实现时强制在 join 之后 drop。

第三轮：不是。风险是 `spawn_blocking` 中的 torrent 生成如果 panic 会导致什么。

修复：`spawn_blocking` 返回 `JoinError`，外层 `??` 会把 panic 转成错误响应，不会 crash 整个服务。

第四轮：现在有事实信心。改动限制在资源复用层面，不触碰业务语义，每个 Phase 可独立交付和回滚。
