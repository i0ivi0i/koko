# 数据库迁移单一基线设计

日期：2026-05-04  
状态：Design  
适用范围：`koko` 后端 PostgreSQL schema、`migrations/` 目录、SQLx 自动迁移启动链、迁移相关测试。  

## 0. 总裁决

`koko` 当前数据库可以丢弃重建，因此 `migrations/` 不再保留 21 个探索期增量迁移。

本轮目标是把运行迁移目录收口成一个当前真相：

```text
migrations/
└── 0001_当前数据库基线.sql
```

旧迁移文件直接删除，不另建文档归档。Git 已经记录历史，不再为旧中间态制造第二份长期维护入口。

## 1. 为什么这样做

当前 21 个 `.sql` 是探索期演进痕迹，不是项目长期数据库真相。

保留它们有三个坏处：

1. 读 schema 必须脑内执行一串历史补丁，维护成本高。
2. 已废弃字段、旧索引、旧唯一约束会继续污染判断。
3. 后续功能迭代容易误以为“每次小改都该新增一个 SQL 文件”。

单一基线更符合当前阶段：

1. 数据库可重建，不需要兼容旧 `_sqlx_migrations` 账本。
2. 源码查询路径不变，业务行为不应受影响。
3. 新人或未来会话只读一个 SQL 就能看到当前完整结构。
4. 后续真正上线后，再恢复 append-only 迁移纪律。

## 2. 硬边界

本设计只处理数据库结构入口，不处理业务逻辑。

允许：

1. 删除旧 `migrations/*.sql`。
2. 新建 `migrations/0001_当前数据库基线.sql`。
3. 把旧迁移链最终状态折叠成直接的 `CREATE TABLE`、`CREATE INDEX`、`COMMENT`。
4. 更新迁移测试，让测试验证当前 schema，而不是验证旧历史文件存在。

禁止：

1. 修改 domain / application / contract 的业务语义。
2. 修改 adapter 查询逻辑来迎合新 baseline。
3. 保留旧历史中间态，如已撤销的唯一索引、旧 peer 字段、旧临时表。
4. 为“以后可能用到”新增表、列、索引、触发器、视图或分区。
5. 把旧迁移改名后留在 `migrations/`，让 SQLx 继续扫描到第二套历史。

## 3. 基线内容

新基线只表达当前最终 schema。

必须覆盖这些当前表：

1. 身份与会话：`anonymous_identities`、`sessions`
2. 房间与消息：`rooms`、`room_members`、`room_events`、`messages`、`room_read_anchors`
3. 附件与消息引用：`attachments`、`message_attachment_refs`
4. 上传会话与运输：`attachment_upload_sessions`、`attachment_upload_transports`
5. 协作分发：`attachment_distribution_metadata`、`swarm_peer_presence`
6. 媒体生命周期：`attachment_streaming_manifests`
7. canonical 媒体资产与 source hash：`canonical_media_assets`、`attachment_canonical_asset_refs`、`attachment_source_hashes`

必须保留这些业务边界：

1. `source_hash` 只服务受权限约束的上传前精确复用，不能成为全站存在性探针。
2. `canonical_media_assets.content_hash` 是媒体资产身份，不是消息事实、房间权限或附件事实。
3. `swarm_peer_presence` 只承载易变 peer 存活事实，不回写到稳定附件元数据。
4. `attachment_streaming_manifests` 只表达服务端 HLS/DASH 冷备窗口，不得成为视频主链第二真相。
5. `current_upload_session_id` 只指向当前上传会话，不替代附件成立状态。

## 4. 后续迁移纪律

基线落地后，后续规则改成：

1. 不改数据库结构，就不新增 SQL。
2. 同一功能批次内的 schema 变化合并成一个迁移。
3. 迁移文件名表达数据库契约变化，不表达临时开发步骤。
4. 上线或共享库应用过的迁移不得回改；只能追加新的修正迁移。
5. 生产加索引、加约束必须先评估锁和数据量；需要时使用 PostgreSQL 官方的低锁路径，例如并发建索引、约束先 `NOT VALID` 后验证。
6. 开发期未落入共享库的临时迁移，合并前可以 squash，避免把探索过程变成长期真相。

## 5. 实施路径

1. 从旧 21 个迁移和当前 Rust 查询路径提取最终 schema。
2. 编写单一 baseline。
3. 删除旧迁移文件。
4. 更新迁移测试：
   - 不再断言旧文件存在。
   - 改为断言空库迁移后核心表、约束、索引、注释存在。
5. 在可重建数据库上运行迁移测试。
6. 跑房间、消息、媒体上传、协作分发相关测试，证明业务路径没有被 baseline 改坏。
7. 如果修改了代码文件，运行 `graphify update .`。

## 6. 验收标准

必须同时满足：

1. `migrations/` 只剩 `0001_当前数据库基线.sql`。
2. 空 PostgreSQL 数据库能从零迁移成功。
3. 迁移测试通过。
4. 房间、消息、媒体上传、协作分发相关测试通过。
5. `git diff --check` 通过。
6. `git status --short` 没有非本轮遗留脏尾巴。

## 7. 明确不支持

本轮不支持旧数据库平滑升级。

如果某个库已经执行过旧 21 个迁移，要么丢弃重建，要么不使用这次单一基线。这个限制是故意的，因为用户已经确认当前数据库可以重建。

第一遍：检查需求意图。  
结论：通过。文档明确回应“不想要很多 SQL”，裁决为单一当前基线，不保留归档。

第二遍：检查架构边界和执行路径。  
结论：通过。设计只触碰迁移目录和迁移测试，不改变业务层、查询路径和领域语义。

第三遍：检查验证闭环和遗漏冲突。  
结论：通过。验收覆盖空库迁移、迁移结构测试、关键业务路径测试、格式检查和脏树检查；同时明确不支持旧库升级，避免误用。
