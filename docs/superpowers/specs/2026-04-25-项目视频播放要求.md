## 0. 总裁决

**同一个 canonical 媒体资产，既是上传复用和转发分享复用的物理真相，也是 `WebTorrent` 正式分发平面的唯一真相；同一颗 `Video.js` player/container，既是消息流自动播放、离屏续播、查看器和全屏的唯一正式播放表面；同一条播放连续性状态链，把候选预热、隐藏接管、露出、暂停帧、查看器升格、全屏接管、退出归位和退场收进同一条会话。**

这句话自然推出四个最高红线：

1. 禁止第二媒体资产真相。
2. 禁止第二正式字节主链。
3. 禁止第二正式播放器真相。
4. 禁止第二套播放位置、视频画面和播放连续性状态链。

## 1. 这份文档要守住的真实问题

### 1.1 视频不能再被拆成三套世界

旧世界最容易长成这样：

1. 时间线看的是一张后端封面图。
2. 点击后播的是另一份视频。
3. 自动播放走第三套状态机。
4. `WebTorrent` 只是旁路加速。

这种做法的问题不是代码不漂亮，而是产品真相分裂：预览不是视频自己，播放不是预览的自然延续，分发也不一定真的帮助后面的人。后续任何小修补都会继续长第二资产、第二入口、第二 owner。

现在必须反过来：

**同一个 `canonical video` 文件，必须同时成为预览源、自动播放源、查看器播放源、`WebTorrent` payload、群友做种源；同一条播放会话，必须同时承接时间线、查看器和全屏的状态转换。**

### 1.2 去重不能变成隐私探针

用户上传同一个原始文件两次，系统应该在预处理和上传前就识别为同一份原始文件，直接复用已有 canonical 资产、torrent 和 swarm。

但这只能是精确原文件去重：

1. `source_hash` 只表示上传前原始 `File` 字节的 `SHA-256`。
2. 它不表示肉眼相似、重新压缩后相似、截图转存后相似、不同封装但视觉接近。
3. 它不能成为“全站是否已有这个文件”的无权限 hash 探针。

这里做的是克制、可靠、可解释的精确复用，不做感知哈希、AI 相似度、帧级比对、音视频指纹或模糊查重。

### 1.3 续播不是只保存 `currentTime`

当前真实体验问题不是一个小闪烁，而是播放位置真相和视觉帧真相分裂：

1. 系统保存了 `currentTime`。
2. 视频滑走后再滑回来，也能从保存位置续播。
3. 但卡片画面会先退回开头 poster、首帧或 `<img>` 静态预览。
4. 浏览器再 seek 到保存位置，用户看到的是“从开头突然跳到续播点”。

所以后续实现不能只说“我保存了时间戳”。只要有同源播放源和有效保存位置，用户可见画面就不能退回开头；缺的不是更多兜底图，而是同一条播放连续性状态链：源一致、位置有效、当前 DOM 真的可显示时才露出，否则隐藏接管、保持暂停帧或 guard，绝不把续播伪装成冷启动。

### 1.4 离屏是中断，不是重开

在万人实时群聊的消息流里，视频必须像同一条连续会话一样存在：

1. 滑出屏幕只是中断，不是自然播完。
2. 滑回屏幕只是续播，不是重新开始。
3. 点击当前自动播视频只是把当前播放器升格到查看器或真全屏，不是重新造一套播放世界。
4. 点另一条视频，也只能把同一颗播放器迁过去，而不是让两颗正式播放器并存。

这是 IM 消息流，不是短视频 feed，也不是网页内容页。消息流里的视频只给画面，不给网页式小播放器控件；离屏、回屏、放大、全屏、归位都必须是同一条会话的状态转换，不能由消息窗、查看器、全屏各自发明局部逻辑。

### 1.5 2026-05-06：自动播放问题重新定性

2026-05-06 复核时，真实肉眼体验仍暴露出一组同源症状：

1. 进入自动播放时经常黑闪。
2. 视频滑走时闪一下才暂停。
3. 滑回时先露首帧或封面，再跳到保存时间点。
4. 点击查看器或全屏时断一下。
5. 退出全屏归位时闪一下。
6. 在群聊消息窗内滚动或页面尺寸变化时，当前正在自动播放的视频画面自己抽搐、前后跳、短暂露首帧或封面；视频卡片尺寸本身不一定抖。

这些症状不能再被拆成几个小 bug。它们共同指向同一件事：

**播放器接管、释放、迁移和归位时，把尚未准备好的中间态暴露给了用户。**

因此后续调查不能继续按“看见黑闪就补黑闪、看见首帧跳就补 seek、看见抽搐就补 timeout”的方式推进。这类修法会继续堆 `guard / fallback / preview / poster / frozen` 分支，短期遮住一帧，长期制造更多第二真相。

本轮重新定性的根问题是：

**当前代码已经有 `媒体运行时.ts`、`全局丝滑自动播.ts`、`全局唯一播放器.ts`、时间线画面缓存和时间线宿主 owner，但“现在到底能露出哪一层画面”仍然散落在多个地方共同决定。多个地方都在好心决定画面，结果谁都不是唯一裁判。**

所以新的执行裁决是：

**状态机必须成为唯一露出门禁；渲染层、宿主层、播放器层只能执行状态机结果，不能各自猜 poster、preview、冻结帧、canonical host 谁应该露出来。**

同时补充一条更底层的不变量：

**当前 owner 不变、source 不变、播放器宿主仍有效、同一颗播放器正在时间线稳态播放时，滚动和 resize 只能刷新几何事实，不能触发 seek、换源、换壳、重挂载、poster 回露、preview 回盖、hidden stage 重新接管或 pause/play 抖动。**

这里的“露出门禁”不是新功能，而是把现有领域真相重新收口：

1. `媒体运行时.ts` 继续拥有 `candidate / pending owner / settled owner / release`。
2. `全局丝滑自动播.ts` 继续拥有播放连续性阶段，但必须成为唯一露出裁判。
3. `全局唯一播放器.ts` 继续拥有唯一 `Video.js` player/container 的挂载、seek、play、查看器和全屏迁移。
4. `房间消息窗` 和附件渲染只消费连续性阶段并投影表面，不能再次发明一套露出规则。
5. `IntersectionObserver / ResizeObserver / 虚拟列表测量` 只提供几何信号；几何信号不是播放动作，不能越层驱动播放器恢复。
6. WebTorrent、上传、去重、后端退字节和房间权限不属于本轮第一刀，禁止借自动播体验修复顺手扩大边界。

### 1.6 体验标杆与资料边界

`TikTok / 抖音 / X.com` 这类产品可以作为体验标杆：时间线视频应当静音自动播，点击后进入放大或全屏视图并继续同一条播放会话，退出后尽量回到原来的时间线语境。X 官方公开说明里也明确写过类似体验：时间线中视频静音自动播放，点击后进入放大视图并继续播放。

但禁止把闭源产品猜成技术依据。我们不能说它们内部一定如何实现，只能学习公开可验证的工程原则：

1. 一个视口内只有一个真正重播放 owner。
2. 进入前先准备正确帧，再允许用户看到。
3. 离开前先锁住当前帧和时间点，再释放重解码。
4. 点击放大或全屏是同一条播放会话升格，不是新建播放器。
5. 虚拟列表尺寸要稳定，否则滚动会反向打乱 owner。
6. 自动播放必须遵守浏览器策略：静音、内联、处理 `play()` Promise 失败。
7. 判断“正确帧已可见”不能只看 `currentTime`，必须尽量使用 `requestVideoFrameCallback` 或等价真实帧提交证据。

成熟轮子的边界如下：

| 成熟能力 | 应该承担 | 不应该承担 |
| --- | --- | --- |
| `XState v5` | 明确自动播、隐藏预热、露出、退场、查看器、全屏、归位这些离散阶段 | 接管 WebTorrent、DOM 高频回调、每帧播放进度或全局事件总线 |
| `Video.js` | 唯一播放器壳、container、source、`currentTime`、fullscreen、dispose 生命周期 | 裁决谁是自动播 owner、媒体是否成立、附件权限或 WebTorrent ready 真相 |
| `requestVideoFrameCallback` | 给出某一帧已经提交给浏览器合成器的证据 | 代替状态机、代替播放器 owner、制造第二视觉缓存 |
| `IntersectionObserver` | 提供候选可见性信号 | 直接决定播放、释放或归位 |
| TanStack Virtual / 虚拟列表实践 | 大列表窗口、测量、滚动状态和尺寸变化控制 | 自动播放业务裁决、播放位置真相或媒体源真相 |
| WebTorrent | 正式媒体字节、stream source、补齐和做种 | UI 黑闪兜底、第二播放链、poster 真相 |

结论是：没有一个热门包能直接替项目完成“公网万人群聊 + WebTorrent 正式源 + 唯一 Video.js 播放器 + 虚拟列表 + 滑走保帧 + 滑回续播 + 查看器/全屏归位”。成熟轮子负责基础设施，本项目只写薄适配和播放连续性协议。

## 2. 术语与分层

### 2.1 四层边界

| 层级 | 拥有的真相 | 不拥有的真相 |
| --- | --- | --- |
| 内容身份层 | `source_hash`、`content_hash`、`canonical_asset_id`、`torrent_info_hash`、`swarm_id` | 播放 UI、自动播放策略、连接调度 |
| 分发层 | `WebTorrent`、`WebSeed`、对象存储、tracker/signaling、peer presence | 附件是否成立、内容是否删除、UI 状态 |
| 播放层 | 原生 `video` 能力、`Video.js` 壳、container、fullscreen | 去重真相、成员权限、swarm ready 真相 |
| 协调层 | RoomRuntime、presence、连接生命周期、背压、恢复提示、播放连续性状态转换 | 媒体字节、播放器内部状态、原文件身份 |

硬裁决：

**去重真相只能属于内容身份层；播放器不能决定两个文件是不是同一个内容，`WebTorrent` 也不能反向决定业务附件是不是同一个附件。**

### 2.2 核心术语

| 术语 | 定义 |
| --- | --- |
| `source_hash` | 上传前原始 `File` 字节的 `SHA-256`，只用于受权限约束的精确原文件复用 |
| `content_hash` | canonical 共享字节的强哈希，用于全局物理资产收口 |
| canonical 媒体资产 | 播放、查看、转发、分享和协同分发共同绑定的唯一物理资产 |
| `swarm_id / torrent_info_hash` | 由 canonical 字节稳定派生的 `WebTorrent` 分发身份 |
| 视频画面真相 | 当前附件在宿主槽位上应该呈现的真实视频画面，由同一播放源、`currentTime` 和当前 DOM 可显示事实共同决定 |
| 播放位置真相 | `媒体运行时.inlineAutoplayPositionByAttachmentId` 持有的自动播时间戳 |
| 全局唯一播放器 | 全应用唯一活着的正式 `Video.js` player/container |
| 播放连续性状态链 | 自动播、离屏、回屏、查看器、全屏和归位共用的同一会话状态转换，只合成 owner、位置、DOM ready 与壳层意图 |
| 时间线宿主槽位 | 消息流里愿意承接全局唯一播放器或只读帧投影的位置 |
| 自动播 owner | 当前时间线唯一允许自动播放的附件 |
| 只读帧投影 | 非 owner 卡片为了继续表达画面而显示的非 live player 画面，不拥有独立播放真相 |
| poster 兜底态 | 没有播放源、没有可恢复帧、没有可用只读帧投影时的临时占位 |

最重要的边界：

1. 只读帧投影不是第二播放器。
2. poster 兜底态不是视频真实状态。
3. 时间线宿主槽位不是播放器生命周期 owner。
4. `source_hash` 是原文件身份，不是 canonical 播放身份。
5. `content_hash` 是 canonical 字节身份，不是消息业务身份。
6. 播放连续性状态链不是第二播放器 owner，也不是第二播放位置真相。

## 3. 媒体资产与复用规则

### 3.1 全局资产池和业务引用必须分开

媒体系统必须先分清两个事实：

1. `canonical_media_asset` 是全局物理资产事实。
2. `message / attachment / attachment_ref` 是房间内业务事实。

同一个视频或图片，不管来自哪个用户、哪个房间、上传、转发还是分享，只要最终 canonical 字节一致，后端物理层就只能有一份 canonical 资产、一套 `content_hash / swarm_id / torrent_info_hash`。

不同用户、不同房间、不同消息只新增业务引用，不新增物理媒体资产。

因此：

**禁止把“发到不同房间”解释成“不同媒体”；房间只拥有消息和附件引用，不拥有媒体资产身份。**

### 3.2 新上传前置查询

前端选择文件后，预处理前先做：

1. 读取原始 `File` 字节流。
2. 计算 `source_hash = sha256(raw file bytes)`。
3. 向后端发起受权限约束的去重预检。

预检只允许在当前会话有发送权限的目标上下文里产生结果。它不是“查全站是否存在某文件”的接口，而是“如果允许复用，就直接创建当前业务附件引用”的入口。

预检允许的复用来源：

1. 当前身份自己已经上传且仍有权复用的相同 `source_hash` 资产。
2. 当前身份当前可见消息中已经存在的相同 `source_hash` 资产。
3. 当前身份通过转发、分享或资产授权链获得复用权的资产。
4. 当前目标房间允许新建消息和附件引用。

预检禁止返回：

1. 原上传者。
2. 原房间。
3. 原消息。
4. “全站已有这个文件”。
5. 任何不能直接用于当前新附件成立的存在性信号。

### 3.3 命中路径

如果命中同一 `source_hash` 且复用授权成立：

1. 不再重新图片转码或视频转码。
2. 不再重新上传媒体字节。
3. 后端创建新的业务附件或消息引用。
4. 新附件绑定已有 canonical 资产和分发元数据。
5. 新消息仍是新消息，发送人、房间、时间、消息位置都按当前发送成立。

复用的是媒体资产，不是复用上一条消息。命中后新增的是当前房间的新附件引用，被复用的是全局 canonical 资产。

### 3.4 未命中路径

如果未命中：

1. 继续当前图片或视频 canonical 预处理。
2. 上传 canonical 字节。
3. 后端生成或复用 `content_hash / swarm_id / torrent_info_hash`。
4. 完成后记录 `source_hash -> canonical 资产` 的受权限索引。

即使前置 `source_hash` 未命中，只要上传后的 canonical 字节与已有资产一致，后端仍必须通过 `content_hash` 合并到同一全局 canonical 资产。

这保证两位不同用户在两个互不可见房间上传同一个视频时，最差也只是第二次无法提前秒传；后端物理资产仍然只能算一份。

### 3.5 转发与分享路径

转发和分享不能被设计成重新上传，也不能要求客户端持有原始文件。

客户端应该提交：

1. 当前用户可见的源附件或源消息引用。
2. 目标房间。
3. 当前会话身份。
4. 可选转发附言。

后端只裁决：

1. 当前会话能否看见源附件。
2. 当前会话能否在目标房间创建消息和附件引用。

裁决成立后，后端创建目标房间的新消息和新附件引用，并绑定同一全局 canonical 资产。转发不复制媒体字节，不重新生成 torrent，不重新创建 swarm，也不要求客户端持有原文件。

### 3.6 三条收口链

后续实现必须同时保留三条互补路径：

1. 本地上传前：`source_hash -> 受权限约束的 canonical 资产 -> 新附件引用`。
2. 转发分享时：`source_attachment_id -> canonical 资产 -> 新附件引用`。
3. 上传完成后：`content_hash -> 全局 canonical 资产 -> WebTorrent 分发平面`。

这三条路径服务不同场景，不能互相替代。禁止把三条链合并成一个万能 `source_hash` 流程，也禁止让转发路径依赖原文件字节。

### 3.7 权限、删除与隐私边界

必须禁止：

1. 跨未授权房间返回命中。
2. 跨用户全局返回“已有这个文件”这类存在性结论。
3. 返回原上传者、原房间、原消息等非必要信息。
4. 附件已删除后继续通过 `source_hash`、`content_hash`、缓存或转发路径复活 canonical。
5. 用 `source_hash` 命中绕过当前发送权限、附件权限和房间权限。
6. 把全局资产池误实现成全局可探测 hash 字典。

正确边界：

1. 媒体资产身份可以全局唯一，但资产复用必须经过当前会话、目标房间、成员和可见性裁决。
2. 命中响应只返回当前新附件成立所需的最小资产引用或一次性复用票据。
3. 删除权威事实优先级高于本地缓存、`source_hash` 和 `content_hash`。
4. 复用成功仍要写入当前消息成立事实，而不是偷拿旧消息事实。
5. 转发分享必须以源附件可见性为授权来源，而不是以 `source_hash` 为授权来源。
6. 未授权用户即使猜中 `source_hash`，也只能继续正常上传；上传完成后由 `content_hash` 在后端物理层收口。

一句话：

**禁止把“全局唯一”偷换成“全局可见”；禁止把“物理去重”偷换成“权限复用”。**

### 3.8 当前 canonical 预处理事实

前端 canonical 是播放和分发用的稳定产物，不是原始文件身份。

当前图片路径：

1. HEIC / HEIF 先经 `heic2any` 转成 JPEG 中间态。
2. 再经浏览器 `createImageBitmap + canvas / OffscreenCanvas` 转成 `canonical.webp`。
3. WebP 编码质量为 `0.95`。

当前视频路径：

1. 可直通 MP4 直接保留。
2. 不可直通时用 Mediabunny 整理为 `canonical.mp4`。
3. 必要时用 WebCodecs 转码到 `avc + aac`。
4. MP4 输出使用 `fastStart: "in-memory"`。

因此必须承认：

1. 同一个原文件在同一浏览器同一路径下大概率得到同样 canonical。
2. 跨浏览器、跨硬件、跨编码器、跨库版本时，前端转码产物不能被当成绝对稳定身份。
3. 两个不同原文件如果最终 canonical 字节相同，`source_hash` 不会提前命中，但上传完成后 `content_hash` 仍应让它们共享同一分发平面。
4. `source_hash` 未命中不能成为为相同 canonical 字节创建第二份物理资产的理由。

## 4. 正式媒体字节与 `WebTorrent` 主链

### 4.1 视频文件本身就是预览、播放、分发真相

新视频链路只允许保留一份正式媒体资产：

1. canonical video。
2. 它服务时间线预览。
3. 它服务时间线自动播放。
4. 它服务查看器和全屏。
5. 它是 `WebTorrent` payload。
6. 它是本地缓存和后续做种来源。

禁止再长出正式的：

1. `preview still`。
2. `thumbnail asset`。
3. `poster asset`。
4. 第二份视频变体。
5. 第二个 torrent。
6. 第二个 swarm。

历史旧视频允许兼容 legacy still，但只能被视为过渡债务，不是新标准。

### 4.2 画质不能被拿来换“看起来更快”

默认禁止：

1. 降分辨率。
2. 降帧率。
3. 降码率。
4. 重编码成更糊版本。
5. 生成低清正式版冒充秒开。

允许的只有：

1. 直通。
2. `remux`。
3. `faststart`。
4. 不伤画质的容器级优化。

顺滑靠链路优化、关键字节优先、缓存、预热和 owner 调度解决，不靠压糊视频解决。

### 4.3 激进补齐不等于激进多解码

用户滑到视频后，系统应该把这次滑动转成真实协同收益：

1. 先拿首眼可显示或可播的关键字节。
2. 再拿首播关键片段。
3. 然后继续补齐整文件。
4. 滑出视口后也不默认停止补齐。
5. 补齐完成后继续做种。

但补块和自动播放不是一回事。可以积极下载和补齐，不能让一屏多个视频同时真播、乱解码、乱抢 owner。

**要的是激进协同，不是激进掉帧。**

### 4.4 `0-24 小时` 和 `24 小时后`

新主链附件的正式媒体字节只允许走唯一 `WebTorrent` whole-file swarm。

1. `0-24 小时` 内，服务器只能作为 swarm 内的 `backend strong seed` 参与，包括 `WebSeed + WebRTC seeder`；它不是前端第二正式播放链。
2. `24 小时` 起点只认后端 `complete_at`；到点后服务器退出该内容的媒体字节供给。
3. 服务器退出媒体字节供给后，控制面、权限、删除语义、metainfo、tracker/signaling 仍可保留。
4. `source_hash` 去重不能改变 `24 小时` 服务器退字节裁决。

### 4.5 状态必须说真话

失败态只允许用稳定状态码表达：

1. `MEDIA_READY`
2. `MEDIA_CONNECTING_TO_PEERS`
3. `MEDIA_NO_ONLINE_SEED`
4. `MEDIA_DELETED`

默认连接窗口：

1. `MEDIA_CONNECTING_TO_PEERS` 默认连接窗口为 `8 秒`。
2. 窗口内重试节奏默认 `2 秒`。
3. 进入 `MEDIA_NO_ONLINE_SEED` 后默认重试节奏为 `15 秒`。

“当前没有在线种子”和“内容已删除”必须分开；前者是可恢复缺席态，后者是不可恢复终态。

### 4.6 生态边界

1. `WebTorrent` 负责 canonical 字节分发，不能负责业务附件成立、成员权限或删除真相。
2. `WebSeed` 是 swarm 分发平面里的强帮助者，不能变回第二正式播放主链。
3. `Video.js` 只能做播放器壳，不能拥有媒体身份、附件权限、删除真相和 swarm ready 真相。
4. Chrome / Safari 的自动播放策略只影响 `video` 元素何时能播，不能上抬成协作分发产品规则。
5. WebCodecs 可以参与生成 canonical，但不能成为原始文件身份系统；原始文件身份必须在 WebCodecs 前用 `source_hash` 锚定。
6. Telegram、微信等产品只能作为状态转换体验参考，不能把闭源实现猜测写成技术依据。

### 4.7 后端保留职责与退场字段

后端对新单文件视频只保留：

1. 唯一 canonical video 存储。
2. `content_hash / swarm_id / torrent_info_hash`。
3. `0-24 小时` swarm 内 WebSeed / 强 seed 能力。
4. 到期后的媒体字节退场和控制面保留。

后端对新单文件视频明确禁止：

1. 长期存封面图。
2. 把 `thumbnail_storage_key` 继续当新主链正式字段。
3. 默认承诺 `preview_asset.still_url`。
4. 再生成第二份静态 poster。
5. 为“首屏体验”偷偷复活第二资产。

验证时必须证明：新单文件视频 `complete` 后，后端不再长期写入 `thumbnail_storage_key`，协议面也不再默认承诺 `preview_asset.still_url`。

## 5. 唯一播放器与消息流状态链

### 5.1 当前代码已经成立的真相

后续规则默认继承当前代码事实，禁止另起一套纸面规则：

1. 同一时刻只允许一个视频成为自动播 owner。
2. 最小可见阈值是 `0.6`。
3. “完整可见优先”阈值是 `0.98`。
4. 候选排序先看离视口中心更近，再看可见比例更高。
5. 当前 owner 仍在竞争集合内时，优先保持粘性。
6. 候选先进入 `pending owner`，经过 `80ms` 稳定等待后才提升为正式 owner。
7. 单次空观测不会立刻释放 owner，必须连续空观测才退场。
8. 时间线 owner 已经承接同一颗 canonical player，不是每条视频各养一颗正式 player。
9. 查看器打开时 inline autoplay owner 会退场，但退场的是 inline owner，不是时间轴真相。
10. 时间线 `<video>` 是 `muted + playsinline + no controls`，并禁用 picture-in-picture、remote playback、下载和原生全屏入口。

### 5.2 单一正式播放器真相

硬裁决：

1. 全应用只允许一颗活着的正式 `Video.js` player/container。
2. 消息流自动播、点击放大、真全屏欣赏、退出归位，必须共享同一颗 canonical player。
3. 禁止当前自动播 owner 走一套播放器真相，非当前视频或 viewer 再走另一套播放器真相。
4. 禁止时间线里偷偷保留第二颗 live `<video>` 作为“视觉兜底正式表面”。
5. 禁止为保帧、保画面、保全屏再长一颗 overlay player。

同一颗全局 live `Video.js` player/container，不能在同一时刻给多条可见消息卡片提供各自独立、真实、活着的暂停视频帧。

因此：

**“全局唯一 live player”与“每条非 owner 卡片维持自己的 live paused video frame”不能同时成立；本项目选择前者。**

### 5.3 自动播状态链

自动播不是第三套状态机，而是同一播放会话在消息流里的生命周期。它不能再散落在消息窗、查看器、全屏和播放器壳里；这些壳层只能回抛事实。状态链固定为：候选观测 -> `pending owner` -> `settled owner` -> 离屏中断 -> 回屏续播 -> 自然循环。

它接收的只能是自动播 owner、当前表面、source 是否一致、DOM 当前 `readyState / canplay / seeked`、保存播放位置、查看器/全屏意图、宿主是否仍存在；输出的只能是继续预热、隐藏接管、允许露出、保持暂停帧、迁移到查看器、迁移到全屏、退场。

实现落点只能有一处，不能扩成 WebTorrent runtime、第二 Video.js owner、消息列表渲染器或通用事件总线。`currentTime` 高频保存仍归 `媒体运行时`，播放器实例仍归 `全局唯一播放器.ts`，候选排序仍归 `消息视频自动播编排.ts`。

#### 唯一露出门禁

`全局丝滑自动播.ts` 必须成为唯一“露出门禁”。它只做一件事：根据当前事实，决定用户此刻允许看到哪一种表面。

它的输入只能是事实：

1. 当前自动播 owner 是谁。
2. 当前 source 是否与保存位置同源。
3. 保存的 `currentTime` 是否有效。
4. 目标时间点附近是否已有真实帧证据。
5. 时间线宿主、查看器宿主或全屏宿主是否存在。
6. 当前意图是时间线自动播、查看器打开、全屏接管、退出归位、退场还是销毁。
7. 当前播放器 DOM 的 `readyState / canplay / seeked / requestVideoFrameCallback` 等浏览器事实。

它的输出只能是阶段：

1. `cold_placeholder`：真正没有 source、没有保存位置、没有可表达帧时的冷占位。
2. `hidden_handoff`：正确帧尚未准备好，唯一播放器只能在隐藏宿主里预热。
3. `visible_canonical`：同源 source、目标时间点和可见帧都成立，允许露出正式播放器。
4. `hold_frame`：重播放 owner 已退场，但仍允许保持当前正确帧或只读帧表达。
5. `viewer_handoff`：时间线会话升格到查看器。
6. `fullscreen_handoff`：当前会话升格到全屏或沉浸态。
7. `timeline_return`：查看器或全屏退出后，回到时间线宿主。
8. `retire`：播放会话真正退场。

其他层只能执行这些阶段：

1. `视频附件渲染.ts` 只能把阶段投影成一个稳定 `VideoSurfaceSlot`，不能自己决定 poster、preview、冻结帧、canonical host 谁露出。
2. `时间线播放器宿主.ts` 只能把唯一播放器挂到状态机批准的可见宿主或隐藏宿主，不能把宿主暂空翻译成播放结束。
3. `全局唯一播放器.ts` 只能按阶段执行挂载、同步 source、seek、play、pause、查看器接管、全屏接管和归位，不能发明第二播放位置真相。
4. `房间消息窗.ts` 只能回抛滚动、DOM、host、flush、frame evidence 等事实，不能越过状态机直接切可见表面。
5. `媒体协作分发` 和 WebTorrent 只提供正式 source 与可用性事实，不能为 UI 闪烁提供第二播放链。

这条门禁的硬验收是：

**状态机没批准可见，任何层都不能露出黑屏、首帧、poster、半加载 video 或错误帧；状态机批准可见，必须能证明首个可见帧已经对齐目标 source 和目标时间点。**

#### 五条状态流

进入自动播放：

1. 候选进入 owner 后，唯一播放器先挂到隐藏宿主。
2. 绑定同源正式 source。
3. 恢复保存时间点；没有保存时间点时才按冷启动处理。
4. 等 `loadedmetadata / canplay / seeked / requestVideoFrameCallback` 或等价证据证明正确帧可表达。
5. 状态机输出 `visible_canonical` 后，时间线才揭开正式播放器。

禁止：一成为 owner 就露出 `<video>`，让用户看到黑屏、首帧、poster 或 seek 过程。

滑走退场：

1. 旧 owner 退场前，先 flush 最新播放位置。
2. 先锁住当前正确帧或只读帧表达。
3. 再释放 inline 重播放 owner。
4. 后台补齐和做种资格按 WebTorrent 协作链继续。

禁止：先撤 host、先销毁播放器、先露 poster、先闪一下，之后才回写 `currentTime`。

滑回续播：

1. 如果 A 在 `0:18` 滑走，`0:18` 就是播放位置真相和视觉帧真相。
2. 滑回时先在隐藏宿主对齐同源 source 和 `0:18` 附近帧。
3. 首个可见帧必须已经是 `0:18` 附近的真实帧。
4. 然后才允许继续播放。

禁止：先露首帧或封面，再偷偷 seek 到 `0:18`；只保存 `currentTime` 但首个可见帧不连续，不算续播成功。

查看器 / 全屏升格：

1. 点击当前自动播 owner，语义是“把正在看的这条会话放大给我”。
2. 同一颗 `Video.js` player/container 从时间线宿主迁到查看器或全屏宿主。
3. `src`、`currentTime`、帧证据和播放状态连续。
4. 手机浏览器优先应用内沉浸态，避免原生 fullscreen 提示、黑场或二次点击。

禁止：新建查看器 player、先进入 recovering、黑一下、从 `0` 或首帧重新 seek。

退出查看器 / 全屏归位：

1. 退出前先把查看器或全屏里的最新时间点回灌到唯一位置真相。
2. 时间线宿主准备好后，同一颗播放器归位。
3. 宿主未准备好时，短暂等待或优雅退场，但不能露出错误表面。
4. 原宿主被虚拟列表卸载时，只能挂到新的 canonical 宿主或退出同一会话。

禁止：退出后先露 poster，再等下一拍偷偷 seek；禁止为了归位再生成第二颗 player。

#### 候选观测

`房间消息窗.ts` 只负责量测位置、可见比例、中心距离，并把候选列表回抛给编排和运行时。

禁止消息窗自己裁决最终 owner、直接进入 fullscreen、或持有播放位置真相。

#### Pending owner

`pending owner` 只允许吸收几何抖动，不允许制造肉眼可见空窗。

禁止 pending 一出现就强切 owner，也禁止 pending 期间为了“先有画面”再造第二颗正式表面。

#### Settled owner

正式 owner 生效后，同一颗 canonical player 挂到时间线宿主槽位，从运行时恢复播放位置并开始或继续自动播。

禁止 settled 后重新从头播放，禁止 settled 后还回退到 poster。

#### 离屏中断

离屏中断包括：

1. 滚动失去 owner。
2. 查看器打开。
3. 页面 hidden / background。
4. 生命周期降级。
5. owner 切给别的视频。

统一语义：

1. flush 当前播放位置。
2. 释放 inline owner 解码占用。
3. 保留续播资格。

禁止把离屏中断当成自然结束，禁止因为释放 owner 就把播放位置清零。

#### 回屏续播

视频重新成为 owner 时：

1. 恢复同源播放位置。
2. 继续同一条会话。
3. 如果当前有静止画面表达，直接过渡到继续播放。

禁止从 `0` 重开，禁止先显示开头再 seek。

#### 自然循环

只有视频真实播到结尾时，才允许自然循环回到 `0`。任何中断都不能冒充 loop。

### 5.4 点击与全屏

当前自动播 owner 被点击时，用户表达的是：

**把现在这条正在看的会话放大给我。**

因此：

1. 禁止先新建第二颗 player 再进入全屏。
2. 禁止先打回 recovering 再冷开另一条播放链。
3. 禁止先换壳、黑一下、时间轴回跳，再进入全屏。
4. 当前活跃播放表面可接管时，必须优先让同一颗 canonical player/container 直接升格到查看器或真全屏。

这里的“全屏”必须按浏览器应用体验裁决，而不是机械等同于系统 `requestFullscreen`：

1. 桌面端可以继续走 `Video.js` container-first 的系统 fullscreen。
2. 手机浏览器默认优先走应用内沉浸全屏，避免浏览器自带退出提示和退出黑场。
3. 手机应用内沉浸全屏仍必须复用同一颗 canonical player、同一条播放位置真相、同一条 history 返回链和同一套退出归位语义。
4. 禁止为了“真全屏”观感强行触发会制造浏览器提示、系统黑场或二次点击的原生 fullscreen。

点击非当前视频时，也只能迁移同一颗 player：

1. 切 attachment。
2. 切 source。
3. 切宿主槽位。
4. 不允许留下旧 owner 的活 player，再让新 viewer 长一颗。

退出 viewer / fullscreen 后：

1. 如果该附件仍符合 owner 条件，归位到消息流继续同一条时间轴。
2. 如果不再符合 owner 条件，释放 inline owner，但保留续播资格。
3. 原宿主槽位被虚拟列表卸载时，要么挂到新的 canonical 槽位，要么优雅关闭；禁止生成第二颗 player。

### 5.5 消息流永远无控件

消息流合法形态只有：

1. 自动播的视频画面。
2. 因离屏或失去 owner 保留下来的静止画面表达。
3. 真正无源或失败时的兜底占位。

消息流禁止：

1. 暂停按钮。
2. 进度条。
3. 音量按钮。
4. 全屏按钮。
5. 播放器工具栏。
6. 网页式小播放器集合。

控件只属于查看器或真全屏欣赏态。

### 5.6 目标运行故事

用户第一次滑到视频：

1. 媒体主链解析 `WebTorrent` / swarm 播放源。
2. 时间线卡片只暴露宿主槽位，不自己变成第二颗正式播放器。
3. 全局唯一播放器挂到当前 owner 槽位并开始自动播放。
4. `timeupdate / pause` 把 `currentTime` 上报给 `媒体运行时`。

用户滑走：

1. 前台自动播 owner 可以释放，但必须先 flush 最新 `currentTime`。
2. 原宿主如果还要保留画面，只能保留只读帧投影、宿主过渡表达或兜底占位。
3. 禁止切回 poster、首帧、`<img>` 静态预览，禁止因为不是 owner 就忘掉这段视频看到哪里。

用户滑回来：

1. 目标消息槽位重新准备承接同一颗播放器。
2. 重新成为 owner 时，同一颗播放器从保存时间点继续。
3. 可接受的是正确帧静止后开始动、短暂 guard、或真实无源失败态；禁止“开头封面 -> 跳到续播点”。

用户打开查看器或全屏：

1. 点击当前 owner 时，同一颗播放器直接进入沉浸或 fullscreen。
2. 点击非当前视频时，同一颗播放器接管新附件和新宿主。
3. 关闭查看器或退出 fullscreen 后，同一颗播放器回到可用宿主槽位；原槽位不存在时优雅关闭，不能生成第二颗 player。

## 6. 视觉连续性与兜底规则

### 6.1 可见区内禁止换壳

禁止在用户可见区内发生：

1. `poster -> video` 主节点换壳。
2. `<img>` 被删掉，再插入 `<video>`。
3. `pending -> owner` 等待期间露出开头 poster 或首帧占位。
4. 正式播放器出现晚于用户已经看见该卡片。

自动播候选预热不能晚于真实可见性。时间线视觉壳不能依赖“owner 已确认”这一刻才第一次长出正式播放器表面。

### 6.2 单帧空观测不准引发视觉回退

禁止一次空观测就把当前画面退回 poster。禁止一次虚拟列表重排就把视频重新当冷启动。禁止一次观察器抖动触发 `loadstart -> poster -> replay` 这类倒退链。

只要当前源还有效、已保存有效 `currentTime`、附件仍在当前消息集合内，视觉状态和播放时间都不能倒退回 `0`。

### 6.3 非 owner 画面表达不是第二真相

非 owner 卡片如果仍需要画面表达，只能是：

1. 同一条会话留下来的静止画面表达。
2. 宿主槽位上的过渡表达。
3. 只读帧投影。
4. 真正失败或无源时的兜底占位。

禁止把静止画面表达升级成第二颗 live `<video>`、第二颗 player、canvas 抓帧缓存或 `lastFramePreviewByAttachmentId` 这类第二视觉真相。

### 6.4 什么情况下允许 poster

只在这些情况下允许 poster / thumbnail / 占位图：

1. 还没有 `WebTorrent` / swarm 可播放源。
2. 还没有保存过有效 `currentTime`。
3. 当前源和保存位置源不一致，不能安全 seek。
4. 浏览器尚未加载 metadata，且没有上一帧可保持。
5. 媒体已经进入 `MEDIA_DELETED / MEDIA_NO_ONLINE_SEED / degraded` 等明确失败态。
6. legacy 旧附件仍处于过渡兼容路径。

### 6.5 什么情况下禁止 poster

只要同时满足：

1. 附件是视频。
2. 当前有同源 swarm 播放源。
3. `媒体运行时` 保存了该附件的有效 `currentTime`。
4. 附件仍属于当前房间消息集合。

就禁止退回 poster。此时 poster 会制造假象：它把已经看到一半的视频伪装回开头。

### 6.6 seek 失败不是播放失败

如果浏览器因为 metadata 尚未稳定而拒绝 seek：

1. 不把它升级成播放失败。
2. 在 `loadedmetadata / canplay / playing / owner 切入前` 再尝试。
3. 仍失败时保持加载或 guard，而不是回开头 poster。

目标不是保证每个微秒都立即 seek 成功，而是禁止视觉状态倒退到第一帧。

### 6.7 帧级连续性定义

“滑走后画面稳定”不能被解释成任意预览态，更不能解释成封面、首帧、thumbnail、poster 或旧 `<img>`。

正确定义是：

1. A 视频在 `0:18` 自动播放时滑走，系统必须把 `0:18` 当成播放位置真相。
2. 同时，`0:18` 附近那一帧也必须成为视觉帧真相。
3. 滑回时，用户第一眼看到的就应该是 `0:18` 附近正确画面。
4. 然后同一条会话从 `0:18` 附近继续播放。

以下都不算续播成功：

1. `currentTime` 保存了，但卡片先露首帧。
2. 卡片先露 poster，再 seek 到保存时间点。
3. `<img>` 预览先出现，下一拍才换成正确视频帧。
4. 黑屏、空白、灰占位先露出，再恢复视频。
5. 查看器或全屏退出后，时间线先露旧图，再跳到新时间点。

因此，后续验收必须同时证明两件事：

1. **时间戳连续**：`currentTime`、保存位置和恢复位置对齐。
2. **首个可见帧连续**：首个用户可见帧已经对齐同源 source 和目标时间点。

只满足第一条不算通过。

### 6.8 进入和退出都不能暴露半成品

自动播放“丝滑”包括进入、退出、切换、升格和归位全过程。

进入自动播放时，禁止出现：

1. 黑一下。
2. 空一下。
3. 露 poster / 首帧 / 占位后再开始播。
4. 先插入半加载 `<video>`，下一拍才有画面。
5. owner 已经变了，但播放器还没接管，形成空窗。

退出自动播放时，禁止出现：

1. 旧视频继续多跑一小段，再突然暂停。
2. 先闪一下，再停住。
3. 先撤掉 live player，再等异步冻结帧补上。
4. 旧 owner 和新 owner 双活。
5. 旧 owner 与新 owner 都空，造成列表里一拍黑洞。

owner 切换必须是一个事务：

1. 旧 owner 先 flush 和锁帧。
2. 新 owner 在隐藏宿主准备 source、时间点和正确帧。
3. 状态机批准后提交新表面。
4. 再释放或降级旧表面。

如果某个实现顺序是“先拆旧，再赌新”，真实浏览器里必然会出现黑闪、首帧跳或抽搐。

### 6.9 `requestVideoFrameCallback` 的使用边界

`requestVideoFrameCallback` 是浏览器给出的真实帧证据，适合回答一个问题：

**目标视频帧是否已经提交给浏览器合成器，且它的 `mediaTime` 是否接近我们要露出的时间点。**

它应该用于：

1. hidden handoff 揭帘前确认首个正确帧。
2. 滑回续播时确认目标时间点帧已经可见。
3. 查看器 / 全屏归位前确认不是先露旧帧。
4. 浏览器烟测中采样是否存在错误帧或丢帧。

它不应该用于：

1. 每帧驱动业务状态机。
2. 替代 `timeupdate` 的节流位置上报。
3. 制造 canvas 抓帧缓存或第二视觉真相。
4. 绕过 `全局丝滑自动播.ts` 的露出门禁。

旧浏览器或不支持该 API 的环境，可以退回 `loadeddata / canplay / seeked / readyState` 等较弱证据，但验收必须把证据强弱写清楚，不能把弱证据包装成帧级确定性。

## 7. 模块职责边界

### 7.1 `src/媒体上传外壳.rs`

负责：

1. `source_hash` 复用入口。
2. canonical 资产写入。
3. 分发元数据落库。

禁止：

1. 把 `source_hash` 做成全局探针。
2. 因为命中复用而跳过当前房间发送事务。
3. 为相同 canonical 字节创建第二份物理资产。

### 7.2 `src/媒体附件适配.rs`

负责：

1. `source_hash` 持久化。
2. 受权限约束的复用查询。
3. 删除事实对复用链的阻断。

禁止：

1. 泄漏原上传者、原房间、原消息。
2. 让删除后的附件通过 hash 复活。

### 7.3 `src/媒体协作分发.rs`

负责：

1. `content_hash / swarm_id / torrent_info_hash`。
2. `WEB_SEED_TTL秒`。
3. 稳定 `media_state`。
4. 重试节奏。
5. tracker / announce 对外语义。

禁止：

1. 给同一 canonical 内容生成重复 swarm。
2. 把 `WebSeed` 做回第二正式播放主链。
3. 把无种子和已删除混成一个状态。

### 7.4 `frontend/房间消息窗.ts`

负责：

1. 量测候选。
2. 暴露消息流宿主槽位。
3. 渲染消息流视频画面。
4. 回抛统一打开意图。
5. 表达无控件时间线表面。

禁止：

1. 自己裁决最终自动播 owner。
2. 自己直接 requestFullscreen。
3. 自己持有播放位置真相。
4. 给时间线每条视频创建正式 player。

### 7.5 `frontend/房间消息窗/视频附件渲染.ts`

负责：

1. 把 `全局丝滑自动播.ts` 给出的连续性阶段投影到一个稳定 `VideoSurfaceSlot`。
2. 在同一个表面槽内表达冷占位、隐藏接管、正式播放器、保持帧、退场等结果。
3. 保持视频卡片尺寸、比例和宿主槽位稳定，避免滚动时反向打乱 owner。
4. 回抛用户点击查看器意图。

禁止：

1. 自己根据局部字段重新裁决 poster、preview video、frozen frame、canonical host 谁是可见主壳。
2. 在状态机未批准时露出半加载 video、黑帧、首帧、poster 或错误帧。
3. 用 canvas 抓帧、第二 preview cache、每条消息一颗 paused video 来掩盖 owner 分裂。
4. 让 `IMG -> VIDEO`、`poster -> video` 或 host 插拔在用户可见区内发生。

如果这里仍然存在多套可见主壳判断，后续必须先把它们降级为 `VideoSurfaceSlot` 的内部表达能力，再由状态机决定露出。

### 7.6 `frontend/聊天媒体编排.ts`

负责：

1. 把消息窗候选送进运行时。
2. 把查看器打开意图送进运行时和唯一播放器 owner。
3. 协调自动播候选预热和查看器请求。
4. 传递运行时 position 快照。

禁止：

1. 长出第二套播放真相。
2. 把当前热会话点击又打回 recovering。
3. 等 owner settled 后才第一次让正式播放器接管可见宿主。

### 7.7 `frontend/媒体运行时.ts`

负责：

1. 自动播 owner 真相。
2. `pending owner` 真相。
3. `inlineAutoplayPositionByAttachmentId`。
4. 当前消息集合内附件的续播位置生命周期。
5. viewer / lifecycle / 候选变化时的状态重算。

禁止：

1. 把位置真相下放回 DOM 私有状态。
2. 让离屏中断等价于自然循环。
3. 新增第二套 position store。

### 7.8 `frontend/媒体/消息视频自动播编排.ts`

负责：

1. owner 阈值。
2. 完整可见优先。
3. 中心距离排序。
4. 当前 owner 粘性。
5. 连续性候选裁决。

禁止：

1. 重写一套“谁先进入谁播”的新规则。
2. 为局部灵敏破坏 owner 粘性。

### 7.9 `frontend/媒体/全局唯一播放器.ts`

负责：

1. 唯一 `Video.js` 实例和 container。
2. 当前宿主槽位。
3. attachment / source 接管。
4. 时间线挂载。
5. 查看器接管。
6. fullscreen 升格。
7. 退出归位。

禁止：

1. 再长第二颗正式 player。
2. 变成第二个媒体运行时。
3. 持有 locator / WebTorrent / 自动播候选裁决。
4. 自己再保存第二份 `src / currentTime / fullscreen owner` 业务真相。
5. 在未获得状态机批准前，把半准备状态直接挂到可见宿主。

### 7.10 `frontend/媒体/全局丝滑自动播.ts`

负责：把自动播 owner、保存位置、DOM ready、查看器和全屏意图合成唯一播放连续性状态；用 XState 表达预热、隐藏接管、露出、暂停帧、升格、归位和退场这些离散状态；让时间线、查看器、全屏共享同一条状态转换。

新增硬裁决：

1. 它是唯一露出门禁。
2. 它输出连续性阶段，不输出 DOM 模板。
3. 它可以消费帧证据，但不能自己制造第二视觉缓存。
4. 它可以表达查看器 / 全屏 handoff，但不能变成查看器 UI owner。

禁止：创建或持有第二颗播放器；持有 WebTorrent、locator、附件权限或上传复用真相；接管候选排序、`currentTime` 高频保存、消息渲染或查看器 UI；为绕过闪烁新增 poster、canvas 抓帧、第二 preview cache 或第二 live video。

### 7.11 `frontend/媒体/videojs播放器壳.ts`

负责：

1. 提供播放器壳能力。
2. 服从唯一播放器 owner。
3. 保留 container-first fullscreen 路径。

禁止：

1. 成为第二个 lifecycle owner。
2. 为当前 owner 或非当前视频默认新建第二颗 player。

### 7.12 第一轮调查范围

第一轮只允许收口：

1. 时间线自动播放。
2. 滑走暂停帧。
3. 滑回续播。
4. 查看器升格。
5. 全屏接管。
6. 退出归位。
7. 滚动时 owner 抽搐。

第一轮禁止触碰：

1. 后端业务契约。
2. 上传复用。
3. WebTorrent 退字节。
4. 数据库 schema。
5. 图片主链收尾。
6. 新播放器框架。
7. 第二媒体源或 HTTP 冷源兜底。

这轮调查要先输出事实归属表，再写 characterization 测试，再做最小实现。禁止一上来把整个播放器链推倒重写。

### 7.13 禁止扩大范围

这份总纲约束后续实现，但单次视觉连续性或播放器收口修复禁止顺手扩大到：

1. 后端业务契约。
2. `WebTorrent` tracker。
3. dev seeder。
4. 上传去重。
5. 数据库 schema。
6. 查看器非相关控制条样式。

如果某次任务确实需要触碰这些边界，必须先写清楚原因、风险、验证和退场计划，不能借“播放器体验优化”顺手改主链。

## 8. 漂移清单

以下方向一律视为失败：

1. 为了首屏稳一点，加回后端长期 poster。
2. 为了顺一点，生成低码率正式版。
3. 为了节流，视频滑走就停止补齐和做种。
4. 把激进补齐做成多视频同时真播。
5. 预览重新依赖 autoplay owner。
6. 把 `source_hash` 做成全局存在性探针。
7. 把媒体资产复用偷换成旧消息复用。
8. 把转发分享实现成重新上传。
9. 为相同 canonical 字节重复生成互不相通的 swarm。
10. 让播放器决定去重、ready、删除或权限。
11. 让消息流视频重新长控件。
12. 用 canvas 抓帧、`lastFramePreview`、每条消息一个 Video.js 去掩盖 owner 分裂。
13. 点击当前自动播 owner 时默认重建查看器 player 再全屏。
14. 点击非当前视频时并存第二颗 player。
15. 为了修 UI 削弱 `WebTorrent` aggressive swarm、补齐和做种。
16. 用“先这样能跑”保留旧支路、旧入口、旧文档或旧裁决。
17. 把进入黑闪、滑走闪、滑回首帧跳、全屏断片拆成互不相干的小补丁。
18. 让 `视频附件渲染.ts` 绕过状态机，自己决定可见主壳。
19. 把“保存了 `currentTime`”冒充“首个可见帧也连续”。
20. 用更长 timeout、更多 guard、更多 poster 层掩盖状态机裁决缺失。
21. 把 `requestVideoFrameCallback` 用成第二状态机、第二帧缓存或高频业务驱动器。
22. 为了保一帧画面，让非 owner 卡片继续持有 live player 或持续解码。
23. 用闭源产品名义幻想内部实现，跳过本项目真实代码和官方资料。
24. 在第一轮调查里顺手改后端、上传、WebTorrent 退字节、图片主链或数据库。

## 9. 验收门禁

### 9.1 资产与复用

必须证明：

1. 同一原始 MP4 在同一授权上下文上传两次，第二次命中 `source_hash`，不重新转码、不重新上传媒体字节。
2. 同一原始图片上传两次，第二次命中 `source_hash`，不重新生成 canonical 图片。
3. `source_hash` 命中后，新消息仍有自己的 `room_event / message / attachment_ref`。
4. `source_hash` 命中后，复用的 `content_hash / swarm_id / torrent_info_hash` 与原 canonical 资产一致。
5. 不同原文件但最终 canonical 字节相同，上传完成后仍通过 `content_hash` 共享 swarm。
6. 重新压缩后肉眼相同但原始字节不同的视频，不被 `source_hash` 命中。
7. 未授权房间不能通过同一 `source_hash` 探测到别处已有媒体。
8. 原附件删除后，`source_hash`、转发、缓存或 viewer 路径不能让新附件继续拿已删除 canonical 装作 ready。
9. 当前用户把可见媒体附件转发到另一个有发送权限的房间时，不重新上传、不重新转码、不重新生成 torrent，只新增新消息和新附件引用。
10. 当前用户看不见的源附件不能被转发，也不能通过 `source_hash` 响应探测出其存在。

### 9.2 分发与状态

必须证明：

1. 新主链附件的正式播放、正式查看、正式补齐都落在同一个 `WebTorrent` whole-file swarm。
2. `0-24 小时` 阶段服务器强参与来自 swarm 内的 `WebSeed + WebRTC seeder`，不是第二播放链。
3. `24 小时` 到点判断只认后端 `complete_at`，服务重启不会重置。
4. `MEDIA_READY / MEDIA_CONNECTING_TO_PEERS / MEDIA_NO_ONLINE_SEED / MEDIA_DELETED` 四种状态在前后端统一存在。
5. “没有在线种子”和“内容已删除”在真实浏览器烟测里走出两条不同路径。
6. 用户滑到某视频后，即使滑走，后台仍继续补齐整文件。
7. 整文件补齐完成后，客户端进入做种态。
8. 后续用户能因为前面的用户变快，而不是只有单人本机能播。
9. 新主链附件如果实际命中 HLS、原文件直链、CDN、`p2p-media-loader` 或临时 range 服务，判定为主链失败。
10. Chrome / Safari 自动播放失败时，不影响后台协作补齐 owner 的判断。
11. 替换或升级播放器壳时，媒体身份层和 `WebTorrent` 分发层测试不需要重写。

### 9.3 播放与连续性

必须证明：

1. 同屏多候选时只有一个 owner。
2. 当前 owner 仍在阈值内时具备粘性。
3. 单帧空观测不会立刻释放 owner。
4. 连续空观测才真正释放 owner。
5. `pending owner` 稳定等待不能制造可见空窗。
6. 离屏中断后回屏从上次中断点继续。
7. 自然播放到结尾时才允许从头循环。
8. 带 `posterSrc` 和不带 `posterSrc` 的场景都通过连续性测试。
9. 有 poster 的视频，owner 释放后不得回切 `<img poster>`。
10. 有 poster 的视频，宿主槽位重挂载后在 `loadedmetadata` / 接管前恢复到保存 `currentTime`。
11. owner 切换只允许当前 owner 承接 live player，其他卡片只能是只读帧投影或兜底占位。
12. 时间线 `<video>` 永远无控件。
13. 点击当前自动播 owner 视频进入全屏时，不得新增第二颗播放器壳、第二个 `<video>` 或第二条正式播放会话。
14. 点击当前自动播 owner 视频时，fullscreen 请求必须由当前活跃播放表面直接触发；`src` 和 `currentTime` 必须连续。
15. 点击非当前 owner 视频时，也必须迁移同一颗 canonical player。
16. fullscreen 中原宿主槽位被虚拟列表卸载时，仍只有同一颗 canonical player。
17. fullscreen 中 owner 切换到另一条视频时，同一颗 player 完成接管而不是重建。
18. 带 `poster` 的 swarm 视频在 `loadeddata / canplay / playing` 任一事件后，只要当前活跃播放器已经提交首帧，就不得再发生“删 poster 才看到真帧”的属性级闪烁。
19. 测试必须覆盖 `posterSrc` 非空场景；只测 `posterSrc: null` 不能冒充完整验收。
20. 播放连续性测试必须覆盖高速滚动、慢速滚动、查看器升格、全屏接管、退出归位、源切换和宿主卸载，不得只覆盖单一路径。
21. 进入自动播放时，状态机未输出可见阶段前，渲染层不得露出黑屏、poster、首帧、半加载 video 或错误帧。
22. 滑走退场时，必须先 flush 播放位置并锁住当前正确帧，再释放 inline 重播放 owner。
23. 滑回续播时，`0:18` 滑走就必须以 `0:18` 附近帧作为首个可见帧；只断言 `currentTime` 已恢复不算通过。
24. 查看器 / 全屏升格必须证明同一颗 `Video.js` player/container 迁移，不能重建、双活或先断片再恢复。
25. 退出查看器 / 全屏归位必须证明最新时间点先回灌，时间线首个可见帧连续，不能先露 poster 再 seek。
26. `全局丝滑自动播.ts` 必须是唯一露出门禁；测试要能证明 `视频附件渲染.ts` 不能绕过它自行露出可见主壳。
27. `requestVideoFrameCallback` 可用时，至少一组测试或浏览器探针要用 `mediaTime` 证明目标帧已经提交；不可用时必须说明降级证据。

### 9.4 真实浏览器烟测

必须在真实 HTTPS 环境下覆盖：

1. 真实图片和真实 MP4。
2. 时间线滚动到视频自动播放。
3. 播放数秒后滑走。
4. 滑走后的卡片不回到开头 poster。
5. 滑回后从保存时间点连续播放。
6. 点击当前自动播 owner 视频进入查看器或真全屏。
7. 退出归位后时间轴连续。
8. 点击另一条视频时同一颗 player 迁移。
9. 多视频消息流中只有一个自动播 owner。
10. 前 `24 小时` 强 seed 阶段。
11. 后 `24 小时` peer 接力阶段。
12. MutationObserver 或等价手段证明：目标视频进入可见区并接管自动播的过程中，不发生可见区内 `IMG` 删除 / `VIDEO` 插入换壳。
13. 控制台无 `MaxListenersExceededWarning`。
14. 网络仍走 `WebTorrent` 主链，没有新的正式冷源播放链。
15. `WebTorrent` 浏览器主链要求安全上下文；生产必须是 HTTPS，本地开发可用 `localhost`。
16. 慢滚、快滚、上下反复滚动时，owner 序列不能出现肉眼抽搐；如果出现，必须记录 owner、pending owner、continuity phase 和 DOM mutation 序列。
17. 进入自动播放、滑走、滑回、查看器打开、全屏进入、全屏退出每一步都必须采样首个可见表面，不能只看最终是否播放。
18. MutationObserver 或等价手段必须证明：可见区内没有 `poster -> video`、`IMG -> VIDEO`、stage host -> visible host 的肉眼换壳。
19. 浏览器探针必须采样 `readyState / paused / currentTime / src / activeVideoCount / activeFormalPlayerCount / autoplayOwnerCount`。
20. 对 `1234b` 的真实烟测必须覆盖至少两条视频，避免只证明单视频 happy path。

### 9.5 性能与架构

必须保持：

1. 禁止同屏多 live 视频同时解码。
2. 禁止 `activeVideoCount > 1`。
3. 禁止 `autoplayOwnerCount > 1`。
4. 禁止为了保帧把所有历史视频 DOM 全量保活到卡顿。
5. 禁止非 owner 卡片继续持有 live player 或持续解码播放。
6. 禁止放宽 `timeupdate` 上报节流。
7. 禁止滚动候选量测新增同步重排热点。
8. 禁止 UI 降载取消 `WebTorrent` 下载、做种、补齐和帮助任务恢复。
9. 禁止把 XState 用成大而全的全局事件总线；本主题只允许把丝滑播放的连续性状态收口到一个已登记 owner。
10. 禁止用稳定视觉为理由增加第二 live player、第二 source owner 或第二播放位置 store。
11. 禁止把状态机裁决结果复制成渲染层第二套布尔矩阵；渲染层只能消费阶段。
12. 禁止让虚拟列表动态高度变化反向触发 owner 抽搐；视频卡片尺寸和宿主槽位必须稳定。
13. 禁止为解决一个浏览器症状引入全平台重路径；移动端和 PC 端只能在能力适配层分歧。

### 10.3 自审结论

按项目约束自审：

1. 不触碰后端业务真相；本主题的核心是媒体资产身份、分发主链和前端播放表面边界。
2. 不削弱 `WebTorrent`；播放源、补齐、做种、帮助任务恢复都必须保留。
3. 只允许用 `全局唯一播放器.ts` 收口播放器生命周期，用 `全局丝滑自动播.ts` 收口播放连续性状态；二者不能互相夺权，也不能绕过 `媒体运行时` 的位置真相。
4. 明确禁止 canvas 抓帧、第二 preview cache、每条消息一个 Video.js、双活 player truth。
5. 根因必须从“视觉壳切回 poster”继续收口到“播放器真相双轨”和“宿主迁移状态矩阵缺测试”。
6. 适合万人群聊的前提是只有一颗 live player，`timeupdate` 继续节流，非 owner 不继续解码。
7. 浏览器事件只回抛事实，生命周期 owner 和播放连续性 owner 各自唯一，不能分层共管。
8. 当前热会话全屏路径必须优先直接接管，同一颗 player 升格，不默认走“新建查看器 -> 新建 player -> fullscreen”。

### 10.4 2026-05-06 自动播露出门禁设计记录

本次补充不是新增第二规范，而是把用户最新确认的真实体验目标收回本文：

1. 自动播放进入不能黑闪、空闪、露占位或首帧后再播放。
2. 自动播放滑走不能闪一下才暂停。
3. A 视频在 `0:18` 滑走，滑回时首个可见帧就必须是 `0:18` 附近，不能先露首帧再跳。
4. 点击查看器或全屏不能断一下。
5. 退出全屏归位不能闪一下。
6. 群聊消息窗滚动或页面尺寸变化时，当前正在自动播放的视频画面不能边播边抽、前后跳、闪回首帧或封面。
7. 视频卡片尺寸稳定但画面在跳，仍然算自动播稳态失败；不能把它归因成正常滚动抖动。

本次裁决来自当前代码事实，而不是纸面幻想。当前代码已经存在以下 owner 和边界：

1. `frontend/媒体运行时.ts`：自动播候选、pending owner、settled owner 和释放语义。
2. `frontend/媒体/全局丝滑自动播.ts`：播放连续性阶段判定。
3. `frontend/媒体/全局唯一播放器.ts`：唯一 `Video.js` player/container。
4. `frontend/房间消息窗/视频附件渲染.ts`：poster、preview、冻结帧、canonical host 和 stage host 等表面投影。
5. `frontend/房间消息窗/时间线画面缓存.ts`：自动播冻结帧和首帧就绪缓存。
6. `frontend/房间消息窗/时间线播放器宿主.ts`：时间线宿主与唯一播放器之间的挂载桥。

因此本次设计判断是：系统不是没有“丝滑”相关代码，而是“能不能露出”和“什么时候允许播放动作”的裁决仍然散在多个层里。后续第一轮执行必须把 `全局丝滑自动播.ts` 收成唯一露出门禁，让渲染层、宿主层和播放器层只执行阶段结果。

本轮新增的稳态不变量：

**同一 owner、同一 source、同一时间线宿主仍有效，且唯一播放器已经处于 visible 播放态时，滚动和 resize 只能更新几何事实；不得触发 `currentTime` 回灌、seek、source 同步、poster 同步、player 重挂载、stage host 与 canonical host 切换、preview video 回盖 live player。**

这条规则的 DDD / 六边形含义是：几何信号属于外层适配器输入，播放连续性状态属于核心应用模型，Video.js / DOM 只执行端口动作。外层观察器不能把“位置变了”翻译成“播放会话要恢复一遍”。

第一轮只允许解决前端播放表面状态链：

1. 时间线自动播放。
2. 滑走暂停帧。
3. 滑回续播。
4. 查看器升格。
5. 全屏接管。
6. 退出归位。
7. 滚动 / resize 触发的当前 owner 稳态画面抽搐。

不碰后端、上传复用、WebTorrent 退字节、图片主链、数据库 schema 和新播放器框架。

本次设计也吸收了成熟实践边界：

1. XState 负责状态流，不负责媒体字节和 DOM 高频事实。
2. Video.js 负责唯一播放器能力，不负责自动播业务裁决。
3. `requestVideoFrameCallback` 负责帧提交证据，不负责第二视觉缓存。
4. 虚拟列表负责窗口和测量，不负责播放 owner。
5. Chrome / Safari autoplay 规则负责浏览器允许与否，不改变产品连续性目标。
6. X.com / TikTok / 抖音只能作为体验标杆，不能把闭源内部实现猜成项目技术依据。

本次补充后的执行原则：

**进入、滑走、滑回、查看器、全屏、归位，全程都必须先准备正确帧，再允许用户看到；任何用户看见的黑帧、空帧、错误帧、首帧回退、poster 闪回或播放器重建感，都算露出门禁失败。**

**稳态播放期间，滚动和 resize 的正确结果是“什么播放动作都没发生”：owner 不变、source 不变、host 不变、正式 player 不重挂、`currentTime` 除自然播放外不被写回、DOM 不从 canonical host 退回 stage / preview / poster。**

### 10.5 2026-05-06 三遍自审结论

第一遍自审，检查用户意图：本文已经把用户肉眼确认的六类症状写入前因后果，并明确“只保存 `currentTime` 不算续播成功，首个可见帧也必须连续”。本次修正点是补清“抽搐”指当前正在播放的视频画面自己前后跳或闪回首帧/封面，不是视频卡片高度抖动，也不是正常 owner 切换。

第二遍自审，检查架构边界：本文已经把状态机定位为唯一露出门禁，把 `Video.js`、DOM、虚拟列表、WebTorrent、浏览器帧回调都降为事实输入或动作适配，符合 DDD / 六边形边界。本次修正点是把滚动 / resize 明确降级为几何事实输入，禁止它越层触发 seek、重挂载、换壳或恢复流程。

第三遍自审，检查执行与验证闭环：本文已经补写第一轮调查范围、禁止扩大范围、characterization 测试方向、真实浏览器烟测门禁和性能红线。本次修正点是把“同一 owner/source/host 稳态播放期间几何变化零重接管”写成可测门禁：必须证明没有 `currentTime` 写回、没有 DOM 表面回退、没有 player 重挂。

## 11. 最终硬裁决

以后在 `koko` 里，视频播放和多媒体复用都按下面这句话理解：

**媒体物理资产按 canonical 字节全局唯一；上传前用受权限约束的 `source_hash` 复用已有资产；转发分享用可见源附件复用已有资产；上传后用 `content_hash` 精确收口同一 canonical 字节；分发层用 `swarm_id / torrent_info_hash` 复用唯一 `WebTorrent` whole-file swarm；播放层只保留同一颗 `Video.js` player/container；连续性层只保留同一条状态链，在消息流、查看器和全屏之间迁移同一条会话。**

从这句话自然推出全部红线：

1. 禁止第二媒体资产真相。
2. 禁止第二正式字节主链。
3. 禁止第二正式播放器真相。
4. 禁止第二套 `currentTime`、视频画面和播放连续性状态链。
5. 禁止把 `source_hash` 做成全局存在性探针。
6. 禁止把房间误当成媒体身份边界。
7. 禁止把转发分享误做成重新上传。
8. 禁止把 poster、thumbnail、runtime preview 做回视频主真相。
9. 禁止把“看过就算了、滑走就停了、补齐后不种了”做成半截协同逻辑。
10. 禁止用降低画质、第二链路、第二播放器、第二播放连续性状态链或旧支路伪造体验。
11. 禁止任何层绕过 `全局丝滑自动播.ts` 这个唯一露出门禁。
12. 禁止把 `currentTime` 连续当成完整续播；首个可见帧也必须连续。
13. 禁止把闭源产品的体验标杆偷换成未经验证的内部实现猜测。

真正要守住的核心只有一句：

**不要再把视频拆成“预览一套、播放一套、分发一套、露出再一套”；让同一个 canonical 媒体资产、同一颗播放器和同一条播放连续性状态链，把这些职责一次性承担完。**
