# Telegram iOS 高保真视觉复刻设计

## 文档元信息
- 日期：2026-04-01
- 适用范围：`Koko` 前台聊天 Web 壳
- 目标页面：
  - `ConversationListScreen`
  - `JoinByCodeScreen`
  - `ChatScreen`
- 设计优先级：
  - 第一优先级：视觉与元素尽可能一比一贴近 Telegram iOS
  - 第二优先级：在不破坏复刻感的前提下做克制响应式适配

## 1. 目标

本轮不是做“更现代的聊天 UI”，也不是做 “Koko 自有品牌重设计”。

本轮目标是把现有三页主链路壳，收口成一个：

- 以 Telegram iOS 为唯一主视觉参照
- 以 iPhone 竖屏聊天体验为主标尺
- 明显减少当前 Web 壳的网页感、卡片感和自研感
- 在不污染 `contract / application / domain` 的前提下，提高壳层复刻度

本轮复刻只覆盖聊天主链路的可见元素，不扩新业务，不调整后端契约。

## 2. 主基准

### 2.1 设备基准

主基准设备固定为：

- `iPhone 15 / 16 Pro` 级别竖屏宽度
- 以 `390pt` 左右的手机宽度作为密度基准

这意味着本轮的判断标准不是“宽屏网页是否铺满得自然”，而是：

- 在手机密度下，是否足够像 Telegram iOS
- 宽屏下是否仍保持 Telegram iOS 手机壳气质

### 2.2 视觉优先级

三页统一按下面顺序打磨：

1. 顶部导航栏层次
2. 搜索栏
3. 会话列表 cell
4. 聊天输入区
5. 聊天气泡与背景
6. 空态与错误态

### 2.3 非目标

本轮明确不做：

- 桌面三栏/双栏产品化改造
- `Koko` 自有品牌视觉语言
- 新增 tab bar、资料页、联系人页等 Telegram 其他壳层
- 为了 UI 复刻新增第二前端栈
- 为了“像 iOS”把业务真相、权限真相、成员真相塞回前端

## 3. 结构与页面设计

### 3.1 会话列表页

目标：更接近 Telegram iOS 的主聊天列表，而不是“搜索卡片 + 聊天卡片列表”。

结构固定为：

1. iOS 风格顶部导航区
2. 列表上方嵌入式搜索栏
3. 原生感更强的聊天列表流

应有观感：

- 顶部不再是当前这种 `Menu / Chats / TL` 式三栏假导航
- 搜索栏看起来像 iOS 搜索栏，而不是单独的业务卡片
- 会话项更像 iOS list cell，而不是厚重浮起卡片
- 头像、标题、预览、时间、未读指示遵守 Telegram iOS 的密度和层次

### 3.2 搜索/加群页

目标：更接近 Telegram 内部搜索页，而不是独立表单页。

结构固定为：

1. 返回式顶栏
2. 聚焦中的搜索栏
3. 搜索结果列表 / 空态 / 加载态

应有观感：

- 搜索输入本体必须像 iOS search field
- 搜索结果沿用 Telegram 列表语言，不单独造一套视觉体系
- 空态更轻，不使用大号说明卡片

### 3.3 聊天页

目标：更接近 Telegram iOS 的聊天页手机壳观感。

结构固定为：

1. 返回式导航栏
2. Telegram 风格消息流
3. Telegram 风格底部输入区

应有观感：

- 顶栏更像 iOS 返回导航，不像网页 header
- 消息区背景更像 Telegram 壁纸层，而不是简单深色渐变
- 输入区是复合操作条，不是网页输入框 + 蓝按钮

## 4. 响应式边界

本轮响应式策略不是无限拉伸，而是：

- 保持 iPhone 密度
- 用留白和壳体展示适配更大容器

具体规则：

- header、search、cell、composer 高度不随宽屏自由长胖
- 宽屏时主要增加外层留白，不增加内部控件密度
- 聊天气泡宽度必须有上限
- 不引入桌面专属布局切换

断点原则：

- 小屏：贴边、满宽、无额外壳体修饰
- 中屏：出现壳体感、圆角、阴影、外边距
- 大屏：继续扩展外部留白，但内部保持手机节奏

## 5. 架构与治理边界

### 5.1 允许改动的层

本轮主要改动应收敛在：

- `src/view.rs`
- `assets/theme.css`

必要时允许做最小壳层接线，但默认不扩散到其他层。

### 5.2 禁止污染的层

以下边界本轮不能被破坏：

- `src/contract.rs`
  - 禁止新增 Telegram 专属字段
  - 禁止新增 cell、header、layout、page-flow 语义
- `src/chat.rs`
  - 禁止让聊天真相状态变成 UI 样式真相
  - 禁止新增只服务页面表现的伪业务状态
- `src/web.rs`
  - 禁止新增 Telegram 专属业务分支
  - 禁止让壳层视觉细节反向控制业务流程

### 5.3 壳层允许承担的职责

壳层允许承担：

- 导航层级
- 搜索聚焦态
- 视觉层次
- 滚动体验
- 输入框本地草稿展示
- 宽屏壳体展示

壳层不得承担：

- 群成员真相
- 权限真相
- 消息成立真相
- 后端流程判断
- 契约字段扩写

## 6. 实施范围

### 6.1 本轮只改什么

- 三页主链路视觉结构
- CSS token、间距、层次、组件外观
- 关键壳层结构命名和最小必要交互补齐

### 6.2 本轮不改什么

- 业务用例
- 房间查询契约
- realtime 业务语义
- admin 页面主视觉
- 多端扩展壳

## 7. 测试与验收

### 7.1 测试策略

按 TDD 执行：

1. 先补失败测试
2. 再做最小壳层实现
3. 跑绿
4. 最后收口样式与命名

本轮优先补的测试类型：

- 壳层结构稳定测试
- 页面状态分流测试
- 必要的壳层交互测试

### 7.2 验收标准

当且仅当以下条件同时成立，才算本轮设计落地：

1. 会话列表页明显更像 Telegram iOS 主聊天列表
2. 搜索/加群页不再像表单页，而是 Telegram 搜索态
3. 聊天页顶部、消息区、输入区明显更像 Telegram iOS
4. 宽屏下保持手机壳感，不发生无限拉伸
5. `contract` 未混入 Telegram UI 语义
6. 前端未新增第二套业务真相
7. 主链路测试保持通过

### 7.3 证明方式

本轮不使用“我感觉像”作为完成证明。

证明方式固定为：

- 新鲜测试结果
- 结构与样式改动证据
- 与 Telegram iOS 学习基准的人工核对

如果没有足够直接证据，不宣称“100% 复刻完成”。

## 8. 实施顺序

1. 先补失败测试，锁定壳层关键结构
2. 重做顶部导航与搜索栏
3. 重做会话列表 cell
4. 重做聊天输入区与消息区背景
5. 收口空态、错误态与宽屏壳体表现
6. 跑测试验证
7. 清理格式化噪音并提交

## 9. 设计结论

本轮设计的本质不是“做一个更好看的 Web 页面”，而是：

- 用 Telegram iOS 作为唯一主参照
- 把当前聊天壳从“像 Telegram 的网页”推进到“更像 Telegram iOS 本体的手机壳”
- 同时守住 `Koko` 的多壳共核和契约边界

最终交付应当呈现为：

- 更高的 Telegram iOS 复刻度
- 更低的网页感
- 更强的壳层一致性
- 不新增架构污染
