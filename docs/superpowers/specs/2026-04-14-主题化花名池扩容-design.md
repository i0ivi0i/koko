## 1. 这份 spec 为什么存在

当前花名生成已经接入 `names`，但项目实际只给了它：

- `4` 个主题；
- 每个主题 `4` 个前缀；
- 每个主题 `4` 个名词；
- 总组合空间 `4 * 4 * 4 = 64`。

所以问题不在 `names` 轮子，而在我们给轮子的主题词典太小、风格太薄。  
继续往 `src/用户身份.rs` 里堆少量数组，只会让“用了轮子”变成表面工程，实际仍然是 MVP 词库。

这次扩容要解决的是：

1. 花名数量必须进入第一版可用规模，目标至少 `10000` 个组合空间。  
2. `names` 继续作为短组合生成主力，不再手搓第二套组合算法。  
3. 中文网络梗、小说素材、历史政治人物和网络抽象幽默要能进入花名体系。  
4. 源码不能变成巨大段子仓；词库要作为业务数据收口，生成器只做薄适配。  

## 2. 已确认口径

1. 长句梗可以直接作为花名，和短组合花名同池出现。  
2. 内容尺度偏互联网原味，允许强抽象、无厘头、赛博玄学、短视频梗和程序员梗。  
3. 允许英文、数字和符号，例如 `CPU / DDL / 404 / bug / +1 / 2.5次元`。  
4. 小说素材可以进入短组合池，既要网文梗味，也要文学意象味。  
5. 历史政治人物可以使用真名和意象，例如 `秦始皇在等WiFi`、`孔明借东风但404`。  
6. 不做撞名治理；靠足够大的花名空间压低撞名概率。  
7. 不做房间级主题；主题库仍是项目级公共资源。  
8. 当前不暴露主题，前台只显示最终花名。  
9. 网上梗库只作为语法和风格输入，不整站搬运；项目生成原创变体，少量完整梗句只收用户明确点名或已经强公共语境化的短句。

实现时仍要守住最低产品边界：

1. 不把花名池做成违法教唆、露骨色情、群体仇恨或现实个体攻击素材库。  
2. 历史政治人物可以出现，但优先以梗化、意象化、抽象化方式使用，不把默认昵称变成现实政治攻击。  
3. 不使用具体小说、动漫、游戏 IP 角色名作为权威花名素材，避免侵权和强指向性；可以使用类型化意象，例如 `剑修`、`旧梦`、`掌柜`、`赛博巡抚`。  

## 3. 核心设计

花名池分成两条输入源：

```text
组合主题池
  -> names(adjectives, nouns)
  -> 短花名

完整梗句池
  -> 直接随机抽取 phrase
  -> 长句梗花名
```

这不是两套生成器。  
`names` 仍然是短组合的唯一生成轮子；完整梗句池只是“完整句子型业务数据”，不适合被强行拆进 adjective/noun。

## 4. 数量目标

第一版下限：

- 至少 `12` 个短组合主题；
- 每个主题至少 `30` 个前缀；
- 每个主题至少 `30` 个名词；
- 短组合空间至少 `12 * 30 * 30 = 10800`；
- 完整梗句池额外至少 `200` 条；
- 总空间至少 `11000` 级别。

这个数量是组合空间，不是要求手写一万条完整花名。

## 5. 主题设计

### 5.1 短组合主题

第一版建议至少包含：

1. `wildlife`：动物与自然  
2. `cosmos`：宇宙与天体  
3. `snack`：零食与吃喝  
4. `weather`：天气与季节  
5. `novel_xianxia`：修仙/网文  
6. `novel_literary`：文学意象  
7. `wuxia_jianghu`：武侠江湖  
8. `cyber_abstract`：赛博抽象  
9. `programmer_mystic`：程序员玄学  
10. `history_politics`：历史政治人物与意象  
11. `short_video_meme`：短视频热梗  
12. `worker_mood`：社畜牛马与发疯文学  

示例方向：

- `novel_xianxia`: `渡劫的剑修`、`闭关的药童`、`退婚的少侠`
- `novel_literary`: `提灯的旧梦`、`夜雨里的纸鹤`、`迟来的长亭`
- `cyber_abstract`: `加载失败的恋爱脑`、`量子纠缠的牛马`
- `programmer_mystic`: `电子木鱼超度DDL`、`404但嘴硬`
- `history_politics`: `秦始皇在等WiFi`、`孔明借东风但404`

### 5.2 完整梗句池

完整梗句直接作为花名，不走 `names`：

- `龙卷风摧毁停车场`
- `乌鸦坐飞机`
- `她说是晒黑的`
- `你那李白吗`
- `我的CPU在渡劫`
- `这瓜保熟但掉帧`
- `赛博功德加一`

完整梗句池的作用是补足中文互联网语感，不承担主要数量空间。

### 5.3 网上梗语法解构

不要把网上梗库当成“可复制素材库”。
更稳的做法是抽出可组合语法，让 `names` 和项目自有词库生成原创花名：

1. 经典动作招式反转
   - 语法：`荒诞主体 + 武打/动画式动作 + 现代故障`
   - 示例：`鲨鱼打太极`、`孔明开漂移`、`猫猫拔网线`
   - 价值：接近 `乌鸦坐飞机` 这类动作梗，但不依赖单一原句复读。
2. 灾难级日常夸张
   - 语法：`宏大灾难 + 小场景/办公物件`
   - 示例：`陨石砸中外卖柜`、`海啸淹了工位`、`黑洞吸走DDL`
   - 价值：接近 `龙卷风摧毁停车场` 的荒诞比例差，适合长句池和短组合池共用。
3. 赛博玄学
   - 语法：`电子/量子/赛博 + 传统玄学动作 + 网络状态`
   - 示例：`电子木鱼超度bug`、`赛博功德+1`、`量子签筒保佑上线`
   - 价值：网络抽象感强，也能和程序员梗自然合流。
4. 程序员精神状态
   - 语法：`HTTP/CPU/缓存/线程/重启 + 情绪或玄学状态`
   - 示例：`404但嘴硬`、`CPU正在渡劫`、`缓存过期的灵魂`
   - 价值：项目技术社区语感更强，但仍是普通用户能读懂的轻梗。
5. 网文与小说叙事
   - 语法：`退婚/闭关/渡劫/夜雨/长亭 + 类型化身份或意象`
   - 示例：`退婚的剑修`、`提灯的旧梦`、`夜雨里的掌柜`
   - 价值：承接 `writer-memory` 的小说素材思路，不使用具体 IP 角色名。
6. 历史人物跨时空错位
   - 语法：`历史人物真名/称谓 + 当代网络物件或系统状态`
   - 示例：`秦始皇等WiFi`、`曹操加载中`、`拿破仑刷功德`
   - 价值：允许历史政治真名进入，但以错位幽默为主，不做现实政治攻击。
7. 短视频嘴替句式
   - 语法：`反问/嘴硬/破防/保熟 + 掉帧/重启/加载中`
   - 示例：`这瓜保熟但掉帧`、`你那李白吗`、`我没破防只是重启`
   - 价值：补足中文短视频口语节奏，适合直接放进完整梗句池。
8. 发疯文学与牛马文学
   - 语法：`情绪状态 + 抽象物件/排队/补票/散装`
   - 示例：`正在量子纠缠的牛马`、`精神状态像散装薯片`、`灵魂在排队补票`
   - 价值：强抽象、低门槛、可大量组合，适合作为第一版扩容主力之一。

实现时按这些语法扩词，而不是按来源网站抄条目。
这能同时满足三件事：

1. 站在网上梗文化和流行语研究的肩膀上；
2. 避免把项目词库变成侵权或过时梗搬运仓；
3. 让 `names` 继续高效地产生万级原创组合。

## 6. 词库落点

推荐把词库从 `src/用户身份.rs` 迁出到静态数据文件，例如：

```text
assets/anonymous_alias_themes.json
```

原因：

1. 词库是业务数据，不是算法。  
2. JSON 可以直接复用项目已有 `serde_json`，不新增 TOML/YAML 依赖。  
3. Rust 源码只保留加载、校验、抽样、调用 `names` 的薄适配。  
4. 后续扩词库不会把 `src/用户身份.rs` 变成巨大段子仓。  

推荐数据形状：

```json
{
  "version": 1,
  "combo_themes": [
    {
      "key": "cyber_abstract",
      "adjectives": ["加载失败的", "量子纠缠的"],
      "nouns": ["恋爱脑", "牛马"]
    }
  ],
  "phrase_themes": [
    {
      "key": "meme_phrase",
      "phrases": ["龙卷风摧毁停车场", "乌鸦坐飞机"]
    }
  ]
}
```

## 7. 随机策略

推荐第一版使用固定权重：

- `combo`: `85%`
- `phrase`: `15%`

理由：

1. `combo` 才是 `names` 轮子的主战场，数量空间大。  
2. `phrase` 更有味道但重复率更高，权重不能太大。  
3. 固定权重足够清楚，不需要现在引入可配置权重系统。  

如果以后要更细，可以在数据文件里给每个主题增加 `weight`，但当前不做。

## 8. 生成与校验

生成链：

1. `随机分配资料投影()` 仍是唯一入口。  
2. 先抽 `combo` 或 `phrase`。  
3. `combo` 选择一个主题后，用 `names::Generator` 从该主题的 `adjectives + nouns` 生成短花名。  
4. `phrase` 选择一个主题后，直接抽一条完整梗句。  
5. 最终只返回 `theme_key + display_alias`。  

校验链：

1. 启动时加载词库。  
2. 断言总空间 `>= 10000`。  
3. 断言每个 `combo` 主题都有足够词条。  
4. 断言 `theme_key` 不重复。  
5. 断言空字符串和全空白词条不存在。  
6. 断言生成结果不会为空。  

这些校验是为了防止词库扩容后悄悄退回 `64` 个组合。

## 9. 非目标

1. 不做房间内花名唯一性。  
2. 不做用户手动选主题。  
3. 不做运营后台编辑词库。  
4. 不做动态热更新词库。  
5. 不做第二套私有昵称组合算法。  
6. 不把完整梗句强行拆成 adjective/noun。  

## 10. 完成定义

做到下面这些，才算第一版花名扩容完成：

1. 总花名空间至少 `10000`。  
2. `names` 仍然负责短组合生成。  
3. 完整梗句池可以直接产出花名。  
4. `src/用户身份.rs` 只保留薄适配和领域入口，不再承载大词库。  
5. 主题仍是项目级公共资源，不对前台展示。  
6. 有测试锁住总量下限、空词条、主题唯一性和生成结果非空。  

## 11. 一句话结论

这次不是“多手写一些昵称”，而是把花名体系升级成：

**`names` 负责万级短组合空间，完整梗句池负责中文网络味，词库作为静态业务数据外置，`用户身份` 模块只保留小而专的生成适配。**
