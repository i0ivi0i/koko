# 启动输出统一设计

日期：2026-04-02

## 背景

当前项目的启动体验被拆成了两层语义：

- Rust 主程序掌握后台口令真相、监听地址真相、启动成败真相
- `run.ps1` 又额外维护一套地址推导、管理员口令读取和人话提示

这不是简单的“文案重复”，而是已经出现了双份启动语义源。问题在于：

1. Windows 本地开发和未来 Linux 直接运行二进制时，部署者看到的关键信息不再由同一份逻辑生成
2. 首页地址、`/admin` 地址、当前管理员口令这些部署真相被脚本复制后，长期一定会漂移
3. 未来线上运行形态是 Linux 服务器直接跑打包后的 Rust 程序，不会依赖 `run.ps1`；因此任何只有脚本知道、只有脚本打印的启动信息，本质上都放错了边界

## 目标

把“启动时该告诉部署者的信息”彻底收回 Rust 主程序，让 Rust 成为唯一启动语义源；`run.ps1` 只保留开发期 adapter 职责。

本次只解决启动输出与日志边界，不改后台会话模型，不改 `/admin` 认证协议，不扩其他运维能力。

## 核心原则

### 1. Rust 是唯一启动语义真相源

这次不是“统一两边输出”，而是删除脚本层启动语义，让 Rust 二进制成为唯一允许生成以下信息的地方：

- 首页地址
- 管理入口
- 当前管理员口令
- 首次生成或首次导入管理员口令的一次性提示

原因：

- 线上真正运行的是 Rust 二进制，不是 PowerShell 包装层
- 部署者需要知道的信息，必须在“不存在 `run.ps1`”的前提下依然完整成立
- 启动真相只能有一份；不能为了本地开发便利，在脚本里复制第二套地址、口令和启动成功语义

### 2. 启动横幅与技术日志分层，但都由 Rust 输出

需要明确区分两类输出：

- 面向人的启动横幅
- 面向排障的技术日志

启动横幅继续由 Rust 使用普通 `println!` 输出，承担“部署者第一眼需要看到的人话提示”：

- 首页地址
- 管理入口
- 当前管理员口令
- 首次生成 / 首次导入 notice

技术日志继续由 Rust 原生日志系统输出，用于未来 Linux 服务器上的排障与修复，包括但不限于：

- 数据库连接失败
- session store 迁移失败
- listener bind 失败
- HTTP / realtime 运行时 warning 与 error

两者职责不同，不能互相替代：

- 启动横幅不是技术日志，不负责承载调试细节
- `tracing` 日志不是部署说明，不应该替代访问地址、管理入口、管理员口令这类人话提示

因此本次设计是“双轨但单源”：

- 面向人的启动横幅由 Rust 输出
- 面向排障的技术日志也由 Rust 输出
- 两类输出都不再由 `run.ps1` 复制一份

### 3. `run.ps1` 退回薄启动器

`run.ps1` 继续负责：

- 准备数据库
- 执行前端 bundle
- 设置环境变量
- 启动 Rust 二进制
- 可选自动打开浏览器

`run.ps1` 不再负责：

- 解析配置文件并打印管理员口令
- 推导首页地址和 `/admin` 地址并生成部署提示
- 复制 Rust 已经知道的启动横幅
- 在 `-DryRun` 中伪造服务已成功启动后的地址、口令与管理入口提示

PowerShell 终端中最终看到的首页地址、管理入口、当前管理员口令，必须直接来自 Rust 标准输出。

技术日志与启动横幅的落盘边界也要分开：

- Rust 的技术日志可以继续进入长期日志文件
- 启动横幅默认只去终端，不进入长期技术日志文件，因为其中包含管理员口令
- 如果调试期确实需要保留一份完整启动转录，也必须显式区分为“启动转录”而不是技术日志，且不能成为默认长期保留行为

不允许：

- 脚本吞掉 Rust stdout/stderr 后自己手工重播核心启动横幅
- 脚本自己拼一套伪日志或伪启动说明
- 把包含管理员口令的启动横幅默认并入长期技术日志文件

同时，`run.ps1` 中必须补上克制但明确的中文注释，说明以下边界：

- 这个脚本只是 Windows 开发期 adapter，不是部署真相源
- 启动地址、管理入口、管理员口令必须以 Rust 输出为准
- 不允许在脚本层重复计算和打印这些语义，避免 Windows 开发与 Linux 部署出现双份真相

### 4. 管理员口令真相保持不变

后台口令真相仍然保持在 `config/koko.toml`：

- 文件存在：直接读取
- 文件不存在：首次启动自动创建目录、生成口令并写入文件
- 若首次启动时存在 `KOKO_ADMIN_TOKEN`：只做一次性导入，写入文件后由文件接管

本次不改变这条真相链，只把“如何把真相告诉部署者”收回 Rust。

## 模块职责

### Rust `support` 层

启动横幅相关的稳定事实和派生规则，应优先收敛在 Rust 侧的 support 边界，而不是继续堆进 `main` 或留在 `run.ps1`。

`support` 应承担：

- `bind_addr` 的对外访问地址派生
- 管理入口 URL 派生
- 当前管理员口令与一次性 notice
- 面向部署者的启动横幅内容组装

### Rust `main` 入口

`main` 只负责启动编排，不再长期承载横幅拼装细节。它的职责应保持为：

- load config
- init tracing
- connect database
- migrate session store
- build router
- bind listener
- 在服务已具备接受请求条件后，触发一次启动横幅输出
- 进入 `axum::serve`

### `run.ps1`

`run.ps1` 只保留开发期外壳动作，不拥有部署语义。若保留自动打开浏览器能力，唯一允许机制是：脚本只从 Rust 已经打印到 stdout 的首条“首页地址”人话行中解析 URL，并据此调用浏览器；如果拿不到这条 Rust 输出或解析失败，就直接禁用 auto-open。脚本不得根据 `bind_addr`、配置文件、环境变量或任何 PowerShell 自己的地址推导规则去猜测 URL。该值只允许作为脚本内部启动动作使用，不允许再被脚本提升为部署提示文案。

Rust 侧新增或重构的启动横幅、地址派生与 notice 代码，也应补上克制但有价值的中文注释，重点解释边界、来源与 why，避免真正的语义核心迁回 Rust 后又变成只能靠猜的隐式规则。

## 启动行为

### Rust 二进制直接启动

无论在 Windows 还是 Linux，只要 Rust 二进制成功启动，都应打印统一启动横幅，例如：

```text
==> 首页地址: http://127.0.0.1:8080/
==> 管理入口: http://127.0.0.1:8080/admin
==> 当前管理员口令: admin-xxxxxxxx
```

如果本次是首次生成配置文件或首次从 `KOKO_ADMIN_TOKEN` 导入口令，再额外打印一次性提示，例如：

```text
==> 本次已写入 config/koko.toml，请立即备份管理员口令
```

地址派生规则只允许保留一份，并且必须在 Rust 中实现：

- 若监听地址是 `0.0.0.0:<port>` 或空 host：
  - Rust 打印本机地址 `http://127.0.0.1:<port>/`
  - Rust 额外打印所有可用局域网 IPv4 地址
- 若监听地址是 IPv6 unspecified（例如 `:::<port>`）：
  - Rust 首个首页地址固定打印为 `http://[::1]:<port>/`
  - Rust 不能把 `::` 直接当作最终用户访问地址
  - 若存在符合规则的局域网 IPv4 地址，则继续按既定顺序追加输出
- 若监听地址是明确 hostname / IPv4 / IPv6：
  - Rust 按该 host 直接生成首页地址与管理入口

Windows 的 `run.ps1` 与未来 Linux 直接运行二进制，都必须消费同一套 Rust 规则，而不是各算一套。

局域网地址列表的过滤与排序规则也必须提前写死，避免不同机器和不同平台上输出漂移。完整规则为：

- 只从状态为 Up 的接口收集候选地址
- 排除接口类型为 loopback 或 tunnel 的接口
- 只保留 IPv4 地址
- 排除 `127.0.0.1/8`
- 排除 `169.254.0.0/16` 这类 link-local IPv4
- 排除接口显示名或系统名中包含 `docker`、`container`、`veth`、`hyper-v`、`vethernet`、`wsl`、`vmware`、`virtualbox`、`tailscale`、`zerotier` 的候选地址
- 地址去重后按字符串升序稳定输出，保证测试与终端输出可预测
- 除上述规则外，不再追加任何平台特定启发式

### 启动横幅触发时机

Rust 只能在以下条件全部成功后打印启动横幅：

- 数据库连接成功
- 后台 session store 迁移成功
- HTTP listener bind 成功

也就是：只有服务已经具备接受请求的条件后，才允许打印首页地址、管理入口、当前管理员口令和一次性 notice。

这也意味着：启动横幅不能在配置刚读完时就抢先输出，更不能在脚本的 dry-run 或准备阶段被伪造。

### `run.ps1` 启动

`run.ps1` 负责把服务启动起来，并让 Rust 自己输出启动横幅与技术日志。

如果脚本需要在服务真正 ready 前提示一些步骤，只允许保留准备阶段信息，例如：

- 正在准备数据库
- 正在构建前端 / 后端
- 正在启动服务

真正的“访问哪里、后台在哪里、口令是多少”，统一由 Rust 输出。

`run.ps1 -DryRun` 只保留准备步骤预演：

- 不伪造 Rust 启动成功后的首页地址
- 不伪造管理入口
- 不自己打印管理员口令
- 不复述一次性 notice

`run.ps1` 的中文边界注释至少应落在以下位置：

- 脚本入口职责说明
- stdout/stderr 直通或转录处理处
- `-DryRun` 分支
- auto-open 分支

## 验证

最小验证应覆盖：

1. Rust 启动横幅 helper / builder：
   - 首页地址
   - 管理入口
   - 当前管理员口令
   - 一次性 notice
2. 地址派生规则：
   - `0.0.0.0`
   - IPv6 unspecified
   - 显式 hostname / IPv4 / IPv6
   - 局域网地址列表生成
3. 首次生成配置文件时：
   - 会打印当前管理员口令
   - 会打印“首次生成并写入配置文件”的一次性提示
4. 首次从 `KOKO_ADMIN_TOKEN` 导入时：
   - 会打印当前管理员口令
   - 会打印“已一次性导入配置文件”的一次性提示
5. 非首次启动时：
   - 仍会打印当前管理员口令
   - 不再打印“首次生成 / 首次导入”的一次性提示
6. `run.ps1 -DryRun`：
   - 只保留准备步骤预演
   - 不伪造 Rust 启动横幅
   - 不自己打印后台口令
   - 不自己打印首页地址与管理入口
7. `run.ps1` 实启动链：
   - PowerShell 终端能直接看到 Rust 打印的首页地址、管理入口和当前管理员口令
   - 如保留日志文件，则验证管理员口令所在启动横幅不会默认进入长期技术日志文件
8. 技术日志链路：
   - Rust tracing 在启动失败与运行期异常时仍能输出可用于排障的日志
9. 负向回归验证：
   - `run.ps1` 自身在正常启动与 `-DryRun` 下都不输出首页地址、管理入口、管理员口令和一次性 notice
   - 这些内容只能来自 Rust 子进程输出
10. 中文注释验收：
   - `run.ps1` 在脚本入口、stdout/stderr 处理、`-DryRun`、auto-open 分支均有明确中文边界注释
   - Rust 侧新增的启动语义代码也有解释边界与 why 的中文注释
11. 现有后台配置文件首次生成 / 导入行为不回归

## 测试迁移要求

现有部分测试已经绑定到 `run.ps1` 持有启动语义的旧实现，后续实现时应主动迁移，不能为了保留这些测试而继续维持脚本层真相。

迁移方向应为：

- 把地址派生、启动横幅、notice 迁到 Rust 侧单测
- 把 `run.ps1` 测试收缩为“准备步骤预演”和“直通 Rust 输出”的边界验证
- 增加负向测试，证明脚本自身不会再打印首页地址、管理入口、管理员口令和一次性 notice
- 删除对 PowerShell 内部实现细节的耦合断言，例如重复调用某个脚本 helper、从脚本直接读取配置并打印口令等

## 风险与边界

- 本次不改变后台口令真相位置，因此不会影响现有 `/admin` 登录逻辑
- 本次不改变 `run.ps1` 的数据库 / 构建 / 启动职责，只删除其部署语义职责
- 本次不试图把所有输出都塞进一种机制；启动横幅与技术日志会并存，但都由 Rust 负责
- 本次不引入额外跨进程协议，不为了开发期脚本再设计一套结构化启动事件通道
