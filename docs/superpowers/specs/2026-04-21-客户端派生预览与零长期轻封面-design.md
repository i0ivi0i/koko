# 客户端派生预览与零长期轻封面设计

日期：2026-04-21  
状态：Draft  
适用范围：`koko` 群聊视频消息时间线预览、自动播放、全屏查看器、客户端预制、`Video.js v10` 唯一播放器壳、`WebTorrent` 长期协作分发。  

---

## 0. 一句话裁决

`canonical video` 必须同时成为：

1. 唯一播放真相源；
2. 唯一预览真相源；
3. 唯一 `WebTorrent` payload；
4. 唯一长期群友互助分发源。

对新单文件视频链路来说：

**同一个 video 文件本身就是预览来源唯一真相源。**

后端不再为新视频长期保存独立封面图片；群友只要在群内滑到过该视频，就进入激进补齐与做种链路，即使之后滑走，也继续补完整文件，帮助后续群友高速加速。

---

## 1. 目标

本设计要同时达到四个结果：

1. 用户第一眼看到的是视频自己，不是后端单独托管的第二张图；
2. 时间线自动播放与查看器播放共享同一个 `canonical video`，不再分裂成“预览系统”和“播放系统”；
3. 群友在时间线里滑动、短暂停留、自动播放时，不是白看，而是在顺手为后续群友补块、预热、做种；
4. 为了秒开和丝滑，不允许系统偷改成低码率、低分辨率、模糊版视频。

---

## 2. 核心原则

### 2.1 单文件唯一真相

新视频链路只能有一份正式媒体资产：

- `canonical video`

它同时服务于：

- 时间线预览；
- 时间线自动播放；
- 全屏查看器播放；
- `WebTorrent` 分发；
- 浏览器本地缓存；
- 群友后续做种。

不允许再为新视频长出第二个长期 `preview still / thumbnail / poster asset`。

### 2.2 质量优先，不拿糊画质换启动速度

默认硬规则：

1. 不降分辨率；
2. 不降帧率；
3. 不降码率；
4. 不重编码成更糊版本；
5. 不为了“看起来更丝滑”偷偷压一版低清视频发出去。

正确做法只能是：

1. 能直通就直通；
2. 能 `remux / faststart` 就只改容器，不改画面与音频；
3. 秒开靠 `faststart`、预览派生、关键分片优先、预览缓存和 swarm 预热解决；
4. 真不兼容时，明确失败，不拿低清版伪装成功。

### 2.3 激进协同加速

用户已明确选择激进模式：

1. 不区分桌面/移动端；
2. 不区分网络环境；
3. 不区分是否充电；
4. 只要滑到过视频，就继续后台补完整文件；
5. 滑出视口后也不停止补齐；
6. 补齐完成后尽量继续做种。

这意味着本产品明确优先：

**群聊内的整体加速收益 > 单次观看时的保守省流策略。**

---

## 3. 运行时主链

### 3.1 时间线预览

时间线预览必须遵守：

1. 预览来自同一个 `canonical video`；
2. 优先使用本地预览缓存；
3. 缓存未命中时，从同一视频文件早期关键字节或首个可解码帧派生；
4. 预览不能依赖后端长期静态封面；
5. 没有任何 `source bytes` 时，只允许稳定占位。

### 3.2 时间线自动播放

自动播放必须遵守：

1. 仍然只消费同一个 `canonical video`；
2. 走秒开优先策略，一旦拿到可播首段就尽快起播；
3. 自动播放不是另一条媒体链，只是同一文件的另一种呈现状态；
4. 自动播放开始后，继续推进整文件补齐与 swarm 预热。

### 3.3 查看器播放

查看器必须遵守：

1. 查看器与时间线共用同一个内容哈希和同一个视频文件；
2. 不允许查看器另外切回原始直读链；
3. 不允许查看器为了“更稳”偷偷吃第二份后端封面资产。

### 3.4 滑到即补齐

只要用户在时间线里滑到过某个视频，就触发：

1. 预览关键字节优先；
2. 秒开首播关键片段优先；
3. 随后继续整文件补齐；
4. 补齐完成后继续做种。

该状态一旦进入，不因视频滑出视口而自动中止。

---

## 4. Owner 设计

### 4.1 真相 owner

唯一媒体真相 owner 是 `canonical video` 本身。  
不是后端封面图，不是时间线 UI，不是 autoplay 状态机。

### 4.2 调度 owner

虽然允许多个视频并行补块，但必须存在一个前端统一调度 owner，用于限制同时重度解码/自动播放的数量。

原因不是省流，而是避免：

1. 一屏多个视频同时真播；
2. GPU/解码器被抢占；
3. 页面滚动掉帧；
4. “为了积极加速，结果用户觉得卡卡的”。

因此系统必须区分两类行为：

1. **补块/补齐/做种**：可以更激进；
2. **实际自动播放解码**：必须由统一 owner 节制。

### 4.3 预览 owner

预览 owner 必须是媒体运行时，而不是壳层。

也就是说：

1. 时间线 UI 只消费“当前预览状态”；
2. 预览缓存、首帧派生、早期关键字节读取，都在媒体运行时里完成；
3. 不允许再出现“必须等 autoplay owner 才有预览”的倒挂关系。

---

## 5. 后端职责

后端对新单文件视频只保留：

1. 存储唯一 `canonical video`；
2. 写入 `content_hash / swarm_id / torrent metadata`；
3. 在 `24 小时` 内做 web seed / 初始冷启动补块；
4. 到期后删除服务器冷备。

后端对新单文件视频明确不做：

1. 长期保存封面图；
2. 写 `thumbnail_storage_key` 作为新主链正式字段；
3. 长期承诺 `preview_asset.still_url`；
4. 再生成第二份静态 poster 资产。

历史旧视频可以继续兼容读取 legacy still，但那只是兼容债务，不是新主链的一部分。

---

## 6. 体验语义

用户看到的产品语义应当是：

1. 视频天然自带预览；
2. 点开就是同一个视频继续播放；
3. 别人滑到过的视频，后面的人会更快；
4. 清晰度优先，不会被系统偷偷压糊。

不应该再出现这些体验：

1. 黑框占位很久，像要等 autoplay 才突然有内容；
2. 时间线看到的是一套，查看器播的是另一套；
3. 为了启动快而变糊；
4. 群友明明已经刷到过视频，却没对后续 swarm 带来任何加速收益。

---

## 7. 否决项

以下方案明确否决：

### 7.1 否决：后端继续长期托管新视频封面图

原因：

1. 再次制造第二真相；
2. 增加 GC 与生命周期复杂度；
3. 让预览继续依赖后端兜底。

### 7.2 否决：为了顺滑默认压低码率

原因：

1. 容易误判；
2. 直接损伤用户原画质；
3. 把“播放链优化问题”错做成“媒体质量牺牲问题”。

### 7.3 否决：视频滑出视口后立刻停止补齐

原因：

1. 与激进协同加速目标冲突；
2. 群友刷过视频却没有形成后续加速收益；
3. 群聊 swarm 难以真正热起来。

### 7.4 否决：多个视频同时无限制解码自动播

原因：

1. 容易让页面卡顿；
2. 会让“激进补齐”错误演化成“激进掉帧”；
3. 这不叫更快，只是乱。

---

## 8. 验证门禁

实现前后必须证明以下事实：

1. 新单文件视频 `complete` 后，后端不再长期写入 `thumbnail_storage_key`；
2. 新单文件视频协议面不再默认承诺 `preview_asset.still_url`；
3. 时间线预览与查看器播放使用同一个 `canonical video`；
4. 时间线预览不依赖 autoplay owner 才存在；
5. 用户滑到某视频后，即使滑走，后台仍继续补齐整文件；
6. 整文件补齐完成后，客户端进入做种态；
7. 自动播放秒开策略不能以降低画质为代价；
8. 自动播放与预览切换过程中不能出现黑闪、白闪、节点重建闪烁；
9. 多视频场景下，补块可激进，但解码自动播必须受统一调度 owner 控制；
10. `chrome-devtools-cli` 真实烟测必须覆盖：
   - fresh user 首次进房第一眼；
   - 自动播放首播速度；
   - 滚动经过视频后继续后台补齐；
   - 滑走视频后 swarm 仍继续升温；
   - 后续用户进房时同视频加载明显更快。

---

## 9. 最终裁决

`koko` 的新视频主链必须收敛成以下形态：

1. **同一个 `canonical video` 文件，就是预览、播放、分发的唯一真相源。**
2. **群友只要滑到过该视频，就继续后台补完整文件并做种，即使之后滑走也不停。**
3. **自动播放采取秒开优先，但不允许通过降低码率、降低分辨率、降低帧率来伪造顺滑。**
4. **后端不再为新单文件视频长期保存独立封面图。**
5. **系统允许激进补块，但不允许无 owner 的乱解码、乱自动播。**

这条设计的本质不是“更会耍小聪明”，而是更克制：

**只保留一个视频文件真相，让预览、自动播放和协同加速都围绕它发生。**
