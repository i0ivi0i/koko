## 0. 这份文档为什么存在

上一版已经看清一件事：

**后端长期保存 preview still 不够优雅。**

因为它依然会让服务器：

1. 长期托管一份非播放真相对象；
2. 维护 preview 生命周期和 GC；
3. 继续承担本该前移给客户端和群友的展示职责。

但现在进一步看，光把 preview 从“后端长期小图”改成“客户端临时抽首帧”，还不够。

因为这仍然可能留下第二层不优雅：

1. 预览依赖 autoplay owner 才出现；
2. 时间线首屏要等播放链热起来；
3. 预览和视频在体验上仍然像两套系统，而不是一个视频文件的两种呈现。

这份文档要把这件事再收紧一次：

**视频和预览在体验上应当是一体的；在资产上只能是一份 canonical 文件；预览不再是第二长期对象，而是同文件内的 preview hint 与客户端运行时派生能力。**

也就是说：

1. 服务器不长期保存 preview 小图；
2. canonical video 仍是唯一媒体真相；
3. canonical 文件本身必须尽量 preview-friendly；
4. 客户端和群友基于同一份文件，秒级拿到预览；
5. 没有 source bytes 时，系统只能诚实占位。

## 1. 问题本质

### 1.1 用户直觉为什么会觉得“视频和预览天然一体”

用户在 Windows 文件夹里看到视频缩略图，会自然觉得：

**视频本来就应该自带预览。**

这个直觉在体验层是对的，但在实现层通常不是“视频自动长出预览”，而是：

1. 本地文件可随机访问；
2. 系统有 thumbnail extractor；
3. 系统有 thumbnail cache；
4. 没命中缓存时再按需抽取。

所以真正优雅的目标不是“神奇地不用做任何工作”，而是：

**让同一份 canonical 文件自己足够适合被快速解析、快速抽帧、快速缓存。**

### 1.2 旧思路为什么不够优雅

“后端长期留一张 preview still”有三个问题：

1. **服务器仍要长期托管展示派生**  
   对象存储里仍然会有一类非播放真相文件。

2. **生命周期更复杂**  
   canonical 视频按 `24 小时` TTL 退场，preview still 却长期存活，系统还得继续处理“何时删 preview”。

3. **预览能力没有真正前移**  
   名义上是客户端预制，实际上展示首屏仍靠服务器长期兜着。

### 1.3 只靠 autoplay 出首帧为什么也不够优雅

“不存小图，等 autoplay 自己把首帧跑出来”同样不够优雅：

1. 预览重新绑定到播放链；
2. 新用户首屏体验不稳定；
3. 非 owner 视频继续占位，导致“进房后好像要等自动播才有预览”；
4. 时间线和查看器都容易重新长出第二套逻辑。

### 1.4 新目标是什么

更优雅的目标是：

1. **canonical video 是唯一媒体资产；**
2. **preview 不再是第二长期对象；**
3. **同一 canonical 文件尽量自带 preview hint；**
4. **客户端优先按需拿最少字节、本地生成、本地缓存；**
5. **在线群友和 `24 小时` 内 web seed 只负责把这些关键字节尽快送来。**

换句话说：

**预览不是服务器第二资产，也不是 autoplay 的副产品，而是单文件 canonical 的天然展示能力。**

## 2. 上位裁决

### 2.1 一句话

**canonical video 继续是唯一媒体真相；preview 改为同文件 preview hint + 客户端本地派生缓存能力；后端不长期保存任何独立 preview still。**

### 2.2 真相分层

以后视频附件只保留两层正式真相：

1. **媒体真相**
   - 只有一份 canonical video 文件；
   - 供时间线预览、自动播放、查看器播放、`WebTorrent` 做种和 `24 小时` 内 web seed 使用。

2. **预览运行时真相**
   - 不是服务器对象；
   - 是“客户端是否已从这份 canonical 文件命中 preview hint、派生 preview、并写入本地缓存”的运行时事实。

### 2.3 “零长期轻封面”的严格定义

这里的“零长期轻封面”指的是：

1. **不能有第二个长期 preview 资产对象；**
2. **不能有 `thumbnail_storage_key` / `still_url` 这种独立生命周期；**
3. **允许 preview hint 作为 canonical 文件内部的一部分存在；**
4. **允许客户端从同一文件早期关键字节或早期关键帧派生 preview。**

也就是说：

**可以有同文件内嵌 preview hint，但不能有同文件之外的第二长期 preview 对象。**

## 3. 核心裁决

### 3.1 后端不长期保存独立 preview still

后端以后不再长期保留任何视频 `preview_still` / `thumbnail_storage_key` / `still_url` 之类的静态预览对象。

后端允许做的事只有：

1. 保留 canonical 视频 `24 小时` 冷备窗口；
2. 在窗口内作为 web seed 帮助冷启动；
3. 继续下发 canonical 视频的稳定读取入口、torrent 元信息和 swarm 线索；
4. `24 小时` 后删掉 canonical 视频冷备。

后端不做：

1. 长期存 preview 图；
2. 维护 preview 生命周期；
3. 为时间线额外托管第二类媒体对象。

### 3.2 canonical 文件必须 preview-friendly

上传侧生成 canonical 视频时，必须尽量做到：

1. **容器可渐进解析**
   例如 MP4 使用 `faststart`，把 `moov` 尽量前置。

2. **尽早可出代表帧**
   早期关键帧不能拖得太后，否则时间线首屏仍然要等。

3. **允许同文件携带 preview hint**
   例如容器 metadata / attached image / preview frame 等单文件内信息。

4. **预览和播放共用同一个内容哈希 owner**
   preview hint 不是第二对象，不单独上传，不单独 GC。

所以：

**真正优雅的目标不是“完全不处理预览”，而是把预览能力压进同一份 canonical 文件和同一条客户端主链里。**

### 3.3 客户端预览来源优先级

客户端在时间线和查看器里读取预览时，统一按以下优先级：

1. **本地 preview cache**
2. **canonical 文件内嵌 preview hint**
3. **canonical 文件早期关键字节派生出的代表帧**
4. **已经拿到可解码首帧时，通过 `requestVideoFrameCallback()` 抓取**
5. **仍然没有 source bytes，则稳定占位**

这条优先级意味着：

1. 预览不再先问后端有没有 still；
2. 预览不再依赖 autoplay owner 才存在；
3. 预览也不再要求先进入正式播放再“顺手”拿到。

### 3.4 `WebTorrent` / web seed 只负责送关键字节

`WebTorrent` 不负责 poster 语义。  
它负责的是：

1. 优先把 metadata / preview hint / 早期关键片段送到浏览器；
2. 再继续保证正式播放所需片段尽快到达；
3. 让已经看过视频的群友尽快开始互帮互助。

同理，`24 小时` 内的后端 web seed 也不再承担“托管 preview 图”的职责，而只承担：

**在 swarm 还没热起来时，帮新用户尽快拿到 canonical 文件前部关键字节。**

## 4. 物理边界必须说清楚

### 4.1 没有字节，就没有预览

如果同时满足：

1. `24 小时` 后服务器 canonical 冷备已删；
2. 当前没有任何完整 peer 在线；
3. 当前客户端本地也没有缓存过这个视频；

那浏览器就**不可能**秒级生成预览。

这不是实现失败，而是因为：

**系统此刻没有任何 source bytes。**

### 4.2 “纳秒级预览”不是正确承诺

即便用户设备 CPU / GPU 比后端服务器强很多，也不应该把承诺写成“纳秒级”。

因为真正的冷启动路径里仍然存在：

1. 网络 RTT；
2. byte-range 返回；
3. 容器头解析；
4. 解码队列；
5. compositor / v-sync；
6. 本地缓存写入。

所以正确的产品承诺只能是：

1. **本地热路径接近瞬时；**
2. **有 source bytes 的冷启动做到毫秒到亚秒级；**
3. **没有 source bytes 时只能稳定占位。**

### 4.3 这不是退化，而是真话

比起“嘴上说零第二资产，实际上服务器还在长期存小图”，
这份方案虽然更克制，却也更诚实：

**系统只有在真的还有同一份 canonical 文件数据源时，才能继续秒级给出预览。**

## 5. 运行时主链

### 5.1 发送端阶段

发送端在本地预制视频 canonical 时，同时完成：

1. 生成 preview-friendly canonical；
2. 尽量前置可解析 metadata；
3. 尽量保证早期关键帧；
4. 需要时把 preview hint 写进同一文件；
5. 上传和做种的仍然只有这一份 canonical 文件。

### 5.2 接收端首屏阶段

新用户或本地未命中缓存时：

1. 房间时间线先只拿到 canonical 文件定位信息；
2. 媒体 runtime 判断本地是否已有 preview cache；
3. 如果没有，则优先拿文件头和最少关键字节；
4. 若命中同文件 preview hint，则立刻显示；
5. 若没有 preview hint，则从最早可解码关键帧派生 preview；
6. 派生成功后写入本地缓存并立刻投影到时间线。

### 5.3 时间线阶段

时间线以后只允许五种状态：

1. **已有本地 preview cache**
   直接显示 preview。

2. **已命中同文件 preview hint**
   直接显示 preview。

3. **正在派生 preview**
   显示稳定占位，但不直接偷开正式播放。

4. **确认当前没有 source bytes**
   显示“暂不可预览”的稳定占位，不假装马上会有首帧。

5. **已进入正式播放**
   从 preview 平滑切到 `Video.js v10` 的播放态。

这里特别强调：

**时间线预览不再依赖 autoplay owner，也不依赖 `playback.mode === "swarm"` 才能先显示。**

### 5.4 自动播放阶段

自动播放只负责：

1. 在 preview 已显示或占位已稳定后，接管正式播放；
2. 从 preview 平滑切换到 `Video.js v10` 的正式播放；
3. 推动更多 canonical 字节进入本地；
4. 让当前用户尽快变成有能力继续做种和继续派生 preview 的完整 peer。

因此自动播放的职责是：

**加热 canonical 文件与 swarm，**
而不是“顺手替时间线补一张 preview”。

### 5.5 全屏查看器阶段

查看器同样遵守：

1. 如果已有 preview cache 或同文件 preview hint，就先显示 preview；
2. 然后统一交给 `Video.js v10` 做正式播放；
3. 切换过程中保持无闪烁；
4. 不再向后端额外请求长期 preview 资源。

## 6. 技术裁决

### 6.1 `Mediabunny` 是首选预览主轮子

客户端预览生成主轮子优先用 `Mediabunny`。

理由：

1. 官方已有 thumbnail generation 示例；
2. 支持 `UrlSource` / `ReadableStreamSource` 等按需读取；
3. 支持 `CanvasSink.getCanvas(timestamp)` 直接取指定时间帧；
4. 支持读取和写入 metadata / attached images；
5. 能和 `WebCodecs` 协同，而不是重复下载浏览器本来就有的 codec。

预期职责：

1. 读取 canonical 文件头和关键字节；
2. 判断是否带有 preview hint；
3. 选取代表帧；
4. 输出轻量 bitmap / blob；
5. 交给本地缓存层。

### 6.2 `MP4Box.js` 是可选容器头解析器

如果实践里需要更细的 MP4 头解析和渐进式规划，可以引入 `MP4Box.js` 作为补充：

1. 它支持 progressive parsing；
2. `moov` 一旦解析出来就能拿到结构信息；
3. 适合作为 byte-range 规划器和 preview hint 定位器；
4. 不取代播放器，只服务于“先看什么字节”这件事。

它不是必须主角，但它很适合作为：

**同文件 preview-friendly packaging 的辅助分析轮子。**

### 6.3 `requestVideoFrameCallback()` 作为轻量补充

当浏览器已经拿到可解码首帧时，可以使用 `requestVideoFrameCallback()` 作为轻量补充路径：

1. 等首帧真正送到 compositor；
2. 精确抓取当前帧；
3. 输出本地 preview。

这条路适合：

1. 已经进入预备播放；
2. 浏览器对当前编码支持良好；
3. 不需要完整自定义解码链。

但它仍然只是：

**同文件 preview 主链的补充实现，不是产品真相 owner。**

### 6.4 `MediaCapabilities` / `WebCodecs` 必须先探测

预览派生不是盲跑：

1. 先用 `MediaCapabilities.decodingInfo()` 探测当前设备对目标视频解码是否 `supported` / `smooth` / `powerEfficient`；
2. 必要时再用 `VideoDecoder.isConfigSupported()` 做更细粒度判断；
3. 设备弱、格式难、浏览器不支持时，不强行走重型本地派生。

### 6.5 `WebTorrent` 必须显式做预览分片优先级

以后 `WebTorrent` 在视频时间线冷启动场景里要做的不只是“等播放器来 `streamTo(video)`”，而是：

1. 优先选择 metadata / preview hint 所在 piece；
2. 优先选择最早关键帧所在 piece；
3. 再继续推进正式播放与完整文件获取。

也就是：

**预览阶段优先拉“够显示 preview 的字节”，播放阶段优先拉“够稳定播放的字节”。**

### 6.6 `OPFS` 是首选 preview cache 存储

preview cache 首选浏览器 `OPFS`：

1. 支持低层字节访问；
2. 适合 worker 内快速读写；
3. 比面向用户文件系统更轻；
4. 可配合 `navigator.storage.persist()` 提高长期保留概率。

### 6.7 Rust 只做薄而重的支路，不替代浏览器 codec

用户设备算力比后端强很多，这一点应当利用，但方式要克制：

1. Rust / WASM 可以用于容器头解析、byte-range 规划、piece planner、preview cache 索引；
2. 不应该拿 Rust / WASM 重新带一套大而全的软件解码器去替代浏览器已有 codec；
3. 主解码能力仍优先交给 `WebCodecs` 和浏览器原生媒体栈。

也就是说：

**Rust 应该成为高性能薄适配层，而不是新的重型媒体主链。**

## 7. 本地缓存裁决

### 7.1 preview cache owner 是本地缓存层

预览缓存 owner 必须是前端本地缓存层，而不是后端数据库。

推荐缓存键：

- `content_hash`
- 或 `attachment_id + content_hash`

缓存对象至少包括：

1. preview bitmap / blob；
2. preview hint 解析结果；
3. 少量已取回的文件头 / 关键片段索引；
4. 最近一次派生时间和大小。

### 7.2 缓存失效语义

preview cache 失效只由这些事件触发：

1. 本地缓存被浏览器清理；
2. 内容哈希变化；
3. 用户主动清缓存；
4. 本地存储预算不足，被 runtime 主动回收。

它不再和服务器 `24 小时` TTL 绑定。

### 7.3 持久化是加分项，不是承诺

浏览器可以申请 persistent storage，但不能把“本地缓存一定永久存在”当成产品承诺。

所以这条能力必须写成：

1. 有本地缓存时，预览接近瞬时；
2. 本地缓存被驱逐时，重新走同文件字节派生；
3. 没有 source bytes 时，回到稳定占位。

## 8. 后端职责重写

### 8.1 后端保留

后端继续保留：

1. canonical video `24 小时` 冷备；
2. canonical 视频 metadata 校验；
3. torrent 元信息；
4. web seed / 初始种子；
5. TTL 删除 canonical；
6. ready 真相、权限真相、定位真相；
7. Range / web seed 能力，保证客户端能按需拿字节。

### 8.2 后端删除

后端从现在开始明确不保留：

1. 长期 preview still；
2. `thumbnail_storage_key` 作为新单文件视频主链的正式组成部分；
3. `preview_asset.still_url` 作为后端长期协议承诺；
4. 任何“为新用户兜底显示预览而长期存在”的小图对象；
5. 任何独立于 canonical 文件之外的第二长期 preview 生命周期。

这才叫真正把服务器从预览职责里撤出去。

## 9. 与旧设计的关系

### 9.1 对 2026-04-20 主链文档的修正

`2026-04-20-客户端预制媒体与WebTorrent单文件主链-design.md` 里关于视频“轻量封面”的理解，要改成：

1. 客户端仍可从 canonical 视频抽代表帧；
2. canonical 文件也可内嵌 preview hint；
3. 但该能力不再表现为后端长期保存的第二对象；
4. 它属于单文件 canonical 设计和客户端本地派生缓存的一部分。

### 9.2 对 2026-04-21 旧稿思路的替代

此前同日旧稿里“后端长期保存轻封面”的裁决，不再是推荐方案。

这份新文档取而代之，成为当前推荐方案。

旧文档可以保留作对照，但其状态应视为：

**Superseded by this spec.**

## 10. 否决的方案

### 10.1 否决：后端长期保存 preview still

否决原因：

1. 服务器仍要长期托管展示派生；
2. 仍会留下一类需要独立 GC 的媒体对象；
3. 没有真正把预览能力前移到客户端。

### 10.2 否决：完全靠 autoplay 自己出首帧

否决原因：

1. 预览是否存在会重新绑定到播放链；
2. 时间线首屏体验不稳定；
3. 容易再次引入闪烁和“触发自动播后才有预览”的 bug。

### 10.3 否决：没有 source bytes 时还承诺秒级预览

否决原因：

1. 这是物理上做不到的；
2. 会逼着系统偷偷复活服务器长期资产；
3. 文档承诺一旦不诚实，后面实现一定重新长歪。

### 10.4 否决：把浏览器变成第二台 ffmpeg 服务器

否决原因：

1. 设备再强，也不该默认把重型全量解码和全量转码当时间线首屏常态；
2. 浏览器本来就有更合适的原生媒体栈和硬件解码能力；
3. 正确的方向是“更薄的按需解析和按需派生”，不是“在前端再造一套服务端流水线”。

## 11. 验证门禁

实现前必须先补失败测试，至少证明这些事实：

1. 新单文件视频 `complete` 后，后端不再写 `thumbnail_storage_key`。
2. 新单文件视频 `complete` 后，协议面不再长期承诺 `preview_asset.still_url`。
3. 新单文件视频上传完成后，服务器只保留 canonical 文件，不额外多一份 preview 资产。
4. canonical 文件满足 preview-friendly packaging：至少能在前部拿到足够 metadata，并能定位 preview hint 或早期关键帧。
5. 新用户以全新隔离上下文进房首屏时，只要存在 web seed / swarm / 本地缓存 source bytes，**无需等待 autoplay owner** 也能在秒级内显示 preview。
6. 如果 canonical 文件带有同文件 preview hint，则首屏优先使用它，而不是等正式播放链热起来。
7. 如果没有内嵌 preview hint，但已有早期关键字节，则客户端能从同一文件派生 preview。
8. 新用户进房时，如果没有任何 source bytes，只显示稳定占位，不偷走 original 直读链。
9. 时间线 preview 不再依赖 autoplay owner 才存在。
10. 自动播放从 preview 切到正式播放时无闪烁。
11. 全屏查看器从 preview 切到正式播放时无闪烁。
12. `WebTorrent` 选择策略能优先拉取 metadata / preview hint / 早期关键片段，而不是必须先拉完整文件。
13. 已拿到完整文件的群友客户端能继续本地复用 preview cache，并继续做种。
14. `24 小时` 后 canonical 冷备被删，后端对象存储里不再保留视频 preview 垃圾。
15. `chrome-devtools-cli` 真实烟测必须覆盖：
    - 发送端选择本地 MP4 后的 draft preview；
    - sender 发出后自己的时间线首屏；
    - fresh user 首次进房首屏第一眼；
    - fresh user 等待数秒后的状态；
    - fresh user 滚动后非 owner 视频仍可独立存在 preview，不再只靠 autoplay owner。

## 12. 官方依据

- [Video.js Poster](https://videojs.org/docs/framework/react/reference/poster)：官方把 poster 明确定义为播放前显示内容，说明预览不应混进播放 owner 语义里。
- [MDN HTMLVideoElement.poster](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/poster)：浏览器原生也把 poster 定义为“没有视频数据可用时显示的图片”。
- [Mediabunny Thumbnail generation example](https://mediabunny.dev/examples/thumbnail-generation/)：官方明确支持在浏览器内从媒体文件提取视频缩略图。
- [Mediabunny 首页](https://mediabunny.dev/)：官方强调“Load only what you need”，并支持从远程 URL、文件、流中按需读取媒体数据。
- [Mediabunny CanvasSink](https://mediabunny.dev/api/CanvasSink)：可直接按时间戳获得视频帧 canvas，适合作为代表帧抽取主链。
- [Mediabunny MetadataTags](https://mediabunny.dev/api/MetadataTags)：官方支持 metadata 中的 `images`，包括 cover art、artwork、preview frames，适合作为同文件 preview hint 载体。
- [Mediabunny ReadableStreamSource](https://mediabunny.dev/api/ReadableStreamSource)：说明可对增量流输入进行顺序读取，并跟踪读取范围。
- [Mediabunny PacketRetrievalOptions](https://mediabunny.dev/api/PacketRetrievalOptions)：支持只取 packet metadata，有助于先规划关键帧而不是盲目全量拉取。
- [MP4Box.js](https://github.com/gpac/mp4box.js)：官方 README 说明支持 progressive parsing，`moov` 解析出来后即可获得结构信息。
- [FFmpeg Formats: faststart](https://ffmpeg.org/ffmpeg-formats.html)：官方明确 `+faststart` 可把索引移到文件开头，利于 progressive playback。
- [WebTorrent Docs](https://webtorrent.io/docs)：官方提供 `select()`、`critical()`、分片优先级和浏览器 streaming 能力，但没有把 preview 当内建语义。
- [MDN requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)：说明浏览器可以在视频帧真正送到 compositor 时高效抓帧。
- [MDN MediaCapabilities.decodingInfo](https://developer.mozilla.org/en-US/docs/Web/API/MediaCapabilities/decodingInfo)：说明可先判断目标媒体配置是否 `supported` / `smooth` / `powerEfficient`，且支持在 Web Worker 中使用。
- [MDN VideoDecoder.isConfigSupported](https://developer.mozilla.org/en-US/docs/Web/API/VideoDecoder/isConfigSupported_static)：说明可用 `WebCodecs` 做更细粒度解码能力探测，但并非所有浏览器都已 Baseline。
- [MDN WebCodecs API](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API)：官方明确它的价值是直接使用浏览器已有 codec，避免重复下载软件 codec。
- [MDN OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)：说明 `OPFS` 适合 origin 私有高性能字节读写。
- [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)：说明 `persist()` 与最佳努力存储的边界。
- [Microsoft Thumbnail Handlers](https://learn.microsoft.com/en-us/windows/win32/shell/thumbnail-providers)：官方说明 Windows 先查 thumbnail cache，再调用 extractor。
- [Microsoft Thumbnail Handler Guidelines](https://learn.microsoft.com/en-us/windows/win32/shell/thumbnail-provider-guidelines)：官方建议对昂贵缩略图在保存时就存好 preview，以避免实时生成拖慢文件视图。

## 13. 最终裁决

以后在 `koko` 里，视频预览主链必须改成这样：

1. **canonical video 继续是唯一媒体真相。**
2. **预览不是后端长期资产，而是同一 canonical 文件内的 preview hint 与客户端本地派生缓存能力。**
3. **发送端要把 canonical 文件做成 preview-friendly，而不是把 preview 留给后端补课。**
4. **`24 小时` 内后端 web seed 只负责帮新用户尽快拿到 preview 所需关键字节。**
5. **`24 小时` 后服务器退场，不再长期保留 preview 小图垃圾。**
6. **只要还有 source bytes，客户端和群友就能继续秒级给出 preview。**
7. **没有 source bytes 时，系统只能诚实显示占位，不能偷偷复活第二条 original 直读链。**

这才是对后端最轻、对体验最像“视频天然自带预览”、对真相最诚实的优雅方案 A。
