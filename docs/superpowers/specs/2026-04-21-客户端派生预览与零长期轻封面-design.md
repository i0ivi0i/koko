## 0. 这份文档为什么存在

上一版 `2026-04-21-单文件视频轻封面与预览真相-design.md` 解决了“新用户进房没有预览”的体验问题，但它仍然保留了一条不够优雅的前提：

**后端长期保存一张 preview still。**

这比长期保存视频冷备轻很多，但本质上仍然是：

1. 后端继续托管一份长期展示派生；
2. 生命周期里还要单独考虑 preview 资产的删除；
3. 系统里仍然会留下一类“不是播放真相、但要长期收口”的服务器对象。

这不是最坏方案，但还不够克制。

如果目标是：

1. 后端只承担最小必要职责；
2. 24 小时后服务器尽量不再留下长期媒体派生垃圾；
3. 预览能力尽量由客户端、浏览器缓存与在线群友自己消化；

那就必须把预览再往前推进一步。

所以这份文档给出新的上位裁决：

**视频预览不是后端长期资产，而是客户端基于 canonical 视频实时派生并缓存的展示能力。**

---

## 1. 问题本质

### 1.1 旧思路为什么不够优雅

“后端长期留一张 preview still”虽然比“后端长期留视频冷备”轻得多，但它依然有三个问题：

1. **服务器仍要长期托管展示派生**  
   这意味着后端对象存储里依然要保留一类非播放真相文件。

2. **生命周期更复杂**  
   canonical 视频按 24 小时 TTL 退场，preview still 却长期存活，系统必须继续处理“哪天才删 preview”这条支线。

3. **预览能力没有真正前移**  
   产品嘴上说“客户端预制、后端轻校验”，但预览最终还是靠服务器长期兜着。

这说明：  
上一版解决了“有没有预览”，但没有把“谁才是预览 owner”收口到最薄。

### 1.2 新目标是什么

更优雅的目标不是“后端一张小图都不能有”这种口号，而是：

1. **后端不长期保存 preview 资产**；
2. **预览由客户端从 canonical 视频派生**；
3. **拿到过视频字节的用户端，本地缓存预览并快速复用**；
4. **在线群友和 24 小时内 web seed 共同承担新用户首进房时的预览冷启动**。

换句话说：

**预览能力仍然存在，但它不再是服务器长期对象，而是客户端运行时能力。**

---

## 2. 上位裁决

### 2.1 一句话

**canonical video 继续是唯一媒体真相；preview 改为客户端派生、本地缓存、best-effort 秒级生成，后端不长期保存 preview still。**

### 2.2 真相分层

以后视频附件只保留两层正式真相：

1. **媒体真相**
   - 只有 canonical video 一份；
   - 供自动播放、全屏播放、查看器播放、`WebTorrent` 做种和 24 小时内 web seed 使用。

2. **预览能力真相**
   - 不是服务器对象；
   - 是“客户端是否已为该 canonical video 成功派生并缓存 preview”的本地运行时事实。

这意味着：

1. 预览不再是后端资产模型里的长期对象；
2. 预览也不再是播放链的副产品；
3. 预览是客户端 runtime 对 canonical video 做出的一个轻派生缓存。

---

## 3. 核心裁决

### 3.1 后端不长期保存 preview still

后端以后不再长期保留任何视频 `preview_still` / `thumbnail_storage_key` / `still_url` 之类的静态预览对象。

后端允许做的事只有：

1. 保留 canonical 视频 24 小时冷备窗口；
2. 在窗口内作为 web seed 帮助冷启动；
3. 继续下发 canonical 视频的稳定读取入口、torrent 元信息和 swarm 线索；
4. 24 小时后删掉 canonical 视频冷备。

后端不做：

1. 长期存 preview 图；
2. 维护 preview 生命周期；
3. 为时间线专门托管第二类媒体对象。

### 3.2 预览必须由客户端从 canonical video 派生

任何时间线视频预览，都必须来自同一份 canonical video。

推荐主链：

1. 客户端拿到 canonical video 的最少关键字节；
2. 在浏览器里完成首帧/代表帧提取；
3. 生成一张本地 preview bitmap；
4. 写入本地缓存；
5. 时间线与查看器未播放前统一先显示这张本地 preview。

所以：

- 预览不是服务器分发给客户端的一张图；
- 预览是客户端对 canonical video 做出的派生缓存。

### 3.3 `WebTorrent` 和 web seed 只负责“把生成预览所需字节尽快送来”

`WebTorrent` 不负责 poster 语义。  
它负责的是：

1. 优先把生成预览所需的关键片段送到浏览器；
2. 优先把正式播放所需的关键片段送到播放器；
3. 让已经看过视频的群友尽快开始互帮互助。

同理，24 小时内的后端 web seed 也不再承担“托管 preview 图”的职责，而只承担：

**在 swarm 还没热起来时，帮新用户尽快拿到 canonical 视频前部关键字节。**

---

## 4. 物理边界必须说清楚

这份方案比“服务器长期留小图”更优雅，但它不是魔法。

必须明确三条硬事实：

### 4.1 没有字节，就没有预览

如果出现下面这种情况：

1. 24 小时后服务器 canonical 冷备已删；
2. 当前没有任何完整 peer 在线；
3. 当前客户端本地也没有缓存过这个视频；

那浏览器就**不可能**秒级生成预览。

这不是实现失败，而是因为：

**系统此刻没有任何 source bytes。**

### 4.2 “秒级获得预览”只能是有条件承诺

以后预览能力的承诺必须写成：

1. **有 source bytes 时，秒级生成预览**；
2. **无 source bytes 时，只能显示占位并等待 source 恢复**。

禁止再写成：

1. “任何时候都秒开预览”；
2. “没有 peer 也一定立刻看得到视频预览”；
3. “删光服务器和 peer 后浏览器还能自己变出预览”。

### 4.3 这不是退化，而是真话

比起“偷偷在后端长期留小图，但嘴上说没有第二资产”，
这份方案虽然更克制，却也更诚实：

**系统只有在真的还有数据源时，才能继续秒级派生预览。**

## 5. 运行时主链

### 5.1 预览生成阶段

新用户或本地未命中缓存时：

1. 房间时间线只拿到 canonical video 的媒体定位信息；
2. 媒体 runtime 判断本地是否已有 preview cache；
3. 如果没有，则尝试从：
   - 本地缓存；
   - 24 小时内 web seed；
   - 在线 swarm peer；
   获取生成预览所需的最少关键字节；
4. 一旦足够，就在前端派生 preview；
5. 写入本地缓存并立刻投影到时间线。

### 5.2 时间线阶段

时间线以后只允许三种状态：

1. **已有本地 preview**  
   直接显示 preview。

2. **正在派生 preview**  
   显示稳定占位，但不直接偷开正式播放。

3. **确认当前没有 source bytes**  
   显示“暂不可预览”的稳定占位，不假装自己马上会有首帧。

这里特别强调：

**时间线预览不再依赖 autoplay owner，也不依赖 `playback.mode === "swarm"` 才能先显示。**

### 5.3 自动播放阶段

自动播放只负责：

1. 在 preview 已显示或占位已稳定后，接管正式播放；
2. 从 preview 平滑切换到 `Video.js v10` 的正式播放；
3. 尽快推动更多 canonical 字节进入本地；
4. 让当前用户尽快变成有能力继续做种和继续派生 preview 的完整 peer。

因此自动播放的职责是：

**加热 canonical video 与 swarm，**  
而不是“顺手替时间线补一张 preview”。

### 5.4 全屏查看器阶段

查看器同样遵守：

1. 如果已有本地 preview，就先显示 preview；
2. 然后统一交给 `Video.js v10` 做正式播放；
3. 切换过程中保持无闪烁；
4. 不再向后端额外请求长期 preview 资源。

## 6. 技术裁决

### 6.1 `Mediabunny` 是首选预览派生轮子

客户端预览生成主轮子优先用 `Mediabunny`。

理由：

1. 官方已有 thumbnail generation 示例；
2. 适合从同一份 canonical video 抽帧；
3. 可与 `WebCodecs` 协同；
4. 比把 `<video>` 当截图工具更可控。

预期职责：

1. 读取 canonical video；
2. 选取代表帧；
3. 输出轻量 bitmap / blob；
4. 交给本地缓存层。

### 6.2 `requestVideoFrameCallback()` 作为浏览器内首帧抓取补充

当浏览器直接通过 `<video>` 已经拿到可解码首帧时，可以使用 `requestVideoFrameCallback()` 作为轻量补充路径：

1. 等首帧真正送到 compositor；
2. 精确抓取当前帧；
3. 输出本地 preview。

这条路适合：

1. 已经进入预备播放；
2. 浏览器对当前编码支持良好；
3. 不需要完整转码链。

但它仍然只是：

**客户端派生 preview 的补充实现，不是产品真相 owner。**

### 6.3 `MediaCapabilities` / `WebCodecs` 必须先探测

预览派生不是盲跑：

1. 先用 `MediaCapabilities.decodingInfo()` 探测当前设备对目标视频解码是否 supported / smooth；
2. 必要时再用 `VideoDecoder.isConfigSupported()` 做更细粒度判断；
3. 设备弱、格式难、浏览器不支持时，不强行走重型本地派生。

### 6.4 `WebTorrent` 必须优先拉取预览关键字节

以后 `WebTorrent` 在视频时间线冷启动场景里要做的不只是“等播放器来 streamTo(video)”，而是：

1. 优先选择视频前部关键 piece；
2. 优先保证生成 preview 所需片段尽快到达；
3. 再继续推进正式播放与完整文件获取。

也就是：

**预览阶段优先拉“够生成 preview 的字节”，播放阶段优先拉“够稳定播放的字节”。**

## 7. 本地缓存裁决

### 7.1 preview 是本地缓存对象，不是后端资产

预览缓存 owner 必须是前端本地缓存层，而不是后端数据库。

推荐缓存键：

- `content_hash`
- 或 `attachment_id + content_hash`

这样可以保证：

1. 同一个 canonical 视频不会重复派生多次；
2. 新进房、回房、滚动回来时可以立即复用；
3. 不需要再向服务器请求 preview 图。

### 7.2 缓存失效语义

preview 缓存失效只由这些事件触发：

1. 本地缓存被浏览器清理；
2. 内容哈希变化；
3. 用户主动清缓存；
4. 本地存储预算不足，被 runtime 主动回收。

它不再和服务器 24 小时 TTL 绑定。

### 7.3 持久化是加分项，不是承诺

浏览器可以申请 persistent storage，但不能把“本地缓存一定永久存在”当成产品承诺。

所以这条能力必须写成：

1. 有本地缓存时，预览秒出；
2. 本地缓存被驱逐时，重新走 source bytes 派生；
3. 没有 source bytes 时，回到稳定占位。

---

## 8. 后端职责重写

### 8.1 后端保留

后端继续保留：

1. canonical video 24 小时冷备；
2. canonical 视频 metadata 校验；
3. torrent 元信息；
4. web seed / 初始种子；
5. TTL 删除 canonical；
6. ready 真相、权限真相、定位真相。

### 8.2 后端删除

后端从现在开始明确不保留：

1. 长期 preview still；
2. `thumbnail_storage_key` 作为新单文件视频主链的正式组成部分；
3. `preview_asset.still_url` 作为后端长期协议承诺；
4. 任何“为新用户兜底显示预览而长期存在”的小图对象。

这才叫真正把服务器从预览职责里撤出去。

## 10. 否决的方案

### 10.1 否决：后端长期保存 preview still

否决原因：

1. 服务器仍要长期托管展示派生；
2. 仍会留下一类需要独立 GC 的媒体对象；
3. 没有真正把预览能力前移到客户端。

### 10.2 否决：完全靠 autoplay 自己出首帧

否决原因：

1. 预览是否存在会重新绑定到播放链；
2. 时间线首屏体验不稳定；
3. 容易再次引入闪烁和“触发自动播后才有预览”的 bug。

### 10.3 否决：没有 source bytes 时还承诺秒级预览

否决原因：

1. 这是物理上做不到的；
2. 会逼着系统偷偷复活服务器长期资产；
3. 文档承诺一旦不诚实，后面实现一定重新长歪。

## 11. 验证门禁

实现前必须先补失败测试，至少证明这些事实：

1. 新单文件视频 `complete` 后，后端不再写 `thumbnail_storage_key`；
2. 新单文件视频 `complete` 后，协议面不再长期承诺 `preview_asset.still_url`；
3. 新用户进房时，如果有 web seed / swarm / 本地缓存 source bytes，可在秒级内派生出 preview；
4. 新用户进房时，如果没有任何 source bytes，只显示稳定占位，不偷走 original 直读链；
5. 时间线 preview 不再依赖 autoplay owner 才存在；
6. 自动播放从 preview 切到正式播放时无闪烁；
7. 全屏查看器从 preview 切到正式播放时无闪烁；
8. 24 小时后 canonical 冷备被删，后端对象存储里不再保留视频 preview 垃圾；
9. 已拿到完整文件的群友客户端能继续本地复用 preview cache，并继续做种；
10. `WebTorrent` 选择策略能优先拉取预览关键片段，而不是必须先拉完整文件。

## 12. 官方依据

- [Mediabunny Thumbnail generation example](https://mediabunny.dev/examples/thumbnail-generation/)：官方明确支持在浏览器内从媒体文件提取视频缩略图。
- [Mediabunny 首页](https://mediabunny.dev/)：官方强调高性能媒体读取、`WebCodecs` 协同和浏览器内处理能力，适合客户端派生预览。
- [MDN requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)：说明浏览器可以在视频帧真正送到 compositor 时高效抓帧，适合作为客户端首帧捕获补充能力。
- [MDN MediaCapabilities.decodingInfo](https://developer.mozilla.org/en-US/docs/Web/API/MediaCapabilities/decodingInfo)：说明可以在前端先判断目标媒体配置是否 supported / smooth / powerEfficient。
- [MDN VideoDecoder.isConfigSupported](https://developer.mozilla.org/en-US/docs/Web/API/VideoDecoder/isConfigSupported_static)：说明可用 `WebCodecs` 做更细粒度解码能力探测。
- [Video.js Poster](https://videojs.org/docs/framework/react/reference/poster)：官方继续把 poster 视为播放前显示内容，而不是把“预览”混进播放链里。
- [WebTorrent Docs](https://webtorrent.io/docs)：官方提供 `streamTo(video)`、`select()`、`critical()`、分片优先级和浏览器 streaming 能力，但没有把 preview / poster 当成内建语义。
- [web.dev Video performance](https://web.dev/learn/performance/video-performance)：官方建议对视频首屏体验明确区分 poster / preload / lazy loading，说明“未播放前显示内容”本来就是单独问题。

## 13. 最终裁决

以后在 `koko` 里，视频预览主链必须改成这样：

1. **canonical video 继续是唯一媒体真相。**
2. **预览不是后端长期资产，而是客户端基于 canonical video 派生的本地缓存能力。**
3. **24 小时内后端 web seed 只负责帮新用户尽快拿到生成 preview 所需关键字节。**
4. **24 小时后服务器退场，不再长期保留 preview 小图垃圾。**
5. **只要还有 source bytes，客户端和群友就能继续秒级派生 preview。**
6. **没有 source bytes 时，系统只能诚实显示占位，不能偷偷复活原文件直读链。**

这才是对后端最轻、对架构最克制、对真相最诚实的优雅方案 A。
