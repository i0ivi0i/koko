# 群聊房间 UIUX 去网页化与社论橙视觉系统设计

日期：2026-04-18  
状态：Draft  
适用范围：`koko` 当前 Web 群聊房间壳、消息时间线、输入区、媒体消息卡片、媒体查看器返回落点与相关前端测试。  
文档目标：在**不改动后端业务契约、不破坏现有 AppRuntime owner 边界**的前提下，把群聊房间从“浏览器里的聊天网页”收口成“浏览器中的持续在场应用界面”，同时解决当前 4 个具体问题：  
1. 夜间主题配色发脏；  
2. 多图/多视频/混发时附件拼贴不工整；  
3. 房间主舞台过窄、顶部与输入区挤占过多空间；  
4. 群友昵称会随着屏幕自适应被折叠，影响扫读。

## 0. 这次设计真正要解决什么

这次不是简单“换个好看皮肤”。

`UIUX禁令.md` 已经把问题说透：  
群聊不是内容网站，用户不是在“看页面”，而是在“持续在场”。  
所以当前 UI 的核心问题也不是某个圆角、阴影、字号不好看，而是它们一起把产品拉回了网页思维：

1. 顶部像页面头，不像会话现场里的细导航；
2. 消息区像被装进了一个中等宽度的列表盒子，不像主舞台；
3. 多媒体附件只是“能显示”，没有进入稳定的 IM 拼贴秩序；
4. 昵称被当成可压缩文本，而不是群聊扫读里的方向信息；
5. 状态分散在各处，用户需要自己猜系统真相。

这份设计的目标只有一句话：

**让房间界面优先服务“持续在场”和“连续使用”，而不是服务单屏截图。**

## 1. 上位裁决

### 1.1 视觉方向

最终方向锁定为：

**`iPhone 式系统骨架 + 社论橙 + 极少量锋边辅色 + 去网页化空间结构`**

它不是：

1. 霓虹赛博；
2. 棕色纸感刊物；
3. 活动海报式强视觉；
4. 居中卡片式高级网页。

它是：

1. 骨架像 iPhone 系统界面，干净、克制、精确；
2. 颜色像被编辑设计过，而不是被营销海报轰炸过；
3. 空间像持续运行的聊天应用，而不是一张“房间详情页”；
4. 媒体、状态、输入都围绕同一段会话流闭环。

### 1.2 本轮禁止项

本轮要把这些写死：

1. 禁止任何棕色、褐色、泥黄、脏米色、锈色、纸黄主色进入房间主界面。
2. 禁止 serif / slab serif / 复古报刊字进入主体标题与房间骨架。
3. 禁止再做成“居中大卡片 + 宽边留白 + 页面标题”式网页结构。
4. 禁止多媒体消息继续沿用“只有单附件好看，多附件就凑合”的策略。
5. 禁止昵称因为响应式压缩而变成省略号或折叠信息。
6. 禁止关键状态继续依赖 toast 或角落弱提示。

### 1.3 保留项

这次不动这些边界：

1. 不改后端 contract。
2. 不改 AppRuntime / actor owner 真相分层。
3. 不重做媒体主链与正式查看器技术路线。
4. 不把 UI 重构成另一套页面流。

## 2. 审美系统裁决

### 2.1 色彩系统

房间界面以后只允许走这套色彩结构：

1. **底色**
   - 近黑主背景：`#0A0B0E` 到 `#101114`
   - 浮层/面板：同一黑系内的浅一级，不得发灰发黄

2. **正文与层级字**
   - 主文字：接近冷白
   - 次级文字：冷灰蓝，不带暖脏色偏

3. **主强调色**
   - 固定为 `活力橙`
   - 建议主橙：`#FF6A00` 或同亮度区间
   - 建议副橙：`#FF9340`

4. **辅色**
   - 极少量 `玫红`：只做锋边、重点 badge、局部系统锚点
   - 极少量 `柠檬黄`：只做高亮提醒或极少数数值状态

5. **禁用区**
   - 禁用棕色家族做底色、主按钮、主 bubble、主媒体填充
   - 禁用大面积渐变铺满整个页面
   - 禁用“为了高级感”硬加旧纸张、旧油墨、旧胶片色偏

### 2.2 字体与字气

字体气质固定为 `iPhone 式系统感`：

1. 全部主体 UI 使用干净无衬线系统栈。
2. 不引入 serif 做房间名、消息名、状态标题。
3. 高级感来自：
   - 字重分层；
   - 字距；
   - 空间节奏；
   - 对齐精度；
   - 标题与正文的呼吸关系。

建议字体栈：

```css
-apple-system, BlinkMacSystemFont, "SF Pro Text", "SF Pro Display",
"PingFang SC", "Helvetica Neue", "Segoe UI", "Microsoft YaHei", sans-serif
```

说明：

1. 这是“像 iPhone”，不是私自内嵌 Apple 字体文件。
2. 在 Apple 设备上优先系统字体；在 Win 上优先干净系统 fallback。

### 2.3 高级感来源

以后房间界面的高级感只允许来自这些东西：

1. 空间比例；
2. 状态位置稳定；
3. 文字层级清楚；
4. 消息流扫读顺滑；
5. 媒体拼贴秩序；
6. 控制区一体化。

不允许来自这些东西：

1. 大面积材质噪音；
2. 复古滤镜；
3. 大量跳色；
4. 装饰性形状抢主流程；
5. “看起来很设计”的空洞留白。

## 3. 信息与空间结构

### 3.1 顶部：从网页头改成细导航带

顶部必须从“页面头”退化成“在场导航带”。

新结构：

1. 返回按钮缩成系统式图标按钮，不再是宽胶囊文案按钮。
2. 房间标题居中，成为唯一强信息。
3. 房间号、在线状态、恢复态等收成一行弱信息，不再占第二层大块高度。
4. 顶部总高度明显收窄，只保留：
   - 你仍在这个房间；
   - 房间当前是不是活着；
   - 你可以回去。

禁止：

1. 返回按钮占据明显横向宽度；
2. 房间号副标题占一整行主要高度；
3. 顶部像“详情页标题区”。

### 3.2 主舞台：消息区必须真正打开

房间页以后要明确承认：

**消息流就是主舞台。**

所以：

1. 房间主空间优先留给消息区；
2. 左右留白更克制，避免像网页内容栏；
3. 上下呼吸更顺，但不是大卡片式营销留白；
4. 滚动容器视觉上要像连续时间流，不像一个内嵌面板。

用户第一眼应感知为：

1. 我已经回到现场；
2. 这里可以直接继续读、继续说；
3. 不是进了一个“房间详情页”。

### 3.3 输入区：从表单底栏改成稳定控制台

输入区不是网页表单，而是会话控制台。

所以：

1. 输入区固定贴近消息主舞台底部；
2. 状态带固定在输入区上方；
3. 附件、草稿、发送动作与状态放在同一控制块中；
4. 输入区视觉应更像系统里的稳定底座，而不是一个独立的表单模块。

禁止：

1. 输入区离消息主舞台太远；
2. 发送中/失败/上传状态漂在别处；
3. 输入区长得像网站评论框。

## 4. 时间线与媒体拼贴裁决

### 4.1 昵称：完整优先，不得折叠

昵称在群聊里是方向信息，不是装饰。

所以：

1. `message-alias` 禁止单行省略号裁决昵称真相。
2. 响应式收窄时，优先让出的是：
   - 气泡宽度；
   - 外层留白；
   - 附件间距；
   - 行内非关键信息。
3. 不允许让昵称在常规使用场景中被压成 `...`。

实现上：

1. 别再让昵称跟随气泡宽度粗暴收口；
2. 昵称可独立于气泡宽度占更稳定的读宽；
3. 昵称必要时允许自然换行，但不允许语义性裁断。

### 4.2 消息气泡：服务扫读，不服务装饰

消息气泡必须继续为扫读效率服务：

1. 自己 / 他人分边清楚；
2. 自己的主 bubble 才允许用主强调色；
3. 他人 bubble 保持近黑系内的清晰分层；
4. 文本与媒体之间的间距必须稳定，不靠碰运气的 margin。

### 4.3 单附件策略

单张图片 / 单个视频继续沿用“大卡片但不过分肥厚”的方向：

1. 保留相对自然的宽高比例；
2. 保持当前较好的大卡片质感；
3. 视频封面与图片卡片继续安静，不默认吵闹；
4. 正式播放与正式查看仍然只进入正式层。

### 4.4 多附件策略：进入稳定拼贴模板

多图、多视频、图视频混发，以后禁止走“逐个小卡片平均排”的土法。

必须改成**稳定拼贴模板**。

建议模板：

1. **2 项**
   - 两列并排
   - 高度一致

2. **3 项**
   - 一大两小
   - 主项占两行或两列
   - 次项堆叠补齐

3. **4 项**
   - 规则 `2 x 2`

4. **5 项**
   - 主项 + `2 x 2` 尾格

5. **6 项**
   - 规则 `3 x 2`

6. **7-9 项**
   - 固定三列骨架
   - 允许第一项作为 hero tile
   - 其余按稳定宫格补齐

硬规则：

1. 图片和视频共用同一套拼贴骨架。
2. 视频只通过：
   - 播放角标；
   - 时长标记；
   - 封面策略
   来区分，不得另起第二套几何规则。
3. 混发时依然按发送顺序决定主项，不允许视觉层偷偷重排业务顺序。
4. 拼贴宽度必须先在展示模型层裁决，再交给 renderer；不能只靠 CSS 临时拼。

### 4.5 这部分必须落在哪一层

多附件工整问题不是纯 CSS 问题，而是展示模型问题。

所以必须这样分层：

1. `frontend/视图.ts`
   - 负责根据附件数量、顺序、媒体类型派生稳定的 `collage template / span / display size`
   - 继续保持“壳层只吃稳定展示模型”的原则

2. `frontend/房间消息窗.ts`
   - 只负责按照模板渲染 grid
   - 不再自己发明附件排版逻辑

3. `frontend/聊天壳.ts`
   - 只负责壳级空间与状态带
   - 不拥有附件拼贴真相

这样才能符合：

1. 展示模型在 view-model 层收口；
2. renderer 保持薄；
3. 后续测试可以直接针对模板而不是靠截图猜。

## 5. 状态与交互裁决

### 5.1 状态固定区

所有关键状态收口到输入区上方固定状态带。

这条状态带负责：

1. 离线；
2. 重连中；
3. 恢复中；
4. 上传中；
5. 发送失败；
6. 其他需要稳定感知的系统态。

禁止：

1. 只靠 toast；
2. 只靠角落浅字；
3. 成功与失败需要用户自己拼。

### 5.2 未读与最新

未读与最新必须继续是清晰锚点：

1. 未读线保持稳定可见；
2. 离底后“回到最新”入口固定悬在消息区右下；
3. 位置要贴近输入区，像会话方向钮，不像网页浮窗。

### 5.3 发送链路

发送链路要符合“现场不断”：

1. 发送中不清输入上下文；
2. 失败不清现场；
3. 重试与失败状态贴着消息或草稿本体显示；
4. 用户不需要猜“这条到底算成功还是失败”。

### 5.4 查看媒体后的返回

查看图片/视频必须像在房间之上打开一层，而不是离开房间去另一个站点。

所以：

1. 打开正式查看器时，房间上下文仍然成立；
2. 关闭查看器时，必须回到原消息位置和原阅读节奏；
3. 不允许关闭后失去滚动定位；
4. 不允许让查看器像第二套房间页。

## 6. 实施边界与文件落点

### 6.1 本轮主要修改面

本轮实现应主要落在：

1. `frontend/聊天壳.ts`
   - 顶部瘦身
   - 输入区控制台化
   - 状态带与壳级空间节奏

2. `frontend/房间消息窗.ts`
   - 消息行布局
   - 昵称显示规则
   - 媒体拼贴 renderer

3. `frontend/视图.ts`
   - 附件展示模型扩展
   - 多附件拼贴模板
   - 气泡宽度与昵称读宽裁决

4. 相关前端测试
   - 聊天壳布局
   - 输入区布局
   - 房间消息窗媒体查看器
   - 视图展示模型

### 6.2 本轮不改的东西

明确不动：

1. 后端业务真相；
2. transport 协议；
3. 正式播放主链；
4. AppRuntime owner 架构；
5. 多标签 / SW / 生命周期主协议。

## 7. 验收标准

### 7.1 体验验收

必须同时满足：

1. 第一眼明显更像 App 房间现场，不像网页详情页；
2. 消息区明显更开阔；
3. 顶部不再抢舞台；
4. 输入区更像稳定控制台；
5. 多媒体混发有稳定、工整、Telegram 式拼贴秩序；
6. 昵称保持完整可读；
7. 状态不需要靠猜。

### 7.2 架构验收

必须同时满足：

1. 拼贴模板真相在展示模型层收口；
2. `房间消息窗` 只渲染模板，不再长排版真相；
3. 壳层不偷长媒体或状态真相；
4. 不引入新的网页式页面流。

### 7.3 测试验收

至少补齐/更新这些测试：

1. `视图.ts`
   - 2/3/4/5/6/7-9 附件模板派生测试
   - 混合图片/视频仍按稳定模板输出测试

2. `聊天壳.ts`
   - 顶部与输入区布局契约测试
   - 状态带固定位置测试

3. `房间消息窗.ts`
   - 昵称不再被省略号裁断的测试
   - 多附件渲染 data shape / class / grid 契约测试

4. 回归验证
   - `pnpm --dir frontend test`
   - `pnpm --dir frontend typecheck`

## 8. 被否决的方向

这次明确否决这些方向，避免后续反复回摆：

1. **霓虹赛博方向**  
   原因：容易躁、容易脏、容易做成活动页。

2. **棕色纸感刊物方向**  
   原因：用户已明确判定会把页面做脏，且不符合当前夜间应用骨架。

3. **强 FlowFest 式海报方向**  
   原因：适合活动页，不适合高频久用聊天产品。

4. **纯企业风极简方向**  
   原因：虽然干净，但会把“真正的波普骨相”全部洗掉，记忆点太弱。

## 9. 当前结论

这次群聊房间 UIUX 的最终结论，不是“换一套更时髦的皮肤”，而是：

1. 用 `iPhone 式` 系统骨架把网页感压下去；
2. 用 `社论橙` 把夜间主题提亮，但保持克制；
3. 用稳定拼贴模板把多媒体消息真正做成 IM 拼贴，而不是凑格子；
4. 用稳定状态带、完整昵称和更开的主舞台，把用户重新留在现场里。

如果后续 implementation 不能同时做到这四件事，那就说明它只是换色，不是去网页化设计。
