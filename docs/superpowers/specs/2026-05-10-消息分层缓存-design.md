## 1. 背景与动机

### 1.1 项目定位

本项目是公网万人实时图文视频群聊（详见 `AGENTS.md` Core 段）。核心使用场景：
- 用户在浏览器里挂多个群、24h 不间断接收消息
- 群里持续发文字、图片、视频
- 实时性优先于历史可达性，但历史可达性也是基本权利

### 1.2 现状诊断（事实而非猜测）

本会话内对前端做了完整的资源累积审查，事实如下：

| 项目 | 现状 | 评估 |
|------|------|------|
| DOM 节点 | TanStack Virtualizer 严格按 viewport 裁剪 (`@frontend/房间消息窗/壳.ts:72`) | ✅ 不会累积 |
| 媒体会话窗口 | 24/4/2 三档预算 + 失活清理 | ✅ 不会累积 |
| WebTorrent swarm | `zeroRefCompletionGraceTimerId` + `按生命周期策略清理协作分发会话` | ✅ 不会累积 |
| `setTimeout/clearTimeout` | 全前端 18:18 完美匹配 | ✅ 不会累积 |
| `addEventListener` | 多余的全在页面级单例运行时 (`平台/生命周期运行时.ts` 等) | ✅ 不会累积 |
| ImageBitmap 冻结帧 | 短时暖状态 TTL + `dispose()` 闭环 | ✅ 不会累积 |
| ObjectURL | `revokeObjectURL` 闭环 | ✅ 不会累积 |
| **消息 `items` 数组** | **纯内存数组，无上限**（`@frontend/房间消息窗/壳.ts:290` 直接读 `this.items.length`，由 `时间线/运行时.ts` 的 `房间时间线机` 状态机驱动） | ⚠️ **唯一会无限增长的资源** |

### 1.3 问题的根因

`items` 是当前唯一会随会话挂着持续增长的资源。具体表现：

- 用户进房间 → `进入房间快照(snapshot)` → `roomKernel.send(SNAPSHOT_LOADED)` + `接收时间线事实({ type: "AUTHORITATIVE_SNAPSHOT_LOADED", ... })`（首屏几十条）
- 用户向上滚加载历史 → `请求加载更早历史()` → `接收时间线事实({ type: "HISTORY_PAGE_APPENDED", ... })`（每页 55 条）
- 服务端推新消息 → `接收时间线事实({ type: "REALTIME_EVENTS_RECEIVED", ... })`
- 三种路径最终都汇入 `roomTimeline`（xstate `房间时间线机`）的 `messages` 字段
- **没有任何上限机制**：用户在一个活跃群里挂 24h，items 数组可以累积到几万到几十万条

每条消息按 1KB 平均估算，5 万条 = 50MB JS heap，10 万条 = 100MB。这本身没让浏览器立刻 OOM（毕竟 V8 默认 heap 上限是 4GB），但会触发：

1. **GC 压力**：每次 array 扩容都涉及大量对象拷贝，长 array 的 GC 回收触发频率上升
2. **属性访问代价**：长 array 的 length 比较、`find`、`findIndex` 都是 O(n)，热路径被拉慢
3. **序列化成本**：lit 渲染管道里属性变更触发的子组件 props diff 在长 array 上代价激增
4. **垃圾对象引用图**：每条消息持有的对象图（attachments、sender、reactions 等）随消息累积，可达性图越来越大

更关键的是：**这违背了"24h 不间断保持丝滑"的硬约束**——单房间使用越久越慢，是任何成熟 IM 都不能接受的体验。

### 1.4 为什么现在做（不是优化是基础设施）

这不是"性能优化"，是**架构补完**：
- 万人多群是项目的明确目标（`AGENTS.md` Core 段："公网万人实时图文视频群聊，稳定秒达不崩"）
- 当前架构在"挂着一个房间 24h"这个最普通的使用场景下就会持续退化
- 修复不需要等到用户量增长——它是**单用户单房间**就能复现的退化路径
- 修复路径与"多群事件头订阅"等更大改造是正交的，可以独立先行

### 1.5 为什么这个 spec 不解决"多群"问题

主人在 brainstorming 阶段确认：当前 `roomKernel` 是单 active 房间架构，"多群挂着"在前端层面其实是 0 开销（除当前房间外其他房间无 socket 订阅、无 swarm）。"用户能看到 N 个群的未读数 + 最后一条预览"需要前后端契约扩展（`joined_rooms[]` + 事件头推送），那是独立子项目。**本 spec 只解决"单房间长期使用越用越卡"这一个根因**。

## 2. 目标 / 非目标

### 2.1 目标

1. **内存恒定**：单房间挂着 24h，`items.length` 永远不超过预定上限（3000 条）
2. **首屏体验不退化**：进房间的首屏速度、未读起点、首屏消息内容与现行行为完全一致（不引入闪屏）
3. **历史可达**：用户向上滚加载历史时，能瞬间命中本地缓存（IndexedDB）；缓存未命中时回落到现有 `room_history` 服务端接口
4. **离线可用**：网络断开时仍能查看本地缓存的历史消息（不能发送、不能接收新消息，但能浏览）
5. **不破坏现有契约**：服务端接口、`消息事件` 类型、`房间内核` 状态机的事件边界全部保持不变
6. **DDD 边界清晰**：新增能力按 Onion 分层落到正确的层（domain 不动、application 新增 port、adapter 新增 IndexedDB 实现）

### 2.2 非目标（明确不做）

1. **不重写 BOOTSTRAP 路径**（不做"IDB 优先 + 服务端校准"的 Telegram 风首屏闪现，因风险高且收益边际）
2. **不做多房间事件头订阅**（独立子项目）
3. **不做消息编辑/删除**（项目目前的 `消息事件` 只有 `message_created`，本 spec 仅为未来扩展预留 schemaVersion）
4. **不修改服务端代码**（除非 IDB 缓存协议要求服务端给出新字段；如有，明确列出并先得到主人确认）
5. **不引入新的外部依赖 crate / npm 包**（IndexedDB 用浏览器原生 API + 现有 `idb` 或 `idb-keyval` 之一；优先零依赖原生 API）
6. **不裁剪 attachment / playback / 媒体会话**（这些已有独立预算机制）

## 3. 关键设计选择与理由

### 3.1 为什么是"分层"而不是"环形裁剪"

**否决方案：纯内存 FIFO 环形（1 万条上限，超过裁最早）**

否决理由：
- 裁掉的消息要重拉网络，每次向上滚都要请求服务端
- 离线场景丢失历史可达性
- 多 Tab 协作时各自维护独立环形，缓存无法共享
- 实质上违背了"24h 丝滑"的承诺，只是把"卡"换成了"重拉"

**采用方案：内存窗口 + IndexedDB 永久缓存 + 服务端权威源**

采用理由：
- 内存恒定，符合 Telegram、WhatsApp Web、Discord 等成熟 IM 的实测策略
- 历史滚动瞬间命中本地缓存，不需要网络
- IndexedDB 跨 Tab 共享、跨刷新持久、用户清浏览器数据时一并清掉（符合用户预期）
- 失败时优雅降级（IDB 故障→走服务端，不是崩溃）

### 3.2 为什么内存窗口选 3000 条（不是 200/1000/10000）

主人在 brainstorming 选定 3000 条。理由依据：

| 候选 | viewport 上下各保留 | JS heap 占用 | 高频跳转命中率 | 评估 |
|------|---------------------|--------------|----------------|------|
| 200 条 | 各 100 条 | ~200KB | 频繁 miss IDB | 闪帧风险 |
| 1000 条 | 各 500 条 | ~1MB | 多数命中 | Telegram 默认体感 |
| **3000 条** | **各 1500 条** | **~3MB** | **几乎不 miss** | ✅ 安全余量 |
| 10000 条 | 各 5000 条 | ~10MB | 100% 命中 | 内存占用偏大 |

3000 条 = 在普通用户极少触发 IDB 读取的前提下，单房间 active state 占 ~3MB JS heap。即使用户开 10 个 tab 共 10 个房间 active（事实上前端只有 1 个 tab × 1 个 room active），峰值也只有 30MB。这给项目其他子系统留出充分余量。

### 3.3 为什么 IndexedDB 永久缓存（不是 30 天/5 万条）

主人选定永久缓存。理由依据：
- 文本消息约 0.3-1KB/条，100 万条文本仅 300MB-1GB IndexedDB 占用
- IndexedDB 默认配额：Chrome 60% 磁盘空间、Firefox 50%；超出后浏览器自身有 LRU 驱逐机制（不需要应用层主动裁）
- 用户清浏览器数据时同步清掉缓存，符合"浏览器数据 = 用户控制"的契约
- 媒体字节由 `idb-chunk-store` 单独管理（已有独立 LRU），不在本 spec 范围
- 与 Telegram/WhatsApp Web 默认行为一致（用户可在设置里手动清缓存）

### 3.4 为什么"服务端首屏 + 上滑用 IDB"（不是 IDB 优先）

主人选定方案 1。理由依据：
- 现有 BOOTSTRAP 路径已经经过完整测试，包含未读起点、首屏消息、滚动锚点恢复等复杂逻辑
- 改成"IDB 优先 + 服务端校准"需要重写 `房间恢复编排.ts`、引入 IDB 与服务端 `event_position` 互验、处理 IDB 数据陈旧的回退路径
- 收益边际（首屏延迟从 ~150ms 降到 ~30ms），不抵实施成本
- 方案 1 是非破坏性增量（IDB 只做"历史加速层"），失败可立即降级回现行行为

### 3.5 为什么不引入新依赖

按 `AGENTS.md` "基础设施、协议、性能敏感组件和工程工具链默认复用成熟方案"——但**前提是有边界压力**。当前需求：
- 简单的 K/V + range query
- 浏览器原生 `IndexedDB` API 完全够用
- 复杂封装库（`idb`、`dexie`）会带来类型边界、版本迁移机制等额外复杂度，但本场景的 schema 极简（一个对象库 + 一个复合索引）

决定：**先用浏览器原生 IndexedDB API 写最小封装**。如果实施过程中发现原生 API 太难用（比如 transaction promise 化代价太大），再单独评估引入 `idb` (Jake Archibald 的轻量封装，3KB)。这个决定不在本 spec 强制，可以在 plan 阶段讨论。

## 4. 整体架构

```
┌──────────────────────────────────────────────────────────────┐
│ Memory Window  (active items array)                          │
│  - 上限：3000 条                                              │
│  - 渲染层：TanStack Virtualizer 按 viewport 裁 DOM            │
│  - 业务层：房间内核接收 SNAPSHOT_LOADED / HISTORY_PAGE_APPENDED│
│           / message_created 事件后写入                        │
│  - 裁剪触发：超过 3000 条时按 viewport 中心保留 ±1500 条      │
└──────────────────┬───────────────────────────────────────────┘
                   │ 后台 fire-and-forget 写入
                   ↓
┌──────────────────────────────────────────────────────────────┐
│ IndexedDB Message Repository                                 │
│  - DB 名：koko-messages                                      │
│  - Schema 版本：1 (预留升级路径)                              │
│  - Object Store：messages                                    │
│    - keyPath：[room_id, event_position]  (复合主键，去重)    │
│    - index：room_id_position (room_id + event_position 升序) │
│  - 写策略：put (upsert，幂等)                                 │
│  - 读策略：openCursor on index, range query                  │
│  - 永久保留 (浏览器存储压力时自身 LRU 驱逐)                   │
└──────────────────┬───────────────────────────────────────────┘
                   │ 用户向上滚 IDB miss 时
                   ↓
┌──────────────────────────────────────────────────────────────┐
│ Server Authority  (Rust + socketioxide + PostgreSQL)         │
│  - 现有 room_history 接口 (load_room_history)                │
│  - 现有 BOOTSTRAP 接口 (load_room_snapshot)                  │
│  - 现有 message_created 实时推送                              │
│  - 不需要任何修改                                              │
└──────────────────────────────────────────────────────────────┘
```

### 4.1 数据流向（写）

```
服务端推消息 (message_created)
   ↓
房间内核接收 → 内存 items 尾部 push
   ↓ (并行 fire-and-forget)
MessageRepository.写入(roomId, [新消息])
   ↓
IndexedDB put (幂等)
```

### 4.2 数据流向（读）

```
用户向上滑到顶
   ↓
房间编排发出 LOAD_HISTORY_REQUESTED
   ↓
现有路径：调 load_room_history(server)
   ↓ ⬇ 改为：先调 MessageRepository.读取窗口
   ↓
IDB 命中 → 直接 HISTORY_PAGE_APPENDED 前插内存
IDB miss → 走原服务端路径，结果同时写回 IDB
```

### 4.3 数据流向（裁）

```
items 长度变化触发钩子（push / unshift）
   ↓
若 length > 3000 且距离上次裁剪 > N ms（防抖）
   ↓
读取当前 viewport 中心 messageId
   ↓
保留中心位置 ±1500 条，两端裁掉
   ↓
注意：裁掉的消息仍在 IDB，重新滑回去能命中
```

## 5. DDD/Onion 分层落点

按 `AGENTS.md` 第 6 条 "Onion Clean Architecture 是总原则" 与第 11 条 "contract 是多壳共核的唯一共享表面"。

### 5.1 各层职责（依赖方向只能向内）

```
┌─ shell (前端 UI 层) ─────────────────────────────────────┐
│ frontend/房间消息窗/壳.ts                                  │
│  - 仍然只调 application 层暴露的接口                        │
│  - 内存窗口裁剪由这一层触发                                 │
│  - 不直接访问 IndexedDB                                    │
└────────────────────────────────────────────────────────┘
              ↓ depends on
┌─ adapter (前端) ─────────────────────────────────────────┐
│ frontend/聊天本地缓存/IndexedDB消息仓库.ts (新建)          │
│  - 实现 application 层定义的 MessageRepository port       │
│  - 仅含 IndexedDB API 调用、序列化/反序列化、错误处理      │
│  - 不携带业务规则                                           │
└────────────────────────────────────────────────────────┘
              ↓ implements
┌─ application (前端) ─────────────────────────────────────┐
│ frontend/聊天本地缓存/消息仓库端口.ts (新建)                │
│  - 定义 MessageRepository port (interface)                │
│  - 不含具体实现                                             │
│  - 现有 `房间/壳层/阅读推进.ts` 与 `恢复/应用.ts` 在加载   │
│    历史/snapshot 时改调这个 port                           │
│  - 选择新建独立 owner 目录的理由：MessageRepository 是      │
│    跨房间编排、恢复编排、时间线 owner 共用的本地持久化层，  │
│    不属于任何单一现有 owner；放在它们任一目录里都会模糊      │
│    职责边界                                                │
└────────────────────────────────────────────────────────┘
              ↓ uses
┌─ domain (跨壳共核) ──────────────────────────────────────┐
│ frontend/聊天共享/契约.ts                                  │
│  - 现有 消息事件 类型保持不变                               │
│  - 不在本 spec 修改                                         │
└────────────────────────────────────────────────────────┘
```

### 5.2 contract 层不动

`AGENTS.md` 第 11 条："`contract` 是多壳共核的唯一共享表面，只放稳定 command/query/event/snapshot/error"。

本 spec **不修改 contract**。`消息事件` 类型保持不变，`load_room_history` / `load_room_snapshot` 接口不变。`MessageRepository` 是前端内部 port，不是跨前后端的契约。

### 5.3 不引入双真相

`AGENTS.md` "禁止把假设当事实"、"路径越少，真相越近"。本 spec 严守：

- **服务端是消息真相**：IDB 只是它的本地镜像，不创造新消息
- **`event_position` 是唯一排序真相**：IDB 不引入 client_clock 之类的本地时序
- **冲突时服务端赢**：如果 IDB 写入的消息和服务端推送的同 `(room_id, event_position)` 内容不同，put 操作会用最新（服务端）覆盖

## 6. 数据模型（IndexedDB schema）

### 6.1 数据库结构

```typescript
// 数据库元信息
const 数据库名 = "koko-messages";
const 数据库版本 = 1;  // 升级时 +1，触发 onupgradeneeded

// Object Store
const 消息库名 = "messages";

// 主键（复合）：[room_id, event_position]
// 复合主键自然去重：同一房间的同一事件位置只能存一条
// IndexedDB 复合主键写法：keyPath: ["room_id", "event_position"]

// 二级索引：按 room_id 范围查询时使用
const 索引名_按房间位置 = "by_room_position";
// indexName: keyPath = ["room_id", "event_position"], unique = true
```

### 6.2 存储记录格式

```typescript
interface IDB消息记录 {
  // 主键字段（必须出现在记录里）
  room_id: string;
  event_position: number;

  // 业务字段（与 frontend/聊天共享/契约.ts 的 消息事件 完全镜像，不引入新字段）
  // 注意：实际 消息事件 schema 是平铺的 sender_session_id / sender_display_alias，
  //     没有 created_at；attachments 是可选字段且类型为 附件快照[]
  type: "message_created";
  message_id: string;
  client_message_id: string;
  sender_session_id: string;
  sender_display_alias: string;
  text: string;
  attachments?: 附件快照[];

  // 缓存元信息（前端本地用，不向后端传）
  cached_at: number;        // Date.now() 写入时间，便于诊断
  schema_version: 1;        // 同步 数据库版本，便于未来升级时识别
}
```

**为什么把 `event_position` 也写入记录而不仅作为主键：**
- IndexedDB 复合主键的字段值必须存在于记录里（这是 IndexedDB 规范要求）
- 范围查询时直接从游标读取，不需要再解析主键

**为什么有 `cached_at`：**
- 仅用于本地诊断（"这个消息什么时候被缓存"），不参与业务判断
- 服务端 `消息事件` 没有 `created_at` 字段；时序由 `event_position` 单调递增承载

### 6.3 索引设计

唯一索引：`by_room_position` on `[room_id, event_position]`

**为什么需要二级索引：**
- 主键即 `[room_id, event_position]`，直接用主键 range 查询就够了，**实际不需要单独建二级索引**
- 复合主键本身就是唯一升序排序

**修订**：决定**不建二级索引**，主键即排序键。代价：未来如果需要按 `created_at` 排序或按 `sender` 过滤再加索引。

## 7. 写路径详细流程

### 7.1 触发点 1：BOOTSTRAP 拉到 snapshot_messages

现有路径 `frontend/恢复/应用.ts` 的 `进入房间快照(snapshot, ...)` 函数会先调 `roomKernel.send({ type: "SNAPSHOT_LOADED", ... })`，紧接着调 `deps.接收时间线事实({ type: "AUTHORITATIVE_SNAPSHOT_LOADED", messages: snapshot.snapshot_messages, ... })`。后者才是真正把消息写进时间线 owner 的入口。

**新增**：在 `进入房间快照` 函数末尾（已经触发了 `AUTHORITATIVE_SNAPSHOT_LOADED` 之后），异步 fire-and-forget 写入 IDB：

```typescript
// 在 frontend/恢复/应用.ts 的 进入房间快照(...) 函数末尾追加
queueMicrotask(() => {
  void deps.消息仓库.写入(snapshot.room_id, snapshot.snapshot_messages).catch((err) => {
    // 不打断业务，只记录
    console.warn("IDB 写入失败（不影响业务）", err);
  });
});
```

**为什么钩在这里而不是 roomKernel `SNAPSHOT_LOADED` 处理器里：**
- `SNAPSHOT_LOADED` 是房间内核状态机事件（`房间内核.ts` 的 xstate machine），主要用于驱动状态转换；它的副作用应保持纯净
- `进入房间快照` 函数已经是 application 层的编排入口，钩在这里能拿到完整的 `snapshot.snapshot_messages` 同步可见

**为什么用 `queueMicrotask`：**
- BOOTSTRAP 主链当下不需要等 IDB 写完
- 让出当前任务给渲染优先

**为什么 `.catch` 而不是 await：**
- IDB 故障不能阻塞业务流程
- 失败时下次 BOOTSTRAP 会再写一次（put 是幂等的）

**错误恢复路径也会触发写入（幂等保证无副作用）：**
- `frontend/恢复/应用.ts` 的 `从房间快照恢复(roomId)` 函数在 realtime 补洞失败时会调 `进入房间快照(snapshot, ...)` 重建基线
- 这意味着同一会话内 IDB 写入可能被多次触发（BOOTSTRAP / 错误恢复）
- IDB `put` 幂等保证多次写入与一次结果一致，无需额外去重

### 7.2 触发点 2：HISTORY_PAGE_APPENDED 加载历史页

现有路径 `frontend/房间/壳层/阅读推进.ts` 的 `请求加载更早历史()` → `deps.transport.loadRoomHistory(roomId, sessionId, oldestEventPosition, 55)`（被 `withSessionRefreshOnInvalid` 包装）→ `接收时间线事实({ type: "HISTORY_PAGE_APPENDED", messages: page.messages, ... })`。

**新增**：同样在 `接收时间线事实` 之后异步写入 IDB。注意只在走服务端路径时回写——IDB 命中走的是已有的本地数据，不需要再写。

### 7.3 触发点 3：实时推送 message_created

现有路径：socket 推 `room_event { kind: "message_created" }` → `接收时间线事实({ type: "REALTIME_EVENTS_RECEIVED", messages, latestEventPosition })`。具体调用点在 `应用根/聊天应用内核.ts` 与 `聊天实时/` 协作链路里。

**新增**：在 `接收时间线事实` 处理 `REALTIME_EVENTS_RECEIVED` 路径之后异步写入 IDB。

**实施提示**：考虑把三个写入触发点（snapshot / history / realtime）合并到一个统一钩子——比如在 `应用根/聊天应用内核.ts` 的 `接收时间线事实` 内部增加一个观察者，按 `event.type` 派发到 `消息仓库.写入`。这样三个路径只需在一处加 IDB 镜像，避免重复 fire-and-forget 散布。是否采用这个收口在 plan 阶段决定。

### 7.4 写入时的幂等保证

IndexedDB `put` 操作：如果主键 `[room_id, event_position]` 已存在则覆盖；不存在则插入。**天然幂等**。

边界情况：
- 同一条消息被 BOOTSTRAP 写一次、又被实时推送写一次 → 两次都成功，第二次覆盖（内容一致，无副作用）
- 多 Tab 同时写同一条消息 → 两个 transaction 串行执行，最终态确定（IndexedDB 提供 ACID 保证）

## 8. 读路径详细流程

### 8.1 入口：用户向上滚到顶

现有路径 `frontend/房间/壳层/阅读推进.ts` 的 `请求加载更早历史()`（无参数，从 state 读 oldestMessage 与 roomId）：

- 锚点位置 = `state.messages[0].event_position`（最老消息的位置）
- 调用 `deps.withSessionRefreshOnInvalid((sessionId) => deps.transport.loadRoomHistory(roomId, sessionId, eventPosition, 55))`
- 成功后 `接收时间线事实({ type: "HISTORY_PAGE_APPENDED", messages: page.messages, hasMoreBefore: page.messages.length > 0 })`
- 历史补偿 `await deps.roomScroller.应用历史补偿(补偿上下文, page.messages.length > 0)`

**新增**：在调服务端 `loadRoomHistory` **之前**先查 IDB。

```typescript
// 改造后的 frontend/房间/壳层/阅读推进.ts 中的 请求加载更早历史() 函数
async function 请求加载更早历史(): Promise<void> {
  const state = deps.读取阅读状态();
  if (!state.roomId || state.historyLoading || !state.hasMoreBefore) return;

  const oldestMessage = state.messages[0];
  if (!oldestMessage) return;
  const 补偿上下文 = deps.roomScroller.读取历史补偿上下文();

  deps.写入阅读状态({
    historyLoading: true,
    historyErrorCode: "",
  });

  const 数量 = 55;
  const 上界位置 = oldestMessage.event_position;

  try {
    // ===== 新增：先查 IDB =====
    const 缓存命中 = await deps.消息仓库
      .读取窗口(state.roomId, { 上界event_position: 上界位置, 数量 })
      .catch(() => [] as 消息事件[]);

    if (缓存命中.length >= 数量) {
      deps.接收时间线事实({
        type: "HISTORY_PAGE_APPENDED",
        messages: 缓存命中,
        hasMoreBefore: true, // 仍可能有更老的，下次再查
      });
      deps.写入阅读状态({ historyLoading: false, historyErrorCode: "" });
      if (缓存命中.length > 0) deps.上报历史前插开始?.();
      await deps.roomScroller.应用历史补偿(补偿上下文, 缓存命中.length > 0);
      return;
    }

    // ===== 现有路径：IDB 未命中或命中不足，走服务端 =====
    const page = await deps.withSessionRefreshOnInvalid((sessionId) =>
      deps.transport.loadRoomHistory(state.roomId, sessionId, 上界位置, 数量)
    );
    deps.接收时间线事实({
      type: "HISTORY_PAGE_APPENDED",
      messages: page.messages,
      hasMoreBefore: page.messages.length > 0,
    });
    // ===== 新增：服务端拉到的页同时写回 IDB =====
    queueMicrotask(() => {
      void deps.消息仓库.写入(state.roomId, page.messages).catch(() => {});
    });
    deps.写入阅读状态({ historyLoading: false, historyErrorCode: "" });
    if (page.messages.length > 0) deps.上报历史前插开始?.();
    await deps.roomScroller.应用历史补偿(补偿上下文, page.messages.length > 0);
  } catch (error) {
    const code =
      typeof (error as { code?: unknown })?.code === "string"
        ? ((error as { code: string }).code || "system_error")
        : "system_error";
    deps.写入阅读状态({ historyLoading: false, historyErrorCode: code });
  }
}
```

**注意保留的现有不变量：**
- `withSessionRefreshOnInvalid` 包装必须保留（处理 session 失效自动续期）
- `historyErrorCode` 用空字符串 `""` 而不是 `null`（与现有代码风格一致）
- 历史补偿 `roomScroller.应用历史补偿(补偿上下文, ...)` 命中分支也要调用，否则视口不会守住锚点

### 8.2 关键决策：完全命中 vs 部分命中

如果 IDB 读到 `< 数量`，是直接全量走服务端，还是用 IDB 命中的 + 服务端补齐？

**决定：完全命中才直接走 IDB；只要不足，就放弃 IDB 结果走服务端。**

理由：
- 拼接两个来源的逻辑复杂，且要处理"IDB 缓存陈旧"的边界
- 服务端拉到的页同时回写 IDB，下次再滑就完全命中
- "完全命中或全走服务端"是单调清晰的语义，调试和测试都简单

### 8.3 读取参数：上界事件位置 + 数量

```typescript
interface 读取窗口请求 {
  上界event_position: number;  // 不含，返回严格小于这个位置的消息
  数量: number;                 // 最多返回多少条
}
```

实现层用 IndexedDB cursor 倒序遍历主键 `[room_id, X]`（X 严格小于上界），取 `数量` 条。

## 9. 内存窗口裁剪策略

### 9.1 触发条件

每次 `items` 数组发生变更（push / unshift / 整段替换）后，检查 `items.length > 3000`。

### 9.2 裁剪算法

```typescript
function 裁剪内存窗口(items: 聊天列表展示项[], viewport中心index: number): 聊天列表展示项[] {
  const 上限 = 3000;
  const 中心保留半径 = 1500;

  if (items.length <= 上限) return items;

  // 以 viewport 中心为锚点，保留 ±1500 条
  const startIndex = Math.max(0, viewport中心index - 中心保留半径);
  const endIndex = Math.min(items.length, viewport中心index + 中心保留半径);

  return items.slice(startIndex, endIndex);
}
```

### 9.3 viewport 中心的获取

`@frontend/房间消息窗/壳.ts` 已经持有 `messageVirtualizer.getVirtualItems()`，取中间一项的 `index` 作为 viewport 中心。

边界情况：
- viewport 还没初始化（首屏）→ 中心默认取 `items.length - 1`（最新）
- viewport 在最顶（用户拉到顶）→ 中心取 0，保留 0..3000 条（实际就是不裁前面，裁后面）
- viewport 在最底（默认情况）→ 中心取最大 index，保留最末 3000 条

### 9.4 裁剪频率防抖

不在每次 push 都执行裁剪（会浪费 CPU）。改为：
- 每 N 次 push 检查一次（N=100），或
- 每超出 500 条才裁一次

具体阈值在实施时确定。**关键不变量是"items.length 永远 ≤ 3500"（含 500 条防抖 buffer）**。

**为什么是 500 条 buffer 而不是 100 条：**
- 100 条 buffer + 每 100 条检查一次 → 高频裁剪反而浪费 CPU
- 500 条 buffer + 每 500 条检查一次 → 裁剪频率低，峰值 3500 条仍然是 ≤3.5MB JS heap，完全可控

### 9.5 用户向上滚时不裁顶部

如果用户正在向上滚（`scrollPhase === "compensating_history"`），暂停裁剪。否则会在用户滑回去时刚加载的历史立刻被裁掉。

## 10. 错误处理与降级

### 10.1 IDB 不可用

可能原因：
- 浏览器隐身模式禁用 IDB
- 用户禁用第三方 storage
- iOS Safari 在低存储时清掉 IDB

降级策略：**所有 IDB 操作 catch 后静默降级**。
- 写入失败 → 业务不感知（消息仍在内存和服务端）
- 读取失败 → 视同 cache miss，走服务端

### 10.2 IDB 数据陈旧

如果服务端某条消息被改写（理论上不发生，因为只有 `message_created`），IDB 旧版本被读到时：
- 用户看到的是缓存版本（旧）
- 下次实时推送或 BOOTSTRAP 时 put 会覆盖

未来支持编辑/删除时再单独考虑。

### 10.3 IDB 配额超限

浏览器在存储压力下会自动驱逐 IDB 数据。表现为读取时数据"不见了"。
- 这是 cache miss，走服务端兜底
- 不需要应用层做任何处理

### 10.4 transaction 失败

IDB transaction 在 commit 前可能失败（如 user 退出 tab）。
- 写入失败 → 下次同消息再次写入会重试
- 读取失败 → 当 cache miss

## 11. 多 Tab / 多设备协作

### 11.1 同一用户开多个 Tab（同浏览器）

IndexedDB 在同源下是共享的（不分 tab）。
- Tab A 写入消息 → Tab B 下次从 IDB 查询时能读到该消息；Tab B 不需要主动被通知，因为它自己的 socket 连接同时在接收实时推送，IDB 仅作为历史加速层
- 写入冲突由 IDB 自身的 transaction 串行化保证

**不需要 `BroadcastChannel` 主动通知**：
- 用户在 Tab B 时，新消息会通过它自己的 socket 推送获得（每个 Tab 都连服务端）
- IDB 只是缓存，不需要跨 tab 同步

### 11.2 多设备协作

每台设备的 IDB 独立。
- 设备 A 缓存 1000 条历史，设备 B 缓存 100 条
- 用户在设备 B 向上滚 → IDB miss → 走服务端 → 拉到后回写 IDB
- 自然地各自冷启动各自缓存

## 12. 全局约束（执行时不可破坏）

按 `AGENTS.md` 与项目惯例：

1. **Onion 不可破坏**：domain 不依赖 IDB；adapter 只做 IDB API 调用；application port 不带具体实现
2. **现有契约不动**：`消息事件` 类型、`load_room_history` 接口、`房间内核` 状态机的事件类型完全不变
3. **TDD 顺序**：每个能力 RED → GREEN → REFACTOR；先写失败测试再写实现
4. **所有现有测试必须保持绿色**：不允许删除或弱化任何现有测试。230 个 frontend 测试 + 全部 Rust 测试在 PR 合入前必须全绿
5. **运行时零新增依赖（首选）**：用浏览器原生 IDB API；如必须引入 `idb` 包则单独说明并得到主人确认。**测试依赖例外**：`fake-indexeddb` 在测试环境下模拟 IDB API，是列表在许多成熟项目（含 vitest 生态）中的事实标准；按 AGENTS.md "复用成熟方案" 允许作为 `devDependencies` 引入
6. **不引入新真相**：服务端是消息真相，IDB 只是它的本地镜像；冲突时服务端赢
7. **失败降级而非崩溃**：所有 IDB 操作必须 catch 并视为 cache miss
8. **不阻塞主链**：所有 IDB 写入异步 fire-and-forget；所有 IDB 读取在历史前插时是阻塞的（替代了原本就阻塞的服务端调用）
9. **函数式优先**：业务逻辑用纯函数表达，IDB 操作隔离到 adapter；按 `AGENTS.md` 第 14 条
10. **简洁硬约束**：实现按 `AGENTS.md` "200 行能写成 21 行就重写"原则审视；如果某模块超过同等问题的合理复杂度，重写

## 15. 实施分块提示（不是详细 plan）

**注意**：详细 plan 由 `writing-plans` skill 在本 spec 批准后生成。这里只是给出建议的分块顺序，作为 plan 的输入。

建议分 5 块独立 PR（每块独立 RED → GREEN → REFACTOR）：

1. **块 1：MessageRepository port + IndexedDB adapter**（纯新建文件，无业务集成，单测全绿后合入）

## 16. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| IDB API 在 vitest happy-dom 环境下有兼容差异 | 中 | 测试不稳定 | 用 `fake-indexeddb` 库（如已有依赖）或在测试里 mock `indexedDB` 全局对象 |
| 用户首次启用本特性时 IDB 是空的，所有滑动都 miss | 高 | 首次体验暂时退化（实际上和现行行为一致） | 不缓解：这是预期行为，IDB 在使用过程中自动填充 |
| 现有 `房间内核` 状态机依赖 items 数组的特定形态 | 中 | 裁剪后某些下游派生函数失效 | 完整跑现有 230 个 frontend 测试；裁剪只在 viewport 已稳定时触发 |
| IDB 写入慢导致 microtask 队列堵塞 | 低 | 渲染卡顿 | 使用 fire-and-forget；批量写入用单 transaction |
| 主键冲突：服务端 `event_position` 不严格唯一 | 低 | 数据丢失 | 测试断言：服务端契约保证 (room_id, event_position) 唯一；冲突时 put 覆盖 |

## 附录 A：术语表
