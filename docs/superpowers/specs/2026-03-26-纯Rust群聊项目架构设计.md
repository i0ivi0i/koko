# 纯 Rust 群聊项目架构设计

## 目标

构建一个前后端解耦、纯 Rust、可高性能演进的群聊系统。

核心目标：

- 前端可以长期替换和演进，而不破坏后端。
- 后端可以替换具体框架和基础设施，而不破坏领域规则。
- Win11 上可以一键顺畅开发。
- Linux 服务器上可以一键优雅部署、升级、回滚。
- 第一版只做文本群聊，但后续媒体、推送、搜索、私聊等能力可平滑扩展。

## 业务约束

- 房间模型偏 QQ 群思维。
- 房间短码格式固定为 `4 个数字 + 1 个英文字母`，字母位置可变。
- 房间短码全局唯一，永久不可复用。
- 用户输入短码时：
  - 若房间存在，则进入已有房间。
  - 若房间不存在，则自动创建房间。
- 第一个进入并创建该房间的用户自动成为群主。
- 当前用户身份为匿名本地身份：
  - 客户端本地生成并持久化。
  - 同设备可认作同一身份。
  - 换设备视为新身份。
- 角色体系固定为：
  - 群主
  - 管理员
  - 成员
- 群主长期失联后，允许按规则接管。
- 第一版只做群聊，但架构上预留私聊。

## 架构原则

本项目采用以下组合思路：

- Domain-first
- Contract-first
- Hexagonal Architecture
- Clean boundaries

设计原则如下：

- 前端只依赖稳定契约，不依赖后端内部实现。
- 后端业务规则只存在于领域层，不散落在接口层或数据库层。
- WebSocket、数据库、框架、缓存都只是基础设施实现。
- 浏览器只是当前宿主，不是系统核心。
- 性能优化只能污染基础设施层，不能污染领域边界。

补充约束：

- 任何单一框架都不能上升为系统核心概念。
- 任何前端实现都只能依赖稳定契约，不能依赖后端内部事件名、表结构、内存状态或具体中间件。
- 任何后端基础设施都必须可替换，替换时最多影响 `platform` 与少量装配代码。
- 所有“高性能优化”必须服从“边界不被破坏”这一前提。

## 总体技术选型

### 前端

- `Dioxus`

理由：

- 纯 Rust。
- Win11 开发顺手。
- 当前适合 Web 起步。
- 后期迁移 iOS/Android 时，能较高复用契约与业务层思路。

### 后端

- `axum`
- `tokio`

理由：

- Rust 生态成熟。
- 适合做清晰分层。
- 对 WebSocket、HTTP、中间件、异步任务支持良好。

### 数据存储

- `PostgreSQL`
- `sqlx`

约束：

- 当前优先标准 PostgreSQL。
- 架构上为未来接入 Supabase Postgres 做准备。
- 不将业务强绑定到 Supabase 特有能力。

### 基础库

- `serde`
- `uuid`
- `time`
- `thiserror`
- `anyhow`
- `tracing`
- `tracing-subscriber`

## 目录结构

前期采用根目录平铺，避免过度设计：

- `web`
- `server`
- `contracts`
- `domain`
- `platform`

在实际落地时，为了减少 crate 数量、降低前期工程噪音，同时保持代码职责均衡，目录结构进一步收敛为：

- `web`
- `server`
- `core`
- `docs`
- `migrations`
- `run.ps1`
- 根目录 `Cargo.toml`

说明：

- `contracts`、`domain`、`platform` 的抽象思想保留
- 但前期实现合并进单个 `core` crate
- 等后续复杂度明显升高后，再从 `core` 内部平滑拆分

这样既保留边界思维，又避免前期目录臃肿

## 目录职责

以下职责以收敛后的 `web + server + core` 结构为准。

### `web`

前端入口。

负责：

- 页面
- 组件
- 路由
- UI 状态
- 调用后端契约

不负责：

- 领域规则
- 数据库存取
- 协议细节

### `server`

后端入口。

负责：

- HTTP 路由
- WebSocket 路由
- 请求组装
- 服务启动
- 依赖装配

不负责：

- 核心业务规则
- SQL 细节

### `core`

系统核心 crate。

前期统一承载：

- 前后端共享契约
- 领域模型
- 用例
- 规则
- 抽象 port
- 通用错误与类型

约束：

- 不依赖 `Dioxus`
- 不依赖 `axum`
- 不依赖 `sqlx`
- 不直接依赖具体数据库或 WebSocket 实现

## 依赖规则

- `web` 只依赖 `core`
- `server` 依赖 `core`
- `core` 只依赖少量基础库
- 具体基础设施实现先由 `server` 内部承载，后续复杂时再拆分出去

核心原则：

- 前端不直接依赖后端实现
- `core` 不依赖框架层
- 基础设施不能反向决定业务规则

落地检查标准：

- 如果一个类型从 `platform` 泄漏到 `contracts`，说明边界设计有问题。
- 如果一个页面组件需要知道 SQL 字段、数据库约束或 WebSocket 连接细节，说明前端耦合过深。
- 如果一个领域对象必须依赖 `axum` 或 `sqlx` 才能存在，说明领域层已被污染。

## 前端分层

Web 第一版前端内部建议分为：

- `pages`
- `components`
- `features`
- `application`
- `platform`

职责：

- `pages`：页面装配与路由
- `components`：纯展示组件
- `features`：按业务模块组合 UI
- `application`：前端用例、状态协调
- `platform`：HTTP、WebSocket、本地存储、浏览器适配

规则：

- 页面不写业务规则
- 组件不直接发请求
- 浏览器能力全部封到前端 `platform`

建议的最小文件组织：

- `web/src/main.rs`
- `web/src/app.rs`
- `web/src/room.rs`
- `web/src/chat.rs`
- `web/src/session.rs`
- `web/src/ui.rs`

命名理由：

- `room/chat/session` 是天然三大主轴，后期代码量最容易接近
- `app` 负责装配
- `ui` 负责纯展示和样式组织

## 后端分层

后端第一版采用：

- `api`
- `application`
- `domain`
- `platform`

职责：

- `api`：参数解析、路由、输入输出映射
- `application`：用例编排
- `domain`：规则与模型
- `platform`：数据库、实时连接、配置、日志

规则：

- `api` 不写业务规则
- `application` 不直接写 SQL
- `domain` 不依赖框架

建议的最小文件组织：

- `server/src/main.rs`
- `server/src/app.rs`
- `server/src/http.rs`
- `server/src/ws.rs`
- `server/src/room.rs`
- `server/src/chat.rs`
- `server/src/session.rs`

命名理由：

- `http/ws` 代表两类入口
- `room/chat/session` 对应主要业务块
- `app` 负责装配与依赖初始化

## 核心领域模型

建议的 `core` 文件组织：

- `core/src/lib.rs`
- `core/src/contract.rs`
- `core/src/model.rs`
- `core/src/room.rs`
- `core/src/chat.rs`
- `core/src/session.rs`
- `core/src/port.rs`
- `core/src/error.rs`

说明：

- `contract`：共享 DTO、事件、错误码
- `model`：基础领域对象定义
- `room/chat/session`：按业务主轴承载规则和用例
- `port`：对数据库、实时层、媒体等外部能力的抽象接口
- `error`：统一错误模型

这样能兼顾三点：

- 文件数不过多
- 单文件不容易暴涨
- 后期继续细拆时有自然边界

- `Session`
- `Profile`
- `RoomCode`
- `Room`
- `RoomMember`
- `Role`
- `Message`
- `MuteState`
- `GovernanceRule`

关键领域行为：

- `JoinOrCreateRoom`

关键约束：

- `RoomCode` 一经绑定永不回收
- 首次创建房间者成为 `Owner`
- 群主失联时可按规则转移所有权

补充说明：

- `RoomCode` 是产品核心入口，不是数据库主键，也不是前端展示用的可选字段。
- `Room` 是业务聚合根之一，成员、权限、消息读取权限等规则都应围绕它收敛。
- `JoinOrCreateRoom` 必须是显式用例，而不是散落在多个路由、多个 SQL 或多个前端页面中的隐式逻辑。
- `GovernanceRule` 不应直接写死在前端，而应由后端领域层统一判定。

## 最小接口契约

### HTTP

- `POST /session/bootstrap`
- `POST /rooms/resolve`
- `POST /rooms/join-or-create`
- `GET /rooms/{room_id}`
- `GET /rooms/{room_id}/members`
- `GET /rooms/{room_id}/messages`
- `POST /rooms/{room_id}/messages`
- `POST /rooms/{room_id}/roles/promote`
- `POST /rooms/{room_id}/roles/demote`
- `POST /rooms/{room_id}/members/{member_id}/mute`
- `POST /rooms/{room_id}/members/{member_id}/remove`

### 实时事件

- `session_ready`
- `room_joined`
- `message_created`
- `member_joined`
- `member_left`
- `member_muted`
- `role_changed`
- `room_state_changed`
- `ownership_transferred`

原则：

- 前端永远只认这些业务事件
- 不暴露底层传输或数据库语义

补充约束：

- HTTP 接口名称要表达业务动作，不表达技术动作。
- 实时事件名称要表达业务事实，不表达底层实现行为。
- 同一业务事实在 HTTP 与实时通道中的字段语义必须一致。
- 错误码必须稳定，便于未来多端前端统一处理。

## 数据库最小表设计

- `sessions`
- `profiles`
- `rooms`
- `room_codes`
- `room_members`
- `messages`
- `room_governance_logs`

关键约束：

- `room_codes.code` 唯一
- `room_codes` 永不复用
- `room_members(room_id, profile_id)` 唯一
- `messages` 需支持按 `room_id + created_at` 高效分页
- 权限变更必须记录审计日志

补充说明：

- `room_codes` 必须显式承载“永久绑定且不可回收”的产品语义，不能只靠业务注释约定。
- `messages` 表要为历史拉取和按房间分页读取服务，避免为了未来媒体、搜索而过早复杂化。
- `room_governance_logs` 不只是运维日志，它是后续做审计、申诉、接管追踪的基础。

## 消息与实时模型

第一版消息只支持文本。

消息字段：

- `message_id`
- `room_id`
- `sender_id`
- `content`
- `created_at`

实时设计原则：

- 数据库存消息真相
- 实时通道只负责分发
- 断线重连后通过 HTTP 拉历史补齐

以下能力第一版不实现，但必须预留接口位：

- `MediaPort`
- `NotificationPort`
- `PresencePort`
- `SearchPort`
- `ModerationPort`
- `AuditPort`
- `InvitePort`
- `SyncPort`
- `ProfilePort`
- `DiscoveryPort`
- `StoragePort`
- `RealtimePort`

扩展原则：

- 第一版不实现，不等于不建模。

- 扩展位之间不能相互缠绕，例如 `MediaPort` 不能直接决定 `NotificationPort` 的行为。

## 性能设计原则

本项目追求 Rust 高性能，但不为性能牺牲结构。

原则如下：

- 热点路径尽量少拷贝
- 不把“零拷贝”当教条
- 写消息先落库，再广播
- 房间是天然分片键
- 历史消息走分页，不走全量加载
- 高频状态先轻量实现，后期再专项提速
- 性能优化集中在基础设施层

### 预期热点

- `join_or_create_room`
- `send_text_message`
- `load_room_messages`
- 房间级广播 fan-out
- 长连接管理
- 权限状态一致性

### 性能约束

- 短码唯一性依赖数据库约束，不依赖内存判断
- WebSocket 连接层尽量轻状态
- 连接管理与业务规则分离
- 查询优先使用索引和游标分页

## Rust 编码风格与“代码即文档”原则

本项目要求代码可读、可维护、可演进。

目标不是依赖大量注释解释代码，而是让：

- 命名
- 类型
- 模块边界
- 公开 API
- 测试

本身就能表达设计意图。

### 总原则

- 先让类型说话，再让注释说话
- 先让模块边界清楚，再考虑技巧和缩写
- 公开 API 必须可直接读懂，不依赖上下文猜测

### 命名规则

- 类型使用 `UpperCamelCase`
- 函数、变量、模块使用 `snake_case`
- 常量使用 `SCREAMING_SNAKE_CASE`

推荐命名：

- `RoomCode`
- `RoomId`
- `SessionId`
- `MessageContent`
- `join_or_create_room`
- `transfer_ownership_if_needed`

禁止或尽量避免：

- `utils`
- `common`
- `helper`
- `misc`
- `process_data`
- `handle_room`
- `do_action`

命名要求：

- 名字必须表达业务含义
- 名字必须能回答“它是什么”或“它做什么”
- 不使用含糊缩写承担核心语义

### 类型规则

- 不裸传业务 `String`
- 不裸传业务 `Uuid`
- 不滥用 `bool`
- 优先使用明确值对象表达业务边界

例如：

- `RoomCode`
- `DisplayName`
- `MessageContent`
- `MuteState`

这样做的目的：

- 函数签名更自解释
- 参数误用概率更低
- 代码在阅读阶段就能暴露语义错误

### 函数规则

- 一个函数只表达一个明确意图
- 名字必须能直接说明功能
- 避免把多步业务规则揉进一个万能函数

例如：

- 好：`resolve_room_code`
- 好：`join_or_create_room`
- 好：`send_text_message`
- 差：`handle_room`
- 差：`process`

### 模块规则

- 一个 `.rs` 只承载一个主职责
- 模块按业务主轴切分，而不是按随意技术分类堆叠

当前推荐：

- `room.rs`
- `chat.rs`
- `session.rs`
- `contract.rs`
- `model.rs`
- `port.rs`
- `error.rs`

模块拆分原则：

- 文件过大再拆
- 文件职责变混杂再拆
- 不为“看起来专业”而提前碎片化

### 注释规则

注释只解释以下内容：

- 为什么这么做
- 这里遵守什么业务规则
- 为什么不能换一种更直观的写法
- 这里的边界或限制是什么

不要写这种注释：

- “给变量赋值”
- “调用函数发送消息”
- “遍历列表”

因为这些内容应由命名和结构自己表达。

### 文档规则

`core` 中所有公开类型、公开函数、公开用例都应写 rustdoc。

文档至少说明：

- 它是什么
- 它解决什么问题
- 输入输出含义
- 失败条件
- 业务约束

要求：

- 对 crate 写总览文档
- 对公开 API 写使用说明
- 能写示例时尽量写最小示例

### 错误规则

- 使用明确错误类型
- 错误名表达业务失败原因
- 不到处返回字符串错误

优先让调用方从类型系统就看出失败路径。

### 测试规则

测试不仅用于验证，还要承担文档职责。

测试命名必须直接表达业务规则，例如：

- `不存在短码时应自动建房`
- `首个进入者应成为群主`
- `短码创建后不应复用`

目标：

- 让测试成为可执行文档
- 让后续维护者通过测试快速理解规则

## Win11 开发方案

目标是“一键启动、即时反馈”。

开发入口：

- `run.ps1`

能力：

- 一键启动前端热更新
- 一键启动后端热更新
- 一键检查数据库连接与 migration
- 集中查看日志

建议工具：

- `cargo-watch`
- `sqlx-cli`
- `run.ps1`

可后补：

- `just`

开发体验约束：

- 开发命令必须足够短，不允许把开发启动复杂度转嫁给人工记忆。
- 任何本地依赖如果未来必须上 Linux，开发时也要保持配置模型一致。
- 开发环境允许“实现简化”，但不允许“边界简化”。

## Linux 部署方案

目标是“一键构建、一键发布、一键升级、一键回滚”。

运行方式：

- `server` 使用 `systemd`
- `web` 构建为静态资源，由 `Caddy` 或 `Nginx` 提供
- `PostgreSQL` 独立运行

运维动作：

- 一键构建
- 一键发布
- 一键迁移
- 一键重启
- 一键回滚
- 一键升级

### 一键升级要求

升级流程应包含：

1. 获取指定版本
2. 构建新版本
3. 执行 migration
4. 切换静态资源
5. 重启服务
6. 健康检查
7. 失败自动回滚

部署约束：

- 一键部署不等于单脚本乱堆命令，而是要有明确的构建、发布、迁移、切换、回滚阶段。
- 一键升级必须支持指定版本，而不是只能升级到最新版本。
- 一键回滚必须能回退后端二进制、静态前端资源和数据库迁移策略。
- 后期如果引入更多基础设施，其升级流程也必须纳入同一运维入口，而不是各自为政。

## 最终结论

这是一个面向长期演进的纯 Rust 群聊架构。

它不把任何具体框架当核心，而是把以下内容固定为系统骨架：

- 领域模型
- 用例
- 稳定契约
- 清晰边界

最终结果应当是：

- 前端未来可替换
- 后端未来可演进
- 高性能 Rust 轮子可持续接入
- Win11 开发体验与 Linux 部署体验都保持优雅
