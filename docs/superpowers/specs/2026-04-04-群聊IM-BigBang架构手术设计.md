# 2026-04-04 群聊 IM Big Bang 架构手术设计

## 1. 背景与目标

当前 `koko` 项目已经具备 `domain / app / contract / adapter` 的分层雏形，但核心链路仍存在“入口变厚、壳层编排过重、边界轻微漂移”的累积问题。  
这些问题会直接放大低级 bug 的复发概率，并拉长根因定位时间。

本次改造目标不是“局部补丁”，而是一次性 Big Bang 重构：

1. 让代码更接近 Unix 设计哲学和《群聊 IM 不再复发低级 bug 的架构铁律》。
2. 在不保留兼容负担的前提下，重排内部结构（允许破坏性调整）。
3. 让 bug 出现后能沿主链路快速定位根因。
4. 保持代码简洁高效，同时补充高价值中文注释。

## 2. 已确认约束

1. 重构策略：`Big Bang 一次性重构`。
2. 契约策略：允许破坏性调整，不做兼容层、迁移脚本、回滚方案（由 Git 历史兜底）。
3. 验收重点：  
   - 根因定位速度  
   - 分层纯度  
   - 复杂度收口  
   三者全部达成。
4. 日志体系：采用 Rust 官方生态主流方案 `tracing + tracing-subscriber + EnvFilter`。
5. 注释策略：允许高密度中文注释，但必须是“职责/边界/原因”类高价值注释，不允许动作复述噪音。

## 3. 架构目标形态

### 3.1 分层职责

1. `domain`  
   - 只保留业务不变量与真相语义：房间码、消息体、成员资格、事件位置语义。  
   - 不依赖 `axum / dioxus / sqlx / socketioxide`。

2. `application`  
   - 只保留用例编排：`join/send/subscribe/recover/admin`。  
   - 通过端口访问存储和外部能力，不直接处理协议细节。

3. `contract`  
   - 作为多壳共享唯一表面：`command / query / snapshot / event / error_code / event_position`。  
   - 禁止写入壳层展示语义与流程状态。

4. `adapter-http`  
   - 仅做 HTTP 协议翻译、鉴权接入、命令映射、错误转码。  
   - 不承载业务裁决。

5. `adapter-rt`  
   - 仅做 Socket 事件翻译、连接鉴权接入、广播适配。  
   - `room` 只作路由概念，不等于成员真相。

6. `shell-web`  
   - 只保留体验态：草稿、pending、连接提示、滚动位置。  
   - 不得宣布成员资格、权限真相、消息成立真相。

7. `store`  
   - 只保留持久化读写与事务。  
   - 不承载业务规则判断。

### 3.2 强约束

1. `ack != message_created`。  
2. `room != membership_truth`。  
3. 快照与实时必须围绕同一 `event_position` 锚点。  
4. gap 必须显式补洞；补洞失败必须显式暴露并回退快照。  
5. 禁止在 `http/rt/web` 层新增业务规则特判。

## 4. Big Bang 切刀顺序

### 切刀 1：冻结基线

1. 冻结当前外部表面（HTTP 路由、Socket 事件、contract 结构）作为对照快照。  
2. 冻结核心测试基线，作为 Big Bang 后回归对照。

### 切刀 2：重构 `web` 壳层

1. 将壳层拆为三段清晰职责：  
   - 壳状态机  
   - HTTP 调用编排  
   - Realtime bridge
2. 壳层移除业务判定，保留体验态处理与状态转译。

### 切刀 3：重构 `http + rt` 入口层

1. 统一为“协议翻译器”角色。  
2. 仅做：鉴权、解码、调用用例、映射错误、编码返回。  
3. 业务裁决全部回收至 `application`。

### 切刀 4：重构 `application`

1. 以用例为主轴重排：`join/send/subscribe/recover/admin`。  
2. 每个用例保持单一职责：  
   - 输入校验（调用 domain）  
   - 权限/成员判定  
   - 持久化事实落地  
   - 事件输出

### 切刀 5：收口 `store`

1. 去除业务语义渗透，仅保留事实模型读写。  
2. 收口重复 SQL 形状与映射逻辑。  
3. 保证事务边界由应用用例驱动，而非入口层散落控制。

## 5. 根因秒定位体系

### 5.1 统一错误模型

统一结构化错误字段：

1. `error_code`
2. `layer` (`shell|adapter_http|adapter_rt|application|domain|store`)
3. `operation`
4. `hint`
5. `retryable`

禁止“裸字符串错误”成为对外或日志主语义。

### 5.2 统一追踪键

所有关键日志统一携带：

1. `request_id`
2. `session_id`
3. `room_id`
4. `client_message_id`
5. `event_position`
6. `error_code`
7. `layer`
8. `operation`

目标：排障时单次 grep 就能锁定根因层和失败点。

### 5.3 事件位置补洞模型

1. `message_created` 必携带 `event_position`。  
2. 快照必携带 `latest_event_position`。  
3. 订阅后增量必须满足锚点约束（不早于快照锚点）。  
4. 发现 gap 进入 `recover_gap`；失败则强制重拉快照并显式报错。

## 6. 日志体系标准（Rust 官方生态）

### 6.1 技术选型

固定采用：

1. `tracing`
2. `tracing-subscriber`
3. `EnvFilter`

### 6.2 分层日志职责

1. `shell`：仅记录交互意图与体验态。  
2. `adapter`：记录协议输入输出、映射结果。  
3. `application/domain`：记录业务裁决点。  
4. `store`：记录事实读写与事务结果。

### 6.3 必须记录的关键节点

1. `join` 受理/拒绝  
2. `subscribe` 受理/拒绝  
3. `send_text_message` 受理/拒绝  
4. `message_created` 广播成功/失败  
5. `gap detect / recover / snapshot fallback`

## 7. 中文注释策略（高密度但高价值）

### 7.1 必加注释

1. 模块职责头注释：说明该模块负责什么、不负责什么。  
2. 边界约束注释：说明该层禁止承载的语义。  
3. 关键分支注释：解释“为什么这样做”，尤其是幂等、补洞、拒绝路径。  
4. 复杂数据流注释：输入事实 -> 裁决 -> 输出事实的主链路。

### 7.2 禁止注释

1. 动作复述型注释（如“这里赋值”“这里调用函数”）。  
2. 用注释掩盖坏命名或混乱边界。  
3. 壳层注释里掺入业务真相裁决。

## 8. 测试门禁与完成定义（DoD）

### 8.1 测试门禁

1. 单元：`domain / application / shell state` 关键分支全覆盖。  
2. 集成：`http / rt / store` 主链路全覆盖。  
3. E2E：进房、发消息、断线恢复三条主链全绿。

### 8.2 日志门禁

1. 抽取至少 3 条失败样例，必须能一次定位到根因层。  
2. 不允许出现“有失败但缺失追踪键”的关键日志。

### 8.3 DoD

满足以下全部条件才算完成：

1. `cargo test` 全绿。  
2. 主链 E2E 全绿。  
3. 无“壳层裁决业务真相”残留。  
4. 无“ack 当成立”残留。  
5. 无“room 当成员真相”残留。  
6. 根因定位链路可复现且可验证。

## 9. 实施后治理规则

1. 新增功能先落 `contract` 真相，再做壳适配。  
2. 入口层只做翻译，不得偷塞业务规则。  
3. 引入新机制前先证明无法复用已有机制。  
4. 每次重构后必须验证日志可追踪性，不仅验证功能正确性。

## 10. 结论

这次 Big Bang 的核心不是“把代码拆得更碎”，而是把真相归属、同步锚点、错误语义和追踪体系一次性钉死。  
只要边界清楚、日志统一、补洞机制明确，即使出现 bug，也能在最短路径内定位并修复，而不是在多层之间反复漂移。
