# Koko 管理后台入口与认证收口设计

## 1. 背景

当前仓库已经有管理后台壳代码与后台只读查询能力：

- 前端壳在 [src/admin.rs](/E:/koko/src/admin.rs)
- 后端接口在 [src/http.rs](/E:/koko/src/http.rs) 的 `/api/admin/overview` 与 `/api/admin/rooms`

但真实 `/admin` 入口在 [src/http.rs](/E:/koko/src/http.rs) 中被主动打成 `404`，导致后台体验退化成：

- 只能靠脚本提示路径
- 只能直接调后台 API
- 需要理解 `x-admin-token` 这类协议细节
- 体验问题被迫外溢到 `run.ps1`

与此同时，项目未来要部署到 Linux 公网并长期演进到多壳共核。后台入口和后台认证必须既顺手，又不能把安全真相放到前端或脚本层。

## 2. 目标

本轮只解决“管理员如何优雅、安全地进入后台”。

细化目标：

- 恢复真实 `/admin` 页面入口
- 管理后台采用“独立登录页 + 单个管理员口令”
- 管理员口令在 Windows 本地开发与 Linux 公网部署中遵守同一套来源逻辑
- 首次部署自动生成管理员口令并持久化，只打印一次供部署者备份
- 后台登录成功后只展示当前代码已经支持的内容：
  - 概览
  - 房间列表
- 后台登录态改为服务端会话，不再让前端长期持有原始管理员口令
- 后台只允许一个有效登录设备
- 连续 3 天未操作自动失效
- 服务重启后后台登录态继续有效
- `run.ps1` 只负责打印可直接访问的地址与首次生成口令提示，不再承载后台业务逻辑

## 3. 非目标

本轮明确不做：

- 不引入管理员账号体系
- 不做多管理员、RBAC、权限组
- 不新增后台功能模块
- 不新增“待开发功能占位区”
- 不改普通用户聊天主路径
- 不改 `socketioxide` 实时聊天主通道
- 不引入 React、Node.js 或其他额外前端工具链
- 不手搓底层 cookie/session 基础设施

## 4. 生态复用结论

### 4.1 不采用整套后台面板框架

已调研 Rust 生态中的后台面板轮子。当前可见的成熟方案大多绑定特定栈，例如：

- `actix-admin` 绑定 `actix-web + sea-orm + tera`
- `rwf-admin` 绑定 `rwf`
- 其他 admin template 往往绑定 `React/Vite`

这些方案都不适合直接塞进当前 `Axum + Dioxus + SQLx + socketioxide` 架构，否则会为了后台入口体验引入整套异构栈。

### 4.2 采用成熟会话轮子

后台认证与会话层复用现成 Rust 生态：

- `tower-sessions`
- `tower-sessions-sqlx-store`

理由：

- 与当前 `axum` 栈天然兼容
- 支持服务端会话、Cookie、失活过期
- 支持 `Postgres + SQLx` 持久化，满足服务重启后继续有效

### 4.3 暂不引入 `axum-login`

`axum-login` 建立在 `tower-sessions` 之上，适合多用户、多权限体系。  
但当前只有“单个管理员口令”这一种认证材料，本轮先不引入，避免提前把后台演进成账号权限系统。

## 5. 关键决策

### 5.1 后台壳与聊天壳分开

- 用户聊天入口继续是 `/`
- 管理后台入口是独立的 `/admin`
- 两个壳在产品入口和交互上分离
- 是否同进程部署不是安全重点；真正的安全边界在后端后台会话校验

### 5.2 管理员口令与后台会话分离

- `admin_token` 是管理员身份校验用的根口令
- `admin_token` 的唯一真相在服务端配置文件
- 后台会话是登录成功后由服务端签发的后台专用会话
- 后台会话的真相在 Postgres 中
- 浏览器永远不长期保存原始管理员口令，只持有后台会话 cookie

### 5.3 后台只允许单有效后台会话

- 任意设备都可以访问 `/admin`
- 但同一时刻只允许一个后台会话有效
- “单设备”在实现上精确定义为“单有效后台会话”
- 同一浏览器的多个标签页共享同一个后台会话，视为同一次登录
- 同一设备上的不同浏览器、隐私窗口、重新登录动作，都视为新的后台会话
- 新后台会话建立成功时，旧后台会话立刻失效

### 5.4 后台会话规则

- 后台会话基于服务端 cookie
- 连续 3 天未操作自动失效
- 成功访问后台数据接口时刷新活跃时间
- `GET /api/admin/session` 只做状态探测，不刷新活跃时间，避免后台轮询把会话无限续命
- 服务重启后后台会话仍可恢复

## 6. 用户流

### 6.1 首次部署与口令获取

服务启动时先读取服务端配置文件中的 `admin_token`：

1. 定位配置文件
2. 若文件存在且包含 `admin_token`，则直接使用
3. 若文件缺少 `admin_token` 但当前环境显式提供 `KOKO_ADMIN_TOKEN`，则将该值写回配置文件并作为迁移导入
4. 若两者都不存在，则生成强随机口令
5. 将新口令写回配置文件
6. 仅在本次首次生成或迁移导入成功时输出一次，供部署者复制备份

统一默认配置文件路径：

- `./config/koko.toml`

统一文件格式：

```toml
admin_token = "..."
```

责任边界：

- Rust 服务端配置加载链负责创建目录、创建文件、写回 `admin_token`
- `run.ps1` 只透传服务端首次输出，不直接写配置文件

迁移边界：

- 现有 `KOKO_ADMIN_TOKEN` 从“主路径真相”降级为“一次性迁移导入入口”
- 迁移完成后，配置文件成为唯一真相来源
- 若后续手工修改 `./config/koko.toml` 中的 `admin_token`，现存后台会话全部立即失效，必须重新登录

### 6.2 进入后台

- 启动后，控制台会明确打印：
  - 首页地址
  - `/admin` 地址
- 管理员在任意设备打开 `/admin`
- 若当前浏览器尚无有效后台会话，则显示独立后台登录页

### 6.3 登录后台

- 登录页只有一个输入项：
  - 管理员口令
- 提交后，后端校验配置文件中的 `admin_token`
- 校验成功则：
  - 废掉旧后台会话
  - 创建新后台会话
  - 写入后台专用 HttpOnly cookie
  - 返回当前已登录状态
- 校验失败则：
  - 停留在登录页
  - 显示明确错误

### 6.4 登录后使用后台

- 后台首页只展示现有代码已支持的内容：
  - 概览
  - 房间列表
- 刷新页面时，如果后台会话仍有效，则自动继续进入后台
- 不需要重新输入口令

### 6.5 会话失效

后台会话失效的原因包括：

- 3 天未操作已过期
- 已在其他设备重新登录
- 管理员主动退出

失效后：

- `/admin` 回到登录页
- 给出明确原因提示

## 7. 路由与接口

### 7.1 页面路由

- `/`：普通聊天壳
- `/admin`：后台壳入口，不再返回 `404`

### 7.2 后台认证接口

- `POST /api/admin/session/login`
  - 请求体：`{ "token": "..." }`
  - 成功：`200 OK`
  - 响应体：
    - `authenticated: true`
    - `idle_timeout_seconds: 259200`
  - 同时写入后台专用 cookie
  - 失败：`401 Unauthorized`
  - 错误码：`invalid_admin_token`
- `GET /api/admin/session`
  - 校验当前后台 cookie 是否仍有效
  - 供后台壳启动时判断“是否已登录”
  - 成功：`200 OK`
  - 响应体：
    - `authenticated: true`
    - `idle_timeout_seconds: 259200`
  - 失败：`401 Unauthorized`
  - 错误码：
    - `admin_session_required`
    - `admin_session_expired`
    - `admin_session_replaced`
- `POST /api/admin/session/logout`
  - 主动退出后台
  - 让当前后台会话失效并清除 cookie
  - 成功：`204 No Content`

### 7.3 后台数据接口

- `GET /api/admin/overview`
- `GET /api/admin/rooms`

这两个接口继续复用现有只读能力，但鉴权入口改为后台会话 cookie。  
不再让前端通过 `x-admin-token` 长期直接访问后台数据。

若后台会话失效：

- `401 Unauthorized`
- 错误码：
  - `admin_session_required`
  - `admin_session_expired`
  - `admin_session_replaced`

## 8. 真相落点

### 8.1 服务端配置文件

服务端配置文件负责保存：

- `admin_token`

它是管理员登录时校验口令的唯一真相来源。

### 8.2 后台会话存储

后台会话持久化在 Postgres，分两层：

- 通用会话存储：复用 `tower-sessions-sqlx-store`
- 后台单设备规则真相：新增一张很小的后台会话约束表，用于记录当前唯一有效后台会话

这样可以做到：

- 不手搓底层 session/cookie 基础设施
- 仍然把“后台只允许一个设备有效”这条业务规则留在自己掌控的真相层

### 8.3 前端本地状态

前端只拥有：

- 当前是否已登录
- 当前错误提示
- 页面加载状态

前端不保存：

- 原始管理员口令
- 后台认证真相

### 8.4 读取失败策略

- 若 `./config/koko.toml` 不存在，则由服务端创建
- 若父目录不存在，则由服务端创建
- 若配置文件存在但无法解析，则服务启动直接报错退出，不允许静默回退到默认口令
- 若配置文件存在但缺少 `admin_token`，按首次初始化规则处理

## 9. 平台一致性

### 9.1 Windows 本地开发

- 第一次启动若没有 `admin_token`，自动生成并输出一次
- 后台地址直接可见
- 本机与局域网设备都可访问 `/admin`

### 9.2 Linux 公网部署

- 第一次部署若没有 `admin_token`，自动生成并输出一次
- 部署者应当当场复制并备份
- 后续重启不重复打印真实口令
- 默认仍使用工作目录下的 `./config/koko.toml`

### 9.3 一致的使用心智

不管开发还是生产，管理员理解的都是同一条规则：

- 后台地址是 `/admin`
- 第一次部署会拿到一次管理员口令
- 后续靠后台登录页输入口令进入
- 登录后靠后台会话保持状态

## 10. `run.ps1` 的收口职责

`run.ps1` 只负责：

- 启动服务
- 打印首页地址
- 打印局域网访问地址
- 打印 `/admin` 地址
- 若本次是首次生成管理员口令，则把这一次输出透传出来，方便开发者复制备份

`run.ps1` 明确不再负责：

- 解释后台 API
- 解释 header 细节
- 承担后台产品入口
- 承担后台认证真相

## 11. 测试策略

本轮测试只围绕后台入口体验、统一口令来源、后台会话规则和生态复用收口。

最小测试集：

- `/admin` 路由真实可进入，不再 `404`
- 未登录访问 `/admin` 时显示管理员登录页
- 正确口令可登录并进入现有后台首页
- 错误口令被拒绝并显示明确错误
- 登录后可读取概览和房间列表
- 刷新后若后台会话仍有效，可自动继续进入后台
- 同一浏览器多标签共享后台会话
- 新设备登录会顶掉旧设备
- 同一设备不同浏览器或隐私窗口登录，也会顶掉旧会话
- 旧设备再次请求后台时会被打回登录页
- 连续 3 天未操作后后台会话自动失效
- 服务重启后后台会话仍有效
- 配置文件缺少 `admin_token` 时，首次启动会生成并写回
- 仅存在 `KOKO_ADMIN_TOKEN` 时，会迁移导入并写回配置文件
- 已存在 `admin_token` 时，后续启动不会重复生成
- 启动输出持续打印首页地址、局域网地址和 `/admin`
- 仅在首次生成口令时打印一次真实口令

## 12. 风险与控制

### 风险 1：继续手搓底层会话系统

控制：

- 会话基础设施复用 `tower-sessions`
- 自己只实现“单设备有效”这一条业务规则薄层

### 风险 2：为了后台引入整套异构栈

控制：

- 后台壳继续复用现有 Dioxus
- 不引入 React/Node 或特定框架后台模板

### 风险 3：原始管理员口令继续在前端长期停留

控制：

- 前端不保存原始管理员口令
- 只使用后台会话 cookie

### 风险 4：后台入口恢复后顺手扩展一堆功能

控制：

- 本轮只展示现有概览与房间列表
- 新后台能力必须另开设计

### 风险 5：过期会话垃圾长期堆积

控制：

- 认证行为先依赖 `tower-sessions` 的失活过期能力
- 存储清理作为后续可独立补的卫生项，不阻塞本轮后台入口体验修复

## 13. 实施边界

本轮预计主要落点：

- [src/http.rs](/E:/koko/src/http.rs)
- [src/admin.rs](/E:/koko/src/admin.rs)
- [src/support.rs](/E:/koko/src/support.rs)
- 存储与迁移层
- [run.ps1](/E:/koko/run.ps1)
- 相关测试

不应扩散到：

- 聊天主页面壳设计
- 实时主通道协议
- 普通用户身份体系
- 后台数据模型扩展

## 14. 最终裁决

这轮最正确、最克制、最不容易继续长歪的方向是：

- 把后台体验拉回 Rust 主应用
- 恢复真实 `/admin` 入口
- 管理员口令真相统一到服务端配置文件
- 后台登录态统一收口为服务端会话
- 会话基础设施站在成熟 Rust 生态轮子上
- 只把“单设备登录、3 天失活、重启续存”这些后台业务规则留在项目自己的薄层里
- 把脚本重新压回启动辅助，而不是继续让它长成后台胶水中心
