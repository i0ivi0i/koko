# Koko 管理后台入口与认证收口设计

## 1. 背景

当前仓库已经有管理后台壳代码与后台只读查询能力：

- 前端壳在 [src/admin.rs](/E:/koko/src/admin.rs)
- 后端接口在 [src/http.rs](/E:/koko/src/http.rs) 的 `/api/admin/overview` 与 `/api/admin/rooms`

但真实 `/admin` 入口在 [src/http.rs](/E:/koko/src/http.rs) 中被主动打成 `404`，导致后台体验退化成：

- 只能靠脚本提示路径
- 只能直接调后台 API
- 需要理解 `x-admin-token` 这类协议细节
- 体验问题被迫外溢到 `run.ps1`

这不符合本项目“多壳共核、adapter 只翻译、shell 承担交互、脚本不承载产品逻辑”的长期边界。

## 2. 目标

本轮只解决一件事：

- 让管理员能够通过真实 `/admin` 页面顺滑进入后台

细化目标：

- 恢复真实 `/admin` 页面入口
- 后台登录改成“独立登录页 + 单个管理员口令”
- 本地 Windows 与未来 Linux 公网部署共用同一套管理员口令来源规则
- 首次部署自动生成管理员口令并写入配置文件，只打印一次供部署者备份
- 管理后台登录后只展示当前代码已经支持的内容：
  - 概览
  - 房间列表
- 浏览器本地保存管理员口令，刷新后自动恢复后台
- `run.ps1` 只打印首页地址与 `/admin` 地址，不再承载后台 API 使用说明

## 3. 非目标

本轮明确不做：

- 不引入管理员账号体系
- 不做后台专用 session / cookie 认证体系
- 不新增后台功能模块
- 不新增“待开发功能占位区”
- 不改普通用户聊天主路径
- 不让 `run.ps1` 继续膨胀成认证中心或后台文档页

## 4. 设计约束

- 保持纯 Rust 主线，不引入额外前端工具链或新运行时
- 业务真相继续在后端，前端本地存储只保存上次输入的管理员口令，不是权威来源
- 管理后台体验必须回到 Rust 应用主链，而不是脚本层补洞
- 现有后台数据模型优先复用，不凭空扩写字段或未来状态
- 首次生成管理员口令的初始化逻辑必须收口到服务端配置加载链路，而不是长期依赖 `run.ps1`

## 5. 选定方案

采用最小恢复方案：

1. 恢复 `/admin` 路由
2. 复用现有 [src/admin.rs](/E:/koko/src/admin.rs) 作为后台壳
3. 管理员认证仍为单个管理员口令
4. 管理员口令真相收口到服务端配置文件
5. 首次启动自动生成并写回配置文件
6. `run.ps1` 只做启动辅助与首次口令展示

不采用以下方案：

- 不继续靠脚本打印 API 和 header 引导进入后台
- 不在本轮扩成正式管理员账号系统
- 不把真实口令长期暴露到日志

## 6. 后台入口流

### 6.1 页面入口

- `/admin` 恢复为真实管理后台页面
- `/api/admin/overview` 与 `/api/admin/rooms` 保留为后台只读查询接口
- `/admin` 不再返回 `404`

### 6.2 登录体验

- 访问 `/admin` 时先进入独立管理员登录页
- 登录页只有一个输入框：
  - 管理员口令
- 提交成功后：
  - 拉取概览
  - 拉取房间列表
  - 进入现有后台壳
- 提交失败后：
  - 停留在 `/admin`
  - 给出清晰错误提示

### 6.3 登录态保持

- 浏览器本地保存管理员口令
- 刷新 `/admin` 页面时自动尝试恢复
- 如果本地保存的口令已失效：
  - 清掉本地旧值
  - 回到登录页
  - 显示明确错误

## 7. 管理员口令统一来源

### 7.1 真相来源

- 管理员口令唯一真相在服务端配置文件
- 前端不拥有口令真相，只拥有上次输入缓存

### 7.2 首次初始化规则

服务端启动时：

1. 定位配置文件
2. 读取 `admin_token`
3. 若存在则直接使用
4. 若不存在则生成强随机口令
5. 写回配置文件
6. 仅在首次生成成功时打印一次供部署者复制备份

### 7.3 后续启动规则

- 若配置文件已有 `admin_token`：
  - 直接使用
  - 不重复生成
  - 不重复打印真实口令

### 7.4 丢失口令处理

- 通过重置配置文件中的 `admin_token` 恢复
- 不依赖翻日志找回旧口令

## 8. 配置文件策略

### 8.1 统一逻辑

Windows 本地开发与 Linux 公网部署遵守同一逻辑：

- 同一字段名
- 同一首次生成规则
- 同一后续读取规则

### 8.2 平台落点

- Windows 本地开发：
  - 放在项目内一个清晰、可见、可备份的配置文件
- Linux 公网部署：
  - 放在系统约定配置目录中的同名配置文件

差异只在默认落点，不在初始化逻辑。

## 9. `run.ps1` 的收口职责

`run.ps1` 本轮收口后只负责：

- 启动服务
- 打印首页地址
- 打印 `/admin` 地址
- 若本次是首次生成管理员口令，则打印一次新口令供复制备份

`run.ps1` 明确不再负责：

- 解释后台 API
- 解释 header 细节
- 承担后台产品入口
- 维护独立认证真相

## 10. 架构治理与技术债结论

本轮本质是一次技术债收口，而不是新增后台功能。

要主动消掉的债：

- 后台壳已存在却没有真实入口
- 体验问题被迫外溢到 `run.ps1`
- 访问后台需要理解 API/header 细节
- 开发与部署的管理员口令逻辑分叉

本轮刻意不新增的债：

- 不引入第二套后台数据接口
- 不引入账号密码体系
- 不引入后台专用 session/cookie 体系
- 不引入未来功能占位和死代码

## 11. 测试策略

本轮测试只围绕真实体验链路与统一口令来源。

最小测试集：

- `/admin` 路由真实可进入
- `/admin` 首屏为管理员登录页
- 正确口令能加载现有概览与房间列表
- 错误口令停留在登录页并显示错误
- 刷新后若本地已保存口令，会自动恢复后台
- 配置文件缺少 `admin_token` 时，服务端首次启动会生成并写回
- 已存在 `admin_token` 时，后续启动不会重复生成
- `run.ps1` 默认只打印首页地址与 `/admin` 地址
- `run.ps1` 仅在首次生成时打印一次新口令

## 12. 风险与控制

### 风险 1：把首次口令生成逻辑继续堆在脚本层

控制：

- 初始化逻辑必须进服务端配置加载链
- 脚本只消费结果，不拥有真相

### 风险 2：后台入口恢复后又开始顺手扩后台功能

控制：

- 本轮只展示现有概览与房间列表
- 任何新后台能力另开设计

### 风险 3：浏览器本地保存口令被误当成真相

控制：

- 明确本地存储只是恢复体验
- 后端配置文件才是唯一真相

### 风险 4：生产日志泄露管理员口令

控制：

- 只在首次生成时打印一次
- 后续启动不打印真实口令

## 13. 实施边界

本轮预计主要落点：

- [src/http.rs](/E:/koko/src/http.rs)
- [src/admin.rs](/E:/koko/src/admin.rs)
- 现有前端入口装配链路
- 服务端配置加载链路
- [run.ps1](/E:/koko/run.ps1)
- 相关测试

不应扩散到：

- 聊天主页面壳设计
- 实时主通道协议
- 普通用户身份体系
- 后台数据模型扩展

## 14. 最终裁决

这轮最正确、最克制、最不易继续长歪的方向是：

- 把后台体验拉回 Rust 主应用
- 恢复真实 `/admin` 入口
- 让管理员口令来源统一为服务端配置文件
- 用首次生成并持久化的方式同时满足本地开发与 Linux 公网部署
- 把脚本重新压回启动辅助，而不是继续让它长成后台胶水中心
