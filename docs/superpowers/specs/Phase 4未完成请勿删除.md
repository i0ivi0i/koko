# 群聊媒体 WebTorrent 协作分发与 24 小时 Web Seed 设计

日期：2026-04-11  
状态：Draft  
适用范围：`koko` 的群聊图片、视频分发主链，并为未来普通文件预留同一套协作分发骨架  
关联文档：

- `docs/superpowers/specs/2026-04-11-群聊媒体上传切换到Tus与Rustus-design.md`
- `docs/superpowers/specs/2026-04-10-群聊媒体P2P热分发与锚点持久化-design.md`

## 1. 这份设计解决什么问题

当前仓库已经把首次上传主链收到了：

`prepare -> tus/rustus -> complete -> create_message`

这条链在代码里已经成立：

- `src/房间外壳.rs::prepare_media_upload()` 负责创建 `prepared` 附件并下发 Tus 契约。
- `src/房间外壳.rs::complete_media_upload()` 负责消费权威字节、提取媒体元数据、把附件升级成 `ready`。
- `frontend/媒体/媒体发布.ts::创建默认媒体上传器()` 已经改成 `@uppy/tus`，前端不再伪装成 S3 上传。

所以当前真正缺的不是“怎么让 A 把第一份字节传进来”，而是：

- 附件 `ready` 之后，后续观看者如何不再长期依赖服务器直出；
- 如何把看过的用户变成新的分发者；
- 如何让服务器只承担短期保底，而不是长期字节仓库。

这里最容易出现的错误理解是：

- 以为“现在要做 P2P”就该把现有 `Tus/Rustus` 主链一起换掉；
- 以为“以后要让群友互相分发”就意味着后端不再需要第一份权威字节；
- 以为“浏览器里已经缓存过文件”就等于系统已经拥有了可控的长期副本。

这三种理解都会把实现重新带回混乱状态。  
所以这份设计的真实任务不是“再发明一条媒体链”，而是：

**在不破坏现有首次上传真相层的前提下，补上一条协作分发层。**

## 2. 目标与非目标

### 2.1 目标

- 保留当前 `Tus/Rustus` 首次上传真相层，不重写 `prepare -> complete -> create_message`。
- 让 Linux 公网服务器只承担 24 小时字节保底。
- 第一版先把 24 小时保底源直接挂在现有 Linux 公网服务器上，先简单跑通，不先拆边车。
- 前期只有 Web 时，浏览器就是主力 peer。
- 已观看用户默认进入协作上传集合，不提供关闭开关。
- 第一版不提供“开始分享 / 停止分享 / 重新加入分发”这类手动按钮。
- 压力必须分散到 B/C/D/E 等多个 peer，不能退化成“所有人只从 B 拉”。
- 第一版图片和视频一起落地，同时命名、契约和分发元数据形状要为未来普通文件预留统一骨架。
- 第一版单个附件上限固定为 `200MB`，先把主链跑稳，不追求超大文件。
- 超过 24 小时后，如果网络里已经没有任何副本，附件允许自然失活，但消息继续存在。

这些目标合在一起，其实只表达一个总方向：

- 服务器负责把内容送进系统、短期托底；
- swarm 负责把内容尽快扩散到更多在线用户；
- 业务层始终只承认“附件是否 ready、消息是否成立”，不承认“现在有没有人在线做种”。

### 2.2 非目标

- 不承诺永久免费保存所有媒体。
- 不把 IPFS / Helia / BTFS 拉进第一阶段主链。
- 不让 WebTorrent 取代 `Tus/Rustus` 的首次入站职责。
- 不在第一阶段就要求 iOS/Android/PC/CLI 一起上。
- 不在第一阶段就把超大文件、长视频或海量普通附件一口气全部打开。
- 不承诺对已经拿到明文字节的恶意客户端做物理回收。

## 3. 候选路线与裁决

### 3.1 不选的路线

- 纯中心化直出：长期硬盘和带宽都回到服务器，直接违背产品方向。
- 纯 WebTorrent 主链：冷启动太脆，后端也拿不到稳定的第一份权威字节。
- IPFS / Helia / BTFS 主链：当前阶段复杂度过高，而且持久可用性仍依赖额外保活机制。

### 3.2 最终裁决

本项目媒体主链固定拆成两层：

1. 上传真相层：继续使用 `Tus/Rustus`
2. 协作分发层：使用 `WebTorrent + 私有 swarm 门禁 + 24 小时 Web Seed`

一句话：

`Tus` 负责“让内容先成立”，`WebTorrent` 负责“让内容继续扩散”。

这里再补一句因果链，防止后面实现时偷换：

- 没有 `Tus/Rustus` 的权威第一份字节，后端就失去 `complete -> ready` 的稳定落点；
- 没有 `WebTorrent + Web Seed`，服务器就永远还是唯一长期字节源。

所以这不是两个可互换方案，而是两个职责不同、先后相接的层。

## 4. 关键边界

### 4.1 后端仍是业务真相权威

后端只掌握这些事实：

- 附件是否存在
- 附件属于谁
- 附件当前是否 `prepared / ready / degraded / deleted`
- 哪条消息引用了哪个附件
- 当前请求者是否有权拿到附件分发元数据

后端不把这些运行态当作业务真相：

- 当前 peer 数
- tracker 是否抖动
- 谁现在缓存了哪些块
- 某次 WebRTC 握手是否成功

原因很直接：

- 这些运行态都可能在几十秒内剧烈变化；
- 但消息是否成立、附件是否 ready、用户是否有权访问，不能跟着这些抖动一起漂。

如果把运行态塞进领域真相，后面就一定会出现这种错误逻辑：

- “现在暂时没人在线” 被误判成 “附件无效”；
- “tracker 抖了一下” 被误判成 “消息发送失败”；
- “peer 数变少” 被误判成 “系统需要回滚业务状态”。

### 4.2 服务器只做 24 小时保底源

Linux 服务器对每份媒体只承担：

- 初始可达；
- swarm 冷启动兜底；
- 24 小时内补缺块。

24 小时一到：

- 服务器删字节；
- 后端保留元数据；
- swarm 继续或自然失活。

这里的 24 小时不是一个随手写的数字，而是产品裁决的一部分：

- 它足够覆盖“刚发出去的热内容”最容易被观看和扩散的窗口；
- 它又不会把服务器重新拖回长期仓库角色。

这里再写死一个实现门槛：

- `24 小时` 保底窗口从附件变成 `ready` 开始算；
- 不能从 `prepare` 或上传开始时起算。
- 第一版先直接挂在现有 Linux 公网服务器上，不为了“看起来更优雅”提前拆成独立 Web Seed 边车。

如果后面真的想改成 12 小时、72 小时或更长，那应该重新改设计，而不是在实现里偷偷延长保留期。

### 4.3 Web 前端在前期就是主力 peer

前期只有 Web，所以浏览器不是“顺手帮忙”，而是第一代主力分发节点。  
但要同时承认它的运行时边界：

- 关页就断；
- 后台会被冻结或限速；
- 缓存清理不可控。

因此正确结论是：

- 前期 Web 是主力 peer；
- 但 Web 不是永久 keeper。

这条边界非常重要，因为它同时阻止两个极端：

- 不能把 Web 当成“只是辅助”，那会让前期 swarm 根本长不起来；
- 也不能把 Web 当成“稳定 seedbox”，那会让后续设计错误地忽略桌面 helper / keeper 的价值。

## 5. 端到端数据流

### 5.1 A 发送图片/视频

1. 前端调用 `prepare_media_upload()`。
2. 后端创建 `prepared` 附件并下发 Tus 契约。
3. A 通过 `Tus/Rustus` 上传第一份权威字节。
4. 后端 `complete_media_upload()` 消费字节并把附件升级成 `ready`。
5. 只有这一步之后，消息才允许引用该附件。

这里必须写死：

- `WebTorrent` 不参与“附件从无到有”的真相建立。

否则会立刻遇到三个工程问题：

1. A 还没把第一份权威字节完整送进系统，就可能先离线；
2. 后端没法稳定提取图片/视频元数据并写回 canonical store；
3. “发送端暂时在线”会被错误地当成“附件已经成立”。

### 5.2 附件 ready 后生成分发元数据

附件 `ready` 之后，系统生成分发侧最小锚点：

- `attachment_id`
- `content_id`
- `content_hash`
- `swarm_id` 或 `torrent_info_hash`
- `web_seed_until`

这些元数据只服务于后续分发，不决定消息是否成立。

第一版还有一个体验优先约束要写死：

- 只要附件已经 `ready`，消息就允许先发出去；
- 协作分发元数据和后续分发接线必须紧随其后；
- 不得把“分发侧是否已经完全暖起”当成消息发送的前置阻塞条件。

这里还有一个容易漂移的点：

- `attachment_id` 仍然是业务锚点；
- `content_id / swarm_id / torrent_info_hash` 是分发锚点。

并且 canonical 分发元数据必须由系统稳定生成，而不是每个客户端各自临时算一份：

- 要么由后端在 `ready` 之后基于 canonical 字节生成；
- 要么由受控后台任务基于 canonical 字节生成；
- 客户端只消费它，不各自发明第二份 torrent/metainfo。

后续如果实现里让 `magnet` 或 `info_hash` 反过来成为业务主键，那就说明边界已经错了。

### 5.3 B 第一次观看

1. B 点击媒体。
2. 前端先向后端请求附件分发元数据，而不是假设某个直链永远存在。
3. 后端校验权限。
4. 权限通过后，返回：
   - swarm ticket
   - magnet/torrent 元数据
   - web seed 信息
5. B 一开始查看，就立即进入协作分发流程，而不是等“看完再说”。
6. B 客户端优先向 peer 请求块；如果此时 swarm 还弱，就从 24 小时 web seed 补块。
7. 一旦开始查看，客户端就默认尽快在后台补齐整个附件，而不是只按当前观看进度懒加载。
8. B 在补齐过程中先分享已经拿到的块；补齐之后，默认作为完整分发者继续在线接力。

这一步的关键不是“B 从哪一个源下到完整文件”，而是：

- 系统要尽快把“只有服务器和 A 有完整内容”的状态，
- 转成“服务器、A、B 都持有部分或全部块”的状态。
- 这里的“B 看过后”指的是“B 已经开始查看并进入协作分发流程”，不是“B 把整个附件完整看完之后”。

只要这一步发生，后续观看者就开始有机会从多源并发拉取，系统才真正进入正反馈。

### 5.4 C / D / E 后续观看

正确目标不是“都从 B 一个人拉”，而是：

- 文件按 piece 分发；
- 后来的观看者同时向 B / C / D / E / web seed 请求不同块；
- 服务器只补缺口，不长期包办全部字节。

这也是为什么成熟 swarm 都是 piece-based，而不是“整文件从单个节点复制”。  
如果实现里看起来还是“谁先看完谁就成为唯一源”，那其实做的不是 swarm，只是换皮的单点中继。

### 5.5 清缓存后重新观看

用户以前是否看过，不重要。  
只要本地现在没有块，就像新请求者一样重新加入 swarm。  
判断依据只有一个：

**当前网络里是否还有可达副本。**

这个结论和传统“本地上传成功后永远从自己的 CDN 回放”完全不同。  
这里的系统承诺不是“你以前看过，所以平台永远替你存着”，而是：

- 只要当前网络里还有来源，你随时都能重新拉；
- 如果当前网络里已经没有任何来源，附件就自然失活。

### 5.6 24 小时之后

- 如果 swarm 里还有副本，附件继续可用；
- 如果已无任何副本，后端明确裁决为“当前不可获取”，前端统一显示“内容已过期”；
- 消息继续存在，不被误判为删除或无效。

## 6. 协作分发规则

### 6.1 不允许把压力全部给一个 B

实现如果退化成：

- B 看过；
- 后面所有人都默认只从 B 拉；

那就说明 swarm 设计失败了。

### 6.2 目标是榨干整体 swarm，而不是保护单个用户

前期产品哲学已经明确：

- 不提供“关闭协作上传”开关；
- 不提供“开始分享 / 停止分享 / 重新加入分发”按钮；
- 观看过、缓存过、拿到过块的在线用户，默认都进入资源池；
- 控制面存在的目的，是避免 swarm 自己乱掉，不是保守地少传。

这意味着后续任何“为了用户省一点上传”而默认缩成单源、少 peer、低并发的实现，都会直接违背这份设计。  
前期这里的默认价值排序是：

1. 先让 swarm 真正长起来；
2. 先让整体吞吐上去；
3. 再在不伤架构的前提下做更细的资源治理。

### 6.3 仍然需要调度，不是无限裸传

需要调度的原因不是“保护用户”，而是：

- 避免所有连接都压到一个 peer；
- 避免浏览器开无限连接先把自己卡死；
- 避免重复拉同一批块，浪费总吞吐。

所以后续调度目标应写成：

- 最大化 swarm 总吞吐；
- 最小化单点热点。

也就是说，这里不是“要不要治理”，而是“治理目标是什么”。  
治理目标不是让所有人尽量轻松，而是让单个 B 不成为唯一瓶颈、让多 peer 更快长出来。

## 7. 权限、门禁和治理

### 7.1 不走公开 tracker

如果直接把群聊媒体丢给公开 tracker，后端就失去准入门禁。  
这和当前房间/成员权限模型冲突。

### 7.2 推荐形态：私有 WSS tracker + 后端签发短期 swarm ticket

流程固定为：

1. 客户端向后端请求附件分发元数据；
2. 后端校验会话、房间成员资格、附件状态；
3. 校验通过后，签发短期 swarm ticket；
4. 客户端拿 ticket 加入对应 swarm。

这样 tracker 只负责 peer 发现，不负责业务裁决。

这里的 ticket 也不能只是一串“能用就行”的随机字符串，至少应绑定：

- `attachment_id`
- `room_id`
- `session_id`
- 短过期时间

这样删除、封禁、退群和附件失效才有稳定的生效面。

但第一版的落法要更克制：

- 先把 ticket 的接口位置、字段位置和中文注释写好；
- 先把 `load_media_locator()` 一侧的门禁落点和后续切换面预留出来；
- 不为了赶第一版上线，把所有入口一次性强切到“无 ticket 完全不让进”。

这条门禁是刚需，不是锦上添花。  
如果没有它，后面会立刻出现两个问题：

- 任何拿到 swarm 标识的人都可能尝试加入；
- 后端删除/封禁附件时，会失去最重要的生效入口。

### 7.3 删除 / 封禁

后端删除或封禁附件时，至少必须做到：

- 停止签发 swarm ticket；
- 停止返回 web seed；
- cooperative 客户端收到 tombstone 后停止继续分享并清理缓存。

但不能对外承诺：

- 技术上抹掉所有已经发出去的明文字节。

这里要非常诚实：  
协作分发网络能做的是“停止继续帮助分发”，不能神化成“从世界上收回所有曾经发出去的字节”。  
这不是设计缺陷，而是选择 P2P 分发之后必须接受的物理边界。

## 8. 本地缓存裁决

### 8.1 不能只靠“预览缓存”

如果后续实现仍然把浏览器缓存理解成：

- 只是给本地 `<img>` / `<video>` 预览复用一下；

那这套 swarm 根本长不起来。

真正需要的是：

- 明确的 piece cache；
- 能支撑再次观看时复用；
- 能支撑给其他 peer 继续提供块。
- 能支撑“开始查看后尽快补齐整个附件”，而不是只缓存已经播放过的那一小段。

### 8.2 第一阶段缓存的真实角色

第一阶段浏览器缓存承担三件事：

1. 用户自己重看时减少回源；
2. 用户在线时给别人继续接力；
3. 在页面刷新或短暂重连后恢复当前 swarm 参与状态。

但它不承担：

- 永久存储；
- 绝对可靠保种；
- 替代未来桌面 helper / keeper。

再补一个实现约束：

- 浏览器 piece cache 是“尽量保留”的运行态缓存；
- 不得把它当成业务真相或长期保种承诺；
- 一旦因为浏览器配额、回收或用户清理而丢失，系统应回到“重新加入 swarm / 回退 web seed”的正常路径。
- 第一版目标是“在就传，刷新尽量续，关页就停”，不假装纯浏览器能做到永久在线保种。

## 9. 实施分期

### Phase 1：补齐分发元数据

- 不碰现有 `Tus/Rustus` 主链；
- 只为 `ready` 附件补齐 `content_id / content_hash / swarm_id / web_seed_until`；
- 这一步从第一版开始同时覆盖图片和视频，并让字段和契约为未来普通文件预留统一骨架。

这一阶段故意不做：

- 真正的 swarm 下载；
- tracker 接线；
- 浏览器 piece cache。

原因是先把“分发元数据真相面”准备对，后面每一层才能有稳定落点。

### Phase 2：让 Web 前端进入 swarm，服务器 24 小时保底

- 发送成功后开始 seed；
- 查看时优先尝试 swarm，再回退 web seed；
- 一旦开始查看，就默认尽快在后台补齐整个附件，而不是只按观看进度懒加载。

这一阶段故意不追求：

- 去掉服务器；
- 长尾永久可用；
- 多端 keeper。

### Phase 3：强化多 peer 调度

- 多 peer 并发拉取；
- 服务器只补缺块；
- 避免单个 B 成为唯一热点。

这一阶段才是“榨干所有在线用户但不单点压垮”的真正开始。  
没有这一步，前面的 Web swarm 只能算“能连起来”，还不能算“能有效分担”。

### Phase 4：引入强 peer

- 桌面 helper；
- NAS keeper；
- 志愿 seed 节点。

这一阶段主要解决 24 小时之后的长尾可用性。

### 第一版代码落位建议

- 后端新增 `src/媒体协作分发.rs`
- 前端新增 `frontend/媒体/媒体协作分发.ts`

这两个文件都只负责协作分发本身，不负责把上传主链、消息真相、页面展示和协议细节揉成一个“大总管”。

`src/媒体协作分发.rs` 负责：

- `ready` 之后的分发元数据收口；
- 24 小时窗口与过期裁决；
- locator 里的分发线索补齐；
- 后续严门禁 ticket 的接口落位与中文注释。

`frontend/媒体/媒体协作分发.ts` 负责：

- 自动加入协作分发；
- “在就传，刷新尽量续，关页就停”的浏览器运行策略；
- swarm 与 24 小时保底源之间的回退；
- 给壳层提供简单、稳定的状态提示。

这里故意不推荐直接新增 `P2P.rs / P2P.ts` 这种大而虚的文件名，因为它太容易长成什么都往里塞的杂物间。

## 10. 实施时最容易漂移的点

后续写计划和代码时，必须守住这几条。

1. 不允许 `WebTorrent` 取代 `Tus/Rustus` 的首次入站职责。
2. 不允许用 peer 可达性去定义消息成立。
3. 不允许把 `seeding / peerless / tracker_failed` 这类运行态做成领域状态。
4. 不允许把“Web 前期主力 peer”实现成“浏览器看完就算了”的假 swarm。
5. 不允许把 24 小时 web seed 偷偷扩张成长期仓库。
6. 不允许把“开始查看后进入协作分发”写成“完整看完后才进入协作分发”。
7. 不允许把协作分发实现成只按观看进度懒加载，而不尽快补齐整个附件。
8. 不允许把“内容已过期”交给前端自己猜，必须由后端裁决、前端展示。
9. 不允许为了图快再做“开始分享 / 停止分享 / 重新加入分发”按钮，把复杂性甩给用户。
10. 不允许新增 `P2P.rs / P2P.ts` 这种大而虚的总管文件，制造第二核心。

再补三个更细的 red flag：

11. 不允许让 `content_id / info_hash` 反客为主，取代 `attachment_id` 作为业务锚点。
12. 不允许把“自然失活”错误展示成“已删除”或“无权限”。
13. 不允许为了图省事，把后续观看流量默认仍然全打回服务器。

## 11. 验证要求

这部分不是计划明细，但以后实现至少要证明这些事情。

### 11.1 上传真相层回归

- `prepare` 仍然只创建 `prepared`
- `complete` 仍然只在权威字节成立后升级 `ready`
- `create_message` 仍然只引用 `ready` 附件

### 11.2 协作分发层回归

- A 发出后，B 第一次观看可以从服务器补块成功；
- B 只要开始查看，就会立即进入协作分发流程，而不是等“看完再说”；
- B 即使只看了部分内容，后台也会默认尽快补齐整个附件，而不是只缓存已播放片段；
- B 看过后，C 来时不只连接 B；
- C / D / E 看过后，后续观看者可以从多 peer 并行拿块；
- 24 小时后服务器退出时，如果 swarm 还有 peer，附件继续可用；
- 24 小时后如果已无任何副本，后端裁决过期，前端统一显示“内容已过期”；
- 同一份 `attachment_id` 对应的 canonical 分发元数据稳定，不会因为不同客户端各自生成 metainfo 而出现多套 swarm。

### 11.3 权限与治理回归

- 非成员拿不到 swarm ticket；
- 附件被删/封后，后端不再返回 swarm 准入和 web seed；
- cooperative 客户端收到 tombstone 后停止继续分享。

## 12. 最终结论

本项目图片/视频的 canonical 路线正式定为：

**首次入站：`Tus/Rustus`**  
**后续扩散：`WebTorrent + 私有 swarm 门禁 + 24 小时 Web Seed`**

这条设计只表达三件事：

1. 后端继续掌握业务真相，消息只引用 `ready` 附件。
2. 第一版先把 24 小时保底直接挂在现有 Linux 服务器上，但它只做短期保底，不重新长成长期媒体仓库。
3. 前期 Web 前端就是主力 peer，所有在线观看者默认自动进入强制协作上传集合，不提供手动分发按钮，并通过多 peer 并发共同分担压力。
