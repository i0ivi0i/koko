# supcode 通用代码宪法技能设计

日期：2026-04-05

## 1. 文档定位

这份文档用于定义 `supcode` 的稳定设计。

`supcode` 不是普通代码生成 skill，也不是“用户提到架构时才出来点评两句”的被动 review skill。

它的定位是：

1. 面向任意编程语言、任意技术栈、任意代码项目的通用代码宪法 skill
2. 在所有代码相关请求上高敏感自动触发的前置守门 skill
3. 在主代理与 subagent 准备写代码、改代码、删代码、审代码、重构代码、验证代码时都默认先触发的统一守门层
4. 优先做取证、分层、裁决与阻断，只有在方案合规后才允许进入实施

这份设计文档优先回答以下问题：

1. `supcode` 到底是什么，不是什么
2. `supcode` 应该在什么时机自动触发
3. `supcode` 先做什么，后做什么，绝不能跳过什么
4. `supcode` 应该阻断哪些方案，放行哪些方案
5. `supcode` 的输出必须长什么样，怎样保持简洁精炼不废话
6. 如何防止 `supcode` 未来发生功能漂移、性能漂移、触发漂移与判断力漂移

这份文档不是对某个项目的专项绑定说明，而是 `supcode` 的母法设计。

`koko` 当前的 [2026-04-04-群聊IM-DDD稳定骨架设计.md](E:\koko\docs\superpowers\specs\2026-04-04-群聊IM-DDD稳定骨架设计.md) 是它的重要智慧来源，但 `supcode` 本体不能被 Rust、IM、PostgreSQL、Socket.IO 或任何单一项目背景绑死。

## 2. 目标与非目标

### 2.1 目标

`supcode` 必须同时达到以下目标：

1. 在所有代码相关请求上高敏感自动触发，而不是只在用户点名时触发
2. 在主代理和 subagent 准备进行任何代码动作前默认先介入
3. 先主动取证，再做架构与边界裁决，不允许凭印象放行或阻断
4. 高优先级阻断“真相漂移、边界漂移、交换面失真、假成功、旁路机制增殖、证据失明”
5. 在阻断时给出简洁精炼的结论、通俗的大白话解释，以及 2-3 个优雅替代方案
6. 在放行时尽量少打断，把舞台让回实现 skill 或当前执行链
7. 可以迁移到任意语言、任意框架、任意业务场景，而不是只对 DDD 显式命名项目有效
8. 能吸收长期经验与禁令体系，但不因堆砌规则而变成噪音机
9. 能通过触发评测、行为评测、description 优化与后续增强持续升级

### 2.2 非目标

`supcode` 明确不追求以下内容：

1. 替代所有代码实现 skill
2. 代替用户做最终产品、业务与权衡决策
3. 对每个轻微格式问题都阻断主线
4. 把任意项目都强行改造成某种固定目录结构
5. 把 DDD 退化成目录命名检查器
6. 把输出做成长篇架构说教
7. 只会在 Rust、后端、群聊系统里表现好
8. 靠项目里的某个文档存在与否才能工作

### 2.3 成功标准

只要满足下面这些标准，就说明 `supcode` 首版设计成立：

1. 用户说“加功能、修 bug、重构、审代码、让 agent 去改文件、写代码”，`supcode` 都能高敏感介入
2. agent 或 subagent 准备动代码时，`supcode` 会先触发，而不是裸执行
3. `supcode` 会先读代码、调用链、接口、注释、测试、日志和对话上下文，而不是直接下结论
4. 明显违规方案会被简洁、稳定、可解释地阻断
5. 阻断输出短、硬、准，不废话
6. 被阻断后用户能从 2-3 个优雅方案中迅速选路继续推进
7. 触发与判断在跨语言场景下仍抓得住“真相、边界、交换面、验证证据”这些本质

## 3. 核心定位裁决

### 3.1 `supcode` 是什么

`supcode` 是一个高优先级、前置型、通用型代码宪法守门 skill。

它的核心职责只有一条：

**先阻止系统滑向真相漂移、边界漂移和工程腐化，再允许代码继续生长。**

### 3.2 `supcode` 不是什么

`supcode` 不是：

1. 普通代码助手
2. 只在 code review 时才触发的附属检查器
3. 只会检查目录结构、命名格式或架构术语的浅层 lint 规则集合
4. 只在 DDD 显式分层项目里才有用的项目专用 skill
5. 只会说“不行”的消极阻断器

### 3.3 优先级裁决

`supcode` 在所有代码相关动作之前优先于实施类 skill 介入。

固定顺序是：

1. 代码动作意图出现
2. `supcode` 先取证
3. `supcode` 先裁决是否合规
4. 若违规则阻断并给优雅方案
5. 若合规则释放到后续实施链

### 3.4 默认工作姿态

`supcode` 的默认工作姿态是：

1. 先安静取证，不先表演观点
2. 先抓高危红线，不先挑枝节毛病
3. 有红线时硬阻断
4. 无红线时简短约束后让路
5. 解释必须说大白话，但不失真
6. 结论必须简洁精炼，不写散文

## 4. 通用母法

`supcode` 的母法来自长期软件设计经验、DDD领域开发智慧、整洁架构边界意识、Unix系统哲学智慧，以及 [2026-04-04-群聊IM-DDD稳定骨架设计.md](E:\koko\docs\superpowers\specs\2026-04-04-群聊IM-DDD稳定骨架设计.md) 中已沉淀出的禁令体系。

这些母法必须被抽象成跨语言通用不变量，而不是某个项目的实现细节。

### 4.1 真相边界母法

1. 业务真相只能在少数核心边界裁决，不能到处宣布成立
2. 同一个业务事实不能由前端、adapter、repo、缓存、脚本、页面状态多地同时定义
3. 传输成功、局部成功、乐观态、缓存命中、连接成功都不等于业务事实成立

### 4.2 分层母法

无论项目文件怎么命名，`supcode` 都必须识别这些事实边界：

1. 业务真相层
2. 业务编排层
3. 共享交换层
4. 接入翻译层
5. 展示与运行外壳层

并始终坚持：

1. 规则归规则层
2. 编排归编排层
3. 翻译归接入层
4. 展示归壳层
5. 不允许边界相互吞并

### 4.3 交换面母法

跨边界的稳定交换面应优先表达事实，而不是某个壳的流程语义。

因此必须长期警惕：

1. 公共 DTO 混入页面状态
2. 共享事件混入展示流程
3. 公共返回结果混入壳专用字段
4. 一层为了方便把事实压成私有形状再向外扩散

### 4.4 闭环母法

任何能力在追求丝滑体验前，都要先证明闭环成立。

闭环最少包括：

1. 权威基线
2. 增量推进
3. 去重或幂等
4. 恢复或补偿
5. 显式失败

没有闭环就做体验，本质上是在用假状态掩盖系统空洞。

### 4.5 Unix 哲学母法

1. 一个部件只做一件核心事
2. 接口先说真话，不说壳话
3. 默认先删冗余，再加能力
4. 先保主链清晰，再谈概念高级
5. 隐式默契少一分，系统稳定就多一分

### 4.6 工程完成定义母法

一个改动是否算完成，不只看“代码跑了”。

还必须看：

1. 是否有足够证据
2. 是否能被日志追证
3. 是否有防回归测试
4. 是否有必要注释同步
5. 是否没有顺手制造新债

## 5. 触发策略

### 5.1 用户触发

只要是代码相关请求，`supcode` 都应默认高敏感触发。

包括但不限于：

1. 写代码
2. 改代码
3. 删代码
4. 加功能
5. 修 bug
6. 重构
7. 审代码
8. 改接口
9. 改 DTO
10. 改 handler、controller、service、repo、adapter、middleware、hook、state、cache、event、queue、workflow
11. 补日志
12. 补测试
13. 优化性能
14. 让 agent 去执行代码工作

这里不要求用户显式提到：

1. DDD
2. Clean Architecture
3. Hexagonal
4. 分层
5. 审查
6. 架构

只要本质是在碰代码，`supcode` 就应先介入。

### 5.2 代理自触发

`supcode` 不仅在用户提到时触发。

主代理和 subagent 只要准备做这些动作，也必须默认先触发：

1. inspect code
2. review code
3. generate code
4. edit code
5. refactor code
6. validate code
7. propose architecture-affecting changes

固定规则：

**Whenever any agent or subagent is about to inspect, review, edit, generate, refactor, or validate code, invoke `supcode` first, even if the user did not explicitly request architectural review.**

### 5.3 不应抢占的场景

为防止它沦为噪音机，下面这些场景默认不应高强度抢占：

1. 纯闲聊
2. 纯翻译
3. 纯总结用户已提供文本
4. 与代码无关的日常建议
5. 不涉及代码动作的轻量说明

即便在这些场景里触发，也应尽量静默，不应强行把话题拖进架构说教。

## 6. 取证优先工作流

### 6.1 总则

`supcode` 的第一原则不是“快裁决”，而是“先取证”。

### 6.2 固定顺序

只要触发，默认按下面顺序推进：

1. 读对话上下文
2. 找目标文件、相关文件、调用链与相邻边界
3. 读注释、契约、接口、错误、日志与测试
4. 判断当前改动涉及哪些事实边界
5. 检查是否命中高危红线
6. 再决定阻断或放行

### 6.3 必查证据

在有条件时，优先检查这些证据：

1. 当前要改的代码
2. 直接调用方与被调用方
3. 相关接口或契约定义
4. 相关测试
5. 相关日志点
6. 相关注释
7. 相关设计文档或规则文件
8. 当前对话里用户给出的真实目标和约束

### 6.4 禁止的裁决方式

以下行为属于 `supcode` 明确禁止的取证失守：

1. 只看用户一句话，不看代码就下裁决
2. 只看一个文件，不看主链就宣布违规或放行
3. 用框架名、目录名、文件名代替事实边界判断
4. 凭历史记忆替代当前证据
5. 证据不足还直接允许核心改动继续推进

### 6.5 证据不足时的动作

如果证据不足，`supcode` 不得装懂。

它应当：

1. 明确当前证据不足
2. 继续搜索所需上下文
3. 若仍不足，则只给出条件性裁决，不给装确定的结论

## 7. 分层识别框架

`supcode` 不能被目录名带偏，它必须识别事实上的边界角色。

### 7.1 通用边界映射

无论项目采用什么术语，默认都尝试映射到以下五类边界：

1. `业务真相层`
2. `业务编排层`
3. `共享交换层`
4. `接入翻译层`
5. `展示与运行外壳层`

### 7.2 识别原则

1. 看“谁在定义规则”，而不是只看“文件夹叫什么”
2. 看“谁在决定某事实是否成立”，而不是只看“谁先接到了请求”
3. 看“谁在做协议翻译”，而不是只看“谁调用得多”
4. 看“谁在准备展示与交互”，而不是只看“谁离用户近”

### 7.3 识别失败的典型误区

1. 把 `service` 名字直接当成业务层
2. 把 `repo` 里的规则当成存储细节
3. 把 `controller` 里的权限判断当成接线顺手做的事
4. 把前端状态机里的业务结论当成只是页面方便
5. 把公共 DTO 里的页面步骤当成无害字段

## 8. 绝对阻断红线

以下情况一旦命中，`supcode` 默认直接阻断，不允许继续编码。

### 8.1 真相漂移

1. 同一业务事实在多个边界被重复裁决
2. 前端或外壳开始决定核心业务成立与否
3. adapter、repo、脚本或缓存开始偷偷定义业务真相

### 8.2 边界漂移

1. 接入层承担业务规则
2. 展示层承担权限、成员资格、成功语义
3. 业务层开始写展示流程、页面状态或协议细节

### 8.3 交换面失真

1. 共享交换结构混入壳层流程语义
2. 公共结果形状混入页面专用字段
3. 公共事件形状混入局部展示语义

### 8.4 假成功

1. transport success 被当作业务成功
2. pending 被当作业务成功
3. ack 被当作业务成功
4. connection success 被当作业务成功
5. cache hit 或局部状态被当作权威事实

### 8.5 旁路机制增殖

1. 为了快新增第二入口
2. 新增第二事件语义
3. 新增第二同步机制或第二主 DTO
4. 绕开主链偷偷落库、广播或写状态

### 8.6 证据失明但仍准备推进

1. 没读相关代码就要改核心边界
2. 没日志、没测试、没错误语义还准备宣布完成
3. 子代理准备裸跑执行，不经过守门审查

### 8.7 隐式默契与黑箱侵蚀

1. 依赖隐式全局状态或调用顺序默契
2. 职责不明的 helper、manager、bridge、wrapper 承载核心逻辑
3. 新代码可运行，但无法说清“谁说了算”

## 9. 强警告区

以下问题默认先发强警告，不一定立即阻断；但如果已进入主链、已影响真相边界或长期不清理，就必须升级为阻断。

### 9.1 注释与可读性问题

1. 关键中文注释缺失
2. 注释与代码语义失真
3. 命名模糊
4. 主链阅读路径变浑

### 9.2 可观测性问题

1. 日志字段不稳定
2. 主链关键证据缺失
3. 错误分类模糊

### 9.3 测试与验证问题

1. 关键改动无失败测试
2. 验证命令不足
3. 回归证据不清

### 9.4 复杂度脏增

1. 巨函数继续膨胀
2. 复制旧逻辑再改
3. 临时分支无退场机制
4. 低价值包装层持续堆积

### 9.5 性能与并发风险

1. 热路径无界增长
2. 热路径长锁
3. 热路径无谓变形、无谓拷贝
4. 恢复链路或重试链路开始泥团化

### 9.6 死代码与冗余代码

1. 无调用路径代码长期保留
2. 旧实现注释块不清
3. 过渡结构长期并存
4. 调试代码和一次性脚本长期悬挂

---

## 10. 升级阻断条件

强警告在以下任一条件出现时，必须升级为绝对阻断：

1. 已进入核心主链
2. 已影响真相边界
3. 已影响共享交换面
4. 已让问题无法靠日志和测试追证
5. 已连续两轮迭代未清理
6. 已明显导致阅读路径和维护成本恶化

## 11. 输出协议

`supcode` 的输出必须稳定、简洁、精炼，不废话。

### 11.1 阻断输出模板

一旦阻断，输出固定由五部分组成：

1. `阻断结论`
2. `违规点`
3. `对应原则`
4. `大白话解释`
5. `优雅方案`

### 11.2 字段要求

#### `阻断结论`

只允许一句话。

例如：

- 当前方案不应直接编码。
- 当前改动应先回收边界再继续。

#### `违规点`

只列关键点，不展开散讲。

例如：

- adapter 正在承载业务裁决
- 共享返回形状混入壳层流程状态

#### `对应原则`

只点原则名，不长篇复述。

例如：

- 真相边界
- 接口先说真话
- 禁止第二套真相

#### `大白话解释`

必须短，必须让人一看就懂为什么危险。

例如：

- 你现在把“谁说了算”塞进接线层，下一次换入口时这段规则就会散。

#### `优雅方案`

必须给 2-3 个可执行替代路径。

每个方案都要明确指出：

1. 把东西收回哪一层
2. 交换面如何变形
3. 如何继续推进而不造新债

### 11.3 放行输出

若未命中红线，`supcode` 不应长篇刷存在感。

它只应：

1. 简短指出当前边界判断
2. 提醒最关键的验证与注意项
3. 让路给实施链

### 11.4 禁止的输出风格

1. 长篇说教
2. 术语堆砌
3. 没有替代方案的纯否定
4. 明明证据不足却装成确定结论
5. 被触发后无差别输出超长 checklist

---

## 12. 放行条件

`supcode` 只有在同时满足以下条件时才允许进入编码：

1. 当前改动的业务事实裁决层清楚
2. 当前改动的交换面边界清楚
3. 没有制造第二套真相或第二套机制
4. 失败如何显式暴露是清楚的
5. 最小验证证据是清楚的
6. 当前主链阅读路径不会因此更浑

若用户在被阻断后明确选择某个合规方案，`supcode` 应允许继续推进。

## 13. 吸收原始禁令的融合策略

`supcode` 应当尽量吸收 [2026-04-04-群聊IM-DDD稳定骨架设计.md](E:\koko\docs\superpowers\specs\2026-04-04-群聊IM-DDD稳定骨架设计.md) 中的长期经验与禁令，只要没有前后矛盾，就优先吸收而不是随意删薄。

### 13.1 可直接内化为通用禁令的部分

这些内容可直接写入 `supcode` 本体：

1. 禁止第二套真相
2. 禁止 adapter 承担业务规则
3. 禁止共享交换面混入壳层语义
4. 禁止控制面、传输结果、失败结果伪装成业务事实
5. 禁止新增私有旁路机制
6. 禁止隐式状态与隐式默契
7. 禁止黑箱 helper 侵蚀边界
8. 禁止没有证据就宣称完成
9. 禁止没有日志、测试、注释同步的“完成”
10. 禁止死代码和临时代码长期悬挂
11. 禁止复制粘贴式扩展主链
12. 禁止命名与注释失真
13. 禁止低价值包装层堆积
14. 禁止热路径吞性能债

### 13.2 需要抽象后吸收的部分

以下内容不应原词硬搬，但要上升抽象后吸收：

1. `event_position`  
   抽象成：稳定同步锚点与顺序依据
2. 快照 / 补洞 / 续接  
   抽象成：基线、增量、恢复与补偿闭环
3. transport ack 语义  
   抽象成：局部技术成功不等于业务成功
4. 热路径 / 冷路径  
   抽象成：高频主链与低频恢复链不得混写
5. Rust/PostgreSQL/Socket.IO 绑定  
   抽象成：实现绑定不是母法

### 13.3 不应写死进通用 skill 的部分

1. 某个框架名字
2. 某种数据库字段细节
3. 某个业务域的专用术语
4. 某个仓库的固定目录结构

## 14. 文件结构设计

为防止 `SKILL.md` 失控膨胀，`supcode` 建议采用分层文件结构。

```text
supcode/
  SKILL.md
  references/
    constitutional-principles.md
    blocking-red-lines.md
    review-output-format.md
    evidence-and-verification.md
    evolution-and-cleanup.md
    trigger-examples.md
  evals/
    evals.json
```

### 14.1 `SKILL.md`

只保留高频规则：

1. 何时触发
2. 何时必须自触发
3. 先取证再裁决
4. 绝对阻断与强警告的基本规则
5. 简洁输出协议
6. 放行条件
7. 何时读取 `references/`

### 14.2 `constitutional-principles.md`

存放通用母法与核心原则解释。

### 14.3 `blocking-red-lines.md`

存放融合后的禁令清单与升级阻断逻辑。

### 14.4 `review-output-format.md`

存放输出协议、简洁性要求、示例格式。

### 14.5 `evidence-and-verification.md`

存放先看什么证据、何时证据不足、如何判断验证闭环。

### 14.6 `evolution-and-cleanup.md`

存放关于长期演进、死代码、技术债与复杂度治理的规则。

### 14.7 `trigger-examples.md`

存放 description 优化与触发评测样例。

### 14.8 `evals/evals.json`

存放正式评测用例。

## 15. frontmatter 设计

`supcode` 的 frontmatter 必须有意做成“高敏感、广触发、先守门、后编码”的 pushy 描述。

建议方向如下：

```yaml
---
name: supcode
description: High-sensitivity constitutional coding skill for any code-related request. Use this whenever the user or any agent/subagent is about to add, edit, delete, refactor, debug, review, optimize, or extend code in any language or stack, even if architecture is not mentioned. First inspect code, comments, interfaces, logs, tests, and conversation context; then block solutions that create truth drift, boundary drift, adapter-owned business rules, shell-shaped shared contracts, fake success semantics, weak evidence, hidden side channels, or low-value complexity. If blocked, respond briefly with the blocking conclusion, key violations, principle names, a plain-language explanation, and 2-3 elegant compliant alternatives before coding proceeds.
---
```

### 15.1 描述必须覆盖的要点

1. 所有代码相关请求都该触发
2. 主代理与 subagent 的代码动作前也该触发
3. 架构未被点名也该触发
4. 先 inspect，再裁决
5. 有红线则先 block，再 coding
6. 输出必须短、准、可执行

### 15.2 描述不能犯的错误

1. 太窄，只写成“DDD review”
2. 太虚，只写成“高质量代码”
3. 太项目化，写死某技术栈
4. 太像实施 skill，削弱前置守门地位

## 16. 评测设计

`supcode` 的评测必须覆盖“触发是否正确”和“触发后行为是否正确”两类问题。

### 16.1 触发评测

目标：

1. 验证高风险代码请求是否会触发
2. 验证 agent/subagent 代码动作是否会触发
3. 验证非代码场景不会被过度抢占

### 16.2 行为评测

目标：

1. 是否先主动取证
2. 是否能识别红线
3. 是否该阻断时阻断
4. 是否该放行时不多嘴
5. 输出是否短而准
6. 是否给出 2-3 个真正优雅的替代方案

### 16.3 评测分组

建议至少覆盖以下分组：

1. `应强触发`
2. `应触发且应阻断`
3. `应触发但应放行`
4. `边界模糊样例`
5. `不应抢占`
6. `subagent 场景`

### 16.4 首版通过标准

1. 高风险代码请求触发率应非常高
2. 明显红线样例阻断率应非常高
3. 输出不应啰嗦
4. 替代方案必须可执行
5. 换语言、换框架、换术语后仍能抓住本质

## 17. 防漂移强化路线

为防止 `supcode` 日后发生功能漂移、性能漂移、触发漂移与判断力漂移，必须预先定义强化路线。

### 17.1 功能漂移防线

防止它从“守门 skill”滑成“普通编码 skill”：

1. 每次改 skill 都检查是否仍坚持“先守门，后编码”
2. 每次改 description 都检查是否仍把阻断放在 coding 之前
3. 每次加能力都检查是否削弱了绝对阻断规则

### 17.2 触发漂移防线

防止它未来漏触发或乱触发：

1. 持续维护 should-trigger 与 should-not-trigger 样例
2. 每次 description 优化后重跑触发评测
3. 特别关注 subagent 代码动作是否仍会触发

### 17.3 输出漂移防线

防止它越写越长、越写越废话：

1. 定期抽样检查阻断输出长度
2. 定期检查是否还保持“五段式输出”
3. 发现大白话解释开始说散，就收紧协议

### 17.4 判断力漂移防线

防止它只会背禁令，不会识别本质：

1. 在评测中加入跨语言、跨框架、跨项目样例
2. 增加边界模糊与近似误导场景
3. 检查它是否抓住事实边界，而不是只盯术语

### 17.5 性能漂移防线

防止 skill 本体越来越重、越来越慢、越来越依赖长文本：

1. `SKILL.md` 只保留高频核心
2. 详细规则下沉到 `references/`
3. 让模型按需读取 references，而不是每次全量吃下
4. 定期裁剪低价值、重复、弱区分度规则

## 18. 实施建议

### 18.1 第一阶段交付

第一阶段只做以下事情：

1. 写出本设计文档
2. 由用户审核设计文档
3. 文档通过后再进入 skill 实作
4. 实作完成后再做评测、description 优化与 skill 强化

### 18.2 第二阶段交付

文档审核通过后，进入这些步骤：

1. 编写 `supcode/SKILL.md`
2. 编写 `references/`
3. 编写 `evals/evals.json`
4. 运行 with-skill / without-skill 评测
5. 做 description 优化
6. 安装到个人全局 skill 目录

### 18.3 安装位置

当前裁决：

`supcode` 最终应安装到用户个人全局技能目录，作为通用全局 skill 使用，而不是只放在 `koko` 仓库里。

## 19. 最终结论

`supcode` 要解决的不是“怎样写出更多代码”，而是“怎样让代码在长期演进里不滑向真相漂移、边界漂移、交换面失真和工程腐化”。

因此它必须长期坚持以下裁决：

1. 高敏感触发，但不做噪音机
2. 先取证，再裁决
3. 先守门，再编码
4. 红线硬阻断，枝节强警告
5. 输出短、准、通俗
6. 不只审用户请求，也审 agent 与 subagent 的代码动作
7. 广泛吸收长期禁令与智慧，但不绑死在单项目技术细节上

只要这些骨架不漂，`supcode` 就能逐步成长为一个真正可迁移、可强化、可持续升级的通用代码宪法 skill。
