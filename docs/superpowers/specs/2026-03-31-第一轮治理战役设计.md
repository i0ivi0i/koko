# Koko 第一轮治理战役设计

## 1. 目标

本设计用于把 [2026-03-31-全仓审查-宏观架构治理巡检.md](/E:/koko/docs/superpowers/specs/2026-03-31-全仓审查-宏观架构治理巡检.md) 中三项正式问题，收敛成一轮可执行、可验证、可持续推进的治理战役。

这一轮不是“顺手清理一点”，而是明确完成以下三件事：

- 收回 `admin` 判权真相，停止让 HTTP 入口层直接持有最终 admin 裁决
- 清掉 `admin` 页面型共享契约，恢复 `contract / application` 的跨壳稳定面
- 收回 `join_or_create_room_by_code` 中建房、建短码、建成员的权威事实归属，并顺手把测试层开始扩散的重复支撑收口

完成后，项目应当更接近：

- 多壳共核
- `adapter` 只翻译、不决策
- `application` 真正拥有用例与事实编排
- `contract` 只表达稳定跨壳共享面
- 测试更少绑定当前写法，更能支撑后续继续治理

## 2. 非目标

这一轮明确不做：

- 不扩展新功能
- 不补齐所有未来 admin 只读能力
- 不重做前端实时链路
- 不提前做 CLI 壳
- 不重做数据库 schema，只在现有 schema 足够表达时重排权威边界
- 不为了“更优雅”重写无关代码

## 3. 总体策略

这轮战役虽然最终要把三项问题都修完，但不适合真正并行改代码。原因不是“工作量大”，而是它们会共同撞到 `src/app.rs`、`src/store.rs`、`src/contract.rs` 这些公共边界。

因此采用同一战役、三刀连续收口：

1. 先打 `admin`
2. 再收 `join_or_create_room_by_code`
3. 最后清测试支撑债

这个顺序的核心理由：

- `admin` 问题先污染的是系统对外共享面，优先级高于内部实现细节
- `room entry` 问题更深，但爆炸半径更大，应该在共享面先收正之后再动
- 测试债最后收，是为了先服务前两刀，而不是先陷进测试形式主义

## 4. 设计一：Admin 边界收口

### 4.1 问题定义

当前 admin 路径存在两个直接问题：

- `src/http.rs` 直接持有 `admin_token` 并在入口层决定谁有 admin 权限
- `src/app.rs` 和 `src/contract.rs` 已经长出 `load_admin_panel / AdminPanelData` 这类页面型共享面

这会导致：

- 判权真相散落在入口层
- 多壳共享契约被当前 Web admin 页绑架
- 后续 CLI / 脚本 / 其他后台壳接入时，不是复制一遍，就是绕过应用层

### 4.2 目标边界

治理后，admin 应满足：

- HTTP 只负责提取 admin 凭证并把它交给应用层
- 应用层统一决定 admin 是否被授权
- `contract` 只保留稳定只读查询结果，不再保留页面组合型 DTO
- Web admin 壳自己组合页面状态，不再让后端提供 `panel` 型页面接口

### 4.3 具体设计

#### 4.3.1 应用层新增 admin 访问裁决 port

在 `src/app.rs` 中新增一类 admin 访问 port，职责只有一个：

- 给定调用方提供的 admin 凭证，判断是否具备 admin 访问资格

应用层不感知 HTTP header、Cookie、Dioxus state，只接受壳层已经提取出的凭证值。

建议形状：

- `AdminAccessPort`
- `AdminQueryContext` 或等价的显式输入结构

重点不在名字，而在边界：

- 判权结论必须在 `application`
- 入口层只做提取和翻译

#### 4.3.2 应用层读查询统一先判权再执行

以下 admin 用例全部改为“先授权，后读取”：

- `get_admin_overview`
- `list_admin_rooms`

如果后续补 `detail / members / search`，也必须走同一模式。

应用层需要新增稳定错误语义，而不是继续由 `support.rs` 暴露字符串错误码。

#### 4.3.3 删除页面型共享面

以下内容应删除：

- `src/contract.rs` 中的 `AdminPanelData`
- `src/app.rs` 中的 `AdminPanelPort`
- `src/app.rs` 中的 `load_admin_panel`
- `src/store.rs` 中的 `load_admin_panel`
- `src/http.rs` 中的 `/api/admin/panel`

`panel` 不是业务真相，它只是 Web admin 页当前的页面组合结果。这个组合应当回到壳层。

#### 4.3.4 Web admin 壳改为本地组合

`src/admin.rs` 继续保留 `AdminPanelState` 作为壳层 viewmodel，但不再从后端拿 `panel` 聚合接口。

改为：

- 通过同一份 admin token 分别拉 `overview`
- 再拉 `rooms`
- 在壳层把两者组合为 `AdminPanelState`

这样：

- 页面仍然能保留当前展示形状
- 共享面却重新回到稳定 query

### 4.4 风险与控制

风险：

- admin 错误语义需要从 `support.rs` 回收到 `contract/app`
- 前端壳和 HTTP handler 会一起改

控制方式：

- 先写失败测试，锁住“未授权不可读”“panel 路由消失但 overview/rooms 仍可用”
- 只做最小边界重排，不顺手扩功能

## 5. 设计二：Room Entry 权威事实回收

### 5.1 问题定义

当前 `join_or_create_room_by_code` 名义上在应用层，但真正的创建事实仍在 `src/store.rs`：

- `room_id` 在 adapter 里生成
- `room_code_id` 在 adapter 里生成
- `member_id` 在 adapter 里生成
- 时间戳在 adapter 里决定

这意味着：

- 应用层并没有真正拥有“房间何时成立、成员何时成立”的权威语义
- adapter 并不只是持久化，而是在定义业务事实落地

### 5.2 目标边界

治理后，`join_or_create_room_by_code` 应满足：

- 应用层决定什么时候创建房间和成员事实
- 应用层决定创建时使用的 ID 与时间语义
- adapter 只负责在事务里检查、写入、提交

### 5.3 具体设计

#### 5.3.1 把创建语义显式化

应用层需要显式构造待持久化事实，而不是把“要不要创建、创建出什么”整包交给 adapter。

建议做法：

- 在 `domain.rs` 或 `app.rs` 中引入明确的新建记录结构
- 至少覆盖：
  - 新房间
  - 新短码
  - 新成员

不要求为“好看”引入复杂聚合，但必须让应用层能明确产出这些事实。

#### 5.3.2 扩展时间与 ID 生成边界

当前 `Clock / IdGenerator` 只服务消息发送，还不够服务房间/成员创建。

这一轮应把它扩成能支撑：

- 房间 ID
- 短码记录 ID
- 成员 ID
- 创建时间

重点是让这些语义由应用层控制，而不是让 `sqlx` adapter 顺手拍一个 `Uuid::now_v7()` 和 `Utc::now()`

#### 5.3.3 重写 RoomEntryTx 边界

`RoomEntryTx` 需要从“你帮我创建吧”改成“我把待持久化事实给你，你负责事务写入”。

也就是说：

- `find_room_by_code` 这类查询型能力可以继续存在
- `create_room` / `ensure_room_member` 要改成接收应用层已经决定好的事实

最终效果是：

- 应用层决定事实
- adapter 决定如何落库

### 5.4 风险与控制

风险：

- 这会直接碰 `src/app.rs`、`src/store.rs`、测试 fake port
- 一旦设计过头，很容易把当前简单流程搞成过度抽象

控制方式：

- 保持现有事务轮廓和 schema，不额外造抽象层
- 只把“事实生成权”拉回应用层，不顺手做新模式

## 6. 设计三：测试层收口

### 6.1 问题定义

当前测试层开始出现两类会阻塞治理的结构：

- 用 `include_str! + source.contains()` 锁定当前代码写法
- 数据库 harness 在 `tests/app_flow.rs` 和 `tests/http_support/mod.rs` 里重复增长

这类测试不证明“边界是对的”，而是在保护“当前实现长这样”。

### 6.2 目标边界

治理后，测试应满足：

- 行为测试优先于源码文本测试
- 数据库测试支撑只有一套
- 改边界时测试保护行为和契约，而不是保护当前 Dioxus/HTTP 写法

### 6.3 具体设计

#### 6.3.1 保留少量真正必要的静态结构测试

例如：

- crate root 对 wasm/non-wasm 的模块门禁

这类测试还算有边界价值，可以保留。

#### 6.3.2 删除或改写页面实现文本断言

以下类型测试要优先移除或改写：

- `web.rs` 里是否用了某个 hook 名字
- `admin.rs` 是否包含某个字符串
- handler 是否包含某段实现文本

改为：

- 行为测试
- API 结果测试
- 权限/契约测试

#### 6.3.3 合并数据库 harness

把测试数据库创建、命名、销毁、迁移逻辑收口到一套共享支撑里。

可以是：

- 统一支持模块
- 或在现有 `tests/http_support/mod.rs` 基础上提升成真正通用支撑

关键不是名字，而是只能有一套。

## 7. 交付顺序

实现顺序固定如下：

1. 先做 admin 判权与共享面治理
2. 再做 room entry 权威事实回收
3. 最后做测试文本断言与 harness 收口

每一刀都必须：

- 先写失败测试
- 看它正确失败
- 再做最小实现
- 绿灯后再收口
- 单独提交

## 8. 验证策略

### 8.1 Admin

至少证明：

- 未提供或提供错误 admin token 时，admin 查询被应用层统一拒绝
- `/api/admin/panel` 不再存在
- `/api/admin/overview` 与 `/api/admin/rooms` 仍然可用
- Web admin 壳仍然能展示组合后的面板状态

### 8.2 Room Entry

至少证明：

- 建房、建成员的事实由应用层产出
- store 不再私自生成这些权威事实
- 原有 join-or-create 行为不回归

### 8.3 测试层

至少证明：

- 文本断言显著减少或消失
- DB harness 收口为一套
- 全量测试仍能运行

### 8.4 最终命令

本轮至少要跑：

- `cargo check`
- `cargo test`

如果测试时长或环境阻塞，再退一步明确说明哪些子集跑了、哪些没跑，不能凭感觉报完成。

## 9. 风险判断

这轮属于高风险治理，但不是“大重写”。

风险等级高的原因是：

- 会碰共享边界
- 会碰核心用例
- 会碰测试基础设施

但它仍然是可控治理，因为：

- 不改 schema
- 不扩功能
- 不并行乱动多个热点
- 每一步都可以用 TDD 和行为测试锁住

## 10. 结论

这轮正确的做法不是“把所有问题同时推平”，而是在一轮战役里按正确顺序连续收口：

- 先把 `admin` 从“当前页面驱动后端”拉回“稳定应用能力”
- 再把 `join_or_create_room_by_code` 从“adapter 代持真相”拉回“application 持有真相”
- 最后把测试层从“保护当前写法”拉回“保护行为和边界”

如果这轮做对，后面再继续做 focused audit，就会从“在坏边界上打补丁”变成“在正确边界上继续精修”。
