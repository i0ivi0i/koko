## 1. 为什么还要补第二轮 spec

第一轮已经把这些问题处理掉了：

1. 视频上传上限从 `50MB` 提到 `200MB`
2. 前端本地 `15s` watchdog 删除
3. 前后端与 `Rustus` 的大小门禁统一
4. `complete` 重活阶段有了基本并发闸门

但这些工作本质上仍然是：

**把链路从“经常被误杀或被门禁拦死”修到“能稳定跑”。**

它还不是：

**把链路从“能跑”推到“高吞吐”。**

现在源码里最关键的现实问题仍然是：

1. 单个大视频上传仍然主要是单流传输
2. 多文件并发仍然停在偏保守的 `limit = 3`
3. 前端 `upload-success` 之后还要等 `complete`，UI 体感会把“传字节慢”和“后处理慢”混成一个“上传慢”
4. `Rustus` 和主服务之间还缺少足够清晰的关联标识，定位“慢在浏览器、sidecar 还是后端”仍然费劲
5. 当前 `run.ps1` 只接了大小门禁，还没有把 `workers / tus-extensions / behind-proxy / hooks proxy headers` 这些吞吐敏感参数显式接出来

所以这份 spec 的任务，不再是“继续改几个常量”，而是：

**在不重做上传协议和不假设对象存储直传的前提下，给当前 `Uppy + Tus + Rustus` 主链做一轮吞吐专项增强。**

## 2. 当前现场事实

### 2.1 当前已经成立的真相边界

当前主链仍然必须保持：

1. `prepare` 成功，不等于附件 ready
2. `Tus upload-success`，只代表 transport finished
3. 只有 `complete` 成功，附件才算业务上的 ready

这条边界不能因为“追吞吐”而被打坏。  
否则系统会退化成：

- transport 成功偷换成业务成功
- 前端壳层再次替后端裁决真相

### 2.2 当前吞吐相关事实

对照当前源码，现状是：

1. 前端上传器只显式设置了：
   - `limit = 3`
   - `retryDelays = [0, 1000, 3000, 5000]`
2. 还没有启用：
   - `parallelUploads`
   - `uploadDataDuringCreation`
   - `addRequestId`
3. 发送区草稿状态只有：
   - `uploading`
   - `ready`
   - `failed`
4. `upload-success` 后前端还会继续等待 `completeMediaUpload()`，所以用户看到的“上传中”混入了后端处理时间
5. `Rustus` 当前只显式接了：
   - `max-body-size`
   - `max-file-size`
   - `hooks`
   - `data-dir / info-dir`
   - `hooks-http-proxy-headers = Authorization`

### 2.3 官方资料给出的关键边界

结合这轮查到的官方资料，可以把边界压成 5 句：

1. `@uppy/tus` 的 `limit` 主要控制“同时多少个上传任务在跑”，不是自动把单文件变成并行上传
2. `tus` 协议默认倾向“单个 PATCH 尽量发送剩余字节”，不是鼓励默认切很多小块
3. `chunkSize` 官方默认就是 `Infinity`，而且官方明确建议不要随便手改
4. `parallelUploads` 确实存在，但依赖 `concatenation`，官方也明确说它不保证平均浏览器会话一定更快
5. `creation-with-upload`、`X-Request-ID`、`workers`、`behind-proxy`、`hooks-http-proxy-headers` 这些才是当前栈里更值得利用的正经杠杆

## 3. 本次目标与非目标

## 3.1 本次目标

这次第二轮专项只做 6 件事：

1. 把前端草稿状态从“一个 `uploading` 混到底”拆成：
   - `transporting`
   - `processing`
   - `ready`
   - `failed`
2. 让发送区和壳层提示能区分：
   - 正在传字节
   - 字节已传完，正在后端处理
3. 给当前栈补最值得用的官方能力：
   - `uploadDataDuringCreation`
   - `addRequestId`
4. 把多文件并发从“保护优先”提升到“吞吐优先但仍有边界”
5. 对单大视频引入**受控的**单文件并行上传实验，而不是全量无脑打开
6. 把 `Rustus` 吞吐敏感参数显式接线，便于本地与公网 Linux 部署对齐

## 3.2 明确非目标

本次明确不做：

1. 不改对象存储架构
2. 不重做上传协议
3. 不把 `complete` 热点整体重写成流式后处理管线
4. 不手动把 `chunkSize` 改成固定小块
5. 不把 `parallelUploads` 直接全量默认开给所有文件
6. 不把 `ready` 真相重新下放到前端

## 4. 方案比较与裁决

### 4.1 方案 A：只拆 UI 状态和补日志

内容：

- 草稿状态拆成 `transporting / processing`
- 补 request id 和日志
- 上传参数不动

优点：

- 风险最低
- 很快能看清“慢在哪里”

缺点：

- 体感会更诚实，但吞吐本身未必明显提升
- 不符合用户这轮明确选择的 `1 + 2`

### 4.2 方案 B：在现有主链上做吞吐专项增强

内容：

- 包含方案 A
- 提高多文件并发
- 开启 `uploadDataDuringCreation`
- 开启 `addRequestId`
- 只对大视频启用受控 `parallelUploads`
- 接出 `Rustus` 吞吐敏感参数

优点：

- 仍然站在成熟轮子上
- 不重做协议
- 同时覆盖“单大文件慢”和“多文件并发慢”
- 能把测速、日志和用户体感一起校准

缺点：

- 需要改前端草稿状态与一批 presenter / 测试
- 需要在 `Rustus` hooks 链路上补 header 透传和日志

### 4.3 方案 C：直接重做上传传输层

内容：

- 放弃当前 `Tus + Rustus` 主链
- 重做大文件并发分片上传方案

优点：

- 理论上长期天花板最高

缺点：

- 和这轮用户锁定的“小改”边界冲突
- 风险和范围都会炸开
- 现在没有足够证据证明必须走到这一步

### 4.4 最终裁决

本次采用 **方案 B：在现有主链上做吞吐专项增强**。

原因：

1. 轮子已经找齐，问题不在“没有轮子”
2. 现在最值钱的是把现有主链用对，而不是重造一层
3. 这符合“DDD 保住真相 owner，Unix 保持小而专”的边界

## 5. 核心设计

### 5.1 前端草稿状态拆分

当前 `uploading` 会把两段时间混在一起：

1. 浏览器到 `Rustus` 的传字节时间
2. `upload-success` 之后到 `complete` 成功之间的处理时间

这次改成：

- `transporting`
  - `prepare` 成功后进入
  - `Tus` 还在传
- `processing`
  - `upload-success` 已发生
  - 正在等待 `complete`
- `ready`
  - `complete` 成功
- `failed`
  - 任意阶段真实失败

这层仍然只是壳层体验态，不是业务真相。  
发送限制继续保持“只有 `ready` 的草稿才可发”，所以：

- `transporting` 和 `processing` 都继续阻塞发送
- 但给用户看到的阻塞原因要更诚实

### 5.2 前端上传参数策略

本次不改 `chunkSize`。  
策略只动这几项：

1. 多文件并发：从 `3` 提到 **`6`**
2. `retryDelays`：保持短阵列，不额外拉长慢网等待
3. `uploadDataDuringCreation = true`
4. `addRequestId = true`
5. 单大视频使用**受控并行上传 profile**

#### 5.2.1 为什么多文件并发先提到 `6`

用户这轮明确选的是“吞吐优先”。  
当前 `3` 更像保护值，不像高吞吐值。

先提到 `6` 的理由：

1. 仍然低于“一次最多 9 个文件全放开”
2. 对公网 Linux 部署更现实
3. 给 `Rustus` 和后端 `complete` 留一点喘息空间

这个值不是神圣真理，但足够成为第二轮的第一版 aggressive baseline。

#### 5.2.2 为什么打开 `uploadDataDuringCreation`

它的价值很直接：

- 减少一次额外往返
- 提前把首段数据带上去

当前 `Rustus` 官方支持 `creation-with-upload`，而且我们本来只依赖：

- `pre-create`
- `post-finish`

这和当前 hook 语义不冲突。

#### 5.2.3 为什么打开 `addRequestId`

它不是为了提速，而是为了让“慢在谁”能更快被确认。

打开后：

1. 浏览器侧 `tus` 失败信息里不再只有 `request id: n/a`
2. `Rustus` 原始请求能携带 `X-Request-ID`
3. `Rustus -> hook` 可以把 `X-Request-ID` 代理给主服务
4. 主服务日志就能把：
   - attachment_id
   - upload_id
   - request_id
   串在一起

### 5.3 单文件并行上传的裁决

这里必须克制，否则很容易从“提速”滑成“乱冲”。

本次只对满足这两个条件的文件启用单文件并行上传：

1. `kind = video`
2. `byte_size >= 64MB`

默认 profile：

- `parallelUploads = 4`

其他文件继续走单流上传。

#### 5.3.1 为什么不用全量默认打开

因为官方自己都没有保证“平均浏览器用户一定更快”。  
如果全量打开：

1. 小文件收益很可能接近 0
2. 浏览器连接数和 sidecar 压力会无谓升高
3. 调试成本也会一起变坏

#### 5.3.2 为什么不用手改 `chunkSize`

因为当前没有证据表明：

- 代理 body limit 在逼着我们切小块
- 输入源是 stream

在这种前提下手动切小块，大概率只会把请求数放大。

### 5.4 前端实现方式裁决

由于 `Uppy` 的插件配置是 uploader 级别而不是按单文件动态改 option，这次不走“在一个 uploader 里塞一堆 if”的路。

本次采用：

**同一工厂生成两种参数 profile 的 uploader，但事件绑定与发布逻辑保持一套。**

也就是：

1. 默认 uploader
   - 多文件并发优先
   - 单文件单流
2. 大视频 uploader
   - 同样基于 `Tus`
   - 只多开 `parallelUploads`

边界要求：

1. 不能复制两套事件处理逻辑
2. 不能造第二套上传协议
3. 不能让两套 uploader 长成两套“业务真相”

### 5.5 Rustus 与 hook 链路增强

这次 `Rustus` 侧不改协议，只补显式接线：

1. `RUSTUS_SERVER_WORKERS`
2. `RUSTUS_TUS_EXTENSIONS`
3. `RUSTUS_BEHIND_PROXY`
4. `RUSTUS_HOOKS_HTTP_PROXY_HEADERS`

默认值建议：

1. `RUSTUS_HOOKS_HTTP_PROXY_HEADERS = Authorization,X-Request-ID`
2. `RUSTUS_TUS_EXTENSIONS` 保留官方默认，不主动删掉 `creation-with-upload` 和 `concatenation`

为什么要把 `X-Request-ID` 加进 hooks proxy headers：

因为当前主服务只收到了：

- `Authorization`
- hook body

还没有办法把浏览器那边的单个 upload request 和 hook/update log 直接对起来。

### 5.6 后端日志与诊断增强

本次不改 ready 真相，不改 `complete` 主流程语义。  
只补诊断与观测：

1. `rustus_hook外壳` 在 `post-finish` 成功和失败日志里带上：
   - `attachment_id`
   - `upload_id`
   - `request_id`
   - `storage_locator`
2. `媒体发布.ts` 继续保留诊断归一化，但现在可以吃到真实 `request id`
3. `complete` 阶段继续保留现有：
   - `phase`
   - `duration_ms`
   - `failure_reason`

这样可以把：

- 传字节阶段
- hook 回执阶段
- complete 阶段

三段日志真正串起来。

## 6. DDD 与 Unix 边界裁决

### 6.1 领域真相不变

领域和用例层继续只拥有：

1. 附件什么时候 ready
2. 什么错误叫 `attachment_not_ready`
3. transport finished 到 ready 成立之间的业务裁决

### 6.2 适配层治理增强

这次新增的所有内容都属于 adapter / shell：

1. 上传器 profile
2. `parallelUploads`
3. `uploadDataDuringCreation`
4. `addRequestId`
5. `Rustus` 启动参数
6. hook header 透传
7. 草稿本地状态拆分

### 6.3 禁止的退化方向

这次明确禁止：

1. 为了状态拆分，造第二套上传状态机
2. 为了单文件并发，手搓私有分片协议
3. 为了观测，改数据库或领域模型去保存 request id
4. 为了快一点，把 `upload-success` 直接映射成 `ready`

## 7. 风险与验证

### 7.1 主要风险

1. `parallelUploads` 在真实环境里可能收益不明显，甚至可能反而更差
2. 多文件并发从 `3` 提到 `6` 后，`Rustus` 和后端 `complete` 压力会上升
3. 草稿状态拆分会触及一批 presenter / shell / tests，改动面不再是单文件

### 7.2 风险控制

1. 单文件并行上传只开给大视频
2. `chunkSize` 保持默认
3. `complete` 并发闸门先不动，防止把 transport 调优和后处理放大耦到一起
4. 必须补保护测试，锁死：
   - 状态流
   - 请求头透传
   - profile 路由
   - launcher 参数

### 7.3 验证重点

实现后至少要证明 4 件事：

1. 单个大视频在本地和公网 Linux 环境下，`transporting` 阶段总时长下降
2. 多个大文件同时上传时，总吞吐高于当前基线
3. `processing` 能单独暴露后端处理时间，不再伪装成“上传慢”
4. `parallelUploads` 如果收益不稳定，可以被安全地下调或关闭，而不用回滚整条链路

## 8. 一句话裁决

这次不是再做一轮“解锁限制”，而是：

**在不重做协议、不手搓轮子的前提下，把当前 `Uppy + Tus + Rustus` 主链推进到真正面向吞吐的第二阶段，并把 transport 与 processing 两段真相拆开。**
