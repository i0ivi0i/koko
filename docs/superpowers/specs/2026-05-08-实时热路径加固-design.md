# 实时热路径加固设计

日期：2026-05-08
状态：待实施

---

## 背景与动机

本项目是公网万人实时图文视频群聊。审查实时消息主链（`src/实时/外壳.rs` → `src/消息/应用.rs` → `src/领域/消息.rs`）后，发现 5 个在当前用户量下可能不显眼、但在万人并发场景下会成为安全漏洞或性能瓶颈的问题。

**为什么现在做：** 这些问题不是"优化"，其中两个是安全漏洞（无限流、无文本上限），三个是性能瓶颈（串行查询、冗余 roundtrip、连接池过小）。在用户量增长到暴露问题时再修，代价远大于现在预防。

**本次只覆盖 🔴 严重 + 🟠 中等共 5 项。** 🟡 低等（广播排除发送者、ack 确认机制）影响范围涉及前后端协议升级，风险独立，留作后续单独 spec。

---

## 全局约束（所有改动必须遵守）

1. **Onion/Hexagonal 架构不可破坏：** domain 不依赖框架/DB/网络；adapter 只做翻译和编排；shell 只做 wiring。依赖方向只能向内。
2. **冷路径（同步 HTTP）不动：** 本次所有性能优化只改热路径（realtime async handler），冷路径保持分步校验、逐条查询的现有结构。原因：冷路径频率低、分步校验的错误定位更清晰，改它没有收益但有回归风险。
3. **错误码对外稳定：** 所有现有错误码（`会话无效` / `房间不存在` / `成员资格不足` / `附件不存在` / `附件不属于当前发送者` / `附件未就绪`）的返回时机和语义不变。前端不需要改任何错误处理逻辑。
4. **不引入外部依赖：** 纯内存 + 现有 PgPool，不加 Redis、不加中间件、不加新 crate。
5. **TDD 顺序：** 每项改动 RED（先写失败测试）→ GREEN（最小实现）→ REFACTOR。
6. **现有测试全绿：** 改动完成后，`cargo test` 和 `pnpm test`（frontend）必须全部通过，不允许删除或弱化任何现有测试。

## 1. 消息发送限流

### 问题的根因

`src/实时/外壳.rs` 第 612 行的 `handle_realtime_create_message` 直接进入业务逻辑，没有任何频率门禁。

**攻击向量：** 恶意客户端用脚本对单个 socket 连接每秒发几百次 `create_message` 事件。每次都会触发 4+ 次 DB 查询 + 1 次事务写入 + 1 次万人房间广播。20 个 DB 连接瞬间耗尽，正常用户全部超时。

**为什么 socketioxide 不自带限流：** socketioxide 是底层传输引擎，和 socket.io 官方一样，限流是业务层责任。官方文档建议在 handler 入口做 per-connection rate limiting。

### 设计

**策略：每连接令牌桶（Token Bucket），存在 socket extension 里。**

| 参数 | 值 | 理由 |
|------|----|------|
| 桶容量（burst） | 10 条 | 允许正常用户快速连发几条消息（如发图+发文字） |
| 补充速率 | 5 条/秒 | 正常人打字速度上限，远高于实际需要 |
| 检查时机 | `handle_realtime_create_message` 入口，**在任何 DB 查询之前** | 超限请求零 DB 成本 |
| 超限响应 | `control_result { kind: "rejected", code: "rate_limited" }` | 复用现有拒绝通道 |
| 生命周期 | 随 socket extension 自动创建和销毁 | 连接断开即回收，不需要定时清理 |

**令牌桶结构：**

```rust
// 放在 src/实时/外壳.rs 内部，不导出到 domain 或 contract
pub(crate) struct 连接消息令牌桶 {
    tokens: f64,
    last_refill: Instant,
}

const 令牌桶容量: f64 = 10.0;
const 令牌补充速率: f64 = 5.0; // 每秒

impl 连接消息令牌桶 {
    pub fn new() -> Self { ... }

    /// 尝试消费一个令牌。返回 true 表示放行，false 表示超限。
    /// 内部先按时间差补充令牌，再扣减。
    pub fn try_consume(&mut self) -> bool { ... }
}
```

**层级归属与理由：**
- 令牌桶是**纯运行态值对象**，只依赖 `std::time::Instant`，不依赖框架。
- 它放在 `src/实时/外壳.rs` 内部（`pub(crate)`），因为它只为 socketioxide handler 服务，不是业务真相。
- 连接建立时在 `src/外壳/mod.rs` 的 connect handler 里插入 socket extension：`socket.extensions.insert(连接消息令牌桶::new());`
- handler 里通过 `socket.extensions.get::<连接消息令牌桶>()` 取出并检查。

**为什么不做双层（会话级+房间级）：**
当前是单节点架构，一个会话只有一个 socket 连接（`frontend/聊天实时/适配/实时连接适配.ts` 第 29 行 `io()` 只创建一个 socket）。连接级限流等价于会话级。房间级限流在当前只有一个公共房间的 MVP 阶段没有意义。未来多房间、多节点时升级。

**为什么不用 `governor` / `tower` 等限流 crate：**
令牌桶实现只需 ~20 行代码，引入 crate 的价值不抵依赖成本。socketioxide handler 不走 tower middleware 层，在 handler 内部检查更直接。

### 要注意的陷阱

- **`socket.extensions` 的 `get` 返回的是 `Ref`，里面是不可变的。** 令牌桶需要可变操作（扣减 token、更新时间戳），必须用 `socket.extensions.get::<Mutex<连接消息令牌桶>>()` 或 `RefCell`。socketioxide extension 底层是 `dashmap`，多个 handler 可能并发访问同一个 socket 的 extension。**必须用 `std::sync::Mutex`**（不是 `tokio::sync::Mutex`），因为锁持有时间极短（一次浮点运算），不会跨 await 点。
- **限流日志级别用 `tracing::info!`，不用 `warn` 或 `error`。** 限流是正常运行态事件，不是异常。如果用 `error` 级别，恶意刷屏者反而会触发海量错误日志，把日志系统也打爆。
- **`subscribe_room_stream` 事件不限流。** 订阅是控制面行为，频率天然低（进入房间时才触发），不需要限流。只限 `create_message`。

### 验证标准

1. 单测：连续调用 `try_consume()` 20 次，前 10 次返回 true，第 11 次返回 false。模拟时间推进 1 秒后，再次调用 5 次成功。
2. 集成验证：通过 socket 连续发 20 条消息，前 10 条产生 `room_event` 广播，后续的收到 `control_result { code: "rate_limited" }`。
3. 确认：限流拒绝的请求 **零 DB 查询**（检查 tracing 日志中不出现 "订阅房间事件流" 或 "创建消息" 的 application 标签）。

## 2. 消息文本长度限制

### 问题的根因

`src/领域/消息.rs` 第 86-88 行：

```rust
let trimmed_text = 文本.trim();
if trimmed_text.is_empty() && 附件.is_empty() {
    return Err(领域错误::消息内容为空);
}
```

只检查了"不能为空"，没有上限。

**攻击向量：** 一条 10MB 的 UTF-8 文本（约 300 万个汉字），通过 `create_message` socket 事件发送。后端序列化为 JSON 后广播给万人房间 = 10MB × 10000 连接 = 100GB 瞬时网络 IO + 内存分配。即使限流放行（一条就够），也能瞬间 OOM 整个进程。

**为什么限流挡不住这个问题：** 限流控制的是消息**条数**，不是消息**大小**。1 条 10MB 消息和 1 条 10 字节消息在限流器看来一样。

### 设计

**改动 1：领域层新增不变量**

在 `src/领域/消息.rs` 中：

```rust
const 单条消息文本最大字符数: usize = 2000;
```

在 `创建消息()` 和 `创建文本消息()` 两个函数中，trim 之后、空检查之后新增：

```rust
if trimmed_text.chars().count() > 单条消息文本最大字符数 {
    return Err(领域错误::消息文本过长);
}
```

**为什么用 `chars().count()` 而不是 `len()`：** `len()` 是字节数，一个汉字 3 字节、一个 emoji 4 字节。用字节数限制会让中文用户只能打 ~666 个汉字，体验不公平。`chars().count()` 是 Unicode 标量值个数，对中英文用户一视同仁。2000 个 char × 最多 4 字节 = 最大 8KB，广播给万人 = 80MB，在可接受范围内。

**为什么是 2000：** Discord 的消息上限也是 2000 字符。群聊场景不需要写长文，2000 字符足够表达完整想法。

**改动 2：新增领域错误变体**

```rust
// src/领域/错误.rs
pub enum 领域错误 {
    // ... 现有变体 ...
    /// 消息文本超过单条消息字符数上限。
    消息文本过长,
}
```

**改动 3：错误映射链路**

```rust
// src/应用/mod.rs — 映射领域错误
domain::领域错误::消息文本过长 => contract::错误码::消息文本过长,

// src/共享/契约基础.rs — 新增错误码
pub enum 错误码 {
    // ... 现有变体 ...
    /// 消息文本超过字符数上限。
    消息文本过长,
}
```

前端 `control_result` 接收到 `code: "message_text_too_long"` 后，走现有的拒绝处理路径（`src/聊天实时/壳层/实时控制面协作.ts` 第 115 行 `deps.处理恢复失败(control, true)`），不需要新增前端错误处理。

**改动 4：前端输入框长度提示（体验优化，不替代后端校验）**

在 `frontend/输入框/应用.ts` 的 `处理消息输入变更` 中，当 `value.length > 2000` 时通过依赖注入通知 UI 层显示提示。具体 UI 实现由壳层决定（如输入框变红、显示剩余字数），不在本 spec 约束范围内。

### 要注意的陷阱

- **`创建消息()` 和 `创建文本消息()` 都要加。** 这两个函数是独立入口。`创建文本消息` 调用链是 HTTP 冷路径，`创建消息` 调用链是 realtime 热路径。两个都不能漏。
- **先空检查、再长度检查。** 顺序：trim → 空检查 → 长度检查 → 附件校验。如果倒过来，空字符串会先命中"过长"的 false negative（空串 count=0 不会过长，但逻辑上应该走空检查分支）。
- **不要在 adapter 层做长度截断。** 领域层必须拒绝过长文本，而不是 adapter 偷偷截断到 2000。截断会改变用户意图，是业务真相被 adapter 篡改。
- **`chars().count()` 对极端 emoji（如组合 emoji 序列）的计算：** 一个 "👨‍👩‍👧‍👦" 在 Rust `chars()` 中算 7 个 char（4 个人 + 3 个 ZWJ）。这意味着重度 emoji 用户实际可输入的"视觉字符"少于 2000。这是可以接受的——Discord 也用标量值计数，业界标准做法。

### 验证标准

1. 领域层单测：`创建消息(true, &"a".repeat(2000), &[])` 返回 Ok。
2. 领域层单测：`创建消息(true, &"a".repeat(2001), &[])` 返回 `Err(消息文本过长)`。
3. 领域层单测：`创建文本消息(true, &"啊".repeat(2001))` 返回 `Err(消息文本过长)`。
4. 领域层单测：`创建消息(true, &"a".repeat(2001), &[valid_attachment])` 也返回 `Err(消息文本过长)`（有附件也不能绕过长度限制）。
5. 确认：contract 错误码 `消息文本过长` 在 JSON 序列化时输出为 `"message_text_too_long"`。
6. 确认：现有测试全绿，`映射领域错误` 的 match 分支无遗漏。

## 3. 附件批量查询

### 问题的根因

`src/消息/应用.rs` 第 148-154 行：

```rust
for attachment_id in 附件标识列表 {
    let snapshot = 仓储
        .查询附件快照(attachment_id)
        .await?
        .ok_or(contract::错误码::附件不存在)?;
    附件快照列表.push(snapshot);
}
```

9 个附件 = 9 次串行 `await` = 9 次独立 DB roundtrip。每次 roundtrip ~2ms（局域网 PG），9 次 = 18ms。万人群里如果 100 人同时发带附件消息，仅附件查询就消耗 100 × 9 = 900 个 DB 连接-时间片。

### 设计

**改动 1：在 `Realtime消息仓储端口` 新增批量方法**

```rust
// src/消息/应用.rs — trait Realtime消息仓储端口
async fn 批量查询附件快照(
    &self,
    附件标识列表: &[String],
) -> Result<Vec<附件读取结果>, contract::错误码>;
```

**改动 2：适配层实现**

在 `src/实时/适配.rs` 中实现此方法，SQL 为：

```sql
SELECT a.attachment_id, a.kind, a.status, a.width, a.height,
       a.allows_thumbnail, ai.identity_id AS owner_identity_id
FROM attachments a
JOIN sessions s ON s.id = a.session_id
JOIN anonymous_identities ai ON ai.id = s.anonymous_identity_id
WHERE a.attachment_id = ANY($1)
```

返回的 `Vec` 不保证与输入顺序一致（SQL `ANY` 不保证顺序）。

**改动 3：应用层 `读取待发送附件_异步` 改写**

```rust
async fn 读取待发送附件_异步(...) -> Result<Vec<待发送附件>, 错误码> {
    if 附件标识列表.is_empty() {
        return Ok(vec![]);
    }
    let snapshots = 仓储.批量查询附件快照(附件标识列表).await?;

    // 关键：结果数量必须与请求数量一致，否则说明有不存在的附件
    if snapshots.len() != 附件标识列表.len() {
        return Err(错误码::附件不存在);
    }

    let 发送者身份 = 仓储.查询会话所属匿名身份(会话标识).await?
        .ok_or(错误码::会话无效)?;

    按统一消息规则校验附件快照列表(Some(&发送者身份), snapshots)
}
```

**同步版（`读取待发送附件`）保持不动。** 理由：同步冷路径只在 HTTP handler 中使用，频率低（手动测试级别），改它需要同步仓储端口也新增批量方法，增加接口面积但几乎没有性能收益。

### 要注意的陷阱

- **重复附件 ID 的处理：** 如果用户在 `attachment_ids` 里传了两个相同的 ID，SQL `ANY` 只会返回一行，导致 `snapshots.len() != 附件标识列表.len()` 返回"附件不存在"。这**恰好是正确行为**——同一附件不应该在一条消息里挂两次。不需要额外去重。
- **`查询会话所属匿名身份` 仍然单独查。** 这条查询只在有附件时才触发（需要校验 owner），且只查一次，合并到附件批量 SQL 里会让 SQL 变复杂且返回结构不清晰。保持独立。但在第 4 节的合并校验中，它会被一起合并掉。
- **不要在批量 SQL 里做 owner 校验。** SQL 只负责读取数据，owner/status/kind 校验由应用层 `按统一消息规则校验附件快照列表` 统一执行。这是 Onion 架构的要求——业务规则不能下沉到 SQL。

### 验证标准

1. 单测：9 个有效附件 ID 调用 `批量查询附件快照`，返回 9 条结果。
2. 单测：混入 1 个不存在的 ID，`读取待发送附件_异步` 返回 `附件不存在`。
3. 单测：传入重复 ID `["a", "a"]`，返回 `附件不存在`。
4. 确认：owner 不匹配时仍返回 `附件不属于当前发送者`。
5. 确认：同步版 `读取待发送附件` **没有被改动**。

## 4. 合并热路径校验 DB roundtrip

### 问题的根因

`src/消息/应用.rs` 第 213-216 行（`创建消息_异步`）的调用链：

```
校验客户端消息标识       ← 纯内存，0 DB
实时应用::校验房间订阅资格_异步  ← 内部分 3 步：
  ├─ 校验实时连接会话_异步     → 检查会话存在    ← 1 DB query
  ├─ 校验房间存在_异步         → 检查房间存在    ← 1 DB query
  └─ 校验房间订阅资格_异步     → 检查成员资格    ← 1 DB query
读取待发送附件_异步           ← 查询匿名身份   ← 1 DB query (有附件时)
                              ← 查询附件快照×N  ← N DB queries
创建统一消息事件               ← 1 事务
```

纯文本消息：4 roundtrip。带 9 附件：13 roundtrip。

### 设计

**核心思路：把"会话存在 + 房间存在 + 成员资格 + 匿名身份"4 个查询合并成 1 条 SQL。**

**改动 1：在 `Realtime消息仓储端口` 新增合并校验方法**

```rust
// src/消息/应用.rs — trait Realtime消息仓储端口 新增：
async fn 校验并读取消息发送资格(
    &self,
    房间标识: &str,
    会话标识: &str,
) -> Result<消息发送资格校验结果, contract::错误码>;
```

返回结构：

```rust
// src/消息/应用.rs 内部类型，不进 contract
pub(crate) struct 消息发送资格校验结果 {
    pub session_exists: bool,
    pub room_exists: bool,
    pub is_member: bool,
    pub 匿名身份标识: Option<String>,
}
```

**改动 2：适配层实现（单条 SQL）**

```sql
SELECT
  EXISTS(SELECT 1 FROM sessions WHERE session_id = $1)
    AS session_exists,
  EXISTS(SELECT 1 FROM rooms WHERE room_id = $2)
    AS room_exists,
  EXISTS(
    SELECT 1 FROM room_members rm
    JOIN sessions s ON s.id = rm.session_id
    WHERE s.session_id = $1
    AND rm.room_id = (SELECT id FROM rooms WHERE room_id = $2)
  ) AS is_member,
  (
    SELECT ai.identity_id
    FROM sessions s
    JOIN anonymous_identities ai ON ai.id = s.anonymous_identity_id
    WHERE s.session_id = $1
    LIMIT 1
  ) AS anonymous_identity_id
```

**改动 3：应用层 `创建消息_异步` 改写**

```rust
pub async fn 创建消息_异步(...) -> Result<contract::领域事件, contract::错误码> {
    校验客户端消息标识(客户端消息标识)?;

    // 一次 DB roundtrip 拿到全部校验结果
    let 资格 = 仓储.校验并读取消息发送资格(房间标识, 会话标识).await?;

    // 按原有顺序检查，保持错误码完全一致
    if !资格.session_exists {
        return Err(contract::错误码::会话无效);
    }
    if !资格.room_exists {
        return Err(contract::错误码::房间不存在);
    }
    if !资格.is_member {
        return Err(contract::错误码::成员资格不足);
    }

    // 附件路径：批量查询 + 统一校验
    let attachments = if 附件标识列表.is_empty() {
        vec![]
    } else {
        let 发送者身份 = 资格.匿名身份标识
            .ok_or(contract::错误码::会话无效)?;
        let snapshots = 仓储.批量查询附件快照(附件标识列表).await?;
        if snapshots.len() != 附件标识列表.len() {
            return Err(contract::错误码::附件不存在);
        }
        按统一消息规则校验附件快照列表(Some(&发送者身份), snapshots)?
    };

    let msg = domain::message::创建消息(true, 文本, &attachments)
        .map_err(application::映射领域错误)?;
    仓储.创建统一消息事件(房间标识, 客户端消息标识, 会话标识, &msg.文本, &msg.附件).await
}
```

**关键约束：错误检查顺序必须保持 session → room → membership。** 合并 SQL 一次返回所有 bool，但应用层仍按原顺序检查。这保证：
- 会话无效时不泄露"房间是否存在"
- 房间不存在时不泄露"用户是否有效"

**为什么成员资格判断从领域函数 `校验成员可发言` 变成了应用层直接检查 bool：**
现有 `校验房间订阅资格_异步` 的调用链是：`仓储.检查成员资格` → `domain::member::校验成员可发言(is_member)`。领域函数只做 `if !is_member { Err(成员资格不足) }` 这一步（见 `src/领域/成员.rs`）。合并后应用层直接检查 `!资格.is_member` 并返回同一个错误码，语义完全等价。不需要再绕回领域层调用一个只做 bool 判断的函数。

**冷路径保持不动。** `src/消息/应用.rs` 的同步版 `创建消息` 仍调用 `房间应用::校验房间订阅资格` 分步校验。原因同上——冷路径频率低，分步结构更清晰。

### 要注意的陷阱

- **`room_members` 表的 `room_id` 列存的是内部自增 ID，不是业务 `room_id` 字符串。** SQL 里需要 `rm.room_id = (SELECT id FROM rooms WHERE room_id = $2)`，不能直接 `rm.room_id = $2`。务必在写 SQL 前确认实际表结构。
- **`anonymous_identity_id` 子查询在会话不存在时返回 NULL。** 应用层用 `Option<String>` 接收，无附件时不关心这个值。有附件但值为 NULL 时返回 `会话无效`——这与现有行为一致。
- **不要把合并校验方法加到 `实时会话房间校验仓储端口`。** 它应该加到 `Realtime消息仓储端口`，因为只有创建消息热路径需要它。订阅路径（`handle_realtime_subscribe`）仍使用现有分步校验，不需要合并。

### 验证标准

1. 纯文本消息：确认只有 2 次 DB roundtrip（合并校验 1 + 事务提交 1）。
2. 带 9 附件消息：确认只有 3 次 DB roundtrip（合并校验 1 + 批量附件 1 + 事务提交 1）。
3. 会话无效时返回 `会话无效`（不是 `房间不存在` 或 `成员资格不足`）。
4. 房间不存在时返回 `房间不存在`（不是 `成员资格不足`）。
5. 非成员时返回 `成员资格不足`。
6. 现有所有测试全绿——特别是 `src/实时/外壳.rs` 底部的测试模块。

## 5. 数据库连接池调参

### 问题的根因

`src/组合根.rs` 第 43-44 行：

```rust
const 默认应用最大连接数: u32 = 20;
const 默认应用最小连接数: u32 = 0;
```

- **max=20：** 经过第 3、4 节优化后，纯文本消息 2 roundtrip、带附件 3 roundtrip。假设每次查询 ~2ms，20 个连接理论峰值 = 20 / 0.002 = 10000 查询/秒。看起来够了，但实际上连接获取、事务提交、锁竞争都有开销，真实吞吐约为理论值的 30-50%，即 3000-5000 查询/秒。万人群聊如果 500 人同时发消息（每条 2-3 查询），需要 1000-1500 查询/秒的持续吞吐——接近真实上限。
- **min=0：** 进程启动后第一批请求全部等待建连（TCP 握手 + PG 认证 ~10ms/连接），导致冷启动延迟尖刺。

### 设计

```rust
const 默认应用最大连接数: u32 = 50;  // 原 20
const 默认应用最小连接数: u32 = 5;   // 原 0
```

**不改接口。** `KOKO_DATABASE_MAX_CONNECTIONS` 和 `KOKO_DATABASE_MIN_CONNECTIONS` 环境变量仍可覆盖。

**为什么 max=50：** 给真实吞吐留 2-3 倍余量。50 个 PostgreSQL 后端连接对现代 PG 实例（默认 max_connections=100）来说仍在安全范围。如果部署环境 PG 只配了 20 连接，运维通过环境变量覆盖即可。

**为什么 min=5：** 预热 5 个连接可以处理进程启动后的前几十个请求而不排队。5 个空闲连接对 PG 的内存开销约 50MB（每连接 ~10MB work_mem 默认配置），可接受。

**为什么不做得更多：** 连接池大小超过 CPU 核数 × 2 后收益递减（PG 内部锁竞争增加）。50 对 4-8 核服务器已经足够。真正需要更多并发时，应该做读写分离或 PgBouncer 连接池化，不是继续加连接数。

### 要注意的陷阱

- **`src/组合根/配置测试.rs` 里有默认值断言。** 必须同步更新，否则测试会断。
- **不要改 `迁移固定连接数`（当前为 1）。** 迁移用单连接是正确的——DDL 操作不应并行。
- **不要改 `默认获取连接超时毫秒`（当前为 3000）和 `默认空闲回收秒数`（当前为 600）。** 这些与本次优化无关，改了反而增加回归风险。

### 验证标准

1. `src/组合根/配置测试.rs` 默认值断言更新后通过。
2. 环境变量 `KOKO_DATABASE_MAX_CONNECTIONS=30` 时，池实际 max=30（覆盖成功）。
3. 环境变量 `KOKO_DATABASE_MIN_CONNECTIONS=10` 时，池实际 min=10（覆盖成功）。
4. `KOKO_DATABASE_MIN_CONNECTIONS` > `KOKO_DATABASE_MAX_CONNECTIONS` 时仍正确报错。
