# 接收者看到黑灰卡片"附件当前不可获取" — 根因分析与修复方案

## 问题现象

万人万群实时群聊 IM（kokoqun.com）中，用户 A 发送图片/视频到群聊后，同时在线的用户 B/C/D **立刻**看到的不是图片内容，而是一个黑灰占位卡片，上面写着"附件当前不可获取"。点击全屏查看也是同样的提示。过一段时间后可能会恢复，也可能一直不出来。

**冒烟测试复现**（playwright-cli 双浏览器同时在线，房间 1234b）：
- 发送者（本地 127.0.0.1:8080）发送图片 → 发送者看到图片 ✅
- 接收者（公网 kokoqun.com）**立刻**看到"附件当前不可获取"黑灰卡片 ❌
- 网络数据：接收者的 8 个 locator 请求全部 **status: 0**（24ms 内被客户端取消）

---

## 根因（代码实证）

### 完整时序链

```
用户 A 点发送
  ↓
前端 complete_media_upload API → 后端 完成上传.rs
  ├─ [同步] 写入 attachment_distribution_metadata（INSERT，此时 torrent_info_hash = NULL）
  ├─ [同步] 写入 torrent 元信息（UPDATE torrent_info_hash = 真值）
  ├─ [同步] 返回 ready snapshot
  ├─ [fire-and-forget] 触发 sidecar 做种 ← 不阻塞 complete 响应
  └─ 返回给前端
  ↓
前端收到 complete 成功 → 草稿变 ready → 发送消息
  ↓
后端创建消息 → 消息\适配.rs
  ├─ tx.commit()
  ├─ 查询 attachment_distribution_metadata 获取 distribution_hint
  │   └─ 要求：content_hash + swarm_id + torrent_info_hash + web_seed_until 四字段全非空
  │   └─ 如果 torrent_info_hash 还是 NULL → hint = None → 消息不携带 distribution_hint
  ├─ 广播消息事件到所有在线用户
  ↓
用户 B/C/D（接收者）收到消息推送
  ↓
前端 预热权威消息媒体分发
  ├─ 消息有 distribution_hint？
  │   ├─ 有 → 路径 A：直接从 hint 构造 locator + 加入 swarm → 快速显示
  │   └─ 无 → 路径 B：HTTP 调 /api/media/{aid}/locator
  │       └─ locator 还没就绪 or seeder 还没做种 → degraded → 黑灰卡片
```

### 根因 #1：消息广播时 distribution_hint 可能为空

**代码位置**：`src/消息/适配.rs` 第 392-460 行

消息创建后查询 `attachment_distribution_metadata`。但 `torrent_info_hash` 是通过 **UPDATE**（不是 INSERT）写入的（`完成上传.rs` 第 542 行 `写入协作分发torrent元信息`），而 INSERT 返回的快照里 `torrent_info_hash: None`（`协作分发/适配.rs` 第 44 行）。

**虽然 INSERT 和 UPDATE 在同一个 `spawn_blocking` 中按序执行**（`完成上传.rs` 第 537-546 行），但从 complete 返回到前端发送消息再到后端创建消息查询分发元数据，中间有网络 RTT。正常情况下 torrent_info_hash 应该已经写入了。

**但问题在于**：如果 complete 和消息创建之间的间隔极短（前端 complete 回调后立刻发送），或者数据库连接池负载高导致查询延迟，就可能查到 `torrent_info_hash = NULL` → hint 为空。

### 根因 #2：seeder 做种是 fire-and-forget

**代码位置**：`完成上传.rs` 第 620-624 行

```rust
// complete 成功后 fire-and-forget 触发 sidecar 做种：
// 1. 不再阻塞 complete 响应（省 ~50-200ms），让前端更早拿到 ready 快照；
```

seeder sidecar 的做种命令是 fire-and-forget 的——complete 响应给前端后，seeder 可能还没开始做种。即使 distribution_hint 到达了接收者，WebTorrent swarm 里可能还没有任何 seed。

### 根因 #3：接收者降级链路没有重试

**代码位置**：`frontend/媒体/媒体播放.ts` 第 726-788 行

当 locator API 失败或 swarm 没有 seed 时，`创建降级结果()` 直接返回 degraded，没有自动重试机制。用户看到"附件当前不可获取"后，只有手动刷新或重新触发播放才可能恢复。

### 根因 #4（最直接的）：locator 请求 status: 0

8 个 locator 请求在 24ms 内返回 status: 0。这意味着请求被**客户端立刻取消**，而不是服务器返回错误。可能原因：

1. **AbortController 取消**：前端 `获取定位()` 内部可能有竞态取消逻辑
2. **inflight 去重冲突**：多个组件同时请求同一个 attachmentId 的 locator，inflight Promise 被覆盖/取消
3. **浏览器连接数限制**：Chrome 对同一域名最多 6 个并行 TCP 连接，8 个同时请求可能被排队/取消

---

## 为什么平时"看起来正常"

1. **用户后进房间**：消息已经广播完毕 → 查询历史消息时 LEFT JOIN 分发元数据 → hint 已到齐 → 路径 A 正常显示
2. **视频先显示 poster/缩略图**：视频附件有 `posterSrc` 缩略图 URL，即使 swarm 还没连上也能先显示静态帧
3. **图片没有 poster 兜底**：图片要么显示 swarm 真实内容，要么显示占位 SVG → 更容易暴露问题

## 修复方案

### 方案优先级

| 方案 | 改动面 | 修的是哪个根因 | 效果 |
|---|---|---|---|
| **A. 广播前确保 seeder 做种完成** | 后端 `实时/外壳.rs` | 根因 #2 | 接收者进 swarm 时一定有 seed |
| **B. 降级时自动重试** | 前端 `媒体播放.ts` | 根因 #3 | degraded 后自动恢复 |
| **C. 图片 fallback 到 web seed/缩略图** | 前端 `图片附件渲染.ts` | 体验层 | 至少先显示模糊图 |
| **D. locator status:0 排查** | 前端 `媒体定位器` | 根因 #4 | 修复请求被取消的问题 |

### 推荐修复顺序

**先 D → 再 B → 再 A**

1. **D 排查 locator status:0**：这是最直接的表层原因。如果 locator 请求不被取消，即使 hint 为空，HTTP fetch 也能拿到 locator → swarm 正常连接 → 图片显示。需要检查 `媒体定位器` 的 AbortController / inflight 去重逻辑。

2. **B 降级后自动重试**：即使第一次 locator 失败，500ms-1s 后重试很可能成功（此时 seeder 已做种）。这是最"乔布斯"的修法——用户永远不该看到"不可获取"。

3. **A 广播前确保 seeder**：把"广播后确认强种子"（`实时/外壳.rs` 第 927 行 `确认消息附件强种子`）**前移到消息创建之前**或至少在广播之前 await。但这会增加发送延迟 ~50-200ms。

### 不推荐的方案

- 在 complete 里阻塞等 seeder 做种 → 增加 complete 延迟，违背 fire-and-forget 设计
- 给接收者加"加载中"动画 → 治标不治本，用户仍然等待
- 延迟广播消息 → 违背实时 IM 核心体验

---

## 验证标准

修复后用 playwright-cli 双浏览器测试：
1. 发送者发图 → 接收者 **< 1 秒**内看到图片内容
2. 不再出现"附件当前不可获取"黑灰卡片
3. Console 无 locator status: 0 的异常请求
4. 现有 31 个媒体发布测试全绿
