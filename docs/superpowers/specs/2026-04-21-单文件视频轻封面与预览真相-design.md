## 0. 为什么要补这份文档

`2026-04-20` 那份文档把“视频 canonical 单文件 + 24 小时后删服务器冷备 + 长期只靠 WebTorrent swarm”这条主链立住了，这个方向没有问题。

问题出在另一件事没有说透：

**视频在产品体验上必须一进房就能看到预览，但在运行时又不能把预览绑死在播放链、自动播链和 `WebTorrent` 链上。**

这层没讲清后，代码就会自然长出矛盾：

1. 一边要求“禁止时间线直接吃 original 视频地址”；
2. 一边又不给新视频稳定的独立 preview 资产；
3. 最后只能退化成“等 autoplay / swarm playback 解析出来后，时间线才终于有首帧”。

于是用户真实感受到的就是：

1. 新用户进房先看到黑块或占位；
2. 只有触发自动播放后才突然出现预览；
3. 时间线预览和正式播放互相牵扯，容易再长出闪烁、抽搐、回退旧源之类的 bug。

这不是某个组件小 bug，而是**产品语义和运行时边界没有立住**。

---

## 1. 当前矛盾到底在哪里

### 1.1 代码事实

当前代码已经同时表达了三件互相打架的事：

1. 新 canonical 视频 `complete` 后，后端明确不再写 `thumbnail_storage_key`，测试也在守这个事实；
2. `preview_asset.still_url` 又只有在“附件真相确认有静态封面”时才会被投影出来；
3. 前端时间线为了防止偷偷回退 original 视频，已经把“无 playback 就不给视频首帧预览”写死了。

这三件事叠在一起的结果就是：

**新用户首进房间时，视频如果没有独立 preview 资产，就只能等 autoplay owner 或 swarm playback 先跑起来，预览才会出现。**

### 1.2 这不是播放器问题

这不是 `Video.js v10` 自己干坏了，也不是 `WebTorrent` 不够快。

真正的问题是：

- `Video.js` 负责“播放前后如何切换 poster / video 的显示”；
- `WebTorrent` 负责“如何把视频字节尽快送到浏览器并让 peer 互帮互助”；
- 但我们现在却让“时间线预览要不要存在”这件事，去等“播放链是否已经建立成功”。

这在职责上就是错位。

---

## 2. 上位裁决

### 2.1 一句话

**单文件视频主链继续成立，但视频必须额外拥有一张轻量、长寿命、客户端预制的静态预览图；它不是第二条媒体主链，只是视频附件必备的展示派生。**

### 2.2 关键定义

以后必须把这三件事彻底分开：

1. **视频分发真相**  
   只有 canonical video 一份，供自动播放、全屏播放、查看器、`WebTorrent` 做种和 24 小时冷备窗口使用。

2. **视频展示预览真相**  
   一张轻量 `preview_still`，负责“还没播之前用户先看到什么”。

3. **运行时播放真相**  
   由 `Video.js v10` 唯一播放器壳和媒体 owner 链裁决“何时开始播、何时切源、何时等待、何时恢复”。

产品语义上它们属于同一个视频附件。  
运行时职责上，它们绝不能混成一个开关。

---

## 3. 新裁决

### 3.1 视频必须自带轻封面

每个 ready 视频附件都必须有一张 `preview_still`。

它的来源不是服务器临时刮削，也不是播放时碰运气拿首帧，而是：

**客户端在预制 canonical 视频时，同步从同一份 canonical 视频里抽一张代表帧。**

这张图：

1. 和 canonical 视频属于同一个发布流程；
2. 和 canonical 视频表达的是同一个附件；
3. 但职责只是“未播放前的可见内容”；
4. 不是第二个视频文件，不是第二条播放主链，不是服务端重加工产物。

### 3.2 后端可以长期保存轻封面，但不能长期保存视频冷备

这次要把两个概念彻底分开：

1. **24 小时后必须删掉的是 canonical 视频冷备**；
2. **可以长期保留的是轻量静态 preview still**。

原因很简单：

1. 视频 canonical 冷备大、热、昂贵，长期保留会把服务器重新拖回重活；
2. preview still 很小，只承担时间线和查看器未播放前的展示职责；
3. 如果连 preview still 都不保留，新用户在 canonical 被删后就只能看到空占位，这不符合聊天产品基本体验。

所以这里要明确：

**“单文件主链”说的是媒体分发和平面真相只有一份 canonical video，不是说服务器上绝对不能存在一个轻量展示派生。**

### 3.3 WebTorrent 不负责 preview 语义

`WebTorrent` 只负责：

1. canonical video 的秒开；
2. peer 间 whole-file / piece 协作分发；
3. 24 小时后 canonical 冷源删掉后的长期互助存活。

`WebTorrent` 不负责：

1. 时间线未播放前要展示哪张图；
2. 给新用户“猜”一个稳定 preview；
3. 替代 `poster / still` 这一层产品语义。

换句话说：

**视频一开始就得有 preview；不是 swarm 建好以后才配有 preview。**

## 4. 角色分工

### 4.1 客户端职责

客户端视频预制流程升级为两个正式产物：

1. `canonical video`
2. `preview still`

推荐流程：

1. 先完成 canonical 判断与处理：
   - 直通；
   - remux / faststart；
   - 必要时 `Mediabunny + WebCodecs` 转码。
2. 再从 canonical 视频抽一张代表帧，生成轻量 preview still。

代表帧要求：

1. 默认避开 `0s` 的纯黑首帧；
2. 优先取开头几秒内最稳定且可识别的一帧；
3. 保留方向、旋转、展示宽高语义；
4. 文件尽量小，但不能糊到失真。

### 4.2 后端职责

后端继续不做重活，但需要接住 preview still 这个轻派生：

1. 校验 preview still 的 MIME、尺寸、大小、hash；
2. 存储 preview still；
3. 把 `preview_asset.still_url` 下发给时间线、查看器和定位接口；
4. 明确它是展示派生，不是视频播放入口。

后端依然不做：

1. 视频抽帧；
2. 视频重编码；
3. 视频封面服务器兜底生成；
4. 让 preview still 反向变成第二条视频主链。

### 4.3 前端运行时职责

前端以后必须遵守这条显示链：

1. 时间线一律先显示 `preview_still`；
2. 自动播放启动时，仍先保持 preview 可见；
3. 只有当正式播放首帧稳定可见后，preview 才退场；
4. 全屏查看器同样遵守这条切换语义。

因此：

1. 预览存在与否，不再取决于 autoplay owner；
2. 预览存在与否，不再取决于 swarm playback 是否先建立；
3. 自动播放只决定“什么时候从 preview 进入 playback”，不决定“有没有 preview”。

## 5. 数据与契约裁决

### 5.1 附件模型

视频附件以后至少要同时具备：

1. `storage_key`：canonical video
2. `preview_storage_key`：preview still

为降低迁移噪音，短期实现允许直接复用现有 `thumbnail_storage_key` 作为视频 `preview_still` 的存储字段，不急着先改名。

但语义上以后要统一叫：

- `preview still`
- `preview_asset`
- `still_url`

不要再让“thumbnail”一词把它误导成“可有可无的小图缓存”。

### 5.2 协议面

对 ready 视频附件，协议面必须满足：

1. `has_preview_asset = true`
2. `preview_asset.still_url` 必有
3. `media_asset` 继续描述 canonical video 和分发平面

这里要明确：

1. `preview_asset` 属于展示资产；
2. `media_asset` 属于媒体播放/分发资产；
3. 二者都是同一附件的一部分，但不能互相冒领职责。

### 5.3 生命周期

以后视频附件的生命周期要分两条：

### canonical video

1. ready 后进入 24 小时服务器冷备窗口；
2. 24 小时内可做 web seed / 初始种子；
3. 到期后删除服务器 canonical；
4. 长期正式播放只能继续依赖 peer swarm。

### preview still

1. ready 后即可长期可读；
2. 不受 24 小时 canonical 冷备退场影响；
3. 只在附件删除、消息删除、治理删除时退场。

## 6. 为什么必须这样做

### 6.1 不这样做会怎样

如果继续坚持“视频零 preview 派生、时间线直接等 playback 首帧”，那就会稳定得到这些后果：

1. 新用户首进房没有预览；
2. 首帧出现时机取决于 autoplay / preload / playback / peer / browser；
3. 预览会和播放切换互相卡住；
4. 一修“别回 original”，就容易把“首屏预览”一起修没；
5. 一修“别闪烁”，又容易把“自动播”修坏。

这不是实现不够巧，是边界本来就错了。

### 6.2 这样做为什么更优雅

这套设计真正优雅的地方在于：

1. **用户视角一体**  
   用户看到的是“同一个视频附件”，先看预览，再无缝进播放。

2. **工程视角分层**  
   preview still 只负责显示；canonical video 只负责播放与分发。

3. **服务器继续轻**  
   服务器不抽帧、不转码、不养长视频冷备，只保留一张小图。

4. **WebTorrent 吃得更满**  
   自动播和查看器不再承担“先帮时间线补预览”的额外职责，可以纯粹把 canonical 视频推向 swarm。

## 7. 轮子选择裁决

### 7.1 Mediabunny

`Mediabunny` 作为客户端预制主轮子继续成立，而且这次职责更明确：

1. 负责读取 canonical 视频；
2. 负责抽代表帧；
3. 负责方向/旋转/尺寸对齐；
4. 负责在浏览器里高性能完成这件事。

它适合做这件事，因为它本来就覆盖：

1. 视频读取；
2. sample / frame 访问；
3. thumbnail generation；
4. 与 `WebCodecs` 协同。

### 7.2 Video.js v10

`Video.js v10` 继续只做唯一正式播放器壳。

但要尊重它的边界：

1. `Poster` 负责播放前显示；
2. `Thumbnail` 主要是时间轴 hover / scrub 预览；
3. 正式播放仍由 `Video` 负责。

它不是用来替你“自动猜出时间线静态 preview”的。

### 7.3 WebTorrent

`WebTorrent` 继续只负责：

1. canonical 视频字节分发；
2. web seed / tracker / peer swarm；
3. 让看过视频的群友尽快参与高速互帮互助。

它不负责生成 preview，不负责替代 poster。

## 8. 否决的方案

### 8.1 否决：完全不存 preview，直接靠视频首帧

否决原因：

1. 浏览器没拿到首帧前，默认就可能什么都不显示；
2. 首帧什么时候出来不是稳定协议，而是浏览器和网络行为；
3. 这会把时间线体验绑到播放链。

### 8.2 否决：让后端抽帧生成 preview

否决原因：

1. 服务器又重新背上媒体加工热路径；
2. 和“客户端预制、后端轻校验”大方向冲突；
3. 会重新长出第二条服务端视频加工链。

### 8.3 否决：24 小时后把 preview 也一起删掉

否决原因：

1. 新用户之后就再也没有稳定预览；
2. 时间线会退化成空块或占位；
3. 这不是减压，而是把产品基本可读性一起删掉。

### 8.4 否决：把 preview 继续混叫 thumbnail，并视作可有可无

否决原因：

1. 这会让系统继续把 preview 当成“有就有，没有算了”的边角料；
2. 实际上它是视频附件体验成立的必要条件；
3. 名字不改，思维就容易继续漂。

---

## 9. 验证门禁

实现前必须先补失败测试，至少证明这些事实：

1. 视频 `complete` 后必定返回 `preview_asset.still_url`；
2. ready 视频附件在数据库里必定有 preview 存储键；
3. 新用户首进房、不触发 autoplay 时，也能立即看到视频预览；
4. 时间线 preview 显示不依赖 `swarm playback` 是否先建立；
5. 自动播放从 preview 切到正式播放时无闪烁、无黑块、无抽搐；
6. 全屏查看器从 preview 切到正式播放时同样无闪烁；
7. 24 小时后 canonical 冷备删除，不影响 preview still 继续展示；
8. preview still 的读取不会拉起正式视频播放链，不会偷吃原视频；
9. 自动播和全屏播放仍统一走 `Video.js v10` 唯一播放器真相；
10. `WebTorrent` 分发逻辑不再承担“补预览”职责。

## 10. 对 2026-04-20 文档的修正

这份文档对 `2026-04-20-客户端预制媒体与WebTorrent单文件主链-design.md` 做如下精确修正：

1. “单文件主链”保留；
2. “后端不承担媒体加工重活”保留；
3. “服务器 24 小时后删除 canonical 视频冷备”保留；
4. 但“后端只存唯一 canonical 文件”这一句需要改成：

**后端长期保存一份 canonical video 的分发真相，以及一张客户端预制的轻量 preview still 展示派生；其中只有 canonical video 参与正式播放与 `WebTorrent` 分发主链。**

这不是推翻原设计，而是把原设计里已经隐含但没说透的部分正式写清。

## 11. 官方依据

- [Mediabunny Thumbnail generation example](https://mediabunny.dev/examples/thumbnail-generation/)：官方直接提供浏览器内视频抽缩略图示例，说明“从同一视频里抽 preview”是它的正用法。
- [Mediabunny 首页](https://mediabunny.dev/)：官方明确强调高性能读取、按需读取、配合 `WebCodecs` 做硬件加速编解码，适合作为客户端预制与抽帧轮子。
- [Video.js Poster](https://videojs.org/docs/framework/react/reference/poster)：官方把 `Poster` 定义为播放前显示的缩略图组件，播放开始后隐藏，换新源时再出现。
- [Video.js Thumbnail](https://videojs.org/docs/framework/react/reference/thumbnail)：官方把 `Thumbnail` 定义为时间轴 scrubbing / hover 预览，而不是时间线首屏 poster。
- [Video.js Options Reference](https://legacy.videojs.org/guides/options/)：`poster` 明确是播放前显示的图片，`preload` 只是浏览器 hint，不保证你想要的首帧时机。
- [MDN `<video>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video)：若未指定 `poster`，则在 first frame 可用之前可能什么都不显示，证明“纯靠视频自己顶 preview”不是稳定 UX。
- [WebTorrent Docs](https://webtorrent.io/docs)：官方示例聚焦 `file.streamTo(video)` 这类字节传输与播放接入，没有把 preview / poster 当成它的职责。

---

## 12. 最终裁决

以后在 `koko` 里，视频附件必须满足这条正式语义：

1. **同一个视频附件，天然同时拥有两种表达：**
   - 一个 canonical video，用于播放与分发；
   - 一张 preview still，用于未播放前展示。
2. **这两个表达来自同一份视频真相，但职责不同。**
3. **轻封面必须客户端预制，服务器只轻量存储，不负责抽帧。**
4. **24 小时后删的是 canonical 视频冷备，不是 preview still。**
5. **`WebTorrent` 继续只负责 canonical video 的秒开与群友互帮互助。**

这才是既符合“后端一身轻”，又符合“新用户进房立刻看得懂这是个什么视频”，同时还能让自动播放和全屏播放把 `WebTorrent` 真正吃满的自洽设计。
