# 实时群聊最小闭环（MVP）设计

## 1. 背景与目标

项目长期目标是万人到亿人实时在线 IM，但当前处于起步阶段。为避免范围失控和架构返工，先交付一个可在 Linux 公网服务器运行的最小闭环：

- 可创建/加入房间
- 可实时群聊
- 消息可持久化并可断线恢复

本阶段部署形态：**公网 Linux + 单节点架构**。

> 说明：单节点是阶段性架构范围，不是本地玩具方案；设计需预留后续横向扩展空间。

---

## 2. 范围定义

### 2.1 In Scope（必须交付）

1. 匿名会话引导，生成稳定 `session_id`
2. 按房间短码加入；不存在则自动建房
3. 房间内实时发送/接收文本消息
4. 消息持久化到 PostgreSQL
5. 房间快照 + 增量事件拉取（支持断线后追平）
6. 关键链路结构化日志（至少含 `room_id/session_id/event_position/error_code`）

### 2.2 Out of Scope（明确不做）

1. 多节点部署、分片与跨节点一致性
2. 已读回执、撤回、@提及、文件消息
3. 房间治理（禁言、踢人、管理员体系）
4. E2E 加密与复杂安全体系
5. 移动端/桌面端壳

---

## 3. 硬约束

1. 实时主通道固定使用 **socketioxide**
2. 禁止手搓同类实时轮子、禁止新增第二套实时真相路径
3. adapter/shell 只做协议与 IO 适配，不承载业务裁决
4. 业务真相以权威持久化为准，不以连接态/ack/本地状态替代

---

## 4. 核心模型与分层职责

## 4.1 核心数据模型（MVP）

1. `Session`：匿名身份
2. `Room`：房间实体（`room_id` / `room_code`）
3. `RoomMember`：成员关系
4. `RoomEvent`：房间事件流（`event_position` 单调递增）
5. `Message`：消息正文（与 `RoomEvent` 对齐）

## 4.2 分层职责

- `domain`：成员资格、短码、消息文本等不变量
- `application/usecase`：进房、发消息、加载快照、恢复编排
- `contract`：稳定命令/查询/快照/事件/错误码
- `adapter`：PostgreSQL + socketioxide + HTTP 翻译实现
- `shell`：路由/接线/运行时编排

---

## 5. 数据流与同步策略

## 5.1 主链路（发消息）

1. 客户端持有 `session_id` 并进入房间
2. 客户端先拉 `snapshot`（拿到 `latest_event_position`）
3. 建立 socketioxide 订阅
4. 发消息时服务端执行：
   - 校验成员资格
   - 在同一事务写入 `RoomEvent + Message`
   - 推进房间 `latest_event_position`
5. 服务端广播已成立的领域事件

## 5.2 断线恢复（最小策略）

1. 客户端重连后按已知位置拉增量
2. 若增量闭合失败，回退到“重拉快照 + 增量追平”

---

## 6. 接口与事件（MVP）

## 6.1 HTTP

1. `POST /api/session/bootstrap`
2. `POST /api/rooms/join-or-create`
3. `GET /api/rooms/{room_id}/snapshot?session_id=...`
4. `GET /api/rooms/{room_id}/events?from=...`

## 6.2 Realtime（socketioxide）

- 客户端上行：
  - `subscribe_room_stream`
  - `send_text_message`
- 服务端下行：
  - `room_event`（已成立业务事实）
  - `control_result`（订阅结果/拒绝/错误）

> 要求：领域事实与控制面语义严格分离，不混用。

---

## 7. 错误语义与可观测

## 7.1 稳定错误码（MVP）

- `invalid_argument`
- `invalid_session`
- `room_not_found`
- `membership_required`
- `system_error`

## 7.2 日志要求（最小）

关键链路日志必须可串联，最少包含：

- `room_id`
- `session_id`
- `event_position`
- `error_code`

---

## 8. 验收标准（可证）

1. 两个用户加入同一房间，可互发实时消息
2. 服务重启后，历史消息可拉取
3. 断线重连后，可通过“快照+增量”追平
4. 非成员发送消息被拒绝（稳定错误码）
5. 失败链路可通过结构化日志快速定位

---

## 9. 测试策略（最小完备）

1. 领域测试：成员校验、短码校验、空消息校验
2. 用例测试：进房/发消息编排与错误映射
3. 集成测试：
   - 实时收发闭环
   - 事务一致性与 `event_position` 连续性
   - 断线恢复链路
4. 日志验证：关键失败路径字段完整

---

## 10. 演进留口（不在本期实现）

1. 多节点与横向扩容
2. 更复杂治理能力（禁言/踢人/角色）
3. 富消息类型
4. 更细粒度恢复与重放策略

本期设计要求：未来能力只能通过稳定契约扩展，不能推翻本期真相链路。
