# 实时群聊最小闭环（MVP）PRD v0.2

日期：2026-04-05  
状态：草案（内部落地优先）

## 1. 问题与目标

### 1.1 要解决的问题

当前项目已有架构设计方向，但缺少一份以“可交付结果”为中心的产品需求文档，导致范围、验收和测试口径容易漂移。

### 1.2 本期目标（MVP）

交付一个可真实使用、可验证、可复现的最小群聊闭环：

1. 用户可创建/加入同一房间并实时收发文本消息
2. 消息可持久化，服务重启后历史仍可读取
3. 断线后可恢复到权威状态（快照 + 增量）
4. 在 Linux 公网服务器部署后，外网用户可访问并参与群聊
5. 在 Win11 开发环境中，可用局域网多设备完成预发布模拟验收

### 1.3 成功判定

只要满足以下四项即视为 MVP 达标：

1. 公网单节点可稳定运行最小闭环
2. 公网域名/IP 可从外网访问并完成实时群聊
3. 关键失败路径可被结构化日志快速定位
4. 需求范围未越界到治理、富消息或分布式主题

---

## 2. 目标用户与核心场景

### 2.1 目标用户

1. 内部开发与测试成员（主要用户）
2. 早期体验者（可选）

### 2.2 核心场景

1. 体验者首次打开页面，完成匿名会话引导
2. 输入房间短码加入房间；房间不存在则创建
3. 房间内多人实时聊天
4. 某设备断网/刷新后恢复并追平消息
5. Linux 公网部署后，不同网络下的用户可接入同一房间完成聊天
6. Win11 开发阶段用局域网多设备提前模拟公网多人联调

---

## 3. 范围定义

### 3.1 In Scope（本期必须交付）

1. 匿名会话引导，生成稳定 `session_id`
2. 按短码加入/创建房间
3. 房间内实时文本消息收发
4. PostgreSQL 持久化消息与事件位置
5. 房间快照和增量拉取能力（断线追平）
6. 关键链路结构化日志（至少含 `room_id/session_id/event_position/error_code`）
7. 公网可访问发布能力（监听地址、端口放通、跨域策略可用）
8. 局域网多设备预发布验收能力（同网段不同终端可访问并完成实时聊天）

### 3.2 Out of Scope（本期明确不做）

1. 多节点、分片、跨节点一致性
2. 已读、撤回、@提及、文件消息
3. 房间治理（禁言、踢人、角色权限）
4. E2E 加密与复杂安全体系
5. 原生移动端/桌面端壳

## 4. 产品需求（FR）

### FR-1 会话引导

1. 用户首次进入可获得可复用的匿名 `session_id`
2. 无效会话应返回稳定错误码

### FR-2 加入或创建房间

1. 用户输入短码后可加入房间
2. 房间不存在时自动创建并加入
3. 非法短码返回稳定错误码

### FR-3 实时消息

1. 同房间成员可实时收发文本消息
2. 非成员发送消息必须被拒绝
3. 传输确认不等于业务成立，消息成立以权威事件为准

### FR-4 持久化与恢复

1. 每条成立消息必须落库
2. 服务重启后历史可读取
3. 客户端断线重连可通过“快照 + 增量”追平

### FR-5 公网可访问发布能力

1. 服务监听地址使用 `0.0.0.0`（或等效全网卡监听），不绑定 `127.0.0.1`
2. 服务器防火墙与云安全组放通对外端口
3. 外网通过域名或公网 IP 可访问并完成房间收发
4. Socket/HTTP 跨域策略允许目标前端来源

### FR-6 局域网预发布模拟

1. Win11 开发阶段可使用局域网不同设备接入同一实例
2. 至少 3 台设备可实时互发消息
3. 至少 1 台设备执行断网/重连并追平成功

## 5. 非功能需求（NFR）

### NFR-1 架构边界

1. 实时主通道固定使用 `socketioxide`
2. 不新增第二套实时真相路径
3. adapter/shell 不承载业务裁决

### NFR-2 可观测性

1. 关键路径必须打结构化日志
2. 失败链路可按 `room_id/session_id/event_position/error_code` 串联追踪

### NFR-3 可测试性

1. 核心链路具备自动化测试（领域、用例、集成）
2. 公网发布和局域网预发布都具备可重复执行的手工验收步骤

---

## 6. 验收标准（UAT + 技术验收）

### 6.1 基础闭环验收

1. 两个不同会话加入同一房间并实时互发消息
2. 服务重启后历史消息仍可拉取
3. 非成员发送消息被拒绝并返回稳定错误码

### 6.2 断线恢复验收

1. 聊天过程中主动断开一端网络或刷新页面
2. 恢复连接后可自动追平缺失消息
3. 追平失败时可通过重拉快照恢复一致状态

### 6.3 局域网多设备真人模拟验收

1. 准备 3 台设备（如手机/平板/笔记本）接入同一局域网
2. 设备 A 创建房间，设备 B/C 加入同一房间
3. 三端轮流发送消息并确认全员实时可见
4. 设备 C 中途断网 30 秒后重连，确认消息追平
5. 验收通过后记录测试时间、设备清单、异常与结论

### 6.4 公网可访问发布验收

1. Linux 服务监听地址为 `0.0.0.0`，并确认对外端口已放通
2. 使用外网网络访问域名或公网 IP，完成会话引导与入房
3. 至少两端在外网环境下实时互发消息成功
4. 至少一端断线后恢复并追平消息成功

---

## 7. 发布边界与依赖

### 7.1 发布边界（本期）

1. 部署形态：公网 Linux 单节点
2. 数据存储：PostgreSQL
3. 客户端形态：Web 壳（浏览器）

### 7.2 关键依赖

1. 可访问的 PostgreSQL 实例
2. 可用的公网域名或公网 IP
3. 最低限度的日志采集与问题回溯能力
4. 局域网测试环境（用于预发布模拟，不替代公网验收）

---

## 8. 风险与缓解

1. 误把 `0.0.0.0` 当成公网可用的充分条件  
缓解：发布验收明确包含监听地址、端口放通、域名/IP 可达、跨域策略四项联合检查。

2. 实时与快照语义混淆导致“看似成功”  
缓解：验收必须以权威事件和快照一致性为准，不以 transport ack 为准。

3. 范围膨胀拖慢首版交付  
缓解：严格按 In Scope/Out of Scope 执行，新增需求进入下一期。
