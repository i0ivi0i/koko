# 聊天 IM 反网页化设计宪法

日期：2026-04-07  
状态：设计已确认，作为后续前端房间页改造与评审的硬边界  
范围：`koko` 聊天房间页、房间搜索页及后续 IM 壳层视觉与交互实现

## 0. 一句话结论

`koko` 的聊天房间页必须被设计成“一个持续在线的会话空间”，而不是“网页里的一块聊天模块”。

以后所有前端房间页改动，都必须先过这一条总裁决：

**如果一个界面去掉消息内容后，看起来仍然像普通网页，那么它就还不是 IM。**

---

## 1. 为什么要立这份宪法

当前前端房间页已经出现了明显的网页化倾向：

1. 页面容易被实现成整页滚动，而不是消息区滚动。
2. 房间页容易退化成居中卡片或普通内容面板。
3. 输入区、标题区、提示区很容易被写成网页表单和网页说明块。
4. 内部技术字段和系统语气容易泄露到主界面。

这些问题不是“审美偏好不同”这么简单，而是会直接破坏群聊 IM 最核心的体验：

1. 用户不再感觉自己“停留在一个会话里”。
2. 用户会觉得自己在“浏览一个网页内容区”。
3. 群聊的持续在线感、对话感、输入即说话感都会被削弱。

所以这份文档不是建议，而是后续前端实现的裁决基线。

---

## 2. 页面主权宪法

### 2.1 根原则

聊天房间不是网页中的一个 `section`，聊天房间本身就是当前屏幕。

### 2.2 必须满足

1. 房间页必须锁定在视口内。
2. 房间页必须作为应用容器占满当前屏幕，而不是内容容器自然撑开。
3. 顶部、消息区、输入区必须属于同一个连续会话空间。
4. 消息区必须拥有中部主权。
5. 输入区必须拥有底部主权。

### 2.3 必须禁止

1. 禁止整页滚动承载聊天内容。
2. 禁止房间页被包进 `max-width` 居中卡片里。
3. 禁止出现“网页头部 + 网页正文 + 网页表单”的视觉分裂。
4. 禁止消息区只是页面中段的一个次要模块。
5. 禁止输入栏像普通表单区一样漂浮在内容结构里。

### 2.4 裁决句

1. 只要滚一下鼠标，整个页面跟着动，就是网页。
2. 只要第一眼看到的是卡片而不是会话空间，就是网页。
3. 只要消息区不是这个屏幕的主角，就是网页。

---

## 3. 视觉主次宪法

### 3.1 正确的主次顺序

在 IM 房间页里，视觉优先级必须固定：

1. 第一主角永远是消息流。
2. 第二主角是输入栏。
3. 第三主角才是房间头部。
4. 其他信息全部降权。

### 3.2 必须禁止的抢戏行为

1. 禁止头部比消息区更厚、更亮、更花。
2. 禁止输入栏弱得像附属表单。
3. 禁止状态提示和说明文案长时间压过消息本身。
4. 禁止背景效果、玻璃感、阴影、渐变比消息更显眼。
5. 禁止每个模块都争夺用户注意力。

### 3.3 结果标准

用户进入房间后的前两秒，注意力必须自然落在：

1. 正在发生的对话。
2. 当前所在房间。
3. 自己随时可以发消息。

凡是让用户先看到标题、装饰、告警条或说明文，再慢慢找到消息区的设计，都判为网页化实现。

---

## 4. 交互语义宪法

### 4.1 根原则

网页交互的核心是“浏览内容”；  
IM 交互的核心是“停留在会话里”。

### 4.2 必须满足

1. 滚动语义必须属于消息流，不属于页面。
2. 返回语义必须是“离开当前会话”，不是网页后退。
3. 进入房间语义必须是“进入一个持续空间”，不是打开内容页。
4. 加载更早消息必须像对话向上延伸，不像网页分页。
5. 恢复和错误提示必须像会话状态变化，不像网页报错区块。
6. 发送语义必须是“说出去”，不是“提交表单”。

### 4.3 必须禁止

1. 禁止鼠标滚轮先推动 `body/html`。
2. 禁止把产品里的返回语义外包给浏览器历史栈。
3. 禁止把历史加载做成“查看更多内容”的网页按钮逻辑。
4. 禁止一出错就把房间打断成异常页面。
5. 禁止发送反馈迟钝到像网页提交。

### 4.4 裁决句

凡是让用户感觉自己在浏览，而不是在停留一个会话里的交互实现，都必须回退重做。

---

## 5. 文案与信息暴露宪法

### 5.1 能站到台前的信息

1. 房间短码，或未来的房间名。
2. 人话化、轻量化的会话状态。
3. 与发送动作直接相关的输入提示。

### 5.2 必须退到幕后

1. `room_id`
2. `session_id`
3. 技术错误码
4. adapter / transport / contract 术语
5. 只对开发者有意义的系统字段

### 5.3 必须禁止的文案方式

1. 禁止把内部技术字段直接渲染给用户。
2. 禁止把主界面写成后台系统状态说明书。
3. 禁止把聊天页文案写成网页操作提示。
4. 禁止提示条说得比聊天本身还多。
5. 禁止主界面同时暴露过多信息层级。

### 5.4 裁决句

凡是用户读完之后，感受到的是“系统在向我汇报状态”，而不是“聊天空间在自然反馈”，这句话就不该待在主界面里。

## 6. 实现层硬禁令

### 6.1 结构禁令

1. 禁止房间页包在 `max-width` 居中卡片里。
2. 禁止房间页依赖 `body` 文档流自然撑开高度。
3. 禁止输入区放在消息区上面。
4. 禁止进房页和会话页复用同一套网页表单骨架。
5. 禁止把头部、消息区、输入区写成互不相干的网页分块。

### 6.2 滚动禁令

1. 禁止 `body/html` 承担聊天滚动。
2. 禁止消息区没有明确的伸缩约束，例如缺少 `min-height: 0` 一类关键布局条件。
3. 禁止历史加载、未读恢复、自动滚动与用户滚动混成一个语义层。
4. 禁止页面滚动条与消息区滚动条竞争主滚动。

### 6.3 视觉实现禁令

1. 禁止后台通用按钮和普通输入框直接充当聊天输入栏。
2. 禁止消息气泡复用普通内容卡片样式。
3. 禁止提示条长期占据固定高度并压缩消息区。
4. 禁止为了“高级感”堆重玻璃、重阴影、重渐变，结果压过消息层。

### 6.4 文案实现禁令

1. 禁止模板层直接渲染 `roomId/sessionId/error.code`。
2. 禁止把共享契约字段直接映射成面向用户的文案。
3. 禁止把错误处理做成长段网页说明块。

### 6.5 组件职责禁令

1. 禁止壳层组件把展示状态和业务真相混写。
2. 禁止为了省事，把加入房间页和房间页揉成一个通用网页模板。
3. 禁止任何调试便利残留在正式房间主视图。

---

## 7. 和 DDD 壳层边界的关系

这份宪法只约束前端 `shell / presenter` 的体验实现，不改变领域真相边界。

### 7.1 不允许被这份宪法误导去做的事

1. 不允许为了“更像 IM”就把成员资格、权限、消息成立真相塞进前端。
2. 不允许为了“更顺滑”就让前端裁决后端业务语义。
3. 不允许为了展示需要就把只服务某个壳的 UI 语义倒灌进共享 `contract`。

### 7.2 这份宪法真正约束的东西

1. 壳层布局怎么组织。
2. 壳层状态提示怎么降权。
3. 房间主界面怎么避免技术泄露。
4. 房间页怎么守住 IM 会话感而不是网页感。

---

## 8. 评审时的快速裁决清单

以后评审任何聊天页改动时，先过这 10 条：

1. 整个页面会不会跟着消息一起滚？
2. 房间页看起来是不是一张网页卡片？
3. 消息区是不是这个屏幕最重要的区域？
4. 输入栏是不是稳定贴底，并且像会话工具而不是表单？
5. 顶部是不是导航栏，而不是资料说明区？
6. 主界面有没有出现任何内部技术字段？
7. 状态提示是不是轻量内联，而不是大块告警面板？
8. 返回动作是不是明确代表离开当前会话？
9. 历史加载是不是像时间流延伸，而不是网页分页？
10. 去掉消息内容后，这个界面还会不会像普通网页？

只要其中任意一条答得不对，就说明设计已经往网页味滑回去了。

---

## 9. 当前项目里的直接落地方向

这份宪法对当前 `koko` 的直接指导含义是：

1. 房间页必须继续朝单屏会话容器收口。
2. 房间搜索页和房间页要明确分开，不复用网页表单骨架。
3. 顶部保留返回、标题、轻状态，不再承载说明块。
4. 消息滚动必须继续严格锁在消息容器里。
5. 任何 `room_id`、技术错误码、系统字段都不能回到主视图。
6. 后续如果新增房间名，也只能替换标题展示来源，不能破坏 IM 主次关系。

---

## 10. 一句话落地原则

以后前端做聊天界面，不是去想“怎么把网页做得像聊天”，而是要反过来想：

**怎么让这个屏幕从一开始就只像会话空间，而不再给网页感留下生长空间。**
