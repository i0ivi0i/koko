# 全项目直接依赖最新稳定化设计

日期：2026-04-06  
状态：设计完成，待实现

## 1. 目标

本设计只解决一个问题：

把 `koko` 当前“直接依赖存在版本滞后，但升级策略仍偏经验化”的状态，收口成一套可执行、可验证、不会漂移的最新稳定化规则与升级顺序。

本设计的强约束如下：

1. 全项目直接依赖默认必须跟到最新稳定版
2. 不能只因为“当前能跑”就长期停留在旧版本
3. 如果升级要求连带提高 `Node`、`Rust`、测试命令或 CI 基线，本次允许同步提高
4. 如果升级引发 breakage，不回退到旧版，而是继续修到兼容
5. 执行顺序固定为：先前端，再 Rust，最后统一收口验证

本设计明确不解决：

1. 间接依赖逐个强制最新化
2. 手工 override 某个 transitive dependency 只为压警告
3. 无边界地“顺手”重构无关业务模块
4. 为升级引入新的私有包管理封装层

## 2. 背景与现状

当前项目已具备：

1. 前端独立 `package.json` 与 `pnpm-lock.yaml`
2. 后端独立 `Cargo.toml` 与 `Cargo.lock`
3. 前端存在 `build / test / watch` 基本验证链路
4. 后端存在 `cargo test` 与集成测试链路

当前暴露出的直接问题：

1. 前端 `jsdom` 不是最新稳定版
2. 由旧 `jsdom` 链路带出 `whatwg-encoding@3.1.1` 的 deprecated 提示
3. 目前项目虽然有“优先最新稳定版”的原则，但缺少明确裁决标准与升级顺序
4. 一旦升级引发 Node / Rust 基线变化，当前没有明确规则说明是否允许一并推进

这意味着项目现在的规则还不够精确：

1. 知道“应该尽量新”，但没有把“最新稳定”落实成默认硬约束
2. 知道某些依赖旧了，但没有定义“什么时候必须升、怎么升、升不动怎么办”
3. 容易在“保持稳定”和“保持最新”之间反复摇摆，导致执行时漂移

## 3. 设计原则

### 3.1 直接依赖默认跟最新稳定

1. `Cargo.toml` 与 `frontend/package.json` 中的直接依赖，默认都要跟到各自生态里的最新稳定版
2. 这里的“直接依赖”同时包含运行时依赖、开发依赖、测试依赖、构建依赖
3. 只要是项目主动声明在依赖清单里的版本，就要承担“尽量最新稳定”的维护责任

### 3.2 不靠手工修补间接依赖掩盖问题

1. 如果 deprecated 或安全提示来自间接依赖，优先通过升级直接依赖解决
2. 不允许为了消一条警告，手工加 `overrides`、私有 patch 或第二套依赖图，除非已有明确证据证明上游长期失修且项目被阻断
3. 升级策略必须尽量沿着上游官方链路推进，而不是自己发明依赖管理旁路

### 3.3 基线可以提高，但必须明示

1. 如果最新稳定依赖要求更高 `Node` / `Rust` / `Cargo` / 测试工具链版本，本次允许同步提高
2. 工具链基线变化必须被记录进实现说明与脚本边界中，不能默默发生
3. 不能一边升级依赖，一边继续假装支持已经不满足上游要求的旧运行环境

### 3.4 先升级，再修兼容，不回退旧版

1. 一旦确认某个直接依赖不是最新稳定版，本次默认目标是升上去
2. 如果升级导致测试失败、类型错误、API 变更或环境变更，不把“暂时不升”作为默认出口
3. 默认出口是继续修复代码、脚本与测试，直到新版稳定通过验证

### 3.5 分阶段推进，避免根因混杂

1. 前端依赖先升级并验证
2. Rust 依赖后升级并验证
3. 最后统一检查脚本、说明、工作树与开发链路
4. 不能把前后端全部混在一次大爆炸升级里，否则 breakage 根因难以归位

## 4. 审计与执行范围

本次范围固定为“全项目直接依赖”，包括：

1. `frontend/package.json` 中的 `dependencies`
2. `frontend/package.json` 中的 `devDependencies`
3. `Cargo.toml` 中的 `[dependencies]`
4. `Cargo.toml` 中的 `[dev-dependencies]`

明确不包含：

1. `pnpm-lock.yaml` 中的每一个间接依赖逐个人工追平
2. `Cargo.lock` 中的每一个传递依赖逐个人工判定
3. 非依赖类工具配置的大面积顺手重写

如果直接依赖升级后自然带动锁文件变化，这是允许且必要的；但锁文件不是独立审计对象。

## 5. 升级顺序

### 5.1 第一阶段：前端直接依赖最新化

目标：

1. 把前端全部直接依赖升到 npm 最新稳定版
2. 修复由此引发的 Node 基线、Vitest、JSDOM、TypeScript、esbuild 或测试环境兼容问题
3. 消化当前类似 `whatwg-encoding` 这类由旧直接依赖链路带出的 deprecated 提示

本阶段默认检查项：

1. `dependencies` 是否全部为最新稳定
2. `devDependencies` 是否全部为最新稳定
3. `package.json` 脚本是否仍与新版工具链匹配
4. Node 基线是否需要抬高
5. 前端测试、构建、watch 链路是否仍成立

必须验证：

1. `pnpm --dir frontend install`
2. `pnpm --dir frontend build`
3. `pnpm --dir frontend test`

### 5.2 第二阶段：Rust 直接依赖最新化

目标：

1. 把后端全部直接依赖升到 crates.io 最新稳定版
2. 修复由此引发的 API、trait、feature、异步运行时、日志、网络框架或测试兼容问题
3. 如果需要，提高 Rust / Cargo 工具链基线，并同步收口脚本和说明

本阶段默认检查项：

1. `[dependencies]` 是否全部为最新稳定
2. `[dev-dependencies]` 是否全部为最新稳定
3. feature 组合是否仍合理
4. `cargo` 子命令与新版依赖是否仍匹配
5. 后端测试和集成测试是否仍成立

必须验证：

1. `cargo test -- --nocapture`

### 5.3 第三阶段：统一收口

目标：

1. 检查 `run.ps1` 是否仍与新版前端/后端工具链兼容
2. 检查是否仍存在明显的 deprecated、版本漂移或脚本漂移
3. 统一复核开发入口、测试入口与依赖基线说明
4. 清理升级过程中产生的低价值兼容胶水与冗余说明

必须验证：

1. `powershell.exe -NoProfile -ExecutionPolicy Bypass -File E:\koko\run.ps1` 的受控烟测
2. `git status --short` 工作树收尾检查

## 6. 裁决标准

### 6.1 最新稳定的判定口径

统一口径如下：

1. npm 侧以 registry 上当前最新稳定版为准
2. Rust 侧以 crates.io 当前最新稳定版为准
3. 不把 alpha、beta、rc、nightly 当作默认目标
4. 不把“文档推荐但尚未稳定”的预发布版本当作默认目标

### 6.2 遇到 breakage 的处理原则

如果升级到最新稳定版后出现：

1. 测试失败
2. 类型错误
3. API 变更
4. 最低 Node / Rust 版本提高
5. 构建脚本或 CI 行为变化

本次默认处理方式是：

1. 保留升级结果
2. 继续修适配
3. 补验证
4. 不回退旧版，除非已出现外部不可控阻断且有明确证据

### 6.3 允许抬高的基线

本次允许同步提高：

1. `Node` 最低版本
2. `Rust` 工具链版本
3. `Cargo` 行为依赖版本
4. 前端测试命令所需环境版本
5. 开发启动脚本中对工具链的版本门禁

要求：

1. 改动后要有新鲜验证
2. 必须把变化范围说清楚
3. 不得偷偷依赖“我本机正好更高版本”而不把门槛明示出来

## 7. 对 `whatwg-encoding` 告警的具体裁决

当前结论：

1. 这条告警是真的
2. 它来自旧版 `jsdom` 直接依赖链，而不是项目业务代码
3. 它属于“前端测试链落后”的表征，不是后端运行时故障
4. 正确处理方式不是手工 patch `whatwg-encoding`
5. 正确处理方式是把前端直接依赖升级到最新稳定，并让上游依赖图自然收敛

所以这条告警在本设计里不是单独的特殊任务，而是“前端直接依赖最新化”阶段的一个验收信号。

## 8. 风险与边界

### 8.1 允许出现的变化

1. 测试基线变化
2. 部分脚本参数变化
3. 运行环境最低版本变化
4. 前后端少量适配代码变化
5. 锁文件大幅更新

### 8.2 不允许出现的退化

1. 为了迁就旧依赖而长期卡在旧版
2. 为了压告警手搓私有 override 体系
3. 升级过程中把无关业务逻辑一起重写
4. 因升级顺手造新的基础设施抽象层
5. 在没有验证的情况下声称“应该兼容”

## 9. 验证策略

### 9.1 每阶段都必须有新鲜验证

前端阶段至少验证：

1. 安装成功
2. 构建成功
3. 前端测试全绿

Rust 阶段至少验证：

1. `cargo test -- --nocapture` 全绿

统一收口阶段至少验证：

1. 开发启动器烟测成立
2. 工作树干净

### 9.2 完成判定

只有同时满足以下条件，升级任务才能声明完成：

1. 全项目直接依赖已对齐到各自最新稳定版
2. 升级引发的 breakage 已修复
3. 工具链基线变化已落进脚本或说明
4. 前端验证通过
5. Rust 验证通过
6. 启动器烟测通过
7. 工作树干净并已提交

## 10. 实施结论

本设计最终裁决如下：

1. `koko` 后续执行“依赖现代化”时，不再以“当前能跑”作为继续停留旧版的理由
2. 全项目直接依赖默认跟最新稳定版，开发依赖与测试依赖也不例外
3. 升级顺序固定为“前端 -> Rust -> 收口”
4. 工具链基线允许自动提高，但必须显式落地并验证
5. 遇到 breakage 默认继续适配，而不是退回旧版

这份设计是后续实现计划与执行的唯一边界依据。
