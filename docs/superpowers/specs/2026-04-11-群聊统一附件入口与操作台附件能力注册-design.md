# 群聊统一附件入口与操作台附件能力注册设计

日期：2026-04-11  
状态：Ready for Planning  
适用范围：`koko` 前端 TypeScript 聊天壳、底部操作台、媒体发送入口  
关联文档：

- `docs/superpowers/specs/2026-04-10-群聊图片发送单链收口与复杂度清理-design.md`
- `docs/superpowers/specs/2026-04-11-群聊媒体上传切换到Tus与Rustus-design.md`

## 1. 背景

当前群聊发送区已经支持图片和视频上传，但用户交互形态存在明显错位：

1. 底部发送区同时暴露了“图片按钮”和“视频按钮”两个并列入口
2. 用户想做的真实任务是“发一个附件/媒体”，不是先决定“我要走图片系统还是视频系统”
3. 当前 UI 形态把内部技术分类过早暴露给用户，导致主路径不自然、输入区拥挤、扩展方向混乱

代码层面的真实情况也已经证明，这不是“底层必须如此”，而是 `shell` 表面形状先裂开了：

1. `frontend/聊天壳.ts` 直接渲染了两套文件输入、两套按钮、四个入口处理器
2. `frontend/媒体/媒体发布.ts` 内部其实已经有较完整的统一上传主链，真正按图片/视频分叉的，只是预处理和元数据读取这类必要差异
3. `准备选择图片()`、`准备选择视频()` 这两个对外表面已经退化成空壳，说明当前 public surface 比内部主链更冗余

一句话：

**问题的本质不是“图片和视频不能统一”，而是“附件入口不该继续由聊天壳用双按钮硬编码”。**

## 2. 为什么要改

### 2.1 用户心智为什么要统一

成熟 IM 的主流做法都不是让输入区长期摆着“图片按钮 + 视频按钮”：

- Telegram 的统一附件入口是小别针，附件能力在入口后展开
- 微信也是统一附件入口，用户先进入附件/照片能力，再由系统和程序判断具体媒体形态

它们真正统一的不是图标，而是心智：

**用户先表达“我要发附件”，再由系统决定展示和处理什么。**

### 2.2 当前代码为什么不应该继续堆在 `聊天壳.ts`

`frontend/聊天壳.ts` 现在已经承担：

- 壳级状态装配
- 操作台渲染
- 草稿带渲染
- 输入和提交编排
- 图片/视频双入口细节

继续把附件入口逻辑留在这里，会导致：

1. `shell` 和附件能力耦合越来越深
2. 将来加 `文件 / 拍摄 / 位置` 时，必须继续改一个越来越肥的热点文件
3. 用户入口组织逻辑和媒体上传实现逻辑互相缠住，违背 DDD 分层和 Unix 单一职责

### 2.3 为什么这次不只是“改一个按钮”

如果只把两个按钮改成一个按钮，但不调整边界，后面还会出现同样的问题：

- 入口逻辑仍然散在 `聊天壳.ts`
- 新能力一来，壳层又会长出第二轮条件分支
- `frontend/媒体` 继续事实和入口都要管

所以这次必须把“统一附件入口”落实成架构边界，而不是一次临时 UI 修补。

## 3. 目标

本设计要达成以下目标：

1. 底部发送区只保留一个统一附件入口
2. 用户点击入口后，当前直接进入统一媒体选择器
3. 统一入口支持图片和视频，由程序按文件事实判断类型
4. 把“附件入口”组织逻辑从 `聊天壳.ts` 中抽出，但本轮不强制迁移整个底部操作台骨架
5. 为未来 `文件 / 拍摄 / 位置` 等能力预留稳定扩展位
6. 不重写现有媒体上传主链，不再重复造轮子
7. 让代码更符合 DDD 分层和 Unix 单一职责

## 4. 非目标

本设计明确不做以下事情：

1. 不修改后端消息与附件真相
2. 不修改 `prepare -> upload -> complete -> create_message` 主链
3. 不在本轮同时落地文件、拍摄、位置等新能力
4. 不强行把图片和视频的内部预处理完全合并
5. 不在本轮追求全项目统一重命名 `shellConsole`
6. 不为了“架构更纯”拆出大量碎文件
7. 不在本轮把整个底部 composer / footer / 主输入框 / 主发送动作一次性迁移到新目录

这份设计只解决：

**群聊底部发送区的附件入口如何统一，同时给未来附件能力演进留出稳定边界。**

## 5. 候选方案与裁决

### 5.1 方案 A：继续由 `聊天壳` 直接维护统一按钮

不推荐。

做法：

- 把两个按钮删成一个
- 统一文件输入
- 其他逻辑继续堆在 `frontend/聊天壳.ts`

优点：

- 第一眼改动最少

缺点：

- 只是把 UI 从“双按钮”换成“单按钮”，没有收边界
- 将来新增附件能力，仍要回头继续改 `聊天壳`
- 热点文件继续变胖，债务只是后移

### 5.2 方案 B：附件能力注册型

推荐。

做法：

- 在 `frontend/操作台` 下引入附件入口层
- 底部发送区只认识一个统一附件入口
- 入口后通过“附件能力注册表”组织当前可用能力
- 当前只注册 `media`
- `media` 再调用现有媒体主链

优点：

- 既解决眼前双按钮错误，又为未来扩展留位
- 符合 `shell` 表达意图、能力模块处理事实的分层
- 不需要修改后端真相和契约
- 可以最大限度复用现有媒体上传主链

缺点：

- 需要新增一层壳级组织模块
- 需要重写部分测试假设

### 5.3 方案 C：直接提升为跨端共享附件契约

本轮不采用。

做法：

- 把附件能力模型上提到跨壳通用契约
- Web、iOS、Android、CLI 共用一个附件能力定义

优点：

- 长期最统一

缺点：

- 本轮问题主要在前端 `shell`
- 现在直接上提到跨端契约，会让一次 UI 纠偏变成重型重构

### 5.4 最终裁决

本轮固定采用：

**方案 B：附件能力注册型**

核心判断：

1. 当前问题在壳层边界，不在后端契约
2. 必须把“附件入口”从“媒体实现细节”里独立出来
3. 当前只注册 `media`，但结构上必须允许未来继续扩展

## 6. 分层裁决

这一节是防止实现漂移的核心约束。

### 6.1 Domain / Application / Contract

领域、应用、共享契约层本轮不新增“附件入口”概念。

原因：

- “附件入口”是用户交互编排，不是业务真相
- `kind=image|video` 这类字段仍然属于媒体事实
- 后端和共享契约不应该承载“小别针”“加号”“菜单项”“是否直达”等壳层语义

### 6.2 Shell

`shell` 层拥有：

- 底部操作台骨架
- 统一附件入口
- 当前有哪些附件能力可见、可点
- 点入口后应该直接执行还是展开面板

`shell` 层不拥有：

- 图片/视频类型真相
- 文件 MIME 判断真相
- 媒体上传业务规则
- ready 真相

### 6.3 Media Adapter

`frontend/媒体` 继续拥有：

- 选中文件后的媒体类型判断
- 图片预处理
- 视频元数据读取
- 草稿状态机
- 上传编排
- complete 前后的媒体链路

`frontend/媒体` 不再拥有：

- 底部发送区入口形态
- 按钮是否显示
- 当前附件能力组织方式

### 6.4 操作台

底部发送区按钮、输入框、附件入口、主发送动作都属于“操作台”。

因此：

- `frontend/操作台` 是合理的新目录
- 不建议再发明“操控台”“控制台”新词
- 现有项目语言已经明显更偏向“操作台”

## 7. 宏观结构设计

目标结构如下：

1. `frontend/操作台`
2. `frontend/操作台/附件入口`
3. `frontend/媒体`
4. `frontend/聊天壳.ts` 作为壳级装配点

### 7.1 `frontend/操作台`

职责：

- 作为“底部操作台相关壳层模块”的承载目录
- 当前第一阶段只要求承接附件入口边界
- 为未来操作台进一步收口预留稳定命名空间

它不负责：

- 图片和视频的上传细节
- 媒体类型识别
- 媒体草稿生成规则

补充裁决：

- 本轮不要求把整个 `shellConsole` 立即搬进 `frontend/操作台`
- 当前只把“附件入口”这一块先迁出热点文件
- 主输入框、主发送动作、状态槽等现有结构仍可继续留在 `frontend/聊天壳.ts`

### 7.2 `frontend/操作台/附件入口`

职责：

- 统一附件按钮
- 统一隐藏文件输入
- 附件能力注册表
- 附件入口编排
- 当前只有一个能力时的直达策略
- 触发统一媒体选择器
- 把已选文件交给具体能力实现方

它不负责：

- 媒体上传
- 媒体预处理
- 媒体错误诊断

### 7.3 `frontend/媒体`

职责：

- 作为 `media` 附件能力的实现方
- 接收“用户已选中文件”的事实
- 逐个文件识别 `kind`
- 调用现有图片/视频预处理
- 复用现有上传状态机与 complete 链路

### 7.4 `frontend/聊天壳.ts`

职责：

- 装配壳级状态
- 连接操作台与媒体模块
- 继续渲染草稿带、主舞台、列表等壳级内容

它应当退位，不再直接拥有：

- 双按钮入口
- 双文件输入
- 四个入口处理器

## 8. 附件能力注册表设计

### 8.1 为什么需要注册表

如果不引入注册表，未来每新增一个附件能力，就会回到：

- `聊天壳.ts` 加一个按钮
- `聊天壳.ts` 加一个条件分支
- `聊天壳.ts` 再接一套细节

这属于明显的热点持续膨胀。

注册表的作用是：

**把“当前有哪些附件能力”从壳级模板硬编码，收口成一张显式能力表。**

### 8.2 注册表拥有的字段

v1 注册表只要求描述当前真正需要的最小字段：

1. `id`
2. `icon`
3. `visible`
4. `disabled`
5. `triggerStrategy`
6. `execute`

说明：

- `triggerStrategy`
  表示当前能力是“直达执行”还是“进入二级面板”

- `execute`
  表示点中该能力后，交给哪个适配器执行

以下字段如果未来需要，可以后续再加，不作为 v1 必需：

- `label`
- `order`
- 分组信息
- 二级面板展示模型

### 8.3 当前版本的注册表裁决

当前先只注册一个能力：

- `media`

它的策略固定为：

- `triggerStrategy = direct`

也就是：

**点击附件入口后，不弹能力面板，直接进入统一媒体选择器。**

统一媒体选择器的形态也在这里一并钉死：

- 采用单个隐藏的 `input[type=file]`
- 该输入启用 `multiple`
- `accept` 使用图片与视频类型的并集
- 不再保留第二个并行隐藏文件输入

同时，v1 的可见/可用规则必须继承当前操作台事实，不允许实现时自由发挥：

- `visible`
  仅在当前 `consoleMode === "message"` 时显示

- `disabled`
  与当前 `派生壳级操作台状态().auxSlot.disabled` 保持同源，现阶段即 `pending === true` 时禁用

- `icon`
  当前默认仍使用 `+`

- `execute`
  直接触发统一媒体选择器，不弹菜单

这让第一版的用户体验保持最克制：

- 外部看起来就是一个入口
- 内部架构上已经为未来多能力扩展留好位

## 9. 统一附件入口设计

### 9.1 当前交互裁决

当前交互固定为：

1. 底部只保留一个统一附件入口按钮
2. 图标皮肤可以是 `+`，也可以以后换成 Telegram 风格的小别针
3. 用户点击后，当前直接进入统一媒体选择器
4. 选择器同时支持图片和视频
5. 程序按文件事实判断媒体类型
6. 按钮只在消息模式显示，进入房间前与 hidden 状态不显示
7. 按钮禁用规则继续继承当前 `pending` 约束，不额外引入第二套判断

### 9.2 为什么当前不弹菜单

原因不是“菜单永远不好”，而是当前注册表里只有一个能力 `media`。

如果这时还强行弹一层菜单，只会增加步骤，不会增加价值。

所以当前逻辑应该是：

- 有且仅有一个默认能力时，直达
- 有多个能力时，再考虑展开附件面板

### 9.3 与 Telegram 小别针逻辑的关系

这次要学习的不是 Telegram 的图标本身，而是它的架构智慧：

- 稳定的统一附件入口
- 附件能力在入口后展开
- 能力组织独立于媒体实现

当前第一版只是把“展开”阶段进一步收敛成“只有一个能力时直接执行”。

## 10. 媒体能力设计

### 10.1 用户层统一

对用户来说，只有一个事实：

**我要发一个附件/媒体。**

用户不需要提前思考：

- 我现在是在走图片系统
- 还是视频系统

### 10.2 实现层轻分叉

选中文件后，程序逐个文件判断：

- 是图片
- 是视频
- 还是不支持的类型

这里必须允许轻分叉，因为：

- 图片要做 MIME 补全和手机图转码
- 视频要读元数据
- 上传上限和错误语义也可能不同

正确做法不是“内部完全不分”，而是：

**统一入口 + 统一主链 + 必要处轻分叉**

### 10.3 当前 public surface 的裁决

`frontend/媒体/媒体发布.ts` 对 `shell` 暴露的表面应收成：

- 一个统一处理所选文件入口

不再继续维持：

- `准备选择图片`
- `准备选择视频`
- `处理选择图片文件`
- `处理选择视频文件`

统一媒体选择器的按钮点击、隐藏文件输入、原生 `input.click()`、`change` 监听，全部归：

- `frontend/操作台/附件入口`

`frontend/媒体/媒体发布.ts` 只负责吃到“已选中的文件集合”之后的媒体事实处理。

因为这组 public API 已经比内部主链更冗余。

## 11. 文件与模块边界

### 11.1 新增目录

允许新增：

- `frontend/操作台`
- `frontend/操作台/附件入口`

这是为了建立真正的壳层边界，而不是为了碎片化拆文件。

目录新增不等于全量搬家。第一阶段只要求把附件入口相关模块放进来。

### 11.2 暂不大规模搬迁的东西

以下内容本轮不要求立刻全搬：

- `#shellConsole*` 这类现有 DOM id
- 所有“操作台”相关 selector 的全量重命名
- 聊天壳中非附件入口的现有结构

原因：

- 先稳行为骨架
- 再收命名和局部噪音
- 防止一次重构同时引爆样式和测试

### 11.3 保持不动的模块

以下模块原则上继续保留在 `frontend/媒体` 下：

- `媒体草稿`
- `媒体发布`
- `媒体诊断`
- `图片预处理`
- `视频元数据`

不要为了这次入口重构，再把媒体模块拆成更多碎片。

## 12. 迁移顺序

迁移顺序固定为三步：

### 12.1 第一步：建立壳层目录与附件入口边界

新增：

- `frontend/操作台`
- `frontend/操作台/附件入口`

并让 `聊天壳` 开始通过它们装配附件入口。

这一阶段的目标是：

- 先把附件按钮、隐藏文件输入、能力注册和入口编排迁出 `聊天壳`
- 不要求同时搬动主输入框、主发送动作和整个 footer 骨架

### 12.2 第二步：收口聊天壳表面

从 `frontend/聊天壳.ts` 中删除：

- 双按钮入口
- 双文件输入
- 双点击处理器
- 双 change 处理器

替换为：

- 由 `frontend/操作台/附件入口` 提供的一个统一附件按钮
- 由 `frontend/操作台/附件入口` 持有的一个统一媒体文件输入
- 由 `frontend/操作台/附件入口` 负责的一个统一文件选择处理器

`frontend/聊天壳.ts` 在这一步只保留装配职责，不再拥有附件入口的 DOM 细节。

### 12.3 第三步：收口媒体模块 public surface

让 `frontend/媒体/媒体发布.ts`：

- 对外只保留统一媒体入口
- 内部改成逐文件识别 `kind`
- 继续复用现有上传主链

## 13. 测试策略

测试必须重新分层，不能再围绕“双按钮旧表面”打。

### 13.1 操作台 / 附件入口测试

应验证：

- 底部只有一个统一附件入口
- 当前只有 `media` 能力时，点击入口会直接执行该能力
- 入口只在消息模式显示
- `pending` 时入口会被禁用，其他规则维持现状
- 壳层不再暴露图片/视频双按钮

### 13.2 能力注册表测试

应验证：

- 当前只注册 `media`
- `media` 是默认直达能力

补充裁决：

- “将来扩能力时，不需要回头修改 `聊天壳` 的结构假设”属于设计验收约束
- 计划阶段不要把它误拆成脆弱的元测试任务

### 13.3 媒体能力测试

应验证：

- 统一入口能同时接收图片和视频
- 逐个文件正确判断 `kind`
- 混合批次时，图片和视频分别走对主链
- 非支持类型被正确拒绝

### 13.4 聊天壳装配测试

应验证：

- 聊天壳仍然能装配操作台、草稿带、发送动作
- 但不再对附件入口内部细节做大量直接断言

### 13.5 TDD 裁决

本轮实现必须先写失败测试，再做重构。

尤其必须先建立失败测试覆盖：

1. 双按钮旧表面已被移除
2. 统一入口仍能选图、选视频
3. 混合选择时媒体类型不会跑错

## 14. 风险与缓解

### 14.1 风险：`聊天壳.ts` 热点继续膨胀

缓解：

- 第一阶段就建立 `frontend/操作台`
- 让附件入口先迁出热点文件

### 14.2 风险：统一入口后混合批次跑错链路

缓解：

- 媒体模块改成逐个文件识别 `kind`
- 先写混合批次失败测试

### 14.3 风险：为“更优雅”制造过度抽象

缓解：

- 当前只建一个壳层注册表
- 不上提到 `contract`
- 不引入私有事件总线、通用平台 SDK、二级框架壳

### 14.4 风险：重命名噪音过大

缓解：

- 第一阶段不追求全量把 `shellConsole` 统一改名
- 先改行为边界，再处理命名收口

## 15. 明确禁止项

本轮实现必须禁止：

1. 把附件入口逻辑继续散在 `frontend/聊天壳.ts`
2. 把“附件入口”语义上提到共享契约层
3. 为这次改动再手搓一个私有前端能力平台
4. 为了“统一”而抹掉媒体内部必要的图片/视频差异
5. 新增第二套并行附件入口活路径
6. 在不删除旧双按钮假设的前提下再叠一层新入口

## 16. 完成标准

只有同时满足以下条件，才算本轮完成：

1. 底部发送区只剩一个统一附件入口
2. 当前点击入口直接进入统一媒体选择器
3. 图片和视频都能通过统一入口发送
4. `聊天壳` 不再直接拥有双按钮/双输入逻辑
5. `frontend/操作台/附件入口` 已建立并成为入口组织边界
6. `frontend/媒体` 继续复用现有主链，不产生第二套上传系统
7. 旧双入口 DOM、旧 public API、旧测试假设被系统性删除

## 17. 总结

这次重构表面上是在修“图片按钮和视频按钮为什么拆成两个”，本质上是在做一件更重要的事：

**把统一附件入口从壳层热点文件里抽出来，建立一个可演进、可扩展、不过度设计的操作台附件边界。**

应该保留的：

- `媒体` 模块内部已有的上传共核
- 图片/视频作为媒体事实的必要差异
- 壳层只表达用户意图的分层原则

应该删除的：

- 双按钮双输入双入口处理器
- `聊天壳` 对附件入口细节的直接拥有
- 将来必然继续长分支的硬编码入口组织方式

最终目标不是“把一个 `+` 换成小别针”，而是：

**让底部操作台拥有一个稳定的统一附件入口，让媒体能力回到它该在的位置，让后续扩展不再继续往代码里堆屎山。**
