# 发送热路径与多房间实时回流优化设计

日期：2026-04-08  
状态：设计已确认，待进入 implementation plan  
范围：后端单机内多房间群聊的发送热路径、权威事件回流路径、实时广播时序、相关测试与验收口径  
约束：不改领域真相，不改前后端共享契约，不提前引入分布式，不把前端乐观态当成性能补丁

## -1. 总原则

这次优化必须继续服从整个项目唯一的 DDD 真相体系：

1. 房间消息是否成立，只能由后端权威事件流裁决。
2. `event_position` 仍然是房间内消息顺序与同步补洞的唯一逻辑锚点。
3. `socketioxide` 和 `socket.io-client` 继续只做实时 adapter，不升级成第二真相源。
4. 热路径优化只允许压薄等待、压缩重复查询、收正事务边界，不允许偷改业务语义。
5. 发送者自己“更快看到消息”也必须建立在同一条权威事件回流之上，而不是新造一条本地假成立主链。
6. 这份 spec 是单独专项，不和“前端房间编排内核重构”“已读锚点稳定化”等已有 spec 混写，避免执行时范围串线。

一句话定性：

**这次不是做“看起来更实时”，而是把“消息成立并回流到当前房间所有在线用户”的后端主链压薄。**

---

## 0. 一句话结论

当前系统的主方向是对的：

1. 先落权威事实，再广播；
2. 房间内顺序靠 `event_position` 保证；
3. realtime 只是快通道，补洞靠 `snapshot + events`。

但当前发送热路径还不够“单机内多房间并发友好”，主要问题是：

1. 同一房间的事件位置推进依赖数据库串行热点；
2. 热路径里还有重复冷查询和可收缩等待；
3. 提交后到广播前的路径还不够短；
4. 缺少足够直观的测试来证明“热房间不会把其他房间一起拖慢”。

本次专项的目标，是在**不改变业务真相**的前提下，把发送主链收成更接近成熟 IM 的单机形态：

1. 同房消息仍然绝对有序；
2. 多房间之间尽量互不拖累；
3. 发送者更快收到自己的权威消息回流；
4. 广播失败不会回头污染“消息已成立”的语义；
5. 断线和补洞链仍然能兜底。

## 1. 背景与问题

### 1.1 当前项目的好处

当前后端已经具备一条正确的 DDD 实时主链：

1. [src/外壳.rs](/E:/koko/src/外壳.rs) 中 `socketioxide` handler 只是把实时输入翻译成稳定命令，并广播权威事件。
2. [src/用例.rs](/E:/koko/src/用例.rs) 负责成员资格、房间存在性、消息命令是否合法等应用层裁决。
3. [src/适配.rs](/E:/koko/src/适配.rs) 负责实际落库，并推进房间的 `latest_event_position`。
4. [src/契约.rs](/E:/koko/src/契约.rs) 里已把 `event_position`、快照、增量事件、阅读锚点等稳定同步语义定义清楚。

因此，这次优化不是“纠正方向错误”，而是“压掉热路径里不必要的重量”。

### 1.2 当前真正的发送热路径

当前发送文本消息的核心热路径，大致是：

1. socket handler 收到 `send_text_message`
2. 应用层验证会话与房间语义
3. 持久化层查询房间、会话、成员资格与当前房间最新事件位置
4. 事务内：
   - `SELECT ... FOR UPDATE`
   - 计算下一条 `event_position`
   - `INSERT room_events`
   - `INSERT messages`
   - `UPDATE rooms.latest_event_position`
5. 事务提交后，把同一条权威 `room_event` 广播给房间在线连接

这条链的优点是清楚；  
问题是它目前还偏“正确但不够薄”。

### 1.3 当前最值得警惕的四个问题

1. **同房串行热点不可避免，但持锁时间还可以更短。**  
   房间内为保证顺序而串行是合理代价，但不应该把可外移的动作继续留在热点事务前后。

2. **热路径里重复冷查询偏多。**  
   会话内部主键、房间内部主键、成员资格、展示字段等，如果每次发送都重复查，吞吐会被拖胖。

3. **提交后回流路径还不够短。**  
   用户最敏感的是“我发了之后，为什么权威消息回流还慢半拍”。  
   这段延迟常常不在“消息能不能成立”，而在“提交后到广播前的尾巴”。

4. **目前还缺少专门证明‘多房间并发互不陪葬’的测试。**  
   没有证据前，不能把“单房间能聊”说成“多房间并发可扛”。

## 2. 外部最佳实践校准

### 2.1 Socket.IO 官方的硬边界

Socket.IO 官方资料给出的关键约束如下：

1. 默认只保证顺序，不保证必达，默认是 **at most once**。  
   来源：[Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)
2. 服务端到客户端要想额外可靠，应用必须自己做：
   - 唯一事件 ID
   - 持久化
   - 客户端 offset
   - 重连后补 missed events  
   来源：[Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)
3. connection state recovery 不是总会成功，失败时仍要准备重新同步。  
   来源：[Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/)
4. rooms 是 server-only 的广播概念，不是业务成员真相。  
   来源：[Rooms](https://socket.io/docs/v4/rooms/)
5. `ackTimeout/retries` 只说明命令收没收到，不说明消息业务上已经成立。  
   来源：[Client options](https://socket.io/docs/v4/client-options/)

对 `koko` 的直接启发：

1. 不能因为优化发送体感，就把“广播发出去了”当成“消息已成立”。
2. 不能把 socket 在线态当成同步真相。
3. 房间广播分组和成员资格真相必须继续分开。

### 2.2 `socketioxide` 官方的硬边界

`socketioxide` 官方文档给出的关键点如下：

1. 它是 Rust 的 Socket.IO server，天然是 adapter，而不是业务内核。  
   来源：[socketioxide crate docs](https://docs.rs/socketioxide/latest/socketioxide/)
2. 每个 incoming connection/message handler 都会在独立任务里执行，不阻塞事件管理主循环。  
   来源：[socketioxide crate docs](https://docs.rs/socketioxide/latest/socketioxide/)
3. 不建议自己长期保存 `SocketRef`，跨任务广播优先用 `SocketIo` 句柄。  
   来源：[socketioxide crate docs](https://docs.rs/socketioxide/latest/socketioxide/)
4. 广播语义已经明确：
   - `to(room)` 不含当前 socket
   - `within(room)` 包含当前 socket
   - 广播和远端 adapter 相关操作需要 `await`  
   来源：[Socket docs](https://docs.rs/socketioxide/latest/socketioxide/socket/struct.Socket.html)

对 `koko` 的直接启发：

1. 不能为了解性能去手搓第二套房间广播核心。
2. 发送者自己看到消息回流，仍然应该复用 `within(room)` 这类权威广播路径。

### 2.3 Telegram / WhatsApp 的共识

Telegram 官方资料表明：

1. 核心是 `seq / pts / qts + getDifference` 这种“增量锚点 + gap repair”主链。  
   来源：[Working with Updates](https://core.telegram.org/api/updates)
2. 已读与会话位置靠逻辑锚点，如 `read_inbox_max_id`，不是像素。  
   来源：[dialog](https://core.telegram.org/constructor/dialog)

WhatsApp 官方公开工程资料表明：

1. 真正要守的是“设备不是 source of truth，后端权威同步状态才是”。  
   来源：[How WhatsApp enables multi-device capability](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)
2. 初次快照 + 后续增量，是成熟 IM 的标准组合。

对 `koko` 的直接启发：

1. 发送者自己更快看到消息，也不该走第二真相。
2. 真正成熟的 IM 都是“权威事件 + 回流 + 补洞”三位一体，而不是“乐观态假装主链”。

## 3. 优化目标

### 3.1 主目标

在单机内多房间并发在线的前提下，优化发送热路径，使其满足：

1. 同一房间消息顺序仍然绝对正确；
2. 不同房间之间尽量互不拖累；
3. 发送者自己更快看到权威消息回流；
4. 广播失败不会污染消息成立语义；
5. 断线与补洞主链保持不变。

### 3.2 次目标

1. 把热路径里重复冷查询收口；
2. 把事务内的非必要动作外移；
3. 明确“事务内只保留真相成立必需动作”的边界；
4. 为后续前端实时体感优化提供更稳后端地基。

### 3.3 非目标

本次明确不做以下事情：

1. 不引入分布式、多实例、负载均衡、跨节点广播总线；
2. 不改共享契约；
3. 不改成员资格或消息成立语义；
4. 不改已读模型；
5. 不把前端 pending/optimistic UI 扩大成第二主链；
6. 不为了“未来也许要扩展”提前造房间 actor 平台或事件平台。

## 4. 允许改哪些层，不允许改哪些层

### 4.1 允许改动的层

1. `adapter / realtime`
   - `socketioxide` 事件 handler 的热路径组织
   - 广播时序
   - 提交后权威事件 fanout 路径

2. `adapter / persistence`
   - 查询组织
   - 事务边界
   - 事务内动作顺序
   - 冷热查询拆分

3. 少量 `application / usecase`
   - 仅在确有必要时收口编排语义
   - 不允许把真相判断下沉到 adapter

### 4.2 不允许改动的层

1. `domain`
   - 消息成立语义
   - 房间成员语义
   - 房间事件语义

2. `contract`
   - 不新增性能补丁式字段
   - 不新增前端专属“伪快感”返回值

3. `shell / frontend`
   - 不通过更重乐观态掩盖后端热路径问题

## 5. 必须保留的真相链

这几步是本次优化绝对不能打坏的真相链：

1. 验证发送命令是否合法；
2. 为房间生成唯一且连续的下一条 `event_position`；
3. 先落权威事件和权威消息，再推进房间最新位置；
4. 事务提交成功后，才广播给房间在线连接；
5. 发送者自己看到的，也必须是同一条权威事件回流。

一句话：

**这次优化只允许压薄负担链，不能改坏真相链。**

## 6. 当前热路径的主要瓶颈假设

### 6.1 房间级行锁是合理的，但持锁窗口还可以压缩

当前为保证同房消息顺序，事务内依赖：

1. `SELECT ... FOR UPDATE`
2. 计算 `next_position`
3. 写入事件表与消息表
4. 推进 `rooms.latest_event_position`

这条链不会被这次优化消灭。  
但需要把“必须在锁内做的事”和“可以外移的事”切开。

### 6.2 重复冷查询会让热路径发胖

当前需要重点审查是否存在这些情况：

1. 会话内部主键每次发送都重复查；
2. 房间内部主键每次发送都重复查；
3. 成员资格查询和房间存在性查询未合并；
4. 提交后广播前仍有额外查询或格式装配。

这类查询若不收口，会直接拖慢单房间高频发送，并间接占用整个连接池。

### 6.3 提交后到广播前的“尾巴”必须最短化

用户主观上的“消息发出后怎么还没出现”，往往发生在：

1. 事务已经提交；
2. 但广播前还做了额外动作；
3. 于是发送者自己仍然要等。

因此本次专项必须把下面这条规则写死：

**事务一旦提交，权威事件广播必须立刻成为最优先的下一步。**

### 6.4 多房间并发不能互相陪葬

单房间内为了顺序而串行，是业务合理代价。  
但不同房间之间不应被同一个热房间大面积拖慢。

因此专项成功的标准不是“热房间本身无限快”，而是：

1. 热房间的问题尽量局部化；
2. 冷房间和普通房间的正常聊天不被明显拖垮。

## 7. 设计方案

### 7.1 总策略：保持“先落权威事实，再广播”，但把热路径压薄

采用保守而正确的方案：

1. 不改变“先落库再广播”的总顺序；
2. 不引入房间级 actor/queue 平台；
3. 不提前做跨节点形状；
4. 只优化热路径组织与事务内外边界。

这是当前最稳的方案，因为：

1. 不改 DDD 真相边界；
2. 风险可控；
3. 能直接改善单机多房间并发体验；
4. 不会为了“像大厂”而平白增加运行时复杂度。

### 7.2 事务内只保留四类动作

事务内原则上只保留：

1. 校验所需的最小权威上下文；
2. 获取并推进房间下一条 `event_position`；
3. 写入 `room_events`；
4. 写入 `messages` 并推进房间最新事件位置。

任何不属于这四类的动作，都默认优先考虑外移。

### 7.3 事务外优先做的事

事务外可以且应该优先承接：

1. 输入解码与 payload 基础校验；
2. 结果序列化/JSON 组装；
3. 提交后的广播；
4. 提交后的日志增强；
5. 可选的诊断观测与统计。

### 7.4 广播路径必须统一

本次不允许出现两条“消息出来了”的路径：

1. 一条是权威 `room_event`
2. 一条是给发送者的本地特判结果

设计要求：

1. 发送者与房间其他在线成员都消费同一条权威事件；
2. 广播使用当前稳定的房间 fanout 语义；
3. 如果广播失败，记录错误，但不能回滚“消息已成立”。

### 7.5 广播失败的语义

广播失败时，必须继续满足：

1. 事务已提交，消息仍然成立；
2. 失败只代表“这次 realtime fanout 失败”；
3. 客户端后续仍可用 `events/snapshot` 补齐；
4. 不允许因为广播失败把结果回译成“消息未创建”。

### 7.6 前端回流体感的设计要求

这次虽然不主攻前端，但后端必须满足一个体感约束：

1. 发送者自己看见消息，必须尽快发生；
2. 但仍然必须等权威事件回流；
3. 不允许靠更重的前端 pending 假装“秒到”来掩盖后端慢路径。

## 8. 具体代码边界建议

### 8.1 `src/外壳.rs`

本次只允许收口：

1. handler 到用例调用之间的热路径组织；
2. 提交成功后的广播和控制面回包次序；
3. 日志字段保持清楚，但不把日志本身塞进事务核心路径。

不允许在这里：

1. 偷做成员资格真相；
2. 偷做房间存在性裁决；
3. 用 `socket` 房间态替代业务真相。

### 8.2 `src/适配.rs`

本次很可能是主战场。

重点收：

1. 查询合并与冷热点拆分；
2. 事务边界重排；
3. 持锁窗口压缩；
4. 提交后最短回流路径所需的最小返回数据。

### 8.3 `src/用例.rs`

这里只允许在必要时做：

1. 热路径编排更清楚；
2. 错误语义更稳定；
3. 把本该在应用层的判断继续留在应用层。

不允许：

1. 为了省 adapter 查询，就把数据库细节倒灌进用例；
2. 为了快，把真相判断偷下沉。

## 9. 测试设计

### 9.1 用例与持久化层测试

必须补或强化：

1. 同一房间并发发送时，`event_position` 仍然严格连续；
2. 事务失败不会导致 `room_events / messages / rooms.latest_event_position` 裂开；
3. 不同房间并发发送时，事件锚点互不污染；
4. 广播失败不影响消息成立。

### 9.2 async 热路径测试

必须证明：

1. 优化后没有把额外慢步骤重新塞回事务内；
2. 没有因为 spawn/await 重排而破坏房间内顺序；
3. 热房间发送不至于让普通房间一起异常抖动。

### 9.3 realtime 真实链路测试

必须补或强化：

1. 发送者 A 发消息后，A 自己尽快收到同一条权威 `room_event`；
2. 房间其他在线用户收到同一条权威事件；
3. B 房间高频发消息时，不会把 A 房间正常消息链整体拖坏；
4. 广播失败时，客户端后续仍能通过增量/快照补齐。

### 9.4 性能验证口径

本次不做“证明万人可扛”的终极压测，但至少要有：

1. 单机内多房间并发发送的基础压测或基准；
2. 热房间与普通房间并发下的延迟对比；
3. 优化前后相同条件下的对照结果。

这不是为了营销，而是为了防止“看起来更优雅，实际没变快”。

## 10. 验收标准

这次专项完成后，必须满足：

1. 不改变领域真相与共享契约；
2. 同房消息顺序仍然绝对正确；
3. 多房间并发下互相拖累比现在更轻；
4. 发送者看到自己的权威消息回流更快；
5. 广播失败不会破坏消息成立语义；
6. 断线与补洞主链保持完整；
7. 测试能直接证明“热路径变薄了”，而不是只证明“功能还活着”。

一句话总结：

**这次专项成功，不是因为代码看起来更 async，而是因为事务更短、回流更快、同房仍真、跨房更稳。**

## 11. 风险与防漂移提醒

### 11.1 最常见的漂移风险

1. 为了快，把消息成立语义提前到广播或 ack；
2. 为了少查表，把真相判断偷塞进 realtime adapter；
3. 为了“像专业 IM”，过早引入 actor/queue 平台；
4. 为了让发送者更快看到消息，重做一条前端本地成立链；
5. 为了让测试更容易过，把热路径问题藏进更松的断言。

### 11.2 本 spec 对执行阶段的硬约束

1. 任何“优化”都必须明确指出：
   - 压掉了哪一步等待
   - 没改坏哪条真相链
   - 哪个测试能直接证明这点
2. 任何想新增并发机制、内存队列、第二广播路径的提议，都应先视为越界，除非另起 spec。
3. 如果实现时发现“必须改 contract / domain 才能继续”，应立即停下并回到设计阶段，不得硬做。
