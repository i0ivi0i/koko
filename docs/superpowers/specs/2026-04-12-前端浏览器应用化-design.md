## 0. 为什么现在必须补这份 spec

最近这轮群聊压测已经把问题说透了：

1. 只是在时间线里收图、收视频、划消息，浏览器就会卡顿、假死甚至崩溃。
2. 不是只有正式查看器，连时间线自动播、缩略图、滚动测量、P2P 冷启动都会互相抢资源。
3. 旧问题反复出现，不是因为某个 `if` 写错了，而是因为前端底层心智还残留着“网页脚本思维”。

所谓“网页脚本思维”，在这个项目里的表现很具体：

1. 把浏览器事件直接当成业务真相。
2. 把页面组件各自的局部状态拼起来，当成应用真相。
3. 把 Service Worker、缓存、WebSocket、WebTorrent、DOM 可见性都当成“当前页面的小功能”，不是应用运行时的一部分。
4. 把“页面还没销毁”误判成“应用仍然稳定运行”。

这套思维在内容站点、管理后台、小列表页面还能勉强凑合；  
但在公网万人实时群聊里，它天然会长出四类故障：

1. 生命周期错判：前后台切换、冻结、恢复、bfcache、缓存更新、存储驱逐都没有正式协议。
2. 资源预算失控：解码器、媒体元素、P2P swarm、HTTP range、DOM 节点、同步量测都一起膨胀。
3. owner 漂移：房间、滚动、媒体、实时链路、离线缓存都可能同时宣布“我是当前真相”。
4. 恢复语义缺失：断线、隐藏、返回、更新、Safari 存储清理之后，系统只能“猜自己还活着”。

这份 spec 就是为了解决这个上位问题。  
它不是一份“前端优化建议”，而是一份**应用运行时主权裁决**。

## 1. 这次复盘得到的根因

### 1.1 直接根因已经在 4 月 17 日性能止血里暴露

最近已经确认的直接根因包括：

1. 时间线 `inline_autoplay` 会为冷视频直接冷启动 whole-file WebTorrent。
2. 最后一个 consumer 释放后，未补齐 swarm 仍继续留在 runtime。
3. 时间线滚动会反复量测整列视频元素，制造主线程布局风暴。

这些都已经修过一轮，但它们其实只是症状层。

### 1.2 更深一层的根因，是前端还没有被当作“应用运行时”

如果前端真按应用运行时来设计，上面那三种问题不会轻易长出来，因为：

1. 时间线不会偷偷拥有查看器级播放权。
2. 冷资源不会因为“划过视口”就被升级成长期重型会话。
3. 浏览器可见性和房间视口会有明确 owner，不会各层都试图解释 `scroll` 与 `visibility`。
4. 媒体、缓存、P2P、SW 都会有预算，不会被局部组件各自拉满。

所以这次要写死的判断是：

**`koko` 的 Web 前端必须从“网页上的若干组件”进化成“浏览器中的应用运行时”，页面只是壳，AppRuntime 才是 owner。**

## 2. 官方资料共同指向什么

### 2.1 Chrome / web.dev 的共同指向：Web App，不是大网页

Chrome 与 web.dev 的口径已经非常一致：

1. PWA 是“用 Web 技术构建的现代高质量应用”。
2. `hidden` 往往是最后一个可靠的生命周期信号，应尽早保存状态、停止无意义工作。
3. Service Worker 更新、缓存、接管时机都必须显式治理，不能指望浏览器替你兜底。
4. 同源范围决定了应用边界；跨多个子域时，存储、SW、manifest 都会被分裂。
5. 多视频页面必须控制 `preload`、poster、懒加载和自动播数量。
6. 静音自动播是可靠路径，有声自动播必须克制。

Chrome 的官方语境，本质上是把浏览器当操作系统，把页面当应用窗口。

### 2.2 WebKit / Safari 的共同指向：缓存和后台能力都是“可被收回的加速层”

WebKit 官方反复强调：

1. Service Worker 是独立生命周期与独立进程，按需启动、无 client 会终止。
2. 存储默认是 best-effort，不保证永久存在。
3. `StorageManager.persist()` 只是申请，不是永远批准。
4. Home Screen Web App 更接近正式应用，但仍必须做 feature detection，而不是 browser sniffing。

这意味着：

1. Safari 不是“不支持应用化”，恰恰相反，它要求你更克制、更真实地面对应用生命周期。
2. SW、Cache、IDB、Blob、媒体段文件都不能被当成业务权威真相。

### 2.3 WebTorrent / WebRTC / p2p-media-loader / Video.js 的共同指向：轮子有分工，不能再混

官方边界已经很清楚：

1. `WebTorrent` 是浏览器里的 whole-file 协作分发层，依赖 WebRTC，适合正式协作分发和已热复用，不适合时间线里到处冷启动。
2. `WebRTC` 是 transport，不是产品语义，不回答资产生命周期和播放主链。
3. `p2p-media-loader` 是 `Hls.js/Shaka` 的分段增强层，不是第二播放真相 owner。
4. `Video.js v10` 当前仍是播放器壳路线，不替你决定 SW、缓存、P2P、业务真相。
5. Apple HLS / DASH-IF / CMAF 都指向标准分段流媒体主链，而不是“把整块大 MP4 当所有场景的统一表面”。

这组资料合起来给出的工程结论只有一个：

**轮子要复用，但 owner 必须自己收口。**

## 3. 上位裁决

### 3.1 一句话版

**把浏览器当运行时，不当真相；把页面当壳，不当大脑；把 AppRuntime 当 Web 应用唯一裁决入口。**

### 3.2 本项目以后必须遵守的六条硬规则

1. 浏览器事件只作信号，不能直接宣布业务或运行时真相。
2. 前端页面组件不得再各自持有房间、滚动、媒体、实时、缓存的最终裁决权。
3. Service Worker、Cache Storage、IndexedDB、OPFS、WebTorrent store 都是加速层，不是权威真相层。
4. 时间线轻量预览、正式查看器、P2P 分发、标准流媒体必须继续分层，不得再混成一条“万能播放链”。
5. 所有高频路径都要有预算：DOM、视频实例、解码器、HTTP 请求、P2P swarm、同步量测、后台任务。
6. 前后台切换、冻结恢复、断线重连、版本更新、缓存驱逐必须有正式恢复协议，不能靠“刚好没坏”。

## 4. 设计四问

### 4.1 权威真相在哪里决定

必须分两层看：

1. 业务真相仍在后端 `domain / application / contract`。
2. 浏览器运行时真相必须在前端 `AppRuntime` 内决定。

前端允许拥有的真相，只有这些：

1. 当前哪个房间视图处于活跃态。
2. 当前时间线窗口、贴底、未读锚点、分页门禁。
3. 当前媒体是时间线预览、自动播，还是正式查看器。
4. 当前 realtime 会话是否连接、补洞、降载、重连中。
5. 当前浏览器生命周期是前台、隐藏、冻结、恢复还是待刷新。

任何 DOM 事件、播放器回调、socket 回调、SW 事件都不能绕过 AppRuntime 直接改这些真相。

### 4.2 稳定交换契约是什么

必须区分三层契约：

1. 后端契约：`command / query / event / snapshot / error code`
2. 前端应用契约：`AppEvent / AppCommand / ActorSnapshot`
3. 浏览器输入信号：`visibilitychange / pagehide / pageshow / freeze / resume / online / offline / click / scroll / intersection / fullscreenchange / controllerchange`

硬约束：

1. 浏览器输入信号必须先翻译成应用事件。
2. 壳层只消费 actor 快照，不偷看其他模块私有状态。
3. 共享 `contract` 不能带壳层页面流程语义。

### 4.3 同步锚点 / 顺序依据是什么

这个项目以后要同时有三类锚点：

1. 业务锚点：服务端 `event_position`、消息 id、权限与成员事实。
2. 应用锚点：actor 内部状态转移顺序、取消与恢复门禁。
3. 视图锚点：虚拟列表窗口、读锚点、活跃媒体 owner。

必须明确：

1. socket 到达顺序不是最终业务顺序。
2. DOM 顺序不是时间线真相。
3. `scrollTop`、可见元素、全屏事件只是输入，不是状态锚点。

### 4.4 重试 / 重连 / 重入后怎么恢复

恢复必须按 owner 来做，不准靠全局共享状态对象硬拼。

至少要有这些恢复语义：

1. `hidden -> visible`：恢复壳层与前台体验，但不直接宣布业务补齐完成。
2. `pagehide -> pageshow` / bfcache：realtime 会话要么安全恢复，要么显式重建。
3. `controllerchange` / SW 更新：进入待刷新或平滑切换协议，不得继续混跑旧新壳。
4. 存储被驱逐：降级为“本地加速层丢失”，重新拉取权威事实，不得把本地缓存空洞误判成业务缺失。
5. P2P swarm 中断：回到标准流媒体或锚点源，不得继续保留悬空重会话。

## 5. 应用运行时总设计

### 5.1 总体结构

```text
浏览器事件 / SW 事件 / 播放器事件 / socket 事件
  -> adapter 翻译成 AppEvent
  -> AppRuntime
  -> 专属 actor owner
  -> shell 只读快照并渲染
```

### 5.2 AppRuntime 的职责

`AppRuntime` 不是第二业务内核，也不是新的“大总管屎山”。  
它只做四件事：

1. 接住浏览器输入并翻译成应用事件。
2. 把事件分发给唯一 owner actor。
3. 组合 actor 快照给壳层使用。
4. 统一生命周期、恢复、预算与观测。

它不负责：

1. 直接裁决后端业务权限真相。
2. 直接操作具体 DOM 细节。
3. 自己吞掉播放器、SW、WebTorrent、socket 的细节实现。

### 5.3 必须具备的 actor owner

#### 1. `AppLifecycleActor`

职责：

1. 吃 `visibilitychange / pagehide / pageshow / freeze / resume / online / offline / controllerchange`
2. 决定前后台切换、待刷新、降载、恢复的应用协议
3. 统一给其他 actor 发出 `应用隐藏`、`应用恢复`、`准备刷新`、`连接降载` 等命令

禁止：

1. 页面层自己解释 `hidden` 就继续拉重媒体
2. 用 `beforeunload` 当统一退出钩子

#### 2. `RealtimeSessionActor`

职责：

1. 持有 socket 生命周期
2. 明确连接、重连、补洞、背压、降载状态
3. 把输入事件转为稳定的时间线增量，不直接改 UI

禁止：

1. socket 回调直接 patch 视图
2. “连着”就等于“状态可靠”

#### 3. `RoomTimelineActor`

职责：

1. 收口快照、实时事件、历史分页结果
2. 负责排序、去重、窗口事实
3. 给壳层提供稳定消息窗口

禁止：

1. DOM 顺序反推业务顺序
2. 让时间线自己长出查看器级媒体逻辑

#### 4. `RoomViewportActor`

职责：

1. 统一滚动意图、程序性滚动、未读定位、历史触顶、贴底跟随
2. 与虚拟列表协作，而不是被 DOM 反向控制

禁止：

1. `scrollTop === 0` 直接等于要翻历史
2. 媒体覆盖层尾波把时间线误判为用户滚动

#### 5. `MediaRuntimeActor`

职责：

1. 区分时间线静态预览、单实例自动播、正式查看器
2. 决定当前唯一媒体 owner
3. 统一预算：同屏真实 `<video>` 数量、自动播数量、活跃 swarm 数量、冷启动上限

禁止：

1. 时间线卡片偷偷拥有正式播放裁决权
2. 自动播为冷视频直接冷启动重链路
3. 查看器、时间线、P2P 各自并行起一套链

#### 6. `AssetDistributionActor`

职责：

1. 持有 WebTorrent 运行时与复用会话
2. 明确何时允许热复用、补齐、做种、释放
3. 管理 HLS/CMAF 与 WebTorrent 的切换策略

禁止：

1. 冷视频路过视口就 whole-file 冷启动
2. 最后一个 consumer 释放后仍保留无意义冷 swarm

#### 7. `CacheAndStorageActor`

职责：

1. 统一 SW、Cache Storage、IndexedDB、OPFS、persistent storage 请求
2. 管理缓存版本、清理、驱逐后的恢复
3. 对壳层暴露“缓存可用性”，不是暴露私有存储细节

禁止：

1. 把本地存储当业务真相
2. 让旧 app shell 悄悄继续长期混跑

#### 8. `MultiContextActor`

职责：

1. 处理多标签 / 多窗口协作
2. 基于 `BroadcastChannel` 进行未读、活跃房间、提示去重等协作

禁止：

1. 每个标签页各猜各的已读和提示状态

## 6. 预算制度

浏览器中的应用，不只是“有 actor”，还必须有预算。

### 6.1 必须长期可观测的预算项

1. 当前 DOM 消息节点数与 overscan 数
2. 当前真实活跃 `<video>` 数
3. 当前自动播 owner 数
4. 当前活跃 WebTorrent session / swarm 数
5. 当前 inflight `/locator`、range、manifest 请求数
6. 主线程长任务数量与同步量测频率
7. 应用处于 `hidden` 后仍继续执行的重型工作数

### 6.2 硬约束

1. 时间线默认态必须偏静态，优先 poster / thumbnail。
2. 自动播必须是单 owner、静音、轻量、可快速释放。
3. 正式查看器才允许进入重型播放与补齐逻辑。
4. `hidden` 后必须主动降载：停止非必要自动播、释放无 consumer 的冷 swarm、减少高频观测。
5. 浏览器预算不够时，必须优雅回落，而不是继续硬拉。

## 7. 当前阶段的实施边界

### 7.1 先做什么

按 AGENTS 当前裁决，阶段 0/1 必须保持克制：

1. 先补保护测试和 characterization tests。
2. 先建立 `AppRuntime` 薄壳，把浏览器输入改成应用事件。
3. 先把生命周期、时间线、视口、媒体 owner 收口。
4. 先把预算和恢复协议落清楚。

### 7.2 暂时不做什么

1. 这份 spec 不要求立刻换掉现有唯一播放器壳。
2. 这份 spec 不要求本轮重写后端契约。
3. 这份 spec 不允许为了“更应用”就顺手再造一层私有播放器、私有虚拟列表、私有缓存框架。
4. 这份 spec 不允许“新包装加上去，旧真相继续活着”。

## 8. 分阶段路线

### 8.1 Phase 0：证据与保护测试

必须先补这类测试：

1. `hidden -> visible` 前后台切换下的房间恢复
2. `pagehide -> pageshow` / bfcache 下的 realtime 恢复
3. 时间线只在真正用户意图下触发历史分页
4. 媒体查看器打开 / 关闭不会误伤时间线
5. 单实例自动播不会冷启动 whole-file swarm
6. SW 更新或旧壳缓存不会让旧 bundle 长期混跑

### 8.2 Phase 1：AppRuntime 薄壳

目标：

1. 保留现有 UI 与轮子
2. 把浏览器事件统一翻译成应用事件
3. 让壳层不再直接解释滚动、媒体、生命周期真相

验收：

1. 旧测试不回归
2. 新测试能证明浏览器输入先过 AppRuntime
3. `聊天壳.ts` 明显变薄

### 8.3 Phase 2：owner 收口

目标：

1. 把 `RoomTimelineActor / RoomViewportActor / MediaRuntimeActor / RealtimeSessionActor` 建起来
2. 删掉旧的平行 owner

验收：

1. 时间线、滚动、媒体、realtime 各只有一个裁决 owner
2. 旧入口要么删，要么只保留翻译职责

### 8.4 Phase 3：预算化升级

目标：

1. 在有保护测试的前提下接虚拟列表
2. 系统化管理媒体与 P2P 预算
3. 让 `hidden` / `visible` 进入正式降载恢复协议

验收：

1. 大房间 DOM 数量受控
2. 重媒体滚动时不再出现多 owner 重链路风暴

### 8.5 Phase 4：缓存与多上下文应用能力

目标：

1. Workbox / SW 更新策略 / 壳缓存 / 多标签协作收口
2. Badge、Push、后台补发这类能力挂到应用协议上

验收：

1. 旧壳更新可控
2. 多标签未读 / 活跃态 / 提醒不再互相打架

## 9. 验收标准

### 9.1 架构验收

1. 浏览器事件不再直接裁决房间、滚动、媒体、realtime 真相。
2. `AppRuntime` 成为唯一前端运行时组合根。
3. 时间线轻预览、正式查看器、P2P 分发、缓存恢复的 owner 清楚且不重复。
4. 新层必须压缩旧层；加一层但不退旧层，视为失败。

### 9.2 性能验收

1. 多媒体时间线滚动时，没有整列同步量测风暴。
2. 时间线默认态不再对冷视频批量冷启动 whole-file P2P。
3. 进入 `hidden` 后，重型媒体与 P2P 工作能被及时释放或降载。
4. 恢复到 `visible` 后，应用能按协议恢复，不靠定时器运气。

### 9.3 恢复验收

1. 切后台、锁屏、切标签、返回、bfcache、SW 更新后，应用状态仍自洽。
2. Safari 下存储被清理时，系统仍能按“加速层丢失”优雅恢复。
3. 旧 bundle / 旧壳不会长期混跑。

## 10. 明确禁止的退化

以后凡是出现下列情况，默认视为违反本 spec：

1. 浏览器事件直接在组件里宣布业务或运行时真相。
2. 时间线静态卡片、自动播、正式查看器、P2P 运行时再次各自长出第二套播放裁决。
3. 把 SW、缓存、WebTorrent store 当作权威事实。
4. 为了“应用化”额外手搓一层私有播放器、私有虚拟列表、私有缓存框架。
5. 新 owner 进来后，旧 owner 仍继续活着。

## 11. 当前结论

`koko` 出现这么多前端性能 bug，不只是实现细节粗糙，  
更根上的原因，是前端底层还残留着“浏览器里的网页”心智。

这份 spec 的裁决很明确：

1. 以后所有浏览器事件都必须先转成应用事件。
2. 以后所有前端运行时真相都必须有唯一 owner。
3. 以后页面只是壳，AppRuntime 才是浏览器中的应用。
4. 以后媒体、缓存、SW、P2P 都必须接受生命周期和预算治理。

先把这条主线写硬，后面的性能、恢复、多人群聊稳定性，才有可能真正进入正循环。
