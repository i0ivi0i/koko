## 1. 这份 spec 要解决什么问题

前端最近连续出现的问题包括：

- 点开图片、视频、附件后，聊天室滚到最早历史；
- 视频全屏、方向、返回流程不稳定；
- 图片点击行为曾退化成下载；
- 媒体查看器和聊天滚动互相影响；
- `聊天壳.ts` 越来越像“所有事情都知道一点”的中心。

这些现象不是单个 CSS 或 click handler 的问题。真正的根因是：部分代码还在把浏览器事件当成应用真相。

错误模型：

- `scrollTop === 0` 直接表示“用户要翻历史”；
- `click` 直接表示“打开媒体/下载附件”；
- `fullscreenchange / popstate` 直接影响聊天房间状态；
- DOM 列表承载消息流真相；
- `聊天壳.ts` 同时负责渲染、状态、恢复、媒体、滚动、实时编排。

目标模型：

- 浏览器只是运行时和输入源；
- 浏览器事件只是“信号”，不是“事实”；
- 应用运行时裁决用户意图、状态转换和副作用；
- Lit 组件只负责表达意图和展示状态；
- 通用能力优先复用成熟轮子，不手搓播放器、虚拟列表、缓存框架。

一句话：把前端从“浏览器里的网页”进化成“浏览器中的 IM 应用”。

## 2. 目标与非目标

### 2.1 目标

- 建立前端应用运行时地基，避免继续在 `聊天壳.ts` 里补丁式堆逻辑。
- 明确消息流、房间视口、媒体查看、实时连接、PWA 壳的唯一真相 owner。
- 用成熟轮子承接通用复杂能力：
  - `XState` 管应用级状态机/actor；
  - `Lit ReactiveController` 管壳层生命周期接入；
  - `TanStack Virtual` 管万人消息列表虚拟化；
  - `Vidstack` 管视频播放器；
  - `PhotoSwipe` 管图片查看器；
  - `Workbox` 管 App Shell 和静态资源缓存；
  - `WebTorrent` 保留为媒体源提供者。
- 用 TDD 分阶段迁移，每一阶段必须有保护性测试和回归测试。
- 让 `聊天壳.ts` 逐步变薄，只负责组合、渲染和事件转译。

### 2.2 非目标

- 不重写成 React/Vue。
- 不把全部逻辑一次性塞进 XState。
- 不自研虚拟列表、播放器、图片查看器、Service Worker 缓存框架。
- 不为了 DDD 增加装饰性的 aggregate / factory / repository / service。
- 不修改后端 Rust 契约，除非前端测试证明现有契约无法表达真实应用语义。
- 不做一次性大扫荡式重构；必须按可验证切片演进。

## 3. 设计原则

### 3.1 DDD：真相只在一个 owner 决定

- 消息是否存在、顺序如何：由 `RoomTimelineActor` 决定。
- 当前视口是否允许加载历史：由 `RoomViewportActor` 决定。
- 当前是否处于媒体查看模式：由 `MediaViewerActor` 决定。
- 实时连接是否需要补事件：由 `RealtimeActor` 决定。
- 应用壳是否处于弱网、待更新、恢复中：由 `AppShellActor` 决定。

shell / adapter 只能翻译和展示，不能偷判业务真相。

### 3.2 Unix：小而专，可组合，可替换

每个 actor/controller 只做一类事情。一个模块如果只是把参数转发给另一个模块，没有压缩复杂度，就不该存在。

新增抽象必须满足至少一个条件：

- 删除旧分支；
- 压缩旧调用链；
- 固化唯一真相 owner；
- 提供真实测试缝；
- 替换手搓通用能力为成熟轮子。

### 3.3 浏览器事件不是应用事实

`scroll`、`click`、`fullscreenchange`、`popstate`、`visibilitychange` 都只是外部信号。

它们必须先被翻译成应用事件：

- `ROOM_SCROLL_INTENT`
- `ROOM_SCROLL_OBSERVED`
- `MEDIA_OPEN_REQUESTED`
- `MEDIA_VIEWER_CLOSED`
- `REALTIME_EVENT_RECEIVED`
- `APP_VISIBILITY_CHANGED`

再由应用运行时裁决是否改变状态。

## 4. 应用运行时结构

新增概念：`AppRuntime`。它不是新框架，不直接操作 DOM，也不是“大总管”。它只是组合根，负责把稳定 actor 接起来。

数据流：

```text
浏览器事件
  -> Lit 外壳
  -> AppRuntime
  -> XState actors / controller
  -> view model
  -> Lit 渲染
```

建议第一阶段文件边界：

- `frontend/应用运行时.ts`
  - 组合 `RoomViewportActor`、后续 `RoomTimelineActor`、`MediaViewerActor`、`RealtimeActor`。
  - 向 `聊天壳.ts` 暴露少量应用事件入口。
- `frontend/房间滚动器.ts`
  - 短期保留，作为 `RoomViewportActor` 的现有行为承载点。
  - 不再继续扩成所有视口逻辑的大脑。
- `frontend/聊天壳.ts`
  - 只做渲染、composition root、事件转译。
  - 逐步删除直接裁决滚动/媒体/实时真相的分支。
- `frontend/媒体/媒体查看器.ts`
  - 短期保留适配 GLightbox/原生全屏。
  - 后续由 `MediaViewerActor` 接管状态后，再替换为 Vidstack/PhotoSwipe。

## 5. 组件职责

### 5.1 AppRuntime

职责：

- 接收壳层应用事件；
- 把事件分发给对应 actor/controller；
- 对外暴露渲染所需的 view model；
- 统一管理 actor 生命周期。

禁止：

- 直接操作 DOM；
- 直接调用播放器/虚拟列表底层 API；
- 直接拼后端契约字段。

### 5.2 RoomViewportActor

职责：

- 裁决一次滚动是否来自用户真实阅读；
- 裁决是否允许加载更早历史；
- 维护贴底跟随、离底浏览、未读定位、程序性滚动尾波；
- 后续接入 TanStack Virtual 的 range/anchor 语义。

稳定输入：

- 用户滚动意图；
- 实际滚动观测；
- 历史页前插完成；
- 媒体查看器开始/结束占用视口；
- 虚拟列表 range 变化。

稳定输出：

- `shouldLoadOlderHistory`;
- `shouldTrackReadAnchor`;
- `viewportMode`;
- `pendingReadAnchorPosition`;
- `programmaticScrollSuppressed`。

### 5.3 RoomTimelineActor

职责：

- 合并快照、历史页、实时增量、重连补事件；
- 按 `event_position` 排序；
- 幂等去重；
- 输出消息窗口和附件索引。

同步锚点：

- 后端 `event_position` 是消息流顺序真相；
- `message_id / client_message_id` 用于去重辅助；
- DOM 顺序不能成为消息流真相。

### 5.4 MediaViewerActor

职责：

- 管理图片/视频查看模式；
- 管理手机返回键、浏览器 history、全屏、方向；
- 通知 `RoomViewportActor` 媒体查看器占用/释放视口；
- 从媒体源适配层拿 WebTorrent/blob/original URL。

轮子边界：

- 图片查看：PhotoSwipe；
- 视频播放：Vidstack；
- WebTorrent：只负责媒体源，不负责播放器 UI 真相。

### 5.5 RealtimeActor

职责：

- socket 连接、断开、重连；
- 订阅/退订房间；
- 根据最后 event position 补事件；
- 把合法事件交给 `RoomTimelineActor`。

禁止：

- socket 回调直接改 DOM；
- socket 回调直接拼消息列表；
- 重连后重复事件进入 timeline。

### 5.6 AppShellActor

职责：

- Service Worker / Workbox 状态；
- 静态壳缓存；
- 应用更新提示；
- 弱网/离线提示；
- 页面可见性变化。

缓存边界：

- App Shell 可以缓存；
- dist 静态资源可以预缓存；
- 实时聊天消息不能被静态缓存当作业务真相。

## 6. 迁移方案

### 阶段 0：保护性测试

先补 characterization tests，确认当前关键行为不被打坏：

- 入房快照恢复；
- 用户滚到顶部才加载历史；
- 媒体打开/关闭不触发历史；
- 贴底时新消息跟随；
- 离底时新消息不抢视口；
- 重连补事件不重复。

### 阶段 1：建立 AppRuntime 薄壳

目标：建立应用事件入口，不改变 UI。

验收：

- `聊天壳.ts` 的滚动、媒体入口通过 AppRuntime 转发；
- 原测试全过；
- 新增测试证明浏览器事件不会直接触发业务副作用，必须经过应用事件入口。

### 阶段 2：RoomViewportActor 收口

目标：把房间视口真相从壳层彻底收口。

验收：

- 历史分页只能由 `RoomViewportActor` 裁决；
- 媒体查看器尾波不能触发历史分页；
- 用户真实新滚动仍能触发历史分页；
- `聊天壳.ts` 不再直接判断 `scrollTop === 0` 的业务含义。

### 阶段 3：TanStack Virtual 接入

目标：万人消息列表不再依赖全量 DOM。

验收：

- 大量消息时 DOM 数量受控；
- 未读定位、历史前插、贴底跟随仍正确；
- virtual range 只是显示窗口，不是消息真相。

### 阶段 4：MediaViewerActor + 成熟媒体轮子

目标：媒体查看从页面弹层变成应用模式。

验收：

- 图片点击进入 PhotoSwipe 高清原图查看；
- 视频点击进入 Vidstack 播放；
- 手机返回键退出媒体查看，不退出房间；
- 竖屏视频按自身方向展示；
- WebTorrent 源优先，原始 URL 兜底。

### 阶段 5：RoomTimelineActor / RealtimeActor

目标：消息流和实时同步从 shell 中退出。

验收：

- snapshot/history/realtime/reconnect 都通过 timeline actor 合并；
- event position 是唯一顺序锚点；
- socket 回调不直接改 UI 真相；
- 重连补事件幂等。

### 阶段 6：Workbox App Shell

目标：浏览器应用壳稳定加载。

验收：

- dist 静态资源由 Workbox 预缓存；
- App Shell 可快速恢复；
- 实时消息不被错误缓存；
- 应用更新有明确提示策略。

## 7. TDD 与验证门槛

每个阶段必须按 TDD 执行：

1. 先写失败测试或 characterization test；
2. 看测试按预期失败；
3. 写最小实现；
4. 跑目标测试；
5. 跑 `pnpm --dir frontend test`；
6. 跑 `pnpm --dir frontend typecheck`；
7. 跑 `pnpm --dir frontend build`；
8. 如果改代码，跑 graphify 重建；
9. `git diff --check`；
10. 单独提交。

任何阶段如果只新增包装层，没有删除或压缩旧逻辑，视为失败。

## 8. 风险与约束

- 风险：XState 过度使用会变成状态机仪式。
  - 约束：只给跨事件、跨生命周期、跨恢复路径的状态用 actor；简单纯函数继续用纯函数。
- 风险：新增 runtime 后旧逻辑还活着，形成双真相。
  - 约束：每一阶段必须列出被 runtime 取代的旧入口和删除/收缩点。
- 风险：虚拟列表破坏未读定位和历史前插。
  - 约束：先做等价测试，再接 TanStack Virtual。
- 风险：媒体轮子替换破坏 WebTorrent 边下边播优势。
  - 约束：WebTorrent 作为媒体源 provider 保留，播放器只消费源。
- 风险：Workbox 错缓存实时数据。
  - 约束：只预缓存 app shell 和静态资源；聊天数据走实时链路和显式请求。

## 9. 第一阶段施工边界

第一阶段只做 `AppRuntime` 薄壳，不接虚拟列表、不换播放器、不改后端契约。

第一阶段完成后应该看到：

- 新增应用事件入口；
- `聊天壳.ts` 少一部分直接业务裁决；
- 滚动/媒体入口能通过 runtime 分派；
- 所有现有用户体验不变化；
- 有测试证明“浏览器事件不能绕过 runtime 直接触发核心副作用”。
