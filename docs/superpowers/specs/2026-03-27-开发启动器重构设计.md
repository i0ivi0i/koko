# 开发启动器重构设计

## 目标

把当前基于 `run.ps1` 的开发启动方式，重构为更符合 Rust 生态的 `just + xtask` 方案。

目标是：

- Win11 上一条命令启动开发环境
- 不再把 PowerShell 当核心编排器
- 不再混淆初始化和日常启动
- 不再把普通 Cargo 输出误标成错误
- 后续 Linux 开发与 CI 也能复用同一套入口

## 当前问题

当前方案虽然已经能启动，但根问题仍在：

- `run.ps1` 既负责初始化，又负责日常开发启动，职责过重
- 用 PowerShell 包裹 `cargo watch` 与 `dx serve`，再二次聚合日志，日志语义脏
- 普通的 Cargo `stderr` 被显示成错误
- 子进程和窗口行为受 PowerShell 控制，Windows 体验不稳定
- 入口逻辑散在脚本里，不符合 Cargo-first 的 Rust 习惯

## 方案对比

### 方案 1：继续优化 `run.ps1`

优点：

- 改动最少

缺点：

- 根问题不变
- 仍以 PowerShell 为核心
- 长期会继续积累启动与日志问题

不采用。

### 方案 2：Python 启动器

优点：

- 进程与日志控制能力强

缺点：

- 多引入一套 Python 运行时
- 工具链不再纯 Rust
- 增加环境与维护负担

不采用。

### 方案 3：`just + xtask`

优点：

- 对外入口简洁：`just dev`
- 对内编排用 Rust 实现，工具链统一
- 更符合 Rust 社区常见做法
- 跨 Win/Linux 一致性更好
- 后续能自然扩展到部署、检查、升级命令

采用。

## 最终设计

### 对外入口

新增：

- `justfile`
- `xtask/`

保留：

- `.env.local`
- `web/`
- `server/`
- `core/`
- `migrations/`

删除：

- `run.ps1`

原因：

- `just` 已经承担了“项目入口命令”的职责
- 继续保留 `run.ps1` 只会形成冗余入口

### 命令模型

对外暴露：

- `just init`
- `just dev`
- `just migrate`
- `just test`
- `just check`

内部映射：

- `just init` -> `cargo run -p xtask -- init`
- `just dev` -> `cargo run -p xtask -- dev`
- `just migrate` -> `cargo run -p xtask -- migrate`
- `just test` -> `cargo run -p xtask -- test`
- `just check` -> `cargo run -p xtask -- check`

### 配置模型

开发环境只认：

- `.env.local`

其中至少包含：

- `DATABASE_URL`
- `KOKO_API_BASE`

规则：

- `xtask` 读取 `.env.local`
- `server` 和 `web` 只接收环境变量，不自行读文件
- 生产环境只使用系统环境变量

### 日志与进程模型

`xtask dev` 直接用 Rust `Command` 启动：

- 后端开发进程
- 前端开发进程

并在主进程里：

- 读取 stdout/stderr
- 统一打前缀
- 尽量按内容区分普通信息、warning、error
- `Ctrl+C` 时统一终止子进程

关键原则：

- 不再用 PowerShell 子进程做控制台编排
- 不再靠 stdout/stderr 粗暴判断错误

### 初始化与启动分离

- `init`
  负责工具检查、数据库创建、迁移
- `dev`
  只负责开发启动
- `migrate`
  只负责迁移

这样日常开发不会每次重复初始化。

## 文件结构

新增：

- `justfile`
- `xtask/Cargo.toml`
- `xtask/src/main.rs`
- `xtask/src/env.rs`
- `xtask/src/process.rs`
- `xtask/src/logging.rs`

修改：

- 根目录 `Cargo.toml`
- `docs/Win11本地开发启动说明.md`
- `docs/superpowers/specs/2026-03-26-纯Rust群聊项目架构设计.md`

删除：

- `run.ps1`

## 风险控制

- 不在这次重构里顺手改业务逻辑
- 不把 `xtask` 做成臃肿框架，只实现当前需要的 5 个命令
- 日志处理先做到“干净可读”，不追求复杂终端 UI
- 若 `just` 未安装，文档中明确安装方式，但不为此保留第二套入口

## 结论

这次重构要解决的不是“脚本写法不好”，而是“启动器站错层”。

最终结果应为：

- 人类入口：`just`
- 编排核心：`xtask`
- 配置来源：`.env.local`
- 服务进程：`server` / `web`

这样才符合你当前项目的几个核心要求：

- 纯 Rust
- 少冗余
- 快速开发
- Windows 体验顺手
- 后续 Linux 也能延续
