## 0. 为什么必须重写这份总 spec

这份总 spec 之所以必须重写，不是因为旧文档没有价值，而是因为它已经完成了它当时的职责。

旧版总纲的职责，是：

1. 把原本容易失控的去屎山工作先按阶段拆开；
2. 防止阶段一执行时顺手把媒体链、共享热点、浏览器应用化热点混成一锅；
3. 防止还没收清聊天主链时就一把梭大重构；
4. 防止只有阶段一 child spec，没有总路线入口。

这些事它已经完成了。
但现在真正要解决的问题，已经不再是“阶段应该怎么拆”，而是下面这组更直接、更危险的问题：

1. 现在这个万人实时群聊项目的核心到底还在不在；
2. 现在这个项目到底有没有长出手搓轮子、重复造轮子和私有胶水屎山；
3. 哪些东西必须继续保留，哪些东西必须删除、合并、收口或退场；
4. 后续怎样一口气把剩余屎山收到底，而不是继续在阶段叙事里绕来绕去；
5. 以后怎样防止维护、运维、兼容修复和应急补丁再次把系统慢慢养回屎山。

所以这里必须先把一句话写死：

**以后在 `koko` 里，这份总 spec 不再用于解释“后续分成几阶段”，而用于解释“当前真相是什么、什么算屎山、什么必须保留、什么必须退场、后续怎样一次性收口到底、怎样长期防止再次漂移”。**

这句话自然带出两个硬裁决：

1. **禁止再把这份文档理解成旧意义上的阶段化路线说明书。**
2. **禁止继续把“讨论阶段数”误当成“已经解决屎山问题”。**

## 1. 当前系统真相裁决

### 1.1 聊天 realtime 核心仍然守正

先把最重要的事实写死：

1. 当前万人实时群聊项目的正式聊天 realtime 主链仍然是**后端纯 Rust `socketioxide` + 前端 `socket.io-client`**；
2. 当前没有发现第二套正式聊天 realtime 核心在暗中接管主链；
3. 当前聊天实时命脉仍然建立在既有 `socketioxide + socket.io-client` 上，而不是建立在某个私有手搓实时框架上；
4. 因此这次去屎山的第一原则，不是“推倒现有成熟核心”，而是“在继续复用成熟核心的前提下，把外围屎山收口回正确 owner”。

这里必须单独再加一条硬裁决：

**禁止把“去屎山”误解成“既然要清理，就把现有成熟聊天核心一起拆掉重来”。**

### 1.2 当前真正危险的不是核心失效，而是外围持续长胖

虽然聊天核心仍在，但这不代表系统健康。
当前真正危险的地方，不是“核心被换掉”，而是外围在长期迭代中持续长胖。

这种长胖主要表现为：

1. 成熟轮子之外又长出越来越厚的私有组合层；
2. shared transport、shared runtime、shared shell、媒体 owner 链周围出现越来越多私有胶水；
3. 一些模块开始同时拥有多条 owner 线，变成热点总控；
4. 旧路径、新包装、兼容旁路和补丁式逻辑如果不退场，就会慢慢变成第二真相；
5. 维护和运维在“先补一下”“先兼容一下”“先别删旧的”中逐步把系统养回屎山。

因此这里必须把当前状态的准确判词写死：

**当前项目应被理解为：聊天核心仍守正，但外围已经形成多处私有重复轮子、私有重复真相、私有重复胶水和热点总控。**

### 1.3 必须同时禁止两种误判

后续任何 plan、review、实现和维护，都必须同时禁止两种误判：

1. **禁止把“外围很乱”误判成“聊天核心已经失效”。**
2. **禁止把“聊天核心还在”误判成“项目没有屎山”。**

如果只犯第一种误判，就会误杀成熟轮子。
如果只犯第二种误判，就会继续纵容私有胶水变厚。

这两种都必须禁止。

## 2. 什么算核心，什么算屎山

这份文档最关键的任务之一，就是把“什么应该保留、什么应该退场”钉成统一裁决。
否则后续任何人都可以把自己的偏好包装成“架构优化”，最后继续制造漂移。

### 2.1 什么算应该保留的成熟核心

下列对象默认属于应该继续保留和复用的成熟核心能力：

1. 已经验证可用、边界清楚、仍满足当前项目需求的正式聊天 realtime 主链轮子；
2. 已经验证可用、仍满足媒体主链裁决的成熟媒体分发能力；
3. 已经验证可用、边界清楚的浏览器运行时原生能力和成熟生态；
4. 只承担薄翻译、薄接线、薄组合职责、且没有偷拿业务真相的 adapter；
5. 能明显压缩私有胶水、减少重复真相、提升边界清晰度的成熟基础设施与通用库。

这里的核心判断准绳是：

**只要某个能力已经是成熟轮子、边界清楚、当前仍适配，继续复用它不是屎山；为了“看起来更纯”去误杀它，才是屎山。**

### 2.2 什么算必须清理的屎山

下列对象默认属于屎山组成部分，必须被删除、合并、收口或退场：

1. 在成熟轮子之外又长出的私有重复轮子；
2. 在正式真相之外又长出的私有重复真相；
3. 只是在成熟能力外再套一层、再搬一层、再转一层，但没有带来真实边界价值的私有胶水；
4. 同时承载多条 owner 线、并且不断吸附职责的热点总控；
5. 为了“保险”保留下来的旧新双活、双路径、双恢复、双 transport、双 runtime；
6. 依赖应急补丁、运维记忆、兼容旁路才能维持正确性的长期路径；
7. 未来维护稍微顺手就会继续往里塞逻辑的超大组合根和超大编排中心。

这里也必须把一句话写死：

**本项目真正要清理的屎山，不是成熟核心轮子，而是成熟核心轮子外层长出来的私有重复轮子、私有重复真相、私有重复胶水和热点总控。**

### 2.3 哪些行为一旦出现，就视为继续造屎山

下列行为一旦出现，哪怕短期能跑，也必须直接视为继续造屎山：

1. 在正式聊天主链之外再长第二套聊天 realtime 主链；
2. 在正式恢复链之外再长第二套恢复真相；
3. 在 shared transport 之外再长第二套私有 transport 真相；
4. 在正式媒体主链之外再长第二套播放或分发真相；
5. 用新包装把旧路径包住，但旧路径继续活着；
6. 让某个热点总控继续同时拥有越来越多 owner；
7. 让 adapter、shell、runtime 偷拿业务判断；
8. 让 shared contract 倒灌某个壳专属语义；
9. 让前端重新养出平行业务真相；
10. 让“以后再删”“先留着旧的保险一点”变成长期现实。

因此必须再写死一句总裁决：

**只要某个改动会让系统多出第二真相、第二路径、第二 owner，或者让热点继续长胖，它就不是去屎山，而是在继续养屎山。**

这里必须直接写死一句：

**以后关于万人实时群聊去屎山的总入口，不再是“阶段数的讨论”，而是“真相裁决 + 总执行规约 + 长期防漂移约束”。**

## 4. 本次总执行范围：一次性收口到底

### 4.1 本次总执行到底要收什么

既然这次不再按多阶段叙事理解路线，那么本次总执行就必须把剩余屎山一次性收口到底。
但“一次性收口到底”并不等于“什么都顺手重写”，它仍然有严格边界。

本次总执行明确纳入：

1. 聊天主链外围仍然残留的 shared transport / shared shell / shared runtime 屎山热点；
2. 浏览器应用运行时与多壳共享协作中仍然残留的 owner 漂移；
3. 媒体查看器、自动播、定位、媒体运行时、协作分发、媒体恢复协作等媒体 owner 链上的剩余屎山热点；
4. 旧胶水、旧包装、旧重复路径、旧双活残骸的统一退场；
5. 为防止未来再次漂移而必须一并建立的长期防漂移约束。

### 4.2 本次总执行明确不收什么

本次总执行明确不纳入：

1. 推倒或替换成熟聊天核心轮子；
2. 重写聊天业务真相；
3. 重写共享 `contract` 的稳定通用表面；
4. 发明第二聊天主链、第二恢复真相、第二 transport 真相、第二媒体主链；
5. 为了“看起来更先进”而顺手更换大批无关基础设施；
6. 为了“更像 DDD”而新增大量没有边界价值的 ceremony。

这里必须把一句话写死：

**本次总执行收的是“私有重复轮子、私有重复真相、私有重复胶水和热点总控”，不是“成熟核心轮子”本身。**

### 4.3 任何越界冲动都必须禁止

后续只要出现下面这些说法，必须直接视为越界：

1. “反正都要一次性做完了，顺手把协议也统一一下。”
2. “反正都要清到底了，shared contract 也一起重写吧。”
3. “反正 transport 很乱，干脆把整个通信栈都重做掉。”
4. “反正媒体也要收，干脆把聊天主链一起换成新的更现代方案。”
5. “反正都在前端，就统一成一个大 runtime 吧。”

这些都必须禁止。
因为它们做的不是“收口到底”，而是“借一口气执行之名，继续制造新一轮体系漂移”。

## 5. DDD / Onion / Unix 在本项目里的唯一解释

这份文档必须把 DDD、Onion 和 Unix 哲学解释成项目级可执行裁决，而不是解释成好听口号。

### 5.1 DDD 在这里不代表加更多层

这次必须写死：

1. DDD 不代表到处加 `manager`、`facade`、`service`；
2. DDD 不代表把原来能直接读懂的代码改成多层空心抽象；
3. DDD 不代表靠更多目录名、更多仪式感、更多中间层来假装更高级。

DDD 在本项目里只代表一件事：

**业务真相必须收口到唯一 owner。**

自然推出：

1. 领域真相归领域 owner；
2. 用例编排归 application owner；
3. 协议翻译归 adapter；
4. 交互协调、临时体验态、本地运行时状态归 shell / runtime；
5. 谁不拥有真相，谁就禁止替真相做决定。

### 5.2 Onion 在这里不代表层数越多越好

Onion 在本项目里只允许按下面这条理解：

1. 越靠近核心，越不能直接依赖协议和框架细节；
2. 越靠近外层，越不能偷拿业务真相；
3. 分层的目的，是守依赖方向，不是制造层数；
4. 只要多一层没有带来真实边界价值，那层就不该存在。

因此必须直接禁止：

1. 禁止为了“更像洋葱”而堆更多无意义 wrapper；
2. 禁止为了“更像分层”而制造纯转发文件海；
3. 禁止让外层继续背着业务决策，只是换了个更好听的名字。

### 5.3 Unix 哲学在这里不代表越碎越高级

Unix 哲学在本项目里只允许按下面这条理解：

1. 模块必须小而专；
2. 但拆分必须带来真实边界价值；
3. 组合必须简单；
4. 不能把简单路径拆成碎片噪音。

所以这里也必须直接禁止：

1. 禁止为了显得模块化而制造碎文件海；
2. 禁止把一个清楚模块切成三层纯转发；
3. 禁止新增没有独立边界价值的 ceremony 文件。

### 5.4 成熟轮子继续复用，私有重复轮子必须退场

这里要把最重要的工程准绳再钉死一次：

1. 通用能力、基础设施、协议封装、浏览器运行时能力、成熟媒体能力，默认先复用成熟生态；
2. 只有当现成轮子确实不能满足边界、性能、维护性或契约约束时，才允许谨慎自研；
3. 只要某个私有实现存在的唯一价值，是把成熟轮子再包一层、再转一层、再搬一层，但没有带来新的边界清晰度，它就属于应该退场的对象。

因此这一章最终只认一句：

**DDD 只用来收真相，不用来制造层数；Onion 只用来守依赖方向，不用来制造 ceremony；Unix 只用来让模块小而专，不用来制造碎片；成熟轮子继续复用，私有重复轮子必须退场。**

## 6. 一口气总执行顺序

这次虽然不再按“多个阶段”叙事，但仍然必须存在唯一执行顺序。
否则“一口气做完”很容易退化成“同时乱拆、到处互伤”。

这里必须单独再写死一条，防止后面有人把“执行顺序”重新偷换成“新阶段路线”：

**下面这套顺序只是单次总执行内部的唯一施工顺序，不是重新回到新的阶段化路线，也不授权任何人再以“阶段二 / 阶段三”名义另起一套总入口。**

### 6.1 先守核心，不先误伤

任何收口开始前，都必须先守住：

1. 正式聊天 realtime 主链不被误伤；
2. 正式恢复链不被误伤；
3. 稳定共享契约不被误伤；
4. 正式媒体主链不被误伤。

这里必须直接禁止：

1. 禁止为了收外围屎山而先动成熟核心轮子；
2. 禁止为了收外围屎山而先改稳定契约；
3. 禁止为了收外围屎山而先发明第二主链。

### 6.2 先收 shared owner，再收 media owner

一口气总执行的唯一顺序，必须先收 shared owner，再收 media owner。

原因不是保守，而是为了禁止真相混写：

1. shared owner 主要服务整个应用、多壳、多链路；
2. media owner 主要服务媒体查看器、自动播、定位、协作分发、媒体恢复协作；
3. 如果 shared owner 还没收清，就直接去收 media owner，很容易把二者重新写成一锅。

所以这里必须写死：

**禁止在 shared owner 还没收清时，把 media owner 和 shared owner 重新混成一个大 runtime、一个大 transport、一个大编排中心。**

### 6.3 再收 media/browser-app owner 链

shared owner 收清后，才能继续收 media/browser-app owner 链。
但这里也必须守住下面这些边界：

1. 禁止重写正式媒体主链裁决；
2. 禁止发明第二播放真相；
3. 禁止把移动端、桌面端、不同浏览器重新拆成多套媒体真相；
4. 禁止把浏览器应用化 owner 链重新打回 DOM 事件拼贴。

### 6.4 最后删旧路径与统一验收

所有 owner 收口完成后，必须最后统一做下面这些事：

1. 删掉旧胶水；
2. 删掉旧包装；
3. 删掉旧双活；
4. 删掉旧旁路；
5. 跑统一验证；
6. 做图谱复核；
7. 只在确认旧路径真正退场后，才允许宣布完成。

因此这一章最终只认一句：

**一口气总执行不是“同时乱拆”，而是“按唯一顺序持续收口，直到旧路径退场、热点减压、真相 owner 清晰”。**

## 7. 跨总执行硬红线

无论谁来执行这次总收口，都必须同时守住下面这些红线：

1. **禁止引入新 bug。**
2. **禁止破坏现有业务功能。**
3. **禁止削弱现有满血特性。**
4. **禁止让项目变得更难长期维护。**
5. **禁止留下技术债务尾巴。**
6. **禁止只加新结构、不删旧胶水。**
7. **禁止保留旧新双活长期共存。**
8. **禁止前端长出平行业务真相。**
9. **禁止 adapter / shell / runtime 承载业务裁决。**
10. **禁止 shared contract 倒灌壳专属语义。**
11. **禁止借“保险一点”之名保留第二套真相。**
12. **禁止借“反正以后再收”之名把技术债尾巴留给未来。**

这里必须再把一句话钉死：

**只要某次收口之后项目多了新 bug、功能受损、特性削弱、冗余垃圾残留、技术债尾巴留下、维护性下降，这次收口就视为失败。**

## 8. 长期防漂移约束

这份文档不是只管“今天清一次”，还必须管“以后不要再慢慢养回来”。

### 8.1 以后维护和运维不准再把临时东西升格成长期真相

下面这些东西默认都只是临时措施：

1. 运维补丁；
2. 兼容旁路；
3. 应急兜底；
4. 临时绕路；
5. 历史遗留的双活保底逻辑。

以后必须直接禁止：

1. 禁止在没有重新收口 owner 的情况下，让这些临时措施长期活着；
2. 禁止用“现在先救火”替代“之后必须退场”；
3. 禁止让运维记忆成为系统正确性的组成部分。

### 8.2 以后任何结构改动都必须同时回答三个问题

以后任何人再碰这些链路时，必须先回答：

1. 这个改动让哪个真相 owner 更清楚了？
2. 这个改动删除了哪段旧路径？
3. 这个改动怎样让未来更不容易再长屎山？

只要这三个问题答不清，就禁止继续扩张代码。

这里还必须再补一条，因为“结构看起来更清楚”和“没有引入新 bug”不是一回事：

4. 这个改动准备用什么新鲜验证证明它**没有引入新 bug、没有破坏业务功能、没有削弱满血特性**？

这第四个问题答不清，也禁止继续扩张代码。

### 8.3 以后只接受“净减复杂度”的改动

以后结构改动即便文件数变多、目录变化，也必须同时满足：

1. 总体真相 owner 更清楚；
2. 重复路径更少；
3. 热点更薄；
4. 维护更轻；
5. 运维更不容易靠旁路维持正确性。

如果做不到这些，就禁止把它包装成“去屎山”。

### 8.4 “先留着旧的保险一点”默认视为漂移预警

以后只要出现下面这种说法，默认视为漂移预警：

1. “旧的先别删，保险一点。”
2. “新的先挂着，旧的也留着。”
3. “反正功能没坏，旧包装先不动。”
4. “这条旁路以后再说。”

除非有**明确退场计划、明确删除时机、明确验证门禁**，否则一律禁止。

因此这一章最终只认一句：

**去屎山不是一次性清扫动作，而是把未来所有维护、运维、补丁和兼容都重新关回正确 owner 的长期约束。**

## 9. 验证门禁与完成判定

### 9.1 没有新鲜验证，禁止宣布完成

以后任何“做完了”“收口了”“完成了”的说法，都必须建立在新鲜验证上。
没有新鲜验证，禁止宣布完成。

### 9.2 这次总收口只有同时满足下面这些条件才算完成

1. 聊天 realtime 成熟主链仍唯一且更清楚；
2. 没有长出第二套聊天 realtime 核心、第二套恢复真相、第二套 transport 真相、第二套媒体主链；
3. shared hotspot 不再继续承担多条 owner 线的混合职责；
4. media owner 链不再继续由超大编排或邻接总控跨层吸附；
5. 旧胶水、旧包装、旧重复路径、旧双活残骸已经退场；
6. 图谱复核显示热点得到实质减压，而不是只改名或只换目录；
7. 外部行为等价，稳定契约未被私自重写，现有功能与特性未因收口退化；
8. 与媒体 / 浏览器应用化相关的 authoritative 验证门禁同步通过，证明总收口没有以“结构更清楚”为名削弱正式媒体主链和浏览器应用能力；
9. 不存在以 TODO、临时兼容、待退场旁路、双活保底为名继续存活的技术债尾巴；
10. 后续维护与运维已不能再低成本地把系统养回同类屎山。

### 9.3 出现下面任一情况，直接视为失败

1. 核心还在，但热点照旧继续胖；
2. 新结构加了，但旧路径没删；
3. 只是把热点换了路径，没有把 owner 收回去；
4. 当前能跑，但长期更难维护；
5. 功能没坏，但特性缩水；
6. 表面更整齐，但冗余垃圾仍活着；
7. 只是把技术债换了位置，没有真正消灭它。

因此这里只认一句总裁决：

**只有当真相 owner 收回正确边界、旧胶水退场、热点实质减压、功能与特性不受损、未来不易反弹时，才算这次去屎山真正完成。**

## 10. 与现有文档的 authoritative 关系

### 10.3 现有媒体 authoritative spec 的地位

## 11. 最终硬裁决

以后在 `koko` 里，必须按下面这句话理解万人实时群聊去屎山这件事：

**当前万人实时群聊项目的正式聊天 realtime 核心仍然是后端纯 Rust `socketioxide` + 前端 `socket.io-client`；真正必须清理的，不是成熟聊天核心轮子，而是长期迭代后围绕核心长出来的私有重复轮子、私有重复真相、私有重复胶水和热点总控；后续必须在不引入新 bug、不破坏业务功能、不削弱满血特性、不留下冗余垃圾、不留下技术债尾巴的前提下，一次性把剩余屎山收口到底，并建立长期有效的防漂移约束，禁止未来维护和运维再把系统慢慢养回屎山。**

从这句话自然推出全部实现边界：

1. 禁止误杀成熟核心轮子；
2. 禁止低估外围私有胶水屎山；
3. 禁止长出第二套聊天核心、恢复真相、transport 真相或媒体主链；
4. 禁止让 adapter / shell / runtime 偷拿业务裁决；
5. 禁止让前端重新养出平行业务真相；
6. 禁止让 shared contract 倒灌壳专属语义；
7. 禁止只加新结构、不删旧胶水；
8. 禁止旧新双活长期共存；
9. 禁止为了“保险”保留技术债尾巴；
10. 禁止未来维护和运维继续用补丁式逻辑把热点养胖；
11. 禁止没有新鲜验证就宣布完成；
12. 禁止把图谱改名换路径冒充热点减压。

后续所有实现、review、plan、验收与维护，只要离开这条边界，或试图重新发明第二套真相、第二条路径、第二组 owner，都应直接视为漂移，必须禁止。
