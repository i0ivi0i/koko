# Koko 原生一键安装部署设计

**目标**

让 `koko` 在 `Ubuntu/Debian` VPS 上支持原生一键安装/升级，使用预编译产物、`systemd`、`Caddy`、`PostgreSQL`，不依赖 Docker，不在服务器现场编译源码。

**设计原则**

- 对用户只暴露一条安装入口：`curl -fsSL ... | bash`
- 安装和升级共用同一个 `install.sh`
- 业务内核不感知部署实现
- 进程守护交给 `systemd`
- `Caddy` 负责静态文件和反代；有域名时走 HTTPS，纯 IPv4 时走 HTTP
- 数据库存储交给 `PostgreSQL`
- 迁移脚本继续复用仓库现有 `migrations/`

## 部署产物

第一版约定未来 release 产物至少包含：

- `koko-server-linux-x86_64.tar.gz`
- `koko-web.tar.gz`
- `koko-admin.tar.gz`
- `koko-migrations.tar.gz`

这些都是部署层产物，不进入领域层。

## 目录布局

- 二进制：`/usr/local/bin/koko-server`
- 静态文件：
  - `/opt/koko/web/`
  - `/opt/koko/admin/`
- 版本文件：`/opt/koko/VERSION`
- 迁移脚本：`/opt/koko/migrations/`
- 配置：`/etc/koko/koko.env`
- 运行用户：`koko`

## 配置模型

`/etc/koko/koko.env` 第一版最小字段：

- `DATABASE_URL`
- `SERVER_BIND`
- `KOKO_PUBLIC_BASE_URL`
- `KOKO_ADMIN_BASE_URL`
- `KOKO_ADMIN_USER`
- `KOKO_ADMIN_PASSWORD`

默认部署策略：

- `SERVER_BIND=127.0.0.1:3000`
- 由 `Caddy` 反代到本机后端
- 有域名时，管理后台与聊天前台走两个域名
- 只有公网 IPv4 时，聊天前台走 `http://<ipv4>`，后台走 `http://<ipv4>:8081`

## 反向代理策略

使用两个站点：

- 域名场景：
  - `chat domain`
  - `/` 提供聊天前台静态文件
  - `/session*`、`/rooms*`、`/ws*` 反代后端
  - `admin domain`
  - `/` 提供后台前端静态文件
  - `/admin*` 反代后端后台接口

- 纯 IPv4 场景：
  - `http://<ipv4>`
    - 提供聊天前台静态文件
    - `/session*`、`/rooms*`、`/ws*` 反代后端
  - `http://<ipv4>:8081`
    - 提供后台前端静态文件
    - `/admin*` 反代后端后台接口

这样不需要改现有后台接口前缀，也避免后台静态页和后台 API 在同一路径冲突。

## systemd 策略

使用单一服务：

- `koko-server.service`

服务职责：

- 读取 `/etc/koko/koko.env`
- 运行 `/usr/local/bin/koko-server`
- 自动重启
- 日志进入 `journald`

不自造守护器。

## install.sh 责任边界

对外只有一个入口：

```bash
curl -fsSL https://raw.githubusercontent.com/i0ivi0i/koko/main/install.sh | sudo bash
```

脚本内部判断：

- 未安装 -> 首次安装
- 已安装 -> 升级

首次安装负责：

- 检测 `Ubuntu/Debian`
- 安装依赖：`curl`、`postgresql`、`caddy`
- 交互询问聊天入口与后台密码（后台密码可留空自动生成）
- 创建 `koko` 用户和目录
- 下载并展开 release 产物
- 生成数据库和配置
- 执行 SQL 迁移
- 写入 `systemd` 和 `Caddy` 配置
- 启动服务

升级负责：

- 保留原配置
- 备份旧版本到 `/opt/koko/backups/<timestamp>`
- 下载新产物
- 执行迁移
- 重启服务
- 健康检查失败则回滚旧版本

## 数据库迁移策略

第一版不要求在服务器安装 Rust 工具链或 `sqlx-cli`。

迁移方式：

- release 产物附带 `migrations/`
- `install.sh` 使用系统 `psql` 顺序执行 SQL 文件

这样更接近原生安装模式，也避免现场编译/安装 Rust 依赖。

## 当前范围

这轮只补部署骨架：

- `install.sh`
- `deploy/koko-server.service`
- `deploy/Caddyfile`
- 相关文档

这轮不做：

- GitHub Release 自动发布
- `.deb` 打包
- 多架构发布
- 备份恢复脚本拆分
- 安装脚本的真实远端托管

## 验证策略

当前阶段最小验证：

- `bash -n install.sh`
- 人工检查 service 模板和 Caddy 模板占位符
- 保证安装脚本在无 release 资产时清晰失败，而不是静默破坏系统

后续第二阶段再补：

- 基于容器或虚拟机的端到端安装验证
- 发布产物自动化
