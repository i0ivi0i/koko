# 媒体集成测试按真相归属瘦身设计

日期：2026-04-16  
状态：Draft  
适用范围：`koko` 当前 Rust integration tests 中与媒体上传、Tus hook、协作分发、后台清理相关的测试组织与测试支撑边界；目标是瘦身测试结构，不改变生产业务语义。  
关联资料：

- `docs/superpowers/specs/2026-04-15-媒体上传重试回收与分发资产生命周期-design.md`
- `docs/superpowers/specs/2026-04-15-媒体上传链路增强与并发治理-design.md`
- `docs/superpowers/specs/2026-04-15-上传吞吐专项优化-design.md`

## 1. 为什么要单独补这一份 spec

当前仓库里，媒体相关 integration test 已经出现明显热点：

- `tests/媒体上传测试.rs`：2046 行
- `tests/协作分发测试.rs`：1830 行
- `tests/测试支撑/媒体.rs`：419 行

问题不只是“文件大”，而是**业务真相 owner 已经混在一起**：

1. 上传主链测试和后台清理测试混在一个文件
2. 协作分发读侧契约和冷源清理回归混在一个文件
3. 通用测试支撑同时承担 tus 协议构造、fixture IO、数据库建数
4. 每个大测试文件都重复自举应用、bootstrap 会话、写入 tus 文件、直写数据库

这会带来三类直接后果：

1. 新增测试时，作者很容易把“和媒体相关”的逻辑继续往旧热点里塞
2. 测试 helper 慢慢变成第二套隐性业务编排层
3. 后续重构时无法快速判断某条断言究竟在守哪条业务事实

所以这份 spec 的目标不是“把大文件切成更多文件”，而是：

**按真相归属拆测试，让每个测试文件只守一类事实，并阻止未来继续失控变胖。**

## 2. 当前事实与风险

### 2.1 `tests/媒体上传测试.rs` 当前混了四类 owner

现有内容至少同时覆盖：

1. `prepare` 契约
2. `complete` 契约
3. `abandon` 与 termination 协调
4. 后台上传残留清理

另外，这个文件自己还带着 fake tus termination sidecar helper。  
这说明它已经不是“上传主链测试”，而是“媒体上传相关万物收纳箱”。

### 2.2 `tests/协作分发测试.rs` 当前混了五类 owner

现有内容至少同时覆盖：

1. locator / torrent 读侧契约
2. snapshot 投影一致性
3. presence 驱动的可用性裁决
4. 冷源 / mezzanine 后台清理
5. 内容读取 range 行为

这说明它已经不是“协作分发测试”，而是把读侧契约、后台维护、对象存储读行为混成了一锅。

### 2.3 `tests/测试支撑/媒体.rs` 是隐藏热点

它当前同时承担：

1. tus hook 请求体构造与断言
2. fixture 文件写入
3. ready 附件建数
4. 协作分发元数据建数

如果只拆两个大测试文件，不拆这个支撑文件，肥肉只会从顶层文件转移到 `测试支撑/媒体.rs`。

### 2.4 仓库里已经有正例

`tests/房间接口测试.rs` 已经采用了“瘦顶层 manifest + 子模块”方式：

1. 顶层文件只声明模块与边界说明
2. 子模块按 owner 划分
3. 顶层不再容纳大量具体测试

这说明这次不需要发明新测试框架，只要把媒体测试也拉回同样纪律即可。

## 3. 设计目标与非目标

### 3.1 目标

1. 保持所有现有生产业务语义不变，只调整测试组织与测试支撑边界
2. 按业务真相 owner 重组媒体集成测试
3. 把后台清理测试从上传主链和协作分发读侧中剥离出来
4. 把 `tests/测试支撑/媒体.rs` 拆成小而专的工具模块
5. 防止未来新增测试再次无边界回灌到热点文件

### 3.2 非目标

1. 不改生产代码的 contract、数据库 schema、错误语义、事件语义
2. 不重写现有断言逻辑，只做迁移和必要 import 修正
3. 不引入新的“测试框架”“测试世界对象”“测试服务层”
4. 不为了好看而把文件切成大量碎片；依然要控制 `.rs` 文件总量和维护成本

## 4. 设计四问

### 4.1 权威真相在哪里决定

仍然由现有生产代码决定：

- 上传语义：`src/媒体上传外壳.rs`、`src/用例.rs`
- 协作分发读侧语义：`src/媒体资产外壳.rs`、相关适配与查询链
- 后台清理语义：`src/外壳.rs` 及现有清理 usecase / adapter

这次重构只允许测试表达这些事实，不允许测试 helper 自己偷偷裁决成功条件。

### 4.2 稳定交换契约是什么

稳定交换契约保持不变：

1. `cargo test --test 媒体上传测试`
2. `cargo test --test 协作分发测试`
3. 新增 `cargo test --test 媒体后台测试`

也就是说：

- 测试 crate 的外部入口保持稳定
- 子模块只是内部组织方式变化

### 4.3 同步锚点 / 顺序依据是什么

迁移按批次推进，每一批只做“搬家 + 收口”：

1. 先建立新模块和薄顶层 manifest
2. 再迁具体测试
3. 再拆测试支撑
4. 最后补软性守卫

禁止一口气同时改测试结构、helper 语义、生产断言。

### 4.4 失败后如何恢复

每一批都必须可回退：

1. 只在测试侧改动，避免业务代码一起漂移
2. 每迁一批都跑定向测试验证
3. 任何失败都先修 import / module / helper 组织，不借机改业务逻辑

## 5. 目标目录结构

```text
tests/
  媒体上传测试.rs
  媒体上传测试/
    prepare.rs
    complete.rs
    abandon.rs
    tus_hook.rs
    公网地址推导.rs

  协作分发测试.rs
  协作分发测试/
    读接口契约.rs
    投影一致性.rs
    可用性裁决.rs

  媒体后台测试.rs
  媒体后台测试/
    上传残留清理.rs
    冷源清理.rs

  测试支撑/
    mod.rs
    媒体.rs
    媒体/
      tus.rs
      seed.rs
      fixture.rs
```

设计原则：

1. 顶层 `*.rs` 只做 manifest 和边界说明
2. 子模块按 owner 聚合，而不是按“都跟媒体有关”聚合
3. `测试支撑` 只保留小工具，不得成为第二套业务编排层

## 6. 具体迁移映射

### 6.1 `tests/媒体上传测试.rs`

#### 迁到 `tests/媒体上传测试/prepare.rs`

1. `旧图片上传路由已移除`
2. `prepare媒体上传会返回Tus契约`
3. `prepare视频上传会拒绝超过200mb的请求并允许200mb边界值`
4. `prepare图片和视频都会返回统一Tus契约`

#### 迁到 `tests/媒体上传测试/complete.rs`

1. `complete图片上传会把prepared附件升级成ready并写入缩略图`
2. `没有上传回执时complete媒体上传会返回attachment_not_ready`
3. `complete在只有partial没有final时会返回attachment_not_ready`
4. `complete会优先消费当前会话的final回执而不是single回执`
5. `post_finish稍后到达时complete媒体上传会等待回执并成功`
6. `complete视频上传会写入静态封面并返回preview_asset`
7. `complete图片上传遇到非图片原图会返回attachment_type_not_allowed`

#### 迁到 `tests/媒体上传测试/abandon.rs`

1. `放弃媒体上传会同时标记附件与transport为abandoned并清掉已登记的临时文件`
2. `abandon会先写业务abandoned再协调官方termination`
3. `放弃媒体上传会清掉当前会话下所有partial临时文件`

其中 fake tus termination sidecar helper 也一并本地化到 `abandon.rs`，不继续挂在顶层文件。

#### 迁到 `tests/媒体后台测试/上传残留清理.rs`

1. `后台会清理final完成后遗留的partial临时文件`
2. `后台会清理过期unfinished上传并把附件标成expired`
3. `后台会收口历史rustus残留locator而不再让清理卡住`

### 6.2 `tests/协作分发测试.rs`

#### 迁到 `tests/协作分发测试/读接口契约.rs`

1. `ready附件会落协作分发元数据`
2. `相同内容的不同附件可以共享同一swarm_id`
3. `locator会返回协作分发片段但不泄漏仓储私货`
4. `同一视频对发送者与群友返回同一套流媒体主链真相`
5. `图片locator会返回blob_asset而不是只给original_url`
6. `torrent接口会返回稳定metainfo并与locator对齐`
7. `locator会返回announce与web_seed并保留ticket占位`
8. `原图内容接口支持标准range读取`

`归一化受控地址` 作为读侧比较 helper 保留在这个模块内，不进入共享 `测试支撑`。

#### 迁到 `tests/协作分发测试/投影一致性.rs`

1. `视频locator与房间快照会共享同一套preview_asset`
2. `查询附件快照会带出图片真实资产与冷源生命周期字段`

#### 迁到 `tests/协作分发测试/可用性裁决.rs`

1. `presence上报会让web_seed过期但最近peer仍存活的locator保持available`
2. `web_seed过期且最近没有peer存活时locator会裁决expired`

#### 迁到 `tests/媒体后台测试/冷源清理.rs`

1. `原始冷源超过24小时后会被后台清理并写入删除时间`
2. `视频mezzanine超过24小时后会被后台清理并写入删除时间`
3. `冷源删除后locator顶层original失效但blob_original仍可读`

`写入测试对象` 只服务这组冷源清理测试，保留在 `冷源清理.rs` 本地，不进入共享 `测试支撑`。

### 6.3 `tests/测试支撑/媒体.rs`

#### 迁到 `tests/测试支撑/媒体/tus.rs`

1. `提取媒体上传授权头`
2. `断言TusHook已接受`
3. `断言TusHook拒绝上传`
4. `断言TusHook拒绝Termination`
5. `构造tus_hook请求体`
6. `构造tus_concatenation_hook请求体`
7. `断言媒体准备结果是Tus契约`

#### 迁到 `tests/测试支撑/媒体/seed.rs`

1. `插入ready图片附件记录`
2. `插入ready视频附件记录`
3. `插入附件协作分发元数据记录`
4. `插入流媒体清单元数据记录`
5. `未来冷源到期时间戳秒`

#### 迁到 `tests/测试支撑/媒体/fixture.rs`

1. `写入tus测试文件`
2. `最小png字节`
3. `最小mp4字节`

#### `tests/测试支撑/媒体.rs` 自身收口

它最终只保留：

1. 子模块声明
2. 必要的 `pub use`
3. 边界说明注释

不再继续保留大块实现。

## 7. 迁移阶段

### 阶段 1：建立薄顶层 manifest

目标：

1. 先把 `媒体上传测试.rs` 和 `协作分发测试.rs` 变成像 `房间接口测试.rs` 一样的薄入口
2. 新建 `媒体后台测试.rs`

约束：

1. 此阶段不改测试断言语义
2. 此阶段不拆 `测试支撑/媒体.rs`

### 阶段 2：按 owner 搬迁测试函数

目标：

1. 把上传主链、读侧契约、后台清理从原热点文件中剥离
2. 每次迁移只修正 import、可见性、局部 helper 所在位置

约束：

1. 任何业务断言变化都必须单独说明
2. 没有红测或编译错误证据，不允许“顺手优化”断言

### 阶段 3：拆测试支撑热点

目标：

1. 把 `测试支撑/媒体.rs` 按 `tus / seed / fixture` 小工具化
2. 保持旧调用方可平滑迁移

约束：

1. 先通过 `pub use` 兼容旧调用，再逐步改 import
2. 不引入 `MediaTestWorld`、`测试服务`、`测试仓储` 之类的新黑盒

### 阶段 4：补最小去重

仅允许抽两类明显重复且不承载业务判断的 helper：

1. 应用自举 / bootstrap 会话
2. 局部 fixture 预置

不允许抽象出带业务语义的“万能测试 DSL”。

### 阶段 5：补软性结构守卫

守卫目标是**阻止明显越界**，不是用机械阈值逼迫工程师。

因此本次不采用“严格行数红线 + 文件数红线”的硬门禁，而采用更克制的软约束：

1. 顶层 manifest 文件应只含模块声明、`use`、边界注释；不再继续堆业务测试
2. 后台清理相关入口不允许再回灌进 `媒体上传测试.rs` 或 `协作分发测试.rs`
3. `测试支撑/媒体.rs` 应保持薄出口，不再新增大块实现

自动化只建议检查**明显越界模式**，例如：

1. `tests/媒体上传测试.rs` 不应再出现 `执行一次媒体冷源清理(`
2. `tests/协作分发测试.rs` 不应再出现 `执行一次媒体上传残留清理(`
3. 顶层 manifest 不应继续定义大量 `#[tokio::test]`

文件行数不作为硬 fail 条件，改由 review checklist 和后续维护纪律处理。

## 8. 验证方案

每一阶段完成后，都必须跑对应定向验证：

```powershell
cargo test --test 媒体上传测试
cargo test --test 协作分发测试
cargo test --test 媒体后台测试
```

全部迁移完成后，再跑：

```powershell
cargo test
python3 -c "from graphify.watch import _rebuild_code; from pathlib import Path; _rebuild_code(Path('.'))"
git status --short
```

验证关注点：

1. 测试 crate 名称与入口保持稳定
2. 迁移前后断言语义不漂移
3. 没有新增冗余 helper 或第二套测试真相层
4. graphify 更新后能更清楚看到媒体测试社区按 owner 收口

## 9. 验收标准

满足以下条件时，才算这次瘦身真正成立：

1. `媒体上传测试` 只剩上传主链相关 owner
2. `协作分发测试` 只剩读侧契约相关 owner
3. 后台清理测试全部归入 `媒体后台测试`
4. `测试支撑/媒体.rs` 只做薄出口
5. 没有为“瘦身”引入新的大而全测试抽象
6. 所有既有媒体相关 integration tests 仍然通过
7. 未来若有人把错误 owner 的测试继续塞回原热点，能被软守卫或 review checklist 明确识别
