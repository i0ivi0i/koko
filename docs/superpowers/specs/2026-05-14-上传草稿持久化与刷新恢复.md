# 上传草稿持久化与刷新恢复 实现计划

> **面向 AI 代理的工作者：** 必需子技能：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐任务实现此计划。

**目标：** 用户在群聊中选择/上传媒体文件后，刷新页面不丢失草稿和上传进度，恢复后自动续传。
**架构：** 引入 Uppy Golden Retriever 插件持久化草稿状态到 localStorage + IndexedDB，配合已有的 Tus 断点存储（`koko-tus-resume`）实现完整的刷新恢复链路。不改变洋葱架构边界，变更范围限定在 adapter 层的媒体发布模块。
**技术栈：** @uppy/golden-retriever ^5.2.1、@uppy/core ^5.2.0（已安装）、@uppy/tus ^5.1.1（已安装）、idb（已安装）

---

## 前因后果

### 问题背景

万人万群实时群聊 IM 项目（https://kokoqun.com/），用户在聊天室选择图片/视频后会出现草稿卡片。但如果用户此时刷新页面（F5 或意外刷新），**所有草稿和上传进度完全消失**。

### 根因分析（冒烟测试 + 代码实证）

1. **草稿状态只在 JS 内存**——`媒体草稿.ts` 的 `写入媒体草稿()`/`更新媒体草稿状态()` 全是纯内存数组操作，没有持久化层
2. **Tus 断点只在上传开始后才写入 IndexedDB**——用户选文件到点发送之间的阶段，Tus 断点尚未创建
3. **Uppy 内部状态也在内存**——没有安装 Golden Retriever 插件，Uppy 的 file list / progress 信息不持久化

### 为什么选 Golden Retriever 而不是手搓

1. **官方方案**：Uppy 团队专门为"刷新后恢复"设计的插件，和 @uppy/tus 天然配合
2. **三层存储**：localStorage（状态）+ IndexedDB（小文件 ≤5MB）+ Service Worker（大文件引用）——覆盖全场景
3. **2025 年 v5.1.1 大修**：修了压缩/编辑图片不存储、失败文件过早清理、IDB 泄漏等多个关键 bug，现在成熟度够高
4. **项目 Uppy 版本兼容**：项目 @uppy/core ^5.2.0 + @uppy/tus ^5.1.1，和 golden-retriever ^5.2.1 同主版本线

### 项目上传链路（当前真实流程）

```
用户选文件
  → 识别媒体种类（图片/视频）
  → [并行] 计算 SourceHash + 预处理（转码/尺寸读取）
  → 预检秒传复用（SourceHash 命中则跳过上传）
  → 调用 prepareMediaUpload API（后端创建附件记录 + 签发上传令牌）
  → uppy.addFile()（此时 Uppy 才接管文件）
  → Tus 分块上传开始（断点写入 koko-tus-resume IndexedDB）
  → complete 确认 → 草稿状态变 ready
  → 用户点发送 → 消息广播到房间
```

**Golden Retriever 的切入点**：在 `uppy.addFile()` 之后，Uppy 内部状态（包括文件元数据、上传进度）被 Golden Retriever 自动持久化。刷新后恢复时，Golden Retriever 还原 Uppy 状态，Tus 通过 fingerprint 匹配旧断点续传。

### 兼容性关键约束

1. 项目使用**自定义编排**（预处理 → prepare API → 才 addFile），不是标准的 `uppy.addFile()` 直接上传
2. 刷新后 Uppy 恢复的文件**没有经过 prepare API**，需要重新 prepare 或跳过直接续传
3. 草稿 UI 状态（`媒体附件草稿`）和 Uppy 文件状态是**两套数据**，需要同步恢复
4. 视频的 `sourceFile`（File 对象）刷新后**不可恢复**（浏览器安全限制），但 Tus 续传不需要原始 File（只需上传 URL）

`frontend/媒体/媒体草稿持久化.ts`：
```typescript
/**
 * 草稿 UI 状态的 localStorage 持久化层。
 *
 * 为什么不用 IndexedDB：草稿列表通常 ≤9 条（媒体单条消息附件上限），
 * JSON 序列化后 ≤2KB，localStorage 完全胜任且同步读取更快。
 *
 * 为什么不复用 Golden Retriever：GR 持久化的是 Uppy 文件状态（进度、meta），
 * 但项目的草稿 UI 状态（localId、attachmentId、status）是独立数据结构。
 *
 * 不持久化的字段：
 * - sourceFile：File 对象不可序列化，刷新后浏览器安全限制无法恢复
 * - previewUrl：Blob URL 刷新后失效，恢复时需要重新生成
 */

const 存储键 = "koko_media_drafts";

export type 可持久化媒体草稿 = {
  localId: string;
  kind: "image" | "video";
  attachmentId: string;
  width: number;
  height: number;
  status: string;
  fileName: string;
  errorCode: string;
};

export function 保存媒体草稿到本地存储(drafts: 可持久化媒体草稿[]): void {
  if (drafts.length === 0) {
    localStorage.removeItem(存储键);
    return;
  }
  try {
    localStorage.setItem(存储键, JSON.stringify(drafts));
  } catch {
    // localStorage 满了不应阻断上传主链
  }
}

export function 从本地存储恢复媒体草稿(): 可持久化媒体草稿[] {
  try {
    const raw = localStorage.getItem(存储键);
    if (!raw) return [];
    const parsed = JSON.parse(raw);
    if (!Array.isArray(parsed)) return [];
    return parsed.filter(
      (item: unknown): item is 可持久化媒体草稿 =>
        typeof item === "object" &&
        item !== null &&
        typeof (item as Record<string, unknown>).localId === "string" &&
        typeof (item as Record<string, unknown>).kind === "string"
    );
  } catch {
    return [];
  }
}

export function 清除本地存储媒体草稿(): void {
  localStorage.removeItem(存储键);
}
```

## Task 4：在草稿写入/更新/清除时同步持久化

### 文件
- 修改：`frontend/媒体/媒体发布.ts`

### 为什么在这里同步

`创建媒体发布器` 内部持有 `deps.writeDraft`、`deps.updateDraft`、`deps.removeDraft`、`deps.clearDrafts` 四个回调。在每次调用这些回调后，额外调用 `保存媒体草稿到本地存储()` 把当前草稿快照持久化。

### 同步时机

| 操作 | 触发点 | 持久化动作 |
|---|---|---|
| 写入草稿 | `deps.writeDraft()` 后 | `保存媒体草稿到本地存储(deps.readDrafts())` |
| 更新草稿 | `deps.updateDraft()` 后 | 同上 |
| 移除草稿 | `deps.removeDraft()` 后 | 同上 |
| 清空草稿 | `deps.clearDrafts()` 后 | `清除本地存储媒体草稿()` |
| 发送成功 | 消息发送后 | `清除本地存储媒体草稿()` |

### 实现方式

在 `创建媒体发布器` 函数内，包装原始 deps 回调，在每次草稿变更后自动同步：

```typescript
import { 保存媒体草稿到本地存储, 清除本地存储媒体草稿, type 可持久化媒体草稿 } from "./媒体草稿持久化.js";

// 在 创建媒体发布器 内部，包装草稿操作以自动持久化
const 同步草稿到本地存储 = (): void => {
  const currentDrafts = deps.readDrafts();
  const persistable: 可持久化媒体草稿[] = currentDrafts.map(d => ({
    localId: d.localId,
    kind: d.kind,
    attachmentId: d.attachmentId,
    width: d.width,
    height: d.height,
    status: d.status,
    fileName: d.fileName,
    errorCode: d.errorCode,
  }));
  保存媒体草稿到本地存储(persistable);
};
```

在每个 `deps.writeDraft()` / `deps.updateDraft()` / `deps.removeDraft()` 调用后追加 `同步草稿到本地存储()`。在 `清空()` 中追加 `清除本地存储媒体草稿()`。

## Task 5：实现刷新恢复入口

### 文件
- 修改：`frontend/媒体/媒体发布.ts`

### 恢复流程

刷新后 `创建媒体发布器` 被重新调用时：

1. 调用 `从本地存储恢复媒体草稿()` 读取上次保存的草稿列表
2. 对每个草稿判断恢复策略：
   - **status === "ready"**（已上传完成）：直接还原草稿 UI，不需要续传
   - **status === "transporting"**（正在上传）：还原草稿 UI 为 "transporting"，Golden Retriever 会恢复 Uppy 文件状态，Tus 自动续传
   - **status === "failed"**：还原草稿 UI 为 "failed"，用户可以看到并决定是否重试（但 sourceFile 已丢失，需要重选文件才能重试）
   - **status === "processing"**（预处理中）：丢弃，因为预处理需要原始 File 对象
3. 恢复后的草稿**不生成 previewUrl**（原始 File/Blob 已丢失），UI 显示占位图标
4. Golden Retriever 恢复 Uppy 文件后，触发 `restored` 事件，此时可以补充 previewUrl（如果 GR 从 IDB 恢复了文件内容）

### 在 `创建媒体发布器` 返回对象中暴露恢复方法

```typescript
恢复未完成草稿(): void {
  const savedDrafts = 从本地存储恢复媒体草稿();
  for (const draft of savedDrafts) {
    if (draft.status === "processing") continue; // 预处理中的草稿丢弃
    deps.writeDraft({
      localId: draft.localId,
      kind: draft.kind,
      attachmentId: draft.attachmentId,
      previewUrl: "", // 刷新后 Blob URL 失效，用空字符串让 UI 显示占位
      width: draft.width,
      height: draft.height,
      status: draft.status === "transporting" ? "transporting" : draft.status as any,
      fileName: draft.fileName,
      errorCode: draft.errorCode,
      sourceFile: null as unknown as File, // 刷新后不可恢复
    });
  }
}
```

### 调用时机

壳层（Dioxus 或调用方）在创建媒体发布器后，调用 `恢复未完成草稿()` 一次。
