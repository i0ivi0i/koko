# 聊天壳单屏布局与软离房设计

日期：2026-04-07  
状态：设计已确认，待同步 implementation plan  
范围：`koko` 前端聊天壳的房间页布局、返回语义、标题展示和响应式适配

## 0. 一句话结论

这次不改后端真相，不加新业务命令，只把前端聊天壳收口成更像 Telegram iOS 的单屏聊天界面：

1. 输入区固定在底部，不再顶在顶部。
2. 房间页加返回按钮，返回语义定义为“暂时离开当前房间”，不是退群。
3. 顶部主标题显示房间短码，不再显示内部 `room_id`。
4. 房间页吃满视口高度，移动端到桌面端都保持单屏、连续、优雅的聊天界面感。

---

## 1. 这次要解决什么

当前前端房间页有四个明显体验问题：

1. 输入框和发送按钮在顶部，聊天动线反着来，用起来别扭。
2. 房间页没有返回到房间搜索页的按钮，用户一旦进房，就像被锁在一个页面里。
3. 当前布局更像固定宽度的小面板，不像现代聊天应用，屏幕尺寸一变就显得拘谨。
4. 房间页把内部 `room_id` 直接显示给用户，例如 `room: r-b950432da9e6`，既不自然，也不利于未来房间名能力演进。

这四个问题都属于前端壳层的布局和展示语义问题，不是业务真相缺失，不需要改共享契约和后端领域语义。

---

## 2. 边界先钉死

这次设计只允许改 `shell / presenter / adapter` 范围，不允许把前端越改越像业务核心。

### 2.1 不改什么

1. 不改 Rust 后端 `domain / application / contract` 的真相裁决。
2. 不新增“离房 / 退群 / 取消成员资格”之类业务命令。
3. 不让前端自己发明成员资格、权限、消息成立或阅读真相。
4. 不修改现有阅读锚点、未读恢复、历史分页和 realtime 的业务语义。

### 2.2 只改什么

1. 房间页结构和视觉层次。
2. 返回按钮的壳层语义。
3. 房间标题展示方式。
4. 响应式布局策略。
5. 对应的前端测试和样式断言。

---

## 3. 设计目标

这次房间页改造要同时满足下面几件事：

1. 让聊天界面符合用户对即时通讯工具的基本直觉：消息在中间，输入在底部，返回在顶部。
2. 让“返回房间搜索页”拥有明确、稳定、不误导的语义。
3. 让界面在手机、平板、桌面上都保持统一的聊天应用感觉，而不是网页卡片感。
4. 让当前显示位能兼容未来“房间名”能力，不要现在写死成只能显示短码或内部 ID。

---

## 4. 参考方向

这次视觉和交互方向明确参考 Telegram，尤其是 Telegram iOS 那种单屏连续聊天界面：

1. 输入区在底部。
2. 顶部有明确返回入口。
3. 顶部主标题显示聊天对象或群组名称，而不是内部 ID。
4. 整个聊天页是一个完整视口内的连续界面，不是中间漂浮卡片。

这里学的是交互方向和布局气质，不是照搬 Telegram 的全部视觉细节。

---

## 5. 核心决定

### 5.1 页面结构：单屏连续式，不做后台卡片感

房间页改成单屏聊天界面：

1. 组件根节点吃满当前视口高度。
2. 头部、消息流、输入区在视觉上连成一个整体。
3. 不再把房间页渲染成居中的窄面板。
4. 桌面端也尽量像聊天应用窗口，只保留克制留白，不做多栏后台布局。

### 5.2 顶部：返回按钮 + 房间短码主标题

房间页顶部收口成紧凑导航栏语义：

1. 左侧放返回按钮。
2. 中间主标题显示用户感知层房间标识，当前先用房间短码。
3. 副信息位保留，但保持很轻，不抢主标题。
4. 内部 `room_id` 不再出现在主视图里。

### 5.3 底部：输入区固定贴底

输入区固定在房间页底部：

1. 输入框是主元素。
2. 发送按钮是附属动作，不反客为主。
3. 小屏优先保证输入体验，不允许按钮把输入框挤坏。
4. 这次只改布局与视觉，不改发送消息流程本身。

### 5.4 中间：消息区吃满剩余空间

消息区必须自动占满顶部和底部之外的剩余空间：

1. 屏幕高时自然变高。
2. 屏幕矮时自然收缩。
3. 历史分页、未读分隔、阅读推进、realtime 恢复仍沿用现有逻辑。
4. 这次不把消息区改成虚拟列表，也不拆成多栏。

---

## 6. 返回语义：软离房，不是退群

这次必须明确区分两种不同概念：

1. 暂时离开当前房间页面
2. 失去这个房间的成员资格

返回按钮只代表第 1 种，不代表第 2 种。

### 6.1 用户语义

点返回后，用户的真实含义是：

1. 我先离开这个房间页面。
2. 我要回房间搜索页。
3. 我不是被踢出群，也不是主动退群。
4. 这个房间仍然属于我的可进入范围。

大白话就是：

**人从卧室回到客厅了，但房子还是他的。**

### 6.2 返回时前端该做什么

返回动作应当收口成前端壳层的“软离房”：

1. 退出当前房间视图。
2. 停掉当前房间的 realtime 订阅。
3. 清掉本地“当前正在看的房间”锚点。
4. 清掉当前房间输入框草稿。
5. 回到房间搜索页。

这里的“回到房间搜索页”是**壳层内部固定切回搜索视图**，不是依赖浏览器历史栈做 `back`。
原因很简单：

1. 当前组件本来就是一个壳层状态机，不是完整路由系统。
2. 如果把“返回”偷偷绑定成浏览器历史后退，后续实现容易受刷新、直接打开、嵌入式容器等场景影响。
3. 这次要的是稳定语义，不是把导航责任外包给浏览器历史。

### 6.3 返回时前端不该做什么

1. 不清匿名身份。
2. 不清当前会话。
3. 不改后端成员资格。
4. 不改后端阅读真相。
5. 不把返回按钮偷偷实现成“退群”。

### 6.4 为什么必须清本地当前房间锚点

如果只切页面、不清本地当前房间锚点，就会出现一个很怪的体验：

1. 用户明明已经点返回回到搜索页了。
2. 页面一刷新，又被自动拉回原房间。

这和“暂时离开当前房间”的语义冲突，所以必须在返回时清掉本地当前房间锚点。

## 7. 房间标题语义：现在显示短码，未来升级为房间名

当前主标题显示房间短码，比如 `ROOM01`。

这样做不是为了把短码永远写死，而是为了给未来房间名能力预留稳定升级位。

### 7.1 当前阶段

1. 主标题显示房间短码。
2. 不显示内部 `room_id`。
3. 副信息位可以先放轻量说明，比如“群聊房间”或轻量状态提示。

### 7.1.1 当前短码显示来源

由于现有后端快照只返回 `room_id`，不返回 `room_code`，所以当前阶段不能指望刷新恢复时再从后端现取短码。

这次先采用壳层本地显示缓存：

1. 用户通过搜索页输入房间短码进房成功后，前端把这份短码作为当前房间标题缓存起来。
2. 这份短码缓存只服务展示，不是恢复锚点，也不是业务真相。
3. 刷新恢复时，如果本地还保留这份短码缓存，就继续用于标题显示。
4. 如果本地没有短码缓存，就回退到通用标题，比如“群聊房间”，而不是把内部 `room_id` 暴露给用户。

这条边界必须写死：

1. `room_id` 仍然是恢复锚点。
2. `room_code` 在这次实现里只是壳层展示缓存。
3. 将来如果共享契约正式返回房间名或短码，再把标题来源切回权威契约，不继续依赖本地缓存。

### 7.2 未来有房间名时

将来新增房间名能力后，标题区直接升级成：

1. 房间名作为主标题。
2. 房间短码退到副标题或详情位。
3. 页面结构不重做，只替换展示来源。

### 7.3 这次实现上的要求

这次改布局时，不要把标题区写死成“只会有一个短码字符串”的一次性结构。
要留出“主标题 / 副标题”这种能平滑演进的槽位。

## 8. 响应式规则

### 8.1 总体原则

不同屏幕下，房间页都必须保持同一种聊天界面语义：

1. 顶部是导航和房间标题。
2. 中间是消息流。
3. 底部是输入区。

相对关系不变，只调整密度和留白。

### 8.2 手机窄屏

1. 房间页全宽。
2. 顶部和底部更紧凑。
3. 消息气泡宽度放宽，但仍保留阅读舒适度。
4. 输入区优先保证可用性。

### 8.3 平板和中屏

1. 允许出现轻微左右留白。
2. 整体仍是一块完整聊天界面。
3. 不拆出额外侧栏。

### 8.4 桌面宽屏

1. 保留克制留白，但整体仍像聊天应用窗口。
2. 不做后台式卡片，也不把输入区和消息区割裂成独立模块。
3. 消息气泡有最大宽度，避免一行摊得太长。

## 10. 测试与验收口径

### 10.1 结构验收

1. 进入房间后，输入框和发送按钮出现在底部。
2. 房间页有明确的返回按钮。
3. 顶部主标题显示房间短码，不再出现 `room: r-xxxx` 这种内部文案。
4. 房间页整体吃满视口高度。

### 10.2 语义验收

1. 点击返回后，回到房间搜索页。
2. 匿名身份和会话仍然保留。
3. 返回不等于退群。
4. 返回后刷新页面，不会因为旧的本地当前房间锚点而自动回到刚才的房间。
5. 之后再次进入同一房间，仍能走已有恢复链路。
6. 刷新恢复时，若存在本地房间短码缓存，则标题继续显示短码；若不存在，则显示通用标题，但都不显示内部 `room_id`。

### 10.3 响应式验收

1. 手机窄屏下，顶部、消息区、底部输入区都不变形。
2. 平板和桌面下，页面仍然像聊天应用，不像表单页或后台卡片页。
3. 不同屏幕高度下，消息区都能自动吃掉剩余空间。

### 10.4 回归验收

1. 不破坏未读分隔条。
2. 不破坏历史分页。
3. 不破坏阅读推进。
4. 不破坏 realtime 订阅恢复。
5. 不把“返回搜索页”误实现成“成员资格失效”。

### 10.5 建议补的测试

至少补这些前端测试：

1. 进房后会渲染返回按钮和房间短码标题。
2. 点击返回后会回到搜索页并清掉本地当前房间锚点。
3. 返回后不再渲染旧房间消息区。
4. 房间页样式包含单屏高度和底部输入区所需的关键规则。
5. 房间主视图不再显示内部 `room_id` 文案。
6. 恢复进入房间时，若本地有短码缓存，则标题继续显示短码；若没有短码缓存，则显示通用标题且不泄露 `room_id`。

---

## 11. 不做什么

为了防止这次“顺手收拾界面”越滚越大，明确这次不做：

1. 不新增房间名后端能力。
2. 不新增退群能力。
3. 不新增多栏桌面布局。
4. 不重做消息协议和契约。
5. 不把整个前端 UI 重写成另一套设计系统。

---

## 12. 一句话落地原则

这次改造的本质不是“换个样式”，而是把聊天壳的页面语义收正：

**让房间页真正像一个现代聊天应用的当前房间视图，而不是一个把内部 ID、顶部输入框和固定宽度面板拼在一起的网页块。**
