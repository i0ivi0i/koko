## 0. 为什么必须升级成“宪法”

到这一步，问题已经不是“性能再优化一点”。

`koko` 当前是公网万人实时群聊，浏览器前端面对的是：

1. 长时间存活的聊天会话；
2. 高频实时事件；
3. 多房间切换与恢复；
4. 多媒体时间线；
5. `Service Worker / Cache / IndexedDB / OPFS / WebTorrent` 这类本地加速层；
6. 多标签、多窗口、前后台切换、锁屏、恢复、bfcache、SW 更新接管。

如果继续按“网页 + 组件 + 局部状态 + 局部优化”思维演进，未来就会反复长出同一类故障：

1. 生命周期错判；
2. owner 漂移；
3. 预算失控；
4. 更新与恢复协议缺失；
5. 新包装加上去，旧真相却还活着；
6. 某次需求赶工后，代码又慢慢漂回“浏览器中的网页”。

所以这份文档不是“优化清单”，而是**前端浏览器应用宪法**。  
它要解决的不是本周一个 bug，而是**未来所有前端演进的方向约束**。

## 1. 上位裁决

### 1.1 一句话

**把浏览器当运行时，不当真相；把页面当窗口，不当大脑；把组件当壳，不当内核；把 `AppRuntime` 当 Web 应用唯一运行时裁决入口。**

### 1.2 四层真相

以后必须把真相分成四层，不能混：

1. **业务真相**  
   仍在后端 `domain / application / contract`。  
   例如：成员资格、权限、消息成立、事件顺序、治理语义。

2. **前端运行时真相**  
   只在前端 `AppRuntime + actor owners`。  
   例如：当前房间活跃态、滚动意图、自动播 owner、重连状态、更新待刷新状态。

3. **加速层状态**  
   存在于 `Service Worker / Cache / IndexedDB / OPFS / WebTorrent swarm`。  
   它们只回答“本地现在加速到什么程度”，**不是业务权威事实**。

4. **视图投影状态**  
   存在于 Lit 组件、DOM、动画、草稿框、滚动位置、可见区。  
   这些只是壳层表达，不得反向宣布业务或运行时真相。

## 2. 官方资料共同指向的硬约束

### 2.1 Chrome / web.dev：浏览器应用必须尊重生命周期与恢复

Chrome 与 web.dev 的口径已经非常清楚：

1. `hidden` 往往是最后一个可靠可见信号；
2. 页面可能进入 `frozen`，此时 JS 不能继续假设自己一直活着；
3. `pagehide / pageshow / bfcache / controllerchange` 都必须进入正式恢复协议；
4. SW 更新与接管时机要显式治理，不能靠浏览器“帮你兜底”；
5. 多视频页面必须控制自动播数量、`preload`、poster 与懒加载。

工程结论：

1. 生命周期不是 UI 细节，而是应用协议；
2. 恢复不是偶然成功，而是 owner 明确接管；
3. 时间线默认态必须轻量、静态、预算化。

### 2.2 WebKit / Safari：存储与后台能力都是可被收回的加速层

WebKit 官方反复强调：

1. `Service Worker` 是独立生命周期与独立进程；
2. 存储默认是 `best-effort`，并不承诺永久保留；
3. `persist()` 是申请，不是永远批准；
4. `localStorage / IndexedDB / Cache API / File System / Service Worker registrations` 都受存储策略与清理影响；
5. Web App 即便像正式应用，也仍然必须做 feature detection。

工程结论：

1. Safari 不是“不适合应用化”，而是要求应用更真实地面对生命周期；
2. 本地缓存、离线数据、swarm 文件、段缓存，都不能被当成权威真相；
3. “加速层丢失后优雅恢复”必须是正式能力，不是兜底补丁。

### 2.3 Lit：组件是浏览器原生壳，不是应用内核

Lit 官方建议同样和这份宪法一致：

1. 组件之间遵守 `properties down, events up`；
2. 组件内部只应该把自己的私有 reactive state 放在 `@state()`；
3. 浏览器 API、观察器、监听器这类可复用集成点，适合放进 `ReactiveController` 或专门运行时模块；
4. 跨组件的大范围数据共享应通过 `Context` 或稳定上层 owner，而不是层层偷偷改状态；
5. 组件组合推荐 mediator 模式，而不是子组件直接长出父层业务真相。

工程结论：

1. Lit 在 `koko` 里应该是**壳层技术栈**；
2. Lit 组件只负责渲染快照、发出意图、消费稳定输入；
3. 不允许把 `LitElement`、`@state`、`CustomEvent` 当成应用真相 owner。

### 2.4 WebTorrent / WebRTC / p2p-media-loader / HLS：轮子边界已经很清楚

官方边界必须继续尊重：

1. `WebRTC` 只是 transport，不回答应用语义；
2. `WebTorrent` 是浏览器 whole-file 协作分发层，适合长期协作分发与热复用；
3. `p2p-media-loader` 是 `Hls.js/Shaka` 的增强层，不是产品真相 owner；
4. Apple HLS / DASH-IF 都指向标准流媒体主链；
5. `Video.js` 只做播放器壳，不吞业务真相与生命周期真相。

工程结论：

1. 轮子继续复用；
2. 但 owner 必须自己收口；
3. 不允许为了“统一”再手搓一层私有媒体/P2P/缓存核心。

## 3. DDD 与 Unix 哲学如何落在前端

### 3.1 前端也必须做边界，不准“只有后端 DDD”

`koko` 的 Web 前端以后必须按这五层看：

1. **domain（前端运行时领域）**  
   回答浏览器应用运行时的本地不变量，例如：
   - 生命周期阶段语义；
   - 自动播唯一 owner；
   - 视口滚动门禁；
   - 多标签主上下文归属；
   - 更新待刷新状态。

2. **application（前端应用用例）**  
   编排各 owner，回答：
   - 何时恢复；
   - 何时降载；
   - 何时切换查看器 owner；
   - 何时接受 SW 更新；
   - 何时排空后台补发。

3. **contract**  
   固定 `AppEvent / AppCommand / ActorSnapshot / PlatformEvent / ErrorCode`。

4. **adapter**  
   DOM、浏览器 API、SW、WebTorrent、Video.js、hls.js、idb、Workbox 适配层。

5. **shell**  
   Lit 组件与视图模型，只负责表达和交互。

### 3.2 Unix 哲学在这里不是口号

以后前端演进必须遵守这些 Unix 式原则：

1. 一个 owner 只拥有一种真相；
2. 一个模块只解决一种边界问题；
3. 能复用成熟轮子，就不手搓；
4. 只有在边界压缩、隔离 vendor churn、或清晰退出路径存在时，才允许加薄适配层；
5. 禁止 pass-through 层堆积；
6. 禁止“为了显得高级”再加一层 orchestrator/manager/facade；
7. 新模块上线时必须压缩旧复杂度，而不是净增高度。

## 4. 轮子复用总裁决

以后必须站在这些轮子肩膀上，不再重复造轮子：

1. `Lit`：壳层组件模型与渲染
2. `@tanstack/lit-virtual`：虚拟列表
3. `Workbox`：app shell 预缓存、更新、导航回退
4. `idb`：结构化本地存储
5. `Video.js`：唯一正式查看器壳
6. `hls.js`：标准 HLS 分支
7. `p2p-media-loader-hlsjs`：HLS 分支 P2P 增强
8. `WebTorrent`：长期协作分发平面
9. `socket.io-client`：实时传输 client

只有在满足下面三个条件时，才允许加薄封装：

1. 真正压缩调用方复杂度；
2. 保留清晰退出路径；
3. 不制造第二套权威真相。

## 5. 宪法级硬规则

### 5.1 浏览器信号只能先翻译，不能直接裁决

`visibilitychange / pagehide / pageshow / freeze / resume / controllerchange / online / offline / click / scroll / intersection / fullscreenchange`  
都只是输入信号。

它们必须先被翻译成 `AppEvent` 或 `PlatformEvent`，再进入 owner。  
禁止在 Lit 组件、播放器回调、socket 回调里直接宣布运行时真相。

### 5.2 `BrowserAppPlatform` 是唯一浏览器能力组合根

以后只有平台层允许直接统一接管这些浏览器能力：

1. 生命周期
2. Service Worker
3. Cache / IndexedDB / OPFS / persistent storage
4. BroadcastChannel / 多上下文
5. Notification / Badge
6. 网络离线状态

其它层不允许再直接偷偷碰这些全局能力。

### 5.3 `AppRuntime` 是唯一前端运行时裁决入口

以后所有浏览器应用运行时语义，都必须通过：

`Browser Signal -> Platform Event -> AppEvent -> AppRuntime -> Actor Owner`

禁止：

1. 组件直接改全局运行时状态；
2. SW 消息直接 patch 壳层；
3. socket 事件直接 patch Lit 视图；
4. 观察器回调直接改消息窗口真相。

### 5.4 Owner 必须明确且唯一

至少要固定这几个 owner：

1. `AppLifecycleActor`
2. `RealtimeSessionActor`
3. `RoomTimelineActor`
4. `RoomViewportActor`
5. `MediaRuntimeActor`
6. `AssetDistributionActor`
7. `CacheAndStorageActor`
8. `MultiContextActor`

任何一个真相只允许一个 owner。  
投影层、视图层、适配层只允许消费或翻译，不得再长出平行真相。

### 5.5 组件局部状态必须收窄

Lit 组件的 `@state` 只允许持有：

1. 输入焦点；
2. 展开/收起；
3. 本地动画态；
4. 临时 hover/drag/selection；
5. 尚未派发出去的本地表单态。

Lit 组件不允许把这些东西当私有真相藏起来：

1. 房间恢复状态；
2. 自动播最终 owner；
3. SW 更新待接管状态；
4. 多标签主上下文归属；
5. 媒体分发正式平面；
6. 权威消息窗口顺序。

### 5.6 媒体主链与 P2P 主链必须继续分层

以后继续遵守：

1. 时间线默认轻预览，偏 poster / thumbnail；
2. 自动播只允许单 owner、静音、轻量、可快速释放；
3. 正式查看器才允许进入重型播放与补齐；
4. `0-24 小时` 标准流媒体仍是可靠主链；
5. `24 小时` 后长期正式协作分发主平面只能是 `WebTorrent`；
6. `p2p-media-loader` 只增强 `HLS` 支路，不得冒充长期 owner。

### 5.7 加速层永远不是业务真相

以后必须一直区分：

1. 缓存命中：只是本地有加速
2. 本地完整文件：只是加速层更强
3. swarm 在线：只是分发可用
4. app shell 已接管：只是运行时已接管

这些都不等于：

1. 消息业务事实成立；
2. 房间恢复已经完成；
3. 媒体真相已经稳定；
4. 更新已经安全落定。

### 5.8 恢复必须是正式协议

至少必须正式覆盖：

1. `hidden -> visible`
2. `pagehide -> pageshow`
3. `freeze -> resume`
4. `controllerchange`
5. 存储被驱逐
6. swarm 中断
7. 离线 -> 在线
8. 多标签主上下文切换

每种恢复都必须写清：

1. 谁是 owner；
2. 谁发起；
3. 谁等待；
4. 何时允许视图宣布“恢复完成”；
5. 失败时如何降级。

### 5.9 预算制度是正式制度，不是建议

以后必须长期可观测这些预算项：

1. `activeDomWindowSize`
2. `activeVideoCount`
3. `autoplayOwnerCount`
4. `activeSwarmCount`
5. `inflightLocatorCount`
6. `inflightManifestOrRangeCount`
7. `hiddenHeavyTaskCount`
8. `longTaskCount`
9. `storageUsage / storageQuota`
10. `updatePendingDuration`

并且明确这些动作：

1. `hidden` 后主动降载；
2. 释放无 consumer 的冷 swarm；
3. 限制同屏真实 `<video>` 数量；
4. 浏览器预算不够时优雅回退，不继续硬拉。

### 5.10 新入口活了，旧入口必须退场

这是防漂移最核心的硬规则：

1. 引入新 owner 时，旧 owner 必须删除或退化成纯翻译；
2. 引入新事件流时，旧事件流不能继续活；
3. 引入新平台握手时，旧手写路径不能偷偷保留。

**任何“新包装加上去，但旧真相仍活着”的实现，一律视为失败。**

## 6. 防漂移治理机制

### 6.1 目录与边界治理

以后按职责收口：

1. `frontend/平台/**`  
   浏览器能力、生命周期、SW、存储、多上下文、通知、离线。

2. `frontend/应用运行时.ts` 及相关 actor 模块  
   统一把平台信号翻成 `AppEvent`，并分发给 owner。

3. `frontend/*应用内核.ts` / `frontend/*编排.ts`  
   只持有应用级真相与编排。

4. `frontend/媒体/**`  
   媒体、查看器、协作分发、播放解析的适配与 owner。

5. `frontend/*壳.ts` / `frontend/*消息窗.ts`  
   Lit shell，只渲染快照、发意图。

### 6.2 CI 守门

后续必须补这类守门检查：

1. 除平台层白名单外，禁止直接使用：
   - `navigator.serviceWorker`
   - `navigator.storage`
   - `BroadcastChannel`
   - `window.addEventListener("visibilitychange" | "pagehide" | "pageshow" | "freeze" | "resume")`

2. 除运行时/owner 白名单外，禁止组件直接调用：
   - transport 实例策略切换
   - SW 更新接受
   - 多上下文主权声明
   - 媒体正式 owner 切换

3. 组件层新增 `@state` 时，必须证明它只是局部视图态。

### 6.3 测试守门

以后每次改动浏览器应用主链，都必须先补失败测试，至少覆盖：

1. `hidden/pagehide/freeze/pageshow/resume` 生命周期恢复
2. SW 更新与 `controllerchange`
3. 存储丢失后的优雅恢复
4. 时间线默认轻预览
5. 自动播唯一 owner
6. 冷视频不会批量 whole-file 启动
7. 多标签主上下文不打架

### 6.4 评审守门

以后所有相关改动都必须回答这五问：

1. 新增/变更的真相 owner 是谁？
2. 旧入口是否已退场？
3. 预算影响是什么？
4. 恢复协议是什么？
5. 证明它没破坏现有功能的测试证据是什么？

答不清，就不能过。

## 7. 分阶段路线

### Phase 0：立宪与门禁先行

目标：

1. 写死这份宪法；
2. 把前端浏览器应用化与防漂移要求挂成正式施工准绳；
3. 补守门测试与静态扫描；
4. 不动业务契约，不动播放器壳，不重写现有轮子。

### Phase 1：生命周期主权收口

目标：

1. 建立 `AppLifecycleActor`
2. 把 `hidden/pagehide/freeze/pageshow/resume/controllerchange` 收口成应用协议
3. 让 transport / media / offline / update 都通过生命周期 owner 协调

验收：

1. 生命周期不再只是 transport 的局部事实
2. 组件不再各自解释浏览器阶段

### Phase 2：运行时 owner 收口

目标：

1. `RoomTimeline / RoomViewport / MediaRuntime / RealtimeSession` 真正独立 owner
2. 壳层只能消费快照
3. 删除平行 owner 与旧直连路径

### Phase 3：预算化升级

目标：

1. 把媒体、DOM、P2P、后台任务预算化
2. `hidden` 后正式降载
3. 有证据地控制大房间与多媒体滚动性能

### Phase 4：缓存、更新与多上下文治理

目标：

1. 收口 SW 更新协议
2. 收口壳缓存、离线补发、多标签主权
3. 让旧壳长期混跑彻底失去生存空间

### Phase 5：P2P 长期平面对齐

目标：

1. 继续按既有主链 spec 落地 `0-24 小时` 与 `24 小时后` 的正式平面切换
2. 保持 `HLS`、`WebTorrent`、`p2p-media-loader` 边界清楚
3. 不再让时间线、查看器、协作分发互相冒领 owner

## 8. 验收标准

### 8.1 架构验收

1. 浏览器事件不再直接改业务或运行时真相
2. `BrowserAppPlatform` 成为唯一浏览器能力组合根
3. `AppRuntime` 成为唯一前端运行时裁决入口
4. 关键真相都只有唯一 owner
5. 新层上线时同步压缩旧层

### 8.2 功能验收

1. 现有聊天、进房、消息、上传、查看器、离线补发、P2P 主链不回归
2. Safari / Chrome 下生命周期与存储语义自洽
3. SW 更新不再让旧 bundle 长期混跑

### 8.3 性能验收

1. 多媒体时间线滚动时不再出现整列重链路风暴
2. `hidden` 后重型任务能及时释放或降载
3. 恢复后按协议回到稳定状态，而不是靠计时器运气

### 8.4 防漂移验收

1. CI 能挡住越层直接碰浏览器全局能力
2. PR 评审模板能挡住第二真相 owner
3. 测试能挡住生命周期与预算回归
4. 后续迭代不再需要靠“记得别写坏”这种人肉提醒

## 9. 当前裁决

`koko` 以后不再把 Web 前端当“浏览器里的网页”，  
而要把它当“浏览器中的应用操作平面”来建设。

这份宪法写死三件事：

1. **轮子继续复用，不重复造轮子**  
   站在 Lit、Workbox、idb、Video.js、hls.js、p2p-media-loader、WebTorrent、socket.io-client 这些成熟轮子上。

2. **真相必须收口，不允许多 owner**  
   页面只是窗口，组件只是壳，`AppRuntime` 才是应用运行时入口。

3. **未来必须可防漂移，不靠自觉**  
   靠 CI、测试、评审门禁与旧入口退场制度，把“浏览器中的网页”心智挡在门外。

## 10. 本轮推荐的第一刀

如果主人确认按这份宪法继续推进，本轮第一刀不是乱改一堆文件，而是：

1. 先补生命周期/恢复/更新的保护测试；
2. 把 `AppLifecycleActor` 从现有平台事件中正式抽出来；
3. 让 `hidden/pagehide/freeze/controllerchange` 驱动统一的降载/恢复协议；
4. 同步删除旧的直连入口；
5. 再进入后续 owner 收口与预算化阶段。

这才符合：

1. DDD：真相 owner 清楚；
2. Unix：模块小而专、可组合、可替换；
3. 不手搓轮子：浏览器、Lit、Workbox、HLS、WebTorrent 各守其职；
4. 不造屎山：新层上线必须压缩旧层；
5. 不破坏现有功能：先保护测试，再小步改造。
