# Web 视频默认循环播放策略设计

日期：2026-04-15  
状态：Draft  
适用范围：`koko` 仓库 Web 前端当前所有视频播放场景，包括消息流内联自动播与正式媒体查看器。  
关联文档：

- `docs/superpowers/specs/2026-04-15-Web群聊视频单一真相与视口自动播-design.md`
- `docs/superpowers/specs/2026-04-14-Web单一视频播放器壳与外置分发层-design.md`

## 1. 为什么要补这份 spec

当前群聊视频已经支持：

1. 消息流视口自动播；
2. 点开后进入唯一正式播放器壳。

但真实体验暴露了一个一致性缺口：

- 消息流自动播的视频只播一遍就停；
- 打开正式播放器后，视频也不是默认循环。

这说明系统里还缺一条明确的统一播放策略：

**视频在“当前播放态”里默认应持续循环，而不是播一遍后停在末帧。**

如果现在只在某个 `<video>` 标签上顺手补 `loop`，问题虽然可能暂时消失，  
但它会继续留下几个隐患：

- 消息流和正式播放器各有各的循环规则；
- `swarm / blob / anchor / manifest` 可能又长出来源特判；
- 后面切源、重建播放器壳、切换 owner 时，循环语义很容易再次丢失。

这份 spec 的目标，是把“视频默认循环”收口成一条统一策略，  
而不是做一次只对当前 DOM 生效的小修补。

## 2. 当前现场证据

### 2.1 消息流内联自动播 `<video>` 当前没有循环语义

`frontend/房间消息窗.ts` 当前渲染消息流自动播视频时：

- 有 `muted`
- 有 `autoplay`
- 有 `playsinline`
- 但没有 `loop`

所以浏览器默认行为就是：

- 播放一次
- 到末尾
- 停止

这和“只要它还是当前自动播 owner，就应该继续循环”的产品语义不一致。

### 2.2 正式播放器壳里的真实 `<video>` 当前也没有循环语义

`frontend/媒体/videojs播放器壳.ts` 当前创建唯一正式播放器壳时：

- 对真实 `<video>` 设置了 `autoplay = true`
- 设置了 `playsInline = true`
- 但同样没有设置 `loop = true`

所以正式查看器当前也没有稳定的默认循环语义。

### 2.3 当前缺的不是第二套恢复逻辑，而是一条统一播放策略

本问题的根因不是：

- P2P 不稳定；
- HLS 拉流失败；
- 浏览器不支持自动播。

本问题更接近：

**同一套视频主链已经跑起来了，但“视频在播放中默认要不要循环”这件事，还没有被系统明确声明。**

## 3. 设计目标

本次设计要同时达成四件事：

1. 所有视频默认都按统一规则循环播放；
2. 消息流自动播与正式播放器共享同一条循环策略，不再各自判断；
3. 循环语义对来源保持中立，`swarm / blob / anchor / manifest` 一视同仁；
4. 循环只是“播放中的默认行为”，不演变成“永不停止”的脏逻辑。

## 4. 核心裁决

### 4.1 统一语义

当前阶段，Web 前端的视频默认语义改为：

**只要视频仍处在当前播放态，就默认循环播放。**

这里的“当前播放态”包括：

- 消息流里当前拿到自动播 owner 的视频；
- 正式媒体查看器当前正在播放的视频。

不包括：

- 已失去自动播 owner 的卡片；
- 已关闭的查看器；
- 已离开当前房间或已销毁的播放器实例；
- 已经不再持有当前视频源的旧播放器实例。

### 4.2 统一 owner

循环播放不是壳层临时技巧，  
它属于**统一播放策略**的一部分。

本期 owner 裁决如下：

- `媒体会话 / 播放策略层`
  - 决定“视频默认是循环播放”
  - 这是唯一策略真相 owner
- 消息流内联 `<video>` 元素
  - 只负责把该策略落到当前自动播 video 元素
- `Video.js 正式播放器壳`
  - 只负责把同一条策略落到唯一正式 video 元素

壳层、列表、按钮点击、来源分支都不得再各自定义一次循环规则。

### 4.3 来源中立

循环播放必须与来源解耦。

不能出现：

- `swarm` 循环、`anchor` 不循环；
- `file/blob` 循环、`manifest` 不循环；
- 消息流循环、正式播放器不循环；
- 正式播放器循环、消息流只播一遍。

本期明确裁决：

**循环是播放策略，不是来源策略。**

### 4.4 停播条件

循环不等于永远不停止。  
系统仍然必须在这些场景下停止播放：

1. 视频失去消息流自动播 owner；
2. 用户切换到另一条视频；
3. 关闭媒体查看器；
4. 离开房间；
5. 播放器实例销毁；
6. 当前视频源失效并被会话 owner 收回。

也就是说：

**循环只在“当前播放态仍成立”时生效；一旦离开该状态，就立即停。**

### 4.5 关于“手动暂停”

本期不额外引入“手动暂停锁”这类第二套前端状态。

裁决是：

- 系统默认循环播放策略始终存在；
- 但不为“手动暂停”再引入一套跨来源、跨重建、跨 reopen 的特殊优先级状态机；
- 避免为了一个小行为补丁，再长出新的真假状态。

换句话说：

**本期要补的是统一循环策略，不是再设计一套复杂的暂停持久化机制。**

## 5. 实施边界

### 5.1 允许修改的层

- `frontend/媒体/videojs播放器壳.ts`
  - 唯一正式播放器壳的真实 video 元素如何承接默认循环策略
- `frontend/媒体/媒体查看器.ts`
  - 查看器如何继续复用同一套循环策略，而不是自己再发明规则
- `frontend/房间消息窗.ts`
  - 消息流内联自动播 video 如何投影统一循环策略
- 如确有必要，可在前端媒体会话或播放策略层增加一个薄的统一策略投影

### 5.2 明确禁止

本期禁止以下实现方式：

1. 在 `ended` 事件里手搓 `currentTime = 0; play()` 第二套循环逻辑；
2. 在消息流和正式播放器分别发明两套不同的循环规则；
3. 按来源分支特判循环行为；
4. 为此新增一套重型状态机、管理器、配置平台或私有轮子；
5. 把这条策略塞进共享后端 contract。

这里必须守住 DDD 和 Unix 哲学：

- 统一规则只保留一个 owner；
- 具体承载层只做投影；
- 不重复造轮子；
- 不为小问题制造新屎山。

## 6. 测试护栏

本次改动至少要补四类测试：

### 6.1 正式播放器壳测试

在 `frontend/tests/videojs播放器壳测试.spec.ts` 锁死：

- 创建唯一播放器壳时，真实 `<video>` 默认具备循环语义；
- 切 `file -> hls`、`hls -> file` 时，循环语义不能丢。

### 6.2 媒体查看器测试

在 `frontend/tests/媒体查看器测试.spec.ts` 锁死：

- 正式视频查看器继续走同一个 `Video.js` 壳；
- 查看器里当前视频默认循环；
- 关闭查看器时仍然正常 `pause + destroy`，不会因为循环导致泄漏。

### 6.3 消息流自动播测试

在 `frontend/tests/房间消息窗媒体查看器测试.spec.ts` 锁死：

- 当前自动播 owner 渲染出的内联 `<video>` 默认具备循环语义；
- 同屏依然只允许一个自动播 owner；
- owner 切换后旧视频必须停，不能因为 `loop` 还继续偷偷跑。

### 6.4 回归测试

需要保证这次循环补完不会打坏：

- 当前消息流自动播裁决；
- 正式播放器单壳原则；
- `swarm / blob / anchor / manifest` 的既有来源裁决；
- 查看器关闭、退房、切源时的释放行为。

## 7. 失败标准

只要还出现下面任意一条，就说明这次设计落地失败：

1. 消息流和正式播放器仍然各自维护不同的循环规则；
2. 某个来源分支被特判成“不循环”；
3. 实现依赖 `ended -> replay` 之类手搓第二套机制；
4. 关闭查看器、切换 owner、离房后，旧视频仍在后台继续跑；
5. 为了补循环，又长出一套新的状态机、管理器或配置层。

## 8. 总结

这次不是要做“视频到末尾再自动重播一下”的小技巧。  
真正要补的是：

**把“视频默认循环播放”收口成统一播放策略，并让消息流自动播与唯一正式播放器壳共同消费这条策略。**

这样才能继续守住：

- 单一真相；
- 单一正式播放器壳；
- 单一媒体主链；
- 不重复造轮子；
- 不把一个小体验问题修成新屎山。
