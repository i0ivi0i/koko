# Rust 集成测试按能力域拆分与防回胖设计

日期：2026-04-11  
状态：Draft  
适用范围：`koko` 仓库 `tests/` 目录下的 Rust 集成测试组织方式  
关联文件：

- `tests/集成测试.rs`
- `tests/用例测试.rs`
- `tests/领域测试.rs`
- `学习/整理笔记/Rust-集成测试与TDD组织实践笔记.md`

## 1. 这份设计要解决什么问题

当前 `koko` 的 Rust 测试分层方向本身没有错：

- `tests/领域测试.rs` 负责纯业务规则与领域不变量；
- `tests/用例测试.rs` 负责用例编排、结构化日志和契约输出；
- `tests/集成测试.rs` 负责模块接线后的真实行为。

真正的问题不在“有没有三层测试”，而在 `tests/集成测试.rs` 已经长成一个测试热点：

- 文件约 4888 行；
- 总测试数约 72；
- `#[serial]` 约 64 个；
- 同时混合了：
  - 配置失败与迁移结构；
  - 共享契约占位；
  - 媒体上传 prepare / complete / Rustus hook；
  - 协作分发 locator / torrent / presence / web seed 过期裁决；
  - 房间快照 / 增量 / 历史 / 阅读推进；
  - 后台接口与静态壳；
  - realtime 与并发；
  - 启动与优雅停机；
  - 环境变量、日志采集、HTTP helper、Rustus fixture 等通用支撑。

这会带来三类实际风险：

### 1.1 TDD 体验会持续变差

当一个集成测试文件同时塞了多条能力线，开发者在写新测试时最省事的动作就会变成：

- 打开最大的那个文件；
- 找一个差不多的测试；
- 在旁边继续追加。

这会让 TDD 从“围绕单个能力闭环迭代”退化成“在杂糅热点里硬找落点”，最后测试虽然越来越多，但可理解性越来越差。

### 1.2 业务边界会在测试里被抹平

测试不是业务真相本身，但测试会反向塑造代码结构。  
如果媒体上传、协作分发、房间阅读、后台接口、实时链路在测试层长期混住，后续实现和重构时也更容易顺手跨边界：

- 把媒体运输态判断塞进房间接口上下文；
- 把协作分发运行态错当成业务成立条件；
- 把测试 helper 长成第二套业务编排。

这和项目要求的 DDD 分层、领域主权和稳定契约是逆向的。

### 1.3 测试支撑层会偷偷长成“第二个大文件”

如果只是把 `集成测试.rs` 粗暴拆碎，但不控制 helper 的边界，结果往往不是更优雅，而是：

- 原来的大文件消失了；
- `tests/common.rs` 或 `tests/support.rs` 变成新的大文件；
- 甚至 helper 里开始偷放业务判断。

这种“只是把屎山切片”不是真正的瘦身。

所以这次拆分不是为了文件数好看，而是为了让 Rust 的 TDD 回到：

1. 以能力域为单位迭代；
2. 以业务边界为单位组织；
3. 以小而专、可组合的测试支撑保持 Unix 哲学；
4. 以明确归属和软约束防止将来重新回胖。

## 2. 目标与非目标

### 2.1 目标

- 把当前单个 `tests/集成测试.rs` 按能力域拆成多个顶层 `xxx测试.rs`。
- 对仍会继续增长的热点能力，允许在同名目录下再拆子模块。
- 用一个统一的 `tests/测试支撑/` 收口通用测试支撑，但严格限制其职责。
- 保持现有三层测试结构：
  - 领域测试
  - 用例测试
  - 集成测试
- 让新增集成测试有稳定归属，避免继续默认塞进“最大那个文件”。
- 让拆分结果和当前业务能力边界一致，反向强化 DDD 与六边形边界。
- 在整个拆分过程中，不主动改变生产代码业务语义，不把结构瘦身混成业务重写。

### 2.2 非目标

- 不在这次工作里重写 `src/` 下业务实现。
- 不把集成测试整体降级成大量 mock 测试。
- 不引入新的测试框架或大规模测试基础设施替换。
- 不在这次工作里强行把所有 `serial` 一次性消灭。
- 不为了“纯度”新增一个复杂的 CI/脚本约束系统。
- 不创建一个新的“杂物测试文件”来接住边界不清的测试。

## 3. 设计裁决

### 3.1 不采用的方案

#### 方案一：继续保留一个 `集成测试.rs`

只在文件内部加注释或局部 `mod`。

不选原因：

- “集成测试.rs” 这个名字本身就会继续吸引追加；
- 热点入口仍然存在，防回胖最弱；
- 后续 review 很容易回到“先顺手加一条再说”。

#### 方案二：全部拆成很多独立顶层测试文件，不允许子模块目录

不选原因：

- 每个顶层文件都是独立 integration test crate；
- 对未来还会继续增长的热点能力不够柔性；
- 容易把“防回胖”变成“测试文件碎片化”。

### 3.2 最终方案：混合式能力文件 + 热点子模块

最终采用：

1. 顶层以能力域新增少量 `xxx测试.rs`；
2. 对未来还会继续增长的热点能力，允许使用：
   - `房间接口测试.rs`
   - `tests/房间接口测试/*.rs`
   这种“顶层入口 + 同名目录子模块”结构；
3. 通用支撑统一放进 `tests/测试支撑/`；
4. 拆分完成后，旧的 `tests/集成测试.rs` 退役删除，不保留一个历史性大入口。

这个方案兼顾了三件事：

- 顶层能力文件让新增测试一眼知道该去哪；
- 热点子模块让未来继续增长时不至于再养第二个巨型文件；
- 不保留 `集成测试.rs`，从入口命名上消掉“默认往这里追加”的心智。

目标形态如下：

```text

  测试支撑/

  消息主链测试.rs
  媒体上传测试.rs
  媒体上传测试/
    rustus_hook.rs
    公网地址推导.rs
  协作分发测试.rs
  房间接口测试.rs
  房间接口测试/
    增量事件.rs
    快照.rs
    阅读推进.rs
    历史分页.rs
  实时链路测试.rs
  后台与静态壳测试.rs
  用例测试.rs
  领域测试.rs
  启动器脚本检查.ps1
```

说明：

- `fixtures/` 保留现有二进制夹具，不额外打散；
- `测试支撑/` 是通用测试支撑目录，不是业务测试兜底区；
- 顶层 `xxx测试.rs` 是能力入口；
- 只有确认是未来会继续增长的热点能力，才允许使用同名子目录继续下沉。

## 5. 各能力文件的所有权边界

### 5.1 `启动与迁移测试.rs`

负责：

- 配置缺失即失败；
- 迁移文件结构存在性与关键字段；
- 共享契约占位；
- 端口监听与优雅停机。

不负责：

- 房间快照、历史、阅读推进；
- 媒体上传运输链；
- 后台与静态壳；
- 实时消息与并发。

原因：

- 这是系统级入口与基础结构验证；
- 关注的是“系统能否启动、结构是否齐全”，不是业务能力流转。

### 5.2 `消息主链测试.rs`

负责：

- 发送消息事务顺序；
- 图片/视频附件引用与消息一起成立；
- `prepared` 附件不能进入消息主链；
- `ready` 附件可以进入消息主链；
- 快照读回时仍能看到已成立附件。

不负责：

- 如何从 `prepare` 变成 `ready`；
- Rustus hook 收到什么 payload；
- locator / torrent / presence 裁决。

原因：

- 这里的权威问题是“消息是否成立、附件是否可被消息引用”；
- 媒体上传只负责把附件送到 `ready`，不负责消息主链裁决。

### 5.3 `媒体上传测试.rs`

负责：

- `prepare_media_upload` 的统一 Tus 契约；
- `complete_media_upload` 的升级与元数据提取；
- 图片 / 视频上传主链；
- 无回执时 complete 失败；
- 有回执时 complete 成功；
- 旧图片上传路由已移除；
- Rustus hook 的最小权威行为；
- 公网地址推导。

允许下沉子模块：

- `rustus_hook.rs`
- `公网地址推导.rs`

不负责：

- 消息创建后如何被引用；
- 分发 locator/torrent 的长期可达性；
- 房间历史与阅读恢复。

原因：

- 这里的核心真相是“附件如何从 prepared 变成 ready”；
- 上传运输层和消息成立层要分开，避免测试组织反向把两个能力揉回一起。

### 5.4 `协作分发测试.rs`

负责：

- ready 附件落协作分发元数据；
- 相同内容共享 swarm；
- locator 返回形状；
- torrent 元信息稳定性；
- presence 上报影响的裁决；
- web seed 过期后的状态判断；
- 原图内容 Range 读取。

不负责：

- 上传主链的 prepare / complete；
- 房间 snapshot / history / events；
- 后台统计与静态壳资源。

原因：

- 这组关注的是“ready 之后的分发层行为”；
- 协作分发不是消息成立真相，不应与上传运输或房间接口纠缠在一起。

### 5.5 `房间接口测试.rs`

负责：

- bootstrap / join；
- snapshot；
- events；
- history；
- 阅读推进。

允许下沉子模块：

- `快照.rs`
- `增量事件.rs`
- `历史分页.rs`
- `阅读推进.rs`

不负责：

- Rustus 上传与 hook；
- 协作分发运行态；
- 后台接口；
- 静态壳缓存；
- 优雅停机。

原因：

- 这组测试的是房间对外接口契约；
- 核心边界是“成员能看到什么、能推进到哪里、历史怎么回放”，不是媒体运输或后台治理。

### 5.6 `实时链路测试.rs`

负责：

- realtime 主链闭环；
- 控制面 kind；
- 幂等消息；
- 同房并发 / 不同房并发的事件位置与隔离。

不负责：

- HTTP 冷路径；
- 房间历史分页；
- 媒体上传；
- 后台与静态壳。

原因：

- 这组聚焦实时入口与顺序/幂等语义；
- 应避免被后台、静态资源或房间查询接口噪音稀释。

### 5.7 `后台与静态壳测试.rs`

负责：

- 后台登录与 overview / rooms / room detail；
- HTTP 冷路径闭环；
- accepted / rejected 结构化日志；
- 静态壳 `no-cache` 与 hashed 资源长缓存；
- media service worker 暴露；
- 非成员不能读取房间图片内容。

不负责：

- 房间历史/阅读推进；
- 媒体上传运输与 hook；
- 实时并发与事件位置。

原因：

- 这组更接近壳层入口与治理侧 contract；
- 和消息主链、媒体运输态不是一个层次。

## 6. `测试支撑` 的边界

`tests/测试支撑/` 必须坚持“小而专、可组合、可替换”的 Unix 哲学。

允许放入：

- HTTP JSON 请求助手；
- 二进制请求助手；
- multipart 请求助手；
- 环境变量备份/恢复；
- 端口等待；
- 日志采集上下文；
- 媒体 fixture 辅助；
- 通用断言壳。

禁止放入：

- “谁应成功 / 谁应失败”的业务判断；
- 附件/消息/房间的业务成立裁决；
- 把多个业务步骤串成高语义编排器；
- 为了图省事把整个房间/上传主链封成一个万能 `创建场景()`。

根本原因是：

- `测试支撑` 是工具层，不是业务层；
- 它可以帮助构造输入，但不能代替测试决定业务真相；
- 否则只是把业务复杂度从大测试文件挪进 helper，屎山并没有消失。

## 8. 迁移顺序

为避免一次大扫除把风险放大，迁移顺序固定如下：

### 第 1 步：`启动与迁移测试.rs`

原因：

- 最独立；
- 最能验证新的顶层能力文件模式是否成立；
- 先把系统级入口从旧热点剥离，能快速形成正反馈。

### 第 2 步：`后台与静态壳测试.rs`

原因：

- 与媒体上传、房间接口主链耦合较弱；
- 可以较低风险地验证 `测试支撑/http`、`测试支撑/日志` 的切分。

### 第 3 步：`房间接口测试.rs`

原因：

- 这是第二大热点，且天然适合按快照 / 增量 / 历史 / 阅读推进继续细分；
- 早拆能显著降低后续 `集成测试.rs` 的复杂度。

### 第 4 步：`媒体上传测试.rs`

原因：

- helper 最多、耦合最重；
- 等 `测试支撑` 形状先稳定后再动更稳。

### 第 5 步：`协作分发测试.rs` 与 `实时链路测试.rs`

原因：

- 两者都更接近专项热点；
- 抽走后旧文件将接近见底。

### 第 6 步：`消息主链测试.rs`

原因：

- 它会复用媒体 fixture、房间前置数据与消息成立真相；
- 放在收尾阶段，能基于已稳定的支撑层和能力边界完成最后归位。

### 第 7 步：删除旧 `tests/集成测试.rs`

原因：

- 只要保留这个文件名，它就会继续成为“最方便的追加入口”；
- 删除旧入口是防回胖设计的一部分，不是纯清理动作。

## 9. 验证闭环

本次工作被定义为“结构重组”，不是业务重写。  
因此验证策略必须直接围绕“行为不变”来设计。

### 9.1 每一刀的局部验证

每迁完一个顶层能力文件：

1. 先跑该文件对应的集成测试；
2. 如果同步修改了 `测试支撑`，再补跑直接依赖它的相邻测试文件；
3. 只有局部通过后，才继续下一刀。

### 9.2 全量验证

所有迁移完成后，至少运行：

- 全量 Rust 测试；
- 需要时额外运行与拆分直接相关的特定筛选测试，确保命名过滤仍正常工作。

### 9.3 语义红线

如果拆分过程中出现以下情况，必须停下，不得继续把它伪装成“瘦身”：

- 需要修改 `src/` 中业务实现才能让测试过；
- 需要改变原测试断言语义；
- 需要把业务判断搬进 `测试支撑`；
- 需要为了目录好看而强行改测试层级边界。

一旦触发，说明工作已经从“结构重组”升级成“行为调整”，必须单独立项处理。

## 10. 防回胖软约束

这次不采用 CI 强卡，而是采用长期可执行的软约束。

### 10.1 新增集成测试先找能力归属

新增测试时，必须先回答它主要验证的是哪一类能力：

- 启动与迁移
- 消息主链
- 媒体上传
- 协作分发
- 房间接口
- 实时链路
- 后台与静态壳

默认只能先进入已有能力文件。  
只有确认现有能力边界都不匹配时，才允许新建新的顶层 `xxx测试.rs`。

### 10.2 `测试支撑` 不是万能收纳盒

任何 helper 想进入 `测试支撑`，都要先过一句判断：

> 它是在帮助构造输入，还是在偷偷替测试下业务结论？

如果是后者，禁止进入 `测试支撑`。

### 10.3 顶层能力文件必须写清楚“负责什么 / 不负责什么”

每个 `xxx测试.rs` 文件头都应写两段：

1. 负责的能力范围；
2. 明确不负责的能力范围。

这样后续 review 时，判断标准是“有没有越界”，不是“还能不能塞”。

### 10.4 热点先开子模块，不等再次变巨型

如果某个 `xxx测试.rs` 明显继续增长，应优先在其同名目录下拆子模块，而不是等它重新长成第二个 `集成测试.rs` 再救火。

### 10.5 不允许出现 `杂项测试.rs`、`其他测试.rs`、`临时测试.rs`

这类命名本质上是在恢复无边界入口。  
一旦允许存在，所有“今天先放这儿”的测试都会把系统重新拉回热点文件模式。

## 11. 这份设计怎样对应 DDD 与 Unix 哲学

### 11.1 DDD 角度

测试目录不直接决定领域模型，但它会反向塑造开发者对系统边界的理解。  
按能力域拆分的目的，是让测试入口也与业务边界一致：

- 媒体上传只关心附件从 `prepared` 到 `ready`；
- 消息主链只关心消息何时成立；
- 协作分发只关心 ready 之后的分发层行为；
- 房间接口只关心成员对 snapshot / events / history / 阅读推进的 contract。

这样测试组织不会反向鼓励跨边界实现。

### 11.2 Unix 哲学角度

`测试支撑` 应该像一组小工具：

- 能组合；
- 不承担多余语义；
- 能替换；
- 不伪装成业务引擎。

这和项目整体要求一致：

- 稳定的是业务边界与契约；
- 可替换的是入口、框架、支撑实现；
- 复杂度要收在小而专的组件里，而不是重新长成一团大胶水。

## 12. 实施完成的判定标准

只有同时满足以下条件，才算本设计落地完成：

1. `tests/集成测试.rs` 已删除；
2. 顶层能力测试文件已建立并能独立运行；
3. 热点能力已按需要落到子模块目录；
4. `tests/测试支撑/` 已收口通用支撑；
5. 没有出现新的“杂项测试”入口；
6. 全量 Rust 测试通过；
7. 拆分过程中没有引入业务语义改动；
8. 顶层能力文件头已写明边界与禁止事项。

## 13. 后续实现的注意事项

本设计只回答“怎么拆、为什么这样拆、怎样防回胖”，不等于自动允许在实现时顺手清理所有历史问题。  
实施阶段必须坚持：

1. 一次只迁一组能力；
2. 先移动，再验证；
3. 不把顺手想到的业务改造夹带进来；
4. 如果发现测试本身断言有问题，要单独标注，不混入本次结构瘦身。

换句话说：

- 本设计的目标是让测试结构更像一个有边界的系统；
- 不是借拆分名义去做一次无上限的大扫除。
