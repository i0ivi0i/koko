# 前端房间编排内核重构

日期：2026-04-07  
状态：设计已确认，待进入 implementation plan  
范围：`frontend` 的聊天房间、大厅搜索页、bootstrap、realtime 连接与滚动恢复逻辑  
约束：前端继续只做 `shell / presenter / orchestration`，不承载后端领域真相

## -1. 总原则

这次前端重构必须服从整个项目的总架构原则：

**整个项目只允许存在唯一的 DDD 领域真相。**

这句话在当前任务里的具体含义是：

1. 真正稳定的只有业务语义、领域规则、共享契约、事件语义和错误语义。
2. 前端、后端、协议、框架、库、语言，都只是可替换的壳和适配层。
3. 前端也必须遵守 DDD 分层，但它拥有的是壳层编排职责，不拥有后端领域真相。
4. 以后无论前端从 Lit 换成别的框架，还是后端 Rust 内部实现继续演进，只要唯一领域真相和共享契约稳定，业务功能都不应被破坏。
5. 新增、删除、修改功能应像搭乐高积木一样沿着稳定边界演进，而不是靠“顺手改一坨”生效。

因此，这次文档中的“房间内核”必须始终理解为：

**前端同步编排内核，不是领域内核。**

## 0. 一句话结论

这次重构的目标，不是把前端拆成很多文件，而是把“容易被 UI 改坏的会话编排逻辑”从 [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 身上剥下来，收进稳定、可测试、可替换的前端编排内核里。

最终结果应满足：

1. 以后改主题、换布局、换交互皮肤，主要只改壳层和展示层。
2. 刷新恢复、realtime 订阅、补洞重拉、软离房、已读推进不再跟着 UI 反复崩。
3. 前端仍然不裁决成员资格、权限、消息成立、治理语义。

## 1. 背景与问题

当前前端房间逻辑虽然方向上已经守住了不少 DDD 边界，但主要风险仍集中在一个事实：

[frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 同时承载了以下职责：

1. bootstrap 与会话恢复
2. 大厅与房间视图切换
3. 房间快照建立
4. socket 订阅、重连与控制面错误处理
5. 首屏未读定位
6. 历史分页
7. 已读锚点采样与推进
8. 乐观消息与权威消息合流
9. 最终模板渲染

这种“超级壳组件”形态虽然短期能跑，但长期会产生两个直接后果：

1. UI 改版很容易顺手碰坏恢复链、滚动链和已读链。
2. 逻辑正确性越来越依赖组件集成行为，而不是独立、稳定、可推演的应用层。

这不符合项目的 DDD 约束，也不符合“前后端完美解耦、多壳共核”的演进方向。

## 2. 设计目标

### 2.1 必须达到

1. 房间会话编排逻辑从 UI 组件里独立出来。
2. 未来换主题、换视觉、换交互布局时，不需要重写房间恢复链。
3. 滚动、副作用、DOM 依赖与同步流程裁决分离。
4. 前端继续只消费共享契约、快照和事件，不自造领域真相。
5. 文件数量保持克制：最多新增 3 个 `.ts` 文件。

### 2.2 明确不做

1. 不把前端做成“领域内核”。
2. 不把成员资格、权限、消息成立真相搬到前端。
3. 不为追求“架构好看”制造文件海和目录海。
4. 不引入只为状态管理而状态管理的第二套私有轮子。

## 3. 外部最佳实践校准

这次设计不是闭门造车，而是对照官方与成熟 IM 设计习惯收敛出来的。

### 3.1 Socket.IO / socketioxide

`socket.io` 官方文档明确给出几条重要事实：

1. 默认保证消息顺序，但默认投递语义只有 `at most once`。  
   来源：[Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)
2. 断线恢复不是必然成功；即便启用 connection state recovery，应用层仍必须准备快照同步与补洞。  
   来源：[Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/)
3. `client -> server` 需要更稳投递时，可以使用 `retries` 与 `ackTimeout`。  
   来源：[Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/) 与 [Client options](https://socket.io/docs/v4/client-options/)
4. `server -> client` 的可靠恢复，官方建议依靠事件唯一 ID、持久化、客户端保存 offset、重连后补发缺失事件。  
   来源：[Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)
5. `socketioxide` 作为 Rust 服务端，沿用 Socket.IO 兼容语义，并提供 ack 提取器。  
   来源：[socketioxide docs.rs](https://docs.rs/socketioxide/latest/socketioxide/) 与 [AckSender](https://docs.rs/socketioxide/latest/socketioxide/extract/struct.AckSender.html)

因此前端架构必须接受一个现实：

**聊天室前端不是普通表单页，它必须自带“同步编排内核”，否则 UI 一改就会把断线、恢复、补洞、已读这些问题重新炸出来。**

### 3.2 Telegram / WhatsApp

Telegram 官方更新机制强调：

1. 客户端必须维护稳定同步锚点；
2. 一旦出现 gap，必须显式补差；
3. 启动恢复本身就是正式同步路径。  
来源：[Working with Updates](https://core.telegram.org/api/updates)

WhatsApp 官方公开资料强调：

1. 多设备体验不能把 UI 设备当唯一真相源；
2. 每个设备都要消费同步后的状态；
3. 同步与展示必须解耦。  
来源：[How WhatsApp enables multi-device capability](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)

这些资料共同指向一个结论：

**真正成熟的 IM 前端，不是“页面会画就行”，而是必须拥有稳定的同步编排层。**

## 4. 分层边界

本次重构后，前端内部仍然遵守项目既有 DDD 总边界：

### 4.1 后端继续负责

1. 成员资格真相
2. 权限真相
3. 消息是否成立
4. 房间阅读真相裁决
5. 首条未读语义

### 4.2 前端负责

1. bootstrap 与恢复编排

4. 何时软离房
5. 何时将滚动意图交给滚动器
6. 如何把状态派生成展示模型

1. 前端根据 UI 自己判定“是否还是成员”
2. 前端把 pending / ack / local optimistic 当成消息成立真相
3. 前端把某个页面流程倒灌进共享契约
4. 后端为了某个壳输出专属页面语义字段

## 6. 房间内核设计

### 6.1 定位

`房间内核.ts` 不是领域内核，而是 **前端同步编排内核**。

它只回答一个问题：

**当前这个前端壳，正处在什么同步阶段？**

### 6.2 技术方案

使用成熟状态机库 `xstate` 承载同步流程，原因是：

1. 当前问题本质是复杂流程管理，不是普通共享状态。
2. 状态机适合描述恢复、订阅、补洞、重连、离房这类有限状态转换。
3. 显式状态比大量布尔字段更稳定，也更利于测试和维护。

### 6.3 核心状态

`房间内核` 至少包含以下稳定状态：

1. `引导中`
2. `大厅中`
3. `入房中`
4. `恢复中`
5. `房间就绪`
6. `订阅中`
7. `在线会话中`
8. `重连中`
9. `可重试失败`
10. `已离房`

这些状态表达的是 **同步编排状态**，不是业务真相状态。

### 6.4 核心事件

状态机只接收同步事件，例如：

1. `BOOTSTRAP_SUCCEEDED`
2. `BOOTSTRAP_FAILED`
3. `JOIN_REQUESTED`
4. `SNAPSHOT_LOADED`
5. `SNAPSHOT_LOAD_FAILED`
6. `SUBSCRIBE_SUCCEEDED`
7. `SUBSCRIBE_REJECTED`
8. `SNAPSHOT_RELOAD_REQUIRED`
9. `SOCKET_DISCONNECTED`
10. `SESSION_INVALIDATED`
11. `RETRY_REQUESTED`
12. `SOFT_LEAVE_REQUESTED`
13. `READ_ANCHOR_SAMPLED`
14. `HISTORY_TOP_REACHED`

### 6.5 上下文允许承载的内容

允许：

1. `sessionId`
2. `displayAlias`
3. `roomId`
4. `roomCode`
5. `latestEventPosition`
6. `lastReadEventPosition`
7. `firstUnreadEventPosition`
8. `messages`
9. `recoveryErrorCode`

禁止：

1. 成员资格真相
2. 权限真相
3. 消息成立真相
4. 房间治理语义

## 7. 房间滚动器设计

### 7.1 定位

`房间滚动器.ts` 是 Lit Reactive Controller。

它只负责 **DOM 滚动副作用**，不负责业务真相，不负责 HTTP / socket 编排。

### 7.2 负责的事情

1. 首屏未读定位
2. 无未读时落到最新消息附近
3. 历史前插补偿
4. 隔离程序性滚动产生的后续 scroll
5. 识别用户真正开始滚动的时机
6. 采样视口中的真实已读锚点
7. 触发“顶部需要加载更早历史”的信号

### 7.3 不负责的事情

1. 不直接请求 HTTP
2. 不直接连接 socket
3. 不裁决任何业务语义
4. 不自己修改核心同步状态

### 7.4 与房间内核的通信方式

只通过稳定意图 / 事件通信，不直接互改内部状态。

内核 -> 滚动器：

1. `settle_first_unread`
2. `settle_to_latest`
3. `preserve_after_history_prepend`

滚动器 -> 内核：

1. `INITIAL_SCROLL_SETTLED`
2. `USER_SCROLL_INTENT_STARTED`
3. `READ_ANCHOR_SAMPLED`
4. `HISTORY_TOP_REACHED`

## 10. 测试重建

### 10.1 测试分层

1. `房间内核` 纯状态机测试  
   验证事件序列、状态迁移、上下文变化。
2. `房间滚动器` DOM 行为测试  
   验证首屏定位、程序滚动隔离、历史补偿、已读采样。
3. `聊天壳` 轻量渲染测试  
   验证“什么同步状态显示什么界面”。
4. 少量真实链路测试  
   验证 socket + snapshot + 补洞 + 软离房主链。

### 10.2 长期守门用例

至少要稳定覆盖：

1. 刷新恢复时不会先闪大厅
2. 刷新恢复时不会跳到最早消息
3. 没有未读时首屏落在较新消息附近
4. 软离房后回到大厅但不退群
5. 软离房后旧房间 realtime 不再灌入当前壳
6. `need_snapshot_reload` 后能正确回退快照
7. 用户未手动滚动前不会误推进已读
8. 上滑补历史后视口不会突然跳变

### 10.3 验收原则

以后若只是纯主题、纯布局、纯视觉改动，不应需要改动：

1. `房间内核` 的状态机正确性测试
2. `房间滚动器` 的核心行为测试
3. 真实链路测试的同步语义断言

如果改 UI 需要同步重写这些测试，说明架构边界已经退化。

## 11. 迁移策略

本次重构按低风险渐进迁移：

1. 先引入 `xstate` 与前端编排类型
2. 先抽出 `存储.ts`，收口本地持久化
3. 再抽 `房间内核.ts`，先接管 bootstrap / restore / subscribe / soft-leave
4. 再抽 `房间滚动器.ts`，接管首屏定位、历史分页、已读采样
5. 最后让 `聊天壳.ts` 退回渲染壳

迁移期间要保证每一步都能独立转绿，不搞一口气掀桌式改写。

---

## 12. 预期结果

重构完成后，前端应达到以下状态：

1. 会话编排逻辑稳定存在于独立模块中
2. UI 皮肤与会话逻辑解耦
3. 房间滚动和阅读行为不再绑死在组件模板里
4. 前端继续不裁决任何后端领域真相
5. 未来再做 Telegram 风、深空风、其它主题时，不需要重写恢复主链

一句话总结：

**前端以后可以频繁换脸，但不能再频繁换脑。**
