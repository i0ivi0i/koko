# 前端首页群列表与双态控制台设计

日期：2026-04-08  
状态：设计已确认，待进入 implementation plan  
范围：前端聊天主壳首页体验重构、首页群列表、本地历史房间条目、固定底部双态控制台、相关测试与验收口径  
约束：不改 Rust 后端契约，不改领域真相，不伪造未读和最近消息，不把首页和房间页拆成两套壳

## -1. 总原则

这次设计不是“给首页加一个列表”，而是把当前前端产品形态从“网页式搜索页 + 房间页”收成更完整的 IM 应用体验。

必须长期守住这几条原则：

1. 整个聊天前端仍然只有一个主壳，用户一直处在同一个应用空间里。
2. 主舞台负责切换“首页群列表”与“房间消息流”，底部控制台始终固定贴底。
3. 底部控制台是同一个组件语义，不是首页一套、房间内一套长得像的假统一。
4. 首页群列表当前只展示前端本地历史房间，不伪造后端尚未提供的会话真相。
5. 点击历史房间直接进房；底部控制台负责输入新房间号进入房间。
6. 进入房间后，底部控制台不跳、不消失、不换位置，只把语义从“进房”切到“发消息”。
7. 返回首页时，也不是“跳回另一个页面”，而是主舞台从消息流退回群列表，底部控制台切回进房态。

一句话定性：

**这次不是做一个“首页功能”，而是把整个前端重构成“同壳双态的 IM 应用空间”。**

---

## 0. 一句话结论

当前前端 [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 的大方向是对的：只有一个聊天主壳，房间实时链路、恢复链路、滚动链路都已经收在这里。

但它当前的产品形态还停留在“先看到进房页，进房后再看到房间页”的网页式切换：

1. 默认主舞台是单独的进房页；
2. 进房输入框只属于这个进房页；
3. 房间输入框只属于房间页；
4. 两个输入区虽然现在都支持回车，但仍然是两套场景、两套布局语义。

这会带来两个问题：

1. 用户感知上像在两个页面之间跳，不像在一个完整应用里连续操作；
2. 首页缺少“我来过哪些房间”的会话感，应用完成度不够高。

本次设计要把它收成一个更完整的 IM 体验：

1. 默认先看到群列表首页；
2. 底部永远存在一块稳定的“控制台”；
3. 首页时控制台负责“输入房间号 + 进房”；
4. 进房后控制台无声切成“输入消息 + 发送”；
5. 首页群列表先由本地历史房间驱动，但结构上按未来真实会话列表预留边界。

## 1. 当前现状与真实问题

### 1.1 当前主壳真实结构

当前 [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 的关键结构是：

1. 启动时先 bootstrap 匿名身份；
2. 如果当前没有 `roomId`，主舞台渲染 `joinView`；
3. 一旦 `roomId` 成立，主舞台切成 `roomView`；
4. 房间内的消息输入条只存在于 `roomView` 里。

这说明当前系统已经具备“一个壳里切换两种主舞台”的基础，只是默认舞台还是“单独进房页”，不是“会话首页”。

### 1.2 当前本地存储的真实能力

当前 [frontend/存储.ts](/E:/koko/frontend/存储.ts) 已经具备这些本地记忆能力：

1. 设备匿名凭证；
2. 当前房间标识；
3. 当前房间短码。

这说明本地存储边界已经存在，不需要为了首页群列表重造一套存储体系。

但当前它还没有：

1. 历史房间列表；
2. 最近进入时间；
3. 供首页群列表消费的会话条目模型。

### 1.3 当前返回语义

当前 `leaveCurrentRoomView()` 的语义是“软离房、回到搜索页”，不是退群。

这是个好基础，因为我们要保留这个业务语义，只把“搜索页”升级成“首页群列表 + 固定控制台”的应用首页。

### 1.4 当前真正的问题，不是技术，而是产品叙事断裂

现在的问题不是“不能进房”或“不能发消息”，而是：

1. 首页不像一个 IM 首页；
2. 进房动作像网页跳转，而不是进入同一应用空间里的某个会话；
3. 底部输入区不够像一个始终在场的控制台；
4. 用户已经进过哪些房间，没有被应用记住并表达出来。

所以这次设计主攻的是：

**同一应用空间里的连续体验。**

## 2. 设计目标

### 2.1 主目标

本次设计必须同时达成这几件事：

1. 默认启动后显示首页群列表，而不是单独进房页；
2. 底部始终有固定控制台，位置稳定；
3. 首页时控制台承担“进房”职责；
4. 房间内时控制台承担“发消息”职责；
5. 点击历史群条目可直接进房；
6. 用户会感觉自己始终在同一个应用里，而不是跳进跳出不同页面。

### 2.2 次目标

1. 先把 Telegram 式首页形态做对；
2. 不依赖后端先提供会话列表接口；
3. 让未来接真实会话列表时不需要推翻当前 UI 结构；
4. 控制台语义切换后继续沿用当前已经存在的 Enter/submit 提交链路。

### 2.3 非目标

本次明确不做：

1. 不改 Rust 后端接口；
2. 不新增会话列表 HTTP/RT 契约；
3. 不伪造最近一条消息摘要；
4. 不伪造未读数；
5. 不做真正 Telegram 那种多会话同步体系；
6. 不顺手重写现有房间滚动、恢复、已读锚点逻辑；
7. 不拆出第二个首页壳或第二个页面入口。

## 3. 目标体验

### 3.1 用户看到的整体空间

整个应用只有一个大壳，分成两部分：

1. 上半部是主舞台；
2. 下半部是固定控制台。

主舞台负责显示当前上下文：

1. 首页时显示群列表；
2. 进房后显示消息流。

底部控制台永远在同一个位置，不跳、不抽离、不塌陷。

### 3.2 首页态

首页态的用户感知应该是：

1. 我打开的是一个聊天应用；
2. 上面是我来过的群列表；
3. 下面是一块可以直接输入房间号进新群的控制台。

首页不是“未连接聊天室”，也不是“搜索页”，而是：

**会话首页。**

### 3.3 房间态

进房后用户感知应该是：

1. 我没有离开这个应用空间；
2. 只是上面的主舞台从群列表换成了消息流；
3. 下面那块控制台还在原地；
4. 但它已经无声切成发消息的控制台。

### 3.4 返回首页

从房间返回首页时，体验也必须连续：

1. 主舞台从消息流退回群列表；
2. 控制台位置保持不动；
3. 控制台语义切回“输入房间号 + 进房”；
4. 用户感觉是在同一台设备上回到了总览，而不是“退出了另一个页面”。

## 4. 结构设计

### 4.1 同壳双态

本次采用 `同壳双态`，不采用“两页伪同构”。

也就是说：

1. [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 继续作为唯一主壳；
2. 主壳内部只增加首页主舞台分支；
3. 房间主舞台继续复用现有房间视图结构；
4. 底部控制台提升为壳级公共区域。

### 4.2 主舞台分区

主舞台需要明确分成两个状态：

1. `home`：群列表首页
2. `room`：房间消息流

这里的 `home/room` 只是前端壳层展示状态，不是后端领域状态。

### 4.3 控制台分区

控制台也明确分成两个模式：

1. `join` 模式
2. `message` 模式

它们不是两套独立组件，而是同一个控制台组件的两种职责。

---

## 5. 页面骨架

### 5.1 首页骨架

首页骨架应为：

1. 顶部轻量品牌/身份区
2. 中间主舞台群列表
3. 底部固定控制台

群列表是首页主角，控制台是底部操作核。

### 5.2 房间骨架

房间骨架应为：

1. 顶部房间头部
2. 中间消息流
3. 底部固定控制台

这与首页共享同一套底部结构，只是主舞台内容不同。

### 5.3 视觉语言要求

必须强调“飞船控制台一样稳”的感受：

1. 控制台是整个界面里最稳定的一块；
2. 它的高度、贴底方式、横向边距、输入框与按钮关系都保持连续；
3. 首页切房间时，不允许底部块突然消失再重新生成一个相似组件；
4. 视觉上可以有文案和 placeholder 的切换，但空间锚点必须稳定。

---

## 6. 首页群列表设计

### 6.1 当前数据来源

这次首页群列表的数据来源先限定为：

**本地历史进入过的房间。**

它们属于前端壳层自己的体验记忆，不是后端领域真相。

### 6.2 当前列表项最小字段

这次每条房间历史记录至少应包含：

1. `roomId`
2. `roomCode`
3. `lastEnteredAt`

如果当前能稳定得到更多可信字段，可以追加；拿不到就不要编。

### 6.3 当前不显示的东西

这次明确不显示：

1. 假未读数
2. 假最近消息
3. 假在线状态
4. 假成员数

拿不到权威来源时，宁可列表更克制，也不要制造“像是真的”假信号。

### 6.4 列表行为

首页群列表的交互要明确：

1. 点击条目，直接进房；
2. 不需要再把房间号回填到底部控制台等待二次确认；
3. 进入成功后，该房间历史记录应更新为最近进入；
4. 列表排序应优先按最近进入时间倒序。

### 6.5 为未来真实会话列表预留边界

虽然这次先用本地历史驱动，但不能把结构写死成“只会渲染字符串数组”。

因此需要提前定义壳层展示模型，例如：

1. `会话列表项`
2. `列表展示标题`
3. `辅助信息`
4. `最近进入时间`

这样未来接后端真实会话列表时，只是替换数据来源，不需要推翻首页 UI 结构。

## 7. 控制台设计

### 7.1 控制台的本质

控制台不是一个“输入框区域”，而是整个应用的稳定操作锚点。

它必须满足：

1. 固定贴底；
2. 始终存在；
3. 只切语义，不切位置；
4. 始终保留当前应用最主要的输入动作。

### 7.2 首页控制台

首页控制台的职责是：

1. 输入房间号；
2. 提交进房；
3. 支持按钮点击；
4. 支持 Enter / 手机输入法回车。

表现为：

1. 房间号输入框
2. 进房按钮
3. 与群聊态同一套空间骨架

### 7.3 房间控制台

房间控制台的职责是：

1. 输入消息；
2. 发送消息；
3. 支持按钮点击；
4. 支持 Enter / 手机输入法回车。

表现为：

1. 消息输入框
2. 发送按钮
3. 与首页态同一套空间骨架

### 7.4 切换原则

控制台切换时只允许变化：

1. 输入值来源
2. placeholder
3. `enterkeyhint`
4. 按钮文案
5. submit 目标动作

控制台切换时不允许变化：

1. 贴底位置
2. 主容器锚点
3. 基本尺寸体系
4. 布局骨架

## 8. 状态设计

### 8.1 壳层新增状态

这次前端壳层应该新增两类状态：

1. 首页主舞台所需状态
2. 房间历史列表所需状态

### 8.2 建议新增的壳层状态

建议新增但保持克制的壳层字段：

1. `homeSessionItems`
   含义：首页要展示的历史房间条目

2. `shellView`
   含义：当前主舞台是 `home` 还是 `room`

3. `consoleMode`
   含义：控制台当前是 `join` 还是 `message`

其中 `shellView` 和 `consoleMode` 虽然可以由 `roomId` 推导，但为了避免 render 里到处散写条件，允许收成清楚的壳层派生语义，只要不和 `roomId` 形成第二真相。

### 8.3 禁止的状态漂移

这次不能出现以下坏味道：

1. 首页一套输入状态、房间页一套控制台状态，彼此复制；
2. `roomId` 为空但控制台仍然处于 message 态；
3. 房间历史列表和当前房间短码缓存各自维护两套标题真相；
4. 点击历史房间时又临时绕过现有 `joinRoom()` / `enterRoomFromSnapshot()` 主链。

## 9. 存储设计

### 9.1 当前存储边界继续保留

[frontend/存储.ts](/E:/koko/frontend/存储.ts) 目前只承载壳层本地记忆，这个边界必须继续保留。

这次新增“历史房间列表”也仍然属于壳层本地记忆，不属于后端领域真相，所以可以继续放在这个端口里。

### 9.2 新增本地存储能力

建议在现有存储端口上新增：

1. 读取历史房间列表
2. 写入或更新某个历史房间条目
3. 删除无效历史房间条目（如硬失败房间）

### 9.3 更新时机

历史房间条目更新时机必须明确：

1. 成功进房后写入/刷新该房间记录；
2. 点击历史房间直接进房成功后，也刷新最近进入时间；
3. 硬失败且房间不存在时，可以清掉该条无效记录；
4. 软离房返回首页时，不删除历史记录。

### 9.4 排序语义

历史房间列表默认按 `lastEnteredAt` 倒序，越最近越靠前。

## 10. 交互设计

### 10.1 首页进入路径

首页存在两条进房路径：

1. 点击历史房间条目直接进房；
2. 在控制台输入房间号后进房。

两条路径最终都必须汇入同一条权威进房主链：

1. 调用既有 `joinRoom()`；
2. 消费后端返回的房间快照；
3. 经由 `enterRoomFromSnapshot()` 进入房间基线。

### 10.2 进房成功后的切换

进房成功后必须发生这些动作：

1. 主舞台从首页切到房间；
2. 控制台从 join 态切到 message 态；
3. 当前房间标识与展示短码写入本地存储；
4. 历史房间列表更新最近进入时间。

### 10.3 返回首页

从房间返回首页时必须发生：

1. 保留会话身份；
2. 软离开当前房间视图；
3. 主舞台切回首页群列表；
4. 控制台切回 join 态；
5. 已经写入的历史房间列表继续保留。

### 10.4 房间硬失败

若房间不存在或成员资格失效导致当前房间硬失败：

1. 仍然退出房间视图；
2. 返回首页；
3. 如该历史条目已失效，可移出历史列表；
4. 不能把错误态伪装成一个仍然可点击的正常群条目。

## 11. 文案与语义

### 11.1 首页文案

首页文案应该强调：

1. 这是群聊首页；
2. 这里陈列你来过的房间；
3. 底部控制台可以输入新的房间号进入。

不要继续沿用“搜索页”“进入群聊房间”这种过于网页表单化、一次性动作感太强的命名。

### 11.2 房间态文案

房间态文案继续服务聊天本身，不要把首页语义残留在房间控制台里。

### 11.3 命名边界

实现中命名也要跟着设计一起纠正：

1. 尽量少再叫 `joinView`
2. 尽量改成更接近 `homeView` / `homeStage`
3. 控制台相关命名应体现它是壳级公共区域，而非房间内专属 composer

---

## 12. 视觉完成度要求

这次设计虽然先不在 spec 里钉死每个像素，但必须明确视觉方向：

1. 首页群列表是主角，不是进房表单附属品；
2. 底部控制台是稳定、沉着、可信赖的操作锚点；
3. 进入房间后的视觉感受是“舞台切换”，不是“重新打开新页面”；
4. 首页与房间页共享同一套应用视觉语言。

一句大白话：

**上面可以变，下面不能飘。**

---

## 13. 风险边界与禁止事项

### 13.1 这次禁止做的事

1. 禁止为了首页列表新增后端接口；
2. 禁止把首页和房间拆成两个独立壳；
3. 禁止额外创造“首页专用进房流程”绕过现有进房主链；
4. 禁止伪造未读、最近消息、在线状态；
5. 禁止把本地历史列表当成真实会话真相；
6. 禁止顺手把房间恢复、实时订阅、滚动逻辑大改一遍。

### 13.2 最容易发生的漂移

最容易出现的漂移是：

1. UI 看起来做成了 Telegram 首页，但代码结构还是“旧 joinView 上面堆个列表”
2. 控制台看起来差不多，但实际上首页和房间是两套组件
3. 列表为了好看开始乱编假消息摘要
4. 点击历史房间走了快捷旁路，结果和正常进房链路出现行为分叉

这几个点必须在实现阶段重点防住。

## 14. 测试与验收

### 14.1 验收标准

这次完成后，必须满足：

1. 启动默认看到首页群列表；
2. 底部控制台始终固定存在；
3. 首页时控制台是“房间号输入 + 进房按钮”；
4. 房间内时控制台是“消息输入 + 发送按钮”；
5. 点击历史房间可直接进房；
6. 输入房间号 submit 可进房；
7. 进入房间后主舞台切到消息流；
8. 返回首页后主舞台切回群列表；
9. 历史房间列表会随着真实进房更新；
10. 没有出现伪造的未读或最近消息。

### 14.2 最低测试覆盖

至少应补这些前端测试：

1. 默认启动渲染首页群列表；
2. 本地历史房间列表恢复与展示；
3. 点击历史房间直接进房；
4. 首页控制台 submit 进房；
5. 房间控制台 submit 发消息；
6. 返回首页后控制台语义切回进房态；
7. 成功进房后历史记录更新；
8. 硬失败房间的历史条目处理。

### 14.3 验证重点

验证时不能只看“页面能不能切换”，还要看：

1. 控制台位置是否真的稳定；
2. 点击历史房间和手动输入房间号是否走同一条进房主链；
3. 首页列表是否真的来自本地历史，而不是临时造的渲染假数据；
4. 返回首页是否仍保留应用连续感。

## 15. 实施建议

实现时建议按这个顺序做，防止漂移：

1. 先补壳层测试，证明默认首页态和控制台双态行为；
2. 再扩展本地存储端口，加入历史房间列表；
3. 再实现首页群列表展示模型；
4. 再把当前 `joinView` 重构为首页主舞台；
5. 最后把底部控制台提升为壳级公共区域并收口双态 submit。

这样做的好处是：

1. 每一步都能验证；
2. 不会一上来就把大壳 render 改得面目全非；
3. 出问题也容易定位到底是存储、列表、还是控制台双态。

---

## 16. 最终判断标准

如果这次实现是对的，用户会产生这样的感受：

1. 我打开的是一个完整聊天应用；
2. 首页像一个真正的会话首页；
3. 底部那块控制台始终是稳定的；
4. 进房不是“跳页面”，而是主舞台自然切换；
5. 这个应用开始有“产品完成度”，不再只是一个能进房聊天的网页壳。

如果做完后仍然让人感觉：

1. 首页只是旧进房页加了个列表；
2. 控制台只是看起来像，但本质还是两套东西；
3. 进房后像打开了另一页；

那就说明实现已经漂了，必须回头修正。
