# 接收者媒体极限秒开修复 Spec

> 目标：群内任一成员发送新图片或视频后，**接收者**在真实群聊链路中 500ms 内看到非黑丑媒体卡片，视频 1s 内开始自动播放。  
> 原则：正式媒体字节只走 WebTorrent whole-file swarm；禁止 HLS/DASH、CDN、range、原文件直链、静态预览或缓存旁路成为第二真相。  
> 本 spec 不是“美化黑卡”，而是重排底层代码逻辑，让接收者收到权威消息事件时，系统已经具备进入 WebTorrent 的因果链。

---

## 1. 背景与问题重述

当前体验是：群内发送新视频或图片后，接收者时间线先出现一个黑色、粗糙、没有确定感的占位卡片；随后视频要等一段时间才真正可见；自动播放又要再等一段时间才开始。这个体验破坏 IM 的“在场感”：用户不是感觉有人刚发来一个可看的媒体消息，而是在看一个网页组件慢慢补齐数据。

这不是单纯的视觉问题。黑卡只是症状，根因是接收者主链在语义上仍是串行的：

```text
发送者 complete 成功
  -> 发送 create_message
  -> 后端创建消息并广播 room_event
  -> 接收者收到“有附件的消息”
  -> 接收者再请求 locator
  -> 接收者才拿到 WebTorrent 入口线索和短票
  -> WebTorrent 才连接 tracker / peer discovery
  -> 播放器才尝试自动播放
```

在这条链路里，`room_event` 到达的时刻并不等价于“接收者已经可以进入媒体 swarm”。UI 只能先画空壳，后面再靠 locator、缓存、播放器重试慢慢补齐。这就是黑卡、晚出现、晚播放的真实来源。

旧优化方案把“发送者乐观渲染”放在优先级前面，但这对接收者体验没有本质帮助。对接收者来说，真正要解决的是：收到实时事件的瞬间，系统是否已经拥有足够的分发真相和运行时动作，能立即进入 WebTorrent，而不是等 UI 触发后再补救。

---

## 2. 成功标准

### 2.1 体验指标

真实双浏览器群聊烟测必须满足：

1. **接收者媒体卡片 500ms 内成形**  
   从接收者收到 `room_event` 到时间线出现非黑丑媒体卡片，耗时必须小于 500ms。卡片必须有真实宽高比例、稳定媒体状态和明确的加载表达，不允许黑块、空壳、跳动布局或让用户猜测系统状态。

2. **接收者视频 1s 内自动播放开始**  
   从接收者收到 `room_event` 到 inline autoplay 的视频首帧进入播放态，耗时必须小于 1s。这个指标以真实浏览器、真实 socket、真实 WebTorrent runtime 为准；单元测试只能证明局部逻辑，不能替代烟测。

3. **接收者不需要手动补救**  
   用户不应通过点击、刷新、重新进房间、重新滚动或等待重试按钮来触发媒体成形。实时事件进入应用运行时后，预热和补齐必须自动发生。

4. **纯 WebTorrent 主链不变**  
   正式媒体字节仍由 WebTorrent whole-file swarm 提供。`web_seed` 只作为受控冷备窗口，不是第二播放真相；任何静态直链、HLS/DASH、range/CDN 方案都不属于本 spec。

### 2.2 工程指标

1. 新消息的 `room_event.attachments[*].distribution_hint` 对 ready 图片和视频必须真实存在，不能只是序列化层支持。
2. 接收者收到含 `distribution_hint` 的事件后，WebTorrent 预热必须先于媒体卡片自动播解析启动。
3. 新媒体消息首次播放路径不能串行依赖“渲染卡片后再请求 locator 再启动 tracker”。完整 locator 可以并行刷新，但不能挡住预热。
4. 做种入口必须在消息广播前后形成强不变量：媒体消息广播出去时，后端强种子启动已被请求，且消息广播成功后有兜底确认，不允许只靠周期对账碰运气。
5. 所有关键链路必须有可观测事件，能定位每一段耗时：`room_event_received`、`media_hint_ingested`、`swarm_prewarm_ticket_fetching`、`swarm_prewarm_tracker_announcing`、`locator_refresh_started`、`swarm_peer_ready`、`inline_autoplay_started`。

## 3. 非目标与禁止事项

1. **不做乐观渲染作为主解法**  
   发送者本地乐观渲染可以以后单独优化，但它不能解决接收者体验。本 spec 不把“发送者自己看着快”当作成功。

2. **不做黑卡美化补丁**  
   可以改视觉表达，但视觉改动必须是底层状态机投影的结果。禁止只把黑块换成渐变、骨架屏或封面占位，然后继续让播放链路串行等待。

3. **不把 `join_ticket` 广播给全房间**  
   `join_ticket` 是接收者准入凭证，必须按当前会话签发。公共 `room_event` 只能带稳定、公开、可缓存的分发线索，如 `content_hash`、`swarm_id`、`torrent_info_hash`、`web_seed_until`。

4. **不让 UI 层拥有媒体分发真相**  
   时间线组件、卡片组件、播放器组件都只能表达状态和发出应用事件。它们不能自行决定附件是否可分发、不能自己拼 locator、不能自己发明重试节奏。

5. **不新增第二套媒体状态机**  
   移动端、PC 端、inline autoplay、viewer、全屏必须共享同一套媒体 owner 和 WebTorrent source owner。差异只允许在能力适配层表达。

6. **不手搓 tracker 或 Socket.IO-WebTorrent 桥**  
   `socketioxide` 负责业务事件快递；WebTorrent tracker/signaling 继续走裸 WebSocket tracker。禁止把 WebTorrent signaling 塞进 Socket.IO 协议层。

## 4. 根因分析

### 4.1 事件语义不够强

当前 `room_event` 的语义偏向“消息已创建，并且引用了若干附件”。这对文本消息足够，但对接收者媒体秒开不够。对媒体消息来说，接收者真正需要的是：

```text
消息已创建，并且每个 ready 媒体附件已经绑定可进入 WebTorrent 的稳定分发身份。
```

如果 `room_event` 只告诉接收者 `attachment_id/kind/width/height`，那接收者收到事件后还不知道：

- 这个附件对应哪个 `torrent_info_hash`；
- 应该进入哪个 `swarm_id`；
- 当前是否仍在 24 小时冷备/强 seed 窗口；
- 是否值得立即启动 peer discovery。

于是 UI 只能先画“一个附件卡片”，而不是“一个正在进入 swarm 的媒体卡片”。这就是语义断裂。

### 4.2 分发事实存在，但没有进入实时主链

代码现状显示：

- `src/外壳/协议响应.rs` 的 `attachments_to_json` 已经支持在 `分发线索: Some(...)` 时输出 `distribution_hint`。
- `src/实时/外壳.rs` 已经有 `room_event附件携带分发线索时输出distribution_hint` 测试，说明序列化表面已经打开。
- 但 `src/消息/适配.rs` 的附件快照装配路径仍大量写死 `分发线索: None`。
- `src/消息/应用.rs` 的 `创建消息_异步` 仍只通过 `批量查询附件快照` 获取消息成立所需的附件事实，没有确保事件投影带出分发线索。

因此现在不是“没有字段”，而是“真实事件没有吃到字段”。这类问题如果只在前端加缓存，会变成掩耳盗铃：缓存没有权威输入，只能继续等 HTTP locator。

### 4.3 接收者 WebTorrent runtime 启动太晚

当前自动播路径更像：

```text
消息进入时间线
  -> 卡片渲染
  -> IntersectionObserver 判定可见
  -> 自动播解析播放结果
  -> 获取 locator
  -> 解析协作分发源
  -> 确保协作分发会话
  -> tracker / peer discovery
```

这个顺序对普通懒加载媒体合理，但对 IM 新消息不够。新媒体消息到达时，接收者大概率正在底部，系统应该在事件进入应用运行时的瞬间预热，而不是等 DOM 可见性和播放器解析之后才开始连接 swarm。

### 4.4 做种就绪还不是消息发布不变量

`complete_media_upload` 成功后会 fire-and-forget 触发 sidecar 做种，这是比阻塞 complete 更好的方向。但对接收者极限秒开来说还不够：

- fire-and-forget 只表示“请求已经发起”，不表示 tracker 已经能发现后端强种子；
- 接收者可能在 sidecar 注册完成前进入 swarm；
- 周期对账能补偿长期一致性，但不能保证 1s 首播体验。

因此 spec 必须把“媒体消息广播时强种子已被启动/可兜底确认”写成发布链路不变量，而不是留给后台对账兜底。

## 5. 目标模型

### 5.1 领域语言

本 spec 统一使用以下概念，避免执行时漂移：

- **媒体消息**：引用一个或多个 ready 图片/视频附件的消息。
- **可分发附件**：ready 且已绑定 `content_hash / swarm_id / torrent_info_hash / web_seed_until` 的媒体附件。
- **分发线索（distribution_hint）**：可公开广播、稳定可缓存、足以让接收者提前进入 WebTorrent 预热的分发身份。不包含准入票据和受控 URL。
- **准入票据（join_ticket）**：按接收者会话签发、短 TTL、用于 tracker 首帧门禁的凭证。
- **预热会话**：不占用播放器、不下载正式播放字节、先并行取得当前会话的入场凭证，再提前建立 tracker/peer discovery 的 WebTorrent runtime 会话。
- **正式播放会话**：播放器需要 source 时接管或复用预热会话，开始真实媒体读取。
- **后端强种子**：服务器 sidecar 在 24 小时冷备窗口内参与 swarm，保证新媒体刚发出时有稳定源。

### 5.2 新的不变量

1. **媒体消息不得广播半成品附件**  
   对 ready 图片/视频附件，消息事件投影必须能拿到分发线索。若分发线索缺失，说明 complete 主链或复用主链没有闭环，应拒绝创建媒体消息或返回系统错误，而不是广播一个无法秒开的半成品。

2. **公共事件只带公共事实**  
   `room_event` 可以广播 `distribution_hint`，因为它不包含会话专属权限；不能广播 `join_ticket`、`web_seed_url`、`presence_url`。

3. **接收者入场凭证按会话补齐**  
   接收者收到 `distribution_hint` 后，由媒体 runtime 立即并行刷新完整 locator 或请求专门的入场凭证接口。这个动作属于当前会话壳层，不属于公共消息事件。

4. **预热先于 UI 播放裁决**  
   `RealtimeActor` 将 `room_event` 交给 `RoomTimelineActor` 的同时，必须把附件分发线索交给 `MediaDistributionRuntime`。预热不能藏在卡片组件或播放器组件里。

5. **卡片只表达真实状态**  
   卡片可显示“连接群友中/准备播放/正在获取入场凭证”等状态，但这些状态必须来自媒体 runtime，不允许组件本地发明 loading 状态。

6. **做种启动与广播同链路可观测**  
   消息广播前应尽量确认强种子 start 已发起；广播成功后必须触发一次幂等的强种子确认。失败要进入结构化日志和可观测指标，而不是静默等待周期任务。

## 6. 目标时序

```text
发送者 complete_media_upload
  -> 生成 canonical 内容、torrent、distribution metadata
  -> 写入 ready 附件 + 分发元数据 + torrent 元信息
  -> 触发后端强种子 start（幂等）
  -> 返回 ready 媒体资产

发送者 create_message
  -> 校验会话、房间、成员、附件 owner
  -> 批量读取附件快照 + 分发线索
  -> 校验媒体附件均为可分发附件
  -> 提交消息事件
  -> 广播 room_event（携带 distribution_hint）
  -> 广播成功后幂等确认强种子 start

接收者 socketioxide 收到 room_event
  -> RealtimeActor 记录 room_event_received
  -> RoomTimelineActor 接收权威消息事实
  -> MediaDistributionRuntime 接收 distribution_hint
  -> 立即创建/复用预热状态机
  -> 立即并行刷新 locator / join_ticket
  -> 凭证返回后立刻 tracker announce / peer discovery
  -> 卡片以真实比例和 runtime 状态投影到时间线
  -> 自动播触发时接管已热 swarm
  -> 1s 内进入播放态
```

这条链路的关键不是“多做一个缓存”，而是把 WebTorrent 入场动作从“UI 需要播放时才做”前移到“权威媒体消息事件到达时就做”。

## 7. 后端设计

### 7.1 `message/application`：保持消息成立真相纯净

`message/application` 仍只负责：

- 会话是否有效；
- 房间是否存在；
- 当前会话是否是成员；
- 附件是否属于发送者匿名身份；
- 文本与附件组合是否符合统一消息规则；
- 消息事件是否提交成功。

它不负责签发 `join_ticket`，不负责构造播放 URL，不负责 tracker 连接，不负责 UI 状态。

但对媒体消息，它必须依赖仓储端口拿到“可分发附件快照”。这里不是把分发逻辑塞进领域层，而是把事件投影需要的稳定事实随附件快照一起读出。领域层仍不读取 `distribution_hint` 做业务校验；adapter/application 边界负责保证 ready 媒体附件不会被投影成半成品。

### 7.2 `Realtime消息仓储端口`：批量附件查询补齐分发线索

`批量查询附件快照` 的实现需要一次批量查询补齐：

- `attachments.attachment_id`
- `attachments.kind`
- `attachments.width`
- `attachments.height`
- `attachments.thumbnail_storage_key IS NOT NULL AS has_preview_asset`
- `attachment_distribution_metadata.content_hash`
- `attachment_distribution_metadata.swarm_id`
- `attachment_distribution_metadata.torrent_info_hash`
- `EXTRACT(EPOCH FROM attachment_distribution_metadata.web_seed_until)`

对 ready 图片/视频附件：

- 若分发元数据完整，构造 `附件分发线索`。
- 若分发元数据缺失或 `torrent_info_hash` 为空，返回系统错误或附件未就绪，不允许继续广播半成品媒体消息。

对非媒体附件或未来其他类型：

- 不强制分发线索。

### 7.3 `event_to_json`：只投影公共分发事实

`attachments_to_json` 当前已支持 `distribution_hint`，目标是保证真实输入不再是 `None`。输出仍必须排除：

- `join_ticket`
- `ticket_expires_at`
- `web_seed_url`
- `presence_url`
- 任何 session 维度 URL

公共 `distribution_hint` 结构固定为：

```json
{
  "content_hash": "<sha256-hex>",
  "swarm_id": "<stable-swarm-id>",
  "torrent_info_hash": "<bt-info-hash-hex>",
  "web_seed_until": 1715500000
}
```

### 7.4 `handle_realtime_create_message`：广播后强种子确认

消息创建成功后，广播 `room_event` 前后需要保证后端强种子不是“随缘”：

1. 创建消息返回的事件中若包含媒体附件分发线索，收集 `attachment_id / torrent_info_hash / swarm_id`。
2. 广播前不做长阻塞等待，但可以发起短路径幂等 start 确认，避免完全依赖 complete 阶段 fire-and-forget。
3. 广播成功后 `tokio::spawn` 触发一次幂等强种子确认。
4. 如果确认失败，记录结构化 warn，字段至少包括 `room_id`、`message_id`、`attachment_id`、`torrent_info_hash`、`seed_confirm_stage`。

这不是第二条做种主链，而是对 `complete` 强种子启动的同链路兜底，目的是消除“接收者先到 swarm、强种子还没注册”的竞态窗口。

## 8. 前端设计

### 8.1 `RealtimeActor`：实时事件进入应用协议

收到 `room_event` 后，socket 回调不能直接让 UI 卡片自己补救。正确顺序是：

1. 解析 `message_created`。
2. 把权威消息交给 `RoomTimelineActor`。
3. 从消息附件中提取 `distribution_hint`。
4. 对每个媒体附件发出应用事件：`MEDIA_DISTRIBUTION_HINT_RECEIVED`。
5. 记录 `room_event_received` 和 `media_hint_ingested` 时间点。

这个 actor 不启动播放器，不解析 DOM 可见性，只做实时事件到应用事件的翻译。

### 8.2 `MediaDistributionRuntime`：唯一预热 owner

新增或收口一个明确入口：

```text
预热媒体分发({ attachmentId, kind, width, height, distributionHint, roomId, messageId })
```

职责：

- 根据 `torrent_info_hash` 建立或复用预热状态机；
- 立刻并行刷新完整 locator 以获得当前会话的 `join_ticket`、`announce_urls`、`ice_servers`、`web_seed_url`；
- 在 `join_ticket` 返回前不向受控 tracker announce，避免伪造无票连接；
- locator 返回后立即补齐预热会话凭证，发起 tracker announce / peer discovery，并允许正式播放会话接管；
- 对同一 `attachmentId + sessionId` 去重，避免重复预热；
- 限制并发，优先处理最新、可见或即将可见的媒体消息。

它不负责：

- 渲染卡片；
- 决定消息是否存在；
- 控制播放器 UI；
- 发明媒体可用性业务真相。

### 8.3 Locator 刷新：并行而非阻塞

`distribution_hint` 足以让系统知道要进入哪个 swarm，但不能替代完整 locator：

- `join_ticket` 必须按接收者会话签发；
- `web_seed_url` 是受控冷备入口；
- `ice_servers` 可能来自运行期配置；
- `media_state` 仍由后端按当前时间、presence、删除状态裁决。

因此前端收到 hint 后必须立即启动预热状态机并并行刷新 locator。这里的“预热启动”不是无票连接 tracker，而是把当前附件推进到 `ticket_fetching` 状态、立刻请求当前会话凭证，并在凭证返回的同一链路里进入 tracker。新的逻辑是：

```text
hint 到达
  -> 立即创建预热状态机（知道 infoHash/swarmId）
  -> 同时请求 locator / join_ticket
  -> locator 返回后注入 ticket/announce/ice/web_seed
  -> 立即发起 tracker announce / peer discovery
  -> 自动播放接管同一会话
```

预热状态必须显式分层，避免执行时误写成表面缓存：

```text
hint_received
  -> ticket_fetching
  -> tracker_announcing
  -> peer_discovering
  -> peer_ready
  -> playable_claimed_by_autoplay
```

如果生产启用了 tracker 门禁，`tracker_announcing` 必须发生在 `ticket_fetching` 成功之后；如果未配置门禁，状态机仍走同一入口，只是凭证为空时直接进入 announce。这样可以保持开发、测试、生产行为同构。

### 8.4 媒体卡片：状态投影，不是补丁

卡片渲染要从“空黑块”变成“媒体运行态投影”：

- 立即使用 `width/height` 固定比例，避免布局跳动；
- 图片/视频都显示轻量、低干扰的准备态；
- 视频首帧未到前展示“正在连接群友”或等价状态，但不能大段说明；
- 状态来源必须来自媒体 runtime；
- 首帧或播放源就绪后自然替换，不闪烁、不重建整块 DOM；
- 不在卡片组件里直接请求 locator 或启动 WebTorrent。

这满足 `UIUX禁令.md` 的核心要求：用户在群聊现场里感到流连续，而不是在网页里等卡片加载。

### 8.5 自动播放：接管已热会话

自动播逻辑不再从零开始解析和连接 swarm。它应：

1. 查询 `MediaDistributionRuntime` 是否已有 `attachmentId` 的预热会话。
2. 若有，接管该会话作为正式播放源。
3. 若 locator 尚未返回，但 tracker/peer discovery 已启动，则等待短窗口补齐凭证。
4. 若没有预热会话，才走现有冷路径，并记录 `prewarm_missed`。

## 9. 测试策略（TDD）

### 9.1 后端 RED

新增或修改测试，先证明当前失败：

1. **创建媒体消息会带真实分发线索**  
   构造 ready 视频附件 + 完整 `attachment_distribution_metadata`，调用 `创建消息_异步`，断言返回事件附件中的 `分发线索` 为 `Some`，且 `torrent_info_hash` 正确。当前应失败，因为真实链路仍可能返回 `None`。

2. **ready 媒体缺失分发线索不得广播半成品**  
   构造 ready 视频附件但不写分发元数据，调用 `创建消息_异步`，断言返回错误而不是成功事件。当前若成功则失败。

3. **room_event 输出 distribution_hint**  
   已有序列化测试可保留，但要补一个真实 create_message 到 event_to_json 的端到端测试，而不是只手写 `分发线索: Some(...)`。

4. **广播成功后触发强种子确认**  
   用假 seeder control 或可观测 stub 验证含媒体附件消息广播成功后，会发起幂等 seed start 确认。失败路径必须有结构化日志或可断言的错误观测。

### 9.2 前端 RED

新增或修改测试，先证明当前失败：

1. **收到 room_event 会派发预热事件**  
   构造含 `distribution_hint` 的 `message_created`，注入 fake `MediaDistributionRuntime`，断言在消息进入时间线同一轮事件处理中调用 `预热媒体分发`。

2. **预热状态机先于自动播解析**  
   使用 fake clock / fake runtime，断言 `media_hint_ingested` 和 `swarm_prewarm_ticket_fetching` 发生在 `解析自动播播放结果` 之前。

3. **locator 刷新与预热状态机并行**  
   fake `loadMediaLocator` 延迟返回，断言预热状态机已经进入 `ticket_fetching`，但不会在无 `join_ticket` 时调用 tracker announce。

4. **自动播放接管预热会话**  
   构造已有预热会话，触发 inline autoplay，断言不创建第二个 WebTorrent 会话，而是接管已有会话。

5. **媒体卡片不黑丑**  
   渲染含 `distribution_hint` 但首帧未到的视频附件，断言卡片有真实比例、稳定状态文本/标记、无黑块 class 或黑色空占位。

### 9.3 真实烟测

必须用两个真实浏览器上下文：

1. A 进入房间，上传并发送视频。
2. B 已在同一房间底部等待。
3. B 记录：
   - `room_event_received_at`
   - `media_card_stable_at`
   - `swarm_prewarm_ticket_fetching_at`
   - `swarm_prewarm_tracker_announcing_at`
   - `locator_refresh_started_at`
   - `inline_autoplay_started_at`
4. 断言：
   - `media_card_stable_at - room_event_received_at < 500ms`
   - `inline_autoplay_started_at - room_event_received_at < 1000ms`
5. 同样覆盖图片：图片卡片 500ms 内稳定成形，不出现黑丑占位。

## 11. 分层边界检查

| 改动 | 层 | 允许原因 | 禁止漂移 |
|---|---|---|---|
| 附件快照补齐 `distribution_hint` | contract / adapter | 稳定共享事件表面，公共分发身份 | 不放 `join_ticket`、URL、UI 文案 |
| `批量查询附件快照` JOIN 分发表 | adapter | 一次 SQL 补齐事件投影事实 | 不把权限/成员治理塞进 SQL 外 |
| ready 媒体缺分发线索时拒绝半成品事件 | application 边界 | 防止权威事件语义变假 | 不让 domain 依赖 DB/tracker |
| 广播后强种子确认 | shell | 基础设施幂等兜底 | 不改变消息成立真相 |
| 收到 hint 后预热 | frontend shell/runtime | 壳层体验编排，先于 UI 投影 | 不让卡片组件拥有分发 owner |
| 自动播放接管预热会话 | frontend media runtime | 复用同一 WebTorrent owner | 不新增第二状态机 |
| 卡片状态表达 | UI shell | 表达 runtime 状态 | 不制造假 loading 真相 |

DDD 当前评分目标：10/10。  
评分依据：媒体消息事件语义、媒体分发事实、WebTorrent runtime owner、UI 投影边界明确；公共事实与会话凭证分离；基础设施强种子不反向污染领域模型。

## 12. 实施顺序

### Phase A：后端事件语义闭环

1. TDD：创建消息真实事件必须带 `distribution_hint`。
2. TDD：ready 媒体缺分发元数据不得广播半成品。
3. 实现 `批量查询附件快照` 补齐分发线索。
4. 保持 `event_to_json` 只投影公共 hint。
5. 加强种确认观测和广播后兜底。

完成后，接收者至少能在 `room_event` 到达时拿到进入 WebTorrent 的稳定身份。

### Phase B：前端预热主链

1. TDD：收到 `distribution_hint` 立即调用媒体预热入口。
2. 实现 `MEDIA_DISTRIBUTION_HINT_RECEIVED` 应用事件。
3. 在 `MediaDistributionRuntime` 建立预热状态机 owner。
4. locator / join_ticket 刷新与预热状态机并行，tracker announce 等凭证后立即发生。
5. 自动播放接管预热会话。

完成后，接收者不再等卡片可见后才开始 WebTorrent 冷启动。

### Phase C：媒体卡片状态投影

1. TDD：含 hint 的新媒体卡片不出现黑丑占位。
2. 用真实宽高比例固定布局。
3. 状态来自媒体 runtime。
4. 首帧/播放 ready 后无闪烁替换。

完成后，用户看到的是“正在进入媒体现场”的稳定卡片，而不是网页加载块。

### Phase D：真实烟测与收口

1. 双浏览器发送视频，验证 500ms/1s。
2. 双浏览器发送图片，验证 500ms 卡片稳定。
3. 检查不走 HLS/DASH/CDN/range/直链。
4. 检查日志能还原每段耗时。
5. 清理无效旧测试、旧补丁、死分支。

## 13. 风险与取舍

### 13.1 1s 自动播放不是只靠前端能保证

如果后端强种子没在 tracker 可见，前端再快也可能找不到 peer。因此 spec 把强种子确认纳入消息广播同链路，而不是只写前端预热。

### 13.2 不广播 `join_ticket` 会多一次受控请求

这是安全与边界必须付出的成本。解决方式不是把 ticket 塞进公共广播，而是让 locator / join_ticket 获取在 `room_event` 到达同一轮应用处理中立即开始，并让 tracker announce 在凭证返回后无 UI 阻塞地继续。本 spec 不新增逐连接私有 socket 事件；若真实烟测证明 HTTP locator 往返仍无法稳定满足 1s，再单独设计“逐连接 media_entry_ready 私有事件”，不能把它混进公共 `room_event`。

### 13.3 预热不能无限并发

万人群聊下大量媒体同时到达时，预热必须有预算。默认策略应优先：最新消息、当前房间、贴底视口、视频优先、最多少量并发。超过预算的附件保持可见状态，但不抢占热路径资源。

### 13.4 图片也要遵守 WebTorrent 主链

图片不能因为“小”就走静态直链当正式真相。图片卡片可以快速成形，但正式字节仍应走 WebTorrent 主链；冷备只作为受控窗口。

---

## 14. 完成定义

本 spec 完成不是“字段加了”或“卡片好看了”，而是以下事实同时成立：

1. 后端真实 `create_message` 事件对 ready 图片/视频附件带 `distribution_hint`。
2. ready 媒体缺失分发元数据不会生成半成品媒体消息事件。
3. 接收者收到 `room_event` 同一轮应用处理中启动 WebTorrent 预热。
4. locator/ticket 刷新与预热状态机并行；tracker announce 等凭证但不等 UI 自动播。
5. 自动播放复用预热会话，不重复创建冷 WebTorrent 会话。
6. 媒体卡片首屏没有黑丑空占位，布局稳定，状态明确。
7. 双浏览器真实烟测满足：卡片 < 500ms，视频 autoplay < 1s。
8. 没有引入第二媒体字节真相。
9. 新增观测能证明每段时序。
10. 相关测试按 RED -> GREEN -> REFACTOR 落地。

## 15. 后续不纳入本 spec 的优化

1. 发送者本地乐观渲染。
2. 前端 WASM 生成 torrent 并提前做种。
3. 多标签共享 WebTorrent 预热会话。
4. 更激进的后台 Service Worker 媒体协作。
5. 进一步压到 300ms 卡片和 700ms autoplay。

这些都可以成为后续优化，但不能替代本 spec 的底层因果链修复。
