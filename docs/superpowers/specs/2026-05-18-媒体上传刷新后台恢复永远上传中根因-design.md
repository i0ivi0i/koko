## 0. 官方资料前置校准

这次根因分析前先核对了相关官方资料，避免把恢复链路写成私有手搓轮子。

### 0.1 Uppy Golden Retriever

官方定位：

- Golden Retriever 保存 Uppy state 和用户选择文件，用于浏览器崩溃、误关标签页、刷新后的恢复。
- `localStorage` 只保存文件元数据和 Uppy state。
- `IndexedDB` 适合保存小文件，官方口径通常是 5 MiB 以下。
- 可选 `Service Worker` 可临时保存大文件引用，但不保证跨浏览器崩溃或重启持久存在。
- 恢复失败的文件会成为 ghost file，需要用户重新选择。

来源：<https://uppy.io/docs/golden-retriever/>

对 `koko` 的裁决：Golden Retriever 是“恢复证据来源”，不是“上传一定会继续”的产品承诺。没有 restored file 时，UI 不能继续显示 `上传中`。

### 0.2 Uppy Tus / tus 协议

官方定位：

- `@uppy/tus` 通过 `tus-js-client` 接入 tus。
- tus 核心恢复语义是：`HEAD` 读取 `Upload-Offset`，再用 `PATCH` 从 offset 继续。
- tus 服务端必须在 `HEAD` 响应里返回 `Upload-Offset`。
- `OPTIONS` 可以暴露 `Tus-Version`、`Tus-Extension`、`Tus-Max-Size`。
- `chunkSize` 默认是 `Infinity`，官方明确说除非被代理/服务端请求体限制或 stream source 逼迫，否则不要设置。
- `retryDelays` 默认 `[0, 1000, 3000, 5000]`。
- `onShouldRetry` / `onAfterResponse` 可用于 401 token refresh 或更精细重试。

来源：

- <https://uppy.io/docs/tus/>
- <https://tus.io/protocols/resumable-upload.html>
- <https://github.com/tus/tus-js-client/blob/main/docs/api.md>

对 `koko` 的裁决：断点续传不是“记住 UI 状态”，而是要能拿到 upload URL / fingerprint / offset / 文件源。恢复旧上传时不应长期持久化 Bearer header，而应由后端重新签发短期 transport 凭证。

### 0.3 Uppy uploader 选择建议

官方选择指南把 `@uppy/tus` 定位为可靠断点续传方案，尤其适合大文件、不稳定网络和避免从头重传；同时也提醒 tus 需要客户端与服务端一起实现。

来源：<https://uppy.io/docs/guides/choosing-uploader/>

对 `koko` 的裁决：继续复用 Uppy/Tus 的成熟恢复能力，不新增第二套私有 HTTP 上传协议；但 Tus 只能是上传 transport，不得篡位 WebTorrent 正式媒体主链。

### 0.4 WebTorrent 浏览器主链

官方资料确认：

- 浏览器端 WebTorrent 依赖 WebRTC。
- `client.createServer({ controller })` 依赖 Service Worker 给 `<video>/<audio>/<img>` 提供 torrent stream URL。
- `client.add()` / `client.seed()` 产生的是 runtime owner，需要显式管理 torrent 生命周期。
- 浏览器端要考虑 store、cache slots、seed outgoing connections、tracker/WebRTC 能力。

来源：<https://webtorrent.io/docs>

对 `koko` 的裁决：WebTorrent 是正式媒体分发和播放主链；刷新恢复必须恢复或重建 WebTorrent/torrent owner，不能用 Tus 上传成功替代 WebTorrent ready。

### 0.5 浏览器存储与 Cloudflare 边界

官方/平台资料要点：

- 浏览器存储按 origin 隔离，默认 best-effort，可能因配额或系统压力被驱逐；可用 Storage API 申请 persistent，但不能把它当绝对可靠磁盘。
- Cloudflare 请求体上限取决于账户套餐，Free / Pro 为 100 MB，Business 为 200 MB，Enterprise 默认 500 MB；超过会返回 413。

来源：

- <https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria>
- <https://developers.cloudflare.com/workers/writing-workers/resource-limits>

对 `koko` 的裁决：当前 `32 MiB` tus chunk 上限有部署边界依据；同时本地恢复数据必须按“可能被清理”设计，不能让 best-effort 存储承担业务成功语义。

## 1. 一句话结论

当前“刷新页面、切后台后媒体永远上传中”的根因不是 Uppy/Tus 单点失效，而是 `koko` 的媒体发送任务缺少一个可恢复的唯一 owner。

现有代码把 `transporting` 草稿持久化到 `localStorage`，恢复时又原样写回 UI；但刷新后实际上传 owner、`File`、Uppy 实例、上传器映射和大视频恢复能力都可能已经丢失。于是 UI 继续显示“上传中”，背后却没有任何活着的任务能推进到 `ready` 或 `failed`。

正确修复不是再加一个提示，也不是盲目依赖 Golden Retriever，而是建立媒体发送任务恢复状态机：

```text
页面恢复
  -> 先恢复/对账真实 owner
  -> owner 活着且文件可恢复：继续传输
  -> 后端已完成：升级 ready
  -> owner 不存在或文件不可恢复：失败可重试/需要重新选择
  -> 禁止停留在无 owner 的 uploading
```

## 2. 用户现象

公网群聊里，用户正在发图片、视频或附件。此时发生：

- 切换页面；
- 浏览器标签页挂后台；
- 手机/桌面休眠；
- 刷新页面；
- 页面被浏览器回收后重新进入。

回来后，媒体卡片一直显示“上传中”。它不会完成、不会失败、不会自动重试，也没有明确的重新选择入口。

这对 IM 产品是硬伤：用户不是在管理上传任务，用户是在群聊现场表达。一个永久 `上传中` 等于系统把表达悬在半空。

## 3. 当前源码事实

### 3.1 草稿状态允许 pending-first 发送

`frontend/媒体/媒体草稿.ts` 把草稿状态映射到消息附件槽位：

```text
transporting -> uploading
processing   -> processing
ready        -> ready
failed       -> null
```

并且 `草稿可发送()` 的规则是：有 `attachmentId` 且非 failed 即可发送。

这意味着用户可以在字节仍上传时先把消息发出去，消息时间线里会出现 `uploading` 附件。这符合 pending-first 体验，但也要求上传任务必须最终有归宿。

### 3.2 发送消息会清空内存草稿

`frontend/实时/应用.ts` 发送消息时会：

```text
创建乐观消息，携带 uploading/processing/ready 附件快照
写入实时状态 composerMediaDrafts: []
emit create_message
```

这里清掉的是聊天输入状态里的内存草稿，不等于已经取消、完成或持久化关闭底层上传任务。

### 3.3 草稿持久化只保存 UI 子集

`frontend/媒体/媒体草稿持久化.ts` 当前只保存：

```text
localId
kind
attachmentId
width / height
status
fileName
errorCode
```

它明确不保存：

- `sourceFile`：刷新后 File 不可序列化；
- `previewUrl`：Blob URL 刷新后失效。

同时它也不保存：

- `uploadSessionId`；
- `tusEndpoint`；
- 上传档位 `default | large-video`；
- `expires_at`；
- 是否已经发布为消息附件；
- 是否仍有可恢复的 Uppy 文件；
- 是否需要重新选择本地文件；
- WebTorrent/torrent 身份或本地 seeding owner。

所以这份持久化数据只能恢复 UI 外观，不能恢复任务 owner。

### 3.4 恢复逻辑把 transporting 原样写回

`frontend/媒体/媒体发布.ts` 的 `恢复未完成草稿()` 当前逻辑：

```text
读取 localStorage 草稿
processing 丢弃
ready / transporting / failed 原样写回输入区
previewUrl 置空
sourceFile 置 null
```

关键问题：它没有重建上传器，也没有证明 Golden Retriever 已恢复文件，更没有检查后端附件是否已经完成或失败。

于是 `transporting` 会变成一个无 owner 的 UI 状态。

### 3.5 Uppy/Golden Retriever 的接线只在上传器被创建后生效

`frontend/媒体/媒体发布上传事件协作.ts` 的 `确保媒体上传器()` 会给 Uppy 接：

- `file-added` -> 写入 `transporting` 草稿；
- `upload-success` -> `processing` -> `completeMediaUpload` -> `ready`；
- `upload-error` -> `failed`；
- `restored` -> `nextUploader.upload()`。

但是刷新恢复时，如果没有根据持久化记录重新创建同一个 uploader，`restored` 事件就没有 owner 可以触发。

而当前草稿持久化又缺少重建 uploader 所需的 transport 信息。

### 3.6 大视频明确禁用了 Golden Retriever

`frontend/媒体/媒体发布.ts` 当前注释和逻辑明确：

```text
large-video 使用 parallelUploads/Concatenation
GoldenRetriever 无法正确持久化 partial sub-upload 状态
因此 large-video 上传器禁用 Golden Retriever
```

对应测试在 `frontend/tests/媒体发布GoldenRetriever配置测试.spec.ts` 已覆盖。

这意味着大视频刷新后不应该继续承诺“自动续传”。如果没有其他恢复 owner，它必须进入明确失败态或重新选择态。

### 3.7 旧规格的关键假设已经被线上现象推翻

`docs/superpowers/specs/2026-05-14-上传草稿持久化与刷新恢复.md` 曾假设：

```text
transporting/failed 草稿：还原 UI 状态，Tus + Golden Retriever 负责续传
```

当前源码和现象证明这不够：

- Golden Retriever 只有在同一个 uploader owner 被重建后才有机会恢复；
- large-video 已禁用 Golden Retriever；
- `sourceFile` 不可恢复时，Tus 客户端也没有真实字节来源；
- UI 草稿恢复不等于上传任务恢复。

## 4. 根因判断

根因是三层状态被混成了一层：

```text
UI 草稿状态
  localId / fileName / preview / transporting

上传 transport owner
  Uppy instance / Tus upload URL / File / Golden Retriever restored files

业务附件事实
  attachment_id / upload_session_id / complete / ready / failed / message slot status
```

当前恢复只恢复第一层，却把第一层当成第二、第三层仍然活着的证据。

这违反了媒体发送任务的不变量：

> `uploading` 只能表示仍有可观测、可推进、可失败的任务 owner。没有 owner 的 `uploading` 是假状态。

## 5. 设计四问

### 5.1 权威真相在哪里决定？

- 业务附件是否成立：后端 `prepare / complete / attachment_status_changed` 决定。
- 本地是否还能继续上传：媒体发布 owner 根据 Uppy restored files、可恢复 File、transport record 决定。
- UI 显示什么：只能投影上述事实，不能单靠 localStorage 的旧 `status` 决定。

### 5.2 稳定交换契约是什么？

现有 `媒体上传准备结果` 是 prepare 后的 transport 指令，不足以覆盖刷新恢复。

需要新增或扩展一个恢复契约，表达：

```text
attachment_id
upload_session_id
kind
file_name
byte_size
upload_profile
expires_at
transport_state: resumable | completed | failed | expired | unknown
next_transport?: { tus_endpoint, tus_headers, tus_metadata }
```

注意：不应把长期 Bearer token 直接塞进 localStorage。刷新恢复需要由后端重新签发短期 transport headers。

### 5.3 同步锚点是什么？

最小锚点必须是：

```text
session_id + room_id + attachment_id + upload_session_id
```

如果消息已发布，还必须带：

```text
message_id 或 client_message_id + attachment_id
```

WebTorrent 主链还需要：

```text
swarm_id / torrent_info_hash / content_hash
```

但这些只能来自后端 locator / ready 分发事实，不能从 UI 文本或 Blob URL 反推。

### 5.4 重试、重连、重入如何恢复和去重？

恢复流程必须幂等：

```text
同一 attachment_id 恢复多次
  -> 不创建重复草稿
  -> 不创建重复消息
  -> 不重复 prepare
  -> 不把旧 complete 复活到新 attachment
```

如果恢复失败：

```text
有 File / Golden Retriever restored file
  -> 可继续上传

无 File 但后端已 completed
  -> 升级 ready

无 File 且后端未 completed
  -> failed_needs_reselect

上传会话过期
  -> failed_retryable 或 failed_needs_reselect
```

## 6. 目标状态机

媒体发送任务需要从“草稿状态”升级为“任务状态 + UI 投影”。

建议最小状态：

```text
selected
preprocessing
prepared
transporting
published_uploading
processing
ready
failed_retryable
failed_needs_reselect
abandoned
```

状态含义：

- `selected`：用户选中文件，还没 prepare。
- `preprocessing`：本地预处理/取 metadata。
- `prepared`：后端已有 `attachment_id / upload_session_id`。
- `transporting`：本地 owner 活着，正在传字节。
- `published_uploading`：消息已发出，附件槽位仍在上传。
- `processing`：字节完成，等待 `complete` 或附件升级事件。
- `ready`：附件成立，可播放/可分发。
- `failed_retryable`：系统可重试，或用户可点继续。
- `failed_needs_reselect`：本地文件不可恢复，必须重新选择。
- `abandoned`：用户删除或 restart 前显式放弃旧上传。

禁止状态：

- 无 uploader owner 的 `transporting`。
- 无恢复检查的 `published_uploading`。
- 无超时、无错误码、无用户动作的永久 `uploading`。

## 7. 修复方向

### 7.1 第一刀：恢复时禁止无 owner uploading

刷新后 `恢复未完成草稿()` 不能再把持久化的 `transporting` 原样写回。

它必须先进入 `recovering` 语义，并做对账：

1. 查持久化任务记录；
2. 查后端 attachment/upload 状态；
3. 尝试重建 uploader；
4. 等待 Uppy `restored` 或读取可恢复文件；
5. 合并结果。

如果无法证明 owner 活着，直接投影为失败：

```text
failed_needs_reselect / attachment_upload_interrupted
```

这能先消灭“永远上传中”。

### 7.2 第二刀：持久化从草稿 UI 升级为发送任务记录

`媒体草稿持久化.ts` 不应继续只保存 UI 子集。应新增独立记录：

```ts
type 媒体发送任务恢复记录 = {
  localId: string;
  roomId: string | null;
  messageId?: string;
  clientMessageId?: string;
  attachmentId: string;
  uploadSessionId: string;
  kind: "image" | "video";
  fileName: string;
  byteSize: number;
  width: number;
  height: number;
  uploadProfile: "default" | "large-video";
  status: "transporting" | "published_uploading" | "processing" | "ready" | "failed";
  createdAtMs: number;
  expiresAt: string;
};
```

注意：不把 `tus_headers` 长期持久化到 localStorage。

### 7.3 第三刀：增加恢复用 transport 重新签发能力

当前 `prepareMediaUpload()` 只适合新上传。

恢复旧上传需要一个窄端口，例如：

```ts
resumeMediaUpload(sessionId: string, attachmentId: string): Promise<媒体上传恢复结果>
```

后端根据 `attachment_id / upload_session_id` 返回：

- 已完成：前端直接 `ready`；
- 可续传：返回新的 Tus endpoint/headers/metadata；
- 已过期/已失败：返回明确错误码；
- 需要重新选择文件：前端显示 `failed_needs_reselect`。

### 7.4 第四刀：Golden Retriever 只作为证据，不作为承诺

Golden Retriever restored 后：

- 有 files：可以重建 uploader 并 upload；
- 没有 files：不能继续显示上传中；
- large-video：默认按不可自动恢复处理，除非后续用 WebTorrent/OPFS/File System Access 建立新的可靠本地文件 owner。

### 7.5 第五刀：消息附件上传中也要有失败归宿

pending-first 允许 `transporting` 附件先发消息，但后端或前端必须能把它升级为：

- `ready`；
- `failed`；
- `needs_reselect`。

否则刷新后时间线里的 `uploading` 会永久残留。

---

## 8. 非目标

本设计不做这些事：

- 不引入 HTTP 直链作为正式媒体播放/分发第二真相。
- 不把 Tus 当成 WebTorrent 的替代主链。
- 不在 domain/application 内引入 Uppy、Tus、WebTorrent 浏览器类型。
- 不靠固定 timeout 假装修复上传 owner 丢失。
- 不把 Bearer upload header 长期写入 localStorage。
- 不为了恢复体验恢复 large-video 的 Golden Retriever，除非先证明 partial upload 恢复不再触发旧问题。

## 9. 测试与验收标准

### 9.1 RED 用例

必须先补失败测试：

1. `transporting` 草稿刷新恢复时，如果没有 uploader/restored file，不得显示 `上传中`。
2. `large-video` 刷新恢复时，不得依赖 Golden Retriever；必须进入 `failed_needs_reselect` 或明确可恢复状态。
3. 已发送 pending-first 消息里的 `uploading` 附件，恢复后若上传 owner 不存在，必须收到失败归宿。
4. `ready` 草稿恢复仍然保留，不回退为 failed。
5. `processing` 草稿恢复必须查后端完成状态；不能简单丢弃或永久 processing。

建议验证命令：

```bash

pnpm vitest run "tests/媒体发布失败恢复测试.spec.ts"

```

### 9.3 真实冒烟

公网或本地 HTTPS 场景必须覆盖：

1. 上传中图片刷新页面；
2. 上传中普通视频刷新页面；
3. 上传中大视频刷新页面；
4. 上传中附件已先发消息，再刷新页面；
5. 后台挂起 30 秒后回来；
6. 上传失败后点击继续/重新选择。

验收口径：

```text
没有任何媒体卡片永久停留在上传中。
用户能看见明确结果：继续、已发送、失败可重试、需要重新选择。
```

## 10. GitNexus / Serena 证据

GitNexus：

- `创建媒体发布器` upstream impact：LOW，直接影响测试支撑和媒体发布测试。
- `确保媒体上传器` upstream impact：LOW，直接影响 `读取或创建上传器 -> 处理选择同类媒体文件 -> 处理选择媒体文件`。
- `从本地存储恢复媒体草稿` upstream impact：LOW，直接影响 `恢复未完成草稿` 和持久化测试。
- `npx gitnexus analyze --force` 已成功重建索引，但 Windows 环境 FTS extension 下载失败，关键词查询退化；本次宏观判断使用 context/impact 结果和源码实读交叉确认。

Serena / 源码实读：

- `恢复未完成草稿()` 只恢复 UI 草稿，不恢复 uploader owner。
- `确保媒体上传器()` 的 `restored` 只有在 uploader 被创建后才会自动 upload。
- `媒体草稿持久化.ts` 明确不保存 `sourceFile` / `previewUrl`，也未保存 upload session 与恢复契约。
- `large-video` 明确禁用 Golden Retriever。

## 11. 结论

这次 bug 的底层不变量应该写死：

> 媒体发送任务必须有唯一 owner。`uploading` 只能是 owner 活着的投影，不是 localStorage 里旧字符串的复读。

后续实现计划应围绕这个不变量拆任务，而不是继续在 UI 文案、重试按钮或 Golden Retriever 配置上补丁式堆叠。
