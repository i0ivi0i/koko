## 0. 这份 spec 要解决的不是“小网络问题”

这次不是“某个端口偶尔没开”“局域网里某台手机偶尔连不上”这么浅的问题。

这次真正要收口的是一句话：

**浏览器用户永远只该认识一个 HTTPS 入口，项目内部再复杂，都不允许把内部地址、内部端口、内部协议真相泄漏给浏览器。**

如果这句话不写成硬规则，项目就会长期漂成下面这些坏状态：

1. 本机作者自己能跑，但局域网其他设备不稳定，最后你只能在自己电脑上“假装多人测试”。
2. 开发阶段和正式上线阶段使用两套完全不同的网络脑子，导致“本地能跑”对正式部署几乎没有参考价值。
3. 页面入口表面是 HTTPS，但上传、实时、媒体下一跳偷偷掉回 HTTP 或 `127.0.0.1`。
4. 浏览器一旦拿到 `127.0.0.1`、`localhost`、`:1081`、`:7072`、`:7073` 这种内部地址，就会把“机器内部零件”误当成“用户入口”。
5. 未来你把项目“甩”进 VPS 之后，还得继续手搓多条外部路径、额外端口和二次解释，完全违背“直接跑起来”的目标。

所以这份 spec 的目标不是“再修一个 LAN bug”，也不是“把 `run.ps1` 修得更强一点”，而是把**项目网络真相**正式收口成：

**开发时和正式部署时，用户视角都只有一个 HTTPS 入口；区别只是在开发时这个入口是局域网 IP，上线时这个入口是正式域名。**

## 1. 主人的真实需求，禁止被执行层偷换

这次网络整顿必须服从下面这句原始需求，禁止执行时偷换成工程师自嗨版本：

> 更正后的硬需求：未来正式部署时，我只想直接把项目源代码二进制甩进公网 VPS 中就能自动完美运行；而且不分正式、非正式、生产、开发、测试，任何环境都全面禁止 `cloudflared`；公网侧只使用 Cloudflare 和域名；现在局域网内网也要能访问本机开发测试时的项目，这样我才能模拟未来公网用户进行测试源代码。

把它翻成项目约束，就是下面 4 句：

1. **现在开发测试时**，局域网里的其他设备必须能直接访问  
   `https://开发电脑局域网IP/`
2. **未来正式上线时**，公网用户必须只访问  
   `https://正式域名/`
3. **开发和上线禁止各玩一套**  
   现在不是“本机特殊玩法”，以后也不是“上线另起炉灶”
4. **用户永远只记一个地址**  
   开发时记局域网 IP  
   上线时记正式域名  
   除此之外，不允许再让用户理解内部端口、sidecar、代理细节

## 2. 前因后果：为什么现在必须整顿

### 2.1 表面现象

之前的项目网络形态已经出现了危险信号：

1. 有些路径在作者自己电脑上能跑。
2. 但局域网其他设备并不能稳定、完整地按未来公网用户的方式使用。
3. 页面入口、上传入口、实时入口并没有被真正收成一个用户视角。
4. 项目内部的回环地址和内部端口，仍然在某些链路里被当成“可下发给浏览器的地址”。

### 2.2 深层原因

真正的问题不是“某个端口忘了开放”，而是**项目里同时存在两套网络真相**：

1. 一套真相说：浏览器应该走统一 HTTPS 入口。
2. 另一套真相又在某些下游步骤里说：浏览器下一跳可以直接去内部地址。

这会导致一种很隐蔽但很致命的错觉：

1. 页面表面能打开，看起来像是“已经通了”。
2. 但真正进入上传、续传、实时、协作分发这些深水区后，浏览器会突然被拉去错误地址。
3. 作者自己电脑因为本机回环、缓存、历史状态、特殊可信上下文等原因，可能“侥幸没暴露完全”。
4. 局域网其他设备和未来公网真实用户，则会把这些问题更早、更直接地撞出来。

### 2.3 已经抓到的真实证据

这次不是靠猜。

已经抓到的真实复现说明：**应用层和 transport 层在说两套话。**

#### 证据 A：HTTPS prepare 正确，但 Tus 下一跳降回 HTTP

实测：

1. `POST https://192.168.100.104/api/media/image/prepare`
2. 返回 `tus_endpoint = https://192.168.100.104/files`
3. 继续 `POST https://192.168.100.104/files`
4. `201 Location` 却返回  
   `http://192.168.100.104/files/...`

这说明：

1. 应用层已经知道浏览器应该走 HTTPS 入口。
2. 但 Tus transport 下一跳又把浏览器拽回了明文 HTTP。
3. **禁止** 出现这种“入口是 HTTPS，协议下一跳却降回 HTTP”的双真相。

#### 证据 B：HTTP 局域网 prepare 已经把内部端口暴露给浏览器

实测：

1. `POST http://192.168.100.104:8080/api/media/image/prepare`
2. 返回 `tus_endpoint = http://192.168.100.104:1081/files`

这说明：

1. 局域网开发路径里，浏览器仍然被允许知道 `1081` 这个内部 Tus 端口。
2. 这和“浏览器只认一个统一入口”的目标直接冲突。
3. **禁止** 再把 `:1081` 这种内部端口当浏览器契约的一部分。

#### 证据 C：同源 `/files` 入口继续把浏览器带回 `127.0.0.1`

实测：

1. `POST http://192.168.100.104:8080/files`
2. `201 Location` 返回  
   `http://127.0.0.1:1081/files/...`

这说明：

1. 即便浏览器先走的是局域网可达入口，
2. 下一跳仍可能被某一层偷偷改写回作者电脑自己的回环地址。
3. 这对局域网其他设备和未来公网用户都是致命错误。
4. **禁止** 浏览器收到任何 `127.0.0.1`、`localhost` 作为下一跳。

## 3. 备选方案比较

### 3.1 方案 A：单 HTTPS 入口收口

开发时：

- 用户只访问 `https://开发电脑局域网IP/`

上线时：

- 用户只访问 `https://正式域名/`

浏览器下的全部能力都只从这个入口继续分发：

- `/api/...`
- `/files/...`
- `/api/swarm/announce`

优点：

1. 最符合主人的真实需求。
2. 开发和上线是同一种网络脑子，局域网测试更接近未来公网测试。
3. 浏览器、上传、实时、协作分发的真相最容易统一。
4. 后续最省心，最不容易漂。

缺点：

1. 必须认真清理现有内部地址泄漏和双真相路径。
2. 不能继续容忍“先这样跑着，以后再说”的灰色地带。

### 3.2 方案 B：页面、上传、实时继续多端口直连

例如：

- 页面一个端口
- 上传一个端口
- tracker 一个端口
- seeder 一个端口

优点：

1. 表面上改动可能少一点。

缺点：

1. 用户要理解更多地址和端口。
2. 局域网测试和正式公网测试仍然不是同一件事。
3. 极易继续出现“本机能跑、别人不行”的幻觉。
4. **禁止** 继续把这种方案当长期真相。

### 3.3 方案 C：多子域拆分

例如：

- 主站一个域名
- 上传一个域名
- 实时一个域名

优点：

1. 某些大型部署里运维边界更细。

缺点：

1. 现在完全没必要。
2. 对主人当前“简单、直接、甩进 VPS 就跑”的目标不友好。
3. 只会增加理解和配置成本。

### 3.4 结论

本次正式采用：

**方案 A：单 HTTPS 入口收口。**

并明确写成禁令：

1. **禁止** 再把多端口直连当成浏览器长期方案。
2. **禁止** 为了短期省事，让浏览器继续知道内部零件地址。
3. **禁止** 在当前阶段引入多子域复杂度，分散主入口真相。

## 4. 正式网络裁决

### 4.1 唯一外部入口裁决

从现在开始，浏览器用户永远只认一个 HTTPS 入口。

开发阶段：

- `https://开发电脑局域网IP/`

正式上线阶段：

- `https://正式域名/`

除此之外，**禁止** 让浏览器用户接触：

- `127.0.0.1`
- `localhost`
- `http://...:1081`
- `ws://...:7072`
- `http://...:7073`
- 任何“这是内部服务，先临时让浏览器直连一下”的入口

### 4.2 浏览器可见路径裁决

浏览器只允许感知下面这些同源路径：

1. `/api/...`
2. `/files/...`
3. `/api/swarm/announce`

这些路径都属于“唯一外部入口”的一部分。

默认优先级也要写死：

1. 浏览器契约**优先**返回同源相对路径
2. 如果某些场景必须返回绝对地址，也只能从“唯一 HTTPS 入口”派生
3. **禁止** 返回“相对路径一套、内部绝对地址一套、开发特例再一套”的三份并存真相

明确禁令：

1. **禁止** 浏览器绕开入口直连 `tusd`
2. **禁止** 浏览器绕开入口直连 tracker
3. **禁止** 浏览器绕开入口直连 seeder
4. **禁止** 上传 prepare 返回 `:1081` 给浏览器
5. **禁止** locator / distribution 返回裸 tracker 端口给浏览器

### 4.3 内部零件裁决

下面这些零件可以继续存在，但只属于机器内部：

1. `koko`
2. `tusd`
3. tracker
4. seeder
5. 本机 sidecar 间的回环通信

它们可以彼此通信，但必须服从下面规则：

1. **禁止** 把机器内部通信地址当成浏览器契约
2. **禁止** 让内部端口决定浏览器该访问什么
3. **禁止** 让开发脚本日志里的内部地址，反过来变成产品真相

## 5. 目标流量走向

### 5.1 开发时局域网测试

局域网用户：

1. 访问 `https://开发电脑局域网IP/`
2. 页面加载后，所有请求继续回到这个入口
3. 上传走 `https://开发电脑局域网IP/files/...`
4. API 走 `https://开发电脑局域网IP/api/...`
5. 实时/协作分发走 `wss://开发电脑局域网IP/api/swarm/announce`

浏览器看不到内部零件。

### 5.2 正式上线时

公网用户：

1. 访问 `https://正式域名/`
2. 页面加载后，所有请求继续回到这个入口
3. 上传走 `https://正式域名/files/...`
4. API 走 `https://正式域名/api/...`
5. 实时/协作分发走 `wss://正式域名/api/swarm/announce`

Cloudflare 和正式域名只负责把用户送到这一个入口。

明确禁令：

1. **禁止** 在本项目任何环境里继续使用 `cloudflared`
2. **禁止** 把 Cloudflare 公开代理/CDN 和 `cloudflared` 本地隧道进程混成一件事
3. **禁止** 让开发阶段和上线阶段使用不同的浏览器契约结构

### 5.3 Cloudflare CDN 公开缓存平面裁决

这里必须先把两个名字彻底裁开，**禁止** 混为一谈：

1. `cloudflared` 是本地隧道/连接器进程，本项目任何环境里都**禁止** 使用
2. `Cloudflare CDN` 才是公网用户真正经过的边缘代理与缓存平面

后续一切正式公网缓存设计，都必须服从下面这条硬规则：

**浏览器公开主入口锁定在 `443`；`80` 只允许做跳转或兜底，不允许把主缓存平面设计到其他端口。**

原因不是个人偏好，而是官方现实：

1. Cloudflare 确实支持代理多组 HTTP / HTTPS 端口
2. 默认常规缓存重点落在 `80`、`443`、`8080` 这类端口
3. 但我们这个项目为了“浏览器只认一个 HTTPS 入口”，免费常规缓存最稳、最省心、最不容易误伤的公开平面，仍然应该收口在 `443`
4. 有些端口虽然能被代理，但默认并不参与常规缓存

所以必须写死下面这些禁令：

1. **禁止** 把“Cloudflare 支持代理这个端口”偷换成“Cloudflare 免费 CDN 默认会缓存这个端口”
2. **禁止** 把公开图片、视频、附件热路径设计成 `:2052`、`:2053`、`:2082`、`:2083`、`:2086`、`:2087`、`:2095`、`:2096`、`:8443`、`:8880` 这类默认不适合免费缓存主平面的端口
3. **禁止** 因为源站内部喜欢跑 `8080`、`1081`、`7072`、`7073`，就把这些端口直接暴露给浏览器
4. **禁止** 因为 Cloudflare 也能处理 `8080`，就把公网产品主入口偷偷漂成 `http://域名:8080`
5. **禁止** 把“源站内部监听端口”和“浏览器公开入口端口”写成同一个概念

允许的真实形态只有这一种：

1. 浏览器只访问 `https://正式域名/`
2. Cloudflare CDN 在 `443` 上接住用户
3. 源站内部继续用 `8080`、`1081`、`7072`、`7073` 都可以
4. 但这些内部端口只属于机器内部，**禁止** 泄漏成浏览器契约

### 5.4 Cloudflare 免费缓存现实约束

如果后续要吃 Cloudflare 免费 CDN，这里还有 4 条比“端口支不支持”更致命的现实，必须提前写死：

1. 默认缓存主要按 **URL 文件扩展名** 判断，不按 MIME 类型判断
2. 默认不把 HTML、JSON 当成静态媒体缓存主平面
3. 默认 cache key 包含完整 URL 和 query string
4. 默认不会缓存带 `private / no-store / no-cache / max-age=0` 的响应，也不会缓存带 `Set-Cookie` 的响应或非 `GET` 请求

这几条会直接推导出下面的硬禁令：

1. **禁止** 把“希望全网共享缓存”的图片或视频公开读路径继续设计成带 `session_id`、用户 token、一次性鉴权 query 的 URL
2. **禁止** 让共享媒体热路径依赖 `GET /api/...?...session_id=...` 这类每个用户一个 cache key 的结构
3. **禁止** 误以为“接口已经返回 `image/webp` / `video/mp4` MIME”就天然会被 Cloudflare 当静态媒体高命中缓存
4. **禁止** 把带 `Set-Cookie` 的媒体响应当成 CDN 主缓存面

所以未来媒体公开读路径要朝下面这个方向收口：

1. 尽量走稳定、可复用、无用户私货 query 的 `GET`
2. 最理想是 `/files/...jpg`、`/files/...webp`、`/files/...mp4` 这种稳定路径
3. 如果历史原因暂时还是扩展名不明显或接口味路径，也必须额外写清楚对应的 `Cache Rules`

### 5.5 Cloudflare 免费大小与上传限制裁决

未来如果准备白嫖 Cloudflare 免费 CDN，这两个官方上限必须提前写成禁令：

1. 代理上传单请求体上限是 `100 MB`
2. 免费 / Pro / Business 可缓存单文件上限是 `512 MB`

这会直接影响我们的媒体主链设计：

1. **禁止** 把“通过 Cloudflare 代理域名上传”默认等同于“任意大文件都能直接稳定上传”
2. **禁止** 在无法证明单请求体不超过 `100 MB` 之前，就宣布当前上传链路已经适配 Cloudflare 免费代理上传
3. **禁止** 把 `512 MB` 以上视频默认宣传成“能稳定吃满 Cloudflare 免费 CDN 缓存”
4. **禁止** 让部署文档对这些硬上限保持沉默，诱导未来运维误判

允许的诚实结论只有：

1. 如果上传流量走 Cloudflare 代理公开域名，就必须验证分块请求体不会撞上 `100 MB`
2. 如果某些超大文件天然会超过免费缓存上限，就必须明确说它们不能指望免费 CDN 完整缓存
3. 是否继续使用代理上传、是否改成更细颗粒度分块、是否把超大上传改走其他路径，都要在实现阶段给出实证，而不是靠想当然

## 6. 当前代码层已经暴露出的根因

### 6.1 上传链路双真相

当前代码里，上传链路已经暴露出最危险的网络漂移：

1. [src/媒体上传外壳.rs](src/媒体上传外壳.rs) 已经在尝试按请求头推导对外 Tus 地址。
2. [src/媒体上传外壳.rs](src/媒体上传外壳.rs) 里的同源 Tus 代理又只是转发 sidecar 响应。
3. [https.ps1](https.ps1) 已经把 `/files` 反代给 `tusd`。
4. 当前运行中的 `tusd` 默认也没有进入“我在代理后面”的正确模式，导致它仍可能按内部服务视角返回 `Location`。
5. 这说明“浏览器该去哪”这件事，现在仍然没有被单一 owner 完全收口。

结果就是：

1. prepare 觉得自己在服务浏览器入口。
2. Tus transport 又按内部服务视角回 `Location`。
3. 浏览器最终拿到的是混合真相。

这条必须写成硬裁决：

**禁止 prepare、proxy、transport 三层各自发明一套“浏览器下一跳地址”。**

### 6.2 开发便利真相和产品真相混在一起

当前一些默认值仍然带着明显的“本机自己跑起来就行”思路：

1. 回环地址默认值
2. 内部端口默认暴露
3. 局域网 HTTP 开发与 HTTPS 可信上下文之间的灰色混用

这在早期开发阶段可以理解，但现在已经进入明显的架构风险区。

必须明确：

1. 开发便利不是长期产品真相
2. 回环地址只能服务内部零件
3. 浏览器契约必须优先服从未来正式部署形态

### 6.3 浏览器 secure context 前提不能继续糊涂

前端已有明确信号表明：

1. `http://localhost` 之所以能跑，是浏览器对 loopback 的特殊照顾
2. `http://局域网IP` 通常不属于可信上下文
3. `WebTorrent` 浏览器协作分发、service worker 接管等能力，需要可信 HTTPS 上下文

所以必须正式禁止：

1. **禁止** 把 `localhost` 特例当成局域网用户体验依据
2. **禁止** 继续拿明文 `http://局域网IP` 当满血模拟未来公网用户的方案
3. **禁止** 因为本机作者电脑能跑，就宣布局域网/公网真相成立

## 7. 启动与部署真相裁决

### 7.1 开发启动真相

开发阶段只允许一个主启动入口。

这个主启动入口的职责是：

1. 把内部零件带起来
2. 准备局域网 HTTPS 单入口
3. 给开发者一个明确、唯一、可转发给别人的局域网测试地址
4. 在 Windows 本地开发适配层里确保 `TCP 443` 入站防火墙规则存在；`LauncherMode` 可以跳过本机证书 trust 和开机自启，但**禁止**连同 HTTPS 入站防火墙 owner 一起跳过

这个主启动入口**不是**第二套业务真相。

明确禁令：

1. **禁止** 开发者再手工向测试用户解释多个内部端口
2. **禁止** 启动脚本打印一堆内部地址后，让人自己猜哪个才是用户入口
3. **禁止** 再把“本机访问入口”和“局域网访问入口”分裂成两套长期产品路径
4. **禁止** 只证明 Caddy 本机 `reload` 成功，就宣布局域网设备一定能访问；局域网入口必须同时证明监听、反代和 Windows 入站防火墙 owner 三件事

### 7.2 Windows 本地脚本不是产品真相

`run.ps1`、`https.ps1`、本机证书导入、Windows 自启动、PowerShell 编排，这些都只允许属于**本地开发适配层**。

它们可以存在，但只能回答下面这个问题：

> 开发者在自己电脑上，怎样最省心地拉起“接近正式公网用户视角”的本地测试环境？

它们**禁止** 被偷换成下面这种错误角色：

1. 正式部署的唯一启动真相
2. 产品网络契约的唯一 owner
3. 浏览器地址生成规则的最终裁决者
4. 只有 Windows 才能成立的产品依赖

必须写死：

1. **禁止** 把 `run.ps1` 是否存在，当成项目网络设计是否成立的前提
2. **禁止** 把 `https.ps1`、Caddy、本机 trust 证书这些 Windows 本地便利，误写成未来 Linux 公网部署必需品
3. **禁止** 让文档、代码、配置默认假设“部署者一定会先跑 PowerShell 脚本”
4. **禁止** 因为当前在 Windows 开发，就把 Windows 启动编排写成系统真相

这条很重要，因为主人说得很明确：未来正式部署时，是把项目源代码二进制“甩”进公网 `VPS` 就要能跑，而不是把整套 Windows 本地脚本也搬上去。

### 7.3 正式 Linux 部署真相

正式部署时，应当做到下面这件简单的事：

1. 把项目放进 VPS
2. 在 Linux 上用明确、最少、可重复的启动方式拉起项目
3. 让 `Cloudflare + 域名` 把公网用户送到唯一 HTTPS 入口

此时项目内部仍然可以继续有多个服务零件，但这些零件不该让部署者天天手动解释。

明确禁令：

1. **禁止** 正式部署时还要求用户理解内部端口拓扑
2. **禁止** 把内部组件地址暴露成运维必须手改的浏览器契约
3. **禁止** 让“上线版网络脑子”和“开发版网络脑子”分裂
4. **禁止** 把 PowerShell 脚本、Windows 路径、Windows 证书导入流程、Windows 计划任务，当成 Linux 正式部署前置条件
5. **禁止** 把“先在服务器上手工跑好几个 sidecar，再人工拼地址”当成省心部署

正式 Linux 部署真正应该依赖的，只能是下面这些更稳的东西：

1. 项目自身的后端二进制与前端静态产物
2. 少量明确的环境变量或配置文件
3. 一个明确的公网入口接入层
4. 一条清楚、重复执行也不变味的启动链路

还要再写死一个容易混淆的点：

1. **浏览器看到的公网入口必须是 HTTPS**
2. **禁止** 把这句话偷换成“Linux 服务器内部每一跳也必须照抄 Windows 本地 `https.ps1` 玩法”
3. Linux 服务器内部可以继续使用回环地址、私网端口、Unix Socket、sidecar 之间的内部通信
4. 但这些内部通信**禁止** 泄漏成浏览器要访问的公开地址

换句话说：

1. `run.ps1` 可以帮助本地开发
2. 但正式 Linux 部署必须有**不依赖 `run.ps1` 也完全成立**的网络真相
3. 本地脚本只能去适配这个真相，**禁止** 反过来让产品真相依赖本地脚本

### 7.4 `cloudflared` 全环境禁令裁决

`cloudflared` 在别的项目里也许有价值，但在这个项目当前网络方案里，不分开发、测试、生产，裁决都很直接：

1. **禁止** 把 `cloudflared` 当正式公网入口组件
2. **禁止** 把 `cloudflared` 当上传、实时、媒体读路径的隐藏修补层
3. **禁止** 在部署文档、启动脚本、验收话术里再保留“以后也可以上 `cloudflared`”这种后门
4. **禁止** 因为它一时方便，就把它写成项目长期网络真相的一部分

原因也写死：

1. 它会把“Cloudflare 公网代理/CDN”与“本地隧道进程”混成两套脑子
2. 它会诱导后续实现继续保留第二条公网入口或第二套部署路径
3. 它和主人当前要求正面冲突：**项目要全面禁止严厉禁止 `cloudflared`**

### 7.5 Cloudflare CDN 的角色裁决

Cloudflare CDN 和 `cloudflared` 不是一个东西，而且前者保留、后者禁用，角色必须继续拆开：

Cloudflare CDN 负责：

1. 在 `443` 上承接公网用户
2. 缓存真正适合缓存的公开静态媒体读流量
3. 用统一公网域名维持“浏览器只认一个入口”的产品真相

Cloudflare CDN **禁止** 被误用成：

1. 一块“什么端口都能免费高速缓存”的魔法布
2. 一种“带用户 query 的私有接口也会天然高命中共享缓存”的幻想
3. 一种“上传链路有没有撞上 `100 MB` 不重要，反正有 Cloudflare 顶着”的幻觉

必须明确：

1. 本项目任何环境的公网入口只允许使用 Cloudflare 的公网代理/CDN 能力
2. `cloudflared` 不属于本项目任何环境的网络真相
3. Cloudflare CDN 解决的是公开读流量加速与缓存问题
4. 它也不能替项目掩盖浏览器契约设计错误

## 8. 本次整顿要删掉的旧网络垃圾

这次整顿不是“多保留一点兼容入口更稳”，而是要有删除勇气。

下面这些旧东西，只要确认没有正当长期价值，就应该删、合、收：

1. 任何返回给浏览器的 `127.0.0.1`
2. 任何返回给浏览器的 `localhost`
3. 任何返回给浏览器的 `:1081`
4. 任何返回给浏览器的 `:7072`
5. 任何返回给浏览器的 `:7073`
6. 任何“浏览器可以直连内部零件”的旧路径
7. 任何“入口先走 HTTPS，下一跳再掉回 HTTP”的行为
8. 任何“同一个能力有两条浏览器出口”的历史兼容逻辑

明确禁令：

1. **禁止** 以“先留着以后再清”为由长期保留这些旧路
2. **禁止** 以“本机自测方便”为理由继续让浏览器知道内部端口
3. **禁止** 为了减少短期改动，保留会制造长期漂移的双真相

## 9. 配置 owner 裁决

为了防漂移，必须先把“谁负责哪种地址”写死。

### 9.1 外部公开地址 owner

外部公开地址只允许有一个 owner：

**唯一 HTTPS 入口**

开发时它是：

- `https://开发电脑局域网IP/`

上线时它是：

- `https://正式域名/`

任何给浏览器的路径，都必须从这个 owner 派生。

### 9.2 内部地址 owner

内部地址只允许服务机器内部零件，例如：

1. `koko -> tusd`
2. `koko -> tracker`
3. `seeder -> koko`
4. `koko -> seeder`

这些地址只属于内部 owner，**禁止** 越权下发给浏览器。

### 9.3 配置边界

真正应该成为“部署可配项”的，只允许保留少数有明确业务价值的入口信息。

例如：

1. 外部唯一入口相关信息
2. 正式域名相关信息
3. 是否开发/正式环境

明确禁令：

1. **禁止** 把内部端口当成用户级配置项长期暴露
2. **禁止** 让部署者靠修改一堆内部地址才能把项目跑起来
3. **禁止** 在启动脚本、后端、前端各保留一份相互打架的入口配置
4. **禁止** 把 Windows 本地脚本里的默认值，当成正式 Linux 部署的配置来源

### 9.4 Cloudflare 缓存配置边界

Cloudflare 相关配置也必须收口 owner，禁止四处乱长：

1. “公开入口是不是 `443` 单入口”属于产品网络真相
2. “哪些路径允许被 CDN 缓存”属于部署与边缘缓存策略
3. “哪些内部端口监听什么服务”属于机器内部编排

所以必须写死：

1. **禁止** 把 `8443`、`8880` 之类默认不适合免费缓存主平面的端口，写成项目推荐公网主入口
2. **禁止** 把 `session_id`、用户 token 这类 cache key 污染源，默默塞进共享媒体主路径
3. **禁止** 把 Cloudflare `Cache Rules`、`Tiered Cache` 这种边缘策略，偷写进浏览器或前端页面逻辑里
4. **禁止** 让前端自己猜“这个 URL 将来会不会被 CDN 缓存”，前端只认稳定公开路径

## 10. 验收标准

网络整顿完成后，不再用“作者电脑能打开页面”当成功，而要同时满足下面 4 组验收。

### 10.1 入口验收

1. 局域网其他设备能直接打开  
   `https://开发电脑局域网IP/`
2. 正式部署后，公网用户能直接打开  
   `https://正式域名/`
3. **禁止** 要求测试用户手动访问内部端口入口

### 10.2 上传验收

1. 从唯一 HTTPS 入口发起上传
2. prepare、创建、续传、完成全程都留在同一入口真相内
3. **禁止** 中途掉回 HTTP
4. **禁止** 中途掉回 `127.0.0.1`
5. **禁止** 中途暴露 `:1081`

### 10.2.1 Cloudflare CDN 验收

如果未来正式公网入口准备接入 Cloudflare 免费 CDN，还必须额外满足下面这些验收：

1. 浏览器公开入口仍然只认 `https://正式域名/` 的 `443`
2. 共享媒体公开读路径不再带 `session_id` 或其他用户私货 query
3. 需要共享缓存的媒体路径，要么具备稳定文件扩展名，要么已经明确配置对应 `Cache Rules`
4. 如果上传继续走 Cloudflare 代理域名，必须有实证证明单请求体不会撞上 `100 MB`
5. `512 MB` 以上的媒体，**禁止** 在文档或实现里假装自己天然享受免费 CDN 完整缓存

### 10.3 实时验收

1. 浏览器实时连接只认  
   `wss://入口/api/swarm/announce`
2. **禁止** 浏览器直连裸 tracker
3. **禁止** 把 sidecar 内部 announce 当成浏览器公开 announce

### 10.4 同构验收

局域网测试和正式公网测试，必须满足下面这句：

**对浏览器来说，局域网开发和正式公网的区别只应是“入口名字不同”，不应是“整套网络规则不同”。**

### 10.4.1 跨平台同构补充验收

对部署者来说，也必须满足下面这句：

**Windows 本地开发脚本和 Linux 正式部署脚本可以不同，但它们背后的网络契约、入口结构、浏览器下一跳规则必须是同一套。**

换句话说：

1. 允许本地开发用 `run.ps1`
2. 允许正式部署用 Linux 自己的启动方式
3. **禁止** 因为启动命令不同，就让网络真相变成两套

### 10.5 失败判定，禁止自我感动式验收

后续执行时，只要出现下面任意一种情况，就应直接判定为**没有整顿完成**：

1. 页面虽然能打开，但上传或续传把浏览器带去了 `http://...`
2. 页面虽然能打开，但浏览器网络面板里出现了 `127.0.0.1`、`localhost`、`:1081`、`:7072`、`:7073`
3. 局域网测试要靠作者自己口头解释“这个阶段先点 A，再改成 B，再连 C”
4. 开发环境和正式环境虽然都叫“单入口”，但实际上地址推导、协议推导、下一跳规则并不是同一套逻辑
5. 页面入口是 HTTPS，但上传、实时、协作分发里仍然偷偷存在第二条浏览器出口
6. 本地只能靠 `run.ps1` 成立，一到 Linux 正式部署就缺少等价真相或等价入口结构

这条必须写死，是因为本次要解决的是“网络真相漂移”，不是“首页勉强能打开”。

### 10.6 执行防漂移清单

后续任何实现、重构、补丁、联调，都必须服从下面这些执行禁令：

1. **禁止** 把“单入口”偷换成“只有首页单入口，上传和实时例外”
2. **禁止** 在前端硬编码一份开发地址、在后端再硬编码一份正式地址、在脚本里再偷留一份回环默认值
3. **禁止** 用 `if 本机`、`if LAN`、`if 正式环境` 长出三套浏览器地址真相，只为掩盖根因
4. **禁止** 把 sidecar 直连暴露给浏览器，再把它包装成“临时开发便利”
5. **禁止** 因为担心动到旧逻辑，就把旧入口和新入口长期并存
6. **禁止** 把“用户入口地址”这个 owner 分散到前端、后端、代理脚本三处共同维护
7. **禁止** 先补表面兼容分支，再把真正的 owner 收口工作无限后拖
8. **禁止** 在 Windows 本地脚本里偷偷补一层 Linux 上并不存在的网络特判，然后把它包装成“正式方案”

允许的方向只有一个：

1. 先把“浏览器公开入口 owner”收成唯一真相
2. 再让上传、API、实时、协作分发全部从这个真相派生
3. 最后删除会泄漏内部地址的旧路、旧默认值和旧兼容分支

## 11. 非目标，禁止借题扩写

这份 spec 虽然很详细，但它不是无边界扩写。

下面这些不属于本次核心目标：

1. STUN / TURN 全套公网穿透策略
2. tracker 高可用集群方案
3. 多机房多区域调度
4. 大规模公网压测平台
5. 与当前单入口收口无关的网络美化工程

明确禁令：

1. **禁止** 借本次网络整顿顺手把范围膨胀成分布式改造大项目
2. **禁止** 在唯一入口真相还没站稳时，先扩张成更复杂的网络拓扑
3. **禁止** 把“未来也许会需要”当成现在不收口的借口

## 12. 最终裁决

本次网络整顿的最终裁决只有一句：

**浏览器用户永远只认一个 HTTPS 入口；开发时是局域网 IP，上线时是正式域名；上传、API、实时、协作分发全部继续挂在这个入口下面；任何内部地址、内部端口、内部协议降级，都禁止再泄漏给浏览器。**

如果后续实现没有达到这句话，就不算真正整顿完成。
