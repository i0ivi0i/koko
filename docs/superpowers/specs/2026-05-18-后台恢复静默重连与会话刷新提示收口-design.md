## 1. 一句话结论

当前页面切后台、冻结或恢复时，前端会主动挂起 realtime socket，但这次主动 `disconnect` 会沿用普通断线路径，被投影成房间 `reconnecting`，最终显示“会话已刷新，正在重新恢复”。

正确修复不是禁止重连，也不是简单隐藏文案，而是把 realtime 生命周期拆成三类稳定语义：

```text
运行时主动挂起 / 短暂后台恢复
  -> 静默处理，不显示会话刷新

普通网络临时断线
  -> 轻量同步态，可短暂显示“正在同步”

invalid_session / 真实恢复失败
  -> 才刷新会话并显示强提示
```

产品标准是：用户切出去再回来，感觉群聊一直开着；系统内部可以重连、补消息、恢复 WebTorrent peer，但不把技术状态暴露给用户。

## 2. 前因后果

### 2.1 用户现象

公网群聊里，用户正在发文字、图片、视频和附件。切换页面、挂后台或稍后回来时，页面似乎会重连，并显示：

```text
会话已刷新，正在重新恢复
```

用户体感不是“系统在后台悄悄补同步”，而是“我是不是掉线了、会话是不是刷新了、群聊是不是重新进入了”。这会破坏万人实时 IM 的丝滑感。

### 2.2 为什么重连本身正常

浏览器和移动端环境里，后台冻结、网络切换、标签页休眠、Cloudflare/Caddy/socket 心跳超时都会造成连接断开。生产级 IM 不应该追求“永不断线”，而应该做到：

```text
断线可恢复
漏消息可补齐
短暂离开不等于新会话
用户无须理解内部重连
```

Socket.IO 官方把临时断线和主动断开区分开；临时断线会自动重连，连接恢复后可以通过 connection state recovery 或业务 cursor 补漏事件。WebTorrent 官方也提供 torrent `pause()` / `resume()` 生命周期，不要求后台回来时销毁媒体会话再重建。

### 2.3 当前产品问题

当前问题不是“会重连”，而是两个语义混在一起：

1. **浏览器后台恢复**：正常生命周期变化，应该静默；
2. **会话失效刷新**：`invalid_session` 之类真实权威会话失效，才应该提示。

现在 UI 文案把普通 `reconnecting` 直接说成“会话已刷新”，语义过重。

## 3. 当前源码事实

### 3.1 生命周期运行时会产生后台/冻结信号

`frontend/平台/生命周期运行时.ts` 把浏览器事件收口成稳定快照：

```text
visibilitychange -> active/background
pagehide         -> page_hidden
freeze           -> frozen
resume/pageshow  -> active/resumed
```

它本身只描述浏览器阶段，不解释聊天业务。

### 3.2 传输运行时会把 page_hidden/frozen 翻译成 suspend

`frontend/平台/传输运行时.ts` 当前策略：

```text
phase=page_hidden/frozen
  -> { intent: "suspend", reconnection: false, reason: "page_hidden" }

visibility=hidden/background
  -> { intent: "resume", reconnection: false, reason: "background" }

active
  -> { intent: "resume", reconnection: true, reason: "active" }
```

这个方向是合理的：后台冻结时节省 realtime 资源，回来再恢复。

### 3.3 平台层先挂起 transport，再广播生命周期事件

`frontend/平台/浏览器应用平台.ts` 的 lifecycle 订阅当前顺序是：

```text
transport.接收生命周期变化(snapshot)
广播浏览器运行时事实({ type: "LIFECYCLE_CHANGED", snapshot })
```

也就是说，传输层可能先触发 socket 行为，应用内核稍后才收到 `LIFECYCLE_POLICY_CHANGED`。

### 3.4 实时连接适配会主动断开 socket

`frontend/聊天实时/适配/实时连接适配.ts` 收到 `intent: "suspend"` 时会执行：

```text
socket.disconnect()
```

并用 `state.由运行时挂起` 记录这是运行时主动挂起。

问题是这个标记只留在适配器内部，没有进入后续 `disconnect` 事件语义。

### 3.5 实时应用把所有 disconnect 都上报为 SOCKET_DISCONNECTED

`frontend/实时/应用.ts` 当前监听：

```text
socket.on("disconnect", reason => {
  接收实时会话事实({
    type: "SOCKET_DISCONNECTED",
    code: reason || "disconnect"
  })
})
```

无论是网络断开、服务端踢下线，还是运行时自己 `socket.disconnect()`，都会变成同一种事实。

### 3.6 实时会话机把断线投影成重连需求

`frontend/实时/会话运行时.ts` 在收到 `SOCKET_DISCONNECTED` 后，如果已绑定房间且当前不是 `suspended`，会设置：

```text
connectionState = "reconnecting"
needsResubscribe = true
```

随后 `frontend/应用根/聊天应用内核.ts` 看到 `needsResubscribe` 从 false 变 true，就发：

```text
RECONNECTING_STARTED
```

房间状态进入 `重连中`。

### 3.7 壳层把重连中显示成“会话已刷新”

`frontend/房间消息窗/视图.ts` 当前逻辑：

```text
recoveryState === "reconnecting"
  -> "会话已刷新，正在重新恢复"
```

但 `reconnecting` 不等于 `session refreshed`。这句文案把普通恢复态误说成权威会话刷新。

## 4. 根因链路

当前最可能的根因链是：

```text
用户切后台 / 浏览器 pagehide / freeze
  -> 传输运行时推导 intent=suspend
  -> 实时连接适配主动 socket.disconnect()
  -> disconnect 事件没有携带 runtime_suspend 语义
  -> 实时应用统一上报 SOCKET_DISCONNECTED
  -> 实时会话机认为需要重连或重订阅
  -> 聊天应用内核发送 RECONNECTING_STARTED
  -> 房间运行时进入 重连中
  -> 壳层显示 “会话已刷新，正在重新恢复”
```

这是一类状态语义错误：**系统自己为了后台省资源做的主动挂起，被后续状态机误认为需要面向用户表达的恢复事件。**

## 5. 产品目标

### 5.1 正常用户体验

用户只应该感受到：

```text
我打开群聊
  -> 切出去一下
  -> 回来以后群聊还在
  -> 新消息补上了
  -> 视频和附件还能继续
```

不应该看到“会话刷新”这种强提示。

### 5.2 分级提示规则

| 场景 | 系统行为 | 用户提示 |
|---|---|---|
| 短暂后台 / pagehide / freeze | 主动挂起 socket，回来静默恢复 | 不提示 |
| background hidden 但未冻结 | 降低重活，保持必要状态 | 不提示 |
| 网络临时断开 | 自动重连，按 latestEventPosition 补订阅 | 可短暂轻提示“正在同步” |
| `need_snapshot_reload` | 重拉房间快照 | 可轻提示 |
| `invalid_session` | 重新 bootstrap + reconnect + restore room | 才显示会话刷新 |
| 恢复失败 | 保留房间或进入可重试失败 | 显示失败提示 |

### 5.3 媒体体验红线

后台恢复不能重置媒体/WebTorrent 主链：

1. 不销毁全局播放器 owner；
2. 不清空附件 locator 缓存；
3. 不把 WebTorrent 会话当成新附件重新创建；
4. 恢复后允许 tracker/WebRTC 重新连 peer；
5. 正在输入的文字、滚动位置和当前房间视图尽量保留。

---

## 6. 修复方案

### 6.1 引入断线来源语义

给 realtime 断线事实增加来源，而不是只传 `code`：

```ts
type 实时断线来源 =
  | "runtime_suspend"
  | "temporary_transport"
  | "server_or_auth"
  | "manual_release";
```

`SOCKET_DISCONNECTED` 扩展为：

```ts
{
  type: "SOCKET_DISCONNECTED";
  code: string;
  source?: 实时断线来源;
}
```

兼容原则：未传 `source` 的旧路径按 `temporary_transport` 处理。

### 6.2 让运行时挂起不进入用户可见重连态

`实时连接适配` 已经知道 `state.由运行时挂起`。修复应把这个事实带给 `frontend/实时/应用.ts`，让 disconnect 回调能判断：

```text
如果当前 socket 是由运行时挂起
  -> 上报 SOCKET_DISCONNECTED source=runtime_suspend
  -> 实时会话机进入 suspended 或保持静默
  -> 不触发 RECONNECTING_STARTED
```

实现可以二选一：

1. 在 socket 上挂一个弱引用状态查询能力，例如 `读取Socket运行时状态(socket)`；
2. 在 `实时连接适配` 包装 socket 时提供 `isRuntimeSuspended(socket)` 给 `实时应用`。

推荐方案：**通过 `聊天实时连接端口` 暴露只读查询方法**，避免把状态塞进 socket 对象。

接口示意：

```ts
interface 聊天实时连接端口 {
  createSocket(sessionId: string, powToken?: string): Socket;
  读取Socket运行时挂起状态?(socket: Socket): boolean;
}
```

### 6.3 调整实时会话机状态推导

`frontend/实时/会话运行时.ts` 应明确区分：

```text
runtime_suspend
  -> connectionState = "suspended"
  -> needsResubscribe = false

temporary_transport
  -> connectionState = "reconnecting"
  -> needsResubscribe = online && heavyWorkPolicy !== "suspended"

server_or_auth / invalid_session
  -> connectionState = "reconnecting"
  -> 交给恢复编排刷新会话
```

这样后台挂起不会触发房间 `RECONNECTING_STARTED`。

### 6.4 恢复 active 时静默 resubscribe

从 `suspended` 回到 `normal` 时，如果房间仍绑定、在线且 socket 已恢复，允许静默重订阅：

```text
heavyWorkPolicy: suspended -> normal
  -> 如果连接不是 active，则 ensureRealtimeSocket
  -> subscribeRoom(latestEventPosition)
  -> 不发送 RECONNECTING_STARTED
```

这里的关键是：**补订阅是业务恢复动作，不等于用户可见会话刷新。**

### 6.5 收口房间提示文案

`frontend/房间消息窗/视图.ts` 不应把所有 `reconnecting` 都叫“会话已刷新”。建议分两步：

第一步最小修复：

```text
reconnecting + lastRecoveryErrorCode=invalid_session
  -> "会话已刷新，正在重新恢复"

reconnecting + 普通断线
  -> "正在同步最新消息"

runtime suspend / silent resume
  -> ""
```

第二步如果状态机需要更清晰，可以把房间壳外观拆成：

```ts
recoveryState:
  | "idle"
  | "silent_resuming"
  | "syncing"
  | "session_refreshing"
  | "retryable_failure";
```

推荐先做第一步，除非 TDD 证明现有三态无法表达静默恢复。

### 6.6 只让 invalid_session 触发“会话已刷新”

`frontend/聊天恢复/壳层/会话失效恢复.ts` 的 `刷新会话()` 才是真正会执行 bootstrap + disconnectRealtime + 应用引导身份 + `SESSION_REFRESHED` 的路径。

因此“会话已刷新”这个文案必须绑定到：

```text
SESSION_REFRESHED
或 invalid_session 恢复链路
```

而不是绑定到普通 `RECONNECTING_STARTED`。

## 7. TDD 设计

### 7.1 RED：runtime suspend 不显示会话刷新

测试位置：

- `frontend/tests/聊天应用内核/平台生命周期与运行时状态测试.spec.ts`
- 或新增 `frontend/tests/聊天应用内核/后台恢复静默重连测试.spec.ts`

用例：

```text
给定用户已进入房间且 realtime 已订阅
当 dispatch PLATFORM_LIFECYCLE_CHANGED phase=page_hidden
并模拟 socket disconnect reason=io client disconnect
则聊天快照 recoveryState 不应变成 reconnecting
且壳层不应派生 “会话已刷新，正在重新恢复”
```

### 7.2 RED：active 恢复后会静默重订阅

用例：

```text
给定后台挂起期间房间仍绑定 latestEventPosition=42
当生命周期从 frozen/page_hidden 回到 active
则 ensureRealtimeSocket(sessionId) 被调用
且 subscribeRoom(42) 被调用
但房间内核不收到 RECONNECTING_STARTED
```

### 7.3 RED：普通网络断线仍能恢复

用例：

```text
给定房间在线中
当 socket disconnect source=temporary_transport
则实时会话 needsResubscribe=true
应用内核仍发送 RECONNECTING_STARTED
后续 SUBSCRIPTION_ESTABLISHED 后 recoveryState 回到 idle
```

这防止修复过头，把真正网络恢复能力关掉。

### 7.4 RED：invalid_session 仍显示强恢复

用例：

```text
当 connect_error/control_result 返回 invalid_session
则恢复编排执行 刷新会话
房间内核收到 SESSION_REFRESHED
壳层允许显示 “会话已刷新，正在重新恢复”
```

这保证安全和会话失效链路不被静默吞掉。

## 9. 不做的事

1. 不禁止 socket 自动重连；
2. 不删除房间恢复编排；
3. 不把所有恢复提示都隐藏；
4. 不把后台恢复改成全量刷新；
5. 不清空 timeline、输入框、滚动位置或媒体 owner；
6. 不在实时 adapter 里直接操作房间 UI；
7. 不引入第二套 WebSocket 或 WebTorrent 生命周期 owner。

## 10. 风险与约束

### 10.1 风险：把真实断线误当静默挂起

如果 source 标记不准，真实网络断线可能不触发重订阅。测试必须覆盖 `temporary_transport` 仍会走 `RECONNECTING_STARTED`。

### 10.2 风险：active 恢复后漏补订阅

如果从 `suspended` 回到 `normal` 时只 connect 不 subscribe，后台期间消息可能漏掉。恢复用例必须断言 `subscribeRoom(latestEventPosition)`。

### 10.3 风险：invalid_session 被静默吞掉

`invalid_session` 是权威会话失效，必须继续走 `会话失效恢复协作.刷新会话()`。任何静默策略都不能覆盖它。

### 10.4 风险：文案修复掩盖状态机错误

单纯把文案改空不是修复。必须先让运行时主动挂起不进入房间 `重连中`，文案只是最后投影。

---

## 11. 成功标准

1. 用户短暂切后台/切页面回来，不再看到“会话已刷新，正在重新恢复”；
2. 后台回来后仍会静默重连和补订阅，后台期间新消息不丢；
3. 普通网络临时断线仍会自动恢复；
4. `invalid_session` 仍会刷新会话并允许强提示；
5. 输入框、滚动位置、媒体播放 owner、WebTorrent 预热状态不因短暂后台被重置；
6. 自动化测试覆盖 runtime suspend、silent resume、temporary disconnect、invalid session 四条路径；
7. 公网冒烟能证明用户体感是“群聊一直开着”。

## 12. 自审记录

### 第一遍：需求意图

本 spec 聚焦用户描述的“切后台回来像重连/刷新，并显示会话已刷新”。它没有把问题偷换成“隐藏提示”，而是定位到运行时主动挂起与真实会话刷新语义混淆。通过。

### 第二遍：架构边界

浏览器生命周期仍由平台层收口；realtime adapter 只暴露连接运行时事实；实时会话机裁决连接状态；房间内核裁决壳层恢复状态；UI 只做文案投影。没有让 adapter 直接操作 UI，也没有让 shell 自作连接真相。通过。

### 第三遍：验证闭环

TDD 覆盖 runtime suspend、active silent resume、temporary disconnect、invalid_session 四条关键路径；公网冒烟覆盖短后台、较长后台、真实断网和媒体不中断。通过。

### 100% 自信循环

当前设计作为修复依据有事实层面的充分信心：根因链路已由源码确认，核心修复是补充断线来源语义并收口用户可见恢复提示。最大风险是误吞真实断线，已通过 `temporary_transport` 和 `invalid_session` 回归测试约束。若实现时发现现有三态不足，应优先小幅扩展房间壳恢复状态，而不是堆 UI 特判。
