# 聊天恢复与展示语义收口设计

日期：2026-04-06  
状态：已确认，已按 review 补充防漂移细节  
范围：`koko` Web 聊天壳恢复体验、普通聊天视图展示语义、冷路径成员门禁一致性

## 0. 设计结论

这次不是继续往聊天页上堆功能，而是把已经暴露出来的体验和边界问题收口成一套一致行为：

1. 刷新房间页后，应自动回到原房间，而不是掉回搜索页。
2. 普通用户视图不该看到 `session_id`、`event_position` 这类内部运行锚点。
3. 聊天列表不该显示 `[1] [2] [3]` 这种内部事件序号。
4. 聊天气泡必须区分“我发的”和“别人发的”，降低群聊阅读成本。
5. 房间快照和房间增量事件必须共用同一套成员资格门禁，不能一条冷路径有门，另一条冷路径裸奔。

这次设计只做“恢复、展示、门禁一致性”三件事，不扩成新的产品子系统。

## 0.1 官方最佳实践对齐点

这份设计不是只按主观体验写的，关键边界直接对齐了已经查过的一手资料：

1. Socket.IO 官方明确：`room` 是 server-only 的广播分组，不是业务成员真相；`connection state recovery` 不保证永远成功；默认交付语义不是“必达”，应用仍要自己做持久化和 offset 补齐。
2. Telegram 官方更新机制明确：一旦本地状态与远端状态之间出现 gap，客户端必须按同步锚点补洞，而不是假设“连接恢复了就一定同步好了”。
3. WhatsApp Multi-device 官方资料明确：设备连接态不是业务真相，真正稳定的是“账号/设备映射 + 消息历史和应用状态同步”。

落到 `koko` 的直接约束只有三条：

1. `current_room_id` 只是壳层恢复锚点，不是成员真相。
2. `event_position` 是同步锚点，不是普通用户主视图元素。
3. 冷路径、热路径、刷新恢复都必须以后端成员资格裁决为准。

## 1. 背景与问题

当前用户测试已经暴露出 4 个直接体验问题：

1. 正在房间里聊天时刷新页面，会回到房间搜索页。
2. 房间搜索页直接展示 `session: s-xxxx`。
3. 消息前面显示 `[1] [2] [3]` 这类事件序号。
4. 我发的消息和别人发的消息都堆在左边，不利于快速阅读。

同时又暴露出一个后端边界问题：

1. 房间快照接口会校验成员资格。
2. 房间增量事件接口当前没有同样的成员资格收口。
3. 这会造成“同一个房间事实，冷热路径两套门禁”的漂移风险。

## 2. 目标

本次设计必须同时达到两个结果：

1. 用户体验变对：
   - 刷新后自动回房；
   - 普通聊天视图更像成熟 IM；
   - 内部锚点不再裸露给普通用户。
2. 真相边界更稳：
   - `room` 仍只是广播分组；
   - 成员资格仍由后端统一裁决；
   - 冷路径补洞与快照门禁保持一致。

## 3. 明确不做

本次明确不做：

1. 改造匿名身份模型或重新设计 bootstrap 契约。
2. 增加已读、在线状态、时间分组、回复链等新聊天功能。
3. 为后端增加“最近房间列表”或“服务端主导页面恢复流程”。
4. 扩大成移动端、CLI 或多节点设计改造。
5. 让共享 `contract` 携带任何 Web 专属展示字段。

## 4. 设计原则

### 4.1 壳层可以记住入口锚点，但不能宣布业务真相

Web 壳可以本地持久化：

1. `device_anonymous_token`
2. `current_room_id`

但它不能因此宣布：

1. 我一定还是该房成员。
2. 我一定能继续看这个房间的快照或增量。
3. 我本地看到的 pending / connected 就等于消息成立或同步成立。

### 4.2 展示模型属于壳层，稳定事实属于契约

共享契约仍然只提供稳定事实字段，例如：

1. `session_id`
2. `sender_session_id`
3. `display_alias`
4. `event_position`

Web 壳允许在本地派生：

1. 这条消息是不是我发的
2. 左右布局
3. 是否弱化自己的名字

但不得把这些展示语义倒灌进共享契约。

### 4.3 冷路径和热路径必须说同一套真话

连接有效、房间成员资格、消息成立、同步恢复这几件事不能分散在不同入口各说各话：

1. connect middleware 只证明连接绑定了有效 `session`。
2. 是否能看某房间，必须由用例层统一做成员资格校验。
3. HTTP 快照接口和 HTTP 增量接口必须共用同一成员资格门禁。
4. realtime 订阅也必须复用同一成员资格门禁。

## 5. 刷新恢复设计

### 5.1 壳层本地持久化

Web 本地只新增一个恢复锚点：

1. `current_room_id`

本地持久化键名固定为：

1. `koko_device_anonymous_token`
2. `koko_current_room_id`

这样做的目的不是“好看”，而是避免后面出现：

1. 同一含义被多个 localStorage key 重复保存
2. 测试和实现各自发明不同键名
3. 恢复逻辑和清理逻辑打不到同一个存储点

写入时机：

1. 进房成功后写入
2. 切换到新房间成功后覆盖旧值
3. 成功恢复房间后保持

清理时机：

1. 恢复时发现成员资格已失效
2. 房间不存在
3. 增量/快照/订阅恢复链路明确返回无权访问

不清理的情况：

1. 页面只是临时断线，但当前房间仍然存在且成员资格仍有效
2. 只是 realtime 尚未连上，但快照仍然可用
3. 请求超时、网络断开、5xx 这类临时失败

### 5.2 页面启动顺序

页面启动后固定执行这条顺序：

1. 用 `device_anonymous_token` 做匿名身份 bootstrap
2. 建立 realtime 连接
3. 如果本地存在 `current_room_id`，则尝试用当前 `session_id` 加载该房间快照
4. 快照成功则进入房间页
5. 再按快照中的 `latest_event_position` 建立订阅或补洞
6. 若快照命中硬失效，则清掉 `current_room_id`，退回搜索页
7. 若快照命中临时失败，则保留 `current_room_id`，停留在“恢复失败可重试”状态，不把它误判成永久失效

这里再明确两个边界：

1. 房间页是否可渲染，首先看快照是否成立，不要求必须等 realtime 已连上才显示房间页。
2. realtime 连接晚一点恢复，只影响是否继续收流，不影响“用户仍在这个房间”的快照事实。

`current_session_id` 的唯一来源也在这里写死：

1. 它只来自 bootstrap 成功后返回的权威 `session_id`
2. Web 壳不在本地自行生成、猜测或长期单独持久化 `session_id`
3. 只有拿到本次 bootstrap 返回的 `session_id` 后，才允许执行：
   - 加载房间快照
   - 拉增量事件
   - 建立 realtime 连接上下文
4. 所以恢复顺序不可倒置成“先按旧 session 恢复房间，再 bootstrap”

### 5.3 恢复链路

恢复语义保持和现有系统一致，只是把刷新后自动恢复补上：

1. 优先沿用现有 `latest_event_position`
2. `from` 的语义保持为“从该事件位置之后开始拉取增量”，也就是服务端返回 `event_position > from` 的事件
3. 所以：
   - 已拿到快照后的 HTTP 补洞使用 `from = latest_event_position`
   - realtime 续订阅也使用当前已知 `latest_event_position` 作为起点
4. 续接成功则继续事件流
5. 若需要补洞，则按 `event_position` 拉增量
6. 再次补洞时仍复用同一边界语义，不使用 `latest_event_position + 1`
7. 若增量闭不上，则重拉快照
8. 若快照和增量都因成员资格失败而拒绝，则退出房间并清掉本地锚点

### 5.4 房间失效、删除、改名边界

为避免实现阶段各写一套边角逻辑，这里把最容易漂的分支写死：

1. 若 `current_room_id` 存在，但后端返回 `room_not_found`：
   - 视为该恢复锚点失效；
   - 清掉 `koko_current_room_id`；
   - 回到搜索页；
   - 不保留“假装还在房间里”的 UI。
2. 若 `current_room_id` 存在，但后端返回成员资格不足：
   - 同样清掉 `koko_current_room_id`；
   - 回到搜索页；
   - 这表示“你曾经在这里，但现在已经没资格了”。
3. 若未来房间展示名、短码、标题发生变化，但稳定 `room_id` 没变：
   - 不清掉 `koko_current_room_id`；
   - 继续按稳定 `room_id` 恢复；
   - 页面展示名称以后端最新快照为准。
4. 若恢复时遇到超时、网络错误或 5xx：
   - 不清掉 `koko_current_room_id`；
   - 不把用户立即踢回搜索页；
   - 页面显示“恢复失败，可重试”或等价提示；
   - 允许用户手动重试恢复。

换句话说：

1. `room_id` 是恢复锚点；
2. `room_code/title` 之类的展示字段不是恢复锚点。
3. 只有 404/403 这类硬失败才让恢复锚点失效；临时失败只中断本次恢复，不宣告锚点失效。

## 6. 聊天视图设计

### 6.1 搜索页与房间页的信息边界

普通用户页允许展示：

1. 当前花名
2. 当前房间标识
3. 消息内容
4. 发送者花名
5. 必要的连接或错误提示

普通用户页不再展示：

1. `session_id`
2. `event_position`
3. 内部错误码
4. 任何“同步序号”或“协议位置”

### 6.2 消息列表展示

消息列表改成气泡式阅读模型：

1. 自己发的消息靠右
2. 别人发的消息靠左
3. 别人的消息显示发送者花名
4. 自己的消息可以弱化名字，但不额外暴露内部身份

补充两条，防止实现时跑偏：

1. “靠右/靠左”是阅读结构，不要求为了视觉效果引入第二套消息事实模型。
2. 消息气泡排版不能依赖“当前 DOM 顺序碰巧是正确的”，仍以 `event_position` 排序后的稳定消息列表为基础。

### 6.3 消息序号处理

`event_position` 继续保留在同步链路里，但不再渲染成普通聊天文案的一部分。

普通用户消息格式从：

1. `[event_position] display_alias: body`

收口为：

1. 面向阅读的聊天气泡

如果未来要保留调试可见性，也只能作为开发调试开关，不进入默认视图。

### 6.4 “是不是我发的”的判断

Web 壳本地按下面的稳定事实派生展示：

1. 若 `message.sender_session_id === current_session_id`，则按“我发的”渲染
2. 否则按“别人发的”渲染

这只是展示判断，不是业务真相判断。

## 7. 后端门禁一致性设计

### 7.1 冷路径增量接口补齐成员门禁

`GET /api/rooms/{room_id}/events` 需要补齐与快照接口一致的调用语义：

1. 请求形状固定为：`GET /api/rooms/{room_id}/events?session_id={session_id}&from={event_position}`
2. `session_id` 继续使用 query 参数，与当前 `snapshot` 接口保持同一风格
3. `from` 的语义固定为“从该事件位置之后开始返回增量事件”
4. 必须执行成员资格校验
5. 成功后才能返回该房间增量事件

错误语义也一并固定：

1. `session_id` 缺失：返回 `invalid_argument`
2. `session_id` 结构存在但不是有效会话：返回 `invalid_session`
3. `room_id` 不存在：返回 `room_not_found`
4. 不是该房成员：返回 `membership_required`
5. `from < 0` 或其它非法偏移：返回 `invalid_argument`

这样可以避免后面出现：

1. 快照接口和增量接口状态码不同
2. 前端对“退出房间还是重试”做错分支

这样它的语义才是：

1. 某个合法会话，请求查看自己有权看到的房间增量事件

而不是：

1. 任何知道 `room_id` 的人都能补洞

### 7.2 用例层责任不变

用例层继续裁决：

1. `session` 是否有效
2. 当前 `session` 是否为该房成员
3. 是否允许看快照
4. 是否允许拉增量
5. 是否允许订阅
6. 是否允许发消息

adapter 层继续只做：

1. HTTP 参数翻译
2. realtime 连接上下文翻译
3. 错误转码

### 7.3 realtime 边界不变

realtime connect 成功只说明：

1. 当前连接绑定了一个有效会话

不说明：

1. 它已经有某房间成员资格
2. 它有权订阅任意房间

是否能 join 某个 room，仍以后端成员资格裁决为前提。

### 7.4 连接、订阅、消息成立三件事必须分开

这三件事容易在执行时重新糊成一锅，这里单独钉死：

1. connect succeeded：
   - 只代表 socket 连接已绑定合法 `session`
   - 不代表已进入某房
2. subscribe succeeded：
   - 代表当前连接已通过成员资格校验，并加入该房间的广播分组
   - 不代表有新消息成立
3. room_event / authoritative snapshot：
   - 才代表某条业务事实已经成立并可见

所以：

1. 不得把 connect ack 当“回房成功”
2. 不得把 subscribed control_result 当“消息已发送成功”
3. 不得把 pending 或 optimistic UI 当权威消息事实

### 7.5 恢复链路失败矩阵

为避免实现阶段在不同失败点各自发挥，这里把 `snapshot -> events -> subscribe` 的前端动作写死：

1. `snapshot` 返回 `room_not_found`：
   - 清掉 `koko_current_room_id`
   - 退出房间页
   - 回到搜索页
2. `snapshot` 返回 `membership_required`：
   - 清掉 `koko_current_room_id`
   - 退出房间页
   - 回到搜索页
3. `snapshot` 返回 `invalid_session`：
   - 不复用旧 `session_id`
   - 立即重新走 bootstrap 获取新权威 `session_id`
   - 若重新 bootstrap 后仍无法恢复，再按新的错误结果走对应分支
4. `snapshot` 返回网络错误 / 超时 / 5xx：
   - 保留 `koko_current_room_id`
   - 不进入“永久退出房间”分支
   - 显示恢复失败，可手动重试
5. `events` 返回 `room_not_found` 或 `membership_required`：
   - 视为当前房间锚点已失效
   - 清掉 `koko_current_room_id`
   - 回到搜索页
6. `events` 返回 `invalid_session`：
   - 重新 bootstrap 获取新权威 `session_id`
   - 不直接清掉 `koko_current_room_id`
   - 若重新 bootstrap 后再次失败，再按新错误结果分支处理
7. `events` 返回网络错误 / 超时 / 5xx：
   - 保留当前房间页基线快照
   - 保留 `koko_current_room_id`
   - 标记为“同步暂时失败，可继续重试”
8. `subscribe_room_stream` 返回 `rejected` 且错误是成员资格不足或房间不存在：
   - 说明快照已过时或资格在恢复间隙内发生变化
   - 清掉 `koko_current_room_id`
   - 退出房间页并回到搜索页
9. `subscribe_room_stream` 返回 `rejected` 且错误是 `invalid_session`：
   - 重新 bootstrap 获取新权威 `session_id`
   - 成功后重新进入恢复链路
   - 不直接把当前房间锚点判死
10. `subscribe_room_stream` 返回 `error` 或 emit/网络类临时失败：
   - 保留当前房间页与快照
   - 保留 `koko_current_room_id`
   - 展示“实时连接暂不可用，正在重试”或等价提示

这张失败矩阵的根规则只有一句话：

1. 403/404 是硬失效，清锚点并退出房间；
2. 超时、断网、5xx 是临时失败，保留锚点并允许重试。

## 8. 测试与验收

### 8.1 前端壳测试

前端测试至少补齐这些场景：

1. 本地存在 `current_room_id` 时，启动后会尝试恢复房间
2. 恢复成功则直接进入房间页
3. 恢复失败则清掉 `current_room_id` 并回到搜索页
4. 进房成功会写入 `current_room_id`
5. 切换房间成功会覆盖旧的 `current_room_id`
6. 搜索页与房间页都不再显示 `session_id`
7. 消息列表默认不显示 `event_position`
8. 自己消息靠右，别人消息靠左
9. `current_room_id` 指向已不存在房间时，会清理本地锚点并回到搜索页
10. `current_room_id` 指向已无成员资格的房间时，会清理本地锚点并回到搜索页
11. `current_room_id` 指向有效房间，但恢复请求超时/5xx 时，不会清理本地锚点
12. 快照成功后订阅临时失败时，会保留房间页并显示可重试/重连提示
13. 快照成功后订阅被硬拒绝时，会清理本地锚点并回到搜索页

### 8.2 HTTP / 集成测试

后端测试至少补齐这些场景：

1. `events` 接口未带 `session_id` 时被拒绝
2. 非成员请求 `events` 接口时被拒绝
3. 成员请求 `events?session_id=...&from=...` 时成功
4. `from = latest_event_position` 时只返回更大的事件位置
5. `snapshot` 与 `events` 两条冷路径对同一成员资格事实保持一致
6. `room_not_found` 与 `membership_required` 会驱动前端走不同恢复分支

### 8.3 realtime 测试

保留并强调这些语义：

1. connect 成功不等于订阅成功
2. 非成员订阅房间被拒绝
3. 成员订阅成功后仍通过权威事件收消息
4. 快照先成功、realtime 后恢复时，不会错误把用户踢回搜索页
5. 快照先成功、但订阅被硬拒绝时，会退出房间而不是挂着旧快照假装在线

### 8.4 用户验收标准

用户验收只看这 5 条：

1. 刷新房间页不会掉回搜索页
2. 搜索页不再展示 `session_id`
3. 消息前面不再出现内部序号
4. 我发的消息靠右，别人靠左
5. 非成员不能通过冷路径事件接口偷看房间事件

## 9. 实施顺序

推荐实施顺序：

1. 先补 spec 对应测试
2. 再收口冷路径 `events` 门禁
3. 再补壳层 `current_room_id` 恢复逻辑
4. 最后收口聊天视图展示
5. 收尾时补一轮用户体验验收，确认恢复与展示没有被实现细节带偏

这个顺序的原因是：

1. 先把真相边界钉住
2. 再补页面恢复
3. 最后改 UI 展示

避免只把界面改顺眼，却把冷路径门禁继续漏着。

## 10. 一句话结论

这次设计要达成的不是“更好看的聊天页”，而是：

**让 Web 聊天壳在刷新恢复、普通用户展示语义、以及房间事实门禁上，重新说回同一套真话。**
