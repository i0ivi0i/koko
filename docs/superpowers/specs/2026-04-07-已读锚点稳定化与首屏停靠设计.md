# 已读锚点稳定化与首屏停靠设计

日期：2026-04-07  
状态：设计已确认，待进入 implementation plan  
范围：`frontend` 的房间首屏停靠、已读锚点采样、已读提交时机、新消息不抢视角、历史前插后的阅读稳定性  
约束：不改后端领域真相，不把前端做成第二套阅读真相源，不并入“前端房间编排内核重构”主 spec

## -1. 总原则

这次优化必须继续服从整个项目唯一的 DDD 真相体系：

1. 房间里“已读到哪里”的唯一业务真相，仍然只在后端成立。
2. 前端只允许观测视口、生成候选、提交推进请求，不允许自造阅读真相。
3. `event_position` 是阅读锚点语义；`scrollTop`、DOM 位置、像素可见性都只是观测工具。
4. UI 风格、布局、主题、组件树未来都可以继续变化，但用户阅读语义不能跟着漂移。
5. 这份 spec 是单独专项，不与“房间编排内核重构”混写，避免执行时主题串线。

一句话定性：

**这次不是改滚动效果，而是把“真实用户读到哪里”这条 IM 主链收稳。**

---

## 0. 一句话结论

当前系统的后端阅读真相模型是对的，问题主要在前端：

1. 首屏虽然围绕 `first_unread_event_position` 恢复，但视口落位仍然过于依赖 DOM 时序；
2. 已读推进仍然偏“滚动驱动”，没有把“围绕未读阅读”和“贴底跟随”清晰区分；
3. 新消息到达时，前端还缺少一套稳定的“是否允许抢视角”裁决语义。

本次专项的目标，是把前端收成更接近 Telegram 的阅读模型：

1. 久未进入房间时，首屏停在第一条未读附近；
2. 用户正在补旧未读时，新消息持续进入也不能把视角抢走；
3. 用户本来就在底部时，新消息才允许自然跟随；
4. 已读推进只按单调前进的 `event_position` 提交，不按滚动条像素猜真相。

## 1. 背景与问题

当前系统已经拥有正确的后端阅读语义：

1. [src/契约.rs](/E:/koko/src/契约.rs) 中明确区分了：
   - `上次已读事件位置`
   - `首条未读事件位置`
   - `首屏消息`
2. [src/用例.rs](/E:/koko/src/用例.rs) 在应用层裁决：
   - `first_unread_event_position = last_read_event_position + 1`
3. [src/适配.rs](/E:/koko/src/适配.rs) 只围绕这个锚点构建恢复快照窗口，不把判断下放给前端。

问题主要集中在前端三处：

1. [frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts) 的首屏落位虽然能工作，但“节点没准备好时是否算完成”仍然不够稳。
2. [frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts) 当前只按“最后一条完全可见消息”采样阅读候选，这在长消息、动态高度、移动端键盘场景下容易抖。
3. [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 的阅读推进仍然更像“节流后的滚动副作用”，而不是成熟 IM 的“视口语义裁决 + 单调提交”。

因此，当前用户会在这些场景里感到“不稳”：

1. 刷新恢复后，视角有时停靠不准；
2. 正在补旧未读时，新的实时消息会和当前阅读状态发生竞争；
3. 已读推进时机不够像真实阅读，更像“碰巧滚到了”。

## 2. 外部最佳实践校准

### 2.1 Telegram 的公开同步模型

Telegram 官方文档能直接确认这几件事：

1. 对话状态里有 `read_inbox_max_id`、`unread_count`、`top_message` 这类逻辑锚点。  
   来源：[dialog](https://core.telegram.org/constructor/dialog)
2. 聊天已读不是像素概念，而是“读到某个最大消息 ID 为止”。  
   来源：[messages.readHistory](https://core.telegram.org/method/messages.readHistory)
3. 服务端会下发权威已读更新，里面仍是 `max_id`。  
   来源：[updateReadHistoryInbox](https://core.telegram.org/constructor/updateReadHistoryInbox)  
   来源：[updateReadChannelInbox](https://core.telegram.org/constructor/updateReadChannelInbox)
4. 客户端启动、断线、漏事件后，必须先补差量，再恢复界面。  
   来源：[Working with Updates](https://core.telegram.org/api/updates)

这些资料共同指向一个结论：

**Telegram 设计的是“从上次读到哪里继续读”，不是“进来就看最新”，也不是“退回最早消息重读”。**

### 2.2 Socket.IO / socketioxide 的公开约束

Socket.IO 官方文档明确给出：

1. 默认保证顺序，但默认投递语义只有 `at most once`。  
   来源：[Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)
2. 断线恢复不一定总成功，应用层仍必须准备快照同步与补洞。  
   来源：[Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/)
3. `retries` 与 `ackTimeout` 只适合建立在服务端 ack 协议上的 `client -> server` 投递。  
   来源：[Client options](https://socket.io/docs/v4/client-options/)  
   来源：[Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)
4. `socketioxide` 兼容这套语义，也原生支持 ack 提取器，但 ack 只代表传输确认，不代表业务成立。  
   来源：[socketioxide](https://docs.rs/socketioxide/latest/socketioxide/)  
   来源：[AckSender](https://docs.rs/socketioxide/latest/socketioxide/extract/struct.AckSender.html)

这意味着：

1. 阅读真相不能建立在“socket 看起来在线”上；
2. 阅读推进不能建立在“页面似乎滚到了某处”上；
3. 前端必须把“视口候选”与“权威已读提交”分开。

## 3. 设计目标

### 3.1 必须达到

1. 久未进入房间时，首屏稳定停在第一条未读附近，而不是最早消息或无脑最新。
2. 用户正在补旧未读时，新消息持续进入也不能抢夺当前视角。
3. 用户已贴近底部时，新消息允许自然跟随。
4. 已读推进继续只按 `event_position` 单调前进。
5. 刷新、重连、补历史、新消息插入都不能让视角突然漂移。
6. 新设计必须能稳定挂在现有的：
   - [frontend/房间内核.ts](/E:/koko/frontend/房间内核.ts)
   - [frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts)
   - [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts)

### 3.2 明确不做

1. 不修改后端 `first_unread_event_position` 的裁决方式。
2. 不让前端把 `scrollTop` 存成阅读真相。
3. 不把“已读稳定化”做成视觉动画专项。
4. 不在这次专项里引入新的协议机制、第二套同步锚点或第二套快照语义。
5. 不在这次专项里顺手改房间成员资格、权限、消息成立等领域规则。

## 4. 真相边界

### 4.1 后端继续拥有的真相

1. `last_read_event_position`
2. `first_unread_event_position`
3. `latest_event_position`
4. 房间快照窗口如何围绕未读起点构建
5. 已读推进只能单调前进
6. 成员资格与订阅资格

### 4.2 前端只允许拥有的壳层事实

1. 当前视口模式
2. 当前候选已读锚点
3. 当前是否贴底
4. 当前是否正在执行程序性恢复滚动
5. 当前首屏停靠是否已经稳定完成

### 4.3 绝对禁止

1. 前端根据“消息已经出现在视口里”直接宣布业务已读成立
2. 前端根据“socket 正常”宣布恢复已完成
3. 前端根据“滚动条在底部附近”直接宣布所有最新消息都已读
4. 前端根据视觉布局变化修改 `first_unread_event_position` 的语义

## 5. 核心概念

### 5.1 视口模式

本次专项引入一个前端壳层概念：

**视口模式**

它不是领域真相，只是前端为了稳住阅读体验所需的同步编排态。

只允许这 3 种：

1. `围绕未读阅读`
   - 用户当前主要在补旧未读；
   - 新消息到达不能抢视角；
   - 已读推进只能围绕当前已稳定看到的更后位置逐步前进。

2. `贴底跟随`
   - 用户当前已经贴近底部；
   - 新消息到达可以自然跟随；
   - 更适合推进已读。

3. `离底浏览`
   - 用户不在底部，也不一定在围绕旧未读阅读；
   - 可能是在浏览中间历史；
   - 新消息到达同样不能抢视角。

### 5.2 候选已读锚点

候选已读锚点是：

1. 前端根据视口稳定观测得出的“用户大概率已经读到这里”的临时结果；
2. 只能单调增大；
3. 不能直接等于后端真相；
4. 必须经过内核裁决后，才允许提交。

### 5.3 已读提交锚点

已读提交锚点是：

1. 前端决定正式调用 `updateRoomReadAnchor` 时使用的位置；
2. 只能建立在：
   - 候选锚点已稳定
   - 当前模式允许推进
   - 当前不是程序性滚动
   - 位置确实大于现有已读

## 6. 首屏停靠规则

### 6.1 有未读时

如果后端快照返回了 `first_unread_event_position`：

1. 首屏必须围绕这条消息落位；
2. 不是把它死贴顶部；
3. 也不是强制永远居中；
4. 更合理的效果是：
   - 让第一条未读附近进入视口中心偏上区域；
   - 同时保留少量上文；
   - 让用户一眼知道“我是从这里继续读”。

### 6.2 无未读时

如果后端返回 `first_unread_event_position = null`：

1. 首屏应停在较新消息附近；
2. 通常接近底部；
3. 如果未来引入本地“最近浏览位置”壳层缓存，也只能作为体验增强，不得覆盖后端已读真相。

### 6.3 首屏定位完成的判定

这次必须把“首屏定位完成”的判定写死：

1. 不是“调用过一次滚动”就算完成；
2. 不是“尝试找过节点”就算完成；
3. 只有当目标落位已经真正稳定，且滚动器完成了一次稳定观测后，才允许把 `initialUnreadSettled` 记为完成。

### 6.4 节点未准备好的处理

如果 `first_unread_event_position` 对应节点这轮还没稳定出现：

1. 不允许直接结案；
2. 不允许退化成默认停在顶部；
3. 应等待下一次渲染稳定后再试；
4. 只有在证据明确表明这次快照窗口里本来就不包含它时，才允许走异常回退路径。

## 7. 新消息到达规则

### 7.1 贴底跟随

如果当前视口模式是 `贴底跟随`：

1. 权威新消息到达后，允许视角自然继续贴底；
2. 允许把这些消息纳入候选已读范围；
3. 允许较快推进已读提交。

### 7.2 围绕未读阅读

如果当前模式是 `围绕未读阅读`：

1. 新消息到达不能抢走当前视角；
2. 不允许因为“新消息进来了”就自动把视角拉到底；
3. 不允许直接把已读推进到这些更新消息；
4. 只能提示“有更新”或累积新消息计数。

### 7.3 离底浏览

如果当前模式是 `离底浏览`：

1. 新消息到达同样不能抢视角；
2. 不允许自动贴底；
3. 可展示“跳到最新消息”入口，但不改变当前阅读位置。

### 7.4 单一原则

这条规则必须成为代码注释和测试都能直接看懂的硬约束：

**只有本来就在底部的人，才应该跟着新消息走。**

## 8. 已读推进模型

### 8.1 两层模型

本次专项把已读推进拆成两层：

1. 观测层：滚动器产出候选已读锚点
2. 裁决层：内核决定是否提交已读推进

### 8.2 观测层职责

[frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts) 只负责：

1. 识别当前可稳定阅读的最靠后消息；
2. 判断是否贴底；
3. 判断是否仍在围绕未读阅读；
4. 区分程序滚动和用户滚动；
5. 在首屏、补历史、新消息到达后重新采样。

### 8.3 裁决层职责

[frontend/房间内核.ts](/E:/koko/frontend/房间内核.ts) 负责：

1. 候选位置是否比现有已读更靠后；
2. 当前视口模式是否允许推进；
3. 当前是否仍处于程序滚动窗口；
4. 是否需要等待一个稳定窗口再提交；
5. 是否应清除未读分隔；
6. 是否应保留“新消息未读”提示。

### 8.4 提交规则

只在同时满足以下条件时，才允许调用 `updateRoomReadAnchor`：

1. `candidate > max(lastRead, pendingReadAnchor)`
2. 当前房间仍然有效
3. 当前不处于 `restoring_unread` 或 `compensating_history`
4. 当前观测结果已经稳定
5. 当前模式允许推进

### 8.5 失败规则

如果提交失败：

1. 不能破坏当前房间视图；
2. 不能清空消息列表；
3. 不能把视口模式重置错；
4. 可以丢弃这次 pending，等待后续更晚的稳定候选再次触发。

## 9. 可见性采样规则

### 9.1 问题

当前“完全可见才算候选”的规则过于死板，会导致：

1. 长消息明明已经被用户读到，但因为气泡稍高而不被计入；
2. 设备键盘弹起或字体高度变化时，候选锚点忽前忽后；
3. 用户体验更像“浏览器算像素”，不像真实 IM。

### 9.2 新原则

候选已读采样要改成：

**稳定可读，而不是死板全可见。**

### 9.3 允许的实现方向

实现时允许采用以下任一稳定策略，但必须统一在滚动器里完成，不得散进壳层模板：

1. 视口覆盖率阈值
   - 消息主体进入视口超过某个比例，就可算候选
2. 中心线命中策略
   - 取视口中心线以下最近的稳定消息作为候选
3. 混合阈值策略
   - 对短消息使用更严格阈值；
   - 对长消息使用更宽容阈值

### 9.4 约束

1. 不能让同一次轻微布局抖动反复前后跳锚；
2. 不能让程序滚动直接触发候选推进；
3. 不能让长消息天然吃亏。

## 10. 刷新、重连、补历史的稳定性

### 10.1 刷新恢复

刷新恢复时应遵守：

1. 先恢复权威快照；
2. 再完成首屏停靠；
3. 首屏停靠稳定后，才允许产出恢复场景下的候选已读；
4. 不允许在 `bootView` 阶段提前结案。

### 10.2 重连恢复

重连时应遵守：

1. 先根据 `latest_event_position` 续接或回退快照；
2. 恢复后不要把用户从当前阅读段强拉到底；
3. 只有当前模式本来就是 `贴底跟随`，才允许继续自动跟底。

### 10.3 历史前插

补历史时应遵守：

1. 视口必须按 `scrollHeight` 差值补偿；
2. 历史前插后的滚动属于程序滚动，不得立刻产出用户已读推进；
3. 补偿稳定后可以重新采样候选，但不能直接跳过裁决层。

### 10.4 新消息与补历史并发

如果“历史页前插”和“realtime 新消息到达”并发发生：

1. 不能产生重复消息；
2. 不能错误清掉未读分隔；
3. 不能把用户从当前历史阅读段拽到底；
4. 不能把 `latestEventPosition` 与 `lastReadEventPosition` 混成一个量。

## 12. 测试矩阵

### 12.1 房间内核测试

必须补齐：

1. 处于 `围绕未读阅读` 时，新消息到达不会切到 `贴底跟随`
2. 用户明确回到底部后，才进入 `贴底跟随`
3. `离底浏览` 下，新消息到达不会自动推进已读
4. 候选已读锚点只允许单调前进
5. 程序滚动完成后，只能产生候选，不能直接视为已读提交

### 12.2 房间滚动器测试

必须补齐：

1. 有 `firstUnreadEventPosition` 但节点未出现时，不能提前宣布首屏定位完成
2. 首屏围绕未读稳定落位后，才允许产出恢复候选
3. 程序滚动不会被误判成用户滚动
4. 用户贴底时，新消息插入后仍保持贴底
5. 用户不贴底时，新消息插入不会把视角拉走
6. 长消息达到“稳定可读阈值”后也能成为候选

### 12.3 聊天壳集成测试

必须补齐：

1. 久未进入房间，恢复后停在第一条未读附近
2. 恢复后实时新消息持续到达，当前视角不会被抢走
3. 用户回到底部后，新消息才开始自然跟随
4. 刷新恢复后不会跳最顶
5. 历史前插后未读分隔不乱跳
6. 新消息到达但用户仍在补旧未读时，不会错误推进 `lastReadEventPosition`

### 12.4 真实链路测试

至少保留并增强以下场景：

1. A 很久没进房，B/C/D/E 持续发消息，A 再进入时停在第一条未读附近
2. A 不贴底时，新的实时消息不会把 A 拉走
3. A 回到底部后，新消息开始跟随
4. A 刷新页面后，仍回到正确未读窗口

---

## 13. 验收标准

这次专项完成后，必须达到：

1. 很久没进房，再进来不会跳最早消息
2. 有未读时，首屏停在第一条未读附近
3. 用户正在补旧未读时，新消息不能抢视角
4. 用户贴底时，新消息可以自然跟随
5. 已读推进只会单调前进，不会乱跳
6. 刷新、重连、补历史都不会把视口打坏

一句话总结：

**房间阅读体验要从“碰巧滚对了”升级成“语义上就是对的”。**
