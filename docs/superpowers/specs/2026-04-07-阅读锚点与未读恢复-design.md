# 阅读锚点与未读恢复设计

日期：2026-04-07  
状态：设计已确认，待写 implementation plan  
范围：`koko` 群聊房间的阅读锚点、未读恢复、历史分页滚动稳定性、Telegram 风格的再次进房体验

## 0. 先说结论

这次不是单纯修一个“上滑闪一下”的前端小毛病，也不是再补一层本地页面记忆。

这次真正要补的是两条真空：

1. 系统里还没有“同一个内部身份在同一个房间里，上次读到了哪”的后端真相。
2. 前端在历史分页时没有守住当前视口锚点，所以一旦顶部插入旧消息，画面就会跳、闪、抽搐。

一句话结论：

**学 Telegram，把“阅读到哪”做成后端保存的用户级状态；进入房间时围绕第一条未读恢复首屏；上滑补历史时由前端守住滚动锚点，不让视口跳动。**

---

## 1. bug 发生经过与表象

这次问题不是凭空猜出来的，而是从真实使用过程里连续暴露出来的。

### 1.1 现象一：上滑历史时会抽搐、闪烁

用户在房间中聊天时，向上滑动查看更早的聊天记录，尤其滑到最旧、最老那一批消息附近时，页面会：

1. 抖一下
2. 闪一下
3. 视觉位置突然跳动

用户感知上像是：

1. 系统在和手势打架
2. 当前正在看的那条消息被顶走了
3. 历史越接近顶部，越不稳定

### 1.2 现象二：再次进入房间时，落点不对

同一个用户正常使用群聊，聊完之后离开房间，或者关闭应用，过了较长时间后再次进入同一个群聊房间。

这时群里其他成员还在持续发消息，正确体验应该是：

1. 用户不是从最老消息开始看
2. 也不是盲目回到最新底部
3. 而是接着自己上次最后阅读到的地方附近继续看
4. 上面保留少量上下文
5. 后面是这段时间新增的未读内容

也就是说，进入房间的正确语义不是“看这房间最开始的内容”，而是“从我上次断开的阅读位置继续往下追”

### 1.3 两个问题其实是同一条链路上的不同断点

表面看，这像两个问题：

1. 滚动抖动问题
2. 再次进房落点问题

但本质上它们都来自同一条链路缺口：

1. 后端没有阅读锚点真相
2. 前端没有守住滚动锚点

所以这次不能只修某个滚动事件判断，也不能只补某个本地缓存键。

## 2. 现状审查结论

### 2.1 当前更像前端滚动锚点问题，不像后端历史真相丢失

根据当前实现，[聊天壳](E:\koko\frontend\聊天壳.ts) 在上滑时：

1. 通过 `scrollTop <= 0` 触发 `loadOlderHistory()`
2. 拉到更早历史后，直接把消息插到列表顶部
3. 立即整段重渲染消息列表
4. 但没有做“插入前后 scrollHeight 差值补偿”

这会直接导致：

1. DOM 变高
2. 浏览器当前可视区域被向下顶
3. 用户眼前正在看的那条消息发生突然位移

所以“抽搐闪烁”主因很像前端视口锚点丢失，不像后端把消息顺序给错了。

### 2.2 当前系统里也确实没有“阅读到哪”的后端真相

现在系统已有：

1. `device_anonymous_token`
2. 稳定的内部身份
3. 对外展示花名
4. 当前会话 `session_id`
5. 房间最新事件位置 `latest_event_position`

但还没有：

1. `identity_id + room_id + last_read_event_position`

也就是说，系统目前知道：

1. 这个房间总共聊到哪了

但不知道：

1. 这个用户自己上次读到哪了

所以“过很久再进房，从上次读到的地方继续看”这个体验，在现状里根本无从成立。

## 3. 对齐官方最佳实践后的直接结论

### 3.1 Socket.IO / socketioxide 不负责阅读锚点真相

查官方资料后，这一点可以直接定死：

1. `Rooms` 只是服务端广播分组，不是业务成员真相，也不是阅读进度真相。  
   来源：[Socket.IO Rooms](https://socket.io/docs/v4/rooms/)
2. Socket.IO 服务器默认不存事件，客户端断线期间错过的事件不会自动长期保留。  
   来源：[Handling disconnections](https://socket.io/docs/v4/tutorial/handling-disconnections)
3. 默认投递语义是 `at most once`；更强一致性必须靠应用层自己的唯一 ID、偏移量和持久化。  
   来源：[Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)
4. `connection state recovery` 只适合短断线恢复，不适合“隔很久再次进入聊天后继续从上次阅读位置看”。  
   来源：[Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/)
5. `socketioxide` 也只是 Rust 侧 realtime adapter，不是阅读历史和阅读进度存储系统。  
   来源：[socketioxide docs.rs](https://docs.rs/socketioxide/latest/socketioxide/)

因此，阅读锚点和未读恢复绝不能塞给 realtime 层解决。

### 3.2 Telegram 的公开模型，本质就是“阅读锚点 + 围绕锚点取历史”

Telegram 官方公开接口直接暴露了这套味道：

1. `messages.readHistory` 的语义就是把阅读进度推进到某个消息。  
   来源：[messages.readHistory](https://core.telegram.org/method/messages.readHistory)
2. `messages.getHistory` 支持按 `offset_id` / `add_offset` / `limit` 围绕某个消息取历史。  
   来源：[messages.getHistory](https://core.telegram.org/method/messages.getHistory)
3. Telegram 的分页模型本身就是围绕消息锚点，而不是每次都从最老消息或最新消息盲目起步。  
   来源：[Pagination in the API](https://core.telegram.org/api/offsets)

这和本次要学的目标完全一致：

1. 用户级阅读进度是真相
2. 首屏围绕未读起点给上下文
3. 历史与未读恢复都围绕稳定消息锚点运作

### 3.3 WhatsApp 的公开资料也支持“历史 + 应用状态同步”

Meta 官方公开资料没有像 Telegram 一样把接口细节摊开，但方向一致：

1. 多设备要同步 `message history`
2. 还要同步 `application state data`
3. 新设备拿到最近历史后，存进本地数据库，再继续同步

来源：[How WhatsApp enables multi-device capability](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)

这说明成熟 IM 的方向不是“记一个当前页面 scrollTop”，而是：

1. 用户级状态可同步
2. 历史有基线
3. 设备只是消费这些状态

## 4. 设计目标

本次设计要同时达到六个结果：

1. 用户再次进入同一个房间时，能回到自己上次阅读位置附近
2. 默认落点是“第一条未读消息附近”，而不是最老消息起点，也不是无脑最新底部
3. 房间首屏要带少量已读上下文，避免用户断片
4. 页面里要出现明确的“未读消息从这里开始”分隔提示
5. 上滑加载更早历史时，当前视口不抖、不闪、不跳
6. realtime 仍然只负责后续新消息，不承担阅读状态真相

---

## 5. 明确不做

为了防止执行时 scope 飘掉，这次明确不做：

1. 不做正式账号注册/登录体系
2. 不做跨手机号、跨账号合并身份
3. 不做消息搜索
4. 不做按时间跳转
5. 不做已读人数回执
6. 不做群成员在线状态
7. 不做虚拟列表重构
8. 不做“导出全部历史”

本次只聚焦：

1. 阅读锚点
2. 未读恢复
3. 首屏落点
4. 上滑分页稳定性

## 6. 核心设计原则

### 6.1 阅读锚点必须是后端保存的用户级真相

这次固定新增一类业务真相：

1. 某个内部身份
2. 在某个房间
3. 最后读到了哪个 `event_position`

大白话就是：

**后端要记住：这个人上次在这个群里，看到了哪里。**

这个真相不是：

1. 页面像素位置
2. 当前浏览器滚动条高度
3. 本地 UI 记忆

### 6.2 房间最新位置与用户阅读位置必须分开

系统必须同时持有两种位置：

1. `latest_event_position`
   含义：这个房间大家总共聊到哪
2. `last_read_event_position`
   含义：这个用户自己看到哪

它们不是一回事，不能混。

### 6.3 首屏恢复不是“最近 55 条”，而是“围绕第一条未读的一屏”

前一个 spec 里“最近 55 条”已经解决了“假空房”问题，但它还不够像 Telegram。

这次要升级成：

1. 后端根据 `last_read_event_position`
2. 计算第一条未读大概从哪里开始
3. 围绕这条未读起点返回一屏消息
4. 这屏既包含少量已读上下文，也包含未读内容

一句话：

**房间首屏不再是简单的“最近 55 条”，而是“围绕未读起点的一屏消息”。**

### 6.4 上滑分页与首次落点是两回事

这两件事不能混成一个机制：

1. 首次进入房间时，要找到“应该从哪开始继续看”
2. 上滑旧历史时，要保持用户眼前内容不动

一个是“找正确入口”，一个是“守住当前视口”。

### 6.5 前端只负责视觉锚点，后端负责阅读锚点

固定分工：

1. 后端负责：
   - 谁读到哪
   - 首屏应该围绕哪条未读恢复
   - 当前房间最新聊到哪
2. 前端负责：
   - 把视图滚到首屏落点
   - 画未读分隔条
   - 上滑分页时补偿滚动位置

## 7. 方案对比

### 7.1 推荐方案：后端保存阅读锚点，首屏围绕第一条未读恢复

做法：

1. 后端新增用户级阅读锚点
2. 进入房间时返回“围绕第一条未读的一屏消息”
3. 前端落到第一条未读附近
4. 前端显示“未读消息”分隔条
5. 前端在上滑分页时守住滚动锚点

优点：

1. 最像 Telegram
2. 同一用户离开很久再回来仍能接上
3. 前后端边界清晰
4. 未来扩展多设备也不需要推翻重来
5. “再次进房落点不对”和“历史翻页闪烁”可以一起收掉

代价：

1. 需要新增后端阅读状态
2. 需要升级房间快照契约
3. 前端需要补一套滚动锚点恢复逻辑

### 7.2 不推荐方案：只在本地存滚动位置

做法：

1. localStorage 记 `room_id + scrollTop`
2. 再次进房时按像素位置滚回去

问题：

1. 这不是 Telegram 语义
2. 插入历史、消息增减、字体变化后像素位置会失真
3. 完全表达不了“第一条未读”
4. 后端根本不知道用户读到哪

### 7.3 折中方案：后端只存 last_read_event_position，前端自己猜首屏

做法：

1. 后端只返回 `last_read_event_position`
2. 前端自己从消息列表里猜“第一条未读在哪”

问题：

1. 如果首屏消息不覆盖锚点附近，上下文还是会断
2. 前端会被迫发明真相
3. 容易再次长出“最近 55 条刚好不够”的边角 bug

**本次设计固定采用 7.1。**

## 8. 核心数据语义

### 8.1 新增阅读锚点真相

后端新增一类稳定事实：

1. `identity_id`
2. `room_id`
3. `last_read_event_position`

约束：

1. 它属于内部身份，不属于临时 session
2. 它属于用户级状态，不属于页面临时状态
3. 它不能只存在前端

### 8.2 房间快照升级为“带阅读落点的房间快照”

房间快照不再只是：

1. `room_id`
2. `latest_event_position`
3. 一组消息

而是要升级为至少表达这些事实：

1. 这个房间当前最新位置
2. 这个用户上次读到哪
3. 首屏里哪条是第一条未读
4. 当前首屏消息列表
5. 是否还存在更早历史

这套语义里，最关键的是：

**前端不能再自己猜“第一条未读在哪里”，而要消费后端给出的稳定落点。**

### 8.3 阅读推进是单独语义，不和进房混用

进入房间不等于“已读已经推进”。

这次固定把“阅读推进”做成单独能力：

1. 前端把用户实际看到的最深位置上报给后端
2. 后端更新 `last_read_event_position`

这样：

1. 进入房间负责恢复首屏
2. 阅读推进负责更新阅读真相

不能混成“只要用户进来了，就把底部都算已读”。

### 8.4 历史分页语义保持克制

历史分页继续只负责：

1. “把当前最老这条之前的，再给我一页”

它不负责：

1. 计算第一条未读
2. 恢复用户阅读落点
3. 替代阅读锚点真相

## 9. 数据流设计

### 9.1 再次进入房间

固定流程：

1. 前端 bootstrap 当前内部身份 / session
2. 前端请求房间快照
3. 后端查出该身份在该房间的 `last_read_event_position`
4. 后端围绕“第一条未读”准备一屏消息
5. 后端返回：
   - 房间当前最新位置
   - 阅读锚点
   - 未读起点信息
   - 一屏消息
6. 前端渲染这屏消息
7. 前端把视口落到第一条未读附近
8. 前端画出“未读消息”分隔条
9. 然后再建立 realtime 续接

### 9.2 首次进入一个自己从未读过的房间

如果该身份在此房间还没有阅读锚点：

1. 视为没有历史阅读记录
2. 首屏回退到“最近一屏消息”
3. 若产品上更符合期待，也可直接落到底部附近

但这不属于“继续上次看”，它属于新用户首次进入语义。

### 9.3 用户继续阅读时的阅读推进

阅读推进要克制：

1. 当首屏稳定落到未读起点附近后
2. 或用户继续向下滑过更多消息后
3. 前端再上报一个新的 `last_read_event_position`

约束：

1. 不能每滚 1 像素就上报
2. 不能页面一进来还没稳定就把最新底部全标已读
3. 不能把“正在加载历史”误算成“已读推进”

### 9.4 上滑加载更早消息

固定流程：

1. 记录当前可视锚点
2. 请求更早历史页
3. 把旧消息插入顶部
4. 重新计算插入前后高度差
5. 把滚动条补偿回去
6. 保证用户眼前原本那条消息尽量留在原位

这条链的关键不是“拉到了消息”，而是：

**拉到了之后，用户眼前正在看的那条不能被顶走。**

## 10. 前端滚动稳定性设计

### 10.1 抖动根因

当前抖动的直接原因是：

1. 顶部触发加载
2. 列表前插消息
3. DOM 高度变化
4. 没有做滚动补偿

所以用户会感觉到“抽一下”。

### 10.2 正确做法

历史分页成功后，前端必须：

1. 在插入前记录滚动容器高度
2. 在插入后再读一次高度
3. 用差值修正 `scrollTop`

这样新增历史只会出现在上方，不会把当前视口强行挤跑。

### 10.3 顶部触发不能过于粗暴

不能只依赖 `scrollTop <= 0` 机械触发。

实现层至少要考虑：

1. 节流
2. 当前是否已经在加载历史
3. 是否已经到最早历史
4. DOM 重渲染导致的短暂顶部回弹

否则在最老消息附近最容易连续触发、连续抖动。

### 10.4 首次落点与上滑补偿不能混为一套

首屏进入房间时：

1. 目标是“滚到第一条未读附近”

上滑补历史时：

1. 目标是“保持当前正在看的内容不动”

这两套逻辑必须分别设计。

## 11. 展示语义设计

### 11.1 未读分隔条

前端新增明确的未读分隔提示：

1. 文案等价于“未读消息”
2. 位置在第一条未读消息前
3. 它是展示语义，不是后端业务裁决结果本身

### 11.2 用户进入房间后的默认视觉体验

正确体验是：

1. 首屏落到第一条未读附近
2. 上面留几条已读上下文
3. 中间有未读分隔条
4. 下面是未读内容
5. 用户可以继续往下追新消息
6. 也可以往上补更早历史

### 11.3 不应该看到的内容

普通用户仍然不应看到：

1. `event_position`
2. `message_id`
3. `session_id`
4. 内部阅读锚点编号
5. 内部恢复偏移

---

## 12. 失败语义设计

### 12.1 房间快照失败

继续沿用已有规则：

1. `room_not_found`：退出房间并清锚点
2. `membership_required`：退出房间并清锚点
3. `invalid_session`：重新 bootstrap 后再试一次
4. 超时 / 断网 / 5xx：保留房间锚点，不渲染假空房

### 12.2 阅读推进失败

阅读推进失败时：

1. 不影响当前消息列表
2. 不影响当前房间可见内容
3. 不把用户踢出房间
4. 只意味着“这次阅读进度还没成功写回”

### 12.3 历史分页失败

继续保持：

1. 不清空当前消息列表
2. 不踢出房间
3. 只显示轻量提示
4. 不把“加载失败”误判成“没有更早历史”

## 13. 验收标准

### 13.1 用户视角

至少满足这些：

1. 同一个用户离开很久再回来，会落在上次未读起点附近
2. 首屏不是从最老消息开始
3. 首屏也不是无脑到底部
4. 页面会显示“未读消息”分隔条
5. 上滑加载更早消息时不闪、不抖、不抽
6. 其他人新发的消息仍然能继续往下看

### 13.2 前端测试

至少补这些：

1. 再次进房时会按未读起点定位首屏
2. 有未读时会显示未读分隔条
3. 上滑补历史时会保住当前视口锚点
4. 顶部附近不会重复触发多次历史请求
5. 历史分页 + realtime 并发时不重复、不乱序

### 13.3 后端 / 集成测试

至少补这些：

1. 后端会为身份 + 房间保存阅读锚点
2. 房间快照会返回阅读锚点相关语义
3. 无阅读锚点与有阅读锚点时，首屏返回逻辑不同
4. 阅读推进成功后，下一次进房会按新的未读起点恢复
5. 房间成员资格与阅读锚点查询仍走同一套门禁

---

## 14. 顺手盯住的更深层风险

这次实现时，除了修已知 bug，还要顺手盯住两个更深层问题：

1. 当前“设备匿名”其实不是严格匿名，而是“设备持久化内部身份 + 对外花名”
   这意味着阅读锚点应该绑在内部身份上，而不是绑在临时 session 上。
2. `joinOrCreateRoom` 与 `loadRoomSnapshot` 的首屏语义必须保持一致
   否则会再次出现“一条入口按未读恢复，另一条入口按最近消息恢复”的双轨 bug。

---

## 15. 一句话结论

这次要补的不是一个单点滚动 bug，而是：

**把“同一个人上次在这个房间读到哪”的真相正式建起来，再让房间首屏、未读分隔、历史分页和 realtime 都围绕这条真相收口。**
