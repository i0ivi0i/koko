# 群聊附件平台与图片实时收发设计

日期：2026-04-09  
状态：设计已确认，待进入 implementation plan  
范围：群聊消息模型从“纯文本”升级为“文本 + 附件”；第一阶段只交付图片实时收发；未来预留视频、语音、GIF、压缩包等附件能力  
约束：前端纯 TypeScript、后端纯 Rust；继续复用 `socketioxide` 作为 realtime adapter；继续坚持 DDD 与六边形边界；不把大文件传输塞进 realtime；不制造第二套消息真相主链；不为未来功能预埋平台屎山

## 0. 一句话结论

这次不是“给文本消息补一块图片 UI”，而是把系统升级成：

1. 一套统一的消息主链
2. 一套统一的附件平台模型
3. 第一阶段只点亮图片附件的上传、发送、实时回流与展示

核心裁决只有一句：

**消息是真相，附件是被消息引用的稳定对象；上传成功不等于消息成立，消息成立只认权威事件。**

---

## 1. 目标与非目标

### 1.1 长期目标

把当前系统从“纯文本消息系统”升级成“文本 + 附件平台消息系统”，为未来这些能力提供统一地基：

1. 图片
2. 视频
3. 语音
4. GIF
5. 压缩包和普通文件
6. 转发与分享

### 1.2 当前交付目标

第一阶段只交付：

1. 选择图片并上传
2. 发送“文字 + 多张图片”消息
3. 群聊房间内实时回流这条消息
4. 房间快照与增量恢复继续可用
5. 前端可以展示图片消息

### 1.3 第一阶段明确不做

1. 不做视频发送
2. 不做语音发送
3. 不做 GIF 特殊播放逻辑
4. 不做压缩包预览
5. 不做浏览器直传对象存储
6. 不做断点续传
7. 不做附件独立 ACL
8. 不做上传完成自动发消息
9. 不做消息占位、边上传边出现“假消息”
10. 不做协议层 Matrix 化改造

## 2. 设计原则

### 2.1 DDD 边界

- `domain` 只定义消息、附件、引用、不变量
- `application` 只编排上传后的可发送性校验与创建消息
- `contract` 只定义稳定命令、事件、快照、错误码
- `adapter` 只做 HTTP、存储、图片处理、数据库、realtime
- `shell` 只做选图、上传、预览、发送、展示

### 2.2 Unix 哲学

每一层只做一件事：

1. 上传链只解决文件进入系统
2. 图片处理链只解决类型校验、尺寸提取、缩略图生成
3. 消息链只解决“这条消息是否成立”
4. realtime 只解决“已成立消息如何尽快送到在线用户”
5. timeline/presenter 只解决“如何展示”

### 2.3 Matrix 可借鉴但不照搬的点

本项目不转 Matrix 协议，但吸收它值得学的架构智慧：

1. `sans-IO` 核心：纯模型和状态机不依赖 HTTP/socket/DB
2. `store trait` 思路：先定义端口，再落具体存储
3. `timeline` 是展示投影，不是底层真相

不照搬：

1. Matrix 协议
2. Matrix 事件命名
3. `mxc://`
4. Matrix room/event 语义

## 3. 核心领域模型

### 3.1 Message

房间里的权威发言记录。

最小稳定字段：

1. `message_id`
2. `room_id`
3. `sender_session_id`
4. `sender_display_alias`
5. `event_position`
6. `text`
7. `forward_from?`

规则：

1. 一条消息可以只有文本
2. 一条消息可以只有附件
3. 一条消息可以同时有文本和附件
4. 文本和附件都为空时，消息不能成立

### 3.2 Attachment

独立稳定存在的附件对象。

最小稳定字段：

1. `attachment_id`
2. `kind`
3. `owner_identity_id`
4. `mime_type`
5. `byte_size`
6. `width?`
7. `height?`
8. `storage_key`
9. `thumbnail_storage_key?`
10. `status`

长期 `kind` 平台枚举：

1. `image`
2. `video`
3. `audio`
4. `gif`
5. `file`

第一阶段只真正实现：

1. `image`

### 3.3 MessageAttachmentRef

消息和附件之间的关系真相。

最小稳定字段：

1. `message_id`
2. `attachment_id`
3. `sort_order`
4. `display_role`

规则：

1. 消息不直接内嵌整坨附件私货
2. 附件也不冒充聊天消息
3. 附件显示顺序通过 `sort_order` 裁决

### 3.4 ForwardSource

转发不是复用原消息，而是在目标房间创建新消息，并保留来源信息。

最小稳定字段：

1. `source_room_id`
2. `source_message_id`
3. `source_sender_display_alias`

规则：

1. 转发后的消息拥有新的 `message_id`
2. 转发后的消息拥有目标房间自己的 `event_position`
3. 转发后的消息可以复用已提交的稳定附件对象

## 4. 所有权、可见性与复用规则

### 4.1 所有权

附件的权威 owner 一律按 `identity` 裁决，不按 `session` 裁决。

规则：

1. HTTP 上传接口通过 `session_id` 认证
2. 服务端把 `session_id` 解析到当前匿名身份或内部身份
3. `attachment.owner_identity_id` 永远记录身份，不记录会话

这样做的原因：

1. 同一身份跨会话重连后仍能继续操作自己刚上传的附件
2. 不把运行时会话锚点误当成稳定业务 owner

### 4.2 可见性

附件访问权限跟着消息可见性走，不另造附件 ACL。

规则：

1. 用户能看到这条消息
2. 才能读取这条消息引用的附件

注意：

1. 下载接口仍然要做服务端校验
2. 只是校验依据来自“消息可见性”，不是独立附件 ACL

### 4.3 复用

必须区分两类附件：

1. `未提交附件`
   - 仅表示“这个身份上传了一份待发送图片”
   - 尚未被任何消息引用
2. `已提交附件`
   - 已被某条成功消息引用
   - 之后允许被转发语义复用

第一阶段规则：

1. 普通发送时，前端只引用自己刚上传得到的图片附件
2. 转发能力暂不实现 UI，但模型允许未来复用已提交附件
3. 未提交附件超时后可以回收

## 5. 第一阶段推荐技术栈

### 5.1 前端

1. `Uppy`
2. `Dashboard`
3. `XHRUpload`

原因：

1. 不手搓选图、上传进度、失败提示、重试 UI
2. 当前只做图片，不需要现在就引入 `tus/tusd`

### 5.2 后端

1. `axum Multipart`
2. `object_store`
3. `infer`
4. `image`
5. `kamadak-exif`
6. 继续复用 `socketioxide`

分工：

1. `Multipart`：接图片上传
2. `infer`：做真实类型识别，不信浏览器 MIME
3. `image + exif`：读取尺寸、方向、生成缩略图
4. `object_store`：存原图与缩略图
5. `socketioxide`：只回流已成立消息事件

### 5.3 未来再接入但第一阶段不引入

1. `tus/tusd`
2. `ffprobe/ffmpeg`
3. `symphonia`

## 6. 合同面：命令、事件、HTTP

### 6.1 图片上传 HTTP

第一阶段先用最小 HTTP 面，避免过度设计：

#### `POST /api/attachments/image`

输入：

1. `session_id`
2. `multipart/form-data` 图片文件

输出：

1. `attachment_id`
2. `kind = image`
3. `mime_type`
4. `byte_size`
5. `width`
6. `height`
7. `status = ready`

裁决：

1. 后端在一个上传请求内完成校验、元数据提取、缩略图生成和存储
2. 成功时直接返回 `ready`
3. 失败时直接返回错误码

说明：

1. `processing` 作为平台状态保留，但第一阶段图片处理尽量同步完成
2. 这样可以减少轮询、减少前后端状态分叉、减少屎山

### 6.2 创建消息命令

统一升级为“创建消息”语义，不再围绕“发送文本消息”继续补丁扩张。

第一阶段传输面明确为：

1. **继续走现有 realtime 命令链**
2. 不新增 HTTP create-message 入口

最小字段：

1. `room_id`
2. `client_message_id`
3. `text`
4. `attachment_ids[]`

规则：

1. `text` 可空
2. `attachment_ids[]` 可空
3. 但二者不能同时为空

### 6.3 领域事件

继续保留统一的 `message_created` 事件，而不是新增“图片消息事件名”。

最小字段：

1. `type = message_created`
2. `room_id`
3. `message_id`
4. `client_message_id`
5. `sender_session_id`
6. `sender_display_alias`
7. `event_position`
8. `text`
9. `attachments[]`
10. `forward_from?`

这样：

1. 同步锚点不变
2. 事件名不变
3. 只是事件内容从“纯文本”升级成“文本 + 附件”

## 7. 创建消息时序

第一阶段固定成下面 8 步：

1. 用户选图
2. 前端通过 `Uppy` 上传图片到 `POST /api/attachments/image`
3. 后端校验并创建 `attachment`
4. 前端拿到 `attachment_id`
5. 前端提交 realtime `创建消息` 命令
6. `application` 校验会话、房间、成员资格、附件 owner、附件状态
7. 后端创建 `message` + `message_attachment_ref` + 房间事件
8. `socketioxide` 广播统一 `message_created`

关键裁决：

1. 上传成功不等于消息成立
2. 只有收到权威 `message_created`，前端才把图片消息放进时间线
3. realtime 不传文件二进制，只传消息事件

## 8. 状态机与错误码

### 8.1 附件状态机

平台层保留 5 个状态：

1. `uploading`
2. `processing`
3. `ready`
4. `failed`
5. `expired`

第一阶段落地规则：

1. `uploading` 是前端壳层暂态
2. 服务端上传请求成功时直接落成 `ready`
3. 服务端上传请求失败时返回错误，不保留长时间 `processing`
4. 只有未被消息引用过的附件，才允许进入 `expired`

允许的迁移：

1. `uploading -> ready`
2. `uploading -> failed`
3. `uploading -> processing -> ready`（保留给未来慢处理）
4. `uploading/processing/ready(未引用过) -> expired`

### 8.2 第一阶段错误码

上传链：

1. `attachment_too_large`
2. `attachment_type_not_allowed`
3. `attachment_decode_failed`
4. `attachment_upload_failed`
5. `attachment_processing_failed`

消息链：

1. `attachment_not_found`
2. `attachment_not_owned`
3. `attachment_not_ready`
4. `attachment_count_exceeded`
5. `message_content_empty`
6. `membership_required`

## 9. 第一阶段领域规则

### 9.1 消息成立条件

一条消息成立必须满足：

1. `text` 不为空，或者 `attachment_ids[]` 非空
2. 每个附件存在
3. 每个附件 owner 等于当前发送者身份
4. 每个附件状态为 `ready`
5. 当前发送者具备房间发言资格

### 9.2 第一阶段图片规则

1. `attachment.kind` 必须是 `image`
2. 一条消息允许 `text + 多张图片`
3. 一条消息允许纯图片
4. 第一阶段不允许非图片附件进入消息

### 9.3 回收规则

1. 从未被任何消息引用过的附件，允许按 TTL 回收
2. 已被消息引用过的附件，第一阶段不回收
3. 这样可以保证未来转发复用有稳定对象可依赖

---

## 10. 前端展示规则

第一阶段前端只做：

1. 文字消息展示
2. 图片网格或顺序展示
3. 图片点击查看

不做：

1. 视频播放器
2. 语音条
3. GIF 特殊动图策略
4. 文件卡片预览

前端必须守住：

1. 本地 blob 预览只是壳层暂态
2. 房间时间线里的图片消息只来自权威事件
3. 不能因为本地上传成功就提前宣布消息成立

---

## 11. 明确禁止事项

执行时必须禁止：

1. 新增 `send_image_message` 之类并行命令
2. 在上传接口里顺手创建聊天消息
3. 在消息事件里塞签名 URL、对象存储桶名等 adapter 私货
4. 让附件 owner 按 `session` 落库
5. 再长一套独立附件 ACL
6. 把 `ready` 当成“已经发出”
7. 先为视频/语音/GIF/文件铺一大堆工作流平台

---

## 12. 验收标准

第一阶段完成必须同时满足：

1. 用户可以发送“纯文字”
2. 用户可以发送“纯图片”
3. 用户可以发送“文字 + 多张图片”
4. 同房间在线用户能实时收到带图片的权威消息
5. 断线恢复后，图片消息仍能通过现有快照/增量链恢复
6. 消息主链仍然只有一条
7. 设计上已为未来视频、语音、GIF、压缩包保留统一附件平台地基

如果这 7 条里任何一条不成立，就说明设计或者实现已经开始漂移。
