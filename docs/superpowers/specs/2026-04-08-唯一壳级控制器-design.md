# 唯一壳级控制器设计

日期：2026-04-08  
状态：设计已确认，待进入 implementation plan  
范围：前端聊天主壳底部控制器重构、唯一控制器实体、固定骨架与槽位、首页/群聊模式切换、相关测试与验收口径  
约束：不改 Rust 后端契约，不新增第二套控制器，不把“视觉接近”误当成“结构唯一”，不让控制器喧宾夺主压过消息气泡

## 0. 一句话结论

当前前端已经把首页和房间里的底部操作区收口到了同一个位置 `#shellConsole`，但它仍然不是“真正唯一的控制器实体”。

根因不是 CSS 没调够，而是底层结构仍然是两套不同模板在同一位置切换：

1. 首页态渲染的是一套 `joinForm`
2. 房间态渲染的是一套 `composerForm`
3. 两套表单拥有不同的 DOM、不同的尺寸约束、不同的行布局

所以用户虽然看见的是“同一个位置”，但实际体感会明确感受到它在变高、变矮、变紧、变松，像换了一把遥控器，而不是同一把遥控器切换了控制目标。

本次设计的目标就是把它从：

**同一位置上的两套控制器**

收成：

**整个应用里唯一的壳级控制器实体。**

---

## 1. 当前问题的本质

### 1.1 现在为什么会“不得劲”

当前“控制器”让人感觉不顺，不是错觉。

真实原因是：

1. 首页时控制器用的是 `joinForm`
2. 群聊时控制器用的是 `composerForm`
3. 首页输入和按钮没有吃到和群聊输入/发送按钮完全相同的高度体系
4. 首页和群聊虽然占据同一个锚点位置，但不是同一个真实实体

于是切换时就会发生：

1. 总高度变化
2. 输入框高度变化
3. 按钮高度变化
4. 行内对齐方式变化
5. 状态槽占位变化

这些变化哪怕只有几像素，用户也会感觉“它换了”。

### 1.2 当前问题不是视觉问题，而是架构问题

如果只继续调 padding / min-height / margin，最多只能把两套控制器调得更像，但仍然不是“唯一”。

真正的问题是：

1. 当前没有一个独立的一等实体 `ShellConsole`
2. 当前只有“首页模板里的一段表单”和“房间模板里的一段表单”
3. 现在的 `#shellConsole` 更像共用插槽，不像真正的唯一控制器组件

所以这次必须改的是架构和 DOM 主骨架，而不只是样式。

---

## 2. 设计目标

### 2.1 主目标

这次设计必须同时满足：

1. 整个应用在任意时刻都只有一个控制器实体
2. 这个控制器实体始终挂在壳级固定底部
3. 首页和群聊只改变它的控制目标与语义，不更换它的身体
4. 控制器总高度、骨架、槽位、材质语言保持稳定
5. 未来即使增加按钮、删除按钮、调整功能，也仍然围绕这一个控制器实体扩展

### 2.2 次目标

1. 让控制器像“飞船操控台一样稳”，但不抢消息区戏份
2. 保持消息气泡与消息流仍然是视觉主体
3. 为未来首页功能、群聊功能、模式扩展预留固定槽位
4. 保持现有 Enter/submit 行为继续成立

### 2.3 非目标

这次明确不做：

1. 不改后端契约
2. 不新增第二块底部面板
3. 不把控制器做成大中控台压缩消息区
4. 不把“未来扩展”提前设计成复杂折叠多层工作台
5. 不把所有未来可能按钮一次性做出来

---

## 3. 核心概念

### 3.1 什么叫“唯一控制器实体”

唯一控制器实体，不是指“首页和群聊长得很像”，而是指：

1. 整个应用里永远只有一个 `ShellConsole`
2. `ShellConsole` 永远只有一套固定 DOM 骨架
3. `ShellConsole` 永远只有一个主输入控件
4. `ShellConsole` 永远只有一个主提交动作
5. `ShellConsole` 的状态槽、左右槽位、主输入槽、主动作槽都是固定骨架的一部分
6. 首页和群聊只是给它喂不同的模式模型

一句大白话：

**不是把两把遥控器放在同一个抽屉里，而是始终只有一把遥控器。**

### 3.2 什么不算“唯一”

下面这些都不算真正唯一：

1. 外层容器叫同一个 id，但内部是两套 form
2. 看起来位置一样，但切换时高度和布局明显变化
3. 首页一个输入框，群聊另一个输入框，只是都贴底
4. 首页一个按钮，群聊另一个按钮，只是都在右边

只要底层存在两套主要控制骨架，用户就能感觉出来。

---

## 4. 最终结构

### 4.1 应用总结构

整个壳继续保持两层：

1. 上层：主舞台 `ShellStage`
2. 下层：唯一控制器 `ShellConsole`

`ShellStage` 负责切换：

1. 首页群列表
2. 房间消息流

`ShellConsole` 负责切换：

1. 当前模式
2. 当前控制目标
3. 当前允许的动作
4. 当前输入语义

### 4.2 控制器固定骨架

`ShellConsole` 必须由固定骨架组成：

1. 顶部 `状态槽`
2. 底部 `主控行`

主控行固定拆成三段：

1. 左侧 `辅助功能槽`
2. 中间 `主输入槽`
3. 右侧 `主动作槽`

这三段骨架在首页和群聊里都必须存在，不能因为模式切换而整体改结构。

### 4.3 控制器的唯一 form 约束

从现在开始，控制器层面应该满足这些硬约束：

1. 永远只有一个 `shellConsoleForm`
2. 永远只有一个主输入元素
3. 永远只有一个主提交按钮
4. 不再并存 `joinForm` 和 `composerForm` 两套主 form

如果未来真的要加次级按钮，也应该加在固定槽位里，而不是再造第二个主 form。

---

## 5. 固定槽位设计

### 5.1 状态槽

状态槽永远存在，高度固定。

它的职责是：

1. 告诉用户当前控制器在控制什么
2. 显示轻量提示、状态、提醒
3. 作为视觉上的稳定上沿

它允许变的是文案，不允许变的是占位高度。

首页时，它可以显示：

1. “输入房间号进入对应群聊空间”
2. 当前身份提示
3. 轻量恢复提示

群聊时，它可以显示：

1. 当前房间文案
2. 恢复/重连/历史加载提示
3. 轻量状态说明

### 5.2 左侧辅助功能槽

左侧槽位是未来扩展的主要缓冲区。

它的职责是：

1. 挂载辅助动作
2. 保持控制器骨架稳定
3. 减少未来新增按钮时对主输入槽的侵蚀

当前阶段它可以：

1. 先保留一个固定按钮位
2. 或先用稳定空占位

但不管当前是否启用，这个槽位都要在结构上存在。

### 5.3 中间主输入槽

这是控制器的绝对中心。

要求：

1. 永远只有一个主输入控件
2. 首页时承担房间号输入语义
3. 群聊时承担消息输入语义
4. 未来即使加按钮，它仍然是视觉和交互中心

允许变化的是：

1. `value` 绑定来源
2. placeholder
3. `enterkeyhint`
4. submit 解释方式

不允许变化的是：

1. 槽位位置
2. 槽位高度
3. 输入框基础尺寸系统
4. 圆角、内边距、字体体系

### 5.4 右侧主动作槽

右侧槽位永远承载当前最主要的执行动作。

首页时：

1. “进房”

群聊时：

1. “发送”

未来即使扩展，它仍然是当前主动作的出口。

允许变化：

1. 按钮文字
2. 按钮是否禁用
3. 点击后的 submit 动作

不允许变化：

1. 按钮基础宽高体系
2. 按钮所在槽位位置
3. 右侧主动作的视觉权重

---

## 6. 固定项与可变项

### 6.1 必须固定的

这些决定“用户是否感觉它还是同一个遥控器”：

1. `ShellConsole` 外层容器只能有一个
2. 状态槽永远存在
3. 主控行永远是同一套三段骨架
4. 控制器总高度尽量固定
5. 主输入槽基础高度固定
6. 主按钮基础高度固定
7. 左右槽位位置固定
8. 底部安全区处理固定
9. 圆角、边框、阴影、材质语言固定
10. 控制器与主舞台之间的间距固定

### 6.2 允许变化的

这些只代表“同一个控制器正在控制不同目标”：

1. 状态槽文案
2. 输入值来源
3. placeholder
4. 主按钮文字
5. submit handler
6. 左右槽位内部当前挂的按钮
7. 某个按钮是否启用
8. 模式提示文案

### 6.3 尽量不要变化的

这些最容易制造“不得劲”：

1. 模式切换后整体高度突然缩一点或长一点
2. 输入框高度明显变化
3. 主按钮宽度抽动
4. 状态槽有时消失有时出现
5. 左右槽位忽隐忽现导致主输入槽宽度突变
6. 首页与群聊切换时内边距和垂直节奏变化

---

## 7. 状态与派生模型

### 7.1 不能继续让 render 直接拼两套控制器

当前控制器体验不稳，根因之一是 `render()` 直接在不同分支里拼模板。

这次需要明确一个新的壳级模型：

`ShellConsoleState`

它应该描述：

1. 当前控制器模式
2. 当前状态槽文案
3. 当前主输入语义
4. 当前主输入值
5. 当前 placeholder
6. 当前 `enterkeyhint`
7. 当前主按钮文案
8. 当前主按钮是否禁用
9. 左侧辅助槽位配置
10. 右侧辅助槽位配置（如果当前阶段需要）

### 7.2 `ShellConsoleState` 的地位

这里必须明确边界：

1. `ShellConsoleState` 是壳层 view model / presenter 产物
2. 它不是领域真相
3. 它不是新的业务状态机
4. 它只回答“唯一控制器现在该怎么表现”

### 7.3 建议派生入口

建议新增一个统一派生函数，例如：

`派生壳级控制器状态(input)`

输入至少包括：

1. 当前主舞台模式
2. 当前房间 id
3. 当前 `roomCodeInput`
4. 当前 `messageInput`
5. 当前 pending 状态
6. 当前恢复提示 / 房间提示

输出则是完整的 `ShellConsoleState`。

这样做的意义是：

1. 首页和群聊共享一个控制器视图模型
2. 控制器切换逻辑不再散在 `render()` 里
3. 未来增加按钮或模式时，只要扩展这个模型，不需要重新拼模板

## 8. DOM 与组件边界

### 8.1 最终目标结构

实现后，壳层应该更接近这种关系：

1. `renderShellStage(...)`
2. `renderShellConsole(shellConsoleState)`

而不是：

1. `if home -> render join form`
2. `if room -> render composer form`

### 8.2 `ShellConsole` 组件边界

控制器应该成为真正的独立边界。

它负责：

1. 渲染固定骨架
2. 根据 `ShellConsoleState` 渲染状态槽文案
3. 渲染唯一主输入框
4. 渲染唯一主按钮
5. 渲染固定槽位里的辅助按钮
6. 执行统一的 submit 入口

它不负责：

1. 判定当前是否在首页或房间
2. 判定当前房间是否可恢复
3. 判定业务上是否允许发消息
4. 决定领域真相

这些必须由壳层先派生后再喂给它。

### 8.3 为什么必须独立成边界

因为你已经明确说了：

1. 未来首页和群聊里都会继续加功能
2. 按钮以后可能新增、删除、调整
3. 但用户手里仍然只能有一个遥控器

这意味着控制器必须先成为独立实体，未来扩展才不会继续在 `聊天壳.ts` 的 `render()` 里长成一团。

---

## 9. 交互语义

### 9.1 首页模式

首页模式下，唯一控制器的语义是：

1. 当前控制目标：首页群列表 / 新房间进入
2. 主输入：房间号
3. 主动作：进房
4. 回车：进房

### 9.2 房间模式

房间模式下，唯一控制器的语义是：

1. 当前控制目标：当前房间消息流
2. 主输入：消息内容
3. 主动作：发送
4. 回车：发送

### 9.3 未来扩展模式

未来即使新增模式，也必须仍然通过同一个控制器骨架表达。

比如：

1. 首页的附加功能
2. 房间里的附加动作
3. 轻量模式切换
4. 面板入口

它们都只能挂进固定槽位，而不能再把控制器裂变成新的主控制区域。

---

## 10. 未来扩展原则

### 10.1 同版本内，槽位尽量固定

你已经明确接受：

1. 产品未来版本可以新增按钮、删除按钮、重排能力
2. 但同一段用户体验里，控制器必须像同一个遥控器

所以实现上要遵守：

1. 同一个版本内，槽位位置尽量固定
2. 不要因为模式切换让按钮位大幅增减
3. 更偏向“按钮位固定、功能切换或禁用”
4. 而不是“模式一切换，整条控制器重排”

### 10.2 版本升级与实时切换要分开看

可以接受：

1. 下一版产品重新定义控制器骨架
2. 新增或删除按钮
3. 调整槽位职责

但不能接受：

1. 用户当前正在用的时候，首页和群聊像突然换了另一台控制台

也就是说：

**版本迭代可以升级遥控器，但当前会话内不能换遥控器。**

---

## 11. 视觉约束

### 11.1 控制器必须克制

控制器虽然重要，但群聊应用里的视觉主角仍然必须是：

1. 消息气泡
2. 消息流
3. 会话内容本身

所以控制器应该像：

1. 飞船操控台
2. 稳
3. 准
4. 长期在场

但不应该像：

1. 大中控屏
2. 厚重工具栏
3. 压缩消息区的操作面板

### 11.2 高度策略

控制器需要保持“细长型唯一控制台”方向：

1. 状态槽薄
2. 主控行紧凑
3. 总高度稳定
4. 尽量不因为模式切换明显增高或缩矮

### 11.3 为什么不能做太大

因为这毕竟是群聊应用：

1. 主体仍然应该是消息流
2. 用户真正要看的不是控制台，而是聊天内容
3. 控制台应稳定托住体验，而不是成为视觉中心

---

## 12. 当前代码改造原则

### 12.1 这次不能只做样式统一

如果只是继续：

1. 给首页输入框加 `min-height: 50px`
2. 给按钮统一高度
3. 把一些 padding 调近

那只能缓解，不算解决。

真正的完成标准是：

1. 不再并存两套主控制 form
2. 不再并存两套主输入骨架
3. 不再在 `render()` 里分首页版/房间版控制器

### 12.2 实施顺序建议

为了防止实现漂移，建议按这个顺序改：

1. 先补测试，锁住“唯一控制器实体”的行为口径
2. 再定义 `ShellConsoleState` / presenter 派生
3. 再把 `joinForm` 和 `composerForm` 收成一个统一 form
4. 再统一输入框与按钮高度体系
5. 最后才微调视觉节奏

这样能避免一开始就陷入“边改结构边调样式”的混乱。

---

## 13. 测试与验收

### 13.1 必须新增或收紧的测试

至少要有这些测试：

1. 首页与群聊共用同一个 `#shellConsole`
2. 首页与群聊都只存在同一个主 form
3. 首页与群聊都只存在同一个主输入元素
4. 首页与群聊都只存在同一个主动作按钮
5. 模式切换时，控制器 DOM 主骨架不重建为第二套结构
6. 首页模式下 submit 走进房主链
7. 房间模式下 submit 走发消息主链
8. 返回首页后控制器切回 join 语义，但骨架不变

### 13.2 样式验收重点

需要验收的不是“像不像”，而是：

1. 总高度是否一致
2. 状态槽占位是否一致
3. 输入框高度是否一致
4. 主按钮高度是否一致
5. 模式切换时是否发生明显跳变

### 13.3 用户体验验收标准

如果做对了，用户的感觉应该是：

1. 我一直握着同一个控制器
2. 我只是从控制首页，切到了控制房间
3. 控制器没有换，只是控制目标换了

如果做完后用户仍然感觉：

1. 进入房间时底部条突然紧了一点
2. 返回首页时又突然松了一点
3. 它像两种不同的条在切换

那就说明实现还没有达到“唯一控制器实体”。

---

## 14. 最终判断标准

这次设计真正的通过标准，不是“首页和群聊的控制器长得更像了”，而是：

1. 结构上，整个应用只有一个壳级控制器
2. DOM 上，整个应用只有一套固定主控制骨架
3. 体验上，模式切换时用户不会感觉遥控器换了
4. 演进上，未来新增按钮与功能仍围绕这一个实体扩展

一句收尾：

**要做的不是“统一两个控制器”，而是“删到只剩一个控制器”。**
