# 群聊 IM DDD 稳定骨架设计

日期：2026-04-04

## 1. 文档定位

这份设计文档用于冻结 `koko` 第一阶段重构的稳定骨架。

它不回答“某个按钮为什么点了没反应”，而是回答更根上的问题：

1. 项目未来几十次增删改，应该沿哪条主链前进
2. 前后端、实时层、数据库层、后台层，分别拥有什么职责，不能拥有什么职责
3. 以后换前端框架、换后端壳、换数据库接入细节时，为什么业务不会塌
4. 为什么低级 bug 会更难混进主干，为什么一旦出现问题可以更快定位根因

这份文档优先级高于临时实现习惯、局部开发方便和壳层短期诉求。

本文中的约束分三层：

1. `A类：架构不变量`  
   这些内容决定业务是否会因为换壳、换库、换 adapter 而崩塌，属于长期冻结边界。
2. `B类：第一阶段当前绑定`  
   这些内容是当前阶段为了尽快落地而选择的技术绑定，可以在未来替换，但替换时不得破坏 A 类边界。
3. `C类：工程与实施约束`  
   这些内容用于提高可观测性、可维护性和开发效率，优先级低于 A 类架构不变量，但高于临时开发方便。

实现可以变化，但以下内容不能轻易变化：

- 领域真相边界
- 用例主链
- 共享契约表面
- 权威事件位置语义
- 热路径 / 冷路径职责划分
- 观测与测试门禁

## 2. 目标与非目标

### 2.1 本次重构的目标

本次重构要建立的是“最小可运行聊天闭环 + 最小后台骨架 + 长期稳定架构骨架”。

第一阶段要同时满足以下目标：

1. 聊天前台可完成匿名会话引导、输入房间短码、加入或创建房间、加载快照、实时发送文本消息、实时接收文本消息
2. 后台可完成最小登录、概览占位、房间列表、房间搜索、房间详情、成员列表等只读运营骨架
3. 所有业务真相落 PostgreSQL，服务重启后不丢失
4. 所有热路径与冷路径都围绕同一套稳定契约运转
5. 所有后续增删改都能沿同一条主链推进，而不是继续长出第二套真相

### 2.2 本次重构的非目标

第一阶段明确不追求以下内容：

1. 一次性做成完整 IM 平台
2. 一次性做完整管理员体系、权限矩阵、审计中心
3. 一次性做复杂事件溯源平台、分布式拆分、全量 CQRS
4. 为未来所有可能需求预埋大量抽象
5. 为了“高级感”把简单问题做成概念秀

### 2.3 成功标准

只要满足下面这几条，第一阶段就算成功：

1. 新人能在较短时间内看懂“领域在哪里、用例在哪里、真相从哪里发生”
2. 前端换壳、后端换壳、adapter 换实现时，不需要重写领域与用例
3. 消息发送、快照加载、事件续接、补洞恢复都能顺着统一主链解释
4. 任何问题都能顺着统一日志字段和分层测试往回追
5. 未来加功能、删功能、改功能时，绝大多数改动都能定位在单层或少数边界内

## 3. 总体架构裁决

### 3.1 A类：架构不变量

本项目采用：

- 模块化单体部署形态
- 六边形内部边界
- 多壳共核
- 请求-响应式命令 / 查询入口
- 增量事件流入口
- 权威持久化真相库

### 3.2 B类：第一阶段当前绑定

当前阶段为了快速落地，选择以下绑定：

- 后端实现语言：Rust
- 前端实现语言：TypeScript
- 当前权威持久化真相库：PostgreSQL
- 当前请求-响应 adapter：HTTP
- 当前增量事件流 adapter：`socketioxide + socket.io-client`

这些绑定是当前阶段决策，不是未来多壳共核的永久架构边界。

### 3.3 A类：不采用形态

本项目当前阶段不采用：

1. 微服务拆分
2. 每层一大片目录树的过度预切分
3. 手搓实时协议、手搓消息总线、手搓房间广播层
4. 由前端维护业务真相
5. 由 adapter 承担业务规则

### 3.4 A类：核心判断

本项目必须长期坚持一个判断：

**技术壳可以换，业务核心不能塌。**

因此系统中最稳定的东西必须是：

1. 领域模型
2. 用例主链
3. 共享契约
4. 事件语义
5. 错误语义
6. 事件位置语义

而最容易替换的东西必须是：

1. 前端框架
2. 前端视图层组织方式
3. 请求-响应 adapter 细节
4. 增量事件流 adapter 细节
5. 数据库存取实现细节
6. 页面路由与壳层状态

## 4. Unix 哲学与系统塑形

这次重构不只是在做 DDD 分层，也是在用 Unix 哲学给代码和团队习惯塑形。

### 4.1 一个部件只做一件事

每一层都必须只承担一类职责：

1. 领域层只表达业务真相
2. 用例层只编排业务动作
3. 契约层只表达跨端稳定接口
4. 适配层只负责翻译协议和 IO
5. 壳层只负责展示与交互编排

任何模块若开始同时做两件以上关键事情，就说明边界开始漂移。

### 4.2 接口先说真话

所有跨层输入输出都必须优先表达权威事实，而不是表达某个壳的页面流程。

因此共享表面只允许存在：

- 命令
- 命令结果
- 查询
- 快照
- 领域事件
- 控制面结果
- 错误码

其中 `event_position` 不是第八类契约原语，而是快照与领域事件上的稳定同步锚点字段。

不允许共享层里出现：

- 页面步骤
- 按钮状态
- 某壳专用布局字段
- UI 文案
- 框架对象

### 4.3 默认先删冗余，再加能力

以后任何新增功能都必须先问：

1. 这是在增强稳定契约，还是在绕开稳定契约
2. 这是在复用主链，还是在主链旁边焊一条方便通道
3. 这是新价值，还是第二套真相

系统越克制，解释成本越低，bug 面积越小。

### 4.4 闭环先于丝滑

在任何新链路上，先证明下面这些成立，再追求体验丝滑：

1. 快照锚点存在
2. 实时续接存在
3. 断线补洞存在
4. 幂等合并存在
5. 失败暴露存在

没有闭环就追求丝滑，本质上是在给假状态化妆。

### 4.5 显式失败优于隐式成功

群聊系统里最危险的不是报错，而是“看起来像成功但其实没成立”。

因此必须长期坚持：

1. transport ack 不是消息成立
2. 前端 pending 不是业务成功
3. 房间 socket room 不是成员真相
4. 页面连上了不是业务已入房

## 5. 分层设计

### 5.1 后端分层

后端保持以下五层边界：

1. `领域`
2. `用例`
3. `契约`
4. `适配`
5. `外壳`

### 5.2 前端分层

前端也必须分层，但它拥有的是“交互领域”，不是“业务真相领域”。

前端稳定层次是：

1. 契约消费层
2. 传输层
3. 本地体验态层
4. 视图壳层

### 5.3 分层裁决总则

#### 领域层允许放什么

领域层只放业务真相，例如：

- 匿名会话语义
- 房间语义
- 成员关系语义
- 消息语义
- 文本消息不变量
- 领域错误

领域层不允许出现：

- `axum`
- `socketioxide`
- `sqlx`
- 浏览器对象
- HTTP 请求 / 响应对象
- 页面流程状态

#### 用例层允许放什么

用例层只放“真相如何发生”的业务编排，例如：

- 引导匿名会话
- 按短码进房或建房
- 加载房间快照
- 发送文本消息
- 订阅房间事件流
- 后台密码登录
- 后台只读查询

用例层不允许：

- 直接依赖框架 handler
- 直接依赖数据库驱动细节
- 直接决定页面展示行为

#### 契约层允许放什么

契约层只放多壳共享的稳定接口。

允许：

- 命令类型
- 命令结果类型
- 查询类型
- 快照类型
- 领域事件类型
- 控制面结果类型
- 错误码类型

不允许：

- 某页面专用字段
- UI 状态枚举
- 框架类型
- 某壳专用文案

#### 适配层允许放什么

适配层只负责：

- 协议解码
- 鉴权接入
- 命令映射
- 查询映射
- IO 编排
- 错误转码
- 结果翻译

适配层不允许：

- 偷偷判成员资格
- 偷偷判权限
- 偷偷定义消息成立
- 偷偷替前端补业务真相

#### 外壳层允许放什么

外壳层只负责：

- 服务启动
- 路由装配
- 日志初始化
- 配置装配
- 前端页面壳

外壳层不允许成为第二业务中心。

## 6. B类：当前推荐目录骨架

为了同时满足 DDD 与简洁，不采用深层文件海，先定为以下克制骨架：

```text
src/
  main.rs
  lib.rs
  入口.rs
  总装.rs
  用例.rs
  契约.rs
  适配.rs
  外壳.rs
  领域/
    mod.rs
    会话.rs
    房间.rs
    成员.rs
    消息.rs
    错误.rs

frontend/
  入口.ts
  聊天壳.ts
  后台壳.ts
  契约.ts
  传输.ts
  状态.ts
  视图.ts
```

这份骨架的裁决原则是：

1. 真正稳定的业务领域单独成目录
2. 其他层在第一阶段先收口成单文件
3. 等某层真因职责过胖再拆，而不是一开始制造碎片目录海
4. `main.rs / lib.rs` 作为工具链基础入口保留英文，其余优先中文命名

## 7. 前后端解耦原则

### 7.1 后端拥有唯一业务真相

以下内容只能由后端裁决：

1. 谁是有效会话
2. 谁属于某房间
3. 谁能发消息
4. 某条消息是否成立
5. 历史是否完整
6. 某个事件位置是否已经推进
7. 后台查询看到的房间事实是什么

### 7.2 前端拥有交互领域，不拥有业务真相

前端允许拥有：

1. 输入框草稿
2. 当前正在发送的 pending
3. 连接提示
4. 滚动位置
5. 页面切换状态
6. 当前选中的房间或后台页签

前端不允许拥有：

1. 成员资格真相
2. 权限真相
3. 消息成立真相
4. 房间是否真的加入成功
5. 历史是否完整

### 7.3 完美解耦的唯一合法接缝

前后端之间只允许通过稳定契约耦合：

- 命令
- 命令结果
- 查询
- 快照
- 领域事件
- 控制面结果
- 错误码

前端不能通过临时字段、私有桥接或壳层猜测与后端共享真相。

### 7.4 多壳共核原则

未来若增加：

- CLI
- iOS
- Android
- 桌面端

它们都必须消费同一套稳定契约与同一套权威快照 / 领域事件。

绝不允许复制 Web 页面状态机作为第二业务内核。

## 8. A类：契约设计

### 8.1 契约只保留七类稳定原语

本项目共享契约固定为以下七类：

1. 命令
2. 命令结果
3. 查询
4. 快照
5. 领域事件
6. 控制面结果
7. 错误码

此外，`event_position` 作为快照与领域事件的共同同步锚点，是必须长期保留的稳定字段。

这里的“领域事件”只指已经成立的业务事实，不包括：

1. transport ack
2. 订阅握手信号
3. 控制面确认
4. 命令失败返回

这些都不占用“领域事件”语义。

因此共享 `contract` 的完整稳定表面应为：

1. `命令`：表达用户或壳层意图
2. `命令结果`：表达受理、拒绝与执行结果
3. `查询`：表达读取意图
4. `快照`：表达某一时刻权威基线
5. `领域事件`：表达已成立的业务事实
6. `控制面结果`：表达订阅、续接、补洞、握手等控制语义
7. `错误码`：表达失败分类

### 8.2 第一阶段最小命令集合

建议第一阶段至少包含：

1. `引导匿名会话`
2. `按短码进房或建房`
3. `发送文本消息`
4. `后台密码登录`

### 8.3 第一阶段最小查询集合

建议第一阶段至少包含：

1. `加载房间快照`
2. `按位置拉取房间增量事件`
3. `获取后台概览`
4. `列出房间`
5. `搜索房间`
6. `获取房间详情`
7. `获取房间成员列表`

### 8.4 第一阶段最小领域事件集合

建议第一阶段至少包含：

1. `成员已加入`
2. `消息已创建`

其中：

- `消息已创建` 表示权威消息成立
- 每条领域事件都必须能和房间真相变化对应上
- 每条进入房间事件流的领域事件都必须拥有明确的 `event_position`
- `消息已创建` 至少要带：`room_id`、`event_position`、`message_id`、`client_message_id`、`sender_session_id`、`body`

### 8.5 第一阶段控制面与失败语义

第一阶段以下内容不属于领域事件：

1. `已订阅房间事件流`  
   它属于订阅控制面结果，不进入房间事实流。
2. `命令被拒绝`  
   它属于命令结果 / 错误码通道，不进入房间事实流。
3. `需要整房快照重拉`  
   它属于补洞失败后的控制面结果，不进入房间事实流。

因此系统必须长期保持三条分离语义：

1. `领域事件`：已经成立的业务事实
2. `控制面结果`：订阅、续接、握手、连接相关结果
3. `命令结果`：受理、拒绝、错误码

并且三者都必须有稳定 `contract` 类型，不允许壳层或 adapter 私自发明结构。

### 8.6 快照的职责

快照只负责给客户端建立权威基线。

房间快照至少包含：

1. 房间标识
2. 当前会话视角下的必要成员信息
3. 最近消息
4. `latest_event_position`

并且快照中的每条消息至少必须带：

1. `message_id`
2. `event_position`
3. `client_message_id`
4. `sender_session_id`
5. `body`

后台快照至少包含：

1. 只读运营所需统计
2. 房间列表或详情
3. 必要分页或游标信息

### 8.7 错误码职责

错误码只表达业务失败，不表达页面文案。

例如：

- `invalid_session`
- `invalid_room_code`
- `membership_required`
- `admin_password_invalid`
- `gap_recovery_required`

前端只根据错误码派生页面提示，不允许把页面文案硬编码进共享契约。

## 9. A类：热路径与冷路径设计

### 9.1 核心判断

万人在线实时群聊不是“尽量别用 HTTP”，而是“不要把热路径放错地方”。

### 9.2 热路径

热路径由“增量事件流 adapter”承担，负责：

1. 房间事件流订阅
2. 文本消息的实时广播
3. 在线连接提示
4. 增量同步

当前第一阶段绑定为：`socketioxide <-> socket.io-client`。

### 9.3 冷路径

冷路径由“请求-响应 adapter”承担，负责：

1. 引导匿名会话
2. 按短码进房或建房
3. 加载房间快照
4. 断线补洞失败后的整房快照重拉
5. 后台密码登录
6. 后台只读查询
7. 健康检查与运维入口

当前第一阶段绑定为：HTTP。

### 9.4 为什么不能把所有能力都塞进实时层

因为那会把以下不同问题强行搅在一起：

1. 权限裁决
2. 快照基线
3. 补洞恢复
4. 幂等重试
5. 断线续接
6. 后台查询

成熟 IM 系统通常都是：

- 请求路径负责建立基线与承接冷命令 / 查询
- 实时路径负责增量推进

### 9.5 正式裁决

**消息增量流走事件流 adapter，真相基线走请求-响应 adapter。**

### 9.6 第一阶段命令入口裁决

为了彻底避免入口漂移，第一阶段明确裁决如下：

1. `引导匿名会话` 走请求-响应命令入口
2. `按短码进房或建房` 走请求-响应命令入口
3. `发送文本消息` 走实时命令入口
4. `后台密码登录` 走请求-响应命令入口
5. 所有查询都走请求-响应入口
6. 所有已成立领域事件都走增量事件流出口

这样热链路和冷链路不会再互相抢语义。

## 10. 快照、事件位置、补洞、幂等

### 10.1 事件位置是权威顺序锚点

每个房间都必须存在单调递增的 `event_position`。

所有影响房间真相的已成立事实，都必须挂到这条顺序线上。

这使系统具备以下能力：

1. 判断某客户端站在哪个历史位置上
2. 判断某次实时续接是否连续
3. 在缺口出现时准确补洞
4. 在快照重拉后重新建立统一同步锚点

### 10.2 快照负责建基线

客户端第一次进入房间时，必须先获得带 `latest_event_position` 的权威快照。

没有锚点的快照不算闭环快照。

### 10.3 实时流负责增量推进

客户端订阅成功后，只应继续接收 `event_position > last_seen` 的事件。

前端本地 UI 只是在：

- 快照基线
- 增量事件

之间做组合展示，而不是自创真相。

### 10.4 消息发送必须幂等

发送文本消息时，客户端必须携带：

1. `room_id`
2. `client_message_id`
3. 文本内容

后端必须以稳定幂等键兜住重复提交。

推荐幂等键：

`(room_id, sender_session_id, client_message_id)`

这样可以防住：

1. 网络重试
2. 用户重复点击
3. 断线重发
4. socket 侧重投

### 10.5 transport ack 不是消息成立

系统必须长期坚持：

1. adapter 收到包，不等于业务成功
2. 实时命令入口的 ack，不等于消息成立
3. 页面 pending，不等于消息成立

只有下面两种东西才能证明消息成立：

1. 权威 `消息已创建` 事件
2. 包含同一 `event_position` 的权威快照

### 10.6 补洞机制

客户端持有自己的 `last_seen_event_position`。

一旦发现事件位置不连续，例如从 `41` 跳到 `44`，说明中间存在缺口。

这时系统固定流程必须是：

1. 尝试增量补洞
2. 若增量补洞成功，则继续实时续接
3. 若增量补洞失败，则退回整房快照重拉

前端不允许脑补缺失事件。

最小补洞闭环必须长期冻结：

1. 客户端用 `last_seen_event_position` 发起 `按位置拉取房间增量事件`
2. 服务端返回一组按位置连续的领域事件，或返回 `需要整房快照重拉`
3. 控制面结果必须通过稳定 `contract` 表达，不允许各壳私自发明补洞协议

### 10.7 事务性顺序不变量

只要求“位置单调递增”还不够，系统还必须长期冻结以下事务性不变量：

1. 分配 `event_position`
2. 写入 `房间事件`
3. 写入 `消息`
4. 推进 `rooms.latest_event_position`

以上四步必须在同一数据库事务内完成。

否则并发发送下，顺序语义、去重语义和快照锚点都会漂。

## 11. PostgreSQL 真相模型

第一阶段数据库必须克制，只落权威真相，不落“方便调页面”的杂项表。

### 11.1 会话表

职责：

1. 表达匿名会话的后端真相身份
2. 为加入房间、发送消息提供稳定主体

建议字段方向：

- 内部主键：`bigint`
- 对外 `session_id`: `text`，唯一
- `display_name`: `text`
- `created_at`: `timestamptz`
- `last_seen_at`: `timestamptz`

### 11.2 房间表

职责：

1. 表达房间本体
2. 表达短码存在性
3. 挂当前房间最新事件位置锚点

建议字段方向：

- 内部主键：`bigint`
- 对外 `room_id`: `text`，唯一
- `room_code`: `text`，唯一
- `title`: `text`
- `created_by_session_id`
- `created_at`
- `latest_event_position`

### 11.3 房间成员表

职责：

1. 表达会话与房间之间的成员资格真相
2. 作为未来权限、治理、成员管理的稳定挂点

建议字段方向：

- 内部主键：`bigint`
- `room_id`
- `session_id`
- `joined_at`
- `left_at`

并为“当前成员”建立必要约束或部分索引。

### 11.4 房间事件表

职责：

1. 管理权威顺序
2. 管理事件类型
3. 作为补洞、续接、回放的基础锚点

建议字段方向：

- 内部主键：`bigint`
- `room_id`
- `event_position`
- `event_kind`
- `actor_session_id`
- `message_id`
- `created_at`

必须保证：

- `(room_id, event_position)` 唯一
- `event_position` 单调递增
- 当 `event_kind = 消息已创建` 时，`message_id` 必须非空

### 11.5 消息表

职责：

1. 表达消息实体内容
2. 通过 `event_position` 钉到权威房间事件上

建议字段方向：

- 内部主键：`bigint`
- 对外 `message_id`: `text`，唯一
- `room_id`
- `sender_session_id`
- `client_message_id`
- `event_position`
- `body`
- `created_at`

必须保证幂等约束：

`(room_id, sender_session_id, client_message_id)` 唯一

并且必须保证：

1. `(room_id, event_position)` 唯一
2. `messages(room_id, event_position)` 通过外键指向 `room_events(room_id, event_position)`
3. `room_events.message_id` 必须能唯一指向 `messages.message_id`
4. 对 `event_kind = 消息已创建` 的房间事件，`message_id` 必须与消息实体成对存在

这用于冻结“一条消息只对应一个权威事件位置”的真相约束，避免悬空引用或重复对位。

### 11.6 C类：第一阶段 PostgreSQL 实施约束

按 PostgreSQL 最佳实践，第一阶段坚持：

1. 内部 ID 用 `bigint`
2. 时间用 `timestamptz`
3. 字符串默认用 `text`
4. 不用 `varchar(255)` 伪约束
5. 不把核心真相塞进 `jsonb`

第一阶段高价值索引至少包括：

1. `会话(session_id)` 唯一索引
2. `房间(room_id)` 唯一索引
3. `房间(room_code)` 唯一索引
4. `房间事件(room_id, event_position)` 唯一索引
5. `消息(room_id, sender_session_id, client_message_id)` 唯一索引
6. `消息(room_id, event_position)` 索引
7. `房间成员(room_id)` 索引
8. `房间成员(session_id)` 索引

除索引外，还必须冻结上述唯一约束与外键约束，不能只靠查询层自觉维护真相。

### 11.7 B类：第一阶段后台初始化策略

第一阶段后台只准备最小认证壳。

当前裁决：

1. 默认用户名固定为 `admin`
2. 密码来自根目录 `.env` 中的 `ADMIN_PASSWORD`
3. 缺失 `ADMIN_PASSWORD` 时，服务必须启动失败，采用 fail-closed
4. 不允许在运行时使用硬编码默认密码回退
5. 本地开发便利性应通过 `.env` 模板解决，而不是通过默认口令解决

第一阶段不引入完整管理员账号表和权限体系。

## 12. 用例设计

用例层的目标只有一个：

**把真相发生过程编排清楚，让 adapter 永远保持薄。**

### 12.1 引导匿名会话

职责：

1. 创建或恢复匿名会话
2. 返回最小身份快照
3. 刷新会话最近活动时间

不负责：

1. 页面跳转
2. 前端显示策略
3. 某 cookie 的具体 transport 细节

### 12.2 按短码进房或建房

职责：

1. 校验短码
2. 找房间或创建房间
3. 建立成员关系
4. 返回必要结果供后续快照与订阅使用

不负责：

1. 前端 toast
2. 页面切换
3. 聊天气泡展示

### 12.3 加载房间快照

职责：

1. 返回房间当前权威基线
2. 带上 `latest_event_position`
3. 返回必要成员信息与最近消息

### 12.4 发送文本消息

固定业务流程应为：

1. 校验会话有效
2. 校验成员资格
3. 校验文本消息规则
4. 以幂等键检查是否重复提交
5. 创建消息实体
6. 分配新 `event_position`
7. 写入 `房间事件 + 消息`
8. 推进房间 `latest_event_position`
9. 产出权威结果供 adapter 广播

广播不属于用例本身。

第一阶段当前绑定：

1. 房间内发送文本消息由实时命令入口承接
2. 该入口的 transport ack 只表示 adapter 已接住命令
3. 真正的业务成立仍以 `消息已创建` 领域事件为准
4. 用例必须在同一事务内完成 `event_position` 分配、房间事件写入、消息写入与房间锚点推进

### 12.5 订阅房间事件流

这不是“开 socket”，而是裁决：

1. 谁能订阅
2. 从哪个位置开始续接
3. 是否需要补洞
4. 是否应回退整房快照重拉

连接管理属于 adapter，订阅合法性与续接起点属于用例。

补洞相关的 query 与控制面结果必须走稳定契约，不允许 adapter 自创私有恢复协议。

### 12.6 后台密码登录

职责：

1. 校验用户名是否为 `admin`
2. 校验输入密码是否匹配配置密码
3. 产出最小后台登录结果

它不是完整权限系统，只是后台认证壳。

### 12.7 后台只读查询

第一阶段只读查询至少包含：

1. 获取后台概览
2. 列出房间
3. 搜索房间
4. 获取房间详情
5. 获取成员列表

读模型可以扩展，但写真相路径必须继续收口在主链上。

## 13. Adapter 设计

Adapter 的存在意义是“翻译”，不是“替核心做决定”。

### 13.1 请求-响应 adapter

负责：

1. 请求解码
2. 承接冷命令与所有查询
3. 返回命令结果、查询结果、快照或错误码

不负责：

1. 判断成员资格
2. 判断消息是否成立
3. 决定页面流程

当前第一阶段绑定为 HTTP。

### 13.2 增量事件流 adapter

负责：

1. 建立连接
2. 承接热命令入口
3. 订阅领域事件流
4. fanout 广播
5. 背压、取消、连接提示等技术性问题

不负责：

1. 裁决消息是否合法
2. 裁决谁能发言
3. 把 room 当成成员真相

当前第一阶段绑定为 `socketioxide + socket.io-client`。

### 13.3 存储 adapter

负责：

1. 把 port 落到 PostgreSQL
2. 维护查询与写入映射
3. 保证必要事务边界

不负责：

1. 重新定义领域规则
2. 偷偷补全壳层逻辑

### 13.4 后台查询 adapter

负责：

1. 组织后台只读查询投影
2. 输出稳定查询结果

不允许后台查询模型反向定义领域真相。

## 14. 前端设计

### 14.1 前端总职责

前端只做三件事：

1. 表达用户意图
2. 展示后端权威事实
3. 管理必要本地体验态

### 14.2 前端契约层

职责：

1. 消费后端共享契约
2. 保持命名与语义一致

不允许变成第二套业务模型。

### 14.3 前端传输层

职责：

1. 封装 `fetch`
2. 封装 `socket.io-client`
3. 调度冷路径与热路径

不允许把 transport 成功误当成业务成功。

### 14.4 前端状态层

职责：

1. 管理草稿
2. 管理 pending
3. 管理连接提示
4. 管理滚动位置与页面切换

不允许管理：

1. 成员资格真相
2. 消息成立真相
3. 权限真相
4. 历史完整性真相

### 14.5 前端视图壳层

职责：

1. 按权威快照与事件更新 UI
2. 把错误码翻译成页面提示
3. 编排聊天页与后台页壳

视图永远不能反向宣布真相。

## 15. C类：日志与可观测性

### 15.1 日志必须天然存在

项目一启动就必须自动初始化日志，不依赖手动开关。

开发环境与生产环境都必须有日志输出，只是详细程度不同。

### 15.2 采用统一结构化日志

后端当前默认采用 Rust `tracing` 风格的结构化日志。

关键链路日志必须尽量包含：

1. `request_id`
2. `session_id`
3. `room_id`
4. `client_message_id`
5. `event_position`
6. `usecase`
7. `adapter`
8. `error_code`

### 15.3 观测裁决

开发环境：

1. 更详细
2. 更利于盯数据流与边界漂移

生产环境：

1. 更克制
2. 但不得消失主链证据

### 15.4 关键排障路径

以后调试任何核心问题，只允许顺主链追：

1. 命令是否进来
2. 用例是否执行
3. 领域是否裁决成功
4. 权威事实是否落库
5. `event_position` 是否推进
6. adapter 是否广播 / 返回
7. 前端壳是否正确消费

日志必须让这条链可见。

## 16. 注释与可读性规则

### 16.1 代码要自解释

命名和边界必须先能自解释，注释是在此基础上补充“为什么”和“边界”。

### 16.2 中文注释必须多，但必须有价值

优先写在这些地方：

1. 模块职责
2. 关键数据流
3. 复杂分支
4. 边界约束
5. 为什么这样设计

不写这种废注释：

1. 给变量赋值
2. 进入 if
3. 调用函数

### 16.3 目标读者

注释和结构的目标是让新维护者快速看懂：

1. 这段代码在系统里干什么
2. 为什么放在这一层
3. 哪些事情不能在这里做
4. 出问题应顺哪条链去查

## 17. C类：测试门禁

### 17.1 分层测试结构

第一阶段建议固定四层测试：

1. 领域测试
2. 用例测试
3. 集成测试
4. 端到端测试

### 17.2 领域测试

负责验证不变量，例如：

1. 非成员不能发消息
2. 空消息不成立
3. 非法短码不成立

### 17.3 用例测试

负责验证真相发生过程，例如：

1. 发送文本消息是否同时写入消息与事件位置
2. 进房或建房是否建立成员关系
3. 补洞是否正确回退

### 17.4 集成测试

负责验证 adapter 接线，例如：

1. HTTP bootstrap
2. HTTP join
3. HTTP snapshot
4. Realtime 订阅与广播

### 17.5 端到端测试

负责验证真实闭环，例如：

1. 匿名进入房间
2. 发一条消息
3. 另一端收到权威事件
4. 断线后继续恢复

### 17.6 提交前门禁

每次重要增删改前后都必须能跑通至少以下门禁：

1. `cargo check`
2. `cargo test`
3. `cargo clippy -D warnings`
4. `cargo fmt --check`
5. 前端 `typecheck + build`
6. 最小冒烟：启动、进房、发消息、收消息

## 18. Bug 闭环制度

以后每个线上或联调 bug，都必须沉淀为资产。

至少补三样：

1. 一个失败测试
2. 一段根因说明
3. 一道防回归门禁

不允许“改好了就算了”。

### 18.1 根因分类口径

以后所有 bug 都应该能归到以下某一层：

1. 领域不变量缺失
2. 用例编排错误
3. 契约漂移
4. Adapter 翻译错误
5. 壳层误用权威事实
6. 日志证据不足
7. 测试门禁缺失

只要归类不清，后续同类 bug 就容易重来。

## 19. 未来增删改的演进规则

### 19.1 加功能的合法路径

以后任何新功能都必须先判断属于哪层：

1. 新业务规则：加到领域
2. 新业务动作：加到用例
3. 新跨端能力：加到契约
4. 新接入方式：加到适配
5. 新界面体验：加到壳层

### 19.2 删功能的合法路径

以后任何功能都应该能顺着边界整体拔掉，而不是删一半留幽灵代码。

因此每个功能都必须尽量具有：

1. 清楚的命令入口
2. 清楚的事件出口
3. 清楚的快照或查询归宿
4. 清楚的壳层表现

### 19.3 改功能的合法路径

改功能时优先改：

1. 契约
2. 领域规则
3. 用例编排
4. adapter 映射
5. 视图派生

不允许直接在 UI、handler、repo 里散点补丁。

### 19.4 扩展原则

未来若增加：

- 图片消息
- 系统公告
- 禁言
- 房间封禁
- 审核动作
- CLI 管理端

都必须继续沿既有主链表达，不允许为了赶进度造旁路。

## 20. 第一阶段明确裁决

### 20.1 A类：已冻结架构裁决

1. 后端拥有唯一业务真相
2. 前端只拥有交互领域
3. 前后端通过稳定契约解耦
4. 共享事件只指领域事件，不混入控制面和失败通道
5. 冷命令 / 查询走请求-响应入口
6. 房间内热命令 `发送文本消息` 走实时命令入口
7. 所有已成立领域事件走增量事件流出口
8. 快照带 `latest_event_position`
9. 事件位置是同步锚点
10. 消息发送必须幂等
11. transport ack 不是消息成立
12. 权威持久化真相必须与业务主链保持一致

### 20.2 B类：第一阶段当前绑定

1. 当前权威持久化真相库为 PostgreSQL
2. PostgreSQL 当前采用 `会话 / 房间 / 房间成员 / 房间事件 / 消息` 五张核心表
3. 当前请求-响应 adapter 为 HTTP
4. 当前增量事件流 adapter 为 `socketioxide + socket.io-client`
5. 后台第一阶段采用 `admin + ADMIN_PASSWORD`

### 20.3 C类：当前工程约束

1. 日志默认开启，统一走结构化链路日志
2. 注释使用大量中文，但必须解释职责、边界与原因
3. 质量门禁必须覆盖 check、test、lint、format、前端构建与最小冒烟

### 20.4 第一阶段实现顺序建议

虽然这份文档不是实施计划，但仍给出推荐顺序：

1. 先立目录骨架与共享契约
2. 再立领域模型与用例主链
3. 再接 PostgreSQL 存储 adapter
4. 再接 HTTP 与 realtime adapter
5. 再接纯 TS 前端壳
6. 最后补后台只读骨架与端到端测试

---

## 21. 最终结论

这次重构真正要防的，不是某个单点 bug，而是系统再次滑回“多个地方都能宣布真相”的旧路。

真正长期稳定的系统有以下特征：

1. 真相只在少数层裁决
2. 共享表面长期稳定
3. 热路径与冷路径各归其位
4. 快照、事件位置、补洞、幂等形成闭环
5. 前端只表达事实，不制造事实
6. adapter 只翻译，不裁决
7. 日志与测试让问题沿主链显形

未来框架能换，壳层能换，页面能换，存储细节能换，但只要这些骨架不乱，业务就不会崩，功能就不会崩，维护成本也不会重新长成屎山。

## 22. 禁止条款

这部分不是价值宣言，而是审查时可直接判定违规的禁令。

总禁令只有一条：

**禁止任何会导致“真相漂移、边界漂移、契约漂移、日志失明、排障失焦”的实现方式进入主干。**

### 22.1 A类：架构禁令

以下行为一旦出现，默认视为架构退化：

1. 禁止前端承载业务真相  
   前端不得裁决成员资格、权限真相、消息成立、历史完整性或治理语义。

2. 禁止 adapter 承担业务规则  
   handler、socket 回调、repo、数据库映射层、后台查询层不得偷偷裁决谁能发、谁能看、谁能订阅、消息是否成立。

3. 禁止绕开用例主链直写真相  
   任何领域真相都不得绕开 `用例 -> 领域 -> 权威持久化` 主链直接落库、直接广播、直接写壳状态。

4. 禁止共享契约混入壳层语义  
   `contract` 中不得出现页面步骤、UI 文案、布局字段、壳层状态枚举、仅某壳可见的展示模型。

5. 禁止把控制面、失败通道和领域事件重新混为一谈  
   transport ack、订阅成功、补洞指令、命令拒绝都不得伪装成领域事件。

6. 禁止新增第二套命令入口、第二套事件语义、第二套同步锚点  
   任何为了“先跑通”的旁路接口、旁路事件、旁路位置编号，默认都是违规。

7. 禁止把连接状态、socket room、页面连通感当业务事实  
   “连上了”“进了 room”“看起来在线”都不得反向定义成“已加入房间”或“消息已成立”。

8. 禁止模块之间靠隐式状态或内部默契协作  
   模块不得依赖全局隐式缓存、隐式单例、隐式上下文、调用顺序默契来保持正确性。

9. 禁止把某一壳的特判数据形状倒灌进核心  
   Web、CLI、移动端都只能消费稳定契约，不允许为某个壳单独改写核心数据形状。

10. 禁止手搓成熟轮子的第二层真相  
    可做薄适配，不可在 `socketioxide`、数据库、日志系统外再包一层没有明确边界价值的私有核心。

11. 禁止黑箱 helper 侵蚀边界  
    职责说不清的 `helper / util / manager / bridge / wrapper` 不得承载跨层核心逻辑。

12. 禁止让系统依赖“默契”运转  
    系统必须依赖契约、字段、类型和显式边界运转，而不是依赖某位维护者脑中的约定。

13. 禁止新增私有信息形状  
    跨层事实不得一进某层就被压成当前壳、当前 adapter 或当前页面专用的私有对象。

14. 禁止核心命名绑定外层协议  
    领域名、用例名、事件名、错误名不得把 `http_`、`ws_`、`web_`、`socket_` 这类绑定写死进核心语义。

15. 禁止增加机制种类  
    能靠现有 `命令 / 命令结果 / 查询 / 快照 / 领域事件 / 控制面结果 / 错误码` 表达的能力，不得再发明平行机制。

16. 禁止局部最优破坏公共交换形态  
    不得为了某一页面、某一 adapter、某一临时性能点，牺牲共享契约的稳定性、可观察性、可回放性或可补洞性。

17. 禁止把修枝当成可选项  
    已识别的手搓桥接、重复协议胶水、壳层假状态、低价值包装和第二套真相，必须优先收口或删除，不能长期挂起。

18. 禁止证据不足就宣布成功  
    未形成与改动相匹配的新鲜证据前，不得宣布链路已绿、功能已稳或 bug 已修完。

19. 禁止新功能跳过设计四问  
    若不能回答“权威真相在哪层、稳定契约是什么、同步锚点是什么、断线/重试/重进如何补洞去重”，则不得进入实现。

20. 禁止把近似真相当真相  
    room、connection、adapter state、transport ack、页面连通感都不得被当作业务事实的近似替代。

### 22.2 C类：工程禁令

以下行为一旦出现，默认视为工程纪律失守：

1. 禁止编写代码时不带有价值的详细中文注释  
   关键模块、关键数据流、复杂分支、边界约束和设计原因必须有中文注释说明。

2. 禁止用注释重复表面动作  
   注释不能只写“赋值了什么”“进入 if 了什么”，必须解释职责、边界和为什么这样做。

3. 禁止做不到“代码即文档”  
   命名、模块边界、函数职责必须先自解释，不能指望靠 README 或口头传承才能理解代码。

4. 禁止项目启动后默认没有日志  
   开发环境和生产环境都必须天然有日志输出，不能依赖手动开关后才可观测。

5. 禁止关键链路没有结构化日志字段  
   核心链路若缺失 `request_id / session_id / room_id / client_message_id / event_position / usecase / adapter / error_code` 等主字段，默认不合格。

6. 禁止静默失败  
   房间打开失败、快照失败、补洞失败、消息发送失败不得被背景成功或 UI 乐观态掩盖。

7. 禁止没有验证就合入  
   未经过门禁验证的修改不得进入主干；不能靠“这次应该没问题”结束任务。

8. 禁止修 bug 不补失败测试  
   同类 bug 若没有沉淀成失败测试、根因说明和防回归门禁，就不算真正修完。

9. 禁止复制粘贴横向扩展同类业务语义  
   同一业务规则、同一错误语义、同一同步语义不得在多处复制实现。

10. 禁止巨函数、巨模块、跨层巨流程长期堆积  
    当一个函数或模块开始同时承担多层职责时，必须优先拆边界，而不是继续往里塞。

11. 禁止把“以后再整理”当借口保留屎山式临时代码  
    临时桥接、临时字段、临时状态、临时特判若没有明确清理计划，默认不允许进入主干。

12. 禁止新增无法整体删除的功能  
    新功能必须能说清自己的命令入口、事件出口、快照归宿和壳层表现，否则后续无法优雅移除。

13. 禁止输入输出接口漂移  
    同一命令、查询、事件、控制面结果不得随页面需要随意改形状、改语义、改字段稳定性。

14. 禁止让排障只能靠猜  
    如果一条链路改完后仍不能靠日志和测试顺主链追根因，这条链路就还不合格。

### 22.3 C类：可读性禁令

以下行为一旦出现，默认视为“代码即文档”原则退化：

1. 禁止命名失真  
   禁止使用 `data`、`info`、`temp`、`misc`、`manager`、`helper` 这类无法表达职责的名字承载核心语义。

2. 禁止函数名只描述技术动作、不描述业务事实  
   名称必须让维护者看出“这段代码在业务上到底做了什么”，而不是只看出“它调用了某个 API”。

3. 禁止同一业务概念在不同层反复改名  
   同一事实必须尽量沿主链保持统一关键词，避免搜索路径断裂。

4. 禁止同名对象在不同层表达不同语义  
   如果一个名字在不同层里代表不同真相，会直接制造理解错位和排障歧义。

5. 禁止模块职责不写在模块头部中文注释里  
   关键模块必须用简洁中文说明“做什么、不做什么、边界在哪里”。

6. 禁止关键不变量和边界约束只存在于人脑  
   只靠聊天记录、口头交接或某位维护者记忆保留规则，默认视为违规。

7. 禁止阅读主链像迷宫  
   一个功能若必须跳过过多碎片文件和无意义跳转才能看懂主流程，说明结构已经退化。

8. 禁止为了“复用”把主链切成过细碎片  
   主链应当清楚、连贯、可读，不能被过度抽象和碎片化拆分破坏阅读体验。

9. 禁止注释与代码脱节  
   代码改了而注释不改，或注释描述的是理想设计、代码却走另一套逻辑，默认视为违规。

10. 禁止长篇注释掩盖坏代码  
    注释用于解释职责、边界和原因，不用于替混乱结构打补丁。

11. 禁止关键能力不可搜索  
    用例名、事件名、错误码名、契约名必须稳定，不能让维护者搜不到代码归宿。

12. 禁止新增功能时不同步补齐命名、中文注释与边界说明  
    新功能若缺失这三样，不得视为达到“代码即文档”要求。

### 22.4 C类：日志禁令

以下行为一旦出现，默认视为项目开始丧失天然可观测性：

1. 禁止新增命令入口不接日志  
   新命令进入主链时，必须同时进入结构化日志主链。

2. 禁止新增查询、事件、补洞或恢复链路不接日志  
   任何新链路只要会影响用户真相或系统状态，都必须天然可观察。

3. 禁止日志字段漂移  
   同一概念不得今天叫 `room_id`、明天叫 `rid`；主字段名必须长期稳定。

4. 禁止关键日志缺少主链字段  
   核心日志若缺 `request_id / session_id / room_id / client_message_id / event_position / usecase / adapter / error_code` 中的必要字段，默认不合格。

5. 禁止只在失败时临时补日志  
   日志必须是天然基础设施，不能等出事了再加 `println!` 式探针。

6. 禁止只有 adapter 日志，没有用例与领域日志  
   否则问题会停留在“包进来了/包出去了”，无法看到真相是如何成立或失败的。

7. 禁止日志不能串出一次完整主链  
   同一条消息、同一次补洞、同一次快照重拉，必须能靠字段把证据串起来。

8. 禁止日志只有模糊文本没有结构化字段  
   “处理失败了”“执行异常”这类日志若没有上下文字段，对排障价值极低。

9. 禁止高频热路径日志完全无级别策略  
   日志不能失明，也不能退化成噪音海；必须能在保留证据的同时控制可读性。

10. 禁止生产环境为了安静直接关掉关键日志  
    生产环境允许降噪，不允许失去主链证据。

11. 禁止功能新增时不补主链日志与失败日志  
    每次增删改都必须同步补齐正常链路与失败链路的结构化日志。

12. 禁止日志体系依赖人工临时约定  
    日志字段、级别和关键事件命名必须稳定，不能靠个人习惯随手发挥。
