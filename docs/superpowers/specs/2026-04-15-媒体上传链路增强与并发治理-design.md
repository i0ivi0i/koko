# 媒体上传链路增强与并发治理设计

日期：2026-04-15  
状态：Draft  
适用范围：`koko` 当前 Web 媒体上传主链，覆盖前端 `Uppy + Tus`、上传 sidecar `Rustus`、后端 `prepare / hook / complete` 控制面，以及当前默认本地存储驱动下的上传完成阶段。  
关联资料：

- `学习/整理笔记/群聊媒体上传-Uppy-Tus-Rustus-2026新实践.md`
- `学习/整理笔记/高并发上传下载官方设计清单-2026.md`

## 1. 为什么要补这份 spec

这次不是普通“把一个常量从 `50MB` 改成 `200MB`”。

当前上传链路已经跑通，但它同时暴露了三类不同性质的问题：

1. **限制过死**
   - 视频 `50MB` 上限太小；
   - 前端本地 `15s` 上传失活 watchdog 容易误杀慢网大文件。

2. **门禁不一致**
   - 前端有自己的大小限制；
   - 后端 `prepare` 有自己的大小限制；
   - HTTP 入口 `DefaultBodyLimit` 有自己的 `50MB`；
   - `Rustus` sidecar 也有自己的 body limit。

   如果这些限制不一致，现实结果就会变成：

   - 前端放过了，后端 413；
   - `prepare` 放过了，入口层挡死；
   - 业务说能传，sidecar 说不能传。

3. **高并发上传下，完成阶段还不够稳**
   - 真正的大字节上传已经交给 `Rustus` 了，这个方向是对的；
   - 但后端 `complete` 阶段仍然有明显的重活热点：
     - 读临时文件；
     - 媒体解析；
     - 视频打包；
     - 写最终存储；
     - 落 ready 结果。

   所以当前系统更像是：

   **上传主链方向对了，但“限制解锁”和“完成阶段抗并发治理”还没补完。**

如果现在只做一个“把 50 改成 200”的快修，会留下三个后患：

1. 上传门禁继续分裂，问题只是往后推；
2. 慢网误杀问题还在；
3. 真正的高并发热点没有治理，系统只是“允许更大的文件把自己压垮”。

这份 spec 的目标，就是把这次工作明确成一轮**现有主链增强**，而不是再长一层新上传轮子。

## 2. 当前现场事实

### 2.1 当前主链是什么

当前仓库的媒体上传主链已经明确是：

1. 前端选择图片 / 视频文件；
2. 前端调用 `prepare`；
3. 前端把文件交给 `Uppy + Tus`；
4. `Rustus` 负责实际字节接收；
5. `post-finish` hook 回到主服务；
6. 前端收到 `upload-success` 后再调用 `complete`；
7. 主服务只有在 `complete` 成功后，才把附件升级成业务上的 `ready`。

这条链最重要的边界已经成立：

- `prepare` 成功不等于上传完成；
- `Tus upload-success` 不等于业务 ready；
- **只有 `complete` 成功才代表上传真正成立。**

这个边界必须保住，不能因为这次“要提上限、要提并发”就被打坏。

### 2.2 当前限制是什么

当前源码里的硬限制是：

- 图片上限：`10MB`
- 视频上限：`50MB`
- 最多文件数：`9`
- 前端本地上传失活 watchdog：`15s`
- HTTP 入口 `DefaultBodyLimit`：`50MB`
- `Rustus max-body-size` 默认值：`50MB`

这几个点里，真正业务上要变的是：

- 视频上限从 `50MB` 改到 `200MB`
- 删除本地 `15s` watchdog

这几个点里，本次不变的是：

- 图片仍然 `10MB`
- 一次最多 `9` 个文件仍然不变

### 2.3 当前部署前提是什么

这里必须写清楚，否则后面执行时最容易漂移：

- 当前源码**有 S3 兼容对象存储适配能力**
- 但当前默认驱动仍然是 `local`
- 当前项目**没有现成“浏览器公网直传对象存储已落地”的前提**
- 当前上传优化必须建立在：

  **继续沿用 `Uppy + Tus + Rustus + 当前存储驱动` 主链**

也就是说，这次不是“顺手把上传架构升级成对象存储原生直传”。

## 3. 目标与非目标

## 3.1 本次目标

这次第一阶段要同时达成六件事：

1. 视频上传上限提升到 `200MB`
2. 删除前端本地 `15s` watchdog，避免慢网误杀
3. 统一前端 / 后端 / 入口层 / sidecar 的大小门禁
4. 显式化前端上传并发与重试策略，不再吃隐式默认
5. 给后端 `complete` 重活阶段增加并发治理，避免高并发大视频上传时无限放大 CPU / 内存峰值
6. 在不新增私有上传轮子的前提下，把这条主链从“能跑”提升到“可控”

## 3.2 明确非目标

本次明确不做：

1. 不改下载链路
2. 不改实时主通道
3. 不改成浏览器直传对象存储
4. 不引入新的独立上传服务
5. 不手搓第二套上传协议
6. 不修改图片 `10MB` 限制
7. 不修改最多 `9` 个文件的约束

## 4. 方案比较与裁决

### 4.1 方案 A：只解锁限制

内容：

- 视频 `50MB -> 200MB`
- 删除本地 `15s` watchdog
- `DefaultBodyLimit`、`Rustus max-body-size` 一起同步到 `200MB`
- 给前端 Tus 显式补 `limit / retryDelays`

优点：

- 改动最小；
- 见效最快；
- 风险最低。

缺点：

- 真正的高并发问题没处理；
- `complete` 阶段的大文件热点还在；
- 更像“放开门”，不算“增强承载能力”。

### 4.2 方案 B：在现有主链上做一轮真正增强

内容：

- 包含方案 A 全部内容；
- 再给 `complete` 重活阶段补并发闸门；
- 再补齐关键观测；
- 再补保护测试，锁死真相边界。

优点：

- 仍然站在成熟轮子上；
- 不重做架构；
- 既解决“限制太死”，也解决“高并发完成阶段容易失控”；
- 最符合当前真实前提。

缺点：

- 设计和测试要更严；
- 不再是“只改几个常量”的小修补。

### 4.3 方案 C：直接切对象存储原生上传架构

内容：

- 浏览器改直传对象存储；
- 业务后端只保留 prepare / auth / complete / callback。

优点：

- 长期扩展性最好。

缺点：

- 当前基础设施前提不成立；
- 会把本次任务升级成“重做上传架构”；
- 签名、生命周期、回调、失败恢复都要一起补；
- 明显超出这次范围。

### 4.4 最终裁决

本次采用 **方案 B：在现有主链上做一轮真正增强**。

原因不是保守，而是边界正确：

- 成熟轮子已经找齐；
- 当前系统真正缺的不是新协议，而是把现有主链做厚；
- 先把现有主链增强到稳，再谈更远的对象存储终局，符合 DDD 和 Unix 的克制原则。

## 5. 核心设计

### 5.1 统一语义

本次把上传链路的成功语义、失败语义和资源治理语义彻底分开：

1. **业务成功语义**
   - 只有 `complete` 成功才代表附件 ready。

2. **transport 成功语义**
   - Tus / Rustus 字节上传成功，只代表 transport finished。

3. **资源治理语义**
   - 前端并发限制；
   - 后端 `complete` 并发闸门；
   - body/file size limit；
   - 重试策略；
   - 这些都属于 adapter / shell 层治理，不属于领域真相。

### 5.2 DDD 分层裁决

为防止这次“为了并发治理”把真相搞漂，明确 owner 如下：

- `domain / application`
  - 附件什么时候算 ready
  - `attachment_not_ready` 是什么语义
  - 完成上传的业务裁决

- `adapter / shell`
  - `Uppy + Tus` 参数
  - `Rustus` limit
  - `DefaultBodyLimit`
  - `Semaphore` 并发闸门
  - 日志、指标、超时、错误映射

- `frontend shell`
  - 只投影 `uploading / failed / ready`
  - 不裁决业务成功

一句话：

**业务真相不下放，资源治理不上浮。**

### 5.3 Unix 哲学裁决

这次明确禁止以下坏方向：

1. 新造第二套上传器
2. 新造“媒体上传管理器”大而全服务
3. 新造第二套完成阶段私有工作流框架
4. 因为要并发治理，就把上传主链拆成更多 forwarding 层

本次允许的增强只有两类：

1. 在现有成熟能力上补参数和门禁
2. 在现有热点上做克制的治理和观测补强

## 6. 详细改动设计

### 6.1 前端：限制与上传器参数

#### 6.1.1 大小门禁

- 图片上限继续保持 `10MB`
- 视频上限提升为 `200MB`
- `maxNumberOfFiles` 继续保持 `9`

原因：

- 当前业务痛点明确在视频，不在图片；
- 图片限制不动，可以避免一次改太多变量；
- `9` 个文件上限是 UX / 编排约束，不是本次上传并发治理的主矛盾。

#### 6.1.2 删除本地 `15s` watchdog

删除现有前端“本地上传失活计时器”整套逻辑，不再用壳层 `setTimeout` 自己裁决上传是否死亡。

原因：

1. 它不是协议层事实，只是壳层猜测；
2. 慢网、大文件、浏览器调度延迟时，很容易误杀本来还能成功的上传；
3. 这属于典型的“壳层偷偷决定业务命运”，必须删。

删除后并不意味着放弃失败处理：

- 仍然保留 `upload-error`
- 仍然保留 `upload-stalled`
- 仍然保留 `complete` 失败处理

只是失败的 owner 改回成熟轮子和真实后端，而不是本地定时器幻觉。

#### 6.1.3 显式化 Tus 参数

在现有 `创建默认媒体上传器()` 中显式设置：

- `limit = 3`
- `retryDelays = [0, 1000, 3000, 5000]`
- 保持 `allowedMetaFields` 最小集
- 继续不手动设置 `chunkSize`

为什么是 `3`：

1. 当前并不是浏览器直传对象存储；
2. 当前 `complete` 阶段仍有重活；
3. 单标签页同时把 `9` 个大视频全并发推进链路，只会把浏览器、Rustus、后端一起顶爆；
4. `3` 是第一阶段更保守、更稳的默认值，后续可再基于实测上调。

为什么仍然不设 `chunkSize`：

1. Uppy 官方明确建议，除非被迫不要设；
2. 当前 `Rustus` 仍是 file-storage 主线，不存在必须调整客户端 chunk 的证据；
3. 在没有新证据前，不为了“看起来更专业”去引入新的分块变量。

### 6.2 后端：统一大小门禁

这次必须统一四个门禁：

1. 前端视频大小校验：`200MB`
2. 后端 `prepare` 视频大小校验：`200MB`
3. HTTP 入口 `DefaultBodyLimit`：`200MB`
4. `Rustus max-body-size`：`200MB`

同时新增并统一：

5. `Rustus max-file-size`：`200MB`

原因：

- 单独改一层没意义；
- 统一门禁是上传系统最基本的诚实；
- `max-body-size` 和 `max-file-size` 语义不同，本次要把它们一起明确。

### 6.3 后端：`complete` 阶段并发治理

#### 6.3.1 为什么热点在 `complete`

当前大字节接收已经交给 `Rustus`，主应用真正危险的不是“上传中”而是“完成中”。

`complete` 当前承担的重活包括：

- 读取临时文件；
- 解析媒体内容；
- 视频打包；
- 写最终存储；
- 更新业务 ready 快照。

如果不治理，多个大视频同时完成时，系统容易出现：

- 内存峰值拉高；
- ffmpeg / packager 并行过多；
- CPU 飙高；
- 请求整体尾延迟恶化；
- 失败原因变得难以定位。

#### 6.3.2 治理策略

在 `complete` 进入重活前增加**全局并发闸门**。

推荐配置：

- 新增环境变量：`MEDIA_COMPLETE_MAX_CONCURRENCY`
- 默认值：`2`

实现归属：

- 启动期配置读取仍放在 `assembly` 风格配置读取里；
- 运行态只在 `应用状态` 保有闸门或闸门额度；
- `媒体上传外壳` 在进入重活阶段前获取 permit；
- 业务 usecase 不感知 `Semaphore`。

这个点是本次 DDD 边界最重要的地方：

**并发治理是适配层资源策略，不是领域规则。**

#### 6.3.3 为什么默认是 `2`

这是第一阶段的稳妥值，不是永久最优值。

理由：

1. 当前视频 complete 不是纯轻量 CPU 任务；
2. `ffmpeg + ffprobe + shaka packager + 文件读写 + 对象写入` 的组合成本不低；
3. 当前数据库连接池只有 `20`，应用本身也不是专门的转码集群；
4. 第一阶段先把系统从“可能无限放大”收口到“可控地慢”，比追求一开始就极限吞吐更重要。

### 6.4 状态流设计

前端草稿状态继续只有这几个核心态：

- `uploading`
- `failed`
- `ready`

状态迁移规则：

1. 选择文件并 `prepare` 成功后 -> `uploading`
2. Tus 上传中 -> 继续 `uploading`
3. Tus `upload-success` 后调用 `complete`
   - 仍然保持 `uploading`
4. `complete` 成功 -> `ready`
5. 任意阶段真实失败 -> `failed`

明确禁止：

- 不允许 `upload-success` 直接把草稿升成 `ready`
- 不允许前端本地状态偷替代后端 ready 真相

### 6.5 失败处理

#### 6.5.1 prepare 失败

场景：

- 文件太大
- prepare 接口失败

结果：

- 直接 `failed`
- 错误码继续走现有 transport/domain 映射

#### 6.5.2 Tus 上传失败

场景：

- `upload-error`
- `upload-stalled`

结果：

- 草稿标记 `failed`
- 保留重试入口

这里要特别写清楚：

删除本地 watchdog 后，`upload-stalled` 仍然可能存在，但它的 owner 是上传轮子，而不是壳层定时器。

#### 6.5.3 complete 尚未就绪

场景：

- `post-finish` 回执还没到

结果：

- 后端继续返回 `attachment_not_ready`
- 前端继续保留 `uploading`

这不是失败，而是链路尚未完成。

#### 6.5.4 complete 真失败

场景：

- 文件读取失败
- 解析失败
- 打包失败
- 最终写存储失败
- 业务完成失败

结果：

- 草稿进入 `failed`
- 错误码保留可诊断性

### 6.6 观测与日志

这次必须补齐关键观测字段，至少包括：

- `attachment_id`
- `kind`
- `byte_size`
- `phase`
  - `prepare`
  - `tus_upload`
  - `complete_wait_transport`
  - `complete_heavy_work`
  - `complete_finish`
- `duration_ms`
- `failure_reason`

目的不是“日志更漂亮”，而是为了证明：

1. 大视频上传失败到底死在哪一段；
2. 是前端限制、入口门禁、sidecar、还是 complete 重活在顶；
3. 并发闸门是否真的在起作用。

## 7. 配置设计

### 7.1 新增 / 调整的配置

本次建议新增或调整：

- `MEDIA_COMPLETE_MAX_CONCURRENCY`
  - 默认 `2`
- `RUSTUS_MAX_BODY_SIZE`
  - 默认 `200MB`
- `RUSTUS_MAX_FILE_SIZE`
  - 默认 `200MB`

现有配置继续沿用，不新增第二套配置系统。

### 7.2 配置归属原则

配置只回答“资源治理如何接线”，不回答业务问题。

也就是说：

- 上传上限可以体现在配置和入口层；
- 并发闸门可以体现在配置和运行态；
- 但“附件 ready 的真相”不能被配置接管。

## 8. 测试与验证

本次必须按风险面对齐验证，不允许“只改代码不补护栏”。

### 8.1 前端测试

至少补这些：

1. 视频上限 `200MB` 测试
2. 图片上限仍为 `10MB` 测试
3. 本地 watchdog 相关测试删除或重写
4. `upload-stalled` 仍能把草稿收口成 `failed`
5. `upload-success` 不会直接把草稿升成 `ready`
6. `complete` 成功后才会进入 `ready`
7. `Tus limit / retryDelays` 有保护测试

### 8.2 后端测试

至少补这些：

1. `prepare` 视频上限 `200MB` 测试
2. `DefaultBodyLimit = 200MB` 保护测试
3. `run.ps1` 里的 `RUSTUS_MAX_BODY_SIZE / RUSTUS_MAX_FILE_SIZE` 保护测试
4. `complete` 没拿到 finished 回执时，仍只返回 `attachment_not_ready`

### 8.3 并发治理测试

至少需要一类明确的并发保护测试：

- 多个大视频同时 `complete` 时，不会无限制并发进入重活阶段

目标不是做压测平台，而是锁死“并发闸门存在且有效”这个边界。

### 8.4 人工验证建议

实现后至少做一轮人工链路验证：

1. 单个接近 `200MB` 的视频上传成功
2. 慢网条件下不再被本地 watchdog 误杀
3. 同时上传多个大视频时，complete 阶段表现为排队变慢，而不是整体失控
4. `ready` 升级仍然只在 `complete` 成功后发生

## 9. 风险与回滚

### 9.1 主要风险

1. 视频上限升高后，系统负载会真实变大；
2. 删除 watchdog 后，如果没有补好观测，短期内失败定位可能更依赖日志；
3. 如果并发闸门位置放错层，容易把资源治理误做成业务语义。

### 9.2 风险控制

1. 第一阶段前端并发保守钉在 `3`
2. 第一阶段 complete 并发保守钉在 `2`
3. 先补护栏测试，再做实现
4. 严守“业务真相不下放，资源治理不上浮”

### 9.3 回滚策略

如果上线后发现系统承载不稳，可以按最小回滚顺序处理：

1. 先调低 `MEDIA_COMPLETE_MAX_CONCURRENCY`
2. 再调低前端 Tus `limit`
3. 如仍不稳，再回退视频上限

明确不采用的回滚方式：

- 重新加回前端本地 watchdog 这种假成功 / 假失败机制；
- 临时手搓第二套上传通道。

## 10. 施工约束

实现时必须同时遵守下面几条：

1. 不重复造轮子
2. 不新增私有上传协议
3. 不新增“上传总管”式屎山模块
4. 不把并发闸门塞进领域层
5. 不把 ready 真相塞回前端
6. 不把 transport 成功偷换成业务成功

一句话总结这次设计：

**这次不是重做上传架构，而是在现有成熟主链上，把限制解锁、门禁统一、并发收口、真相守住。**
