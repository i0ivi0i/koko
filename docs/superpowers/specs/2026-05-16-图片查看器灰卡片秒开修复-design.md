# 图片查看器灰卡片秒开修复 设计文档

## 前因后果

用户报告：群聊点开图片全屏欣赏时，先显示一块丑灰色"卡片"，等好一会才出来图片。即使之前已看过的图片，再次打开还是灰底等加载。

**核心矛盾**：用户点击的那一刻，时间线 `<img>` 已经渲染了该图片（WebTorrent blob URL），但 PhotoSwipe 查看器重新创建了一个 `<img>` 元素来加载同一 URL，中间没有任何视觉桥接。

## 根因

三条路径叠加：

1. **动态 import 延迟**：用户点击后要 `await import("photoswipe/lightbox")` + `pswpModule: () => import("photoswipe")` 两次异步加载才能初始化查看器。冷启动或弱网下 200-500ms。

2. **缺少缩略图桥接**：`映射PhotoSwipe图片` 只传了 `src/width/height/alt`，没有传 `msrc`（低分辨率占位图）也没有注册 `thumbEl`/`placeholderSrc` filter。PhotoSwipe 打开时无法从时间线缩略图"就地放大"，只能显示灰色占位区域等待原图加载。

3. **blob URL 重复解码**：虽然 blob URL 是本地内存，但浏览器创建新 `<img>` 仍需图片解码，大图在手机上可能几十到几百毫秒。

## 修复方案

### Phase 1: PhotoSwipe 预加载（消除 import 延迟）

在 `创建媒体查看器` 构造时预加载 PhotoSwipe 模块，类似已有的 `预热默认VideoJs元素()`：

```typescript
// 在 创建媒体查看器 函数开头
const photoSwipePreload = import("photoswipe/lightbox").then(() => import("photoswipe"));
```

后续打开图片时 `await` 的是已经缓存的 Promise，零延迟。

### Phase 2: thumbEl + placeholderSrc filter（缩略图就地放大）

利用 PhotoSwipe v5 的 filter API：

1. **`thumbEl` filter**：在 dataSource 项目中记录 `attachmentId`，打开时从时间线 DOM 查找对应的 `<img>` 元素作为动画起点
2. **`placeholderSrc` filter**：用时间线 `<img>` 的当前 src 作为 placeholder，确保查看器打开瞬间就有像素

这样用户看到的效果：点击 → 时间线图片就地平滑放大到全屏 → 无灰色间隙。

### Phase 3: msrc 字段补齐

在 `映射PhotoSwipe图片` 中将 `src` 同时作为 `msrc` 传入。这样即使 thumbEl 查找失败，PhotoSwipe 也会用 msrc 作为即时占位。

## 拒绝方案

- **Canvas 截图做 placeholder**：额外的 CPU 开销和内存消耗，blob URL 本身就是最佳 placeholder
- **预渲染隐藏的全屏 img**：DOM 膨胀，图片数量多时资源浪费
- **Service Worker 缓存 blob URL**：blob URL 本身是内存地址，SW 缓存无意义

## 影响边界

仅 adapter/shell 层：
- `frontend/媒体/媒体查看器.ts`：预加载 + 传递 attachmentId
- `frontend/媒体/媒体查看器全屏策略.ts`：`映射PhotoSwipe图片` 增加 `msrc`
- `frontend/房间消息窗/时间线媒体基类.ts`：`读取媒体查看器项目` 无需改（已有 attachmentId）

不触及 domain/application/contract。
