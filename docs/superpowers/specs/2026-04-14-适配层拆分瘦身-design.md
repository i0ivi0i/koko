# 适配层拆分瘦身设计

日期：2026-04-14  
状态：Draft  
适用范围：`koko` 仓库后端 `src/适配.rs` 及其承接的 PostgreSQL 持久化 adapter。  
关联文档：

- `docs/superpowers/specs/2026-04-14-房间外壳拆分瘦身-design.md`
- `docs/superpowers/specs/2026-04-13-群聊媒体实时收发全链路TDD疏通-design.md`
- `docs/superpowers/specs/2026-04-13-跨端志愿者媒体资产与P2P分发协议-design.md`

## 1. 背景

`src/适配.rs` 当前已经不只是“PostgreSQL adapter 实现”，而是把下面几类职责全揉在一起：

1. 会话、房间、成员资格与阅读锚点；
2. 消息事件提交、幂等冲突识别、消息页组装；
3. 媒体附件、上传运输授权、Rustus 回执、协作分发、流媒体清单；
4. 后台统计与房间列表查询；
5. `PgPool + Runtime Handle + 事务桥` 这些真正应该留在 adapter 壳层的基础设施。

继续在这个文件里加 SQL、映射和事务编排，只会放大几个问题：

1. 一个文件同时承载多个领域 owner，边界继续漂移；
2. 改消息要重新读媒体逻辑，改媒体要重新确认房间逻辑；
3. 行映射和 SQL helper 更容易演化成私有垃圾层；
4. `Pg仓储` 会从“adapter 壳”继续退化成“全项目数据库神对象”。

本次设计目标不是把大文件机械切碎，而是把 `src/适配.rs` 恢复成真正的 Postgres adapter 装配壳，并把具体持久化能力重新收口到明确的领域 owner。

## 2. 目标与非目标

### 2.1 目标

1. 允许新增 `3` 个 `.rs` 文件，按领域 owner 拆分 `src/适配.rs`；
2. 拆分后 `src/适配.rs` 只保留 `Pg仓储` 壳、运行时桥、事务入口和极少量真正共享的基座；
3. 不改变现有 `usecase::仓储端口 / Realtime仓储端口` 契约；
4. 迁移过程坚持 TDD，先补失败测试，再搬实现，再删旧代码；
5. 拆分后没有双轨旧实现、没有 `common/utils/sql_helper` 垃圾层、没有重复 SQL/重复映射。

### 2.2 非目标

1. 不改 `src/用例.rs`、`src/领域/*` 的业务真相 owner；
2. 不更换 `sqlx`、`tokio`、`postgres` 等成熟轮子；
3. 不为了“仓储更纯”再新造 repository framework、query builder wrapper、通用 manager 层；
4. 不顺手做跨上下文 schema 重写或数据库迁移重构。

## 3. 核心原则

### 3.1 DDD 边界

1. `适配层` 只负责把稳定的仓储端口翻译到 PostgreSQL，不负责业务裁决；
2. 房间与阅读、消息与事件、媒体与分发，各自拥有唯一持久化 owner；
3. 领域真相只能出现在 `application / domain`；adapter 只做查询、写入、事务与映射。

### 3.2 Unix 哲学

1. 一个文件只负责一类清楚的能力；
2. 文件名直接表达 owner，不用 `utils / common / helpers / service / manager` 这类垃圾名；
3. helper 默认跟 owner 走，只有两个以上 owner 真共享且语义完全一致时才允许留在 `src/适配.rs`；
4. 拆分必须同时删掉旧复杂度，不能做 add-only refactor。

## 4. 目标结构

### 4.1 保留在 `src/适配.rs`

只保留：

1. `Pg仓储` 结构体；
2. `连接并迁移`、`从连接池构建`、`在运行时执行`；
3. `impl 仓储端口 for Pg仓储`、`impl Realtime仓储端口 for Pg仓储` 的薄转发；
4. 极少量跨 owner 共享、且语义完全一致的错误转码与事务基座。

不再保留：

1. 具体房间 SQL；
2. 具体消息 SQL；
3. 具体媒体 SQL；
4. 具体事件/附件/分发表达映射。

### 4.2 新增 3 个文件

#### `src/房间阅读适配.rs`

职责：

1. 会话存在与所属匿名身份查询；
2. 房间存在与成员资格检查；
3. 房间快照、历史页、增量事件读取；
4. 阅读位置读取与推进。

不负责：

1. 消息事件提交；
2. 媒体附件写入；
3. 协作分发与流媒体清单。

#### `src/消息事件适配.rs`

职责：

1. 消息事件提交；
2. 统一消息提交；
3. 发送者投影；
4. 消息页与消息事件组装；
5. 幂等冲突识别；
6. 消息附件映射读取与校验快照转契约。

不负责：

1. 阅读锚点；
2. 媒体运输授权；
3. 协作分发元数据。

#### `src/媒体附件适配.rs`

职责：

1. 附件快照与待完成附件查询；
2. prepare / ready 附件记录落库；
3. 媒体上传运输授权、运输记录、Rustus 回执更新；
4. 协作分发元数据、torrent 元信息、流媒体清单元数据；
5. 附件可读内容查询；
6. 原始冷源列出与删除标记。

不负责：

1. 房间成员资格；
2. 消息事件提交；
3. 后台房间概览统计。

## 5. `impl` 归属策略

`src/适配.rs` 中的 `impl 仓储端口 for Pg仓储` 和 `impl usecase::Realtime仓储端口 for Pg仓储` 继续保留，但方法体收口成薄转发：

1. 房间与阅读相关方法转发到 `房间阅读适配`；
2. 消息与事件相关方法转发到 `消息事件适配`；
3. 媒体与分发相关方法转发到 `媒体附件适配`。

这样做的目的是：

1. 不改变 `Pg仓储` 对外稳定表面；
2. 不让调用方因为内部瘦身而跟着大面积改动；
3. 但同时把真正复杂的 SQL 和映射从热点文件里挪走。

## 6. 迁移顺序

迁移顺序必须遵守“先 owner，后薄壳；先低耦合，后高耦合”：

1. 先补护栏测试，不改行为；
2. 先抽 `媒体附件适配.rs`；
3. 再抽 `房间阅读适配.rs`；
4. 最后抽 `消息事件适配.rs`；
5. 最后统一把 `src/适配.rs` 的 `impl` 收口成薄转发。

这样安排的原因：

1. 媒体链路边界已经在外壳层拆分里被压清楚，先抽最容易形成完整 owner；
2. 房间阅读主要是读取和锚点推进，事务耦合比消息链轻；
3. 消息事件最贴近事务提交和事件组装，放最后最稳。

## 7. TDD 与验证护栏

### 7.1 施工规则

1. 先写失败测试或补 characterization，再搬实现；
2. 每一轮只搬一个 owner；
3. 每一轮迁移后，同提交删除 `src/适配.rs` 中对应旧实现；
4. 不允许出现“新文件已生效，但旧 SQL/旧映射还躺着”的双轨共存。

### 7.2 必跑验证

至少覆盖并通过这些风险面：

1. 房间接口测试；
2. 消息主链测试；
3. 媒体上传测试；
4. 协作分发测试；
5. 用例测试；
6. 最终全量 `cargo test`；
7. 最终 `cargo clippy --all-targets --all-features -- -D warnings`。

## 8. 完成定义

做到下面这些，才算这份设计真正落地：

1. `src/适配.rs` 不再直接包含房间、消息、媒体三类具体 SQL owner；
2. 新增的 `3` 个文件各自只有一个明确领域 owner，没有第二职责；
3. `impl 仓储端口 for Pg仓储` 只剩薄转发；
4. 没有新旧双轨实现，没有重复 SQL/重复映射；
5. 没有新增 `common / utils / helpers / sql_helper / manager / service` 之类垃圾抽象；
6. 迁移后全量测试与 clippy 全绿；
7. 项目 `.rs` 文件总数仍满足仓库约束：当前 `17`，新增 `3` 个后为 `20`，未超过上限。

## 9. 一句话结论

这次拆分不是把 `src/适配.rs` 机械切碎，而是把它恢复成真正的 Postgres adapter 装配壳：  
房间与阅读归房间阅读适配，消息与事件归消息事件适配，媒体与分发归媒体附件适配。  
只新增 `3` 个有明确 owner 的文件，不引入垃圾抽象，不保留双轨旧代码，不再让这个热点继续失控变胖。
