# 后端唯一真相源结构化日志设计

日期：2026-04-06  
状态：设计完成，待实现

## 1. 目标

本设计只解决一个问题：

把 `koko` 当前“启动期有日志，但业务主链缺少稳定可追踪证据”的状态，收口成：

1. 后端唯一真相源的结构化日志体系
2. 开发态终端可直接读懂，生产语义保持一致
3. 关键业务链路在正常、拒绝、异常三种结果下都可快速定位
4. 日志不能阻塞主业务，不能让实时链路和 HTTP 主链因日志 IO 卡死
5. 当前不落盘，但未来可以优雅接入 `warn/error` 自动落盘

本设计明确不解决：

1. Loki / ELK / OpenTelemetry Collector 接入
2. 分布式 tracing 全链路平台化建设
3. 前端调试面板或第二套日志协议
4. 把所有函数都变成密集日志点
5. 为日志新增独立业务子系统

## 2. 现状与问题

当前项目已经具备：

1. 启动时默认初始化 `tracing_subscriber`
2. 启动链路存在结构化日志
3. 部分 realtime 失败路径已有 `warn/error`
4. 测试中已验证最小字段 `usecase / adapter / error_code`

当前主要缺口：

1. 正常业务成功链路几乎没有 `info`
2. HTTP 冷路径缺少统一的进入、成功、拒绝、异常日志
3. realtime 热路径只有部分失败日志，没有完整成功主链
4. 还没有把 panic 与日常业务日志统一到同一份后端证据体系
5. 未来若直接临时补文件写入，容易把日志 IO 带进主业务阻塞路径

当前最大问题不是“没有日志库”，而是“日志架构尚未形成单一真相源的主链”：

1. 启动阶段可见，但业务阶段不够可见
2. 失败路径部分可见，但成功路径不够可见
3. 日志事件存在，但还没有形成稳定字段纪律和埋点边界

## 3. 设计原则

### 3.1 后端唯一真相源

1. 后端 `tracing` 事件是唯一权威日志源。
2. 前端 `console.log`、临时 `println!`、未来的调试面板都不得承担权威排障职责。
3. 终端输出、未来文件落盘、未来采集系统接入，只是同一份后端日志事件的不同消费端。

### 3.2 日志不能再造第二套事实

1. 日志只能描述已经发生的权威事实或明确的系统结果。
2. 不能在 adapter 里再造一套业务成功语义。
3. 不能让前端本地状态、socket 在线态、ack 或 room join 结果冒充业务真相。

### 3.3 结构化优先

1. 默认先写字段，再写消息文本。
2. 消息文本是辅助阅读，不是主索引。
3. 错误判断优先依赖 `error_code`、`outcome` 与业务锚点字段，不依赖模糊文本。

### 3.4 不阻塞主业务

1. 日志是运行证据系统，不得拖垮业务主链。
2. 当前终端输出实现必须保持简单。
3. 未来文件落盘必须优先采用后台写入模型，不把同步文件 IO 压进实时主链。

### 3.5 不过度设计

1. 当前阶段不引入完整 observability 平台。
2. 当前阶段不新增 `日志.rs`。
3. 当前阶段仍以现有 `assembly` 装配层承载 subscriber / panic hook / layer 组合。

## 4. 总体架构

### 4.1 单一事件源 + 多消费端

整个日志体系固定为：

1. 业务代码只产生 `tracing` 事件
2. 装配层统一初始化 subscriber / layer / panic hook
3. 当前唯一消费端是终端输出
4. 未来可增加文件输出层，但不改变业务代码埋点方式

核心约束：

1. 业务代码不感知日志写到哪里
2. 输出目标变化不允许反推业务代码改造
3. 任何日志扩展只能在装配层完成，不能把 handler / usecase / repo 变成输出编排器

### 4.2 模块归属

本设计强制以下归属：

| 内容 | 唯一允许归属 |
|---|---|
| 日志事件产生 | 最接近真相成立的位置 |
| subscriber 初始化 | `assembly` |
| `RUST_LOG` 读取与过滤 | `assembly` |
| panic hook 安装 | `assembly` |
| HTTP / realtime 协议结果日志 | `shell` |
| 用例裁决成功/拒绝日志 | `usecase` 或最接近用例结果的主链 |
| 外部 IO 异常日志 | `shell` / `adapter` |

禁止：

1. 新建“日志中心业务模块”收口所有业务语义
2. 在多个层重复宣告同一个事实
3. 为输出格式新增第二套 DTO 或日志协议对象

### 4.3 文件边界判断

当前不新增 [日志.rs](E:/koko/src)。

原因：

1. 当前日志装配复杂度仍在 [总装.rs](E:/koko/src/总装.rs) 的合理职责范围内
2. 现在拆文件容易形成低价值包装和额外跳转
3. 项目本身对 `.rs` 文件数量有克制要求

允许未来拆分的条件：

1. `总装.rs` 同时承载配置、迁移、日志 layer、panic hook、落盘策略后已明显失焦
2. 拆分能减少耦合，而不是只多一个转发函数
3. 拆出的模块仍归属于 `assembly`，而不是变成新的横切“核心”

## 5. 日志字段规范

### 5.1 全局固定字段

所有关键业务日志默认要求具备：

1. `usecase`
2. `adapter`
3. `outcome`

发生拒绝或异常时，还必须具备：

1. `error_code`

说明：

1. `usecase` 表示该日志属于哪条业务语义主链
2. `adapter` 表示该事件来自哪个入口或基础设施边界
3. `outcome` 统一收口结果语义，避免每条日志自造结果词
4. `error_code` 是稳定错误码，不使用临时自由文本替代

### 5.2 业务锚点字段

按场景补充，不要求所有日志都带全：

1. `session_id`
2. `room_id`
3. `client_message_id`
4. `event_position`
5. `app_port`
6. `request_kind`
7. `from`

规则：

1. 哪个阶段已经掌握该字段，就应在该阶段日志里补上
2. 哪个阶段拿不到，不允许硬编字段值
3. 不允许同一概念在不同日志里换名字

### 5.3 文本消息规范

1. 文本消息只做人类阅读辅助
2. 文本消息必须简洁，能说明“发生了什么”
3. 不允许把关键判断藏在长文本里

推荐风格：

1. `匿名身份引导成功`
2. `按短码进房成功`
3. `发送文本消息被拒绝`
4. `房间权威事件广播失败`

避免风格：

1. `处理失败了`
2. `执行出现异常`
3. `进入函数`
4. `debug 1`

### 5.4 `outcome` 统一枚举

当前阶段统一使用以下结果词：

1. `accepted`
2. `succeeded`
3. `rejected`
4. `failed`
5. `recovered`

约束：

1. 进入入口但尚未完成裁决时可用 `accepted`
2. 权威业务成立后用 `succeeded`
3. 业务未成立但系统完好时用 `rejected`
4. 系统异常、内部不变量破坏、基础设施失败时用 `failed`
5. 补洞、回退快照、重试成功等恢复动作成功时用 `recovered`

## 6. 级别策略

### 6.1 `info`

`info` 只打关键成功节点，不做全函数漫灌。

必须覆盖：

1. 服务启动完成
2. `bootstrap_session` 请求进入与成功完成
3. `join_or_create_room` 请求进入与成功完成
4. `load_room_snapshot` 成功完成
5. `admin_login` 成功
6. 后台只读查询成功完成
7. realtime 连接认证成功
8. realtime 订阅成功
9. 发送文本消息已成立
10. 房间权威事件广播成功
11. 补洞回退到 HTTP 快照或恢复动作完成

### 6.2 `warn`

`warn` 用于“业务未成立，但系统没坏”。

必须覆盖：

1. 参数非法
2. 会话无效
3. 成员资格不足
4. 管理员鉴权失败
5. 订阅锚点超前，需要客户端重拉快照
6. 任何显式业务拒绝

### 6.3 `error`

`error` 只用于系统异常和基础设施故障。

必须覆盖：

1. 任务执行失败
2. 数据库连接或查询执行失败
3. 启动迁移失败
4. 端口绑定失败
5. 返回快照类型不匹配
6. 广播失败
7. panic hook 捕获的不可恢复崩溃
8. 未来文件落盘失败或日志队列溢出

### 6.4 不允许的级别漂移

1. 不允许把业务拒绝打成 `error`
2. 不允许把系统异常打成 `warn`
3. 不允许用 `info` 假装“消息已成立”，如果权威事实尚未成立

## 7. `koko` 当前项目的埋点边界

### 7.1 启动链路

在 [入口.rs](E:/koko/src/入口.rs) 与 [总装.rs](E:/koko/src/总装.rs) 中保留并增强：

1. 日志初始化开始与完成
2. 配置读取失败
3. 自动迁移失败
4. HTTP 服务启动成功

### 7.2 HTTP 冷路径

以下入口要具备统一风格：

1. `bootstrap_session`
2. `join_or_create_room`
3. `load_room_snapshot`
4. `load_room_events`
5. `admin_login`
6. `admin_overview`
7. `admin_rooms`
8. `admin_room_detail`

每条 HTTP 主链至少要有：

1. 入口 accepted
2. 成功 succeeded 或拒绝 rejected 或异常 failed

### 7.3 Realtime 热路径

以下链路必须补齐：

1. connect middleware 认证成功
2. connect middleware 认证失败
3. `subscribe_room_stream` accepted
4. `subscribe_room_stream` succeeded / rejected / failed
5. `send_text_message` accepted
6. `send_text_message` succeeded / rejected / failed
7. `room_event` 广播 succeeded / failed

### 7.4 真相只记录一次

同一个事实只允许有一条主日志：

1. `消息已成立` 只能由最接近用例返回权威事件的位置宣告
2. `成员资格不足` 只能作为一次明确拒绝记录
3. `房间广播成功` 只能由广播实际成功的位置宣告

允许额外存在的，只能是：

1. 协议进入日志
2. 基础设施失败日志

## 8. panic 与后端日志统一

### 8.1 Rust 默认行为

Rust 默认 panic hook 会把 panic 信息打印到 `stderr`。本设计不取消该行为。

### 8.2 本项目策略

1. 保留 Rust 默认 panic 输出
2. 在初始化阶段安装轻量 panic hook
3. panic hook 负责把 `location`、`payload` 等信息转成一条 `tracing::error!`
4. 然后继续调用原默认 hook，保留原生 panic / backtrace 输出

### 8.3 目的

这样可以同时满足：

1. 后端统一日志主链中能看到 panic
2. Rust 默认崩溃证据不丢
3. 不引入第二套异常日志体系

## 9. 非阻塞约束

### 9.1 当前阶段

当前仅终端输出时，要求：

1. 初始化逻辑保持简单
2. 不在业务代码里直接操作 `stdout/stderr`
3. 不在 handler 里手写同步文件日志

### 9.2 未来文件落盘

未来当新增 `warn/error` 自动落盘时：

1. 优先使用 `tracing` 生态后台写线程模型
2. 落盘层只消费 `warn/error`
3. 文件落盘失败不得拖垮业务主链
4. 需要有界缓冲、失败可观测、丢弃可计数

### 9.3 不允许的实现方式

1. 在实时 handler 内同步打开文件并写日志
2. 在 `warn/error` 分支临时 `append` 文本文件
3. 为了保日志而让 socket 热路径背压失控
4. 为了“无丢失”而让主业务线程无限等待日志 IO

## 10. 环境变量与输出策略

### 10.1 当前阶段

继续使用：

1. `RUST_LOG`

当前默认：

1. 开发态 `info`
2. 终端输出保留 level、target、thread id

### 10.2 输出显示原则

1. 开发态以人类可读为主
2. 字段不能因为“好看”被隐藏掉
3. 文本顺序应便于肉眼快速识别 `usecase / outcome / 关键锚点`

### 10.3 未来演进

未来若增加文件输出层：

1. 终端层继续保留
2. 文件层只筛 `warn/error`
3. 两个 layer 消费同一份 `tracing` 事件
4. 业务代码零感知

## 11. 为什么现在不新增 `日志.rs`

### 11.1 当前判断

现在新增单独 `日志.rs` 属于低价值拆分。

### 11.2 原因

1. 当前真正的复杂度还在“埋点策略”而不是“装配代码量”
2. 日志初始化仍属于 `assembly` 的天然职责
3. 项目有明确的文件数量克制要求
4. 现在拆文件更像形式主义，不会增加真边界价值

### 11.3 未来允许拆分的阈值

仅当同时满足以下条件时才考虑拆：

1. `总装.rs` 已明显过载
2. 日志 layer、panic hook、未来落盘策略已形成独立阅读单元
3. 拆出后能减少耦合并提升理解成本

即使拆出，也应是 `assembly` 边界内的装配文件，不是新的横切“日志中心”。

## 12. 禁止事项

为防止实现期漂移，以下做法明确禁止进入主干：

1. 用 `println!` 临时补主链日志
2. 前端 `console.log` 充当排障主证据
3. 在多个层重复宣告同一业务事实
4. 用消息文本代替 `error_code`
5. 用 `socket connected`、`room joined`、`ack` 冒充业务成立
6. 同步写文件进入热路径
7. 为日志新增专用 DTO / manager / wrapper 核心
8. 为了“统一”而把所有业务日志都塞进一个大工具函数
9. 因为开发态可读性而牺牲字段稳定性
10. 当前阶段为日志新增 `日志.rs`

## 13. 测试与验证要求

实现时至少要补以下验证：

1. 结构化字段测试继续保留并扩展 `outcome`
2. HTTP 成功路径具备 `info` 日志
3. HTTP 拒绝路径具备 `warn` 日志
4. realtime 成功路径具备 `info` 日志
5. realtime 广播失败具备 `error` 日志
6. panic hook 至少能验证“进入统一日志主链”

验证方式优先：

1. 单元测试验证字段存在
2. 集成测试验证真实链路会产生日志
3. 手动运行 `run.ps1` 后，终端能看到业务主链，而不是只有启动日志

## 14. 实现期自检清单

任何日志相关改动在合并前必须回答：

1. 这条日志的真相归属在哪一层？
2. 这条日志是否重复宣告了别处已宣告的事实？
3. 这条日志是否具备 `usecase / adapter / outcome`？
4. 失败或拒绝时是否具备稳定 `error_code`？
5. 这条日志会不会让主业务因 IO 被阻塞？
6. 这条日志未来是否能自然进入文件落盘而无需改业务代码？
7. 这次改动是否偷偷引入了第二套日志源？

若任何一项答不上来，默认说明实现有漂移风险，不能直接落地。

## 15. 推荐实现顺序

为降低一次性改动风险，实现时建议按以下顺序推进：

1. 先统一初始化装配与 panic hook
2. 再补 HTTP 冷路径关键 `info/warn/error`
3. 再补 realtime 热路径关键 `info/warn/error`
4. 最后补测试与手动运行验收

理由：

1. 先把输出底座稳住
2. 再点亮成功链路
3. 最后用测试锁住字段纪律，防止回退

## 16. 结论

本设计最终要得到的不是“更多日志”，而是：

1. 后端唯一真相源
2. 稳定字段纪律
3. 关键主链可追踪
4. 拒绝与异常边界清晰
5. 当前简单，未来可平滑扩展到 `warn/error` 自动落盘

在这个约束下，当前最优雅的答案是：

1. 保持 `tracing` 为唯一事件源
2. 保持 `assembly` 为日志装配边界
3. 当前不新增 `日志.rs`
4. 当前不落盘
5. 未来通过额外 layer 接入非阻塞 `warn/error` 文件落盘
