## 1. 为什么要单独补这一份 spec

前两轮上传优化已经做了两类事：

1. 把明显不合理的限制解锁，比如视频 `50MB -> 200MB`
2. 把上传吞吐往上推，比如提高前端并发、补 `parallelUploads`、补 `Rustus` 参数

这些改动解决的是：

- 上传经常被门禁拦住
- 上传容易被前端 watchdog 误杀
- 上传吞吐偏保守

但用户在真实模拟里又发现了一条更伤系统的问题：

1. 上传视频 A，中途中断
2. 服务器端已经出现了 A 的相关文件或临时残留
3. 之后点击“重试”，服务器端又新长出一份 A 的相关文件

这说明现在的问题已经不只是“快不快”，而是：

**上传生命周期语义本身不干净。**

更直白一点说：

- 用户以为自己点的是“继续上传”
- 系统有时实际执行的是“再新建一份上传”
- 中断残留没有被统一回收
- 原片、临时文件、打包资产、冷源 TTL 没有收成一套统一真相

如果不把这个问题先收口，后面继续堆吞吐优化，只会把“更快地制造重复文件和垃圾残留”这件事放大。

所以这份 spec 的目标不是“继续调参数”，而是：

**把媒体上传从“能传、能快”推进到“语义干净、资产生命周期单一真相、对服务器友好”。**

## 2. 当前现象与源码事实

### 2.1 用户看到的现象

当前模拟里最典型的异常是：

1. 一个视频上传中断
2. 服务器已经留下相关文件
3. 之后再点“重试”，服务端又长出第二份相关文件

从运营和工程角度看，这都不友好：

- 存储对象数膨胀
- 目录和对象定位更乱
- 清理成本变高
- 排障更难
- 用户以为是续传，系统实际上可能在重复造资产

### 2.2 现有源码里的真正原因

对照当前源码，现象并不是错觉，而是有明确原因的。

#### 2.2.1 前端当前的“重试”语义并不纯

当前前端 `重试草稿()` 的逻辑是：

1. 先把草稿的 `attachmentId` 清空
2. 如果原 uploader 或原 file 还在，则尝试 `retryUpload`
3. 如果原 uploader / file 已经不在了，则重新调用 `prepareMediaUpload(...)`
4. 重新拿到一个新的 `attachment_id`
5. 再把文件重新塞进新的 uploader

这意味着：

- 有些“重试”是真继续
- 有些“重试”其实已经变成“重新开始一次新上传”

而当前 UI 并没有把这两种语义明确分开。

这就是第一层漂移：

**用户表达的是一个词 `重试`，系统内部却可能走两种完全不同的生命周期。**

#### 2.2.2 后端 prepare 目前没有幂等收口

当前 `prepare` 主链只是：

1. 校验会话
2. 创建 `prepared` 附件占位
3. 记录上传运输信息

它并没有做这些事：

- 同一文件/同一次失败重试时是否应该复用旧附件
- 同一用户短时间重复 prepare 是否应该幂等
- 旧的 `prepared` 附件何时算废弃

所以现在如果前端重新 `prepare`，后端就会老老实实再给一份新的 `prepared`。

#### 2.2.3 Rustus hook 只登记 finished，不负责收尸

当前 `post-finish` hook 做的是：

1. 读 `attachment_id`
2. 校验 upload token
3. 写回 transport receipt
4. 记 `storage_locator / upload_id / finished_at`

它没有负责：

- 把旧的失败上传标成废弃
- 删除旧的中断临时文件
- 统一处理“resume 失败后 restart”的切换

这本来并不一定是 bug，因为 hook 本来就应该薄。  
但问题在于：**如果应用层也没有统一裁决和回收，那这块残留就没人收。**

#### 2.2.4 当前冷源清理只清 ready 冷源，不清中断残留

当前代码里已经有一条清理链：

- 查询到期的 `ready` 原始冷源
- 删除对象存储里的原始冷源
- 回写 `origin_deleted_at`

但这条链只处理：

**已经 ready 的原始冷源。**

它不处理：

- `prepared` 但再也不会完成的附件
- transport 已失效的 upload
- orphan 临时文件
- 用户已经放弃的旧上传

这就是第二层漂移：

**系统只定义了“成功后的尾清理”，没有定义“失败/放弃后的回收清理”。**

## 3. 核心问题到底是什么

把现象压缩后，问题不是一个，而是三个连锁问题：

### 3.1 “继续上传”和“重新开始上传”被混成一个按钮语义

这会直接导致：

- 用户以为是断点续传
- 系统实际上重新 `prepare`
- 服务端长出新的附件和新的一套文件

### 3.2 资产生命周期没有统一真相 owner

现在至少存在这些资产层：

1. 用户上传的原片
2. Rustus/shared 临时文件
3. 当前 canonical original
4. 打包后的 HLS/DASH/CMAF 资产
5. WebTorrent/P2P 分发元数据
6. 最高质量最高码率母本

如果没有统一 owner，就会出现：

- 这里删一份
- 那里留一份
- 另一个地方又拿着旧定位继续读

最终系统里只有“文件越来越多”，没有“生命周期越来越清楚”。

### 3.3 失败与放弃路径没有被建模

现在只有：

- `prepared -> ready`
- `ready -> cold source deleted`

但没有明确建模：

- `prepared -> abandoned`
- `transporting -> expired`
- `packaging failed -> hold / retry / cleanup`
- `orphan temp file -> reclaimed`

没有这些状态，后面所有所谓“清理”都会退化成：

**写几个脚本，到目录里猜一猜。**

这不符合 DDD，也不符合 Unix。

## 4. 这次要守住的架构原则

这次设计必须同时满足 4 组原则。

### 4.1 DDD：真相 owner 唯一

业务层必须只有一套关于媒体资产生命周期的真相。

也就是说：

- 前端不能决定某个上传是不是业务上成功
- hook 不能决定附件已经 ready
- 打包器不能决定什么时候删原片
- 清理器不能根据目录猜一个文件是不是该删

所有这些只能由应用层统一裁决。

### 4.2 Unix：裁决和执行分离

谁该删、什么时候能删、删完如何推进状态，这是**裁决**。  
真正去删对象、删临时文件、删残留，这是**执行**。

这两件事必须分开：

- 应用层列出待执行动作
- shell / adapter 执行副作用
- 执行成功后再回写真相

不能把“裁决 + 执行 + 写状态”糊在一个随手函数里。

### 4.3 复用成熟轮子，不重造上传器

这轮明确继续站在成熟轮子上：

- 前端仍然是 `Uppy + Tus`
- 上传 sidecar 仍然是 `Rustus`
- 视频处理仍然复用 `ffmpeg / ffprobe / Shaka Packager`
- 分发仍然复用 `HLS / DASH / CMAF / WebTorrent`

我们要做的是：

**补业务生命周期和薄适配层，不是另起炉灶手搓第二套上传体系。**

### 4.4 不再制造多套活路径

这次必须防止这几类“看起来很灵活，实际上很脏”的退化：

1. `retry` 既可能 `resume` 又可能 `restart`，但没有明确裁决
2. 删除原片的逻辑同时散落在 hook、打包器和清理器
3. 旧上传不真正退场，只是又叠一层新实现
4. 新旧生命周期同时活着，没有 cutover 和删除计划

## 5. 方案比较

### 5.1 方案 A：只修“重试重复创建”一个点

做法：

- 只改前端 `retry`
- 尽量让它更多走旧 uploader

优点：

- 看起来改动小
- 短期可能缓解重复文件

缺点：

- 治标不治本
- 没有定义 `resume` / `restart`
- 没有定义废弃上传清理
- 没有定义原片 / mezzanine / 分发资产的长期真相

结论：

**不能选。**

这会变成典型的“症状修复，不修根因”。

### 5.2 方案 B：先只补清理器，不改交互和状态机

做法：

- 后台定时清理 orphan 文件
- 维持当前前端“重试”语义不变

优点：

- 对现有 UI 改动少
- 能减少一部分残留

缺点：

- 用户仍然会被假语义误导
- 旧上传和新上传仍然会被混成一团
- 清理器会沦为兜底垃圾站，而不是生命周期的一部分

结论：

**也不选。**

这会让系统依赖“事后扫地”，而不是“事前把路径走对”。

### 5.3 方案 C：统一上传生命周期 + 资产生命周期 + 回收清理

做法：

1. 把 `resume` 和 `restart` 明确分开
2. 应用层统一裁决附件和资产生命周期
3. 原片、mezzanine、分发资产各自有明确保留策略
4. 后台清理器只执行应用层给出的回收清单

优点：

- 一次性把真相收口
- 以后吞吐优化和删除策略都建立在干净生命周期上
- 最符合 DDD / Unix / 成熟轮子复用

缺点：

- 改动面更广
- 需要补较多测试和观察字段

结论：

**本次采用方案 C。**

## 6. 最终裁决：长期真相是什么

这次最重要的裁决不是一个参数，而是：

**长期应该保留什么，短期应该保留什么，什么该尽快删。**

### 6.1 长期真相

长期真相定成：

- `HLS/DASH/CMAF` 分发资产
- `WebTorrent/P2P` 分发元数据

这是系统长期保留、长期服务播放、长期支撑边下边播和群友互助分发的资产层。

### 6.2 短期回退层

最高质量最高码率的 `mezzanine` 只保留 `24h`。

它的职责不是长期服务，而是：

- 打包问题回退
- 短期重打包
- 线上问题排障
- 紧急校验

### 6.3 临时输入层

用户原片不是长期资产，只是上传输入。

裁决定为：

**打包成功且分发真相成立后，原片立即删除。**

这也意味着：

- 原片不再是长期权威母本
- 最高质量 `mezzanine` 也不是长期权威母本
- 真正长期存在的是分发资产层

换句话说：

**长期真相 = 分发资产；24 小时母本 = 短期回退层；原片 = 打包成功即删。**

## 7. 生命周期状态机

### 7.1 附件上传生命周期

建议把上传真相拆成这些阶段：

1. `prepared`
2. `transporting`
3. `transport_finished`
4. `packaging`
5. `distribution_ready`
6. `abandoned`

这里要特别强调：

- `prepared` 不等于上传开始
- `transport_finished` 不等于业务 ready
- `distribution_ready` 才是视频在业务上的成功成立

### 7.2 资产删除生命周期

原片与 mezzanine 删除分别建模：

1. `original_pending_delete`
2. `original_deleted`
3. `mezzanine_pending_delete`
4. `mezzanine_deleted`

分发资产这轮不进入自动 TTL 删除主链。  
否则会和“长期真相 = 分发资产”直接冲突。

### 7.3 非法状态必须显式拒绝

至少这些路径必须被当成非法：

1. `prepared` 直接跳 `distribution_ready`
2. 分发资产未 ready 就删原片
3. 已 `abandoned` 的附件还能继续 `complete`
4. 已 `original_deleted` 的旧上传仍然尝试 `resume`
5. `mezzanine_deleted` 后还尝试按它重打包，但没有 fallback

## 8. 重试、继续上传与重新开始

### 8.1 必须把一个“重试”拆成两个明确意图

当前最大的问题之一，是“重试”同时背了两种语义：

- 继续旧上传
- 放弃旧上传并重新开始

这必须拆开。

### 8.2 `resume`：继续上传

`resume` 的定义是：

- 同一个 `attachment_id`
- 同一个上传语义
- 同一个资产生命周期

只有在这些条件同时满足时才允许：

1. 旧附件仍处于 `prepared / transporting`
2. transport token 仍有效
3. Rustus 侧原 upload 仍存在且可继续
4. 原片尚未进入删除路径

满足这些条件时：

- 前端只能复用旧上传
- 后端不能重新 `prepare`
- 这才叫“真正续传”

### 8.3 `restart`：重新开始

`restart` 的定义是：

- 明确放弃旧上传
- 显式创建新上传

它不是 bug，而是一个被建模的合法动作。  
但前提是必须先做这件事：

**应用层先把旧附件标成 `abandoned`。**

然后才允许：

- 创建新的 `prepared`
- 分配新的 transport
- 进入新的上传链

这样就不会再出现：

“名义上是 retry，实际上偷偷长出第二条活路径”

### 8.4 前端按钮语义也必须改清楚

建议前端直接拆成两个动作：

1. `继续上传`
2. `重新上传`

前者只允许走 `resume`，后者只允许走 `restart`。  
不要再用一个模糊的 `重试` 承载两种业务语义。

## 9. 原片、mezzanine、分发资产的删除裁决

### 9.1 原片删除条件

原片不能因为“ffmpeg 跑完了”就删。  
删除原片的前提必须是：

1. 打包产物已成功上传
2. 分发元数据已成功写入
3. 附件已正式进入 `distribution_ready`

只有这 3 件事都成立，原片才允许进入：

- `original_pending_delete`
- `original_deleted`

这条裁决必须由应用层给出。  
禁止：

- `Rustus hook` 自己删
- 打包器自己删
- 前端按钮顺手删

### 9.2 mezzanine 删除条件

mezzanine 是短期回退层，所以比原片删得晚。

建议条件是：

1. 附件已经 `distribution_ready`
2. 当前没有重打包 / 修复任务
3. 没有人工 hold
4. 已超过 `24h TTL`

满足时进入：

- `mezzanine_pending_delete`
- `mezzanine_deleted`

### 9.3 分发资产长期保留

当前裁决是：

**这轮不对分发资产做自动 TTL 删除。**

原因不是偷懒，而是因为：

- 它们就是系统的长期分发表面
- WebTorrent/P2P/HLS/DASH/CMAF 都依赖它们
- 如果现在把它们也和原片/mezzanine 一起删，长期真相就又漂了

## 10. 废弃上传与垃圾回收

### 10.1 这次必须把“失败和放弃”建模

这次清理不再是“目录卫生”，而是生命周期的一部分。

需要纳入回收范围的至少有：

1. `abandoned` 附件
2. 已过期的 `prepared`
3. 已失效的 transport 记录
4. 无主的 Rustus/shared 临时文件
5. 已到期的 `mezzanine`

### 10.2 清理器的边界

清理器不允许自己猜业务真相。  
它只能做 3 步：

1. 应用层列出待回收清单
2. shell / adapter 执行删除
3. 删除成功后回写删除事实

也就是说，清理器不是法官，它只是执行员。

### 10.3 幂等性要求

所有删除和回收动作都必须按幂等来设计。

因为实际线上一定会出现：

- 重复调度
- 重复执行
- 部分成功
- 对象已不存在

所以正确做法是：

- 对象不存在不算灾难
- 删除成功后才能回写删除事实
- 重复执行应稳定，不应把状态打乱

## 11. 模块职责划分

### 11.1 前端

前端只做：

1. 表达用户意图：`resume / restart`
2. 展示上传与处理状态
3. 保持必要本地草稿态

前端不能做：

1. 决定附件是否业务成功
2. 决定资产删不删
3. 决定是否还能继续 `resume`

### 11.2 应用层 / 用例层

应用层拥有：

1. 上传状态推进裁决
2. 删除资格裁决
3. 回收清单生成
4. `resume / restart` 合法性判定

这层是这次设计的唯一真相 owner。

### 11.3 adapter / shell

adapter / shell 只负责：

1. Rustus hook 接入
2. 对象存储读写
3. 调用 ffmpeg / Shaka Packager
4. 执行删除动作
5. 记录日志和可观测字段

它们不能偷偷承载这些业务真相：

1. ready 判定
2. 删除资格
3. 上传语义切换

## 12. 可观测性要求

这轮如果不补可观测性，后面线上还是只会凭感觉猜。

每条上传链至少要串出这些字段：

1. `attachment_id`
2. `request_id`
3. `transport_upload_id`
4. 当前生命周期阶段
5. 删除原因
6. 删除时间
7. `resume / restart / abandon / gc` 动作类型

这样以后看到“怎么又多出一份文件”，才能直接回答：

- 是旧上传没 abandon
- 是 restart 产生的新附件
- 还是 orphan 文件未被回收

## 13. 测试与验证门禁

### 13.1 先补表征测试，再改实现

必须先把当前 bug 钉成失败事实：

1. 中断上传后，若仍满足条件，`继续上传` 必须复用旧 `attachment_id`
2. 不满足 resume 条件时，`重新上传` 才允许新建 `attachment_id`
3. 不能再出现“点了 retry，后台实际上偷偷新建一份”的伪语义

### 13.2 应用层状态机测试

至少覆盖这些流转：

1. `prepared -> transport_finished -> packaging -> distribution_ready`
2. `distribution_ready -> original_deleted`
3. `distribution_ready + TTL到期 -> mezzanine_deleted`
4. `prepared / transporting -> abandoned`

同时要显式测非法流转拒绝。

### 13.3 回收与删除测试

要覆盖：

1. orphan 临时文件回收
2. expired prepared 回收
3. expired transport 回收
4. 原片秒删
5. `24h` 后 mezzanine 删除
6. 分发资产不误删

### 13.4 幂等测试

重复执行时必须稳定：

1. 对象已不存在也不应炸
2. 重复回收不应产生二次破坏
3. 删除事实不能乱写

## 14. 这次明确不做的事

为了防止范围炸开，这次明确不做：

1. 不重做上传协议
2. 不放弃 `Uppy + Tus + Rustus`
3. 不把 WebTorrent/P2P 改成新的私有分发协议
4. 不把分发资产生命周期也一起设计成复杂的自动淘汰系统
5. 不在这一轮把所有视频处理链升级成完整多档 ABR 工厂

这次只做两件根事：

1. 把上传语义收干净
2. 把资产生命周期收成单一真相

## 15. 最终结论

这次设计的最终裁决可以压成 6 句：

1. `retry` 不能再是模糊词，必须拆成 `resume` 和 `restart`
2. 应用层是媒体上传与资产生命周期的唯一真相 owner
3. 原片在分发真相成立后立即删除
4. 最高质量 `mezzanine` 只保留 `24h`，作为短期回退层
5. 长期真相是 `HLS/DASH/CMAF + WebTorrent/P2P` 分发资产
6. 清理器只执行应用层给出的回收清单，不自己猜业务真相

如果这一套落成，系统会从现在的：

**“上传能跑，但中断、重试、删除和残留都不够干净”**

推进到：

**“上传语义清楚，资产层次清楚，回收路径清楚，对服务器和未来公网部署都更友好。”**
