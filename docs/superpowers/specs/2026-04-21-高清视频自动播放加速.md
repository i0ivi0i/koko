## 0. 为什么要补这份文档

前面的文档已经把大方向裁死了：

1. 后端不再承担媒体加工主链；
2. 新视频只保留一份 `canonical video`；
3. 长期协作分发主平面是 `WebTorrent`；
4. 后端不该再长期养一堆视频派生垃圾。

但如果只停在这些结论上，执行时还是很容易漂：

1. 有人会为了“首屏稳一点”重新加回后端封面图；
2. 有人会为了“播起来更顺”偷偷压低码率、降分辨率；
3. 有人会把预览重新绑定到 autoplay owner，结果又回到“先黑框，等自动播才有内容”；
4. 有人会把“滑到视频就帮助 swarm 加速”做成半截，视频一滑走就停；
5. 有人会把“激进补齐”误实现成“一屏多个视频同时真播”，最后页面更卡。

所以这份文档的作用不是重复上一份设计，而是把下面这件事讲透：

**为什么 `video` 文件本身必须成为预览、播放、分发的唯一真相源；以及为什么系统要在不牺牲画质的前提下，把群友的滑动行为转成真正的协同加速收益。**

---

## 1. 前因后果

### 1.1 旧世界的问题

旧世界最容易长成这样：

1. 时间线看的是一张后端封面图；
2. 点击后播的是另一份视频；
3. 自动播放又走第三套状态机；
4. `WebTorrent` 只是“也许能加速一下”的旁路。

这种做法的问题不是“代码丑”，而是产品真相分裂：

1. 预览不是视频自己；
2. 播放不是预览的自然延续；
3. 分发不一定真正在帮后面的人；
4. 任何一个环节要补丁，都会继续长第二资产、第二入口、第二 owner。

结果就是：

- 后端越来越重；
- 时间线和查看器越来越像两套系统；
- 用户看到的不是“视频天然自带预览”，而是“这儿先放了一张图，等会再切成视频”；
- swarm 很难真正热起来。

### 1.2 用户真正想要的是什么

用户真正想要的，不是“系统给我做了很多聪明小优化”，而是下面这种直觉：

1. 这是一个视频；
2. 我第一眼就看到它是什么；
3. 它自己就能预览；
4. 我点开还是它；
5. 别人刷过这个视频，后面的人就应该更快。

也就是说，用户直觉要的其实就是：

**同一个视频文件本身就是预览来源唯一真相源。**

### 1.3 为什么现在要走到这一步

因为现在项目已经具备这个方向的基础：

1. 客户端主链已经往单文件 canonical 收拢；
2. 前端已经在做时间线首帧预览与运行时预览缓存；
3. `WebTorrent` 已经不是实验玩具，而是正式分发平面；
4. 你已经明确裁决：质量优先，不能误判把用户视频压烂。

所以现在不把逻辑彻底收死，后面执行时最容易重新长歪。

---

## 2. 最终一句话裁决

以后在 `koko` 里：

**同一个 `canonical video` 文件，必须同时成为预览源、自动播放源、查看器播放源、`WebTorrent` payload、群友做种源。**

由此推出三个硬结论：

1. 禁止后端为新视频长期保存独立封面图片；
2. 禁止群友滑到过该视频后又在滑走时中途停止后台补齐和做种；
3. 禁止用降低画质去换秒开和丝滑。

---

## 3. 为什么必须这样做

### 3.1 为什么预览必须回到视频自己

因为只要预览不是视频自己，系统就会再次分裂：

1. 封面图有自己的生命周期；
2. 封面图有自己的缓存键；
3. 封面图有自己的协议字段；
4. 时间线和查看器会围绕它长出第二套判断。

这类“先临时加一张图再说”的做法，短期像省事，长期一定会把主链重新做回网页思维。

真正高级的做法不是把体验拆成更多小资产，而是让同一个对象承担更多真实职责。

所以这里必须反过来：

**不是“给视频配一张图”，而是“让视频自己承担被快速看见的能力”。**

### 3.2 为什么协同加速必须激进

你已经明确选择：

- 不区分设备；
- 不区分网络；
- 不区分是否充电；
- 只要滑到就继续补到底。

这背后的逻辑很简单：

1. 群聊是高频流式场景；
2. 用户不会认真思考“我刚刚帮没帮别人加速”；
3. 如果系统太保守，swarm 永远热不起来；
4. 只有足够多人顺手补到底，后面的人才会越来越快。

所以这里不应该搞“看一眼就只拉一点点”的保守思路。  
你要的不是单个用户最省流，而是整个群聊系统越来越快。

### 3.3 为什么不能靠压画质换丝滑

因为一旦开了这个口子，执行时就极容易退化成：

1. “为了更快，先压一版吧”；
2. “为了兼容，再降一点吧”；
3. “为了稳定，干脆默认低码率吧”。

最后产品会得到一个表面顺、实际糊的系统。

这在你这里是明确错误方向，因为你已经给出最高优先级：

**高码率、高清晰度、原画质优先。**

所以必须把这句话写死：

**顺滑靠链路优化、缓存、分片优先和调度 owner 解决，不靠压糊视频解决。**

## 4. 核心禁令

### 4.1 禁止新视频长出第二正式媒体资产

新视频链路只允许保留一份正式媒体资产：

- `canonical video`

它同时服务于：

- 时间线预览；
- 时间线自动播放；
- 查看器播放；
- `WebTorrent` 分发；
- 本地缓存；
- 后续做种。

禁止再长出：

- `preview still`
- `thumbnail asset`
- `poster asset`
- 第二份正式视频变体

### 4.2 禁止拿糊画质换启动速度

默认禁止：

1. 不降分辨率；
2. 不降帧率；
3. 不降码率；
4. 不重编码成更糊版本；
5. 不允许“为了顺”偷偷生成低清版。

允许的只有：

1. 直通；
2. `remux`；
3. `faststart`；
4. 在不伤画质前提下做容器级优化。

### 4.3 禁止为了“大缓冲很稳”牺牲第一眼秒开

自动播放策略明确裁决为：

1. 拿到可播首段就尽快播；
2. 不为了“大缓冲很稳”而先等很久；
3. 用户第一眼应该优先感受到“立刻有内容”，不是“很高级但慢半拍”。

### 4.4 禁止用户滑过视频后半途停止补齐

只要滑到过视频，就进入补齐链路：

1. 先拿预览关键字节；
2. 再拿首播关键片段；
3. 然后继续补完整文件；
4. 滑出视口后也不停止；
5. 补齐完成后继续做种。

### 4.5 禁止无 owner 的乱解码、乱自动播

虽然补块可以激进，但解码自动播不能失控。

必须存在统一调度 owner，负责限制：

1. 同时真正自动播放的视频数量；
2. 同时进入重度解码的视频数量；
3. 自动播 owner 的切换时机；
4. 自动播和时间线滚动之间的冲突。

原因很现实：

**你要的是“激进加速”，不是“激进掉帧”。**

---

## 5. 运行时主链禁令

### 5.1 禁止时间线第一眼重新退回后端封面图

时间线第一眼只能有三种合法来源：

1. 本地预览缓存；
2. 同一个视频文件已拿到的早期关键字节派生结果；
3. 同一个视频文件首个已解码帧。

禁止第四种来源重新变成：

4. 后端长期独立封面图。

### 5.2 禁止把自动播放做成第二条媒体链

自动播放不是另一条媒体链，只是同一个 `canonical video` 的另一种运行时状态。

它只负责：

1. 立刻用同一视频文件起播；
2. 继续推动补块和补齐；
3. 在合适时机接手视觉主体；
4. 不重建节点、不闪烁、不切到第二真相源。

### 5.3 禁止查看器切回另一份视频或第二真相源

查看器必须是时间线的自然延续：

1. 进查看器之前看的是这个视频；
2. 进查看器之后播的还是这个视频；
3. 只是壳层从时间线切到查看器，媒体真相不变。

### 5.4 禁止让用户滑动视频却不给 swarm 带来持续收益

用户每一次滑过视频，都应当被系统视为一次真实预热机会：

1. 先让当前用户快；
2. 再让下一个用户更快；
3. 再让 swarm 越来越热。

如果做完之后，后续群友仍没有明显加速收益，那就说明实现没有真的达到设计目标。

---

## 6. 后端禁令与保留职责

后端对新单文件视频只保留：

1. 唯一 `canonical video` 存储；
2. `content_hash / swarm_id / torrent metadata`；
3. `24 小时` web seed / 冷启动补块；
4. 到期删除服务器冷备。

后端对新单文件视频明确禁止：

1. 长期存封面图；
2. 把 `thumbnail_storage_key` 继续当新主链正式字段；
3. 默认承诺 `preview_asset.still_url`；
4. 再生成第二份静态 poster；
5. 为“首屏体验”偷偷复活第二资产。

历史旧视频允许兼容 legacy still，但必须被视为过渡债务，而不是新标准。

## 7. 最容易漂移的地方

这部分是给后面执行的人看的，目的是防止“明明都认同，写着写着又长歪”。

### 7.1 漂移一：为了稳一点，先加个后端 poster

看起来像是小补丁，实际上是在重新制造第二真相。

一旦这么做，后面一定会继续长：

- poster URL
- poster cache
- poster 生命周期
- poster 协议面

这个方向必须直接掐掉。

### 7.2 漂移二：为了顺一点，先压一版低码率

看起来像是“先保证体验”，实际上是在偷改用户资产。

这是明确禁止的。  
你这里的原则不是“成功播出来就行”，而是“优先高清原画质”。

### 7.3 漂移三：为了节流，视频滑走就停补齐

看起来像省资源，实际上会让 swarm 永远半死不活。

如果用户滑到过视频，却没给后续群友带来持续收益，那这个设计就没完成。

### 7.4 漂移四：把激进补齐做成激进真播

补齐和自动播不是一回事。

可以 aggressively 补块，但不能让一屏多个视频同时乱播、乱解码。  
否则页面卡顿，用户主观体验反而更差。

### 7.5 漂移五：预览重新依赖 autoplay owner

这会直接把系统做回旧毛病：

1. 不播就没预览；
2. 先黑框；
3. 等自动播起来后才突然有内容。

这个逻辑必须严格禁止。

---

## 8. 防漂移执行禁令

后续写 implementation plan 和代码时，禁止踩下面这些红线：

1. 禁止引入任何不能明确回答“是否仍只围绕同一个 `canonical video` 工作”的新逻辑。
2. 禁止为了优化体验重新引入第二长期资产。
3. 禁止把降低画质当成默认优化手段。
4. 禁止让预览重新依赖 autoplay owner。
5. 禁止让滑走视频后停止补齐重新成为默认行为。
6. 禁止让多个视频同时无节制解码自动播。

换句话说：

**后面不是“自由发挥实现这个感觉”，而是禁止越过这些真相边界。**

---

## 9. 验证门禁

实现前后至少要证明这些事实：

1. 新单文件视频 `complete` 后，后端不再长期写入 `thumbnail_storage_key`；
2. 新单文件视频协议面不再默认承诺 `preview_asset.still_url`；
3. 时间线预览、自动播放、查看器播放都使用同一个 `canonical video`；
4. 时间线预览不依赖 autoplay owner 才存在；
5. 用户滑到某视频后，即使滑走，后台仍继续补齐整文件；
6. 整文件补齐完成后，客户端进入做种态；
7. 自动播放秒开策略不能以降低画质为代价；
8. 自动播放与预览切换过程中不能出现黑闪、白闪、节点重建闪烁；
9. 多视频场景下，补块可激进，但解码自动播必须受统一调度 owner 控制；
10. `chrome-devtools-cli` 真实烟测必须覆盖：
    - fresh user 首次进房第一眼；
    - 自动播放首播速度；
    - 滚动经过视频后继续后台补齐；
    - 滑走视频后 swarm 仍继续升温；
    - 后续用户进房时同视频加载明显更快。

---

## 10. 最终硬裁决

`koko` 的新视频主链必须收敛成下面这句话：

**同一个高清视频文件，就是预览、自动播放、查看器播放、协同分发和后续做种的唯一真相源。**

从这句话往外推，所有具体裁决都只是自然结果：

1. 禁止后端再长期保存新视频封面图；
2. 禁止预览再独立于视频本体长期存在；
3. 禁止让群友滑到视频却没有顺手帮后面的人加速；
4. 禁止把这种加速做成滑走就停的半截逻辑；
5. 禁止绕开主链设计、缓存、关键分片优先和 owner 调度，改用第二资产或第二链路伪造体验；
6. 禁止系统用牺牲画质来伪造“更顺”。

这份文档比上一版写得更长，不是为了显得更复杂，而是为了防止后面执行时重新长歪。

真正要守住的核心只有一句：

**不要再把视频拆成“预览一套、播放一套、分发一套”；让同一个视频文件把这些职责一次性承担完。**
