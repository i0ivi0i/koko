## 实现与验收记录（2026-04-23）

本次实现已经落地，关键收口如下：

1. 后端 `swarm_peer_presence` 已扩展 `partial_peer`，但 `MEDIA_READY` 仍只认 `complete_peer / backend_strong_seed / 可用 web_seed`。
2. 前端协作分发 runtime 已默认进入 eager 补齐，并在进入 swarm 后先上报 `partial_peer`，补齐完成后升级为 `complete_peer`。
3. 视频协作补齐已去掉 `reuseOnly` 保守门槛，自动播放 / 查看器继续共用同一条 swarm owner 链。
4. 页面重开后，只要本地完整缓存仍在，当前房间内的附件会恢复帮助任务；不再只恢复 `locally_complete` 表象。

自动化验证已通过：

- `pnpm --dir frontend test`
- `pnpm --dir frontend typecheck`
- `pnpm --dir frontend build`
- `cargo test -j 1`
- `pwsh -File tests/启动器脚本检查.ps1`

真实浏览器烟测已完成：

- 环境：`https://localhost`，房间 `1234b`，`sender / A / B / C / D` 多隔离上下文。
- 素材：发送端先上传 1 张图片，再上传 2 条 MP4；其中后一条视频使用了 `D:\200-生活\230-照片备份\233-Telegram\色色\VID_20230823_122115_920.mp4`。
- 现象 1：`A/B/C/D` 入房后都会真实发起 locator / torrent / `webtorrent/{infohash}/content-*.mp4` 请求，说明帮助链已经不是“只在显式 viewer 打开后才勉强开始”。
- 现象 2：`A/B/C` 点开同一条最新视频后，前端真实上报 `POST /api/media/{attachment}/presence`；数据库 `swarm_peer_presence` 中同一附件同时出现多个 `complete_peer` 和 `backend_strong_seed`，群聊活跃度已经直接转成 swarm 强度。
- 现象 3：`D` 在前 `24 小时` 阶段进入同一房间时，同时出现 `/webtorrent/{infohash}/content-*.mp4` 与 `/api/attachments/{attachment}/content?variant=original` 的 `206` 请求，符合“服务器强帮助者 + 群友 swarm”共同参与的现实，而不是单来源串行。
- 现象 4：把 `web_seed_until` 人工拨到 `24 小时` 之后并清空该附件的 peer presence 后，前端先进入 `正在尝试连接群友`，随后稳定落到 `当前没有在线种子，等待群友上线`。
- 现象 5：再把同一附件强制切到删除终态后，前端重试立即切成 `内容已删除`，没有继续伪装成一般加载失败。

补充说明：

- 在本机局域网 + aggressive eager 补齐环境下，浏览器侧 `partial_peer` 窗口极短，真实烟测里很快就晋级成 `complete_peer`；`partial_peer` 的连接语义、非 ready 语义、以及 stale 窗口裁决已由后端/前端定向测试单独覆盖。
- 本轮没有新增 deferred 项；未实现项为 `0`。

## 0. 为什么还要补这一份设计

`2026-04-22` 那份 spec 已经把三件最危险的事情裁住了：

1. 前端正式媒体字节不能绕开 `WebTorrent`；
2. `24 小时` 后服务器必须退出媒体字节供给；
3. 没种子和已删除都必须说真话。

但它还没有把下面这类“系统到底该激进到什么程度”写死，所以实现仍然容易保守化漂移：

1. 自动播放过的 A、B、C 到底算不算后面 D、E、F 的正式帮助者；
2. D 进来时，到底该只靠服务器、只靠某一个群友，还是该同时吃多个来源；
3. A、B、C 手里只有半成品片段时，到底算不算有价值的 swarm 成员；
4. A 划走视频后，到底该继续帮后人还是默认停掉；
5. 一个活跃群里连续播过很多条视频后，到底该不该只保最近几条，还是默认都继续帮；
6. 浏览器、WebRTC、WebTorrent 的物理边界，到底该不该被上抬成产品层保守规则。

如果这些边界不写死，后续 plan 和实现很容易掉进几种“看起来合理、实际上会把系统做弱”的漂移：

1. 为了省资源，把自动播放用户当成一次性消费者，而不是未来帮助者；
2. 为了降低复杂度，把“多人协同分发”偷换成“服务器先发，群友只是顺带”；
3. 为了让状态更容易判断，误把“必须是完整 peer 才算有用”写成硬规则；
4. 为了所谓稳态，把“只保最近 `3-5` 条帮助任务”做成产品默认；
5. 为了照顾移动端或弱网，重新长出“手机端保守版协作分发真相”；
6. 把底层运行时上限包装成产品哲学，最后把系统做回“名义上 P2P，行为上依旧谨慎兜底”的弱 swarm。

所以这份设计不是重写上一份 spec，而是补上上一份 spec 故意没展开的一层：

**当主链真相已经收口后，系统必须怎样把群聊活跃度直接转成分发能力。**

## 1. 这次真正要写死的运行真相

先把一句话写死：

**一段新视频进入群后，系统必须尽快把每一个看过它且仍在线的群友，都养成后来者的帮助者；前 `24 小时` 由服务器和群友一起并行猛拉，`24 小时` 后尽量由群友自己接住；群越活跃，这段视频的协同分发能力就越强。**

这句话展开后，就是下面八条硬裁决：

1. **禁止把自动播放用户当成一次性消费者。** 只要用户已经自动播放或观看过该附件，就默认进入“尽量补齐、尽量帮助后人”的链条。
2. **禁止把新来者的正式来源压成单来源。** D 进来时，应尽量同时从服务器、A、B、C 等多个可用来源并行拿片段，而不是只连一个人慢慢等。
3. **禁止把“不是完整 peer”偷换成“毫无价值”。** A、B、C 即便还没拿完整，只要手里已经有 D 当前缺的有用片段，也应立刻参与帮助。
4. **禁止把滑走、失焦、切别的消息，偷换成“帮助任务结束”。** 只要页面还活着，后台补齐和对外帮助默认继续。
5. **禁止把活跃群的多附件协作任务做成小水管保守模式。** 用户在活跃群里自动播放过很多条视频时，产品层默认不主动裁掉旧帮助任务。
6. **禁止把移动端、弱网、浏览器类型差异，上抬成第二套产品真相。** 只要同属浏览器壳，默认都共享同一套激进协作语义；差异只能收在能力适配和底层运行时边界。
7. **禁止把服务器强参与误解成背叛 P2P。** 前 `24 小时` 服务器越强，越是在帮助 swarm 尽快烧热；前提是它始终作为 swarm 成员参与，而不是偷偷开第二正式播放主链。
8. **禁止把“没有产品层保守刹车”理解成“无限全连、无限任务、无限资源”。** 产品语义必须激进，但底层仍只允许保留不可避免的协议级、浏览器级、运行时级硬边界。

这八条一起成立，才是你要的那种系统：

- A、B、C 看过不是白看；
- D 进来不是只靠一个来源吃；
- E、F 同时进来也不会被排成单线程；
- 服务器前期足够强，后期足够克制；
- 群越活跃，后面的人越快；
- 但系统不会靠第二主链或保守产品规则假装自己很稳。

## 2. 官方/生态实践真正支持什么，不支持什么

这部分必须写透，因为后面所有“要不要做得更猛”都不能脱离协议和成熟实现的现实。

### 2.1 官方支持多来源并行，不支持“只靠单来源慢慢传”

BitTorrent / WebTorrent 的本质，从来都不是“一个下载者对一个上传者单对单顺序拿”。  
它的正常世界本来就是：

1. 同时向多个来源请求不同片段；
2. 把请求做成流水线；
3. 谁在线、谁快、谁手里有缺的片段，谁就多发一点；
4. 服务器 `WebSeed`、浏览器 `WebRTC peer`、本地已缓存数据都可以共同组成当前分发面。

所以 D 同时吃 `服务器 + A + B + C`，不是离经叛道；  
真正离经叛道的，是把系统写成“D 只连单来源，其余人都只是背景噪音”。

### 2.2 官方支持高吞吐，但不支持“无限全连”

高吞吐不等于 full mesh，不等于所有人和所有人都永久全连。  
官方与成熟生态真正支持的是：

1. 有控制的 peer 连接上限；
2. 有控制的请求队列；
3. 多来源并行；
4. 及时利用已有片段；
5. tracker / signaling / NAT 穿透等基础设施配合。

所以这里必须补一个边界，防止后面实现时走向两个极端：

1. **禁止把“要做多对多”偷换成“只保守连一个来源”。**
2. **也禁止把“要做激进协同”误写成“所有人和所有人无限全连”。**

我们要的是前者不保守、后者不愚蠢：  
**产品层追求多来源并行，底层只保留协议与运行时的硬边界。**

### 2.3 官方支持浏览器 peer 和 WebSeed 并行，不支持“服务器自己演双面人”

浏览器侧 WebTorrent 的正常世界，就是：

1. 浏览器之间走 `WebRTC`；
2. 服务器可通过 `WebSeed` 和可用的 WebRTC seeder 能力参与；
3. 这些来源可以并行存在；
4. 但它们都应属于同一条 swarm 分发平面。

因此这里必须再写死一条：

**禁止把“服务器也参与 swarm”偷换成“前端还是主要直连服务器，群友只是装饰”。**

### 2.4 官方没有要求“帮助者必须先完整，才能开始帮别人”

协议世界里，真正重要的是：

1. 某个来源现在手里有没有你缺的有用片段；
2. 它现在能不能发给你；
3. 多个来源合起来，能不能让你更快进入可播和持续补齐。

协议并没有说：

**必须每个帮助者都先完整，才能参与当前分发。**

所以本项目这里必须明确：

- 对 swarm 内部协同，**部分片段帮助者**就是有价值的帮助者；
- 对前端失败态真相，仍然必须说真话，不能把几个零散碎片吹成“已经百分百稳了”。

换句话说：

**禁止把“部分 peer 有价值”和“已经拥有稳定 ready 真相”混成一回事。**

## 3. 角色与术语收口

为了防止后面每个人对“谁算帮助者”“什么时候算可用”理解不同，这里先把术语收口。

### 3.1 角色

1. **发片人**：把附件发进群的人。
2. **服务器强帮助者**：前 `24 小时` 内参与 swarm 的后端强 seed。
3. **已看群友**：已经自动播放或点开过该附件的在线群友，例如 A、B、C。
4. **后来者**：较晚进入该视频的人，例如 D、E、F、G、H。
5. **返回者**：之前看过、后来页面关闭或离开，之后又回来的人；如果本地数据还在，应重新加入帮助链。

### 3.2 术语

| 术语 | 定义 |
| --- | --- |
| `片段帮助者` | 当前虽未持有完整 payload，但已持有后来者缺少的有用片段，能够立即参与分发的 peer |
| `完整帮助者` | 已持有完整 payload，能够稳定继续做种的 peer |
| `服务器强帮助者` | 前 `24 小时` 内由服务器提供的 swarm 内强来源，包括 `WebSeed` 与真正可连的 WebRTC seeder |
| `帮助链` | 某个用户在观看或自动播放后进入的“继续补齐 + 继续帮助后来者”持续任务 |
| `帮助任务` | 某个具体附件在某个客户端上的后台补齐与对外分发任务 |
| `当前可恢复来源` | 当前重试窗口内，能真实为该客户端提供首播所需关键字节或持续补齐所需字节的来源集合；允许由多个来源共同构成 |

这里最重要的两个边界是：

1. **禁止把“帮助者”默认缩成只剩完整帮助者。** 片段帮助者同样有价值。
2. **禁止把“有几个帮助者存在”直接偷换成“前端一定 ready”。** 是否 ready，只认当前客户端在当前重试窗口里是否真的拿到了可恢复来源。

## 4. 一段视频进入群后的 `48 小时` 运行故事

这一节不用术语堆砌，直接用人话把 A、B、C、D、E、F、G、H 和服务器的关系写清楚。

### 4.1 第 `0` 分钟：发片人把视频发进群

发片人把视频发进群后，后端先落权威事实：

1. 附件 `complete` 成立；
2. 生成该视频正式 payload 的分发真相；
3. 写下 `complete_at`；
4. 把服务器强帮助者加入 swarm。

从这一刻开始，这段视频的产品目标就不只是“能让第一个人播出来”，而是：

**尽快把这段视频养成一个会越来越强的协同分发网。**

### 4.2 第一个看的人 A

A 第一个划到这条视频，自动播放触发。

此时应该发生的事情不是：

1. A 只从服务器拿一点首屏内容；
2. A 划走后就停；
3. A 对后面的人没有意义。

应该发生的是：

1. A 先尽快拿到首播关键片段；
2. 同时系统尽快继续补齐 A 手里的数据；
3. 只要 A 页面还活着，A 的帮助任务就不因划走而结束；
4. A 之后应尽快成为 B、C、D 的帮助者。

所以这里必须写死：

**禁止把 A 看过这件事，只当成一次消费；系统必须尽量把 A 养成后面人的供应者。**

### 4.3 B、C 也看了这条视频

B、C 后续也自动播放或点开这条视频后，A、B、C 三个人都应开始积累自己手里的片段。

这时系统不该把他们看成：

1. 三个互相隔离的观看会话；
2. 三个只会向服务器索取的消费者；
3. 三个只有完整后才勉强算有用的人。

正确理解是：

1. A、B、C 各自手里的片段，都会慢慢变成后面用户的帮助来源；
2. 即便某人还没完整，他已经拥有的片段也可能马上对别人有价值；
3. 服务器在前 `24 小时` 内仍然很强，但不是唯一来源。

### 4.4 D 新进来

当 D 新进来点开这条视频时，你要的不是：

1. D 只连服务器；
2. D 只连 A；
3. D 按顺序排队等某一个人慢慢传。

你要的是：

1. D 同时吃服务器强帮助者；
2. D 同时吃 A、B、C 手里已经有的有用片段；
3. 谁当前更快、谁当前有 D 正缺的片段，谁就多给一点。

也就是说：

**D 的冷启动，不是“找唯一来源”，而是“从一组正在活着的帮助者里并行猛拉”。**

### 4.5 D 看过以后，也继续帮助 E、F

D 看过以后，不应该只是一个被服务的对象。  
只要他继续在线，帮助链就默认应该继续：

1. D 自己继续补齐；
2. D 拿到的片段立刻对 E、F 可见；
3. 一旦 E、F 进来，D 也进入帮助者集合。

这就形成你要的那种效果：

1. A、B、C 帮 D；
2. D 很快又反过来帮 E、F；
3. 群里在线并看过的人越多，这张网越强；
4. 后面的人不是更慢，而往往应该更快。

### 4.6 第 `24` 小时以后：G、H 再进来

到了 `24 小时`，服务器强帮助者退出媒体字节供给。  
但只要 A、B、C、D、E、F 中还有人在线，而且手里还有 G、H 需要的有用字节，G、H 仍然应该能继续被这张网接住。

因此第 `24-48 小时` 的真相不是：

1. 服务器一退，所有人立刻都死；
2. `24 小时` 后视频天然就不该再好播；
3. 只有完整 peer 才允许出现在后半段。

真正的真相是：

1. 前 `24 小时` 服务器负责把这张网养热；
2. 后 `24 小时` 靠群友之间继续互相接力；
3. 群友越活跃、保留下来的数据越多，G、H 越容易被接住；
4. 如果当前真的没人能提供有用字节，就必须说真话，而不是偷偷回服务器。

### 4.7 A 后来离开了，过一阵子又回来

A 后来可能刷新页面、关掉标签页、浏览器重启，甚至隔几个小时再回来。

这里的真相必须写死：

1. **如果 A 本地之前留下的数据还在，A 回来后应尽量恢复之前的帮助任务。**
2. **如果 A 是主动清缓存、清站点数据，那就视为 A 明确结束了那批旧帮助任务。**

禁止两种漂移：

1. 禁止“页面一关，一切帮助记忆都失忆”；
2. 禁止“用户明明主动清缓存了，系统还硬把旧帮助任务强行复活”。 

---

## 5. 协同扩散规则

这一节收口“具体怎么变强”，不是讲故事，而是讲裁决。

### 5.1 禁止把后来者的下载面压成单来源

后来的 D、E、F、G、H 进入时，系统默认目标必须是：

1. 同时探测服务器强帮助者（仅前 `24 小时`）；
2. 同时探测在线完整帮助者；
3. 同时探测在线片段帮助者；
4. 尽量并行地从这些来源拉取不同片段。

因此必须禁止：

1. 只连服务器；
2. 只连某一个 peer；
3. 先等一个来源失败，再试下一个；
4. 把多来源并行偷换成伪串行重试。

### 5.2 禁止把片段帮助者排除在帮助链之外

系统必须承认一个现实：

**很多时候，后面的人之所以能更快，不是因为前面一定已经有很多完整帮助者，而是因为前面已经分散地拥有了大量有用片段。**

因此必须写死：

1. 片段帮助者允许立即参与；
2. 不要求先完整再帮；
3. 片段帮助者和完整帮助者都属于当前 swarm 的有效成员；
4. 当前片段是否有价值，只看它对后来者当前缺口是否有帮助。

这里禁止两种极端：

1. **禁止把“只有完整帮助者才算有用”写成规则。**
2. **也禁止把“只要有任何碎片存在”就吹成“当前一定 ready”。**

前者会把 swarm 做弱；后者会让失败态说假话。

### 5.3 禁止把多人同时进入做成排队模型

如果 D、E、F 几乎同时进入同一段视频，系统不应把他们排成：

1. 先服务 D；
2. D 好了再服务 E；
3. E 好了再服务 F。

而应理解成：

1. 服务器强帮助者、A、B、C、D、E 自己都可能同时参与；
2. 谁手里有谁缺的片段，谁就对谁上传；
3. 多人同时进入，反而会更快地把更多用户变成帮助者。

所以这里必须写死一句：

**禁止把活跃群里的 swarm，当成一个串行工单队列。**

### 5.4 禁止把服务器放在 swarm 之外做中心化调度员

服务器在前 `24 小时` 虽然很强，但它不是中心化总控，不是另一个传统 CDN 调度器。  
它在这套模型里的位置只能是：

1. 一个超强帮助者；
2. 一个冷启动推进器；
3. 一个在前 `24 小时` 把 swarm 尽快烧热的正式成员。

禁止：

1. 让服务器主导一切分流判断，群友只是被动兜底；
2. 让服务器成为“真实主链”，群友成为“表演主链”；
3. 让 swarm 沦为服务器旁边的装饰层。

---

## 6. 补齐与长期帮助规则

这一节专门收口“什么叫看过就不该白看”。

### 6.1 禁止把自动播放看成低价值观看

本 spec 明确采用极限激进的产品语义：

1. 自动播放算进入帮助链；
2. 明确点开查看器当然也算进入帮助链；
3. 不要求用户先表达“我愿意帮助别人”的主观意图。

原因很简单：

1. 如果只把查看器用户算正式帮助者，群里大量时间线自动播放用户就永远不会变成后续分发能力；
2. 群越活跃、越多人自动播放过，这条视频才越有机会变强；
3. 你要的是“群聊活跃度直接转成分发能力”，而不是“只有极少数深度观看者才算贡献者”。

所以这里必须写死：

**禁止把自动播放用户降级成不值得补齐、不值得继续帮助的二等观看者。**

### 6.2 禁止滑走后默认停掉帮助任务

用户滑走某条视频后，可以停止的是：

1. 高负载解码；
2. 视觉 owner；
3. 当前播放 UI 的前台资源争用。

不能默认停的是：

1. 已经开始的后台补齐；
2. 已经持有片段的对外帮助；
3. 帮助任务本身的继续生长。

因此必须禁止：

1. “滑出可视区就停下载”；
2. “切到别的消息就停帮助”；
3. “只在用户盯着这条视频时才允许它对后面的人有价值”。

### 6.3 禁止把帮助任务做成“只保最近几条”的产品规则

活跃群里，一个用户可能连续自动播放过 `10` 条、`20` 条视频。  
本 spec 在产品层明确选择的是：

1. 不主动把旧帮助任务裁掉；
2. 不写“默认只保最近 `3-5` 条”；
3. 不写“默认只保当前屏幕内”；
4. 不写“默认只保最热视频”。

原因是：

1. 你要的是极限协作分发，不是小水管谨慎版；
2. 一旦产品层先裁掉大多数帮助任务，群活跃度就无法真实转成分发能力；
3. 这类“只保几条”的策略一旦写进产品层，后续只会越来越保守。

这里允许的只有一类边界：

**底层不得不有的运行时级资源仲裁。**

但必须注意：

1. 它只能存在于底层；
2. 它不能改变产品承诺；
3. 它不能被包装成新的产品语义；
4. 它更不能变成“我们决定默认只保几条”的借口。

### 6.4 禁止为移动端和弱网单独长出第二套保守真相

本 spec 明确选择：

1. 桌面端激进；
2. 移动端也默认激进；
3. 弱网环境也不自动切换为“保守协作分发产品规则”。

这不意味着物理世界不存在差异，而是意味着：

1. 差异只能收在能力适配层；
2. 不能因此长出“手机端默认不补齐”“移动端默认不长期帮助”之类的新产品真相；
3. 同属浏览器壳，就应共享同一条业务语义。

### 6.5 禁止把“恢复帮助任务”理解成违背用户清理行为

系统应尽量恢复帮助任务，但恢复前提必须真实：

1. A 回来时，本地数据仍在；
2. 或者浏览器允许恢复相关持久化状态；
3. 用户没有主动清空站点数据。

因此要同时禁止两种漂移：

1. **禁止保守化：页面一关就失忆，回来什么都不接。**
2. **禁止越权化：用户都清缓存了，系统还装作旧帮助任务应该继续。**

---

## 7. 前 `24 小时` 与后 `24 小时` 的切换规则

这一节收口“什么时候服务器最猛、什么时候必须退场、退场后如何继续不说谎”。

### 7.1 禁止把 `24 小时` 起点写成任何前端主观时间

`24 小时` 的权威起点只认：

**后端 `complete_at`。**

禁止：

1. 以首次观看时间为起点；
2. 以前端本地时间为起点；
3. 以消息发送时间粗糙替代；
4. 以“首次进入 swarm 时间”动态漂移。

### 7.2 前 `24 小时`：禁止服务器装弱

前 `24 小时` 里，服务器必须积极参与：

1. 让 A 第一次更快起播；
2. 让 A、B、C 更快补齐；
3. 让 D、E、F 同时进来时仍有强吞吐冷源；
4. 尽快把更多群友养成后面的帮助者。

所以这里必须明确：

**禁止因为“怕看起来不够 P2P”而故意让服务器在前 `24 小时` 装弱。**

装弱不是去中心化，装弱只会让 swarm 烧不起来。

### 7.3 `24 小时` 到点：禁止服务器继续偷做第二字节主链

到了 `24 小时`，服务器必须退出的是：

1. `WebSeed` 字节供给；
2. `WebRTC seeder` 字节供给；
3. 任何仍在偷偷扮演第二正式播放主链的兜底路径。

但它仍然可以保留：

1. 附件存在性真相；
2. 鉴权、房间关系；
3. metainfo / tracker / signaling 所需控制面；
4. 删除语义；
5. 当前能否探测到可恢复来源的状态事实。

这里必须再补一条：

**禁止把“服务器退出媒体字节”误解成“服务器全失忆”或者“前端必须一无所知地瞎等”。**

### 7.4 后 `24 小时`：禁止把“没有单个完整 peer”直接偷换成“全无希望”

后 `24 小时` 阶段，这份设计比前一份 spec 更强调一点：

1. 完整帮助者当然仍然是最强来源；
2. 但片段帮助者也仍然可以有价值；
3. 当前是否还有希望恢复，不应简单粗暴地只看“有没有单个完整帮助者在线”；
4. 应看当前重试窗口内，是否还能真实拼出首播关键字节与持续补齐能力。

这并不意味着失败态可以撒谎。  
真正的裁决是：

1. 如果当前重试窗口内，服务器已退场，群友集合也无法给出有效可恢复来源，就必须明确说现在没人能发给你；
2. 如果当前重试窗口内，群友集合仍能真实为你供给必要字节，即便他们不是单点完整来源，也不该过早判死。

因此这里要同时禁止两种错误：

1. **禁止保守误杀：没有单个完整帮助者，就立刻宣布没种子。**
2. **禁止乐观撒谎：明明拼不出任何可恢复来源，还硬说还能播。**

---

## 8. 允许的硬边界，和禁止上抬成产品规则的伪边界

这一节是整份设计最容易被偷换的地方，必须写得非常死。

### 8.1 允许存在的，只有基础设施级硬边界

浏览器、WebRTC、WebTorrent、网络环境，本来就存在客观上限。  
因此底层允许存在：

1. 单 torrent 的 peer 连接上限；
2. 单页面的并发 swarm 数上限；
3. 单 peer 的请求队列上限；
4. 单时刻的内存、带宽、socket、DataChannel 等运行时边界；
5. 浏览器自身的标签页调度与资源限制。

这些边界允许存在，但它们只能被理解成：

**运行时的物理上限。**

### 8.2 禁止把物理上限包装成产品层保守哲学

下面这些说法，后续实现时一律视为漂移：

1. “既然浏览器有限，所以默认只保最近 `3-5` 条帮助任务。”
2. “既然移动端更脆弱，所以默认手机不长期帮助别人。”
3. “既然弱网不好，所以默认自动播放用户不继续补齐。”
4. “既然标签页会切后台，所以默认滑走就停。”
5. “既然 full mesh 不现实，所以就退回单来源或双来源保守拉取。”

这些都不是物理上限，而是：

**把底层限制上抬成产品层退缩。**

本 spec 明确禁止这种偷换。

### 8.3 这次采用的不是“无限无脑”，而是“产品层极限激进 + 底层克制硬边界”

这份设计的选型，不是：

1. 产品层也保守；
2. 底层也保守；
3. 最后系统整体很弱。

也不是：

1. 产品层假装极限；
2. 底层什么都不管；
3. 最后浏览器直接失控。

这次明确选的是第三条路：

1. **产品层语义极限激进**：看过就尽量补齐、尽量继续帮、多人并行互助；
2. **底层只保留必须存在的运行时硬边界**；
3. **禁止把这些硬边界上抬成新的产品规则。**

这就是本 spec 的核心抉择。  
如果后续有人想在产品层重新发明一套“默认只保几条”“默认只保前台”“默认只保查看器用户”的哲学，都应直接视为背离本设计。

---

## 9. 失败态、恢复态与删除态的真话规则

这份设计虽然更激进，但在说真话这件事上只能更严格，不能更松。

### 9.1 禁止把“正在找来源”混成“已经 ready”

当前还在尝试服务器、完整帮助者、片段帮助者时，前端只能表达：

1. 系统还在找；
2. 还在试图拼出可恢复来源；
3. 还不能假装已经 ready。

因此必须禁止：

1. 还在找时就当成 ready；
2. 只因为 swarm 里有人在线，就盲目进入正常播放态；
3. 只因为片段帮助者存在，就宣称已经稳了。

### 9.2 禁止把“当前没人能发”混成一般网络错误

一轮合理重试结束后，如果当前没有任何可恢复来源，就必须明确告诉用户：

**当前没有在线种子，等待群友上线。**

不能改写成：

1. “加载失败”；
2. “网络异常”；
3. “资源不可用”；
4. 无限转圈不解释。

这里的关键是：

1. 视频仍然存在；
2. 权限也可能没问题；
3. 只是这会儿群里没人能把它发给你；
4. 这是协同分发生态的真相，不是一个需要被掩盖的羞耻 bug。

### 9.3 禁止把“内容已删除”和“现在没人能发”混成一类

删除优先级永远更高。  
一旦删除权威事实成立：

1. 当前帮助任务应退出；
2. 本地缓存应进入 purge 流程；
3. 前端必须切到 `内容已删除`；
4. 不允许继续假装只是暂时没种子。

这里必须再补一条，防止和“本地有缓存就能继续播”冲突：

1. **附件未删除时，本地缓存继续帮助与继续播放是正确的。**
2. **附件已删除时，本地缓存不能继续被拿来装作 `MEDIA_READY`。**

### 9.4 禁止为了掩盖失败态而偷偷回退服务器

这条是整份设计和上一份 spec 共同的底线：

1. 当前没有可恢复来源时，可以说真话；
2. 不能说假话；
3. 更不能为了遮羞偷偷再开服务器直供。

否则一切“群越活跃越强”的设计，都会退化回：

1. 表面上有 swarm；
2. 实际上还是靠服务器；
3. 所有帮助任务都只是装饰。

---

## 10. 实现时最容易发生的漂移

### 10.1 漂移一：把极限协作分发偷偷做回“服务器优先，群友辅助”

这种实现最危险，因为表面上看起来仍然有 swarm。  
但实际效果是：

1. 服务器负担始终最高；
2. 群友很难真正进入帮助链；
3. 群越活跃，后面的人也不一定更快；
4. 产品失去自增强能力。

### 10.2 漂移二：把“片段帮助者有价值”误杀成“只有完整帮助者才算数”

这会直接砍掉系统最核心的扩散速度。  
后面的人无法及时吃到前面的人已经持有的有用片段，swarm 只会越等越冷。

### 10.3 漂移三：为了省事，把滑走后继续帮助重新砍掉

这会让用户都只拉一点点，几乎没人真的变成后面的帮助者。  
最后系统会永远停在“每个人都是半消费者、很少有人真帮助”的弱状态。

### 10.4 漂移四：为了稳态，把帮助任务做成“只保最近几条”

这看起来很工程化，实际上是产品层主动认怂。  
一旦这样做，群聊活跃度再高，也很难真实转成分发能力。

### 10.5 漂移五：为了所谓兼容，把移动端重新做成保守版

这会直接打破“同属浏览器壳，共享同一套媒体与帮助真相”的前提，后面所有 Web 应用化 owner 链都会被重新撕裂。

### 10.6 漂移六：把底层硬边界上抬成产品哲学

这是最隐蔽的一种漂移。  
工程上明明只是“这里有连接上限”“这里有请求队列”，最后却被包装成：

1. 自动播放用户不值得继续补齐；
2. 非前台视频不值得继续帮助；
3. 活跃群默认只保少数帮助任务；
4. 后 `24 小时` 过早宣布没戏。

这类漂移一旦发生，产品语义就已经变了。

---

## 11. 实现红线

后续写 plan 和落代码时，禁止越过下面这些红线：

1. 禁止把自动播放用户从帮助链里剔除。
2. 禁止把滑走、失焦、切屏默认实现成帮助任务结束。
3. 禁止把多人并行帮助偷换成单来源或伪串行拉取。
4. 禁止把片段帮助者排除出 swarm 有效成员集合。
5. 禁止为了省资源，在产品层写死“只保最近几条帮助任务”。
6. 禁止为移动端、弱网、某浏览器单独长出第二套保守协作分发真相。
7. 禁止把前 `24 小时` 服务器强参与做回第二正式播放主链。
8. 禁止把后 `24 小时` 的失败态重新做成模糊加载失败。
9. 禁止把“当前没有人能发”和“内容已删除”混成一类。
10. 禁止把底层协议/运行时硬边界，上抬成新的产品保守规则。

---

## 12. 验证门禁

后续 plan 与实现至少要验证下面这些事实：

1. A、B、C 自动播放过同一段视频后，D 新进入时，抓到的正式分发行为应体现为多来源并行，而不是单来源串行。
2. 在前 `24 小时`，D 的来源集合默认应同时包含服务器强帮助者与已看群友，而不是只偏向其中一个。
3. A、B、C 即便尚未完整，只要手里已有 D 当前缺的片段，也必须被证明能够参与帮助。
4. D 看过后，E、F 几乎同时进来时，D 应被证明已进入帮助者集合，而不是只作为新的消费者存在。
5. A 划走该视频、切到别的消息甚至滚出视口后，帮助任务仍继续运行；不能复活“滑走即停补齐”。
6. 同一用户在活跃群里自动播放过多条视频后，产品层不能偷偷把旧帮助任务裁掉；若底层确有运行时仲裁，其行为必须证明未改变产品承诺。
7. 移动端与桌面端必须共享同一套帮助链语义，不得出现“桌面补齐、移动端不补齐”的业务分裂。
8. A 关闭页面后再次回来，如果本地数据仍在，帮助任务应能恢复；若 A 明确清缓存，则旧帮助任务不应被强行恢复。
9. `24 小时` 前后切换必须只认后端 `complete_at`，且服务重启不会重置。
10. `24 小时` 后若群友集合仍能提供首播关键字节与持续补齐字节，G、H 仍应被接住，不得因“缺少单个完整帮助者”而被保守误杀。
11. `24 小时` 后若合理重试窗口内确实找不到任何可恢复来源，前端必须明确进入“当前没有在线种子，等待群友上线”。
12. 附件删除后，前端必须进入“内容已删除”；本地缓存不能继续伪装成正常 ready。
13. 全链路不得因高活跃协作而偷偷回退第二正式播放主链。
14. `chrome-devtools-cli` 真实烟测至少覆盖：
    - `https://localhost`
    - 房间 `1234b`
    - sender / A / B / C / D 多隔离上下文
    - 视频与图片都验证
    - 前 `24 小时` 服务器与群友共同参与验证
    - 模拟后 `24 小时` 的群友接力验证
    - “当前没有在线种子”与“内容已删除”两种失败态验证

## 13. 最终硬裁决

以后在 `koko` 里，必须按下面这句话理解“越活跃越强”的协作分发系统：

**一段新视频发进群后，系统默认要把每一个看过它且仍在线的群友，都尽量养成后来者的帮助者；前 `24 小时` 服务器和群友一起并行猛拉，后 `24 小时` 尽量由群友继续接力；产品层禁止主动保守收手，只允许底层保留不可避免的运行时硬边界；没有人能发时必须说真话。**

从这句话自然推出全部实现边界：

1. 禁止把自动播放用户当一次性消费者；
2. 禁止把后来的人压成单来源下载；
3. 禁止把片段帮助者误杀出 swarm；
4. 禁止滑走后默认停止帮助任务；
5. 禁止把多附件协作任务做成“只保几条”的保守产品规则；
6. 禁止移动端、弱网、浏览器类型各自长出第二套协作分发真相；
7. 禁止把底层硬边界上抬成产品退缩借口；
8. 禁止为了遮羞偷偷回退服务器第二主链；
9. 禁止把“当前没人能发”和“内容已删除”混成一类。

后续 implementation plan 和代码改动，都只能在这条边界内工作；凡是离开这条边界去“先保守一下”“先缩小一点”“先只保几条看看”的，都应直接视为漂移，必须禁止。
