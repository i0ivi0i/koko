# 真 DDD 满分验收规格

日期：2026-05-02
状态：Design
适用范围：`koko` 后端 Rust、前端 TypeScript、实时群聊、媒体上传与播放、恢复链、架构门禁、完成矩阵和后续所有“满分完成”声明。

本文回答一个问题：**到底怎样才能把 `koko` 证明到 `DDD: 10/10`、`六边形边界: 10/10`、`简洁度: 10/10`。**

## 0. 前因后果和执行者读法

### 0.1 为什么之前要求满分，现在仍不能说满分

前一轮重构已经解决了一批真实问题：根目录业务 owner 清零、旧恢复门面删除、自动播观察 owner 下沉、测试重新转绿。这些都是有效进展。

但这些进展只证明了“第一层旧入口和一部分兼容壳退场”，没有证明下面三件事：

1. 模块内部所有热点 owner 都已经足够薄。
2. adapter / shell / 总装 不再偷做业务或跨层借道。
3. 真实浏览器里的万人群聊关键体验已经重新闭环。

所以不能因为“某一批旧文件删除了”就宣布满分。满分必须证明系统的主链更短、owner 更清楚、边界更硬、测试和真实浏览器证据都闭合。

这不是降低目标，而是把目标从口号改成可验收事实。

### 0.2 为什么必须写得更细

这个项目的风险不是“没人知道要 DDD”，而是执行时容易把 DDD 做成下面这些假进展：

1. 把旧函数搬到新目录，但旧职责还在。
2. 把旧入口改名成新入口，但兼容链还在。
3. 把一个大文件切成三个纯转发文件，但主链更长。
4. 为了测试先保留私有包装函数，结果测试反向锁死冗余结构。
5. 为了“先跑通”把业务判断塞进 adapter、shell、总装或前端状态。

本文写得细，是为了让执行者在每一步都能回答：

1. 这一步删除了什么旧路径？
2. 这一步减少了什么概念？
3. 这一步把哪个业务事实收回唯一 owner？
4. 这一步新增了什么门禁防止回流？
5. 这一步有没有为了安全感留下第二入口？

五个问题答不清，就不能继续写实现。

### 0.3 执行者必须先按这条顺序读

执行本 spec 前必须先读：

1. `AGENTS.md`
2. `graphify-out/GRAPH_REPORT.md`
3. `docs/superpowers/specs/2026-05-01-真DDD领域驱动重构铁律.md`
4. 本文
5. 即将修改的目标文件、调用方、被调用方、测试和门禁脚本

禁止只读本文就开改。本文是验收尺，不是代码上下文替代品。

### 0.4 防漂移总规则

执行时遇到下面任何情况，必须停下重新审查，不准继续硬写：

1. 想新增 `facade / wrapper / helper / common / utils / manager / service`。
2. 想“先保留旧路径，等后面再删”。
3. 想用 `Ok(None)`、`Ok(vec![])`、默认空实现或泛化 `系统错误` 让编译通过。
4. 想把业务判断放进 HTTP handler、SQL adapter、DOM 组件、播放器回调或总装文件。
5. 想调高热点文件预算来让门禁通过。
6. 想用纯 mock 绿化替代真实浏览器烟测。
7. 想把测试改成依赖新私有包装函数。
8. 想用“这个只是临时”解释生产代码里的新入口。

这些不是小问题，而是屎山回流信号。

禁止句式：

1. 禁止说“先兼容一下”。
2. 禁止说“先留着更稳”。
3. 禁止说“只是换个位置”。
4. 禁止说“以后再删”。
5. 禁止说“测试需要这个包装”。
6. 禁止说“门禁太严，先调高预算”。
7. 禁止说“这不是业务，只是方便判断一下权限”。
8. 禁止说“这只是 shell 层，放一点逻辑没事”。

允许句式：

1. “这个逻辑属于哪个唯一 owner？”
2. “这个入口能不能删除，而不是兼容？”
3. “这个抽象删除了哪些复杂度？”
4. “这个测试证明的是不变量，还是证明旧结构还在？”
5. “这个 adapter 是否只做翻译？”
6. “这个 shell 是否只表达交互？”
7. “这个总装是否只接线？”

2. 旧 `房间快照恢复` 兼容门面已删除并有防回流门禁。
3. `房间消息窗` 内自动播观察的一跳包装函数已删除，并直连 `自动播候选观察Owner`。

但还不能满分的硬证据：

1. 仍有过厚 owner：`src/媒体/适配.rs` 约 2068 行，`src/媒体/上传/外壳/媒体上传.rs` 约 1995 行，`frontend/房间消息窗/壳.ts` 约 1888 行，`frontend/总装/聊天壳.ts` 约 1398 行，`frontend/总装/聊天应用内核.ts` 约 1137 行，`frontend/媒体/播放会话/应用.ts` 约 1100 行。

## 2. 满分定义

### 2.1 DDD 满分

DDD 满分不是目录名像 DDD，而是代码里的业务模型能被业务语言直接解释。

必须同时满足：

1. `身份 / 房间 / 消息 / 媒体 / 恢复 / 实时` 六个后端 bounded context 都有唯一业务 owner。
2. 前端 `房间 / 时间线 / 媒体播放会话 / 媒体查看器 / 协作分发 / 恢复 / 实时 / 总装` 只拥有交互真相和展示真相。
3. 权限、成员资格、消息成立、媒体成立、恢复合法性只在后端 domain / application 裁决。
4. 同一业务事实不能在 adapter、shell、前端状态、localStorage、播放器或测试支架里再判一遍。
5. 领域对象和值对象必须承载行为和不变量，不能只是字段袋子。
6. 事件必须是领域已经发生的事实，不能是 UI 指令、框架回调或技术状态冒充领域事件。
7. 业务术语必须稳定：禁止用 `manager / helper / wrapper / common / utils / processor` 解释业务职责。
8. 完成矩阵里每个“已完成”必须有当前代码和当前命令证据，禁止把未来计划写成完成态。

DDD 满分失败条件：

1. 有任何业务事实同时存在两个 owner。
2. 有任何旧入口、过渡入口、兼容链、re-export、只转发一次的桥接函数仍在生产代码里。
3. 前端用本地状态、实时回声、恢复缓存或播放状态自行发明业务成立性。
4. handler、repo、adapter、shell 里出现“顺手裁决业务”的分支。

### 2.2 六边形边界满分

六边形满分是依赖方向真实向内，不是只画了 port / adapter。

必须同时满足：

1. `domain / application` 不引用 `Axum / SQLx / socketioxide / DOM / localStorage / Video.js / WebTorrent` 具体 API。
2. adapter 只负责 IO、协议、鉴权材料读取、错误转码、SQL 或外部系统翻译。
3. shell 只负责用户交互编排、DOM 表达、事件转译和调用应用端口。
4. `contract` 只放跨壳稳定 command / query / event / snapshot / error，禁止混入页面文案、布局词、框架类型和某个壳专属流程。
5. 缺少端口实现必须编译期暴露，不能靠 `Ok(None)`、`Ok(vec![])`、默认空方法或 `系统错误` 把能力缺口藏到运行期。
6. adapter 不能横向调用另一个 adapter 的私有 helper 来拼业务结果。
7. 总装只能装配依赖，不能承载业务判断、媒体对账、清理策略、恢复策略或实时补发规则。
8. 每条外部入口都有一条可追踪路径：inbound adapter -> application -> domain / port -> outbound adapter -> contract response。

六边形满分失败条件：

1. 内层出现外层框架类型。
2. 适配器之间互相借道。
3. 总装文件继续承担业务主链。
4. 端口 trait 有默认空实现或默认成功实现。
5. 错误语义被框架错误或泛化 `系统错误` 吞掉。

### 2.3 简洁度满分

简洁度满分不是机械压行数，而是更少概念、更少路径、更短主链、更低维护成本。

必须同时满足：

1. 没有只转发一次的函数。
2. 没有只包一层的对象。
3. 没有为了“像架构”存在的文件、trait、类或目录。
4. 没有长期存在的 `兼容 / legacy / facade / wrapper / helper / common / utils` 生产路径。
5. 热点文件必须继续下降到可读范围，且每个剩余大文件都能解释为什么不能再拆。
6. `cargo clippy -- -W dead_code -W unused_imports -W unused_variables` 零 warning。
7. `pnpm --dir frontend test`、`cargo test` 和架构门禁都全绿。
8. 新增抽象必须删除更多复杂度；如果抽象只是搬家，判负。

简洁度满分失败条件：

1. 为了收口旧复杂度新建一层门面。
2. 为了迁移安全保留旧路径和新路径并存。
3. 代码变短但主链更难追。
4. 测试改成依赖私有转发壳，反向锁死冗余结构。

### 2.4 满分禁止语句库

下面这些表达在 review、commit message、完成矩阵、执行报告里出现时，默认判为未完成，除非紧跟明确删除计划和已落门禁：

| 禁止表达 | 为什么禁止 | 正确表达 |
| --- | --- | --- |
| “兼容入口” | 兼容入口会保留第二路径，长期一定变成第二真相。 | “旧入口已删除，调用方已迁到唯一 owner。” |
| “临时门面” | 门面会掩盖真实 owner 未收口。 | “直接迁调用，删除门面文件。” |
| “wrapper 更安全” | wrapper 经常只是把主链拉长。 | “新增抽象必须删除旧复杂度，否则不新增。” |
| “helper 复用一下” | helper 容易跨 bounded context 泄漏业务语义。 | “把行为放回拥有该业务语言的模块。” |
| “先调高门禁” | 调高预算是在承认回胖。 | “先删冗余或拆 owner，再收紧预算。” |
| “只是 adapter 顺手查一下” | adapter 顺手查就是业务判断外泄。 | “adapter 翻译数据，application/domain 裁决语义。” |
| “shell 里先判断一下” | shell 判断业务会让前端长出第二真相。 | “shell 只转译交互，业务交给后端或应用 owner。” |
| “真实浏览器后面再测” | 没有真实浏览器证据，媒体和实时体验不能算闭环。 | “真实浏览器烟测通过后再写完成。” |

## 3. 必须删除或收口的剩余债务

### 3.1 后端

必须继续审查并收口：

1. `src/媒体/适配.rs`
   - 当前风险：媒体资产、locator、内容读取、origin 描述、冷源退场、仓储翻译集中度过高。
   - 满分方向：按 `资产读取 / 上传会话 / 协作分发 / 清理退场 / locator 投影` 拆成真实 owner，不新增纯转发文件。
   - 为什么做：媒体适配是后端媒体字节和数据库之间的主要翻译层；如果这里继续变厚，它会自然吸收业务裁决，最后让 domain/application 失去权威。
   - 禁止：禁止新建 `媒体适配helper.rs`、`媒体适配wrapper.rs`、`媒体公共查询.rs` 这类垃圾桶；禁止把 SQL 复制到多个 adapter；禁止让 locator、origin、冷源退场各判一次可读性。
   - 做到哪才算完成：每个拆出的文件都有独立业务翻译职责，调用方不需要知道 SQL 细节，且 `cargo test --test 媒体测试边界守卫` 能证明没有旧冷源和第二字节入口回流。

2. `src/媒体/上传/外壳/媒体上传.rs`
   - 当前风险：HTTP/Tus/转发/source_hash/做种触发/响应构造混在同一外壳热点。
   - 满分方向：按协议入口和业务命令拆薄，外壳只翻译请求、调用用例、返回响应。
   - 为什么做：上传外壳靠近 HTTP、Tus sidecar、source_hash、转发分享和做种触发，最容易因为“先跑通”把协议状态当业务状态。
   - 禁止：禁止在外壳里决定媒体是否成立；禁止在外壳里复用 canonical 资产；禁止在外壳里发明做种业务规则；禁止保留旧上传路由的兼容桥。
   - 做到哪才算完成：每个入口只做 `解析请求 -> 构造 command -> 调用 use case -> 翻译 response`，source_hash、forward、complete、abandon 的业务裁决都能在应用/领域测试里直接证明。

3. `src/总装.rs`
   - 当前风险：配置、依赖装配、测试支撑、媒体路径推导等可能继续吸附。
   - 满分方向：只保留装配和启动必要 glue，业务推导下沉到对应 owner。
   - 为什么做：总装天然知道所有模块，最容易从“接线”滑向“顺手裁决”。一旦总装拥有业务判断，六边形依赖方向就被破坏。
   - 禁止：禁止总装推导媒体业务语义；禁止总装决定恢复策略；禁止总装处理权限、成员、消息成立；禁止为了减少改动把新配置解释逻辑塞回总装。
   - 做到哪才算完成：删除 Axum、SQLx、socketioxide 之外的业务判断后，总装仍能启动系统；业务模块测试不依赖总装也能跑。

4. `src/应用/mod.rs`
   - 当前风险：跨业务端口和共享校验仍可能成为新的总入口。
   - 满分方向：共享端口只保留真正跨业务稳定基础；业务用例端口下沉到各业务应用。
   - 为什么做：`应用/mod.rs` 如果继续收所有用例，它会变成新 `用例.rs`，只是文件名更好看。
   - 禁止：禁止在这里新增业务 use case；禁止 `pub use` 各业务应用函数；禁止给端口 trait 写默认成功实现；禁止用共享校验替代业务模块自己的不变量。
   - 做到哪才算完成：这里只剩跨业务最小基础语义；身份、房间、消息、媒体、恢复、实时的用例入口都在各自模块。

5. `src/外壳/mod.rs`
   - 当前风险：总路由壳继续聚合过多协议细节。
   - 满分方向：只保留 route mount 和状态装配，具体 handler 落到业务外壳。
   - 为什么做：外壳总入口如果继续写 handler 细节，就会让 adapter/shell 变成第二 application。
   - 禁止：禁止在总外壳写具体业务 handler；禁止在总外壳构造业务响应体；禁止在总外壳吞掉领域错误。
   - 做到哪才算完成：总外壳只挂载业务外壳路由和共享状态，具体协议翻译下沉到对应业务外壳。

### 3.2 前端

必须继续审查并收口：

1. `frontend/房间消息窗/壳.ts`
   - 当前风险：虽已删除自动播观察包装，但仍承担滚动、虚拟列表、媒体窗口、唯一播放器宿主、冻结帧、查看器入口等多种交互 owner。
   - 满分方向：保留消息视口壳，继续把冻结帧、唯一播放器宿主同步、媒体窗口观察等可独立 owner 下沉。
   - 为什么做：消息窗应该是消息视口表达，不应该继续同时管理自动播、冻结帧、唯一播放器宿主和查看器入口的多重生命周期。
   - 禁止：禁止恢复 `dispatch自动播候选 / 调度自动播候选 / 读取自动播候选` 这类一跳包装；禁止在消息窗里创建 WebTorrent、Video.js 或第二播放器；禁止把冻结帧当媒体真相。
   - 做到哪才算完成：消息窗只接收展示项、挂载视口、发出交互事件；媒体窗口、冻结帧、播放器宿主同步都有独立 owner 和门禁。

2. `frontend/房间消息窗/附件渲染.ts`
   - 当前风险：附件投影函数和渲染模板仍偏密。
   - 满分方向：把纯投影、图片附件、视频附件、viewer 入口拆成小而真实的模块，不做模板碎片海。
   - 为什么做：附件渲染同时靠近图片、视频、viewer、自动播、预算投影，继续膨胀会让 UI 模板偷做媒体状态机。
   - 禁止：禁止把 `originalSrc`、旧 manifest、缓存旁路重新塞进正式播放源；禁止为了少改测试保留大宿主接口；禁止把图片和视频的成立规则写在模板分支里。
   - 做到哪才算完成：纯投影函数可单测，图片和视频渲染职责分明，模板只表达投影结果。

3. `frontend/总装/聊天壳.ts`
   - 当前风险：总壳仍可能持有交互编排和业务流程粘合。
   - 满分方向：只读快照、挂子组件、转译 UI 事件，不直接操作内核 helper。
   - 为什么做：聊天壳靠近所有 UI 事件，如果它直接操作内核细节，就会把应用流程锁死在一个大壳里。
   - 禁止：禁止聊天壳直接读取或写入业务状态；禁止聊天壳调用内核私有 helper；禁止聊天壳拥有恢复、实时、媒体、发送消息的成立判断。
   - 做到哪才算完成：聊天壳只把用户事件翻译成公开 command，只把 snapshot 投影给子组件。

4. `frontend/总装/聊天应用内核.ts`
   - 当前风险：应用内核仍聚合房间、恢复、实时、媒体、输入、后台存储等多条流程。
   - 满分方向：各应用 owner 自治，内核只做命令路由和快照合并。
   - 为什么做：应用内核应该是前端交互应用的协调点，不是所有业务流程的最终所有者。
   - 禁止：禁止在内核里重建后端权限、成员、房间存在、消息成立；禁止把恢复/实时/媒体的内部状态机揉进内核；禁止新增测试 setter 暴露内部结构。
   - 做到哪才算完成：房间、恢复、实时、媒体各自应用能独立测试，内核只组合快照和转发公开命令。

5. `frontend/媒体/播放会话/应用.ts`
   - 当前风险：播放会话、查看器、协作分发、自动播热路径仍需要证明没有第二 player / 第二字节 owner。
   - 满分方向：保持 `全局唯一播放器`、`资产协作分发运行时`、`全局丝滑自动播` 三者边界，删掉任何回流候选。
   - 为什么做：媒体播放链是最容易出第二真相的区域；一旦播放会话同时拥有播放器、字节、自动播候选和查看器状态，就会回到多 owner 竞争。
   - 禁止：禁止在播放会话里 new WebTorrent；禁止创建第二颗正式 Video.js player；禁止把查看器、时间线和全屏写成三套播放状态机；禁止用 fallback source 绕过 `资产协作分发运行时`。
   - 做到哪才算完成：唯一播放器、协作分发、自动播判定各自只做一件事，跨模块只交换稳定事件和 snapshot。

## 4. 满分执行顺序

必须按顺序推进，不能先做看起来容易的大搬家。

### 4.1 第一阶段：消灭假的安全感

目标：让不能满分的事实都被测试和门禁看见。

必须新增或强化：

1. 后端架构守卫：禁止端口 trait 默认空实现。
2. 后端架构守卫：禁止 `src/应用/mod.rs` 新增业务用例转发。
3. 后端架构守卫：禁止 adapter 横向调用另一个 adapter 私有 helper。
4. 前端架构守卫：禁止 `门面 / facade / wrapper / legacy / 兼容` 生产文件回流。
5. 前端架构守卫：热点文件只允许变薄，不允许靠调高预算通过。
6. 完成矩阵守卫：只要热点未收口或真实浏览器未复跑，禁止写“满分完成”。

验收：

```powershell
cargo test --test 架构边界守卫
node scripts/check-frontend-architecture-fitness.mjs
node scripts/check-frontend-browser-app-constitution.mjs
```

### 4.2 第二阶段：先删兼容链，再拆过厚 owner

目标：删除第二入口、过渡桥、兼容链，避免一边拆一边留垃圾。

必须处理：

1. 所有生产路径里的 `兼容 / legacy / facade / wrapper / helper / common / utils` 命名。
2. 所有只转发一次的函数和 re-export。
3. 所有测试直接依赖旧私有包装函数的锚点。
4. 所有完成矩阵里把迁移债务写成完成态的描述。

验收：

```powershell
rg -n "兼容|legacy|facade|wrapper|helper|common|utils|pub use|re-export" src frontend tests scripts docs/superpowers
```

命中不等于一定失败，但每一处都必须能解释为业务语义或测试支撑；解释不通就删。

### 4.3 第三阶段：后端六边形收口

目标：后端业务核心删掉总控吸附，adapter 变薄。

执行顺序：

1. 先处理 clippy warning，包含 `SourceHash媒体复用结果` 的 `large_enum_variant`。
2. 拆薄 `src/媒体/适配.rs`，把仓储翻译按业务 owner 下沉。
3. 拆薄 `src/媒体/上传/外壳/媒体上传.rs`，把 HTTP/Tus/source_hash/forward 的协议壳分开。
4. 拆薄 `src/总装.rs`，只留下启动和依赖装配。
5. 检查 `src/应用/mod.rs` 和 `src/外壳/mod.rs`，删掉跨业务总入口趋势。

验收：

```powershell
cargo check --all-targets
cargo test
cargo clippy -- -W dead_code -W unused_imports -W unused_variables
cargo test --test 架构边界守卫
cargo test --test 媒体测试边界守卫
```

### 4.4 第四阶段：前端交互核心收口

目标：前端只保留交互真相，不抢业务真相，不制造第二播放器或第二媒体字节 owner。

执行顺序：

1. 拆薄 `frontend/房间消息窗/壳.ts`，继续下沉冻结帧、媒体窗口观察、唯一播放器宿主同步等独立 owner。
2. 拆薄 `frontend/房间消息窗/附件渲染.ts`，把图片、视频和纯投影分开。
3. 拆薄 `frontend/总装/聊天壳.ts`，让它只读快照和挂组件。
4. 拆薄 `frontend/总装/聊天应用内核.ts`，把房间、恢复、实时、媒体命令还给各自应用 owner。
5. 拆薄 `frontend/媒体/播放会话/应用.ts`，继续守住唯一播放器、协作分发和自动播边界。

验收：

```powershell
pnpm --dir frontend test
pnpm --dir frontend exec tsc --noEmit
node scripts/check-frontend-architecture-fitness.mjs
node scripts/check-frontend-browser-app-constitution.mjs
```

### 4.5 第五阶段：真实浏览器闭环

目标：证明架构收口没有破坏万人群聊关键体验。

必须覆盖：

1. 进入稳定烟测房间 `1234b`。
2. 加载历史时间线。
3. 接收实时消息。
4. 图片附件和视频附件卡片正常表达。
5. 自动播放、查看器打开关闭、滚动切换、唯一播放器 owner 交接正常。
6. 第二浏览器身份能看到同一条媒体体验。

验收方式：

```powershell
pnpm --dir frontend test
pnpm --dir frontend exec tsc --noEmit
cargo test
```

同时用真实浏览器或项目既有 Playwright/browser-trace 链路复跑 `1234b`。没有这一步，不得把前端体验写成满分。

## 6. 满分宣称格式

只有全部验收通过后，最终报告才允许这样写：

```text
DDD: 10/10
六边形边界: 10/10
简洁度: 10/10
```

报告必须同时列出：

1. 删除了哪些旧入口、兼容链、转发壳。
2. 哪些 owner 被拆薄，拆到了哪里。
3. 哪些门禁新增或收紧。
4. 哪些真实浏览器路径已经验证。
5. 哪些命令新鲜通过。
6. `git status --short` 是否为空。

禁止写法：

1. “基本满分”。
2. “理论上满分”。
3. “除了烟测都满分”。
4. “还有少量 warning 但不影响满分”。
5. “先保留兼容层，后续再删”。
