## 2. 满分定义

### 2.1 DDD 满分

DDD 满分不是目录名像 DDD，而是业务模型、业务语言、业务不变量都落在唯一 owner。

必须同时满足：

1. 后端 `身份 / 房间 / 消息 / 媒体 / 恢复 / 实时` 都有唯一业务 owner。
2. 前端 `房间 / 时间线 / 媒体播放会话 / 媒体查看器 / 协作分发 / 恢复 / 实时 / 总装` 只拥有交互真相、展示真相和浏览器能力适配。
3. 权限、成员资格、消息成立、媒体成立、恢复合法性只在后端 domain / application 裁决。
4. 同一业务事实不能在 adapter、shell、前端状态、localStorage、播放器、测试支架里再判一遍。
5. 领域对象和值对象必须承载不变量，不能只是字段袋子。
6. 事件必须是已经发生的领域事实，不能是 UI 指令、框架回调或技术状态冒充领域事件。
7. `contract` 只放跨壳稳定 command / query / event / snapshot / error，不放页面文案、布局词、框架类型和某个壳专属流程。
8. 完成矩阵必须与当前代码状态一致，不能把计划、历史通过记录、局部烟测写成完成态。
9. 同步 / 异步两条主链如果表达同一业务事实，必须共用同一条业务规则 owner，不能长期复制实现。
10. 后端不得长期存在跨身份 / 房间 / 消息 / 媒体 / 恢复的总仓储壳；前端不得长期存在跨恢复 / 实时 / 阅读推进 / 平台桥接 / 媒体会话的总编排壳。
11. 长期正式架构名词必须说真话：允许薄组合根，禁止继续把模糊的“总装”当成正式终态名词。
12. 迁移壳必须有终态：像 `src/实时/契约.rs`、`src/房间/契约.rs`、`src/消息/契约.rs`、`src/身份/契约.rs` 这类“第一阶段先复用”的文件，最终只能收成真正上下文契约或被删除。

DDD 满分失败条件：

1. 任何业务事实有两个 owner。
2. 身份 bootstrap 真相仍由 adapter / persistence 裁决，而不是由身份上下文的 domain / application owner 裁决。
3. 任何旧入口、过渡入口、兼容链、只转发一次的桥接函数仍在生产主链。
4. 前端用本地状态、实时回声、恢复缓存或播放状态自行宣布业务成立。
5. handler、repo、adapter、shell、总装里出现“顺手裁决业务”的分支。
6. 完成矩阵写满分，但当前门禁、测试或真实烟测无法证明。
7. 同步 / 异步主链各自复制同一条业务规则。
8. “已经进入模块目录”被拿来给总仓储壳或总编排壳续命。
9. 迁移壳长期停留在 `pub use crate::shared::contract...` 或同类转发状态。
10. 文档、代码、门禁已经开始使用 `组合根 / 应用根 / 协调器` 的终态语言，真正生产路径却继续把 `总装` 当成永久正式名字。
11. 执行时拿“现在先复用、以后再说”给第二入口或第二契约续命。
12. 生产公开表面仍暴露 `forTest / 供测试` seam，让测试绕开真实 owner。

### 2.2 六边形边界满分

六边形满分是依赖方向真实向内，不是文件夹名字像 port / adapter。

必须同时满足：

1. `domain / application / contract / 稳定共享语义` 不引用 `Axum / SQLx / socketioxide / tower / reqwest / DOM / localStorage / Video.js / WebTorrent` 具体 API。
2. adapter 只负责 IO、协议、鉴权材料读取、错误转码、SQL 或外部系统翻译。
3. shell 只负责用户交互编排、DOM 表达、HTTP / socket 路由、事件转译和调用应用端口。
4. 稳定共享语义只接收原始字符串、自有值对象或标准库类型；协议类型在 shell / adapter 边界被翻译掉。
5. 缺少端口实现必须编译期暴露，不能靠 `Ok(None)`、`Ok(vec![])`、默认空方法或 `系统错误` 把能力缺口藏到运行期。
6. adapter 不能横向调用另一个 adapter 的私有 helper 来拼业务结果。
7. 组合根只能装配依赖，不能承载业务判断、媒体对账、清理策略、恢复策略、实时补发规则、总仓储总线或前端总编排逻辑。
8. 任何 repository / adapter 只对一个明确 bounded context 负责；跨上下文协作必须回到 application 编排。
9. 每条外部入口都有可追踪路径：inbound adapter / shell -> application -> domain / port -> outbound adapter -> contract response。
10. 允许存在最外层组合根，但组合根的命名和职责必须一致；一旦它仍以“总装”名义吸附业务判断、总仓储或总编排逻辑，就不算六边形终态。

六边形满分失败条件：

1. 内层出现外层框架类型。
2. 稳定语义模块需要 `axum::http::HeaderMap`、`SocketRef`、`HTMLElement`、`Video.js` 这类外层类型。
3. 适配器之间互相借道。
4. 组合根文件继续承担业务主链。
5. `Pg仓储` 这类总仓储壳继续跨上下文持有 port 实现。
6. adapter 在 bootstrap 时继续生成 identity / session / display truth，而不是只落库 / 读库 / 翻译幂等冲突。
7. 错误语义被框架错误或泛化 `系统错误` 吞掉。
8. 组合根名义和真实职责分离，导致维护者必须靠口头历史理解边界。

### 2.3 简洁度满分

简洁度满分不是机械压行数，而是更少概念、更少路径、更短主链、更低维护成本。

必须同时满足：

1. 没有只转发一次的函数。
2. 没有只包一层的对象。
3. 没有为了“像架构”存在的文件、trait、类或目录。
4. 没有长期存在的 `兼容 / legacy / facade / wrapper / helper / common / utils / fallback / shim / temp / old / 旧 / 门面 / 包装` 生产路径。
5. 所有生产 `.rs` / `.ts` 热点都进入统一预算扫描；最终满分状态不允许生产源码文件超过 `987` 有效代码行（空行与注释不计数）。
6. Rust 侧 `cargo clippy --all-targets -- -D warnings` 必须零 warning。
7. TypeScript 侧 `pnpm --dir frontend exec tsc --noEmit --noUnusedLocals --noUnusedParameters` 必须通过。
8. 前端 barrel / re-export 只能服务真正稳定公开表面；不得让 `index.ts` 重新成为大而全的业务总入口。
9. 新增抽象必须删除更多复杂度；如果抽象只是搬家或拉长主链，判负。
10. 即使文件已经在预算内，也不得容忍总仓储壳、总编排壳或同步 / 异步双实现继续长期并存。
11. 生产 `barrel / re-export` 必须逐项说明 owner 理由；像 `frontend/媒体/index.ts` 这类宽表面，如果解释不通就必须收窄或删除。
12. 当前不判主缺口的公开表面，例如 `frontend/平台/index.ts`、`frontend/操作台/index.ts`、`frontend/操作台/附件入口/index.ts`，也必须在独立审计里给出“为什么保留”的说明；说明不了就转为缺口。

简洁度满分失败条件：

1. 为了收口旧复杂度新建一层门面。
2. 为了迁移安全保留旧路径和新路径并存。
3. 代码变短但主链更难追。
4. 测试改成依赖私有转发壳，反向锁死冗余结构。
5. TypeScript 或 Rust 默认检查允许未使用代码、死导入、死参数长期存在。
6. 文件虽然小于 `987` 有效代码行，但本质上仍是总仓储壳、总编排壳或复制业务规则的双实现。
7. 宽 barrel、迁移壳、只转发一次的 re-export 因为“暂时省事”长期共存。
8. 生产公开表面仍暴露 `setTransportForTest`、`setKernelForTest`、`供测试` 族 seam，把测试语义混进正式 API。
9. 为了改名而制造大爆炸 churn，导致主链更长、验证面更大、owner 更模糊。

## 3. 必须先落地的硬门禁

这些不是“优化项”，而是三满分前置条件。没有它们，不准开始大规模拆文件。

### 3.1 完成矩阵降级门禁

目标：仓库不能同时存在“当前不是满分”的 spec 和“已经满分”的完成矩阵。

必须做：

1. 把 `docs/superpowers/reports/2026-05-01-真DDD重构完成矩阵.md` 状态改为 `验证中`。
2. 在矩阵中登记本轮真实结构缺口，而不是保留已经过期的热点数字和旧门禁红灯。
3. 新增守卫：只要任一满分前置门禁失败，完成矩阵不得出现 `DDD: 满分`、`六边形边界: 满分`、`简洁度: 满分` 或 `状态：已完成`。
4. 矩阵中的“还差什么”必须和当前代码真相同步；已经被修掉的旧缺口必须删除，当前新暴露的总仓储壳 / 总编排壳 / 规则复制问题必须写进去。

验收：

```powershell
cargo test --test 架构边界守卫
```

### 3.2 同步 / 异步业务规则不得复制门禁

目标：同一业务事实如果同时被 HTTP 冷路径和 realtime 热路径消费，必须共用同一条业务规则主链。

必须做：

1. `src/消息/应用.rs` 的同步 / 异步消息创建链不能继续各自维护 owner、status、kind、width、height、preview 校验。
2. 允许 transport / await 方式分叉；禁止业务规则 owner 分叉。
3. 必须用测试或结构守卫证明：修改消息成立性时，不会再出现“只改同步，漏改异步”或反过来的路径。
4. 如果某条链暂时仍分成同步 / 异步两个入口，必须明确其中一个只是调度壳，真正业务规则只存在一处。

验收：

```powershell
cargo test --test 消息主链测试
cargo test --test 用例测试
```

### 3.3 薄组合根与总仓储壳门禁

目标：允许存在组合根，不允许存在跨上下文总仓储壳。

必须做：

1. `src/适配/mod.rs` 不能继续以 `Pg仓储` 形式长期承接身份、房间、消息、媒体、恢复的 repository 责任。
2. `src/应用/mod.rs` 不能继续回流成总业务中心；它只能保留真正跨上下文共享的最小端口、最小错误映射和最小公共校验。
3. 后端可以保留 `总装`，但它只能是薄组合根：读取配置、创建 concrete adapter、注入依赖、连接入口。
4. 任何“总装还需要顺手判一点业务”的理由都视为结构退化，不给豁免。
5. 跨上下文协作必须显式回到 `application` 编排，不得靠统一 repo 壳偷偷抹平边界。

验收：

```powershell
cargo test --test 架构边界守卫
cargo test --test 用例测试
cargo clippy --all-targets -- -D warnings
```

### 3.4 前端总编排壳门禁

目标：允许存在 app root，不允许存在跨恢复 / 实时 / 阅读推进 / 平台桥接 / 媒体会话的总编排壳。

必须做：

1. `frontend/应用根/聊天应用内核.ts` 最终只能保留顶层 command 路由、snapshot 汇总和子 owner 生命周期装配。
2. 恢复补锚、实时补洞、阅读推进、平台桥接、本地状态折叠细节必须继续下沉到真实 owner。
3. 不能因为它已经不在前端根目录，就把它当作合格架构。
4. 前端如果仍需要一个 root class，也必须证明它不再拥有跨子域流程主权。

验收：

```powershell
node scripts/check-frontend-architecture-fitness.mjs
pnpm --dir frontend test
```

### 3.4.1 命名、公开表面与迁移壳门禁

目标：执行时不能只拆逻辑，不拆语言；不能只拆生产 owner，不拆第二入口和过渡壳。

必须做：

1. “总装”如果继续存在，必须被正式降格为迁移命名；终态命名要么收成 `组合根 / 应用根 / 协调器 / 装配`，要么明确标注仍在迁移中且有退出路径。
2. `frontend/媒体/index.ts` 必须进入正式审计：要么收成窄而稳定的公开表面，要么删除并改成直连真实 owner。
3. `src/实时/契约.rs`、`src/房间/契约.rs`、`src/消息/契约.rs`、`src/身份/契约.rs` 必须退出“第一阶段先复用”的迁移态。
4. 门禁脚本必须能直接拦下：
   - “总装”命名长期滞留；
   - 迁移壳长期滞留；
   - 生产宽 barrel 长期滞留。
5. 本轮不判主缺口的 `frontend/平台/index.ts`、`frontend/操作台/index.ts`、`frontend/操作台/附件入口/index.ts` 仍要在独立复核里给出保留理由。

### 3.5 清洁与反垃圾门禁

目标：项目代码不能有冗余垃圾；清洁不是副目标，而是满分的一部分。

必须做：

1. 生产代码和测试代码都不得长期保留未使用 import、变量、参数、类型、fake、helper。
2. 热点预算必须持续保持全量扫描，但“低于 `987` 有效代码行”只是一条底线，不是总仓储壳 / 总编排壳的豁免证。
3. 不允许为了拆分引入 `helper / utils / common / facade / wrapper / shim / temp / old / legacy / fallback` 生产路径。
4. 不允许为了“稳一点”长期保留旧入口、新入口、过渡门面双活。
5. 不允许新增只转发一次的函数、只包一层的对象、只服务“看起来像架构”的空壳抽象。

验收：

```powershell
pnpm --dir frontend exec tsc --noEmit --noUnusedLocals --noUnusedParameters
cargo clippy --all-targets -- -D warnings
node scripts/check-frontend-architecture-fitness.mjs
```

### 3.6 独立全仓复核门禁

目标：最终满分不能只依赖“当前门禁脚本自己说通过”；还必须反查是否仍有高风险汇聚点和冗余垃圾。

必须做：

1. 输出所有生产 Rust / TypeScript 超 `987` 有效代码行文件清单；清单非空时不得满分。
2. 输出所有内层候选文件中外层协议类型命中清单；清单非空时不得满分。
3. 输出所有生产文件名兜底桶命中清单；清单非空时不得满分。
4. 输出所有 `pub use`、`export * from`、`export { ... } from` 清单，并逐项判定是稳定公开表面还是过宽 barrel；解释不通就删除。
5. 输出当前仍存在的高风险汇聚点清单：总仓储壳、总编排壳、同步 / 异步规则复制点；清单非空时不得满分。
6. 输出 `graphify-out/GRAPH_REPORT.md` 的 god nodes 与 knowledge gaps；任何新出现的跨社区总入口、低连接孤岛 owner、或高连接 helper 都必须解释或收口。

这一步是复核，不是替代 TDD。它的作用是防止“门禁数组漏了某个文件”或“文件已经变小但总壳还在”再次发生。

## 4. 执行顺序

必须按顺序推进，不能先做看起来爽的大搬家。

本轮顺序必须额外满足一条元约束：

1. 先修权威 spec，让执行语言、命名裁决、公开表面裁决、迁移壳裁决和 scope 不再漂。
2. 再修 plan，把门禁、命名、公开表面、迁移壳、高密度 owner 的顺序写死。
3. 再进入代码实现；任何跳过前两步直接开改的行为，都视为制造第二套隐含计划。

### 4.1 第一阶段：先让谎话不能通过

目标：把完成矩阵和门禁对齐，让“还没满分”能被自动检测出来，同时让旧版过期缺口描述自动失效。

步骤：

1. 降级完成矩阵为 `验证中`。
2. 加完成矩阵守卫：满分前置门禁失败时禁止 `状态：已完成`。
3. 加同步 / 异步业务规则复制门禁，先让“消息主链两边各改各的”失败。
4. 加总仓储壳 / 总编排壳识别门禁，先让“虽然预算内但还是总壳”失败。
5. 保持现有全量热点、unused、clippy、前后端架构门禁继续为绿。
6. 加独立全仓复核输出，确认没有硬编码数组漏项，也没有“文件变小但总壳仍在”的假绿。

这一阶段允许 RED。没有 RED，就说明门禁没有抓到真实缺口。

### 4.2 第二阶段：TDD 先拆消息主链重复

目标：先把最典型、最危险、最容易未来漂移的业务规则复制点拆掉。

步骤：

1. 先写或加强测试，明确锁住 `src/消息/应用.rs` 当前同步 / 异步两条消息成立链的行为。
2. 把 owner、status、kind、width、height、preview 校验收成同一条业务规则主链。
3. 让同步入口和异步入口只在 transport / await 方式上分叉，不再在业务规则上分叉。
4. 跑消息主链测试、用例测试和相关边界守卫。

验收：

```powershell

cargo test --test 用例测试
cargo clippy --all-targets -- -D warnings
```

### 4.3 第三阶段：TDD 拆后端总仓储壳和共享业务中心

目标：把 `src/适配/mod.rs` 和 `src/应用/mod.rs` 收到真正的六边形边界。

步骤：

1. 按 bounded context 拆 `Pg仓储` 持有的 port 实现：身份、房间、消息、媒体、恢复分别落位。
2. 把 `src/应用/mod.rs` 缩回真正跨上下文共享的最小公开面。

## 6. 满分宣称格式

只有全部验收通过后，最终报告才允许这样写：

```text
DDD: 满分
六边形边界: 满分
简洁度: 满分
```

报告必须同时列出：

1. 删除了哪些旧入口、兼容链、转发壳。
2. 哪些稳定语义移除了外层协议类型。
3. 哪些 owner 被拆薄，拆到了哪里。
4. 哪些生产热点降到 `987` 有效代码行以下。
5. 哪些门禁新增或收紧。
6. 哪些 unused / dead-code 入口被清掉。
7. 哪些总仓储壳 / 总编排壳被拆掉，拆到了哪里。
8. 哪些真实浏览器路径已经验证。
9. 哪些命令新鲜通过。
10. `git status --short` 是否为空。
11. “总装”命名残留清到了哪里，哪些地方仍是迁移态、何时退出。
12. 哪些宽 barrel 被收窄或删除，哪些公开表面被保留以及理由。
13. 四个迁移壳契约最终是被收成真上下文契约，还是被删除。

禁止写法：

1. “基本满分”。
2. “理论上满分”。
3. “除了烟测都满分”。
4. “还有少量 warning 但不影响满分”。
5. “文件虽然超过 `987` 有效代码行但 owner 明确所以算满分”。
6. “文件已经低于 `987` 有效代码行，所以总仓储壳 / 总编排壳也算满分”。
7. “先保留兼容层，后续再删”。
8. “这只是 TypeScript unused，不影响运行”。
