外部资料校准后的本文裁决：

1. Eric Evans / Domain Language 的核心不是“分层目录”，而是核心领域、统一语言、显式边界和模型一致性；本文把它落成 `业务事实唯一 owner + 模块内统一语言 + 跨模块只走契约`。
2. Martin Fowler 对 Bounded Context、Domain Model 和 Anemic Domain Model 的警告，落到本文就是：模块必须有行为和不变量，禁止只有字段搬运、DTO 转抄和 controller/service 脚本式业务。
3. Cockburn 的 Hexagonal Architecture、Palermo 的 Onion Architecture 和 Clean Architecture 的依赖规则，落到本文就是：内层业务不知道外层技术，外部世界只能通过 port / adapter / contract 进入，依赖方向永远向内。
4. Microsoft Tactical DDD 对 aggregate、application service 和 invariant 的实践边界，落到本文就是：`领域` 守业务不变量，`应用` 编排用例，`适配/外壳` 只翻译和投影；事务一致性只包必须一起成立的最小业务闭包。
5. 这些资料在本文里不作为引用装饰存在，而是作为执行尺：凡是不能证明 owner、语言、依赖方向、不变量、测试门禁都收口的改动，禁止被称为“真 DDD / 真洋葱 / 真积木”。

## 0. 总裁决

**`koko` 的目标不是“目录看起来像分层”，而是真正形成一套只有单一业务真相轴的后端核心、一套只拥有交互真相的前端核心、若干高内聚业务积木、极薄适配与外壳，以及只通过稳定契约协作的前后端边界。**

从这句话推出全部硬边界：

1. 应该先按业务模块切，再按 `领域 / 应用 / 契约 / 适配 / 外壳` 切。  
   禁止先全局横向切层，再把不相关业务揉进同层超级大文件。
2. 应该让后端成为唯一业务真相 owner。  
   禁止让前端、本地缓存、实时层、播放器、恢复链、仓储实现或接口层拥有业务成立性。
3. 应该让前端只拥有交互真相、体验真相和平台适配真相。  
   禁止让前端重建权限、成员、消息成立性、房间存在性、媒体成立性。
4. 应该让前后端只共享稳定契约，不共享核心实现。  
   禁止前端依赖后端内部实现，禁止后端依赖前端壳层流程。
5. 应该让每个模块只因一种业务变化而变化。  
   禁止“统一内核”“统一用例”“统一外壳”“公共助手”长期吸附多条 owner 线。
6. 应该把适配层和外壳层收薄，限定为翻译、投影、编排。  
   禁止 adapter / shell 偷做业务裁决。
7. 应该让物理文件位置表达真实 owner：根目录只放真实入口、总装、配置、类型声明、service worker 和必要静态入口或开发工具脚本；旧根文件只要不再是唯一真实入口，就必须删除。
   禁止让大量 `.rs` / `.ts` 长期散落在根目录，形成“看似有模块、实际靠根目录总控”的第二套结构。
8. 应该把真实主链、真实 owner、真实依赖方向写成测试和门禁。
   禁止靠口头共识维护架构，禁止无门禁裸奔。
9. 应该把历史命名为“总装”的东西收成**薄组合根**：它只负责启动、选 concrete adapter、连接端口和注入依赖。
   禁止总装继续长成跨上下文业务总控、总仓储总线或前端总编排壳。

## 1. 为什么现在必须做这份设计

### 1.1 项目现实不是普通 CRUD

`koko` 不是一个静态网页，也不是一个低并发后台表单系统。它的真实目标是：

1. 公网万人实时图文视频群聊。
2. 稳定秒达，不崩，不靠侥幸。
3. 前端要在真实浏览器里承接房间切换、时间线滚动、恢复、查看器、全屏、播放、协作分发这些复杂交互。
4. 后端要在高并发下持续守住身份、房间、消息、媒体、恢复的业务真相。

这直接推出一个结论：

**这个项目如果没有清晰 owner、清晰边界、清晰契约，复杂度不会消失，只会换一种更脏的方式回流到大总管文件里。**

### 1.2 当前代码并不是“完全没分层”，但也远没到“真 DDD”

当前仓库已经有真实边界意识，不是纯假分层：

1. 后端已经存在 `domain / application / contract / adapter / shell` 的结构意图。
2. 后端里已经能看到仓储端口、适配实现、外壳翻译、领域不变量这些真边界。
3. 前端也已经开始收窄公开入口，并有架构边界测试意识。

但它还没有到“真 DDD 洋葱积木”的程度，原因很直接：

1. 后端仍有超大文件，例如 `src/用例.rs`、`src/外壳.rs`、`src/媒体上传外壳.rs`、`src/媒体附件适配.rs`，说明模块颗粒还不够细。
2. 前端曾经也有大总控式根文件，例如 `frontend/聊天应用内核.ts`、`frontend/聊天壳.ts`、`frontend/聊天媒体编排.ts`；这些根目录业务 owner 已经完成第一轮清零，但这只说明根目录层面暂时收住了，不代表模块内部永远不会重新长胖。
3. 目录上虽然已经出现分层词汇，但跨模块 owner 还没有完全稳定收口。
4. 根目录仍散落不少 `.rs` 文件，历史上也散落过大量 `.ts` 文件，说明物理文件位置曾经没有完全跟上 owner 收口；这些文件不能被长期解释成“方便”，只能被视为迁移期债务。
5. 当前最危险的问题已经不再只是旧根文件，而是**进入模块后仍保持高风险汇聚形态**的文件：`src/消息/应用.rs` 仍同时维护同步/异步两条消息成立规则链，`src/适配/mod.rs` 仍以 `Pg仓储` 形式承接跨上下文总仓储壳，`frontend/应用根/聊天应用内核.ts` 仍承担恢复、实时、阅读推进、平台桥接和本地状态折叠的大总编排壳。
6. 这些文件今天即使预算内、测试全绿，也只能说明“当前行为可用”，不能说明“结构已经满分”；因为它们仍然是未来屎山最容易回流的位置。
7. 如果不把这些高风险汇聚点继续拆掉，项目只是从“根目录屎山”变成“模块内屎山”，本质问题没有解决。

如果继续沿着现在的惯性加功能，会发生三件事：

1. 新逻辑会继续往大文件、大类、大总控里堆。
2. 真实业务真相会在前端、本地缓存、恢复链、实时层之间长出第二份影子。
3. 维护者会越来越依赖“先补一下”“先兼容一下”“先别删旧的”，最后把系统养回屎山。

### 1.3 这份设计解决什么，不解决什么

本文负责：

1. 给出 `koko` 真 DDD 结构的 authoritative 目标形态。
2. 说清楚为什么必须这样切，哪些路径允许，哪些路径禁止。
3. 定义前后端 owner、模块 owner、层级 owner。
4. 定义根目录散落文件的合法边界、迁移归宿和删除时机。
5. 给出防漂移、可迁移、可验收的落地顺序。

本文不负责：

1. 把当前代码伪装成已经完全实现。
2. 用漂亮目录树掩盖 owner 未收口的事实。
3. 给无边界的“顺手重构”开绿灯。
4. 把历史散落文件永久合理化。

## 2. 这里说的“真 DDD / 真洋葱 / 真积木”到底是什么意思

### 2.0 外部资料进入 `koko` 后只保留可执行含义

本文不把 DDD、洋葱、六边形、Clean Architecture 当成四套并列仪式。它们在 `koko` 里只合成一条规则：

**业务语言和不变量在内，技术框架和 IO 在外；外圈可以很多，核心真相只能一套；积木靠清楚边界拼接，不靠散文件和空接口伪装。**

所以后续所有重构都先回答五个问题：

1. 这条逻辑属于哪个业务语言边界？
2. 它守住了哪个业务不变量？
3. 它的唯一 owner 是谁？
4. 它和外部技术之间通过哪个契约或端口说话？
5. 如果删掉 Axum、SQLx、socketioxide、浏览器 DOM 或某个播放器壳，核心业务语义是否仍能被测试？

五个问题答不清，禁止先动目录，禁止先造接口，禁止把“看起来更 DDD”的命名当作进展。

### 2.1 真 DDD 不是给文件取了几个高级名字

真 DDD 的核心不是“文件夹叫 `领域/应用` 就算数”，而是：

1. 每条业务事实都有唯一 owner。
2. 每个模块都只负责一类业务变化。
3. 跨模块协作只通过稳定语义，而不是偷看彼此肚子里的实现。
4. 模型必须说业务真话，术语必须和本模块的业务语言一致。
5. 聚合必须守不变量，不能只是数据库行、DTO 或字段袋子。

应该这样理解：

- `领域` 决定业务上什么成立，什么不成立。
- `应用` 决定命令怎么流转，查询怎么汇总，事件怎么编排。
- `契约` 决定跨边界时双方说什么话。
- `适配` 决定外部世界怎么翻译进来、怎么翻译出去。
- `外壳` 决定展示和交互怎么编排。

禁止这样理解：

- 把 `领域` 当工具函数堆放区。
- 把 `应用` 当总控脚本。
- 把 `契约` 当所有类型的大杂烩。
- 把 `适配` 当偷放业务判断的后门。
- 把 `外壳` 当“反正 UI 特殊，所以可以随便写”的免责区。
- 把贫血模型、字段映射、DTO 搬运、SQL 脚本和 handler 分支包装成 DDD。

### 2.2 “洋葱只有一个真核心”不等于“只能有一个巨型核心文件”

这句话必须说准。

“只有一个真核心”真正表达的是：

1. 整个系统只有一套业务真相主轴。
2. 同一条业务事实不能在多个地方各判一次。
3. 前后端不能各自长出一套互相不认的事实体系。
4. 依赖方向只能从外圈指向内圈，内圈不能知道外圈技术。

它**不**表达下面这些错误意思：

1. 整个仓库只能有一个超级大核心文件。
2. 所有业务都必须塞进一个“聊天总核心”。
3. 只要能在一个类里全控，就叫“单核心更纯”。
4. 只要画了洋葱图，handler、repo、前端状态机就可以继续各判一份业务。

正确落法是：

**全局只有一套业务真相主轴，但每个业务模块内部各有自己的小洋葱核心。**

这才既符合“唯一真相”，又不会把项目重新压回单个超大总控。

洋葱的验收标准不是“目录像圆圈”，而是：

1. `领域 / 应用` 不引用 Axum、SQLx、socketioxide、DOM、Video.js、WebTorrent 具体 API。
2. `适配 / 外壳` 可以依赖内层契约，但内层不能反向依赖适配实现。
3. 技术替换时，修改集中在 adapter / shell / 总装，不牵动业务不变量。
4. 测试可以绕开真实 UI、真实数据库、真实网络，直接验证领域和用例。

### 2.3 真积木不是碎文件，而是高内聚、可替换、可理解

积木式架构追求的是：

1. 每一块积木做一件清楚的事。
2. 别人通过清楚接口使用它。
3. 别人不需要知道它内部怎么长。

应该拆成“小而完整的业务块”。  
禁止拆成“名字很多、职责更乱的碎片文件”。

所以本文的结构原则不是：

- 文件越多越高级。

而是：

- 模块边界越清楚越高级。
- 每个模块越能独立推理越高级。
- 每条依赖方向越单纯越高级。

真正像乐高的模块还必须满足：

1. 插口少而清楚：对外只暴露 command / query / event / snapshot / error 或明确 port。
2. 内部能换：数据库、协议、播放器、浏览器能力、测试替身都不能反向塑造业务模型。
3. 拼接不漏真相：一个模块只能消费另一个模块的稳定语义，不能偷看内部结构。
4. 删除有边界：拆掉旧入口、旧适配、旧根文件时，不需要在全仓找第二套隐藏真相。
5. 复用成熟轮子，但轮子只能当二副，不能决定业务航线。

### 2.4 没有屎山代码的真 DDD 硬判定

没有屎山代码不是“文件短一点”或“名字高级一点”，而是维护者能快速判断系统为何这样运行、哪里能改、哪里不能改。

应该同时满足：

1. 一条业务规则只出现一次，且出现在正确 owner。
2. 一个模块的公开表面小到能被完整读懂。
3. 一个用例的主链能从 shell 追到 application / domain，再追回 event / response，中途没有隐藏分支。
4. 错误语义是业务语言，不是外部框架错误码裸奔。
5. 测试按不变量、用例、契约、适配、壳层分开证明，不靠一个大集成测试赌运气。
6. 删除旧路时不会牵出一堆“其实还有人偷偷用”的影子入口。
7. 新人不用背口头历史，只看命名、契约、测试和门禁就知道边界。

如果一个改动让文件更多、接口更多、映射更多、状态更多，但 owner 没更清楚、主链没更短、测试没更准，它就是屎山增长，不是 DDD 进步。

### 2.5 组合根不是业务总装

真正的 DDD / Hexagonal / Onion 需要的是**最外层组合点**，不是长期存在的“业务总装层”。

这条裁决来自几套经典资料的共同交集：

1. 核心业务必须和 UI、数据库、协议、网络、浏览器能力隔离。
2. 外层负责把具体技术装进去，内层只表达业务语言和不变量。
3. 配置与使用必须分离；业务对象不应该自己到处找依赖。

本文把这条共识在 `koko` 里落成一句硬话：

**组合根可以存在，但它只能是薄的启动装配点；一旦它开始承载跨上下文业务规则、跨模块仓储总线或前端总编排逻辑，它就不再是组合根，而是待拆垃圾。**

应该：

1. 把后端 `总装` 理解成 `composition root / bootstrap / wiring point`。
2. 让它只负责读取配置、创建 concrete adapter、注入依赖、连接入口。
3. 让前端 app root 只负责顶层 command 路由、snapshot 汇总和子 owner 生命周期装配。
4. 能并回 `main / entry` 的装配逻辑就并回去，不为“总装”这个名字单独养一层。

禁止：

1. 禁止组合根承载业务裁决。
2. 禁止组合根成为跨 bounded context 的总用例中心。
3. 禁止组合根持有跨身份/房间/消息/媒体/恢复的统一大仓储壳。
4. 禁止组合根持有跨恢复/实时/阅读推进/平台桥接/媒体会话的统一大编排壳。
5. 禁止因为它“不在根目录”或“只是 glue code”就豁免对它的结构审查。

### 2.6 Onion Explicit Architecture：显式洋葱，不要模糊洋葱

这次重构的目标，不是“目录长得像洋葱”，而是**显式洋葱架构**：

1. 最内层显式写明谁拥有业务真相。
2. 中间层显式写明谁只能通过契约说话。
3. 外层显式写明谁只做翻译、投影、装配和编排。
4. 任何模糊层、方便层、过渡层都必须带着退出路径存在，不能靠“先这样”长期续命。

为什么必须强调“显式”两个字：

1. `koko` 当前面对的是万人实时群聊、媒体上传与播放、恢复、协作分发和浏览器应用化体验，不是普通 CRUD 项目的轻量整理。
2. 在这个复杂度下，真正危险的不是“完全没分层”，而是“表面上像分层，实际 owner、边界和依赖方向没有被写死”。
3. 一旦边界没有被显式写死，执行时就会出现大量临场判断：这个判断到底放后端还是前端，这个 adapter 能不能顺手判一点业务，这个组合根能不能顺手补一个仓储方法，这个 `index.ts` 能不能先全导出去再说。
4. 这种“临场判断”短期看省事，长期看就是屎山再生口。因为每次都只多加一点点，最后没有一个地方能说清楚谁才是真 owner。

本文因此把 Onion Explicit Architecture 写成四层硬裁决：

1. **业务核心层**
   - 后端按 bounded context 拥有 `领域 / 应用`。
   - 前端只拥有交互真相、体验真相和平台适配真相。
   - 权限、成员资格、消息成立、媒体成立、恢复合法性，只能由后端内层裁决。
2. **稳定契约层**
   - 前后端共享的只能是稳定 `contract`。
   - `contract` 只放 command / query / event / snapshot / error。
   - 禁止把页面文案、布局词、框架类型、SQL 形状、浏览器对象和壳层流程塞进契约。
3. **薄适配层**
   - HTTP、WebSocket、数据库、浏览器 API、Video.js、WebTorrent、对象存储、日志都属于 adapter / shell。
   - adapter 只做协议翻译、IO、错误转码、鉴权材料提取和框架胶水。
   - shell 只做交互编排、DOM 表达、路由、调用应用端口和必要的体验态维护。
4. **薄组合根层**
   - 只负责启动、装配、注入和连接端口。
   - 禁止业务总装、仓储总装、编排总装借着“组合根”名义长期存在。

这四层的收益，不是“看起来高级”，而是：

1. 新功能来了，先能判断该进哪层，而不是先堆到最大文件里。
2. 测试能按不变量、用例、契约、适配、壳层分开证明，而不是全靠大集成测试赌运气。
3. 技术替换集中在外层；真正的业务语义、事件语义、错误语义和 owner 关系不会被框架 API 牵着走。
4. 维护者不用背口头历史，只要看命名、契约、测试和门禁，就能知道哪里允许改、哪里绝对不能改。

所以这里给出最硬的总裁决：

**`koko` 未来允许存在“薄组合根”，不允许存在“模糊总层”；允许存在“显式公开表面”，不允许存在“方便式第二入口”；允许存在“带退出路径的迁移态”，不允许存在“无限期过渡态”。**

### 2.7 命名、公开表面与迁移壳：语言必须说真话

DDD 的一个核心要求，是模型、文档、讨论和代码都使用统一语言。
这条要求落到 `koko`，不只是“业务名尽量中文”这么简单，而是：

**名字必须揭示真实 owner，公开表面必须揭示真实边界，迁移壳必须揭示真实时效。**

#### 2.7.1 命名裁决

应该：

1. 让模块名、文件名、类型名直接说出它的业务职责。
2. 让“组合根 / 应用根 / 协调器 / 壳 / 契约 / 适配 / 领域 / 应用”这些词各自只表达一种结构含义。
3. 让中文业务名继续作为正式物理命名与 review 语言，避免中英双轨 owner 词汇长期并存。
4. 允许业务概念、owner、领域类型、前端壳层使用中文名。
5. 对外部互操作敏感表面优先使用 ASCII：crate 名、环境变量、外部协议字段、工具链敏感入口。

禁止：

1. 禁止把 `总装` 当成长期正式架构名词继续保留。
2. 禁止把“总装内核”“总装桥接”“总装状态”这类历史迁移命名包装成终态语言。
3. 禁止为了名字整齐做大爆炸式全仓重命名。
4. 禁止一边在文档里说 `组合根`，一边在代码和门禁里继续默认 `总装` 是永久正式名字。

#### 2.7.2 公开表面裁决

公开表面是最容易被忽视的第二真相入口。
一个模块表面上没有业务总控，但只要它有一个过宽的 `index.ts`、一个过宽的 `pub use`、一个过宽的 facade，它仍然会把本该显式的 owner 关系重新抹平。

应该：

1. 让公开表面只服务真正稳定的消费者。
2. 让每个 `index.ts`、`pub use`、`export { ... } from` 都能说清楚：
   - 谁在消费它；
   - 它为什么不是第二入口；
   - 为什么不应该直接依赖真实 owner。
3. 让测试支架的公开表面和生产表面分开评估。
4. 让生产宽 barrel 进入正式门禁和独立审计输出。

禁止：

1. 禁止“为了方便 import”建大而全 barrel。
2. 禁止让 `frontend/媒体/index.ts` 这类聚合面重新成为媒体子域的事实总入口。
3. 禁止把 `pub use crate::shared::contract...` 这种过宽转发长期解释成“只是形式问题”。
4. 禁止测试公开表面反过来绑架生产结构，让生产 owner 只能继续绕着旧 facade 走。

#### 2.7.3 迁移壳裁决

迁移壳是允许存在的，但只有一种前提：**它必须是临时的、显式的、可验证要被拆掉的。**

应该：

1. 把“第一阶段先复用”“先显式 owner、暂不复制类型定义”这类写法视为迁移期声明，而不是完成态说明。
2. 给每个迁移壳指定终态：
   - 收成真正上下文契约；
   - 或删除。
3. 把迁移壳存在本身纳入门禁和完成态检查。

禁止：

1. 禁止让迁移壳长期停在 `pub use crate::shared::contract...` 状态。
2. 禁止靠注释解释“先这样”来延长迁移壳寿命。
3. 禁止因为迁移壳今天测试还绿，就把它当作稳定结构。

### 2.8 Unix 式克制：该改的坚决改，不该改的不制造噪音

这次路线之所以不是“大爆炸式全仓重命名”，不是因为我们接受妥协，而是因为这不符合 Unix 式克制。

真正的克制不是少改，而是：

1. 只改真实 owner 和真实边界需要改的地方。
2. 不为整齐感制造第二轮复杂度。
3. 不把“看起来更高级”的目录 churn 当作架构进展。

所以本文把这次执行路线正式定成：

1. 先修权威 spec 与验收 spec，让执行时没有第二套口径。
2. 再修 plan，让门禁、命名、公开表面、迁移壳、高密度 owner 的顺序写死。
3. 再用 TDD 做实现：先 RED 证明门禁能抓坏结构，再 GREEN，再 REFACTOR。
4. 最后做完成态审计：文档口径、代码形态、门禁、graphify、真实烟测必须一致。

禁止：

1. 禁止跳过 spec，直接按印象开拆。
2. 禁止跳过 plan，把多个结构目标混成一团同时推进。
3. 禁止只改生产代码、不改门禁、不改文档、不改测试写死路径。
4. 禁止把“今天脚本绿了”误读成“结构已经满分”。

## 3. 单一真相轴：后端拥有业务真相，前端拥有交互真相

### 3.1 后端为什么必须拥有唯一业务真相

后端应该拥有这些真相：

1. 身份是否成立。
2. 房间是否存在。
3. 成员是否有资格。
4. 消息是否成立。
5. 媒体是否提交、是否可读、是否可分发。
6. 恢复时哪些事实可以信，哪些只能辅助。

为什么必须这样做：

1. 前端天然可被阅读、逆向、篡改、重放。
2. 浏览器本地状态天然不可信。
3. 实时层和适配层天然更接近 IO，最容易为了“先跑通”偷放判断。

所以必须立铁律：

**默认前端已经失守，后端仍必须守住业务真相。**

应该：

1. 把权限、成员资格、消息成立性、媒体成立性全部留在后端 `领域 / 应用`。
2. 把所有最终裁决结果都通过稳定契约返回或推送给前端。

禁止：

1. 把“前端先判断一下”当作长期真相。
2. 把“本地缓存里有，就先算成立”当作业务逻辑。
3. 把“实时连接已经通了”误判为“业务事实已经成立”。

### 3.2 前端为什么也有“真核心”，但不是业务核心

前端并不是完全没有核心。  
它有自己的真核心，但那是**交互核心和体验核心**，不是业务核心。

前端应该拥有：

1. 当前正在看哪个房间。
2. 当前时间线可见窗口和滚动锚点是什么。
3. 当前是否打开查看器、是否有播放意图、是否进入全屏。
4. 当前草稿、回复目标、输入中附件是什么。
5. 当前本地恢复态能帮助恢复哪些体验位置。

为什么前端需要这些 owner：

1. 这些是浏览器应用体验的一部分。
2. 后端不应该知道你是弹窗、侧栏、查看器还是全屏。
3. 不把这些交给前端，所有交互都会被后端展示流程反向绑架。

应该：

1. 让前端只判断“我怎么交互、我怎么展示、我怎么编排体验”。
2. 让前端通过契约接收后端裁决后的业务事实。

禁止：

1. 让前端自己判“这个房间是不是存在”。
2. 让前端自己判“这条消息算不算成立”。
3. 让前端自己判“我是不是这个媒体的有效分发者”。

### 3.3 安全收益来自“被破解后也拿不到主脑”

前后端解耦不是神话，不能阻止攻击发生。  
它真正的安全价值是：

1. 缩小攻击面。
2. 降低前端被逆向后的收益。
3. 防止前端壳被改掉以后，系统的业务真相也跟着被篡改。

应该：

1. 假设前端 JS、HTML、网络请求都可以被黑客看见和重放。
2. 把所有重要权限和业务裁决都放在后端核验。

禁止：

1. 因为“前端看起来已经限制了”就放松后端判定。
2. 把接口参数当作已被证明的业务事实。

## 4. 总结构原则：先按业务模块切，再按层切

### 4.1 为什么业务模块必须先于层

如果先全局按层切，很容易长成下面这种形态：

1. 一个超大的统一 `用例`。
2. 一个超大的统一 `外壳`。
3. 一个超大的统一 `聊天内核`。

这种结构表面整齐，实际最危险，因为：

1. 不同业务很快会混进同一个大文件。
2. 一个修改会牵动越来越多不相关责任。
3. Review 很难看出 owner 是否漂移。

所以本文明确裁决：

**目录树首先回答“这是哪个业务模块”，然后才回答“它在这个业务模块里属于哪一层”。**

这也是 Bounded Context 在 `koko` 的落地方式：先确定身份、房间、消息、媒体、实时、恢复这些语义边界，再在边界内部保持统一语言和模型一致；跨边界时只能翻译语义，不能把两个模型揉成一团。

应该：

1. 先把身份、房间、消息、媒体、恢复、实时这些业务块切清楚。
2. 再在每个块里放 `领域 / 应用 / 契约 / 适配 / 外壳`。
3. 先判断模块内聚合要守住哪些不变量，再决定文件怎样落位。

禁止：

1. 继续维持跨业务的超级 `用例.rs`。
2. 继续维持跨业务的超级 `聊天应用内核.ts`。
3. 用“公共逻辑很多”当借口继续把不相关业务揉在一起。
4. 把数据库表、HTTP 路由、前端页面当成业务边界；它们只能影响适配和外壳，不能替代业务语言。
5. 继续容忍 `src/适配/mod.rs` 这类跨上下文总仓储壳长期存在。
6. 继续容忍 `frontend/应用根/聊天应用内核.ts` 这类跨子域总编排壳长期存在。

### 4.2 后端目标目录树

目录树解释规则：

1. 下面给出的目录树，是职责与 owner 的目标图，不是第一阶段必须立刻执行的物理重命名清单。
2. 第一阶段应该优先收口 owner、契约和依赖方向；现有仓库根目录 `src`、`frontend` 可以暂时保留，先把内部模块职责收干净。
3. 只有在 owner、契约、测试门禁都稳定后，才应该考虑是否做更外层的目录落位。
4. 物理目录名和文件名一旦进入正式 owner 落位，默认必须使用仓库统一语言的中文业务名；`lib.rs`、`main.rs`、`mod.rs`、`index.html`、`package.json`、service worker、框架约定入口和工具链强制文件可保留英文，其他业务路径禁止再长出 `upload`、`distribution`、`manager`、`service` 这类英文 owner 目录或文件名。
5. 禁止为了追求“名字更像真 DDD”而先做高风险根目录改名，禁止把“中文目录树更好看”误当成“架构已经收口”；但当 owner 已收口且正在新建正式物理路径时，仍必须直接落成中文业务名，不能再制造中英两套词汇。
6. 根目录允许留下的后端文件只能是 `lib.rs`、`main.rs`、真实入口、总装（仅允许薄组合根）和必要配置；凡是承载某个业务或适配 owner 的 `.rs`，最终都必须落进对应业务模块；凡是只为旧路径服务的包装文件，生产引用切完后必须删除。
7. 后端根目录散落文件如果继续增长，就说明 owner 正在回流；必须先拆回业务模块，再继续加功能。
8. 历史命名为 `总装` 的文件如果仍在长期承载业务裁决、跨上下文仓储总线或前端总编排逻辑，就不算组合根，而算待拆汇聚点；这种文件即使测试全绿、行数达标，也不得被称为满分结构。

3. 媒体必须拆成播放、查看器、分发、上传，不然 owner 永远打架。
4. 前端根目录大量 `.ts` 文件会让“入口 / 总装 / 壳层 / 应用 owner / 平台适配”再次混成一层，长期看仍然不是洋葱。

应该：

1. 让前端核心围绕交互真相分块。
2. 让 `平台` 只承接浏览器能力，不承接业务真相。
3. 让前端根目录长期只保留 `入口.ts`、构建配置、类型声明、service worker，以及确有必要的静态入口文件或开发工具脚本。
4. 让 `房间*`、`聊天*`、`媒体*`、`实时*`、`恢复*`、`后台*`、`状态.ts`、`传输.ts`、`存储.ts`、`应用运行时.ts`、`应用生命周期.ts` 这类带业务或平台 owner 含义的根目录文件全部回到对应模块。
5. 前端根目录不允许保留旧路径包装文件；一旦生产引用已经改到真实 owner，就必须删除旧根文件，而不是长期保留。

禁止：

1. 让 `HTMLElement`、`window`、`document`、`localStorage`、全屏 API 直接进入前端核心。
2. 让 `聊天应用内核.ts` 继续承担房间、时间线、滚动、媒体、恢复、平台混合总控。
3. 把 `房间滚动器.ts`、`房间时间线运行时.ts`、`媒体运行时.ts`、`实时会话运行时.ts`、`应用运行时.ts`、`聊天媒体编排.ts` 这类历史根文件当成长期正常形态。
4. 把“方便 import”当成前端根业务文件长期存在的理由。

### 4.4 根目录散落文件的正式判定

看到很多 `.rs` / `.ts` 散落在 `src/` 或 `frontend/` 根目录时，不能一句“现在能跑”就放过，也不能一句“马上全搬”就开拆。
正式判定分三类：

1. **合法根文件**
   - 后端：`lib.rs`、`main.rs`、`入口.rs`、`总装.rs` 和必要配置。
   - 前端：`入口.ts`、构建配置、类型声明、service worker，以及确有必要的静态入口文件或开发工具脚本。
   - 这些文件只允许做入口、装配、配置或平台注册，不允许拥有业务真相，也不允许为了旧路径继续包一层。
2. **待删除旧根文件**
   - 例如当前仍存在的 `src/用例.rs`、`src/契约.rs`、`src/适配.rs`、`src/外壳.rs`，以及历史上已经清掉的 `frontend/聊天应用内核.ts`、`frontend/聊天壳.ts`。
   - 它们在完成态没有保留资格；执行时必须把生产引用、测试引用和门禁引用改到真实 owner，然后删除旧根文件。
   - 禁止在待删除旧根文件里新增业务判断、新状态机、新缓存真相、新协议分支、新包装层或新导出表。
3. **必须落位的散落 owner 文件**
   - 任何名称已经带出业务含义的根文件，例如 `媒体*`、`房间*`、`消息*`、`实时*`、`恢复*`、`聊天媒体*`，都必须有明确归宿。
   - 如果它只做翻译，落到对应模块 `适配 / 外壳`。
   - 如果它做裁决，落到对应模块 `应用 / 领域`。
   - 如果它只是跨模块装配，落到 `总装`。

这条规则的目的不是追求文件树漂亮，而是防止出现第二套真实结构：

1. 目录里有 `身份 / 房间 / 消息 / 媒体 / 实时 / 恢复`。
2. 根目录又有一批同名大文件继续掌握真正逻辑。
3. 新人和未来 agent 不知道该信目录里的 owner，还是该信根目录旧总控。

这种“双结构”比没有结构更危险。
它看起来像真 DDD，实际会让 owner 漂移更隐蔽。

### 4.4.1 frontend 根目录零业务旧文件裁决

前端根目录必须比后端更严格。
前端如果继续保留大量业务根文件，最容易把真正的交互 owner 偷回根目录。

因此本文对 `frontend/` 追加一条更硬的前端专属裁决：

1. `frontend/` 最终态不保留业务旧路径包装文件。
2. `frontend/房间视口运行时.ts`、`frontend/房间滚动器.ts`、`frontend/房间时间线.ts`、`frontend/房间时间线运行时.ts`、`frontend/房间消息窗.ts`、`frontend/媒体运行时.ts`、`frontend/实时会话运行时.ts`、`frontend/房间恢复编排.ts`、`frontend/后台*.ts`、`frontend/聊天应用编排桥接.ts`、`frontend/状态.ts`、`frontend/传输.ts`、`frontend/存储.ts`、`frontend/应用运行时.ts`、`frontend/应用生命周期.ts` 这类根文件，不因“看起来像总装 / 平台 / 旧适配壳”而自动获得长期保留资格。
3. 这类文件只要生产 import 已经全部切到真实 owner，测试和门禁也必须同步改向真实 owner，然后删除旧根文件本身。
4. 测试如果继续断言“旧根文件存在”，就等于在反向保护旧结构；这种测试必须随着迁移一起被改掉。

一句话钉死：

**`frontend/` 根目录不是旧路径垃圾桶；除入口、service worker、构建配置、类型声明和确有必要的静态入口文件或开发工具脚本外，业务语义文件默认删除，而不是默认保留。**

### 4.4.2 全仓统一物理架构裁决：为什么不能只收前端或只收后端

这条裁决来自当前仓库的真实演进过程，不是为了让目录树看起来整齐。

最初的问题不是“文件名不好看”，而是同一套系统同时存在两种结构：

1. 文档和目录已经开始声明 `身份 / 房间 / 消息 / 媒体 / 实时 / 恢复 / 总装 / 平台`。
2. 但根目录历史文件仍然可能继续承载真正逻辑。
3. Review、测试、未来 agent 和后续开发者很容易不知道该信模块目录，还是该信根目录旧文件。

这会制造三种长期风险：

1. **owner 回流**：新功能为了省事继续写进根目录旧文件，模块目录变成空壳。
2. **第二真相**：模块内有一套判断，根目录旧文件又有一套判断，线上行为最后按谁运行变得不清楚。
3. **执行漂移**：今天说要真 DDD，明天又以“兼容、方便、先别动”为理由把旧入口长期留下。

所以本文对前端和后端使用同一条总原则：

**先按业务模块确定 owner，再在模块内按层确定职责；根目录只允许真实入口、总装、配置、声明、service worker 和必要开发入口。旧根文件只要不是这些真实入口，就必须迁移引用后删除。**

这条原则在后端和前端的表达不同，但底层意思相同：

1. 后端 `src/` 根目录不能长期承载业务 owner、适配 owner 或外壳 owner；`媒体附件适配.rs`、`媒体上传外壳.rs`、`房间外壳.rs` 这类文件名字本身已经说明它们应该回到业务模块。
2. 前端 `frontend/` 根目录不能长期承载交互 owner、状态 owner 或平台 owner；`聊天应用内核.ts`、`聊天壳.ts`、`聊天媒体编排.ts` 这类历史根文件已经清掉，后续禁止以任何名义恢复同类根业务文件。
3. 根目录允许存在的文件必须能用一句话证明自己只是入口、总装、配置、声明或必要开发入口；证明不了，就默认它应该进入业务模块或被删除。
4. 模块目录内部也不能借“已经进模块了”继续堆大总控；进入模块只是第一步，后续仍要按 `领域 / 应用 / 契约 / 适配 / 外壳` 分清业务裁决、命令编排、边界语言、IO 翻译和展示编排。

这条裁决不是要求一次性大爆炸搬完。
正确执行顺序是：

1. 先读当前文件、调用链、测试和门禁，确认它真实拥有哪条 owner。
2. 再把生产 import 改到真实模块路径。
3. 再把测试和架构门禁改成保护新路径，而不是继续保护旧根文件。
4. 再删除旧根文件；禁止把旧根文件改成长期包装层继续存在。
5. 最后用测试、构建、架构门禁、必要时真实浏览器烟测证明没有把业务链路删坏。

### 4.4.3 全仓物理命名裁决：默认中文业务名，不保留中英两套 owner 词汇

这条规则不是为了“中文看起来更整齐”，而是为了避免同一条业务线同时出现两套物理词汇，继续制造认知分叉。

如果文档、注释、测试、讨论和目录树都在说 `上传 / 协作分发 / 房间 / 恢复 / 总装`，但物理路径又写成 `upload / distribution / room / recovery / assembly`，未来维护者和 agent 会再次面对两个问题：

1. 这是同一个 owner，还是两套不同抽象？
2. 新文件到底该跟中文业务词走，还是跟英文路径走？

所以本文补一条硬规则：

1. **正式业务目录名和文件名默认使用中文业务词。**
2. **只有语言、框架或工具链强制的入口文件、保留名和生态标准文件可以继续保留英文。**
3. **协议名、产品名、标准缩写可以作为中文业务名的局部修饰，但不能喧宾夺主。** 例如 `tus回调.rs` 可以，纯 `tus_hook.rs` 不可以；`WebTorrent` 可以出现在注释、常量和值语义里，但业务 owner 路径仍应叫 `协作分发`、`媒体上传`、`内容读取` 这类中文名。
4. **本文约束的是正式物理路径，不要求为了这条规则立刻同步重命名所有稳定模块标识符。** 如果公开 API 或模块标识已经稳定，可以先保持标识不动，只把新建或迁移后的正式目录/文件路径落成中文，避免一次性放大改动面。

验收时只问一件事：**owner 已经确认的新路径，是否还在继续制造中英双轨命名。** 只要答案是“是”，就不能算收口完成。

禁止两种相反的漂移：

1. 禁止为了“看起来 DDD”先造一堆目录、复制一份代码、让新旧双活。
2. 禁止为了“稳一点”把根目录旧 owner 永久保留，最后让模块目录变成展示架。

当前基线必须写清：

1. `frontend/` 根目录业务 owner 已完成第一轮清零，后续任务是防回流和继续拆薄模块内部大文件，不是重建旧路径包装文件。
2. `src/` 根目录仍存在较多后端历史 owner 文件，后续物理架构收口应优先处理这些 `.rs` 文件。
3. 每次执行计划都必须先复核当前文件系统，不能照搬过期清单；已经删除的根文件只能作为历史教训，不能作为新计划的待处理目标。

## 5. 后端模块详细职责

### 5.1 身份

身份模块应该拥有：

1. 会话、匿名身份、设备身份恢复的业务真相。
2. 身份令牌和身份快照的稳定契约。

为什么：

1. 身份是一切权限和成员资格判断的前提。
2. 如果身份真相分散在多个模块，后面所有业务都会变脏。

禁止：

1. 房间模块私自改写身份成立性。
2. 前端自己创造业务身份。

### 5.2 房间

房间模块应该拥有：

1. 房间存在性。
2. 房间成员资格。
3. 房间可见性与加入规则。

为什么：

1. 房间是消息、媒体、恢复的上下文。
2. 不把房间边界钉死，消息和媒体都会偷做房间判断。

禁止：

1. 消息模块直接替代房间判成员资格。
2. 实时层以“已经订阅成功”为由跳过房间判定。

### 5.3 消息

消息模块应该拥有：

1. 消息成立性。
2. 消息事件顺序语义。
3. 附件引用与消息关系。

为什么：

1. 消息是群聊最核心的业务事实之一。
2. 一旦消息成立逻辑被广播层、恢复层或前端分走，系统就会长出第二真相。

禁止：

1. 广播成功与否影响消息是否成立。
2. 恢复补洞逻辑补成第二个消息写入口。

### 5.4 媒体

媒体不能再粗放地当成一个“媒体大桶”。  
它必须按真实 owner 分为：

1. 上传。
2. 资产。
3. 协作分发。
4. 内容读取。

为什么：

1. 媒体复杂度远高于图片附件上传这种简单场景。
2. 上传成功、资产就绪、可读、可播、可分发，这些不是同一件事。
3. 如果不拆，播放器、分发器、恢复链、接口层会互相偷权。

禁止：

1. 让播放器决定媒体业务成立性。
2. 让分发层替代上传提交真相。
3. 让读取旁路变成第二字节主链。

### 5.5 实时

实时模块应该拥有：

1. 连接事实。
2. 订阅事实。
3. 广播运行态结果。

为什么：

1. 实时层需要自己的运行事实，否则无法可观测。
2. 但这些事实不是业务真相，只是运行真相。

应该：

1. 让实时层管理连接、订阅、广播、背压、取消、重试。
2. 让业务是否合法仍由 `应用 / 领域` 裁决。

禁止：

1. 在实时层判权限。
2. 在实时层宣布消息成立。
3. 在实时层把“socket 连上了”冒充成“业务已经成功”。

### 5.6 恢复

恢复模块应该拥有：

1. 恢复锚点。
2. 增量补洞。
3. 恢复查询编排。

为什么：

1. 恢复非常重要，但它本质上是“追平事实”的辅助手段，不是事实 owner。
2. 恢复最容易因为“为了用户体验”偷偷变成第二真相。

禁止：

1. 恢复模块自己宣布消息或成员资格成立。
2. 恢复把本地旧缓存升格成业务权威来源。

## 6. 前端模块详细职责

### 6.1 身份接入

身份接入模块应该拥有：

1. 前端侧会话接入和恢复流程。
2. 身份令牌的持有与重放。

为什么：

1. 前端必须能承接启动和恢复体验。
2. 但它只能持有令牌，不能发明身份业务真相。

禁止：

1. 前端根据本地缓存自创业务身份。
2. 前端根据旧页面状态绕过后端重新核验。

### 6.2 房间

房间模块应该拥有：

1. 当前房间选择。
2. 房间列表交互状态。
3. 房间切换体验规则。

为什么：

1. 房间切换是整个浏览器应用的上下文切换器。
2. 它属于前端交互真相，不应被时间线或媒体模块反向接管。

禁止：

1. 时间线直接决定房间业务存在性。
2. 查看器或播放器越权修改房间真相。

### 6.3 时间线

时间线模块应该拥有：

1. 可见窗口。
2. 滚动锚点。
3. 选中消息。
4. 未读定位。

为什么：

1. 这些都是高频交互事实，必须独立收口。
2. 不独立收口，就会继续混入大内核和 DOM 查询逻辑。

禁止：

1. 时间线直接控制 `WebTorrent`。
2. 时间线直接决定媒体业务成立性。

### 6.4 输入框

输入框模块应该拥有：

1. 草稿。
2. 回复目标。
3. 本地附件选择态。

为什么：

1. 输入相关状态有清楚的交互闭环。
2. 不独立出去，就会继续散落在房间、时间线和媒体逻辑之间。

禁止：

1. 输入框直接拥有消息成立性。
2. 输入框把本地选中的附件直接视作后端已提交媒体。

### 6.5 媒体

前端媒体必须拆成四块：

1. 播放会话。
2. 查看器。
3. 协作分发。
4. 上传。

为什么：

1. 播放、查看、字节分发、文件上传是四种不同 owner。
2. 不拆开就会出现“播放器既是界面又是业务裁判又是分发 owner”的混乱局面。

应该：

1. 让唯一播放器只是壳。
2. 让播放会话模块拥有播放意图、拥有者切换、全屏意图。
3. 让查看器模块拥有查看目标和缩放状态。
4. 让协作分发模块只处理 `WebTorrent` 等字节协作适配。

禁止：

1. 播放器壳拥有 source 真相。
2. 分发桥拥有播放裁决。
3. 恢复链拥有媒体成立性。

### 6.6 实时、恢复、平台

这三者都很重要，但都不该成为前端业务总控。

实时应该拥有：

1. 连接器。
2. 订阅器。
3. 重连器。
4. 事件分发。

恢复应该拥有：

1. 本地恢复锚点。
2. 临时恢复态。

平台应该拥有：

1. 浏览器能力。
2. 可见性。
3. 全屏。
4. 剪贴板。
5. 文件选择。

禁止：

1. `平台` 渗进 `领域 / 应用`。
2. `恢复` 直接宣布业务成功。
3. `实时` 直接判案。

## 7. 前后端真正解耦的硬边界

### 7.1 什么耦合允许存在

前后端不是“完全没耦合”，而是只能保留下面三类耦合：

1. 业务语义耦合：房间、消息、成员、媒体、恢复这些统一语言。
2. 契约耦合：命令、查询、事件、快照、错误码。
3. 时序耦合：先入房，再拉历史，再接增量这类明确业务流程。

为什么：

1. 完全零耦合在协作系统里是伪命题。
2. 真正有害的不是耦合本身，而是实现细节耦合和多处真相耦合。

### 7.2 什么耦合绝对禁止

1. 禁止前端依赖后端内部模块、数据库表、仓储实现、广播实现。
2. 禁止后端依赖前端展示流程、组件状态、布局概念。
3. 禁止前端重建业务真相。
4. 禁止适配层和外壳层偷放业务裁决。
5. 禁止契约混入页面文案、按钮语义、布局语义。
6. 禁止本地缓存升格成业务权威来源。

### 7.3 正确的数据流

正确链路必须始终是：

1. 前端外壳把浏览器动作翻译成应用命令。
2. 前端应用通过稳定契约向后端表达意图。
3. 后端外壳接收并翻译请求。
4. 后端 `应用 / 领域` 裁决业务真相。
5. 后端适配落库、广播、调用外部基础设施。
6. 后端把结果按契约返回或推送。
7. 前端适配接收并翻译。
8. 前端应用更新交互真相。
9. 前端外壳负责渲染与体验编排。

一句话钉死：

**前端发出意图，后端裁决事实，前端把事实变成体验。**

禁止：

1. 前端直接把临时本地态当成已裁决事实。
2. 后端为了迎合某个壳层流程把业务语义写歪。

## 8. 模块之间怎样才算高内聚、低耦合

### 8.1 高内聚标准

高内聚不是“相关代码放在一起”这么简单。  
真正标准是：

**一个模块只因为一种业务变化而变化。**

例如：

1. 房间规则变化，主要影响房间模块。
2. 消息成立逻辑变化，主要影响消息模块。
3. 查看器交互变化，主要影响查看器模块。

禁止：

1. 同一个变更同时必须改五个无关模块才能成立。
2. 一个模块同时负责房间、消息、媒体、恢复四种不同变化。

### 8.2 低耦合标准

低耦合不是“完全互不认识”。  
真正标准是：

**跨模块只能通过稳定表面协作，不能摸对方内部器官。**

应该：

1. 跨模块只看契约或端口。
2. 让别人知道“你提供什么能力”，而不是“你内部怎么实现”。

禁止：

1. `消息` 直接读 `房间` 仓储实现。
2. `媒体` 直接改 `消息` 聚合内部状态。
3. `时间线` 直接操作 `WebTorrent` 细节。

### 8.3 后端允许的依赖主轴

后端建议主轴：

**身份 -> 房间 -> 消息 -> 媒体**

支撑模块：

- `实时`
- `恢复`
- `后台运营`

允许：

1. `房间` 依赖 `身份` 的稳定契约或端口。
2. `消息` 依赖 `房间` 的稳定契约或端口。
3. `媒体` 依赖 `消息 / 房间` 的稳定契约或端口。
4. `恢复` 依赖 `房间 / 消息 / 媒体` 的查询契约。
5. `实时` 依赖各业务模块事件契约，但业务模块不依赖 `实时` 内部。

禁止：

1. `消息` 直连 `房间` 仓储实现。
2. `媒体` 直连 `消息` 内部聚合状态。
3. `实时` 反向成为权限 owner。

### 8.4 前端允许的依赖主轴

前端建议主轴：

**身份接入 -> 房间 -> 时间线 -> 输入框 / 媒体**

支撑模块：

- `实时`
- `恢复`
- `平台`

允许：

1. `房间` 看 `身份接入` 契约。
2. `时间线` 看 `房间` 契约。
3. `输入框` 看 `房间` 与媒体上传契约。
4. `媒体播放会话 / 查看器` 看时间线暴露出的媒体快照契约。
5. `恢复` 只恢复体验态。

禁止：

1. `媒体播放会话` 直接读本地存储。
2. `恢复` 直接判权限。
3. `平台` 进入领域对象。

### 8.5 层级依赖方向

这是全文最重要的硬约束之一：

1. `领域` 只能看本模块领域和极少量共享基础类型。
2. `应用` 只能看本模块领域、本模块契约、别的模块契约或端口。
3. `契约` 只能看共享基础类型。
4. `适配` 只能实现应用要求，不能发明业务真相。
5. `外壳` 只能做交互和展示编排，不能偷做领域裁决。

一句话钉死：

**跨模块协作发生在“应用对契约/端口”，不是“领域对领域”，更不是“外壳对外壳”。**

依赖规则再钉细一点：

1. 内层可以定义 port，外层实现 port；禁止外层为了方便反向修改内层模型。
2. application service 可以开事务、调端口、发事件、组响应，但不能把本该属于聚合的不变量写成脚本分支。
3. repository 是持久化端口或适配，不是业务事实 owner；数据库里有一行，不等于业务上已经成立。
4. domain event 表达业务事实已经发生，不能退化成“某技术动作成功了”的日志别名。
5. contract 是稳定边界语言，不是后端结构体、前端组件 props、SQL 行和 WebSocket payload 的公共垃圾场。
6. adapter 失败只能转成契约错误或应用层可理解的结果，不能让外部库错误码直接泄进业务模型。

## 9. 迁移怎么落地，才不会把系统拆崩

### 9.1 先钉真相和契约，再搬目录

迁移顺序绝不能是“先把目录改漂亮”。  
正确顺序必须是：

1. 先钉死真相 owner。
2. 先钉死契约边界。
3. 先收依赖方向。
4. 再做文件落位。
5. 最后删旧路。

为什么：

1. 目录树只是外观，owner 才是内核。
2. 如果 owner 没钉死，搬文件只是把脏耦合搬到新地址。

禁止：

1. 大爆炸改目录。
2. 先全仓重命名再慢慢找逻辑。
3. 复制一份旧逻辑到新目录里长期双活。

### 9.1.1 当前热点文件到目标模块的首轮映射

光有目标目录树还不够。
如果不把“当前大文件先拆到哪里”写出来，执行时很容易再次漂移成“大家都觉得有道理，但每个人拆法都不一样”。

因此第一轮落位必须先按下面这张映射表执行：

1. `src/用例.rs`
   - 应该先按业务责任拆入 `身份/应用`、`房间/应用`、`消息/应用`、`媒体/*/应用`、`恢复/应用`、`实时/应用`。
   - 禁止继续把新用例、新判定、新编排追加回统一 `用例.rs`。
2. `src/契约.rs`
   - 应该先把稳定 command / query / event / snapshot / error 按业务块拆入各模块 `契约/`，共性基础类型收进 `共享/契约基础.rs`。
   - 禁止把所有跨边界类型继续堆在一个超级 `契约.rs` 里。
3. `src/适配.rs`
   - 应该按持久化、广播、外部协议、数据映射的真实 owner 拆回对应业务模块 `适配/`。
   - 禁止让统一 `适配.rs` 长期同时承接数据库映射、权限旁路、媒体旁路、实时胶水。
4. `src/房间外壳.rs`
   - 应该落入 `房间/外壳/`，只保留房间相关接口编排和响应翻译。
   - 禁止继续在房间外壳里混入消息、媒体、恢复的业务真相。
5. `src/实时外壳.rs`
   - 应该拆成 `实时/外壳/Socket接口.rs` 与 `实时/适配/` 下的连接注册、广播、背压实现。
   - 禁止让实时外壳继续同时拥有 socket 接线、运行态管理和业务判权。
6. `src/媒体附件适配.rs`、`src/媒体内容解析.rs`、`src/媒体上传外壳.rs`、`src/媒体资产外壳.rs`、`src/媒体协作分发.rs`
   - 应该按真实 owner 拆入 `媒体/上传`、`媒体/资产`、`媒体/协作分发`、`媒体/内容读取` 的 `应用 / 契约 / 适配 / 外壳`。
   - 禁止继续保留一个根目录媒体带，表面有 `媒体/` 目录，实际媒体主链还在根目录文件里判。
7. `src/房间阅读适配.rs`
   - 应该落到 `房间/适配/阅读进度.rs` 或 `房间/应用/阅读.rs`，取决于它只做数据翻译还是拥有阅读推进编排。
   - 禁止让阅读进度既像房间业务，又像独立根级基础设施。
8. `src/消息事件适配.rs`
   - 应该落到 `消息/适配/事件投影.rs` 或 `消息/契约/事件.rs`。
   - 禁止让消息事件投影停在根目录，继续模糊“消息成立性”和“事件投影”的边界。
9. `src/用户身份.rs`
   - 应该落到 `身份/领域` 或 `身份/应用`，只留下公共标识类型时才允许进入 `共享/标识.rs`。
   - 禁止让用户身份在根目录绕开 `身份` 模块继续被到处引用。
10. `src/tus_hook外壳.rs`
    - 应该落到 `媒体/上传/外壳/TusHook.rs`，只负责 Tus 协议翻译和响应。
    - 禁止让 Tus hook 外壳拥有附件成立性、媒体 ready 真相或协作分发真相。
11. `src/后台外壳.rs`
    - 应该落到 `后台运营/外壳`，并且只能通过业务模块应用层读取投影。
    - 禁止后台运营成为绕开正式业务 owner 的第二入口。
12. `frontend/` 根目录历史业务 owner
   - 当前基线：`frontend/聊天应用内核.ts`、`frontend/聊天壳.ts`、`frontend/聊天媒体编排.ts`、`frontend/房间视口运行时.ts`、`frontend/媒体运行时.ts`、`frontend/实时会话运行时.ts` 等根目录业务文件已经完成第一轮清零。
   - 后续计划不得再把这些文件写成“当前待迁移根文件”，只能写成“历史上已经清掉、禁止恢复”的反例。
   - 如果测试、文档或门禁还在引用这些旧根路径，应该修正为真实 owner 路径，而不是重新创建兼容文件。
13. `frontend/应用根/聊天应用内核.ts`、`frontend/应用根/聊天壳.ts`
   - 当前它们已经从根目录进入 `应用根/`，下一步关注点不再是根目录清零，而是防止 `应用根/` 变成新的超级大总控。
   - 应该继续把可独立 owner 下沉到 `房间/应用`、`时间线/应用`、`媒体/播放会话/应用`、`恢复/应用`、`实时/应用`、`平台/适配`。
   - 禁止用“已经不在根目录”掩盖总装内部继续吸附 DOM、滚动、媒体、恢复、房间切换、平台能力。
14. `frontend/房间/`、`frontend/时间线/`、`frontend/房间消息窗/`
   - 应该继续按“房间上下文、时间线窗口、滚动视口、消息展示外壳”分别守住 owner。
   - 禁止让房间相关交互在某个新模块内重新并排生长，导致房间 owner 和时间线 owner 分不清。
15. `frontend/实时/`、`frontend/聊天实时/`
   - 应该继续把实时连接、离线补发、重连控制面落到 `实时/应用`、`实时/适配`、`实时/外壳`，浏览器事件先转应用事件，再由 owner 裁决。
   - 禁止让某个运行时文件重新拥有隐形状态机或第二套连接真相。
16. `frontend/恢复/`、`frontend/聊天恢复/`
   - 应该继续让恢复只追平后端事实和体验锚点。
   - 禁止让恢复文件宣布房间存在、消息成立或成员身份成立。
17. `frontend/媒体/`
   - 应该继续按 `媒体/播放会话`、`媒体/查看器`、`媒体/协作分发`、`媒体/上传` 拆分。
   - 禁止让任何“媒体运行时”式文件成为新的万能 owner，重新吞掉播放、查看器、分发、上传四条线。
18. `frontend/平台/`
   - 应该只承接浏览器能力、传输、存储、生命周期、调试兼容等平台适配。
   - 禁止平台适配绕开契约，成为前端访问后端的第二套 API 表面。
19. `frontend/后台/`、`frontend/操作台/`
   - 应该只做运营投影和操作编排，并且只能通过业务模块应用层读取或提交。
   - 禁止后台或操作台文件直接改写房间、消息、媒体业务真相。
20. `frontend/tests/`
   - 应该随着生产 owner 拆分同步迁移到对应模块测试目录，保留架构守卫。
   - 禁止测试继续引用旧总控路径，逼迫生产代码保留或恢复旧结构。

### 9.1.2 当前仍未满分的高风险汇聚点

上一轮收口已经解决了大量旧根文件问题，但这不等于当前结构已经满分。执行时必须先盯住下面四个高风险汇聚点，它们不拆掉，后续所有“真 DDD / 真六边形 / 真积木”结论都会继续漂：

1. `src/消息/应用.rs`
   - 应该把同步 / 异步消息成立链收成**同一条业务规则主链**，只在 transport / await 方式上分叉，不能在 owner、status、kind、width、height、preview 校验上复制两份。
   - 禁止继续以“冷路径和热路径调用方式不同”为理由维护两份业务规则。
2. `src/应用/mod.rs`
   - 应该继续缩到“真正跨上下文共享的最小端口、最小错误映射和最小公共校验”。
   - 禁止它继续充当身份、房间、消息、媒体、恢复、实时的总业务中心。
3. `src/适配/mod.rs`
   - 应该拆成按 bounded context 负责的 PostgreSQL outbound adapters / repositories，只留下极薄组合根做装配。
   - 禁止 `Pg仓储` 继续作为跨身份/房间/消息/媒体/恢复的总仓储壳长期存在。
4. `frontend/应用根/聊天应用内核.ts`
   - 应该继续把恢复补锚、实时补洞、阅读推进、平台桥接、本地状态折叠细节下沉到真实 owner。
   - 禁止它继续以“总装内核”名义持有跨恢复/实时/阅读推进/平台桥接/媒体会话的统一大编排壳。

这张映射表的目的不是把所有东西一次性硬搬完，而是先钉死“第一刀往哪切”。
禁止执行时再临场发明第二套拆分坐标系。

### 9.1.3 本轮正式 scope 与非目标

为了防止执行到一半再次翻案，本轮 scope 必须在动手前显式冻结。
冻结之后，不允许再把今天已经看到的遗漏包装成“后面新发现的问题”。

#### 必须纳入本轮正式 scope 的项目

1. **`总装` 命名残留全链路**
   - 不只是生产代码，还包括 `src/lib.rs`、`src/main.rs`、架构门禁脚本、前端测试、文档与路径断言。
   - 禁止只改生产代码，把门禁、测试和文档里的旧名字继续留着。
2. **生产宽 barrel 收口**
   - 本轮必须明确审查并处理 `frontend/媒体/index.ts`。
   - 它当前已经被多个真实生产 owner 消费，不能被降格成“只是导出习惯”。
3. **后端迁移壳契约收口**
   - 本轮必须明确处理 `src/实时/契约.rs`、`src/房间/契约.rs`、`src/消息/契约.rs`、`src/身份/契约.rs`。
   - 它们不能长期停留在“第一阶段先复用”的迁移态。
4. **门禁补齐**
   - 本轮必须把“总装命名长期滞留”“迁移壳长期滞留”“生产宽 barrel 长期滞留”都拉进正式失败项。

#### 本轮明确不作为主缺口的项目

这不是永久免检，而是为了避免本轮误伤 scope：

1. `frontend/平台/index.ts`
   - 当前可以被解释为稳定平台公开表面，不直接判成业务总入口。
   - 但它仍需在独立审计中给出存在理由。
2. `frontend/操作台/index.ts`
   - 当前不作为主缺口处理。
3. `frontend/操作台/附件入口/index.ts`
   - 当前不作为主缺口处理。

#### 防翻案规则

本轮 scope 一旦冻结，后续如果再宣称“还差一点”，只能来自下面三类新证据：

1. 新补的正式门禁失败；
2. 新发现的真实生产主链消费者；
3. 新的 graphify / 真实烟测反证。

禁止：

1. 禁止把今天已经确认的 `总装` 命名残留、`frontend/媒体/index.ts`、四个 `契约.rs`、门禁覆盖盲区，留到实现后再当成“新发现问题”。
2. 禁止 scope 漂移成“顺手把所有 barrel 都清零”或“顺手全仓改名”。
3. 禁止把“当前不列为主缺口”误解成“以后永不复查”。

### 9.2 正确迁移顺序

执行顺序必须先被文档锁死，再被 plan 锁死，最后才允许进入代码。

#### 9.2.0 先修文档，再修计划，再修代码

应该：

1. 先修权威 spec，把设计语言、命名裁决、公开表面裁决、迁移壳裁决和正式 scope 写死。
2. 再修执行 plan，把门禁、命名、公开表面、迁移壳、高密度 owner 的顺序排死。
3. 再开始代码实现，而且每一刀都要按 TDD：RED -> GREEN -> REFACTOR。
4. 最后做完成态审计：文档口径、代码形态、门禁、graphify、真实烟测一致后，才允许恢复满分说法。

禁止：

1. 禁止 spec 还没写死就直接开改。
2. 禁止只修生产代码、不修门禁、不修测试路径、不修文档。
3. 禁止为了赶进度，把多条结构线混成一次性大爆炸改造。

#### 第 0 步：冻结真相与验证基线

应该先冻结：

1. 后端哪些模块拥有业务真相。
2. 前端哪些模块拥有交互真相。
3. 现有稳定契约有哪些。
4. 现有哪些旧入口、旧旁路、旧假状态后面必须删。

同时冻结验证基线：

1. 后端测试基线。
2. 前端测试基线。
3. `1234b` 真实房间烟测基线。
4. 媒体播放、查看器、切换、恢复基线。

禁止：

1. 没基线就拆。
2. 只靠肉眼感觉判断“应该没坏”。

#### 第 1 步：先拆后端 owner

为什么先拆后端：

1. 后端是业务真相 owner。
2. 后端不稳，前端再怎么拆也只是围着模糊真相兜圈。

应该：

1. 先把 `契约` 收成稳定共享面。
2. 先把 `应用` 按业务块拆开。
3. 先把 `适配 / 外壳` 里偷做的业务判断推回 `应用 / 领域`。

禁止：

1. 后端真相还没收稳，就让前端先补一堆临时逻辑兜底。

#### 第 2 步：再拆前端平台污染

当前前端最危险的问题，不只是目录不整齐，而是平台能力和核心逻辑纠缠。

应该先从大内核里抽出去：

1. `HTMLElement`
2. 节点查询
3. 滚动容器
4. `localStorage`
5. 全屏 API
6. 可见性 API
7. 浏览器事件
8. 媒体元素直接控制

为什么先做这个：

1. 不先退平台，前端再怎么分模块也仍然是假核心。

禁止：

1. 保留平台 API 在核心里，只做表面目录拆分。

#### 第 3 步：优先收媒体 owner

应该优先收：

1. 播放会话。
2. 查看器。
3. 协作分发。
4. 上传。

为什么：

1. 媒体是最容易多 owner 打架的地方。
2. 媒体不先收，房间、时间线、恢复的后续拆分都会反复返工。

禁止：

1. 让唯一播放器继续拥有业务真相。
2. 让分发桥继续拥有播放裁决。

#### 第 4 步：再拆前端业务主轴

顺序建议：

1. 房间
2. 时间线
3. 输入框
4. 恢复

为什么：

1. 房间先定上下文。
2. 时间线再定主视图。
3. 输入框依赖前两者。
4. 恢复最后贴回体验态最稳。

#### 第 4.1 步：frontend 根业务旧文件已清零后的防回流规则

`frontend/` 根业务旧文件曾经需要按风险清零。
当前基线已经完成这一步：根目录不再保留 `聊天壳.ts`、`聊天应用内核.ts`、`聊天媒体编排.ts`、`房间*`、`媒体运行时.ts`、`实时会话运行时.ts`、`后台*.ts`、`状态.ts`、`传输.ts`、`存储.ts`、`应用运行时.ts`、`应用生命周期.ts` 这类业务或平台 owner 文件。

后续执行时，`frontend/` 的重点从“清根目录”变成“防回流和拆薄模块内部热点”：

1. 禁止为了旧 import 方便重新创建根目录旧路径包装文件。
2. 禁止测试继续断言旧根文件存在。
3. 禁止把 `应用根/聊天应用内核.ts`、`应用根/聊天壳.ts` 当成新的长期超级总控。
4. 禁止把房间、时间线、媒体、实时、恢复、后台、平台能力重新塞回一个跨模块文件。
5. 新增前端业务文件时，必须先选择业务模块，再选择层；根目录新增 `.ts` 默认失败。

如果未来再次出现前端根业务旧文件，必须按同一套顺序删除：

1. 先查清生产 import、测试 import 和门禁引用。
2. 先把引用改到真实 owner。
3. 再把测试和门禁从“旧根文件存在”改成“生产直连真实 owner，旧根文件不存在”。
4. 再删除根文件本身。
5. 最后跑该片测试和真实浏览器烟测，证明进房、时间线、恢复、实时、媒体、后台等受影响链路没有被删坏。

#### 第 5 步：最后才做目录落位和旧路清理

只有当前后端 owner、契约、依赖方向都稳定后，才做：

1. 改目录树。
2. 改模块名。
3. 合并旧文件。
4. 删除旧入口。
5. 删除历史胶水。

为什么：

1. 太早做目录美化，只是在给旧问题换新壳。

## 10. 测试、门禁与长期防漂移

### 10.1 按层测试，不许混着测

应该长期保留五类测试：

1. `领域` 测试：只测业务不变量，纯内存，不碰 IO。
2. `应用` 测试：用假端口测用例编排。
3. `契约` 测试：锁定命令、查询、事件、快照、错误码稳定性。
4. `适配` 测试：只测翻译是否正确。
5. `外壳` 测试：只测交互编排和展示流程。

为什么：

1. 不分层测试，就不知道失败是边界问题还是业务问题。
2. DDD 的价值必须落成可证明的不变量；只测接口能返回 200，不能证明业务模型没有贫血和漂移。

禁止：

1. 用 UI 测试代替业务真相测试。
2. 用集成大测试掩盖 owner 漂移。
3. 用 mock 绿化替代真实不变量测试；fake port 只服务应用编排验证，不能掩盖领域规则缺失。
4. 只测 DTO 映射，不测聚合行为和事件语义。

### 10.2 必须有架构边界测试

应该把下面这些边界写成自动失败规则：

1. 后端 `领域 / 应用` 禁止引入 `axum / sqlx / socketioxide / tokio` 这类壳层或运行时具体实现依赖；如果必须异步，应该停留在语言级 future、trait、端口抽象，禁止把 runtime 细节直接带进核心。
2. 前端核心禁止直接碰 `HTMLElement / localStorage / document / window / Fullscreen API`。
3. `契约` 禁止混入页面文案、组件状态、布局语义。
4. `实时` 层禁止偷做权限裁决。
5. `恢复` 层禁止宣布业务事实成立。
6. `播放器` 禁止变成媒体真相 owner。

为什么：

1. 这些东西只靠人工 code review 很容易漏。
2. 既然边界已经知道是高危区，就应该让工具自动守。

### 10.3 必须有跨模块真实主链烟测

应该长期守住这些真实链路：

1. 进入房间 -> 拉历史 -> 接增量。
2. 发送消息 -> 自己看到 -> 别人看到。
3. 上传媒体 -> 预览 -> 播放 -> 切换 owner。
4. 查看器打开 -> 关闭 -> 归位。
5. 全屏切换 -> 回退 -> 状态连续。
6. 断线 -> 重连 -> 继续收流。
7. 恢复进入 -> 只恢复体验态，不伪造业务成立性。

为什么：

1. 你这个项目的真实风险不在“能不能显示一个按钮”，而在链路交汇处。

禁止：

1. 只跑单元测试就宣布群聊主链安全。
2. 不做真实浏览器烟测就宣布媒体链路安全。

### 10.4 安全守护也必须落成测试

应该长期验证：

1. 伪造身份参数，后端必须拒绝。
2. 伪造权限动作，后端必须拒绝。
3. 重放旧事件，后端必须按契约处理或拒绝。
4. 篡改前端本地缓存，不能改变后端业务真相。
5. 即使前端代码被看光、被改壳、被重放，请求仍不能绕过后端裁决。

为什么：

1. 安全不是靠“感觉前后端解耦了”来证明的。
2. 既然本文已经把“默认前端已失守”当成前提，就必须真测。

### 10.5 文件和模块退化预警

应该建立以下预警：

1. 单文件持续膨胀到难以独立推理时，先拆 owner，再继续加功能。
2. 新功能禁止塞进“统一内核”“统一外壳”“公共助手”“临时协调器”。
3. `共享` 目录只允许放基础类型，禁止变垃圾场。
4. 跨模块直连一旦出现，必须解释为什么不能走契约。
5. 根目录业务文件数量必须进入门禁视野：除入口、总装、配置、类型声明、service worker 和确有必要的静态入口文件或开发工具脚本外，新增根目录 `.rs` / `.ts` 默认失败。
6. 待删除旧根文件必须有删除条件和禁止新增业务符号的检查；旧根文件只允许减少引用直到删除，不允许继续变厚。
7. 当一个根文件名已经带业务词，例如 `房间`、`媒体`、`实时`、`恢复`、`消息`、`身份`，必须在完成矩阵里记录它的目标模块和删除条件。
8. 对 `frontend/` 来说，只要某个根业务旧文件已经没有生产 import，只剩测试或门禁还在引用，它就必须进入同一轮删除清单，不能留到“以后再说”。

禁止：

1. 以“先凑合一下”为理由继续养大总管文件。
2. 以“这段只是 glue code”为理由放任跨边界偷权。
3. 以“这只是根目录旧文件”为理由继续往里面加业务分支。
4. 以“搬文件风险大”为理由无限期保留散落 owner。
5. 以前端根目录业务旧文件“还能跑”为理由拒绝删除。

## 11. 实现与验收时的总禁令

为了防止执行时漂移，本文最后把所有高频误判收成一组总禁令。

### 11.1 目录与重构禁令

1. 禁止把“改目录”当成“完成架构升级”。
2. 禁止大爆炸式全仓重命名。
3. 禁止旧新双活长期共存。
4. 禁止复制旧逻辑到新模块后不删旧路。
5. 禁止新增业务含义明确的根目录 `.rs` / `.ts` 文件；必须先选择业务模块，再选择层。
6. 禁止把历史散落文件标成“已经完成”，除非生产引用已切到真实 owner，旧根文件已删除，测试和门禁已改向真实 owner。
7. 禁止让测试继续锚定旧根文件结构，导致旧结构被测试反向保护。
8. 禁止把“方便 import”当成 `frontend/` 根业务旧文件长期保留理由。
9. 禁止 `frontend/` 用第二套根导出表面冒充模块公开入口。
10. 禁止为了“真 DDD”无依据新增 repository / service / manager / factory / interface 空壳。
11. 禁止为未来幻想提前引入 CQRS、事件溯源、插件框架、通用总线或跨模块抽象；只有边界压力被代码和测试证明后才允许。
12. 禁止把“减少屎山”误读成“到处拆小文件”；拆分必须让 owner 更清楚、主链更短、验证更准。
13. 禁止把“预算内、测试绿、暂时可用”当成高风险汇聚点长期存活的理由。

### 11.2 owner 禁令

1. 禁止前端拥有业务真相。
2. 禁止恢复拥有业务成立性。
3. 禁止实时拥有权限裁决。
4. 禁止播放器拥有媒体真相。
5. 禁止适配层和外壳层拥有领域裁决。
6. 禁止 repository、数据库行、缓存条目、连接状态、ack、播放器状态冒充业务事实。
7. 禁止总仓储壳拥有跨上下文 owner。
8. 禁止总编排壳拥有跨子域流程主权。

### 11.3 协作禁令

1. 禁止跨模块直连内部实现。
2. 禁止 `领域` 对 `领域` 的随意互相耦合。
3. 禁止 `外壳` 对 `外壳` 的跨模块协作。
4. 禁止绕开契约直接偷看底层数据结构。
5. 禁止 contract 泄漏某一端的页面流程、数据库结构、框架类型或临时兼容字段。
6. 禁止 domain event 退化成技术日志、任务通知或 adapter 成功回调。

### 11.4 安全禁令

1. 禁止信任前端传来的业务结论。
2. 禁止信任本地缓存中的业务权威状态。
3. 禁止把“连接成功”当“业务成功”。
4. 禁止把“广播成功”当“消息成立”。

### 11.5 验收禁令

1. 禁止没有新鲜测试就宣布完成。
2. 禁止没有真实浏览器烟测就宣布前端主链安全。
3. 禁止没有主链烟测就宣布媒体链路安全。
4. 禁止没有边界测试就宣布架构已经稳固。

## 12. 最终目标与完成判词

这套架构设计最终要达成的，不是“看起来高级”，而是下面这五件真实结果：

1. 每条业务事实都有唯一 owner。
2. 每个模块都能独立解释自己负责什么、不负责什么。
3. 前后端只通过稳定契约协作，不共享内部实现。
4. 复杂浏览器体验和后端业务真相各归其位，不互相偷权。
5. 根目录不再散落真正 owner；其中前端根目录只剩入口、service worker、构建配置、类型声明和必要静态入口或开发工具脚本，后端根目录只剩真实入口、薄组合根和必要配置。
6. 架构边界能靠测试、门禁和烟测长期守住，而不是靠个人记忆。
7. 核心业务模型有行为、有不变量、有事件语义，不是贫血字段袋子。
8. 外部成熟轮子被复用在 adapter / shell / infrastructure 边界内，不能篡夺领域主权。
9. 新增代码让主链更短、owner 更清楚、验证更直接，而不是让接口、映射、状态和兼容分支继续增殖。

最终完成判词应该是：

**后端拥有唯一业务真相，前端拥有唯一交互真相，模块按业务闭包，协作只过契约表面；前端根目录只剩入口、service worker、构建配置、类型声明和必要静态入口或开发工具脚本，后端根目录只剩真实入口、薄组合根和必要配置；领域模型有行为和不变量，应用层只编排，适配与外壳保持极薄，同步/异步主链不再复制同一业务规则，总仓储壳和总编排壳都被继续拆掉，真实主链有测试与门禁守护，成熟轮子只在外圈当二副，旧路、旧根文件、冗余垃圾和影子真相被持续删除而不是继续共存。**

在没有同时满足这几条之前，禁止把项目称为“已经完成真 DDD 洋葱积木架构升级”。
