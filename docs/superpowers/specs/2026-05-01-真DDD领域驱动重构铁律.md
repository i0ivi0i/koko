## 0. 总裁决

**`koko` 的目标不是“目录看起来像分层”，而是真正形成一套只有单一业务真相轴的后端核心、一套只拥有交互真相的前端核心、若干高内聚业务积木、极薄适配与外壳，以及只通过稳定契约协作的前后端边界。**

从这句话推出全部硬边界：

1. 应该先按业务模块切，再按 `领域 / 应用 / 契约 / 适配 / 外壳` 切。  
   禁止先全局横向切层，再把不相关业务揉进同层超级大文件。
2. 应该让后端成为唯一业务真相 owner。  
   禁止让前端、本地缓存、实时层、播放器、恢复链、仓储实现或接口层拥有业务成立性。
3. 应该让前端只拥有交互真相、体验真相和平台适配真相。  
   禁止让前端重建权限、成员、消息成立性、房间存在性、媒体成立性。
4. 应该让前后端只共享稳定契约，不共享核心实现。  
   禁止前端依赖后端内部实现，禁止后端依赖前端壳层流程。
5. 应该让每个模块只因一种业务变化而变化。  
   禁止“统一内核”“统一用例”“统一外壳”“公共助手”长期吸附多条 owner 线。
6. 应该把适配层和外壳层收薄，限定为翻译、投影、编排。  
   禁止 adapter / shell 偷做业务裁决。
7. 应该把真实主链、真实 owner、真实依赖方向写成测试和门禁。  
   禁止靠口头共识维护架构，禁止无门禁裸奔。

## 1. 为什么现在必须做这份设计

### 1.1 项目现实不是普通 CRUD

`koko` 不是一个静态网页，也不是一个低并发后台表单系统。它的真实目标是：

1. 公网万人实时图文视频群聊。
2. 稳定秒达，不崩，不靠侥幸。
3. 前端要在真实浏览器里承接房间切换、时间线滚动、恢复、查看器、全屏、播放、协作分发这些复杂交互。
4. 后端要在高并发下持续守住身份、房间、消息、媒体、恢复的业务真相。

这直接推出一个结论：

**这个项目如果没有清晰 owner、清晰边界、清晰契约，复杂度不会消失，只会换一种更脏的方式回流到大总管文件里。**

### 1.2 当前代码并不是“完全没分层”，但也远没到“真 DDD”

当前仓库已经有真实边界意识，不是纯假分层：

1. 后端已经存在 `domain / application / contract / adapter / shell` 的结构意图。
2. 后端里已经能看到仓储端口、适配实现、外壳翻译、领域不变量这些真边界。
3. 前端也已经开始收窄公开入口，并有架构边界测试意识。

但它还没有到“真 DDD 洋葱积木”的程度，原因很直接：

1. 后端仍有超大文件，例如 `src/用例.rs`、`src/外壳.rs`，说明模块颗粒还不够细。
2. 前端仍有大总控式核心，例如 `frontend/聊天应用内核.ts`，说明平台细节、交互协调、媒体逻辑、恢复逻辑仍然缠在一起。
3. 目录上虽然已经出现分层词汇，但跨模块 owner 还没有完全稳定收口。

如果继续沿着现在的惯性加功能，会发生三件事：

1. 新逻辑会继续往大文件、大类、大总控里堆。
2. 真实业务真相会在前端、本地缓存、恢复链、实时层之间长出第二份影子。
3. 维护者会越来越依赖“先补一下”“先兼容一下”“先别删旧的”，最后把系统养回屎山。

### 1.3 这份设计解决什么，不解决什么

本文负责：

1. 给出 `koko` 真 DDD 结构的 authoritative 目标形态。
2. 说清楚为什么必须这样切，哪些路径允许，哪些路径禁止。
3. 定义前后端 owner、模块 owner、层级 owner。
4. 给出防漂移、可迁移、可验收的落地顺序。

本文不负责：

1. 把当前代码伪装成已经完全实现。
2. 用漂亮目录树掩盖 owner 未收口的事实。
3. 给无边界的“顺手重构”开绿灯。

## 2. 这里说的“真 DDD / 真洋葱 / 真积木”到底是什么意思

### 2.1 真 DDD 不是给文件取了几个高级名字

真 DDD 的核心不是“文件夹叫 `领域/应用` 就算数”，而是：

1. 每条业务事实都有唯一 owner。
2. 每个模块都只负责一类业务变化。
3. 跨模块协作只通过稳定语义，而不是偷看彼此肚子里的实现。

应该这样理解：

- `领域` 决定业务上什么成立，什么不成立。
- `应用` 决定命令怎么流转，查询怎么汇总，事件怎么编排。
- `契约` 决定跨边界时双方说什么话。
- `适配` 决定外部世界怎么翻译进来、怎么翻译出去。
- `外壳` 决定展示和交互怎么编排。

禁止这样理解：

- 把 `领域` 当工具函数堆放区。
- 把 `应用` 当总控脚本。
- 把 `契约` 当所有类型的大杂烩。
- 把 `适配` 当偷放业务判断的后门。
- 把 `外壳` 当“反正 UI 特殊，所以可以随便写”的免责区。

### 2.2 “洋葱只有一个真核心”不等于“只能有一个巨型核心文件”

这句话必须说准。

“只有一个真核心”真正表达的是：

1. 整个系统只有一套业务真相主轴。
2. 同一条业务事实不能在多个地方各判一次。
3. 前后端不能各自长出一套互相不认的事实体系。

它**不**表达下面这些错误意思：

1. 整个仓库只能有一个超级大核心文件。
2. 所有业务都必须塞进一个“聊天总核心”。
3. 只要能在一个类里全控，就叫“单核心更纯”。

正确落法是：

**全局只有一套业务真相主轴，但每个业务模块内部各有自己的小洋葱核心。**

这才既符合“唯一真相”，又不会把项目重新压回单个超大总控。

### 2.3 真积木不是碎文件，而是高内聚、可替换、可理解

积木式架构追求的是：

1. 每一块积木做一件清楚的事。
2. 别人通过清楚接口使用它。
3. 别人不需要知道它内部怎么长。

应该拆成“小而完整的业务块”。  
禁止拆成“名字很多、职责更乱的碎片文件”。

所以本文的结构原则不是：

- 文件越多越高级。

而是：

- 模块边界越清楚越高级。
- 每个模块越能独立推理越高级。
- 每条依赖方向越单纯越高级。

## 3. 单一真相轴：后端拥有业务真相，前端拥有交互真相

### 3.1 后端为什么必须拥有唯一业务真相

后端应该拥有这些真相：

1. 身份是否成立。
2. 房间是否存在。
3. 成员是否有资格。
4. 消息是否成立。
5. 媒体是否提交、是否可读、是否可分发。
6. 恢复时哪些事实可以信，哪些只能辅助。

为什么必须这样做：

1. 前端天然可被阅读、逆向、篡改、重放。
2. 浏览器本地状态天然不可信。
3. 实时层和适配层天然更接近 IO，最容易为了“先跑通”偷放判断。

所以必须立铁律：

**默认前端已经失守，后端仍必须守住业务真相。**

应该：

1. 把权限、成员资格、消息成立性、媒体成立性全部留在后端 `领域 / 应用`。
2. 把所有最终裁决结果都通过稳定契约返回或推送给前端。

禁止：

1. 把“前端先判断一下”当作长期真相。
2. 把“本地缓存里有，就先算成立”当作业务逻辑。
3. 把“实时连接已经通了”误判为“业务事实已经成立”。

### 3.2 前端为什么也有“真核心”，但不是业务核心

前端并不是完全没有核心。  
它有自己的真核心，但那是**交互核心和体验核心**，不是业务核心。

前端应该拥有：

1. 当前正在看哪个房间。
2. 当前时间线可见窗口和滚动锚点是什么。
3. 当前是否打开查看器、是否有播放意图、是否进入全屏。
4. 当前草稿、回复目标、输入中附件是什么。
5. 当前本地恢复态能帮助恢复哪些体验位置。

为什么前端需要这些 owner：

1. 这些是浏览器应用体验的一部分。
2. 后端不应该知道你是弹窗、侧栏、查看器还是全屏。
3. 不把这些交给前端，所有交互都会被后端展示流程反向绑架。

应该：

1. 让前端只判断“我怎么交互、我怎么展示、我怎么编排体验”。
2. 让前端通过契约接收后端裁决后的业务事实。

禁止：

1. 让前端自己判“这个房间是不是存在”。
2. 让前端自己判“这条消息算不算成立”。
3. 让前端自己判“我是不是这个媒体的有效分发者”。

### 3.3 安全收益来自“被破解后也拿不到主脑”

前后端解耦不是神话，不能阻止攻击发生。  
它真正的安全价值是：

1. 缩小攻击面。
2. 降低前端被逆向后的收益。
3. 防止前端壳被改掉以后，系统的业务真相也跟着被篡改。

应该：

1. 假设前端 JS、HTML、网络请求都可以被黑客看见和重放。
2. 把所有重要权限和业务裁决都放在后端核验。

禁止：

1. 因为“前端看起来已经限制了”就放松后端判定。
2. 把接口参数当作已被证明的业务事实。

## 4. 总结构原则：先按业务模块切，再按层切

### 4.1 为什么业务模块必须先于层

如果先全局按层切，很容易长成下面这种形态：

1. 一个超大的统一 `用例`。
2. 一个超大的统一 `外壳`。
3. 一个超大的统一 `聊天内核`。

这种结构表面整齐，实际最危险，因为：

1. 不同业务很快会混进同一个大文件。
2. 一个修改会牵动越来越多不相关责任。
3. Review 很难看出 owner 是否漂移。

所以本文明确裁决：

**目录树首先回答“这是哪个业务模块”，然后才回答“它在这个业务模块里属于哪一层”。**

应该：

1. 先把身份、房间、消息、媒体、恢复、实时这些业务块切清楚。
2. 再在每个块里放 `领域 / 应用 / 契约 / 适配 / 外壳`。

禁止：

1. 继续维持跨业务的超级 `用例.rs`。
2. 继续维持跨业务的超级 `聊天应用内核.ts`。
3. 用“公共逻辑很多”当借口继续把不相关业务揉在一起。

2. 让 `实时 / 恢复 / 后台运营` 成为支撑模块，但不反客为主。

2. 让 `外壳` 目录拥有治理、判权、真相裁决。
3. 让 `后台运营` 为了图快越过业务语义边界直接成为另一套业务入口。

## 5. 后端模块详细职责

### 5.1 身份

身份模块应该拥有：

1. 会话、匿名身份、设备身份恢复的业务真相。
2. 身份令牌和身份快照的稳定契约。

为什么：

1. 身份是一切权限和成员资格判断的前提。
2. 如果身份真相分散在多个模块，后面所有业务都会变脏。

禁止：

1. 房间模块私自改写身份成立性。
2. 前端自己创造业务身份。

### 5.2 房间

房间模块应该拥有：

1. 房间存在性。
2. 房间成员资格。
3. 房间可见性与加入规则。

为什么：

1. 房间是消息、媒体、恢复的上下文。
2. 不把房间边界钉死，消息和媒体都会偷做房间判断。

禁止：

1. 消息模块直接替代房间判成员资格。
2. 实时层以“已经订阅成功”为由跳过房间判定。

### 5.3 消息

消息模块应该拥有：

1. 消息成立性。
2. 消息事件顺序语义。
3. 附件引用与消息关系。

为什么：

1. 消息是群聊最核心的业务事实之一。
2. 一旦消息成立逻辑被广播层、恢复层或前端分走，系统就会长出第二真相。

禁止：

1. 广播成功与否影响消息是否成立。
2. 恢复补洞逻辑补成第二个消息写入口。

### 5.4 媒体

媒体不能再粗放地当成一个“媒体大桶”。  
它必须按真实 owner 分为：

1. 上传。
2. 资产。
3. 协作分发。
4. 内容读取。

为什么：

1. 媒体复杂度远高于图片附件上传这种简单场景。
2. 上传成功、资产就绪、可读、可播、可分发，这些不是同一件事。
3. 如果不拆，播放器、分发器、恢复链、接口层会互相偷权。

禁止：

1. 让播放器决定媒体业务成立性。
2. 让分发层替代上传提交真相。
3. 让读取旁路变成第二字节主链。

### 5.5 实时

实时模块应该拥有：

1. 连接事实。
2. 订阅事实。
3. 广播运行态结果。

为什么：

1. 实时层需要自己的运行事实，否则无法可观测。
2. 但这些事实不是业务真相，只是运行真相。

应该：

1. 让实时层管理连接、订阅、广播、背压、取消、重试。
2. 让业务是否合法仍由 `应用 / 领域` 裁决。

禁止：

1. 在实时层判权限。
2. 在实时层宣布消息成立。
3. 在实时层把“socket 连上了”冒充成“业务已经成功”。

### 5.6 恢复

恢复模块应该拥有：

1. 恢复锚点。
2. 增量补洞。
3. 恢复查询编排。

为什么：

1. 恢复非常重要，但它本质上是“追平事实”的辅助手段，不是事实 owner。
2. 恢复最容易因为“为了用户体验”偷偷变成第二真相。

禁止：

1. 恢复模块自己宣布消息或成员资格成立。
2. 恢复把本地旧缓存升格成业务权威来源。

## 6. 前端模块详细职责

### 6.1 身份接入

身份接入模块应该拥有：

1. 前端侧会话接入和恢复流程。
2. 身份令牌的持有与重放。

为什么：

1. 前端必须能承接启动和恢复体验。
2. 但它只能持有令牌，不能发明身份业务真相。

禁止：

1. 前端根据本地缓存自创业务身份。
2. 前端根据旧页面状态绕过后端重新核验。

### 6.2 房间

房间模块应该拥有：

1. 当前房间选择。
2. 房间列表交互状态。
3. 房间切换体验规则。

为什么：

1. 房间切换是整个浏览器应用的上下文切换器。
2. 它属于前端交互真相，不应被时间线或媒体模块反向接管。

禁止：

1. 时间线直接决定房间业务存在性。
2. 查看器或播放器越权修改房间真相。

### 6.3 时间线

时间线模块应该拥有：

1. 可见窗口。
2. 滚动锚点。
3. 选中消息。
4. 未读定位。

为什么：

1. 这些都是高频交互事实，必须独立收口。
2. 不独立收口，就会继续混入大内核和 DOM 查询逻辑。

禁止：

1. 时间线直接控制 `WebTorrent`。
2. 时间线直接决定媒体业务成立性。

### 6.4 输入框

输入框模块应该拥有：

1. 草稿。
2. 回复目标。
3. 本地附件选择态。

为什么：

1. 输入相关状态有清楚的交互闭环。
2. 不独立出去，就会继续散落在房间、时间线和媒体逻辑之间。

禁止：

1. 输入框直接拥有消息成立性。
2. 输入框把本地选中的附件直接视作后端已提交媒体。

### 6.5 媒体

前端媒体必须拆成四块：

1. 播放会话。
2. 查看器。
3. 协作分发。
4. 上传。

为什么：

1. 播放、查看、字节分发、文件上传是四种不同 owner。
2. 不拆开就会出现“播放器既是界面又是业务裁判又是分发 owner”的混乱局面。

应该：

1. 让唯一播放器只是壳。
2. 让播放会话模块拥有播放意图、拥有者切换、全屏意图。
3. 让查看器模块拥有查看目标和缩放状态。
4. 让协作分发模块只处理 `WebTorrent` 等字节协作适配。

禁止：

1. 播放器壳拥有 source 真相。
2. 分发桥拥有播放裁决。
3. 恢复链拥有媒体成立性。

### 6.6 实时、恢复、平台

这三者都很重要，但都不该成为前端业务总控。

实时应该拥有：

1. 连接器。
2. 订阅器。
3. 重连器。
4. 事件分发。

恢复应该拥有：

1. 本地恢复锚点。
2. 临时恢复态。

平台应该拥有：

1. 浏览器能力。
2. 可见性。
3. 全屏。
4. 剪贴板。
5. 文件选择。

禁止：

1. `平台` 渗进 `领域 / 应用`。
2. `恢复` 直接宣布业务成功。
3. `实时` 直接判案。

## 7. 前后端真正解耦的硬边界

### 7.1 什么耦合允许存在

前后端不是“完全没耦合”，而是只能保留下面三类耦合：

1. 业务语义耦合：房间、消息、成员、媒体、恢复这些统一语言。
2. 契约耦合：命令、查询、事件、快照、错误码。
3. 时序耦合：先入房，再拉历史，再接增量这类明确业务流程。

为什么：

1. 完全零耦合在协作系统里是伪命题。
2. 真正有害的不是耦合本身，而是实现细节耦合和多处真相耦合。

### 7.2 什么耦合绝对禁止

1. 禁止前端依赖后端内部模块、数据库表、仓储实现、广播实现。
2. 禁止后端依赖前端展示流程、组件状态、布局概念。
3. 禁止前端重建业务真相。
4. 禁止适配层和外壳层偷放业务裁决。
5. 禁止契约混入页面文案、按钮语义、布局语义。
6. 禁止本地缓存升格成业务权威来源。

### 7.3 正确的数据流

正确链路必须始终是：

1. 前端外壳把浏览器动作翻译成应用命令。
2. 前端应用通过稳定契约向后端表达意图。
3. 后端外壳接收并翻译请求。
4. 后端 `应用 / 领域` 裁决业务真相。
5. 后端适配落库、广播、调用外部基础设施。
6. 后端把结果按契约返回或推送。
7. 前端适配接收并翻译。
8. 前端应用更新交互真相。
9. 前端外壳负责渲染与体验编排。

一句话钉死：

**前端发出意图，后端裁决事实，前端把事实变成体验。**

禁止：

1. 前端直接把临时本地态当成已裁决事实。
2. 后端为了迎合某个壳层流程把业务语义写歪。

## 8. 模块之间怎样才算高内聚、低耦合

### 8.1 高内聚标准

高内聚不是“相关代码放在一起”这么简单。  
真正标准是：

**一个模块只因为一种业务变化而变化。**

例如：

1. 房间规则变化，主要影响房间模块。
2. 消息成立逻辑变化，主要影响消息模块。
3. 查看器交互变化，主要影响查看器模块。

禁止：

1. 同一个变更同时必须改五个无关模块才能成立。
2. 一个模块同时负责房间、消息、媒体、恢复四种不同变化。

### 8.2 低耦合标准

低耦合不是“完全互不认识”。  
真正标准是：

**跨模块只能通过稳定表面协作，不能摸对方内部器官。**

应该：

1. 跨模块只看契约或端口。
2. 让别人知道“你提供什么能力”，而不是“你内部怎么实现”。

禁止：

1. `消息` 直接读 `房间` 仓储实现。
2. `媒体` 直接改 `消息` 聚合内部状态。
3. `时间线` 直接操作 `WebTorrent` 细节。

### 8.3 后端允许的依赖主轴

后端建议主轴：

**身份 -> 房间 -> 消息 -> 媒体**

支撑模块：

- `实时`
- `恢复`
- `后台运营`

允许：

1. `房间` 依赖 `身份` 的稳定契约或端口。
2. `消息` 依赖 `房间` 的稳定契约或端口。
3. `媒体` 依赖 `消息 / 房间` 的稳定契约或端口。
4. `恢复` 依赖 `房间 / 消息 / 媒体` 的查询契约。
5. `实时` 依赖各业务模块事件契约，但业务模块不依赖 `实时` 内部。

禁止：

1. `消息` 直连 `房间` 仓储实现。
2. `媒体` 直连 `消息` 内部聚合状态。
3. `实时` 反向成为权限 owner。

### 8.4 前端允许的依赖主轴

前端建议主轴：

**身份接入 -> 房间 -> 时间线 -> 输入框 / 媒体**

支撑模块：

- `实时`
- `恢复`
- `平台`

允许：

1. `房间` 看 `身份接入` 契约。
2. `时间线` 看 `房间` 契约。
3. `输入框` 看 `房间` 与媒体上传契约。
4. `媒体播放会话 / 查看器` 看时间线暴露出的媒体快照契约。
5. `恢复` 只恢复体验态。

禁止：

1. `媒体播放会话` 直接读本地存储。
2. `恢复` 直接判权限。
3. `平台` 进入领域对象。

### 8.5 层级依赖方向

这是全文最重要的硬约束之一：

1. `领域` 只能看本模块领域和极少量共享基础类型。
2. `应用` 只能看本模块领域、本模块契约、别的模块契约或端口。
3. `契约` 只能看共享基础类型。
4. `适配` 只能实现应用要求，不能发明业务真相。
5. `外壳` 只能做交互和展示编排，不能偷做领域裁决。

一句话钉死：

**跨模块协作发生在“应用对契约/端口”，不是“领域对领域”，更不是“外壳对外壳”。**

## 9. 迁移怎么落地，才不会把系统拆崩

### 9.1 先钉真相和契约，再搬目录

迁移顺序绝不能是“先把目录改漂亮”。  
正确顺序必须是：

1. 先钉死真相 owner。
2. 先钉死契约边界。
3. 先收依赖方向。
4. 再做文件落位。
5. 最后删旧路。

为什么：

1. 目录树只是外观，owner 才是内核。
2. 如果 owner 没钉死，搬文件只是把脏耦合搬到新地址。

禁止：

1. 大爆炸改目录。
2. 先全仓重命名再慢慢找逻辑。
3. 复制一份旧逻辑到新目录里长期双活。

### 9.2 正确迁移顺序

#### 第 0 步：冻结真相与验证基线

应该先冻结：

1. 后端哪些模块拥有业务真相。
2. 前端哪些模块拥有交互真相。
3. 现有稳定契约有哪些。
4. 现有哪些旧入口、旧旁路、旧假状态后面必须删。

同时冻结验证基线：

1. 后端测试基线。
2. 前端测试基线。
3. `1234b` 真实房间烟测基线。
4. 媒体播放、查看器、切换、恢复基线。

禁止：

1. 没基线就拆。
2. 只靠肉眼感觉判断“应该没坏”。

#### 第 1 步：先拆后端 owner

为什么先拆后端：

1. 后端是业务真相 owner。
2. 后端不稳，前端再怎么拆也只是围着模糊真相兜圈。

应该：

1. 先把 `契约` 收成稳定共享面。
2. 先把 `应用` 按业务块拆开。
3. 先把 `适配 / 外壳` 里偷做的业务判断推回 `应用 / 领域`。

禁止：

1. 后端真相还没收稳，就让前端先补一堆临时逻辑兜底。

#### 第 2 步：再拆前端平台污染

当前前端最危险的问题，不只是目录不整齐，而是平台能力和核心逻辑纠缠。

应该先从大内核里抽出去：

1. `HTMLElement`
2. 节点查询
3. 滚动容器
4. `localStorage`
5. 全屏 API
6. 可见性 API
7. 浏览器事件
8. 媒体元素直接控制

为什么先做这个：

1. 不先退平台，前端再怎么分模块也仍然是假核心。

禁止：

1. 保留平台 API 在核心里，只做表面目录拆分。

#### 第 3 步：优先收媒体 owner

应该优先收：

1. 播放会话。
2. 查看器。
3. 协作分发。
4. 上传。

为什么：

1. 媒体是最容易多 owner 打架的地方。
2. 媒体不先收，房间、时间线、恢复的后续拆分都会反复返工。

禁止：

1. 让唯一播放器继续拥有业务真相。
2. 让分发桥继续拥有播放裁决。

#### 第 4 步：再拆前端业务主轴

顺序建议：

1. 房间
2. 时间线
3. 输入框
4. 恢复

为什么：

1. 房间先定上下文。
2. 时间线再定主视图。
3. 输入框依赖前两者。
4. 恢复最后贴回体验态最稳。

#### 第 5 步：最后才做目录落位和旧路清理

只有当前后端 owner、契约、依赖方向都稳定后，才做：

1. 改目录树。
2. 改模块名。
3. 合并旧文件。
4. 删除旧入口。
5. 删除历史胶水。

为什么：

1. 太早做目录美化，只是在给旧问题换新壳。

## 10. 测试、门禁与长期防漂移

### 10.1 按层测试，不许混着测

应该长期保留五类测试：

1. `领域` 测试：只测业务不变量，纯内存，不碰 IO。
2. `应用` 测试：用假端口测用例编排。
3. `契约` 测试：锁定命令、查询、事件、快照、错误码稳定性。
4. `适配` 测试：只测翻译是否正确。
5. `外壳` 测试：只测交互编排和展示流程。

为什么：

1. 不分层测试，就不知道失败是边界问题还是业务问题。

禁止：

1. 用 UI 测试代替业务真相测试。
2. 用集成大测试掩盖 owner 漂移。

### 10.2 必须有架构边界测试

应该把下面这些边界写成自动失败规则：

1. 后端 `领域 / 应用` 禁止引入 `axum / sqlx / socketioxide / tokio` 等壳层依赖。
2. 前端核心禁止直接碰 `HTMLElement / localStorage / document / window / Fullscreen API`。
3. `契约` 禁止混入页面文案、组件状态、布局语义。
4. `实时` 层禁止偷做权限裁决。
5. `恢复` 层禁止宣布业务事实成立。
6. `播放器` 禁止变成媒体真相 owner。

为什么：

1. 这些东西只靠人工 code review 很容易漏。
2. 既然边界已经知道是高危区，就应该让工具自动守。

### 10.3 必须有跨模块真实主链烟测

应该长期守住这些真实链路：

1. 进入房间 -> 拉历史 -> 接增量。
2. 发送消息 -> 自己看到 -> 别人看到。
3. 上传媒体 -> 预览 -> 播放 -> 切换 owner。
4. 查看器打开 -> 关闭 -> 归位。
5. 全屏切换 -> 回退 -> 状态连续。
6. 断线 -> 重连 -> 继续收流。
7. 恢复进入 -> 只恢复体验态，不伪造业务成立性。

为什么：

1. 你这个项目的真实风险不在“能不能显示一个按钮”，而在链路交汇处。

禁止：

1. 只跑单元测试就宣布群聊主链安全。
2. 不做真实浏览器烟测就宣布媒体链路安全。

### 10.4 安全守护也必须落成测试

应该长期验证：

1. 伪造身份参数，后端必须拒绝。
2. 伪造权限动作，后端必须拒绝。
3. 重放旧事件，后端必须按契约处理或拒绝。
4. 篡改前端本地缓存，不能改变后端业务真相。
5. 即使前端代码被看光、被改壳、被重放，请求仍不能绕过后端裁决。

为什么：

1. 安全不是靠“感觉前后端解耦了”来证明的。
2. 既然本文已经把“默认前端已失守”当成前提，就必须真测。

### 10.5 文件和模块退化预警

应该建立以下预警：

1. 单文件持续膨胀到难以独立推理时，先拆 owner，再继续加功能。
2. 新功能禁止塞进“统一内核”“统一外壳”“公共助手”“临时协调器”。
3. `共享` 目录只允许放基础类型，禁止变垃圾场。
4. 跨模块直连一旦出现，必须解释为什么不能走契约。

禁止：

1. 以“先凑合一下”为理由继续养大总管文件。
2. 以“这段只是 glue code”为理由放任跨边界偷权。

## 11. 实现与验收时的总禁令

为了防止执行时漂移，本文最后把所有高频误判收成一组总禁令。

### 11.1 目录与重构禁令

1. 禁止把“改目录”当成“完成架构升级”。
2. 禁止大爆炸式全仓重命名。
3. 禁止旧新双活长期共存。
4. 禁止复制旧逻辑到新模块后不删旧路。

### 11.2 owner 禁令

1. 禁止前端拥有业务真相。
2. 禁止恢复拥有业务成立性。
3. 禁止实时拥有权限裁决。
4. 禁止播放器拥有媒体真相。
5. 禁止适配层和外壳层拥有领域裁决。

### 11.3 协作禁令

1. 禁止跨模块直连内部实现。
2. 禁止 `领域` 对 `领域` 的随意互相耦合。
3. 禁止 `外壳` 对 `外壳` 的跨模块协作。
4. 禁止绕开契约直接偷看底层数据结构。

### 11.4 安全禁令

1. 禁止信任前端传来的业务结论。
2. 禁止信任本地缓存中的业务权威状态。
3. 禁止把“连接成功”当“业务成功”。
4. 禁止把“广播成功”当“消息成立”。

### 11.5 验收禁令

1. 禁止没有新鲜测试就宣布完成。
2. 禁止没有真实浏览器烟测就宣布前端主链安全。
3. 禁止没有主链烟测就宣布媒体链路安全。
4. 禁止没有边界测试就宣布架构已经稳固。

---

## 12. 最终目标与完成判词

这套架构设计最终要达成的，不是“看起来高级”，而是下面这五件真实结果：

1. 每条业务事实都有唯一 owner。
2. 每个模块都能独立解释自己负责什么、不负责什么。
3. 前后端只通过稳定契约协作，不共享内部实现。
4. 复杂浏览器体验和后端业务真相各归其位，不互相偷权。
5. 架构边界能靠测试、门禁和烟测长期守住，而不是靠个人记忆。

最终完成判词应该是：

**后端拥有唯一业务真相，前端拥有唯一交互真相，模块按业务闭包，协作只过契约表面，适配与外壳保持极薄，真实主链有测试与门禁守护，旧路和影子真相被持续删除而不是继续共存。**

在没有同时满足这几条之前，禁止把项目称为“已经完成真 DDD 洋葱积木架构升级”。
