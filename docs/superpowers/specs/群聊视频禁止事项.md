## 设计总纲：从“修换壳”转向“稳定表面槽”

本轮自动播放调查的起点不是“再修一个闪烁点”，而是用户在真实群聊里反复观察到同一类系统性症状：滚动时自动播放抽搐、画面跳来跳去；正在播放的 A 视频滑走后退成黑卡或占位，而不是停在刚才那一帧；视频预览入场有明显空窗。这些现象看起来分散，底层却指向同一件事：播放事实、表面事实、DOM 宿主事实和媒体源事实没有被一条稳定领域链路统一裁决。

按第一性原理，用户要的不是 `poster / preview / canonical / frozen / placeholder` 这些壳之间切得足够快，而是同一条视频在同一张卡片里始终保持连续表达。既然可见换壳本身容易制造 bug，正确问题就不再是“怎么把换壳修稳”，而是“为什么还允许可见换壳存在”。因此本文把后续方向收成一个核心设计：时间线视频卡片只保留一个稳定 `VideoSurfaceSlot`，壳层能力可以在内部切换，但用户可见层必须由同一个表面槽连续表达。

按 DDD 领域驱动开发看，`poster`、`preview video`、`canonical host`、`frozen frame`、`guard` 都不是领域概念，它们只是表达能力；真正的领域概念是“视频播放会话”“自动播 owner”“播放连续性阶段”“稳定表面槽”和“WebTorrent 正式源”。所以后续修复不能继续让 `附件渲染.ts` 靠一堆分散分支拼出体验。渲染层只应该消费领域快照：谁是 owner、当前 source 是否成立、是否已有可表达帧、连续性阶段是什么，然后把这些事实投影到同一个表面槽。

当前项目已经有状态机，后续不是新造第二套状态机。`frontend/媒体运行时.ts` 已经用 XState 承担 `candidate -> pendingOwner -> settledOwner -> release` 等运行时事实；`frontend/媒体/全局丝滑自动播.ts` 已经承担 `coldPlaceholder / hiddenHandoff / visible / pausedFrame / viewerHandoff / fullscreenHandoff / retired` 等播放连续性阶段判断。真正要做的是把现有状态机的输出提升为唯一 UI 投影真相，查清哪些事实仍被 DOM、消息窗、渲染分支、预览缓存或播放器挂载逻辑偷写。

成熟轮子的边界也要讲清。TanStack Virtual 适合管理大列表虚拟窗口、测量和滚动范围；XState v5 适合表达复杂状态转移；Video.js v10 适合承担唯一播放器能力；WebTorrent 适合承担正式媒体字节、streamURL、piece 缓存和协作分发；IntersectionObserver 与 requestVideoFrameCallback 适合输入浏览器事实。它们都是应该复用的基础设施，但没有一个能替项目直接完成“群聊消息流 + WebTorrent + 唯一播放器 + 滑走保帧 + 滑回续播 + 查看器/全屏归位”的业务连续性协议。后续执行要站在这些轮子肩膀上，而不是重复手搓基础设施，也不能幻想存在一个全包自动播轮子。

参考资料用于支撑分层边界，而不是替代本项目裁决：[TanStack Virtual](https://tanstack.com/virtual/v3/docs/introduction) 官方文档说明它是 headless virtualizer，负责窗口和测量；[XState v5](https://stately.ai/docs) 官方文档说明它适合状态机、actor、transition、guard 和 action；[Video.js Player API](https://docs.videojs.com/player) 覆盖播放器 source、currentTime、ready、dispose 等能力；[WebTorrent API](https://webtorrent.io/docs) 覆盖浏览器端 streamURL、createServer/service worker、torrent/file 流式能力；[MDN IntersectionObserver](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API) 说明它是可见性观测 API；[MDN requestVideoFrameCallback](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback) 说明它用于接收视频帧提交回调；web.dev 的[虚拟列表](https://web.dev/articles/virtualize-long-lists-react-window)、[视频性能](https://web.dev/learn/performance/video-performance)和[懒加载视频](https://web.dev/articles/lazy-loading-video)文章共同指向同一个原则：浏览器里同时活着的重对象必须被窗口、预算和生命周期控制。

调查方法也必须防漂移。第一轮先做事实归属表，沿 `几何观测 -> 候选编排 -> pending owner -> settled owner -> 媒体运行时 -> 全局唯一播放器 -> 附件表面 -> 虚拟列表 -> WebTorrent 源` 查清每个事实字段的当前写入者和正确 owner。第二轮用真实房间 `1234b` 做浏览器反证，覆盖慢滚、快滚、来回滚、滑走滑回、切视频、查看器打开关闭，观察 owner 序列、surface 阶段、DOM mutation、播放器数量、帧提交、正式源和错误日志。第三轮才定位结构修复层：owner 抖动改运行时，surface 错投影改连续性阶段和稳定表面槽，player 迁移断裂改唯一播放器事务，source 生命周期断裂改媒体会话和 WebTorrent 协作链。

这份设计的最终目的，是让后续执行者看到前因后果后不再回到局部补丁：不是给黑卡加一个兜底图，不是给滚动加一个 timeout，不是让每张卡片保一颗 video，也不是绕开 WebTorrent 找快源。正确的收口路径是复用成熟基础设施，把现有状态机事实压回领域 owner，把可见换壳消灭成稳定表面槽，把浏览器证据反向校验到状态机不变量，直到真实用户滚动时看到的是连续视频体验，而不是系统内部状态分裂的残影。

## 0. 采访裁决

1. 禁止把本轮工作继续理解成局部 bugfix；裁决是全链路调查并疏通自动播放底层逻辑。
2. 禁止在真实浏览器体验和状态机不变量之间二选一；裁决是两者同时作为验收门禁。
3. 禁止按“先浏览器取证、再临时补状态”执行；裁决是先状态机和不变量收口，再真实浏览器取证。
4. 禁止只循环一次就宣布复杂自动播问题结束；裁决是状态机收口和浏览器取证多轮往返。
5. 禁止把方案 1 和方案 2 平行推进成两条路线；裁决顺序是先方案 2，再方案 1，再按证据回到方案 2。
6. 禁止新建第二份调查 spec；裁决是把第一性原理、成熟轮子边界和调查方法融合进本文。
7. 禁止把成熟轮子调查当成可选资料；裁决是动手前必须查官方实践和成熟热门轮子。
8. 禁止因为没有全包轮子就回到全手搓；裁决是复用每层成熟轮子，只自建本项目的连续性协议。
9. 禁止围绕“怎么把换壳修稳”继续设计；裁决是从模型上消灭可见换壳。
10. 禁止把稳定表面槽理解成每张卡片一颗 live video；唯一 live player 和单路解码红线不变。
11. 禁止让 `附件渲染.ts` 继续靠分散分支表达体验；裁决是它只投影状态机给出的表面模式。
12. 禁止把调查设计和代码修复混成一步；裁决是先把本文和执行计划审清，再进入代码修改。
13. 禁止把“先方案 2”理解成重写第二套状态机；裁决是以现有 `全局丝滑自动播.ts`、`媒体运行时.ts` 和 owner 链为收口对象。
14. 禁止把成熟轮子调查写成泛泛资料；裁决是必须写清复用什么、不复用什么、为什么不迁移或新增。
15. 禁止把多轮循环理解成无期限试错；每轮都必须产出失败归类、不变量修正、浏览器证据和下一轮退出条件。

## 1. 播放真相

1. 禁止同一条视频在群聊时间线、查看器和全屏之间拥有多套播放真相。
2. 禁止把自动播放、预览、续播、查看器和全屏拆成互相不知道的局部流程。
3. 禁止让几何观测结果直接拥有播放事实；几何只能提供候选，不能取代状态机裁决。
4. 禁止让 DOM 节点私有状态成为播放位置、播放画面或播放 owner 的最终真相。
5. 禁止为了局部稳定新增第二播放器、第二播放链路、第二位置存储或第二视觉缓存。
6. 禁止把 WebTorrent 主链之外的冷源、临时源或兜底源包装成正式播放体验。
7. 禁止让自动播 owner、播放器 owner、查看器 owner、表面 owner 各自成为独立真相；它们只能来自同一条会话链。
8. 禁止把保存 `currentTime` 误判成续播成立；续播必须同时包含源一致、位置有效、帧可表达和表面连续。

## 2. 滚动稳定

1. 禁止滚动过程中的瞬时候选抖动立刻触发 owner 释放、播放器迁移或可见表面重建。
2. 禁止在用户连续滚动时让同一颗播放器在多个候选之间来回抢占。
3. 禁止把滚动中的短暂无候选窗口表达成视频播放结束、播放失败或冷启动。
4. 禁止用过度敏感的阈值、排序、计时器或 DOM 清理制造自动播放抽搐。
5. 禁止在滚动热路径里扫描整段历史消息、全量视频附件或不可见无关表面。
6. 禁止为了“更积极自动播”牺牲 owner 粘性、连续性和浏览器主线程流畅度。
7. 禁止把 `IntersectionObserver` 的一帧读数升级成播放命令；它只允许作为异步传感器输入。
8. 禁止滚动越快迁移越频繁；高速滚动时系统更应该减少迁移、减少解码、保持会话稳定。

## 3. 滑走暂停画面

1. 禁止正在自动播放的视频滑走后退化成无真实画面的占位表达。
2. 禁止把已经产生过播放帧的视频重新伪装成未播放、未加载或冷占位状态。
3. 禁止 owner 释放时丢失用户刚才看到的那一刻画面。
4. 禁止用默认 poster、黑底、骨架、空卡片或播放图标替代已成立的暂停画面。
5. 禁止把离屏中断解释成自然结束；离屏只能表示暂停、保留资格和等待回屏。
6. 禁止因为节省资源而删除唯一能表达连续性的最后可见画面。
7. 禁止把 owner 释放和画面退场绑定成同一个动作；释放 live player 前必须先形成可持续的只读表面意图。
8. 禁止把“保画面”实现成同屏多 `<video>` 保活；保画面是视觉事实，不是多路解码事实。

## 4. 滑回续播

1. 禁止视频滑回视口时从开头、封面、首帧或占位重新开始表达。
2. 禁止先显示错误画面再 seek 到正确位置。
3. 禁止把保存 `currentTime` 当成续播已经成立；用户可见画面也必须连续。
4. 禁止在源一致、位置有效、附件仍存活时回退到冷启动视觉状态。
5. 禁止把 seek、metadata、canplay 或 hidden handoff 的短暂等待暴露成画面跳变。
6. 禁止让回屏续播依赖用户再次点击、等待长时间空窗或重新触发查看器。
7. 禁止让虚拟列表重挂载把同一视频误判成新会话；DOM 回来只是宿主回来，不是播放真相重开。
8. 禁止先拆旧宿主再赌新宿主可播；播放器迁移必须具备准备、确认、提交、退场的事务语义。

## 5. 预览入场

1. 禁止视频进入近视口后才开始第一次准备可见表达。
2. 禁止预览等待正式 owner 完全 settled 后才出现。
3. 禁止让用户先看到长时间空卡片，再看到视频画面。
4. 禁止把预热、候选、播放源解析和表面挂载串成肉眼可见的长队列。
5. 禁止把没有正式播放资格的视频伪装成正在播放；也禁止把已有预览资格的视频压成空窗。
6. 禁止为了少写状态而让“可预览”“可自动播”“可查看”互相阻塞。
7. 禁止让预热、续播、自动播互相死等；预热和表面准备应服务于 owner 成立前后的连续性。
8. 禁止隐藏探针、首帧预热和真实播放抢同一份解码预算；帮助任务必须低优先级、可取消、可合并。

## 6. 稳定表面槽

1. 禁止在可见区内发生 `poster -> video -> poster`、`preview -> canonical -> frozen` 这类可见换壳。
2. 禁止把 poster、preview video、canonical host、frozen frame、guard 做成互相抢 DOM 的多个可见主壳。
3. 禁止在同一张视频卡片里存在多个可见表面事实；卡片只允许拥有一个稳定的时间线视频表面槽。
4. 禁止让 `附件渲染.ts` 用分散 `if` 自己裁决壳层切换；它只能投影状态机给出的 `surfaceMode`。
5. 禁止把 `cold / preparing / live / frozen / resuming / failed` 之外的临时状态偷塞成新表面真相。
6. 禁止让同一张卡片在真实画面、暂停画面、封面和占位之间无语义跳转。
7. 禁止把 pending、hidden handoff、首帧 guard 或资源清理暴露成闪烁。
8. 禁止让非 owner 卡片继续解码播放；也禁止让非 owner 卡片失去应有的只读画面表达。
9. 禁止把视觉连续性建立在偶然 DOM 复用、浏览器缓存命中或计时器运气上。
10. 禁止用“把换壳做快一点”代替“消灭可见换壳”。

## 7. 性能边界

1. 禁止用保活所有视频 DOM、同屏多 live 视频或后台多路解码换取看似稳定。
2. 禁止让自动播放稳定性依赖主线程高频同步测量、强制回流或全量重算。
3. 禁止把滚动事件变成播放状态、媒体预算、附件全量索引和 DOM 清理的大杂烩。
4. 禁止为了消除闪烁增加更重的持久表面、重复播放器或额外媒体下载。
5. 禁止为了节流 UI 而破坏 WebTorrent 补齐、做种、帮助链和正式字节主链。
6. 禁止把性能问题转嫁给用户硬件、浏览器缓存或“多发几个视频就这样”。
7. 禁止用主线程高频同步读 DOM 来弥补状态模型缺口。
8. 禁止让 `requestVideoFrameCallback()` 变成逐帧业务状态机；它只允许确认帧已提交。

## 8. 成熟轮子边界

1. 禁止重复手搓虚拟列表基础设施；大列表、动态高度、滚动窗口继续优先复用 `@tanstack/lit-virtual`。
2. 禁止让虚拟列表轮子拥有播放事实；TanStack Virtual 只管理可见窗口和测量，不裁决 owner、position 或 surface。
3. 禁止重复手搓复杂状态机基础设施；离散播放连续性继续优先复用 `XState v5` 表达。
4. 禁止把 XState 用成大而全事件总线；它只收口 owner、handoff、resume、frozen、retire 等播放连续性状态。
5. 禁止重复手搓播放器壳；正式播放器能力继续优先复用 `Video.js v10` 和项目的全局唯一播放器薄适配。
6. 禁止让 Video.js 反向拥有自动播候选、WebTorrent 分发、附件权限或业务会话真相。
7. 禁止绕开浏览器原生能力；可见性观测用 `IntersectionObserver`，帧提交确认用 `requestVideoFrameCallback()`。
8. 禁止把 Chrome 自动播放策略包装成业务状态；muted autoplay、`play()` Promise 成败只作为浏览器事实输入。
9. 禁止把 `react-virtuoso`、短视频 feed 库或任意热门组件库误当成完整答案；它们不能直接解决 Lit、WebTorrent、唯一播放器和群聊续播会话。
10. 禁止因为没有全包轮子就回到全手搓；成熟轮子负责基础能力，项目代码只负责业务连续性协议和薄适配。

## 9. 调查与修复方法

1. 禁止在复杂自动播 bug 中先补表面 UI；必须先收口状态机、不变量和事实归属。
2. 禁止一次调查只看单个文件；必须沿 `几何观测 -> 候选编排 -> pending owner -> settled owner -> 媒体运行时 -> 全局唯一播放器 -> 附件表面 -> 虚拟列表 -> WebTorrent 源` 查到底。
3. 禁止把信号当事实；几何、DOM ready、video event、play Promise、MutationObserver 都只能输入状态机。
4. 禁止没有事实归属表就开始改代码；`candidate / pendingOwner / settledOwner / savedPosition / livePlayerHost / visibleSurface / frozenFrame / previewSource / webTorrentSource / virtualHost` 必须先明确 owner。
5. 禁止把浏览器烟测放在最后一次性碰运气；每轮都必须先状态机收口，再真实浏览器取证，再回到状态机修正。
6. 禁止少于三轮就宣布复杂自动播修复完成；至少要经历主病因、次级病因和压力回归三轮。
7. 禁止把失败统一写成“闪烁”；必须归类为 owner 抖动、surface 错投影、player 迁移断裂、source/预热/WebTorrent 生命周期断裂之一。
8. 禁止用最终 DOM 形态证明过渡正确；必须观察状态转移序列、MutationObserver、帧提交、owner 变化和 active video 数。
9. 禁止不跑真实房间烟测就关闭问题；`1234b` 必须覆盖慢滚、快滚、来回滚、滑走滑回、切视频、查看器打开关闭。
10. 禁止把 `browser-trace`、Playwright 或浏览器取证结果只当截图；它们必须反向校验状态机不变量。
11. 禁止每轮调查没有书面输出；必须记录本轮破坏的不变量、涉及模块、修正点、验证命令和仍未关闭的风险。
12. 禁止把同一失败在下一轮换名字重报；如果失败没有归到新的底层原因，就必须回到原不变量继续收口。

## 10. 第一性原理错误设计

1. 禁止把几何观测设计得离播放事实太近；可见度只是传感器读数，不是播放命令。
2. 禁止让 render 分支承担状态机职责；模板只投影结果，不裁决连续性。
3. 禁止把保画面理解成保 DOM 或保活多个 video；用户要的是画面连续，不是后台多路解码。
4. 禁止把 owner 释放、画面退场和资源清理合并成一个不可分动作。
5. 禁止把虚拟列表卸载解释成会话死亡；DOM 宿主不是会话本体。
6. 禁止让预热、续播和自动播互相等待；它们必须被统一连续性协议编排。
7. 禁止用时间戳单独证明续播；没有正确可见帧的 `currentTime` 只是半截事实。
8. 禁止让失败、冷态、加载态和续播态共用 poster 表达。
9. 禁止多个 owner 概念并存；一个会话 owner 之外只能有投影或宿主能力。
10. 禁止用局部 guard、timeout、cooldown 掩盖状态模型缺口。
11. 禁止隐藏探针和真实播放争抢资源；探针必须受统一预算和取消协议管理。
12. 禁止测试只看最终 DOM；复杂播放 bug 必须测过渡、事务和肉眼体验。
13. 禁止把复杂性暴露给用户滚动速度；滚动越快，系统越应该克制迁移。
14. 禁止把播放器迁移设计成“先拆旧，再试新”；迁移必须像事务一样提交。
15. 禁止把成熟轮子当完整产品答案；轮子解决基础设施，不解决本项目群聊视频连续性协议。

## 11. 验收红线

1. 禁止只用单条视频、低速滚动或理想网络证明群聊视频体验成立。
2. 禁止只验证最终能播放，而不验证滑走保帧、滑回续播和滚动中无抽搐。
3. 禁止只看状态字段正确，而不看真实浏览器可见画面是否连续。
4. 禁止只看单元测试通过，而不做真实浏览器滚动、自动播放和查看器烟测。
5. 禁止忽略 console error、非预期网络失败、播放器数量、active video 数和正式源类型。
6. 禁止把“没有崩溃”当成“丝滑”；丝滑必须同时满足画面连续、owner 稳定、主链不破和滚动不卡。
7. 禁止在 `activeVideoCount > 1`、`canonicalPlayerCount > 1` 或 `autoplayOwnerCount > 1` 时判定通过。
8. 禁止在可见区仍存在黑卡、空卡、默认 poster 闪回、错误帧后 seek 时判定通过。
9. 禁止在 WebTorrent 正式源被 UI 修复旁路掉时判定通过。
10. 禁止在滚动热路径新增全量扫描、强制回流或多路解码时判定通过。

## 12. 最终禁止

1. 禁止让用户在群聊里看黑乎乎的占位卡片，而不是刚才看到的视频画面。
2. 禁止让用户用滚动速度、等待时间或重复点击来弥补系统播放链路不连续。
3. 禁止用表面兜底掩盖 owner、状态机、播放器迁移和时间线投影之间的真实分裂。
4. 禁止为了修一个闪烁引入更大的第二真相。
5. 禁止把“视频能播放”误判成“群聊视频体验已经成立”。
6. 禁止继续围绕“怎么把换壳修稳”思考；正确问题是为什么还允许可见换壳存在。
