## 0. 为什么这次要单独写一份“去屎山收口”spec

这份 spec 不是为了“代码看起来更整洁”，也不是为了给现有聊天系统套一层更时髦的 DDD 名词。  
它要解决的是一个更现实、更危险的问题：

**聊天 realtime 主链虽然还没丢，但它外围的恢复链、编排层、transport 胶水、壳层热点正在持续长胖；如果再继续靠补丁和临时收口推进，系统会慢慢从“核心没坏”滑向“外围越来越难懂、越来越容易漂移、越来越容易出 bug”的状态。**

前面那轮针对媒体协作分发的工作，已经把一个事实照得很亮：

1. 目前项目并没有偷偷换掉聊天 realtime 核心；
2. 真正危险的不是“核心换了”，而是**壳层、编排层、恢复链、transport 热点开始吸附越来越多职责**；
3. 如果不在这时主动收口，后面每次修 bug、补恢复、加兼容、做运维兜底，都会继续往热点里塞；
4. 最后系统就算表面仍叫 `socketioxide + socket.io-client`，实际外围也会越来越像私有胶水屎山。

这份 spec 的根本目的，就是在**核心还没坏之前先收边界**，让后续维护和运维没有那么容易把系统再养歪。

## 1. 当前已经确认的事实，不准被误判

先把几个事实钉死，防止后面写 plan 或落代码时方向跑偏。

### 1.1 聊天 realtime 核心还在

这次架构审查确认过：

1. 后端聊天 realtime 主入口仍然是 `socketioxide`；
2. 前端聊天 realtime 主入口仍然是 `socket.io-client`；
3. `subscribe_room_stream` 与 `create_message` 仍然是主链上的正式业务入口；
4. 当前没有发现第二套正式聊天实时核心在暗中接管主链。

因此这次收口的基本立场必须是：

**禁止把“去屎山”误解成“把现有成熟核心也拆掉重来”。**

### 1.2 真正的问题在外围热点，不在核心轮子

当前的风险主要来自下面这类热点：

1. 后端大文件把 handler、用例、胶水和边界判断不断吸进同一个地方；
2. 前端 `传输 / 房间实时编排 / 房间恢复编排 / 聊天壳 / 聊天应用内核` 一类文件持续长胖；
3. 恢复链、补洞链、重连链、transport 层和壳层之间的职责边界越来越模糊；
4. 旧路径和新包装如果不删，会越来越容易形成“表面只是一点点兼容，实际上已经多出一层真相”的漂移。

因此这次要处理的是：

**外围壳层、恢复链、编排热点、transport 胶水和低价值包装。**

不是：

1. 重写聊天业务真相；
2. 新造实时基础设施；
3. 重写媒体协作分发；
4. 顺手做全仓大重排。

### 1.3 这次的危险不是“做太少”，而是“借去屎山之名改真相”

任何“这次顺手把协议也统一一下”“顺手把事件也重命名一下”“顺手把 transport 全改了”“顺手把恢复链换成更先进的状态机”的冲动，都默认视为高风险。

原因很简单：

1. 第一阶段目标是**结构收口**；
2. 不是**业务重写**；
3. 更不是**协议重写**。

这条边界如果不守住，bug 和漂移会比当前屎山更快出现。

## 2. 这次真正要写死的目标

先把一句话写死：

**万人实时群聊第一阶段，只允许把“聊天 realtime 主链 + 恢复/编排热点”做结构守正：继续复用 `socketioxide + socket.io-client` 作为唯一聊天实时主链，允许用中文目录、中文文件、中文模块、适量新增 `.rs/.ts` 重新收口边界，但禁止改业务真相、禁止改协议表面、禁止长出第二套实时核心或第二套恢复真相，并且必须同步删除旧胶水与旧重复路径。**

这句话展开后，就是下面这些硬裁决：

1. **禁止把“去屎山”做成推倒重来。**
2. **禁止把 `socketioxide`、`socket.io-client` 这种成熟主链轮子错杀。**
3. **禁止把“DDD”理解成多一层 manager、多一层 facade、多一层 helper。**
4. **禁止把“Unix 哲学”理解成文件无限细碎、目录无限增生。**
5. **禁止只加新结构、不删旧胶水。**
6. **禁止为了重构顺手改变外部行为。**
7. **禁止把恢复链做成第二实时主链。**
8. **禁止让未来维护继续往热点文件里无成本塞补丁。**

---

## 3. 这次为什么必须这样做，而不是继续“先补一刀再说”

### 3.1 因为“核心没坏”不代表系统健康

很多项目的退化不是从“核心突然换掉”开始的，而是从下面这种慢性过程开始的：

1. 某次为了补一个断线问题，往 transport 加一个特殊分支；
2. 某次为了补一个 invalid session 问题，往恢复编排里再塞一点状态；
3. 某次为了适配某个壳、某种展示、某种异常，又加一层低价值包装；
4. 几轮下来，核心轮子虽然还在，外围却开始出现多处 owner 争夺、重复路径和真假难辨的恢复语义。

这类退化最危险的地方在于：

**它不会在某一天突然看起来很糟，而是会在每一次“先补一下”“先绕一下”“先别动老的”里慢慢变得不可维护。**

### 3.2 因为当前已经出现典型的热点吸职责信号

本轮审查已经确认：

1. 前端 `传输` 已经开始兼管 socket 创建、HTTP 调用、房间恢复相关配合与多条链路入口；
2. `房间实时编排`、`房间恢复编排` 一类文件已经承担过多运行时协作责任；
3. 后端部分壳层与用例文件体积过大，说明职责吸附已经真实发生；
4. 如果不先收口 owner，后续每个需求都会继续沿着“最大热点最顺手”的路径堆进去。

所以这份 spec 必须选择：

**先把边界收口，再继续开发。**

### 3.3 因为“未来维护和运维漂移”本身就是这次要解决的问题之一

这次不只是去掉今天眼前的屎山，更要解决后面为什么会继续长屎山。

如果 spec 里只写“整理一下结构”，而不写：

1. 以后哪些行为视为漂移；
2. 以后哪些路径禁止再次出现；
3. 以后新增模块必须满足什么条件；
4. 以后修 bug 时什么做法不准合法化；

那这次就只是把代码搬了一次家，后面仍然会长回去。

所以这份 spec 必须同时是：

1. 一份**收口文档**；
2. 一份**防漂移文档**。

## 5. 目标、范围与非目标

### 5.1 目标

第一阶段只做一件事：

**在不改变聊天业务语义、不改变 realtime 对外协议、不破坏现有功能的前提下，把“万人实时群聊”的聊天主链、恢复链、编排热点，从正在变厚的大文件和胶水层里收口出来，重新钉死 owner，删除冗余包装，建立更适合长期维护的 DDD 洋葱边界。**

### 5.2 范围

本阶段要收的，是：

1. 聊天 realtime 正式主链；
2. 房间恢复链；
3. 断线、补洞、重新接回主链的编排热点；
4. 围绕这些链路长出来的低价值 transport / shell 胶水；
5. 相关中文目录、中文文件和边界重排。

### 5.3 非目标

本阶段明确不是为了做这些事：

1. 不是为了重写聊天业务；
2. 不是为了重写协议；
3. 不是为了顺手换实时轮子；
4. 不是为了大规模前后端一起推倒；
5. 不是为了“更像 DDD”而加很多层；
6. 不是为了让目录看起来工整，而忽视真实 owner 是否更清楚。

## 6. DDD 洋葱边界与 Unix 哲学：这次到底怎么理解

这次你要求：

1. 用 DDD；
2. 用洋葱架构；
3. 用 Unix 系统哲学；
4. 禁止制造新的屎山、重复轮子和冗余包装。

这些要求必须解释清楚，否则实现时很容易被误用。

### 6.1 DDD 在这次里的真实含义

这次的 DDD 不是：

1. 到处加 `manager`；
2. 到处加 `service`；
3. 到处加空心接口；
4. 到处套“领域层、应用层、基础设施层”名字但职责没变。

这次的 DDD 只允许意味着：

1. **业务真相回到领域与用例层；**
2. **协议翻译停在 adapter；**
3. **交互编排停在壳层；**
4. **任何人一看目录和模块名，就知道 owner 在哪。**

### 6.2 Unix 哲学在这次里的真实含义

这次的 Unix 哲学也不是：

1. 文件越多越高级；
2. 模块越碎越高级；
3. 一个函数拆三层转发就叫可组合。

这次只允许按下面这条理解：

**模块要小而专，但必须有独立边界价值；组合要简单，但不能把简单路径拆成碎片噪音。**

### 6.3 这次的根本准绳

因此这次实现时，必须按下面这句话裁决：

**DDD 只用来收口领域真相和 owner，不用来制造层数；Unix 哲学只用来让模块更小、更专、更可替换，不用来制造碎片和样板；成熟轮子继续复用，禁止再手搓第二套 realtime / recovery / transport 核心。**

## 7. 目录收口与中文文件策略

这次已经明确允许：

1. 新建中文目录；
2. 新建中文文件；
3. 新增 `.rs`；
4. 新增 `.ts`；
5. 为了边界更清楚而移动文件、重命名模块。

但这些权限不是开放给“随便拆”的，而是开放给**有边界价值的收口**。

### 7.1 为什么允许新建文件和目录

如果只要求“尽量别加文件”，最后经常会出现一种假克制：

1. 超大文件继续变胖；
2. 明明已经有两个不同 owner，还硬塞在一个文件里；
3. 因为怕多文件，就把 adapter、用例、壳层编排继续写在一起；
4. 结果看似文件没增，实际维护性更差。

所以这次明确允许新建 `.rs/.ts` 和中文目录，原因不是鼓励扩张，而是：

**允许为了真正收边界而付出适量的物理重排成本。**

### 7.2 这次建议的目录方向

本阶段允许向类似下面这种方向收：

```text
src/
  聊天实时/
    领域/
    应用/
    适配/
  聊天恢复/
    应用/
    适配/

frontend/
  聊天实时/
    本地模型/
    适配/
    壳层/
  聊天恢复/
    适配/
    壳层/
```

这不是强制镜像，也不是说必须一次性全部整理成这个形状。  
真正必须满足的是：

1. 同一条链路的文件物理上要更靠近；
2. 同一个 owner 不准散落全仓各处；
3. 目录名和文件名默认优先中文，让阅读者直接看懂。

这里必须再单独补一条，防止后面实现时偷长出第二套前端真相：

1. **禁止把前端目录写成“也拥有一套聊天业务领域 / 应用真相”。**
2. 前端可以有 `本地模型 / 适配 / 壳层 / presenter / runtime` 一类结构；
3. 但这些结构只服务浏览器应用运行时、本地临时状态、交互编排和契约消费；
4. **禁止把房间成员资格、权限、消息成立、治理语义重新养成前端自己的 `领域 / 应用`。**

换句话说：

**后端 `domain / application` 仍是业务真相 owner；前端只允许有本地运行时模型与壳层协作，不允许再长一套平行领域核心。**

### 7.3 哪些新文件允许存在

允许新增的文件类型：

1. 从 god file 中拆出的单一职责文件；
2. 原来混在 adapter 里的应用编排文件；
3. 原来混在壳层里的恢复协作文件；
4. 用来承接旧逻辑退场的过渡性收口文件。

### 7.4 哪些新文件禁止存在

下面这些新增文件，一律视为失败：

1. 纯转发包装文件；
2. 没有独立边界价值的 facade / manager / helper；
3. 为了“看起来分层”而硬拆出来的 ceremony 文件；
4. 与旧实现长期并行的新路径文件。

### 7.5 禁止“只加不删”

最重要的一条必须再单独写死：

**允许新增文件，不代表允许净增垃圾。**

凡是新增文件：

1. 必须说清替代了什么旧路径；
2. 必须删掉什么旧胶水；
3. 必须让 owner 更清楚；
4. 必须让总复杂度下降。

做不到这四条，就不准新增。

## 8. 分层边界：领域、应用、适配、壳层到底各自管什么

这次第一阶段只允许保留 4 层表达，而且每一层都必须说各自该说的话。

### 8.1 领域层

领域层只允许拥有：

1. 聊天 realtime 真相本身的稳定概念；
2. 房间事件流、消息成立、恢复锚点等稳定业务语义；
3. 与框架无关的核心约束。

领域层禁止拥有：

1. `socketioxide` 细节；
2. `socket.io-client` 细节；
3. HTTP 调用细节；
4. 浏览器状态；
5. 某个壳专属的展示流程。

### 8.2 应用层

应用层只允许拥有：

1. 用例编排；
2. 命令和查询的执行顺序；
3. 恢复、补洞、重接入主链这类流程的权威编排。

应用层禁止拥有：

1. 框架胶水；
2. 页面 UI 流程；
3. 协议编码细节；
4. transport 连接管理细节。

### 8.3 适配层

适配层只允许拥有：

1. 协议翻译；
2. handler / socket callback / HTTP 请求和响应映射；
3. IO 接入和错误转码。

适配层禁止拥有：

1. 业务真相；
2. 房间成员资格真相；
3. 消息成立真相；
4. 权限裁决真相；
5. 恢复链的业务 owner。

### 8.4 壳层

壳层只允许拥有：

1. 前端应用壳的交互编排；
2. 必要本地临时状态；
3. 什么时候触发调用、什么时候展示连接提示、什么时候交给恢复链。

壳层禁止拥有：

1. 权限真相；
2. 房间成员资格真相；
3. 消息成立真相；
4. 能否订阅、能否发言这类业务裁决。

### 8.5 `contract` 在第一阶段的处理原则

这次 reviewer 提醒得对：如果不把 `contract` 单独钉死，后面写 implementation plan 时很容易分成两种错误方向：

1. 一种人会绕开 `contract`，直接在 adapter / shell 里各自长形状；
2. 另一种人会借“顺手整理一下”之名，把 `contract` 也拖进第一阶段重构。

这两种都危险，所以这里必须单独写死：

1. **`contract` 是多壳共享的唯一稳定通用表面。**
2. **第一阶段禁止新造第二份 `contract`。**
3. **第一阶段禁止重排 `src/契约.rs` 与 `frontend/契约.ts` 的共享边界。**
4. **第一阶段禁止把某个壳专属的页面流程、展示文案、布局字段、UI 状态枚举倒灌进 `contract`。**
5. 第一阶段只允许继续消费既有 `contract`，并借此把 `adapter / shell / recovery` 的 owner 收清；
6. 如果某处之所以混乱，是因为消费 `contract` 的位置不对，那就调整消费边界；
7. **禁止把“消费边界不清”误判成“需要先改 `contract` 本身”。**

这里的核心裁决是：

**第一阶段收的是“谁消费 `contract`、谁不该持有真相”，不是“把 `contract` 本身再重写一遍”。**

## 11. 轻约束防漂移规则

你这次选择的是轻约束，不是复杂预算表，但也绝不能只是“提醒一下以后注意”。

所以这次必须至少把下面这些轻门禁写死：

### 11.1 以后谁再碰 realtime / recovery 热点，先判断 owner 属于哪一层

每次再改这些热点前，先回答：

1. 这是 `domain` 里的事？
2. 这是 `application` 里的事？
3. 这是 `adapter` 里的事？
4. 这是 `shell` 里的事？

回答不清，就禁止直接下刀。

### 11.2 以后新增模块，必须同时回答两个问题

1. 这个模块的独立边界价值是什么？
2. 它替代或删除了哪段旧路径？

这两个问题答不清，禁止新增。

### 11.3 以后修 bug，禁止让临时补丁升格成长期真相

运维补丁、恢复兜底、兼容分支、临时旁路，默认都只应该是临时措施。  
禁止在没有重新收口 owner 的情况下，把它们慢慢变成正式路径。

### 11.4 以后只接受“净减复杂度”的结构改动

文件数可以增加，目录可以变化，但必须同时满足：

1. owner 更清楚；
2. 重复路径更少；
3. 热点吸职责更弱；
4. 未来更不容易往同一热点塞补丁。

### 11.5 “先留着旧的保险一点”默认视为漂移信号

除非有非常明确的退场计划、验证门禁和时间边界，否则一切“旧的先别删”都默认当作漂移预警。

## 13. 第一阶段实施顺序

禁止在这个阶段：

先收：

### 13.4 阶段四：删旧路径与全量验证

最后做：

1. 删掉旧胶水；
2. 删掉旧包装；
3. 删掉旧重复路径；
4. 跑全量验证；
5. 重建 graphify，确认热点真的减压。

至少要满足下面这些结果中的大部分，才算真正发生了减压：

1. `frontend/传输.ts` 不再同时兼管 `socket` 创建、HTTP 调用、恢复触发、重接协作这几类不同 owner；
2. `frontend/房间恢复编排.ts` 不再继续充当“恢复总控 + transport 拼接器 + UI 协调器”的混合热点；
3. `frontend/房间实时编排.ts` 与 `frontend/房间恢复编排.ts` 的边界更清楚，禁止继续互相吸成一个双头总控；
4. `frontend/聊天壳.ts` 只保留壳层交互编排，禁止继续回收恢复、权限或业务判断；
5. `src/外壳.rs`、`src/实时外壳.rs` 至少有一部分不属于 adapter 的职责被真实剥离，而不是只换名字继续留在原地；
6. `src/用例.rs` 不再继续充当所有聊天 realtime 与恢复相关编排的无上限汇聚点；
7. graphify 复核时，不能再看到单一 transport / 编排节点同时垄断“聊天主链 + 恢复 + 壳层协作”三种职责。

同样必须写死反面判定：

1. 如果只是把 `传输.ts` 改名后继续承载同样 4 类职责，不算减压；
2. 如果只是把 `房间恢复编排.ts` 切成多个纯转发文件，不算减压；
3. 如果后端只是把大函数搬到新文件，但 handler 仍持有相同业务判断，不算减压；
4. 如果 graphify 热点只是从一个文件迁移到另一个文件，而不是职责被拆回正确 owner，也不算减压。

所以这里最终只认一条：

**这次减压必须是职责回到正确 owner，而不是热点换个路径继续胖。**

## 16. 与现有 WebTorrent 协作分发 spec 的关系

这份新 spec 和 `2026-04-23-WebTorrent群聊越活跃越强的极限协同分发.md` 是**并列关系**，不是父子关系，也不是附录关系。

### 16.1 WebTorrent spec 负责什么

它负责：

1. 媒体正式分发真相；
2. swarm；
3. 片段帮助者；
4. `24 小时` 前后切换；
5. 删除态与无种子态说真话。

### 16.2 这份去屎山 spec 负责什么

它负责：

1. 聊天 realtime 主链；
2. 房间恢复链；
3. 编排热点；
4. transport 胶水；
5. DDD 洋葱边界；
6. 防未来维护漂移。

### 16.3 禁止两个 spec 互相污染

因此必须禁止：

1. 在聊天去屎山 spec 里偷偷改媒体协作分发真相；
2. 在 WebTorrent spec 里偷偷长出聊天 realtime 重构边界；
3. 用一份 spec 替代另一份 spec 的 owner。

## 17. 最终硬裁决

以后在 `koko` 里，必须按下面这句话理解这次第一阶段去屎山收口：

**万人实时群聊的第一阶段去屎山收口，只允许做“聊天 realtime 主链 + 恢复/编排热点”的结构守正；必须继续复用 `socketioxide + socket.io-client` 作为唯一聊天实时主链；允许用中文目录、中文文件、中文模块、适量新增 `.rs/.ts` 把边界收清，但禁止新造第二套实时核心、第二套恢复真相、第二套 transport 真相；所有改动都必须净减复杂度、删除旧胶水、保持业务行为等价，并让未来维护更不容易漂移。**

从这句话自然推出全部实现边界：

1. 禁止把去屎山做成推倒重来；
2. 禁止把成熟 realtime 核心误杀；
3. 禁止把结构收口偷换成业务重写；
4. 禁止把 DDD 做成 ceremony；
5. 禁止把 Unix 哲学做成文件碎片化；
6. 禁止新旧双活长期共存；
7. 禁止新增文件却不删除旧胶水；
8. 禁止为了“保险”保留第二套恢复或 transport 真相；
9. 禁止未来维护和运维继续用补丁把热点养胖。

后续 implementation plan 和代码改动，都只能在这条边界内工作；凡是离开这条边界去“先顺手改一下协议”“先保留旧的”“先多加一层包装”“先把 transport 全家桶推倒重来”的，都应直接视为漂移，必须禁止。
