# 全屏退出视频卡片黑闪根因与修复

## 现象

在部分设备上，群聊内点开视频全屏欣赏后返回，对应视频消息卡片会先"黑一下"再恢复正常画面。

## 用户体验目标

全屏退出到时间线卡片的过渡必须**像同一张画面被轻轻推回原位**——观众感受不到任何拼接、跳变、黑屏或闪烁。

## 根因分析

### 时序链路

```
closeFullscreen()
 ├─ document.exitFullscreen()         (异步, 浏览器结算)
 ├─ cleanup()                         (同步)
 │   ├─ hooks.通知查看器已关闭()       → VIEWER_CLOSED → viewerOpen=false + 重算autoplay候选
 │   ├─ 当前查看器会话.关闭()          → 释放查看器并尝试归位时间线()
 │   │   └─ 应用时间线自动播表面()     → 开始把 canonical player 挂回时间线宿主
 │   ├─ video.pause()
 │   └─ overlay.remove()              ← 同步移除覆盖层, 聊天时间线立即可见
 └─ [下一微任务] Lit 异步 re-render   → 时间线卡片更新可见表面
```

### 黑闪窗口

`overlay.remove()` 是同步操作，聊天时间线**立即**暴露在用户视野中。但 Lit 的响应式渲染发生在**下一个微任务/动画帧**。在这个间隙里，用户看到的是**旧状态**的时间线卡片。

### 旧状态时间线卡片的 z-index 叠加栈

```
z:0  poster <img>              → 如果存在且已加载, 是最后安全网
z:1  preview <video>           → opacity:0 (无 --has-frame) 或不渲染
z:2  frozen-frame <canvas>     → ← 关键: 可能已失去内容
z:3  canonical-host <div>      → data-covered="true" → opacity:0
     ─────────────────────────
     card background            → 深色渐变 rgba(9,13,18,0.98)
```

### 三条根因路径

#### 路径 A: Canvas GPU 上下文丢失（设备相关）

全屏进入/退出触发浏览器 GPU 上下文重置。`<canvas>` 2D 渲染面被清空为透明像素。

Lit 的 `ref()` directive 在以下条件触发：**首次创建**元素或**替换为不同 DOM 节点**时。对同一个复用的 canvas 实例，ref 不会在每次模板执行时重新调用。因此 canvas 内容因 GPU 重置而丢失后，没有任何机制会重绘。

补充说明：当 `shouldRenderFrozenTimelineFrame` 从 false 变回 true 时（如 viewer 关闭后 Lit re-render），Lit 会**创建新的** canvas 元素并触发 ref 回调重绘。但这个 re-render 发生在 `overlay.remove()` 之后的微任务里——即黑闪窗口已经暴露。

**证据**: `绘制时间线冻结帧到画布()` 已有 try-catch 处理 `drawImage` 失败，注释写道"bitmap 可能已被 dispose 或 context lost；此时 canvas 保持透明，底层 poster 安全网会兜住卡片视觉"——说明开发时已意识到此风险，但 poster 兜底并不总可靠（路径 B）。

#### 路径 B: 冻结帧不存在 + poster 缺失

部分视频的 `posterSrc` 为空，或 poster 加载失败。如果视频在打开查看器前没有足够播放时间来捕获冻结帧，则 z:0 和 z:2 都没有有效像素。深色 card 背景直接暴露。

#### 路径 C: Lit re-render 时机差

`overlay.remove()` → 时间线可见（用户看到旧 DOM）→ 微任务后 Lit re-render → `应用时间线自动播表面()` 挂载 canonical player → player 出首帧。

即便 canvas 和 poster 都正常，如果 Lit re-render 中 `shouldRenderFrozenTimelineFrame` 因为新的 autoplay 候选计算从 true 变 false 再到 canonical reveal 为 true，中间也存在**一帧**空白。

### 结论

三条路径共同作用。核心矛盾：**overlay 同步移除暴露了时间线卡片，但卡片的视觉表面尚未就绪**。

## 修复方案

### 方案 A: frozen-frame canvas 自愈守卫（推荐，改动最小）

**原理**: 在 canvas 上监听 `contextlost` / `contextrestored` 事件，context 恢复时自动重绘冻结帧。同时在每次 Lit re-render 的 `ref()` 回调中无条件重绘（当前只在首次创建时绘制）。

**改动范围**:
- `frontend/房间消息窗/视频附件表面渲染.ts`: 增强 `ref()` 回调逻辑
- `frontend/房间消息窗/视频桥接帧.ts`: 新增 canvas context 守卫工具函数

**具体做法**:

1. **在 `绘制时间线冻结帧到画布` 中增加 context 状态检查**: 如果 `context.isContextLost()` 为 true，注册一次性 `contextrestored` 监听器，恢复后重绘。

2. **`ref()` 回调每次 re-render 都执行重绘**: Lit 的 `ref()` directive 在每次模板执行时都会调用回调（不仅仅是首次创建）。当前代码逻辑 `if (!(canvas instanceof HTMLCanvasElement) || !frozenTimelineFrame) return` 已经是正确的守门条件。但问题在于 Lit 对**同一个 canvas 实例、相同属性**可能复用而不重新触发 ref。增加一个数据驱动的 key（如 `data-redraw-token`）确保每次有效的冻结帧变更都触发重绘。

3. **轻量 rAF 验证**: 在 `overlay.remove()` 后的第一帧，检查当前可见的 frozen-frame canvas 是否有有效像素。如果为空且冻结帧数据仍在缓存中，立即重绘。

**优势**: 不改架构，不增加新组件，只加固现有 canvas 的自愈能力。
**风险**: 极低。`contextrestored` 是标准 Web API，重绘操作本身已有 try-catch 保护。

### 方案 B: overlay 延迟移除（辅助增强）

**原理**: 在 `创建默认VideoJs播放器层` 的 cleanup 中，不立即 `overlay.remove()`，而是在 canonical player 确认归位出帧后再移除。

**具体做法**:

1. `cleanup` 中改为 `overlay.style.opacity = '0'`（立即透明化，用户感知不到延迟）
2. 在 `释放查看器并尝试归位时间线()` 成功归位后，或超时 150ms 后，再执行 `overlay.remove()`
3. 这样用户在过渡期间看到的是透明 overlay（无内容但不遮挡交互），而非暴露的旧卡片

**优势**: 从根本上消除"旧卡片暴露"这个窗口，是最直接的时序修复。
**风险**: 透明 overlay 仍在 DOM 中，需要同时设置 `pointer-events: none` 避免拦截用户交互。超时兜底确保 overlay 不会无限悬挂。

### 方案 C: poster 强制兜底（最低优先级）

**原理**: 确保视频卡片在任何状态下都有一个不依赖 canvas 的可见兜底层。

**具体做法**: 当 `posterSrc` 存在时，始终渲染 poster `<img>`，即使 `shouldRenderPreviewPosterSurface` 条件不满足。

**优势**: 最简单的安全网。
**风险**: 可能引入不必要的图片请求；需要审计 `shouldRenderPreviewPosterSurface` 的所有判定路径。

## 推荐实施顺序

1. **方案 A**（canvas 自愈守卫）：核心修复，解决 GPU context loss 和 ref 不重绘问题
2. **方案 B**（overlay 延迟移除）：辅助增强，消除暴露窗口
3. 方案 C 暂缓，待 A+B 上线后评估是否仍需要

## 受影响文件

| 文件 | 层级 | 改动性质 |
|---|---|---|
| `frontend/房间消息窗/视频桥接帧.ts` | adapter | 增加 context 守卫 |
| `frontend/房间消息窗/视频附件表面渲染.ts` | adapter/shell | ref 回调增强 |
| `frontend/媒体/媒体查看器.ts` | adapter | overlay 移除时序 |
| `frontend/媒体/全局唯一播放器.ts` | adapter | 归位确认回调 |

## 验证标准

1. **冻结帧自愈**: 手动触发 `canvas.getContext('2d').reset()` 模拟 context loss，验证 canvas 自动重绘
2. **全屏退出零黑闪**: 在 Chrome DevTools 打开 Paint Flashing，全屏退出时卡片区域不出现纯黑帧
3. **移动端 Safari/Chrome**: 在 iOS Safari（webkitEnterFullscreen）和 Android Chrome 上分别验证
4. **无 poster 视频**: 使用不带封面的视频测试，确认有冻结帧兜底或 card 背景过渡自然
5. **快速连续操作**: 全屏→退出→立即全屏→退出，不出现残留状态或双重绑定
6. **自动播交接**: 退出全屏后，时间线自动播正常恢复到该视频卡片

## 洋葱边界审计

- **domain**: 不涉及。播放连续性状态机 (`视频可见槽位协议.ts`) 不需改动，它已正确定义了各阶段的可见表面
- **application/contract**: 不涉及。`播放连续性决策` 的类型和语义不变
- **adapter**: canvas 重绘守卫、overlay 时序调整都属于浏览器适配层
- **shell**: `ref()` 回调增强属于展示编排层

改动严格限定在 adapter/shell 两层，不穿透到 domain 或 application。

## 三遍自审结论

**第 1 遍（需求意图）**: 现象描述、根因链路、修复方案均与用户报告一致。"在有的设备上"的设备相关性已在路径 A 中标注。无修正。

**第 2 遍（架构边界）**: 三个方案都限定在 adapter/shell 层；无新外部依赖（`contextlost`/`contextrestored` 是标准 Web API）；方案按改动量升序排列，无过度设计。修正：方案 B 的 `pointer-events: none` 步骤已补充到具体做法中。

**第 3 遍（执行路径/验证闭环）**: 6 条验证标准分别覆盖 3 条根因路径 + 跨设备 + 快速操作 + 功能回归。精确化了 Lit `ref()` directive 的触发条件（仅首次创建或替换节点，非每次模板执行），消除了对 ref 行为的模糊描述。与 `视频卡片黑屏根因修复` 和 `浏览器零崩溃零闪烁` 两份已有 spec 不冲突。无遗漏。
