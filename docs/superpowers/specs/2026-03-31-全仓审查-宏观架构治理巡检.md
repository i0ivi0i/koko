# 总体结论

当前仓库的聊天主链路比 admin 路径更接近宪法目标：`domain / app / rt / http / shell` 的大框架已经站住，`socketioxide` 热路径也保持了“先应用判真相、后 adapter 发效果”的基本纪律。真正的宏观问题集中在 admin 边界和长期演进支撑上：admin 仍然是“当前 HTTP + Web 页面怎么方便就怎么接”的形状，而不是稳定的应用能力；另外，房间/成员创建真相仍部分滞留在 SQL adapter，测试层也开始出现实现绑定和重复支撑。

# 立即治理

- 标题: Admin 访问控制真相仍滞留在 HTTP adapter，而不是应用层能力
- 违反法则: `AGENTS.md` 要求“后端访问控制也不能散落在多个入口层”，`审查维护.md` 要求 `adapter` 只负责“鉴权接入”而不拥有“权限真相”
- 类别: 权限真相落错层
- 关键证据: `src/http.rs` 在 [`42-50`](../../src/http.rs) 挂出 admin 路由并把 `admin_token` 放进 `HttpState`，在 [`116-168`](../../src/http.rs) 直接用 `require_admin_token` 判权；对应的 `src/app.rs` 在 [`132-228`](../../src/app.rs) 只有读查询 port，没有任何 admin 身份/鉴权输入
- 为什么重要: 现在只有 HTTP 入口知道什么叫 admin；以后接 CLI、移动端后台或脚本入口时，要么重复同一套鉴权判断，要么直接绕过应用层，admin 能力会天然分叉
- 修复方向: 把 admin 身份与判权收敛成应用层显式输入和 port，HTTP 只负责提取凭证；应用层对 admin 查询统一判权，禁止再让入口层自带最终裁决

- 标题: Admin 共享面已经长出页面专属组合查询，`contract` 和用例边界被当前壳带偏
- 违反法则: `AGENTS.md` 与 `审查维护.md` 都明确要求“`contract` 是多壳共享唯一通用表面”“后端不得为某个壳硬编码页面流程或壳层专属数据形状”；设计基线只冻结了 `AdminOverview / AdminRoomListItem / AdminRoomDetail / AdminRoomMemberItem` 与对应稳定用例
- 类别: `contract` 污染 / 多壳共享面退化
- 关键证据: 设计基线在 `docs/superpowers/specs/2026-03-29-koko-第一阶段系统设计.md` 的 [`433-459`](../specs/2026-03-29-koko-第一阶段系统设计.md) 只定义稳定 AdminReadModel 和稳定用例；当前 `src/contract.rs` 在 [`50-69`](../../src/contract.rs) 新增 `AdminPanelData`，`src/app.rs` 在 [`142-228`](../../src/app.rs) 新增 `AdminPanelPort/load_admin_panel`，`src/http.rs` 在 [`47-49`](../../src/http.rs) 暴露 `/api/admin/panel`，`src/admin.rs` 在 [`11-49`](../../src/admin.rs) 直接围绕这个页面组合接口建壳
- 为什么重要: 这会把“后台首页怎么取数”伪装成稳定业务契约。等 CLI 或别的 admin 壳进入后，只会继续叠更多页面型接口，最终把共享面变成一堆当前页面的投影
- 修复方向: 删除 `load_admin_panel` 这类页面组合用例；把 admin 稳定面收回到真正跨壳的 query 上，由壳层自己组合 `overview + rooms + detail + members`

- 标题: 房间创建与成员建立的权威事实仍由 SQL adapter 生成，核心没有真正拥有这段真相
- 违反法则: `AGENTS.md` 要求“删掉 sqlx 后核心业务和用例仍可测试、可复用”，`审查维护.md` 要求 `adapter` 只翻译不决策；设计基线也把 `Clock / IdGenerator` 列为稳定出站能力
- 类别: 业务事实落入基础设施
- 关键证据: `src/app.rs` 在 [`85-111`](../../src/app.rs) 与 [`312-345`](../../src/app.rs) 的 `RoomEntryTx` / `join_or_create_room_by_code` 只把“建房、入会”整体委托给 adapter；`src/store.rs` 在 [`190-245`](../../src/store.rs) 里由 `PgRoomEntry::create_room` 和 `ensure_room_member` 直接生成 `room_id / room_code_id / member_id / now`
- 为什么重要: 这意味着“房间何时创建、成员何时成立、这些事实用什么 ID/时间语义落地”并不属于应用层，而属于当前 PostgreSQL 实现。以后换存储、补 CLI、做离线重放或引入第二个 adapter 时，这段真相会被迫复制
- 修复方向: 让应用层显式创建 `Room / RoomCode / Member` 事实，并通过 `Clock / IdGenerator` 或专用 factory 产出 ID/时间；adapter 只负责事务与持久化，不再私自生成权威实体事实

# 可延期精修

- 标题: 测试层开始用源码文本断言和重复 harness 固化实现，正在反向拖慢后续架构治理
- 违反法则: `AGENTS.md` 要求 TDD 和验证服务于“清晰、可维护、可演进”；`审查维护.md` 反对重复实现、低价值包装和让清理战役失控的结构
- 类别: 结构性测试债 / 重复支撑
- 关键证据: `tests/http_flow.rs` 的 [`82-152`](../../tests/http_flow.rs) 和 `tests/admin_flow.rs` 的 [`69-95`](../../tests/admin_flow.rs) 大量用 `include_str! + source.contains()` 钉死实现文本；同时 `tests/http_support/mod.rs` 的 [`13-222`](../../tests/http_support/mod.rs) 与 `tests/app_flow.rs` 的 [`1448-1800`](../../tests/app_flow.rs) 基本复制了一整套测试数据库建库/删库支撑
- 为什么重要: 这类测试并不证明架构边界，只是在保护当前写法和当前脚手架。后面一旦我们想重排模块、抽出共享支撑或替换实现，测试会先因为文本和复制脚手架碎掉，反而增加治理成本
- 修复方向: 把数据库 harness 收口到单一测试支撑模块；把源码文本断言替换成“边界行为是否成立、跨层依赖是否被守住”的测试

# 待补证观察项

- 当前 `contract` 还没有落出设计文档承诺的 `search_admin_rooms / get_admin_room_detail / list_admin_room_members` 等稳定 query。它现在更像“阶段未完成”还是“已经被页面接口替代”，需要结合下一轮 admin 需求确认。
- Web 壳目前只完成 bootstrap 与静态聊天页表达，realtime 和房间交互还没有形成完整壳层闭环。现阶段它更像“未完工”，还不足以单独升格为正式结构问题。

# 重复造轮子与冗余实现专项结论

- 生产代码没有看到新的成熟轮子手搓，聊天 realtime 主通道继续复用 `socketioxide`，这一点是对的。
- 冗余主要出现在测试支撑和 admin 页面组合层：前者是重复脚手架，后者是重复“页面即接口”思路，二者都会在后续演进中不断抬高维护成本。

# 分层与前后端解耦专项结论

- 聊天主链路基本守住了“adapter 先翻译 command，再交 application 判真相”的边界。
- admin 路径没有守住同样标准：判权在 HTTP，页面组合 query 进入 `contract/app`，说明这条链路还不是“多壳共核”，而是“当前壳优先”。
- `join_or_create_room_by_code` 这条链路表面上在 `application`，但关键创建事实实际下沉到 `store`，这是当前核心与基础设施仍未彻底切开的证据。

# 后续治理建议

1. 先打 admin 热点，不要立刻全仓大改。第一刀应该是把 admin 判权和稳定 query 面重新归位。
2. 第二刀收 `join_or_create_room_by_code`：把 Room / RoomCode / Member 的创建事实从 `store` 拉回应用层。
3. 第三刀处理测试债，把复制的 DB harness 和文本断言一起收口，不然前两刀会被测试层阻滞。
4. 完成以上三刀后，再做下一轮 focused audit，分别审 `admin.rs + http.rs` 和 `app.rs + store.rs`。
