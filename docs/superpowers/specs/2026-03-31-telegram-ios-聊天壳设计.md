# Koko Telegram iOS 聊天壳设计

## 文档定位

本文档定义 `Koko` 下一轮前台聊天壳设计，目标不是“再补一个能用页面”，而是把当前仓库收口成一个：

- 前后端完美解耦
- 主体纯 Rust
- 尽量复用现有成熟生态
- 高还原 Telegram iOS 深色主题聊天壳
- 不额外堆私有 UI framework / manager / coordinator

本轮是**前台普通用户聊天主链路设计**，不是 admin 重做，也不是桌面端专属产品设计。

---

## 1. 目标

本轮目标固定为七项：

1. 把前台聊天入口收口成可实际体验的单栏移动端聊天壳
2. 让普通用户能够完成完整主流程：
   - 打开页面
   - 自动拿 session
   - 查看会话列表
   - 搜索群号
   - 进入或加入群
   - 查看历史消息
   - 发送消息
   - 收到 realtime 更新
3. 会话列表页、搜索流程页、聊天页尽量高还原 Telegram iOS 深色主题
4. 会话列表支持：
   - 已加入群列表
   - 每个群最后一条消息预览
   - 未读占位
   - 本地恢复上次打开群
5. 搜索栏支持“边输入边搜群号”的真实功能，而不是样式占位
6. 保持后端只提供稳定契约，不返回 Telegram 专属 UI 数据形状
7. 整体实现保持简洁、可维护，不因高还原 UI 堆出新的私有框架债

---

## 2. 非目标

本轮明确不做：

- admin 页面联动改造
- 联系人体系
- 账号体系
- 置顶、归档、文件夹
- 语音、图片、文件、表情、贴纸
- 真未读计数真相
- 服务端保存“上次打开哪个群”
- iPad 专属布局语言
- 桌面专属三栏/双栏产品设计
- 为了高还原 UI 新引入另一套前端框架或组件库

本轮也不做“为了前端体验顺手全仓翻新”。变更范围只收在：

- 会话列表相关查询面
- 前台 Web 壳
- 搜索群号与加入群流程
- 聊天页与 realtime 接入

---

## 3. 产品体验目标

### 3.1 产品参照物

本轮体验目标不是“像 Telegram”，而是：

- 以 **Telegram iOS 默认深色主题** 为主要视觉参照
- 以 **iPhone 竖屏聊天体验** 为主基准
- iPad / 桌面浏览器必须响应式可用，但不是本轮的主设计语言

### 3.2 页面层级

本轮前台壳收成三个主页面：

1. `ConversationListScreen`
   - 会话列表页
   - 顶部为 Telegram iOS 风格导航栏与搜索区
   - 主体为已加入群列表
   - 每项显示群标题/群号、最后一条消息预览、未读占位

2. `JoinByCodeScreen`
   - 搜索/加入群流程页
   - 用户手动输入群号
   - 支持边输入边搜，实时显示匹配结果
   - 点击结果后加入或直接进入

3. `ChatScreen`
   - 单群聊天页
   - 顶部先只显示群标题/群号
   - 中间是消息流
   - 底部是 Telegram iOS 风格输入区
   - 进入页后立即建立实时在线态

### 3.3 首次打开行为

首次打开页面时：

- 自动 bootstrap session
- 查询当前 session 已加入的群列表
- 如果会话列表为空，则直接进入 `JoinByCodeScreen`
- 如果已有群，则进入 `ConversationListScreen`
- 如果浏览器本地保存了 `last_open_room_id` 且仍存在于会话列表中，则优先直接进入对应 `ChatScreen`

### 3.4 导航与动效目标

本轮导航体验要尽量贴近 Telegram iOS：

- 会话列表进入聊天页要有层级推进感
- 聊天页返回列表要有 iOS 风格返回层级
- 搜索/加入流程也应按 app 内层级切换表达，而不是粗暴切页面
- 点击反馈、输入区交互、列表项动效都尽量贴近 Telegram iOS

但本轮不允许为了动画效果引入新的前端 runtime 或私有动画框架。

## 4. 前后端完美解耦原则

本轮必须严格遵守：

- 后端不要干前端的活
- 前端也不许干后端的活

翻译成可执行边界如下。

### 4.1 后端允许做什么

后端只负责：

- session 真相
- 我加入过哪些群
- 群的稳定标题/群号
- 每个群最后一条消息预览
- 排序所需的稳定字段
- 房间快照
- 发消息的权威结果
- realtime 推送

### 4.2 后端禁止做什么

后端不得返回：

- Telegram 专属 cell 结构
- 导航栏状态
- 搜索栏焦点态
- 页面流程语义
- iOS 专属视觉字段
- “应该先打开哪个页面”这种壳层决策

### 4.3 前端允许做什么

前端只负责：

- 页面导航
- 高还原 Telegram iOS 展示层
- 搜索输入态
- 焦点态
- 动效
- 草稿
- 滚动位置
- 连接提示
- 本地 `last_open_room_id`

### 4.4 前端禁止做什么

前端不得自己伪造：

- 已加入群列表真相
- 最后一条消息预览真相
- 是否已经是某群成员
- 消息是否最终成立
- 是否有权限进入群

## 5. 技术栈决策

### 5.1 前端主栈

前端继续沿现有 Rust 主线，不另开第二技术栈：

- UI 壳：`Dioxus 0.7`
- 组件表达：`RSX`
- 样式：手写 CSS
- HTTP：`reqwest`
- 浏览器本地能力：`web-sys`

理由：

- 当前仓库已经在用 Dioxus
- 不额外引入 React / Next / Vue / Tailwind / 组件库
- 避免“双前端栈 + 高还原 UI 驯服成本”带来的长期债务

### 5.2 Realtime 技术决策

本轮实时链路遵守两个优先级：

1. 先满足 `socketioxide` 官方最佳实践
2. 在此基础上尽量使用 Rust

结合官方资料，技术决策固定为：

- 后端继续使用 `socketioxide 0.18.2`
- 后端继续使用：
  - connect middleware
  - socket extensions
  - room operator
  - direct handler
- 浏览器侧 realtime 客户端优先走 `socketioxide` 官方兼容路径

本轮不允许：

- 为了“全纯 Rust”手搓浏览器 Socket.IO 协议层
- 再包一层 repo 私有 realtime bridge framework

补充约束：

- “主体纯 Rust”在本轮中的准确定义是：
  - 页面结构、状态机、HTTP 调用、浏览器本地状态、样式组织继续由 Rust 主导
  - 如果浏览器 realtime 客户端最终必须借官方 Socket.IO client 才最符合 `socketioxide` 官方最佳实践，那么允许使用最薄的一层互操作接入
  - 但这层互操作不能膨胀成第二套前端应用层，也不能把 UI 或业务真相搬到 JS 侧

### 5.3 Wasm 决策

本轮前端继续走 Dioxus Web 的 Wasm 主线。

项目偏好固定为：

- 最新稳定版能力，主动用
- 新的浏览器/Wasm稳定能力，只要主流环境能跑，可以主动采用
- 不默认因为“新”而保守回避

唯一底线：

- 如果某能力依赖浏览器实验开关、非默认特性或明显破坏部署稳定性，则必须单独说明，不能偷偷混入

## 6. 领域与契约新增范围

### 6.1 新增会话列表查询

后端本轮应新增一个最小查询面，用于前台会话列表：

- `list_joined_rooms`

它只返回稳定业务数据，不返回 UI 结构。

### 6.1.1 新增群号搜索查询

后端本轮还应新增一个最小搜索查询面，用于搜索群号：

- `search_rooms_by_code`

它承担的职责只有：

- 按当前稳定群号规则做大小写不敏感匹配
- 返回稳定搜索结果
- 标记当前 session 是否已加入该群

它不承担：

- 返回 Telegram UI cell
- 决定前端页面切换
- 生成搜索栏交互状态

### 6.1.2 加入群命令复用决策

本轮**不新增第二套加入群命令**。

加入群流程固定复用现有稳定能力：

- HTTP：`join_or_create_room_by_code`

这意味着：

- 搜索结果点击后的“加入或进入”流程，不新造 `join_room_from_search`、`open_room` 之类平行命令
- 前端统一通过现有加入群命令进入房间
- 如果房间已存在，则复用现有“加入已有房间”的语义
- 如果房间不存在且当前业务仍允许按短码创建，则继续复用现有行为；若后续要切成“只能搜索现有群不能创建”，那是下一轮单独产品规则调整，不混在本轮

成功返回：

- 复用现有 `RoomSnapshot`

失败分支：

- 继续复用现有稳定错误语义
- 前端只把错误转成壳层提示，不新增 transport-only 错误体系

### 6.2 建议返回字段

每个会话项建议最小字段集：

- `room_id`
- `room_code`
- `display_title`
- `latest_preview`
- `latest_message_at`

说明：

- `display_title` 目前可以等于 `room_code` 或由稳定业务规则派生
- `latest_preview` 是业务可复用预览，不是 Telegram UI 专属字段
- `latest_message_at` 是排序字段，不是展示语义

### 6.3 明确不新增的契约字段

本轮不应进入共享契约的字段：

- `is_selected`
- `cell_style`
- `avatar_color`
- `nav_title`
- `search_highlight_ranges`
- `telegram_section_kind`
- `ios_transition_state`
- `unread_badge_style`

## 7. 搜索群号设计

### 7.1 目标

搜索栏本轮不是占位，而是要有真实功能：

- 支持按群号/房间码搜索
- 行为更像“搜索 QQ 群号进入”
- 边输入边搜
- 结果实时展示

### 7.2 当前规则与未来兼容

当前规则继续兼容现有房间码语义：

- 4 个数字 + 1 个英文字母
- 大小写不敏感

但本轮前后端都不得把“5 位长度”写死成到处散落的 UI 常量和流程判断。

要为未来“群号长度增长”留出升级口：

- 前端校验与展示优先引用统一规则
- 后端查询与 domain 规则保持单一来源
- 页面文案尽量避免硬编码“5 位群号”这种未来会漂移的说法

### 7.3 搜索结果形态

搜索结果采用：

- 边输入边搜
- 实时结果列表
- 点击结果进入目标群流程

搜索匹配建议默认采用：

- 归一化后的前缀匹配
- 精确命中优先排序
- 已加入的群优先排在未加入群之前

这三条是稳定查询语义，不是 Telegram 专属展示语义。

点击后的行为：

- 若当前 session 已经是该群成员：直接进入聊天页
- 若尚未加入：走加入后进入聊天页

### 7.4 搜索边界

后端只负责：

- 搜索匹配
- 返回稳定结果
- 判断群是否存在
- 判断是否已加入

前端只负责：

- 搜索框样式
- 动画
- 结果列表样式
- 空结果态
- 焦点态

## 8. 前端状态机设计

### 8.1 壳层状态原则

前端状态机必须保持薄，不允许把壳层体验态膨胀成第二套业务系统。

### 8.2 建议状态分层

前端状态分成三类：

1. 远端真相快照
   - 会话列表
   - 房间消息快照
   - realtime 增量事件

2. 本地体验态
   - 当前选中群
   - 搜索输入
   - 草稿
   - 滚动位置
   - 页面层级
   - 动画过渡态
   - 连接状态

3. 本地持久化体验态
   - `last_open_room_id`

### 8.3 本地恢复规则

本轮只在浏览器本地保存：

- `last_open_room_id`

恢复规则：

- 页面启动后先获取会话列表
- 如果 `last_open_room_id` 仍存在于会话列表中，则直接进入该群
- 如果不存在，则正常回到会话列表或加群流程

本轮不把“上次打开哪个群”升级成服务端真相。

## 9. 页面级详细设计

### 9.1 ConversationListScreen

职责：

- 展示已加入群列表
- 承载搜索群号入口
- 承载进入聊天页的导航起点

页面元素：

- Telegram iOS 风格顶部导航栏
- 搜索栏
- 会话列表
- 空列表时的过渡逻辑

行为：

- 如果列表为空，立即转入 `JoinByCodeScreen`
- 如果列表不为空，优先显示会话列表
- 点击会话项进入聊天页

### 9.2 JoinByCodeScreen

职责：

- 搜索群号
- 展示实时匹配结果
- 触发进入/加入群

页面元素：

- 顶部导航栏
- 搜索输入区
- 实时结果列表
- 空结果态
- 加载态

行为：

- 输入变化触发搜索
- 点击结果后：
  - 已加入则直接进入聊天页
  - 未加入则调用加入流程，再进入聊天页

### 9.3 ChatScreen

职责：

- 展示某个群的消息流
- 建立房间快照 + realtime 在线态
- 发送消息

页面元素：

- 顶部导航栏
- 消息流
- 输入区
- 基本连接状态

行为：

- 进入页先拉快照
- 再建立 realtime 订阅
- 收到事件后增量更新消息流
- 发送消息遵守现有 `message_accepted` / `message_created` 语义

### 9.3.1 聊天页快照复用决策

`ChatScreen` 本轮固定复用现有稳定查询：

- HTTP：`load_room_snapshot`

不新增第二套聊天页初始化查询。

聊天页依赖的最小数据仍来自现有 `RoomSnapshot`：

- `room_id`
- `room_code`
- `messages`

因此本轮聊天页初始化的契约范围是：

- 复用 `join_or_create_room_by_code`
- 复用 `load_room_snapshot`
- 不新增 `load_chat_screen`、`open_room_snapshot` 之类平行查询

### 9.4 顶部导航

聊天页顶部本轮先只要求显示：

- 群标题 / 群号

本轮不强行加入：

- 成员数真相
- 在线人数真相
- 复杂资料页入口

## 10. Realtime 接入设计

### 10.1 后端复用原则

后端继续复用当前已收口完成的 realtime 主通道：

- 身份承接走 cookie + connect middleware + extension
- handler 直接进 application
- `socketioxide` 原生 room / emit / broadcast

### 10.2 前端接入原则

前端进入聊天页后：

1. 先通过 HTTP 拉房间快照
2. 再建立 realtime 连接
3. 再订阅房间流

理由：

- 先拿快照，后接增量，避免“空白页等实时消息”体验
- 保持快照与事件语义清楚

### 10.2.1 快照与订阅之间的补齐语义

本轮必须明确处理“快照返回到订阅成功之间的新消息窗口”，否则实现会漂。

固定策略如下：

1. 前端先调用 `load_room_snapshot`
2. 前端立即发起 realtime 连接与 `subscribe_room_stream`
3. 订阅确认成功后，前端**立即再拉一次 `load_room_snapshot`**
4. 第二次快照覆盖或合并第一份快照期间的缺口
5. 之后只依赖 realtime 增量事件推进

选择这个策略，而不是本轮新增游标/消息序号同步协议，原因是：

- 复用现有稳定查询即可闭合窗口
- 不需要在这一轮额外设计消息游标、事件序号、追赶协议
- 范围更克制，更适合当前仓库体量

实现约束：

- 第二次快照不是永久轮询，只在订阅成功后做一次补齐
- 前端合并逻辑必须按消息稳定标识去重，避免把补齐快照和 realtime 事件重复渲染成两条消息
- 如果后续需要真正的游标式一致性追赶，再单独开 spec，不在本轮顺手扩协议

### 10.3 事件语义

前端应直接消费现有稳定事件：

- `room_stream_subscribed`
- `message_accepted`
- `message_created`
- `command_rejected`

前端禁止再定义一套 transport-only 伪语义去替代后端事件真相。

---

## 10.4 前台交付模型

本轮必须明确一个统一的公网交付模型，避免实现阶段在“前端怎么打开”上漂移。

交付模型固定为：

- 浏览器通过同源 Web 入口加载前台聊天壳
- 前台壳通过同源 HTTP API 访问后端
- 前台壳通过同源 Socket.IO 路径接入 realtime

目标效果是：

- 用户打开一个网页入口即可使用
- 不要求用户分别启动“前端 dev server”和“后端 API server”才能体验
- 不把公网部署形态拆成难维护的双入口体验

实现上允许：

- 由 Axum 提供前台静态壳资源
- 或由稳定的一体化开发/部署装配提供同源访问

但不允许：

- 把“前端怎么打开”留成实现阶段再临时决定
- 让最终部署形态长期依赖两个互相独立、体验割裂的公网入口

## 11. 代码组织原则

### 11.1 简洁高效优先

本轮实现必须满足：

- 不增加新的私有 UI framework
- 不新增多层 manager / coordinator / facade
- 不为“高还原 UI”拆出大量低价值文件海
- 保持组件边界清楚、状态源头明确

### 11.2 建议的代码组织方向

优先在现有文件中收口职责，而不是无节制增加新文件。

允许的新增抽象必须满足：

- 真能降低理解成本
- 真能降低重复
- 真能保护边界

不允许仅仅因为“这样看起来更高级”就新增中间层。

### 11.3 反债务约束

以下做法本轮默认禁止：

- 为页面导航再包一层 app router framework
- 为搜索再包一层 search manager

## 13. 风险与控制

### 风险 1：高还原 Telegram 壳导致范围膨胀

控制：

- 只做普通用户聊天主链路
- 不混 admin
- 不混联系人/账号体系
- 不混媒体消息

### 风险 2：为了高还原 UI 引入第二套前端栈

控制：

- 前端继续沿 Dioxus + Rust + CSS 主线
- 不引入 React / Tailwind / UI kit

### 风险 3：前端状态机长成第二套业务真相

控制：

- 会话列表、消息、房间进入真相都留在后端
- 前端只保留壳层体验态

### 风险 4：为了纯 Rust 手搓浏览器 realtime 协议层

控制：

- 先服从 `socketioxide` 官方兼容路径
- 不手搓浏览器 Socket.IO 协议

### 风险 5：群号规则未来增长时，当前实现写死长度

控制：

- UI 文案、前端校验、查询接口都不把 `5 位` 散落写死
- 统一从稳定规则来源取约束
