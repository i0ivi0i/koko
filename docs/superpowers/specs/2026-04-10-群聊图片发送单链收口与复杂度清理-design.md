# 2026-04-10 群聊图片发送单链收口与复杂度清理设计

## 背景

当前群聊图片发送能力同时存在两类复杂度：

1. 必要复杂度
   图片先形成附件真相，再被消息引用；消息成立不能靠前端自说自话；附件内容读取还受成员可见性约束。
2. 垃圾复杂度
   新旧上传链并存，前端壳承担过重上传状态机，错误流与测试流围绕双链扩散，导致 bug 多、排障慢、增删改阻力大。

本设计的目标不是继续补丁修上传，而是把图片发送能力收口成唯一主链，删除旧链和冗余状态，让后续维护回到可读、可测、可定位的状态。

## 目标

1. 图片发送只保留一条主链：`prepare -> 本地回环/对象存储直传 -> complete -> create_message`
2. 删除旧的 `POST /api/attachments/image` 上传链，不做兼容保留
3. 保留 DDD 边界：附件真相、消息真相、壳层体验态各归其位
4. 保留 Unix 哲学：每层只做一件事，不保留双活路径，不重复手搓同类能力
5. 让失败路径统一、可见、可重试，不再出现“上传中卡死”“草稿消失”“真假成功混淆”

## 非目标

1. 本轮不引入视频、语音、文件等其它附件种类
2. 本轮不改变消息领域模型对“图片附件可进入消息”的业务裁决
3. 本轮不要求本地开发环境真的切到远端对象存储服务
4. 本轮不顺手重做整个聊天壳，只收口与图片发送直接相关的职责

## 唯一主链

### 前端

1. 用户选图后，前端只创建本地草稿体验态
2. 前端只调用 `prepareImageUpload`
3. 上传器只根据 `prepare` 返回的上传参数执行 PUT
4. 上传完成后，前端只调用 `completeImageUpload`
5. 只有 `complete` 返回 ready 附件快照后，草稿才允许进入 `ready`
6. 用户发送消息时，前端只上送 `text + attachment_ids`
7. 带图消息不插入本地伪权威消息，最终仍以 `room_event` 为准

### 后端

1. `prepare_image_upload` 只创建 prepared 附件真相并返回上传参数
2. `upload_prepared_image_content` 仅作为 local 模式的上传桥，不创建消息，不升级 ready
3. `complete_image_upload` 负责读取真实对象、解码图片、确认真实 MIME、生成缩略图、升级附件为 ready
4. `create_message` 只接受已 ready 的 `attachment_ids`
5. `load_attachment_content` 继续按会话与消息可见性裁决图片读取权限

## 边界划分

### domain / application

只保留以下业务真相：

1. 附件状态：prepared / ready
2. 附件 owner
3. 附件是否允许进入消息
4. 消息是否成立
5. 附件内容可见性

不把以下内容带入领域或应用层：

1. 预览 URL
2. 上传进度条
3. 重试按钮
4. watchdog 定时器
5. Uppy 事件细节

### adapter / http

图片相关 HTTP 入口只保留：

1. `prepare_image_upload`
2. `upload_prepared_image_content`
3. `complete_image_upload`
4. `load_attachment_content`

明确删除：

1. `upload_image_attachment`
2. 围绕旧入口存在的专用诊断分支
3. 任何“新旧两套上传都支持”的协议翻译

### frontend transport

传输层只保留：

1. `prepareImageUpload`
2. `completeImageUpload`
3. `buildAttachmentContentUrl`

明确删除：

1. `uploadImageAttachment`
2. 老链专用响应类型和测试断言

### frontend shell

聊天壳只保留三类职责：

1. 本地图片草稿体验态
2. 上传器事件到草稿状态的桥接
3. ready 草稿到 `sendMessage` 命令的转接

聊天壳不再承担：

1. 双上传链判断
2. 旧接口兼容
3. 与消息主链无关的第二套成功语义

## 删除范围

必须在同一轮删除，不能留活口：

1. 后端旧路由 `/api/attachments/image`
2. `房间外壳.rs` 中旧直传实现与相关分支
3. `前端传输端口` 中 `uploadImageAttachment`
4. 前端测试假件中旧上传实现
5. 集成测试、传输测试、夹具中所有针对旧链的断言
6. 任何“为了平滑迁移先留着”的双链兼容代码

## 错误流

### 允许的失败收口

1. `prepare` 失败：草稿进入 failed，可重试
2. 上传过程失败、stalled 或 watchdog 超时：草稿进入 failed，可重试，不允许消失
3. `complete` 失败：草稿进入 failed，不允许误标 ready
4. `create_message` 失败：ready 草稿不得被偷偷清空，用户仍可再次发送或移除

### 禁止出现的错误表现

1. 上传失败后草稿直接消失
2. 字节上传成功就把消息当成功
3. `complete` 未完成却允许发送
4. 带图消息失败后，前端与后端对成功状态各说各话

## 元数据原则

当前图片附件最小元数据保留：

1. `attachment_id`
2. 真实 `mime_type`
3. `width`
4. `height`
5. 原图存储键
6. 缩略图存储键
7. 状态

原则：

1. 解码图片是必要动作，因为需要确认真实 MIME 并生成缩略图
2. `width/height` 仅作为附件元数据服务渲染和稳定布局，不上升为额外业务语义
3. 不在本轮继续引入更多媒体元数据字段

## 测试策略

### 必须保留并重写到唯一主链的测试

1. `prepare -> upload -> complete -> create_message` 成功链
2. 上传 stalled / watchdog 超时后草稿失败但不消失
3. `complete` 失败后草稿失败且不可发送
4. 只有 ready 附件才能进入消息
5. `create_message` 失败时 ready 草稿不丢失
6. 房间快照和增量事件仍能带出图片附件
7. 附件内容读取仍按成员可见性裁决

### 必须删除的测试

1. 旧 `/api/attachments/image` 上传成功链测试
2. 旧传输层 `uploadImageAttachment` 测试
3. 任何为双链兼容而存在的假件行为

## 实施约束

1. 先删旧链，再收口前端壳职责，避免新旧逻辑继续纠缠
2. 每次删除或收口都必须先有失败测试锁住唯一主链
3. 不新增第二套上传状态机，不重复包装成熟上传轮子
4. 不把“未来可能上对象存储”实现成现在的双链复杂度

## 风险

1. 删除旧链会影响现有测试夹具和部分集成测试，需要同轮更新
2. `create_message` 失败后的 ready 草稿恢复策略若没锁测试，容易再次出现“草稿丢失”
3. 前端壳收口时如果不显式命名体验态与业务真相边界，容易再次长出混合状态机

## 验收标准

1. 代码中不再存在 `uploadImageAttachment` 和 `/api/attachments/image`
2. 图片发送相关入口只剩唯一主链
3. 前端与后端测试全部围绕唯一主链通过
4. 图片失败路径统一表现为“草稿保留且可定位失败原因”
5. 后续维护者能够沿着单一链路快速定位 bug：`prepare -> upload -> complete -> create_message`

## 备注

本设计在本地 Win11 开发环境下继续使用本地目录作为对象存储适配器；未来部署到 Linux 公网服务器时，仅替换存储适配器，不改变图片发送主链、业务语义和共享契约。
