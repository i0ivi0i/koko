# 2026-04-10 群聊图片发送单链收口与复杂度清理设计

## 背景与判断

这轮不是继续补一个图片上传 bug，而是针对当前“图片发送能力已经进入迁移期双活、壳层过厚、排障成本过高”的结构性问题做一次收口。

当前源码里，图片发送复杂度已经不是单点问题，而是贯穿后端路由、HTTP handler、应用用例、前端 transport、聊天壳、测试夹具的整条链路问题。

重新勘察后的关键证据如下：

1. 后端路由同时存在新旧两条上传链
   `src/外壳.rs` 同时挂载：
   - `/api/media/image/prepare`
   - `/api/media/{attachment_id}/upload`
   - `/api/media/{attachment_id}/complete`
   - `/api/attachments/image`

2. HTTP handler 同时存在新链和旧链
   `src/房间外壳.rs` 同时保留：
   - `prepare_image_upload`
   - `upload_prepared_image_content`
   - `complete_image_upload`
   - `upload_image_attachment`

3. 前端 transport 同时暴露两种上传心智模型
   `frontend/传输.ts` 同时存在：
   - `prepareImageUpload`
   - `completeImageUpload`
   - `uploadImageAttachment`

4. 前端聊天壳承担过多图片上传职责
   `frontend/聊天壳.ts` 约 2000 行，既负责页面壳，也负责：
   - Uppy 初始化
   - 本地图片预处理
   - prepare 调用
   - upload-success/error/stalled/watchdog
   - 草稿状态推进
   - 失败诊断
   - 重试
   - 预览 URL 生命周期
   - 发送前 attachment_id 提取

5. 测试也在维护双链
   - `frontend/tests/传输测试.spec.ts` 同时测试旧 `uploadImageAttachment` 和新 `prepare/complete`
   - `tests/集成测试.rs` 同时覆盖旧 `/api/attachments/image` 和新主链

这说明当前复杂度不是“图片发送天然复杂”，而是“必要复杂度 + 迁移期垃圾复杂度”叠在一起：

1. 必要复杂度
   - 图片先形成附件真相，再被消息引用
   - 后端必须确认真实图片内容，而不是信前端扩展名或 MIME
   - 消息成立只能认 `ready attachment`

2. 垃圾复杂度
   - 双上传链长期共存
   - 壳层承担过重状态机
   - 测试继续替双链兜底
   - 历史兼容逻辑继续扩散到新代码

本设计的目标，就是把这些垃圾复杂度一口气删掉，并把图片发送能力收口成单一、可读、可测、可定位的主链。

## 目标

1. 图片发送只保留唯一主链：
   `prepare -> 本地回环/对象存储直传 -> complete -> create_message`
2. 删除旧的 `POST /api/attachments/image` 及其整条实现、传输接口、测试、夹具，不做兼容保留
3. 把前端图片发送相关逻辑从 `frontend/聊天壳.ts` 抽离到 `frontend/图像/`
4. 保留 DDD 边界：
   - 附件真相收口到 `application / adapter`
   - 消息成立真相收口到 `application / domain`
   - 草稿、预览、watchdog、失败提示只属于前端壳层体验态
5. 保留 Unix 哲学：
   - 每个模块只做一件事
   - 不再保留双活路径
   - 不重复手搓第二套上传器
6. 让 bug 排查路径足够短：
   - 上传链问题先查 `frontend/图像/图片收发.ts`
   - 草稿真相问题先查 `frontend/图像/图片草稿.ts`
   - 后端主链问题沿 `prepare -> upload -> complete -> create_message` 查

## 非目标

1. 本轮不扩展视频、音频、语音、文件发送
2. 本轮不做“通用附件系统”泛化
3. 本轮不改动消息领域规则对“图片附件可进入消息”的裁决
4. 本轮不把本地 Win11 开发环境改成真实远端对象存储
5. 本轮不重写整个聊天页面，只重写与图片发送复杂度直接相关的边界

## 轮子复用与依赖原则

本轮复杂度清理不是“把旧代码拆散后换成新手搓私有层”，而是明确站在已经验证过的成熟轮子肩膀上，把项目代码压缩回业务编排和薄适配层。

必须继续复用的成熟能力：

1. 前端上传继续复用 `@uppy/core` 与 `@uppy/aws-s3`
   - Uppy 继续作为唯一上传器核心
   - 本轮只允许把 Uppy 事件桥接、状态收口、壳层接线抽离到 `frontend/图像/图片收发.ts`
   - 不允许再包出一套私有“上传平台”“上传内核”“上传管理器”来复制它的职责

2. 前端图片转码继续复用 `heic2any`
   - HEIC/HEIF 转码继续站在现有依赖上
   - 不允许为了“统一风格”再手搓私有图片转码流程

3. 后端对象存储继续复用 `object_store`
   - local 文件系统与未来 S3 兼容直传都继续基于 `object_store`
   - 不允许再手搓第二套私有对象存储抽象或上传签名器核心

4. 后端图片探测、解码、缩略图与 EXIF 处理继续复用：
   - `infer`
   - `image`
   - `kamadak-exif`
   这些库已经覆盖当前所需的真实 MIME 探测、解码、方向修正、缩略图生成能力

禁止新增的私有重复层：

1. 私有上传器核心
2. 私有图片解析器或 MIME 探测器
3. 私有对象存储 SDK 包装核心
4. 与成熟依赖职责等价、但只服务当前图片链的二次基础设施平台层

允许新增的代码只应属于：

1. 业务编排
2. 草稿状态收口
3. 壳层接线
4. 失败诊断归一化
5. 薄适配层

如果后续有人想偏离上述依赖复用原则，必须先给出明确证据：

1. 当前成熟依赖在哪个具体边界不满足需求
2. 为什么薄适配不能解决
3. 新增私有实现要替代什么、删除什么、如何避免双核心并存
4. 如何验证它不是“为了统一而统一”的重复造轮子

## 保留的必要复杂度

以下复杂度必须保留，不能误删：

1. `complete` 阶段后端读取真实字节并解码图片
   理由：
   - 确认真实 MIME
   - 获取真实宽高
   - 生成缩略图
   当前逻辑位于 `src/房间外壳.rs` 的 `解析图片内容`

2. `create_message` 只能接受 ready 附件
   理由：
   - 图片字节上传成功，不等于消息成立
   - prepared 附件不得进入消息主链
   当前逻辑位于 `src/用例.rs` 的 `创建消息`

3. 附件内容读取仍按成员可见性裁决
   理由：
   - 图片不是公开静态资源
   - 不能因为附件存在就允许任何会话读取
   当前逻辑位于 `src/用例.rs` 的 `读取附件内容`
   和 `src/适配.rs` 的附件内容查询

4. 本地开发继续允许“本地目录 + 本地回环 PUT”
   理由：
   - 当前开发环境不需要真实对象存储
   - 但要保留对象存储语义边界，未来部署 Linux 公网服务器时只换适配器，不换主链

## 目标架构

### 后端唯一主链

1. `prepare_image_upload`
   - 校验 `session_id / file_name / mime_type / byte_size`
   - 创建 prepared 附件真相
   - 返回 `attachment_id + upload_url + upload_headers`

2. `upload_prepared_image_content`
   - 仅在 local 模式下作为 PUT 回环入口
   - 复用 prepared 真相校验
   - 不创建消息
   - 不升级 ready

3. `complete_image_upload`
   - 读取原图对象
   - 解码图片
   - 校验真实 MIME
   - 生成缩略图
   - 写入 ready 附件真相

4. `create_message`
   - 接受 `text + attachment_ids`
   - 校验 owner / status / kind
   - 只允许 ready 图片附件进入消息

5. `load_attachment_content`
   - 继续按成员可见性裁决 original / thumbnail 读取

### 前端唯一主链

1. 选图后先形成本地草稿体验态
2. 调用 `prepareImageUpload`
3. 把 prepare 返回的上传参数交给 Uppy PUT
4. 上传完成后调用 `completeImageUpload`
5. `complete` 成功后草稿进入 `ready`
6. 发送消息时只提交 `attachmentIds`
7. 带图消息最终仍以权威 `room_event` 为准

## `frontend/图像/` 目录结构

本轮允许新增 `.ts` 文件，但必须集中在 `frontend/图像/`，不把图片发送逻辑继续散落在 `frontend/` 根目录。

目标目录：

- `frontend/图像/index.ts`
- `frontend/图像/图片草稿.ts`
- `frontend/图像/图片收发.ts`
- `frontend/图像/图片预处理.ts`
- `frontend/图像/图片上传诊断.ts`
- `frontend/图像/图片草稿视图.ts` 可选，仅当 `聊天壳.ts` 仍明显过厚时启用

### `frontend/图像/图片草稿.ts`

职责：

1. 定义图片草稿相关纯状态操作
2. 写入草稿
3. 更新草稿状态
4. 移除草稿
5. 提取可发送 `attachmentIds`
6. 回收本地 `previewUrl`
7. 作为 `房间实时编排.ts` 提取可发送图片附件标识的唯一来源，避免再次散落一份独立判定逻辑

约束：

1. 不依赖 Uppy
2. 不直接调用 transport
3. 不直接碰 socket / realtime
4. 尽量保持为纯函数或极薄的 state helper

### `frontend/图像/图片预处理.ts`

职责：

1. 识别图片 MIME
2. 扩展名修正
3. HEIC/HEIF 转码
4. 本地大小上限前置校验
5. 预览地址创建辅助

约束：

1. 只处理“上传前文件规范化”
2. 不负责草稿状态推进
3. 不负责 Uppy

### `frontend/图像/图片上传诊断.ts`

职责：

1. 安全解析上传失败响应体
2. 提取稳定错误码
3. 以 `attachment_id` 为主关联键归一化 `prepare / PUT / complete` 诊断上下文
4. 记录上传诊断日志

约束：

1. 只做失败归一化与日志
2. 不推进草稿状态
3. 不拥有任何 DOM 或页面逻辑
4. `attachment_id` 来自 `prepare` 返回值，是新主链唯一稳定关联锚点
5. 不得再把 `x-koko-upload-id` 视为 canonical 诊断主键；未来如有网关请求 id，也只能作为附加上下文

### `frontend/图像/图片收发.ts`

职责：

1. 初始化 Uppy
2. 绑定 `file-added / upload-progress / upload-success / upload-error / upload-stalled / file-removed`
3. 串起 `prepare -> addFile -> upload -> complete`
4. 维护 watchdog
5. 处理上传失败重试
6. 把上传事件翻译成草稿状态动作
7. 通过明确依赖端口与回调工作，例如：
   - 当前 `sessionId`
   - `transport.prepareImageUpload / completeImageUpload`
   - `图片草稿.ts` 的状态操作
   - 壳层传入的清理与刷新回调

约束：

1. 不负责页面壳渲染
2. 不直接负责消息发送
3. 不再手搓第二套上传器
4. 只复用 Uppy，不再围绕 Uppy 包第二个私有大轮子
5. 不允许直接依赖 `LitElement`、`聊天壳.ts` 或整份 `聊天状态` 实现细节；否则这种拆分只是“把厚逻辑换个文件继续耦合”

### `frontend/图像/图片草稿视图.ts`

是否启用：

1. 如果拆出上面 4 个文件后，`frontend/聊天壳.ts` 仍明显过厚，再启用
2. 如果拆出后 `聊天壳.ts` 已经降到合理复杂度，则不强制启用

职责：

1. 渲染草稿带 DOM
2. 渲染失败文案
3. 转发移除/重试按钮事件

约束：

1. 只做视图
2. 不拥有上传编排
3. 不直接操作状态

### `frontend/图像/index.ts`

职责：

1. 收口图像 feature 对外导出
2. 让 `frontend/聊天壳.ts` 只从一个 feature 入口依赖图片发送能力

## `frontend/聊天壳.ts` 重构后的职责

保留：

1. 页面级渲染
2. 发送区图片入口按钮
3. 文件选择 DOM 事件接线
4. 调用图像 feature
5. 房间恢复、realtime、阅读推进、页面切换
6. 页面退出时统一清理图像 feature

3. 上传失败诊断细节

## 数据流

### 成功链

1. 用户在输入区点“选择图片”
2. `聊天壳.ts` 把文件交给 `frontend/图像/图片收发.ts`
3. `图片预处理.ts` 规范化文件
4. `图片收发.ts` 调用 `transport.prepareImageUpload`
5. `图片收发.ts` 把 prepare 返回参数交给 Uppy PUT
6. Uppy 成功后，`图片收发.ts` 调用 `transport.completeImageUpload`
7. complete 返回 ready 附件快照
8. `图片草稿.ts` 把草稿推进到 `ready`
9. 用户发送消息
10. `房间实时编排.ts` 从 `composerImageDrafts` 中提取 ready `attachmentId`
11. socket 发出 `create_message`
12. 后端 `create_message` 校验并落权威事件
13. 前端以 `room_event` 为准完成时间线显示

### 失败链

1. `prepare` 失败
   - 草稿进入 failed
   - 保留预览
   - 用户可重试或移除

2. PUT 失败
   - 草稿进入 failed
   - 保留预览
   - 用户可重试或移除

3. `upload-stalled`
   - 草稿进入 failed
   - 不允许继续卡在 uploading

4. watchdog 超时
   - 草稿进入 failed
   - 不允许凭空消失

5. `complete` 失败
   - 草稿进入 failed
   - 不允许误标 ready

6. `create_message` 失败
   - ready 草稿不得被偷偷清空
   - 用户仍可再次发送或移除

## 错误与状态不变量

以下不变量必须在代码和测试里同时成立：

1. 上传失败后草稿不能直接消失
2. `upload-success` 不等于消息成功
3. `complete` 之前附件不能进入消息主链
4. 只有 `status=ready` 且 `attachmentId` 非空的草稿才可发送
5. 发送失败时 ready 草稿不能无声丢失
6. 页面退出、离房、断开时，本地预览 URL 必须被回收
7. 本地回环上传只属于 local 模式，不能倒灌成第二业务主链

9. 只有 ready 草稿才能被 `房间实时编排.ts` 提取为 `attachmentIds`

2. `图片预处理.ts`
   - MIME 推导
   - HEIC/HEIF 转码前后行为
   - 大小前置校验

3. `图片上传诊断.ts`
   - 错误码提取
   - `attachment_id` 关联键归一化
   - 响应体解析

4. `图片收发.ts`
   - prepare 到 complete 的编排
   - stalled/watchdog/retry 行为

5. `聊天壳.ts`
   - 只保留页面接线与渲染测试

## 迁移顺序

为了降低回归风险，本轮按以下顺序实施：

1. 先补 characterization tests，锁住当前唯一主链与关键失败路径
2. 同步删除前端旧链：
   - `前端传输端口.uploadImageAttachment`
   - `frontend/传输.ts` 中旧实现
   - `frontend/tests/传输测试.spec.ts` 旧测试
   - 所有旧链假传输/测试桩实现
   这一小步完成后，前端应保持可编译、可测试，不允许长时间红
3. 同步删除后端旧链：
   - `/api/attachments/image`
   - `upload_image_attachment`
   - `登记图片附件`
   - 旧链集成测试
   这一小步完成后，后端应保持可测试，不允许把“先删实现后补测试”拖成大红窗
4. 新建 `frontend/图像/` 目录和 `index.ts`
5. 抽出 `图片草稿.ts`
6. 抽出 `图片预处理.ts`
7. 抽出 `图片上传诊断.ts`
8. 抽出 `图片收发.ts`
9. 如有必要，再抽 `图片草稿视图.ts`
10. 收尾精简 `frontend/聊天壳.ts`
11. 全量跑 Rust + frontend 测试
   - 至少执行 `cargo test`
   - 至少执行 `pnpm --dir frontend test`
   - 至少执行 `pnpm --dir frontend typecheck`
12. 清理死代码、死注释、残留旧命名

原因：

1. 先锁测试，再删旧链，避免把“是否还能工作”交给猜
2. 每一小步删除都必须连同对应测试和假件一起更新，仓库始终保持在可验证状态
3. 先删旧链，避免把历史垃圾结构搬进新文件
4. 先纯状态，再上传编排，最后再收壳层，风险最低

## 风险与防护

### 风险

1. 删除旧链会导致测试和支架一次性报红
2. 前端拆模块时，草稿状态和 Uppy 事件顺序容易被改坏
3. `create_message` 失败后的 ready 草稿保留策略容易回归
4. `file-removed` 与 watchdog/stalled 的相互作用容易再次制造“草稿消失”

### 防护

1. 每一步删除都先补红测再落实现
2. 不在同一个提交里同时做“删旧链 + 改视觉”
3. 不允许新增 fallback 和兼容桥
4. 所有“草稿不消失”的行为都必须有测试锁死
5. 所有模块拆分都必须通过显式依赖端口/回调接线，禁止新文件直接反向依赖 `聊天壳.ts`
6. 不能承诺绝对零 bug，但必须通过删双链、减热点、补测试来最大化降低结构性 bug 再发概率

## 验收标准

1. 代码中不再存在：
   - `/api/attachments/image`
   - `upload_image_attachment`
   - `uploadImageAttachment`
   - `登记图片附件`

2. 图片发送相关代码能沿单一路径读通：
   `prepare -> upload -> complete -> create_message`

3. `frontend/聊天壳.ts` 不再承担完整图片上传状态机

4. 图片发送 feature 收口在 `frontend/图像/`

5. 前端与后端测试全部围绕唯一主链通过

6. 真实用户遇到失败时，表现统一为：
   - 草稿保留
   - 错误可见
   - 可以重试或移除
   - 不再出现“上传中后凭空消失”

7. 后续维护者排障时，可以明确按以下顺序定位：
   - 前端草稿问题：`frontend/图像/图片草稿.ts`
   - 前端上传编排问题：`frontend/图像/图片收发.ts`
   - 前端文件预处理问题：`frontend/图像/图片预处理.ts`
   - 前端失败诊断问题：`frontend/图像/图片上传诊断.ts`
   - 后端主链问题：`prepare -> upload -> complete -> create_message`

## 备注

1. 本轮目录名固定为 `frontend/图像/`，不提前泛化为“通用附件目录”
2. `图片草稿.ts` 的命名比“附件发送.ts”更准确，因为当前只处理图片草稿本地体验态
3. 未来若要扩展视频、音乐、语音，再单独评估是否抽出更通用的附件层，不在本轮提前泛化
