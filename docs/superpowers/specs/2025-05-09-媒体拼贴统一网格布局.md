# 媒体拼贴统一网格布局

**日期**: 2025-05-09
**状态**: 设计已确认，待实施
**涉及模块**: `frontend/房间消息窗/媒体拼贴几何.ts`, `frontend/tests/媒体拼贴几何.spec.ts`

---

## 1. 背景与问题

### 1.1 当前实现

当前多媒体附件拼贴采用移植自 Telegram Web K 的 `groupedLayout` 算法（`媒体拼贴几何.ts`，614 行）。该算法的核心思想是**保持每个媒体的原始宽高比**，根据媒体数量和方向组合选择最优排列模板：

- 2 张：按比例分左右宽度，横屏给宽卡片、竖屏给窄卡片
- 3 张：首张竖屏则"左列满高 + 右列两叠"；首张横屏则"上行满宽 + 下行两并排"
- 4 张：类似 3 张的变体，增加一列或一行
- 5~10 张：暴力搜索 2~4 行的最优分配方案

### 1.2 存在的问题

**问题一：视觉重量严重不均匀**

混合横竖屏视频时，算法为了保持原始比例会给不同媒体分配差异极大的卡片面积。例如 3 个视频（1 竖 2 横），竖屏可能占整个容器的 60% 面积，而两个横屏分别只占 20%。用户发了 3 个同等重要的视频，但展示上有的大有的小，视觉传达不均匀。

**问题二：奇数视频排列尤其不整齐**

3 个、5 个、7 个视频时，Telegram 模板会制造"一大多小"的非对称布局。这在桌面端尚可接受（屏幕宽），但在聊天消息流的有限宽度（248~384px）内，小卡片被挤到几乎看不清内容。

**问题三：横屏视频在拼贴卡片内的黑边/闪烁**

这是触发本次改动的直接 bug。当横屏视频被放入一个竖向比例的卡片时，Video.js canonical player 的 `provider/container` 使用 `aspect-ratio` 约束和无 `height:100%` 的布局，导致视频无法铺满卡片，露出黑色背景。在 poster(cover) 到 canonical(contain 区域) 切换时产生闪烁。

> 注：黑边/闪烁的直接修复已在本次前序工作中完成（`videojs播放器壳.ts` 的 `同步播放器挂载布局` 检测 `data-presentation="inline"` 时使用 `height:100%` 无 `aspect-ratio` 布局）。但根本原因是拼贴算法本身产生了与视频原始比例差距过大的卡片形状，本 spec 从源头解决。

### 1.3 设计决策

放弃 Telegram 的"保持原始比例的智能拼贴"，改为**统一卡片形状的均匀网格**。理由：

1. **万人群聊场景**：消息流信息密度高、滚动快，均匀网格的视觉扫描效率远高于非对称拼贴
2. **视频为主**：项目媒体以视频为主（不是图片画廊），视频内容靠播放而非静态预览传达，卡片形状一致性比单帧预览的比例保真更重要
3. **cover 裁切可接受**：所有视频/图片已使用 `object-fit: cover`，统一卡片只是增加裁切量，不会出现黑边或变形

## 2. 设计规格

### 2.1 核心参数

| 参数 | 值 | 说明 |
|------|-----|------|
| 卡片比例 | **2:3（宽:高）** | 竖向修长型，接近 TG/Instagram Stories |
| 每行列数 | **固定 2 列** | 卡片更大更清晰，适合有限宽度消息流 |
| 间距 | **8px** | 保持现有 |
| 最大数量 | **10** | 保持 TG 上限 |
| 容器最大宽度 | **配置传入（默认 384px）** | 保持现有 |

### 2.2 各数量布局规则

**单张（count = 1）**：保持现有行为不变，按原始比例缩放到 `maxWidth`。

**2 张及以上（count ≥ 2）**：统一网格布局。

计算公式：
```
cols = 2
cellWidth = (maxWidth - spacing) / cols
cellHeight = cellWidth * 3 / 2          // 2:3 比例
rows = ceil(count / cols)
lastRowCols = count - (rows - 1) * cols // 最后一行实际列数
```

**正常行（非最后一行）**的每张卡片：
```
x = col * (cellWidth + spacing)
y = row * (cellHeight + spacing)
width = cellWidth
height = cellHeight
```

**最后一行**的处理：
- **偶数（lastRowCols === 2）**：与正常行一致
- **奇数（lastRowCols === 1）**：单张卡片拉满整行宽度
  ```
  x = 0
  y = lastRow * (cellHeight + spacing)
  width = maxWidth                      // 拉满
  height = cellHeight                   // 行高不变
  ```

### 2.3 具体布局示意

以 `maxWidth = 384, spacing = 8` 为例：

```
cellWidth  = (384 - 8) / 2 = 188
cellHeight = 188 * 3 / 2   = 282

2 张:  [188×282] [188×282]                    totalHeight = 282
3 张:  [188×282] [188×282]                    totalHeight = 282+8+282 = 572
       [    384×282     ]
4 张:  [188×282] [188×282]                    totalHeight = 572
       [188×282] [188×282]
5 张:  [188×282] [188×282]                    totalHeight = 282+8+282+8+282 = 862
       [188×282] [188×282]
       [    384×282     ]
6 张:  [188×282] [188×282]                    totalHeight = 862
       [188×282] [188×282]
       [188×282] [188×282]
10 张: 5 行 × 2 列                            totalHeight = 282*5+8*4 = 1442
```

### 2.4 容器总高度计算

```
totalHeight = rows * cellHeight + (rows - 1) * spacing
```

### 2.5 contentWidth

始终返回 `maxWidth`（保持现有契约不变）。

## 4. 实现策略

### 4.1 替换而非追加

当前 `媒体拼贴几何.ts` 有 614 行，其中 `count >= 2` 的代码（布局两张/三张/四张/复杂布局等内部函数）约 460 行。新算法对 `count >= 2` 的逻辑只需约 30~40 行。

**删除**：`布局两张`、`布局三张`、`布局四张`、`复杂布局`、`均分兜底` 及所有子函数（`两张上下叠`、`两张等宽左右`、`两张按比例左右`、`三张左加右叠`、`三张上加下排`、`四张上加下三列`、`四张左加右三叠`）。

**保留**：`布局单张`（单张行为不变）、`转换为拼贴结果`（仍可复用）、工具函数（`取`、`累加`、`夹紧` — 视需要保留或清理）。

**新增**：统一网格布局函数，代替上述所有多张布局函数。

### 4.2 TDD 执行顺序

1. **RED**：先按新规则重写测试（`媒体拼贴几何.spec.ts`），确认失败
2. **GREEN**：实现新算法，确认测试通过
3. **REFACTOR**：清理死代码和不再需要的内部函数

### 4.3 新测试清单

| 测试用例 | 验收标准 |
|---------|---------|
| 空输入 | 返回空，保持不变 |
| 0 尺寸 fallback | 保持不变 |
| 超过 10 张截断 | 保持不变 |
| 单张横屏 | 保持现有行为（按原始比例缩放） |
| 单张竖屏 | 保持现有行为 |
| 2 张 | 1 行 2 列，两张等宽等高，卡片比例 2:3 |
| 3 张 | 2+1，前两张等宽 2:3，第三张拉满宽度同行高 |
| 4 张 | 2+2，四张全等 2:3 |
| 5 张 | 2+2+1，底部单张拉满 |
| 6 张 | 2+2+2，六张全等 2:3 |
| 10 张 | 5×2，全等 2:3 |
| 混合横竖屏 | 不影响卡片几何（都是统一网格），只影响 cover 裁切 |
| 所有用例无溢出 | `x+width ≤ maxWidth`, `y+height ≤ totalHeight` |
| 统一卡片宽高比 | 正常行卡片 `width/height ≈ 2/3`（容忍取整 ±1px） |

## 5. 风险与边界

### 5.1 裁切量增大

统一 2:3 卡片意味着横屏视频（16:9）会被裁切更多内容。这是**预期行为**——用户已确认视觉均匀性优先于单帧预览的完整性。视频内容靠播放传达，不靠静态缩略图。

### 5.2 最后一行拉满卡片的比例偏离

3 个视频时，底部单张 `384×282` 的比例约 1.36:1（略横），与上行的 2:3 不同。这是**预期行为**——用户选择了"拉满填满"而非"居中缺位"，以避免底部留白。

### 5.3 对现有消息的影响

布局是纯前端实时计算，不持久化。改动后所有已有消息会按新算法重新渲染。不需要迁移，不需要版本判断。

### 5.4 已完成的前序修复

本 spec 实施前，已完成以下修复确保 canonical player 在任何卡片形状下都能正确填满：

- `videojs播放器壳.ts`：`同步播放器挂载布局` 检测 `data-presentation="inline"` 时使用 `width:100%;height:100%` 无 `aspect-ratio`
- `videojs播放器皮肤.ts`：添加 `:host([data-presentation="inline"]) ::slotted(video) { object-fit: cover }` 防御层
- `videojs播放器壳测试.spec.ts`：新增回归测试

这些修复在新算法实施后仍然必要——即使统一网格减少了卡片与视频的比例差距，canonical player 仍需要正确铺满任何尺寸的卡片。
