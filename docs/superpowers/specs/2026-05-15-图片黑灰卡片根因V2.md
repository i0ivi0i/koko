# 图片黑灰卡片 Bug — 根因分析 V2（公网实证）

## 问题现象

万人万群实时群聊 IM（kokoqun.com），用户 A 发送图片后：
- B/C/D **立刻看到灰色占位卡片**（mountain SVG），不是高清图
- 点击全屏 → 半透灰黑一片
- **过很久**（10 秒 ~ 几十秒）才出高清图
- 用户体验：感觉"服务器没发力"

**期望体验**：A 发图 → B 秒看到清晰图片。像微信一样零等待。

---

## V1 spec 的误判

V1 spec（`2026-05-14-接收者图片黑灰卡片根因与修复.md`）基于本地 vs 公网测试，结论是 locator status:0 和 distribution_hint 时序竞态。

**V2 公网双浏览器冒烟测试推翻了 V1 的部分结论**：
- locator 请求 → **200**（不是 status:0）
- content 请求 → **206**（数据确实下载到了）
- distribution_hint 在消息中 → **有**（不是空）
- **连发送者自己都看到灰卡片**

---

## 真正的根因（代码实证）

### 根因：`解析播放结果` 在 WebTorrent 还没下完时就投降

**位置**：`frontend/媒体/媒体播放.ts` 第 777-810 行

时序链：

```
B 收到消息
  → 预热权威消息媒体分发
  → 获取 locator → 200, status: ready
  → 调用 尝试协作分发主链(input, locator)
      → 服务器 media_state.code = "MEDIA_CONNECTING_TO_PEERS"
      → resolveSwarmSource() → null（WebTorrent 还在连接 seeder / web seed）
      → 因为 处于连接群友态 = true:
        return { playback: 创建降级结果("connecting_to_peers"), failureReason: null }

  ← 回到 解析播放结果:
    第 779 行: if (swarmAttempt.playback) ← "connecting_to_peers" 是对象，truthy！
    第 780 行: return swarmAttempt.playback  ← 立即返回降级结果！
    ↓↓↓ 第 798-808 行的重试逻辑被完全跳过 ↓↓↓

  → 媒体会话收到 mode:"degraded" → 渲染灰色占位卡片

同时 WebTorrent 在后台继续：
  → 连接 tracker → 发现 seeder → web seed 开始下载 → 下载完成
  → blob URL 可用了...但没人来取了

过很久后：
  → 某个 UI 事件（滚动、viewport 变化）触发重新解析
  → 这时 WebTorrent 缓存里已经有了 → swarm 成功 → 图片出来
```

### 为什么第 779 行是 bug

```typescript
// 第 777-781 行
const swarmAttempt = await 尝试协作分发主链(input, locator);
locator = swarmAttempt.locator;
if (swarmAttempt.playback) {     // ← 降级结果也是 truthy
  return swarmAttempt.playback;  // ← 直接返回，跳过重试
}
```

`尝试协作分发主链` 对临时状态返回的是**降级对象**（非 null），而不是 null。
降级对象是 truthy → 第 779 行条件为 true → 立即返回 → 第 798-808 行的重试逻辑被跳过。

### 重试逻辑本身没问题

第 798-808 行的重试逻辑设计正确（指数退避 500ms→1s→2s + 20% jitter），但**永远不会被执行**，因为第 779 行把降级结果直接返回了。

### 为什么不能简单改 `if (swarmAttempt.playback)` → `if (swarmAttempt.playback?.mode === "swarm")`

尝试过：导致 3 个测试失败。

`connecting_to_peers` 和 `no_online_seed` 有自己的状态机（8 秒连接窗口 + 15 秒重试间隔），这些状态应该被 UI 消费（显示"正在连接群友"等）。如果让它们走 `解析播放结果` 的重试，会和 `无在线种子连接窗口表` 状态机冲突，且重试耗尽后返回 `anchor_unavailable` 而不是正确的 `connecting_to_peers` 状态。

## WebTorrent 官方最佳实践（调研结论）

| 来源 | 做法 |
|---|---|
| **WebTorrent 官方 Web Seed 文档** | torrent 自带 web seed URL → 无 peer 时自动从 HTTP 下载 → 秒出 |
| **`noPeers` 事件** | 每几秒触发一次，可用于动态添加 web seed 兜底 |
| **PeerTube** | 先 HTTP 播放 → 后台 WebTorrent 预热 → P2P 连上后无缝切换 |
| **WebTorrent `done` 事件** | torrent 下载完成后触发，应在此更新 UI |

**核心洞察：WebTorrent 自身支持通过 web seed 秒下载。问题不在 WebTorrent，在我们的 `解析播放结果` 太早投降。**

---

## 修复方案

### 方案选择：在 `尝试协作分发主链` 内部等待 WebTorrent 就绪

**不改第 779 行**（保持 `connecting_to_peers` 状态机不被破坏），而是让 `尝试协作分发主链` 在首次调用时给 WebTorrent 足够时间通过 web seed 下载。

### 具体设计

当 `resolveSwarmSource()` 返回 null 且处于 `MEDIA_CONNECTING_TO_PEERS` 状态时：

**当前行为**：立即返回 `connecting_to_peers` 降级结果
**修复后行为**：等待一小段时间（指数退避，最多 ~3 秒），期间轮询 `resolveSwarmSource()`，一旦 WebTorrent 下完就返回成功播放结果

```typescript
// 伪代码：在 尝试协作分发主链 内部（第 564-577 行之间）
if (!swarmSource && 处于连接群友态) {
  // 给 WebTorrent 的 web seed 一个时间窗口
  for (const delay of [300, 600, 1200]) {
    await sleep(delay + jitter);
    const retrySource = await resolveSwarmSource({ ... });
    if (retrySource) {
      return { locator, playback: 成功播放结果(retrySource), failureReason: null };
    }
  }
  // 真正超时才返回 connecting_to_peers
  释放协作分发占用(input);
  return { locator, playback: 创建降级结果("connecting_to_peers"), failureReason: null };
}
```

### 关键设计决策

1. **重试在 `尝试协作分发主链` 内部**：不改变 `解析播放结果` 的流程，不破坏现有状态机
2. **只对 `connecting_to_peers` 重试**：`no_online_seed` 和 `media_deleted` 仍然立即返回
3. **最多等 ~2.5 秒**（300+600+1200+jitter）：图片几百 KB 通过 web seed 下载 < 1 秒足够
4. **轮询 `resolveSwarmSource`**：这是已有函数，会检查 WebTorrent 是否有可用的 blob URL
5. **jitter 20%**：避免万人群聊同时重试雷暴

### 不改什么

- 不改 WebTorrent 底层
- 不改 `解析播放结果` 的流程和第 779 行
- 不改 `connecting_to_peers` / `no_online_seed` 状态机
- 不改后端 seeder fire-and-forget 行为
- 不引入 HTTP 直取旁路（项目约束：正式媒体字节只走 WebTorrent）

## 验证标准

1. Playwright 双浏览器公网 kokoqun.com 冒烟测试：
   - 发送者发图 → **发送者自己 < 2 秒看到图片**
   - 接收者 **< 3 秒看到图片**（不是灰色卡片）
2. `media_state与终态提示测试.spec.ts` 3 个测试仍然通过
3. 全量前端测试不引入新的回归
4. WebTorrent 下载统计确认走的是 web seed 路径（不是纯 P2P）

## 风险与边界

| 风险 | 缓解 |
|---|---|
| 等待 2.5 秒期间 UI 无反馈 | `resolveSwarmSource` 轮询间隙可派发 progress 事件 |
| 弱网下 web seed 也慢 | 最多等 2.5 秒就放弃，不会无限卡 |
| 多图消息同时等待 | 每个附件独立等待，不互相阻塞 |
| autoplay 调度器能否容忍 2.5s | 代次守卫保护 stale 结果被丢弃（已验证） |
