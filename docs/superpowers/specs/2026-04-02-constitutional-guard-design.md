# `constitutional-guard` 设计稿

## 1. 背景

现有的 `koko-constitutional-audit` 已经不只是一个“代码写完后的治理审查 skill”。它实际上已经具备了更强的倾向：

- 它会判断手搓轮子、私有基础设施债、DDD 边界污染、前后端越位、`contract` 污染、长期维护风险。
- 它已经能加载内置通用宪法 baseline，并在有项目文档时叠加项目治理 overlay。
- 它的价值观已经明显接近 [审查维护.md](/E:/koko/审查维护.md) 的总目标：让系统长期朝“先进、优雅、可插拔、像乐高积木一样可自由组装”的架构演进。

但它当前仍然有一个结构性缺口：

- 它的产品心智仍然偏“审查器”。
- 它还没有正式升格成“开发前、开发中、开发后都持续守边界的治理器”。
- 它还没有把“写代码前先校准习惯、写代码中持续纠偏、写完后再做治理审查”做成并列的一等模式。

这会导致两个问题：

- skill 的真实能力被低估，触发面偏窄。
- 它容易继续向“越来越重的审查 skill”膨胀，而不是演进成一个清晰、优雅、长期可维护的生命周期治理 skill。

因此，本设计稿的目标不是继续给 `koko-constitutional-audit` 打补丁，而是把它正式升级为一个新的、通用的、宿主无关的 skill：`constitutional-guard`。

---

## 2. 设计目标

### 2.1 核心目标

把现有 skill 升级为一个统一的、生命周期覆盖的宪法治理器，使其在同一套法则下同时覆盖：

- 开发前：防止设计一开始就跑偏
- 开发中：持续轻量纠偏，防止写着写着漂移
- 开发后：继续进行全仓或局部的治理审查

### 2.2 架构目标

`constitutional-guard` 必须帮助项目持续逼近以下状态：

- 不管前端技术、库、框架如何更换，还是后端技术、基础设施、运行时如何迭代，业务真相、功能边界、插件能力和未来 CLI / 移动端扩展能力都不应轻易崩溃。
- 系统应尽量像乐高积木一样依赖稳定契约、稳定边界和成熟生态，而不是依赖 repo 私有框架、私有 wrapper、私有 bridge、私有 manager 或手搓基础设施。
- skill 的默认价值判断必须偏向“站在成熟高性能生态肩膀上”，而不是鼓励“自己再包一层试试”。

### 2.3 使用体验目标

这个 skill 的输出必须：

- 清晰
- 优雅
- 高效
- 高密度
- 少打断
- 少废话
- 少把选择题抛给用户

它的理想形态不是“长篇训话”，而是一个有执行力的同行，在必要时短而硬地把方向拉正。

---

## 3. 非目标

本次升级不追求以下事情：

- 不把 skill 变成自动修复器。
- 不把 skill 变成项目漫游器、依赖树分析器、普通 PR review 器。
- 不把 skill 变成风格、命名、格式、lint 的通用检查器。
- 不让“开发前校准”替代“开发后治理审查”。
- 不把 host-specific 能力假设重新绑死到某个特定 Agent、CLI、App 或厂商能力模型上。

---

## 4. 一等模式与组合路由

`constitutional-guard` 对外只有一个 skill，但对内只有三种一等运行模式；`combo` 不是第四种平级模式，而是一个显式的组合路由策略。

### 4.1 `pre-code calibration`

用于开发前的前置架构校准。

适用场景：

- 用户准备开始写功能
- 用户准备抽象一层
- 用户准备封装 helper / wrapper / bridge / manager
- 用户准备引入依赖
- 用户准备自研某类通用能力
- 用户准备设计接口、契约、边界或前后端职责分工
- 用户只有方案描述，没有现有代码，但需要先判断“这样写会不会跑偏”

默认输出极短四栏：

- `建议落层`
- `复用结论（含在线调研与取舍理由）`
- `边界与长期演进风险`
- `禁止动作`

执行规则：

- 没有现有代码时，先做方案级校准，不等待代码出现才开始判断。
- 有现有代码时，再叠加上下文级校准，检查方案与现状是否冲突。
- 该模式只直接给出校准结论，不顺手推荐别的 skill 来分叉流程。
- 该模式自动介入后，应继续原任务，而不是把流程卡死在新的选择题里。

### 4.2 `in-flight drift correction`

用于开发过程中的持续轻量纠偏。

适用场景：

- 正在执行实现
- 正在重构
- 正在补边界
- 正在引入新抽象或新依赖
- 正在写着写着开始出现漂移苗头

典型漂移信号至少包括：

- 新增 `helper / manager / wrapper / bridge / facade`
- 准备引入新依赖或新运行时接入
- 修改 `contract` 或向共享面塞壳专属语义
- 跨层移动业务真相、权限真相、成员真相或消息成立真相
- 前端开始保存后端之外的权威状态
- handler / repo / socket 回调开始承担业务裁决
- 出现 repo 私有基础设施外壳，准备重复包装成熟生态能力

默认行为：

- 发现明显漂移时，输出极短双句纠偏
- 第一句指出漂移点
- 第二句给出立即纠偏方向
- 然后继续按纠偏后的方向执行
- 没有明显问题时，静默通过

### 4.3 `post-code audit`

用于代码完成后的治理审查。

继续保留现有能力：

- `repo mode`：全仓治理审查
- `focused mode`：局部宪法审查

继续覆盖：

- 手搓成熟轮子
- 重复造轮子
- 私有基础设施债
- DDD 边界污染
- 前后端越位
- `contract` 污染
- 双重真相
- 冗余胶水
- 长期演进风险

### 4.4 `combo` 组合路由

当用户同时给出现有代码和“准备这样改/这样设计/这样抽象”的意图时，不新增第四种平级模式，而是进入固定的组合路由：

1. 先极短点出现状风险
2. 再切入 `pre-code calibration`
3. 然后继续原任务

`combo` 的输出契约继承：

- 第一段使用 `post-code audit` 的极短风险点出能力
- 第二段使用 `pre-code calibration` 的四栏输出

它没有自己的独立价值观，只是两个既有协议的串联执行。
它同样遵循统一执行规则：先极短纠偏或校准，再继续原任务，不额外制造新的决策负担。

## 5. 法则层

三态模式共享同一套法则层，禁止各自维护不同价值观。

法则栈顺序固定为：

1. 内置通用宪法 baseline
2. 项目治理 overlay
3. 外部主源校准

### 5.1 内置 baseline

继续保留并强化 [generic-constitutional-baseline.md](C:/Users/home/.claude/skills/koko-constitutional-audit/references/generic-constitutional-baseline.md) 的作用：

- 业务真相高于框架便利
- 成熟生态复用高于手搓通用能力
- 薄 adapter 高于 repo 私有伪框架
- 多壳共享契约必须保持壳中立
- 重复轮子、重复真相、重复流程都是治理问题
- 长期技术可替换性是核心判断维度

### 5.2 项目 overlay

在目标仓库存在这些文件时，作为 overlay 叠加，而不是替代 baseline：

- `审查维护.md`
- `AGENTS.md`
- `ARCHITECTURE.md`
- 仓库内同等地位的治理文档

治理文档发现与装载顺序必须机械化，禁止靠“看起来哪个更重要”临场拍脑袋：

1. 先找仓库根目录的 `审查维护.md`
2. 再找仓库根目录的 `AGENTS.md`
3. 再找仓库根目录的 `ARCHITECTURE.md`
4. 再找仓库根目录其他明确声明为治理/架构法则的文档
5. 若仍无结果，再退回到内置 baseline-only 模式

装载顺序必须与发现顺序一致；后发现的 overlay 只能补充和收紧，不能弱化先前已装载的更高位法则。

对 `Koko` 而言：

- [审查维护.md](/E:/koko/审查维护.md) 是最高项目治理法则
- [AGENTS.md](/E:/koko/AGENTS.md) 是最高执行 overlay

若两者出现冲突，终审顺序固定为：

1. [审查维护.md](/E:/koko/审查维护.md)
2. [AGENTS.md](/E:/koko/AGENTS.md)
3. 其他仓库治理文档

也就是说：

- `审查维护.md` 决定治理法则与判题
- `AGENTS.md` 决定执行纪律与本仓库操作约束
- 其他文档只能补充，不能反向改写这两者的终审顺序

### 5.3 外部校准

凡是涉及通用能力、基础设施、成熟生态复用、自研准入判断时，优先调用：

- 官方文档
- Context7
- 一手维护方资料
- 已收录的外部 anti-wheel 校准文件

目标不是堆引用，而是回答四件事：

- 为什么该复用
- 为什么不该手搓
- 为什么这个候选更合适
- 为什么别的候选不合适

### 5.4 冲突裁决规则

法则层一旦出现冲突，必须按下面顺序裁决，禁止让不同宿主、不同上下文各自随意理解：

1. baseline 是不可被削弱的最低法则，只能被 overlay 收紧，不能被覆盖掉。
2. overlay 可以增加仓库特有红线、边界和门禁，但不能把 baseline 降格成“仓库里现在怎么写都算合理”。
3. external calibration 只负责校准“复用/自研/成熟生态候选”的判断，不得推翻 baseline 和 overlay 的边界红线。
4. 当多个外部主源冲突时，优先级固定为：
   - 官方文档
   - 维护方一手资料
   - Context7 主源内容
   - 其他最佳实践资料
5. 当 overlay 与 external calibration 在“具体候选怎么选”上冲突时：
   - 边界与红线问题以 baseline + overlay 为准
   - 生态候选问题保留冲突说明，并明确标记为 `调研未完成 / 结论暂定`

任何没有按这组规则裁决的输出，都应视为不合规。

## 6. 路由层设计

`SKILL.md` 应薄化为路由层，而不是继续承载所有细节。

它只负责：

- 判定 skill 是否适用
- 判定当前运行模式
- 做能力协商
- 加载法则层
- 路由到对应模式协议

### 6.1 模式判定优先级

模式判定必须先做一次前置判断：

- 只有同时满足下面三条，才允许进入 `combo` 组合路由：
  - 用户提供了现有代码、现有 diff、现有片段或现有结构作为判断锚点
  - 用户明确或强烈暗示“接下来准备怎么改/怎么抽象/怎么设计”
  - 当前请求的核心不是“我已经在执行实现中，请继续写”，而是“先基于现状判断接下来怎么写”

若不命中 `combo`，再按下面顺序继续判定：

1. 如果用户明显在准备开写、准备抽象、准备自研、准备引依赖，则进入 `pre-code calibration`
2. 如果用户正在执行开发且出现漂移信号，则进入 `in-flight drift correction`
3. 如果用户明确要求全仓或局部治理审查，则进入 `post-code audit`

下列情况禁止误判成 `combo`：

- 纯 `post-code audit`：只审现有代码，不讨论接下来怎么改
- 纯 `in-flight drift correction`：已经在实现过程中，只需要轻量纠偏
- 纯 `pre-code calibration`：没有现有代码锚点，只是在讨论准备怎么写

### 6.2 能力协商

继续保留 host-neutral 能力协商机制，但只允许降级“执行方式”，不允许降级“审查标准”。

### 6.3 统一执行规则

三态模式都必须共享下面这条统一执行规则：

- 自动介入时，先给最短必要的校准/纠偏/审查结论
- 然后继续原任务
- 不默认停下来把选择题抛给用户
- 只有在证据不足且继续执行会明显放大风险时，才允许升级成显式确认

### 6.4 高风险识别器

`constitutional-guard` 不能只会“给建议”，还必须内置高风险识别器，用来判断当前请求是否已经进入不得轻放的治理区间。

默认规则：

- 只要不能被证明为低风险，就按高风险处理

只有同时满足下面条件，才允许被视为低风险：

- 只涉及单一层级
- 不新增依赖
- 不改工具链
- 不改运行时接入
- 不改共享契约
- 不跨层移动业务真相
- 不新增通用 `helper / wrapper / bridge / manager / facade`
- 不触碰热路径
- 不涉及例外放行
- 不涉及债务延期

只要有一条不满足，默认按高风险处理。

高风险信号至少包括：

- 新增依赖
- 工具链或运行时接入调整
- 修改 `contract`
- 跨层移动业务真相
- 触碰权限、成员、消息成立、治理语义真相
- 触碰聊天热路径
- 申请例外放行
- 债务延期
- 跨多个模块或多个文件簇的清理型维护

### 6.5 审查状态机

这个 skill 必须内置和 [审查维护.md](/E:/koko/审查维护.md) 对齐的四态治理状态机：

- `通过`
- `驳回`
- `例外放行`
- `延期处理`

它们不是可选标签，而是决定后续动作是否合法的治理状态。

状态语义固定为：

- `通过`
  - 允许继续实现、提交、合并、收口
- `驳回`
  - 禁止进入实现、继续提交、继续合并
  - 必须回到设计、补证据或重做校准
- `例外放行`
  - 只允许在批准范围内继续
  - 必须附带批准者、失效条件、补审要求
  - 不得突破根本红线
- `延期处理`
  - 只允许带着显式债务记录继续
  - 不得伪装成 `通过`

硬规则：

- 没有最终治理状态的输出，视为无效输出
- 对高风险请求，如果没有显式治理状态，就不得视为合格守卫结果

### 6.6 独立复核规则

`constitutional-guard` 必须明确区分“可以自判的轻量结论”和“必须独立复核的高风险结论”。

以下情况必须要求独立复核，不允许作者自判通过：

- 新增依赖
- 工具链或运行时接入调整
- 修改 `contract`
- 跨层边界移动
- 触碰聊天热路径
- 触碰权限、成员、消息成立、治理语义真相
- 申请例外放行
- 债务延期
- 跨多个模块或多个文件簇的清理型维护

独立复核人只能是：

- 仓库主人
- 主维护者
- 仓库主人明确指定的 reviewer

AI / agent 不得既是实施者又是唯一放行者。

### 6.7 例外审批与延期闭环

这个 skill 必须内置“例外存在，但例外有边界”的治理观，而不是把紧急情况当成万能绕行证。

例外审批规则：

- 例外只能绕过非核心流程，不能突破根本红线
- 例外必须附带批准者
- 例外必须附带失效时间或失效触发点
- 例外必须附带补审要求
- 例外不得永久挂起

延期处理规则：

- 延期不是“先放着”，而是显式债务
- 延期必须记录：
  - 债务内容
  - 延期原因
  - 当前风险
  - 临时控制措施
  - 回看触发点
- 没有这组字段，就不算合法延期

也就是说：

- `例外放行` 解决的是“这次必须继续，但要有边界”
- `延期处理` 解决的是“这次先不清，但不能失踪”

二者都不能伪装成 `通过`

## 8. 输出契约

### 8.1 写前校准

默认输出为极短四栏，每栏 1 到 2 句，必要时带极短理由短句。

#### `建议落层`
- 直接回答这次改动应落在哪层
- 不做长篇解释

#### `复用结论（含在线调研与取舍理由）`
- 默认给出结论倾向
- 需要时点名成熟生态候选
- 必须说明“为什么这么选/为什么不能这么选”
- 若调研不足，必须标记：
  - `调研未完成`
  - `结论暂定`
  - `不足以支持自研放行`

#### `边界与长期演进风险`
- 同时覆盖：
  - 分层污染
  - 前后端越位
  - `contract` 污染
  - 多壳共核破坏
  - 框架绑定过深
  - 乐高式可演进性受损

#### `禁止动作`
- 只写 2 到 4 条最关键的硬红线
- 不扩写成长段

### 8.2 写中纠偏

默认输出极短双句：

- `这里开始像私有 wrapper 了。先并回现有 adapter，不要继续包。`
- `这里已经在前端保存后端真相了。把裁决收回 application，前端只保留体验态。`

### 8.3 写后审查

继续沿用现有高密度结构，不缩水，但应重新对齐新名字与三态体系。

### 8.4 条件显性化规则

默认情况下，这个 skill 仍应保持短、硬、清晰，不把完整制度一股脑摊给用户。

但当命中以下情况时，必须把隐藏规则显性化，最少追加一行或一个极短字段：

- 当前属于高风险改动
- 当前结论不是 `通过`
- 当前需要独立复核
- 当前命中了例外放行
- 当前命中了延期处理

最小显性字段应至少包括：

- `治理状态`
- `是否需要独立复核`
- 若非 `通过`，再补最小必要原因

这样既不把日常输出写胖，也不会在真正高风险时装作一切正常。

## 9. 触发语义

`constitutional-guard` 的 description 需要从“审查器触发”升级成“生命周期治理触发”。

它应覆盖三类意图：

1. 开发前校准意图
2. 开发中纠偏意图
3. 开发后治理审查意图

它应明确说明：

- 它不只适用于“全仓治理审查”
- 也适用于“准备怎么写才不跑偏”
- 还适用于“正在写的时候发现开始像手搓轮子/开始像私有伪框架”

## 10. 迁移策略

### 10.1 命名迁移

旧入口：

- `koko-constitutional-audit`

新入口：

- `constitutional-guard`

本次设计的主入口是 `constitutional-guard`，但迁移不得硬切。

迁移策略固定为：

- 新文档、fixture、description、评测、目录说明全部以 `constitutional-guard` 为唯一规范名称
- 旧名 `koko-constitutional-audit` 仅在迁移窗口内作为兼容入口或兼容说明存在
- 兼容入口的职责只有转发与过渡，不再承载新设计
- 当引用、自动化、fixture、工作区说明、历史文档入口全部迁完后，才允许移除旧名

单一真值定义如下：

- canonical name：`constitutional-guard`
- compatibility alias：`koko-constitutional-audit`
- alias 状态：迁移期间只读兼容，不得新增语义
- alias 失效条件：所有仓库内文档、fixture、脚本、自动化、样例与说明均已迁到 canonical name
- alias 回收时点：首次完整通过迁移回归套件之后的下一个稳定版本

任何双入口一旦出现行为差异，默认视为严重设计错误，优先修正。

也就是说：主入口直接升级，但执行层必须有过渡期，不能让现有触发、文档引用和自动化一夜失效。

### 10.2 能力迁移原则

迁移不能削弱已有的：

- 全仓治理审查
- 局部宪法审查
- anti-wheel 校准
- baseline + overlay 机制
- conformance fixtures
- batch runner

新能力必须是叠加，而不是替代。

### 10.3 host-neutral 保持

迁移后仍然必须：

- 不绑定 Claude
- 不绑定 Codex
- 不绑定某个特定 CLI
- 允许任何具备基础能力的 Agent 使用

## 11. 评测与回归

现有 fixtures 和脚本必须继续保留，并扩展为三态矩阵。

### 11.1 新增 fixture 维度

- `pre-code-calibration`
- `in-flight-drift-correction`
- `post-code-audit`
- `combo-mode`
- `baseline-only`
- `project-overlay`
- `anti-hand-rolled-wheel`
- `frontend-backend-boundary`
- `lego-evolvability`

### 11.2 新增评测问题

新的评测不只看“会不会审”，还要看：

- 会不会在开发前自动校准
- 会不会在开发中发现漂移并极短纠偏
- 会不会在没有明显问题时静默通过
- 会不会在通用能力场景下主动查成熟生态并给出取舍理由
- 会不会维持短、硬、清晰、不臭不长
- 会不会正确判定高风险与低风险
- 会不会在需要时显性输出 `通过 / 驳回 / 例外放行 / 延期处理`
- 会不会在高风险场景下要求独立复核，而不是自己假装能放行
- 会不会在延期处理时要求显式债务字段
- 会不会在例外放行时守住根本红线

### 11.3 硬通过阈值

本次重构后的 skill，只有同时满足以下条件，才允许判定为通过：

- 模式路由 fixture 命中率 `100%`
- `combo` 相关 fixture 命中率 `100%`
- `pre-code calibration` 的四栏输出 fixture 命中率 `100%`
- `in-flight drift correction` 的双句纠偏 fixture 命中率 `100%`
- “无明显问题时静默通过” fixture 命中率 `100%`
- 原有 `post-code audit` 的高价值 anti-wheel / boundary / contract fixture 不得退化
- baseline-only 与 project-overlay 两组 law-hierarchy fixture 必须全通过
- 高风险识别相关 fixture 命中率 `100%`
- 治理状态机相关 fixture 命中率 `100%`
- 独立复核 / 例外放行 / 延期处理相关 fixture 命中率 `100%`

只通过大部分、不通过关键路由样本，不算合格。

### 11.4 最小覆盖规模与防过拟合约束

为了防止“fixture 很少，所以看起来全绿”的假通过，至少必须满足：

- 每个一等模式至少 `5` 个正例 + `5` 个近似负例
- `combo` 至少 `6` 个专门路由样例：
  - `3` 个必须命中
  - `3` 个必须不命中
- 每个关键 law-hierarchy 冲突至少 `2` 组对照样例
- 每种治理状态至少 `2` 个正例 + `2` 个近似负例
- 至少 `20%` 的样本保留为 holdout，不参与日常调 prompt 或调规则
- 每条关键路由规则至少要有 `1` 个变异样例，用来证明不会因为提示词表面变化就误判

如果这些覆盖规模不满足，即使通过率是 `100%`，也不得宣称设计已经稳定。

### 11.5 必备冲突样例

至少必须长期保留以下冲突类 fixture：

- 现有代码 + 改动意图并存时是否正确进入 `combo`
- baseline 与 overlay 对同一边界的 tightening 场景
- external calibration 与项目 overlay 对候选生态方案存在张力的场景
- 开发中漂移提醒应触发与应静默的对照场景
- 写前校准中“调研不足但仍需给暂定倾向”的场景
- 高风险改动是否正确要求独立复核的场景
- 例外放行是否附带批准者、失效条件、补审要求的场景
- 延期处理是否附带显式债务记录字段的场景

没有这些冲突样例，评测不能证明 skill 真正稳定。

## 12. 风险

### 12.1 最大风险

如果仍然把所有逻辑继续塞回 `SKILL.md`，这个 skill 会继续膨胀成一个高耦合大文件，未来越改越乱。

### 12.2 次级风险

如果写前、写中、写后三态分别形成不同价值观，skill 会出现自相矛盾：

- 写前说不要手搓
- 写中却默许继续包一层
- 写后再来批判私有框架债

所以法则层必须共享，模式协议只允许改变输出契约与介入时机，不允许改变价值判断。

---

## 13. 验证计划

本设计落地后，至少需要完成这些验证：

- 新 `SKILL.md` 能正确判定三态模式
- 高风险识别器能正确区分低风险与高风险
- 审查状态机能正确给出 `通过 / 驳回 / 例外放行 / 延期处理`
- 需要独立复核时不会被 agent 自己假装放行
- 例外放行不会突破根本红线
- 延期处理会留下完整债务字段
- 三态协议在没有项目治理文档时仍能使用 baseline
- 遇到项目文档时能正确叠加 overlay
- `pre-code calibration` 输出保持短、硬、清晰
- `in-flight drift correction` 在明显漂移时给出双句纠偏，在无问题时静默
- `post-code audit` 的原有治理能力不被削弱
- batch runner 能按模式或标签回放三态 fixtures

---

## 14. 最终结论

`constitutional-guard` 不应被实现成“更大的审查 skill”，而应被实现成：

- 一个统一的、宿主无关的、生命周期覆盖的宪法治理 skill
- 对外一个名字
- 对内三份协议
- 共享一套法则层
- 以短、硬、清晰、优雅的方式，在开发前、开发中、开发后持续守住边界

这样它才真正符合 [审查维护.md](/E:/koko/审查维护.md) 的原始精神，也更符合项目长期追求的那条主线：

不手搓轮子，不沉淀私有伪框架，不让系统一年比一年更乱，而是持续逼近一个可替换、可扩展、可长期维护、像乐高积木一样自由拼接的稳定架构。
