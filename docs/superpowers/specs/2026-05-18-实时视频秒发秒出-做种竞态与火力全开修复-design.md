## 1. 用户现象

在群聊中，用户 A 发送视频后，B/C/D 用户看到一个黑灰占位卡片，等很久视频才自动播放，全屏后一卡一卡。但**刷新页面后视频立即播放**。

---

## 2. 根因分析

### 根因 1：竞态——广播比做种跑得快

`src/媒体/上传/外壳/完成上传.rs` 第 674 行和 718 行：

```rust
// (1) fire-and-forget：启动 sidecar 做种
tokio::spawn(async move {
    尝试启动协作分发做种(&state, &命令).await;
});
// (2) fire-and-forget：广播给所有群友
tokio::spawn(async move {
    广播附件状态升级事件(&io, &pool, &aid, ...).await;
});
```

两个 `tokio::spawn` 并行赛跑。广播只做一次 SQL + Socket.IO emit（毫秒级），而做种需要：

1. HTTP POST 到 dev-seeder
2. dev-seeder `client.add()` 解析 torrent 元信息
3. piece verification（本地硬链接成功时 1500ms，网络下载时更久）
4. tracker announce

**结果**：B/C/D 收到 Socket.IO 消息时，服务器还没入群。所有人连上 tracker 找不到 peer，卡在黑灰占位卡片。

**为什么刷新后秒出**：刷新时服务器已经做种完毕（`torrent.done = true`），peer 发现秒连。

### 根因 2：服务端 WebTorrent 客户端火力为零

`frontend/dev-seeder.mjs` 第 504 行：

```javascript
client = WebTorrentCtor ? new WebTorrentCtor() : null;
```

**没传任何配置**，全用默认值：

| 参数 | 默认值 | 对万人群的影响 |
|---|---|---|
| `maxConns` | 55 | 服务器每个 torrent 最多连 55 个群友 |
| `uploads` | 10 | 同时只给 10 个人传数据 |
| `storeCacheSlots` | 20 | 内存只缓存 20 个 piece，高并发时磁盘 IO 打满 |

对比浏览器端（`媒体协作分发.ts` 第 915 行）已经调到 `maxConns: 128`，服务器做种反而更弱。

### 根因 3：做种会话也没调优

`frontend/dev-seeder.mjs` 第 297-315 行，`client.add()` 时没有传入：

- `storeCacheSlots`（piece 内存缓存）
- `uploads`（上传槽位）
- `skipVerify`（跳过 piece 验证——本地硬链接文件已由 Rust 验证过）

## 3. 官方文档支撑

### 3.1 skipVerify（WebTorrent 官方 API）

> When you add a torrent with `skipVerify`, WebTorrent will mark all pieces in the torrent as already downloaded, skipping the verification/checking process.

我们的场景完全适用：硬链接后的文件就是 Rust 写入的 canonical 原文件，内容完整且一致。使用 `skipVerify: true` 可以消除 piece verification 延迟（当前 1500ms 等待窗口）。

### 3.2 maxConns / uploads / storeCacheSlots（WebTorrent 官方 API）

- `maxConns`：每个 torrent 的最大连接数。服务器做种需大幅调高。
- `uploads`：同时允许多少 peer 从你下载。默认 10 对万人群是致命瓶颈。
- `storeCacheSlots`：内存缓存 piece 数。调高后减少磁盘随机读，多 peer 并发拉取时吞吐量翻倍。

### 3.3 seedOutgoingConnections（WebTorrent v2.4.0+）

默认 `true`，做种时主动建立出站连接，改善 peer 发现。必须确认未被意外关闭。

### 3.4 BEP 16 Super-Seeding 启示

虽然 WebTorrent 未实现 BEP 16，但核心思想适用：**初始做种时应最大化带宽利用率和 piece 分发覆盖率**。调高 `uploads` 是直接的实现方式。

---

## 4. 修复方案

### 修复 1：消除竞态——做种就绪后再广播

**改动文件**：`src/媒体/上传/外壳/完成上传.rs`

**当前**（两个 fire-and-forget 并行）：

```text
tokio::spawn(做种) ─────────→ sidecar start（慢，1-2秒）
tokio::spawn(广播) ─────────→ Socket.IO emit（快，毫秒级）
```

**修复后**（做种成功后再广播）：

```text
做种 ──→ sidecar start ──→ done? ──→ 广播
                               └──→ 超时兜底也广播（但附带 media_state: CONNECTING_TO_PEERS）
```

**关键发现**：sidecar `/seed/start` 响应已包含 `done: Boolean(session.torrent?.done)`（`dev-seeder.mjs` 第 420 行），Rust 端可直接读取此字段判断做种是否就绪，无需额外协议。

具体逻辑：

1. 把做种 `tokio::spawn` 改为 `await`（或有限超时的 `tokio::time::timeout`）
2. 做种返回 `done: true` 后，再 fire-and-forget 广播
3. 做种超时（例如 5 秒）或失败时，仍然广播（不能阻塞用户体验），但此时 `media_state` 为 `CONNECTING_TO_PEERS`——客户端会走 noPeers 重试路径
4. 典型情况下（本地硬链接 + skipVerify），做种在毫秒级完成，广播几乎不延迟

**为什么不无限等待**：complete HTTP 响应不能被做种卡死。设置合理超时兜底，最差情况与当前一致（客户端先看到占位，等 peer 慢慢来）。

**为什么不让 complete HTTP 响应等做种**：complete 响应是给发送者 A 的，发送者不需要等做种。做种是为接收者准备的，广播才是关键门控点。

### 修复 2：服务端 WebTorrent 客户端火力全开

**改动文件**：`frontend/dev-seeder.mjs`

**当前**（第 504 行）：

```javascript
client = WebTorrentCtor ? new WebTorrentCtor() : null;
```

**修复后**：

```javascript
client = WebTorrentCtor
  ? new WebTorrentCtor({
      maxConns: 512,
      seedOutgoingConnections: true,
      uploadLimit: -1,
      downloadLimit: -1,
    })
  : null;
```

参数选择依据：

| 参数 | 值 | 依据 |
|---|---|---|
| `maxConns` | 512 | 万人群服务器需要同时连接大量 peer。512 是 libtorrent 大规模做种常见值 |
| `seedOutgoingConnections` | true | 显式声明，防止默认值变化 |
| `uploadLimit` | -1 | 显式声明无限制（默认已为 -1），防止未来默认值变更 |
| `downloadLimit` | -1 | 显式声明无限制（默认已为 -1），防止未来默认值变更 |

### 修复 3：做种会话级调优

**改动文件**：`frontend/dev-seeder.mjs`

**当前**（第 297-315 行，`client.add()` 的 options）：

```javascript
const options = {
  announce,
  urlList,
  ...(stagingDir ? { path: stagingDir } : {}),
  getAnnounceOpts: () => { ... },
};
```

**修复后**：

```javascript
const options = {
  announce,
  urlList,
  ...(stagingDir ? { path: stagingDir } : {}),
  // 硬链接成功时跳过 piece 验证——文件已由 Rust 权威验证
  ...(stagingDir ? { skipVerify: true } : {}),
  // 服务器做种：同时给 64 个 peer 上传（默认 10）
  uploads: 64,
  // 内存缓存 500 个 piece，减少磁盘随机读 IO
  storeCacheSlots: 500,
  getAnnounceOpts: () => { ... },
};
```

参数选择依据：

| 参数 | 值 | 依据 |
|---|---|---|
| `skipVerify` | true（仅硬链接成功时） | Rust 写入的 canonical 文件内容已验证，跳过 piece verification 节省 1500ms+ |
| `uploads` | 64 | 万人群需要同时给多人传。64 是 rtorrent super-seed 推荐的 max-uploads 范围 |
| `storeCacheSlots` | 500 | 浏览器端已调到 150（默认 20），服务器做种需更高。500 × 256KB piece ≈ 125MB 内存，可接受 |

**为什么 skipVerify 只在硬链接成功时用**：硬链接失败时文件可能不存在或不完整（S3 模式、路径错误等），此时仍需正常验证。

### 修复 4：做种就绪后消除 readinessWaitMs 冗余等待

**改动文件**：`frontend/dev-seeder.mjs`

**当前**（第 335-341 行）：

```javascript
if (stagingDir && !torrent.done) {
  const waitMs = typeof payload.readinessWaitMs === "number" ? payload.readinessWaitMs : 1500;
  await new Promise((resolve) => {
    if (torrent.done) return resolve();
    const timer = setTimeout(resolve, waitMs);
    torrent.once("done", () => { clearTimeout(timer); resolve(); });
  });
}
```

**修复后**：当 `skipVerify: true` 时，`torrent.done` 在 `client.add()` 回调时已经为 `true`，这段等待自然跳过（`if (stagingDir && !torrent.done)` 为 false）。无需修改代码，但需在测试中验证。

**同时修改 `src/外壳/协作分发做种.rs`**：`readinessWaitMs` 可以从 1500 降到更低值（如 500），仅作为 skipVerify 失败时的兜底窗口。

## 5. 预期效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| B/C/D 收到消息到视频可播放 | 5-30 秒（等做种 + peer 发现） | < 1 秒（做种已就绪，peer 秒连） |
| 服务器同时给多少人传 | 10 人 | 64 人 |
| 服务器每 torrent 最大连接 | 55 | 512 |
| piece 验证延迟（硬链接） | ~1500ms | 0ms（skipVerify） |
| 刷新后行为 | 秒出（不变） | 秒出（不变） |

## 6. 风险与约束

1. **complete 响应时间不受影响**：做种等待只影响广播时机，不影响 complete HTTP 响应返回给发送者 A。
2. **超时兜底**：做种超时后仍广播，最差情况与当前一致。
3. **skipVerify 安全性**：仅在硬链接成功时使用，硬链接保证文件内容与 canonical 一致。
4. **内存开销**：`storeCacheSlots: 500` × 256KB piece ≈ 125MB/torrent。做种对账会回收过期 torrent，实际内存可控。
5. **maxConns: 512**：服务器 CPU 和网络能力通常远超普通客户端，512 连接在合理范围内。
6. **不改动浏览器端**：浏览器端配置（`maxConns: 128`、`storeCacheSlots: 150`）已经合理，本次不动。

---

## 7. 不做的事

1. 不改 torrent 生成逻辑——Rust 仍是 torrent bytes 和 infoHash 唯一 owner
2. 不改 tracker 架构——仍用项目已有的同源 tracker 代理
3. 不改浏览器端 WebTorrent 配置——浏览器端已调优
4. 不引入 HLS/DASH/CDN 第二主链——纯 WebTorrent whole-file swarm
5. 不实现 BEP 16 super-seeding——WebTorrent 不支持，且调高 uploads 已满足需求
