# 房间消息窗口独立化与历史补偿重构设计

日期：2026-04-09  
状态：设计已确认，待进入 implementation plan  
范围：`frontend` 房间页壳层、消息窗口、历史分页补偿、阅读推进接线、对应测试  
约束：最多新增 2 个前端运行时代码 `.ts` 文件；不改 Rust 后端契约；不改 HTTP / realtime 协议；不改变现有业务语义；以“体验更稳、边界更清”为目标，而不是为了拆文件而拆文件

## 0. 一句话结论

这次不是继续在大壳组件上补丁，而是把“房间页外壳”和“消息窗口”真正拆成两个稳定边界：

1. 房间壳只负责头部、底部操作台、进房与恢复上下文
2. 消息窗口独立负责消息列表、未读分隔、上滑补历史、跳到最新、局部提示、滚动补偿
3. 历史补偿从“总 `scrollHeight` 差值”升级成“锚点消息位置恢复”，让视口在历史前插时仍然稳定

最终目标不是让文件更多，而是让“历史分页只是消息窗口内部事件”这条边界真正成立，不再把整页房间壳一起拖着重绘。

---

## 1. 当前问题与根因

### 1.1 现象

当前聊天室往上滑历史时，在接近第 55 条消息附近会出现闪烁、抽搐、画面先跳再回的体验问题。

### 1.2 为什么集中在第 55 条附近

这不是随机问题，而是首屏历史窗口边界暴露出来的：

1. 后端房间首屏围绕 `55` 条消息建立
2. 前端加载更早历史页时也固定请求 `55` 条
3. 所以当用户滑到首屏最上方附近时，第一次进入“向上补历史”分支，问题就集中暴露

这说明问题主战场在前端第一次历史前插链路，而不是后端接口偶发抖动。

### 1.3 已确认的第一层根因

上一轮已经确认并修掉一层问题：消息列表在历史前插时没有使用 keyed 渲染，导致旧 DOM 节点按位置复用，造成可见消息身份错乱。

这层问题虽然已经修掉，但它不是全部根因。

### 1.4 当前剩余主根因

当前历史补偿链路依然是两步完成的：

1. 先把历史页前插进 `messages`
2. 再等渲染完成后，通过前后 `scrollHeight` 差值回补 `scrollTop`

这会留下一个真实浏览器可见的窗口：

1. DOM 已经长高
2. 旧内容先被顶下去
3. 视口随后才被程序拉回去

这一前一后两步，在真实浏览器里就是用户看到的“闪一下”。

### 1.5 架构放大器

除了补偿时序，当前前端壳层内部还有一个更高层的问题：  
“历史加载”本来只是消息窗口内部状态，却泄漏成了整个房间页状态。

当前 `historyLoading / historyErrorCode` 会同时影响：

1. 房间头部副标题
2. 底部操作台状态文案
3. 消息列表自身

这导致消息窗口内部的一次局部更新，被放大成整页头部、消息区、底部一起响应。

所以这次要同时解决两件事：

1. 视口为什么跳
2. 为什么局部状态会外溢成整页重绘

## 2. 设计目标

### 2.1 必须达到

1. 历史分页前插时，当前可见消息在视口中的位置保持稳定
2. 历史加载状态只在消息窗口内部表达，不再驱动整页头部和底部
3. 房间页形成“外壳 / 消息窗口”两个明确边界
4. 现有业务能力保持不变：
   - 进房
   - 恢复
   - 未读分隔
   - 阅读推进
   - 跳到最新
   - realtime 并流
   - 发送消息
5. 测试能够覆盖“历史页前插 + realtime 同时发生”这类容易出新 bug 的时序

### 2.2 明确不做

1. 不改 Rust 后端用例、仓储、HTTP handler、socket 协议
2. 不改消息语义、未读语义、阅读锚点语义
3. 不为了“组件化”把前端拆成文件海
4. 不顺手重写主题、视觉风格、页面结构语言

## 3. 方案比较

### 方案 A：继续在大壳组件里补丁

做法：

1. 保持当前 `聊天壳` 为唯一房间页渲染器
2. 只微调历史补偿和少量局部状态

优点：

1. 改动最小
2. 上手最快

问题：

1. 整页壳和消息窗口的边界依然是糊的
2. `historyLoading` 仍然容易继续外溢
3. 以后同类问题还会重复出现

不采用。

### 方案 B：把消息窗口独立成组件，并升级为锚点补偿

做法：

1. 房间壳负责外壳上下文
2. 消息窗口独立负责消息视口内部一切行为
3. 历史补偿改为锚点恢复，而不是纯 `scrollHeight` 差值

优点：

1. 主根因和结构放大器一起处理
2. 页面边界更清晰
3. 风险和收益平衡最好

问题：

1. 会动到多个现有前端模块和测试
2. 需要认真设计状态归属，不能机械搬家

采用。

### 方案 C：继续向下拆成多个 service / manager / controller

做法：

1. 再新增多个文件，分别拆渲染、滚动、提示、分页、阅读推进

优点：

1. 名义上的职责更细

问题：

1. 容易过度工程化
2. 文件数量膨胀
3. 不符合当前项目“克制新增文件”的纪律

不采用。

---

## 4. 选定方案

本次采用 **方案 B：消息窗口独立组件 + 锚点补偿**。

### 4.1 预计新增文件

最多新增 2 个运行时代码文件：

1. 必增 1 个：`frontend/房间消息窗.ts`
2. 可选 1 个：仅当滚动锚点补偿逻辑无法优雅收进现有 `房间滚动器.ts` 时，才新增一个极薄的消息窗 presenter / helper 文件

原则是：

1. 优先用现有 `阅读推进编排.ts`、`房间滚动器.ts`、`视图.ts`
2. 只把真正属于“消息窗口”的边界抽出来
3. 不把已有正确边界再打碎

---

## 5. 新的前端边界

### 5.1 房间壳职责

房间壳只保留以下职责：

1. 渲染顶部栏：返回按钮、房间标题、稳定副标题
2. 渲染底部操作台：输入框、发送按钮、恢复态提示、发送态提示
3. 持有房间级上下文：
   - `roomId`
   - `roomDisplayTitle`
   - `sessionId`
   - `displayAlias`
   - `messageInput`
   - `pending`
   - `recoveryState`
4. 装配现有恢复编排、realtime 编排、阅读推进编排、房间滚动器
5. 把消息流和阅读语义传给消息窗口组件

房间壳不再负责：

1. 历史加载文案
2. 历史失败文案
3. 历史前插时的局部占位
4. 跳到最新按钮

### 5.2 消息窗口职责

消息窗口独立负责：

1. 消息列表渲染
2. 未读分隔条渲染
3. 跳到最新按钮
4. 顶部上滑补历史
5. 历史加载提示与失败提示
6. 与滚动容器直接相关的交互：
   - 用户滚动意图
   - 视口采样
   - 历史补偿
   - 程序滚动隔离

这意味着一句话边界：

**“消息窗口发生的局部滚动和局部提示，不再升级成房间页壳层状态。”**

---

## 6. 状态归属调整

### 6.1 继续保留在房间壳

以下状态继续由 `聊天壳` 持有，并作为房间级上下文存在：

1. `roomId`
2. `roomDisplayTitle`
3. `sessionId`
4. `displayAlias`
5. `messageInput`
6. `pending`
7. `recoveryState`
8. `lastRecoveryErrorCode`

这些仍然属于整页壳层、会话恢复和发送链路，不应该挪进消息窗口。

### 6.2 从整页表达中收回消息窗口

以下状态仍可留在全局 `chatState` 里用于编排，但它们的**显示与交互解释权**收回消息窗口：

1. `historyLoading`
2. `historyErrorCode`
3. `hasUnreadNewerMessages`
4. `viewportMode`
5. `firstUnreadEventPosition`
6. `lastReadEventPosition`
7. `candidateReadAnchorPosition`

这里要强调：

1. 不要求所有状态都搬出 `chatState`
2. 这次要做的是**边界收口**，不是无意义状态搬家
3. 真正需要收回的是“谁消费它、谁渲染它、谁把它解释成 UI”

### 6.3 副标题与底部状态的新规则

重构后：

1. 房间头部副标题只显示稳定信息：
   - 当前匿名身份
   - 恢复失败 / 重连这类真正房间级状态
2. 底部操作台状态只表达：
   - 输入说明
   - 发送态
   - 恢复态
3. “正在加载更早消息”与“更早消息加载失败”只在消息窗口内部显示

这样历史分页不再驱动整页头部和底部切文案。

## 7. 历史补偿设计

### 7.1 为什么不再以总高度差值为核心

纯 `scrollHeight` 差值补偿有两个天然问题：

1. 历史页前插和滚动补偿不是原子动作，中间会露出一帧可见跳动
2. 如果补历史时底部同时有 realtime 新消息进入，总高度差值会把“顶部前插”和“底部追加”一起算进去

所以它不够稳，也不够像真正的 IM。

### 7.2 新的补偿原则：锚点恢复

历史分页时，消息窗口在触发请求前要记录：

1. 当前视口里一条稳定可见的锚点消息
2. 这条消息的稳定标识：
   - 优先 `message_id`
   - 无法使用时退回 `event_position`
3. 该锚点消息相对滚动容器顶部的偏移

历史页回来并前插后：

1. 重新找到这条锚点消息节点
2. 读取它新的相对位置
3. 调整 `scrollTop`，让该锚点回到原来的偏移

### 7.2.1 锚点选择规则

为避免实现阶段各自猜“哪条消息算锚点”，这里把规则锁死：

1. 只在真正的消息行里选锚点，不使用未读分隔条、局部提示条或其他装饰节点
2. 候选集合沿用现有滚动器的“稳定可读”判定，避免再造第二套阈值：
   - 可见高度不少于 `40px`
   - 或者可见比例不少于整条消息高度的 `55%`
3. 若同一时刻有多条消息满足条件，选择**最靠近视口顶部的那条稳定可读消息**作为锚点
4. 若没有消息达到“稳定可读”阈值，则退一步选择**当前与视口有真实重叠、且最靠近视口顶部的那条消息**
5. 若连“有真实重叠的消息”都不存在，再退回旧的 `scrollHeight` 差值补偿兜底，而不是放弃补偿

这条规则的核心意图是：

1. 优先守住用户正在向下阅读时最先接触到的那条消息
2. 选择规则与现有阅读锚点采样口径尽量一致
3. 真遇到极端视口，也仍有明确回退路径，而不是实现者各自发明特判

### 7.2.2 锚点恢复后的容差标准

补偿完成后，测试不要求像素绝对零误差，但必须满足可执行口径：

1. 锚点消息恢复后，相对容器顶部的偏移误差默认不超过 `4px`
2. 若浏览器布局产生小数像素，允许按四舍五入后的误差比较
3. 超过 `4px` 就视为视口不稳定，需要回到实现阶段继续收口

这个容差只用于测试验收，不代表运行时可以接受肉眼可见跳动。

### 7.3 这个设计解决什么

它直接解决：

1. 历史前插时视口不再依赖整个列表总高度
2. realtime 新消息同时进入时，不会把底部追加误算成补偿量
3. 只要锚点消息还在 DOM 里，用户看到的内容就能稳定停在原处

### 7.4 与现有滚动器的关系

现有 `房间滚动器.ts` 仍然保留，职责不变：

1. 处理 DOM 滚动副作用
2. 隔离程序滚动和用户滚动
3. 采样阅读锚点
4. 处理贴底跟随

变化的是它的历史补偿输入输出：

1. 旧接口以 `scrollHeight` 基线为中心
2. 新接口升级为“补偿上下文”：
   - 旧滚动高度可保留作为兜底
   - 但主要依据改成锚点消息恢复

也就是说，这次是**增强现有滚动器**，不是重写滚动系统。

## 8. 组件与数据流

### 8.1 页面层次

新的渲染结构应接近：

1. `聊天壳`
   - `房间头部`
   - `房间消息窗`
   - `壳级操作台`

### 8.2 数据流

1. 恢复编排 / realtime 编排 / 阅读推进编排继续更新共享状态与房间内核
2. `聊天壳` 从共享状态提取：
   - 房间壳上下文
   - 消息窗口所需输入
3. `房间消息窗` 只消费与消息视口相关的数据
4. `房间消息窗` 通过回调把滚动意图和局部动作回送现有编排器

### 8.3 交互流

#### 上滑补历史

1. 用户在消息窗口内上滑到顶
2. 消息窗口记录补偿锚点
3. 通过现有阅读推进编排请求历史页
4. 历史页前插后，滚动器按锚点恢复位置
5. 局部提示仅在消息窗口内部切换

#### 新消息进入

1. realtime 编排并入权威消息
2. 若当前贴底跟随，则消息窗口继续贴底
3. 若当前离底浏览，则只在消息窗口内出现“跳到最新”

#### 未读恢复

1. 恢复链仍由现有编排负责
2. 首屏落位仍由滚动器负责
3. 消息窗口只负责表现未读分隔和消息列表

## 9. 对现有模块的影响

### 9.1 `frontend/聊天壳.ts`

变化方向：

1. 房间页 JSX / 模板明显变薄
2. 头部与底部只保留稳定壳层语义
3. 消息列表、局部提示、跳到最新按钮下沉到 `房间消息窗`

### 9.2 `frontend/视图.ts`

变化方向：

1. 房间级文案派生不再消费历史加载提示
2. 历史提示相关 presenter 下沉到消息窗口边界

### 9.3 `frontend/阅读推进编排.ts`

变化方向：

1. 历史请求主链仍保留
2. 但历史补偿上下文从“高度基线”升级成“锚点上下文”

### 9.4 `frontend/房间滚动器.ts`

变化方向：

1. 继续负责程序滚动隔离与 DOM 观测
2. 历史补偿逻辑增强为“锚点恢复优先、高度差值兜底”

### 9.5 `frontend/房间内核.ts`

原则：

1. 不把历史加载这种局部滚动状态倒灌进房间内核
2. 房间内核仍只承接房间壳级同步语义，而不是消息窗口局部副作用

## 10. 测试策略

### 10.1 必须新增或改造的验证

1. 历史前插后，原有可见消息 DOM 身份保持稳定
2. 历史前插后，锚点消息在视口中的相对位置不变
3. `historyLoading` 变化时，房间头部和底部不再一起切换
4. 历史页和 realtime 新消息同时并入时，视口仍稳定
5. 跳到最新仍然只在消息窗口内部生效

### 10.2 必须保回归的现有能力

1. 首屏未读恢复
2. 阅读推进
3. 贴底跟随
4. 离底浏览时新消息累积提示
5. 发送消息乐观态与权威并流
6. 房间恢复失败与历史分页失败语义

### 10.3 测试层次

1. 组件 / presenter 级：消息窗口局部文案、局部渲染边界
2. 编排 / 滚动级：锚点补偿、程序滚动隔离
3. 集成级：进房、上滑补历史、realtime 并入、跳到最新

## 11. 风险与控制

### 风险 1：锚点找不到

场景：

1. 历史前插后，原锚点消息由于异常去重或列表重排丢失

控制：

1. 优先用稳定 `message_id`
2. 兜底可退回 `event_position`
3. 若锚点仍找不到，再退回高度差值补偿，而不是直接放弃补偿

### 风险 2：realtime 与历史页同时进入

场景：

1. 历史请求未完成时，底部又到了一条新消息

控制：

1. 锚点恢复优先，不再只依赖总高度差值
2. 增加专门时序测试，锁住该场景

### 风险 3：重构后未读恢复退化

场景：

1. 消息窗口独立后，首屏围绕未读落位、未读分隔与阅读推进接线出错

控制：

1. 不改未读语义来源
2. 不改房间内核的房间级同步语义
3. 保留并增强现有未读恢复测试

### 风险 4：文件拆分后反而更碎

控制：

1. 运行时代码新增文件上限 2 个
2. 只抽“消息窗口”这个真正稳定边界
3. 其余逻辑优先增强现有模块，不滥造 helper

---

## 12. 实施顺序建议

1. 先引入 `房间消息窗` 组件，搬迁房间页消息区渲染
2. 收回历史提示与跳到最新的渲染边界，不再由整页壳层表达
3. 升级滚动器的历史补偿上下文为锚点恢复
4. 保留高度差值作为兜底
5. 补齐并调整测试，先锁稳定性再清理实现细节
6. 最后再做小幅收口和命名整理

## 13. 验收标准

满足以下条件才算这次重构完成：

1. 用户上滑到首屏顶部附近，首次触发历史分页时不再出现明显闪烁或抽搐
2. 历史加载时，房间头部和底部不再因局部状态切换而一起重绘
3. 历史页与 realtime 新消息同时进入时，视口仍稳定
4. 现有未读恢复、阅读推进、跳到最新、发送消息、房间恢复都保持正确
5. 运行时代码新增文件数不超过 2 个 `.ts`

---

## 14. 最终裁决

这次最优雅的做法，不是继续往大壳里补丁，也不是把前端拆成一堆 manager / service。  
真正优雅的是：

1. 让房间页外壳只做外壳该做的事
2. 让消息窗口独立承担消息视口内部的一切局部行为
3. 让历史补偿围绕“用户当前正在看的消息锚点”展开，而不是围绕整个列表总高度展开

这样改完后，“拉历史只影响消息窗口，不再影响整页”才会从口头原则变成代码事实。
