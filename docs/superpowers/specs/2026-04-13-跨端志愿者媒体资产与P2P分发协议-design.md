## 1. 这份 spec 为什么存在

当前媒体链路已经出现了一个非常具体、非常刺眼的症状：

- 服务器或者后端一关，群聊里用户发送过的视频或者观看过的视频，会变成黑色、灰色、疯狂转圈，最后不可播放。

这不是一个普通的“播放器小 bug”。  
它暴露的是更深一层的事实：

1. 项目当前虽然已经接了 `WebTorrent`，但媒体真相还没有被正式收口成跨端统一协议。  
2. 当前前端对“本地已持有字节”“本地完整资产”“当前播放会话”“当前做种状态”没有单一 owner。  
3. 当前链路仍然更像“普通附件 + 一次性解析 `src` + 局部热分发”，不是“一个默认暴力互助的媒体分发网络”。  

如果继续按传统前端 bug 修法走，最容易发生三种漂移：

- 在壳层继续加 retry、guard、timer，把黑屏暂时压下去；
- 在现有 `WebTorrent` 外再包一层私有恢复逻辑，最后长成第二核心；
- 继续把图片、视频、Web、移动端、桌面端各写一套“看起来差不多”的媒体逻辑。

这三条路最终都会把项目带回屎山。

这份 spec 的任务，不是“补一个视频恢复 patch”，而是一次把终局协议、真相 owner、轮子边界、退场路径讲清楚，保证后续实现虽然可以分阶段，但不会再在方向上反复返工。

## 2. 问题的前因后果：为什么现在会黑屏、灰屏、转圈

### 2.1 当前代码不是完全没缓存，但没有正式媒体资产真相

从现有代码逻辑看，项目并不是“完全没有缓存”：

- 浏览器 `<video>` 自己会有播放缓冲；
- `WebTorrent` 底层也可能保留已经拿到的 piece；
- 前端有媒体定位缓存；
- 浏览器原生也可能对部分请求做 HTTP 缓存。

但这些都不等于“产品级媒体资产缓存已经成立”。

根因在于：

1. 这些缓存彼此没有被统一 owner 收口；  
2. 系统没有正式回答“哪些字节已经是我的本地资产”；  
3. 系统也没有正式回答“当前附件在恢复、等待、补齐、做种中的哪一种状态”。  

于是看起来像缓存，实际上只是局部临时字节在若隐若现地工作。

### 2.2 当前媒体播放主链仍然是“一次性解析结果”

现有前端大致在做这件事：

1. 根据消息附件读取媒体定位信息；  
2. 尝试解析一个可用播放源；  
3. 成功后把结果塞进 `playbackByAttachmentId`；  
4. 壳层拿着这个 `src` 直接渲染 `<video>` / 图片查看器。  

问题在于：

- 这个播放结果更像“一次性解析产物”，不是正式会话状态机；
- 后端挂掉、peer 消失、`video` 元素进入 `stalled / waiting / error` 后，没有一条正式链路把失败信号回流成新的会话裁决。

所以浏览器一旦失去当前 `src`，系统并不会自动进入“静默恢复 -> 等待 peer/网络 -> 自动续播”的正式语义，而是直接退化成用户可见的坏状态。

### 2.3 当前 WebTorrent 集成已经有价值，但只是半截

现有 `WebTorrent` 集成并不是摆设：

- 页面会接入官方 `webtorrent` 浏览器端能力；
- 会使用 `createServer({ controller })` 绑定媒体 Service Worker；
- 会从后端拿 `torrent_url`、`announce_urls`、`web_seed_url`；
- 会在开始查看后主动 `select` 附件，尽量补齐；
- 会消费 `wire / noPeers / done` 等运行态事件。

这说明两个事实：

1. 项目不是没用 `WebTorrent`；  
2. 项目也不是完全没想过“开始查看后尽快补齐整附件”。  

但问题在于，它还停留在“热分发层”的位置：

- `WebTorrent` 负责尽量把内容弄过来；
- 但它不拥有“本地完整资产”的正式真相；
- 它也不拥有“页面恢复后如何重挂”“当前会话失败后如何静默恢复”的正式协议。

这就像把一台很强的发动机装进了半截底盘。

### 2.4 当前后端仍然是主冷源，前端没有摆脱对它的运行时依赖

现有主链里，前端仍然依赖后端提供这些东西：

- 媒体定位信息；
- torrent 元信息入口；
- web seed 冷源地址；
- 原始附件内容冷路径。

这意味着：

1. 新页面、新会话通常还得先问后端；  
2. 尚未补齐的内容还高度依赖后端冷源；  
3. 后端一旦不可用，前端只要没有完整本地资产或足够 peer，就会直接暴露恢复缺口。  

所以“后端一关就坏”不是一个偶然 bug，它是当前架构语义的自然结果。

## 3. 核心结论

这份设计的核心结论只有一句：

**媒体不再被当成“普通附件 + 一个可选 WebTorrent 播放源”，而要正式升级成跨端统一的第一类媒体资产协议。**

这句话展开后，就是下面这些决定：

1. 图片、视频、音频都进入统一的 `MediaAsset` 协议。  
2. 视频不再以“原始附件文件直链”作为正式主播放链。  
3. 图片也不再只是“普通图片附件 + 浏览器自己随便缓存”。  
4. `WebTorrent` 不再只是热补丁，而是正式的 P2P 分发平面之一。  
5. 原始上传文件只保留 `24 小时`，作为冷备真相和冷源保底窗口。  
6. `24 小时` 后，资产是否继续存活，主要依赖：
   - 流媒体分片资产或图片完整资产；
   - 本地完整持有者；
   - 在线 peer 网络。  
7. 协议是强分发、强互助、弱永久性：  
   - 人越多越强；  
   - 但若没有足够完整持有者，内容允许自然死亡。  

## 4. 这份设计要达到什么目标

### 4.1 目标

1. 让用户在现实网络波动下，获得持续播放、静默恢复、尽量无感的体验。  
2. 让用户一旦开始查看媒体，就尽快补齐整资产到本地。  
3. 让设备在补齐后自动成为群体分发网络里的强节点，而不是只服务自己。  
4. 让图片和视频都纳入同一套媒体协议，而不是各写一条弱路径。  
5. 让 `Web / iOS / Android / Desktop / CLI` 共用同一个媒体协议核心，多壳共核。  
6. 用 `DDD + Unix` 哲学把媒体复杂度压缩进少数明确 owner，不制造新的大壳和私有大框架。  
7. 在充分复用成熟轮子的前提下，把项目代码收口到真正属于自己的业务真相和策略。  

### 4.2 非目标

1. 不保证所有内容永久可用。  
2. 不把后端继续做成永久冷源。  
3. 不在当前实现阶段就同时把所有端都完整落地。  
4. 不手搓播放器核心、媒体缓存核心、P2P 核心。  
5. 不允许原始附件主链和新媒体资产主链长期双活。  
6. 不用大量壳专属字段污染共享契约。  

## 5. 设计原则

### 5.1 DDD：真相只能有一个 owner

必须明确：

- 资产身份、资产种类、变体集合、过期规则：后端领域真相；
- 当前播放会话与恢复状态：客户端会话 owner 真相；
- 本地完整度、保留状态、本地已持有内容：客户端缓存 owner 真相；
- 当前 peer/做种运行态：分发 runtime 真相；
- 壳层不拥有媒体业务真相，只拥有展示临时态。  

同一个事实不允许在后端、runtime、壳层、播放器里被“顺手判一次”。

### 5.2 Unix：每层必须小而专

必须拒绝：

- “媒体大总管”
- “统一媒体大状态对象”
- “播放器 + 缓存 + 做种 + 恢复 + 展示”全塞一个 runtime

每个 owner/runtime 都必须回答：

- 我只负责哪类真相？
- 我只暴露什么稳定接口？
- 去掉我之后，哪类复杂度会重新扩散？

回答不清，就是边界没立住。

### 5.3 浏览器/端侧事件只是信号，不是业务事实

下面这些都只能当输入信号：

- `error`
- `stalled`
- `waiting`
- `canplay`
- `playing`
- `offline`
- `online`
- `visibilitychange`
- `pagehide`
- `pageshow`
- `freeze`
- `resume`
- `wire`
- `noPeers`
- `done`

它们必须先进入会话 owner / runtime，再裁决成正式状态。

### 5.4 新抽象必须压缩旧复杂度

新增 owner/runtime/adapter，如果没有带来以下至少一项，就不该存在：

- 删掉旧主链；
- 删掉旧分支；
- 删掉旧壳层逻辑；
- 让真相 owner 更单一；
- 让测试边界更清楚；
- 让成熟轮子直接被认出来。  

否则就是又长一层新壳。

### 5.5 绝不重复手搓轮子

项目自己只做：

1. 资产协议  
2. 恢复与保留状态机  
3. 薄适配层  

项目绝不再造：

1. 私有播放器核心  
2. 私有 SW 媒体缓存框架  
3. 私有 P2P 引擎  
4. 私有媒体数据库框架  
5. 私有跨端媒体前端框架  

## 6. 顶层架构骨架

终局媒体体系分成五层：

```text
Domain
  -> Application
  -> Contract
  -> Adapter / Runtime
  -> Shell
```

### 6.1 Domain

负责：

- `MediaAsset`
- 资产生命周期
- 保留规则
- `24 小时` 冷备窗口
- 自然死亡语义

禁止：

- 直接知道浏览器、播放器、Service Worker、UI 细节

### 6.2 Application

负责：

- 当前媒体会话状态机
- 恢复、等待、补齐、做种编排
- 跨 owner 协调

禁止：

- 直接操作 DOM
- 直接持有基础设施内部对象

### 6.3 Contract

负责：

- `MediaAssetDescriptor`
- `VariantDescriptor`
- `ManifestDescriptor`
- `SwarmDescriptor`
- `OriginDescriptor`
- 错误语义
- 快照语义

禁止：

- Web 壳专属字段
- iOS/Android 专属字段
- 播放器特有内部结构

### 6.4 Adapter / Runtime

负责：

- `WebTorrent`
- `Workbox`
- `CacheStorage`
- `IndexedDB/OPFS`
- `Shaka/hls.js`
- 原生播放器适配
- 生命周期、后台任务、网络信号适配

禁止：

- 决定业务真相
- 决定保留策略
- 决定何时自然死亡

### 6.5 Shell

负责：

- 收输入
- 翻译端侧事件
- 订阅 snapshot
- 渲染恢复提示与媒体 UI

禁止：

- 决定业务恢复状态
- 自己 patch 大媒体状态
- 自己拼播放主链

## 7. 统一媒体资产模型

以后不再是“图片是普通附件、视频是特殊附件”，而是统一成：

```text
MediaAsset
  -> BlobMediaAsset
  -> StreamingMediaAsset
```

### 7.1 `MediaAsset`

所有媒体共享：

- `asset_id`
- `content_hash`
- `kind`
- `variants`
- `swarm_id`
- `origin_expires_at`
- `retention_policy`
- `local_completeness`
- `seeding_state`

### 7.2 `BlobMediaAsset`

适用于：

- 图片
- GIF
- 静态大图

特征：

- 主链是完整资产 + 多尺寸变体
- 不需要流媒体续播状态机
- 需要 preview/full/original 分层
- 同样进入长期本地保留与 P2P 分发

### 7.3 `StreamingMediaAsset`

适用于：

- 视频
- 音频

特征：

- 主链是 `manifest + segments + P2P`
- 首播后立即高优先级补齐剩余分片
- 本地完整后进入长期保留与做种

## 8. 核心 Owner / Runtime

### 8.1 `MediaAssetOwner`

负责：

- 资产身份
- 资产种类
- 资产变体
- 资产保留策略
- `24 小时` 规则

不负责：

- 播放器交互
- 具体网络实现
- 做种运行时细节

### 8.2 `MediaSessionOwner`

负责：

- 当前查看/播放会话
- 静默恢复
- 等待群友/网络恢复
- 自动续播
- 自动续补齐
- 自动续做种

不负责：

- 持久存储实现
- 具体 P2P 引擎实现

### 8.3 `MediaCacheOwner`

负责：

- 本地已持有内容
- 本地完整度
- 长期保留
- 逐出策略
- 重启/重进页面后如何恢复本地资产真相

不负责：

- 播放器行为
- 壳层提示文案

### 8.4 `SwarmRuntime`

负责：

- 进入 swarm
- 重入 swarm
- 补块
- 做种
- 网络恢复后重 announce

不负责：

- 业务上该不该失败
- 何时提示用户等待
- 何时自然死亡

### 8.5 `PlayerAdapter`

负责：

- 对接 `Shaka/hls.js`、原生播放器、图片查看器
- 转译播放器信号到会话 owner

不负责：

- 定义恢复状态
- 定义缓存真相

## 9. 恢复状态机

### 9.1 视频状态机

视频至少有这些状态：

- `bootstrapping`
- `playing`
- `backfilling`
- `recovering`
- `waiting_for_peer_or_network`
- `locally_complete`
- `seeding`
- `degraded`

关键语义：

1. `bootstrapping -> playing`
   - 首批清单、首段、首批 peer 足够后进入正常播放。
2. `playing -> backfilling`
   - 播放过程中立即开始高优先级补齐剩余分片。
3. `playing/backfilling -> recovering`
   - 当前可用源失效，系统进入静默重建。
4. `recovering -> playing`
   - 本地分片、peer 或冷源重新凑够播放条件后自动恢复。
5. `recovering -> waiting_for_peer_or_network`
   - 暂时真的无 enough bytes，开始等待。
6. `waiting_for_peer_or_network -> playing`
   - 网络或 peer 恢复后自动续播。
7. `backfilling -> locally_complete -> seeding`
   - 整资产补齐后，进入长期本地保留与做种。
8. 只有恢复预算耗尽，才 `-> degraded`。

### 9.2 图片状态机

图片至少有这些状态：

- `bootstrapping`
- `preview_ready`
- `backfilling_full_asset`
- `recovering`
- `waiting_for_peer_or_network`
- `locally_complete`
- `seeding`
- `degraded`

关键语义：

1. 先给 preview，不阻塞打开；
2. 再静默补齐 full/original；
3. 补齐后长期保留并做种；
4. 冷源或 peer 暂时不可用时，先恢复、再等待、最后才降级。

### 9.3 恢复优先级

视频：

1. 本地已持有分片  
2. peer swarm  
3. 冷源保底  
4. 等待网络/peer  
5. 最后才 `degraded`  

图片：

1. 本地完整资产  
2. 本地 preview + peer 补 full  
3. 冷源保底  
4. 等待网络/peer  
5. 最后才 `degraded`  

### 9.4 明确不是无限静默

产品已明确选择：

- 先静默恢复
- 再等待群友/网络恢复
- 超过等待预算后，明确提示“正在等待群友/网络恢复”

这保证体验既优雅，又诚实。

## 10. 24 小时冷备与自然死亡规则

这条规则必须是领域规则，不是注释习惯。

正式写成：

- `origin_retention = 24h`
- `origin_service_window = 24h`

含义：

1. 原始上传文件只保留 `24 小时`；  
2. `24 小时` 内：
   - 原始文件作为冷备真相和冷启动回源存在；
   - 系统允许它为弱 swarm、冷门资产、首批节点兜底；  
3. `24 小时` 后：
   - 原始文件删除；
   - 正式可用性主要依赖分片资产、完整持有者与 peer 网络；  
4. 若没有足够完整持有者：
   - 资产允许自然死亡；
   - 这不是 bug，而是协议语义。  

这一步必须明确写进 spec，防止后续有人偷偷把旧冷源继续保活成第二主链。

## 11. 后端契约

后端以后不再主要提供“普通附件直链”，而要提供稳定媒体契约。

### 11.1 `MediaAssetDescriptor`

提供：

- 资产身份
- 资产类型
- 变体列表
- 冷备窗口
- 保留策略
- swarm 所需稳定标识

禁止：

- 壳专属展示字段
- 播放器内部字段
- 某个端专属流程控制字段

### 11.2 `ManifestDescriptor`

用于视频/音频：

- 标准流媒体主链
- 清单地址/版本
- 分段描述
- 必要的 bootstrap 信息

### 11.3 `VariantDescriptor`

用于图片等 blob 资产：

- thumbnail
- preview
- full/original

### 11.4 `SwarmDescriptor`

提供：

- `swarm_id`
- tracker/bootstrap 线索
- 必要 token
- peer 协作基础契约

不提供：

- 前端本地存储键
- 壳层私有缓存结构

### 11.5 `OriginDescriptor`

明确：

- 原始冷源只在窗口内有效
- 何时失效
- 何时应彻底退出主链

## 12. 多壳共核边界

跨端必须共享：

- `MediaAsset` 协议
- 恢复状态语义
- 做种语义
- 保留规则
- `24 小时` 规则
- 错误语义
- snapshot 语义

各壳只自己决定：

- UI 怎么画
- 文案怎么显示
- 播放器怎么接
- 端侧后台能力怎么适配

这意味着：

- `Web`、`iOS`、`Android`、`Desktop`、`CLI` 共核；
- 不允许各端各自发明自己的“本地完整”“等待 peer”“恢复成功”语义。

## 13. 轮子策略

### 13.1 视频主链

优先复用成熟流媒体生态：

- 流媒体协议：`HLS / DASH`
- 播放核心：`Shaka Player` 或 `hls.js`
- P2P 分发：`p2p-media-loader`

### 13.2 平台级 P2P 能力

`WebTorrent` 继续是正式能力，但不把它宗教化成所有媒体唯一主链：

- 在 `Web` 第一参考实现中继续发挥满血能力；
- 在 blob 资产、冷启动、现有文件级协作分发、过渡阶段里持续扮演强角色；
- 若某类标准流媒体链在某端有更成熟的分片级 P2P 轮子，也允许通过 adapter 接入，不改变协议核心。

这不是削弱 `WebTorrent`，而是把它放在它最擅长的位置，而不是逼它冒充完整媒体平台。

### 13.3 Web 端底座

直接复用：

- `Workbox`
- `CacheStorage`
- `IndexedDB / OPFS`
- `WebTorrent`
- `Shaka / hls.js`
- `p2p-media-loader`
- `PhotoSwipe`
- 必要时保留 `Vidstack` 作为 UI/provider 层

### 13.4 坚决不手搓

- 私有 SW 媒体缓存框架
- 私有 `Range` 媒体缓存协议
- 私有播放器恢复核心
- 私有分片 P2P 引擎
- 私有媒体数据库框架
- 私有跨端媒体平台框架

## 14. 哪些旧路径必须退场

后续一旦新协议上来，下面这些必须定义退场点：

1. 以单次解析 `src` 为中心的媒体播放结果缓存；
2. 以原始附件内容地址为主链的播放路径；
3. 把 `WebTorrent` 只当作 hint 层的半截集成；
4. 壳层或聊天媒体编排继续持有恢复语义；
5. `app-sw` 之外再长一套私有媒体缓存拼接逻辑；
6. 各端各自写一套不同的恢复状态分支。  

只要这些旧路径长期并存，就说明设计没有真正落地。

## 15. 为什么这次能一次修好，而不是再返工

“一次修好”不是指一次提交，而是指一次把下面这些东西都讲清楚：

1. 终局协议  
2. 资产模型  
3. 真相 owner  
4. 恢复状态机  
5. `24 小时` 规则  
6. 多壳共核边界  
7. 轮子边界  
8. 旧路径退场原则  

后续实现虽然可以分阶段，但不会再在：

- 附件主链还是资产主链？
- `WebTorrent` 是 hint 还是正式平面？
- 图片是不是也进入协议？
- 原始文件是不是长期主真相？

这些方向性问题上反复摇摆。

## 16. 分阶段落地顺序

这是一份全吃下终局的 spec，但实现必须分阶段。

### 阶段 0：保护性失败测试

先补 characterization test：

- 后端关闭后正在播放的视频如何表现；
- 网络恢复后是否自动静默恢复；
- 本地已完整资产是否能重开；
- peer 消失时是否进入等待态而不是无限转圈；
- 图片 full/original 在 peer/冷源波动时如何恢复。  

### 阶段 1：协议核心与 owner 收口

先立住：

- `MediaAssetOwner`
- `MediaSessionOwner`
- `MediaCacheOwner`
- `SwarmRuntime`

并写清旧媒体编排与壳层路径的退场点。

### 阶段 2：Web 参考实现先修当前问题

目标：

- 在 `Web` 上先解决黑屏、灰屏、转圈；
- 但必须站在新 owner 模型上，不走补丁路线。

### 阶段 3：视频主链升级

后端开始产出标准流媒体资产：

- manifest
- segments
- swarm bootstrap 信息

原始附件链正式退到 `24 小时` 冷备。

### 阶段 4：图片全面纳入统一协议

图片进入：

- 长期本地保留
- P2P 分发
- 统一保留/过期/恢复语义

### 阶段 5：跨端适配

`iOS / Android / Desktop / CLI` 只做 runtime adapter，不改协议核心。

## 17. 失败判定

后续实现只要出现下面任一情况，就说明已经开始漂：

1. 壳层继续持有恢复语义；  
2. 媒体主真相仍然是静态 `src`；  
3. 本地完整度在多个层重复判定；  
4. 原始附件主链和资产主链长期双活；  
5. `WebTorrent` 外又包第二套私有 P2P 核心；  
6. `Workbox` 外又长第二套私有缓存核心；  
7. 不同端各自定义不同恢复状态语义；  
8. 新 owner/runtime 上线后，旧路径没有同步退场；  
9. 只补成功路径，不补失败路径测试；  
10. 为了图快继续在热点模块堆分支，不做边界收缩。  

## 18. 完成定义

### 18.1 当前阶段完成定义

做到下面这些，就算本次 `Web` 阶段真正收口：

1. 图片与视频都已进入统一 `MediaAsset` 协议；
2. 视频播放不再以原始附件直链为正式主链；
3. 图片正式拥有本地长期保留元数据与 P2P 分发语义；
4. `Web` 客户端在网络波动下获得持续播放、静默恢复、自动续补齐；
5. 开始查看后，客户端默认尽快补齐整资产并长期保留；
6. `MediaCacheOwner` 已负责 `kind / contentHash / retainedAt / lastAccessAt` 这类本地完整资产真相；
7. `SwarmRuntime` 已具备 acquire / release / presence 停止 / runtime reset 清理闭环；
8. `24 小时` 冷备窗口与自然死亡规则已正式入编；
9. 项目没有再造第二套播放器、缓存、P2P 核心；
10. 旧附件直链主链在 `Web` 当前阶段已经明显退场为冷备。

### 18.2 跨端终局完成定义

做到下面这些，才算完整跨端媒体协议真正完成升级：

1. 图片、视频、音频都已进入统一 `MediaAsset` 协议；  
2. 视频播放不再以原始附件直链为正式主链；  
3. 图片也正式拥有本地长期保留与 P2P 分发语义；  
4. `Web / iOS / Android / Desktop / CLI` 共用同一套媒体协议核心；  
5. 用户在网络波动下获得持续播放、静默恢复、自动续做种；  
6. 开始查看后，客户端默认尽快补齐整资产并长期保留；  
7. `24 小时` 冷备窗口与自然死亡规则已正式入编；  
8. 项目没有再造第二套播放器、缓存、P2P 核心；  
9. 旧附件直链主链已经明显退场。  

## 19. 一句话结论

终局不是把现有“附件 + 一次性 `src` + 半截 WebTorrent”继续补成更复杂的网页逻辑。  
终局应该是：

**一个默认暴力互助、跨端共核、图片与视频统一资产化、以成熟轮子为底座、原始冷源只保底 `24 小时` 的志愿者型媒体分发系统。**
