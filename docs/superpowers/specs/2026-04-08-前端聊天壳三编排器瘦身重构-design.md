# 前端聊天壳三编排器瘦身重构设计

日期：2026-04-08  
状态：设计已确认，待进入 implementation plan  
范围：`frontend` 聊天主壳、房间恢复链、realtime 编排、阅读推进链、对应测试重排  
约束：最多新增 3 个前端运行时代码 `.ts` 文件；本期测试默认复用现有 spec 文件，不额外申请新的测试文件预算；不改 Rust 后端契约；不改变现有业务行为语义；重构过程必须以“保行为迁移”为第一原则

## 0. 一句话结论

这次重构不是为了把 [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 拆成更多文件，而是为了把它体内已经形成的三条完整业务编排链剥离出来，分别收进三个稳定、可测试、可替换的前端 application orchestration 模块里：

1. `房间恢复编排`
2. `房间实时编排`
3. `阅读推进编排`

最终要得到的不是“文件更多”，而是：

1. `聊天壳` 更薄，只负责装配、接线、渲染
2. `房间内核` 更像前端同步编排核心，而不是摆设
3. 新功能以后不再默认回流进一个超级壳组件
4. 测试覆盖跟着稳定边界走，而不是继续堆进一个巨型 spec

## 1. 当前问题

当前 `frontend` 已经摸出了若干正确方向：

1. [frontend/契约.ts](/E:/koko/frontend/契约.ts) 负责共享契约
2. [frontend/传输.ts](/E:/koko/frontend/传输.ts) 负责 transport adapter
3. [frontend/视图.ts](/E:/koko/frontend/视图.ts) 负责 presenter 派生
4. [frontend/房间滚动器.ts](/E:/koko/frontend/房间滚动器.ts) 负责 DOM 滚动副作用
5. [frontend/房间内核.ts](/E:/koko/frontend/房间内核.ts) 已经承接了一部分状态机语义

真正的问题不在于这些文件“太小”，而在于职责分布失衡：

1. [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 同时承担了恢复、自愈、订阅、重订阅、权威事件并流、乐观消息、已读推进、贴底跟随、历史补偿后的协调以及最终模板渲染
2. 旁边的模块虽然存在，但很多只承接了部分边角逻辑，没有真正分走完整规则链
3. 每次迭代一旦追求“先跑通”，新需求就很容易顺手继续塞回 `聊天壳`

这会直接导致：

1. 壳层文件重新膨胀
2. 测试越来越依赖集成式大 spec，而不是各模块自己的局部确定性
3. 新功能增删改必须读懂整个壳组件，维护成本持续上升

## 2. 设计目标

### 2.1 必须达到

1. [frontend/聊天壳.ts](/E:/koko/frontend/聊天壳.ts) 不再持有三条完整业务编排链
2. 前端继续遵守“DDD 领域真相在后端，前端只承载壳层编排”的边界
3. `frontend` 内部形成更接近 Unix 的职责分解：每个模块只回答一种问题
4. 重构后功能增删减应主要落在编排器、内核或 presenter，而不是继续堆回壳层
5. 重构全程不能改变现有用户可见行为

### 2.2 明确不做

1. 不把前端做成新的领域中心
2. 不改后端 API、socket 协议、错误码、契约字段
3. 不顺手重写 UI 结构、样式语言或文案体系
4. 不为“拆文件”制造碎片化文件海

## 3. 架构原则

### 3.1 DDD 约束

前端这里只有 **同步编排真相**，没有 **业务领域真相**。

后端继续负责：

1. 成员资格
2. 权限裁决
3. 消息是否成立
4. 首条未读语义
5. 房间快照与事件顺序事实
6. 阅读推进的权威持久化结果

前端负责：

1. 什么时候 bootstrap
2. 什么时候恢复房间
3. 什么时候建立 / 重建订阅
4. 什么时候把滚动观测解释成壳层阅读意图
5. 什么时候把稳定状态翻译成展示模型

### 3.2 Unix 智慧

这次拆分遵守三个约束：

1. 一个模块只回答一种问题
2. 模块之间通过清晰接口协作，而不是共享一大坨隐式上下文
3. 能放进成熟现有边界里的逻辑，就不再额外手搓新层次

所以这次新增的 3 个文件不是“工具箱”，而是三个明确的 application orchestration 单元。

## 4. 选型比较

### 方案 A：继续维持一个大壳组件，只做零碎抽函数

优点：

1. 改动表面最小
2. 短期感觉最快

问题：

1. 规则链仍然留在壳里
2. 文件还会继续回胖
3. 测试结构不会真正改善

不采用。

### 方案 B：大量新增 `service / strategy / coordinator / manager` 文件

优点：

1. 看起来拆得很干净
2. 每块都能单独命名

问题：

1. 很容易把前端拆成碎片海
2. 认知负担会上升
3. 和当前项目“文件数量长期克制”的纪律相冲突

不采用。

### 方案 C：在现有边界之上，只补 3 个真正缺失的编排器

优点：

1. 保持现有正确边界不推翻
2. 只把真正该独立的三条规则链抽出来
3. 风险最低，最符合“保行为迁移”

采用此方案。

## 6. 三个编排器的边界

### 6.1 房间恢复编排

它只回答一个问题：

**当前房间如何从无到有，以及从损坏恢复到稳定。**

承接的能力包括：

1. bootstrap
2. 首次进房
3. 读取本地恢复锚点并恢复房间
4. 基于快照建立房间基线
5. `invalid_session` 触发的重新 bootstrap
6. `room_not_found / membership_required / 5xx` 等恢复分支
7. 房间标题与历史房间缓存的收口写入
8. realtime 上报的 `need_snapshot_reload / invalid_session` transport 异常的业务解释与处理

它不负责：

1. socket 生命周期
2. DOM 滚动
3. 文案渲染

### 6.2 房间实时编排

它只回答一个问题：

**实时通道如何接上、恢复，并把权威事件稳定送回壳层与内核。**

承接的能力包括：

1. 建立 socket
2. 订阅房间
3. 控制面结果处理与事件解码
4. 把 `need_snapshot_reload / invalid_session` 上报成 transport 异常
6. 权威事件并流
7. 乐观消息与权威消息收敛

它不负责：

1. 首次 bootstrap
2. 真正执行 session 刷新
3. 真正执行 snapshot reload
4. 阅读推进 flush
5. DOM 视口观察

### 6.3 阅读推进编排

它只回答一个问题：

**什么时候前端观测到的阅读位置，才算可以正式上报。**

承接的能力包括：

1. 采样候选已读位置
2. 候选转待提交
3. 节流 flush
4. 首屏稳定后何时允许进入正式推进
5. 贴底跟随时的被动补读
6. 跳到最新后的跟随与补读协同
7. 历史页请求、历史页并入与 `historyLoading / historyErrorCode / hasMoreBefore` 这条冷路径规则

它不负责：

1. 房间恢复分支
2. socket 生命周期
3. 模板渲染
4. DOM 可见性与 near-bottom 原始判断

### 6.4 稳定 command / event 契约

这次重构前必须先把编排器之间的协作表面钉死，避免它们退化成 3 个共享可变状态 helper。

#### 房间恢复编排输入

1. `启动引导`
2. `请求进房(roomCode)`
3. `请求恢复当前房间(roomId)`
4. `接收 transport 异常(kind, roomId?)`
5. `请求处理恢复失败(error, keepRoomVisible)`
6. `请求刷新会话`
7. `请求按 roomId 重载快照(roomId)`

#### 房间恢复编排输出

1. `房间基线已建立(snapshot, roomDisplayTitle)`
2. `恢复被拒绝(code, keepRoomVisible)`
3. `会话已刷新(sessionId, displayAlias)`
4. `需要重建 realtime(sessionId)`

#### 房间实时编排输入

1. `确保已连接(sessionId)`
2. `请求订阅(roomId, from)`
3. `请求发送消息(roomId, clientMessageId, text)`
4. `接收 transport connect_error`
5. `接收 transport control_result`
6. `接收 transport room_event / room_events`

#### 房间实时编排输出

1. `transport 异常已上报(kind, roomId?)`
2. `订阅已建立(latestEventPosition)`
3. `权威事件已到达(events, latestEventPosition)`

#### 阅读推进编排输入

1. `接收候选已读位置(position)`
2. `首屏稳定完成(mode)`
3. `权威事件已到达`
4. `请求跳到最新`
5. `请求加载更早历史`

#### 阅读推进编排输出

1. `待提交已读位置已变化(position)`
2. `请求 flush 已读(position)`
3. `历史页已并入(messages, hasMoreBefore)`
4. `历史页失败(code)`

这张契约表的目的只有一个：

**先定义命令和事件，再搬实现；不允许先搬一坨函数，再回头猜模块边界。**

## 8. 安全迁移顺序

### 8.1 总原则

不能做“一次大搬家”，必须做 **保行为迁移**。

每一步遵守：

1. 先锁测试
2. 再复制同语义实现到新文件
3. 再让 `聊天壳` 变成转调
4. 全绿后才删旧实现

### 8.2 推荐顺序

0. 先在壳层内部抽出“恢复编排 <-> 实时编排 <-> 阅读推进编排”的固定 command / event 契约，但暂时不搬行为
1. 再迁 `房间恢复编排`
2. 再迁 `房间实时编排`
3. 最后迁 `阅读推进编排`

原因：

1. 恢复链和 realtime 链当前通过 `invalid_session / need_snapshot_reload` 交织最深，必须先钉契约再搬
2. 恢复编排落稳后，realtime 才能安全退回到“只上报 transport 异常，不自己解释恢复语义”
3. 阅读推进依赖稳定的房间基线和事件并流，放最后风险最低

### 8.3 明确禁止

1. 不边迁移边改协议
2. 不边迁移边改状态机事件名
3. 不边迁移边重写样式
4. 不一次同时改三条链
5. 不把新文件做成“万能工具箱”

## 9. 测试策略

### 9.1 先锁当前行为

在现有 [frontend/tests/聊天壳测试.spec.ts](/E:/koko/frontend/tests/聊天壳测试.spec.ts) 基础上，迁移前必须确保这些关键场景已被锁住：

1. bootstrap 恢复 / 首次进房 / 刷新恢复
2. `need_snapshot_reload`
3. `invalid_session` 自愈
4. `room_not_found` 与 `membership_required` 分支差异
5. 首屏未读定位
6. 历史分页补偿
7. 已读推进节流
8. realtime 与 history 并流不重复消息

### 9.2 重构后的测试重排

壳层大 spec 不再继续无上限吸附新规则。

本期不新增新的测试文件；测试预算默认复用现有 spec，并通过新的 `describe` 分组直测新编排器。

本期至少要补出三类“直接测试”：

1. `房间恢复编排` 的规则测试
2. `房间实时编排` 的规则测试
3. `阅读推进编排` 的规则测试

这里的“直接测试”指：

1. 测试直接 import 编排器模块
2. 不必经由壳层 render 才能覆盖规则
3. 但文件层面优先复用现有 spec，避免本期额外吃掉文件预算

壳层保留：

1. 少量高价值集成场景
2. UI 接线是否贯通
3. render 是否消费正确展示模型

### 9.3 长期约束

以后单个 spec 一旦出现下面任一信号，就必须先重整边界再继续加案例：

1. 明显出现第二条完整规则链
2. 只看测试文件标题就已经跨越多个应用层职责
3. 一个 spec 同时维护大量 fake transport / fake socket / fake storage / fake scroll 细节
