## 0. 这份手册是干什么的

这份手册只做一件事：

**让你这种电脑小白，也能把 `koko` 用“点 GitHub 按钮”的方式，正式上线到一台 Debian 12 VPS。**

它不讲源码细节，不讲架构术语，不讲 Docker 原理课。  
它只讲：

1. 你要先准备什么；
2. 哪些值必须填；
3. 先点哪里、后点哪里；
4. 出错先看哪里；
5. 以后升级和回滚怎么做。

一句话：

**这不是开发文档，这是值班操作手册。**

---

## 1. 先记住整个上线主链

先不要急着看细节，先把全局顺序记住：

1. 你有一台公网 Debian 12 VPS。
2. 你有一个已经推到 GitHub 的私有仓库。
3. 你有一个正式域名，走 Cloudflare。
4. 你把生产环境变量填好。
5. 你把 GitHub Secrets 填好。
6. 你在 GitHub 的 `Actions` 页面点一次 `Initial Deploy`。
7. GitHub Actions 会把发布包送到 VPS。
8. VPS 自己执行 `install.sh`、`deploy.sh`、`healthcheck.sh`。
9. 成功后，域名就会指向正式站点。

以后日常：

1. 新代码 push 到 `main`；
2. 自动触发 `Deploy`，或者你手动点 `Deploy`；
3. 出问题就手动点 `Rollback`。

一句话：

**GitHub 负责发命令，VPS 负责真正运行，Cloudflare 负责把正式域名流量转进来。**

---

## 2. 你现在至少要有这 4 样东西

正式上线前，你必须先有：

1. **一台 Debian 12 VPS**
   - 必须有公网 IP
   - 你必须能用 SSH 连上去

2. **一个正式域名**
   - 例如 `koko.example.com`
   - 域名 DNS 要能在 Cloudflare 里管理

3. **一个 GitHub 仓库**
   - 代码已经推上去
   - 你有这个仓库的写权限

4. **VPS 登录方式**
   - 推荐用 SSH 私钥
   - 因为 GitHub Actions 要靠它进 VPS

如果这 4 样里少任何一样，现在先别点上线按钮。

## 5. 每个环境变量到底是什么意思

下面这些变量，按“必须立刻改”和“可以先默认”分开讲。

### 5.1 必须改的变量

#### `KOKO_DOMAIN`

示例：

```env
KOKO_DOMAIN=koko.example.com
```

作用：

- 这是你的正式公网域名
- Caddy 只认这一套正式入口

不要填：

- `localhost`
- `127.0.0.1`
- 只写裸 IP

#### `POSTGRES_PASSWORD`

示例：

```env
POSTGRES_PASSWORD=换成很长很复杂的密码
```

作用：

- 这是 Postgres 容器自己的数据库密码

要求：

- 不要用 `change-me`
- 不要太短
- 最好是长随机串

#### `DATABASE_URL`

示例：

```env
DATABASE_URL=postgres://postgres:你的数据库密码@postgres:5432/koko
```

作用：

- 这是 Rust 后端连数据库时使用的连接串

最关键的一点：

- 这里的主机名要写 `postgres`
- 不能写 `127.0.0.1`
- 因为正式部署里，服务之间通过 Compose 内部服务名互相找

#### `ADMIN_PASSWORD`

示例：

```env
ADMIN_PASSWORD=换成后台管理密码
```

作用：

- 这是后台管理相关的主密码

要求：

- 也不要用 `change-me`
- 和数据库密码不要一样

#### `SWARM_TICKET_SECRET`

示例：

```env
SWARM_TICKET_SECRET=换成很长的随机密钥
```

作用：

- 这是协作分发票据签发用的密钥

要求：

- 必须改
- 必须足够长
- 不要和别的密码混用

### 5.2 一般可以先保留默认的变量

#### `POSTGRES_DB`

默认：

```env
POSTGRES_DB=koko
```

意思：

- 数据库名
- 一般不用改

#### `POSTGRES_USER`

默认：

```env
POSTGRES_USER=postgres
```

意思：

- 数据库用户名
- 小白阶段可以先不改

#### `RUST_LOG`

默认：

```env
RUST_LOG=info
```

意思：

- 后端日志级别
- 初次上线先用 `info` 就够了

#### `APP_PORT`

默认：

```env
APP_PORT=8080
```

意思：

- `app` 容器内部监听端口
- 一般不用改

### 5.3 同源路径类变量，一般不要乱改

#### `MEDIA_TUS_PUBLIC_ENDPOINT`

默认：

```env
MEDIA_TUS_PUBLIC_ENDPOINT=/files
```

意思：

- 浏览器上传媒体时对外看到的同源路径

#### `SWARM_TRACKER_PUBLIC_URL`

默认：

```env
SWARM_TRACKER_PUBLIC_URL=/api/swarm/announce
```

意思：

- 浏览器侧 tracker 公开路径

这两个值不要随便改成完整 URL。  
当前部署设计就是要求它们继续保持**同源相对路径**。

### 5.4 内部 sidecar 协作变量，一般先别动

这些值主要是容器之间内部通信：

- `ATTACHMENT_STORAGE_DIR`
- `MEDIA_TUS_SERVER_PORT`
- `MEDIA_TUS_BASE_PATH`
- `MEDIA_TUS_UPLOAD_DIR`
- `MEDIA_TUS_INTERNAL_BASE_URL`
- `SWARM_TRACKER_PORT`
- `SWARM_TRACKER_UPSTREAM_URL`
- `SWARM_SEEDER_PORT`
- `SWARM_SEEDER_CONTROL_BASE_URL`
- `SWARM_SEEDER_TRACKER_URL`
- `SWARM_WEB_SEED_PUBLIC_ENDPOINT`
- `SWARM_PEER_PRESENCE_STALE_SECONDS`

小白阶段建议：

**先全部照模板默认值，不要自己发明新端口。**

原因很简单：

- 这些值互相咬合
- 一处乱改，可能整条媒体链都断

## 6. GitHub Secrets 要填什么

GitHub Actions 真正要用的 Secrets，至少有这 4 个。

进入路径：

1. 打开 GitHub 仓库
2. `Settings`
3. `Secrets and variables`
4. `Actions`
5. `New repository secret`

### 6.1 `VPS_HOST`

填什么：

- VPS 公网 IP
- 或者已经指向 VPS 的 SSH 域名

示例：

```text
203.0.113.10
```

### 6.2 `VPS_USER`

填什么：

- 你 SSH 登录 VPS 用的用户名

示例：

```text
root
```

或者：

```text
debian
```

### 6.3 `VPS_SSH_KEY`

填什么：

- 你的 SSH 私钥全文

注意：

- 是私钥，不是公钥
- 一般内容以 `-----BEGIN OPENSSH PRIVATE KEY-----` 开头

### 6.4 `PROD_ENV_FILE`

这次主链实现里，workflow 还**没有直接消费**这个 secret。  
当前版本是：

- 由 VPS 上的 `/opt/koko/env/production.env` 作为生产真相
- `install.sh` 会先复制模板
- 你再在 VPS 上把模板改成真实值

所以当前你必须知道：

**这个仓库当前的一键部署主链，生产环境变量真相在 VPS 文件，不在 GitHub Secret。**

这不是 bug，是当前设计选择。

如果以后你想把整份环境变量也托管进 GitHub Secret，可以再做第二阶段收口。

## 7. Cloudflare 该怎么配

这一步只讲最小必要配置。

### 7.1 先建 DNS 记录

如果你要用子域名，比如：

```text
koko.example.com
```

那就在 Cloudflare 里加一条：

- 类型：`A`
- 名称：`koko`
- 内容：你的 VPS 公网 IP

Cloudflare 官方文档：

- [Create subdomain records](https://developers.cloudflare.com/dns/manage-dns-records/how-to/create-subdomain/)

### 7.2 SSL/TLS 模式要用 `Full (strict)`

不要用：

- `Flexible`

要用：

- `Full (strict)`

原因：

- `Flexible` 会把回源链路降成不严格模式
- 和我们现在的正式 HTTPS 主链不一致

Cloudflare 官方文档：

- [Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/)

一句话：

**正式环境就是 `Full (strict)`，不要自己发明别的。**

## 8. VPS 上第一次该做什么

在点 `Initial Deploy` 前，你至少要确认 3 件事：

1. 这台 VPS 是 Debian 12
2. 你能 SSH 上去
3. 这个 SSH 用户是：
   - `root`
   - 或者有 `sudo`

因为 workflow 里会在远端执行：

- `install.sh`
- `deploy.sh`
- `healthcheck.sh`

如果你连 `sudo` 都没有，这条主链跑不起来。

### 8.1 第一次上线前要手工改环境变量文件

当前最稳的做法是：

1. 先让 `install.sh` 在 VPS 上生成模板
2. 你 SSH 进去修改：

```text
/opt/koko/env/production.env
```

把里面这些值改掉：

- `KOKO_DOMAIN`
- `POSTGRES_PASSWORD`
- `DATABASE_URL`
- `ADMIN_PASSWORD`
- `SWARM_TICKET_SECRET`

这是第一次正式上线前最重要的人工步骤。

如果你不改这些值，服务可能能起，但那不叫正式环境。

## 9. 第一次正式上线怎么点

官方前提：

- workflow 必须在默认分支
- workflow 里要有 `workflow_dispatch`

GitHub 官方文档：

- [Manually run a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)
- [Workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)

### 9.1 第一次上线的顺序

1. 代码已经在 `main`
2. GitHub Secrets 已填
3. Cloudflare DNS 已指向 VPS
4. VPS 能 SSH 登录
5. VPS 上 `/opt/koko/env/production.env` 已改成真实值
6. 打开 GitHub 仓库的 `Actions`
7. 点 `Initial Deploy`
8. 输入版本号，例如：

```text
v0.1.0
```

9. 点 `Run workflow`

### 9.2 它背后会做什么

`Initial Deploy` 会自动：

1. 打包当前仓库
2. 上传发布包到 VPS
3. 在 VPS 上准备 `/opt/koko` 目录树
4. 安装 Docker / Compose
5. 执行正式部署
6. 跑健康检查

### 9.3 成功以后你该看到什么

成功后至少应该满足：

1. GitHub Actions 运行变绿
2. `healthcheck.sh` 通过
3. 你的正式域名能打开首页

## 10. 以后日常怎么升级

### 自动升级

当前 `deploy.yml` 已配置：

- `push` 到 `main` 会自动触发

所以以后日常最简单的方式是：

1. 你把代码合到 `main`
2. GitHub 自动跑 `Deploy`

### 手动升级

如果你想自己控制时机：

1. 打开 `Actions`
2. 点 `Deploy`
3. 可以手动填版本号，也可以让它自动生成

## 11. 出问题怎么回滚

### 11.1 回滚入口

1. 打开 GitHub 仓库 `Actions`
2. 点 `Rollback`
3. 填 `target_version`

例如：

```text
v0.1.0
```

4. 点 `Run workflow`

### 11.2 回滚做的事

回滚不是重新 git 拉代码。  
当前设计是：

1. 切 `/opt/koko/current`
2. 重新用目标版本目录起服务
3. 再跑健康检查

也就是说：

**回滚真相是“切版本目录”，不是“VPS 自己 git pull”。**

## 12. 出错先看哪里

小白排障时，不要一上来全世界乱翻。  
按这个顺序看。

### 第 1 层：看 GitHub Actions

先看：

- 是 `Initial Deploy` 挂了
- 还是 `Deploy` 挂了
- 还是 `Rollback` 挂了

最常见问题：

1. `VPS_HOST / VPS_USER / VPS_SSH_KEY` 填错
2. VPS 不能 SSH 登录
3. 远端没有 `sudo`
4. `production.env` 里值没改

### 第 2 层：看健康检查

核心脚本：

- [ops/healthcheck.sh](</E:/koko/ops/healthcheck.sh>)

它主要查：

1. `https://正式域名/`
2. `app`
3. `postgres`
4. `tusd`
5. `tracker`
6. `seeder`

如果这里挂了，就说明不是“日志看着像没事”，而是真没活。

### 第 3 层：看正式环境变量

先看 VPS 上：

```text
/opt/koko/env/production.env
```

重点查：

1. `KOKO_DOMAIN` 对不对
2. `DATABASE_URL` 对不对
3. `POSTGRES_PASSWORD` 和 `DATABASE_URL` 里密码是不是一致
4. `SWARM_TICKET_SECRET` 有没有保留成 `change-me`

## 13. 现在这套主链明确不做什么

为了让你少踩坑，这里把“不做的事”也说死。

当前这套正式部署主链：

1. 不用 `cloudflared`
2. 不让 VPS 自己 `git pull`
3. 不做多机高可用
4. 不做 Kubernetes
5. 不做蓝绿发布
6. 不做金丝雀发布
7. 不做复杂控制台

一句话：

**先把“单机、单域名、可升级、可回滚”做到稳定，再谈花活。**

## 16. 当前总裁决

`koko` 当前的正式部署真相可以压成一句话：

**Cloudflare 负责域名入口，GitHub Actions 负责发起部署，Debian 12 VPS 负责真正运行，生产环境变量真相先收口在 VPS 文件，正式服务只保留一条 Docker Compose + Caddy 主链。**

不要在这句话外面再长第二套上线入口、第二套运行入口、第二套环境变量真相。
