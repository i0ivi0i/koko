# Koko 审查维护宪法设计

## 1. 目标

本设计文档用于冻结 `Koko` 仓库根目录 [审查维护.md](/E:/koko/审查维护.md) 的目标、结构、边界与长期使用方式。

这份文档不是一次性的清理计划，不是普通开发规范，也不是“写得好看一点”的风格指南；它是一份面向前人、现在的人、后来者，以及未来任何 AI / agent / 外包维护者的“架构审查与维护宪法”。

它的核心目标只有一个：

- 让任何人每次对项目做开发、重构、修复、依赖调整、工具链变更、运行时接入时，都必须按同一把尺子先审查、再动手、再验收，从制度上持续防止：
  - 手搓成熟轮子
  - 重复造轮子
  - 冗余代码与冗余抽象累积
  - 框架或壳层倒灌核心
  - 业务真相泄漏到错误层级
  - 代码在长期维护中逐步堆成屎山

这份文档必须服务于以下长期架构目标：

- 多壳共核
- DDD 领域清晰
- 乐高积木式可插拔
- 前后端可演进但业务核心不漂移
- 代码简洁、高效、优雅、低心智负担

## 2. 非目标

这份文档明确不承担以下职责：

- 不直接替代 [AGENTS.md](/E:/koko/AGENTS.md) 的代理人格、执行纪律与会话级记忆职责
- 不替代具体功能的 PRD、实现计划或任务拆解文档
- 不沉入某一轮具体清理任务的执行细节
- 不指导单个页面、单个接口或单个测试如何实现
- 不变成空泛的“代码要写好”口号集

它要做的是比 PRD 更稳、比计划更长期、比实现更抽象、但又比普通原则更可执行的治理层文档。

## 3. 文档定位与层级关系

`Koko` 仓库后续将存在三类不同文档，各自职责不能混淆：

### 3.1 [AGENTS.md](/E:/koko/AGENTS.md)

职责：

- 约束代理如何思考、行动、验证、提交
- 保存项目级长期记忆与高优先级执行纪律

局限：

- 它更像“执行者的脑内纪律”和“高密度长期约束”
- 它不适合承载一份所有维护者都拿来过审查门禁的正式制度文档

### 3.2 [审查维护.md](/E:/koko/审查维护.md)

职责：

- 作为仓库根目录的正式制度文件存在
- 约束所有维护者和改动者，不区分人类、AI、agent 或外包人员
- 规定每次开发前、开发中、开发后都必须执行的审查与验收流程
- 规定“禁止手搓轮子”“禁止重复造轮子”“DDD 清晰边界”“反屎山”如何落成硬门禁

### 3.3 [2026-03-30-codebase-audit-and-cleanup.md](/E:/koko/docs/superpowers/plans/2026-03-30-codebase-audit-and-cleanup.md)

职责：

- 作为一轮具体审查/清理战役的执行计划
- 服务于当前这一轮代码清理，而不是永恒治理

关系：

- `审查维护.md` 是制度
- `plans/*.md` 是制度驱动下的阶段性战役方案

## 4. 用户真实诉求冻结

基于本次连续澄清，用户的真实诉求不是“帮我再做一次代码审查”，而是：

- 把架构判断从个人经验升级成一套可重复执行、可交接、可约束未来维护者的长期治理机制
- 让任何人以后改这个项目时，不是问“能不能改”，而是先回答：
  - 这次改动属于哪层
  - 有没有在手搓通用能力
  - 有没有在重复造轮子
  - 有没有制造冗余结构
  - 有没有污染 DDD / 多壳共核边界
  - 有没有提供足够证据证明自己没把系统改乱

更直白地说，用户要的是：

- 一份谁来改都不能把系统改乱的“宪法”
- 一份能让维护者看一眼就知道项目哪里有问题、什么问题不能放行的制度文档

## 5. 设计方案选择

本次脑暴明确排除了两个不够稳的方向：

### 5.1 纯清单式文档

优点：

- 好执行

缺点：

- 太机械
- 无法回答“为什么”
- 一旦遇到新型问题就容易失效

### 5.2 纯原则式文档

优点：

- 高度抽象

缺点：

- 太虚
- 维护者容易各自解释
- 很难作为实际门禁使用

### 5.3 最终采用：制度 + 清单

最终方案明确采用“制度 + 清单”的混合结构：

- 前半部分定义目标、定位、红线、分层判定、复用准入、巨人经验
- 后半部分定义开发前、开发中、开发后、债务延期与回看机制

这是最适合长期维护的形态，因为它同时满足：

- 有原则，不容易漂
- 有清单，不会落空
- 可扩展，可持续新增经验
- 可作为以后所有战役计划的共同上位依据

## 6. 外部经验吸收原则

这份文档不应该凭空长出来，而应明确吸收成熟 IM 系统已公开的结构性经验。

### 6.1 Telegram / TDLib

公开资料显示，TDLib 把复杂客户端基础设施集中收口，负责网络实现、加密、本地存储与有序更新分发，并提供稳定异步接口：

- [TDLib](https://core.telegram.org/tdlib)
- [TDLib Client 文档](https://core.telegram.org/tdlib/docs/classtd_1_1_client.html)
- [Telegram iOS 开源仓库](https://github.com/TelegramMessenger/Telegram-iOS)

本项目应吸收的不是它的具体技术栈，而是：

- 通用复杂性要集中收口
- 更新、同步、连接、存储等基础能力不要散落手搓
- 壳层消费稳定能力，不到处复制胶水

### 6.2 WhatsApp Multi-Device

Meta 官方公开的多设备架构文章清楚体现了“多壳共享同一权威事实”的方向：

- [WhatsApp Multi-Device](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)

本项目应吸收的是：

- 多端不是多套业务真相
- 本地体验态可以存在，但权威事实必须统一
- 壳层不能各自维护自己的业务规则

### 6.3 企业微信 IM 架构

公开工程分享体现了另一类值得吸收的经验：

- [企业微信 IM 架构设计揭秘](https://segmentfault.com/a/1190000040368812)

本项目应吸收的是：

- 主链路与外围能力必须隔离
- 接入、逻辑、存储、外部交互要分层
- 外围能力应异步化、可降级、可隔离

### 6.4 折叠后的通用原则

这份宪法中应固化以下折叠后的结论：

- 核心业务必须独立于壳和框架存在
- 通用复杂性应集中收口，不应散落为手搓胶水
- 消息、权限、成员资格、事件顺序必须有权威事实源
- 主链路优先，外围能力不得拖垮核心链路
- 本地体验态允许存在，但不能冒充业务真相

## 7. 文档必须承载的核心总审美

这份文档不能只强调“正确”，还必须明确 `Koko` 长期接受什么样的代码审美。

这里的“优雅”不能被解释成花哨、炫技、过度技巧化的写法，而必须定义为：

- 简洁
- 高效
- 低冗余
- 低心智负担
- 高可读性
- 高可替换性
- 高可维护性

真正像智者写出来的代码，不是把简单事情写复杂，而是用更少的重复、更清楚的边界、更小的维护成本，把事情做对。

因此，`审查维护.md` 必须明确把以下内容写成价值判断：

- 会让代码越来越厚、越来越绕、越来越难改的写法，默认不优雅
- 为了短期方便增加长期复杂度的结构，默认不通过
- 低价值抽象、重复包装、技巧化浓缩写法、无意义中间层、假状态增长，都应视为劣化信号

## 8. 根目录文档的建议结构

最终落地的 [审查维护.md](/E:/koko/审查维护.md) 建议采用以下结构：

### 8.1 文档目标与适用范围

写清：

- 这是仓库级长期制度文件
- 覆盖代码、依赖、工具链、配置、运行时接入
- 每次开发前、开发中、开发后都必须使用
- 适用于所有改动者

### 8.2 核心原则与不可触碰的红线

写清：

- 业务核心高于具体技术实现
- 复用优先，自研受限
- 分层必须可证明
- 多壳共核，前后端绝不越位
- adapter 只翻译，不决策
- 删除优先于堆叠
- 简洁、高效、优雅优先于“看起来很高级”

并列出不可放行的红线清单。

### 8.3 分层判定法

必须把 `domain / application / contract / adapter / shell` 的允许内容、禁止内容、快速判错法写清。

要求：

- 任何改动在落代码前，必须先写明所属层级
- 说不清归属的改动，不允许直接实现
- 最终文档必须附带一张“依赖方向矩阵”，至少冻结：
  - `domain` 不依赖框架、协议、数据库、壳层
  - `application` 可以依赖 `domain` 与稳定 `contract`，但不依赖具体基础设施实现
  - `contract` 不承载壳层展示语义，不依赖某个具体入口框架
  - `adapter` 可以依赖 `application / domain / contract` 与基础设施，但不得把基础设施细节反推回核心
  - `shell` 只拥有交互编排与本地体验态，不拥有业务真相
- 最终文档必须附带一张“真相归属矩阵”，至少冻结：
  - 权限真相、成员资格真相、消息成立真相、治理语义真相只允许存在于 `domain / application`
  - `contract` 只表达稳定契约，不表达某壳专属 UI 语义
  - `adapter` 只拥有协议态、连接态、运行态投影、错误转码
  - `shell` 只拥有草稿、滚动位置、乐观态、连接提示等本地体验态

### 8.4 复用优先与自研准入门禁

必须把“禁止手搓轮子”变成硬门禁：

- 先查生态、官方文档、现有实现
- 再做候选对比
- 再写不可复用理由
- 最后才允许有限自研
- 最终文档必须冻结“最小证据集”，至少要求：
  - 候选实现列表
  - 比较维度：性能、维护性、生态成熟度、边界适配、可替换性
  - 每个候选被淘汰的明确理由
  - 为什么现有仓库实现不能直接复用
  - 为什么一个薄适配层是合理翻译，而不是重复包装
- 最终文档必须规定：只写一句“我查过了”不算完成复用审查

### 8.5 巨人经验与本项目吸收原则

以 Telegram / WhatsApp / 企业微信等公开经验为证据来源，明确我们吸收的是结构性原则，而不是照抄技术栈。

### 8.6 开发前审查清单

固定要求：

- 分层判定
- 目标与非目标
- 复用预审
- 重复实现排查
- 边界污染预判
- 依赖影响检查
- 验证计划先行
- 债务处理策略

### 8.7 开发中审查清单

固定要求：

- 一旦像轮子就停下来复核
- 禁止边写边放错层
- 禁止偷塞业务真相
- 禁止新增重复入口、重复流程、重复真相
- 新抽象必须有真实压力来源
- 热路径持续保持薄
- 小步开发也要顺手清掉明显冗余
- 技术债即时登记

### 8.8 开发后验收清单

固定要求：

- 结果必须更清楚，而不只是能跑
- 必须复查是否引入新轮子或新冗余
- 必须复查边界是否守住
- 验证必须是新鲜证据
- 债务必须显式处理
- 提交必须干净、可读、可追溯
- 必须做一次长期维护视角复盘

### 8.9 债务记录与延期规则

必须写清：

- 什么债务可以延期
- 什么债务禁止延期
- 每条债务的最小记录字段
- 债务与未来开发的回看绑定关系
- 什么才叫真正清债

### 8.10 固定输出格式与判定顺序

最终文档不能只讲“应当写什么”，还必须冻结它自己的使用格式。

必须至少定义以下固定格式：

- 每次审查都必须输出：
  - 变更范围
  - 层级归属
  - 复用/自研结论
  - 边界风险
  - 验证计划或验证结果
  - 债务处理结论
  - 最终判定：`通过 / 驳回 / 例外放行 / 延期处理`
- 每次审查都必须按固定判定顺序执行：
  1. 先判层级
  2. 再判复用与自研
  3. 再判边界污染风险
  4. 再判冗余/重复实现风险
  5. 再判验证是否充分
  6. 最后才允许通过、驳回或例外放行
- 没有最终判定状态的审查记录，视为无效记录
- 最终文档必须把审查状态与可执行动作绑定写死：
  - `通过`：允许继续实现、提交、合并或收口
  - `驳回`：不得进入实现或不得继续提交/合并，必须先回到设计或审查补证
  - `例外放行`：只允许在已批准的例外范围内继续，且必须附带失效条件与补审要求
  - `延期处理`：只允许带着显式债务记录继续，且不得伪装成通过
- 无有效审查记录的改动，不得视为完成

## 9. 宪法文档的执行方式

最终文档不能只是阅读材料，必须具备明确执行方式。

### 9.1 触发时机

默认在以下时机强制触发：

- 新功能开发前
- 功能开发过程中
- 开发完成准备收口时
- 重要重构前后
- 引入新依赖前
- 调整工具链、配置、运行时接入前
- 涉及 contract、adapter、shell 边界变更时

### 9.2 使用方式

推荐的实际使用方式：

- 开发前对照开发前清单逐项回答
- 开发过程中用开发中清单做阶段性自检
- 提交前用开发后清单做收口
- 若发现债务，则立即登记
- 若开启具体清理战役，再由 `plans/*.md` 承接执行

### 9.3 适用对象

必须明确写入：

- 适用于人类开发者
- 适用于 AI / agent
- 适用于未来接手者与协作者
- 任何人都不能因为“只是小改动”绕过制度

### 9.4 例外审批、争议裁决与紧急变更机制

最终文档必须明确：

- 谁可以放行例外：
  - 默认只有仓库主人或其明确指定的主维护者可以批准例外
  - AI / agent 不得自批例外
- 哪些情况允许走紧急豁免：
  - 安全事故
  - 数据损坏风险
  - 生产阻断
  - 必须立即止血的运行故障
- 紧急豁免也必须满足：
  - 仅允许绕过非核心流程，不允许绕过根本红线
  - 必须在当前修复结束后立即补做事后审查
  - 例外必须有失效时间或失效触发点，不能永久挂起
- 对审查结论有争议时，必须以上述固定证据集提交给仓库主人/主维护者裁决

### 9.5 证据留痕的固定落点

最终文档必须冻结“审查结果记到哪里”，避免制度沦为口头自检。

必须冻结如下规则：

- 普通且低风险改动：
  - 审查证据可留存在当前活跃 plan/spec 文档中，但必须包含完整必填字段
- 以下情况必须单独落为审查记录：
  - 跨层边界移动
  - 新增依赖或新基础设施能力
  - 申请例外放行
  - 债务延期
  - 明确发现重复造轮子或高风险冗余
- 单独审查记录固定落点为：
  - `docs/superpowers/reviews/YYYY-MM-DD-<topic>-审查记录.md`
- 最小记录模板必须至少包含：
  - 变更范围
  - 层级归属
  - 复用/自研结论
  - 候选对比摘要
  - 风险点
  - 验证命令
  - 债务结论
  - 债务责任人
  - 回看触发点
  - 最晚处理时机
  - 审查最终状态

### 9.6 清理型维护的反失控约束

最终文档必须明确防止“以审查/清理之名重构一切”。

至少应冻结以下约束：

- 清理默认一轮只打一个热点或一个热点簇
- 先做表征测试或强化现有行为验证，再做清理
- 优先删除、合并、收口，不优先大改写
- 禁止一轮跨多个独立子系统的大面积重写，除非仓库主人明确批准
- 若清理会改变多个层级的公共边界，必须升级为单独计划，不得混在普通开发里顺手完成

## 10. 与现有仓库规则的兼容性

这份文档必须与 [AGENTS.md](/E:/koko/AGENTS.md) 保持一致，并在以下核心问题上直接承接：

- 反手搓轮子
- DDD 清晰边界
- 多壳共核
- adapter 只翻译，不决策
- Rust 优先、成熟生态优先
- 非必要不制造噪音
- 代码即文档

同时，它还应当把 `AGENTS.md` 中偏执行者脑内纪律的内容，翻译成全维护者都能执行的公开制度语言。

此外，外部经验章节在最终 `审查维护.md` 中不应长篇保留为论证材料，而应被压缩成可判题条款：

- 例如“主链路优先、外围能力隔离”“权威事实单点”“壳层只持本地体验态”等
- 这样可以保留巨人经验的精华，而不把宪法文档写成架构读书笔记

## 11. 验收标准

这份设计文档的验收标准不是“写得长”，而是未来生成的 [审查维护.md](/E:/koko/审查维护.md) 必须做到：

- 新维护者看完能立刻知道这项目怎么判问题
- 改动者能按它完成开发前/中/后的实际审查
- 它能明确否决手搓轮子和重复造轮子
- 它能明确指出边界漂移、冗余结构、屎山化趋势
- 它能长期复用，而不是只服务当前一轮清理
- 它能成为未来所有清理计划和重构计划的共同上位约束

## 12. 风险与克制点

这份宪法文档在设计时必须克制几个风险：

### 12.1 风险：写成空洞口号

应对：

- 每条原则后都要有实际判定法或清单

### 12.2 风险：写成巨长流程文书，没人真用

应对：

- 制度部分追求高密度
- 清单部分追求可执行
- 不把执行细节膨胀成战役计划

### 12.3 风险：写成“禁止一切”的保守文件

应对：

- 允许演进
- 允许重构
- 允许有限自研
- 但必须拿出证据与边界判断

### 12.4 风险：把“优雅”误解成炫技

应对：

- 明确优雅 = 简洁、高效、易读、低负担、低冗余
- 明确反对技巧化、谜语化、过度紧凑、过度抽象

## 13. 结论

`Koko` 后续需要的不只是“继续写得更快”，而是建立一个能长期压住架构漂移、手搓轮子冲动、冗余增长与屎山化趋势的制度性结构。

根目录 [审查维护.md](/E:/koko/审查维护.md) 的使命，就是让以后任何一次开发都不再只是问“能不能做”，而是先问：

- 这次改动是不是让核心更独立
- 边界是不是更清楚
- 复用是不是更多
- 私有轮子是不是更少
- 冗余是不是更少
- 证据是不是更硬

如果答案是否定的，那么无论功能是否完成，这次改动都不应被视为真正合格。
