## 0. 这份 spec 要修的不是一个小闪烁

当前真实 bug 是：

1. 时间线自动播放已经能保存 `currentTime`。
2. 滑走视频后，下一次滑回来也能从保存时间戳续播。
3. 但视频滑走后，卡片画面会偷偷退回开头封面 / 首帧 / poster。
4. 再滑回来时，浏览器先显示开头画面，再 seek 到保存时间戳。
5. 视觉结果就是“从开头突然跳到续播位置”，体验割裂。

这说明旧修复只修住了“播放时间真相”，没有修住“视觉帧真相”。

历史证据：

1. `e0eb4091 修复：消息流视频自动播重挂载续播`：把自动播播放时间戳收口到 `媒体运行时`，DOM 重挂载后从运行时恢复。
2. `58ac3c4c 优化：保护当前消息集合的视频续播位置`：修掉固定 `256` 条裁剪导致当前消息集合里的续播时间戳丢失。
3. `94aea189 / 12e69682 / 3c78631c`：曾经修过自动播切换闪烁、复用同一颗 video、首帧黑闪。

这些修复方向本身没有错。现在的问题是后续迭代又把时间线视频拆成两套视觉真相：

1. 自动播 owner 时显示 `<video>`。
2. 不是 owner 或滑走后显示 `<img poster>`、静态预览或占位首帧。

于是系统嘴上说“续播”，画面却先回开头。这不是优雅降载，而是视觉真相和播放真相分裂。

## 1. 最终裁决

一句话写死：

**视频本身就是预览；只要当前附件已经有可播放源和可恢复时间戳，时间线卡片就必须继续用同一条视频画面真相表达它，而不是退回 poster、预览图或首帧占位。**

展开成十条硬规则：

1. **视频卡片的首选视觉表达是 `<video>` 当前帧，不是预览图。**
2. **自动播放、暂停预览、滑走后的静止画面、滑回续播，必须共享同一条时间轴真相。**
3. **`currentTime` 是自动播体验态的唯一播放位置真相，owner 在 `媒体运行时`。**
4. **时间线壳层只能读取 `currentTime` 并把事实回抛，不能自己另存一套播放位置。**
5. **有同源播放源和已保存时间戳时，非 owner 视频也应 seek 到保存时间戳并暂停显示该帧。**
6. **poster / thumbnail / runtime preview 只允许作为无可播放源、无可恢复帧、加载前占位的兜底。**
7. **禁止在自动播和非自动播之间切换 `<video>` / `<img>` 两种主视觉节点来表达同一个视频。**
8. **查看器和全屏继续由唯一 Video.js v10 播放器壳承载；时间线不为每条消息实例化 Video.js。**
9. **WebTorrent 继续是视频正式字节与互帮互助主链；修 UI 不能削弱 aggressive swarm、补齐和做种。**
10. **为了修视觉 bug，不新增 canvas 抓帧、第二预览缓存、第二自动播 owner 或第二媒体状态机。**

这十条一起成立，才是本项目要回到的简洁模型：

**视频是一段时间轴画面；自动播只是让这段画面动起来；滑走只是暂停前台解码；回来只是继续同一条时间轴。**

## 2. 官方资料给出的边界

### 2.1 Video.js v10 的位置

Video.js v10 是播放器框架，不是群聊时间线每个视频卡片都要背上的重壳。

官方文档给出的关键边界：

1. `currentTime()` 是标准的播放位置读写 API。
2. `poster()` 是播放器 poster 源，不是续播帧真相。
3. 动态创建和移除完整播放器时要走 `dispose()`，避免 DOM 被移走后播放器还残留。
4. Video.js 设计围绕原生 `<video>` 能力工作；浏览器策略仍然是底层事实。

对本项目的裁决：

1. 查看器 / 全屏：继续走唯一 Video.js v10 播放器壳。
2. 时间线：只用轻量原生 `<video>` 表达视频帧，不给每条消息创建 Video.js player。
3. 时间线与查看器共享播放源真相和时间位置真相，但不共享同一个 DOM player。
4. 切换 source、恢复 currentTime、处理 play Promise 都走成熟媒体 API，不自造播放内核。

### 2.2 Chrome 和浏览器自动播放边界

Chrome 官方自动播放策略最关键的事实：

1. muted autoplay 总是允许。
2. 不要假设 `play()` 一定成功。
3. 应检查 `play()` 返回的 Promise。
4. `playsinline` 对移动端内联自动播是必要条件。

对本项目的裁决：

1. 时间线自动播仍然必须 `muted + playsinline + loop`。
2. 切入 owner 后可以显式调用 `video.play()`，但必须吞掉浏览器拒播，不把拒播误判成媒体主链失败。
3. 非 owner 状态不需要播放，只需要暂停在正确帧，所以不需要额外挑战 autoplay 策略。

### 2.3 MDN / web.dev 对 poster 的真实定义

MDN 对 `<video poster>` 的定义很朴素：poster 是视频下载时显示的图片；没有 poster 时，浏览器会等第一帧可用后显示第一帧。

web.dev 对性能的建议也很清楚：

1. 非自动播放视频可以用 poster 和 `preload="none"` / `preload="metadata"` 降成本。
2. GIF 替代式自动播放视频使用 `autoplay muted loop playsinline`。
3. 视频可 lazy-load，但加载后要调用 `load()`，由浏览器按 autoplay 属性尝试播放。

对本项目的裁决：

1. poster 是无可播放帧前的占位，不是已经看过视频后的真实预览。
2. 一旦某个附件已经有播放源和保存时间戳，继续显示 poster 就是状态倒退。
3. 时间线视频可以 `preload="metadata"`，但不能因为降载把画面退回开头。

### 2.4 WebTorrent 的边界

WebTorrent 的正式职责仍然是：

1. 整文件协作分发。
2. 边下边播。
3. 后台补齐。
4. 看过后继续帮助后来者。

本 spec 不改 WebTorrent 主链，不新增第二播放源，不减少 peer 互助强度。视觉修复只允许在壳层处理：

1. 读取已解析的 swarm 播放源。
2. 读取已保存的播放位置。
3. 把 `<video>` seek 到对应时间点并暂停或播放。

## 3. 术语收口

| 术语 | 定义 |
| --- | --- |
| 视频画面真相 | 当前附件应该在时间线展示的真实视频帧，由播放源和 `currentTime` 共同决定 |
| 播放位置真相 | `媒体运行时.inlineAutoplayPositionByAttachmentId` 持有的自动播时间戳 |
| 时间线轻量视频 | 房间消息流里用于展示视频帧和自动播的原生 `<video>` |
| 自动播 owner | 当前时间线唯一允许自动播放的附件 |
| 暂停预览态 | 有播放源但不是自动播 owner 时，`<video>` 暂停在有效时间点作为预览 |
| poster 兜底态 | 没有播放源或没有可恢复帧时，临时展示 poster / thumbnail / 占位图 |
| 查看器播放器壳 | 打开媒体查看器或全屏时使用的唯一 Video.js v10 播放器壳 |

最重要的边界：

1. **暂停预览态不是第二播放器。** 它只是同一颗轻量 `<video>` 暂停在当前帧。
2. **poster 兜底态不是视频的真实状态。** 它只是还没拿到视频帧时的占位。
3. **查看器播放器壳不是时间线播放器。** 时间线只做轻量帧表达和自动播，不承担完整控制条播放器职责。

## 4. 目标运行故事

### 4.1 用户第一次滑到视频

视频进入视口后：

1. 媒体主链解析 WebTorrent/swarm 播放源。
2. 时间线卡片拿到可播放源后渲染轻量 `<video>`。
3. 如果它成为自动播 owner，`video.play()` 被请求。
4. 播放过程中 `timeupdate / pause` 把 `currentTime` 上报给 `媒体运行时`。

此时不需要单独生成预览图。视频自己就是画面。

### 4.2 用户滑走

视频滑走或不再是 owner 时：

1. 前台自动播 owner 可以释放。
2. 当前 `<video>` 在暂停前必须 flush 最新 `currentTime`。
3. 如果该附件仍在当前消息集合中，播放位置继续由 `媒体运行时` 保存。
4. 再渲染这条视频时，只要源没变，就 seek 到保存时间戳并暂停在该帧。

禁止发生：

1. 切回 poster。
2. 切回首帧。
3. 切回 `<img>` 静态预览。
4. 因为不是 owner 就忘掉这段视频已经看到了哪里。

### 4.3 用户滑回来

视频再次接近视口后：

1. 时间线轻量 `<video>` 已经或会尽快停在保存帧附近。
2. 如果它重新成为自动播 owner，直接从该时间点继续播放。
3. 用户不应看到“开头封面 -> 跳到续播点”的割裂过程。

滑回来时可以出现的状态只有：

1. 正确帧静止后开始动。
2. 如果浏览器 seek 还没完成，短暂保持上一帧或轻量 guard。
3. 如果源不可用，才进入真实加载 / 无种子 / 删除态。

### 4.4 用户打开查看器或全屏

查看器 / 全屏：

1. 继续使用唯一 Video.js v10 播放器壳。
2. 使用同一条媒体播放源真相。
3. 可以从时间线保存的 `currentTime` 初始化播放位置。
4. 关闭查看器后不能误释放时间线视频的播放位置和协作分发帮助任务。

时间线和查看器可以各自拥有 DOM，但不能各自拥有一套业务真相。

## 5. 架构裁决

### 5.1 `媒体运行时` 是自动播时间戳 owner

`媒体运行时` 继续持有：

1. 当前自动播 owner 附件。
2. 当前自动播 playback。
3. `inlineAutoplayPositionByAttachmentId`。
4. 当前消息集合内附件的续播位置生命周期。

禁止：

1. 把 `currentTime` 存回 DOM 私有字段当真相。
2. 让 `房间消息窗` 自己裁决播放位置生命周期。
3. 用 preview cache 代替播放位置表。

### 5.2 `房间消息窗` 只做轻量投影

`房间消息窗` 只负责：

1. 根据 `mediaPlaybackByAttachmentId` 和 `inlineAutoplayPlaybackByAttachmentId` 选择播放源。
2. 根据 `inlineAutoplayPositionByAttachmentId` 恢复 `<video>.currentTime`。
3. 根据是否为 owner 决定 `autoplay / loop / play()`。
4. 根据真实 video 事件上报位置和播放信号。

禁止：

1. 自己新建第二套“预览源 owner”。
2. 为修闪烁新增 canvas 抓帧缓存。
3. 有可播放源和时间戳时切回 `<img>`。
4. 把 poster 当成续播帧。

### 5.3 查看器 / 全屏唯一使用 Video.js v10

Video.js v10 只在查看器 / 全屏播放器壳中出现。

原因：

1. 查看器需要完整播放器能力、控制条、全屏、播放状态表达。
2. 时间线是高密度万人群聊消息流，不能每条消息背一个完整播放器实例。
3. Video.js 官方也强调动态 DOM 场景要管理完整 player 生命周期；时间线反复虚拟滚动不适合到处实例化完整 player。

### 5.4 WebTorrent owner 不动

这次修复不碰：

1. WebTorrent client owner。
2. swarm source 解析。
3. 后台补齐。
4. 帮助任务恢复。
5. peer presence。
6. `0-24 小时` 服务器强帮助者和 `24 小时` 后 peer 接力规则。

如果为了修 UI 而降低 WebTorrent 并发、减少帮助任务、重新引入冷源播放旁路，视为失败。

## 6. 需要退场的设计漂移

### 6.1 预览图不再是视频主路径

本项目的目标不是“每个视频都要一张预览图”，而是：

**每个可播放视频都能用视频自身的帧自然预览。**

因此：

1. 新代码不得把 runtime preview / thumbnail / poster 设为视频卡片主视觉真相。
2. 已有 preview 能力只能作为过渡兜底或冷启动占位，不能凌驾于视频帧。
3. 不允许为了消除闪烁继续加更多预览图缓存。

### 6.2 `<img>` / `<video>` 互切不能再表达同一视频状态

同一个附件已经拿到同一条播放源时：

1. owner 与非 owner 之间只切 `autoplay / loop / paused / currentTime`。
2. 不切 DOM 节点类型。
3. 不切到 poster。
4. 不因为滑出视口就把画面降级成图片。

虚拟列表确实可能销毁 DOM。DOM 重建可以接受，但重建后的第一件事必须是：

1. 读取同源播放位置。
2. seek 到保存时间戳。
3. 暂停或继续播放。

### 6.3 不再补第二套“视觉缓存状态机”

禁止新增：

1. `lastFramePreviewByAttachmentId` 这类私有帧缓存。
2. canvas 抓帧来模拟暂停帧。
3. 每条消息一个 Video.js 实例。
4. 自动播 preview actor。
5. poster 和 currentTime 的双向同步协议。

这些都会把一个简单事实做复杂：视频元素本身已经能显示某个时间点的画面。

## 7. 实现边界

后续实现只允许围绕下面几个点动：

1. `frontend/房间消息窗.ts`
   - 让有播放源和恢复位置的视频继续渲染轻量 `<video>`。
   - owner 释放后暂停并保留帧，不退回 poster。
   - DOM 重挂载、`loadedmetadata`、`canplay`、owner 切入时都尝试恢复 `currentTime`。
   - 只有没有播放源或没有可恢复帧时才显示 poster。

2. `frontend/媒体运行时.ts`
   - 只在必要时补行为测试或收紧现有 position 生命周期。
   - 不新增第二表。
   - 不改变帮助任务与 WebTorrent 语义。

3. `frontend/聊天媒体编排.ts`
   - 只负责把运行时 position 快照继续传给壳层。
   - 不新增展示决策。

4. 测试文件
   - 优先补 `房间消息窗媒体查看器测试.spec.ts` 的 DOM 行为回归。
   - 必要时补 `媒体运行时测试.spec.ts` 的 owner 释放 / 消息集合保留边界。
   - 浏览器烟测用 `chrome-devtools-cli` 覆盖真实滑动、视频帧和续播。

禁止扩大到：

1. 后端。
2. WebTorrent tracker。
3. dev seeder。
4. 上传去重。
5. 数据库 schema。
6. 查看器非相关控制条样式。

## 8. TDD 验收清单

### 8.1 单元 / 组件测试

必须新增或修正这些测试：

1. **有 poster 的视频，owner 释放后仍渲染同源 `<video>`，不回切 `<img poster>`。**
2. **有 poster 的视频，DOM 重挂载后在 `loadedmetadata` 时恢复到保存 `currentTime`。**
3. **有 poster 的视频，滑回重新成为 owner 前，非 owner 轻量 `<video>` 已经暂停在保存帧。**
4. **无 poster 视频既有回归继续通过。**
5. **没有播放源时仍显示 poster / 占位，不偷走 original 冷源。**
6. **非 owner 的 `<video>` error 不上抛为当前播放会话失败，避免恢复风暴。**
7. **owner 切换只允许当前 owner 自动播放，其他视频只能暂停预览。**
8. **timeupdate 高频上报仍然节流，不能因为视觉修复增加万人群聊滚动压力。**

测试必须覆盖 `posterSrc` 非空场景。旧测试只覆盖 `posterSrc: null`，不能再冒充完整验收。

### 8.2 架构门禁

必须确认：

1. 时间线没有引入 Video.js 实例。
2. 没有新增 canvas 抓帧作为续播帧。
3. 没有新增第二套自动播 position store。
4. 没有重新引入 `originalSrc` 正式播放旁路。
5. 没有降低 WebTorrent eager 补齐、做种和帮助任务恢复强度。

### 8.3 浏览器烟测

真实浏览器烟测至少覆盖：

1. `https://localhost`
2. 房间 `1234b`
3. 使用真实 MP4 附件
4. 时间线滚动到视频自动播放
5. 播放数秒后滑走
6. 观察滑走后的卡片不回到开头 poster
7. 滑回后从保存时间点连续播放
8. 控制台无 `MaxListenersExceededWarning`
9. 网络仍走 WebTorrent 主链
10. 多视频消息流中只有一个自动播 owner

### 8.4 性能验收

修复后必须保持：

1. 时间线最多只有当前必要的轻量 `<video>` 节点，不因所有历史视频都保活而卡顿。
2. 非 owner 视频只暂停显示帧，不持续解码播放。
3. `timeupdate` 上报节流不放宽。
4. 滚动候选量测不新增同步重排热点。
5. WebTorrent 下载 / 做种 / 补齐不因 UI 降载被取消。

## 9. 失败态和兜底规则

### 9.1 什么情况下允许 poster

只在这些情况下允许 poster / thumbnail / 占位图：

1. 还没有 WebTorrent/swarm 可播放源。
2. 还没有保存过有效 `currentTime`。
3. 当前源和保存位置源不一致，不能安全 seek。
4. 浏览器尚未加载 metadata，且没有上一帧可保持。
5. 媒体已经进入 deleted / no seed / degraded 等明确失败态。

### 9.2 什么情况下禁止 poster

只要同时满足：

1. 附件是视频。
2. 当前有同源 swarm 播放源。
3. `媒体运行时` 保存了该附件的有效 `currentTime`。
4. 附件仍属于当前房间消息集合。

就禁止退回 poster。此时 poster 会制造假象：它把已经看到一半的视频伪装回开头。

### 9.3 seek 失败怎么办

如果浏览器因为 metadata 尚未稳定拒绝 seek：

1. 不把它升级成播放失败。
2. 在 `loadedmetadata / canplay / playing / owner 切入前` 再尝试一次。
3. 仍失败时保持加载或 guard，而不是回开头 poster。

这里的目标不是保证每个微秒都能立即 seek 成功，而是禁止视觉状态倒退到第一帧。

## 10. 防止过度设计

这次修复的审美底线：

1. 能用 `<video>.currentTime` 解决，就不用 canvas。
2. 能用现有 `媒体运行时` 解决，就不加新 owner。
3. 能用暂停帧表达预览，就不造预览图主链。
4. 能用现有 WebTorrent 播放源，就不新开冷源旁路。
5. 能用测试锁住行为，就不堆注释解释复杂状态机。

不接受的方案：

1. 给每条消息挂完整 Video.js。
2. 为每次滑走抓一张 canvas 静态图。
3. 做一个 `lastFramePosterCache` 当第二视觉真相。
4. 因为担心性能而默认滑走就删掉播放位置。
5. 因为修闪烁而禁用 aggressive WebTorrent 帮助链。

接受的方案：

1. 时间线继续用轻量 `<video>`。
2. 只有当前 owner 自动播放。
3. 非 owner 暂停在保存帧。
4. DOM 被虚拟列表重建时从运行时恢复。
5. 没有源或没有时间戳时才兜底 poster。

这就是“少做事”的修复：不再发明图片预览世界，只让视频按视频本来的方式工作。

## 11. 自审

按本项目约束自审如下：

1. **是否触碰后端业务真相？** 不触碰。该 bug 是前端时间线视觉投影问题。
2. **是否削弱 WebTorrent？** 不削弱。播放源、补齐、做种、帮助任务恢复都不变。
3. **是否新增轮子？** 不新增。只使用原生 `<video>`、现有 `媒体运行时`、查看器现有 Video.js v10。
4. **是否过度设计？** 不过度。明确禁止 canvas、第二 preview cache、每条消息 Video.js。
5. **是否覆盖真实根因？** 覆盖。根因是有 poster 场景下非 owner 回切 `<img>`，而旧测试只覆盖 `posterSrc: null`。
6. **是否适合万人群聊？** 适合。只有 owner 播放，非 owner 暂停帧，timeupdate 继续节流。
7. **是否守住浏览器应用化 owner 链？** 守住。浏览器事件只回抛事实，裁决仍在运行时 / 编排层。
8. **是否保持体验一致？** 保持。自动播、暂停预览、滑走、滑回、查看器都认同一条播放源和时间轴。

结论：

**这次修复不应该扩大成新播放器架构；它应该把已经分裂的视觉真相重新收口回视频自身。**

---

## 12. 最终硬裁决

以后在 `koko` 里，所有视频播放和自动播放都按这句话理解：

**视频卡片不是图片封面加播放器的混合物；视频卡片就是视频本身。自动播放只是让它动起来，滑走只是让它暂停，滑回来只是让它继续。只要有同源播放源和保存时间戳，画面就必须停在那个时间点附近，不能退回开头 poster。**

从这句话自然推出全部红线：

1. 禁止自动播与非自动播使用两套视觉节点表达同一视频。
2. 禁止有保存时间戳时退回 poster。
3. 禁止把预览图重新做成视频主路径。
4. 禁止给时间线每条视频实例化 Video.js。
5. 禁止为了视觉修复削弱 WebTorrent 互帮互助。
6. 禁止新增第二套播放位置真相。
7. 禁止用 canvas 抓帧掩盖 owner 分裂。
8. 禁止只测无 poster 场景就宣称完成。

后续 implementation plan 和代码修复只能在这条边界内工作。
