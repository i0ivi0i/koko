# Socket.IO 主通道与 DDD 解耦设计

## 目标

将 `Koko` 从“`HTTP + 手搓 raw WebSocket` 混合交互”演进为“`Socket.IO` 主通道 + 少量 HTTP 辅助通道”的群聊架构，同时保持领域层稳定，不让任何前端框架、后端框架、通信协议或客户端语言绑死业务。

最终希望长期成立：

- 前端从 `Dioxus` 换到别的框架，领域不崩。
- 服务端从 raw WS 换到 `socketioxide`，领域不崩。
- 未来接移动端或别的语言客户端，领域不崩。

## 当前判断

当前 `Koko` 已经不是“全 HTTP”：

- HTTP 负责 `bootstrap / join / history / members / governance`
- raw WebSocket 负责房间实时消息

但现状仍有三个问题：

- realtime 层仍然是手搓的 [`server/src/ws.rs`](/E:/koko/server/src/ws.rs)，核心是单进程内存广播
- 前后端实时协议是项目自定义 JSON over raw WS，没有复用成熟轮子
- transport 形态已经开始影响交互组织方式，继续演化容易把协议细节和领域语义缠在一起

这不符合“不要重复造轮子”和“领域稳定高于技术细节”的长期原则。

## 设计原则

### 1. 领域层永远不认识具体 transport

`core` 只表达：

- 房间
- 成员资格
- 消息
- 治理动作
- 领域命令
- 领域事件
- 领域错误

`core` 不应该认识：

- `HTTP`
- `Socket.IO`
- `axum`
- `socketioxide`
- `Dioxus`
- 浏览器 API

### 2. transport 只是 adapter，不是业务真相

`HTTP`、raw `WebSocket`、`Socket.IO`、未来移动端 SDK，都只是调用领域用例的入口与出口。

系统真正稳定的部分应该是：

- 命令语义
- 事件语义
- 权限语义
- 成员关系语义
- 错误语义

### 3. 主交互统一，系统接口例外

聊天主流程应尽量收敛到一条主交互通道，减少“同一业务散落在多种 transport”的维护成本。

但不是一切都必须进入主通道：

- 健康检查
- 管理型低频接口
- 部署运维接口

这些保留为 HTTP 并不违背 DDD。

### 4. 不为“优雅”牺牲演进安全

目标架构可以是 `Socket.IO` 主通道，但迁移动作必须分阶段，避免一次性重写 transport、状态同步、客户端接入和领域边界。

## 目标架构

### 领域层

`core` 提供稳定的业务能力：

- `JoinRoom`
- `LoadRecentMessages`
- `LoadOlderMessages`
- `LoadMembers`
- `SendMessage`
- `PromoteAdmin`
- `MuteMember`
- `RemoveMember`

以及稳定的业务结果：

- `RoomSnapshot`
- `MessageCreated`
- `MemberChanged`
- `GovernanceResult`
- 领域错误

这里的“命令/结果”是逻辑概念，不要求当前立刻重命名代码文件或引入新的 crate；重点是先把边界想清楚。

### 服务端

`server` 承担应用层与 adapter 职责：

- 接收 Socket.IO 事件或 HTTP 请求
- 认证会话
- 组装命令参数
- 调用 `core`
- 把结果映射为响应或事件

当 `socketioxide` 接入后，`server` 中关于房间交互的主入口将逐步从 [`server/src/http.rs`](/E:/koko/server/src/http.rs) 和 [`server/src/ws.rs`](/E:/koko/server/src/ws.rs) 收敛到统一的 Socket.IO handler 组织方式，但领域调用保持不变。

### 前端

`web` 只负责：

- 收集用户意图
- 发送命令
- 接收事件
- 更新界面状态

`web` 不负责：

- 权限判断
- 成员资格真相
- 房间规则
- 协议主导的业务决策

前端可以从当前 `Dioxus + gloo-net raw WS` 演进为 `Dioxus + Socket.IO client adapter`，未来也可以换成别的框架，只要保持同一组命令/事件语义即可。

## transport 策略

### Socket.IO 主通道

以下能力应逐步进入 Socket.IO 主通道：

- `join_room`
- `load_recent_messages`
- `load_older_messages`
- `load_members`
- `send_message`
- `promote_admin`
- `mute_member`
- `remove_member`
- `message_created`
- `member_changed`
- `room_snapshot`
- `governance_result`

原因：

- 这些能力天然依赖会话上下文
- 这些能力需要实时反馈或状态连续性
- 使用成熟轮子可复用 rooms、ack、reconnect、adapter 等现成能力

### HTTP 辅助通道

以下能力可继续保留在 HTTP：

- 会话 bootstrap
- 健康检查
- 低频管理接口
- 部署与诊断接口

保留理由：

- 这些能力并不需要强会话流式上下文
- 强行迁入 Socket.IO 不会显著提升业务价值
- 它们更适合简单清晰的 request/response

## canonical 语义

无论 transport 如何变化，系统都应围绕同一组稳定语义组织：

- Command: `JoinRoom`
- Command: `LoadRecentMessages`
- Command: `LoadOlderMessages`
- Command: `LoadMembers`
- Command: `SendMessage`
- Command: `PromoteAdmin`
- Command: `MuteMember`
- Command: `RemoveMember`
- Event: `RoomSnapshot`
- Event: `MessageCreated`
- Event: `MemberChanged`
- Event: `GovernanceResult`
- Event: `Error`

这不是要求现在立刻引入完整 CQRS 框架，而是要求从今天开始，HTTP 路由名、Socket.IO 事件名、前端状态更新逻辑都尽量围绕同一组业务语义，而不是各自发明一套名字。

## 迁移策略

### 阶段 A：替换手搓 realtime 轮子

目标：

- 用 `socketioxide` 替代当前 hand-rolled raw WS 房间广播
- 前端接入 Socket.IO client adapter
- 保持 `core` 领域规则不动

约束：

- 不把协议语义直接塞进 `core`
- 不因为替换 transport 就改坏权限规则、成员规则、治理规则
- 尽量不新增无意义文件与抽象

阶段 A 完成后，系统将达到：

- 主 realtime 交互不再依赖手搓广播
- 房间实时能力复用成熟轮子
- 领域与 transport 的分工更清晰

### 阶段 B：将主业务交互收敛进 Socket.IO

目标：

- 把聊天主流程从“HTTP + realtime 补充”收敛为“Socket.IO 主通道”
- 保留少量真正适合 HTTP 的系统接口

收敛方式：

- 先迁最强实时语义的交互
- 再迁需要持续会话上下文的查询
- 最后视收益决定治理回执与更多房间状态同步是否完全事件化

阶段 B 的重点不是“消灭 HTTP”，而是减少主业务交互分散在多条 transport 上。

## 兼容性原则

### 前端兼容

- 前端框架可替换
- 客户端语言可替换
- 只要 adapter 能表达同一组命令/事件语义，就可以接入

### 后端兼容

- 后端框架可替换
- realtime 实现可替换
- 只要应用层仍调用相同领域能力，就不会破坏业务真相

### 协议兼容

- transport 升级不应要求领域层一起改名或重写
- 事件字段与错误语义需要版本意识
- 对外契约的演进优先追加，不轻易破坏性修改

## 非目标

这份设计当前不追求：

- 一次性删除全部 HTTP 接口
- 一次性引入完整事件溯源体系
- 一次性重写所有前端状态管理
- 为了理论完美而大规模拆 crate 或新增大量 `.rs` 文件

## 成功标准

当以下条件成立时，可认为这次设计落地成功：

- `socketioxide` 取代当前手搓 realtime 主通道
- 聊天主流程优先走 Socket.IO
- `core` 不依赖具体 transport
- 前端不承担业务真相与权限判断
- 未来更换前端框架、客户端语言、服务端 realtime 实现时，主要修改 adapter，而不是重写领域逻辑

## 总结

这次演进的本质不是“把 raw WS 换成另一个库”，而是：

- 停止手搓 realtime 轮子
- 让成熟轮子接管 transport 能力
- 让领域重新站回系统中心

真正的目标不是某个框架胜出，而是无论框架怎么换，`Koko` 的业务都不崩。
