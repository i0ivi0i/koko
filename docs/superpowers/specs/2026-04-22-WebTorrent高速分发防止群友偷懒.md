## 0. 为什么要重写这份设计

旧文档已经把几个重要方向压住了：

1. 视频不能再被拆成多份正式真相；
2. 不能靠压糊画质换秒开；
3. `WebTorrent` 不能只是“也许能顺便加速一下”的旁路；
4. 后端不该继续长期养一堆派生媒体垃圾。

但旧文档还有两个边界没有彻底写死，所以后面实现仍然容易漂：

1. 它没有把“前端正式媒体字节是否允许绕开 `WebTorrent`”写成绝对禁令；
2. 它没有把“`24 小时` 后服务器到底退什么、不退什么、失败时怎么说真话”彻底收死。

这就会导致执行时出现几种危险的自作聪明：

1. 为了首屏更稳，偷偷把查看器或时间线切回 `HLS` / 原文件直链；
2. 为了让 swarm 看起来存在，前端其实继续依赖第二条服务器播放链；
3. 为了不让用户看到“当前没有在线种子”，用模糊加载态或偷偷兜底来掩盖真相；
4. 为了让服务器退场时看起来平滑，又重新让磁盘上长出重复冷备和派生垃圾。

所以这份新设计的目标不是“把旧设计再润色一遍”，而是把真正决定实现方向的边界裁死，防止 implementation plan 和后续编码时再次漂移。

## 1. 这次真正要守住的产品真相

先把一句话写死：

**`koko` 的图片和视频，前端正式媒体内容字节统一只允许走 `WebTorrent` 分发平面；服务器只允许作为 swarm 成员参与，不允许再为前端提供第二条正式播放主链。**

这句话展开后，就是下面五个硬裁决：

1. 前端正式媒体字节主链唯一，不能再有 `HLS`、`original_url` 直链、`poster/still` 正式查看链、第二查看器媒体链。
2. `HTTPS/WSS` 仍然允许存在，但它们只属于控制面：鉴权、房间消息、metainfo/bootstrap、tracker signaling、presence、删除通知，不属于正式媒体播放字节主链。
3. `0-24 小时` 内，后端不是“旁路 CDN”，而是 swarm 内正式强 seed，同时承担 `WebSeed + WebRTC seeder` 两个角色。
4. `24 小时` 到点后，后端退出该内容的媒体字节供给；之后只剩在线群友继续互帮互助。
5. `24 小时` 后如果没有在线完整 peer，内容允许暂时不可播；前端必须把这个真相说出来，不能伪装成一般加载错误，更不能偷偷绕回服务器。

这五条不是建议，而是硬禁令。一起成立，才是你要的那种系统：

- 服务器前期足够强，群友没理由偷懒；
- 前端没有第二条路可以偷跑；
- `24 小时` 后磁盘压力被切掉；
- 真正的长期分发平面只剩 `WebTorrent`；
- 失败时系统也不撒谎。

## 2. 官方实践到底支持什么，不支持什么

这部分必须写透，因为很多“我以为官方要求这样”的误会，最后都会演变成架构漂移。

### 2.1 官方支持服务器参与 swarm，但不要求永久保留媒体字节

官方资料说明的是：

1. BitTorrent/WebTorrent 的正常世界里，本来就允许存在 `.torrent/metainfo`、tracker、普通 web server 这些角色；
2. `WebSeed` 是协议内正式能力，服务器可以作为持续不拒绝的 seed；
3. WebTorrent 浏览器端正常支持 `wss tracker`、`https torrent metadata`、`web seed` 组合；
4. 浏览器下载完成后会自动做种，但前提仍然是页面还活着、会话没被停掉、手里确实有完整字节。

官方没有要求下面这件事：

**文件发布超过 `24 小时` 后，服务器仍必须继续保留媒体字节。**

也就是说：

- 服务器在 `24 小时` 后退出某个内容的字节供给，不违反协议；
- 但退出后的代价是可用性不再由服务器保证，而是进入纯 peer best-effort 模式。

这不是 bug，也不是实现缺陷，而是产品主动选择的运行真相。

### 2.2 禁止把 `WebSeed` 理解成“第二主链豁免证”

很多实现会在这里偷换概念：

1. 口头上说“我们还是 `WebTorrent` 主链”；
2. 实际上前端播放器却继续直接拉服务器字节；
3. `WebTorrent` 只拿来做一个顺带存在的后台会话；
4. 最后群友几乎没有真实上传压力，swarm 永远热不起来。

这条路在本项目里必须直接禁止。

因为 `WebSeed` 的正确位置是：

**后端作为 swarm 成员参与分发，而不是给前端开一条绕开 swarm 的第二播放主链。**

也就是说：

- 允许服务器在 swarm 里很强；
- 不允许前端正式播放绕开 swarm。

### 2.3 禁止把“纯 peer 暂时不可用”误当成协议违规

只要你选择 `24 小时` 后服务器退出字节供给，就必须接受下面这个现实：

1. 若有在线完整 peer，内容继续可用；
2. 若没有在线完整 peer，内容暂时不可用；
3. 直到某个完整群友再次上线，内容才重新恢复可用。

这不是什么实现瑕疵，而是纯 peer 生存的真实代价。

系统不能为了“看起来总是可播”重新绕回第二服务器主链，因为那样等于把前面的所有裁决都做回影子。

## 3. 目标与非目标

### 3.1 目标

这份设计要同时达到下面几件事：

1. 把图片和视频的前端正式媒体字节统一收口到同一条 `WebTorrent` 主链；
2. 让时间线、查看器、全屏、自动播放围绕同一份正式 payload 工作；
3. 在 `0-24 小时` 内让后端成为足够强的 swarm 成员，快速把群聊用户推入互帮互助状态；
4. 在 `24 小时` 后去掉服务器对该内容的媒体字节职责，真正转为在线群友协作分发；
5. 在没有在线完整 peer 时，说真话、不伪装、不偷偷兜底；
6. 全程坚持“高清、高码率、原画质优先”，不靠压糊换体验。

### 3.2 非目标

这份设计明确不追求下面这些事情：

1. 不承诺 `24 小时` 后内容仍然像传统 CDN 一样始终可用；
2. 不为了减少用户等待，就重启第二播放链或第二正式媒体资产；
3. 不把“用户主观上先看到一点内容”误实现成“先给一张服务器封面图混过去”；
4. 不为不同设备各写一套媒体真相；
5. 不为了表面丝滑，偷做低清重编码或隐性转码降质。

### 3.3 迁移与切换范围

这份设计在实施范围上也必须克制，不允许一边写“统一主链”，一边把计划偷偷膨胀成无边界的大迁移工程。

本次 spec 的默认切换范围写死如下：

1. **前向生效优先。** 新上传并 `complete` 的图片/视频附件，必须进入这条新主链。
2. **旧媒体默认兼容保留。** 已经落地的 legacy `HLS/poster/thumbnail/still` 资产，在本次设计里视为历史兼容债务，不要求一口气全量回填或全量重种。
3. **不把全量历史迁移作为当前主线前置条件。** 是否后续补做 backfill、批量重种、历史垃圾清理，可以在独立 plan/独立 spec 中处理，不能阻塞这次“新主链真相收口”。
4. **允许按附件代际分流，但不允许新附件继续落回旧真相。** 换句话说，`legacy` 可以暂时存在，但它只能是旧债务，不是新标准。
5. **回滚边界也按代际划分。** 若上线初期需要局部回滚，只允许在“新代际附件”边界内控制，不允许因为旧附件兼容问题把整套新主链裁决打回去。

## 4. 为什么这和旧的 `24 小时` 退场规则并不冲突

之前产生“是不是冲突”的根因，是“退场”这个词太容易被理解错。

这次必须把它拆开：

### 4.1 禁止把 `24 小时` 退场理解成“什么都不分就一起退”

退的是服务器对该内容的**媒体字节供给职责**，以及因此必须长期占磁盘、占维护成本的东西：

1. 冗余冷备；
2. 派生流媒体资产；
3. 重复副本；
4. 只为了服务器直播放而存在的第二套资产与协议面。

### 4.2 禁止把控制面真相误删成“服务器全失忆”

在退场之前保留、退场之后仍可存在的，不是第二字节主链，而是控制面和协议真相：

1. 附件元信息；
2. `infohash / magnet / tracker` 信息；
3. 鉴权与房间关系；
4. “这东西还在不在”“有没有 peer”这种状态真相；
5. 删除语义。

### 4.3 真正要禁止的不是“后端太强”，而是“前端还有第二条正式播放链”

只要前端正式媒体字节主链仍然唯一是 `WebTorrent`，那后端在前 `24 小时` 强不强都不违背主链裁决。

真正会导致系统退化的，是下面这类偷换：

1. 前端前 `24 小时` 继续正式拉 `HLS` / 原文件；
2. swarm 只是顺带存在；
3. 用户滑走就停补齐；
4. 看完也不继续做种。

这才叫“群友偷懒”，也才是真正该禁的东西。

## 5. 总体架构裁决

### 5.1 禁止每个附件长出第二正式 payload 真相

对每个图片或视频附件，系统只允许存在一份正式 payload 真相。

它必须同时服务于：

1. 时间线媒体显示；
2. 时间线自动播放；
3. 查看器播放 / 查看；
4. 全屏切换；
5. 本地持续补齐；
6. 后续做种。

禁止再为新媒体链路长期保留：

1. 第二正式视频版本；
2. 第二正式图片版本；
3. 只给查看器用的独立播放源；
4. 只给时间线用的独立媒体真相源；
5. 长期 poster / still / thumbnail 正式资产。

### 5.2 禁止前端正式媒体字节绕开 `WebTorrent`

前端正式媒体内容字节只允许从同一个 `WebTorrent` 会话进入 UI。

这句话对图片和视频都成立。

可以存在的差异只有：

1. 不同媒体类型的展示组件；
2. 不同浏览器能力的适配；
3. 不同阶段的 piece 选择策略；
4. 本地缓存与解码策略不同。

不允许存在的差异是：

1. 某个壳偷偷走服务器直链；
2. 某个场景偷偷回到 `HLS`；
3. 某个设备偷偷启用第二媒体链；
4. 时间线和查看器对同一个附件使用两份不同正式真相。

### 5.3 禁止把后端强 seed 做成假 swarm

在 `0-24 小时` 内，后端对每个新媒体附件都同时承担两个角色：

1. `WebSeed`
2. `WebRTC seeder`

原因不是“多做点显得高级”，而是这两者正好分别解决两类冷启动问题：

1. `WebSeed` 负责把服务器稳定吞吐直接注入 swarm；
2. `WebRTC seeder` 负责让浏览器端 peer 更直接地感知一个足够强的正式群友。

这样做的目的很明确：

**不是让服务器替群友干完，而是用服务器把最冷的阶段推过去，逼 swarm 尽快烧热。**

这里还要补死一个执行边界，避免后面 plan 写成空话：

1. `WebSeed` 是现有后端字节服务作为 swarm 正式 seed 的 adapter 角色，不是前端第二播放主链；
2. `WebRTC seeder` 必须是一个真正能和浏览器 web peer 建立 `WebRTC DataChannel` 的后端侧 seeding 进程；
3. 默认落地形态是独立 seeder adapter / sidecar，而不是把这套能力揉进领域内核；
4. 默认优先采用官方已证明能给浏览器做种的 `WebRTC-capable` seeder 路径，例如 WebTorrent 官方 FAQ 明确列出的 `webtorrent-hybrid` 这类实现；除非后续已经验证存在同等能力、同等成熟度的 Rust 方案，否则禁止为这件事手搓私有 WebRTC torrent 协议栈；
5. 无论底层最终由哪个具体实现承接，对 `koko` 业务来说，稳定真相只有一条：后端在 `0-24 小时` 内提供一个真正可被浏览器 WebTorrent peer 连接的强 seed 能力，而不是伪装成“名字叫 WebRTC seeder、其实前端还是在拉第二直链”。

### 5.4 禁止 `WebRTC seeder` 没有 owner 边界

为了让后续 plan 能真正拆活，`WebRTC seeder` 的运行边界也必须写死。

1. `WebRTC seeder` 默认是**独立受管 sidecar 进程**，不是前端页面，不是手工运行脚本，也不是揉进 Rust 业务内核里的临时线程。
2. Rust 后端是权威 owner，负责：
   - 哪个附件该开始做种；
   - 哪个附件到点该退场；
   - 删除后哪个附件必须立刻停种；
   - 进程重启后需要恢复哪些 active seeding intent。
3. Seeder sidecar 只负责协议与传输执行：
   - 加载 `torrent metadata / magnet`
   - 接入 tracker
   - 建立 `WebRTC` peer 连接
   - 承担 `WebSeed` / `WebRTC seeding` 字节发送
4. Rust 后端与 seeder sidecar 之间必须通过稳定的本地 adapter 契约通信，例如本机回环 `HTTP` / `IPC` 命令面；禁止把“启动/停止做种”的真相散落在脚本、人工步骤或浏览器端。
5. Sidecar 崩溃、重启、升级，不得改变业务真相：后端必须能基于持久化 seeding intent 重新对账并恢复该做种的附件。
6. 这意味着后续 implementation plan 必须把 seeder 写成“可替换基础设施 adapter”，而不是业务核心的一部分；未来若 Rust 生态出现等价成熟实现，可以替换 adapter，但不能改变本 spec 的业务边界。

## 6. 运行时数据流设计

### 6.1 上传完成后的正式真相生成

上传完成后，系统必须生成并持久化该附件后续协作分发所需的最小正式真相：

1. 唯一正式 payload 标识；
2. `infohash / magnet / torrent metadata`；
3. piece 相关元信息；
4. `0-24 小时` 强 seed 生命周期信息；
5. 删除后终态标识。

`24 小时` 倒计时的权威起点必须写死为：

**后端 `complete` 成功落权威事实的 `complete_at` 时间戳。**

由此推出下面几个执行边界：

1. 倒计时不从“首次发消息”“首次被观看”“首次被预热”开始算；
2. 倒计时由后端权威时钟写入并持久化，进程重启不重置；
3. `24 小时` 到点判断必须由后端基于持久化 `complete_at` 计算，前端只消费结果，不自作主张本地推算真相；
4. 测试与烟测必须支持可注入时钟或时间推进开关，以便稳定验证到点前后行为；
5. 未 `complete` 的临时上传、被放弃上传、已删除附件都不进入这条计时语义。

这里不允许重新长出：

1. “为了先显示一下”而创建的长期 still 资产；
2. “为了播放更稳”而创建的第二正式播放版本；
3. “为了兼容某端”而写死在 contract 里的壳专属媒体链字段。

### 6.2 禁止时间线媒体只拿一点就走

用户滑到媒体后，客户端统一进入三段式：

1. 先拿到足够快显出第一眼内容的关键片段；
2. 再把完整 payload 补齐到本地；
3. 补齐完成后继续进入做种态。

这里要强调两个禁令：

1. “先看到一点内容”不等于允许第二真相源；
2. “补齐完成后进入做种”不是可选优化，而是主链闭环的一部分。

### 6.3 禁止滑走后默认停止补齐

滑走后可以停止的只有重度展示负载，比如：

1. 自动播放解码；
2. 当前活跃渲染 owner；
3. UI 上的高优先级展示占用。

滑走后**不能停止**的，是这次浏览已经触发的后台补齐。

因为只要默认“滑出就停”，swarm 的真实热度就永远起不来，系统只会反复停在“每个人都只拉一点点，后面的人还是慢”的半死不活状态。

这里顺带补一个本地缓存边界，避免后面把“服务器退场”误写成“本地也必须失忆”：

1. `24 小时` 退场只影响服务器字节供给，不会让已存在的本地完整 payload、本地已下载字节或本地派生预览缓存自动失效；
2. 只要附件未被删除，本地完整 payload 仍然可以继续用于本地展示与继续做种；
3. 删除发生后，本地完整 payload、本地部分字节缓存、本地派生预览缓存都必须进入 purge 流程，并停止继续对外做种；
4. 删除后的当前活跃媒体壳必须尽快切到 `MEDIA_DELETED`，不能继续把本地缓存当成“虽然被删了但我还能偷偷看”的例外真相。

### 6.4 禁止查看器和全屏长成第二媒体链

查看器与全屏不能是第二媒体链。

它们只是：

1. 同一份 payload 的另一种展示壳；
2. 同一份 `WebTorrent` 会话的另一种视觉 owner；
3. 同一条媒体时间真相的连续表达。

禁止出现：

1. 时间线是 torrent，进查看器改走直链；
2. 时间线看的是 payload，进查看器改看 still/poster；
3. 全屏重新创建第二媒体会话导致黑闪、白闪、节点重建感。

### 6.5 禁止图片首屏体验偷偷回退服务器缩略图

这次设计明确覆盖图片，不只覆盖视频。

统一原则是：

1. 正式查看字节统一来自 `WebTorrent` payload；
2. 时间线首屏允许使用本地早期可解码字节或本地派生缓存；
3. 但不能重新回到服务器 thumbnail 主链；
4. 查看器仍必须围绕同一正式 payload。

也就是说，图片和视频的差别只在解码与显示，不在正式分发真相。

为了防止后面执行时重新把“首屏体验”偷换成服务器缩略图，这里再把图片冷启动规则写死：

1. 如果图片格式支持渐进式或分段可解码显示，那么首屏应优先使用同一 payload 的早期可解码字节；
2. 如果图片格式本身不支持渐进式显示，且当前设备上没有本地预览缓存，那么首屏允许出现**稳定的应用级占位态**，例如按附件已知宽高比保位的骨架屏/占位框；
3. 这个占位态是 UI 态，不是第二媒体资产，禁止把它实现成服务器生成的 thumbnail/still；
4. 一旦同一 payload 达到首次完整解码门槛，就立即切入正式图像显示；
5. 图片冷启动允许“先稳定占位、后真实显示”，但不允许“为了避免占位而偷偷回服务器拿缩略图”。

---

## 7. 防止群友“偷懒”的机制设计

你明确不想要那种“口头说 P2P，实际上所有人都继续靠服务器”的假 swarm。

所以这里必须把“偷懒”拆成系统层面的坏行为，而不是道德判断。

### 7.1 什么叫真正的“群友偷懒”

下面这些行为都属于系统在纵容群友偷懒：

1. 前端还能绕开 swarm 直接拿服务器字节；
2. 用户滑到媒体后只拿一小点预览，不继续补齐；
3. 用户滑走后后台补齐被停掉；
4. 用户补齐完成后不继续做种；
5. 查看器或全屏偷偷切到另一条服务器链；
6. 系统为了不显示真相而偷偷开服务器兜底。

### 7.2 防偷懒的正解

真正有效而且必须执行的做法只有三件事：

1. 前端正式媒体字节主链唯一；
2. 滑到即补齐，滑走不停；
3. 补齐完成后默认进入做种。

后端前 `24 小时` 足够强，不是在帮群友偷懒，而是在缩短“冷启动最冷的那一段”。  
只要前端没有第二主链，服务器越强，swarm 热得越快；真正让 swarm 永远冷的，反而是第二播放链。

### 7.3 不能把激进补齐做成激进真播

激进补齐和激进解码不是一回事。

你要的是：

1. 分发尽量激进；
2. 自动播放与解码受统一 owner 调度；
3. 页面不被多个高负载媒体同时拖垮。

所以这里必须明确：

- 补齐可以 aggressive；
- 真播不能失控。

## 8. `24 小时` 退场后的系统真相

### 8.1 禁止 `24 小时` 到点后服务器继续偷做第二字节主链

`24 小时` 到点后，后端对该内容停止：

1. `WebSeed` 字节供给；
2. `WebRTC seeder` 字节供给；
3. 任何直接或间接重新变成前端第二正式媒体链的兜底路径。

这里的“到点”只认后端权威 `complete_at + 24h`，不认前端本地时间，不认“这条消息什么时候第一次有人看到”，也不认浏览器会话自己的推测。

### 8.2 到点后保留的东西

为了让系统还能说真话、还能知道自己在等什么，到点后仍可保留：

1. 附件存在性真相；
2. 协议与 metainfo 真相；
3. 鉴权、房间关系、删除语义；
4. “当前是否探测到在线完整 peer”的状态。

为了防止后面实现时每个人对“在线”“完整”“可用来源”理解不一样，这里把最小术语表先收口：

| 术语 | 定义 |
| --- | --- |
| `complete peer` | 已持有目标 payload 全量 piece / 全量字节的 swarm 参与者 |
| `online complete peer` | 当前会话重试窗口内可被发现且至少有一条可用传输路径的 `complete peer` |
| `backend strong seed` | `0-24 小时` 内由服务器提供的可用来源，包括 `WebSeed` 与 `WebRTC seeder sidecar` |
| `available source` | 本地完整 payload、本地已足够显示/播放的权威字节、`backend strong seed`（仅退场前）、或 `online complete peer` |

这里的关键是：

1. “完整”不是“也许有些字节”，而是确实持有全量 payload；
2. “在线”不是数据库里记了一条 presence，而是当前重试窗口内对本次媒体访问真的可用；
3. 后端 sidecar 在 `0-24 小时` 内当然算 `available source`，但它只能以 swarm 成员身份被计入，不能偷换成第二前端直链。

### 8.3 禁止前端对“没种子”说假话

用户点击媒体后，前端流程固定为：

1. 先显示“正在尝试连接群友”；
2. 在合理超时窗口内持续尝试 swarm 恢复；
3. 若仍无在线完整 peer，明确显示“当前没有在线种子，等待群友上线”。

这里的“合理超时窗口”不能再留成模糊词，默认参数先写死：

1. 单次 `MEDIA_CONNECTING_TO_PEERS` 尝试窗口默认 `8 秒`；
2. 在这 `8 秒` 内，tracker / presence / swarm 可用性探测默认按 `2 秒` 周期重试；
3. `8 秒` 内若出现 `available source`，立即回到 `MEDIA_READY`；
4. `8 秒` 到点仍无 `available source`，转入 `MEDIA_NO_ONLINE_SEED`；
5. 进入 `MEDIA_NO_ONLINE_SEED` 后，若媒体壳仍处于活跃查看状态，默认每 `15 秒` 发起一次新的连接尝试；用户手动点击重试则可立即重新进入 `MEDIA_CONNECTING_TO_PEERS`。

这些数值后续可以实现成配置项，但默认语义与默认量级必须保持一致，不能在 plan 阶段再次放空。

禁止下面这些糊弄：

1. 只显示“加载失败”；
2. 无限转圈不解释；
3. 把“没有在线种子”混成一般网络错误；
4. 为了遮羞偷偷回退服务器直链。

### 8.4 禁止把“内容已删除”混成“暂时没种子”

删除和“暂无在线种子”不是一回事，必须严格分开：

1. “暂无在线种子”是可恢复缺席态；
2. “内容已删除”是不可恢复终态。

删除后系统必须明确返回终态，而不是让前端继续假装在等 peer。

### 8.5 禁止前后端各自发明失败态真相

为了防止前后端各自理解“正在等 peer / 没 peer / 已删除”，这里必须先定义稳定 contract code，再派生 UI 文案。

建议的权威状态与最小转移规则如下：

| Contract code | 含义 | 默认 UI 文案 | 允许进入条件 | 允许退出条件 |
| --- | --- | --- | --- | --- |
| `MEDIA_READY` | 当前已具备正式 payload 可用字节来源，能够继续正常显示/播放 | 不额外提示 | 本地已完整、已连上可用 peer、或仍在 `0-24 小时` 且后端强 seed 可用 | 若访问时需要重新找 peer 且当前暂无可用字节来源，可转入 `MEDIA_CONNECTING_TO_PEERS` |
| `MEDIA_CONNECTING_TO_PEERS` | 附件仍存在，系统正在合理重试窗口内寻找可用完整 peer | `正在尝试连接群友` | `24 小时` 后访问时缺少当前可用来源；或从 `MEDIA_NO_ONLINE_SEED` 被用户/系统再次触发重试 | 找到可用来源后回到 `MEDIA_READY`；超过重试窗口转入 `MEDIA_NO_ONLINE_SEED`；若附件被删则转入 `MEDIA_DELETED` |
| `MEDIA_NO_ONLINE_SEED` | 附件仍存在，但当前重试窗口结束后仍无在线完整 peer | `当前没有在线种子，等待群友上线` | `MEDIA_CONNECTING_TO_PEERS` 在重试预算内未找到完整 peer | 用户手动重试、被动收到 peer 恢复信号、或系统周期性重新探测时，可重新转回 `MEDIA_CONNECTING_TO_PEERS`；若附件被删则转入 `MEDIA_DELETED` |
| `MEDIA_DELETED` | 附件已被删除，不再允许恢复 | `内容已删除` | 删除权威事实已成立 | 不允许退出 |

这里再补一个硬约束：

1. 前端文案只能从这些稳定 contract code 派生，不能自己再发明另一套状态机；
2. 后端返回的也必须是稳定状态真相，而不是某次请求里临时拼一句模糊错误文案；
3. “没有在线种子”和“内容已删除”必须是不同 code，不允许只靠文案区分。
4. 本地仍握有完整 payload 的客户端，在附件未删除前，可以直接判定 `MEDIA_READY`；删除权威事实一旦成立，必须无条件切到 `MEDIA_DELETED`，不能因为本地有缓存就继续装作 `MEDIA_READY`。

---

## 9. 质量与高清裁决

这次设计必须再把画质边界写死一次，因为“为了更顺先压一点”是最容易复活的漂移。

### 9.1 默认禁止

默认禁止：

1. 降分辨率；
2. 降码率；
3. 降帧率；
4. 生成更糊的第二正式视频版本；
5. 用“更好播”为名做隐性降质重编码。

### 9.2 允许的优化

允许的只有不损画质的路径，例如：

1. 直通；
2. `remux`；
3. `faststart`；
4. 不改变清晰度的容器级优化；
5. piece 选择与缓存策略优化；
6. owner 调度与资源预算优化。

### 9.3 禁止靠第二链和降质伪造秒开

秒开要靠的是：

1. 单一主链；
2. 早期关键片段优先；
3. 后端前 `24 小时` 的双强 seed；
4. 滑到即补齐、滑走不停；
5. 补齐完成后持续做种；
6. 统一 owner 调度。

秒开不能靠：

1. 第二播放链；
2. 服务器封面图伪装；
3. 降质版本；
4. 模糊失败态。

---

## 10. 实现时最容易漂移的地方

### 10.1 漂移一：把 `WebSeed` 偷换成服务器第二正式播放链

这是最危险也最隐蔽的漂移。

外表上它看起来像“我们仍在使用 `WebTorrent`”，但实际结果是：

1. 前端正式播放继续依赖服务器；
2. 群友上传参与度很低；
3. swarm 只是背景装饰。

这条路必须直接判死。

### 10.2 漂移二：为了首屏好看，重启 poster/still 正式资产

这会直接把系统做回“预览一套、播放一套、分发一套”的旧世界。

### 10.3 漂移三：为了省流量，滑走就停止补齐

这会让每个用户都只拉一点点，后面的人仍然冷启动，群聊整体永远不热。

### 10.4 漂移四：为了稳住体验，偷偷回退服务器兜底

这会让失败态真相彻底被掩盖，后面再也无法判断系统到底有没有真正进入纯 peer 生存态。

### 10.5 漂移五：把“纯 peer 不可用”误当成必须补第二链的 bug

如果设计已经明确接受“无在线完整 peer 时暂时不可播”，那这件事本身就不是 bug。  
真正的 bug 是：

1. 说不清楚；
2. 状态不稳定；
3. 把“无在线种子”和“内容已删除”混掉；
4. 在不同壳里给出不同真相。

---

## 11. 实现红线

后续写 implementation plan 和落代码时，禁止越过下面这些红线：

1. 禁止新增前端正式媒体直链入口。
2. 禁止恢复 `HLS` 为正式图片/视频播放主链。
3. 禁止让 `poster / still / thumbnail` 回到新媒体正式真相。
4. 禁止让时间线、查看器、全屏维护第二套媒体 owner。
5. 禁止把滑走即停补齐重新做成默认行为。
6. 禁止把“无在线种子”混成一般加载失败。
7. 禁止 `24 小时` 后继续让服务器对前端承担该内容的第二字节主链职责。
8. 禁止为了某个端单独长出另一套媒体分发真相。
9. 禁止以降质换取所谓秒开。

## 12. 验证门禁

后续 plan 与实现至少要验证下面这些事实：

1. 新上传图片和视频，前端正式内容字节都只从同一个 `WebTorrent` 会话进入时间线与查看器。
2. 前 `24 小时` 内，后端确实同时以 `WebSeed + WebRTC seeder` 身份参与 swarm。
3. 用户滑到媒体后，即使滑走，后台补齐仍继续进行。
4. payload 补齐完成后，客户端进入做种态，而不是只缓存不上传。
5. 查看器正式播放与时间线媒体真相一致，不存在“时间线是 torrent、查看器回到直链”的裂缝。
6. `24 小时` 到点后，后端对该内容停止媒体字节供给。
7. `24 小时` 后若还有在线完整 peer，新用户仍能通过 swarm 正常加载。
8. `24 小时` 后若没有在线完整 peer，前端先显示“正在尝试连接群友”，随后明确进入“当前没有在线种子，等待群友上线”。
9. 文件删除后，前端得到的是“内容已删除”，而不是“无在线种子”。
10. 全链路没有偷偷生成更糊的第二正式媒体版本。
11. `chrome-devtools-cli` 真实烟测必须覆盖：
    - `https://localhost`
    - sender / viewer 双会话
    - 房间 `1234b`
    - 图片与视频都验证
    - `0-24 小时` 强 seed 阶段验证
    - 模拟超过 `24 小时` 后的纯 peer 阶段验证
    - “无在线种子”与“内容已删除”两种失败态验证
12. `24 小时` 退场测试必须证明：
    - 判定基于持久化 `complete_at`
    - 服务重启不会重置倒计时
    - 可通过测试时钟/时间推进稳定触发退场
13. 图片冷启动测试必须证明：
    - 无本地缓存时不会偷偷请求服务器 thumbnail
    - 支持渐进式解码的格式会优先使用同一 payload 早期字节
    - 不支持渐进式解码的格式会进入稳定占位态，而不是空白失真或第二资产回退

## 13. 最终硬裁决

以后在 `koko` 里，必须按下面这句话理解媒体系统：

**服务器可以在前 `24 小时` 内作为 swarm 里的超强群友，但前端正式媒体字节永远只能走 `WebTorrent`；`24 小时` 后服务器退出字节供给，只剩在线群友继续高速互帮互助；没有在线完整 peer 时，系统必须说真话。**

从这句话自然推出所有实现边界：

1. 禁止第二正式播放主链；
2. 禁止新媒体长期仍依赖服务器 poster/still；
3. 禁止滑走即停补齐；
4. 禁止补齐完成后不做种；
5. 禁止 `24 小时` 后偷偷回退服务器直供；
6. 禁止用模糊失败态掩盖纯 peer 真相；
7. 禁止牺牲画质伪造顺滑。

后续 implementation plan 和代码改动，都只能在这套真相边界内工作；凡是离开这条边界去“临时兜一下”的，都应直接视为漂移，必须禁止。
