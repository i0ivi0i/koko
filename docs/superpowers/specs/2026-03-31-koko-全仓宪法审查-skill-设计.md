# Koko 全仓宪法审查 Skill 设计

## 1. 目标

本设计文档用于冻结一个面向 `Koko` 仓库的专用审查型 skill。

这不是普通 code review skill，也不是只看当前 diff 的轻量检查器；它的目标是把根目录 [审查维护.md](/E:/koko/审查维护.md) 升级成一套可重复触发、可长期复用、可持续进化的“全仓宪法审查机制”。

这套 skill 必须做到：

- 默认从全仓视角审查，而不是只盯当前改动
- 默认拉起多位大师级 subagent 分工审查整个仓库
- 默认以 [审查维护.md](/E:/koko/审查维护.md) 为最高裁决依据
- 默认主动使用 web 与 Context7 获取官方文档和最佳实践
- 默认输出高密度、可行动、去噪后的问题清单、治理优先级与修复建议
- 默认生成正式 `specs` 审查档案，沉淀到 [docs/superpowers/specs](/E:/koko/docs/superpowers/specs)

它服务的不是一次性体检，而是长期治理：持续防止 `Koko` 在长期演进中出现手搓成熟轮子、重复造轮子、DDD 分层漂移、前后端越位、多壳共核失守、冗余胶水膨胀和热路径污染。

## 2. 非目标

这套 skill 明确不承担以下职责：

- 不直接进入自动修复模式
- 不默认替用户做大规模代码重写
- 不把 subagent 原始结论原样倾倒给用户
- 不退化成普通静态扫描器或风格检查器
- 不把“发现很多问题”当成目标，而忽略结论质量
- 不只服务当前一次清理战役，它必须可在未来反复复用

第一版的定位是：`治理型全仓审查 skill`，而不是 `自动重构 skill`。

## 3. 用户真实诉求冻结

基于本轮连续澄清，用户真正要的不是“做一个会审查代码的小工具”，而是：

- 把 [审查维护.md](/E:/koko/审查维护.md) 变成一个以后可直接调用的制度型 skill
- 让 skill 一旦触发，就自动进入“多位大师级专家 + 主 agent 总裁决”的审查模式
- 让未来谁来改仓库，都更难把系统改乱
- 让这套机制长期守住这些根本边界：
  - 禁止手搓成熟轮子
  - 禁止重复造轮子
  - DDD 边界清晰
  - 前端不许干后端的活
  - 后端不许干前端的活
  - 多壳共核
  - 核心业务不被具体框架绑死

更直白地说，这套 skill 要成为 `Koko` 仓库的长期“架构巡检宪兵”，而不是临时陪审团。

## 4. 设计总原则

### 4.1 以制度为中心，不以实现技巧为中心

这套 skill 的核心价值不是“怎么调 agent 更花哨”，而是把 [审查维护.md](/E:/koko/审查维护.md) 的制度落成稳定工作流。

### 4.2 审查重于产量

宁可少报，也不泛报。最终报告只保留“作者知道后大概率会修”的结构性问题，不追求堆数量。

### 4.3 扫描可以全仓，结论必须去噪

它默认逐行扫描整仓，但最终产物必须高度收敛，不能把整仓碎片噪音直接倒给用户。

### 4.4 主 agent 是总裁决官，不是搬运工

主 agent 必须主动交叉比对、去重、裁决冲突、筛证据、定治理优先级，而不是仅汇总 subagent 回复。

### 4.5 职责固定，能力动态选择

主 agent 固定的是职责，不是 skill 名单。未来 skill 越来越多，它越不能依赖硬编码 skill 清单，而必须按实际证据缺口、代码热点、阶段目标动态选择合适能力。

### 4.6 大师级专家 + 外部资料校准

subagent 不是普通执行器，必须是大师级审查角色；它们既要懂本地代码，也要主动用 web 和 Context7 查最佳实践、官方文档与成熟实现。

## 5. 触发策略

### 5.1 显式触发

显式触发也必须满足 `仓库级范围前置条件`。

也就是说，只有当用户明确表达“整个仓库 / 整个项目 / 全仓 / 当前代码库整体 / 长期维护治理”这类 repo-scope 语义时，下面这些审查主题才应触发本 skill。

用户明确表达以下语义时，这套 skill 应直接触发：

- 全仓审查
- 审查整个仓库
- 深度代码审查
- 架构治理审查
- 全仓清理前体检
- 检查重复造轮子
- 检查冗余代码/冗余框架胶水
- 检查架构是否变乱
- 检查 DDD 分层
- 检查前后端解耦
- 检查有没有手搓成熟轮子
- 检查多壳共核是否失守

如果用户说的是“看这个模块的 DDD 分层”“帮我审一下这个文件”“检查这个 PR 的前后端边界”，即使出现了相同关键词，也默认不触发本 skill，而应走局部 review / 局部审查流程。

### 5.2 语义自动触发

即使用户没有点名这个 skill，只要请求明显落入以下场景，也应自动触发：

- 长期维护审查
- 架构体检
- 历史技术债排查
- 全仓清理前的基线治理审查
- 多壳共核/边界漂移排查
- 长期防屎山化治理
- 审查维护制度执行情况复核

这里的“明显落入”必须同时满足两类信号：

- `仓库级治理信号`
  - 全仓、整个项目、长期维护、架构治理、制度执行、技术债治理、重复造轮子、冗余结构、多壳共核、前后端解耦
- `审查动作信号`
  - 审查、体检、排查、检查、治理、清理、复核

只有动作信号，没有仓库级治理信号时，不得自动触发。

### 5.3 触发后的默认模式

一旦触发，默认不是当前 diff 审查，而是：

- 先全仓结构扫描
- 再热点深挖
- 再主 agent 总裁决
- 再输出最终报告与 `specs` 档案

只有用户显式要求局部模式时，才允许缩小范围，但即使如此也应先做一次最小全仓背景扫描，避免脱离系统上下文。

### 5.4 不触发与降级规则

以下场景默认不应自动升级成这套全仓审查 skill：

- 单个 bug 修复
- 单个测试修复
- 单个文件讲解
- 单个接口开发
- 普通实现任务
- 普通代码 review
- 用户只是让 agent “继续开发”或“直接修”

这些请求只有在同时出现以下语义时，才应升级：

- 明确要求全仓、长期维护、架构治理、审查宪法执行、排查重复造轮子、排查冗余结构
- 或用户明确说要对整个项目做治理级审查

skill description 也不得把 `清理代码`、`重构治理`、`深度检查` 这类通用词单独写成触发条件，必须和仓库级治理信号绑定。

### 5.5 触发优先级规则

当用户请求既像实现任务又像治理审查时，按以下顺序处理：

1. 用户明确要求“全仓/治理/架构审查”时，本 skill 优先
2. 用户明确要求“先修/先实现”且未要求治理审查时，本 skill 不抢占主流程
3. 用户只表达模糊的“看看代码”“清一下”时，应先判断是否存在全仓治理语义；没有则不触发

这样可以保留这套 skill 的重武器定位，同时避免把普通局部任务误触成全仓审查。

## 6. 审查范围与输入契约

### 6.1 默认输入

这套 skill 的默认输入包括：

- 当前仓库完整代码
- 当前仓库关键文档
- [审查维护.md](/E:/koko/审查维护.md)
- [AGENTS.md](/E:/koko/AGENTS.md)
- 必要时的 git 历史、既有计划、既有 specs
- 外部官方文档与最佳实践资料
- Context7 提供的库级资料

### 6.2 可选输入

用户可以额外声明聚焦主题，例如：

- 只关心前后端解耦
- 只关心重复造轮子
- 只关心实时链路
- 只关心测试债
- 只关心某个模块

但这些聚焦目标只影响深挖优先级，不取消默认的全仓背景扫描。

## 7. 总体编排模型

本 skill 采用 `C+B` 混合架构：

- `C`：分阶段宪法式审查流程
- `B`：固定底盘 + 动态增援的专家阵容

### 7.1 阶段 1：全仓结构扫描

先由主 agent 启动固定底盘专家，对整仓建立全局地图：

- 模块边界
- 依赖走向
- DDD 五层归属
- 前后端职责归属
- 热路径与冷路径
- 重复能力分布
- 历史胶水与低价值抽象分布
- 测试覆盖结构

这一阶段的目标是定位热点和高疑点，而不是直接定最终结论。

### 7.2 阶段 2：热点深挖与动态增援

如果第一阶段发现特定热点，就补充对应大师级专家，例如：

- wasm / 浏览器壳层
- Dioxus / web shell
- Axum / HTTP adapter
- SQLx / repo 映射
- socketioxide / realtime 主链路
- CLI / 多入口适配
- Rust async 并发边界
- 依赖治理与成熟生态复用
- 测试债与验证质量

### 7.3 阶段 3：主 agent 总复核与裁决

所有 subagent 返回后，主 agent 必须做：

- 交叉比对
- 去重合并
- 冲突裁决
- 证据强弱筛选
- 最终治理优先级归档
- 问题条目收敛

### 7.4 阶段 4：正式产物落盘

最终同时输出：

- 会话内最终审查报告
- 自动写入 [docs/superpowers/specs](/E:/koko/docs/superpowers/specs) 的正式审查档案

## 8. 固定底盘专家阵容

以下专家每次审查都必须出场。

### 8.1 宪法架构总审官

职责：

- 以 [审查维护.md](/E:/koko/审查维护.md) 为最高标准
- 审查整仓是否违反根本红线
- 识别整体退化方向与系统性模式问题

### 8.2 DDD 分层与边界审官

职责：

- 专查 `domain / application / contract / adapter / shell`
- 审查业务真相是否放错层
- 审查 handler/repo/shell 是否偷承载业务规则

### 8.3 前后端解耦审官

职责：

- 审查前端是否承载权限、成员、治理、消息成立真相
- 审查后端是否为某个壳硬编码页面流程、展示字段、壳专属数据形状
- 审查多壳共核是否被破坏

### 8.4 重复造轮子与冗余实现审官

职责：

- 查重复 helper、重复 wrapper、重复入口、重复状态来源
- 查低价值包装、历史胶水、冗余抽象
- 查“旧问题没收，先叠新层”的结构退化

### 8.5 依赖复用与成熟生态审官

职责：

- 审查本该复用成熟方案的地方是否被私有实现替代
- 审查手搓成熟轮子、重复造轮子与依赖选型偏差
- 结合 web 与 Context7 校准判断

### 8.6 测试与验证审官

职责：

- 审查测试是否验证真实行为
- 审查是否存在实现细节绑定型测试
- 审查关键路径是否缺少验证

### 8.7 访问控制、成员真相与契约稳定审官

职责：

- 审查权限、成员资格、房间可见性、消息成立真相是否放在正确层级
- 审查访问控制是否散落在多个入口 adapter
- 审查 `contract` 是否保持多壳共享的稳定表面
- 审查错误码、事件、快照、命令是否被壳层语义污染

## 9. 动态增援专家清单

以下不是每次必出，但一旦热点出现，应自动增援：

- WASM / 浏览器壳层专家
- Dioxus / Web shell 专家
- Axum / HTTP adapter 专家
- SQLx / repo / 持久化映射专家
- socketioxide / realtime 主链路专家
- CLI / 多入口适配专家
- Rust async 并发边界专家
- 依赖治理 / Cargo 特性收口专家
- 性能与热路径专家
- 代码简化 / tech debt 清理专家

## 10. 主 agent 的角色与动态能力调度

### 10.1 主 agent 的固定职责

主 agent 必须承担三类稳定职责：

- 审查总调度
- 证据总裁决
- 最终产物总收口

### 10.2 主 agent 不是固定 skill 调用器

主 agent 能调用的 skill 不能写死成封闭名单。

应固定的是：

- 它要补什么能力
- 什么时候自己补，什么时候派 subagent
- 如何把外部资料与本地证据合起来裁决

不应固定的是：

- 永远只能调用某几个既定 skill

### 10.3 动态能力调度原则

当主 agent 发现当前审查需要额外能力时，应按实际情况动态选择合适的 skill，例如：

- 需要架构校准时，调用最匹配的架构类 skill
- 需要技术债判断时，调用最匹配的技术债类 skill
- 需要代码简化判断时，调用最匹配的简化/清理类 skill
- 需要实现规划时，调用最匹配的计划类 skill
- 需要外部资料校准时，优先使用 web 与 Context7

这条规则必须写进 skill 正文，防止未来随着 skill 增长而过时。

## 11. subagent 输出约束与去噪规则

每个 subagent 输出的问题，如果要进入主 agent 视野，至少必须满足：

- 具体指出问题是什么
- 指出它违反了哪类宪法/边界
- 说明它影响了什么真实场景
- 提供最小可验证证据
- 说明为什么这不是单纯风格偏好

以下内容默认不应进入最终报告：

- 只有感觉没有证据的结论
- 只能泛泛而谈“可能有风险”的说法
- 无法证明影响范围的怀疑
- 重复性很高但未去重的问题碎片

### 11.1 问题条目最小结构

每个候选问题条目至少必须包含：

- 问题标题
- 违反的宪法/边界
- 本地代码证据
- 影响链路
- 建议修复方向
- 证据等级

### 11.2 同根因合并规则

如果多个 subagent 的结论同时满足以下条件，主 agent 必须合并为同一问题：

- 指向同一条权威事实或同一层级错放
- 共享同一根因，而不是只共享表面症状
- 修复方向高度一致

如果只是同一模块里出现多个表现，但根因不同，则不得强行合并。

## 12. 冲突裁决顺序

当多个 subagent 结论冲突时，主 agent 按以下顺序裁决：

1. [审查维护.md](/E:/koko/审查维护.md) 的硬红线与根本原则
2. 本地代码中的真实调用链、依赖关系、状态真相
3. 官方文档与 Context7 的一手资料
4. 成熟 IM / DDD / 六边形架构最佳实践
5. 当前仓库既有模式与历史约束

注意：

- “仓库以前也这么写”不能自动成为合理性的证据
- 历史代码如果违反宪法，只能说明债务已存在，不能说明它是对的

### 12.1 证据权重规则

主 agent 裁决时按以下证据权重排序：

1. 本地直接证据
   - 明确调用链、状态流、依赖图、数据落点、测试或可复现实例
2. 宪法映射证据
   - 能明确指向 [审查维护.md](/E:/koko/审查维护.md) 的具体红线或边界
3. 外部校准证据
   - 官方文档、Context7、一手资料、成熟工程公开经验
4. 经验性辅助证据
   - 合理的工程判断、历史模式、相邻模块对照

经验性辅助证据不能单独支撑正式问题结论。

### 12.2 问题确认阈值

只有同时满足以下条件，才可进入正式问题清单：

- 至少存在一条本地直接证据
- 至少存在一条宪法映射证据，或一条可直接验证的外部校准证据
- 能说明影响链路，而不是只指出局部写法

否则只能进入 `待补证观察项`，不得提前定性成正式问题。

### 12.3 降级规则

若候选问题满足以下任一情况，主 agent 必须将其降级为 `待补证观察项`：

- 只有外部最佳实践支持，但本地影响链路不清楚
- 只有局部代码异味，没有根因与边界映射
- subagent 结论冲突，但当前证据不足以完成裁决
- 只能合理怀疑，不足以确认对公网 IM 主链路的实际影响

`待补证观察项` 不参与治理分级，但必须进入 `specs` 档案，防止重要疑点失踪。

### 12.4 冲突 tie-break 机械规则

为避免裁决漂移，主 agent 还必须遵守以下机械规则：

1. 如果只有一方具备本地直接证据，另一方只有经验判断或外部资料，则保留前者
2. 如果双方都具备本地直接证据，但指向不同根因，则拆成两个候选问题，分别判定
3. 如果双方共享同一根因，只是治理等级不同，则按是否触及以下核心面决定：
   - 权威事实归属
   - 公网 IM 热路径
   - 多壳共享契约
   - 第二套真相/第二套入口/第二套轮子
   触及则优先归入 `立即治理`，否则归入 `可延期精修`
4. 如果双方都没有本地直接证据，则双方都不得进入正式问题清单
5. 如果冲突无法在当前轮完成裁决，必须降级到 `待补证观察项`，并记录补证所需的下一步

### 12.5 观察项升级条件

`待补证观察项` 只有在补齐以下任一条件后，才允许升级成正式问题：

- 新增一条本地直接证据，并能连上影响链路
- 通过测试、运行、调用链追踪或文件间关系证明其确实影响真实行为
- 通过官方文档或 Context7 补齐关键外部校准，且能映射回本地代码边界

## 13. 结果分级体系

由于 `Koko` 是严格面向公网部署的群聊 IM 项目，最终问题分级不采用多层优先级，而采用两级治理体系。

### 13.1 立即治理

凡是如果现在不处理，就会继续破坏系统边界、放大维护成本、加深架构退化的问题，都归入 `立即治理`。

典型包括：

- 前端承载后端真相
- 后端承载前端壳层流程/展示语义
- DDD 分层污染
- `contract` 被 UI 语义污染
- 手搓成熟轮子已进入有效路径
- 重复造轮子开始形成第二套事实源
- 热路径被明显污染
- 双重真相、双重入口、双重流程
- 会显著阻碍多壳共核和未来 CLI / 移动端演进的问题

### 13.2 可延期精修

凡是短期不处理也不会继续制造结构污染、不会继续放大系统风险、不会阻碍后续增删改的问题，才允许归入 `可延期精修`。

典型包括：

- 局部命名可更稳
- 局部代码还能更简洁
- 某些文档表达还能更清晰
- 某些测试还可进一步优雅化，但当前不阻碍演进

分级本质不是看“严重感”，而是看：

- 现在不动，会不会继续让系统变乱
- 现在不动，会不会继续把未来改动成本抬高

### 13.3 待补证观察项

`待补证观察项` 不是第三个治理优先级，而是证据状态。

它只用于承载那些：

- 结构风险明显
- 很可能涉及公网 IM 核心边界
- 但当前还缺少最后一跳证据

的疑点。

它们不得混入 `立即治理` 或 `可延期精修`，但也不得消失在附录里；必须被单列记录，并在后续专项治理或下一次审查中优先补证。

会话内最终报告与自动落盘的 `specs` 档案都必须单列这一栏，不能只放在附录。

## 14. 问题分类法

每条最终问题除了治理等级，还必须归入一个主分类。

建议固定分类包括：

- 分层污染
- 前后端越位
- 重复造轮子
- 手搓成熟轮子
- 冗余代码
- 冗余抽象
- 冗余框架胶水
- 双重真相 / 双重入口 / 双重流程
- 热路径污染
- 依赖与生态复用问题
- 测试与验证债务
- 历史技术债
- 性能与并发边界问题
- 可替换性 / 可演进性风险

## 15. 输出格式

### 15.1 会话内最终报告

最终报告至少包含：

- 审查结论
- `立即治理` 问题清单
- `可延期精修` 问题清单
- 每个问题的证据与影响范围
- 修复建议
- 重复造轮子 / 手搓成熟轮子专项清单
- 冗余代码 / 冗余抽象 / 冗余胶水专项清单
- 分层污染与前后端越位专项结论
- 测试与验证债务专项结论
- 总体治理判断

### 15.2 自动落盘的 `specs` 文档

每次运行后，必须在 [docs/superpowers/specs](/E:/koko/docs/superpowers/specs) 自动生成一份正式档案。

建议命名：

`YYYY-MM-DD-全仓审查-<主题>.md`

至少包含以下章节：

- 审查元数据
- 审查目标
- 审查范围
- 审查依据
- 专家阵容与调度说明
- 总体结论
- `立即治理` 清单
- `可延期精修` 清单
- `待补证观察项`
- 重复造轮子与冗余实现专项结论
- 分层与前后端解耦专项结论
- 测试与验证结论
- 冲突裁决与过滤说明
- 后续治理建议
- 附录与引用资料

### 15.2.1 `dry-run` 例外

默认 full audit 模式应自动落盘；但以下情况允许进入 `dry-run`，只输出会话内报告，不写入仓库：

- 用户明确要求只预览、不落文件
- 当前工作树状态不适合新增审查档案
- 本轮只是测试 skill 触发与裁决流程，而不是正式治理审查

进入 `dry-run` 时，主 agent 必须显式说明为什么未落档。

### 15.2.2 写盘失败兜底

如果 full audit 模式下正式档案写入失败，主 agent 必须执行以下强制降级状态机：

1. 保留并正常输出会话内最终审查报告
2. 明确告知用户 `specs` 档案未成功写入
3. 记录失败原因
   - 权限
   - IO
   - 路径缺失
   - 并发冲突
   - 其他可识别错误
4. 将本次运行标记为 `archive_failed`
5. 禁止静默声称“已自动落盘”
6. 如果发生部分写入，必须丢弃不完整文件，禁止留下伪成功档案

写盘实现应优先采用“临时文件 + 原子替换”策略。

如果能安全重试一次，应重试一次；重试后仍失败，则停止写盘并显式告警，不得无限重试。

### 15.3 审查元数据强制字段

`specs` 档案必须至少记录：

- 本次审查时间
- 仓库路径
- 审查时的 git commit / 工作树状态
- 主 agent 使用的 skill 与能力来源
- 实际启用的固定底盘 subagent
- 实际启用的动态增援 subagent
- 实际查阅的外部资料与 Context7 资料
- 被过滤掉的候选问题数量
- `待补证观察项` 数量
- 结论整体置信度

### 15.4 冲突裁决记录要求

凡是经过主 agent 裁决后才保留、合并或降级的问题，都必须在 `specs` 档案中留下最小裁决记录：

- 冲突点是什么
- 为什么保留/合并/降级
- 最终依据是什么

否则日后无法复盘这次审查为什么得出该结论。

## 16. 失败兜底与不确定性处理

### 16.1 证据状态区分

主 agent 必须区分三种状态：

- `已确认问题`
- `高疑点，需补证`
- `不进入最终问题清单`

只有第一类进入最终正式问题清单。

第二类可以进入 `specs` 档案中的观察项，但不能冒充正式结论。

### 16.2 subagent 超时或失败

当专项 subagent 超时、失败或质量不足时：

1. 先看固定底盘是否已足够覆盖
2. 不够时由主 agent 补做关键复核
3. 若仍无法确认，必须在最终文档中显式记录缺口和影响范围

允许局部审查失败，但不允许静默失败。

### 16.3 外部资料冲突

当官方文档、Context7 和外部实践资料冲突时：

- 一手资料优先于二手解读
- 官方文档优先于博客总结
- 成熟工程公开资料优先于零散经验帖
- 若仍冲突，回到本仓库宪法与本地代码事实裁决

### 16.4 全仓扫描的降噪要求

最终报告必须模式级收敛，避免：

- 逐文件刷屏
- 同根因拆成多条
- 噪音压过主问题

## 17. 技能创建落地冻结项

本设计文档只冻结 skill 设计，不直接实施；但 skill 自身的落地约束必须在这里先冻结，不能留到实现阶段自由发挥。

### 17.1 目录与命名

第一版 skill 应按 `Koko` 专用能力创建，而不是抽象成通用框架。

建议冻结为：

- skill 根目录：`C:\Users\home\.codex\skills\koko-constitutional-audit`
- 主文件：`C:\Users\home\.codex\skills\koko-constitutional-audit\SKILL.md`

后续如果用户要求迁移位置或改名，可在单独 spec 中变更；第一版实现不得擅自漂移。

### 17.2 资源组织

第一版 skill 至少应采用以下结构：

- `SKILL.md`
- `references/`
- `evals/`

其中：

- `SKILL.md` 承载触发 description、主流程、裁决规则、输出格式
- `references/` 收纳对 [审查维护.md](/E:/koko/审查维护.md) 的引用说明、固定模板和必要补充规则
- `evals/` 收纳针对 skill 的测试 prompt 与断言描述

### 17.3 触发 description 冻结项

skill description 必须同时覆盖：

- 全仓审查
- 架构治理
- DDD 边界排查
- 前后端解耦排查
- 重复造轮子与冗余实现排查
- 审查维护制度执行复核

并且必须带有负向边界提示，明确它不是普通实现/普通 bugfix/普通局部 review skill。

### 17.4 输出契约冻结项

skill 实现时必须默认输出：

- 会话内最终审查报告
- 自动生成的 `specs` 档案

并默认包含：

- `立即治理`
- `可延期精修`
- `待补证观察项`

### 17.5 验证与 eval 冻结项

skill 实施后必须至少准备一组 eval，用来验证：

- 不会误触普通局部实现任务
- 碰到全仓治理语义时会正确触发
- 能正确生成两级治理结果和观察项
- 能落出完整 `specs` 元数据
- 能在多 subagent 结论冲突时完成收口
- `dry-run` 与正式落档模式都能按规则工作

没有这些 eval，就不应宣称 skill 已稳定落地。

## 18. 验收标准

只有满足以下条件，这份 skill 设计才算通过：

- 触发条件明确，不会退化成普通 review skill
- 全仓扫描与去噪收口并存，不会一头重一头空
- 主 agent 裁决职责明确，不是汇总器
- 主 agent 的证据权重、确认阈值、降级规则明确
- subagent 大师级与外部资料校准要求明确
- 动态 skill 调度原则明确，不写死 skill 名单
- `立即治理 / 可延期精修` 两级治理体系明确
- `待补证观察项` 有单独承载位，不会失踪
- 输出格式与 `specs` 档案结构明确
- `specs` 元数据足够支撑后续复盘
- IM 访问控制、成员真相、契约稳定性有专门审面
- skill 的目录、命名、资源组织、description、eval 要求已冻结
- 失败兜底与证据不足处理明确
- 设计能长期复用，不依赖本次对话上下文才成立

## 19. 下一步

在本设计通过 review 并经用户确认后，下一步不是直接写代码，而是：

1. 为 skill 本体写实现计划
2. 明确 skill 目录、命名、触发 description 与资源组织
3. 再进入 skill 实施与测试阶段

这能确保 skill 自身也遵守 `先设计、后计划、再实施` 的制度。
