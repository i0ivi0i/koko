# 房间历史基线与分页恢复设计

日期：2026-04-06  
状态：设计已确认，待写 implementation plan  
范围：`koko` 房间进入/刷新恢复时的最近消息基线、上滑加载更早消息、历史与 realtime 并发边界

## 0. 设计结论

这次不是继续修“刷新能不能回房间”这个表面问题，而是把房间恢复语义补完整：

1. 进入一个已经有历史的房间时，普通用户应直接看到最近 `55` 条消息。
2. 刷新页面重新回房间时，普通用户也应直接看到最近 `55` 条消息。
3. realtime 连接只负责“最近 `55` 条之后的新消息”，不负责倒流旧历史。
4. 更早历史通过“上滑继续加载”单独分页获取，不在刷新恢复链路里一次性灌全量历史。
5. 房间历史真相仍以后端为准；前端不靠内存残影、本地猜测或 socket 暂存去伪造历史恢复。

一句话总结：

**房间恢复的正确语义不是“回到这个房间号”，而是“回到这个房间时，顺手拿到最近一段真实聊天内容”。**

## 0.1 直接对齐的官方最佳实践

这次设计继续只采纳一手资料里已经反复验证过的共识，不发明第二套私有基础设施：

1. Socket.IO / `socketioxide` 负责连接、房间广播、临时断线恢复，不负责替业务保存聊天历史真相。
2. Socket.IO 的 `room` 是 server-only 广播分组，不是业务成员真相，也不是历史存储抽象。
3. Socket.IO 的 `connection state recovery` 只解决一段有限的断线恢复与漏包问题，不等于聊天历史分页。
4. Telegram 的公开同步模型明确区分“当前状态基线”和“继续补差异”；历史消息本身通过历史接口按锚点和数量读取。
5. WhatsApp Multi-device 的公开资料明确强调设备历史与应用状态同步，而不是靠 realtime 连接把旧历史“自动变出来”。

落到 `koko` 的直接约束只有四条：

1. `socketioxide / socket.io` 已有的房间广播、断线生命周期、重连机制直接复用，不手搓重复轮子。
2. “最近 `55` 条消息基线”与“更早消息分页”属于业务查询层，不假装让 realtime 库替我们做。
3. `event_position`、`message_id` 这类内部锚点必须继续存在，但默认不暴露给普通用户。
4. 无论是首次进房、刷新回房、realtime 新消息，还是上滑分页，都必须对同一组权威事实说同一套真话。

## 1. 背景与问题

当前系统在“刷新后掉回搜索页”这件事修完后，又暴露出一个更本质的问题：

1. 房间恢复后，页面虽然回到了原房间，但历史消息消失了。
2. 用户看到的是一个“空荡荡的房间”，仿佛历史被清空了。
3. 实际上，更像是前端把消息列表清空后，没有再把历史基线重新装回来。

从当前代码和契约看，这个问题不是“后端历史被删了”，而是“恢复链路缺了一块真相”：

1. 当前房间快照只返回房间标识和 `latest_event_position`。
2. 前端进入房间时会把当前消息列表重置为空。
3. 然后恢复链路只会从 `latest_event_position` 之后继续等增量。
4. 但“之后的新消息”并不能替代“这房间最近已经聊过什么”。

所以当前故障不是单点小 bug，而是恢复语义不完整：

1. 首次进入已有历史的房间，也可能看不到旧消息。
2. 刷新回房时，更稳定地暴露出这个问题。
3. 如果只靠前端缓存或本地内存补丁掩盖，换浏览器标签页、硬刷新、跨设备后仍会露馅。

## 2. 目标

本次设计必须同时达到五个结果：

1. 首次进入已有历史的房间时，直接看到最近 `55` 条消息。
2. 刷新页面回房间时，直接看到最近 `55` 条消息。
3. 上滑时可以继续加载更早消息，而不是把全量历史一次性灌回页面。
4. 历史分页与 realtime 新消息并发时，不重复、不乱序、不把现有列表清空。
5. 整个方案继续保持前后端解耦：后端提供稳定事实，前端只负责展示和滚动体验。

## 3. 明确不做

这次明确不做这些事，防止 scope 失控：

1. 不新增“全量聊天记录下载”或“导出全部历史”。
2. 不设计消息搜索、按时间跳转、按天分组、已读回执、在线状态。
3. 不把普通聊天历史查询强行改成全部走 socket 协议。
4. 不把这次房间历史恢复扩成多设备漫游产品设计。
5. 不把共享契约改成 Web 专属视图模型。

## 4. 设计原则

### 4.1 房间可见基线必须是权威事实，不是前端残影

前端可以记住：

1. `current_room_id`
2. 当前滚动位置
3. 当前是否正在加载更早消息

但前端不能宣布：

1. 我内存里残留的消息列表就是真实历史
2. 只要 room 还在，历史就能凭空从 `latest_event_position` 倒推出来
3. socket 连接恢复成功就等于历史恢复成功

### 4.2 历史基线、历史分页、realtime 新消息三件事分开

这三件事不能再混成一团：

1. 最近 `55` 条消息，负责“先看到房间现在聊到哪”。
2. 上滑分页，负责“继续看更早的历史”。
3. realtime，负责“从当前基线之后继续接新消息”。

任何实现只要把其中两件事混成一个机制，后面就很容易长出：

1. 空房
2. 重复消息
3. 顺序错乱
4. 断线后真假状态混淆

### 4.3 内部锚点保留，但不端给普通用户

成熟 IM 的共同点不是“把编号给用户看”，而是系统内部始终保留稳定锚点。

对 `koko`，至少要继续保留这些稳定锚点：

1. `message_id`
2. `sender_session_id`
3. `event_position`
4. `sent_at`
5. `client_message_id`（如果当前发送链路已有）

这些锚点的用途是：

1. 去重
2. 排序
3. 刷新恢复
4. 历史分页
5. realtime 并发合流

默认普通用户界面不展示这些内部锚点。

### 4.4 不重复造轮子，只在业务边界补真空

这次必须明确什么该复用、什么该自己负责：

1. `socketioxide / socket.io` 已有的广播分组、连接生命周期、断线恢复机制直接复用。
2. 不手搓第二套房间广播器、第二套断线恢复壳、第二套私有 ack 协议。
3. 但“最近 `55` 条消息基线”和“更早消息分页”是应用自己的业务查询语义，本来就该由后端查询接口提供。
4. 不能因为用了 socket 库，就假设房间历史和分页也该让 socket 层魔法解决。

## 5. 核心方案对比

### 5.1 推荐方案：进入房间时直接带回最近 55 条消息

进入房间或恢复房间时，后端直接返回：

1. 房间基本信息
2. `latest_event_position`
3. 最近 `55` 条消息

优点：

1. 首次进房、刷新回房、断线后重进三条路径统一。
2. 用户第一眼直接看到最近聊到哪。
3. 前端编排最简单，最不容易再出现“房间回来了但内容是空的”。
4. 共享契约只是在“房间快照”里补齐“房间当前可读基线”，没有把 Web 页面流程硬编码进后端。

代价：

1. 房间快照接口会比现在更胖。
2. 需要把“房间元信息快照”和“最近消息基线”组合在一起设计清楚。

### 5.2 备选方案：房间快照和最近消息分两个请求

前端先拿房间快照，再立刻发第二个请求拿最近 `55` 条历史。

优点：

1. 接口职责更细。
2. 历史查询以后更容易扩成更通用的分页接口。

问题：

1. 前端恢复链路更绕。
2. 页面会出现“房间先出来，消息晚一拍到”的空档。
3. 首屏空房闪烁和多一步失败分支更难管。

### 5.3 不推荐方案：继续靠前端缓存或从 latest_event_position 猜历史

优点只有一个：短期改得快。

但它有三个根问题：

1. 刷新、硬重载、跨设备都会暴露真空。
2. 历史真相变成“前端刚好还记得什么”。
3. 后面实现上滑分页时还得推倒重来。

**本次设计固定采用 5.1。**

## 6. 契约设计

### 6.1 房间快照升级为“房间信息 + 最近 55 条消息基线”

现有房间快照的语义要升级，不再只是：

1. 你在不在这个房间
2. 当前最新事件位置是多少

而是升级成：

1. 你有权看这个房间
2. 这个房间当前最新事件位置是多少
3. 这个房间最近 `55` 条消息是什么

返回形状应至少包含：

1. `room_id`
2. `latest_event_position`
3. `recent_messages`

其中 `recent_messages` 固定为：

1. 最多 `55` 条
2. 老的在前，新的在后
3. 可直接渲染

这样前端拿到快照后，不再需要“先清空，再等以后增量来补”。

### 6.2 单条消息的稳定事实字段

为了让历史分页和 realtime 并发时还能稳定合流，一条消息至少要继续提供这些稳定事实：

1. `message_id`
2. `sender_session_id`
3. `display_alias`
4. `event_position`
5. `sent_at`
6. `body`

如果已有 `client_message_id`，则继续保留，不在这次设计里删改它的职责。

说明：

1. `event_position` 是房间内顺序锚点。
2. `message_id` 是单条消息的稳定身份。
3. `body` 相同不代表消息相同，所以不能按文本内容去重。

### 6.3 更早历史分页接口

这次设计不把“更早历史”塞回 realtime，而是提供明确分页语义。

大白话的接口语义是：

1. “把当前最老这条之前的，再给我 `55` 条。”

为了防漂移，分页条件固定用稳定顺序锚点，而不是用 UI 时间文案：

1. `before_event_position`
2. `limit`
3. `session_id`

固定规则：

1. `limit` 默认也是 `55`
2. 后端仍按“老的在前，新的在后”返回
3. 返回的是“严格早于 `before_event_position` 的消息”
4. 如果已经没有更早消息，就返回空数组

本次设计不强行规定历史接口的 URL 命名，但必须满足以上稳定语义。

### 6.4 realtime 与增量补洞语义不变

本次不会把当前 `events` 增量补洞语义推翻重来。

仍然保持：

1. `from` 的语义是“返回 `event_position > from` 的事件”
2. `events` 用于“当前基线之后的新事件补洞”
3. realtime 用于“继续接当前基线之后的新消息”

也就是说：

1. 历史分页不复用 `events`
2. `events` 不倒流更早历史
3. 房间快照里的 `recent_messages` 解决“当前基线”
4. 上滑分页接口解决“更早历史”

## 7. 数据流设计

### 7.1 首次进入已有历史房间

固定顺序：

1. bootstrap 得到当前权威 `session_id`
2. 请求房间快照
3. 后端返回房间信息 + 最近 `55` 条消息 + `latest_event_position`
4. 前端直接渲染最近 `55` 条
5. 然后再用 `latest_event_position` 建立 realtime / events 补洞续接

关键点：

1. 首次进房和刷新回房不再是两套语义。
2. “有房间但没历史”在这个路径里不再是正常状态。

### 7.2 刷新回房

固定顺序：

1. 读取本地 `koko_current_room_id`
2. bootstrap 得到当前权威 `session_id`
3. 请求房间快照
4. 快照直接带回最近 `55` 条消息
5. 渲染最近 `55` 条后，再继续接新消息

这里特别强调：

1. 前端不再靠刷新前的内存消息列表复原历史。
2. 刷新只是重新取一份权威房间基线，不改变后端历史真相。

### 7.3 上滑加载更早消息

固定顺序：

1. 前端找出当前列表里最老那条消息的 `event_position`
2. 请求“这个位置之前的 `55` 条”
3. 后端返回一页已经排好序的更早消息
4. 前端把它插到现有列表顶部
5. 如果这页为空，就标记“已经没有更早消息”

关键点：

1. 上滑加载失败时，不清空当前列表。
2. 用户已经看到的消息继续保留。
3. 失败只影响“这一页更早消息没拿到”，不影响当前房间基线。

### 7.4 realtime 新消息并发到达

这时最容易长出重复或顺序错乱，所以边界写死：

1. 当前列表始终以稳定锚点合并。
2. 历史分页插顶部，realtime 新消息插底部。
3. 任何一条消息进列表前都要先按稳定锚点去重。
4. 去重主判断依据是 `message_id`；若当前系统更稳定的主锚点是 `event_position`，也必须在实现中固定下来，不允许不同入口各用一套。
5. 合并后的最终展示顺序仍以房间内稳定顺序锚点为准。

如果实现阶段只靠“数组 append/prepend 正好没撞上”来维持顺序，后面一定会漂。

## 8. 失败语义设计

### 8.1 房间快照失败

1. `room_not_found`：
   - 清掉 `koko_current_room_id`
   - 退出房间页
   - 回到搜索页
2. `membership_required`：
   - 清掉 `koko_current_room_id`
   - 退出房间页
   - 回到搜索页
3. `invalid_session`：
   - 重新 bootstrap 获取新权威 `session_id`
   - 再重试一次当前房间快照
4. 超时 / 断网 / 5xx：
   - 保留 `koko_current_room_id`
   - 不渲染假空房
   - 显示“恢复失败，可重试”或等价提示

### 8.2 更早历史分页失败

1. 任何分页失败都不清空当前消息列表。
2. 任何分页失败都不把用户踢出房间。
3. 顶部显示轻量失败提示，并允许重试。
4. 临时失败不会把“已无更早消息”误判成真。

### 8.3 realtime / events 补洞失败

继续沿用上一个 spec 已确定的根规则：

1. 403/404 这类硬失效，退出房间并清锚点。
2. 超时、断网、5xx 这类临时失败，保留当前房间基线并重试。

补充一条新的强约束：

1. 即使 realtime 暂时失败，只要当前房间快照和最近 `55` 条基线已成立，也不能把页面退化成假空房。

## 9. 前端展示边界

### 9.1 普通用户应该看到什么

1. 最近 `55` 条真实消息
2. 之后陆续到来的新消息
3. 上滑时继续出现更早消息
4. 顶部或局部的轻量加载 / 失败提示

### 9.2 普通用户不应该看到什么

1. `session_id`
2. `event_position`
3. `message_id`
4. “内部同步位置”
5. “房间恢复偏移”

### 9.3 展示判断与业务真相分离

前端可以继续派生：

1. 这条是不是我发的
2. 该靠左还是靠右
3. 是否还在加载更早消息
4. 是否已经没有更早消息

但这些都只是展示状态，不倒灌进共享契约。

## 10. 测试与验收

### 10.1 前端壳测试

至少补齐这些：

1. 首次进入已有历史房间时，会直接渲染最近 `55` 条
2. 刷新恢复房间时，会直接渲染最近 `55` 条
3. 当房间最近消息少于 `55` 条时，按实际条数展示
4. 上滑时会请求“当前最老消息之前的 `55` 条”
5. 上滑失败不会清空当前消息列表
6. 上滑成功会把更早消息插入顶部
7. realtime 新消息到来时，不会和分页结果重复
8. 合并后顺序稳定，不会前后颠倒

### 10.2 后端 / 集成测试

至少补齐这些：

1. 房间快照会返回最近 `55` 条消息基线
2. 返回消息按“老的在前，新的在后”排序
3. 进入已有历史房间时，即使没有后续新消息，最近 `55` 条也能拿到
4. 历史分页接口会返回 `before_event_position` 之前的消息
5. 分页接口返回的每一页仍按“老的在前，新的在后”
6. 没有更早历史时返回空数组
7. 分页与房间快照对成员资格裁决保持一致

### 10.3 用户验收标准

用户视角只看这五条：

1. 首次进入老房间，不再是空房
2. 刷新回房间，不再是空房
3. 默认先看到最近 `55` 条
4. 往上滑还能继续看更早聊天记录
5. 一边翻旧消息一边来新消息时，不重复、不乱序

## 11. 顺手盯住的更高价值逻辑风险

这次实现时，除了修“刷新后空房”，还要顺手盯住两个更深层风险：

1. 首次进入已有历史房间的路径是否和刷新恢复复用同一套“最近 `55` 条基线”逻辑  
   如果不是，后面还是会出现“一条路径正常，一条路径空房”的双轨问题。
2. 分页与 realtime 合流时是否只有一套稳定去重/排序规则  
   如果快照、分页、实时三条路径各自用不同判断，后面一定会冒出重复消息或顺序错乱。

## 12. 实施顺序建议

推荐顺序：

1. 先补失败测试，锁定“房间快照直接带最近 `55` 条消息”
2. 再补历史分页接口和分页测试
3. 再收口前端“最近 `55` 条 + 上滑分页 + realtime 合流”
4. 最后做整条链路的回归验证

这样可以避免：

1. 先硬改 UI，后面再补后端真相
2. 先临时塞前端缓存，后面再推翻重做

## 13. 一句话结论

这次要修的不是“刷新为什么空一下”，而是：

**把房间当前可读历史、向前翻页历史、以及之后实时新消息，重新收口成同一套不打架的数据流。**
