# 设备级花名匿名身份最小群聊 MVP 设计

日期：2026-04-06  
状态：待实现  
定位：多壳共核的最小群聊产品设计，Web 为第一实现壳

## 0. 设计结论

这次要做的不是“再加一个 Web 聊天页面”，而是一个真正成立的最小群聊产品：

1. 启动项目
2. 进入 Web 页面
3. 系统自动恢复同一设备绑定的稳定花名身份
4. 用户输入合规房间码
5. 立即进入房间页 / 聊天区
6. 看到消息流并实时聊天

同时，后端主链不能是 demo 级接线，而必须满足：

1. 身份真相单一
2. 成员真相单一
3. 消息成立语义单一
4. 同步锚点单一
5. 失败语义明确

这个 MVP 不是“真正匿名聊天室”，而是：

**设备级稳定伪匿名群聊 MVP**

它也不是 Web 专属版本，而是：

**多壳共核的最小群聊 MVP，Web 只是第一个壳。**

---

## 1. 目标

本设计只解决一个问题：

把 `koko` 从“有实时主链基础，但产品形态还没成立”推进成：

1. 用户一进来就能输入房间码并开聊
2. 同一设备在不同房间共用同一个稳定花名
3. 先不做注册系统，也已经有稳定内部身份
4. 后续可接 Web / iOS / Android / CLI 多壳
5. 后续可接花名修改与正式注册，而不推翻当前核心

### 1.1 本次必须达到的产品感

用户不该先看到：

1. 登录页
2. 注册页
3. 房间列表页
4. 设置页
5. 多入口导航页

用户该直接感受到的，是这条主路径：

1. 打开页面
2. 看到当前系统给自己的花名
3. 输入房间码
4. 进入房间
5. 看到消息
6. 发出消息
7. 收到别人的消息

### 1.2 本次明确不做

1. 正式注册/登录系统
2. 花名手动修改
3. 房间列表
4. 已读
5. 在线人数
6. 撤回
7. 文件消息
8. 多节点部署
9. 推送通知
10. 富治理体系

这些未来都可以做，但不能压过当前的最小群聊闭环。

## 2. 现状与问题

### 2.1 当前已经成立的东西

当前仓库已经具备：

1. HTTP 冷路径：
   - 会话引导
   - 按短码进房或建房
   - 房间快照
   - 增量事件
2. Realtime 热路径：
   - connect middleware
   - `auth.session_id`
   - 房间订阅
   - 权威 `room_event` 广播
   - `event_position` 续接
   - `need_snapshot_reload`
3. 真实链路测试：
   - 双客户端同房广播
   - 跨房间隔离
   - 非成员拒绝
   - 非法 `from`
   - 续接恢复

### 2.2 当前还没成立的东西

当前真正没成立的，不是技术主链，而是产品主链：

1. 进入 Web 页后还没有“真正的进房页 -> 房间页”产品流
2. 还没有设备级稳定花名身份
3. 当前身份更像“技术会话”，不是“产品里持续存在的人”
4. 还没有把未来多壳与未来注册的边界提前钉死

一句话：

**现在已有的是“群聊主链基础”，缺的是“最小产品形态”。**

## 3. 设计原则

### 3.1 船长与二副仍然不变

1. `domain + application` 仍是船长
2. `socketioxide` 仍是实时主通道二副
3. Web / iOS / Android / CLI 都只是壳

禁止：

1. Web 页面流程倒灌进核心
2. `socketioxide` 裁决身份真相、成员真相或消息真相
3. 任何壳层定义“谁是谁”

### 3.2 多壳共核先于 Web 顺手

这次虽然先做 Web，但从设计上必须先站在多壳角度：

1. 稳定的是 command / query / event / snapshot / error code
2. 不稳定的是某个壳的页面布局、导航、控件形态、本地存储实现

所以必须禁止：

1. 把“房间页”写成核心对象
2. 把 `localStorage` 写成业务真相
3. 把 Web 路由结构写进共享契约

### 3.3 MVP 也必须是严肃系统，不是假世界

本设计强制：

1. 先落权威事实，再广播
2. 发送者与接收者统一事件流
3. 失败显式暴露
4. 不用 ACK 冒充消息成立
5. 不用连接态冒充身份真相
6. 不用页面成功态冒充业务成功

### 3.4 不做浏览器指纹系统

这次要做的是设备级稳定身份，不是设备指纹识别。

所以禁止：

1. 收集 UA / 时区 / 字体 / 硬件特征拼设备画像
2. 用浏览器指纹替代本地持久化随机入口凭证
3. 让设备识别逻辑变成未来隐私负担

## 4. 核心真相模型

### 4.1 四层身份模型

本设计从第一天就强制区分 4 个概念。

#### 4.1.1 设备入口凭证

例如：

- `device_anonymous_token`

职责：

1. 作为某个壳本地持久化的“再次进入系统入口”
2. 由壳层保存
3. 传给后端做匿名身份恢复

边界：

1. 它不是最终用户身份
2. 它不是展示名
3. 它不是房间成员关系
4. 它未来可以与正式认证入口并存

#### 4.1.2 匿名内部身份

例如：

- `anonymous_identity_id`

职责：

1. 这是系统真正认“这个人”的内部锚点
2. 同一设备入口凭证默认映射到同一个匿名内部身份
3. 未来注册系统要链接到它，而不是替代它

边界：

1. 内部身份不可等于展示花名
2. 内部身份不可等于设备入口 token
3. 内部身份必须后端权威持有

#### 4.1.3 展示花名身份

例如：

- `display_alias`

职责：

1. 当前对房间中其他成员展示的名字
2. 现在系统自动分配
3. 未来允许手动修改

边界：

1. 花名不是主键
2. 花名不是身份真相
3. 花名修改不能影响聊天历史归属

#### 4.1.4 未来正式身份

例如：

- `account_id`
- `email`
- `oauth_subject`

职责：

1. 为现有匿名内部身份增加正式认证入口
2. 让用户跨设备、跨壳稳定登录

边界：

1. 未来注册不是造第二个人
2. 未来注册是给同一个内部身份追加新的认证入口

### 4.2 当前 MVP 要固定的规则

1. 同一设备在不同房间共用同一个花名
2. 当前花名由系统自动分配
3. 当前不可手动修改
4. 未来允许修改，但必须是“改展示名”，不是“改身份”

### 4.3 真相归属矩阵

| 内容 | 唯一允许归属 |
|---|---|
| 设备入口凭证本地保存 | 壳层 |
| 设备入口与匿名内部身份绑定关系 | 后端权威 |
| 当前展示花名 | 后端权威 |
| 房间成员关系 | application + repository |
| 消息成立 | usecase + repository 事务 |
| `event_position` | repository 权威锚点 |
| 页面输入框内容/滚动位置 | Web shell |
| 连接是否在线 | realtime runtime |

禁止：

1. 前端自作主张生成永久花名真相
2. 前端把 `device_anonymous_token` 当最终身份
3. 房间 runtime 状态冒充成员真相

## 5. 产品主流程

### 5.1 首页 / 进房页主流程

Web 首页必须极简，只保留一个主流程：

1. 页面初始化
2. 检查本地是否已有 `device_anonymous_token`
3. 如果没有，则生成一个新的随机 token 并本地持久化
4. 调用 `bootstrap_anonymous_identity`
5. 后端返回当前匿名内部身份与花名展示信息
6. 页面显示当前花名
7. 用户输入房间码
8. 调用 `join_or_create_room_by_code`
9. 成功后进入房间页

页面上不要先出现：

1. 欢迎介绍流
2. 资料页
3. 多步设置向导
4. 房间导航树

### 5.2 房间页 / 聊天区主流程

进入房间页后，主链必须是：

1. 拉房间快照
2. 建立 realtime 订阅
3. 显示当前消息流
4. 用户输入消息
5. 发出命令
6. 后端权威成立后回流 `room_event`
7. 消息区更新

### 5.3 页面状态分层

房间页必须分开 3 层状态：

#### 5.3.1 事实层

1. 当前花名
2. 当前房间
3. 已成立消息流
4. 当前最新 `event_position`

#### 5.3.2 本地体验层

1. 输入框内容
2. 待发送乐观态
3. 滚动位置
4. 正在重连提示

#### 5.3.3 错误与恢复层

1. 房间码非法
2. 订阅被拒
3. `need_snapshot_reload`
4. 系统错误

禁止：

1. 本地 pending 冒充消息成立
2. 页面已显示消息冒充后端已成立
3. connect 成功冒充身份有效

## 6. 跨壳稳定契约

这次设计必须先定义共享契约，而不是先定义页面流程。

### 6.1 最小命令 / 查询 / 事件

#### 6.1.1 `bootstrap_anonymous_identity`

输入：

```json
{
  "device_anonymous_token": "uuid"
}
```

输出：

```json
{
  "anonymous_identity_id": "a-xxxx",
  "display_alias": "暴躁的企鹅"
}
```

职责：

1. 设备匿名入口凭证首次建档或恢复
2. 自动分配或取回稳定花名

#### 6.1.2 `join_or_create_room_by_code`

输入：

```json
{
  "identity_id": "a-xxxx",
  "room_code": "ABCD1234"
}
```

输出：

```json
{
  "room_id": "r-xxxx",
  "latest_event_position": 0
}
```

职责：

1. 用稳定内部身份按房间码进房或建房
2. 返回房间快照锚点

#### 6.1.3 `load_room_snapshot`

职责：

1. 拉取当前房间基线
2. 建立进入聊天区的事实层

#### 6.1.4 `subscribe_room_stream`

职责：

1. 建立实时事件流
2. 从 `event_position` 续接

#### 6.1.5 `send_text_message`

职责：

1. 提交发消息意图
2. 等待后端权威成立并广播统一 `room_event`

### 6.2 共享快照与事件

共享层必须稳定的返回面：

1. `anonymous_identity_snapshot`
2. `room_snapshot`
3. `room_events_snapshot`
4. `room_event`
5. `control_result`
6. `error_code`

### 6.3 为什么必须这样定义

因为未来：

1. Web 可以继续走页面导航
2. iOS 可以做原生房间页
3. Android 可以做 Compose 页面
4. CLI 可以走：
   - 输入房间码
   - 订阅事件流
   - 发送文本命令

但它们都不该要求后端再为各壳长出一套专用业务协议。

## 7. Realtime 主链要求

### 7.1 这次 MVP 的实时主链必须是什么

1. `bootstrap_anonymous_identity`
2. `join_or_create_room_by_code`
3. `load_room_snapshot`
4. `subscribe_room_stream`
5. `send_text_message`
6. `room_event`
7. `event_position` 续接
8. `need_snapshot_reload`

任何壳都只是消费这条主链。

### 7.2 连接准入

Web 第一壳可以继续通过当前 realtime 会话机制接入，但要逐步收口成：

1. 壳层先通过冷路径拿到当前匿名内部身份
2. realtime 连接握手携带的是稳定内部身份会话锚点
3. connect middleware 校验该锚点合法

注意：

1. Web 当前怎么持有 token 是壳层实现细节
2. realtime 层最终只认后端发放的稳定身份锚点

### 7.3 订阅主链

1. 客户端携带稳定身份建立 realtime 连接
2. 输入房间码进房成功后，房间页先拉快照
3. 再调用 `subscribe_room_stream`
4. 用例层校验成员资格
5. `join(room)`
6. 发 `control_result.subscribed`
7. 回补 `room_events`

### 7.4 发送主链

1. 壳层发送文本命令
2. 后端先做成员资格与文本不变量校验
3. 事务提交：
   - 写 `room_events`
   - 写 `messages`
   - 推进 `latest_event_position`
4. 统一广播 `room_event`
5. 发送者和接收者都收同一份事件

### 7.5 恢复主链

1. 断线后按 `event_position` 重订阅
2. 若能补齐，则回补缺失事件
3. 若闭合不了，则 `need_snapshot_reload`
4. 壳层退回快照再恢复主链

禁止：

1. 第二套恢复锚点
2. ACK 冒充恢复成功
3. 页面偷偷自愈而后端并不知情

---

## 8. 后端也必须“完美”的最低标准

### 8.1 身份真相单一

1. 谁是谁，由后端权威维护
2. 花名只是展示面
3. 设备入口凭证只是进入系统的钥匙

### 8.2 成员真相单一

1. 订阅资格由 usecase 裁决
2. 发言资格由 usecase + domain 裁决
3. room runtime 不得冒充成员真相

### 8.3 消息成立语义单一

1. 只有领域事件才代表消息成立
2. `control_result`
3. `ack`
4. 本地 pending

这些都不是消息成立。

### 8.4 同步锚点单一

1. 只认 `event_position`
2. 不允许第二套“前端推测位置”
3. 不允许第二套“快速同步 token”

### 8.5 失败语义明确

必须显式存在：

1. 非成员拒绝
2. 非法房间码拒绝
3. 非法 `from` 拒绝
4. `need_snapshot_reload`
5. 系统错误

不允许：

1. 静默失败
2. 假装成功
3. 偷偷吞错

### 9.2 房间页

2. 当前花名
3. 消息流

1. 还没实现的社交功能占位

### 9.3 UI 与核心边界

页面允许派生：

1. 花名展示样式
2. 房间页布局
3. 乐观态
4. 错误提示文案

页面不允许决定：

1. 身份真相
2. 成员真相
3. 消息成立
4. 同步是否成功

## 10. 数据与持久化模型要求

### 10.1 当前至少要准备的持久化关系

即使现在不完整落库，也必须按这个关系建模：

1. `device_anonymous_token -> anonymous_identity_id`
2. `anonymous_identity_id -> display_alias`
3. `anonymous_identity_id <-> room membership`
4. `room -> room_events -> messages`

### 10.2 为未来注册预留的关系

将来可以追加：

1. `anonymous_identity_id -> account_id`
2. `account_id -> auth credentials`

但不允许把匿名历史迁移成另一套人。

### 10.3 花名修改的准备

现在虽然不做“改花名”，但必须提前保证：

1. 花名不是消息主键的一部分
2. 消息显示允许拿当前或事件时刻的展示名策略演进
3. 改花名不破坏历史归属

## 12. 测试与验收

### 12.1 MVP 必须通过的产品验收

1. 第一次打开页面，会自动获得一个花名
2. 刷新页面后，花名不变
3. 进入不同房间，花名不变
4. 输入合规房间码能进入房间页
5. 房间页能看到消息流
6. 发消息后自己和别人都能收到
7. 断线后能恢复
8. 非法状态有明确反馈

### 12.2 MVP 必须通过的主链验收

1. 身份恢复不会制造第二个人
2. 输入房间码进房不绕过成员真相
3. `room_event` 仍是唯一消息成立路径
4. `event_position` 仍是唯一同步锚点
5. `need_snapshot_reload` 仍能兜底

### 12.3 明确视为失败的情况

1. 同一设备刷新后花名变了
2. 不同房间里同一设备花名不一致
3. 前端本地花名与后端花名不一致
4. 输入房间码后只是在 UI 上切页，但房间主链没真正建立
5. 页面能显示消息，但后端并没有权威事件成立
6. 为了先跑通，临时把身份真相放到前端

---

## 13. 防漂移检查点

### 13.1 做身份 bootstrap 时检查

1. 壳层只保存设备入口凭证，不保存最终身份真相
2. 花名由后端分配或恢复
3. 同一 token 不会重复创建不同匿名内部身份

### 13.2 做 Web 进房页时检查

1. Web 页面只消费共享契约
2. 输入房间码是主动作
3. 没有被额外设置流拖慢

### 13.3 做房间页时检查

1. 房间页事实层来自快照 + realtime
2. 乐观态不冒充真相
3. 断线恢复仍走现有主链

### 13.4 为未来注册预留时检查

1. 内部身份与展示花名已分开
2. 内部身份与设备入口已分开
3. 不需要未来再做“匿名用户迁移到正式用户”的大搬家

---

## 14. 实施顺序

1. 先补设备级匿名身份 bootstrap 设计与契约
2. 再补 Web 壳的本地设备入口持久化
3. 再把首页收成进房页
4. 再把房间页收成最小聊天区
5. 最后补对应真实链路与产品测试

这条顺序不能倒：

1. 不先做花哨 UI
2. 不先做资料页
3. 不先做注册系统
4. 不先做多节点

---

## 15. 结论

这个 MVP 真正要做的是：

1. 让用户第一次感受到 `koko` 是一个真的群聊产品
2. 让“人”的连续性先成立，但不被注册系统拖住
3. 让 Web 先跑通，但不把未来 iOS / Android / CLI 堵死
4. 让后端主链继续保持严肃、单一真相和可恢复

所以最准确的表述是：

**`koko` 接下来要实现的是：多壳共核、设备级稳定花名身份、输入房间码即可进房开聊的最小群聊 MVP。**
