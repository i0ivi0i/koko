## 0. 总裁决

**`koko` 需要大量自动化测试，但不需要巨型测试文件、测试支架总管、端到端倒金字塔，也不需要用覆盖率和文件数量冒充 TDD。**

本项目是公网万人实时图文视频群聊，风险比普通 CRUD 高得多。测试多本身不是坏事；坏的是测试失去层级、职责、速度和可定位性。以后判断测试是否“优雅现代”，只看这四件事：

1. 是否先按 RED / GREEN / REFACTOR 小步推进。
2. 是否保持金字塔：大量小而快的单元 / 领域测试，适量集成 / 契约测试，少量真实浏览器烟测。
3. 是否让失败能直接定位到唯一 owner，而不是把一个断言失败扩散成几十个文件一起红。
4. 是否让测试代码本身也服从 DDD、六边形和简洁度，不长出第二套业务真相。

当前测试规模不是立刻判死刑，但已经进入治理区：

| 指标 | 当前值 | 判定 |
| --- | ---: | --- |
| 生产源文件 | 197 | 正常 |
| 生产代码行 | 49,301 | 正常偏大 |
| 测试文件 | 151 | 可接受 |
| 测试代码行 | 62,565 | 偏重但可解释 |
| 测试 / 生产行数比 | 1.27 | 可接受但需要分层 |
| 超 500 行测试文件 | 41 | 需要治理 |
| 超 1000 行测试文件 | 15 | 必须拆分或登记理由 |
| 最大测试文件 | 2,655 行 | 不符合长期优雅标准 |

因此本文裁决：

1. **不做“删测试减数量”的短视清理。**
2. **要做“测试金字塔、测试 owner、测试文件预算、测试支架瘦身、真实浏览器烟测少而准”的长期治理。**
3. **新增功能和修 bug 仍必须 TDD；重构测试本身也必须先 characterization，再拆分，再验证等价。**

## 1. 官方资料进入 `koko` 后的可执行含义

### 1.1 TDD 不是一次写一堆测试

Agile Alliance 对 TDD 的核心流程是：写一个描述行为的测试、确认失败、写刚好通过的实现、重构、重复。它同时把“测试一次写太多”“测试过大过粗”“测试套件维护差导致太慢”列为常见坑。

落到 `koko`：

1. 每次语义改动先写一个最小 RED。
2. RED 必须失败在预期原因上，不能只是编译错、路径错、fixture 坏。
3. GREEN 只写让这个 RED 通过的最小实现。
4. REFACTOR 才允许抽 helper、拆文件、改命名。
5. 一个测试名里如果出现“并且 / and / 同时覆盖多个无关行为”，默认拆成多个测试。

### 1.2 Rust 测试必须分清 unit 与 integration

Rust 官方把测试分成两类：单元测试关注一个模块的隔离行为，集成测试站在库外只使用公开 API。Cargo 官方还说明，`tests` 目录里的每个顶层测试文件会作为单独 crate 编译；如果集成测试很多，可以把一个顶层集成目标拆成多个模块以减少编译和运行成本。

落到 `koko`：

1. 领域不变量、纯 reducer、错误语义优先放在 `src/**` 内的 `#[cfg(test)] mod tests` 或同模块子测试里。
2. `tests/*.rs` 顶层文件只保留跨模块、跨 adapter、数据库、HTTP、实时、迁移、契约级验证。
3. `tests/协作分发测试.rs` 这类顶层目标可以继续作为“集成测试 crate owner”，但内部必须拆成 `tests/协作分发测试/*.rs` 这种业务子模块。
4. 共享测试 helper 放在 `tests/common` 或测试目标内部 `mod 支撑`，不能反向成为业务真相 owner。
5. 如果一个 Rust 集成测试文件超过 800 行，默认拆内部模块；超过 1200 行，必须拆或登记为临时债务。

### 1.3 Vitest 测试必须浅层组织、快反馈、单独 typecheck

Vitest 官方允许 `.test.ts` / `.spec.ts` 放在源码旁边或专门测试目录；`describe` 可组织测试，但嵌套要浅；Vitest 执行 TypeScript 很快，但不会在普通测试执行时完整 typecheck，类型检查要另跑 `tsc` 或 Vitest typecheck。

落到 `koko`：

1. `frontend/tests` 可以继续存在，但按业务 owner 分目录，不允许所有复杂交互塞回单个 `聊天壳测试.spec.ts`。
2. `describe` 最多两层：文件 owner 一层、行为分组一层；更深嵌套默认说明测试文件在做太多事。
3. 单个 `.spec.ts` 文件目标长度：
   - `0-400` 行：健康。
   - `401-800` 行：允许，但应观察。
   - `801-1000` 行：需要拆分计划或登记理由。
   - `>1000` 行：默认不合格。
   - `>2000` 行：必须拆，除非是明确生成矩阵且有生成源。
4. `pnpm --dir frontend test` 不能替代 `pnpm --dir frontend typecheck`；两者都是硬验收。
5. `test.only`、`describe.only`、长期 `test.skip`、无理由 `todo` 都不得进入提交。

### 1.4 Playwright 与 Testing Library 指向用户可见行为

Playwright 官方强调测用户可见行为、隔离测试状态、避免依赖实现细节；Testing Library 的原则是测试越接近真实使用方式，越能给信心。

落到 `koko`：

1. 真浏览器烟测只测用户和群友真实关心的路径：进房、发消息、发图、发视频、滚动、查看器、全屏、断线恢复、第二浏览器观看。
2. 真浏览器测试不能断言私有函数名、内部数组形状、CSS class 私货；必要的 `data-testid` 必须是稳定交互契约，不是实现细节泄漏。
3. 每个浏览器测试都必须隔离 localStorage、IndexedDB、service worker、cookies、房间状态和媒体文件来源。
4. 浏览器烟测数量要少，但每条都要有高价值。`1234b` 作为稳定烟测房间要保留，但不能让所有场景都依赖同一个旧状态。
5. CI 或本地失败时优先保留 trace / console / network / video 状态证据，而不是只说“页面没动”。

### 1.5 测试金字塔不是 70/20/10 的机械指标

Google Testing Blog 用测试金字塔表达稳定策略：底部大量小单元测试，中部适量集成测试，顶部少量端到端测试。它提到 70/20/10 只是初始估算，不是所有产品的死规则。

落到 `koko`：

1. 本项目不是普通页面，媒体 / WebTorrent / 实时链路必须保留比普通项目更强的集成和真实浏览器证据。
2. 即便如此，也不能倒金字塔。不能用大量端到端测试覆盖本该在 domain / application / contract 层验证的边界情况。
3. 边界条件、错误语义、状态机转换、权限裁决、媒体可用性裁决，优先在更低层测试。
4. 真浏览器只保留“低层无法证明”的真实体验：浏览器能力、滚动窗口、播放器、自动播放、service worker、WebTorrent 真实协作、跨上下文观看。

### 1.6 好测试要快、隔离、可重复、自校验、及时

Microsoft 的单元测试最佳实践强调好测试应快速、隔离、可重复、自校验、及时，且测试名应表达被测对象、场景和期望行为；同时警告覆盖率数字不能直接证明质量。

落到 `koko`：

1. 单元测试失败后，维护者应能在 1 分钟内知道哪个 owner 的哪个行为坏了。
2. 测试名必须说业务行为，不写 `test1`、`works`、`should handle case` 这类空名。
3. Arrange / Act / Assert 必须清楚。复杂 fixture 构造必须命名表达业务意图。
4. 覆盖率只能做辅助指标；不准用高覆盖率替代金字塔、失败定位和真实浏览器证据。

## 2. `koko` 的测试金字塔定义

### 2.1 第 0 层：类型检查、格式和架构门禁

这层不是测试金字塔里的业务测试，但它是所有测试前的地基。

必须长期保留：

```powershell
cargo check
cargo clippy --all-targets -- -D warnings
pnpm --dir frontend typecheck
node scripts/check-frontend-architecture-fitness.mjs
pnpm --dir frontend check:browser-app-constitution
```

这层负责：

1. Rust 编译、借用、trait、生命周期、未使用项和 lint。
2. TypeScript 类型、未使用 import / 参数、模块边界。
3. DDD / 六边形 / 前端应用化边界。
4. 禁止 `test.only`、长期 `skip`、巨型测试文件、测试 helper god node 回流。

### 2.2 第 1 层：领域 / 纯函数 / 状态机单元测试

目标：最快、最多、失败最可定位。

应该覆盖：

1. 后端领域不变量：身份、房间、消息、媒体、恢复、权限、冷源生命周期。
2. 后端纯 reducer / enum 裁决：协作分发可用性、peer kind、seeder decision、错误语义。
3. 前端纯状态机 / reducer：时间线、视口、媒体预算、播放会话、查看器会话、恢复编排。
4. 纯地址 / 契约归一化函数：只接收字符串和值对象，不触碰 DOM / HTTP / DB。

要求：

1. 不访问数据库。
2. 不启动后端。
3. 不启动浏览器。
4. 不依赖真实时间；需要时间时注入 clock。
5. 不依赖随机；需要随机时注入 seed。
6. 不 mock 被测逻辑，只替换外部 IO。

### 2.3 第 2 层：应用 / 契约 / adapter 集成测试

目标：证明几个 owner 拼起来仍然成立。

应该覆盖：

1. Rust application usecase + repository fake。
2. Rust HTTP / realtime shell 对稳定契约的翻译。
3. SQLx 迁移、约束、索引和事务闭包。
4. 前端 runtime + fake transport。
5. 前后端共享契约的 JSON 形状、错误码、媒体 locator、room snapshot。
6. WebTorrent 协作分发运行时与本地 fake tracker / fake seeder 的边界。

要求：

1. 一个集成测试文件只证明一个业务 slice。
2. fixture 只能表达业务前置条件，不能藏断言。
3. fake 必须按端口命名，例如 `假媒体资产仓储`，不要叫 `mockManager`。
4. helper 不能跨越多个 bounded context 后仍叫 `common`。
5. 集成测试失败时，失败信息必须指向一个业务 owner，而不是“全链路失败”。

### 2.4 第 3 层：真实浏览器 / 多上下文 / 媒体烟测

目标：只验证低层无法证明的真实浏览器体验。

应该覆盖：

1. `1234b` 或隔离房间进房。
2. 发文本、发图片、发 MP4。
3. 第二浏览器群友滚动观看。
4. 自动播放 owner 切换。
5. 查看器打开 / 关闭 / 归位。
6. 移动端与桌面全屏差异。
7. service worker、IndexedDB、localStorage 恢复失败降级。
8. WebTorrent 主链真实 source、非 HTTP 第二真相。
9. console error / warning / network tailwave。

要求：

1. 数量少，价值高。
2. 每条烟测都必须生成可复查证据：trace、console、network、关键 DOM / video 状态。
3. 不把所有边界条件塞进浏览器烟测。
4. 失败后先把 bug 下沉成更低层 RED，再修低层，再保留一条浏览器回归证明。

## 3. 测试文件大小与组织硬规则

### 3.1 文件大小预算

测试文件从现在起也要有完成态预算。预算不是为了机械压缩，而是防止测试本身成为屎山。

| 测试类型 | 健康区 | 警戒区 | 强制治理 |
| --- | ---: | ---: | ---: |
| Rust 单元测试模块 | 0-300 行 | 301-500 行 | >500 行 |
| Rust 集成测试子模块 | 0-500 行 | 501-800 行 | >800 行 |
| Rust 顶层集成目标 | 0-800 行 | 801-1200 行 | >1200 行 |
| Vitest 单 owner spec | 0-400 行 | 401-800 行 | >800 行 |
| Vitest 复杂交互 spec | 0-700 行 | 701-1000 行 | >1000 行 |
| Playwright / 真浏览器烟测 | 0-500 行 | 501-800 行 | >800 行 |
| 测试支架 helper | 0-500 行 | 501-800 行 | >800 行 |

当前已经超过 1000 行的测试文件必须进入治理清单。治理方式只有三种：

1. 按业务 owner 拆分。
2. 抽出只表达业务前置条件的 fixture builder。
3. 删除重复、过时、实现细节锁死的断言。

禁止用下面方式绕过预算：

1. 把大文件改名成 `common`。
2. 把断言藏进 helper。
3. 把测试拆成多个无语义小文件。
4. 用 barrel re-export 让旧入口继续存在。
5. 删除有价值的覆盖来满足行数。

### 3.2 测试文件命名

文件名必须表达 owner 与行为，不表达工具或临时目的。

允许：

- `frontend/tests/房间消息窗/自动播owner切换测试.spec.ts`
- `frontend/tests/媒体查看器/全屏归位测试.spec.ts`
- `tests/协作分发测试/可用性裁决.rs`
- `tests/媒体上传测试/source_hash.rs`

禁止：

- `大测试.spec.ts`
- `临时测试.spec.ts`
- `新测试.spec.ts`
- `utils测试.spec.ts`
- `common2.rs`
- `misc.rs`

### 3.3 测试支架边界

测试支架只能降低重复，不能拥有业务真相。

允许支架做：

1. 创建假端口实现。
2. 构造最小业务输入。
3. 启动受控后端或 fake sidecar。
4. 封装重复的 Arrange。
5. 给断言失败提供更清楚的错误信息。

禁止支架做：

1. 自己裁决权限、成员、媒体成立性。
2. 自己推导生产契约应有字段。
3. 用 helper 名字掩盖多个 bounded context 混在一起。
4. 让测试只读 helper，看不出业务意图。
5. 让一个 helper 被几十个无关测试依赖，形成测试 god node。

当前 graphify 已显示这些测试节点连接过高：

1. `创建图片消息传输()`
2. `提取媒体上传授权头()`
3. `构造tus_hook请求体()`
4. `断言TusHook已接受()`
5. `写入tus测试文件()`

这些不一定错，但必须进入测试支架审查。审查目标不是删除，而是确认它们是否仍是薄 fixture，还是已经变成隐藏业务模型。

## 4. 分层归位规则

### 4.1 Rust 后端

Rust 测试应按真实架构分层：

1. `src/**` 内 `#[cfg(test)]`：领域不变量、纯函数、强类型状态裁决。
2. `tests/领域测试.rs`：只测跨领域公开语义，不测 HTTP / DB。
3. `tests/用例测试.rs`：application 用例，使用 fake repo / fake port。
4. `tests/消息主链测试.rs`、`tests/房间接口测试.rs`：HTTP / realtime 合约和用例串联。
5. `tests/启动与迁移测试.rs`：数据库迁移、配置、启动生命周期。
6. `tests/协作分发测试.rs` + 子模块：媒体分发集成 slice。
7. `tests/架构边界守卫.rs`、`tests/媒体测试边界守卫.rs`：架构规则，不夹业务 happy path。

硬规则：

1. domain 测试不 import Axum / SQLx / socketioxide。
2. application 测试不启动真实 HTTP。
3. adapter 测试可以碰外部协议，但不能重新裁决业务。
4. 迁移测试必须真实跑数据库迁移，不用源码 grep 代替。
5. 架构守卫只能检测边界，不应变成业务逻辑测试合集。

### 4.2 TypeScript 前端

前端测试应按真实 owner 分层：

1. `frontend/tests/时间线/**`：时间线领域、视口、滚动窗口。
2. `frontend/tests/房间消息窗/**`：Lit 壳层、可见交互、媒体卡片表面。
3. `frontend/tests/媒体/**` 或现有 `媒体*.spec.ts`：媒体发布、播放、查看器、协作分发。
4. `frontend/tests/聊天应用内核/**`：应用运行时组合，不直接测 DOM 细节。
5. `frontend/tests/common/**`：只放 fixture builder 和 fake port，不放跨 owner 剧本。
6. `frontend/tests/端到端测试.spec.ts`：保留少量集成剧本，不扩成大杂烩。

硬规则：

1. 纯状态机测试不依赖 DOM。
2. Lit 组件测试只验证稳定交互表面，不读私有字段。
3. WebTorrent 运行时测试不得真的访问公网 tracker；真实协作放浏览器烟测。
4. 媒体查看器测试必须覆盖用户行为：打开、切换、关闭、归位、全屏，不绑内部函数名。
5. 平台能力测试必须隔离 localStorage、IndexedDB、BroadcastChannel、service worker。

### 4.3 真实浏览器烟测

真实浏览器烟测必须另成层级，不混进 Vitest happy-dom。

建议目录：

```text
e2e/
  房间入场.spec.ts
  文本图片消息.spec.ts
  视频自动播放双浏览器.spec.ts
  媒体查看器全屏.spec.ts
  恢复与离线降级.spec.ts
```

保留原则：

1. 只测最关键的用户价值链。
2. 一条烟测最多覆盖一个完整用户故事。
3. 不在浏览器烟测里穷举所有边界条件。
4. 每条烟测失败后必须能落回更低层测试定位。

## 5. TDD 执行纪律

### 5.1 新功能

必须按这个顺序：

1. 重新读目标 owner、调用链、相关 contract、现有测试。
2. 选择最低可证明层级。
3. 写一个 RED。
4. 运行并确认失败原因正确。
5. 写最小实现。
6. 跑目标测试转绿。
7. 跑同层相关测试。
8. REFACTOR 清理重复和命名。
9. 跑完整验证链。

### 5.2 bug 修复

必须按这个顺序：

1. 复现 bug 或找到能稳定表达 bug 的 characterization。
2. 把复现下沉到最低层 RED。
3. 如果 bug 只在真实浏览器出现，先保留浏览器证据，再补低层 RED。
4. 修真正 owner，不打表面 guard。
5. 保留一条能防回归的最小测试。
6. 删除临时日志、临时 fixture、临时 debug 入口。

### 5.3 重构测试本身

测试重构不是随便挪文件。必须先证明行为等价：

1. 记录当前目标测试命令和通过结果。
2. 如果拆大文件，先只搬迁不改语义。
3. 每搬一个业务分组就跑对应测试。
4. 支架抽取必须减少重复或提高意图，不得隐藏断言。
5. 拆完跑完整同层套件。
6. 删除旧入口，禁止旧新双活。

## 7. 长期门禁

### 7.1 测试文件预算门禁

新增脚本或扩展现有架构体检：

```powershell
node scripts/check-test-architecture-fitness.mjs
```

脚本必须检查：

1. 测试文件行数预算。
2. `test.only` / `describe.only` / `it.only` 禁止。
3. 长期 `skip` 必须带 `TODO(owner, date, reason)`。
4. `common` helper 不得超过预算。
5. 测试支架不得 import 生产 shell 私有路径来绕 contract。
6. 前端测试必须被 `pnpm --dir frontend typecheck` 覆盖。
7. Rust 顶层集成测试数量和大文件清单必须输出。

### 7.2 测试金字塔报告

新增报告：

```text
docs/superpowers/reports/测试金字塔健康报告.md
```

报告必须记录：

1. 单元 / 集成 / 浏览器烟测的数量和耗时。
2. 最大测试文件排行。
3. 测试 helper god node。
4. 新增 / 删除 / 拆分测试文件。
5. 本轮是否新增真实浏览器证据。
6. 本轮是否有 RED -> GREEN 证据。

### 7.3 CI 分层命令

本地和 CI 最终应分层执行：

```powershell
cargo check
cargo clippy --all-targets -- -D warnings
cargo test
pnpm --dir frontend typecheck
pnpm --dir frontend test
pnpm --dir frontend build
node scripts/check-frontend-architecture-fitness.mjs
node scripts/check-test-architecture-fitness.mjs
```

真实浏览器层：

```powershell
pnpm --dir e2e test
```

如果暂时没有 `e2e` 包，第一轮计划必须先建立最小 Playwright 项目，而不是继续把真实浏览器体验塞进 Vitest。

## 8. 禁止事项

1. 禁止为了减少文件数，把多个 owner 合并成巨型 spec。
2. 禁止为了减少行数，删除有价值的边界测试。
3. 禁止为了让测试快，跳过 typecheck、clippy、架构门禁。
4. 禁止把 happy-dom 测试当作真实浏览器烟测。
5. 禁止把 Playwright 烟测当作所有边界条件的垃圾桶。
6. 禁止测试 helper 裁决业务真相。
7. 禁止新增 `common/helpers/utils/misc` 这类无 owner 文件。
8. 禁止长期 `skip`、`todo`、`only`。
9. 禁止用覆盖率数字替代失败定位和业务价值。
10. 禁止测试绑定私有实现细节，除非该测试就是架构守卫。
11. 禁止重构测试后留下旧入口和新入口双活。
12. 禁止没有新鲜验证就宣称“测试体系已满分”。
