## 0. 为什么还要再补一份“总 spec”

现在已经有了一份阶段一 spec：  
`docs/superpowers/specs/2026-04-23-万人实时群聊去屎山收口与实时主链守正.md`

它写得足够细，已经能直接指导阶段一 implementation plan。  
但它解决的是**阶段一怎么做**，不是**整个万人实时群聊去屎山路线怎么分阶段推进**。

如果只有阶段一 spec，没有总 spec，后面会立刻出现 3 种漂移：

1. 有人会把阶段一 spec 误读成“这就是整个总路线”，后续阶段失焦；
2. 有人会在阶段一执行时顺手扩张范围，把原本应该放在阶段二、阶段三的事偷偷带进去；
3. 有人会在后续继续写 plan 时各自理解一套“第二阶段是什么、第三阶段是什么”，最后总路线重新变模糊。

所以这份总 spec 的存在，不是为了重复阶段一文档，而是为了把下面 4 件事钉死：

1. **为什么必须分阶段，而不能一把梭大重构；**
2. **默认应该拆成几阶段；**
3. **每阶段各自解决什么，不解决什么；**
4. **总 spec 与各阶段 child spec 各自负责什么。**

## 1. 这次必须采用“总 spec + child spec”双层结构

先把一句话写死：

**以后这条万人实时群聊去屎山路线，必须按“一个总 spec 管阶段关系 + 每个阶段各有 child spec 管执行细则”的双层结构推进；禁止再把总纲、阶段范围、执行细则、媒体语义和聊天主链收口混写在同一份文档里。**

这句话展开后，就是下面这些裁决：

1. **总 spec 只负责总路线、阶段关系、跨阶段红线与进入条件。**
2. **阶段 spec 只负责本阶段的详细范围、owner、验证门禁和实现红线。**
3. **禁止拿总 spec 直接替代阶段 spec 执行。**
4. **禁止把阶段 spec 偷偷写成总纲。**
5. **禁止因为已有阶段一 spec，就假装后续阶段不需要明确路线。**

为什么必须这样分层，而不是继续把东西写在一份文档里？

因为这类去屎山工程最容易发生的 bug，不是“不会写文档”，而是：

1. 文档粒度混乱；
2. 总纲和执行细则混在一起；
3. 结果阶段边界越来越糊；
4. 最后执行时每个人都按自己理解扩张范围。

所以这里必须明确：

**总 spec 的任务，是防止路线漂移；阶段 spec 的任务，是防止实现漂移。**

## 2. 为什么不能直接一把做完

这条路线必须分阶段，不是因为“喜欢慢一点”，而是因为系统现实决定了它不能粗暴推倒。

### 2.1 当前系统不是“核心全错”，而是“外围持续长胖”

目前已经确认的事实是：

1. 聊天实时核心仍然是 `socketioxide + socket.io-client`；
2. 危险主要来自恢复链、编排热点、transport 胶水、壳层和部分共用热点持续长胖；
3. 媒体协作分发这边也已经有自己的高风险真相和独立 spec；
4. 浏览器应用化 owner 链已经有明文施工准绳，不能再随便发明新 runtime 真相。

这意味着：

**当前系统不是一块整板全烂，而是多个高风险热点在不同链路上以不同方式积累债务。**

这种情况下如果一把大重构，风险会同时叠加在：

1. 聊天实时主链；
2. 恢复链；
3. transport；
4. 前端浏览器应用化运行时；
5. 媒体协作分发主链；
6. 跨端 contract 消费边界。

这不是“更快”，这是把所有真相一起推到同一个手术台上。

### 2.2 分阶段不是保守，而是为了维持真相 owner

这次分阶段的根本目的，是让每一阶段只处理一组最相关、最应该一起收口的热点。

如果阶段边界不明确，最容易发生的事情就是：

1. 阶段一碰到 transport，顺手把媒体也带进去；
2. 阶段二碰到前端 runtime，顺手把 contract 也重写；
3. 阶段三碰到 media owner 链，顺手把聊天 realtime 恢复语义改掉。

所以这里必须写死：

**分阶段不是为了拖延，而是为了让每一轮改动只在一个可验证的真相边界内发生。**

## 3. 这条路线默认按 3 个阶段设计，但允许在明确复核后收缩为 2 个阶段

你之前说的是“一个总 spec 包含 2 到 3 个渐进阶段”。  
这句话现在正式落成下面这条裁决：

**默认按 3 个阶段设计整条路线；只有在前一阶段完成并复核后，才允许基于新证据把后续两个阶段合法收缩为 2 个阶段。禁止在一开始就模糊地说‘反正后面看情况’，也禁止在执行过程中不写文档就偷偷合并阶段。**

### 3.1 为什么默认是 3 阶段，不是先写成 2 阶段

因为当前至少存在 3 组本质不同的热点：

1. **聊天 realtime 主链 + 恢复/编排热点**
2. **共享 transport / shell / runtime 协作热点**
3. **媒体浏览器应用化与协作分发热点**

这 3 组问题：

1. owner 不同；
2. 风险不同；
3. 施工准绳不同；
4. 失败方式也不同。

如果一开始就强行写成 2 阶段，最大的风险是把后两组问题粗暴捏在一起，结果阶段二变成新的“大杂烩阶段”。

所以总纲默认采用：

1. 阶段一：聊天主链守正
2. 阶段二：共享热点收口
3. 阶段三：媒体与浏览器应用化热点收口

### 3.2 什么情况下允许从 3 阶段收缩成 2 阶段

只有当阶段一结束后，重新审查代码与 graphify，发现下面这些条件同时成立，才允许讨论收缩：

1. 阶段二与阶段三剩余热点高度重合；
2. 合并后不会把聊天主链、媒体主链、浏览器应用化 owner 三套真相重新混成一锅；
3. 有新的 child spec 明文重写阶段边界；
4. 主人明确批准。

这里还必须把“怎么收缩”写实，不允许留模糊口子：

1. **合法的 `3 -> 2` 只指一种情况：原计划的阶段二与阶段三合并成一个新的后续阶段。**
2. 合并后，必须落成**一份新的合并 child spec**，明确接管原阶段二、阶段三的范围；
3. 原来按三阶段写的阶段二、阶段三草案边界，必须在文档里显式退场或改写，不能口头说“反正差不多”；
4. **禁止把“仍保留两个 child spec，但大家心里把它当两阶段”冒充合法收缩。**
5. **禁止不改总 spec 就直接在 implementation plan 里把阶段二、阶段三揉成一锅。**

也就是说：

**合法收缩不是“说法变少一点”，而是把原后两阶段正式合并成一个新阶段，并重新写清 authoritative 边界。**

禁止下面这种假收缩：

1. “先做到一半再说，后面应该可以合在一起。”
2. “看起来都属于前端，就一起改吧。”
3. “反正 transport 和 media 离得近，一锅收掉更省事。”

这些都不是收缩路线，而是在制造新的范围漂移。

## 4. 三个阶段的正式定义

### 4.1 阶段一：聊天 realtime 主链 + 恢复/编排热点

阶段一已经有正式 child spec：

- [2026-04-23-万人实时群聊去屎山收口与实时主链守正.md](/E:/koko/docs/superpowers/specs/2026-04-23-万人实时群聊去屎山收口与实时主链守正.md)

阶段一只解决：

1. 聊天 realtime 主链继续守正；
2. 房间恢复链、补洞链、重连链的结构收口；
3. 与聊天主链直接相关的编排热点与低价值胶水减压；
4. 保证 `socketioxide + socket.io-client` 作为唯一聊天主链不被误伤。

阶段一明确不解决：

1. 媒体协作分发热点；
2. 浏览器应用化媒体 owner 链；
3. transport 全家桶全面重写；
4. 共享 shell / runtime / launcher 侧剩余热点总收口。

这里必须再单独写一条：

**禁止把阶段一做成“顺手把所有前端热点一起清掉”。**

阶段一的价值，是先把聊天命脉从持续长胖的外围热点里救出来。  
不是把整个系统一次性做成完美架构。

### 4.2 阶段二：共享 transport / shell / runtime 协作热点收口

阶段二默认负责解决阶段一之后仍然残留、且不宜继续挂在聊天主链上的那批**共享热点**。

典型会落在这里的问题包括：

1. `HttpRealtime传输` 一类跨聊天主链、恢复协作、其他运行时路径的高耦合节点；
2. 前端多个壳层之间共享但 owner 仍不清的 runtime / shell 协作；
3. 某些本来不该继续绑在聊天主链上的通用 transport 胶水；
4. 阶段一结束后仍然吸职责的共用热点文件与桥接模块；
5. `launcher / bootstrap / run-script / dev-runtime` 一类与全应用启动、壳层接线、通用运行时协作相关的剩余热点。

阶段二必须坚持下面这些硬边界：

1. **禁止把“共享 transport 收口”偷换成“重写 shared contract”。**
2. **禁止把“shared runtime 收口”偷换成“前端重养一套业务真相”。**
3. **禁止因为它是共用层，就顺手倒灌某个壳专属流程语义。**
4. **禁止把媒体独有主链语义提前挪进阶段二。**
5. **禁止把 canonical owner 已经属于媒体链的 runtime / hotspot 伪装成“shared runtime”提前在阶段二收掉。**

这里必须把阶段二到底接什么，再钉得更硬一点：

1. 凡是 **media-agnostic** 的 shared transport / shared shell / shared runtime / shared launcher 问题，默认归阶段二；
2. 凡是它的 canonical owner 主要服务整个应用、多个壳、多个链路，而不是只服务媒体主链，默认归阶段二；
3. 只要某个热点脱离媒体播放、查看器、时间线自动播放、全屏、swarm、locator 之后仍然成立，它大概率属于阶段二；
4. **只要某个热点的存在价值主要来自媒体播放或媒体协作分发 owner 链，它就不属于阶段二。**

为什么阶段二要单列出来？

因为阶段一的目标是保聊天命脉，不适合顺手处理所有 shared hotspot；  
但如果完全不单列，后面这些热点又会继续成为新屎山的温床。

### 4.3 阶段三：媒体浏览器应用化与协作分发热点收口

阶段三默认负责处理**媒体链上的高风险热点**，但它不能重新发明媒体真相，而是必须站在已存在的媒体 spec 之上推进。

这一阶段的 authoritative 前置边界已经由下面几份文档钉住：

- [2026-04-22-WebTorrent高速分发防止群友偷懒.md](/E:/koko/docs/superpowers/specs/2026-04-22-WebTorrent高速分发防止群友偷懒.md)
- [2026-04-23-WebTorrent群聊越活跃越强的极限协同分发.md](/E:/koko/docs/superpowers/specs/2026-04-23-WebTorrent群聊越活跃越强的极限协同分发.md)
- `学习/浏览器中的应用-前端应用化方案.md`
- `学习/整理笔记/浏览器内应用与前端应用化官方实践笔记.md`
- `学习/整理笔记/Web大视频秒开播放与P2P协同主链官方实践清单-2026.md`

阶段三只允许做：

1. 媒体浏览器应用化 owner 链的结构收口；
2. 媒体壳层 / runtime / 编排热点的去屎山；
3. 在不破坏既有 WebTorrent 主链裁决的前提下，收口媒体相关胶水和热点；
4. 接走一切 canonical owner 已经明确属于媒体播放、媒体查看器、时间线自动播放、全屏、locator、swarm、媒体恢复协作的 runtime / transport / shell 邻接热点。

阶段三禁止做：

1. **禁止重新发明第二媒体正式播放主链。**
2. **禁止为了去屎山回退服务器第二字节主链。**
3. **禁止把移动端、桌面端、不同浏览器重新拆成多套媒体真相。**
4. **禁止把浏览器应用化 owner 链重新打回 DOM 事件驱动拼贴。**

这里也必须和阶段二做反向切线，防止后面再混：

1. 凡是 canonical owner 属于媒体链的 runtime / hotspot，一律归阶段三；
2. 即便某个点表面上长得像 transport 或 runtime，只要它的存在意义主要服务媒体主链，它仍归阶段三；
3. **禁止把 media-adjacent runtime/transport 清理，借“看起来更通用”之名提前塞进阶段二。**
4. 只有在脱离媒体 owner 链之后仍成立的 media-agnostic shared 问题，才允许回到阶段二。

为什么它不能和阶段二直接写成同一件事？

因为媒体链不是普通共享 transport 问题，它已经有自己的主链裁决、失败态真话规则和 24 小时前后切换语义。  
把它和阶段二混写，会直接增加误伤概率。

## 5. 总 spec 与 child spec 的关系

这里必须再钉一次，防止后面文档层次重新乱掉。

### 5.1 总 spec 负责什么

总 spec 只负责：

1. 阶段为什么这样拆；
2. 阶段之间什么先做、什么后做；
3. 哪些事禁止跨阶段偷做；
4. 各 child spec 的 authoritative 关系。

### 5.2 child spec 负责什么

child spec 负责：

1. 本阶段的详细范围；
2. owner；
3. 文件 / 模块 planning baseline；
4. 实现红线；
5. 验证门禁；
6. 完成判定。

### 5.3 禁止两者互相替代

因此必须禁止：

1. 拿总 spec 直接写 implementation plan；
2. 拿阶段 spec 反向替代总纲；
3. 把总 spec 改成一份新的大而全执行细则；
4. 把 child spec 写成空泛口号。

---

## 6. 跨阶段共用红线

无论后面进入哪个阶段，都必须同时守住下面这些红线：

1. **禁止推倒现有成熟核心轮子再手搓第二套。**
2. **禁止前端长出平行业务真相。**
3. **禁止 adapter / shell 承载业务裁决。**
4. **禁止 `contract` 倒灌某壳专属语义。**
5. **禁止借清理之名保留新旧双活。**
6. **禁止只加文件、不删旧胶水。**
7. **禁止让阶段边界在执行时无文档扩张。**
8. **禁止为了省事，把浏览器应用化 owner、聊天主链 owner、媒体主链 owner 混写。**
9. **禁止把临时补丁、运维兜底、兼容旁路升格为长期真相。**

---

## 7. 总路线的进入与退出条件

### 7.1 进入下一阶段前必须满足什么

任何阶段进入下一阶段前，都必须满足：

1. 当前阶段 child spec 已存在并经 reviewer 复审通过；
2. 当前阶段 implementation plan 已写完；
3. 当前阶段验证门禁和完成判定已通过；
4. graphify 已重建并用于复核热点是否真实减压；
5. 主人明确批准进入下一阶段。

### 7.2 禁止什么情况下继续推进下一阶段

禁止在下面这些情况下继续推进：

1. 当前阶段还没真正收口，就靠感觉进入下一阶段；
2. 当前阶段 spec 没写清楚，先边做边想；
3. 当前阶段验证没过，只是“看起来问题不大”；
4. 当前阶段留下大量旧胶水和双活残骸；
5. 阶段边界已经漂移，但没有回写文档修正。

## 8. 这份总 spec 的最终硬裁决

以后在 `koko` 里，必须按下面这句话理解这条去屎山总路线：

**万人实时群聊去屎山不是一次性推倒工程，而是一条“总 spec 管路线、child spec 管阶段、每阶段只收一组最相关热点”的渐进式收口路线；默认按 3 个阶段设计，必要时经复核和批准可收缩为 2 个阶段；禁止任何人绕开总纲把范围偷偷扩张，也禁止把阶段一执行细则误当成全局总路线。**

从这句话自然推出全部实现边界：

1. 禁止只有阶段一 spec，没有总路线；
2. 禁止只有总路线，没有阶段 child spec；
3. 禁止把“2 到 3 个阶段”写成模糊口号，不落成具体阶段骨架；
4. 禁止在执行过程中无文档地合并阶段；
5. 禁止在阶段之间偷偷夹带额外大手术；
6. 禁止把后续媒体或共享热点顺手塞进阶段一；
7. 禁止为了“少写一份文档”而重新回到大而全 spec；
8. 禁止未来维护继续绕开这份总纲各起一套阶段理解。

后续只要继续推进万人实时群聊去屎山路线，就必须先从这份总 spec 进入，再下钻到对应 child spec，再写 implementation plan；凡是跳过其中任一层，或把三层边界重新混在一起的，都直接视为漂移，必须禁止。
