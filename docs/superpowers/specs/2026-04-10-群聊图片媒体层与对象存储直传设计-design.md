# 群聊图片媒体层与对象存储直传设计

日期：2026-04-10  
状态：设计已确认，待主人复核后进入 implementation plan  
范围：把当前“聊天主服务直接吃图片上传”的方案，升级为“媒体层独立负责图片上传与存储，聊天主服务只认媒体引用”的方案  
约束：前端纯 TypeScript、后端纯 Rust；开发环境当前为 Win11；未来部署目标为 Linux 公网服务器；系统目标是面向大规模实时群聊；继续坚持 DDD、Unix 哲学、模块化单体边界；不再手搓成熟上传轮子；不把图片字节上传继续塞进聊天主服务热路径

## 0. 一句话结论

这次不是“继续补图片上传 bug”，而是把系统升级成：

1. 一套独立的媒体层
2. 一套稳定的媒体引用契约
3. 一条“上传图片不等于消息成立”的清晰主链

核心裁决只有一句：

**聊天服务只裁决消息真相和访问真相，媒体服务只负责媒体字节、缩略图、存储与受控下载。**

当前推荐主路不是 `tusd`，而是：

**前端 `Uppy + @uppy/aws-s3`，开发期直传本地 `MinIO`，生产期可切 `MinIO / S3 / R2`，Rust 聊天主服务只做 `prepare / complete / 引用 / 鉴权`。**

---

## 1. 背景与问题复盘

### 1.1 当前现象

当前群聊图片发送已经暴露出明显问题：

1. 某些 iOS / Android / 移动浏览器长时间停留在“上传中”
2. 有的浏览器能发，有的浏览器不能发
3. 后端终端很多时候没有对应错误日志
4. 前端为了补洞，已经开始堆越来越多状态判断和兜底逻辑

### 1.2 根因判断

这不是单一的小 bug，而是边界设计本身不够稳：

1. 聊天主服务直接扛图片字节上传，热路径和冷路径混在一起
2. 前端壳层承担了过多上传过程判断，开始手搓上传状态机
3. 上传成功、媒体完成、消息成立，这 3 个真相没有彻底分开
4. 当前上传链太依赖浏览器和单条 HTTP 请求的稳定性
5. 未来目标是 Linux 公网服务器和万人实时群聊，这条路会越来越脆

### 1.3 为什么不能继续沿旧路补丁

继续沿“聊天主服务直接吃上传”这条路补，会越来越差：

1. 每兼容一个浏览器边角，就会再长一层壳层逻辑
2. 每多一个上传异常，就会再长一个本地状态或计时器
3. 图片字节上传继续挤占聊天主服务资源
4. 未来切对象存储、CDN、签名地址、媒体鉴权时，改动面会越来越大

这条路的本质问题不是“补丁不够多”，而是**职责放错地方了**。

## 2. 目标与非目标

### 2.1 当前目标

这轮设计只解决群聊图片发送的正确架构与稳定落地方向：

1. 发图主链不再继续手搓
2. 聊天服务不再直接吃图片字节
3. 图片发送流程升级为“媒体引用驱动”
4. 开发期可在 Win11 本地跑通
5. 生产期可平滑切到 Linux 公网服务器
6. 以后可接 `MinIO / S3 / R2`
7. 默认媒体访问受控，不走永久裸链

### 2.2 当前明确不做

1. 不在这轮里做视频、语音、通用文件
2. 不在这轮里做公开分享链接
3. 不在这轮里强依赖某一家云厂商
4. 不在这轮里把聊天主服务拆成微服务海
5. 不在这轮里硬抄 Matrix 协议或 Telegram 协议
6. 不在这轮里为了“纯 Rust”去手搓一个新的上传协议服务

### 2.3 当前不再推荐的方向

以下方向本设计明确判定为非主路：

1. 继续 `XHR multipart -> Rust 聊天主服务`
2. 为了上传兼容性继续在壳层堆更多手搓状态机
3. 现在就把项目强绑到 `tusd`
4. 现在就为了对象存储直传去引入 Node-only 体系

## 3. 设计原则

### 3.1 DDD 原则

- `domain` 只定义消息、媒体引用、可见性、不变量
- `application` 只编排 prepare、complete、send message
- `contract` 只定义稳定的媒体命令、消息命令、错误码、快照
- `adapter` 只实现对象存储、签名 URL、缩略图、HTTP 和数据库
- `shell` 只做选图、上传、发送、展示和本地暂态

### 3.2 Unix 哲学

每个部件只做一件事：

1. 上传轮子只解决浏览器上传
2. 对象存储只解决对象读写
3. 媒体层只解决媒体生命周期
4. 聊天服务只解决消息真相
5. 前端壳层只解决交互体验

### 3.3 成熟 IM 借鉴原则

本设计吸收成熟 IM 的共同智慧，但不照搬具体协议：

1. 消息和媒体必须分开
2. 消息里只引用媒体，不携带图片字节
3. 先申请媒体占位，再上传，再发消息
4. 图片默认鉴权，不发长期裸链
5. 缩略图、元数据、缓存都归媒体层

借鉴对象：

1. Telegram：受控文件引用、受控下载、媒体与消息分离
2. Matrix：先 create media，再 upload bytes，再 message 引用 media
3. Discord：附件和消息分开建模，附件链接受控和可过期

## 4. 方案比较与裁决

### 4.1 方案 A：继续让 Rust 聊天主服务直接吃上传

优点：

1. 眼前改动最少

缺点：

1. 上传兼容性继续压在聊天主服务和前端壳层
2. 热路径继续混入大文件上传
3. 很难优雅切对象存储、签名 URL、受控下载
4. 对未来公网规模不友好

裁决：

**阻断。**

### 4.2 方案 B：`Uppy + tus/tusd + 可替换存储`

优点：

1. 断点续传和弱网恢复很强
2. 生态成熟

缺点：

1. 要额外维护一个上传服务
2. 首版就引入 `tusd`，整体更重
3. 对你们当前“图片最多 10MB”的场景，不一定是最简洁主路
4. 多机扩容时锁和代理细节更复杂

裁决：

**可作为后续增强路线，但不是首版默认主路。**

### 4.3 方案 C：`Uppy + S3兼容直传 + Rust 媒体登记`

优点：

1. 架构更简洁
2. 聊天主服务不再扛图片字节
3. 本地开发可用 `MinIO`
4. 生产可切 `MinIO / S3 / R2`
5. 更符合“媒体层独立，聊天服务只管真相”
6. 对 `10MB` 图片上传足够合适

缺点：

1. 必须把 prepare / complete / serve 契约一次设计清楚
2. 前端和后端都要从“直接上传”迁到“媒体占位 + 引用”

裁决：

**推荐主路。**

## 5. 最终架构裁决

### 5.1 总体结构

系统收敛成 3 个角色：

1. **前端壳层**
   - 选图
   - 本地预览
   - 调用媒体 prepare
   - 使用成熟上传轮子直传对象存储
   - complete 媒体
   - 发送引用 `media_id` 的消息

2. **Rust 聊天主服务**
   - 校验当前用户/身份是否允许申请媒体
   - 分配 `media_id`
   - 校验 complete 合法性
   - 校验消息发送时 `media_id` 是否已完成
   - 裁决谁能看这个媒体
   - 通过受控接口或签名地址提供媒体访问

3. **对象存储**
   - 接收原图和缩略图对象
   - 保存原图和缩略图
   - 通过受控临时地址服务上传/下载

### 5.2 开发期与生产期部署形态

开发期：

1. Win11 本地继续跑前端和 Rust 主服务
2. 本地额外跑一个 S3 兼容对象存储，默认 `MinIO`

生产期：

1. Linux 公网服务器部署 Rust 聊天主服务
2. 对象存储可选：
   - 自建 `MinIO`
   - `AWS S3`
   - `Cloudflare R2`

### 5.3 为什么首版不把 `tusd` 作为默认主路

理由不是 `tusd` 不好，而是它对当前场景不是最简：

1. 你们首阶段只做 `10MB` 内群聊图片
2. 现在更缺的是“职责分清”，不是“必须先上 resumable server”
3. 对象存储直传更接近长期主路，也更少一个长期依赖
4. 真要补超大文件和更强弱网恢复，以后还能在同一媒体契约上平滑升级到 `tus`

## 6. 核心流程

### 6.1 发送图片主链

新的发送流程固定为：

1. 用户选图
2. 前端向 Rust 请求 `prepare media`
3. Rust 返回：
   - `media_id`
   - 上传目标信息
   - 上传所需临时凭证或签名
4. 前端通过成熟轮子直传原图到对象存储
5. 前端上传成功后调用 Rust `complete media`
6. Rust 验证对象存在、记录元数据、生成/登记缩略图、把媒体状态改成 `ready`
7. 前端发消息，只引用 `media_id`
8. Rust 在消息命令里校验 `media_id` 已 `ready`
9. 聊天主链生成权威消息事件

### 6.2 下载图片主链

1. 前端根据消息里的 `media_id` 请求图片内容
2. Rust 校验当前用户是否能看这条消息
3. 通过校验后：
   - 可以由 Rust 代理输出
   - 或返回短期受控下载地址
4. 前端加载原图或缩略图

### 6.3 为什么必须先 `prepare` 再上传

这样做的好处：

1. 先把“谁能发图”裁决清楚
2. 先拿到稳定 `media_id`
3. 上传阶段和消息阶段彻底分开
4. 未来不管换存储、换上传协议、换 CDN，消息契约都不改

## 7. 核心领域模型

### 7.1 Media

独立媒体对象，不是消息本身。

最小稳定字段：

1. `media_id`
2. `owner_identity_id`
3. `kind`
4. `mime_type`
5. `byte_size`
6. `width`
7. `height`
8. `original_object_key`
9. `thumbnail_object_key`
10. `status`
11. `created_at`
12. `completed_at`
13. `expires_at`

第一阶段 `kind` 只实现：

1. `image`

### 7.2 MessageMediaRef

消息和媒体之间的关系对象。

最小稳定字段：

1. `message_id`
2. `media_id`
3. `sort_order`
4. `display_role`

规则：

1. 消息只引用媒体，不内嵌媒体私货
2. 已发送消息的媒体引用是稳定事实

### 7.3 Media Status

平台层媒体状态最少保留：

1. `prepared`
2. `uploading`
3. `ready`
4. `failed`
5. `expired`

语义：

1. `prepared`：已拿到 `media_id`，但还没完成上传
2. `uploading`：壳层本地暂态，可不必长期持久化
3. `ready`：对象已存在且已完成登记，可被消息引用
4. `failed`：这次媒体准备或完成失败
5. `expired`：准备后长期未完成，已失效

## 8. 稳定契约面

### 8.1 `prepare media`

作用：

1. 校验当前身份是否允许在该上下文发图
2. 创建一条 `prepared` 媒体记录
3. 生成上传所需信息

最小输入：

1. `session_id`
2. `kind = image`
3. `filename`
4. `content_type`
5. `byte_size`

最小输出：

1. `media_id`
2. `upload_strategy`
3. `upload_target`
4. `required_headers`
5. `expires_at`

约束：

1. 首版默认上传策略是 `s3_compatible_presigned_put`
2. 契约层不暴露厂商私货语义到消息模型

### 8.2 `complete media`

作用：

1. 告诉 Rust：浏览器已上传完成，请登记这个媒体

最小输入：

1. `session_id`
2. `media_id`

最小输出：

1. `media_id`
2. `kind`
3. `mime_type`
4. `byte_size`
5. `width`
6. `height`
7. `status = ready`

约束：

1. 只有 owner 才能 complete
2. 只有对象存在且合法时才能转成 `ready`
3. Rust 必须在这里提取最终元数据，不信任前端上报

### 8.3 `send message with media_id`

作用：

1. 创建一条引用媒体的权威消息

最小输入：

1. `room_id`
2. `text`
3. `media_ids[]`

约束：

1. `text` 和 `media_ids[]` 不能同时为空
2. 每个 `media_id` 必须：
   - 存在
   - 属于当前发送者身份
   - 状态为 `ready`

### 8.4 `serve media`

作用：

1. 受控读取媒体原图和缩略图

约束：

1. 默认鉴权
2. 权限跟随消息可见性
3. 可以返回受控输出流，也可以返回短期签名下载地址
4. 不返回永久裸链

## 9. 图片处理与存储

### 9.1 首版处理链

首版图片处理责任仍然放在 Rust 媒体登记阶段：

1. 识别真实 MIME
2. 校验是否为图片
3. 读取宽高
4. 处理 EXIF 方向
5. 生成缩略图
6. 写入对象存储
7. 写入媒体元数据

### 9.2 为什么图片处理不放前端

因为前端不可信，也不稳定：

1. 浏览器可能压根读不准 MIME
2. 前端处理结果不可作为业务真相
3. 缩略图和原图最终键位必须以后端登记为准

### 9.3 为什么对象存储必须可替换

因为当前阶段和未来阶段差异很大：

1. 现在是 Win11 开发
2. 以后是 Linux 公网生产
3. 以后可能会换 `MinIO / S3 / R2`
4. 但这些都不该影响消息契约和前端交互主链

所以必须让“对象存储具体实现”停留在 adapter 层。

## 10. 安全与可见性

### 10.1 默认鉴权

首版默认裁决：

1. 图片不是公开资源
2. 只有有权看到消息的人，才有权看到图片

### 10.2 下载策略

下载不走长期固定 URL：

1. 可以由 Rust 做鉴权后代理下载
2. 也可以由 Rust 签发短期下载地址
3. 下载地址必须短期有效

### 10.3 为什么不能默认公开

因为这会把整个群聊可见性边界打穿：

1. 转发链接的人可能绕过群权限
2. 图片一旦成永久裸链，就很难收回
3. 未来做 CDN 也会被公开语义绑定

## 11. 失败、恢复与回收

### 11.1 上传失败

上传失败只代表媒体失败，不代表消息失败。

规则：

1. 前端显示上传失败
2. 不产生权威消息
3. 用户可以重试或重新选图

### 11.2 上传成功但消息未发送

规则：

1. 已 `ready` 的媒体短时间内可继续复用
2. 不强迫用户重传
3. 只要消息还没引用，这个媒体就仍是“未提交媒体”

### 11.3 过期回收

规则：

1. `prepared` 后长时间未完成的媒体进入 `expired`
2. 未被任何消息引用过的 `ready` 媒体可以按 TTL 清理
3. 已被消息引用过的媒体第一阶段不自动清理

### 11.4 为什么消息主链不能被媒体失败拖死

因为媒体和消息不是一回事：

1. 图片没传成，不应该污染房间事件流
2. 某张图片下载失败，也不应该影响文字消息和其他消息

## 12. 技术选型裁决

### 12.1 前端轮子

首版推荐：

1. `Uppy`
2. `@uppy/aws-s3`
3. 视需要逐步加入：
   - `@uppy/compressor`
   - `@uppy/golden-retriever`

不推荐：

1. 继续 `@uppy/xhr-upload` 直打聊天主服务上传接口

### 12.2 开发期对象存储

首版推荐：

1. 本地 `MinIO`

原因：

1. Win11 可跑
2. Linux 也可跑
3. S3 兼容
4. 开发期不用先买云桶

### 12.3 生产期对象存储

可替换候选：

1. `MinIO`
2. `AWS S3`
3. `Cloudflare R2`

### 12.4 为什么当前不把 `tusd` 作为默认主路

1. `tusd` 是成熟轮子，值得尊重
2. 但当前不是最简主路
3. 你们现在的图片体量不大
4. 当前更重要的是先把媒体边界做对
5. 真要补更强弱网恢复，以后仍可在稳定媒体契约上升级

## 13. 开发期与生产期差异治理

### 13.1 开发期默认形态

1. Win11 本地前端
2. Win11 本地 Rust 聊天主服务
3. Win11 本地 `MinIO`

### 13.2 生产期默认形态

1. Linux 公网 Rust 聊天主服务
2. Linux 自建 `MinIO` 或云对象存储
3. 反向代理和 TLS 在外层处理

### 13.3 必须守住的稳定点

以下内容开发期和生产期都不能变：

1. `media_id` 语义
2. `prepare / complete / serve` 契约
3. 消息引用 `media_id` 的方式
4. 图片默认鉴权
5. 聊天主服务不直接扛上传字节

## 14. 迁移策略

### 14.1 迁移原则

迁移必须分阶段，不准一把梭：

1. 先把媒体契约定义清楚
2. 再接对象存储直传
3. 再让消息改为引用 `media_id`
4. 最后再退掉旧上传路径

### 14.2 推荐迁移顺序

1. 新增媒体记录模型和 `prepare / complete / serve` 契约
2. 本地接通 `MinIO`
3. 前端接 `Uppy + @uppy/aws-s3`
4. 聊天主链改成发送 `media_id`
5. 图片展示改走受控媒体读取
6. 观察稳定后，再删除旧的主服务图片上传路径

### 14.3 明确禁止事项

迁移期间禁止：

1. 同时长期保留两套活的消息真相
2. 在壳层自己宣布图片消息已成立
3. 把对象存储桶名、签名私货塞进消息事件
4. 让前端直接决定媒体最终元数据
5. 让聊天主服务继续吃上传字节作为长期主路

---

## 15. 测试与验收原则

### 15.1 设计层验收

设计完成后，必须保证：

1. 聊天主服务不再负责图片字节上传
2. 消息和媒体彻底分开
3. 图片默认鉴权
4. 开发期不要求先买云桶
5. 未来切对象存储不改业务契约

### 15.2 实现层必须覆盖的测试面

以后进入实现时，至少要锁死：

1. `prepare media` 权限和参数校验
2. `complete media` 只有 owner 可完成
3. 未 `ready` 媒体不能发消息
4. 已 `ready` 但未引用媒体可过期
5. 已引用媒体不会被误清理
6. 图片读取必须过消息可见性校验
7. 前端上传成功不等于消息成立

### 15.3 第一阶段验收标准

1. Win11 本地可选图上传并发送图片消息
2. 发送流程不再走聊天主服务直接吃图片字节
3. 房间在线成员能实时收到带图片引用的权威消息
4. 断线恢复后图片消息仍可通过既有快照/增量链恢复
5. 切换到 Linux 生产部署时不需要改业务契约

---

## 16. 漂移防线

后续执行时，以下任何一条出现，都视为实现开始漂移：

1. 又在聊天主服务里新长一条直接吃图片字节的长期主路
2. 又在前端壳层手搓一套上传成功真相
3. 消息事件里开始夹带对象存储私货
4. 媒体访问变成永久裸链
5. 为了对象存储切换而修改消息契约
6. 为了“先跑起来”把 `media_id` 设计省掉
7. 为了“纯 Rust”重新手搓成熟上传轮子

### 16.1 最后裁决

这次设计的真正目的不是“换个上传库”，而是：

**把图片上传从聊天真相里剥离出去，让媒体层回归媒体，聊天主服务回归聊天。**

如果执行时还能守住这句话，系统就会越做越稳；守不住，后面只会继续补丁化。
