## 0. 这份 spec 不是在“再优化一个小手感”

这份 spec 要解决的，不是某一个按钮点击后有没有反应，也不是某一段 CSS 动画顺不顺眼。

它真正要收口的是一句话：

**在万人实时群聊的消息流里，视频必须像同一条连续会话一样存在。滑出屏幕只是中断，不是重开；滑回屏幕只是续播，不是重新开始；点当前自动播视频只是把当前这颗正式播放器升格到真全屏，不是重新造一套播放世界。**

如果这句话没有被写成硬规则，后续实现就很容易继续漂移成下面几种坏结果：

1. 时间轴上明明保存了 `currentTime`，画面却先回到开头 poster / 首帧，再跳回续播点。
2. 当前自动播视频点击后，虽然最后也进了全屏，但中途先冷开、先换壳、先重建 player，用户体感像“重播了一次”。
3. 消息流里为了“看起来丝滑”偷偷养第二颗 live `<video>` 或第二颗 player，最后把解码、滚动、调度、P2P 会话都拖乱。
4. 为了修视觉问题，反过来削弱 `WebTorrent` 主链、热会话复用、后台补齐和做种，最后变成“体验修好了，主链削弱了”。

这份 spec 的任务，就是把这些漂移全部提前写死为禁止项。

## 1. 当前代码已经存在的真相

后文的所有规则，**默认继承当前代码已经成立的真相**，不允许另起一套纸面规则。

### 1.1 自动播 owner 不是“谁先进入就播”

当前代码已经明确：

1. 同一时刻只允许一个视频成为自动播 owner。
2. 候选先要过最小可见阈值，当前实现是 `0.6`。
3. 如果同屏里有接近完整可见的视频，当前实现用 `0.98` 作为“完整可见优先”阈值。
4. 在进入竞争集合后，优先按“离视口中心最近”裁决。
5. 如果距离一样，再按可见比例更高者优先。
6. 如果当前 owner 仍在竞争集合里，优先保持粘性，不因为相邻视频稍微更近就立刻跳走。

证据：

- `frontend/媒体/消息视频自动播编排.ts`
- `frontend/tests/消息视频自动播编排测试.spec.ts`

这里的工程含义是：

1. **禁止** 重新发明另一套“谁该自动播”的裁决规则。
2. **禁止** 执行时把“离视口中心最近”偷换成“最先进入可见区”。
3. **禁止** 为了某个局部感觉“更灵敏”就破坏当前 owner 粘性，导致消息流轻微上下滑时自动播来回抖。

### 1.2 候选不是立即切 owner，而是先稳定

当前代码已经明确：

1. 候选观测先进入 `pending owner`。
2. 经过 `80ms` 稳定等待后，才提升为正式 `owner`。
3. 这个等待存在的目的，是吸收轻微滚动和观察器抖动，不是制造肉眼可见的空窗。

证据：

- `frontend/媒体/壳层/自动播协作.ts`

这里的工程含义是：

1. **禁止** 因为追求“更快切换”而删掉稳定等待，导致 owner 频繁抽动。
2. **禁止** 反过来把这个等待放大成用户能感知的延迟，导致视频进入可见区后长时间还在等。

### 1.3 单次空观测不会立刻释放 owner

当前代码已经明确：

1. `IntersectionObserver` 与虚拟列表重排可能会偶发一帧候选清空。
2. 当前实现不会因为一次空观测就立刻释放 owner。
3. 连续两次空观测才真正释放 owner。

证据：

- `frontend/媒体运行时.ts`
- `frontend/tests/媒体运行时测试.spec.ts`

这里的工程含义是：

1. **禁止** 单帧空观测就把时间线从 `<video>` 退回 poster。
2. **禁止** 因为一次虚拟列表重排就把 `currentTime`、播放结果和 visual continuity 一起清空。

### 1.4 时间线 owner 已经在承接同一颗 canonical player

当前代码已经明确：

1. 时间线会为当前 owner 暴露 canonical host。
2. `全局唯一播放器.ts` 会把同一颗 `Video.js v10` shell 挂到该宿主槽位。
3. 时间线不是给每条视频各养一颗正式 player。

证据：

- `frontend/房间消息窗.ts`
- `frontend/媒体/全局唯一播放器.ts`

这里的工程含义是：

1. **禁止** 把后续优化写成“让每条消息视频各自长期拥有一颗 live player”。
2. **禁止** 用“这样更好保画面”作为借口，把唯一播放器真相重新拆回多播放器真相。

### 1.5 查看器打开时，inline autoplay owner 会退场

当前代码已经明确：

1. 正式查看器打开后，inline autoplay owner 会立即退场。
2. 这是为了避免消息流自动播和正式欣赏态双活。
3. 但退场的是 inline owner，不是这条视频的时间轴真相。

证据：

- `frontend/媒体运行时.ts`
- `frontend/tests/媒体运行时测试.spec.ts`

这里的工程含义是：

1. **禁止** 同时让消息流自动播和真全屏欣赏持有两条正式播放会话。
2. **禁止** 把“自动播退场”误执行成“播放位置清零”。

### 1.6 时间线视频本来就不是带控件的小播放器

当前代码已经明确：

1. 时间线 `<video>` 是 `muted`。
2. 时间线 `<video>` 是 `playsinline`。
3. 时间线 `<video>` 没有 `controls`。
4. 时间线 `<video>` 禁用 `picture-in-picture`、`remote playback`、下载和原生全屏入口。

证据：

- `frontend/房间消息窗.ts`
- `frontend/tests/房间消息窗媒体查看器测试.spec.ts`

这里的工程含义是：

1. **禁止** 把消息流里的视频重新做成一个带进度条、暂停按钮、静音按钮的网页式小播放器。
2. **禁止** 把“视频能播”偷换成“消息流里就该长控制条”。

## 2. 最终硬裁决

后续实现、评审、测试都以这一节为最高裁决。凡是和这一节冲突的实现，默认视为失败。

### 2.1 单 owner 裁决

1. **禁止** 同一时刻让两条或更多消息视频同时成为自动播 owner。
2. **禁止** 为了“更热闹”或“更像短视频 feed”把消息流改成多视频同时自动播。
3. **禁止** 让 `activeVideoCount` 大于 `1`。
4. **禁止** 让 `autoplayOwnerCount` 大于 `1`。

### 2.2 单一正式播放器真相

1. **禁止** 在消息流、查看器、全屏之间并存两颗正式 `Video.js v10` player。
2. **禁止** 当前自动播 owner 走一套播放器真相，非当前视频再走另一套播放器真相。
3. **禁止** 时间线里偷偷保留第二颗 live `<video>` 作为“视觉兜底正式表面”。
4. **禁止** 为了保帧或保画面，再长一颗新的 overlay player。

一句话：

**消息流自动播、点击放大、真全屏欣赏、退出归位，必须共享同一颗 canonical `Video.js v10`。**

### 2.3 离屏中断不是自然重开

这条必须写死：

1. **禁止** 把“因为上下滑离屏而中断”解释成“自然播放到结尾”。
2. **禁止** 视频离屏后回到消息流时，从 `0` 重新开始。
3. **禁止** 只因为失去 owner、页面 hidden、查看器打开、生命周期降级，就把这条视频的续播资格清空。

这里要明确区分两类情况：

1. **离屏中断**
   - 原因：滚动离屏、owner 切换、查看器接管、hidden/background、生命周期降级
   - 行为：保存当前 `currentTime`
   - 结果：回到 owner 时从该 `currentTime` 继续

2. **自然循环**
   - 原因：视频真实播放到了结尾
   - 行为：允许 `loop`
   - 结果：从头开始下一轮播放

这两件事在体验上完全不同，**禁止混淆**。

### 2.4 回屏续播必须像同一条会话继续

1. **禁止** 回屏时先显示开头 poster / 首帧，再跳到续播点。
2. **禁止** 回屏时先触发一次新的“开播仪式”，再假装自己是续播。
3. **禁止** 时间轴在用户可见的情况下回到 `0` 再 seek。
4. **禁止** 用户感知到“这条视频像是重新打开了一次”。

用户该看到的只有两种结果：

1. 正确时间点的静止帧，然后继续播放。
2. 如果接管正在等待或元数据仍在稳定，短暂保持 guard / 静止状态，但**禁止**退回开头画面。

### 2.5 消息流永远无控件

1. **禁止** 消息流里的视频出现暂停按钮。
2. **禁止** 消息流里的视频出现进度条。
3. **禁止** 消息流里的视频出现音量按钮。
4. **禁止** 消息流里的视频出现全屏按钮。
5. **禁止** 把“群聊消息里的自动播视频”做成一个小型网页播放器。

消息流的合法形态只有：

1. 自动播的视频画面
2. 因离屏或失去 owner 保留下来的静止画面表达
3. 真正无源或失败时的兜底占位

控件只允许在真全屏欣赏态出现。

### 2.6 当前自动播视频点击后必须直达真全屏

1. **禁止** 点击当前自动播 owner 视频后，先新建第二颗 player，再进入全屏。
2. **禁止** 点击当前自动播 owner 视频后，先把当前会话打回 recovering，再冷开另一条播放链。
3. **禁止** 点击当前自动播 owner 视频后，用户先看到换壳、抽搐、黑一下、时间轴回跳，再进入全屏。
4. **禁止** 把“统一查看器入口”误执行成“用户体感必须绕远路”。

这里要分清两层：

1. 壳层可以保留统一的打开媒体入口。
2. 但产品结果必须是：**当前这颗 canonical player 直接升格到真全屏**。

也就是说：

1. 统一入口是内部编排事实。
2. 直达真全屏是用户体验裁决。
3. **禁止** 用前者掩盖后者失败。

### 2.7 非当前视频点击也只能迁移同一颗 player

1. **禁止** 点击非当前视频时，新开第二颗正式 player。
2. **禁止** 留下旧 owner 的活 player，再让新 viewer 再长一颗。
3. **禁止** 把当前视频和目标视频变成两条并存的正式播放会话。

允许的只有：

1. 同一颗 canonical player 切 attachment
2. 同一颗 canonical player 切 source
3. 同一颗 canonical player 切宿主槽位

### 2.8 不得为了体验修复削弱主链

1. **禁止** 为了修消息流体验，削弱 `WebTorrent` 主链。
2. **禁止** 因为自动播 owner 切换，而放弃热会话复用。
3. **禁止** 因为全屏接管，而降低后台补齐、做种、帮助任务恢复强度。
4. **禁止** 借体验优化之名，重新引入冷源正式播放旁路。

## 3. 为什么必须这样做

这里必须把前因后果写清楚，防止后续执行时又被“看起来也能跑”的替代方案带偏。

### 3.1 这是 IM，不是短视频 feed，也不是内容页

群聊消息流的核心不是“把视频当内容卡片展示得多完整”，而是“在持续滚动的会话流里，让视频像现场的一部分自然存在”。

这意味着：

1. 用户的主动作不是“打开一个视频页”，而是在消息流里持续在场。
2. 视频只是会话里的一段动态消息，不该反客为主长成网页式小播放器。
3. 视频的存在方式必须服从消息流连续性，而不是反过来打断消息流。

所以：

1. **禁止** 把时间线视频做成网页内容卡片。
2. **禁止** 为了视觉表达而伤害滚动连续性。
3. **禁止** 让用户频繁感知“我离开了消息流，又进入了另一个播放器页面”。

### 3.2 真问题是“视觉真相”和“播放真相”分裂

如果系统只保存了 `currentTime`，却没有保证“屏幕上看到的像素也仍然代表同一条会话”，就会出现这种典型坏体验：

1. 实际播放位置是 `00:18`
2. 用户滑走视频
3. 视频回到消息流时先露出 `00:00` 的 poster / 首帧
4. 然后再跳到 `00:18`

这时候系统可以嘴上说“我支持续播了”，但用户体感仍然是失败的。

所以：

1. **禁止** 只修播放位置真相，不修视觉连续性。
2. **禁止** 把 poster 当成续播画面。
3. **禁止** 把“最终还是跳回来了”当成可接受结果。

### 3.3 真全屏必须是升格，不是重开

当前自动播视频已经在消息流里成为正式 owner 时，用户点击它想看大，本质上是在表达一句非常明确的意图：

**“把现在这条正在看的会话放大给我。”**

这不是：

1. “请帮我重新找一条播放链”
2. “请帮我新开一个播放器”
3. “请帮我从头重新组织一次播放表面”

所以：

1. **禁止** 把当前 owner 点击理解成重新打开新世界。
2. **禁止** 让用户手势推动的是“新建 player”，而不是“升格当前 player”。

### 3.4 多 live 视频在万人群聊里本来就是错方向

如果消息流里允许多个 live `<video>` 或多个正式 player 同时解码，看起来好像更容易“保画面”，但真实代价是：

1. 滚动线程压力更大
2. 解码和合成预算更高
3. 虚拟列表更难稳定
4. observer / owner / surface 的时序更容易漂移
5. `WebTorrent` 热会话与 UI 表面更容易脱钩

所以：

1. **禁止** 为了局部视觉问题，把整体架构推回多实例方向。
2. **禁止** 在“丝滑”和“多人同时 live 解码”之间幻想两者都要。

## 4. 自动播状态机与时间轴真相

这一节的重点是：把自动播、离屏、回屏、查看器接管写成一条清晰因果链。

### 4.1 候选观测阶段

消息窗负责：

1. 量测视频按钮位置
2. 计算候选可见比例
3. 计算离视口中心距离
4. 把候选列表回抛给编排和运行时

消息窗不负责：

1. 自己裁决最终 owner
2. 自己决定是否进入全屏
3. 自己持有播放位置真相

因此：

1. **禁止** 在消息窗里长第二套 owner 决策。
2. **禁止** 在消息窗里把浏览器几何直接当成最终业务真相。

### 4.2 Pending owner 阶段

候选进入 `pending owner` 后：

1. 系统开始稳定等待
2. 可以前置预热正式媒体会话
3. 但还不能因为某一帧几何波动就立刻宣布新 owner 生效

因此：

1. **禁止** pending 一出现就立刻强切 owner
2. **禁止** pending 期间让用户看到明显空窗
3. **禁止** pending 期间为了“先有画面”再造第二颗正式表面

### 4.3 Settled owner 阶段

正式 owner 生效后：

1. 同一颗 canonical player 挂到时间线宿主槽位
2. 播放位置从运行时恢复
3. 自动播开始或继续

因此：

1. **禁止** owner settled 后重新从头播放
2. **禁止** owner settled 后还回退到 poster

### 4.4 离屏中断阶段

离屏中断包括：

1. 滚动失去 owner
2. 查看器打开
3. hidden / background
4. 生命周期降级
5. owner 切给别的视频

这类阶段统一语义：

1. flush 当前播放位置
2. 释放 inline owner 解码占用
3. 保留续播资格

因此：

1. **禁止** 把离屏中断当成自然结束
2. **禁止** 因为释放了 owner，就把播放位置清零

### 4.5 回屏续播阶段

视频重新成为 owner 时：

1. 恢复同源播放位置
2. 继续同一条会话
3. 如果当前有静止画面表达，直接过渡到继续播放

因此：

1. **禁止** 从 `0` 重开
2. **禁止** 先显示开头再 seek

### 4.6 自然循环阶段

只有在视频真实播到结尾时，才允许自然循环。

因此：

1. **禁止** 把任何中断都冒充成 loop
2. **禁止** 用“video 设置了 loop”偷换产品语义

## 5. 视觉连续性规则

这一节只关心一件事：用户眼睛看到的是否像同一条连续会话。

### 5.1 可见区内禁止换壳

1. **禁止** 在用户可见区内明显发生 `poster -> video` 主节点换壳。
2. **禁止** 让用户看到 `<img>` 被删掉，再插入 `<video>`，然后再开始播。
3. **禁止** 让“正式播放器出现”晚于“用户已经看见这条卡片”。

这就是为什么当前实现要把预热窗口前移，而不是等完全进入视口后才动。

### 5.2 单帧空观测不准引发视觉回退

1. **禁止** 一次空观测就把当前画面退回 poster。
2. **禁止** 一次虚拟列表重排就把视频重新当冷启动。
3. **禁止** 一次观察器抖动就触发 `loadstart -> poster -> replay` 这类倒退链。

### 5.3 静止画面表达不是第二套真相

非 owner 卡片如果还要有画面表达，只能是：

1. 同一条会话留下来的静止画面表达
2. 宿主槽位上的过渡表达
3. 真正失败时的兜底占位

因此：

1. **禁止** 把静止画面表达升级成第二颗 live `<video>`
2. **禁止** 把静止画面表达升级成第二颗完整 player

### 5.4 时间轴倒退属于 P0 失败

只要满足：

1. 当前源还有效
2. 已保存有效 `currentTime`
3. 这条消息仍在当前消息集合内

那么：

1. **禁止** 视觉状态倒退回开头
2. **禁止** 播放时间倒退回 `0`

---

## 6. 真全屏接管规则

这一节专门锁“点击当前自动播视频后到底该发生什么”。

### 6.1 消息窗只表达用户意图，不直接抓原生全屏

当前实现已经把“当前 owner 点击”回抛成统一查看器入口。

因此：

1. **禁止** 让消息窗自己抓原生 `<video>` 去 `requestFullscreen`
2. **禁止** 恢复“当前 owner 一条路，非当前 owner 另一条路”的双轨旧逻辑

### 6.2 但产品结果必须是直达真全屏当前这颗 player

这条是产品裁决，不是壳层实现细节。

因此：

1. **禁止** 点击当前自动播视频后，用户先经历重新开播、换壳、黑一下、时间轴跳变，再进入全屏。
2. **禁止** 把“内部统一入口”当成“用户可以接受的脏动作”。
3. **禁止** 当前自动播视频点击后冷开第二颗正式 player。

正确结果必须是：

1. 当前 canonical player 直接升格到真全屏
2. `src` 连续
3. `currentTime` 连续
4. 画面连续

### 6.3 非当前视频点击只能迁移同一颗 player

1. **禁止** 点击另一条视频时并存第二颗正式 player。
2. **禁止** 当前 owner 还活着，新 viewer 又长一颗。
3. **禁止** 当前视频和目标视频各持一条正式播放真相。

允许的只有迁移和接管，不允许并存。

### 6.4 退出全屏后必须回到同一条消息流真相

1. **禁止** 退出全屏后把时间线状态重置。
2. **禁止** 退出全屏后丢失这条视频的续播位置。
3. **禁止** 退出全屏后重新冷开消息流视频。

退出全屏后只允许两种结果：

1. 如果这条视频仍符合当前 owner 条件，归位到消息流继续同一条时间轴
2. 如果不再符合 owner 条件，释放 inline owner，但保留正确续播资格

---

## 7. 消息流无控件规则

这件事要写得更硬一点，因为执行时最容易被“顺手加一个按钮”破坏。

### 7.1 消息流不是欣赏界面

消息流的职责只有：

1. 自动播
2. 离屏暂停
3. 回屏续播
4. 点击进入真全屏欣赏

因此：

1. **禁止** 在消息流里提供暂停按钮
2. **禁止** 在消息流里提供进度拖动
3. **禁止** 在消息流里提供音量控件
4. **禁止** 在消息流里提供全屏控件
5. **禁止** 在消息流里提供“播放器工具栏”

### 7.2 真全屏才是完整欣赏态

完整欣赏能力只属于真全屏：

1. 控件
2. 更完整的观看操作
3. 更明确的沉浸式交互

因此：

1. **禁止** 把全屏控件下放回消息流
2. **禁止** 把消息流逐步改回网页播放器集合

---

## 8. 模块职责边界

后续执行必须守住分层，不允许某个模块顺手长成大总管。

### 8.1 `房间消息窗.ts`

职责：

1. 量测候选
2. 暴露消息流宿主槽位
3. 渲染消息流视频画面
4. 回抛统一打开意图

禁止：

1. **禁止** 自己裁决最终自动播 owner
2. **禁止** 自己直接 requestFullscreen
3. **禁止** 自己持有播放位置真相

### 8.2 `聊天媒体编排.ts`

职责：

1. 把消息窗候选送进运行时
2. 把查看器打开意图送进运行时
3. 协调自动播候选预热和查看器请求

禁止：

1. **禁止** 长出第二套播放真相
2. **禁止** 把当前热会话点击又打回 recovering

### 8.3 `媒体运行时.ts`

职责：

1. 持有自动播 owner 真相
2. 持有 pending owner 真相
3. 持有自动播播放位置真相
4. 在 viewer / lifecycle / 候选变化时重算状态

禁止：

1. **禁止** 把自动播位置真相重新下放回 DOM 私有状态
2. **禁止** 让离屏中断等价于自然循环

### 8.4 `自动播协作.ts`

职责：

1. 稳定等待
2. 解析自动播播放结果
3. 释放自动播 owner 占用

禁止：

1. **禁止** 把稳定等待做成肉眼可见空窗
2. **禁止** 自动播 owner 切换时破坏热会话复用

### 8.5 `全局唯一播放器.ts`

职责：

1. 同一颗 canonical player 的时间线挂载
2. 同一颗 canonical player 的查看器接管
3. 同一颗 canonical player 的全屏升格
4. 同一颗 canonical player 的退出归位

禁止：

1. **禁止** 再长第二颗正式 player
2. **禁止** 变成第二个媒体运行时
3. **禁止** 自己再持有第二份业务真相

---

## 9. 性能与架构红线

这一节是万人群聊下的硬边界，后续任何“体验优化”都不能越线。

1. **禁止** 同屏多 live 视频同时解码。
2. **禁止** `activeVideoCount > 1`。
3. **禁止** `autoplayOwnerCount > 1`。
4. **禁止** 为了保帧把大量历史视频 DOM 全量保活。
5. **禁止** 为了减少换壳而引入第二颗正式 player。
6. **禁止** 因为消息流体验优化而削弱 `WebTorrent` 主链、补齐、做种和热会话复用。
7. **禁止** 把消息流优化成“看起来像短视频 feed”的多播放器模型。

---

## 10. TDD 验收清单

这篇 spec 最终必须由测试和烟测共同证明。

### 10.1 单测 / 组件测试

必须证明：

1. 同屏多候选时只有一个 owner。
2. 当前 owner 仍在阈值内时具备粘性。
3. 单帧空观测不会立刻释放 owner。
4. 连续空观测才真正释放 owner。
5. 离屏中断后回屏从上次中断点继续。
6. 自然播放到结尾时才允许从头循环。
7. 当前自动播视频点击后，不会让消息窗直接 requestFullscreen。
8. 当前自动播视频点击后，不会新增第二颗正式 player。
9. 非当前视频点击时，只迁移同一颗 canonical player。
10. 消息流 `<video>` 永远无控件。

### 10.2 浏览器烟测

必须证明：

1. 滑出屏幕就停
2. 滑回来续播
3. 不是自然播完就绝不从 `0` 重开
4. 点击当前自动播视频后直达真全屏
5. 不出现 `poster -> video` 可见换壳
6. 不出现双播放器并存
7. 不出现页面抽搐、黑一下、时间轴倒退

---

## 11. 非目标

这篇 spec 明确不处理这些事情：

1. 不重写 `WebTorrent` 主链
2. 不改后端契约
3. 不改上传链路
4. 不引入新的多播放器架构
5. 不把消息流视频变成短视频 feed
6. 不把消息流视频变成带控件的网页播放器集合

---

## 12. 最终一句话

**群聊视频是一条在消息流与真全屏之间迁移的单一播放会话。滑出屏幕只是中断，不是重开；滑回屏幕只是续播，不是从头；消息流只给画面，不给控件；点当前自动播视频时，必须让当前这颗 canonical `Video.js v10` 直接升格到真全屏，禁止任何第二播放器、时间轴回零和可见换壳。**
