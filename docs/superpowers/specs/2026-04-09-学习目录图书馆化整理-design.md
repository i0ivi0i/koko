# 学习目录图书馆化整理设计

日期：2026-04-09  
状态：设计已确认，待进入 implementation plan  
范围：`学习/` 目录结构重整、资料来源分馆化、文件重命名、总地图与分馆地图建立、旧索引吸收、graphify 配合边界  
约束：不新增 `官方资料/` 这一层；`学习/` 顶层必须永远保留一份主索引 `README.md`；不让目录层级继续加深；不把 graphify 社区编号当物理目录真相；不因为整理而丢失资料可达性

## 0. 一句话结论

`学习/` 要从“顶层散落大量按日期命名的笔记 + 一层过深的旧官方资料目录”，收成“一座图书馆”：

1. 顶层只有总地图 `README.md` 和少量来源分馆
2. 资料按“来源”入馆，不按日期堆放
3. 文件名去掉日期，只保留通俗、统一、可扫读的主题名
4. 每个分馆自己有 `README.md`
5. graphify 负责跨来源关联，不负责物理目录真相

---

## 1. 当前问题

### 1.1 当前结构为什么不顺手

当前 `学习/` 的问题不是“文件太多”，而是“真相分散，入口混乱”：

1. 顶层有一串按日期命名的个人整理笔记
2. 官方资料被包在 `学习/2026-04-04-官方IM架构资料/` 这层旧壳里
3. 旧壳内部再按来源分目录，导致真实资料入口偏深
4. 地图存在两套倾向：顶层零散文件名是一套，旧目录 `README.md` 又是一套
5. 用户很难一眼回答“这份资料属于哪个来源”“我应该从哪开始看”

### 1.2 当前问题不是“缺资料”，而是“缺馆藏秩序”

现在不需要继续发明更多说明文件，而是要把已有资料真相收束成稳定秩序：

1. 人类入口必须是一张总地图
2. 每份资料必须能一眼看出属于哪个来源分馆
3. 顶层不应继续承担“散放单篇 `.md`”的职责
4. 旧索引内容不能丢，但必须吸收进新地图，不能并存两套真相

---

## 2. 设计目标

### 2.1 主目标

这次整理必须同时满足：

1. `学习/` 顶层只保留一份主索引 `README.md`
2. 其他 `.md` 全部进入各自来源分馆
3. 分馆只按“资料来源”划分，不按日期或 graphify 社区划分
4. 目录深度控制在“顶层总馆 -> 分馆 -> 文件”这一层级
5. 任意资料都能通过总地图和分馆地图快速定位

### 2.2 次目标

1. 文件名统一风格，去日期、去套话、保留主题
2. 让目录像图书馆一样整洁，但不牺牲历史资料的可读性
3. 为 graphify 提供更稳定的语料入口，减少“人类目录混乱”对图谱理解的干扰

### 2.3 非目标

这次明确不做：

1. 不改动资料正文内容本身
2. 不新增 `官方资料/` 中间层
3. 不按 graphify 社区编号或临时关系自动生成物理目录
4. 不把 `学习/` 改造成知识库产品式复杂站点
5. 不为了整齐继续把目录向更深层钻下去

## 3. 目标结构

### 3.1 顶层结构

`学习/` 收口后的目标结构如下：

```text
学习/
  README.md
  socket-io/
    README.md
    ...
  socketioxide/
    README.md
    ...
  telegram/
    README.md
    ...
  whatsapp-meta/
    README.md
    ...
  整理笔记/
    README.md
    ...
```

### 3.2 结构解释

1. `学习/README.md` 是总馆地图
2. `socket-io/`、`socketioxide/`、`telegram/`、`whatsapp-meta/` 是来源分馆
3. `整理笔记/` 存放用户自己的总结、对齐清单、理解笔记、补强笔记
4. 旧目录 `学习/2026-04-04-官方IM架构资料/` 被拆解吸收后删除

### 3.3 为什么不保留旧壳

保留旧壳会产生两个问题：

1. 资料来源已经在旧壳内部再次分好类，外面再包一层只会把入口藏深
2. 旧壳 `README.md` 会和新总地图形成两套入口，破坏“永远只有一张总地图”的要求

## 4. 命名规则

### 4.1 命名原则

文件名统一遵守以下规则：

1. 去掉日期
2. 去掉“官方资料”“再学习”“补充”“整理”这类低信息词，除非它承担真实区分作用
3. 保留来源名或主题名中最能帮助快速识别的部分
4. 读起来要像图书馆书名，不像流水账日志
5. 优先“通俗易懂”，不追求文艺感

### 4.2 建议风格

建议使用以下两类命名：

1. 来源资料：直接保留主题  
   例如：`delivery-guarantees.md`、`working-with-updates.md`
2. 用户整理笔记：`来源名-主题.md` 或 `主题.md`  
   例如：`socketioxide-多房间群聊落地笔记.md`

### 4.3 例子

以下是本次整理的重命名方向示例：

1. `2026-04-06-socketioxide官方最佳实践与多房间群聊落地笔记.md`
   -> `socketioxide-多房间群聊落地笔记.md`
2. `2026-04-06-DDD领域主权与乐高式可插拔系统理解笔记.md`
   -> `ddd-领域主权与乐高系统笔记.md`
3. `2026-04-08-单机多房间实时主链官方资料再学习整理.md`
   -> `单机多房间实时主链笔记.md`
4. `2026-04-09-socketioxide-socket.io与Telegram-WhatsApp官方资料再补强.md`
   -> `实时主链资料补强笔记.md`

### 4.4 不做的命名动作

1. 不把中文标题全改成英文
2. 不为了统一而把主题名改得抽象空泛
3. 不制造过度短缩写，让人看不懂

## 5. 地图设计

### 5.1 总馆地图

`学习/README.md` 必须承担以下职责：

1. 说明整个图书馆怎么分馆
2. 给出每个分馆一句话用途
3. 给出推荐阅读路径
4. 说明 graphify 在这里的角色边界

总馆地图不承担长篇正文，不重复每篇资料的大段内容。

### 5.2 分馆地图

每个来源目录自己的 `README.md` 必须承担以下职责：

1. 说明这个来源为什么值得看
2. 列出该分馆下的资料清单
3. 给每篇资料一句话摘要
4. 给出建议阅读顺序或入门路径

### 5.3 旧索引吸收规则

旧文件 [README.md](E:\koko\学习\2026-04-04-官方IM架构资料\README.md) 的有效信息要被吸收到：

1. 顶层总馆地图中的分馆说明与阅读路径
2. 对应来源分馆的 `README.md`

吸收后不再保留旧壳索引，以免出现第二张地图。

## 6. graphify 分工边界

### 6.1 graphify 负责什么

graphify 负责：

1. 跨来源关联
2. 热点节点、桥节点、社区关系
3. 让人快速看“这些资料和代码、文档之间怎么互相连”

### 6.2 graphify 不负责什么

graphify 不负责：

1. 物理目录结构真相
2. 图书馆分馆标准
3. 人类长期稳定入口

### 6.3 设计原则

这次整理要明确：

1. 物理目录靠 `README.md`
2. 跨来源导航靠 graphify
3. 不按 graphify 社区名创建物理目录
4. 不因为某次图谱聚类变化而改动物理馆藏结构

---

## 7. 迁移规则

### 7.1 迁移顺序

建议迁移顺序如下：

1. 创建新的总馆与分馆目录
2. 先写新的总馆地图与分馆地图骨架
3. 搬迁并重命名文件
4. 修正地图中的文件引用
5. 删除旧目录壳
6. 重新运行 graphify 更新图谱

### 7.2 搬迁原则

1. 旧官方资料按来源直接入对应分馆
2. 顶层个人笔记全部移入 `整理笔记/`
3. 地图文件最后统一复核，确保没有死链

### 7.3 风险点

需要特别防的风险：

1. 改名后 README 内链接失效
2. graphify 旧图谱还保留旧路径，造成一段时间内图谱与目录不一致
3. 部分文件名改得过度简化，失去识别性

---

## 8. 验收口径

整理完成后，至少要满足这些验收标准：

1. `学习/` 顶层除了总馆地图和来源分馆，不再散落大量单篇 `.md`
2. 不存在 `学习/2026-04-04-官方IM架构资料/` 这层旧壳
3. 每个来源分馆都有自己的 `README.md`
4. 顶层 `README.md` 能独立承担总地图角色
5. 任意资料都可以通过总地图 -> 分馆地图 -> 文件三步内到达
6. graphify 更新后，`学习/` 的新路径能被正确纳入图谱
