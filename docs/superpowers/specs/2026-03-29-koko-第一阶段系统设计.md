# Koko 第一阶段系统设计

## 1. 目标

本设计文档用于把 `Koko` 第一阶段的系统设计冻结为可执行边界。

目标不是先写一个能跑的聊天室，而是用最少但边界清楚的代码，交付以下四个闭环：

- 聊天闭环
- admin 只读闭环
- 持久化闭环
- 架构闭环

本设计服从 [2026-03-29-koko-第一阶段PRD](E:/koko/docs/2026-03-29-koko-%E7%AC%AC%E4%B8%80%E9%98%B6%E6%AE%B5PRD.md)。

## 2. 核心架构原则

- 采用模块化单体部署，不提前拆服务。
- 采用 Rust 六边形架构思想落地为五层工程边界：`domain / application / contract / adapter / shell`。
- 这是纯 Rust 项目；测试文件除外，非测试用途的 `.rs` 文件总数必须控制在 `13` 个以内。这个上限不是为了机械压文件数，而是为了让主代码文件的职责和代码量保持均衡：该拆分的拆分，避免巨石文件；该整合的整合，避免碎片化模块。实现时应通过清晰收口、模块内聚、职责均衡和单文件复杂度控制来维持这个边界。
- 前端只负责表达意图、展示状态、维护必要的本地体验态，不承载业务真相。
- 后端独占业务真相：匿名会话、房间、成员、消息、admin 查询语义。
- `socketioxide` 是第一阶段唯一实时主通道实现，属于 `adapter` 层，不进入核心层。
- 不重复造轮子；优先复用成熟 Rust 生态，特别是 `socketioxide` 的 rooms、namespace、adapter 和连接能力。
- 乐高式可插拔是硬目标：前端技术、后端框架、具体库和适配实现可以演进，但业务语义、功能边界和插件扩展点不能崩。

## 3. 五层落位

### 3.1 domain

职责：

- 核心领域对象
- 领域错误
- 领域不变量
- 领域语义规则

禁止：

- 直接依赖 `axum`
- 直接依赖 `sqlx`
- 直接依赖 `socketioxide`
- 直接依赖前端框架

### 3.2 application

职责：

- 用例编排
- 输入输出边界
- 调用出站 port

禁止：

- 写 SQL
- 处理 HTTP 细节
- 处理 Socket.IO 协议细节
- 写 UI 逻辑

### 3.3 contract

职责：

- 命令结构
- 查询结构
- 稳定 DTO
- 错误码
- realtime 事件类型

### 3.4 adapter

职责：

- PostgreSQL 仓储实现
- `socketioxide` realtime 适配
- HTTP handler 适配
- admin 查询适配
- 认证适配

原则：

- 只翻译，不做业务裁决

### 3.5 shell

职责：

- 服务启动
- 依赖装配
- Web 前台壳
- admin 壳
- 路由壳

### 3.6 第一阶段 Rust 文件预算分配

第一阶段非测试用途的 `.rs` 文件总数固定控制为 `13` 个，并按以下预算分配：

- 后端：`5`
- 前端：`3`
- admin：`2`
- 其余跨层与壳层：`3`

这不是粗糙的“按端分堆”，而是为了在保持六边形边界的同时，让主代码文件的职责和体量尽量均衡。

建议的第一阶段文件分配如下：

1. `src/domain.rs`
   归属：后端
   职责：集中承载 `AnonymousSession / Room / RoomCode / Member / Message / DomainError / invariants`

2. `src/application.rs`
   归属：后端
   职责：集中承载第一阶段全部用例、port 定义、用例输入输出与应用服务编排

3. `src/contract.rs`
   归属：后端
   职责：集中承载稳定 DTO、命令、查询、错误码与 realtime 事件契约

4. `src/persistence.rs`
   归属：后端
   职责：集中承载 PostgreSQL repo、事务边界与 admin 只读查询实现

5. `src/realtime.rs`
   归属：后端
   职责：集中承载 `socketioxide` 连接中间件、房间订阅、命令翻译、权威事件广播

6. `src/web_app.rs`
   归属：前端
   职责：前台应用壳、页面入口、前台路由编排

7. `src/web_state.rs`
   归属：前端
   职责：前台本地体验态、命令发起、快照装载、realtime 客户端协同

8. `src/web_view.rs`
   归属：前端
   职责：前台页面与组件表达，只负责展示与事件转发

9. `src/admin_app.rs`
   归属：admin
   职责：admin 应用壳、后台路由、后台登录入口

10. `src/admin_view.rs`
    归属：admin
    职责：admin 页面表达、概览、列表、搜索、详情、成员视图

11. `src/http.rs`
    归属：跨层与壳层
    职责：HTTP adapter，承载匿名会话引导、join-or-create、room snapshot、admin API 映射

12. `src/main.rs`
    归属：跨层与壳层
    职责：总装配入口，负责 runtime、依赖注入、路由挂载、服务启动

13. `src/support.rs`
    归属：跨层与壳层
    职责：集中承载真正跨层但不属于业务核心的支撑能力，例如时间、ID、配置、统一错误映射、少量共享辅助类型

### 3.7 文件预算背后的边界理由

- `domain / application / contract` 各自独立成文件，是为了让核心树干自解释，不混层。
- `persistence / realtime / http` 分开，是为了防止把 PostgreSQL、`socketioxide`、HTTP 入口搅成一个 adapter 大杂烩。
- 前台 `3` 个文件的目标是把“壳、状态、视图”拆开，避免前端代码又把展示、状态和网络揉成一团。
- admin `2` 个文件比前台更少，是因为第一阶段 admin 只有只读运营能力，不值得做更厚的壳。
- `main.rs` 单独保留，是为了保证总装配逻辑不会反向污染其他层。
- `support.rs` 只允许放真正跨层但非业务的支撑能力，不能演化成“什么都塞一点”的万能垃圾桶。

### 3.8 文件预算执行规则

- 新增 `.rs` 文件前，必须先证明现有文件无法在保持职责清晰和代码量均衡的前提下承载变化。
- 若某个文件体量明显失衡，应优先考虑在预算内调整拆并，而不是直接突破 `13` 个文件上限。
- 允许在单个文件内使用内联模块、清晰分区和明确标题来维持可读性，但不能把它变成不可维护的巨石文件。
- 文件预算服务于架构清晰，不允许为了“凑数量”做无意义拆分或合并。

## 4. 稳定领域对象

### 4.1 AnonymousSession

稳定语义：

- `session_id`
- `issued_at`
- `last_seen_at`
- `status`

说明：

- 匿名会话采用设备级长期匿名身份。
- 客户端只保存不透明凭证，不拥有身份真相。

### 4.2 Room

稳定语义：

- `room_id`
- `created_at`
- `status`

说明：

- `room_id` 是内部权威标识。

### 4.3 RoomCode

稳定语义：

- `room_code_id`
- `room_id`
- `original_code`
- `normalized_code`
- `code_version`
- `created_at`
- `status`

说明：

- 当前版本规则为 `4 个数字 + 1 个英文字母，位置任意`。
- 比较时不区分大小写，由服务端归一化。
- 短码规则未来可演进到更长，因此 `room_code` 必须作为独立入口语义建模，不能焊死进 `Room` 本体。

### 4.4 Member

稳定语义：

- `member_id`
- `room_id`
- `session_id`
- `joined_at`
- `status`

说明：

- 成员关系必须持久化。
- 同一匿名身份允许同时属于多个房间。
- runtime 在线连接态不是成员真相。

### 4.5 Message

稳定语义：

- `message_id`
- `room_id`
- `sender_session_id`
- `body`
- `created_at`
- `status`
- `client_message_id`（预留）

说明：

- 第一阶段只支持文本消息。
- 前端可以有“发送中”乐观态，但只有服务端确认后才算正式消息事实。

### 4.6 AdminReadModel

稳定查询语义：

- `AdminOverview`
- `AdminRoomListItem`
- `AdminRoomDetail`
- `AdminRoomMemberItem`

说明：

- 这些都是查询投影，不是业务聚合根。

## 5. 稳定用例

第一阶段必须稳定存在以下用例边界：

- `bootstrap_anonymous_session`
- `join_or_create_room_by_code`
- `load_room_snapshot`
- `send_text_message`
- `subscribe_room_stream`
- `get_admin_overview`
- `list_admin_rooms`
- `search_admin_rooms`
- `get_admin_room_detail`
- `list_admin_room_members`

## 6. Port 与 Adapter API 边界

### 6.1 入站 port

稳定业务入口是用例，不是具体 URL，也不是具体 socket event 名字。

示例：

- `send_text_message(command)` 是稳定业务入口
- `POST /api/...` 只是 HTTP adapter 映射
- `socket.on("send_text_message")` 只是 realtime adapter 映射

### 6.2 出站 port

第一阶段建议稳定以下出站能力抽象：

- `AnonymousSessionRepository`
- `RoomRepository`
- `RoomCodeRepository`
- `MemberRepository`
- `MessageRepository`
- `AdminReadRepository`
- `RealtimeEventPort`
- `AdminAuthPort`
- `Clock`
- `IdGenerator`
- `TransactionPort`

### 6.3 边界纪律

- 带有 `axum/sqlx/socketioxide/dioxus` 的类型不应穿透 adapter 边界。
- 框架 API 不得进入 `domain` 和 `application`。
- repo、handler、realtime adapter 不得偷偷长业务规则。

## 7. 聊天主流程权威时序

### 7.1 冷路径

1. 客户端调用 `bootstrap_anonymous_session`
2. 服务端签发或续用匿名会话
3. 客户端建立 `socketioxide` 连接，并附带会话凭证
4. 客户端调用 `join_or_create_room_by_code`
5. 服务端归一化短码，查询或创建房间
6. 服务端持久化成员关系
7. 服务端返回房间快照，包括最近 `50` 条消息

### 7.2 热路径

1. 客户端调用 `subscribe_room_stream`
2. 服务端校验该会话在持久化真相中已是房间成员
3. 校验通过后，将当前 socket 加入 runtime room
4. 客户端发送 `send_text_message`
5. realtime adapter 将事件翻译为应用用例命令
6. 用例层校验会话、成员资格、房间和消息正文
7. 在事务内持久化消息
8. 消息写库成功后，广播权威事件
9. 客户端用权威结果把本地乐观态升级为正式消息

### 7.3 不可违反的顺序

- 先形成成员关系，再建立 runtime 订阅
- 先持久化消息，再广播 realtime 事件
- runtime room membership 只是运行态投影，不是真相

## 8. 数据库真相模型

第一阶段必须持久化以下真相集合：

- `anonymous_sessions`
- `rooms`
- `room_codes`
- `members`
- `messages`

关系要求：

- 一个 `room_code` 指向一个 `room`
- 一个 `member` 归属一个 `room`
- 一个 `member` 归属一个 `anonymous_session`
- 一个 `message` 归属一个 `room`
- 一个 `message` 指向一个发送者 `anonymous_session`

第一阶段不提前落库以下运行态或未来能力：

- 在线状态
- socket 连接状态
- 已读回执
- typing 状态
- 治理日志
- 事件溯源存储

## 9. Realtime 事件契约

### 9.1 客户端命令

- `subscribe_room_stream`
- `send_text_message`

### 9.2 定向确认事件

- `room_stream_subscribed`
- `message_accepted`
- `command_rejected`
- `session_invalid`

### 9.3 房间广播事件

- `message_created`

### 9.4 错误码

- `invalid_session`
- `room_not_found`
- `membership_required`
- `invalid_room_code`
- `invalid_message_body`
- `forbidden`
- `internal_error`

### 9.5 事件骨架

建议所有稳定 realtime 事件都携带：

- `event_name`
- `event_version`
- `occurred_at`
- `target`
- `correlation_id`

### 9.6 不上升为稳定业务契约的内容

- `connect`
- `disconnect`
- `ping/pong`
- Socket.IO transport 细节
- runtime join/leave 细节
- 内部 namespace 生命周期事件

## 10. Admin 设计边界

- admin 第一阶段只承载只读运营能力。
- admin 登录采用服务端账号密码登录 + 服务端会话或 token。
- admin 不承担治理写操作。
- admin 查询语义通过 `AdminReadRepository` 表达，不反向定义业务真相。

## 11. 前端与多端边界

- Web 只是第一种壳，不是业务真相所在地。
- 未来 iOS 和 Android 必须消费同一组稳定业务契约和 realtime 事件契约。
- 前端允许乐观 UI，但只能维护体验态，不能决定业务事实。
- 房间存在性、成员资格、消息是否成立都由后端权威裁定。

## 12. 测试与验证策略

### 12.1 测试分层

- `domain`：纯单元测试
- `application`：用例测试，使用 fake port
- `adapter`：PostgreSQL、HTTP、`socketioxide` 集成测试
- `end-to-end`：最小闭环测试

### 12.1.1 TDD 约束

- 第一阶段实现必须采用 TDD：先写失败测试，再做最小实现，再转绿，再做必要重构。
- 新功能、缺陷修复和关键边界重构都不允许绕过这条流程。
- 若某类改动难以直接测试，必须先把设计调整到可测试，再实现，而不是以“先写代码再补测试”作为默认路径。

### 12.2 第一阶段必须验证的场景

- 无有效会话时不能 join/send
- 输入不存在短码时自动建房
- 大小写不同但归一化相同的短码进入同一房间
- 加入房间后成员关系已持久化
- 消息必须先写库再广播
- 服务重启后房间、成员、消息历史仍可读取
- admin 可查看概览、列表、搜索、详情、成员列表
- 乐观消息只有收到权威结果后才转为正式消息

### 12.3 架构反回归要求

- `application` 层测试中不得出现 `axum/sqlx/socketioxide` 类型
- realtime adapter 测试要证明无成员资格时不能订阅或发消息
- 持久化失败时不能广播成功消息

## 13. 代码即文档与可维护性要求

第一阶段编码时必须贯彻“代码即文档”。

这里的意思不是“完全不写文档”，而是：

- 任何一个新接手项目的维护者，在不依赖口头传承、不翻聊天记录、不先读一堆外部说明的前提下，看到任意一段核心代码，都应能较轻松地理解这段代码在做什么、为什么存在、依赖什么、边界在哪。

这条要求必须落实为具体编码标准，而不是停留在口号层面。

### 13.1 命名必须表达业务语义

- 类型名、函数名、字段名优先表达业务意图，而不是框架动作或技术细节。
- 优先使用 `join_or_create_room_by_code`、`send_text_message` 这种业务名词，不使用含糊的 `handle_it`、`process_data`、`do_send` 之类名字。
- 变量名必须让读者知道它代表的是业务真相、运行态状态还是适配层对象，不能混淆。

### 13.2 代码结构必须顺着人的理解路径展开

- 一个函数应先让人看懂“它要完成什么”，再看清“它如何完成”。
- 控制流必须尽量直白，避免层层嵌套、过度链式调用、过度压缩表达。
- 相比“更少行数”，优先选择“更容易一眼读懂”的写法。
- 同一函数内不要混合多个层级的职责；业务判断、协议翻译、存储细节不要挤在一起。

### 13.3 模块边界本身要能自解释

- 维护者看到文件位置，就应大致推断它属于 `domain / application / contract / adapter / shell` 哪一层。
- 一个模块只做一类事，避免“文件名是 A，内容里顺手做了 B、C、D”。
- 如果某段逻辑必须依赖框架或外部库，应明确留在 adapter 或 shell，不允许悄悄渗进核心。
- 纯 Rust 主代码的 `.rs` 文件数量必须受控；新增文件前应先证明现有文件无法在保持清晰职责和均衡体量的前提下继续承载该变化；保留文件时也应防止某个文件膨胀成维护成本过高的巨石文件。

### 13.4 隐式规则必须显式化

- 重要业务约束不能藏在 if 分支角落、默认值、魔法常量、命名模糊的布尔变量里。
- 会影响业务语义的规则必须以清晰的领域方法、显式校验、稳定错误语义或契约字段表达出来。
- 像短码归一化、成员资格校验、消息成立条件这类规则，必须能被读代码的人直接看出来，而不是靠猜。

### 13.5 注释只解释“为什么”，不重复“代码表面在做什么”

- 默认先靠清晰命名、清晰分层、清晰函数拆分让代码自解释。
- 注释用于解释设计取舍、边界原因、反直觉约束、与 PRD 或稳定契约的关系。
- 禁止写“给变量赋值”“循环遍历数组”这种低价值注释。
- 当某段代码故意违反直觉但有正当理由时，必须写清楚为什么要这样做。

### 13.6 新维护者可理解性是硬验收标准

任何新增代码在设计和评审时都必须经得起下面这些问题：

- 不看实现上下文，只看类型名和函数签名，能否大致知道它负责什么？
- 不跳出当前文件，能否看懂这段逻辑的主流程？
- 不读框架文档，能否分清这段代码是在表达业务、协议翻译还是基础设施细节？
- 将来别人接手修改这个功能时，是否能主要改局部，而不是从头猜整条链路？

如果答案是否定的，就说明这段代码还不够“代码即文档”。

### 13.7 明确反对的写法

- 为了炫技而写过度紧凑、过度抽象、过度泛型的代码
- 用宏、链式调用或技巧把正常逻辑压成难读的一行
- 用重复包装掩盖简单事实
- 用框架生命周期和隐式状态机偷装业务规则
- 让维护者必须同时打开很多文件才能看懂一个基础流程

### 13.8 对 Koko 的直接要求

- 核心聊天链路中的每个用例，都应能从名字、输入输出和错误语义直接看懂职责。
- `socketioxide` handler 必须薄，读代码时一眼就能看出它只是在翻译 realtime 命令，不是在定义业务。
- 仓储实现应让人一眼分清“这里在做存储映射”，而不是“这里在补业务规则”。
- 前端代码应让维护者一眼看出哪些是体验态，哪些来自服务端权威事实。

## 14. 第一阶段刻意不做的事

- 提前实现治理写能力
- 提前实现消息分页
- 提前实现插件平台
- 提前实现在线/离线复杂状态系统
- 提前引入完整 CQRS / 事件溯源
- 提前并行实现第二套 realtime 通道

## 15. 总结

`Koko` 第一阶段不是围绕页面、路由、表结构或 `socketioxide` API 组织，而是围绕稳定业务语义和可替换边界组织。

系统的长期稳定树干只有一套：

- 匿名会话
- 房间
- 房间短码入口
- 成员关系
- 消息事实
- admin 只读查询
- 稳定用例
- 稳定 realtime 事件

未来无论 Web、iOS、Android，还是后端框架、数据库访问库、实时适配方式如何演进，都必须围绕这套稳定树干去拼装，而不是反过来重写核心。
