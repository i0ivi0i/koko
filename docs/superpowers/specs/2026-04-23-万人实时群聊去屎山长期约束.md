## 0. 总裁决

**当前万人实时群聊项目的正式聊天 realtime 核心仍然是后端纯 Rust `socketioxide` + 前端 `socket.io-client`；真正必须清理的，不是成熟聊天核心轮子，而是长期迭代后围绕核心长出来的私有重复轮子、私有重复真相、私有重复胶水和热点总控。后续必须在不引入新 bug、不破坏业务功能、不削弱满血特性、不留下冗余垃圾、不留下技术债尾巴的前提下，把剩余屎山收口到底，并建立长期有效的防漂移约束，禁止未来维护和运维再把系统慢慢养回屎山。**

从这句话推出全部硬边界：

1. 禁止误杀成熟核心轮子。
2. 禁止低估外围私有胶水屎山。
3. 禁止长出第二套聊天核心、恢复真相、transport 真相、媒体主链或浏览器应用运行时真相。
4. 禁止让 adapter / shell / runtime 偷拿业务裁决。
5. 禁止让前端重新养出平行业务真相。
6. 禁止让 shared contract 倒灌壳专属语义。
7. 禁止只加新结构、不删旧胶水。
8. 禁止旧新双活长期共存。
9. 禁止为了“保险”保留技术债尾巴。
10. 禁止未来维护和运维继续用补丁式逻辑把热点养胖。
11. 禁止没有新鲜验证就宣布完成。
12. 禁止把图谱改名换路径冒充热点减压。

## 3. 当前系统真相

### 3.1 聊天 realtime 核心仍然守正

当前必须承认：

1. 正式聊天 realtime 主链仍然是后端纯 Rust `socketioxide` + 前端 `socket.io-client`。
2. 当前没有发现第二套正式聊天 realtime 核心在暗中接管主链。
3. 当前聊天实时命脉仍然建立在成熟主链上，而不是某个私有手搓实时框架上。
4. `subscribe_room_stream` 与 `create_message` 仍是主链上的正式业务入口。

因此：

**去屎山不是推倒成熟核心，而是在继续复用成熟核心的前提下，把外围屎山收回正确 owner。**

### 3.2 真正危险的是外围持续长胖

核心仍在，不等于系统健康。当前真正危险的是外围在长期迭代中持续长胖：

1. 成熟轮子之外又长出越来越厚的私有组合层。
2. shared transport、shared runtime、shared shell、媒体 owner 链周围出现越来越多私有胶水。
3. 壳层、编排层、恢复链、transport 热点开始吸附越来越多职责。
4. 旧路径、新包装、兼容旁路和补丁式逻辑如果不退场，就会慢慢变成第二真相。
5. 维护和运维在“先补一下”“先兼容一下”“先别删旧的”中逐步把系统养回屎山。

准确判词是：

**聊天核心仍守正，但外围已经形成多处私有重复轮子、私有重复真相、私有重复胶水和热点总控。**

### 3.3 必须同时禁止两种误判

1. 禁止把“外围很乱”误判成“聊天核心已经失效”。
2. 禁止把“聊天核心还在”误判成“项目没有屎山”。

只犯第一种，会误杀成熟轮子。只犯第二种，会继续纵容私有胶水变厚。两种都错。

## 4. 什么算核心，什么算屎山

### 4.1 应该保留的成熟核心

下列对象默认应继续保留和复用：

1. 已验证可用、边界清楚、仍满足当前需求的正式聊天 realtime 主链轮子。
2. 已验证可用、仍满足媒体主链裁决的成熟媒体分发能力。
3. 已验证可用、边界清楚的浏览器运行时原生能力和成熟生态。
4. 只承担薄翻译、薄接线、薄组合职责、且没有偷拿业务真相的 adapter。
5. 能明显压缩私有胶水、减少重复真相、提升边界清晰度的成熟基础设施与通用库。

判断准绳：

**成熟、边界清楚、当前仍适配的能力，继续复用不是屎山；为了“看起来更纯”误杀它，才是屎山。**

### 4.2 必须退场的屎山

下列对象默认属于屎山，必须删除、合并、收口或退场：

1. 成熟轮子之外长出的私有重复轮子。
2. 正式真相之外长出的私有重复真相。
3. 只是在成熟能力外再套一层、再搬一层、再转一层，但没有真实边界价值的私有胶水。
4. 同时承载多条 owner 线并不断吸职责的热点总控。
5. 为了“保险”保留下来的旧新双活、双路径、双恢复、双 transport、双 runtime。
6. 依赖应急补丁、运维记忆、兼容旁路才能维持正确性的长期路径。
7. 未来维护稍微顺手就会继续往里塞逻辑的超大组合根和超大编排中心。

最终裁决：

**本项目真正要清理的屎山，不是成熟核心轮子，而是成熟核心轮子外层长出来的私有重复轮子、私有重复真相、私有重复胶水和热点总控。**

### 4.3 继续造屎山的行为

下列行为一旦出现，哪怕短期能跑，也视为继续造屎山：

1. 在正式聊天主链之外再长第二套聊天 realtime 主链。
2. 在正式恢复链之外再长第二套恢复真相。
3. 在 shared transport 之外再长第二套私有 transport 真相。
4. 在正式媒体主链之外再长第二套播放或分发真相。
5. 用新包装把旧路径包住，但旧路径继续活着。
6. 让某个热点总控继续同时拥有越来越多 owner。
7. 让 adapter、shell、runtime 偷拿业务判断。
8. 让 shared contract 倒灌某个壳专属语义。
9. 让前端重新养出平行业务真相。
10. 让“以后再删”“先留着旧的保险一点”变成长期现实。

## 6. 聊天 realtime 主链守正边界

### 6.1 纳入范围

4. 前端房间订阅、房间恢复、snapshot + 增量补洞相关编排热点。
5. 相关 transport 胶水和低价值包装。
6. 为了收口这些链路而必须新建的中文目录、中文文件、中文模块。

### 6.2 非范围

聊天主链守正不能顺手扩张到：

1. WebTorrent / swarm / locator / 媒体协作分发主链重构。
2. 消息业务语义重写。
3. 权限模型重写。
4. 房间成员资格真相重写。
5. 对外 realtime 事件名和 payload 重构。
6. transport 全家桶全面重写。
7. 整仓 onion 化大重排。
8. 共享 `contract` 的稳定通用表面重写。

### 6.3 当前代码映射的处理方式

旧文档记录过一批当时命中的热点基线，例如后端 realtime 入口、用例与契约文件，前端传输、房间实时编排、房间恢复编排、聊天壳、聊天应用内核、契约文件等。

这些名称的地位是：

1. 它们是 2026-04-23 的已验收基线和 implementation plan 下钻线索。
2. 它们不是长期总纲的永久正文结构。
3. 后续执行必须重新读取当前代码，再确认最新热点。
4. 禁止把旧文件名机械套用到新结构，也禁止因为总纲不硬编码文件名就忽略这些历史热点。

### 6.4 关键行为必须等价

后续任何聊天主链收口都必须证明：

1. 房间订阅主链不变：订阅成功、重复订阅、重连后的重新订阅行为等价。
2. 发消息主链不变：消息成立、广播、回显外部行为等价。
3. 恢复链不变：`invalid_session`、snapshot、增量补洞、补洞后接回 realtime 主链的顺序和责任等价。
4. 错误语义不变：没有借重构顺手改状态、改错误码、改事件名。
5. 断线与重连协作不变：断开、重连、重新订阅、恢复补洞没有长出第二套临时真相。

## 7. DDD / Onion / Unix 的唯一解释

### 7.1 DDD 只用来收真相

DDD 不代表：

1. 到处加 `manager`。
2. 到处加 `service`。
3. 到处加空心接口。
4. 套“领域层、应用层、基础设施层”名字但职责没变。

DDD 在本项目只代表：

**业务真相必须收口到唯一 owner。**

自然推出：

1. 领域真相归 domain owner。
2. 用例编排归 application owner。
3. 协议翻译归 adapter。
4. 交互协调、临时体验态、本地运行时状态归 shell / runtime。
5. 谁不拥有真相，谁就禁止替真相做决定。

### 7.2 Onion 只用来守依赖方向

Onion 只允许按下面理解：

1. 越靠近核心，越不能直接依赖协议和框架细节。
2. 越靠近外层，越不能偷拿业务真相。
3. 分层的目的是守依赖方向，不是制造层数。
4. 多一层如果没有真实边界价值，就不该存在。

禁止为了“更像洋葱”堆 wrapper，禁止为了“更像分层”制造纯转发文件海。

### 7.3 Unix 只用来保持小而专

Unix 哲学只允许按下面理解：

1. 模块必须小而专。
2. 拆分必须带来真实边界价值。
3. 组合必须简单。
4. 不能把简单路径拆成碎片噪音。

禁止为了显得模块化制造碎文件海，禁止把一个清楚模块切成三层纯转发。

### 7.4 成熟轮子继续复用

通用能力、基础设施、协议封装、浏览器运行时能力、成熟媒体能力，默认先复用成熟生态。

只有当现成轮子确实不能满足边界、性能、维护性或契约约束时，才允许谨慎自研。

如果某个私有实现的唯一价值只是把成熟轮子再包一层、再转一层、再搬一层，且没有带来新的边界清晰度，它就应退场。

允许：

1. 新建中文目录和中文文件。
2. 新增 `.rs` / `.ts` 文件。
3. 移动文件、重命名模块、重排目录。
4. 从大文件中拆出应用编排。
5. 从大文件中拆出恢复协作。
6. 把协议翻译从业务逻辑里剥出来。
7. 删除重复 helper、重复 transport 包装、低价值 facade。
8. 为了 owner 清晰而调整内部依赖方向。

但所有允许都必须满足：

**外部行为等价，且总复杂度下降。**

### 8.2 新文件必须有边界价值

允许新增：

1. 从大文件中拆出的单一职责文件。
2. 原来混在 adapter 里的应用编排文件。
3. 原来混在壳层里的恢复协作文件。
4. 用来承接旧逻辑退场的过渡性收口文件。

禁止新增：

1. 纯转发包装文件。
2. 没有独立边界价值的 facade / manager / helper。
3. 为了“看起来分层”而硬拆出来的 ceremony 文件。
4. 与旧实现长期并行的新路径文件。

新增文件必须说清替代了什么旧路径、删掉什么旧胶水、怎样让 owner 更清楚、怎样让总复杂度下降。

### 8.3 四层职责

领域层只拥有：

1. 聊天 realtime 真相本身的稳定概念。
2. 房间事件流、消息成立、恢复锚点等稳定业务语义。
3. 与框架无关的核心约束。

领域层禁止拥有 `socketioxide`、`socket.io-client`、HTTP 调用、浏览器状态或某个壳专属展示流程。

应用层只拥有：

1. 用例编排。
2. 命令和查询的执行顺序。
3. 恢复、补洞、重接入主链这类流程的权威编排。

应用层禁止拥有框架胶水、页面 UI 流程、协议编码细节、transport 连接管理细节。

适配层只拥有：

1. 协议翻译。
2. handler / socket callback / HTTP 请求和响应映射。
3. IO 接入和错误转码。

适配层禁止拥有业务真相、房间成员资格真相、消息成立真相、权限裁决真相、恢复链业务 owner。

壳层只拥有：

1. 前端应用壳的交互编排。
2. 必要本地临时状态。
3. 什么时候触发调用、展示连接提示、交给恢复链。

壳层禁止拥有权限真相、房间成员资格真相、消息成立真相、能否订阅或能否发言这类业务裁决。

### 8.4 `contract` 只能是稳定通用表面

1. `contract` 是多壳共享的唯一稳定通用表面。
2. 禁止新造第二份 `contract`。
3. 禁止把某个壳专属的页面流程、展示文案、布局字段、UI 状态枚举倒灌进 `contract`。
4. 如果混乱来自消费 `contract` 的位置不对，就调整消费边界。
5. 禁止把“消费边界不清”误判成“需要先改 `contract` 本身”。

核心裁决：

**收的是谁消费 `contract`、谁不该持有真相，不是把 `contract` 本身重写一遍。**

## 9. 总执行范围与顺序

### 9.1 本次总执行要收什么

纳入：

1. 聊天主链外围残留的 shared transport / shared shell / shared runtime 屎山热点。
2. 浏览器应用运行时与多壳共享协作中残留的 owner 漂移。
3. 媒体查看器、自动播、定位、媒体运行时、协作分发、媒体恢复协作等媒体 owner 链上的剩余屎山热点。
4. 旧胶水、旧包装、旧重复路径、旧双活残骸的统一退场。
5. 为防止未来再次漂移而必须一并建立的长期防漂移约束。

不纳入：

1. 推倒或替换成熟聊天核心轮子。
2. 重写聊天业务真相。
3. 重写共享 `contract` 的稳定通用表面。
4. 发明第二聊天主链、第二恢复真相、第二 transport 真相、第二媒体主链。
5. 顺手更换大批无关基础设施。
6. 为了“更像 DDD”新增无边界价值 ceremony。

### 9.2 唯一执行顺序

这套顺序是单次总执行内部的施工顺序，不是重新回到阶段化路线。

1. 先守核心：正式聊天 realtime 主链、正式恢复链、稳定共享契约、正式媒体主链不被误伤。
2. 先收 shared owner，再收 media owner。
3. shared owner 收清后，再收 media/browser-app owner 链。
4. 最后删旧路径、旧包装、旧双活、旧旁路，并统一验证。

禁止在 shared owner 还没收清时，把 media owner 和 shared owner 混成一个大 runtime、一个大 transport、一个大编排中心。

### 9.3 越界冲动

下面说法一律视为越界：

1. “反正都要一次性做完了，顺手把协议也统一一下。”
2. “反正都要清到底了，shared contract 也一起重写吧。”
3. “反正 transport 很乱，干脆把整个通信栈都重做掉。”
4. “反正媒体也要收，干脆把聊天主链一起换成新的更现代方案。”
5. “反正都在前端，就统一成一个大 runtime 吧。”
6. “旧的先别删，保险一点。”

## 10. 跨总执行硬红线

1. 禁止引入新 bug。
2. 禁止破坏现有业务功能。
3. 禁止削弱现有满血特性。
4. 禁止让项目变得更难长期维护。
5. 禁止留下技术债务尾巴。
6. 禁止只加新结构、不删旧胶水。
7. 禁止保留旧新双活长期共存。
8. 禁止前端长出平行业务真相。
9. 禁止 adapter / shell / runtime 承载业务裁决。
10. 禁止 shared contract 倒灌壳专属语义。
11. 禁止借“保险一点”之名保留第二套真相。
12. 禁止借“反正以后再收”之名把技术债尾巴留给未来。
13. 禁止因为重构顺手统一错误语义、状态命名、事件名。
14. 禁止因为目录重排引入大量纯格式化和搬家噪音。

只要某次收口之后项目多了新 bug、功能受损、特性削弱、冗余垃圾残留、技术债尾巴留下、维护性下降，这次收口就视为失败。

## 11. 长期防漂移约束

### 11.1 临时措施不能升格成长期真相

下面这些默认只是临时措施：

1. 运维补丁。
2. 兼容旁路。
3. 应急兜底。
4. 临时绕路。
5. 历史遗留的双活保底逻辑。

禁止在没有重新收口 owner 的情况下，让这些临时措施长期活着。禁止让运维记忆成为系统正确性的组成部分。

### 11.2 以后任何结构改动必须回答四个问题

1. 这个改动让哪个真相 owner 更清楚了？
2. 这个改动删除了哪段旧路径？
3. 这个改动怎样让未来更不容易再长屎山？
4. 这个改动准备用什么新鲜验证证明它没有引入新 bug、没有破坏业务功能、没有削弱满血特性？

答不清，就禁止继续扩张代码。

### 11.3 只接受净减复杂度

结构改动即便文件数变多、目录变化，也必须同时满足：

1. 总体真相 owner 更清楚。
2. 重复路径更少。
3. 热点更薄。
4. 维护更轻。
5. 运维更不容易靠旁路维持正确性。

如果做不到，就禁止包装成“去屎山”。

## 12. 验证门禁与完成判定

### 12.1 没有新鲜验证，禁止宣布完成

任何“做完了”“收口了”“完成了”的说法，都必须建立在新鲜验证上。

### 12.2 定向验证

至少要按改动范围覆盖：

1. 聊天 realtime 订阅链路测试。
2. 发消息链路测试。
3. 恢复 / 补洞 / 重连链路测试。
4. 前端 `pnpm --dir frontend test`、`typecheck`、`build`。
5. 后端 `cargo test -j 1`。
6. 架构适应度检查。
7. 必要真实浏览器烟测。

### 12.3 结构验证

必须复核：

1. 新目录、新文件真实承接 owner。
2. 旧路径已删或有清楚退场。
3. `git diff` 没有大量纯格式化噪音和无价值搬家。
4. 代码修改完成后重建 graphify，并复核热点是否真减压。

graphify 复核命令：

```powershell
python3 -c "from graphify.watch import _rebuild_code; from pathlib import Path; _rebuild_code(Path('.'))"
```

### 12.4 热点减压的最低可观察判定

至少要满足大部分结果，才算真正减压：

1. 前端 transport 不再同时兼管 socket 创建、HTTP 调用、恢复触发、重接协作这几类不同 owner。
2. 房间恢复编排不再充当“恢复总控 + transport 拼接器 + UI 协调器”的混合热点。
3. 房间实时编排与房间恢复编排边界更清楚，禁止继续互相吸成双头总控。
4. 聊天壳只保留壳层交互编排，禁止继续回收恢复、权限或业务判断。
5. 后端 adapter 至少有一部分不属于 adapter 的职责被真实剥离，而不是只换名字继续留在原地。
6. 用例层不再继续充当所有聊天 realtime 与恢复相关编排的无上限汇聚点。
7. graphify 复核时，不能再看到单一 transport / 编排节点同时垄断“聊天主链 + 恢复 + 壳层协作”三种职责。

反面判定：

1. 只是把热点改名后继续承载同样职责，不算减压。
2. 只是把编排文件切成多个纯转发文件，不算减压。
3. 后端只是把大函数搬到新文件，但 handler 仍持有相同业务判断，不算减压。
4. graphify 热点只是从一个文件迁移到另一个文件，不算减压。

### 12.5 完成判定

只有同时满足下面条件，才算完成：

1. 聊天 realtime 成熟主链仍唯一且更清楚。
2. 没有长出第二套聊天 realtime 核心、第二套恢复真相、第二套 transport 真相、第二套媒体主链。
3. shared hotspot 不再继续承担多条 owner 线的混合职责。
4. media owner 链不再继续由超大编排或邻接总控跨层吸附。
5. 旧胶水、旧包装、旧重复路径、旧双活残骸已经退场。
6. 图谱复核显示热点得到实质减压，而不是只改名或只换目录。
7. 外部行为等价，稳定契约未被私自重写，现有功能与特性未因收口退化。
8. 与媒体 / 浏览器应用化相关的 authoritative 验证门禁同步通过。
9. 不存在以 TODO、临时兼容、待退场旁路、双活保底为名继续存活的技术债尾巴。
10. 后续维护与运维已不能再低成本地把系统养回同类屎山。

## 13. 与其他 authoritative spec 的关系

### 13.1 本文地位

本文是万人实时群聊去屎山的唯一总入口。以后任何总路线、总执行、总验收、总防漂移约束，都必须先服从本文。

### 13.2 媒体 spec 地位

媒体 / WebTorrent 相关 spec 继续各自保留 authoritative 地位：

1. 本文负责总执行规约与长期防漂移。
2. 媒体 spec 负责媒体主链真相。
3. 后续任何清理，必须同时服从本文与媒体 authoritative spec。
4. 禁止用“总收口”之名改写媒体正式主链裁决。

### 13.3 implementation plan 来源

以后 implementation plan 只能这样产生：

1. 先读本文。
2. 再读相关媒体 authoritative spec、浏览器应用化文档和当前代码。
3. 当前代码映射、当前 god node 事实、剩余热点必须下沉到 implementation plan。
4. 禁止再要求补一套新的阶段 child spec 才能启动。

总纲保持抽象、可复用、可长期演进；当前文件名和当前模块名只属于实现计划和当次验收，不属于永久总规约。

## 14. 自审

按本项目约束自审如下：

1. 是否误杀成熟核心？没有。本文继续裁定 `socketioxide + socket.io-client` 是正式聊天 realtime 主链。
2. 是否低估外围屎山？没有。本文明确将私有重复轮子、重复真相、重复胶水和热点总控列为退场对象。
3. 是否留下第二文档入口？不应留下。旧两份 spec 的仍有效内容已吸收，旧文件应删除。
4. 是否把 child spec 机械拼进总纲？没有。已完成事实、主链边界、验收基线被保留，阶段叙事被降为历史基线。
5. 是否和媒体 spec 打架？没有。本文只管总规约和长期防漂移，媒体 spec 继续管媒体主链真相。
6. 是否保留了第一份的具体工程价值？保留。订阅、发消息、恢复链、contract、热点减压、graphify 和验证门禁都已进入本文。
7. 是否保留了第二份的长期治理价值？保留。核心 / 屎山定义、总执行顺序、长期防漂移、完成判定和文档关系都已进入本文。
8. 是否存在“只加不删”的风险？本文反复禁止，且本次文档融合应删除旧两个入口。
9. 是否用阶段路线替代总入口？没有。本文明确不再以阶段数为总路线。

结论：

**融合后的总纲必须只保留一个正式入口，同时保留旧两份文档各自的有效裁决；任何继续引用旧两份 spec 的入口，都应更新到本文。**

## 15. 最终硬裁决

以后在 `koko` 里，必须按下面这句话理解万人实时群聊去屎山：

**聊天 realtime 成熟主链继续复用，外围私有重复轮子、重复真相、重复胶水和热点总控必须退场；所有收口都必须让业务真相回到唯一 owner，让 adapter / shell / runtime 停止偷拿业务裁决，让旧路径真实删除，让热点实质减压，并用新鲜验证证明没有新 bug、没有功能退化、没有满血特性缩水。**

从这句话推出最终红线：

1. 禁止第二聊天核心。
2. 禁止第二恢复真相。
3. 禁止第二 transport 真相。
4. 禁止第二媒体主链。
5. 禁止前端平行业务真相。
6. 禁止 shared contract 倒灌壳专属语义。
7. 禁止纯包装、纯转发、纯 ceremony。
8. 禁止旧新双活。
9. 禁止临时补丁长期化。
10. 禁止没有新鲜验证宣布完成。
11. 禁止把 graphify 改名换路径冒充热点减压。
12. 禁止任何未来维护继续把热点养胖。
