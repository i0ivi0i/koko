# 媒体延迟优化：发送端即时做种 + 接收端即时播放

> 状态：draft
> 日期：2025-05-09

## 1. 问题

群聊中发送视频/图片后，接收方经历"黑色卡片占位 → 漫长等待 → 预览/播放"的体验。
核心瓶颈在于**当前整条链路是串行的**：

```
选文件 → 预处理 → TUS 上传 → completeMediaUpload(后端: torrent/thumbnail/DB)
  → 草稿 "ready" → 用户才能点发送
    → create_message → 后端广播 room_event
      → 接收方 locate() HTTP → fetch .torrent HTTP → join swarm → 找到 peer → 下载 → 播放
```

从"TUS 上传完成"到"接收方首帧"的延迟分解：

| 环节 | 耗时 |
|------|------|
| completeMediaUpload（torrent 生成 + thumbnail + DB） | 2-10s |
| 用户点发送 + 服务器广播 | ~200ms |
| 接收方 locate() HTTP | 200-500ms |
| 接收方 fetch .torrent HTTP | 100-300ms |
| 接收方 join swarm + 找到 peer + 首块下载 | 500-2000ms |
| **合计** | **3-13s** |

## 2. 目标

- **消除 complete 阻塞**：用户不再等 complete 就能发送
- **消除接收方 locate() 往返**：distribution 信息随 room_event 到达
- **发送者即时做种**：本地 torrent 生成完成就开始 WebTorrent seed
- **接收者即时播放**：room_event 到达后立即加入 swarm，视频字节就是画面
- **不需要独立预览帧管线**：视频自身的首帧就是最好的预览
- **不破坏 WebTorrent 唯一主链**：所有正式媒体字节仍走 P2P

## 3. 核心设计：前后端同一份 Rust 并行发力

### 3.1 关键洞察

后端 `生成附件torrent元信息` 是**纯确定性函数**：

```rust
// e:/koko/src/媒体/协作分发/共享语义.rs
pub(crate) fn 生成附件torrent元信息(
    content_hash: &str,   // SHA-256 of bytes
    稳定扩展名: &str,       // e.g. ".mp4"
    共享字节: &[u8],        // file bytes
) -> Result<附件torrent元信息, String>
```

- 文件名：`content-{content_hash}{ext}`
- piece_length：`PieceLength::OptBalanced`（由文件大小确定性计算）
- private：`true`

**同一字节输入 → 同一 info_hash 输出。** 把这份 Rust 代码编译成 WASM 跑在前端 →
前后端字面执行同一函数 → info_hash 100% 一致，零对齐风险。

### 3.2 新链路总览

### 3.3 延迟对比

| 环节 | 旧 | 新 |
|------|----|----|
| complete 阻塞 | 2-10s | **0**（异步） |
| locate() HTTP | 200-500ms | **0**（room_event 内含） |
| fetch .torrent | 100-300ms | 100-300ms（从缓存取） |
| join swarm | 500-2000ms | **200-500ms**（发送者已在 tracker） |
| **总计** | **3-13s** | **0.3-0.8s** |

## 4. 组件设计

### 4.1 WASM Crate：`koko-torrent-wasm`

新增 workspace member，编译目标 `wasm32-unknown-unknown`。

**依赖**：仅 `sha2`、`hex`、`wasm-bindgen`，以及 torrent 生成逻辑。

> **WASM 兼容风险**：`bip_metainfo` 0.12 内部可能依赖非 WASM 友好的 crate（如 `ring`）。
> 缓解方案：将 torrent 生成核心逻辑提取为不依赖 `bip_metainfo` 的纯计算函数，
> 仅使用 RustCrypto 生态的 `sha1`（piece hash）和 `sha2`（content hash），
> 加上极薄的 bencode 编码层。前后端共享这份提取后的代码，
> 后端可额外保留 `bip_metainfo` 做交叉验证。

**导出接口**：

```rust
#[wasm_bindgen]
pub fn generate_torrent(
    bytes: &[u8],
    extension: &str,  // e.g. ".mp4"
) -> JsValue {
    // 1. content_hash = hex(SHA-256(bytes))
    // 2. file_name = format!("content-{content_hash}{extension}")
    // 3. piece_length = opt_balanced(bytes.len())
    // 4. pieces = SHA-1 of each piece
    // 5. bencode info dict → torrent_bytes
    // 6. info_hash = hex(SHA-1(bencoded info dict))
    // → { content_hash, torrent_info_hash, torrent_bytes: Uint8Array }
}
```

**piece_length 算法**：必须与 `bip_metainfo::PieceLength::OptBalanced` 完全一致。
实现后用集成测试验证：对同一字节切片，提取函数和 `bip_metainfo` 产出相同 info_hash。

### 4.2 前端：Torrent 生成 Worker

新增 `torrent-generator.worker.ts`（或扩展现有 `源文件哈希.worker.ts`）。

```
输入: { type: "generate-torrent", requestId, file: File, extension: string }
处理: 读取 File 字节 → 调用 WASM generate_torrent() → 返回结果
输出: { requestId, ok: true, content_hash, torrent_info_hash, torrent_bytes: Uint8Array }
```

调用时机：`准备待上传媒体文件` 完成后（预处理后的文件），与 TUS 上传并行启动。

### 4.3 前端：草稿状态变更

```
当前: transporting → processing(complete) → ready
新增: transporting → ready(TUS完成 + WASM完成，不等 complete)
```

**协调逻辑**：草稿扩展两个标记：`tusComplete: boolean`, `torrentReady: boolean`。
当两者都为 true 时，草稿转为 `ready`。

`处理媒体上传成功事件` 变更：
- TUS 成功 → 设 `tusComplete = true` → 检查是否可转 ready → 异步启动 complete
- WASM 回调 → 设 `torrentReady = true` + 存储 `{ content_hash, info_hash, torrent_bytes }` → 检查是否可转 ready
- complete 完成 → 更新 preview_asset 等元数据（不再阻塞草稿状态）

### 4.4 前端：发送者即时做种

WASM Worker 返回 torrent 信息后：

```typescript
const torrent = runtime.client.seed(preprocessedFile, {
  name: `content-${contentHash}${extension}`,
  announce: [同源announce路径],
  private: true,
  // 注入 WASM 生成的 torrent 参数以确保 info_hash 一致
});
```

发送者同时用 `blob:` URL 播放本地文件（乐观预览），不等任何网络。

### 4.5 前端：发送者本地 blob 播放

发送者发送视频后，立即用本地文件的 `blob:` URL 播放：
- 草稿的 `previewUrl` 改为 `URL.createObjectURL(preprocessedFile)`
- 视频播放器识别到 `发送者本地源` 时直接使用 blob，不走 locate → swarm 链路
- WebTorrent seed 在后台运行，两者互不干扰
- 正式 swarm src 就绪后，发送者继续保留 blob（已经拥有完整文件）

### 4.6 后端：create_message 扩展

`create_message` 事件 payload 新增可选字段：

```json
{
  "room_id": "...",
  "client_message_id": "...",
  "text": "...",
  "attachment_ids": ["att-1"],
  "distribution_hints": [{
    "attachment_id": "att-1",
    "content_hash": "abc123...",
    "torrent_info_hash": "def456...",
    "torrent_bytes_base64": "ZDg6..."
  }]
}
```

后端处理：
1. **校验** attachment_id 属于当前会话且已 TUS 上传完成
2. **缓存** torrent_bytes（内存 HashMap，TTL 5 分钟，按 info_hash 键）
3. **签发** join_ticket（复用现有 `签发协作分发join_ticket` 逻辑）
4. **广播** room_event 时，attachment snapshot 携带 distribution 字段
5. **提供** torrent_url 端点：优先从缓存返回，miss 时从 DB 返回

### 4.7 后端：异步 complete

`completeMediaUpload` 不再阻塞前端草稿。它异步执行：
1. 读取上传字节 → 生成 torrent → **验证 info_hash 与 sender hint 一致**
2. 如不一致（理论不可能，同一 Rust 代码同一字节）→ 告警日志，以后端为权威
3. 生成 thumbnail / preview_asset
4. 写入 DB（分发元数据、preview_asset）
5. locator 端点可用（为晚加入者和刷新页面的用户服务）

### 4.8 前端：接收者即时播放

接收方收到 room_event：
1. **attachment snapshot 含 distribution** → 跳过 locate() HTTP 调用
2. 从 `torrent_url` fetch `.torrent` bytes（后端从缓存返回，~100ms）
3. `client.add(torrentBytes, { announce, joinTicket })` → 加入 swarm
4. 发送者已在 tracker 上 announce → 立即发现 peer → 开始下载
5. 视频字节到达 → `<video>` 元素渲染首帧 → 自动播放
6. 接收者自己也成为种子 → 互帮互助

**无需独立预览帧管线**——视频的第一块字节渲染出的画面就是最好的预览。

### 4.9 晚加入者兜底

complete 异步完成后，locator 端点正常可用。
页面刷新、新进房间、或 room_event 中 distribution 信息丢失时，
走现有 locate() → join swarm 链路，行为与当前一致。

## 5. 边界与约束

### 5.1 WebTorrent 唯一主链不变

- 发送者 blob 播放只是"本地消费同一文件"，做种照常
- 接收者严格通过 WebTorrent 下载视频字节
- 每个观看者自动成为种子
- 不引入 CDN、HLS、直链等第二真相

### 5.2 发送前仍需 TUS 完成

消息发送条件：`TUS 上传完成 AND WASM torrent 生成完成`。
理由：后端必须持有文件字节，确保：
- 发送者离线后 web_seed 兜底可用
- complete 可以异步执行
- 不会出现"消息发了但后端没有文件"的悬空状态

### 5.3 source_hash vs content_hash

- `source_hash`：原始文件的 SHA-256，用于跨房复用预检（现有）
- `content_hash`：预处理后文件的 SHA-256，用于 torrent 身份（新增）
- 视频经过 remux/transcode 时两者不同
- WASM Worker 输入的是**预处理后的文件**，产出 content_hash

### 5.4 Onion 架构遵守

| 层 | 变更 |
|----|------|
| **domain** | 无变更 |
| **application** | 无变更（torrent 生成是 infra 行为） |
| **contract** | `create_message` payload 新增可选 `distribution_hints`；room_event attachment snapshot 新增可选 `distribution` |
| **adapter** | 后端：缓存 torrent_bytes、签发 ticket、广播分发信息；前端：WASM Worker、种子管理 |
| **shell** | 前端：草稿协调逻辑、blob 播放、种子启动 |

### 5.5 图片也适用

同一设计对图片完全适用：
- 图片无预处理（passthrough）→ source_hash = content_hash
- WASM 生成 torrent → 发送者即时做种 → 接收者即时下载渲染

## 6. 风险与缓解

| 风险 | 缓解 |
|------|------|
| `bip_metainfo` 不能编译到 WASM | 提取核心逻辑为纯 RustCrypto 实现；后端保留 `bip_metainfo` 交叉验证 |
| piece_length 算法不一致 | 集成测试：同一字节 → 提取函数 vs `bip_metainfo` → 断言 info_hash 相同 |
| WASM 大文件性能（200MB SHA-256 + SHA-1 pieces） | Web Worker 隔离主线程；WASM SHA 性能接近原生 |
| 恶意客户端发送错误 torrent_bytes | 后端 complete 阶段独立验证 info_hash；不一致时告警并以后端为权威 |
| torrent_bytes 缓存 miss | 降级到现有 locate() → 从 DB 读取 torrent 链路 |

## 7. 自审修正点

### 7.1 distribution_hints 校验边界

后端收到 `distribution_hints` 时必须校验：
1. `attachment_id` 确实属于当前 session
2. 该 attachment 的 TUS 上传确实已完成（不能在上传中就声称有 torrent）
3. `torrent_bytes_base64` 解码后大小 ≤ 256KB（防止恶意大 payload）
4. `torrent_info_hash` 格式为 40 位 hex

校验不通过 → 忽略 distribution_hints，消息仍正常发送（降级到旧链路）。

### 7.2 complete 异步失败处理

消息已发但 complete 异步失败时：
- 缓存中的 torrent_bytes 在 TTL 到期后消失
- locator 端点返回 `attachment_not_ready`
- 晚加入者走现有降级路径（`MEDIA_CONNECTING_TO_PEERS` → 重试）
- 如果发送者和早期接收者仍在线，他们作为 seed 继续服务
- 后端应重试 complete（现有 retry 机制或新增 dead-letter 队列）

### 7.3 共享 torrent 生成模块

Phase 0 提取的共享模块必须：
- `no_std` 兼容（可选 `alloc`），确保 WASM 和 native 都可用
- 后端 crate 和 `koko-torrent-wasm` 都依赖同一个 `koko-torrent-core` 模块
- 后端可额外保留 `bip_metainfo` 做交叉验证断言

## 8. 实施阶段建议

### Phase 0：提取共享 torrent 生成函数
- 从 `bip_metainfo` 提取 piece_length 算法
- 实现纯 `sha1` + `sha2` + bencode 的 torrent 生成器
- 集成测试验证与 `bip_metainfo` 输出一致
- **验证**：对 1KB / 1MB / 50MB / 200MB 字节切片，提取函数 vs `bip_metainfo` 产出相同 `info_hash`

### Phase 1：WASM Crate + Worker
- 创建 `koko-torrent-wasm` crate
- 前端 Worker 集成
- 前端并行执行：TUS 上传 + WASM torrent 生成
- **验证**：浏览器内 Worker 对一个 10MB 测试文件产出与后端一致的 `info_hash`；build 产物 `.wasm` ≤ 200KB

### Phase 2：发送端即时做种 + 草稿状态解耦
- 草稿 ready 条件变更（不等 complete）
- 发送者 WASM 完成后立即 `client.seed()`
- 发送者 blob 本地播放
- **验证**：发送视频后，草稿在 TUS 完成时立即变 ready（不等 complete）；DevTools Network 中 complete 请求在消息发送后才开始；发送者可见本地 blob 播放

### Phase 3：create_message 扩展 + room_event 携带 distribution
- 后端接收并缓存 distribution_hints
- 后端广播时注入 distribution + join_ticket
- complete 改为异步
- **验证**：room_event payload 含 `distribution.torrent_info_hash`；`/api/media/{id}/torrent` 从缓存返回 ≤100ms；恶意 hint 被校验拒绝且消息正常发送

### Phase 4：接收端即时播放
- 接收方从 room_event 读取 distribution
- 跳过 locate() → 直接 join swarm
- 从发送者 peer 即时下载 → 渲染 → 播放
- **验证**：第二个浏览器标签收到视频消息后，DevTools 中无 locate() HTTP 调用；WebTorrent 连接到发送者 peer ≤ 2s；视频首帧渲染 ≤ 3s（从 room_event 到达计）
