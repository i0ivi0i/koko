# 群聊媒体秒达优化 Spec

> 目标：发送视频/图片后，群内所有人 **1 秒内看到消息、2 秒内自动播放开始**。
> 当前状态：发送后数秒才出现消息，自动播放再延迟数秒。

---

## 1. 现状瓶颈分析

### 完整时序链

```
发送者                                      服务器                                    接收者
  |                                           |                                         |
  |--- complete_media_upload (重活) ---------->|                                         |
  |<-- ready response (含 distribution) ------|                                         |
  |                                           |--- 尝试启动sidecar做种 (异步)            |
  |--- 用户点发送 --------------------------->|                                         |
  |    emit("create_message")                 |                                         |
  |    [无乐观消息!]                           |--- 创建消息_异步 (2-3 DB roundtrip) ---->|
  |                                           |--- emit("room_event") ----------------->|
  |<-- room_event (含最小附件信息) ------------|                                         |
  |    [消息才出现]                            |                  [消息出现, 无分发信息]   |
  |                                           |                                         |
  |                                           |<-- loadMediaLocator (HTTP) -------------|
  |                                           |--- locator (含 distribution) ---------->|
  |                                           |                                         |
  |                                           |              [WebTorrent 加入 swarm]     |
  |                                           |              [tracker 连接 + peer 发现]  |
  |                                           |              [自动播放开始]               |
```

### 瓶颈量化

| # | 瓶颈 | 影响 | 延迟贡献 |
|---|---|---|---|
| B1 | 发送者无乐观渲染 | 发送者自己也要等服务器 roundtrip 才看到消息 | ~200-500ms |
| B2 | 广播不含分发信息 | 每个接收者需额外 HTTP 请求获取 locator | ~100-300ms |
| B3 | WebTorrent 冷启动 | tracker 连接 + peer discovery | ~500ms-数秒 |
| B4 | sidecar 做种时序 | complete 返回后才异步启动做种，接收者可能比 sidecar 更早到达 swarm | ~200-1000ms |

### 受影响代码

- **B1**: `frontend/实时/应用.ts:259-271` — `attachmentIds.length === 0` 时才创乐观消息
- **B2**: `src/外壳/协议响应.rs:33-67` — `attachments_to_json` 只输出 kind/id/width/height
- **B2**: `src/共享/契约基础.rs:146-174` — `附件快照` 枚举无分发字段
- **B3**: `frontend/媒体/媒体播放.ts:107` — `连接群友窗口毫秒 = 8_000`
- **B4**: `src/媒体/上传/外壳/完成上传.rs:624-641` — complete 成功后才调 sidecar

## 2. 优化方案

### Phase 1：乐观渲染（砍掉 B1，效果最大）

**改动范围**: 仅前端

**核心思路**: 带附件的消息也立即插入时间线，用发送者本地已有的 complete 响应数据渲染。

#### 2.1.1 改动点

**`frontend/实时/应用.ts` — `sendMessage()`**

当前逻辑：
```typescript
if (attachmentIds.length === 0) {
  deps.接收时间线事实({ type: "OPTIMISTIC_MESSAGE_ADDED", ... });
}
```

改为：无论有无附件，都创建乐观消息。乐观消息的 attachments 从当前 `composerMediaDrafts` 中读取已 ready 的附件元数据（kind, attachment_id, width, height）。

**`frontend/时间线/领域.ts` — `创建乐观房间消息()`**

扩展输入，接受可选的 `attachments` 数组：
```typescript
export type 创建乐观房间消息输入 = {
  // ...现有字段
  attachments?: Array<{
    kind: "image" | "video";
    attachment_id: string;
    width: number;
    height: number;
  }>;
};
```

乐观消息的 `attachments` 字段直接从输入填充。

**`frontend/媒体/媒体草稿.ts` — 新增 `提取可发送媒体附件元数据()`**

从 `composerMediaDrafts` 中提取 ready 草稿的 attachment 元数据，供乐观消息使用。

#### 2.1.2 乐观消息与权威消息的合流

已有机制已经处理了这个问题：
- `时间线/领域.ts` 的 `选择更可信消息()` 会用 `client_message_id` 匹配，权威消息到达时自动替换乐观消息
- 乐观消息的 `message_id` 以 `local-` 开头，`是本地乐观消息()` 可识别
- 附件渲染依赖 `attachment_id`，乐观消息和权威消息引用同一个 `attachment_id`，因此渲染连续无闪烁

#### 2.1.3 发送者的媒体播放

发送者在 `complete` 响应中已经拿到了完整的 locator + distribution 信息。乐观消息出现后，媒体播放链会尝试 `获取定位(attachment_id)`，此时 locator 已在缓存中（complete 返回时前端应写入缓存）。

**前置确认（必须先验证再动手）**: complete 响应中的 distribution 信息是否已缓存到 `媒体定位器` 中。
- 如果**已缓存**：乐观消息出现后，媒体播放链直接命中缓存，零额外 HTTP 请求。
- 如果**未缓存**：必须在 complete 成功后将 locator 预写入 `媒体定位器` 缓存（`repo.保存()`），否则乐观渲染的效果被后续 HTTP locator 请求抵消。
- 验证方法：在 `处理媒体上传成功事件()` 中 complete 返回后，检查 `媒体定位器.读取缓存(attachmentId)` 是否有值。

#### 2.1.4 预期效果

- 发送者：消息 **立即出现**（0ms），不再等 socket roundtrip
- 接收者：不变（仍等 socket 广播）

### Phase 2：广播携带分发信息（砍掉 B2）

**改动范围**: 后端 contract + 序列化 + 前端消息处理

**核心思路**: `room_event` 广播中的 attachment 带上 distribution 线索，接收者无需额外 HTTP 请求即可加入 swarm。

#### 2.2.1 后端改动

**`src/共享/契约基础.rs` — 扩展 `附件快照`**

附件快照增加**可选**的分发线索：

```rust
pub struct 视频附件快照 {
    pub 附件标识: String,
    pub 宽: i32,
    pub 高: i32,
    pub mime_type: String,
    pub 有预览图: bool,
    // Phase 2 新增：广播携带分发线索
    pub 分发线索: Option<附件分发线索>,
}

pub struct 附件分发线索 {
    pub content_hash: String,
    pub swarm_id: String,
    pub torrent_info_hash: String,
    pub web_seed_until秒: i64,
}
```

同理 `图片附件快照` 也加上。

**洋葱边界约束**：`附件分发线索` 是**可选投影字段**，不参与消息成立的领域校验。domain 层的 `创建消息()` 函数不读取、不校验此字段。它仅在 adapter 序列化 `event_to_json()` 时投影到 JSON 输出中，供前端壳层优化使用。

**`src/消息/应用.rs` — `创建消息_异步()` 的附件查询**

当前 `读取待发送附件()` 只读 kind/id/width/height。需要同时带出 distribution 元数据（content_hash, swarm_id, torrent_info_hash, web_seed_until）。

这些数据已经在 `media_attachment_distributions` / `media_attachment_torrent_meta` 表中，可以 JOIN 一次读出。

**`src/外壳/协议响应.rs` — `attachments_to_json()`**

序列化时增加分发线索字段。但**不包含**：
- `join_ticket`（受控签名，不能广播给所有人）
- `announce_urls`（每个客户端自己从后端获取）
- `web_seed_url`（受控地址，需要 session 签名）
- `presence_url`（受控地址）

只广播**公开不变的**分发线索：
```json
{
  "kind": "video",
  "attachment_id": "xxx",
  "width": 1920,
  "height": 1080,
  "distribution_hint": {
    "content_hash": "abc123...",
    "swarm_id": "swarm_abc123...",
    "torrent_info_hash": "def456...",
    "web_seed_until": 1715500000
  }
}
```

#### 2.2.2 前端改动

**`frontend/聊天共享/契约.ts` — `消息事件` 的 attachment 类型**

attachment 增加可选 `distribution_hint` 字段。

**`frontend/媒体/媒体定位.ts` — 预写入 locator 缓存**

收到含 `distribution_hint` 的 `room_event` 时，前端可以用 hint 构造一个**部分 locator**，预写入 `媒体定位器` 缓存。这个部分 locator 包含 `torrent_info_hash` 和 `swarm_id`，足够让前端提前开始 WebTorrent 对等搜索。

但正式播放仍需完整 locator（含 join_ticket、web_seed_url 等），因此：
- 部分 locator 标记为 `stale: true`，且写入时使用**接收者自己的 sessionId**（`deps.getSessionId()`），确保 `缓存命中当前会话()` 检查通过
- 自动播解析时，如果缓存中有 `stale` 记录且含 swarm 线索，先发起 WebTorrent peer discovery（只连接不下载），同时并行请求完整 locator
- 完整 locator 到达后替换缓存，正式开始下载

#### 2.2.3 预期效果

- 接收者：消息出现后 **0ms** 即可开始 peer discovery（省掉 100-300ms HTTP roundtrip）
- 实际效果：peer discovery 和 locator 获取并行，总延迟取两者最大值而非之和

### Phase 3：WebTorrent 预热（缩短 B3）

**改动范围**: 仅前端

**核心思路**: 收到 `room_event` 含 distribution_hint 时，立即开始 tracker 连接和 peer discovery，不等自动播裁决。

#### 2.3.1 预热策略

当前自动播链路：
```
消息出现 → 渲染 → IntersectionObserver 观测到可见 → 80ms settle → 解析播放结果 → 获取定位 → swarm 加入
```

优化后：
```
消息出现 → [后台] 预热 swarm 连接（不下载）
         → 渲染 → IntersectionObserver 观测到可见 → 80ms settle → 解析播放结果 → [swarm 已热] → 立即开始
```

#### 2.3.2 改动点

**`frontend/媒体/播放会话/应用.ts` — 新增 `预热媒体分发()`**

当时间线收到新消息且附件含 `distribution_hint` 时：
1. 如果 `torrent_info_hash` 存在，立即通知协作分发运行时预建 tracker 连接
2. 不创建正式媒体会话，不占用播放器资源
3. 仅建立 tracker WebSocket 连接并发出 announce（告知 swarm "我在这里"）

**约束**:
- 预热上限 2 条（复用 `自动播预览预热候选上限`）
- 消息滚出视口后释放预热连接
- 预热连接可被正式媒体会话接管，避免重复连接

#### 2.3.3 预期效果

- 接收者：自动播触发时 tracker 连接已建立，peer 已发现，直接开始下载
- 预计省掉 **300-800ms** tracker 连接 + peer discovery 时间

---

### Phase 4：做种时序前移（缩短 B4）

**改动范围**: 后端

**核心思路**: 确保 sidecar 在接收者到达 swarm 之前已经准备好做种。

#### 2.4.1 当前问题

`complete_media_upload` 的做种触发在 HTTP 响应返回前的最后一步：

```rust
// src/媒体/上传/外壳/完成上传.rs:624
if let Some(启动命令) = 从协作分发响应构造做种启动命令(...) {
    if let Err(err) = 尝试启动协作分发做种(&state, &启动命令).await { ... }
}
```

这意味着：
1. complete 返回 → 前端收到 ready → 用户点发送 → 服务器广播 → 接收者收到
2. 做种启动是 complete 内部的最后一步，但 sidecar 启动、torrent 加载、tracker 注册还需要时间
3. 接收者可能在 sidecar 完成注册前就查询 tracker，导致初始 "no peers"

#### 2.4.2 改动点

**`src/媒体/上传/外壳/完成上传.rs`**

将做种触发从 complete 响应流程中**提前**。不用改时序——当前已经在返回前调用了。但要确保：

1. **做种启动改为 fire-and-forget 并发**：当前是 `.await` 等待 sidecar 响应，但 complete 不应等它。改为 `tokio::spawn` 让做种在后台完成，complete 立即返回，让前端更早拿到 ready 响应。

2. **消息广播后再次确认做种**：在 `handle_realtime_create_message` 中，消息成功广播后，如果消息含视频附件，异步检查该附件的 sidecar 是否已在做种，如果没有则补发启动命令。这是兜底，不是主链。

#### 2.4.3 预期效果

- 做种启动不再阻塞 complete 响应（省 ~50-200ms complete 延迟）
- 消息广播时 sidecar 大概率已就绪
- 兜底确认消除了竞态窗口

## 3. 实施优先级与风险

| Phase | 难度 | 风险 | 效果 | 建议顺序 |
|---|---|---|---|---|
| Phase 1: 乐观渲染 | 低 | 低（已有合流机制） | **高**（发送者延迟→0） | 🥇 第一 |
| Phase 4: 做种时序 | 低 | 极低（仅改 await→spawn） | 中（减少 sidecar 竞态） | 🥈 第二 |
| Phase 2: 广播带分发 | 中 | 中（改 contract） | **高**（省掉接收者 HTTP RT） | 🥉 第三 |
| Phase 3: swarm 预热 | 中 | 中（新前端概念） | 高（peer discovery 前移） | 🏅 第四 |

### Phase 1 + Phase 4 可以独立交付

这两个改动互不依赖，侵入度最低，合起来就能把发送者延迟砍到接近 0、接收者做种可用性提高。

### Phase 2 + Phase 3 是一对

Phase 3 的 swarm 预热依赖 Phase 2 在广播中携带 `torrent_info_hash`。这两个应一起设计、分步实施。

## 4. 验证标准

### 烟测场景

1. **发送者秒见**: 发送带视频的消息后，消息立刻出现在时间线（< 100ms）
2. **接收者秒见**: 另一个浏览器标签页中，消息出现延迟 < 1s（socket roundtrip + render）
3. **自动播放秒达**: 接收者看到视频消息后，自动播放在 2s 内开始
4. **乐观消息替换无闪烁**: 权威消息到达时，附件渲染不闪烁、不重新加载

### 可观测指标

- 后端 `complete_heavy_work_stage` 日志中 `seed_start` 不再出现（因为不 await 了）
- 前端 `INLINE_AUTOPLAY_PLAYBACK_RESOLVED` 事件的时间戳 - `room_event` 到达时间戳 < 2s
- `loadMediaLocator` 请求数：Phase 2 之后，新消息的首次 locator 请求应减少（缓存命中）

## 5. 洋葱边界检查

| 改动 | 层 | 是否越界 |
|---|---|---|
| 乐观消息增加 attachments | shell (前端时间线) | ✅ 不越界，仅壳层展示投影 |
| `附件快照` 增加分发线索 | contract | ✅ 属于共享契约扩展，分发线索是稳定业务事实 |
| `attachments_to_json` 序列化分发线索 | adapter (协议响应) | ✅ 不越界，adapter 负责翻译 |
| `创建消息_异步` JOIN 分发表 | adapter (消息适配) | ✅ 不越界，SQL 适配层的读取职责 |
| swarm 预热 | shell (前端媒体壳层) | ✅ 预热是壳层体验编排，不改媒体会话 owner |
| 做种 spawn 化 | shell (后端外壳) | ✅ 不越界，sidecar 调用属于外壳基础设施编排 |

## 6. 不做的事

- **不在广播中携带 `join_ticket`**: ticket 是受控签名，必须每连接单独签发
- **不在广播中携带 `web_seed_url`**: 冷源 URL 受控，需要 session 维度签名
- **不预下载媒体字节**: 预热只建立 tracker 连接，不消耗带宽
- **不改变 WebTorrent 做正式字节入口的架构**: 优化的是时序，不是数据流
- **不新增 HLS/DASH 第二真相**: 继续只走 WebTorrent whole-file swarm
