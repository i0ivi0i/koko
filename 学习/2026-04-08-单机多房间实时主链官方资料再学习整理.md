# 2026-04-08 单机多房间实时主链官方资料再学习整理

适用范围：`koko` 当前“单机内多房间实时在线 + 群聊发送主链 + 已读/恢复同步链”的下一步架构判断。  
目标：只收一手资料里最硬的结论，不空谈“高并发很复杂”，而是回答：**官方和成熟 IM 到底把哪些东西当主链，哪些东西当辅助层。**

---

## 1. 先给结论

如果先不谈硬件、负载均衡、多机分布式，只谈**单机内代码架构**，那一个多人多房间群聊要想“实时且稳”，优先级最高的不是花哨广播技巧，而是下面这 5 条：

1. **房间内事件顺序必须有唯一权威锚点。**
2. **socket 只负责快通道，不负责最终一致性。**
3. **断线、漏事件、重进房必须能补洞。**
4. **房间广播分组和业务成员真相必须分开。**
5. **发送命令收到、消息真正成立、客户端看到回流，这三件事必须分开。**

一句大白话：

**成熟 IM 从来不是“在线时看起来很快”就算成功，而是“离线重进、漏消息、热房间、多人并发时仍然不乱”。**

---

## 2. `socket.io` 官方真正强调的是什么

### 2.1 默认只保证顺序，不保证必达

Socket.IO 官方文档写得很直接：

- 会保证消息顺序。
- 但默认投递是 **at most once**。
- 连接断掉时，服务端不会自动替断线客户端补发它错过的事件。
- 额外投递保证，必须由应用自己实现。

来源：

- [Socket.IO Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)

对 `koko` 的直接启发：

1. 不能把“当前 socket 还在线”当成消息同步真相。
2. 不能把“广播发出去了”当成“以后客户端一定都能补到”。
3. 必须保留 `event_position / snapshot / 增量补洞` 这条链，不能为了省事削掉。

### 2.2 官方给出的 server -> client 正路就是：唯一事件 ID + 落库 + offset

同一份官方文档还明确给了服务端到客户端“额外保证”的实现思路：

1. 给每条事件一个唯一 ID。
2. 事件持久化到数据库。
3. 客户端保存自己最后处理到的 offset。
4. 重连时把 offset 带回来，服务端按 offset 补缺失事件。

这和我们现在坚持的 `latest_event_position + snapshot + room_events` 思路是同路的。

来源：

- [Socket.IO Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)

### 2.3 connection state recovery 只是缓冲垫，不是总真相

Socket.IO 官方 4.6+ 的 connection state recovery 能恢复一部分断线状态，但官方也明确提醒：

- 临时断线不可避免；
- recovery **不会总是成功**；
- 所以应用层仍然必须准备“客户端和服务端重新同步”。

来源：

- [Socket.IO Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/)

对 `koko` 的直接启发：

1. 可以把 recovery 当“临时加速”，不能把它当“唯一恢复方案”。
2. `need_snapshot_reload` 这种控制面回退不是丑陋补丁，而是官方正路。

### 2.4 rooms 是服务端广播概念，不是业务成员真相

Socket.IO 官方明确说：

- room 是 server-only concept；
- 客户端拿不到自己加入过哪些 room；
- 多 room 广播是 union 语义；
- socket 断开时会自动 leave 所有 room。

来源：

- [Socket.IO Rooms](https://socket.io/docs/v4/rooms/)

对 `koko` 的直接启发：

1. `room.join/leave` 只能表达“这个连接在哪些广播分组里”。
2. 真正“是不是成员”“能不能发言”“能不能看到消息”，只能在后端 `application/domain` 裁决。
3. 这正好符合 DDD：**广播分组不是业务事实。**

### 2.5 `retries + ackTimeout` 只能说明“命令收到”，不能说明“消息成立”

Socket.IO 官方客户端文档说明：

- `ackTimeout` 必须和 `retries` 一起用；
- 如果服务端不 ack，客户端会重试；
- 这只能说明“服务端回没回你这个 emit”，不是“业务已经成立”。

来源：

- [Socket.IO Client options](https://socket.io/docs/v4/client-options/)

对 `koko` 的直接启发：

1. 前端可以未来在**控制面命令**上用 ack/retry。
2. 但“消息已创建”仍然必须以权威 `room_event` 回流为准。

## 3. `socketioxide` 官方真正有价值的点

### 3.1 它是 Tower/Hyper 生态里的 Socket.IO server，不是业务内核

`socketioxide` 官方 crate 文档写得很清楚：

- 它是 Rust 的 socket.io server 实现；
- 作为 tower layer/service 工作；
- 和 `tokio / hyper / tower` 生态天然兼容；
- 完全兼容官方 Socket.IO client。

来源：

- [socketioxide crate docs](https://docs.rs/socketioxide/latest/socketioxide/)

对 `koko` 的直接启发：

1. `socketioxide` 就应该待在 adapter/realtime 层。
2. 不能为了“更纯”再手搓一套私有房间广播核心。

### 3.2 官方明确：每条消息/连接 handler 都会被放进新任务，不阻塞事件管理主循环

crate 文档写了：

- 每个 incoming connection/message 都会 spawn 新任务，
- 目的是不阻塞 event management task。

来源：

- [socketioxide crate docs](https://docs.rs/socketioxide/latest/socketioxide/)

这条的含义不是“你一定高性能”，而是：

**框架没有先天把你锁死在单线程串行事件循环里。**

所以后面如果慢，更多是你自己的业务热路径、数据库串行点、广播方式、背压策略在慢。

### 3.3 官方建议：不要自己长期保存 `SocketRef`

crate 文档明确提醒：

- `SocketRef` 不应该被你长期塞进自己的 `HashMap/Vec`；
- 否则断开时得自己清理，不然会有内存泄漏风险；
- 真要跨 handler/任务广播，优先拿可便宜 clone 的 `SocketIo` 句柄。

来源：

- [socketioxide crate docs](https://docs.rs/socketioxide/latest/socketioxide/)

对 `koko` 的直接启发：

1. 不要自己手搓“room -> sockets 列表”。
2. 继续让 `socketioxide` adapter 负责房间成员与 fanout。

### 3.4 官方广播语义已经足够清楚

`Socket` 文档里把这些操作边界说得很明白：

- `to(room)`：发给房间其他人，不含当前 socket。
- `within(room)`：发给房间所有人，包含当前 socket。
- `emit_with_ack`：用于等客户端 ack。
- 广播 `emit()` 在涉及远端 adapter 时要 `await`。

来源：

- [socketioxide Socket docs](https://docs.rs/socketioxide/latest/socketioxide/socket/struct.Socket.html)

对 `koko` 的直接启发：

1. 发送者自己看到的消息回流，可以继续走 `within(room)` 这种权威事件广播。
2. 这比前端自己拼第二套“本地成立消息”更稳。

### 3.5 官方适配器设计说明了一件事：多节点是以后可以长出来的，不必先手搓

crate 文档说明：

- 默认是 `LocalAdapter`；
- 也支持 Redis / Postgres / Kafka 等跨节点 adapter 方向；
- 真要用别的 adapter，要让相关 extractor 泛型化。

来源：

- [socketioxide crate docs](https://docs.rs/socketioxide/latest/socketioxide/)

对 `koko` 的直接启发：

1. 当前单机可以先把主链做对；
2. 不必现在就自己造跨节点广播层；
3. 但热路径代码要避免写死在“只有本机内存广播”这一种假设上。

## 4. Telegram 官方资料给出的 IM 共识

### 4.1 核心不是“永远在线”，而是“任何时候都能补齐更新”

Telegram 官方 `Working with Updates` 文档写得极其硬核：

- 更新通过连接推送；
- 客户端必须维护本地 `seq / pts / qts` 状态；
- 收到更新后要检查是否有 gap；
- 一旦有 gap，就必须用 `updates.getDifference / updates.getChannelDifference` 补齐；
- 启动时也要主动拉离线期间差量；
- 对用户当前正在看的频道/超级群，还建议持续短轮询差量。

来源：

- [Telegram Working with Updates](https://core.telegram.org/api/updates)

这说明成熟 IM 的真正主链是：

**push 实时通知 + 本地同步状态 + gap repair + 必要时差量轮询。**

### 4.2 已读真相是逻辑锚点，不是滚动条像素

Telegram 官方 schema 里 `dialog` 明确有：

- `top_message`
- `read_inbox_max_id`
- `unread_count`

`messages.readHistory` 也明确按 `max_id` 把消息读到某个逻辑上限。

来源：

- [Telegram dialog](https://core.telegram.org/constructor/dialog)
- [Telegram messages.readHistory](https://core.telegram.org/method/messages.readHistory)

对 `koko` 的直接启发：

1. 继续坚持 `event_position` 是已读真相锚点。
2. 前端滚动位置只是观测工具，不是真相本身。

### 4.3 Telegram 对“当前正在看的会话”会给更多同步力度

Telegram 官方建议：

- 对当前正在看的频道/超级群，客户端应该周期性调用 `updates.getChannelDifference`；
- 而不是只被动等 socket 推送。

来源：

- [Telegram Working with Updates](https://core.telegram.org/api/updates)

对 `koko` 的直接启发：

1. “用户当前停留在房间里”这件事，值得给更高同步优先级。
2. 当前我们已有 `snapshot + events + realtime`，以后可以继续向“在看中的房间更积极补洞”演进。

## 5. WhatsApp 官方公开资料给出的 IM 共识

### 5.1 真正的问题不是“能不能多端在线”，而是“多端在线时谁是 source of truth”

Meta 官方工程文章写得很清楚：

- 旧方案里手机是 source of truth，其他设备只是镜像；
- 这会导致慢、断线多、可靠性差；
- 新 multi-device 架构不再要求手机当唯一真相源。

来源：

- [How WhatsApp enables multi-device capability](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)

对 `koko` 的直接启发：

1. 不要把“某个在线 socket”或“某个前端标签页”当真相源。
2. 真相仍然应在后端权威事件流和持久化状态里。

### 5.2 每个设备各自连接，但同步靠稳定映射和本地数据库

同一篇文章里还说：

- 每个设备有自己的 identity key；
- 服务端维护账号到设备身份的映射；
- 新设备初次接入时会拿一份最近历史；
- 之后设备从自己的本地数据库继续工作；
- 其他应用状态会持续同步。

来源：

- [How WhatsApp enables multi-device capability](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)

对 `koko` 的直接启发：

1. “初次快照 + 后续增量”是成熟 IM 共识。
2. 前端壳层应努力做成本地可恢复，但仍然只消费后端真相。

### 5.3 群聊扩展靠 sender key / fanout，不靠把业务判断塞进实时层

公开文章提到：

- 一对一消息走 client fanout；
- 群组继续使用可扩展的 sender key 方案；
- 重点始终是“安全和同步模型”，不是在实时层临时裁业务。

来源：

- [How WhatsApp enables multi-device capability](https://engineering.fb.com/2021/07/14/security/whatsapp-multi-device/)

对 `koko` 的直接启发：

1. 即使未来扩展大群、高热房间，也不该把成员判断、消息真相塞进 socket handler。
2. handler 仍然只应该做：接命令、转用例、发权威事件。

## 6. 把这些资料压缩成 `koko` 当前最该守住的 8 条

1. **同一房间内，消息顺序锚点只能有一个权威拥有者。**  
   现在这个拥有者就是后端落库时推进的 `event_position`。

2. **socket 在线态不是业务真相。**  
   它只是快通道。

3. **广播成功不是消息成立。**  
   先落库，再广播，这条不能倒。

4. **房间 room 不是成员资格真相。**  
   room 只是实时广播分组。

5. **断线恢复要靠快照 + 增量补洞。**  
   recovery 能用就用，但不能依赖它永远成功。

6. **发送者自己也应该看见同一条权威事件回流。**  
   不要让发送者走另一条“本地假成立”主链。

7. **单机内允许单房间为顺序而串行，不允许所有房间互相陪葬。**  
   这是当前发送热路径优化最该盯住的地方。

8. **前端只优化体感，不裁决真相。**  
   即使要做乐观态，也只能是壳层体验，不是第二真相源。

---

## 7. 对当前 `koko` 的直接落地判断

结合这些资料，`koko` 现在最对的方向是：

1. 继续保留 `socketioxide + socket.io-client` 这套主通道，不要自毁成熟轮子。
2. 继续坚持 `event_position + snapshot + history + room_events` 这条同步锚点主链。
3. 下一步真正该收的是：
   - 发送热路径里不必要的查询和等待；
   - 单房间热点对整机其他房间的拖累；
   - 发送者自己看到权威消息回流的体感延迟；
   - 当前房间视图的补洞与已读推进时机。

一句话总结：

**官方和成熟 IM 反复证明的不是“永远在线就够了”，而是“把权威锚点、补洞、房间分组、业务真相、前端体感这五件事分清楚”。**
