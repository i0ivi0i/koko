# 2026-04-06 群聊主通道下一步官方资料与高性能榜样补充

目的：

这份笔记只服务 `koko` 下一步实现，不讨论泛泛架构。
重点回答 4 件事：

1. `socketioxide` 官方到底建议怎么用
2. `socket.io` 官方在房间、投递、恢复、测试、多节点上到底怎么说
3. 高性能群聊榜样在“发送成功、事件流、补洞恢复”上到底怎么做
4. 我们下一步哪些可以直接复用，哪些绝不能手搓第二套轮子

补充提醒：

- 当前仓库实际依赖的是 `socketioxide 0.16.x`
- 这份资料查的是官方最新 `docs.rs` 与 `socket.io 4.x`
- 语义层基本一致，但后面真抄 API 代码时，必须回到当前锁定版本再核一遍签名与配置项

---

## 1. 这轮最该信谁

第一优先：

- `socketioxide` 官方文档与 `docs.rs`
- `socket.io` 官方文档

第二优先：

- Discord 官方开发者文档
- Telegram 官方更新同步文档
- Matrix 官方 Client-Server Sync 文档

结论：

- `koko` 的实时基础设施语义，先按 `socket.io` 官方模型理解
- Rust 落地细节，按 `socketioxide` 官方方式写
- 补洞与恢复的思路，可借鉴 Telegram / Matrix 这种“有序事件流 + 本地游标 + 缺口恢复”的成熟做法

---

## 2. socketioxide 官方，下一步最相关的硬建议

### 2.1 它本来就是按 socket.io 语义设计的

`socketioxide` 官方明确说：

- Fully compatible with the official `socket.io` client
- API tries to mimic the equivalent JS API as much as possible

这意味着：

- room
- connect middleware
- extensions
- operators
- adapter
- ack

这些都应该优先按官方模型用，不要自己再包一层私有 realtime 核心。

来源：

- [socketioxide docs.rs](https://docs.rs/socketioxide/latest/socketioxide/)

### 2.2 connect middleware 才是认证收口点

官方说明：

- connect middleware 在 namespace 连接前执行
- middleware 返回 `Err` 时，连接会被拒绝，并通过 `connect_error` 回给客户端
- middleware 里不能给还未完成 namespace 连接的 socket 发业务消息

这正对应我们现在已经在做的事：

- `auth.session_id` 进 connect middleware
- 在 middleware 里只做会话存在性校验
- 不在这里做房间权限或业务发送

来源：

- [socketioxide connect handler / middleware 文档](https://docs.rs/socketioxide/latest/socketioxide/)

### 2.3 `Extension` / `State` 是正路，`SocketRef` 长持不是

官方说明：

- `Extension` 用来存 per-socket 数据
- `State` 用来存全局共享状态
- `SocketRef` 不应长期存进你自己的 `HashMap/Vec`，否则要自己清理断连，容易泄漏

对应 `koko` 的边界：

- `session_id` 放 socket extension
- 共享 `PgPool` / runtime handle 放应用共享状态
- 禁止手搓 `room -> sockets` 广播表

来源：

- [socketioxide docs.rs](https://docs.rs/socketioxide/latest/socketioxide/)

### 2.4 Builder 上真正和性能相关的项

这轮最相关的 builder 配置是：

- `max_payload`
- `max_buffer_size`
- `ack_timeout`
- `connect_timeout`
- `ping_interval`
- `ping_timeout`
- `transports`
- `ws_read_buffer_size`
- `with_state`
- `with_adapter`

现阶段判断：

- 单节点先不急着魔改这些值
- 但要知道 `max_buffer_size` 满了时 `emit()` 会报错
- 后续要做日志与背压门禁时，优先围绕这些官方配置，不自己造“内部消息队列配置体系”

来源：

- [SocketIoBuilder 文档](https://docs.rs/socketioxide/latest/socketioxide/struct.SocketIoBuilder.html)

## 3. socket.io 官方，下一步最相关的硬建议

### 3.1 Room 只是服务端广播分组，不是真相

官方明确说：

- room 是 server-only concept
- client 端并不持有“自己加入了哪些 room”的真相

这和 `koko` 的 DDD 边界完全一致：

- room 只能当广播分组
- 成员真相仍然必须由领域 / 应用层裁决

来源：

- [Socket.IO Rooms](https://socket.io/docs/v4/rooms/)

### 3.2 多房间选择是并集，不是多次重复发送

官方说明：

- 给多个 room 广播时，做的是 union
- 同一个 socket 即使在多个 room，也只会收到一次

这提醒两件事：

1. 不要自己在业务层再做“去重广播”
2. 如果一个连接未来加入多个群，广播去重先信 operator 语义，不自己补私有去重层

来源：

- [Socket.IO Rooms](https://socket.io/docs/v4/rooms/)

### 3.3 默认只有 at most once，不要自欺欺人

官方说明：

- 默认投递保证是 `at most once`

这意味着：

- 单靠 socket 推送，不能假装天然不丢
- 真正想补强服务端到客户端恢复，必须自己保留事件 ID、持久化、客户端 offset

来源：

- [Socket.IO Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)

### 3.4 官方给的“服务端到客户端补强方案”正好就是我们现在该走的路

官方建议要素：

1. 给每个事件唯一 ID
2. 把事件持久化到数据库
3. 客户端保存最后收到的 offset
4. 重连时把 offset 带回来

这和 `koko` 现在的主链高度一致：

- `event_position`
- `message_id`
- `client_message_id`
- 持久化 `room_events`
- 重连订阅带 `from`

结论：

我们不该再造第二套恢复协议，只需要把现有 `event_position` 路走硬。

来源：

- [Socket.IO Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)

### 3.5 connection state recovery 不是权威补洞真相

官方说明：

- state recovery 适合 temporary disconnection
- server 会在适配器层暂存一段时间的状态
- reconnect 时客户端会带 session ID 和 last offset，服务端尝试恢复

结论：

- 这可以当“短暂断线加速器”
- 不能替代 `koko` 自己基于 `event_position` 的权威补洞
- 单节点现在先不依赖它当主恢复机制

来源：

- [Socket.IO Connection state recovery](https://socket.io/docs/v4/connection-state-recovery/)

### 3.6 官方 testing 范式就是“真实 server + 真实 client”

官方 testing 文档直接给了 `vitest + socket.io-client` 的模式。

这正是我们已经采用并应继续坚持的方向：

- 不要手搓第二套 websocket 假客户端
- 不要只靠内部假对象证明 realtime 主链
- 继续用真实 `socket.io-client` 跑主链验收

来源：

- [Socket.IO Testing](https://socket.io/docs/v4/testing/)

### 3.7 多节点前，sticky-session 和 transport 约束要先记牢

官方说明：

- 多节点时，如果启用了 long-polling，就需要 sticky sessions
- 否则会出现 `Session ID unknown` / HTTP 400
- 但如果只用 websocket transport，则没有这个 sticky-session 限制

这和我们当前单节点设计很匹配：

- 第一阶段继续 `transports: ["websocket"]`
- 未来上多节点时，优先保持 websocket-only，减少 sticky 复杂度

来源：

- [Socket.IO Using multiple nodes](https://socket.io/docs/v4/using-multiple-nodes/)

### 3.8 前端认证入口优先走 `auth`，不要把会话塞回 query

官方 `client options` 明确给了 `auth`：

- 进入 namespace 时携带凭证
- server 端从 `socket.handshake.auth` 读取
- 如果收到 `connect_error`，客户端可以更新 `socket.auth` 后重连

这和我们现在的做法是一致的：

- 前端继续走 `auth.session_id`
- 禁止为了“兼容一点”又把会话真相塞回 query string

来源：

- [Socket.IO Client options](https://socket.io/docs/v4/client-options/)

### 3.9 websocket-only 是当前阶段的合理收口，但要记住官方回退建议

官方说明：

- 只用 `transports: ["websocket"]` 时，服务端不需要 sticky sessions
- 如果要做 websocket-first 再回退，官方建议在 `connect_error` 时把 transport 顺序切回经典模式

对应 `koko`：

- 单节点阶段继续 websocket-only 是对的
- 未来若遇到弱网或代理兼容问题，再按官方回退建议做，不先手搓 transport 策略机

来源：

- [Socket.IO Client options](https://socket.io/docs/v4/client-options/)

### 3.10 `retries + ackTimeout` 只能用于“命令是否被接住”，不能晋升成消息成立语义

官方说明：

- `retries` 要和 `ackTimeout` 配合
- 如果服务端不 ack，客户端会重复发送，直到超限后丢弃

这对 `koko` 的警告非常明确：

- 这套机制可以用在控制面命令
- 绝不能拿来宣布“消息已经成立”
- 否则就会重新长出“ACK 真相”这套假系统

来源：

- [Socket.IO Client options](https://socket.io/docs/v4/client-options/)

## 4. 高性能群聊榜样，下一步最该学什么

### 4.1 Discord：发送成功不等于只看请求返回，要看事件流

Discord 官方消息资源文档写得很明确：

- 创建消息会触发 `Message Create Gateway event`

这说明成熟聊天系统的关键不是“HTTP / 命令返回成功”，而是：

- 消息成立后，统一进入权威事件流

对应 `koko`：

- 我们现在统一发 `room_event` 是对的
- 不能给发送者保留一条与别人不同的“私有成功真相路径”

来源：

- [Discord Message Resource](https://docs.discord.com/developers/resources/message)

### 4.2 Discord Gateway：恢复依赖 session + sequence，不靠猜

Discord Gateway 恢复要求：

- `session_id`
- `resume_gateway_url`
- 上次收到的 sequence

这告诉我们：

- 高性能实时系统恢复一定依赖明确的同步锚点
- 不是“断线了重连一下应该就好了”

对应 `koko`：

- `event_position` 必须继续做唯一同步锚点

来源：

- [Discord Gateway](https://docs.discord.com/developers/events/gateway)

### 4.3 Telegram：先看本地状态，再决定接受、忽略还是补洞

Telegram 官方更新文档最值钱的点：

- `local_pts + pts_count === pts`：可直接应用
- `local_pts + pts_count > pts`：已处理，忽略
- `local_pts + pts_count < pts`：出现 gap，必须恢复

这几乎就是所有成熟 IM 续接问题的通用答案。

对应 `koko`：

- `from < latest`：补发缺失
- `from == latest`：无缺口，正常订阅
- `from > latest` 或闭合不了：明确 `需要重拉快照`

来源：

- [Telegram Working with Updates](https://core.telegram.org/api/updates)

### 4.4 Telegram：gap 太大时不要硬补，要回退到差量/状态恢复

Telegram 官方还强调：

- gap 太大时返回 `*TooLong`
- 客户端应重新获取状态再继续

对应 `koko`：

- 这就是我们下一步要补的 `需要重拉快照`
- 不要把“闭合不了的 gap”继续伪装成可直接流式补完

来源：

- [Telegram Working with Updates](https://core.telegram.org/api/updates)

### 4.5 Matrix：`next_batch` 这种“稳定游标”思路值得学

Matrix `/sync` 模型的关键不是 websocket，而是：

- 服务端给稳定游标
- 客户端下次带回这个游标续接

对应 `koko`：

- 我们已经选了 `event_position`
- 所以下一步要做的是把这个游标的失败语义、重连语义、重拉快照语义彻底钉死

来源：

- [Matrix Client-Server Sync](https://spec.matrix.org/unstable/client-server-api/index.html)

## 5. 对 `koko` 下一步最直接的结论

### 5.1 能直接复用的，不要再手搓

1. 连接认证：继续用 `socketioxide` connect middleware
2. per-socket 身份：继续用 `Extension`
3. 房间广播：继续用 `join / within / to`
4. 真实链路测试：继续用官方 `socket.io-client`
5. 多节点适配：以后优先看 `socketioxide-redis`

来源：

- [socketioxide docs.rs](https://docs.rs/socketioxide/latest/socketioxide/)
- [socketioxide-redis docs.rs](https://docs.rs/socketioxide-redis)

### 5.2 绝不能再手搓第二套的东西

1. 私有 `room -> sockets` 广播表
2. 第二套 ACK 成功语义
3. 第二套断线恢复协议
4. 第二套实时测试客户端
5. 多节点前就自己发明跨节点广播总线

### 5.3 眼下最该补的，不是新功能，而是恢复门禁

按这轮资料判断，`koko` 下一步优先级应当是：

1. 明确 `from` 无法闭合时的 `需要重拉快照`
2. 前端掉线后按 `latestEventPosition` 自动重订阅
3. 补“过大 gap / 非法 from / room 不一致”测试
4. 热路径日志带上 `session_id / room_id / client_message_id / event_position`

## 6. 多节点前的提前记忆

虽然现在不做多节点，但有两条必须先记住：

1. `socketioxide-redis` 不兼容 JS 的 `@socketio/redis-adapter`
2. 如果未来不是 websocket-only，而是保留 polling，就必须认真处理 sticky sessions

来源：

- [socketioxide-redis docs.rs](https://docs.rs/socketioxide-redis)
- [Socket.IO Using multiple nodes](https://socket.io/docs/v4/using-multiple-nodes/)

---

## 7. 动手前最终禁令

1. 禁止把 socket 恢复能力当成业务真相恢复能力
2. 禁止把 room 当成员真相
3. 禁止把 ack / connect / subscribed 当消息成立
4. 禁止 gap 闭合不了时继续假装可以流式追平
5. 禁止为了“看起来更 Rust”手搓成熟 realtime 基础设施
6. 禁止在测试里回退到假 websocket 世界，真实主链必须用真实 client 验
