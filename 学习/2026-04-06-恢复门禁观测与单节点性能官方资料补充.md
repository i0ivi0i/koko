# 2026-04-06 恢复门禁观测与单节点性能官方资料补充

目的：

这份笔记只服务 `koko` 接下来的几步实现，不重复上一份“事件流 / gap / 快照回退”笔记。
这次重点补 4 件事：

1. `socketioxide + socket.io` 在恢复门禁和单节点性能上还有哪些官方建议
2. Rust 官方推荐怎么做结构化观测，避免 async 主链变成黑盒
3. `sqlx` 官方对连接池有哪些直接影响实时热路径的建议
4. 高性能群聊产品在“少拉、少发、少重复、可恢复”上有哪些值得直接学的设计

当前仓库版本：

- `socketioxide = 0.16.x`
- `sqlx = 0.8.x`
- `tracing = 0.1.x`
- `tracing-subscriber = 0.3.x`
- `socket.io-client = 4.8.x`

结论先说：

- 下一步不要再造恢复协议，也不要开始手调一堆 builder 参数
- 先把 `结构化观测 + 连接池常识 + 少拉少发` 做硬
- 有了这三样，再谈单节点压测和未来多节点

## 1. socketioxide / socket.io，下一步最该继续信什么

### 1.1 `socketioxide` 继续负责 realtime 能力，不负责业务真相

官方文档的能力边界仍然很清楚：

- namespace
- room / operators
- middleware
- extension / state
- adapter
- builder 配置

对 `koko` 的含义：

- 继续用 `middleware + Extension + join/within`
- 继续禁止自己手搓 `room -> sockets`
- 继续禁止把 `ack` 或连接态晋升成业务真相

来源：

- [socketioxide docs.rs](https://docs.rs/socketioxide/latest/socketioxide/)

### 1.2 真正和单节点性能最相关的 builder 项，先记住边界，不急着乱调

当前最相关的官方配置项：

- `max_buffer_size`
- `ws_read_buffer_size`
- `max_payload`
- `ping_interval`
- `ping_timeout`
- `connect_timeout`
- `transports`
- `with_state`
- `with_adapter`

对 `koko` 的实际启发：

1. 先别在没有压测证据时乱改这些值
2. 但要知道 `emit()` 在缓冲满时会报错，不能假装广播永远成功
3. 真要做性能收口，优先调官方 builder，而不是新造一层“私有实时配置系统”

来源：

- [SocketIoBuilder docs.rs](https://docs.rs/socketioxide/latest/socketioxide/struct.SocketIoBuilder.html)

### 1.3 `socket.io` 官方对恢复门禁的态度仍然没变

官方 `Delivery guarantees` 说得很直接：

- 默认只有 `at most once`
- 想补强服务端到客户端投递，就要：
  - 唯一事件 ID
  - 持久化事件
  - 客户端记住 offset
  - 重连时带回 offset

这和我们当前的 `event_position` 路完全一致。

真正重要的不是再发明恢复机制，而是把：

- 什么时候可以补
- 什么时候必须退回快照
- 什么时候应该拒绝继续追平

这些门禁钉死。

来源：

- [Socket.IO Delivery guarantees](https://socket.io/docs/v4/delivery-guarantees/)

### 1.4 官方 testing 仍然要求真实 client，不要回退假世界

`socket.io` 官方 testing 文档本质上就在说：

- 真 server
- 真 client
- 真事件收发

不要只靠假对象证明 realtime 主链。

这对 `koko` 的含义非常实际：

- 当前 [realtime真实链路.spec.ts](E:\koko\frontend\tests\realtime真实链路.spec.ts) 这条路是对的
- 后续补“非法 from / 非法 room / 重连 / 多房隔离 / 广播失败”也继续走真实链路

来源：

- [Socket.IO Testing](https://socket.io/docs/v4/testing/)

## 2. Tokio / tracing 官方，下一步最该学什么

### 2.1 async 系统别再满足于普通日志

Tokio 官方 tracing 指南说得很清楚：

- async 系统里，普通日志很难看出因果链
- `tracing` 的优势是：
  - 结构化字段
  - spans / events
  - 上下文因果关系

这对 `koko` 的意义非常直接：

- 订阅、补发、发送、广播失败都不该只打一串字符串
- 必须带字段：
  - `session_id`
  - `room_id`
  - `client_message_id`
  - `event_position`
  - `expected_position`
  - `latest_event_position`

否则单节点一上量，就会进入“知道出事了，但不知道哪条链坏了”的状态。

来源：

- [Tokio: Getting started with Tracing](https://tokio.rs/tokio/topics/tracing)

### 2.2 subscriber 要尽早装，字段要可过滤，不要全靠 message

Tokio 和 `tracing-subscriber` 官方建议：

- executable 尽早初始化 subscriber
- 用 `EnvFilter` 控制日志级别
- `fmt` 可以加线程、文件、行号等信息

对 `koko` 的直接落点：

1. 启动期就固定 subscriber，不要在库层乱初始化
2. 重要链路多放结构化字段，少靠拼字符串 message
3. 后续若要查热路径问题，可逐步切：
   - `compact`
   - thread ids
   - line number
   - target 取舍

来源：

- [Tokio: Getting started with Tracing](https://tokio.rs/tokio/topics/tracing)
- [tracing_subscriber::fmt docs.rs](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/fmt/)

### 2.3 现在最值得补的不是 fancy tracing，而是稳定 forensic 字段

从官方能力反推，`koko` 现在最该做的是：

1. 所有 `control_result` 拒绝/错误都有统一错误码字段
2. 所有订阅/重订阅/回退快照日志都带锚点字段
3. 所有广播失败日志都带房间和客户端消息标识

不要一开始就把事情做复杂：

- 不急着上 OpenTelemetry
- 不急着上 metrics 平台
- 不急着引入第二套观测框架

先把热路径字段做对，比盲目接平台更值钱。

## 3. sqlx 官方，下一步最该学什么

### 3.1 连接池必须长期共享，不要频繁创建和丢弃

`sqlx::Pool` 官方文档明确提醒：

- 每个数据库连接都很贵
- 池不是为了让你“随便新建”
- 如果反复创建和销毁 pool，服务端连接清理可能滞后
- 会遇到连接数上限问题

这正是为什么 `koko` 现在改成了应用启动时共享 `PgPool`。

下一步要坚持的纪律：

1. 热路径继续只复用共享 pool
2. 禁止回到 per-request / per-handler 建池
3. 未来优雅停机时记得 `pool.close().await`

来源：

- [sqlx::Pool docs.rs](https://docs.rs/sqlx/latest/sqlx/struct.Pool.html)

### 3.2 `min_connections` 是“稳定性能”工具，不是默认越大越好

官方文档提到：

- 设定 `min_connections` 可以提前预热一部分连接
- 帮助请求来时更稳定

对 `koko` 的结论：

- 这项可以作为后续压测后的调优工具
- 不是现在没有证据就先拍脑袋调大的东西

也就是说：

- 先测
- 再看是否需要预热连接
- 不要把数据库连接数当作“越多越猛”

来源：

- [sqlx::Pool docs.rs](https://docs.rs/sqlx/latest/sqlx/struct.Pool.html)

## 4. 高性能群聊榜样，下一步最值得抄什么

### 4.1 Discord：先减少 websocket 流量，再谈更花哨的优化

Discord 官方工程文章《How Discord Reduced Websocket Traffic by 40%》最值钱的启发不是某个具体算法，而是方向：

- 高并发实时系统，带宽和 payload 体积本身就是成本中心
- 压缩、字典、被动会话、减少无效数据传输，都是一等优化

对 `koko` 的直接启发：

1. 先让事件 payload 保持瘦身
2. 不要为了壳层方便把大块冗余字段塞进 `room_event`
3. 能用单独快照 / 冷路径查到的东西，不要每条 realtime 事件都重复发

来源：

- [How Discord Reduced Websocket Traffic by 40%](https://discord.com/blog/how-discord-reduced-websocket-traffic-by-40-percent)

### 4.2 Slack：WebSocket 收实时，历史和状态不要全都一口气预加载

Slack 官方工程文章《Making Slack Faster By Being Lazy》讲得很明白：

- WebSocket 负责接收实时消息
- 历史可以按需拉
- 不要在启动时把所有频道历史都加载进客户端
- 不需要的就别取

这是对 `koko` 非常重要的一课：

- 当前“房间快照 + 增量事件 + realtime 房间事件”的冷热分离方向是对的
- 不要把未来的 unread / mentions / presence 设计成“进来先把全世界拉一遍”

来源：

- [Making Slack Faster By Being Lazy](https://slack.engineering/making-slack-faster-by-being-lazy/)

### 4.3 Slack RTM 文档提醒：重复投递不是理论问题，是现实问题

Slack 官方 RTM 文档提到：

- 在 Enterprise 等场景下，可能从多个 websocket 连接收到同一条消息
- 这些重复消息会共享同一个时间戳标识

对 `koko` 的教训：

- 重复投递不是“以后再说”的假设问题
- `message_id / client_message_id / event_position` 这些去重锚点必须继续守住

来源：

- [Slack Legacy RTM API](https://docs.slack.dev/legacy/legacy-rtm-api/)

## 5. 对 `koko` 下一步最实际的动作建议

### 5.1 先做，不要再拖的

1. 给订阅 / 回退快照 / 增量补发 / 广播失败统一补结构化字段
2. 继续补真实链路测试：
   - 非法 `from`
   - `room_id` 不一致
   - 非成员重订阅
3. 保持 realtime payload 克制，不为图省事扩张事件体

### 5.2 先别做，不然容易飘

1. 没压测证据就乱调 `SocketIoBuilder`
2. 自己造背压队列系统
3. 自己造第二套指标/观测 SDK
4. 先上 Redis adapter 再说
5. 进房就预加载所有历史或所有房间状态

### 5.3 等有证据再做

1. `PgPoolOptions::min_connections`
2. `socketioxide` builder 细调
3. `Tokio Console` / OpenTelemetry / 更重的 tracing 分层
4. websocket-only 到 mixed transports 的回退策略

---

## 6. 动手前最后的禁令

1. 禁止把“多打一堆日志”误当成观测；字段不稳定的日志，排障价值很低
2. 禁止把 builder 参数调优当主工作；没有测量前，调参大多是幻觉
3. 禁止让前端因为图快就预拉全历史、全房间状态或大块冗余元数据
4. 禁止回到 per-request 建池
5. 禁止在恢复门禁上新增第二套 sync 机制
6. 禁止为了“以后万人在线”现在就手搓分布式轮子
