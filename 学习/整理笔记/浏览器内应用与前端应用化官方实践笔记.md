# 2026-04-12 浏览器内应用与前端应用化官方实践笔记

适用范围：`koko` 前端架构治理、万人实时群聊 IM 的生命周期边界、离线/后台能力、奇怪 bug 的根因收口。  
目标：把“浏览器里的网页”和“浏览器中的应用”这两种思维的差别，用官方资料和一线作者的文章压成一份可复用判断依据。

## 1. 先说结论

对万人实时群聊来说，前端不能再按“一个页面 + 一堆事件处理器 + 一个共享状态对象”来组织。  
官方和一线作者的共识已经很清楚：

- 安装式 Web App 应该有自己的窗口、导航和生命周期，不只是浏览器标签页里的页面。
- 浏览器事件是信号，不是业务真相。
- 主应用 UI、Service Worker、离线数据、后台任务、本地通知、多标签协作，本来就是不同部件。
- `WebSocket`、缓存、页面可见性、后台冻结、bfcache、存储驱逐，这些都会直接影响正确性，不只是性能。
- 如果前端还保持“网页脚本思维”，就特别容易出现偶发、难复现、难追因的 bug。

## 2. 官方与大神共识

### 2.1 安装后的 Web App 是应用，不只是网页

- MDN 明确把安装后的 PWA 描述成“有自己专用窗口”的应用，推荐通过 manifest 的 `display: standalone` 让它以独立窗口运行。
- web.dev 也把“可安装、独立窗口、像系统应用一样启动和运行”当成好 PWA 的基础能力，而不是锦上添花。

对 `koko` 的含义：

- 不能只盯着 DOM 渲染和路由跳转；
- 要把窗口模式、启动方式、返回行为、标题/徽章/通知、应用更新都当成应用问题处理。

### 2.2 PWA 的高层结构天然分成“主应用 UI”和“后台部件”

- MDN 的 PWA 指南明确指出：一个 PWA 在高层结构上天然分成两块：
  - 主应用：HTML/CSS/处理用户交互的 UI JavaScript
  - Service Worker：离线和后台任务
- Service Worker 与页面不共享状态，只能靠消息、缓存、请求结果协作。

对 `koko` 的含义：

- 聊天壳、媒体逻辑、实时链路、离线缓存、后台补发，不能再假装都在“同一个页面逻辑”里。
- App Shell、离线缓存、后台同步、推送通知，必须被看成应用架构部件，而不是页面补丁。

### 2.3 页面生命周期已经是“应用生命周期”，不是老式页面 unload 思维

- Chrome Page Lifecycle API 明确建议把 `hidden` 当作最后一个可靠可观察状态，尽早持久化未保存状态、停止无意义任务。
- 该指南还明确指出：`beforeunload` 不可靠，而且会影响 bfcache 资格，不该继续被当作统一的“退出钩子”。
- MDN 的 Page Visibility API 也强调：切后台、最小化、锁屏都会触发隐藏状态；浏览器还会对后台页节流 `requestAnimationFrame()` 和 `setTimeout()`。

对 `koko` 的含义：

- 需要明确：切后台时哪些 actor 继续工作，哪些必须冻结，哪些状态必须立即落盘。
- 不能把“页面还没被销毁”误判成“应用仍然前台活跃”。
- 不能依赖浏览器是否还继续跑 timer 来判断恢复逻辑是否正确。

### 2.4 WebSocket 不是“万事大吉”的实时真相载体

- MDN 现在明确提醒：标准 `WebSocket` 不支持 backpressure。
- 当消息到达速度快于应用处理速度时，浏览器端可能会堆内存、打满 CPU，页面变得无响应。
- MDN 还特别提醒：页面保持打开 WebSocket 连接时，浏览器可能不把它放进 bfcache；推荐在用户离开页面时关闭连接，并在 `pageshow` 恢复。

对 `koko` 的含义：

- 实时消息链路要把“批量处理、节流、虚拟列表、可见窗口裁剪、消息合并 owner”当成正确性的一部分。
- 不能默认“Socket 连着 = 应用状态可靠”。
- 页面进入 `pagehide` / `pageshow`、`hidden` / `visible` 的切换必须进入实时 actor 的协议。

### 2.5 离线和后台能力不是附属功能，而是应用能力

- web.dev 的 PWA checklist 把“离线仍可继续使用”“离线仍能保持身份”“离线动作稍后补发”直接定义成优质 PWA 的核心特征。
- MDN 的 Offline and background operation 进一步说明：背景同步、后台获取、周期同步等能力，依赖的是“主应用登记任务，Service Worker 在合适时机接手执行”的模式。

对 `koko` 的含义：

- 草稿、未读、会话恢复、媒体上传、发送补发，不该只是页面状态。
- 用户发消息时断网、切后台、关闭标签页，系统仍应按应用协议处理，而不是简单失败。

### 2.6 存储需要分层，不是随手塞进 localStorage

- web.dev Storage for the web 的建议很明确：
  - 静态资源：Cache Storage
  - 结构化数据：IndexedDB
  - 文件类内容：OPFS
- 同时它也明确写了浏览器的存储驱逐策略：默认是 best-effort，不申请 persistent storage 时可能被清理。
- Safari 还有更苛刻的脚本可写存储清理边界。

对 `koko` 的含义：

- `localStorage` 适合很小、很简单、可丢失的壳级状态，不适合作为复杂应用真相承载层。
- 未读锚点、恢复语义、离线消息队列、缓存索引、媒体状态，应该按数据性质分层存储。

### 2.7 多标签/多上下文协作是应用级问题

- MDN Broadcast Channel API 明确支持同源标签页、iframe、worker 之间的跨上下文通信。
- 这不是可有可无的小功能，而是浏览器提供的“同一应用多上下文协作”能力。

对 `koko` 的含义：

- 多标签已读同步、当前活跃房间、会话失效、重复通知消抖，不该由每个标签页各自猜测。
- 需要应用协议来协调多窗口/多标签行为。

### 2.8 未读徽章、推送通知和后台补发都属于应用能力

- MDN 的 Badging 指南明确把 app icon badge 当成 PWA 的正式能力，适合表示未读数量这类“低打扰提醒”。
- MDN 的离线与后台指南把聊天应用列为 Push API 的典型用例之一，同时明确提醒：通知会打断用户，应该克制使用。
- Background Sync 官方文档也给出非常贴切的例子：用户离线时提交动作，前台只登记同步请求，等网络恢复后由 Service Worker 接手补发。

对 `koko` 的含义：

- 未读数、消息提醒、后台补发，不该继续散落在页面脚本里。
- badge、notification、background sync 都应该挂到应用协议上，由明确 owner 负责发起、撤销和去重。
- 对聊天应用来说，“发了没发出去”“提醒发给哪个窗口”“已读后何时清 badge”，都应该是应用语义，不是页面细节。

### 2.9 “应用壳”不是营销词，而是稳定壳资源与动态真相分离

- Addy Osmani / Chrome 的 App Shell 模型强调：先把最小 UI 壳稳定、快速、可缓存地交付，再动态取内容。
- Jake Archibald 对 Service Worker 生命周期的解释也强调：必须让新旧版本在更新时不互相打架，避免同站同时运行多版本壳逻辑。
- Workbox 官方学习资料也反复强调：Service Worker 和缓存逻辑一旦长大，很容易长出细碎 bug，应该交给成熟工具链管理。

对 `koko` 的含义：

- 聊天实时数据和应用壳资源必须分开管理。
- Workbox、asset precache、更新提示、版本切换策略是稳定性工程，不只是性能优化。

### 2.10 Actor model 很适合前端，因为前端本来就是分布式系统

- Stately/XState 官方写得很直接：前端应用天然就是分布式系统，因为状态和事件源本来就分散在 DOM、router、local storage、query、network I/O、第三方组件等多个地方。
- Actor model 的关键点是：每个 actor 只修改自己的内部状态，通过事件通信，不共享内部状态。

对 `koko` 的含义：

- 滚动、时间线、恢复、实时、媒体、离线补发，适合各自拥有唯一 owner。
- 一个“大壳状态对象 + 各处 patch”会天然削弱因果链，提升漂移和覆盖风险。

### 2.11 前后端边界仍要遵守 coarse-grained facade 思维

- Martin Fowler 的 Remote Facade 模式强调：跨进程调用比进程内调用昂贵得多，因此远程接口应 coarse-grained；Facade 只做翻译，不承载领域逻辑。

对 `koko` 的含义：

- 前端壳层、HTTP adapter、realtime adapter 应该是粗粒度命令/查询/事件边界。
- 不能把前端点一下按钮就映射成多次细粒度远程取数/改写，再让壳层自己拼真相。

### 2.12 Jeremy Keith 的“韧性 Web”提醒：Web 先是 Web，再增强成 App

- Jeremy Keith 的《Resilient Web Design》持续强调 progressive enhancement 和 layered thinking：
  - 先保证核心内容和核心动作成立；
  - 再逐层增强成交互更强、体验更像应用的形态；
  - 不要把 JavaScript 成功执行当成唯一真相来源。

对 `koko` 的含义：

- “浏览器中的应用”不是否定 Web，而是先守住 Web 的韧性，再把它增强成 IM 应用。
- 真正该被消灭的不是 HTML / form / link，而是“浏览器事件直接裁决业务真相”的网页化思维。

## 3. 为什么这种问题会长出“奇怪 bug”

把前端停留在“网页脚本思维”时，常见症状是：

1. 多个入口直接共写同一块大状态，时序覆盖后很难知道谁改坏了什么。  
2. DOM 观测结果被当成业务真相，滚动、分页、未读、媒体占用互相串扰。  
3. 页面隐藏、冻结、恢复、多标签切换没有进入正式协议，只能靠临时判断。  
4. 实时 socket、缓存层、离线层、壳层状态没有 owner，边界互相漏水。  
5. 浏览器节流、bfcache、存储驱逐、后台重启一旦触发，系统就显得像“随机坏掉”。  

这类 bug 难排查，不是因为工程师不努力，而是因为因果链没有被架构显式表达出来。

## 4. 给 `koko` 的判断标尺

以后判断某段前端代码是不是还停留在“网页思维”，可以直接看这几条：

1. 浏览器事件进来后，是不是先变成应用事件，再由 owner 裁决。  
2. DOM / `scrollTop` / `fullscreenchange` / `popstate` 有没有直接宣布业务状态。  
3. 是否存在“多个模块共写一个共享大状态对象”的总线。  
4. 页面 `hidden` / `visible` / `pagehide` / `pageshow` 有没有进入正式生命周期协议。  
5. 实时连接有没有把 backpressure、冻结、恢复、多标签协作纳入设计。  
6. App Shell / SW / 缓存 / 存储是否已经按职责分层，而不是杂糅在壳层。  
7. 后台壳、聊天壳、媒体壳是否都遵守同一套“应用而非网页”的边界。  

只要这些问题里还有几条答不上来，就说明前端应用化还没做完。

## 5. 这批资料对当前项目最重要的提醒

- `hidden` 比 `unload` 更重要。  
- `pagehide/pageshow` 和 bfcache 会影响实时连接恢复。  
- `WebSocket` 不支持 backpressure，消息窗口和批处理必须是硬约束。  
- `Service Worker` 是后台部件，不是页面脚本的延长线。  
- 多标签通信不是临时 hack，浏览器已经有正式能力。  
- badge / push / background sync 都是应用级能力，不是页面零散特效。  
- App Shell 只缓存壳，不缓存聊天业务真相。  
- Actor / owner 收口不是“高级感”，是为了把 bug 还原成稳定因果链。
