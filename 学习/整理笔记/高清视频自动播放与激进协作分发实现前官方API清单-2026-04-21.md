# 高清视频自动播放与激进协作分发实现前官方 API 清单（2026-04-21）

适用范围：`koko` 当前这轮“时间线第一眼就有内容、自动播放秒开、滑过即继续补齐、群友越多越快”的实现计划。  
目标：只收这轮 plan 真会直接用到的官方 API、浏览器边界和高性能做法，避免写 plan 时靠印象补脑、手搓已有能力，或者把错误假设写进任务。

---

## 1. 这轮实现真正要查清的东西

不是所有媒体/PWA 资料都要再学一遍。  
这轮只需要把下面几类接口和边界查准：

1. 浏览器侧 `WebTorrent` 到底怎么建流、怎么保留 store、怎么选块、怎么观察 swarm 状态；
2. “首个真实已解码视频帧”到底用什么官方 API 判断，不再拿 `play()` 成功或 `loadeddata` 乱充数；
3. 自动播放被浏览器拦截时，官方要求怎样处理 promise / `NotAllowedError`；
4. 页面切后台、冻结、恢复时，哪些生命周期信号可信，哪些不可信；
5. “滑到视频就继续补齐”该如何复用浏览器现成的可见性、存储和性能观测能力，而不是自己手搓第二套轮子；
6. `Video.js v10` 在当前阶段到底该扮演什么角色，避免把 UI 壳误写成 source owner。

---

## 2. 官方 API 与边界

### 2.1 WebTorrent 浏览器主链

官方资料：

1. WebTorrent Docs: <https://webtorrent.io/docs>
2. WebTorrent FAQ: <https://webtorrent.io/faq>
3. WebTorrent 官方教程 / API（Context7 对应官方仓库）：`docs/tutorials.md`、`docs/api.md`

这轮最关键的官方事实：

1. 浏览器侧要用 `client.createServer({ controller })`，而且 `controller` 是现成的 `ServiceWorkerRegistration`；不是自己手搓另一个 Range 服务。
2. `client.createServer()` 官方明确支持 HTTP Range。
3. `client.add()` 已经直接支持这轮实现会用到的关键选项：
   - `announce`
   - `getAnnounceOpts`
   - `urlList`
   - `maxWebConns`
   - `private`
   - `destroyStoreOnDestroy`
   - `strategy`
4. `strategy` 官方就支持 `sequential` 和 `rarest`，默认是 `sequential`。
5. `file.streamURL` 是官方表面；在 `createServer()` 已运行时可以直接拿来给 `<video>` 或其它消费方。
6. `file.select([priority])` 是官方表面；如果你知道这个文件后面需要继续下载，可以直接提升优先级。
7. WebTorrent 官方明确写了：下载中的 torrent 会自动继续做种。
8. WebTorrent 也明确写了：如果你想在页面关闭时删除跨会话 store，最晚要在 `beforeunload` 时显式 destroy；反过来也说明，默认不 destroy 才能留住 store。

这轮 plan 的直接含义：

1. 不要再手搓“私有补块协议”或“第二套下载内核”。
2. 不要再把 swarm session 做成“看一眼就停”的一次性对象。
3. 要围绕现有 `createServer + streamURL + add opts + select + store 保留` 写任务，而不是另造轮子。

### 2.2 WebTorrent FAQ 的硬限制

官方资料：

1. WebTorrent FAQ: <https://webtorrent.io/faq>

这轮最关键的官方事实：

1. 浏览器里的 WebTorrent 走的是 `WebRTC`。
2. 浏览器只能下载由 `WebRTC-capable` 客户端做种的 torrent。
3. `MediaSource` 是流式播放的前提。
4. `.mp4` / `.m4v` / `.m4a` 才是官方点名“包括 seek 在内的 full support”格式。

这轮 plan 的直接含义：

1. “滑过后继续补齐”和“后面的人更快”，前提是 swarm 里真的有完整且在线的可用 peer。
2. canonical video 的容器/编码继续优先围绕浏览器友好 MP4 路线，不要在这轮计划里引入非目标格式折腾。
3. 不要把“浏览器支持 WebTorrent”误写成“任何 BT peer 都能喂浏览器”。

### 2.3 首个真实视频帧与可播状态

官方资料：

1. MDN `HTMLVideoElement.requestVideoFrameCallback()`: <https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback>
2. MDN `HTMLMediaElement.readyState`: <https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/readyState>

这轮最关键的官方事实：

1. `requestVideoFrameCallback()` 是按视频帧节奏触发的官方 API，能拿到每一帧以及对应 metadata。
2. 这个 API是“下一帧送去 compositor 时”触发，比只盯 `play()` 或 `loadeddata` 更接近“屏幕上真的有帧了”。
3. `readyState` 的官方语义里：
   - `HAVE_METADATA` = 元数据可用
   - `HAVE_CURRENT_DATA` = 当前播放位置至少有一帧
   - `HAVE_FUTURE_DATA` = 至少再往后还有一点数据
   - `HAVE_ENOUGH_DATA` = 理论上可播到尾

这轮 plan 的直接含义：

1. “时间线第一眼出现内容”和“自动播放首播成立”要优先围绕 `requestVideoFrameCallback()` 和 `readyState` 写验证。
2. 不要再把 `play()` promise resolve 当成“已经有画面”。
3. 预览派生和正式自动播的验证口径都要锁在“同一 video 节点上的真实已解码帧”。

### 2.4 自动播放 promise 与浏览器拦截

官方资料：

1. MDN Autoplay Guide: <https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay>
2. MDN `HTMLMediaElement.play()`: <https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play>

这轮最关键的官方事实：

1. 自动播放拦截不适用于无音轨视频，或者 muted 的视频。
2. `play()` 返回 Promise。
3. 如果浏览器不允许当前上下文自动播，`play()` 会 reject，而且典型错误就是 `NotAllowedError`。
4. MDN 明确要求：UI 不能假定播放已经开始，必须按 promise fulfilled / rejected 的真实结果更新。

这轮 plan 的直接含义：

1. inline autoplay 必须继续坚持 `muted` / `playsinline` / promise 显式处理。
2. 不能把“尝试 play 了”当成“自动播成功了”。
3. 需要把 `NotAllowedError`、用户交互补救、owner 切换后的二次显式 `play()` 写进任务和测试。

### 2.5 持久化存储与生命周期

官方资料：

1. MDN `StorageManager.persist()`: <https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist>
2. Chrome Page Lifecycle API: <https://developer.chrome.com/docs/web-platform/page-lifecycle-api>

这轮最关键的官方事实：

1. `navigator.storage.persist()` 返回 `Promise<boolean>`；`true` 代表拿到 persistent storage，`false` 代表没拿到，但这不等于异常。
2. Chrome Page Lifecycle 明确建议把 `hidden` 当作最后一个可靠可观察状态。
3. Chrome 也明确写了：`beforeunload` 不是可靠的 end-of-session 信号，而且会影响 bfcache 资格；只该在“真有未保存改动”时临时挂上。

这轮 plan 的直接含义：

1. “继续补齐”和“继续做种”的产品策略不能建立在 `beforeunload` 这种不可靠钩子上。
2. `persist()` 是 best-effort 增强，不是前置硬依赖；拿不到也不能把产品策略降级成“默认不补齐”。
3. 生命周期相关任务要围绕 `hidden/pagehide/pageshow/visible` 写，不要围绕 `beforeunload` 写。

### 2.6 可见性与自动播候选

官方资料：

1. MDN Intersection Observer API: <https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API>

这轮最关键的官方事实：

1. `IntersectionObserver` 是异步可见性观察能力。
2. 官方明确强调：它的价值就是避免在主线程不断跑 `getBoundingClientRect()` 和滚动循环，从而减轻性能问题。

这轮 plan 的直接含义：

1. 自动播候选检测继续优先基于 `IntersectionObserver`，而不是退回整列同步量测。
2. 如果要补“首次回调晚一拍”的问题，也应该是在现有 `IntersectionObserver + 热启动量测` 路线里修，而不是推翻它重写一套。

### 2.7 平滑度与重活预算

官方资料：

1. Chrome Long Animation Frames API: <https://developer.chrome.com/docs/web-platform/long-animation-frames>

这轮最关键的官方事实：

1. LoAF 通过 `PerformanceObserver` 观察 `long-animation-frame`。
2. 它比只看 long task 更适合发现 UI 卡顿、掉帧和渲染阻塞。
3. Chrome 官方明确把它定位为识别 responsiveness / smoothness 问题的可行动信号。

这轮 plan 的直接含义：

1. 多视频同屏时的“重活预算”与“自动播 owner 争抢”不该只靠主观感觉调。
2. 可以围绕现有 `longTaskCount / heavyWorkPolicy` 再接上更适合 UI 卡顿的 LoAF 观测，而不是自己发明“卡顿评分”。

### 2.8 Video.js v10 在这轮里的位置

官方资料：

1. Video.js v10 概览（Context7 对应官方仓库 `overview.mdx`）
2. Video.js v10 source feature（Context7 对应官方仓库 `feature-source.mdx`）

这轮最关键的官方事实：

1. v10 方向是 `video-player` / `media-container` 这类可组合 custom elements。
2. 官方把 UI 组件和 source 状态分开，不要求 UI 壳自己决定 source。

这轮 plan 的直接含义：

1. `Video.js v10` 继续只当壳，不把 source 选择真相塞进壳里。
2. 这轮计划里如果改 viewer / player，应该落在“壳消费已裁决 source”，而不是“壳自己新增 source owner”。

## 4. 这轮 plan 明确不要手搓什么

1. 不手搓第二套 Range / 流媒体服务，优先复用 `WebTorrent createServer()`。
2. 不手搓“首帧已出现”判定，优先用 `requestVideoFrameCallback()` 和 `readyState`。
3. 不手搓自动播策略例外，优先显式处理 `play()` Promise 与 `NotAllowedError`。
4. 不手搓滚动可见性轮询，优先继续用 `IntersectionObserver`。
5. 不手搓生命周期真相，优先用 `hidden/pagehide/pageshow/visible`。
6. 不手搓 UI 卡顿评分，优先基于 LoAF / 现有运行时预算信号扩展。
7. 不把 `Video.js` 壳提升成 source owner。

---

## 5. 一句话

这轮 implementation plan 应该建立在“复用浏览器和官方库已经给出的主表面”上：  
`WebTorrent` 负责浏览器 swarm 流和 store，`requestVideoFrameCallback()` 负责真实首帧观测，`play()` promise 负责自动播成败语义，`persist()` 和 Page Lifecycle 负责持久化/恢复边界，`IntersectionObserver` 负责可见性候选，`Video.js` 只负责壳。
