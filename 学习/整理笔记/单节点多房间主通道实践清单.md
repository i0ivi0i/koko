# 2026-04-06 单节点多房间群聊主通道关键轮子官方最佳实践清单

适用范围：`koko` 即将开始的单节点多房间群聊主通道实现。  
目标：在正式动工前，把这次会真正碰到的关键轮子官方实践吃透，避免边写边补文档、边写边手搓。

本清单只覆盖这次主线真正会用到的轮子：

1. `socketioxide`
2. `socket.io-client` / Socket.IO 官方语义
3. `axum`
4. `sqlx`

## 1. 总结先行

这次实现的正确组合是：

1. 实时语义看 `Socket.IO` 官方
2. Rust 服务端落地看 `socketioxide`
3. HTTP 状态与应用共享状态看 `axum`
4. 数据库连接池与事务边界看 `sqlx`

一句话压缩：

**用 Socket.IO 的官方语义，按 socketioxide 的 Rust 方式落地，用 axum 管共享状态，用 sqlx 管长期连接池和事务。**

## 2. `socketioxide` 官方最佳实践

### 2.1 它本来就是按 Socket.IO 语义设计的

`socketioxide` 官方文档明确：

1. 完全兼容官方 `socket.io` client
2. API 尽可能模仿 JS 版 `Socket.IO` API
3. 支持 namespace / rooms / acknowledgements / adapters / polling / websocket

这意味着：

1. 我们可以直接沿用 Socket.IO 官方关于 room、ack、delivery、recovery、testing 的语义建议
2. Rust 端只是在实现方式上不同，不是在协议语义上另起炉灶

来源：

- [socketioxide docs.rs](https://docs.rs/socketioxide/latest/socketioxide/)

### 2.2 同一事件只能有一个 handler

官方文档明确写了：

- `Only one handler can exist for an event so registering a new handler for an event will replace the previous one.`

对 `koko` 的直接约束：

1. 同一 socket event 名必须只在一处注册
2. 不允许在不同模块各挂一个同名 handler
3. 不允许靠“后注册覆盖前注册”这种隐式行为实现功能

### 2.3 连接中间件适合做认证，不适合做业务流程

`socketioxide` 文档和 Socket.IO middlewares 文档都一致说明：

1. 中间件适合做 authentication / authorization / logging / rate limiting
2. middleware 运行时，socket 还没真正接入 namespace
3. 失败时应拒绝连接，而不是把它拖成半连接状态

对 `koko` 的直接约束：

1. `session_id` 认证应优先放 connect middleware
2. 入房、补洞、发消息不能塞进 middleware
3. middleware 失败时统一走 `connect_error`

来源：

- [socketioxide docs.rs](https://docs.rs/socketioxide/latest/socketioxide/)
- [Socket.IO middlewares](https://socket.io/docs/v4/middlewares/)

### 2.4 不要自己长期保存 `SocketRef`

`socketioxide` 官方明确提醒：

1. `SocketIo` 句柄便宜可 clone，可在程序里到处传
2. `SocketRef` 是 socket 引用，不建议自己塞进 `HashMap/Vec` 长期保存
3. 如果你真这么做，断开时要自己清理，否则会有内存泄漏风险

对 `koko` 的直接约束：

1. 禁止自建 `room_id -> Vec<SocketRef>` 广播表
2. 广播优先使用 `socketioxide` 的 room/operator
3. 如果要做 broadcaster，就围绕 `SocketIo` 句柄做薄封装

### 2.5 状态分两层：global state 与 per-socket extension

`socketioxide` 官方把状态分得很清楚：

1. global state：通过 `SocketIoBuilder::with_state`
2. per-socket state：通过 `extensions`

对 `koko` 的直接约束：

1. `session_id` 这类连接上下文放 extension
2. 应用级共享对象如 `PgPool`、配置、广播器句柄放 global state 或外层共享状态
3. 禁止把房间成员真相、消息成立真相塞进 extension 当权威缓存

### 2.6 为未来 adapter 预留，handler 从现在开始写成泛型友好形态

官方文档明确建议：

```rust
async fn my_handler<A: Adapter>(s: SocketRef<A>, io: SocketIo<A>) { }
```

对 `koko` 的直接约束：

1. 单节点先跑默认 adapter
2. 但 handler / broadcaster 从现在开始就按 `A: Adapter` 兼容方式组织
3. 这样未来切多节点 adapter 不需要重写主链

## 3. `socket.io-client` / Socket.IO 官方最佳实践

### 3.1 优先用 `auth` 传连接级凭据

Socket.IO 官方文档明确推荐：

```ts
const socket = io({
  auth: { token: "abc" }
})
```

服务端通过 `socket.handshake.auth` 读取。

对 `koko` 的直接约束：

1. 浏览器端连接级 `session_id` 应放 `auth`
2. 不要继续在每个业务事件 payload 里重复自带身份

来源：

- [Socket.IO middlewares](https://socket.io/docs/v4/middlewares/)

### 3.2 浏览器环境下，`extraHeaders` 不能替代 `auth`

Socket.IO 官方 client options 文档明确：

1. 浏览器里如果只启用 `websocket` 传输，`extraHeaders` 会被忽略
2. 因为浏览器 WebSocket API 本身不允许自定义 headers

对 `koko` 的直接约束：

1. 浏览器前端不要指望用 header 传 `session_id`
2. 连接身份优先走 `auth`

来源：

- [Socket.IO client options](https://socket.io/docs/v4/client-options/)

### 3.3 `transports` 策略必须显式决定

Socket.IO 官方 client options 文档明确：

1. 默认会优先 polling，再升级 websocket
2. 也可以强制只用 `websocket`
3. 只用 `websocket` 时，sticky session 不再是必须条件
4. 但失去 long-polling fallback

对 `koko` 的当前建议：

1. 单节点开发期可以保守使用当前客户端配置
2. 但必须把 `transports` 当成显式架构决策，不要默认无所谓

### 3.4 `Manager` 会被多个 namespace socket 复用

Socket.IO 官方 client options 文档明确：

1. 一个 `Manager` 负责底层连接与重连逻辑
2. 多个 namespace 可以复用同一个底层连接

对 `koko` 的直接约束：

1. 前端不要为了多个 namespace 或房间盲目建立多个连接
2. 单节点阶段应优先复用一条连接

### 3.5 ACK 与 catch-all 监听不是一回事

Socket.IO 官方 listening-to-events 文档明确：

1. acknowledgements 不会被 catch-all listener 捕获
2. validation 不属于库内置职责，需要业务自己做

对 `koko` 的直接约束：

1. 不要指望 `onAny` 拦到所有 ACK
2. 事件 payload 校验必须在我们自己的契约/handler 层做

来源：

- [Socket.IO listening to events](https://socket.io/docs/v4/listening-to-events/)

## 4. `axum` 官方最佳实践

### 4.1 共享状态应该在 Router 启动时创建，并通过 `State` 注入

`axum` 官方 `State` 文档明确：

1. `State` 是全局状态 extractor
2. Router 通过 `.with_state(state)` 持有共享状态
3. 可放配置、数据库连接池等

对 `koko` 的直接约束：

1. `PgPool` 应在服务启动时创建一次
2. 配置和共享句柄应进入应用级状态
3. 不要在每个 handler 里新建一套数据库连接对象

来源：

- [axum State extractor](https://docs.rs/axum/latest/axum/extract/struct.State.html)

### 4.2 请求派生数据不要混进全局状态

`axum` 官方文档明确写了：

- `State` 是全局状态；像 authorization data 这种从请求派生的数据，应看 `Extension`

对 `koko` 的直接约束：

1. `PgPool`、配置走全局 state
2. 连接级 `session_id`、socket 扩展上下文走 `socketioxide` extension
3. 不要把连接级身份写进全局 state

### 4.3 可变共享状态必须考虑锁边界

`axum` 官方文档说明：

1. 全局状态若需要共享可变性，常见方案是 `Arc<Mutex<_>>`
2. 但 `std::sync::Mutex` 不应跨 `.await` 持有

对 `koko` 的直接约束：

1. 不要在 async 热路径跨 `.await` 长持业务锁
2. 尽量减少全局可变共享状态
3. 对于数据库与 realtime 主链，优先使用连接池和短生命周期局部变量，而不是大锁

## 5. `sqlx` 官方最佳实践

### 5.1 连接池应在应用启动时创建一次并全局共享

`sqlx::Pool` 官方文档明确：

1. `Pool` intended to be created once at the start of your application`
2. `Pool` 是 `Send + Sync + Clone`
3. clone 很便宜，本质上是引用计数句柄

对 `koko` 的直接约束：

1. 当前按请求 `连接并迁移()` 的模式不适合作为正式实时主链形态
2. 正式实现应把 `PgPool` 提升为启动期一次创建、全局共享

来源：

- [sqlx Pool docs](https://docs.rs/sqlx/latest/sqlx/struct.Pool.html)

### 5.2 不要每请求新建连接

`sqlx` 官方文档明确指出：

1. 新建数据库连接成本高
2. 每连接都有认证、协商、资源分配成本
3. 连接池的意义就是摊平这些开销并优雅承压

对 `koko` 的直接约束：

1. 实时热路径不能继续每次消息都新建数据库连接池/运行时
2. 应共享一个长期 `PgPool`

### 5.3 用事务守住权威事实，不要把外部 IO 包进事务

虽然 `sqlx` 文档本身主要讲 Pool / Executor，但对当前设计而言，官方模式很清楚：

1. 从池里取连接或直接用 `&Pool` 执行
2. 需要原子性时使用 `begin()`
3. 事务边界用于数据库事实提交，不应用来包广播和网络 IO

对 `koko` 的直接约束：

1. `创建消息事件` 的事务链继续保持“写事件、写消息、推进锚点”原子提交
2. realtime 广播应在事务成功返回之后执行

### 5.4 应用关闭时要显式 `.close().await`

`sqlx` 官方文档明确建议：

1. 长生命周期应用退出时调用 `.close().await`
2. 否则连接可能不会优雅关闭

对 `koko` 的直接约束：

1. 这不是当前第一阶段的核心功能点
2. 但后续整理启动/关闭路径时应补上

## 6. 对 `koko` 下一步实现的直接约束

把四个轮子的官方实践合起来，对这次实现的直接约束只有这些：

1. 浏览器前端用 `socket.io-client` 的 `auth` 传 `session_id`
2. Rust 服务端用 `socketioxide` connect middleware 做连接级认证
3. `socketioxide` room/operator 负责订阅分组和广播，不自建广播表
4. `axum` 持有应用级共享状态
5. `sqlx::PgPool` 在启动时创建一次并共享，不再按请求创建连接池
6. 事务提交成功后再广播权威领域事件
7. ACK 和 `control_result` 都不允许冒充消息成立

## 7. 目前最值得警惕的漂移点

在正式实现时，最容易违反官方实践的地方是：

1. 继续让 payload 自带 `session_id`
2. 继续每请求创建数据库连接池
3. 为了方便广播而自建 `room -> sockets` 私有结构
4. 为了快速成功而让发送者走旁路成功事件
5. 把请求派生数据塞进全局 state

这些点后续动工时必须先收掉。

## 8. 结论

动工前最重要的准备已经够明确：

1. `socketioxide` 和 `socket.io-client` 这对组合，在语义和兼容性上没有问题
2. 真正要防的是实现层漂移，而不是协议层不兼容
3. 后续第一阶段实现时，最该遵守的官方实践并不是更多新功能，而是：
   - 连接级认证
   - 房间广播复用
   - 共享状态正确归位
   - 长生命周期连接池
   - 事务后广播
