# 2026-04-06 DDD 领域主权与乐高式可插拔系统理解笔记

适用范围：`koko` 的长期架构方向判断。  
目标：把“DDD 领域当船长，但可以应聘二副”这句话吃透，避免把 DDD 理解成“拒绝成熟轮子”或“只剩分层口号”。

## 1. 先给结论

你说的这类 DDD，不是“什么都自己写”，也不是“技术都不重要”，而是：

1. 业务真相必须有主权。
2. 技术实现必须可替换。
3. 外部轮子可以重用，但不得反过来塑造业务核心。
4. 前后端、协议、数据库、实时框架、插件壳都应该是可插拔适配层，而不是业务内核本身。
5. 增删改之所以要像乐高一样优雅，不是因为抽象很多，而是因为边界清楚、真相单一、适配薄、契约稳。

所以“领域当船长，但可以应聘二副”这个说法，本质上是对的。  
前提是：二副只能辅佐，不得篡位。

## 2. 你说的这类 DDD，到底和官方资料怎么对上

### 2.1 Eric Evans：DDD 的三点总结，本来就不是框架中心

Eric Evans 在 `DDD Reference` 里给出的三点总结是：

1. 聚焦核心领域
2. 让领域实践者和软件实践者协作探索模型
3. 在显式边界内说统一语言

这说明 DDD 从一开始关注的就不是“选什么框架”，而是：

1. 业务核心是不是被看清了
2. 模型是不是在说真话
3. 边界是不是清楚

也就是说，DDD 首先是“让业务模型成为软件结构的主导力量”，不是“让技术结构主导软件”。

### 2.2 Evans 对 Bounded Context 的定义，直接支持你说的“乐高式可插拔”

Evans 对 `Bounded Context` 的定义是：

- 一个边界描述，在这个边界内某个模型被定义且适用。

他还明确写了：

- 大型项目里多个模型是不可避免的。
- 一旦不同模型的代码混在一起，系统就会变得 buggy、难懂、不可靠。
- 所以必须显式定义模型生效的上下文，并在边界内保持术语和模型一致。

这和你说的“项目增删改像乐高一样自由拼接”并不矛盾，反而正是它的前提：

1. 不是整个系统只有一个超大模型。
2. 而是每个边界内部有自己的稳定模型。
3. 边界之间靠清楚契约接驳。
4. 所以外层技术换了，内层业务不会一起塌。

换句话说，真正的“乐高”不是全系统一锅炖，而是“边界内统一，边界间解耦”。

### 2.3 Martin Fowler：Bounded Context 的重点是“显式关系”，不是“统一天下”

Fowler 对 `Bounded Context` 的解释很关键：

1. DDD 处理大系统的方式，不是强行做一个覆盖全组织的统一模型。
2. 而是把它拆成多个 Bounded Context。
3. 每个上下文内部保持模型一致。
4. 上下文之间显式定义关系和映射。

这直接说明：

1. DDD 不要求全系统只有一种语言。
2. DDD 要求的是不要把不同上下文的语义偷偷混在一起。

所以你要的“业务、功能、插件不会因技术替换而崩”，不是靠“大家都共用一套模糊大模型”，而是靠：

1. 核心域有自己的稳定边界
2. 插件、前端、后端入口、实时通道各有自己的位置
3. 它们和核心之间只通过稳定契约说话

## 3. Ports & Adapters 为什么正好补上你说的“二副”

### 3.1 Cockburn 说的不是“分层优雅”，而是“内外有别”

Alistair Cockburn 在 2005 年原始文章里说得很直接：

1. 应用应该在没有 UI 的情况下也能运行。
2. 应用应该在没有数据库的情况下也能运行和被测试。
3. 外部事件到来时，由技术适配器把它转换成应用可理解的调用。
4. 应用内部不应该知道外面到底是 GUI、HTTP、批处理、数据库还是别的设备。

他最重要的一句话是：

- 真正要抓住的对称性不是左右，而是 inside / outside。

这句话翻成你的语言就是：

1. 船长在里面。
2. 二副、水手、码头工、雷达、发动机都在外面。
3. 外面的东西可以换。
4. 里面的航线和裁决不能跟着乱漂。

### 3.2 Ports & Adapters 的本意，本来就允许多个“二副”

Cockburn 还明确说：

1. 一个 port 可以对应多个 adapter。
2. 同一个应用边界可以同时被 GUI、自动化测试、批处理、HTTP 接口、程序接口等驱动。
3. 数据侧同一个 port 也可以接真实数据库、内存 mock、测试数据库等不同 adapter。

这直接对应你说的：

1. 前端技术可以换
2. 后端框架可以换
3. 数据库可以换
4. 实时库可以换
5. CLI、Web、移动端、插件壳都可以换

但前提永远是：

1. 它们都是 adapter
2. 不是领域本身

所以 DDD 并不排斥“二副”，恰恰相反，它要求“二副要专业、可换、边界清楚”。  
真正违反 DDD 的，不是用了成熟轮子，而是让轮子篡位。

## 4. 你说的这类 DDD，真正反对什么

它真正反对的不是技术，而是以下几件事：

1. 业务规则写进前端状态机
2. 业务真相被框架 API 绑死
3. 房间成员资格被 runtime room 冒充
4. 消息成立被 ack、页面状态、连接状态冒充
5. 插件系统只是表面可插，核心却绑死某个具体实现
6. 同一个概念在多个层里被不同代码各自偷偷解释

换句话说，DDD 真正反对的是：

1. 真相漂移
2. 边界漂移
3. 术语漂移
4. 依赖方向漂移

而不是“不要复用成熟二副”。

## 5. 你说的这类 DDD，真正赞成什么

### 5.1 赞成“领域主权”

领域主权的意思不是“领域层最大”，而是：

1. 谁能发言
2. 谁能入房
3. 消息什么时候成立
4. 事件位置怎么推进
5. 历史如何补洞
6. 插件接口允许什么扩展

这些问题都必须由核心业务语义来决定，而不是由 UI、socket、数据库表结构或框架回调来偷偷决定。

### 5.2 赞成“技术可替换”

技术可替换不是指“今天就把所有技术都抽象一层”，而是：

1. 内部业务语义不直接依赖具体框架
2. 契约先稳定
3. 适配层尽量薄
4. 替换某项技术时，影响面被限制在边界处

只有这样，前端壳、后端壳、实时库、数据库、消息协议、插件载体才能像积木一样换。

### 5.3 赞成“多模型共存，但边界显式”

DDD 从来不要求全系统只准有一个模型。  
DDD 要求的是：

1. 一个边界内只说一种统一语言
2. 超出边界时明确做映射
3. 不允许两个模型偷偷混写在一起

这也正是“多壳共核、乐高式可插拔”的根基。

## 6. 放回 `koko`，应该怎么理解

对于 `koko` 来说，这种 DDD 不意味着：

1. 不许用 `socketioxide`
2. 不许用 `sqlx`
3. 不许用 `axum`
4. 不许用成熟 adapter

它真正意味着：

1. `socketioxide` 可以当实时主通道二副，但不能决定成员资格和消息成立。
2. `sqlx` 可以当持久化二副，但不能决定哪些事实成立。
3. `axum` 可以当 HTTP 入口二副，但不能决定页面流程和业务真相。
4. 插件机制可以有很多 adapter，但插件契约和核心语义必须稳定。

也就是说，`koko` 的正确方向不是“纯领域孤立主义”，而是：

1. 领域继续当船长
2. 成熟轮子应聘二副
3. 二副各司其职
4. 不得篡位

## 7. 这套理解对架构判断意味着什么

以后判断一项技术或轮子该不该上，不要先问：

1. 它是不是轮子
2. 它是不是很强
3. 它是不是很多人用

而要先问：

1. 它是船长，还是二副？
2. 它会不会篡夺领域主权？
3. 它替换时会不会牵动核心业务？
4. 它接入后，系统会更像乐高，还是更像焊死的大铁块？

如果答案是：

1. 它只是一个专业二副
2. 它不改写业务真相
3. 它通过稳定 port / contract 接入
4. 它可替换且边界收益明确

那它就符合你说的这类 DDD。

## 8. 结论

你说的 DDD，本质上可以压成一句话：

**不是拒绝二副，而是禁止二副篡位。**

真正高级的系统，不是所有东西都自己手搓，而是：

1. 领域模型稳定掌舵
2. 外部技术各守边界
3. Port 稳定
4. Adapter 可换
5. Context 显式
6. 真相单一

做到这一步，前端、后端、协议、数据库、实时库、插件壳的替换，才不会把业务和功能一起拖死。  
这才是你说的“像乐高积木一样，自由拼接、优雅增删改”的真正前提。
