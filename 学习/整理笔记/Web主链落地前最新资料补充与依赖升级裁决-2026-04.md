# 2026-04-18 Web 主链落地前最新资料补充与依赖升级裁决

适用范围：`koko` 当前这条「大视频秒开播放 + WebTorrent 协作分发 + 24 小时冷备退场」主链。
目标：回答两个问题：

1. **在已经有现成半成品主链的前提下，还缺哪些最新官方资料才适合继续往前施工。**
2. **当前前端相关依赖里，哪些该升，哪些先别乱动。**

## 1. 先说结论

还需要最新资料，但不需要再撒网式重查一圈。
截至 `2026-04-18`，真正还值得继续盯的只有这 `4` 组：

1. `p2p-media-loader-hlsjs 2.2.2` 的最新配置文档。
原因：项目已经接上库了，但还没正式使用它的性能旋钮。
2. `bittorrent-tracker 11.2.2`、`wt-tracker`、`aquatic_ws` 的最新官方资料。
原因：项目还缺私有 swarm 的正式门禁与容量路线，不能继续停在“能连上”阶段。
3. `hls.js 1.6.16` 与 `@videojs/html 10.0.0-beta.22` 的最新官方状态。
原因：一个是当前真正的 HLS 引擎，一个是播放器壳表面；两者不能混着升级。
4. `StorageManager.persist()`、浏览器配额、Safari/WebKit 存储策略的最新官方说明。
原因：这直接决定我们能不能把“删源后还能继续活”写成正式承诺。

一句话：

**现在最缺的不是“再找一个更厉害的新轮子”，而是把现有主链缺的 `tracker 门禁 / HLS-P2P 调参 / 存储持久化边界 / 依赖升级节奏` 用最新官方依据钉死。**

## 2. 当前项目其实已经做到哪了

这部分是基于当前仓库代码，不是纸面设想。

### 2.1 后端已经有的东西

`src/媒体上传外壳.rs` 的 `complete_media_upload` 已经在做：

- 图片产 `preview/full/original`
- 视频产 `mezzanine`
- 生成 `HLS/DASH`
- 生成 `.torrent`
- 写协作分发元数据
- 标记上传源退场

而且视频协作分发共享的不是原始上传文件，而是**规范化后的 mezzanine MP4**。这条裁决是对的，因为 WebTorrent whole-file 长尾分发应该围绕稳定载荷，而不是围绕原始上传偶发形态。

`src/媒体资产外壳.rs` 也已经有受控的：

- `manifest`
- `segment`
- `.torrent`
- `web seed`

出口。

### 2.2 前端已经有的东西

前端这条链也不是空白：

- `frontend/媒体/媒体播放.ts`
  - 查看器优先 `HLS`
  - whole-file swarm 只做短预算 warm reuse
  - 后台再补 whole-file
- `frontend/媒体/媒体协作分发.ts`
  - 已经用官方 `webtorrent`
  - 已经把 `torrent_url`、`announce`、`urlList`、`private`、`maxWebConns` 接上
  - 已经预留 `getAnnounceOpts()` 给私有 tracker 参数
- `frontend/媒体/资产协作分发运行时.ts`
  - 已经是单例 runtime / actor owner
  - 已经有 whole-file backfill 激活逻辑
- `frontend/媒体/媒体查看器.ts`
  - 已经把 `p2p-media-loader-hlsjs` 放在 `HLS` 支路增强层
  - 没让它篡位成播放器壳

也就是说，主方向并没有走错。
接下来不该“重写媒体系统”，而该继续补完生产级真相。

## 3. 现在真正缺的生产级真相

### 3.1 私有 swarm 门禁还没闭环

`src/媒体协作分发.rs` 现在返回的响应里已经有：

- `torrent_url`
- `announce_urls`
- `web_seed_url`
- `presence_url`

但 `join_ticket` 和 `ticket_expires_at` 还是 `null`。
这说明当前链路里，**私有 swarm 的入场券还没正式落地**。

所以现在最该补的不是“更多播放器技巧”，而是：

1. 服务器签发 join ticket
2. tracker 校验 ticket
3. 浏览器 announce 时稳定携带 ticket
4. ticket 过期与刷新语义

### 3.2 `p2p-media-loader` 只是接上了，还没调到高性能态

当前前端只是 `new HlsJsP2PEngine()` 默认配置。
但官方文档暴露出来、而我们还没正式接进去的关键参数包括：

- `highDemandTimeWindow`
- `httpDownloadTimeWindow`
- `p2pDownloadTimeWindow`
- `simultaneousHttpDownloads`
- `simultaneousP2PDownloads`
- `announceTrackers`
- `rtcConfig`
- `httpNotReceivingBytesTimeoutMs`
- `p2pNotReceivingBytesTimeoutMs`

这意味着：

**现在项目已经选对了轮子，但还没把它用到“高性能设计”的那一层。**

### 3.3 浏览器持久化还没有产品级承诺边界

`WebTorrent` / IndexedDB / OPFS 这条路不是“写进去就永远在”。
官方资料已经把边界说得很清楚：

- 默认是 `best-effort`
- `persist()` 只是请求，不保证一定批准
- Safari / WebKit 仍可能按策略回收
- Safari 17 起配额和策略比旧时代好很多，但也不是无限、不是绝对承诺

所以正式产品语义不能写成：

- “删源后永远还能播”

更准确的语义应该是：

- “在支持且授予持久化的环境里，尽量延长存活时间”
- “不支持或未授予时，继续按 best-effort 协作分发处理”

### 3.4 观测还不够像生产系统

下一步至少要有：

- HLS 首播耗时
- whole-file backfill 启动率
- backfill 完成率
- swarm 命中率
- peer presence
- cold start 落 HTTP / 落 P2P 的比例
- tracker 拒绝率与 ticket 过期率

没有这组指标，后面再调 `p2p-media-loader` 和 tracker 都还是靠体感。

## 4. 这轮补齐后，依赖该怎么裁决

检索日期统一按 `2026-04-18`。

| 包 | 当前项目 | 最新稳定/发布状态 | 裁决 |
| --- | --- | --- | --- |
| `webtorrent` | `^2.8.5` | `2.8.5` | 已对齐最新版，先不动 |
| `bittorrent-tracker` | `^11.2.2` | `11.2.2` | 已对齐最新版，先不动 |
| `p2p-media-loader-hlsjs` | `^2.2.2` | `2.2.2` | 已对齐最新版，先不动，先把配置接进来 |
| `hls.js` | `^1.6.15` | `1.6.16` | 建议补一个小步 patch 升级 |
| `@videojs/html` | `10.0.0-beta.17` | `10.0.0-beta.22` | 暂不跟着追，单开一轮评估 |

### 4.1 为什么 `webtorrent / bittorrent-tracker / p2p-media-loader` 先不升

因为它们已经是当前最新版本。
现在的问题不是“版本太旧”，而是：

- `tracker` 门禁没闭环
- `p2p-media-loader` 没调参
- 存储持久化边界没正式落产品语义

先把这些做对，比继续追版本更值。

### 4.2 为什么 `hls.js` 建议升到 `1.6.16`

`hls.js` 是当前真实负责 HLS 播放兼容和 MSE/MMS 处理的引擎。
项目现在是 `^1.6.15`，而 npm 最新已是 `1.6.16`，发布时间是 `2026-04-13`。

这是小版本内 patch 升级，风险相对可控。
建议在下面这些冒烟前提下升级：

1. Chrome 桌面端 HLS 观看器
2. Safari macOS 原生 HLS 路径
3. Safari iOS `17.1+` / MMS 路径
4. 前后台切换、seek、重进查看器

### 4.3 为什么 `@videojs/html` 先别从 `beta.17` 直接追到 `beta.22`

原因不是它不值得看，而是它现在仍明确标着：

- `Beta`
- `Close to stable`
- `Experimental adoption in real projects`

再加上它自己的 beta 发布节奏很快，`2026-04-11` 到 `2026-04-18` 之间已经从 `beta.17` 跑到 `beta.22`。
这说明这条版本线还在快速收敛期。

而当前项目里，`@videojs/html` 更偏播放器壳表面，不是 HLS 真正的兼容核心。
所以更稳的做法是：

1. 先把 `tracker` 门禁、`p2p-media-loader` 调参、持久化语义补完
2. `hls.js` 单独 patch 升级
3. `@videojs/html` 再独立做一次 beta 追版评估，不跟媒体主链修补混在一起

## 5. 还需要继续追的官方资料清单

### 5.1 `p2p-media-loader` 官方 API 文档

这组资料现在是必须继续盯的，因为性能旋钮都在这里：

- `HlsJsP2PEngine`
- `StreamConfig`
- `announceTrackers`
- `rtcConfig`
- `highDemandTimeWindow`
- `simultaneousHttpDownloads`
- `simultaneousP2PDownloads`

直接用途：

- 给 `HLS` 支路补正式调参
- 决定是否要分 `viewer` / `inline` / `background` 三套配置

### 5.2 `bittorrent-tracker` 官方 README 与 `wt-tracker` / `aquatic` 官方资料

当前最关键的不是“哪个 tracker 最酷”，而是：

- 哪个更适合先实现私有 swarm ticket 门禁
- 哪个文档更清楚地支持自定义 announce 参数和校验
- 哪个更适合后续容量扩展与观测

目前按资料成熟度看：

1. 第一阶段优先 `bittorrent-tracker`
2. 如果后面吞吐或运维诉求上来，再认真评估 `wt-tracker` 和 `aquatic_ws`

原因很简单：
`bittorrent-tracker` 的 client `getAnnounceOpts()` 和 server `filter()` 这条参数/校验路径已经很清楚，最适合先把私有 swarm 门禁闭环。

### 5.3 `hls.js` 官方 README / 文档

这里要盯的不是“播放器长什么样”，而是官方兼容裁决：

- Safari / iOS 17.1+ 的 MMS 支持边界
- 什么时候该走原生 HLS，什么时候该走 Hls.js
- 多平台兼容时，manifest 要严格遵守 HLS 规范

这些直接影响 `koko` 观看器里“谁拿首播路径”的裁决。

### 5.4 `@videojs/html` 官方 README / npm

这里要盯的是：

- 它仍然是 beta
- 它是 HTML / Web Components 播放器壳库
- 它并不是 `HLS` 兼容层本身

这能防止我们把“升级播放器壳”和“修播放主链”误绑到一起。

### 5.5 MDN + WebKit 的存储策略文档

这组资料直接决定删源后还能不能正式承诺：

- `navigator.storage.persist()`
- `navigator.storage.persisted()`
- `navigator.storage.estimate()`
- best-effort vs persistent
- Safari / WebKit 的 quota 和 eviction

当前最重要的产品判断是：

**Web 端本地持久化只能作为增强能力，不该被写成无条件承诺。**

## 6. 下一步最实际的施工顺序

如果继续落到代码，最稳的顺序是：

1. 先补 `join_ticket` 签发、tracker 校验、过期刷新和失败测试。
2. 再把 `p2p-media-loader` 的核心配置正式接入 `HLS` 支路。
3. 再补 `persisted()/persist()/estimate()` 的持久化 owner 和退化语义。
4. 再把 HLS 首播、backfill、swarm、ticket 命中率收成指标。
5. 然后只做一个小步依赖升级：`hls.js 1.6.15 -> 1.6.16`。
6. 最后单开一轮 `@videojs/html beta.17 -> beta.22` 评估，不要和主链修补混批。

## 7. 这次最该记住的一句话

**项目现在最缺的不是新轮子，而是把现有主链的正式门禁、正式调参、正式持久化语义和正式观测补齐；依赖升级也要按主次来，先补 `hls.js` 小步 patch，再单独评估 `@videojs/html` beta 追版。**

## 9. 哪些判断是推论

下面这些不是官方原文，而是基于上面资料对 `koko` 的工程推论：

1. 第一阶段优先把私有 swarm 门禁落在 `bittorrent-tracker`，而不是直接切 `wt-tracker` / `aquatic_ws`。
2. `hls.js 1.6.16` 应优先于 `@videojs/html beta.22` 升级。
3. 浏览器本地持久化只能写成增强语义，不能写成绝对承诺。
