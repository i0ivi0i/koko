# 浏览器媒体持续播放与静默恢复：官方能力与现成轮子盘点

日期：2026-04-13  
适用范围：`koko` 浏览器端群聊视频/音频附件，目标是网络波动时尽量不断播，网络恢复后自动静默恢复，避免继续手搓媒体缓存、恢复与分发基础设施。

## 1. 先说结论

先把结论说死，避免后面讨论漂：

1. 现代浏览器确实自带多层缓存与持久化能力，但这些能力不会自动把“持续播放 + 静默恢复 + 离线可重开”整套体验替项目做完。  
2. 这类体验必须由应用正式拥有一个媒体恢复 owner / runtime 来编排；浏览器原生能力与第三方库只负责提供底座。  
3. 对 `koko` 当前栈，最该先复用的不是新播放器，而是已经在依赖里的 `Workbox` 与现有 `WebTorrent`；`Vidstack` 继续只做桌面播放器壳，不要误判成缓存/恢复方案。  
4. 如果后续愿意把热点视频改造成 `HLS/DASH` 分片流媒体，`Shaka Player` 或 `hls.js` 再配 `p2p-media-loader`，比继续手搓“附件 MP4 + 自定义恢复状态机 + 自定义分片缓存”更接近成熟方案。  
5. 实时层不要再找“神奇重连轮子”了。`socket.io` 官方已经把短断线恢复、ack/retry、重连退避这些能力给了；真正缺的仍是应用自己的事件补洞与媒体恢复协议。  

## 2. 浏览器原生到底给了什么

### 2.1 浏览器已经有的能力

浏览器现在已经有这些正式能力：

- `HTTP cache`：浏览器会按 `Cache-Control`、`ETag`、`Last-Modified` 等头自动缓存响应。  
- `CacheStorage + Service Worker`：可以精确控制哪些请求进缓存、何时命中、何时更新。  
- `IndexedDB`：适合存媒体索引、任务队列、恢复元数据、结构化状态。  
- `OPFS`：适合更大、更偏文件型的持久字节存储。  
- `navigator.storage.persist()`：可以请求更稳定的持久存储，减少在存储压力下被淘汰。  
- `Background Sync`：网络恢复后由 SW 继续重试失败请求。  

这些能力足够搭一个正式媒体恢复体系，但前提是应用自己把它们接成明确边界。

### 2.2 浏览器没有自动替你做的事

浏览器不会自动处理这些业务语义：

- 当前播放源失效后，是否切到本地缓存 / swarm / 锚点源。  
- 什么时候进入 `recovering`，什么时候退回 `degraded`。  
- 视频元素 `error / stalled / waiting` 出现后，如何重判播放源。  
- 网络恢复后，哪些媒体任务该静默续拉、哪些该继续补块、哪些该放弃。  
- 哪些字节算“已经完整可离线重开”，哪些只是曾经播过几个片段。  

所以“浏览器有缓存”不等于“群聊视频一定会优雅恢复”。

## 3. 官方实践里最关键的几条

### 3.1 Workbox 对媒体缓存的正式建议

`Workbox` 官方对音视频缓存说得很直接：

1. 媒体请求必须正确处理 `Range`，要用 `workbox-range-requests`。  
2. `<video>` / `<audio>` 需要显式带 `crossorigin`。  
3. 如果想真正从缓存里播媒体，应该提前把完整媒体放进缓存；“边播边顺手缓存”不可靠，因为播放过程通常只拿到部分 `206 Partial Content`。  

这三条非常关键，因为它们直接解释了为什么“看过一次”并不自动等于“以后断网还能播”。

### 3.2 Workbox 对恢复与补发的正式建议

`workbox-background-sync` 官方建议：

1. 失败请求可进入 SW 队列，浏览器在网络恢复后自动重放。  
2. 支持 `Background Sync` 的浏览器会按浏览器自己的节奏重试，通常带退避。  
3. 不支持 `Background Sync` 的浏览器，Workbox 也会在 SW 再启动时尝试重放。  
4. 默认只有真正抛异常的网络失败才会重试；如果想把 `5xx` 也视为可重试，需要在 `fetchDidSucceed` 里主动把它转成失败。  

这更适合“待发送消息 / 上报 / 补发命令”，不是直接替代视频字节缓存。

### 3.3 Socket.IO 官方对断线恢复的边界

`Socket.IO` 官方文档的边界很清楚：

1. 客户端不可能永远在线。  
2. 服务端默认不存事件。  
3. `connectionStateRecovery` 只能处理短暂断线，而且恢复不保证总成功。  
4. 真要做更强一致性，还是得应用自己持久化事件并按 offset 补发。  
5. `retries + ackTimeout` 只对有服务端 ack 的命令有意义。  

所以实时层的结论是：官方轮子已经给到“短断线恢复 + 退避重连 + ack 重发”，但不会替媒体系统定义恢复真相。

### 3.4 WebTorrent 官方给到的能力边界

`WebTorrent` 官方浏览器侧能力主要是：

1. 通过 `Service Worker` 建立浏览器侧 server。  
2. `client.add(...)` 加入 swarm。  
3. `torrent.on('wire')`、`torrent.on('noPeers')`、`torrent.on('done')` 这些运行态信号可直接消费。  
4. `destroyStoreOnDestroy` 只是控制销毁 torrent 时要不要删 store，不等于应用已经拥有“跨重启恢复播放”的正式协议。  

所以它很适合做“在线分发层”，但不该被误判成“产品级离线恢复层已经自动完成”。

## 4. 为了你要的用户体验，现成轮子该怎么分层看

### 4.1 `Workbox`：最应该优先吃满的 SW 缓存/补发层

这是 `koko` 当前最该先复用的成熟轮子，因为项目已经在依赖里了。

建议优先考虑的官方模块：

- `workbox-range-requests`
  - 负责媒体 `Range` 请求正确命中缓存。
  - 这是音视频缓存主路径的必选项，不是可选优化。
- `workbox-cacheable-response`
  - 负责严格限定哪些媒体响应才允许进入缓存。
  - 适合结合 `200`、自定义头、同源策略做收口。
- `workbox-expiration`
  - 负责媒体缓存数量/年龄治理，避免配额无限膨胀。
- `workbox-broadcast-update`
  - 负责缓存更新后通知页面侧，让页面静默刷新可用源或提示“已补齐本地可播版本”。
- `workbox-background-sync`
  - 负责失败命令、上报、presence、补发请求的重放，不负责完整媒体离线播放。

结论：

- 这不是“要不要另找轮子”的问题。  
- `Workbox` 就是现成轮子，而且 `koko` 已经有了。  
- 当前缺的是把它从“只管 app shell 预缓存”升级成“正式媒体 runtime 缓存层”。  

### 4.2 `WebTorrent`：继续保留，但只当文件级 P2P 分发层

`WebTorrent` 很适合继续承担：

- 在线热分发；
- peer 间补块；
- 后端抖动时的 swarm 兜底；
- `wire / noPeers / done` 这些运行态信号。

但它不该被赋予它没有承诺的职责：

- 不要把它当作完整离线媒体仓库。  
- 不要把“浏览器里可能留着 store”误判成“应用已经拥有本地可重开资产真相”。  
- 不要让它单独承担静默恢复状态机。  

结论：

- 继续复用。  
- 不用重写。  
- 但上面必须补正式的 `MediaOwner / MediaRuntime`。  

### 4.3 `Vidstack`：继续做播放器壳，不是恢复方案

`Vidstack` 官方定位本来就偏播放器 UI / provider 编排，不是媒体离线与恢复引擎。  
如果错把它当成“更换播放器就能自动解决黑屏、转圈、掉源”的方案，会走偏。

结论：

- 保留 `Vidstack` 做桌面视频壳是合理的。  
- 不要指望它替代缓存、恢复、P2P、离线资产管理。  

### 4.4 `Shaka Player`：如果愿意转 `HLS/DASH`，这是最重磅的现成轮子

`Shaka Player` 官方明确支持：

- `HLS` / `DASH`；
- 离线存储与离线播放；
- `NetworkingEngine` 级别的请求、失败、重试、响应回调；
- 更完整的分片流媒体能力。

这意味着：

1. 如果以后热点视频愿意转成 `HLS/DASH` 分片流，`Shaka` 能直接给到更成熟的离线存储与恢复钩子。  
2. 这比继续手搓“原始附件 MP4 的缓存切片协议 + 恢复状态机 + 自定义播放器集成”更省坑。  
3. 它的代价也很明确：需要后端或媒体管线配合产出分片清单与分段资源，不适合零改造硬塞到当前附件直链模式里。  

结论：

- 如果目标升级到“热点媒体标准流媒体化 + 更强离线能力”，优先看 `Shaka Player`。  
- 它不是小修小补方案，而是“媒体形态升级”方案。  

### 4.5 `hls.js`：恢复能力不错，但离线资产管理不如 `Shaka` 完整

`hls.js` 官方有这些优点：

- 成熟的 `HLS` 播放引擎；
- `recoverMediaError()` 这类现成恢复入口；
- 浏览器端跨平台 `MSE` 播放经验丰富；
- 跟 `Vidstack`、`p2p-media-loader` 有成熟集成面。

但它的边界也清楚：

- 它强在播放与错误恢复；  
- 不强在完整离线存储协议。  

结论：

- 如果未来只做 `HLS`，`hls.js` 是成熟轮子。  
- 但若你同时想要更正式的离线下载与离线播放，`Shaka` 通常更重、更完整。  

### 4.6 `p2p-media-loader`：如果走分片流媒体，这个轮子很值得重点看

这个库官方明确主打：

- 浏览器内 `HLS` / `MPEG-DASH` 的 `P2P` 分发；
- 直接集成 `hls.js`、`Shaka Player`；
- 还能和 `Vidstack` 这类播放器 UI 结合；
- 文档里有正式的 `SegmentStorage` 接口，允许把 segment 存起来，而不是只做内存级接力。

这非常重要，因为它说明：

1. 如果未来把群聊热点视频做成 `HLS/DASH`，不必自己手搓“分片级 P2P + segment 存储协议”。  
2. 现成生态已经把 `player + segment + P2P + storage hook` 这条链打出来了。  
3. 对“多人同时看一个视频”的场景，它比继续围着单文件 MP4 自己拼所有能力更像成熟路。  

结论：

- 若未来接受媒体形态升级，`Shaka + p2p-media-loader` 或 `hls.js + p2p-media-loader` 是最值得认真评估的成熟组合。  

### 4.7 `Dexie`：如果 IndexedDB 逻辑继续变复杂，可以考虑，但不是当下首选

项目当前已经有 `idb`。  
如果以后媒体索引、缓存目录、恢复元数据、逐出策略、后台队列都往 IndexedDB 里涨，`Dexie` 会比继续手写更省心。

但当前判断是：

- 现在还没到必须为此再引一个更厚封装的程度；  
- 先把媒体恢复协议与存储边界定义清楚更重要；  
- `idb` 目前足够做第一轮媒体元数据仓库。  

结论：

- `Dexie` 可以列入候选。  
- 但它不是当前最急缺的轮子。  

## 5. 回到 `koko`，最现实的路线怎么选

### 5.1 短中期最现实路线：不换媒体形态，先把当前栈补完整

如果还不想把附件体系升级成 `HLS/DASH`，那最现实的路线是：

1. 保留现有 `WebTorrent + Vidstack + socket.io-client`。  
2. 把 `Workbox` 从“只管应用壳”扩成正式媒体缓存层。  
3. 新建正式 `MediaOwner / MediaRuntime`，统一处理：
   - `playing / recovering / degraded / done-local`
   - 视频元素 `error / stalled / waiting`
   - `socket` 重连、`online/offline`、`pageshow/pagehide`
   - `wire / noPeers / done`
4. 用 `CacheStorage + RangeRequestsPlugin` 管“完整可播媒体”。  
5. 用 `IndexedDB` 先管媒体索引、恢复元数据、缓存状态，必要时再把大字节挪到 `OPFS`。  

这条路复用最多、风险最小，也最符合当前仓库状态。

### 5.2 中长期升级路线：热点视频流媒体化

如果后续愿意为热点视频引入媒体处理链：

1. 后端产出 `HLS/DASH` 分片。  
2. 播放层切到 `Shaka` 或 `hls.js`。  
3. P2P 层接 `p2p-media-loader`。  
4. `Vidstack` 继续只做 UI/player shell。  

这条路更像“正式媒体平台”，对持续播放、ABR、自恢复、多人观看成本分摊都更友好，但改造面更大。

## 6. 不建议继续手搓的东西

明确列出来，防止后面又滑回去：

- 不要手搓媒体 `Range` 缓存协议。先吃 `Workbox range-requests`。  
- 不要手搓后台补发队列。先吃 `Workbox background-sync`。  
- 不要手搓播放器错误恢复壳，尤其是如果以后转 `HLS`。先看 `hls.js` / `Shaka` 已有能力。  
- 不要手搓分片级 P2P 引擎。若走 `HLS/DASH`，先评估 `p2p-media-loader`。  
- 不要为了实时恢复再包一层私有 `socket.io` 客户端框架。先用官方 `connectionStateRecovery`、`retries`、`ackTimeout`，把真正的业务补洞协议做对。  

## 7. 对当前仓库的直接判断

截至 `2026-04-13`，`frontend/package.json` 已经有：

- `socket.io-client`
- `vidstack`
- `webtorrent`
- `idb`
- `workbox-core`
- `workbox-precaching`

而 `pnpm-lock.yaml` 里已经出现：

- `workbox-background-sync`
- `workbox-broadcast-update`
- `workbox-cacheable-response`
- `workbox-expiration`
- `workbox-range-requests`

这说明当前更合理的方向不是“再找一个全新的大轮子推倒重来”，而是：

1. 先把已经在依赖图里的成熟轮子吃满。  
2. 再决定是否要把热点视频升级成 `HLS/DASH + Shaka/hls.js + p2p-media-loader`。  

## 8. 最后给一个清晰判断

围绕你要的用户体验，现成轮子的判断如下：

- 立即该复用：`Workbox` 全家桶里和媒体缓存/补发相关的模块。  
- 继续保留：`WebTorrent`，但只当文件级 P2P 分发层。  
- 继续保留：`Vidstack`，但只当播放器壳。  
- 未来若升级媒体形态，优先评估：`Shaka Player`、`hls.js`、`p2p-media-loader`。  
- 现在不急着再引：`Dexie`。  
- 不值得再去找神奇替代品：`socket.io-client` / `socketioxide` 这层已经有成熟官方能力，真正缺的是应用协议。
