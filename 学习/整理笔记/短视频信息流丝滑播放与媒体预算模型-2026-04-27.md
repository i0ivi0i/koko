# 2026-04-27 短视频信息流丝滑播放与媒体预算模型

适用范围：`koko` 浏览器群聊消息流里的视频自动播放、预览、滑动切换、查看器、`WebTorrent` 协同分发与前台资源预算。  
目标：把 X / TikTok 这类短视频信息流的公开技术模型，压成 `koko` 可直接施工的边界。重点不是照抄产品形态，而是学习它们为什么能“看起来全页面都能播”，但浏览器仍不卡、不崩、不闪。

## 1. 先说结论

短视频信息流丝滑的核心不是“很多视频同时播放”，而是：

1. 列表只渲染当前窗口和少量邻近项。
2. 真正重播放的媒体对象极少，通常只有当前项和少数 warm 项。
3. 视频源不是整块原始 MP4 直塞，而是多码率、分片、可自适应的播放源。
4. 预加载按距离分层：当前重播放，下一两个预热，远处只保留封面、metadata 或轻索引。
5. 旧请求、旧预览、旧 reader、旧 source 必须能被取消，而不是等它自然跑完。
6. 页面隐藏、切后台、低性能设备、弱网时，系统主动降级资源，而不是让浏览器崩了再补救。

一句话：**用户感觉是全页面都能播；系统真实执行是“一个 owner 重播放，少数邻居轻预热，远处全部冷表达”。**

## 2. X / TikTok 公开资料能确认什么

### 2.1 X 的视频是变体模型，不是单一路径

X API 的 media 数据公开暴露 `variants`，每个 variant 有 `bit_rate`、`content_type`、`url`。这说明它的媒体交付至少不是“一个固定源一路播到底”，而是带有多格式或多码率候选。

对 `koko` 的启发：

1. 前端不应把“附件 URL”当成唯一播放真相。
2. 播放入口应该消费 source descriptor，而不是自己猜 URL。
3. 码率、封装、来源、冷启动路径、长期协作路径应该先被上游 owner 裁决。

### 2.2 TikTok/Dashlet 研究暴露了短视频流的真实模型

NSDI 2023 的 Dashlet 论文专门研究 TikTok 这类短视频流。论文描述的核心是：

1. 服务端给客户端一组按顺序排列的视频 manifest。
2. 每个视频有 chunk 和 bitrate 信息。
3. 客户端维护多个 logical buffer。
4. ABR 不只考虑当前视频，还考虑用户可能继续滑到下一个视频。
5. 下载顺序不是盲目全量拉，而是按预期观看路径、网络估计、rebuffer 代价和浪费字节综合决定。

对 `koko` 的启发：

1. “下一个可能看的视频”可以预热，但不等于整房历史都要预热。
2. 预热必须有窗口和预算，不是消息一到就全量启动。
3. 远离当前交互路径的视频，即使曾经出现过，也必须退回轻态。

### 2.3 ByteDance XGPlayer 的价值是“短视频播放器工程经验”

XGPlayer 官方说明里明确提到：ByteDance 视频业务多是短视频，早期基于 video.js 二次开发，后来为了 UI 定制、无缝切换、流量节省和 MP4 分段加载等目标做了自己的播放器，并支持 FLV、HLS、DASH。

对 `koko` 的启发：

1. XGPlayer 值得作为短视频播放器体验与预加载策略参考。
2. 但 `koko` 现阶段已经裁决一颗 canonical `Video.js v10`，不能因为看到 XGPlayer 就再长第二颗正式播放器。
3. 可以借模型，不急着替换主播放器。

## 3. 它们真正靠什么丝滑

### 3.1 虚拟列表挡住 DOM 爆炸

大信息流不能让 DOM 等于全量数据。只渲染当前窗口和少量 overscan，是丝滑的第一层地基。

`koko` 施工裁决：

1. 继续复用 `@tanstack/lit-virtual`。
2. 消息是否存在、是否已读、是否可见，不能由 DOM 宣布。
3. `房间消息窗.ts` 只投影窗口，不拥有整房媒体真相。

### 3.2 单 owner / 少量重对象挡住解码器和 GPU 爆炸

浏览器真正贵的不是一个 `<div>`，而是视频解码、MSE buffer、GPU texture、WebRTC/DataChannel、reader、range 请求和播放器状态机。

`koko` 施工裁决：

1. `activeFormalPlayerCount == 1`。
2. `autoplayOwnerCount == 1`。
3. 非 owner 视频默认走 preview truth overlay。
4. 近视口真实 preview `<video>` 必须有硬上限。
5. owner 交接结束后，旧 owner 的真实媒体表面必须退场。

### 3.3 分层预热挡住请求风暴

短视频流的正确预热不是“越多越好”，而是按距离分层：

1. 当前项：正式播放、解码、统计、帧监控。
2. 下一两个候选：manifest / metadata / 首片段 / preview truth。
3. 更远项：poster、尺寸、轻索引。
4. 离开窗口：取消请求、释放 source、释放 reader、释放 preview consumer。

`koko` 施工裁决：

1. `room-media-window-observed` 到达前，禁止整房历史预热。
2. 窗口缩回后，旧代次 locator / preview / bootstrap 必须中止。
3. `inflightLocatorCount` 不是自然回落指标，而是可取消链是否成立的证据。

### 3.4 ABR / 分片流挡住弱网卡顿

高帧率、高码率不等于永远给最高码率。成熟平台会根据设备、网络、buffer 和硬解能力做选择。

`koko` 施工裁决：

1. `HLS/DASH/CMAF + hls.js` 仍适合作为 `0-24 小时` 标准流媒体冷启动支路。
2. `p2p-media-loader-hlsjs` 只能增强 HLS 支路的分段 P2P，不能篡位成长期正式主链。
3. 长期正式协作分发主链仍是 `WebTorrent` whole-file swarm。
4. `MediaCapabilities.decodingInfo()` 可用于判断当前设备是否适合某 codec / 分辨率 / 码率。

### 3.5 帧级证据挡住“感觉丝滑”的幻觉

是否丝滑不能只靠肉眼。浏览器已经有帧级和长任务级观测能力。

`koko` 施工裁决：

1. `requestVideoFrameCallback()` 用来采集真实视频帧提交、掉帧和处理延迟。
2. `PerformanceObserver(long-animation-frame)` 用来抓滚动期间主线程长帧。
3. Chrome DevTools Performance 用来复核 layout/style 是否超过预算。
4. 验收必须记录数据，不允许只说“看起来不卡”。

## 4. 现成轮子与在 `koko` 的位置

### 4.1 已经在项目里的轮子

1. `@tanstack/lit-virtual`
   - 位置：万人消息流虚拟化。
   - 边界：只算窗口，不决定消息真相。
2. `Video.js v10`
   - 位置：唯一播放器壳。
   - 边界：不拥有 source owner，不拥有 WebTorrent 主链，不拥有整房媒体生命周期。
3. `hls.js`
   - 位置：标准 HLS 播放引擎。
   - 边界：冷启动和标准流媒体支路，不是长期删源后主链。
4. `p2p-media-loader-hlsjs`
   - 位置：HLS 支路的 segment-level P2P 增强。
   - 边界：不替代 WebTorrent whole-file swarm。
5. `WebTorrent`
   - 位置：长期正式协作分发主链。
   - 边界：不能被前台重播放对象绑死；应拆出轻帮助态。
6. `Workbox`
   - 位置：App Shell、静态资源和 range/cache 辅助。
   - 边界：不能缓存聊天业务真相。
7. `xstate`
   - 位置：AppRuntime / actor owner。
   - 边界：只收口应用真相，不直接操作 DOM 和播放器细节。

### 4.2 可参考但不直接替换的轮子

1. `xgplayer`
   - 可借鉴：短视频无缝切换、MP4 分段加载、流量节省、播放器插件化。
   - 当前裁决：只作为参考或 POC，不替换 canonical `Video.js v10`。
2. `Shaka Player`
   - 可借鉴：DASH/HLS/DRM/ABR 能力。
   - 当前裁决：除非未来明确需要 DASH/DRM 统一引擎，否则不引入第二播放器栈。
3. 托管视频平台如 Mux / Cloudflare Stream
   - 可借鉴：转码、ABR ladder、CDN、监控。
   - 当前裁决：可以学习流水线，不应替代 `WebTorrent` 长期协作主链。

## 5. `koko` 的正式逻辑模型

```text
浏览器滚动/可见性/生命周期信号
  -> AppRuntime / actor owner
  -> 当前媒体窗口 truth
  -> 媒体编排层只启动当前窗口 + owner + viewer + warm candidates
  -> 正式播放交给唯一 Video.js player
  -> 长期分发交给 WebTorrent
  -> 冷启动/标准流媒体交给 HLS/hls.js/p2p-media-loader 支路
  -> 退场后 heavy 对象必须降为轻帮助态或冷态
```

这里最重要的是顺序：

1. 先有窗口真相。
2. 再启动重媒体对象。
3. 窗口缩回先取消旧请求。
4. 退场后先释放 heavy，再保留必要轻帮助。

## 6. 必须写进实施计划的红线

1. 禁止 `activeWindowIds.size === 0 -> return attachments` 这类整房回退。
2. 禁止每个视频卡片都长期挂真实 `<video>`。
3. 禁止每个卡片都有自己的播放器实例。
4. 禁止旧 locator / preview / bootstrap 请求在窗口缩回后继续写回 ready。
5. 禁止 `cached-help` 只凭“本地完整缓存”重新拉活整房历史。
6. 禁止零引用 WebTorrent 会话继续持有 whole-file heavy reader。
7. 禁止为了不崩而削弱 `WebTorrent` 正式主链。
8. 禁止把 `p2p-media-loader` 或 HLS 支路提升成长期资产 owner。
9. 禁止用静态预览图假装丝滑，真实 owner handoff 仍必须无闪烁。
10. 禁止没有 browser smoke 数据就宣布完成。

## 7. 对当前零崩溃计划的直接补强

当前 [万人群聊浏览器零崩溃零闪烁最终根因收口计划](../../docs/superpowers/plans/2026-04-27-万人群聊浏览器零崩溃零闪烁最终根因收口计划.md) 的主线是对的：根因不是单个播放器，而是窗口真相、请求取消、帮助链轻重态。

这份笔记给它补上一个更明确的短视频信息流模型：

1. 不追求“所有视频都活着”。
2. 追求“所有视频看起来随时能接管，但真实 heavy 永远受预算控制”。
3. 当前项重播放，邻近项轻预热，远处项冷表达。
4. 协作分发继续积极，但前台资源不能被协作收益绑架。
