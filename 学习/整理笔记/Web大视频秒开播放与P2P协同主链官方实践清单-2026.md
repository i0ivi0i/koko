# 2026-04-16 Web 大视频秒开播放与 P2P 协同主链官方实践清单

适用范围：`koko` 当前 `Web 前端 + Rust 后端` 的大视频上传完成后播放、秒开体验、`24 小时` 冷备窗口、以及服务器已删原视频和母本后的长期协作分发。  
目标：只看当前 `Web` 阶段最该站的官方路线，把 `WebTorrent / WebRTC / HLS / DASH / CMAF / hls.js / p2p-media-loader / Video.js v10` 的真实边界一次讲透，不再靠想象拼主链。

## 1. 先说结论

这一轮最该记死的结论有八条：

1. **如果目标是“服务器已经没有原视频和母本了，群友仍能高速点开、高速边下边播、高速互帮互助”，那长期正式分发主平面必须是 `WebTorrent` 满血 whole-file swarm。**
2. `HLS / DASH / CMAF` 仍然是当前浏览器标准流媒体主链和秒开冷启动主路，但它们本身不解决“服务器删光后仍能活”这件事；如果清单和分段也跟服务器一起删掉，长期存活就不能继续指望它们。
3. `p2p-media-loader` 官方定位是 `Hls.js / Shaka` 的**分段级 P2P 增强层**，不是第二播放器壳，也不是长期 whole-file 协作分发平面。
4. `Video.js v10` 官方当前仍是 **beta**。对 `koko` 当前阶段，最稳口径仍是：它只做**唯一播放器壳**，不吞 `hls.js`，不吞 `WebTorrent`，不碰业务真相。
5. `WebRTC` 官方定位只是 peer-to-peer 连接与 `RTCDataChannel` 传输能力；它是 transport，不是业务真相，不是媒体协议，不是播放主链。
6. 当前阶段最像样的双层 P2P 结构是：
   - `WebTorrent` 负责整文件长期协作分发、补齐、做种、服务器删源后的继续存活。
   - `hls.js + p2p-media-loader` 负责 `HLS/CMAF` 支路的分段带宽分摊和冷启动增强。
7. 想让 `24 小时` 后仍高速播放，不是只把库接上就行，而是**必须尽快把完整资产补齐到足够多的 peer**。没有完整持有者，P2P 再“满血”也无源可传。
8. 当前阶段最现实的秒开策略，不是宗教式只押一条路，而是：**播放时先 aggressively 尝试 swarm，同时并行或近并行预热 `HLS/CMAF`；swarm 不够热就立刻让标准流媒体顶上，但 whole-file backfill 和 seeding 不能停。**

## 2. 官方资料里最关键的事实

### 2.1 `WebTorrent` 官方真正强在哪里

`WebTorrent` 官方文档把自己直接定义成：

- “streaming torrent client for Node.js and the web”
- 浏览器侧直接支持 `service worker + client.createServer({ controller }) + file.streamTo(...)`
- `client.add()` 原生支持：
  - `announce`
  - `getAnnounceOpts`
  - `urlList` (`Web Seed`)
  - `maxWebConns`
  - `private`
  - `store`
  - `destroyStoreOnDestroy`
  - `strategy`

更关键的是官方明确写了：

- 下载中的 torrent 默认会自动继续做种。
- 浏览器侧如果不想跨会话保留数据，最晚要在 `beforeunload` 前手动销毁 store。
- `strategy` 直接支持 `rarest` 和 `sequential`，而默认就是 `sequential`。

这几句合起来的真实含义是：

1. `WebTorrent` 官方就鼓励浏览器侧边下边播，不需要你再手搓第二套“顺序拉块内核”。
2. `Web Seed` 是官方一等公民，不需要你自造私有 HTTP 补块协议。
3. “看完继续帮传”本身就是它的自然路径，不需要再补一套私有 seeding 状态机。
4. 当前 `Web` 阶段如果想让服务器退出后内容还能继续活，最该做的是把 `WebTorrent` 的 store / stream / seed 路径吃满，而不是把它降级成旁路 hint。

### 2.2 `WebTorrent` FAQ 明确写死的限制

`WebTorrent` FAQ 里有几条必须正视：

1. 它在浏览器里走的是 `WebRTC`，而不是普通 TCP/uTP。
2. 浏览器里的 `WebTorrent` 只能下载由 **WebRTC-capable** 客户端做种的 torrent。
3. 它支持顺序流式播放；缓冲足够后，官方方向是回到更健康的 `rarest-first`。
4. 它**不能 out-of-the-box 做 live streaming**。
5. 浏览器里要想稳定流式播放和 seek，官方点名最稳的是 `.mp4 / .m4v / .m4a`。

这几条很重要，因为它们直接决定了“满血 P2P”到底能做到什么：

1. `24 小时` 后想继续播，peer 里至少要有能给 web peer 做种的 `WebRTC` 能力。
2. 你不能把 `WebTorrent` 误判成“天然 live、天然任意封装、天然永生”。
3. 想让 whole-file plane 在浏览器里长期承担正式播放，就要保证长期资产的封装形态适合它直接 stream 和 seek。

### 2.3 `WebRTC` 官方的定位非常克制

WebRTC 官方文档说得很直接：

- peer-to-peer 连接靠 `RTCPeerConnection`
- 任意数据传输靠 `createDataChannel()` 返回 `RTCDataChannel`
- 数据通道发送的是字符串、`Blob`、`ArrayBuffer` 等原始数据

所以 `WebRTC` 的位置就是：

- 浏览器之间的底层传输
- 连接建立、开关、消息、流控

它**不**回答：

- 媒体业务真相
- HLS/DASH 清单语义
- 视频该选哪条正式主链
- 资产生命周期和 `24 小时` 规则

一句话：`WebRTC` 是 transport，不是媒体产品协议。

### 2.4 Apple 对 `HLS` 的主张仍然是“标准流媒体 + 普通 HTTP/CDN”

Apple 的 `HTTP Live Streaming` 主页当前直接写明：

- HLS 可以把 live 和 on-demand 音视频发送到 Apple 设备和 PC。
- 它使用普通 web 协议，因此可以部署在普通 web servers 和 CDNs 上。
- 它被设计成可靠的，并会按当前网络条件动态调整播放。
- 官方文档入口里同时给出：
  - `HLS Authoring Specification for Apple Devices`
  - `Enabling Low-Latency HLS`
  - `Using CMAF with HTTP Live Streaming`
  - `RFC 8216`

这说明两件事：

1. `HLS` 的官方心智始终是**标准自适应流媒体主链**，不是“拿一个整块大 MP4 凑合播”。
2. `CMAF` 已经是 Apple 官方正面承认和推动的路线，不是边缘话题。

### 2.5 `hls.js` 官方定位也很克制

`hls.js` 官方 README 当前写得非常清楚：

- 它是 HLS client。
- 它依赖 HTML5 `<video>` 和 MSE。
- 它会把 TS/AAC/MP3 等流转成 `ISO BMFF (MP4) fragments`。
- 它也支持 `HLS + fMP4`。
- 它直接工作在标准 `<video>` 元素上。
- Safari 浏览器已经有原生 HLS，官方建议做能力检测，在原生和 `hls.js` 之间选择。
- 如果要跨更多平台，流必须严格遵守 `RFC8216`。
- 所有 HLS 资源都必须给到允许 `GET` 的 CORS。

这几句的工程含义很直接：

1. `hls.js` 是标准流媒体播放引擎，不是播放器壳。
2. 它吃的是 manifest + segments，不是 whole-file swarm。
3. 它天然适合接 `p2p-media-loader`，因为后者就是官方围着它和 `Shaka` 写的。
4. 对 `koko` 当前阶段，`hls.js` 该继续承担标准流媒体冷启动与秒开支路，不该被 `Video.js` 或 `WebTorrent` 篡位。

### 2.6 `DASH / CMAF / MSE` 官方方向是什么

`DASH-IF IOP v5` 首页把方向写得很硬：

- v5 是围绕 MPEG DASH 定义的
- 并且“further constrained to deliver media formatted according to the MPEG CMAF Specification”
- Part 2 的摘要就是 “Core principles and CMAF mapping”
- Part 7 的摘要写明：视频部分定义 `CMAF Media Profiles`

W3C 的 `ISO BMFF Byte Stream Format` 则把浏览器真正吃的格式写得非常清楚：

- initialization segment：`ftyp + moov`
- media segment：`styp? + moof + mdat`

这几份官方资料一起给出的结论非常稳定：

1. 浏览器标准流媒体主链，真正推荐的不是“整块大文件当唯一高级主路”，而是**初始化段 + 媒体分段**。
2. `CMAF / fMP4` 不是可有可无的“高级选项”，而是 `HLS / DASH` 在现代浏览器世界里越来越收口的共同底座。
3. 所以当前阶段秒开、标准播放器兼容、码率自适应这条线，最正的路仍然是 `HLS/DASH/CMAF`。

### 2.7 `p2p-media-loader` 官方到底是什么

`p2p-media-loader` 最新文档首页直接写：

- 它是一个 JavaScript library，利用 HTML5 video 和 WebRTC 让媒体通过 P2P 网络传递。
- 它提供现成的：
  - `p2p-media-loader-hlsjs`
  - `p2p-media-loader-shaka`
- 官方示例不是自己造播放器，而是：
  - `HlsJsP2PEngine.injectMixin(Hls)`
  - `ShakaP2PEngine.registerPlugins(shaka)`
  - 然后继续 `attachMedia(video)` / `loadSource(streamUrl)` / `player.load(streamUrl)`

文档还明确提醒：

- npm 集成时要给 `bittorrent-tracker` 依赖准备 Node polyfills。

这说明它的官方定位极其明确：

1. 它是 **segment-level engine**。
2. 它是 **existing streaming engine enhancer**。
3. 它不是 UI。
4. 它不是第二播放器壳。
5. 它不是 whole-file swarm plane。

也就是说，你想让它“尽量满血”，也只能是在 `HLS/DASH` 支路里尽量打满，不可能把它拧成 `WebTorrent` 的替代品。

### 2.8 `Video.js v10` 官方当前到底建议什么

`Video.js v10` 官方 blog、overview、roadmap 现在给出的信息是一致的：

1. 它仍然是 **v10 beta**。
2. roadmap 明确写：
   - `March 2026: v10 Beta Release`
   - `Close to stable, but API changes are still possible`
   - `Intended for experimental adoption in real-world projects`
   - `Mid-2026: v10 GA Release`
3. overview 明确把播放器结构拆成：
   - state
   - UI
   - media
4. `media-container` 文档明确写：
   - 它负责 layout、fullscreen、media attachment、interaction surface
   - fullscreen 是 container 进全屏，不是 video element
   - media discovery 是 provider 负责，不是 container
5. 官方 blog 明确写：
   - v10 今天就能和 `HLS.js / Shaka / dash.js` 这类 streaming engines 一起工作
   - SPF 当前**不是**立刻替代 `HLS.js` 这类 full-featured engine 的东西

这对 `koko` 当前阶段的意义非常直接：

1. `Video.js v10` 当前适合作为**唯一播放器壳**。
2. 它当前不适合顺手吞掉 `hls.js` 正式主链。
3. 更不适合吞掉 `WebTorrent` / `SwarmRuntime` / `MediaSessionOwner`。
4. `Video.js v10` 的 HTML custom elements 路线是正路，不需要为了它引 React。

## 3. 给 `koko` 当前阶段的直接工程裁决

下面这些是**基于官方资料做的工程裁决，不是原文逐句复述**。

### 3.1 你真正要的终局，当前 Web 阶段该怎么落

如果你的硬目标是：

- `24 小时` 后服务器已经没有原视频和母本
- 群友依然能高速点开
- 依然能高速边下边播
- 依然能高速互帮互助

那当前 Web 阶段必须把两条链拆开看：

1. **长期存活链**
   - owner：`WebTorrent`
   - 语义：whole-file、补齐、保留、做种、服务器删源后继续活
2. **标准流媒体秒开链**
   - owner：`HLS/DASH/CMAF + hls.js`
   - 语义：浏览器标准播放、冷启动秒开、ABR、标准播放器兼容

如果把这两条链搅成一条，你后面一定会在“谁负责长期活”“谁负责首播稳定”“谁负责分段 P2P”“谁是正式真相”上继续打架。

### 3.2 `p2p-media-loader` 应该尽量满血，但边界必须守住

“尽量满血”对 `p2p-media-loader` 的正确理解是：

1. 在 `HLS` 支路里尽量打满 segment-level P2P。
2. 播放开始后，不只吃 HTTP segment，也尽量快速建立 peer segment 交换。
3. 让它承担：
   - `HLS` 后续片段带宽分摊
   - `HLS` 支路的 peer 扩散
   - `HLS` 冷启动后的持续减压

但它**不能**承担：

1. 服务器删掉 manifest/segments 后的长期资产存活。
2. whole-file backfill。
3. `24 小时` 后仍无 origin 情况下的正式长期播放平面。

这不是它不强，而是官方定位就不是这个方向。

### 3.3 真正的“满血 P2P”核心不是多接一个库，而是 complete peers

官方资料拼起来以后，最容易被误判的一点是：

很多人会把“P2P 满血”理解成：

- 开启 WebRTC
- 接上 WebTorrent
- 接上 p2p-media-loader

然后就以为系统自然会活。

这不对。

真正决定 `24 小时` 后还能不能高速播的，是：

1. 有没有足够多的 **完整持有者**
2. 这些持有者是否在线
3. 浏览器会不会在播放后尽快把整资产补齐
4. store / retain / seed 路径有没有真的持续活着

所以当前阶段“满血 P2P”最关键的产品动作其实不是 UI，而是：

- 一旦开始看，就尽快 backfill 完整资产
- 一旦完整，就继续做种
- 别把 peer 永远停留在只缓存前几分钟

### 3.4 秒开策略最合理的不是单押一条路

当前阶段最现实的秒开策略应当是：

1. 打开播放器时立即加入 `WebTorrent` swarm。
2. 立刻尝试 `service worker + streamURL/streamTo` 的 whole-file 流式播放。
3. 同时或近同时预热 `HLS/CMAF`。
4. 如果 swarm 在很短预算内不够热，就让 `HLS/hls.js` 顶上首播。
5. 但 whole-file backfill、peer 扩散、seeding 不停止。
6. 一旦本地完整度和 swarm 热度起来，后续优先让 whole-file plane 承担长期活路。

这条路线的重点不是“先服务器”，而是：

- 冷启动要诚实
- 长期存活要坚定
- 两条链互相打配合，不互相篡位

### 3.5 `24 小时` 后如果服务器删掉了原视频和母本，也删掉了 HLS/DASH 产物，会怎样

这里必须说得非常硬：

如果服务器在 `24 小时` 后删掉的不只是原视频和母本，**连 `HLS/DASH manifest + segments` 也一起删了**，那：

1. `HLS/DASH/CMAF` 支路本身就不再有权威资产可读。
2. 这条支路不能靠“P2P 精神”自动继续活。
3. 当前 Web 阶段真正能继续扛住播放的，只能是 `WebTorrent` whole-file swarm。

这正是为什么：

- 长期正式协作分发主平面必须是 `WebTorrent`
- `p2p-media-loader` 只能是增强层
- whole-file complete backfill 必须优先级很高

### 3.6 `Video.js v10` 在这条主链里的正确位置

当前阶段的正确位置只有一个：

- **唯一播放器壳**

它不该决定：

- 先走 swarm 还是 HLS
- 什么时候算 ready
- 什么时候继续做种
- `24 小时` 后资产能不能活

它只应该消费已经裁决好的 source descriptor，并且把 layout/fullscreen/controls 统一收口。

## 4. 当前阶段哪些事不能自我感动

下面这些都不该再浪漫化：

1. **“有了 `HLS + p2p-media-loader`，就算服务器删了 master 和 segments 也还能长期活。”**
   - 不对。官方根本不是这个心智。
2. **“只要接了 `WebTorrent`，就自然能永久保种。”**
   - 不对。浏览器保留和在线时长都有硬限制。
3. **“WebRTC 很强，所以它应该上升成产品主真相。”**
   - 不对。它只是 transport。
4. **“`p2p-media-loader` 和 `WebTorrent` 都是 P2P，可以揉成一个统一私有核心。”**
   - 不对。它们分属不同层级。
5. **“`Video.js v10` 很新，可以顺手接管 `hls.js` 和分发逻辑。”**
   - 不对。官方自己都还在 beta，并明确兼容既有 streaming engines。
6. **“只要前几分钟能播，就说明 `24 小时` 后的长期方案成立了。”**
   - 不对。长期成立要看完整资产补齐与持续做种。

## 5. 对 `koko` 当前阶段最直接的落地判断

当前阶段最稳的路线，应当压成下面六句：

1. 上传完成后，后端继续产出 `poster + 可播 MP4 母本 + HLS/DASH/CMAF + torrent/metainfo + Web Seed`。
2. `24 小时` 内，服务器继续提供 `Web Seed` 和标准流媒体兜底。
3. 正式播放器壳继续收口到 `Video.js v10`，但 source owner 不在壳里。
4. 冷启动先 aggressively 抢 swarm；swarm 不够热，就让 `HLS/hls.js` 秒开顶上。
5. `p2p-media-loader` 在 `HLS` 支路里尽量打满，但不提升成长期资产 owner。
6. `24 小时` 后如果服务器删掉原视频和母本，系统仍要靠 `WebTorrent` 的 complete peers 继续高速分发和播放。

一句话：

**当前 Web 阶段真正优雅的路线，不是让一个轮子统治全场，而是让 `HLS/DASH/CMAF` 负责标准流媒体秒开，让 `p2p-media-loader` 负责 `HLS` 支路的分段 P2P，让 `WebTorrent` 满血承担服务器删源后的长期协作分发，让 `Video.js v10` 只做唯一播放器壳，让 `WebRTC` 老老实实待在 transport 层。**
