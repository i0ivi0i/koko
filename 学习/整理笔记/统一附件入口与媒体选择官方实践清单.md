# 2026-04-11 统一附件入口与媒体选择官方实践清单

适用范围：`koko` 群聊底部发送区即将进行的“统一附件入口 / 操作台附件能力注册”实现。  
目标：在真正改代码前，先把统一附件按钮、统一媒体选择器、壳层边界、浏览器 picker、Uppy 事件边界这些关键点，用官方资料和成熟实践钉死，避免一边实现一边漂。

补充说明：

- 操作台壳层和 Lit 性能细节，继续参考 [唯一壳级操作台与不手搓轮子依据.md](./唯一壳级操作台与不手搓轮子依据.md)
- `Uppy / Tus / Rustus` 上传主链细节，继续参考 [群聊媒体上传-Uppy-Tus-Rustus官方实践清单.md](./群聊媒体上传-Uppy-Tus-Rustus官方实践清单.md)

## 1. 先给结论

这次“统一附件入口”真正该学的不是某个 App 的图标皮肤，而是下面这几条成熟做法：

1. **用户入口应该统一成“选媒体/附件”，而不是输入区并列两个主按钮。**
   Apple `PhotosPicker / PHPickerViewController` 和 Android Photo Picker 都把“图片 + 视频”放进同一个系统选择器里。

2. **Web 端一个 `input[type=file]` 就足够承接图片和视频。**
   平台原生已经支持：
   - `accept` 传多种类型
   - `multiple` 一次选多项
   - `files` 作为统一返回面

3. **`accept` 只是选择提示，不是校验真相。**
   统一 chooser 之后，前端仍然必须复用当前图片 MIME 推导、HEIC/HEIF 转码、视频元数据探测和服务端校验，不能因为入口统一了就把类型判断偷懒掉。

4. **统一入口应该属于壳层，媒体事实处理继续留在媒体模块。**
   `shell` 负责一个按钮、一个隐藏输入、一个点击编排；`frontend/媒体` 继续负责“这到底是图片还是视频”“怎么进上传主链”。

5. **不要手搓第二套上传系统。**
   统一入口不等于重写上传主链。`Uppy` 官方已经给了 `restrictions`、`addFile(meta)`、`file-added`、`upload-stalled`、`retryUpload()` 这些边界，继续复用。

一句话：

**这次正确方向是“一个统一入口 + 一个统一 chooser + 一条统一上传主链 + 必要处轻分叉”，不是“把两个旧按钮换个地方摆”。**

## 2. `koko` 当前代码现实

当前代码已经说明问题主要在壳层表面，不在上传核心：

1. [聊天壳.ts](../../frontend/聊天壳.ts) 现在直接维护：
   - 两个隐藏文件输入
   - 两个按钮
   - `openImagePicker / openVideoPicker`
   - `handleImageFileInputChange / handleVideoFileInputChange`

2. [媒体发布.ts](../../frontend/媒体/媒体发布.ts) 已经有统一上传主链：
   - `prepare -> Uppy/Tus -> complete`
   - `file-added / upload-success / upload-error / upload-stalled / retryUpload`
   - 图片 / 视频的必要差异集中在预处理与元数据读取

3. 当前 public surface 比内部主链更分裂：
   - `准备选择图片 / 准备选择视频`
   - `处理选择图片文件 / 处理选择视频文件`

所以这次真正要修的，不是“媒体上传器为什么有差异”，而是：

**底部操作台为什么还把内部差异提前暴露成两个入口。**

## 3. 官方资料告诉我们的事

### 3.1 Apple：系统 picker 的主心智是“统一选视觉媒体”

Apple 官方文档和 WWDC 资料里，`PhotosPicker` 的定义就是：

- 用来浏览和选择照片库里的 **images and videos**
- `PHPickerViewController` 是推荐的隐私增强路径
- 如果只是给用户选图/选视频，不该优先去申请整库访问

官方给出的直接启发：

1. 如果 app 只是让用户挑图片或视频，**最简单、体验最好的方式是用系统 picker**，而不是自己在第一层 UI 逼用户先选“图片按钮”还是“视频按钮”。
2. 请求原始媒体格式时，应使用更通用的内容类型，比如 `.image` 和 `.movie`，而不是一开始就把入口切碎到特定格式。

对 `koko` 的直接含义：

1. 发送区应该先让用户表达“我要选媒体”。
2. 图片/视频的差异应该在选择后和预处理阶段体现，而不是输入区两个主按钮并列体现。

来源：

- Apple `PhotosPicker` 文档：<https://developer.apple.com/documentation/PhotosUI/PhotosPicker>
- Apple `Delivering an Enhanced Privacy Experience in Your Photos App`：<https://developer.apple.com/documentation/PhotoKit/delivering-an-enhanced-privacy-experience-in-your-photos-app>
- Apple WWDC23 `Embed the Photos Picker in your app`：<https://developer.apple.com/videos/play/wwdc2023/10107/>

### 3.2 Android：官方 Photo Picker 直接支持 `ImageAndVideo` 和多选

Android 官方 Photo Picker 文档写得更直接：

1. 单选时可以直接 `PickVisualMedia.ImageAndVideo`
2. 多选时可以 `PickMultipleVisualMedia(n)`，同样可以选择 image + video
3. Photo Picker 是官方推荐的、内建的、面向用户的视觉媒体选择方式
4. Android 官方隐私文档也明确把 Photo Picker 当成“不需要整库访问权限”的更安全入口

这说明成熟平台本身就支持：

- 一个统一入口
- 一个统一视觉媒体 chooser
- 由系统选择器承接“图片/视频都是 visual media”的用户心智

对 `koko` 的直接含义：

1. 统一附件按钮后直接进入统一媒体选择器，是符合成熟平台设计的。
2. 当前 phase 只保留一个 `media` 能力并直达，不算偷懒，反而是更接近系统级最佳实践。
3. `multiple` 不是额外 hack，而是平台原生能力。

来源：

- Android Photo Picker：<https://developer.android.com/training/data-storage/shared/photo-picker>
- Android Privacy：<https://developer.android.com/privacy>
- Android Shared Media Storage：<https://developer.android.com/training/data-storage/shared/media>

### 3.3 Web 平台：一个 file input 就能覆盖图片 + 视频 + 多选

MDN / WHATWG 给出的结论很关键：

1. `accept` 是一个逗号分隔列表，可以同时写：
   - MIME 类型
   - 扩展名
   - `image/*`
   - `video/*`
2. `multiple` 打开后，一个 file input 就可以一次选多个文件
3. 文件选择结果统一从 `HTMLInputElement.files` 读取
4. `accept` 只是提示，不会替你完成验证；用户仍可能选到不合规文件

这对我们这次实现非常重要：

1. 不需要两个 `input[type=file]`
2. 不需要“图片按钮专属 input + 视频按钮专属 input”
3. 正确做法是一个统一 input，把当前图片 accept 列表和视频 accept 列表并起来
4. 图片侧 `.heic/.heif` 这些扩展补充必须保留，因为 MDN 也明确支持扩展名 specifier

对 `koko` 的直接含义：

1. [图片预处理.ts](../../frontend/媒体/图片预处理.ts) 里的 `可选择图片文件类型` 继续保留是对的
2. [视频元数据.ts](../../frontend/媒体/视频元数据.ts) 里的 `可选择视频文件类型` 继续保留是对的
3. 统一 chooser 的 `accept` 应该是二者并集，而不是偷懒只写一个 `image/*,video/*`

来源：

- MDN `<input type="file">`：<https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file>
- MDN `accept`：<https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/accept>
- MDN `multiple`：<https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/multiple>
- WHATWG HTML `input/file`：<https://html.spec.whatwg.org/multipage/input.html>

### 3.4 `showPicker()` 可以用，但不要把它误当成新的真依赖

MDN 对 `HTMLInputElement.showPicker()` 的说明也值得记住：

1. 它确实可以从按钮点击里触发 file picker
2. 但它要求 **transient user activation**
3. 需要做 feature detection
4. 某些环境下仍然可能抛 `NotAllowedError` 或 `SecurityError`

这对 `koko` 的直接含义：

1. 当前继续使用“按钮点击 -> 统一 file input `.click()`”是稳定方案
2. 如果未来想升级成 `showPicker()`，必须：
   - 先 feature detect
   - 保留 fallback
   - 继续把这个能力关在附件入口编排里

也就是说：

**`showPicker()` 可以作为未来增强，不该成为这次重构的前提。**

来源：

- MDN `HTMLInputElement.showPicker()`：<https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/showPicker>
- MDN User Activation：<https://developer.mozilla.org/en-US/docs/Web/Security/User_activation>

### 3.5 Uppy 官方：统一入口后，关键边界是 `restrictions + addFile(meta) + event`

Uppy 官方文档和当前项目的关系非常直接：

1. `restrictions.allowedFileTypes` 对应浏览器 file input 的 `accept` 语义
2. `addFile()` 是把文件放进 Uppy 状态机的统一入口
3. `meta` 可以挂你真正需要的每文件信息
4. `file-added`、`upload-stalled`、`retryUpload()` 都是官方支持的边界，不需要自己再包一层私有上传框架
5. `allowedMetaFields` 可以显式限制哪些字段真正发给 Tus 端点

对 `koko` 的直接含义：

1. 当前 [媒体发布.ts](../../frontend/媒体/媒体发布.ts) 用一个 Uppy 实例同时承接图片和视频，是对的
2. 统一附件入口以后，应该继续复用这条 Uppy 主链，而不是拆成第二个“视频专用 Uppy”
3. `relativePath = attachment_id` 这种本地 fingerprint 设计要保留，不能因为入口统一就回退
4. chooser 的 `accept` 和 Uppy 的 `restrictions.allowedFileTypes` 应保持同源，别长出两份名单

来源：

- Uppy Core：<https://uppy.io/docs/uppy/>
- Uppy Tus：<https://uppy.io/docs/tus/>

### 3.6 Lit 和前端性能：附件入口是壳层热路径，必须克制

Lit 官方和 web.dev 已经把底部高频交互区的性能纪律讲得很清楚：

1. `render()` 必须纯，不做副作用
2. 样式优先 `static styles`
3. 高热区交互要尽量薄，避免同步重布局和重计算
4. INP 是高频交互的直接指标，不要在按钮点击和输入时顺手做太多事

对这次附件入口实现的直接含义：

1. `frontend/操作台/附件入口` 应该只是：
   - 一个按钮
   - 一个隐藏 input
   - 一个极薄编排器
2. 不要在这个层里塞媒体类型判断、草稿状态推进、上传状态机
3. `聊天壳.ts` 应该退回装配点，不要继续长出四个入口处理器

来源：

- Lit Rendering：<https://lit.dev/docs/v2/components/rendering/>
- Lit Styles：<https://lit.dev/docs/components/styles/>
- web.dev Optimize INP：<https://web.dev/articles/optimize-inp>
- 另见本仓已有笔记：[唯一壳级操作台与不手搓轮子依据.md](./唯一壳级操作台与不手搓轮子依据.md)

## 4. 对 `koko` 这次实现最直接的落地约束

结合官方资料和当前仓库现实，这次实现前应先钉死这些约束：

### 4.1 UI 与壳层边界

1. 底部发送区只保留一个统一附件按钮
2. 当前只有 `media` 一个能力时，按钮点击直接进统一媒体选择器
3. 当前 phase 不弹菜单，不制造第二层交互
4. 统一按钮和统一 file input 归 `frontend/操作台/附件入口`
5. `聊天壳.ts` 不再直接拥有：
   - 双按钮
   - 双输入
   - 四个入口处理器

### 4.2 统一 chooser 边界

1. 一个统一隐藏 `input[type=file]`
2. `multiple = true`
3. `accept = 可选择图片文件类型 + 可选择视频文件类型`
4. 选择结果统一从 `files` 读取
5. 清空 `input.value`，保证重复选择同一文件仍能触发 `change`

### 4.3 媒体模块边界

1. `frontend/媒体` 只处理“选中文件之后”的事实
2. 必须按文件级识别 `kind`
3. 图片侧继续复用：
   - `推导图片Mime类型`
   - HEIC/HEIF 转码
   - MIME 补全
4. 视频侧继续复用：
   - 浏览器元数据探测
5. 不支持文件不能误进 `prepare -> uploading`

### 4.4 不该做的事

1. 不要再保留双按钮双输入作为第二条活路径
2. 不要把 `accept` 当成校验真相
3. 不要把“附件入口”上提到 `contract`
4. 不要手搓第二套上传器
5. 不要为了 `txt/pdf` 这类不支持文件扩张 `媒体附件草稿.kind`
6. 不要为了“更现代”强上 `showPicker()` 而破坏兼容路径

## 5. 现在最稳的实现判断

如果只看这次实现，最稳的路线已经足够清楚：

1. **统一入口**
   一个按钮，不再并列图片/视频主按钮。

2. **统一 chooser**
   一个 file input，同时接受图片和视频，支持多选。

3. **统一上传主链**
   继续复用一个 Uppy/Tus 主链，不重写上传核心。

4. **必要处轻分叉**
   图片/视频的差异只留在预处理、元数据和 ready 展示上。

5. **壳层表达意图，媒体模块处理事实**
   这才符合当前 spec 里定下来的 DDD 和 Unix 边界。
