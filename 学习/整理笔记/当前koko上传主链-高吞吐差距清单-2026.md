# 当前 koko 上传主链高吞吐差距清单（2026）

## 这份笔记的目的

前两份笔记回答的是“官方轮子怎么说”。  
这一份只回答：

**这些官方结论对照 `koko` 当前源码后，还差什么。**

## 先给结论

当前 `koko` 上传链路已经做到的是：

- **门禁统一**
- **误杀删除**
- **最小并发治理**

但还没做到的是：

- **单大文件高吞吐上传**
- **多文件并发的激进吞吐调度**
- **把 transport 时间和 complete 时间彻底分离**
- **对 Rustus / complete 热点做可量化的吞吐观测**

所以你现在实测“还是慢”，从源码看是成立的，不是瞎猜。

## 当前已经做到的

1. 视频大小上限已经从 `50MB` 提到 `200MB`。  
   见 [视频元数据.ts](</E:/koko/frontend/媒体/视频元数据.ts:5>)、[媒体上传外壳.rs](</E:/koko/src/媒体上传外壳.rs:808>)
2. 前端本地 `15s watchdog` 已删。  
   见 [媒体发布.ts](</E:/koko/frontend/媒体/媒体发布.ts:267>)
3. `Rustus` 的 body/file 限额已同步到 `200MB`。  
   见 [run.ps1](</E:/koko/run.ps1:338>)
4. 后端 `complete` 已加全局并发闸门，避免重活无限并发冲垮进程。  
   见 [外壳.rs](</E:/koko/src/外壳.rs:94>)、[媒体上传外壳.rs](</E:/koko/src/媒体上传外壳.rs:327>)

## 当前还没做到的关键点

### 1. 单大文件高吞吐上传还没做

当前前端只配置了：

- `limit = 3`
- `retryDelays = [0, 1000, 3000, 5000]`

见 [媒体发布.ts](</E:/koko/frontend/媒体/媒体发布.ts:80>)、[媒体发布.ts](</E:/koko/frontend/媒体/媒体发布.ts:207>)。

这说明：

- 现在能控的是“同时几个文件在传”
- 还没启用 `parallelUploads`
- 也没启用 `uploadDataDuringCreation`
- 也没显式打开 `addRequestId`

所以单个大视频上传时，本质上仍然主要是**单流传输**。

### 2. 多文件并发也还是保守策略

当前 `limit = 3` 是偏保守的资源保护值，不是高吞吐值。  
它更像：

**避免前端、Rustus、后端 complete 一起炸。**

而不是：

**尽量吃满你 40Gbps 大带宽。**

### 3. UI 仍然把“字节传输”和“后端处理”混在一起

前端现在 `upload-success` 之后，仍然直接等 `completeMediaUpload()` 跑完，最后才把草稿从 `uploading` 改成 `ready`。  
见 [媒体发布.ts](</E:/koko/frontend/媒体/媒体发布.ts:300>)、[媒体发布.ts](</E:/koko/frontend/媒体/媒体发布.ts:316>)、[媒体发布.ts](</E:/koko/frontend/媒体/媒体发布.ts:326>)。

这意味着：

- 你眼里看到的“上传慢”
- 其实包含了后端 `complete / 解析 / 打包 / 写库`

所以当前 UI 体感速度**不是纯 transport 吞吐速度**。

### 4. complete 热点仍然不是高吞吐流式管线

后端 `complete` 仍有这些明显热点：

- 整文件 `fs::read` 到内存  
  见 [媒体上传外壳.rs](</E:/koko/src/媒体上传外壳.rs:360>)
- 视频打包走 `spawn_blocking` 外部进程  
  见 [媒体上传外壳.rs](</E:/koko/src/媒体上传外壳.rs:509>)
- 打包产物上传逐文件 `fs::read` 后再 `put`  
  见 [流媒体打包.rs](</E:/koko/src/流媒体打包.rs:304>)、[流媒体打包.rs](</E:/koko/src/流媒体打包.rs:311>)、[流媒体打包.rs](</E:/koko/src/流媒体打包.rs:332>)

这条链路现在更偏“稳妥完成”，不是“流式高吞吐后处理”。

### 5. Rustus 仍未按公网高吞吐部署角度接全参数

当前脚本只显式接了：

- `RUSTUS_MAX_BODY_SIZE`
- `RUSTUS_MAX_FILE_SIZE`

但还没显式接：

- `RUSTUS_SERVER_WORKERS`
- `RUSTUS_TUS_EXTENSIONS`
- `RUSTUS_BEHIND_PROXY`
- metrics 采集

见 [run.ps1](</E:/koko/run.ps1:338>)。

## 按优先级排的差距清单

### P0：必须先补

1. 前端状态拆成 `transporting / processing / ready / failed`
2. 打开请求级关联标识，让浏览器、Rustus、后端日志能串起来
3. 把“单文件大视频”和“多文件并发”分开做吞吐实验

### P1：最值得做的当前栈优化

1. 受控实验 `parallelUploads`
2. 只在大文件场景实验，而不是全量默认打开
3. 把 Rustus workers / Linux 公网部署参数接成显式配置

### P2：再往后才考虑

1. 把 complete 热点进一步流式化
2. 把 transport done 和 ready done 彻底拆成两个用户可见阶段
3. 评估是否仍值得继续守着当前 sidecar 方案

## 现在最不该做的事

1. 没做对照实验前就默认开全局 `parallelUploads`
2. 为了“像分片上传”就主动把 `chunkSize` 调小
3. 还没拆清楚 transport 和 complete 时间，就宣布“上传层已经优化好了”

## 我当前的判断

基于官方资料和当前源码，我的判断是：

**现在的 `koko` 上传链路还没有把高吞吐上传这件事做完。**

它现在处在的阶段是：

- 比之前更能传
- 更不容易误杀
- 更不容易被重活并发拖垮

但离“单大文件快、多个文件一起传也快”还差一轮**吞吐专项优化**。
