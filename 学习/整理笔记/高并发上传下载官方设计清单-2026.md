# 2026-04-15 高并发上传下载官方设计清单 2026

适用范围：Linux 公网部署下的媒体高并发上传 / 下载，不限于 `koko`，但重点落到 `koko` 当前源码的差距上。  
目标：不用手搓“多线程上传下载轮子”，直接站在对象存储和成熟上传协议的官方建议上。

## 1. 先说结论

这一轮最有价值的结论有十条：

1. 高并发媒体链路的核心原则是：**业务服务做控制面，字节流尽量做数据面直通**。
2. 官方对象存储建议非常一致：大文件上传要走 multipart / resumable；失败重传要尽量只重传局部。
3. 上传吞吐不是靠单连接硬怼，而是靠并发连接、并行 part、重试和更短恢复路径。
4. 下载吞吐不是靠应用服务整块读进内存再回给客户端，而是靠对象存储 range、并发范围请求、CDN、presigned URL 或直接回源。
5. `S3` 官方明确建议：`100MB+` 用 multipart；并行上传 parts 能提升吞吐。
6. `S3` 官方还明确建议：下载大对象时用 byte-range fetch，而且最好按 multipart 边界对齐。
7. `GCS` 官方明确提醒：chunk / buffer 越大，速度可能越快，但内存占用也越高；高并发时这是硬成本，不是抽象概念。
8. resumable session / presigned URL 都带授权含义，过期和凭证轮换是正经设计项，不是“出错再看”。
9. 对正式公网产品来说，全球上载如果距离远，`Transfer Acceleration` 这类成熟加速能力比手搓代理更像正路。
10. 回头看 `koko` 当前源码：上传下载链路已经可用，但应用服务仍有明显“自己吃整块字节 / 整块内存”的热点，还没完全达到生产级高并发字节面设计。

## 2. 上传侧官方最佳实践

### 2.1 Amazon S3

AWS 官方 2026 文档里最重要的点：

- Multipart upload 适合把单个对象拆成多个 parts 上传。
- 每个 part 可以独立、无序上传。
- 某个 part 失败时，只需要重传该 part。
- 官方明确说：对象 `100 MB` 及以上，最佳实践是用 multipart。
- multipart 的直接收益就是：
  - 吞吐更高
  - 网络失败后恢复更快

还有两个容易忽略但特别关键的生产点：

- 未完成 multipart upload 的 parts 会持续占用成本，官方建议配 lifecycle 自动清理不完整 multipart。
- 对大对象下载，官方建议用 `Range` 请求，而且可以并发取同一对象的不同字节范围；如果对象是 multipart 上传的，最好让下载 range 尽量对齐 part 边界。

这对 `koko` 的直接约束：

1. 如果未来大视频继续增长，上传专线应该越来越靠近 multipart / resumable，而不是让应用服务一次性吞整文件。
2. 下载专线最终应该越来越靠近对象存储 range / CDN / 直链，而不是应用进程 `bytes().await` 后再转发。

### 2.2 Google Cloud Storage

GCS 官方 2026 文档里几个特别有用的现实点：

- resumable upload session 是正式一等能力。
- session URI 本身带授权意义，必须小心暴露。
- resumable session 会绑定在创建它的 region。
- 如果可能，避免过度切小块；切块会增加额外延迟和操作成本。
- 但浏览器和受限客户端常常必须分块。
- chunk / buffer 越大通常越快，但内存开销也同步变大。

这对 `koko` 的直接约束：

1. 未来如果你们是全球公网用户，不要忽略“谁来创建 resumable session，以及它在哪个 region 创建”。
2. 浏览器大文件上传不是只看速度，还要看每个并发上传占多少内存。

## 3. 下载侧官方最佳实践

### 3.1 S3 Download / Range / Presigned URL

AWS 官方对下载侧的口径其实很清楚：

- 用 `Range` 做部分读取。
- 可以对同一对象做多个并发范围读取，提高聚合吞吐。
- 对象存储访问最好和计算节点同区域，减少时延和费用。
- presigned URL 允许有限时直接下载 / 上传，不必让应用服务中转对象字节。
- 但 presigned URL 的有效期不会超过底层凭证本身的有效期。

这对 `koko` 的直接约束：

1. 正式公网高并发下载，应用服务不该长期卡在“自己回源对象存储 -> 整块读内存 -> 再发给客户端”这条链上。
2. 下载热点更合理的终局是：
   - CDN / 对象存储直链
   - 或带权限门禁的 presigned URL / 302 跳转
   - 或至少应用层流式透传，而不是整块缓冲

### 3.2 Peer-assisted delivery

从 WebTorrent 官方 use case 看，热门内容浏览器互传、冷门内容 HTTP origin 兜底，本身就是成熟思路。

这对 `koko` 的直接约束：

1. 你们现有 `WebTorrent + web seed` 方向本身就符合成熟思路。
2. 但它应该是“减源站压”和“热点协作分发”，不是唯一下载主链。

## 4. 真正的“多线程高并发上传下载”该怎么理解

通俗说，真正靠谱的高并发字节链路不是：

1. 应用服务自己开很多线程。
2. 把整个文件一次次读进内存。
3. 再手工切块、手工重试、手工回源、手工补传。

而是：

1. 复用成熟协议或 SDK 的并发 part / resumable 能力。
2. 让大文件失败恢复尽量局部化。
3. 让控制面和数据面分开。
4. 让下载侧尽量靠近对象存储 / CDN / P2P。
5. 让应用服务只做授权、裁决、编排、状态升级。

## 5. 回到 `koko` 当前源码，差距在哪里

基于我前面用 Serena 查到的源码现实，`koko` 当前已经做对的地方：

1. 上传主入口已经拆成 `prepare -> Tus/Rustus -> hook -> complete`，业务服务没有直接接收整个浏览器大文件。
2. 下载侧已经有 `Range` 支持。
3. 浏览器侧已经有 `WebTorrent + web seed` 协作分发能力。

但离“源码本身已完成生产级高并发字节面设计”还差这些：

1. `complete_media_upload` 里仍有整文件 `fs::read` 进内存的路径。
2. 视频打包和对象存储写入仍有整块读写热点。
3. 下载 handler 仍存在从对象存储整块 `bytes().await` 再回给客户端的路径。
4. 我没查到明确的上传/下载并发闸门、统一背压、下载流量卸载、对象存储直链主路径。

一句话翻译：

**现在的 `koko` 是“控制面方向对了，字节面还没完全瘦下来”。**

## 6. 对 `koko` 最有价值的下一步裁决

### 6.1 上传侧

1. 短期继续站在 `Uppy + Tus + Rustus` 上。
2. 视频上限提到 `200MB` 可以做，但同步要清理前后端和入口层全部上限。
3. 中期要把“业务后端仍整文件读内存”的热点继续往下消。
4. 如果以后视频越来越大，再评估是否切到更对象存储原生的 multipart 上传主链。

### 6.2 下载侧

1. 短期保持当前 HTTP / Range / WebTorrent 共存。
2. 中期优先把下载主链往“流式透传或对象存储直链”推进。
3. 热点内容继续鼓励 peer-assisted delivery，冷门内容继续由源站兜底。

### 6.3 基础设施

1. 同区域部署对象存储和计算节点。
2. 明确超时、重试、生命周期清理、不完整上传清理。
3. 如果未来全球上传很多，再评估对象存储加速能力，不要先手搓全球代理。
