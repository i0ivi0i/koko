# 客户端派生预览与零长期轻封面-官方实践清单-2026-04-21

日期：2026-04-21  
主题：`koko` 视频时间线预览、同文件 preview hint、客户端派生 preview cache、`Video.js v10`、`Mediabunny`、`WebTorrent`

---

## 1. 这次开工前必须先记住的结论

### 1.1 最重要的一句话

**官方主流路线不是“让后端长期存第二张 preview 图”，也不是“等 autoplay 自己跑出首帧”，而是：**

1. 单一 canonical 视频文件继续做媒体真相；
2. 文件本身尽量 preview-friendly；
3. 客户端拿到最少关键字节后，本地派生 preview 并缓存；
4. 播放器壳只负责显示，不拥有 preview 真相。

### 1.2 对 `koko` 最直接的裁决

1. **不要再手搓第二长期 still 资产主链。**
2. **不要让 `Video.js` 或壳层缓存成为 preview owner。**
3. **不要手搓 MP4 解析器或软件解码器主链。**
4. **要优先复用 `Mediabunny`、`WebCodecs`、`MediaCapabilities`、`OPFS`、`WebTorrent` 的现成能力。**
5. **如果没有任何 source bytes，就只能诚实占位。**

## 2. 官方资料给出的核心边界

### 2.1 `Video.js v10` 和浏览器原生 `poster` 的边界

官方结论很清楚：

1. `Video.js` 的 `Poster` 是独立组件，职责就是“播放前显示一张图”。
2. 浏览器原生 `HTMLVideoElement.poster` 也是单独 URL，不会自动从视频文件里帮你抽出封面。
3. 这说明 **“视频文件里可能有 preview hint”** 和 **“UI 最终怎么显示 preview”** 是两层事。

对 `koko` 的直接意义：

1. 就算 canonical 文件里真的带了 embedded preview hint，浏览器 / `Video.js` 也不会自动把它变成 `poster`。
2. 所以我们必须自己在客户端把 preview 读出来，再喂给时间线 / 查看器 / `Video.js` 壳层。

这是基于官方文档的**工程推断**，不是某一个页面直接逐字写死的承诺。

官方来源：

- [Video.js Poster](https://videojs.org/docs/framework/react/reference/poster)
- [MDN `HTMLVideoElement.poster`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/poster)
- [web.dev Video performance](https://web.dev/learn/performance/video-performance)

### 2.2 `Mediabunny` 已经覆盖了我们最容易手搓错的部分

`Mediabunny` 官方已经直接给了这几类能力：

1. 用 `CanvasSink` 从视频轨按时间戳拿 canvas thumbnail。
2. 用 `getMetadataTags()` 读取 `MetadataTags.images`，也支持写 metadata。
3. `MetadataTags.images` 对 MP4/QuickTime 指向 `moov` 层 `udta/meta` 原子。
4. `ReadableStreamSource` 能吃增量 `ReadableStream<Uint8Array>`。
5. `PacketRetrievalOptions.metadataOnly` 能先只取 packet metadata，不急着拉整块数据。

对 `koko` 的直接意义：

1. **预览派生主轮子优先 `Mediabunny`。**
2. **同文件 embedded preview hint 可以优先放在 metadata images。**
3. **要做“先规划关键帧、再按需拿字节”，不要直接整文件暴力拉。**
4. **如果输入是 append-only stream，`ReadableStreamSource` 可用；如果要频繁 random access，就别误用它。**

官方来源：

- [Mediabunny Quick Start](https://mediabunny.dev/examples/thumbnail-generation/)
- [Mediabunny `CanvasSink`](https://mediabunny.dev/api/CanvasSink)
- [Mediabunny `MetadataTags`](https://mediabunny.dev/api/MetadataTags)
- [Mediabunny `ReadableStreamSource`](https://mediabunny.dev/api/ReadableStreamSource)
- [Mediabunny `PacketRetrievalOptions`](https://mediabunny.dev/api/PacketRetrievalOptions)

### 2.3 `WebCodecs` / `MediaCapabilities` 是“薄而快”的正路

MDN 的边界也很明确：

1. `WebCodecs` 用的是浏览器里已经有的 codec，不是再下载一套软件 codec。
2. 它没有容器 demux API，所以不能替代 `Mediabunny` / `MP4Box.js` 这类容器层工具。
3. `MediaCapabilities.decodingInfo()` 可以先看 `supported / smooth / powerEfficient`。
4. `VideoDecoder.isConfigSupported()` 更细，但截至 2026-02-09 仍不是 Baseline。
5. `requestVideoFrameCallback()` 自 2024-10 起才算跨最新浏览器 Baseline，适合作为补充分支。

对 `koko` 的直接意义：

1. **能力探测顺序应该是 `MediaCapabilities` 先，`VideoDecoder.isConfigSupported()` 再。**
2. **`requestVideoFrameCallback()` 只做“已经拿到可解码帧之后的补抓帧”，不是主链唯一依赖。**
3. **不要拿 Rust/WASM 再带一套软件解码器来替代浏览器 codec。**

官方来源：

- [MDN WebCodecs API](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API)
- [MDN `MediaCapabilities.decodingInfo()`](https://developer.mozilla.org/en-US/docs/Web/API/MediaCapabilities/decodingInfo)
- [MDN `VideoDecoder.isConfigSupported()`](https://developer.mozilla.org/en-US/docs/Web/API/VideoDecoder/isConfigSupported_static)
- [MDN `requestVideoFrameCallback()`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)

### 2.4 `WebTorrent` 官方给的是优先级机制，不是 preview 语义

`WebTorrent` 官方文档重点在：

1. `torrent.select(start, end, priority, notify)` 可以做分片范围优先级。
2. `torrent.critical(start, end)` 可以把某些 piece 标为 ASAP。
3. `file.select(priority)` 是文件级优先，不等于“预览 ready”。

对 `koko` 的直接意义：

1. 我们现在 `file.select(1)` 的整附件补齐还太粗。
2. 真正的 preview-first 需要先算出 metadata / embedded hint / early keyframe 对应的 pieces，再 `critical/select`。
3. `WebTorrent` 不替我们决定什么叫 poster，只负责把该来的字节尽快送来。

官方来源：

- [WebTorrent API Docs](https://webtorrent.io/docs)

### 2.5 `MP4Box.js` 和 `FFmpeg faststart` 说明 preview-friendly packaging 不是幻觉

官方资料说明：

1. `MP4Box.js` 支持 progressive parsing，`moov` 一解析出来就能拿结构信息。
2. FFmpeg 官方 `movflags=+faststart` 会把索引移到文件前面，更适合 progressive playback。

对 `koko` 的直接意义：

1. canonical 文件必须持续保持 preview-friendly packaging。
2. 发送端预处理不能只追求“能播”，还要追求“前部足够早可解析”。
3. 如果 `Mediabunny` 不够精细，再加 `MP4Box.js` 做 header planner，而不是手搓 MP4 parser。

官方来源：

- [MP4Box.js 官方仓库](https://github.com/gpac/mp4box.js)
- [FFmpeg Formats `faststart`](https://ffmpeg.org/ffmpeg-formats.html)

### 2.6 `OPFS` 是 preview cache 正路，`localStorage` 不是

MDN 对 OPFS 的边界很清楚：

1. OPFS 适合 origin 私有、高性能、按字节读写。
2. Worker 里可以用同步 access handle，速度更好。
3. 浏览器默认是 best-effort 存储，不是永不清理。
4. `navigator.storage.persist()` 只能争取更稳，不是绝对承诺。

对 `koko` 的直接意义：

1. preview cache 的字节层应该优先放 OPFS。
2. `localStorage` / 轻 metadata 存储只适合索引，不适合 bitmap/blob 主体。
3. 计划里要明确“best-effort + persist 尝试 + 被清理后重新派生”的语义。

官方来源：

- [MDN OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)
- [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- [MDN `navigator.storage.persist()`](https://developer.mozilla.org/docs/Web/API/StorageManager/persist)

### 2.7 Windows 缩略图直觉背后是 extractor + cache，不是魔法

微软官方写得很直白：

1. Windows 需要 thumbnail 时，先查 thumbnail cache。
2. 没命中缓存，才调用 extractor / provider。
3. 对昂贵缩略图，指南建议在保存时就存好 preview。

对 `koko` 的直接意义：

1. 用户“视频和预览天然一体”的直觉没错，但实现上是“同一文件 + extractor + cache”。
2. 我们的新主链应该尽量接近这个体验模型，而不是偷偷回到后端 still 资产。

官方来源：

- [Microsoft Thumbnail Handlers](https://learn.microsoft.com/en-us/windows/win32/shell/thumbnail-providers)
- [Microsoft Thumbnail Handler Guidelines](https://learn.microsoft.com/en-us/windows/win32/shell/thumbnail-provider-guidelines)

## 3. 这次实现最该抄的 API 形状

### 3.1 `Mediabunny` 抽取 thumbnail

```ts
import { Input, ALL_FORMATS, BlobSource, CanvasSink } from "mediabunny";

const input = new Input({
  formats: ALL_FORMATS,
  source: new BlobSource(file),
});
const videoTrack = await input.getPrimaryVideoTrack();
const sink = new CanvasSink(videoTrack, { width: 320 });
const result = await sink.getCanvas(10);
```

适合：

1. 发送端本地 draft preview。
2. 接收端拿到早期关键字节后的代表帧。
3. 从同一 canonical 文件统一派生 preview。

### 3.2 `Mediabunny` 读 metadata / images

```ts
const tags = await input.getMetadataTags();
const images = tags.images;
```

适合：

1. 先查 embedded preview hint。
2. 同文件 hint 命中后直接喂时间线 / 查看器。

### 3.3 `MediaCapabilities`

```ts
const info = await navigator.mediaCapabilities.decodingInfo({
  type: "file",
  video: {
    contentType: 'video/mp4; codecs="avc1.64001F"',
    width: 1920,
    height: 1080,
    bitrate: 4_000_000,
    framerate: 30,
  },
});
```

适合：

1. 预览主链前先判断是不是值得本地派生。
2. 弱设备提前走 fallback，不要硬解。

### 3.4 `WebTorrent`

```ts
torrent.select(startPiece, endPiece, 0);
torrent.critical(startPiece, endPiece);
```

适合：

1. 先拉 preview 所需片段。
2. preview ready 后再切回整附件补齐。

### 3.5 OPFS

```ts
const root = await navigator.storage.getDirectory();
const fileHandle = await root.getFileHandle("preview-hash-1.bin", { create: true });
```

适合：

1. preview cache blob/bitmap 正文。
2. worker 里的高频读写。

## 4. 明确不该手搓的东西

### 4.1 不要手搓 MP4 parser

优先级：

1. `Mediabunny`
2. `MP4Box.js`
3. 自研 parser

只有前两者都证明不满足边界时，才允许讨论自研。

### 4.2 不要手搓软件解码主链

优先级：

1. `WebCodecs`
2. 浏览器原生媒体栈
3. Rust/WASM 软件 codec

Rust/WASM 适合做：

1. container/header planner
2. piece planner
3. cache index

不适合做：

1. 默认首屏解码主链
2. 第二套全量转码流水线

### 4.3 不要把壳层缓存继续养成 preview owner

`房间消息窗.ts` 里的：

- `无封面视频稳定预览源`

只能退场，不能继续升级。

真正 owner 应该是：

1. `聊天媒体编排` 里的 preview runtime 状态
2. `预览缓存.ts` 的 `content_hash` 索引

### 4.4 不要误把 `ReadableStreamSource` 当随机访问文件

官方已经写了：

1. 它是 append-only、unknown length、unsized source。
2. 默认不适合 random access。

所以：

1. preview 派生如果依赖随机定位关键帧，就别把它当万金油。
2. 真要 random access，需要 sized source / URL range / header planner。

## 5. 对当前 implementation plan 的直接修正意见

这次学习没有推翻现有 plan，但把三个地方收得更准：

1. **Task 3** 必须明确：若 `Mediabunny` 可写 `MetadataTags.images`，发送端优先写同文件 preview hint；失败时只是降级，不准升成第二 still 上传。
2. **Task 4** 必须明确：preview cache 正文优先 OPFS，不要只落在现有 `媒体缓存.ts` 这种 metadata 仓库。
3. **Task 5** 必须明确：preview-first 需要 `torrent.select/critical(piece-range)`，不能只继续 `file.select(1)`。

---

## 6. 最后收口

如果只压成一句施工原则，就是：

**同一 canonical 文件继续做唯一真相；发送端把它做得 preview-friendly；接收端优先读 embedded hint 或早期关键字节，本地派生 preview 并写 OPFS；`Video.js` 只负责显示；`WebTorrent` 只负责把关键 pieces 尽快送到。**

这条路最接近“视频天然自带预览”的用户直觉，也最不容易把系统重新带回“后端长期 still 垃圾”和“前端壳层偷偷养第二真相”的老路。
