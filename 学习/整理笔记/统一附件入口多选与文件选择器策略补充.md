# 2026-04-11 统一附件入口多选与文件选择器策略补充

适用范围：`koko` 群聊底部统一附件入口在 Web 端的多选、混选、文件选择器打开路径。  
目标：把这轮真正要依赖的官方依据补齐，避免再用“猜某些移动端会不稳”这种拍脑袋方式主动砍掉多选能力。

---

## 1. 先给结论

这轮实现最该遵守的结论只有四条：

1. `multiple` 应该默认保留，不要因为怀疑移动端兼容性就由我们主动关闭。
2. `accept` 只负责给系统 picker 宽提示，不负责替代真正的类型校验。
3. 隐藏 `input[type=file]` 的自定义入口，继续以 `input.click()` 作为主路径；`showPicker()` 不是必须依赖。
4. `Uppy` 的限制层和浏览器 file input 表层必须同源：如果上传器允许多文件和图片视频混选，壳层不要反向砍掉能力。

一句话：

**平台自己不支持的多选/混选，是平台限制；但我们不能在自己的壳层里先把能力阉掉。**

## 2. Web 官方边界

### 2.1 `multiple` 的真实语义

MDN 对 file input 的定义很直接：

1. 当 `multiple` 存在时，用户可以选择一个或多个文件。
2. 当 `multiple` 省略时，用户一次只能选一个文件。
3. 用户具体怎么多选，由各平台自己的文件选择器决定。

对 `koko` 的直接约束：

1. 统一附件入口既然建模成“选择媒体”，默认就不该主动去掉 `multiple`。
2. 某些设备最终只返回单文件，是系统 picker 的能力差异，不是我们该提前代劳决定的事情。

来源：

- MDN `<input type="file">`：<https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file>
- MDN `multiple`：<https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/multiple>

### 2.2 `accept` 的真实语义

MDN 和 WHATWG 的边界也很清楚：

1. `accept` 定义的是“哪些类型在 picker 里被视为可选”。
2. 它支持 MIME、扩展名、通配符，比如 `image/*`、`video/*`、`.heic`。
3. 它不是验证真相，不能替代选后校验。

对 `koko` 的直接约束：

1. `accept` 应该尽量保持宽提示，比如 `image/*,video/*`。
2. 图片 HEIC/HEIF 的真正兜底，继续放在选后图片预处理，不要再靠 picker 过滤承担真相。
3. 视频/图片最终能不能进入主链，仍然由 `frontend/媒体` 的文件级识别和预处理决定。

来源：

- MDN `accept`：<https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file>
- WHATWG HTML `input/file`：<https://html.spec.whatwg.org/multipage/input.html>

### 2.3 自定义按钮打开 file input，`click()` 仍然是标准保守路径

MDN 对“隐藏 file input + 自定义按钮”的推荐示例，仍然是：

1. 隐藏真正的 file input。
2. 用户点击自定义按钮时，调用 `input.click()`。

这说明：

1. `click()` 不是土办法，它本来就是 Web 官方文档里仍然成立的主路径。
2. 只要调用发生在真实用户手势里，这条路径就是正统方案。

来源：

- MDN `Using files from web applications`：<https://developer.mozilla.org/en-US/docs/Web/API/File_API/Using_files_from_web_applications>

### 2.4 `showPicker()` 可以存在，但不该成为这次重构的刚性依赖

MDN 对 `showPicker()` 的说明是：

1. 它能显示浏览器原生 picker。
2. 仍然要求用户激活。
3. 会抛 `NotAllowedError`、`InvalidStateError` 等异常。
4. 本质上它展示的是“本来就会显示的 picker”，不是一个新的更强能力层。

对 `koko` 的直接约束：

1. 统一附件入口不该围绕 `showPicker()` 设计。
2. 如果未来要支持，也只能是增强项，而不是替代 `click()` 的主路径。

来源：

- MDN `HTMLInputElement.showPicker()`：<https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/showPicker>

## 3. Uppy 官方边界

Uppy 官方文档对多文件和文件选择限制讲得很清楚：

1. `restrictions.maxNumberOfFiles` 会直接影响系统文件对话框可选文件数量。
2. 当这个值是 `1` 时，UI 插件和文件对话框都只能单选。
3. 只要不是 `1`，用户就可以一次选择多个文件。
4. `allowedFileTypes` 会通过 `<input accept>` 传给浏览器，最终仍受浏览器能力限制。
5. `allowMultipleUploadBatches: true` 允许用户在一轮上传开始后继续添加更多文件。

对 `koko` 的直接约束：

1. 我们既然已经把 Uppy 配成 `allowMultipleUploadBatches: true`，壳层就不该再把 picker 预先砍成单选。
2. `Uppy.restrictions.allowedFileTypes` 和 file input `accept` 应保持同源语义，不要一宽一窄。
3. “一次多选 + 后续继续追加”本来就是 Uppy 支持的成熟能力，不需要自己手搓第二套队列系统。

来源：

- Uppy Core：<https://uppy.io/docs/uppy/>
- Uppy migration guides（`allowMultipleUploadBatches`）：<https://uppy.io/docs/guides/migration-guides>

## 4. 原生平台最佳实践

### 4.1 Android

Android 官方 Photo Picker 文档明确把下面两件事当成一等能力：

1. `PickVisualMedia.ImageAndVideo`
2. `PickMultipleVisualMedia`

这说明系统级最佳实践不是“担心兼容性所以默认单选”，而是：

1. 统一视觉媒体入口。
2. 统一支持图片+视频。
3. 多选作为标准能力存在。

来源：

- Android Photo Picker：<https://developer.android.com/training/data-storage/shared/photo-picker>

### 4.2 Apple

Apple 官方对 Photos picker/PHPicker 的描述同样强调：

1. 这是系统级照片和视频选择入口。
2. 它天然支持多图选择与搜索。
3. 新版 `PhotosPicker` 还显式提供 `maxSelectionCount`。

对 `koko` 的直接启发：

1. 成熟平台并不会把“多选照片/视频”当成异常能力。
2. 如果 Web 端有平台差异，应该视为 Web 壳的局限，而不是反向修改产品心智。

来源：

- Apple `Selecting Photos and Videos in iOS`：<https://developer.apple.com/documentation/photokit/selecting_photos_and_videos_in_ios>
- Apple `PhotosPicker`：<https://developer.apple.com/documentation/PhotosUI/PhotosPicker>
- Apple WWDC21 `Improve access to Photos in your app`：<https://developer.apple.com/videos/play/wwdc2021/10046>

## 5. 成熟产品的真实发送心智

### 5.1 Slack

Slack 官方帮助文档明确写了：

1. 桌面端可在消息框附近通过 `+` 添加文件。
2. 一次可以拖放最多 10 个文件进入消息框。
3. 消息可以携带多个附件文件。

这说明成熟协作/群聊产品的默认心智不是“保守单选”，而是：

1. 统一入口。
2. 多文件自然成立。
3. 如果平台限制存在，也应尽量让系统自己暴露，而不是产品先砍。

来源：

- Slack `Uploading and sharing files`：<https://slack.com/hc/en-us/articles/201330736-Uploading-and-sharing-files>

### 5.2 Telegram

Telegram iOS 官方翻译词条里长期存在：

1. `Photo or Video`
2. `Send %@ Photos`
3. `Send %@ Videos`
4. `Send %@ Items`

这说明 Telegram 的媒体发送心智也是：

1. 统一媒体入口。
2. 批量发送是自然语义，不是边缘功能。

来源：

- Telegram iOS camera and media 词条：<https://translations.telegram.org/en/ios/camera_and_media/AttachmentMenu.SendPhoto>
- Telegram iOS camera and media 总页：<https://translations.telegram.org/ar/ios/camera_and_media/>

## 6. 对 `koko` 这轮实现的直接约束

这次改代码前，先把下面几条钉死：

1. `frontend/操作台/附件入口/附件能力注册.ts`
   - 不要再按 UA 或触点数主动关闭 `multiple`
   - `accept` 继续保持 `image/*,video/*`

2. `frontend/操作台/附件入口/附件入口编排.ts`
   - 隐藏 file input 的主路径继续使用 `input.click()`
   - 不再把 `showPicker()` 当成默认主路径

3. `frontend/媒体/媒体发布.ts`
   - 继续支持多文件、混选、批量追加
   - 保持 `allowMultipleUploadBatches: true`

4. `frontend/媒体/图片预处理.ts` 与 `frontend/媒体/视频元数据.ts`
   - 图片/视频真实校验继续放在选后处理
   - 不把 picker 配置当成真相

5. 测试层
   - 必须把“移动端默认单选”改回失败用例
   - 必须把“优先 showPicker”改回失败用例

一句话收口：

**统一附件入口可以做兼容兜底，但不能通过预先砍掉多选能力来伪装稳定。**
