# 2026-04-08 唯一壳级操作台官方最佳实践与不手搓轮子依据

适用范围：`frontend/聊天壳.ts` 即将进行的“唯一壳级操作台 / ShellConsole”重构。  
目标：先用官方资料把这次前端重构的边界钉死，避免重复手搓轮子，避免把“同一位置”误做成“两套模板轮流上场”。

---

## 1. 先给结论

这次前端操作台重构，真正应该复用和依赖的成熟能力，不是自己再造一层“输入框框架”，而是下面这几样：

1. **浏览器原生表单语义**
   用一个真实 `<form>`、一个真实主输入、一个真实提交按钮，统一接住桌面 Enter、手机输入法回车、按钮点击和脚本触发。

2. **Lit 原生响应式渲染**
   让 `render()` 只吃状态，不在里面偷偷改状态、不手动操作 DOM、不在首页和房间里各拼一套主表单。

3. **Lit 原生 DOM 更新与批处理**
   Lit 已经会批量更新，并且只更新变化的表达式。我们该做的是把 DOM 骨架稳定下来，不是手搓第二套缓存/同步层。

4. **原生 `disabled` / `inert` 语义**
   boot 态要“实体还在但不可交互”，优先复用平台已有语义，不自己造 `data-disabled-like` 之类半残状态。

5. **静态样式 + CSS 自定义属性**
   操作台的固定骨架、高度、圆角、边框、状态槽单行策略，优先放进 Lit 的 `static styles`，不要再搞模板内 `<style>` 动态拼接。

6. **INP / 布局性能基本纪律**
   操作台是高频交互区，提交、切模式、输入时的同步工作必须薄；不要在输入回调里做重布局、重测量、重计算。

一句话：

**这次不该手搓“输入器框架”，而该把原生 form + Lit 响应式更新 + 平台禁用语义真正吃透。**

## 2. 对 `koko` 这次重构最有用的官方结论

### 2.1 Lit 官方真正支持的方向：`render()` 必须纯

Lit 官方对“好的 render 方法”说得非常直接：

1. 不要在 `render()` 里改组件状态
2. 不要在 `render()` 里产生副作用
3. `render()` 只用组件属性作为输入
4. 相同输入必须返回相同结果

这对我们这次重构的直接含义是：

1. `ShellConsoleState` 应该先派生好，再喂给模板
2. `render()` 不该自己散写 join/message 的业务判断
3. 更不该在 `render()` 里顺手修输入值、补按钮文案、偷偷改 DOM

所以，**唯一操作台的正确做法是“单一骨架 + 状态派生”，不是“render 分支里各写一套 form”。**

来源：

- [Lit Rendering: Writing a good render() method](https://lit.dev/docs/v2/components/rendering/)

### 2.2 Lit 已经帮我们做了高效更新，不需要再手搓第二层 DOM 同步

Lit 官方说明了两件很关键的事：

1. 多个属性变更会被批处理成一次更新
2. 更新时只重渲染变化的表达式，静态 HTML 只创建一次

这意味着：

1. 只要我们把操作台收成一个固定骨架，Lit 本身就会高效更新文案、值、禁用态
2. 没必要再发明“首页输入框实例”和“群聊输入框实例”之间的手工同步
3. 也没必要自己造一个“操作台切换缓存层”来弥补错误架构

来源：

- [Lit Rendering: When templates render](https://lit.dev/docs/v2/components/rendering/)
- [Lit Lifecycle: Reactive update cycle](https://lit.dev/docs/v2/components/lifecycle/)

### 2.3 `cache` 指令是成熟轮子，但它不是这次的主解

Lit 官方有 `cache()`，用途很明确：

1. 在多个模板之间快速切换
2. 缓存被切走的 DOM 节点和模板实例

它适合什么：

1. 上半部主舞台 `home list / room stream` 这种“大视图切换”

它不适合拿来当这次的主解：

1. 我们这次要的不是“两套操作台切换得更快”
2. 我们要的是“整个应用里只有一个真实操作台实体”

所以判断很清楚：

1. **操作台本体不要继续保留两套 form 再用 `cache()` 缓存**
2. 如果以后上半部主舞台切换真的很重，`cache()` 可以考虑用在 `ShellStage`
3. 但 `ShellConsole` 本体应该先做成真正唯一的一套骨架

来源：

- [Lit cache directive](https://lit.dev/docs/api/directives/)

### 2.4 样式不要模板内现算，官方推荐 `static styles`

Lit 官方明确建议：

1. 组件样式优先写在 `static styles`
2. 这是最优性能路径
3. 模板内 `<style>` 是按实例更新的，文本一变浏览器要重解析整块样式

这对我们操作台的直接含义是：

1. 操作台的高度体系、单行状态槽、按钮与输入框固定尺寸，要放在 `static styles`
2. 颜色和少量差异用 CSS 变量驱动
3. 不要在 `render()` 里根据模式去拼新的 `<style>`

来源：

- [Lit Styles](https://lit.dev/docs/components/styles/)

### 2.5 表单提交不要手搓键盘总线，浏览器原生就支持

MDN 和 WHATWG 都很清楚：

1. `<form>` 的 `submit` 事件会在用户点提交按钮、用户在表单字段里按 Enter、或脚本调用 `requestSubmit()` 时触发
2. `requestSubmit()` 会像真的点了提交按钮一样，包含校验和 `submit` 事件
3. `submit()` 会绕过这些语义

对 `koko` 的直接含义：

1. 操作台必须统一成一个 `#shellConsoleForm`
2. 首页进房和房间发消息都走同一个 `submit` 入口
3. 代码里优先处理 `submit`，不要四处散写 `keydown === Enter`
4. 如果有脚本触发提交，优先 `requestSubmit()`，不要直接 `submit()`

来源：

- [MDN: submit event](https://developer.mozilla.org/en-US/docs/Web/API/HTMLFormElement/submit_event)
- [MDN: requestSubmit()](https://developer.mozilla.org/en-US/docs/Web/API/HTMLFormElement/requestSubmit)
- [WHATWG HTML Standard: form.requestSubmit() / submit()](https://html.spec.whatwg.org/multipage/forms.html)

### 2.6 手机输入法回车文案，平台已经给了 `enterkeyhint`

MDN 明确说：

1. `enterkeyhint` 用来告诉虚拟键盘把回车键显示成什么动作
2. 常见值包括 `go`、`send`、`done`

这和我们现在要做的正好一一对应：

1. 首页进房：`go`
2. 群聊发送：`send`
3. 其他完成类操作：`done`

这意味着：

1. 不要自己猜手机键盘会怎么显示
2. 操作台模式切换时，`enterkeyhint` 也应该跟着同一个主输入一起切语义

来源：

- [MDN: enterkeyhint](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/enterkeyhint)

### 2.7 boot 态“实体还在但不可交互”，优先用 `disabled` 和 `inert`

MDN 对 `inert` 的定义很适合这次需求：

1. inert 子树不能被点击、不能聚焦、不能编辑
2. 会从 tab 顺序和无障碍树里移除
3. 但 MDN 也明确提醒：如果只是单个控件不可用，更适合直接用 `disabled`

对这次重构的直接启发非常重要：

1. boot 态下主输入和主动作按钮应该显式 `disabled`
2. 如果要让主控行整块不可交互，可以考虑把 **主控行** 设为 `inert`
3. 但不要粗暴把整个操作台都 `inert`，否则状态槽提示也会从无障碍树里消失

所以更稳的落法是：

1. `#shellConsole` 实体常驻
2. `#shellConsoleStatus` 继续可见、可读
3. `#shellConsoleMainRow` 在 boot 态使用 `inert` 或明确控件级 `disabled`

来源：

- [MDN: inert](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inert)

### 2.8 高性能的关键不是“花哨动画”，而是交互延迟和避免强制布局

web.dev 对 INP 和布局问题说得很直白：

1. 好的 INP 目标是 200ms 以内
2. 交互回调里要尽量只做让下一帧必要的工作
3. 样式写完立刻读布局，会触发 layout thrashing
4. DOM 越大、布局越复杂，交互后出下一帧越慢

对操作台的直接含义：

1. 提交、切模式、输入回调里不要做重计算
2. 不要在输入时不断读写尺寸，避免强制同步布局
3. 状态槽保持单行、高度固定，本质上是在减少交互后的重排成本
4. 这个底部区域是高频热路径，任何“按一下再算很多东西”的写法都要警惕

来源：

- [web.dev: Optimize INP](https://web.dev/articles/optimize-inp)

## 3. 这次实现时必须遵守的工程判断

### 3.1 该复用什么

这次应该直接复用：

1. 原生 `<form>` / `submit` / `requestSubmit()`
2. 原生 `disabled`
3. 需要整块冻结时的 `inert`
4. Lit 的响应式更新和模板 diff
5. Lit 的 `static styles`
6. CSS 自定义属性

### 3.2 这次不要手搓什么

这次明确不要手搓：

1. 第二套“首页版操作台”模板
2. 第二套“房间版操作台”模板
3. 自定义键盘提交总线
4. 私有 DOM 缓存/同步层
5. 模板内动态 `<style>` 注入
6. 靠 JS 每次输入时读写尺寸来“调高度”
7. 用本地假成功状态代替真实 `submit` 主链

### 3.3 对 `ShellConsole` 的直接落地约束

后面动手时，操作台至少要满足：

1. 整个壳里只有一个 `#shellConsoleForm`
2. 整个壳里只有一个 `#shellConsolePrimaryInput`
3. 整个壳里只有一个 `#shellConsolePrimaryAction`
4. 首页和房间只切：
   - 状态文案
   - placeholder
   - value 绑定来源
   - `enterkeyhint`
   - submit 目标
   - disabled / inert
5. 不能再保留 `joinForm/composerForm` 作为两条主控制链

### 3.4 一个重要的无障碍提醒

如果 boot 态把整个 `#shellConsole` 直接设为 `inert`：

1. 主控行会不可交互，这是对的
2. 但状态提示也会一起从无障碍树消失，这通常不是你想要的

所以更推荐：

1. 操作台实体常驻
2. 状态槽继续活着
3. 主控行冻结

## 4. 对这次“唯一操作台”最稳的实现原则

后面真正改代码时，优先按下面这条主线走：

1. **用一个固定 DOM 骨架做唯一操作台**
2. **用 presenter 派生 `ShellConsoleState`**
3. **让 Lit 只更新变化的值和属性**
4. **让原生 form 负责 Enter / 回车 / submit 语义**
5. **让 `disabled` / `inert` 负责不可交互语义**
6. **让 `static styles` 负责固定尺寸系统**

这就是“工欲善其事，必先利其器”在这次前端重构里的实际含义：

**先站在浏览器原生能力和 Lit 官方能力上，再写业务代码；不要自己再造一台半成品轮子。**
